第 1 帧的 filesystem_walk/ 建 fs_demo/ 并递归遍历，format_basic/ 拼三种格式，file_io/ 写读一个文本文件。第 2 帧的 print_lib/ 用 std::println，清单带 -lstdc++exp 与干净 PATH；generator_basic/ 用 co_yield 产出一个整数序列。第 3 帧的 generator_pipeline/ 把两个生成器接起来，先产出 0..4，再平方。

19.2 <filesystem>：路径、目录与遍历

std::filesystem::path 表示路径，可以用 / 拼接（Windows 上也能用，库会转成合适的分隔符），可以取文件名、扩展名、父目录。遍历目录用 directory_iterator（只一层）或 recursive_directory_iterator（递归）。遍历顺序没有标准保证，要稳定输出就得自己排序。

create_directories 会连同缺失的父目录一起建；recursive_directory_iterator 会进入 sub/，所以一共看到三项：a.txt、sub/、sub/b.txt。fs::relative(entry.path(), root) 把绝对/相对路径转成“相对 root 的路径”，generic_string() 统一用 / 作为分隔符，便于跨平台比较。排序是为了让输出可复现：标准不规定迭代顺序，不排序就可能在不同文件系统上得到不同顺序。

remove_all(root, ignored) 接收一个 std::error_code&，不抛异常，把错误写进 ignored；第一次调用是为了清掉上次可能残留的目录，第二次是清理本例创建的东西。文件系统操作可能失败（权限、占用、路径不存在），工程代码要么用 error_code 重载检查，要么用会抛异常的版本并 try / catch；本例用前者，避免把“清理失败”升级成异常。

path 的 / 运算符是拼接，不是除法；root / "sub" 得到 fs_demo/sub，root / "sub" / "b.txt" 得到 fs_demo/sub/b.txt。path 还提供 filename()、extension()、parent_path()、stem()；路径是平台相关的字符串，但 path 的拼接与分解是标准化的，比手写字符串拼接更安全。

路径的“字符串编码”是跨平台的坑：Windows 的 path 内部用宽字符，string() 返回本地编码，u8string() 返回 UTF-8；Linux 通常直接用字节串。把 path 转成 std::string 再交给别的接口，可能丢失非 ASCII 字符；需要跨平台传递时，明确用 u8string() 或统一用 path 对象。generic_string() 只统一分隔符，不统一编码；不要把它当成“跨平台字符串”的万能解。

标准原文标准原文：filesystem 管什么

Subclause 31.12 describes operations on file systems and their components, such as paths, regular files, and directories.

大意：<filesystem> 描述对文件系统及其组成部分（路径、普通文件、目录）的操作。

出处：N4950 §31.12.1「In general」（[fs.general]）。

recursive_directory_iterator 默认不跟随符号链接；需要跟随时在构造时传 directory_options::follow_directory_symlink，但要小心循环链接。遍历时目录可能被别的进程修改，标准不保证你在遍历期间看到一致快照；需要一致性时，先收集再处理，或接受“边遍历边变化”的现实。

19.3 文件读写：文本模式与字节数

std::ofstream 写文件，std::ifstream 读文件，std::getline 逐行读。流的析构会关闭文件；但删除文件前要确保流已经关闭，否则 Windows 会报“文件被另一个进程使用”。本例用一对花括号限制流的作用域，出了作用域就关闭，再删除。

文件写完后，内层作用域结束，ofstream 析构关闭文件；接着读回内容，读完再让 ifstream 关闭，最后删除文件。

内容看起来是 alpha、beta、gamma 三行，逻辑字符是 5+1+4+1+5+1=17 个；但 file_size 报 20。原因是 Windows 的文本模式：std::ofstream 默认以文本模式打开，写入时把每个 \n 转成 \r\n，三个换行各多一个字节，17+3=20。std::getline 读的时候会按行切分并去掉行尾的 \r，所以 first / last 仍是干净的字符串。同一个程序在 POSIX 上通常报 17；要精确控制字节，就用 std::ios::binary 打开，或接受文本模式的平台差异。

这也是“文本”与“二进制”的边界：文本模式负责换行转换，二进制模式原样读写。如果你写的是自定义二进制格式、图片、序列化数据，必须用 binary；否则 Windows 会把数据里的 \n 改掉，读回来就对不上。文本文件则可以用文本模式，让平台处理换行习惯。

std::getline 返回流引用，放在 while 条件里会隐式转 bool：读到一行返回真，遇到 EOF 或错误返回假。循环结束后要区分“正常读完”与“读出错”，可以检查 in.eof() / in.bad()；本例只关心行数与内容，省略了这层检查。工程代码处理外部文件时，建议在读完后确认流状态，避免把“读到一半失败”当成“文件就这么短”。

打开文件后还要检查流是否可用：std::ofstream out(path); if (!out) { /* 处理失败 */ }。流构造失败默认不抛异常，后续写入会静默失败，对象本身却仍然存在；“文件没写成”比“程序崩溃”更难发现。写外部路径前，先确认父目录存在，需要时用 std::filesystem::create_directories 建好，再打开文件。

删除文件用 std::filesystem::remove(path)；如果文件不存在，它返回 false，不抛异常；如果删除失败（权限/占用），会抛 filesystem_error。本例在流关闭后删除，所以不会撞上 Windows 的占用错误；这也是为什么要把 ifstream 放进内层花括号。

19.4 <format>：类型安全的格式串

std::format 用 {} 作为替换字段，按参数顺序填值；{} 里可以写格式说明：{:03d} 表示十进制、至少 3 位、不足补零，{:.2f} 表示两位小数，{:>6} 表示右对齐、宽度 6，{:#x} 表示带 0x 前缀的十六进制。类型由参数决定，格式串只描述“怎么显示”，不需要像 printf 那样手写 %d / %f 并保证类型匹配。

score={:03d} 把 90 显示成 090；pi={:.2f} 把 3.14159 四舍五入到两位小数 3.14；|{:>6}| 把 ok 放在宽度 6 的区域右对齐，左边补四个空格；{:#x} 把 255 显示成 0xff。格式说明写在冒号后面，类型由实参推导；如果格式与类型不匹配（例如对字符串用 d），std::format 会抛 std::format_error（或编译期检查失败）。

C++20 的 std::format 对字面量格式串做编译期检查：格式串是常量表达式时，编译器能发现未知的格式说明、参数个数不匹配等问题；运行期拼接出来的格式串只能用 std::vformat，检查推迟到运行期。这是“类型安全”的一半：参数类型由模板推导，格式串在编译期尽量检查；剩下的一半是运行期的值检查（例如宽度是否为负）。

std::format 返回 std::string，可以继续 +、可以写文件、可以交给日志库。它不直接输出，所以适合“先拼好再决定去哪”；需要直接输出时用下一节的 std::print。

std::format 的格式串在编译期检查，这个“编译期”有边界：只有字面量、且类型可被 format_string 推导时才检查；运行期拼接的字符串要用 std::vformat，检查推迟到运行期，格式错误抛 std::format_error。不要把用户输入直接当格式串，那等于把格式串注入交给运行期；需要动态格式时，用 vformat 并准备好捕获异常。

自定义类型默认不能直接格式化，需要特化 std::formatter<MyType>；标准库已经为整数、浮点数、字符串、指针、chrono 类型等提供了格式说明。格式串里的字段数量必须与实参匹配，多了少了都会在编译期报错，这也是它比 printf 安全的地方：参数与占位符由同一套类型信息绑定，不靠人肉对齐。

19.5 <print>：直接输出，但本机要额外链接

std::print / std::println 把格式串直接写到标准输出（或指定文件），语法与 std::format 一致：std::println("sum={}", 3 + 4) 打印 sum=7 并换行。它比 std::cout << 少写很多 <<，也比 printf 类型安全；代价是本机工具链需要额外链接 -lstdc++exp，运行时还需要干净的 MSYS2 PATH。

std::println 自动换行，std::print 不换行，需要自己写 \n。这个例子的清单里写了：

  • libs: ["-lstdc++exp"]：不加时链接器报 undefined reference to std::__open_terminal / std::__write_to_terminal；
  • env.PATH 固定为 C:/msys64/ucrt64/bin;C:/msys64/usr/bin;C:/Windows/System32：本机运行 std::print 时需要干净的 MSYS2 环境，否则可能以 3221225785 退出。

这两条都是本机工具链事实，不是标准要求。标准只规定 std::print 的行为；某个实现把它放在哪个库、运行时依赖什么环境，是平台细节。正文把清单里的 libs / env 明确写出来，是为了让例子可复现；换到 Linux + libstdc++ 的新版本，可能直接链接通过，不需要这些设置。

std::print 的格式化失败会抛 std::format_error；输出失败（例如管道断开）会设置流状态或抛异常，具体看重载。它不会像 printf 那样因为格式符与参数不匹配而打印垃圾；类型不匹配在编译期或运行期被拦住，这是它相对 C 风格输出的核心优势。

std::print 的缓冲行为与 std::cout 类似：不保证每次调用立刻刷新，程序崩溃时缓冲区里的内容可能丢失。需要“立刻可见”时，用 std::flush 或 std::endl（对 cout）；日志场景尤其要注意，别让最后一行日志留在缓冲区里。输出到管道/文件时，缓冲策略还可能与终端不同；调试输出不要假设“打印了就一定写出去了”。

19.6 std::generator：要一个，算一个

std::generator<T> 是 C++23 的协程生成器：函数里用 co_yield 产出一个值，调用方用范围 for 逐个取。它不是一次性算完再返回容器；每次迭代请求下一个值，生成器从上次暂停的地方继续，产出一个就停。这样内存里只需要当前值，不需要把整个序列存下来。

生成器是惰性的：调用函数只创建协程帧，函数体要等到第一次迭代才开始执行，运行到第一个 co_yield 就暂停。生成器对象销毁时，协程帧也跟着销毁，局部对象按析构规则清理；如果生成器内部持有引用，要保证被引用的对象活得比遍历更久。惰性省内存，也带来生命周期约束，不要在返回生成器的函数里引用局部变量。

count_up(4) 返回一个生成器对象；范围 for 第一次迭代让生成器运行到第一个 co_yield 0，拿到 0 后暂停；第二次迭代从暂停点继续，到 co_yield 1，以此类推；循环结束（i == 4）时生成器函数返回，迭代结束。控制流在“生成器”和“调用方”之间来回切换，而不是先跑完整个循环。

第 1、2 帧的往返是“拉取式”的：调用方要一个，生成器才算一个。这与返回 vector 的函数相反：vector 版本会先把所有元素算完、存进内存，再交给调用方；生成器版本把“计算”和“消费”交错进行，适合大序列、无限序列、或计算代价高的元素。

生成器是单遍的：迭代器只能向前，不能回头，也不能复制生成器对象后各自独立遍历（生成器对象本身可移动，但底层协程状态是单一的）。需要多次遍历就重新调用生成函数；需要随机访问就用容器。生成器的价值在“流式”，不在“可重复”。

19.7 生成器管线：把两个生成器接起来

生成器可以作为参数传给另一个生成器：squares(numbers(5)) 里，numbers(5) 产出 0..4，squares 逐个读取并平方，再 co_yield 出去。外层每要一个平方数，内层才算一个原数；两层都是惰性的，没有中间容器。

squares 接收 std::generator<int> 是按值传递，取得内层生成器的所有权；范围 for 从 source 拉一个值，平方后 co_yield，再等下一次请求。如果内层是无限序列，外层也可以无限产出，调用方用 break 或 take 限制数量；这正是生成器适合“惰性管线”的原因。

第 2 帧的生成器把“解析”和“消费”解耦：解析器不需要知道消费者要多少条，消费者也不需要等全部解析完。惰性让内存占用与输入规模脱钩；代价是调用链更长、调试时栈帧会来回切换，且生成器只能单遍消费。

生成器与 views 的区别：std::views 是范围适配器，组合的是“视图”，通常也是惰性的；std::generator 是协程，能把“有状态的、需要暂停/恢复的计算”写成普通循环。简单的过滤/变换优先用 views；需要协程式暂停、或把复杂控制流写成顺序代码时用 generator。两者都能避免中间容器，选择看表达力与习惯。

19.8 本机实测：六个读数

实验记录本机实测：目录、文件、格式与生成器

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • filesystem_walk 的 stdout 是 count=3 / entry=a.txt / entry=sub / entry=sub/b.txt：递归遍历看到三项，排序后输出稳定；
  • file_io 的 stdout 是 lines=3 / first=alpha / last=gamma / bytes=20：三行逻辑字符 17 个，Windows 文本模式把三个 \n 写成 \r\n，所以文件是 20 字节；

  • generator_pipeline 的 stdout 是 0 1 4 9 16 / count=5：两个生成器串联，外层按需拉取。

小结这一节要带走的四件事

自测题自测题（先自己做，再对答案）
  1. recursive_directory_iterator 的遍历顺序有标准保证吗？为什么例子要先 sort？
  2. file_io 写的内容逻辑上是 17 个字符，为什么 file_size 报 20？换到 Linux 可能报多少？
  3. std::format 与 std::print 的分工是什么？本机使用 std::print 需要哪些额外设置？
  4. std::generator 与返回 std::vector 的函数在求值时机上有什么不同？
  5. 生成器管线 squares(numbers(5)) 中，外层每要一个值，内层会做什么？生成器为什么不能重复遍历？
注自测答案
  1. 没有标准保证；不同文件系统、不同实现的迭代顺序可能不同。先收集再 sort，输出才可复现。
  2. 文本模式把三个 \n 各转成 \r\n，多出 3 个字节，17+3=20；Linux 上通常不做转换，报 17。
  3. std::format 返回字符串，适合先拼好再决定输出到哪；std::print 直接写标准输出。本机需要 libs: ["-lstdc++exp"] 和干净的 MSYS2 PATH，否则链接或运行会失败。
  4. vector 版本先把所有元素算完并存进内存，再返回；生成器版本在调用方请求时才计算下一个值，计算与消费交错，内存只保留当前值。
  5. 外层请求一个平方数时，内层从上次暂停处恢复，算出一个原数交给外层；生成器的协程状态是单份的，迭代器只能向前，所以不能像容器那样重复遍历。
