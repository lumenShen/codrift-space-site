上一单元的模板只问“类型能不能填进来”，不问“这个类型能不能做我要求的事”。max_of 要求类型支持 <，dump 要求类型能遍历；如果没有约束，传错类型时错误会在模板体深处炸开，一屏都是实例化栈。concepts 把“类型必须满足什么”写成编译期谓词，放在 template 头上；不满足时，编译器在调用点就说“constraints not satisfied”。

这一单元从标准 concepts（std::integral、std::floating_point、std::ranges::range）开始，再写自定义 concept（requires 表达式），最后用旧式 enable_if 对照。目标是让你能读懂约束失败的真实诊断，并能自己写一个“只接受支持某操作的类型”的模板。

学习目标看完这一单元，你应该能
  • 用 std::integral / std::floating_point 约束模板参数，并说出约束失败时诊断停在哪；
  • 写一个 requires 表达式，检查类型是否有某个成员函数、返回类型是否可转换；
  • 用多个约束重载同一函数名，解释重载决议怎样选到更匹配的那个；
  • 用 std::ranges::range 约束容器/视图参数，并说清“满足 range”不等于“元素类型可打印”；
  • 读懂 enable_if 旧写法与 concepts 的对应关系，知道 concepts 报错为什么更直接。

9.1 先看工程长什么样

这一单元在 examples/ch04/ 下再加六个多文件例子。约束都写在头文件里的模板头上，.cpp 只放非模板辅助函数，main.cpp 做调用与打印。

第 1 帧的 concept_basic/ 用 std::integral 约束 twice；concept_error/ 故意传 std::string，让约束失败。第 2 帧的 concept_overload/ 用 integral / floating_point 两个约束重载 kind；concept_compose/ 自定义 Named concept。第 3 帧的 ranges_concept/ 用 std::ranges::range 接收 vector / list；sfinae_old/ 用 enable_if 写同样的约束，作为旧写法对照。

9.2 标准 concept：把要求写在 template 头上

std::integral 是 <concepts> 里的标准 concept，等价于“std::is_integral_v<T> 为真”。template <std::integral T> 把约束写在模板参数位置；也可以写 template <typename T> requires std::integral<T>，两种写法等价。约束是编译期的：T 不满足时，这个模板根本不进入候选集，不会生成函数体。

twice 的函数体只用了 value + value，这个操作对整型成立；如果传入 double，std::integral 不满足，即使 + 也能用，模板仍然被拒绝——约束是“我要求整型”，不是“我要求能加”。约束应该表达接口真正需要的能力：如果函数只需要“能相加”，用 std::integral 太窄；如果需要“整型”，用它就合适。标准库提供了一批常用 concept：std::integral、std::floating_point、std::same_as、std::convertible_to、std::totally_ordered、std::ranges::range 等。

标准原文标准原文：concept 是什么

A concept is a template that defines constraints on its template arguments.

大意：concept 是一种模板，用来给它的模板实参定义约束；concept 本身不会被实例化，它在编译期求值为真或假。

出处：N4950 §13.7.9「Concept definitions」（[temp.concept]）。

concept 求值看的是“替换后的类型”，但模板参数推导会先去掉引用与顶层 const：twice(21) 推导 T = int；传一个 const int 变量，按值传参仍然推导 T = int。如果参数写成 const T&，T 也会去掉 const。不要把“concept 对 T 为真”误解成“对实参的原始类型逐字为真”；推导规则先发生，concept 再检查推导结果。

std::integral 与 std::signed_integral 是包含关系：signed_integral<T> 蕴含 integral<T>，但不反过来。写两个重载时，template <std::integral T> 与 template <std::signed_integral T> 对 int 都可行，编译器会选后者，因为它的约束更强。这种“更强约束优先”是 concepts 的重要能力；它让“通用版本 + 特化版本”可以用约束表达，不必靠标签分发或 enable_if 技巧。

标准 concept 也可以组合成自己的 concept：template <class T> concept Number = std::integral<T> || std::floating_point<T>;。组合后的 concept 仍然参与包含关系，Number 不会自动比 std::integral 更强或更弱，除非编译器能证明逻辑包含。写组合 concept 时，保持定义简单、可读；过度嵌套会让诊断变长，也会让“谁更特殊”变得难以判断。

9.3 约束失败：诊断停在调用点

诊断的前三行就把问题说清了：调用点 twice(std::string) 找不到匹配，候选是 requires integral<T> T twice(T)，失败原因是 constraints not satisfied；后面的 is_integral_v<...> evaluated to 'false' 是约束被拒绝的具体证据。concepts 的收益不是“编译更快”，而是“错误信息指向约束，而不是模板体深处的某一行”。

这份诊断之所以只有 12 行，是因为清单里加了 -fdiagnostics-plain-output（去掉彩色与源码箭头）与 -fconcepts-diagnostics-depth=1（限制约束展开深度）；不加这些参数，GCC 会把约束链展开成二十多行。诊断格式参数只影响“怎么显示”，不影响“是否满足约束”；本书的基础警告档没有变。

陷阱把 `requires` 当成运行期 `if`

你会看到：写了 requires 表达式，就以为函数里可以随便用被约束的操作，运行期再判断“类型对不对”。你会误判成“concepts 是运行期反射”。真相是：concept 在编译期求值，约束不满足时模板不会被选中，根本不会生成运行期代码；函数体里也不需要再写 if (is_integral<T>)。约束是“进门前检查”，不是“进门后判断”。

9.4 约束重载：更匹配的约束胜出

kind(7) 只满足 std::integral，kind(2.5) 只满足 std::floating_point；两个模板的约束互斥，重载决议没有歧义。如果一个类型同时满足两个约束（例如自定义类型同时满足两个 concept），编译器会比较约束的“包含关系”，选择更严格的那个；如果无法比较，就报歧义。约束不是标签，它参与重载决议；这就是 concepts 相对 enable_if 的最大区别之一——约束可以被编译器比较，而不是只做“能不能替换”的开关。

第 1 帧的 int 只进入 integral 候选；第 2 帧的 double 只进入 floating_point 候选。约束把“这个重载适不适合”从函数体里的 if 前移到了候选集构造阶段。

9.5 自定义 concept：用 requires 表达式描述操作

requires(const T& value) { ... } 是一个要求列表：它不求值，只检查“这些表达式在给定类型上是否合法、返回类型是否满足约束”。{ value.name() } -> std::convertible_to<std::string> 的意思是：value.name() 必须合法，且结果能转换成 std::string。Item::name() 返回 std::string，满足；如果某个类型没有 name()，Named 为假，label 不会进入候选集。

requires 表达式里可以写多行要求：简单要求（value.size()）、类型要求（typename T::value_type）、复合要求（带返回类型约束）、嵌套要求（requires std::integral<T>）。要求列表只做语法与类型检查，不执行函数体；所以 name() 里有没有副作用、返回的是不是临时对象，concept 都不知道。约束越宽，模板越通用，但函数体越容易在实例化时才发现问题；约束越窄，错误越早，但复用越少。

四种要求各有分工。简单要求只检查表达式“写不写得出来”，例如 requires(T value) { value.size(); }；它不关心 size() 返回什么，也不关心调用是否真的会产生结果。类型要求检查某个嵌套类型是否存在，例如 typename T::value_type，很多容器用它暴露元素类型。复合要求用 { expression } -> constraint 同时检查“表达式合法”与“结果满足约束”，前面的 Named 就是复合要求。嵌套要求写 requires 条件，把另一个布尔常量表达式并进来，常用来组合两个 concept。

requires 表达式还可以写成“参数列表 + 要求体”，参数列表里的变量只是占位，不会真的构造对象，也不会求值。requires(T value) 不代表 T 必须能默认构造；它只是给要求体一个类型为 T 的名字。不要因为写了 T value 就以为 concept 检查了构造；要检查构造，得写 requires { T{}; } 或 std::default_initializable<T>。

concept 只能检查“语法与类型”，不能检查“语义”。一个类型可以有 size() 但返回负数，可以有 name() 但返回空字符串，concept 都认为它满足要求。concept 是编译期的接口检查，不是行为契约；行为契约要靠文档、测试与运行期断言。把 concept 当成“自动证明实现正确”会失望；它的价值是把“这个类型有没有这个操作”从模板实例化深处提到候选集构造阶段。

约束可以组合：std::integral<T> && std::signed_integral<T> 表示两个条件都要满足；|| 表示任一满足。约束之间还有包含关系（subsumption）：如果约束 A 逻辑上包含约束 B，A 更特殊，重载决议会优先选 A。例如 template <std::integral T> 与 template <std::signed_integral T>，后者包含前者，传 int 时选后者。包含关系不是“谁写得更长”，而是编译器能证明的原子约束组合；不要把运行期的 if 逻辑套到约束排序上。

标准库已经提供了大量 concept：std::integral、std::floating_point、std::same_as、std::convertible_to、std::totally_ordered、std::ranges::range 等。优先用标准 concept，再考虑自定义；标准 concept 经过广泛使用，边界更清楚，诊断也更容易被工具识别。自定义 concept 应聚焦“你的接口真正需要什么”，不要把实现细节写进约束。

第 1 帧的 Named 定义必须放在头文件里，和模板定义一样，因为使用点需要它来求值；第 2 帧的 Named<Item> 在编译期得到真，label 才会被实例化。concept 不能只在 .cpp 里定义，除非使用点也在同一个翻译单元。

9.6 std::ranges::range：约束“能遍历”

std::ranges::range 只要求类型有 begin() / end()（或可被 std::ranges::begin/end 取到），不要求它是容器，也不要求元素类型能 to_string。dump 的函数体用了 std::to_string(item)，这要求元素是算术类型；如果传一个 vector<std::string>，range 约束仍然满足，但函数体实例化时会报 no matching function for call to to_string(std::string)。约束只检查你写出来的要求；函数体里隐含的要求，约束不会自动知道。 要让 dump 接受字符串元素，应该把元素约束也写进 concept（例如 std::ranges::range R + requires 元素可格式化），或者改用 std::format / std::print。

range 只是范围概念层级的最底层。再往上还有 std::ranges::input_range（能单遍读取）、forward_range（能多遍向前）、bidirectional_range（能后退）、random_access_range（能随机访问）、sized_range（size() 是常数时间）、borrowed_range（迭代器可以活得比范围长）等。约束越往上，算法能用的操作越多：std::ranges::sort 要求 random_access_range，std::ranges::find 只要求 input_range。写泛型算法时，按你实际用到的能力选最弱的 concept；要求过强会把本来能用的类型挡在外面。

range 不要求 size()，因为有些范围是“惰性”的，算长度需要遍历一遍；sized_range 才要求常数时间拿到大小。std::ranges::begin / end 还能处理数组、C 风格字符串与自由函数 begin/end，所以“有 begin() 成员”不是唯一条件。concept 描述的是“能用哪些操作”，不是“像不像容器”；一个 std::string_view、一个 std::span、一个 views::iota 都能满足 range。

约束的位置有三种常见写法：template <class T> requires C<T> 把约束写在模板头后面；template <C T> 把 concept 直接放在类型参数位置；函数尾部的 requires C<T> 适合约束依赖多个参数或返回类型的情况。三种写法语义相近，但可读性与重载决议的呈现不同；团队里选一种主写法，别在同一文件里混用三种。

9.7 旧写法对照：enable_if 与 concepts

enable_if_t<条件, int> = 0 是 C++11 时代的常见写法：条件为假时，enable_if_t 没有 type，默认模板参数替换失败，模板从候选集里消失（SFINAE）。它工作，但可读性差：约束藏在默认参数里，错误信息只告诉你“没有匹配的函数”，不会直接说“integral 不满足”；重载之间的约束也无法比较，只能靠“谁替换成功”来选。concepts 把同一件事写成 template <std::integral T>，约束在签名上可见，诊断也更直接。新代码优先用 concepts；旧代码里的 enable_if 仍然要能读懂。

SFINAE 的“替换失败不是错误”只适用于直接上下文里的类型与表达式；如果替换成功、但函数体里出错，仍然是硬错误。这也是旧写法难调的原因：约束没写全时，错误会落到函数体深处。std::void_t 是另一个旧工具：它把一串类型映射成 void，用来探测“某个嵌套类型/成员函数是否存在”；配合 enable_if 或特化，能写出“有 value_type 就走这条重载”的代码。这些技巧在标准库实现里仍然大量存在，读得懂就行，新接口不必再手写。

concept 与 if constexpr 的分工也不同：if constexpr 是在模板内部按类型选分支，两个分支的语法都要能写出来；concept 是在候选集阶段决定“这个模板参不参与重载”。能用 concept 表达“这个类型必须支持某操作”时，优先用 concept；只有在函数体内部需要按类型走不同实现、而接口本身仍然接受所有类型时，才用 if constexpr。一个管“能不能进来”，一个管“进来之后走哪条路”，不要混用。

concept 也会“过度约束”。如果你写 requires(T t) { t.size(); t[0]; }，就把“可用下标访问”写成了硬要求，链式容器 std::list 即使能遍历也会被挡住。按算法真正用到的操作写约束：只遍历就要求 range，只读大小就要求 sized_range，不要顺手把 operator[] 也写进去。约束越贴近需求，模板的适用范围越准确。

读 concept 诊断时，先找 constraints not satisfied 这一行，再看它下面列出的“不满足的原子约束”。is_integral_v<double> evaluated to false 这类信息会直接指出是哪一条要求没过；如果只看到 no matching function，把诊断往下翻，通常会有一行 because ... 解释候选被剔除的原因。诊断长不代表没有信息，关键是把“候选集为什么变成空”找出来。

9.8 本机实测：四个读数

实验记录本机实测：约束的通过与失败

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g；concept_error 额外用 -fdiagnostics-plain-output -fconcepts-diagnostics-depth=1 压缩诊断。

  • concept_basic 的 stdout 是 twice=42 / demo=40：int 满足 std::integral；

9.9 下一单元从哪继续

下一单元 8.3 可变参数模板与完美转发 会把模板参数从“一个类型”扩展到“一包类型”：template <typename... Ts>、折叠表达式、std::forward。concepts 也会与参数包结合（例如要求每个类型都可打印）；先确保你能读懂单个约束的诊断，再处理“一包类型里哪个不满足”的长诊断。

在工程里，concept 的最大价值往往不是“让模板更强”，而是“让接口意图写出来”。一个新模板如果只写 typename T，调用者要从函数体猜需要什么操作；写成 template <Named T> 或 template <std::ranges::range R>，要求就在签名上。先写约束，再写函数体，能逼你想清楚“这个模板到底接受什么、拒绝什么”。

约束也不是越多越好。把实现细节（例如“必须有 size()”）写进 concept，会让接口比实际需要更窄；把本该检查的前提漏掉，又会让错误落到函数体。判断标准是“调用者需要知道的最小契约”：算法真正依赖的操作写成约束，算法内部的临时实现细节不写。这样既保住复用，又让错误尽早出现；约束写得准，模板才既好用又好懂，调用者也能从签名读出你的意图，而不是从一长串模板报错里猜。

小结这一节要带走的五件事
  • concept 是编译期谓词；template <std::integral T> 把约束写在模板头上，不满足时模板不进入候选集。
  • 约束失败时诊断会指向 constraints not satisfied 与具体求值结果；格式参数只影响显示。
  • 约束参与重载决议；互斥约束各选一个，重叠约束按包含关系比较，无法比较就报歧义。
  • requires 表达式检查操作是否合法、返回类型是否满足约束；函数体里的隐含要求不会被自动检查。
  • enable_if 是旧写法，concepts 可读性与诊断更好；新代码优先 concepts。

  1. double 不满足 std::integral，模板不进入候选集，调用点报“没有匹配的函数”；不是函数体里的 + 出错，因为模板根本没被实例化。
  2. 前者说明这个候选因为约束不满足被排除；后者是约束求值的具体证据：is_integral_v<double> 为假，所以 integral<T> 不满足。
  3. int 只满足 integral，不满足 floating_point，所以只有一个候选，不会歧义。
  4. 检查 value.name() 这个表达式合法，并检查它的返回类型能转换成 std::string；它不执行 name() 的函数体。
  5. range 只要求能遍历，不要求元素能 to_string；dump 函数体里的 std::to_string(item) 对 std::string 不成立，实例化时才会报错。约束没有覆盖函数体的全部隐含要求。
