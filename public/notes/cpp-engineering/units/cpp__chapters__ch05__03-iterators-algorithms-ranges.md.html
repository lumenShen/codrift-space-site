容器负责“存”，算法负责“算”，迭代器是两者之间的接口。std::sort(v.begin(), v.end()) 不认识 vector，只认识“随机访问迭代器”；std::find_if 不认识 list，只认识“能从头走到尾的迭代器”。ranges 把这层接口再往前推一步：你可以写 v | views::filter(...) | views::transform(...)，像搭管道一样组合操作，而且求值是惰性的——不遍历就不计算。

这一单元有六个小实验：四个算法、lambda 谓词、惰性 view、zip / enumerate、range 管线、算法与手写循环的等价结果。重点是“什么时候用算法、什么时候用循环”，以及“view 不拥有数据”这条寿命规则。

学习目标看完这一单元，你应该能
  • 用 sort / find_if / transform / accumulate 完成常见容器处理，并说出它们要求什么迭代器类别；
  • 用 lambda 捕获外部变量作为谓词，并解释按值捕获与按引用捕获的差别；
  • 解释 views::filter / transform 为什么是惰性的，修改源容器后 view 的结果为什么会变；
  • 用 views::zip / views::enumerate 同时遍历多个序列/带下标，并正确解构；
  • 说出 view 的悬空风险，知道什么时候必须把源容器放在 view 之前声明。

13.2 四个算法：排序、查找、变换、累加

std::sort(begin, end) 要求随机访问迭代器：vector / deque / array 满足，list 只提供双向迭代器，不能直接用 std::sort（要用 list::sort）。std::find_if 只要求输入迭代器，list 也能用；std::transform 把每个元素交给函数并写回（或写到另一段），std::accumulate 在 <numeric> 里，按顺序把元素累加。算法不关心容器的类型，只关心迭代器能做什么；这就是“迭代器类别”的实际意义。

sum_after_double(values) 在辅助 .cpp 里又做了一次 sort、transform，再 accumulate，得到 2+4+6+8+10=30。注意 values 是按值传进去的，函数内的排序不会影响 main 里的 values；算法修改的是“你给它的那个范围”，按值传参时修改的是副本。

迭代器分成几类：输入、输出、前向、双向、随机访问、连续。类别越高，算法能用的操作越多：std::find 只要输入迭代器，std::reverse 要双向，std::sort 要随机访问。算法文档里的“要求”不是建议，而是编译期约束；给 std::sort 传 list 的迭代器，会在模板实例化深处报错。选算法前先看它要求哪一类迭代器，再确认容器是否满足；这比试错快。

输出迭代器是另一类：它只写不读，典型代表是 std::back_inserter(v)。std::transform(first, last, std::back_inserter(out), f) 会把结果追加到 out，而不是覆盖已有元素；std::copy、std::remove_copy_if 也常用它。back_inserter 会调用 push_back，所以目标容器必须有 push_back；std::array 没有，就不能用它。输出范围的大小由算法写入的元素个数决定，调用者要保证目标能容纳（或使用插入器）。

std::sort 不保证相等元素的相对顺序；需要稳定排序时用 std::stable_sort，代价是额外内存或更慢。std::partial_sort 只排出前 k 个，std::nth_element 只保证第 n 个位置正确、左右分区，适合“找中位数/前 k 小”而不需要全排序。算法名字里的限定词（stable / partial / nth）就是复杂度与语义的提示；不要一律用 sort，也不要在需要稳定时用 sort 然后自己补救。

13.3 lambda 作为谓词：捕获外部状态

[threshold] 是按值捕获：lambda 内部保存一份 threshold 的副本，之后外部改 threshold 不影响 lambda。[&threshold] 是按引用捕获：lambda 内看到的是外部变量本身，外部改了它，lambda 下次调用也会看到新值；代价是 lambda 活得比外部变量久时，引用会悬空。捕获列表决定“lambda 拥有什么、借用什么”，不是“写起来方不方便”。

find_if 返回第一个满足谓词的迭代器；找不到返回 end()。count_if 数满足谓词的元素个数。谓词可以是 lambda、函数对象、普通函数；算法只要求“能对元素调用并返回可转成 bool 的结果”。lambda 的类型是编译器生成的闭包类型，每个 lambda 表达式类型唯一；这也是为什么 std::sort 的第三个参数可以是 lambda，而不需要写一个具名函数对象。

算法按值接收谓词，所以你传进去的 lambda 会被复制一份。如果 lambda 按引用捕获了外部变量，复制后仍然指向同一个外部变量；算法执行期间外部变量必须活着。如果 lambda 按值捕获，复制的是闭包成员，谓词内部的修改不会回到你的 lambda（除非传 std::ref）。理解“算法复制谓词”这件事，才能解释“为什么我在 lambda 里加计数，外面没变”。

谓词应该是纯的：同样的输入返回同样的结果，不修改外部状态。有副作用的谓词会让算法行为依赖调用次数与顺序，而标准只规定算法结果，不规定它内部调用谓词多少次。需要“遍历时做副作用”，用手写循环或 for_each；需要“筛选”，用无副作用的谓词。把副作用塞进 count_if，代码可能对某个实现正确，换一个标准库就变样。

13.4 views：惰性，不拥有数据

第一次遍历 view 时，filter 挑出偶数 2, 4，transform 乘 10，输出 20 40。然后 values[1] = 10 把原来的 2 改成 10（仍是偶数）；第二次遍历同一条 view，filter 重新读取源容器，输出 100 40。view 不缓存结果、不拥有元素；它只是“遍历时怎么取/怎么算”的描述。 修改源容器后，view 的结果会跟着变——这既是惰性的好处，也是悬空风险的来源。

view 的寿命依赖源容器：上面的 values 在 view 之前声明、之后销毁，所以 view 在 values 活着时使用是安全的。如果写 auto view = make_values() | views::filter(...);，make_values() 返回的临时 vector 在整条语句结束后销毁，view 就指向已销毁的容器；再遍历它是未定义行为。view 不延长源数据的寿命；要么把源容器存进一个有名字的变量，要么让 view 只在该变量活着的作用域内使用。

陷阱把 view 当成容器保存

你会看到：auto view = values | views::filter(...); 之后，把 view 返回/存进成员、过一会儿再遍历，结果偶尔正确、偶尔乱码。你会误判成“views 不稳定”。真相是：view 通常只保存指向源范围的迭代器/指针，不拥有元素；源容器销毁、扩容、修改后，view 可能悬空或结果变化。view 是“借来看”的，不是“拿走保存”的；需要长期保存就把结果物化到 vector（例如 std::ranges::to<std::vector>()，C++23）。

view 对象通常很小，复制一个 view 不会复制元素；它只是复制“怎么遍历”的描述。filter 会保存谓词的副本，transform 会保存函数的副本，take 只保存计数。如果谓词/函数有状态，复制 view 会复制这些状态；算法按值接收函数对象时，状态变化可能不会回到你原来的对象——需要共享状态时，用 std::ref 包一层，或者把状态放到 view 外部。

C++23 的 std::ranges::to<std::vector>() 把 range 物化成容器，例如 auto v = pipeline | std::ranges::to<std::vector>();。物化会立即遍历整条管线，把结果存下来；之后源容器再变，物化结果不跟着变。需要“快照”时物化，需要“实时视图”时保留 view。两种语义要明确选，不要一会儿当 view 用、一会儿当容器用。

views::take 会短路：取够 n 个元素就停止向上游要数据，所以它能用在无限序列上，例如 views::iota(0) | views::take(5)。惰性 + 短路是 view 最实用的组合；如果先 filter 再 take，filter 可能已经扫描了很多元素才凑够 n 个，这仍然是按需的，只是“需求”由 take 决定。

13.5 zip 与 enumerate：并行遍历与下标

views::zip(numbers, letters) 把两个范围按位置配成 tuple，auto [number, letter] 用结构化绑定拆开；遍历长度取两者较短的那个（标准规定 zip 在任一范围结束时停止）。views::enumerate(letters) 产生“下标 + 元素”的 tuple，index 从 0 开始；它不需要你手写计数器，也不会因为 continue 忘加下标。这两个 view 都是 C++23 才进入标准库的设施；本机 g++ 已实测可用，换一个较老的编译器可能没有。

zip / enumerate 返回的是 view，不是容器；它们同样不拥有源数据。zip 的迭代器类别取决于两个源范围中最弱的一个；如果其中一个只能输入遍历，zip 也只能输入遍历。组合 view 时，先看每个源范围的迭代器能力，再看算法要求；不要假设 zip 之后还能随机访问。

enumerate 的 index 默认是 std::size_t 或实现定义的无符号类型，参与算术时要注意有符号/无符号混用；需要 int 时显式转换，不要把它直接和有符号数比较。zip 的元素是引用 tuple，auto [a, b] 按值复制元素；要修改源元素，写 auto&& [a, b] 或 auto& [a, b]。结构化绑定的 auto 与范围 for 的 auto 一样，默认是复制；在 zip 上改元素却没生效，先检查这里漏没漏 &。

13.6 range 管线：filter → transform → take

values = {1,2,3,4,5,6}；filter(>2) 留下 3,4,5,6；transform(*2) 变成 6,8,10,12；take(3) 只取前三个，输出 6 8 10。整条管线是逐元素拉取的：take 要一个元素，才向 transform 要，transform 再向 filter 要，filter 再读源容器；不会先建一个中间 vector。这就是惰性管线的价值：少分配、少拷贝，且可以提前停止。

管线也有边界：take(3) 之后的元素不会被计算；如果你需要“结果保存下来”，要把管线物化成容器。filter 的谓词与 transform 的函数会被反复调用，函数体不要依赖“只调用一次”的假设；有副作用时，顺序与次数由遍历方式决定。

第 1 帧是源容器；第 2 帧的 filter 不建新容器，只在遍历时跳过不满足的元素；第 3 帧的 transform 与 take 继续按需拉取，最终只计算到第三个结果。整条管线只在 for 循环真正遍历时工作；没有遍历，就没有计算。

管线里的函数最好无副作用。filter / transform 在每次遍历时都会重新调用，调用次数取决于上游要多少元素、take 何时停止；你无法从“源容器有 6 个元素”推断谓词一定调用 6 次。需要“每个元素只处理一次”时，先物化成容器，再在容器上做后续操作；需要“流式处理、提前停止”时，接受按需调用。

filter / transform 返回的元素类型可以变化：transform 可以把 int 变成 std::string，后面的 take 只关心“能不能取”，不关心具体类型。view 的组合是类型层面的组合，编译器会为整条管线生成一个具体的 view 类型；如果类型太长，用 auto 接住，不要手写。C++23 的 views::zip / enumerate 也返回 view，可以继续接 filter / transform。

13.7 算法与手写循环：什么时候用哪个

std::count_if 与手写循环得到相同的 3。算法的优势是意图清楚、少写边界条件：count_if 的名字直接说明“数满足条件的元素”，循环则要读一遍才知道；算法的劣势是有时不够灵活：需要提前退出、多个条件、复杂状态时，手写循环可能更直接。判断标准不是“算法更高级”，而是“这段代码的主要读者要一眼看懂什么”。

std::ranges 版本的算法可以直接收范围（std::ranges::sort(values)），不用写 begin/end；本单元仍用迭代器版本，是为了让你看清“算法与容器之间是迭代器”这层关系。两种写法可以混用，但一个项目里最好统一风格。

std::ranges 还支持投影（projection）：std::ranges::sort(people, {}, &Person::age) 按 age 排序，不必写比较 lambda；第三个参数是“取哪个成员参与比较”。投影让你把“比较什么”与“怎么比较”分开：std::ranges::sort(people, std::greater{}, &Person::age) 按年龄降序。传统 std::sort 没有投影，只能写 lambda；新代码可以优先用 ranges 版本。

算法与手写循环的性能通常没有本质差别：编译器会把 find_if 内联成类似的循环，ranges 的 view 也能被优化。选择标准是可读性与正确性，不是“算法一定更快”。如果手写循环能更清楚地表达“提前退出、多个状态、复杂边界”，就手写；如果算法名字能一眼说明意图，就用算法。把简单循环硬套成算法，反而会让读者多跳一层。

用算法不等于自动安全：std::remove_if 只把保留的元素移到前面并返回新逻辑结尾，并不删除元素，必须再接 erase 才是“删除”；在遍历中修改容器结构，仍然要遵守迭代器失效规则。算法负责“怎么处理元素”，不负责“容器的生命周期”，这两件事要分开想。

13.9 下一单元从哪继续

下一章 14.1 auto、decltype 与结构化绑定 会把这一单元里的 auto [number, letter] 拆开讲：auto 怎样推导、为什么有时候会丢掉引用与 const、decltype((x)) 为什么多一层括号。容器与算法会继续作为例子出现，但重点转到“类型推导”——写模板与泛型代码时，这是每天都用的基本功。

算法与 view 的边界要分清：算法通常“立即执行并返回结果/迭代器”，view 通常“描述怎么遍历，遍历时才执行”。std::ranges::find 是算法，会立刻扫描；views::filter 是 view，不扫描。名字里带 views:: 的通常是惰性适配器，名字是动词的通常是算法；不确定时看它返回的是“结果”还是“范围”。

读标准算法文档时，重点看三件事：要求哪类迭代器、是否修改输入范围、返回什么。std::sort 修改范围并返回 void；std::find 不修改、返回迭代器；std::transform 可修改输出、返回输出末尾。把“是否修改”记错，是算法误用的常见来源；例如 std::remove 并不删除元素，只是把要保留的往前挪，必须配合 erase。

读算法返回值也要看清：std::find 返回迭代器，std::count 返回数量，std::for_each 返回函数对象（C++17 起），std::transform 返回输出范围的末尾。返回值不是装饰：连续操作时，上一个算法的返回值常常是下一个算法的输入；把返回迭代器当成 bool 用，是另一个常见错误。

小结这一节要带走的五件事
  • 算法通过迭代器工作：sort 要随机访问，find_if 只要输入迭代器；list 不能直接用 std::sort。
  • lambda 的捕获列表决定它拥有副本还是借用引用；按引用捕获要保证生命周期。
  • views 是惰性描述，不拥有数据；修改源容器会改变 view 的结果，源容器销毁会让 view 悬空。
  • views::zip 并行遍历、views::enumerate 带下标，二者都是 C++23 设施，返回 view 而非容器。
  • 算法与手写循环都能正确时，选“读者一眼看懂意图”的那个；不要为了用算法而用算法。
自测题自测题（先自己做，再对答案）
  1. 为什么 std::sort 不能直接排 std::list？应该用什么替代？
  2. [threshold] 与 [&threshold] 两种捕获，在外部修改变量后行为有什么不同？
  3. views_lazy 里第二次遍历为什么输出 100 40，而不是缓存下来的 20 40？
  4. views::zip(numbers, letters) 在其中一个范围更短时会怎样？它返回的是容器还是 view？
  5. 为什么 auto view = make_values() | views::filter(...) 有悬空风险？安全的写法是什么？
注自测答案
  1. std::sort 要求随机访问迭代器，list 只提供双向迭代器；用 list::sort 成员函数。
  2. 按值捕获保存一份副本，外部改动不影响 lambda；按引用捕获借用外部变量，外部改动会被 lambda 看到，但外部变量先销毁时引用悬空。
  3. 因为 view 不缓存结果；第二次遍历重新从源容器读取，values[1] 已从 2 改成 10，filter 仍放行，transform 得到 100。
  4. zip 在任一范围结束时停止，长度取较短者；它返回一个 view，不拥有两个源范围的数据。
  5. make_values() 返回的临时容器在整条语句结束后销毁，view 仍引用它；再遍历就是悬空。安全写法是把源容器存进有名字的变量，保证它活得比 view 长，或把结果物化成容器。
