上一单元的模板只有一个 T；这一单元处理“一包类型”。sum_all(1, 2, 3.4) 的参数个数与类型都可以变，模板要能接住任意多个实参，并且保持每个实参的值类别——左值仍是左值，右值仍是右值。前者靠参数包与折叠表达式，后者靠转发引用（T&&）与 std::forward。

这一单元的重点不是写“万能函数”，而是理解两条规则：参数包在一次展开里逐项处理；T&& 在推导语境下不是右值引用，而是转发引用。 把这两条搞错，就会写出“看起来能转发、实际把左值搬空”的包装函数。

10.1 先看工程长什么样

这一单元在 examples/ch04/ 下再加六个多文件例子。参数包、折叠、转发、emplace 各占一个目录；模板定义仍然在头文件里。

第 1 帧的 sum_fold/ 用 (... + values) 折叠求和；print_all/ 用逗号折叠逐个打印。第 2 帧的 forward_wrapper/ 用转发引用 + std::forward 保持值类别；forward_vs_move/ 故意把 forward 写成 move，观察左值被搬空。第 3 帧的 emplace_demo/ 对照 push_back / emplace_back 的拷贝/移动计数；sizeof_pack/ 用 sizeof... 数参数个数。

10.2 参数包：Ts... 是类型包，args... 是值包

typename... Ts 声明一个类型参数包：它可以收零个、一个或多个类型。Ts... values 声明一个函数参数包：每个实参对应包里的一个类型。调用 sum_all(1, 2, 3, 4) 时，Ts 推导为 int, int, int, int，values 是四个 int。包不是数组，也不是 std::vector；它在编译期展开，每个元素可以是不同类型（例如 sum_all(1, 2.5, 3) 会得到 double，因为 + 逐项提升了类型）。

sizeof...(Ts) 返回包里元素个数，sizeof...(values) 同理（对值包）。sizeof... 是编译期常量，可以用在 static_assert、数组长度、模板参数里。参数包也可以递归展开：处理第一个元素，把剩下的包继续传给同一个模板，直到包为空；C++17 的折叠表达式把常见递归写法压缩成一行，本书优先用折叠。

参数包能出现的位置比想象中多：函数参数、模板参数、基类列表、成员初始化列表、std::tuple 的构造、花括号初始化、using 声明、lambda 捕获。每出现一次 ...，就是一次“把包展开成逗号分隔的元素”；展开的模式必须包含包名，否则编译器不知道按哪个包展开。例如 std::tuple<Ts...> 展开类型包，std::make_tuple(args...) 展开值包。

空包是合法的，但要看使用场景。print_all() 的折叠是逗号折叠，空包展开成“什么也不做”，仍然会打印一个换行；sum_all() 用 (... + values) 折叠，空包没有初始值，无法形成一个合法表达式，编译失败。一元折叠对空包不一定有定义：&& 的空折叠是 true，|| 是 false，逗号是 void()，而 +、* 之外的很多运算符没有默认单位元。需要支持空包时，用二元折叠给一个初始值，例如 (0 + ... + values)。

递归展开要写两个重载：一个处理“至少一个元素”，一个处理空包作为出口。折叠表达式出现后，很多递归可以删掉；但当每一步的逻辑依赖前一步的结果、或需要提前终止时，递归仍然更自然。折叠适合“把同一运算套到每个元素”，不适合“元素之间要互相协调”的复杂逻辑。

10.3 折叠表达式：把包“折叠”成一个表达式

((std::cout << values << ' '), ...) 是逗号折叠：把包里的每个 values 依次代入 std::cout << values << ' '，用逗号连接，从左到右执行。(... + values) 是二元折叠：把 + 放在每个元素之间，等价于 1 + 2 + 3 + 4。折叠有四种形式：一元左折、一元右折、二元左折、二元右折；对 + 与 , 来说，结合顺序在多数场景下不影响结果，但对 -、/ 这类非结合运算，左折与右折结果不同。

print_all 的参数是 const Ts&...，所以它接受左值和右值，但不会移动它们；values 在折叠里被逐项使用。折叠表达式不是循环：它在编译期展开成固定长度的表达式，运行期没有“遍历参数包”的循环变量；包里有几个元素，就展开成几段代码。

第 1 帧的包有三个元素；第 2 帧的折叠把它们展开成三条输出语句，按从左到右的顺序执行。折叠的“顺序”由运算符决定：逗号折叠保证从左到右；+ 折叠不保证求值顺序（但 + 本身通常不依赖顺序）。不要在折叠里放有副作用的表达式，除非你确认顺序语义。

折叠的身份值（identity）值得单独记：&& 的空一元折叠是 true，|| 是 false，逗号是 void()；+、*、&、| 等运算符没有标准的空折叠结果（除非写二元折叠提供初值）。“空包能编译”不是对所有运算符都成立；写通用模板时，要么要求至少一个元素，要么显式提供初值。static_assert 配合 sizeof...(Ts) > 0 可以把“至少一个”写成编译期要求。

折叠的括号不能省：(... + values)、(values + ...)、(init + ... + values) 是三种不同形式。省略号在运算符左边还是右边，决定结合方向；对 + 这种结合律成立的运算，结果一样；对 -、/、>> 这类不满足结合律的运算，左折与右折结果不同。不要凭“看起来差不多”选择，先确定你要的是 ((a - b) - c) 还是 a - (b - c)。

&& 与 || 的折叠保留短路语义：从左到右求值，遇到 false / true 就停止。但短路只对逻辑运算符成立；+ 折叠会把所有元素都求值，即使前面的结果已经“够用”。需要“遇到第一个不满足就停止”的逻辑，用 && 折叠或显式循环，不要用 + 模拟。

10.4 转发引用：T&& 不是右值引用

第一次 invoke_all(take, target) 传入左值 target，Args 推导为 Target&，引用折叠后 Args&& 变成 Target&；std::forward<Args>(args) 返回左值，take(Target) 按值接收时调用拷贝构造，所以 lvalue_copies=1 moves=0。第二次传入临时对象 Target{}，Args 推导为 Target，Args&& 是 Target&&；std::forward 返回右值，take 调用移动构造，所以 moves=1。转发引用保留的不只是类型，还有值类别。

T&& 只有在模板参数推导语境下才是转发引用；如果 T 是具体类型（例如 void f(int&& x)），它就是普通右值引用，只能绑定右值。转发引用的两条规则：

  • 实参是左值 U：T 推导为 U&，T&& 经引用折叠变成 U&；
  • 实参是右值 U：T 推导为 U，T&& 是 U&&。

引用折叠规则只有四条：& & → &、& && → &、&& & → &、&& && → &&。左值“传染”：只要有一个 &，结果就是左值引用。这就是 std::forward<T> 能“还原”值类别的原因——它只是 static_cast<T&&>(t)，真正做判断的是 T 的推导结果。

第 1 帧的左值在折叠后仍是左值引用，第 2 帧的右值保持右值引用。转发引用不是“万能引用”这种魔法，它是“推导 + 引用折叠”的结果；离开模板推导，T&& 就只是右值引用。

转发引用有三个常见失效场景。第一，写成 const T&& 不是转发引用，它只能绑定右值，而且 T 不再按左值/右值推导；第二，类模板里的 T&& 成员不是转发引用，因为 T 在类实例化时已经确定，不会在每次调用时重新推导；第三，花括号初始化无法推导：invoke_all(f, {1, 2}) 里的 {1,2} 不是一个有类型的表达式，Args 推不出来。看到“转发引用不转发”，先检查它是不是在推导语境里、有没有 const、实参是不是花括号列表。

std::forward 只应该用一次。forward<T>(x) 把 x 还原成 T&& 的值类别；如果同一个 x 被转发两次，第一次可能已经把它移走，第二次拿到的是 moved-from 对象。转发是“把值类别传下去”，不是“复制一份”；需要多次使用同一个参数时，先想清楚所有权，或者只转发给一个目标。

转发引用也常与 auto&& 混淆。auto&& x = expr; 是转发引用式的推导，能绑定左值也能绑定右值，但 x 本身是一个具名变量，表达式 x 永远是左值；要把它继续按原值类别传下去，仍然需要 std::forward<decltype(x)>(x)。“变量有名字就是左值”，这是值类别最基本的规则之一。

10.5 std::forward 与 std::move：一个保留，一个强制

bad_wrapper(bad) 传入左值 std::string，T 推导为 std::string&；std::move(value) 不管 T 是什么，一律转成右值，于是 std::string sink 移动构造，bad 被搬空，输出 bad=empty。good_wrapper(good) 用 std::forward<T>(value)，T = std::string& 时返回左值，sink 拷贝构造，good 不变，输出 good=hello。std::move 是“我确定不要这个对象了”，std::forward 是“按调用者原来的值类别传下去”；包装函数不知道调用者要不要保留实参，所以必须用 forward。

std::move 与 std::forward 都只是类型转换，不搬任何东西：真正搬资源的是移动构造/移动赋值。std::forward<T> 的定义就是 static_cast<T&&>(t)；std::move(t) 等价于 static_cast<remove_reference_t<T>&&>(t)。转发函数里写 std::move 是常见的 bug：它会把左值实参静默搬空，调用者还以为自己的对象还在。

对 const 对象用 std::move 不会变成移动，而是变成“拷贝”：const T&& 不能绑定到 T&& 移动构造，编译器退回复制构造。move 只是把表达式变成右值，能不能移动取决于类型有没有可用的移动构造；对 const 对象、没有移动构造的类型、或者被 const 成员拖住的类，move 可能毫无效果。

moved-from 对象“有效但未指定”：标准不保证它为空，也不保证还能做什么，只保证可以安全析构、可以重新赋值。不要读 moved-from 对象的值来判断“移动成功没有”；如果类型没有明确文档化 moved-from 状态，最安全的做法是把它当成“只能销毁或重新赋值”。本单元的例子用 std::string 的空状态做演示，是因为标准库对 string 的 moved-from 状态有实际保证；换成自定义类型，不能照搬。

对同一个对象自我移动（x = std::move(x)）通常是合法的，但结果由类型决定；标准库容器一般能保持有效，自定义类型未必。移动赋值要处理自赋值，尤其是在手写资源管理类时；std::swap 式的实现通常能自然处理，但不要假设所有类型都安全。

标准原文标准原文：参数包与 forward 的返回

A template parameter pack is a template parameter that accepts zero or more template arguments.

Returns: static_cast<T&&>(t).

大意：模板参数包接受零个或多个模板实参；std::forward<T>(t) 返回 static_cast<T&&>(t)，它只做类型转换，不搬对象。

出处：N4950 §13.7.4「Template parameter packs」（[temp.variadic]）与 §22.2.4「Forward」（[forward]）。

陷阱在包装函数里用 `std::move` 转发

你会看到：包装函数把参数原样传给下层，测试时用临时对象一切正常；换成左值实参后，调用者的对象莫名其妙变空。你会误判成“下层函数有 bug”或“std::string 有问题”。真相是：包装函数的 T&& 是转发引用，左值传进来时 T 是 U&；你写 std::move(arg) 强制把它变成右值，下层按右值搬走了资源。包装函数要用 std::forward<T>(arg)；只有你确实要放弃这个对象时，才用 std::move。

10.6 emplace_back 与 push_back：少一次临时对象

push_back(Widget("a")) 先构造一个临时 Widget，再把它移动进 vector，所以 moves=1；emplace_back("b") 把 "b" 直接转发给 Widget 的构造函数，在 vector 的存储里就地构造，没有临时对象，也不需要移动。emplace_back 的收益是“少一次临时对象 + 移动”，不是“一定更快”：如果参数本来就是一个已经构造好的对象，push_back 可能更清晰；如果容器需要扩容，emplace_back 也可能触发元素搬移，收益被扩容成本盖过。本机读数只说明这个例子的情况，不承诺所有场景。

emplace_back 也依赖完美转发：它把参数包原样传给元素的构造函数。vector<Widget>::emplace_back("b") 里，const char* 被转发给 Widget(std::string)，先构造 std::string 再构造 Widget，仍然可能有一次临时 std::string；要彻底少一次转换，可以传 std::string("b") 或给 Widget 加 const char* 构造函数。“emplace 一定比 push 少一次拷贝”是过度简化；看构造链，别看名字。

emplace_back 与花括号初始化配合时还有一个坑：std::vector<std::vector<int>> v; v.emplace_back({1, 2}); 通常编译失败，因为 emplace_back 是模板，无法从 {1, 2} 推导出 std::vector<int> 的构造参数。要写成 v.emplace_back(std::initializer_list<int>{1, 2})，或者直接用 v.push_back({1, 2})。花括号不是表达式，没有类型，模板推导接不住；这是 emplace 与 push_back 最常被忽略的差别。

emplace_back 用直接初始化构造元素，因此可以调用 explicit 构造函数；push_back 需要隐式转换，遇到 explicit 构造函数就要显式构造临时对象。这也是某些场景下 emplace_back 更方便的原因。但方便不等于更好读：如果参数已经是一个完整对象，push_back 的意图更清楚；emplace_back 适合“把构造参数直接交给容器”的场景。

标准库里的 std::make_unique<T>(args...)、std::make_shared<T>(args...) 也是把参数包转发给构造函数；它们和 emplace 一样，参数会按原值类别传给 T 的构造函数。如果你在自己的工厂函数里再包一层，别忘了 std::forward：template <class T, class... Args> auto make(Args&&... args) { return std::make_unique<T>(args...); } 会把右值实参当成左值传下去，正确写法是 std::forward<Args>(args)...。参数包的转发，本质就是把每个 args 单独 forward，再用 ... 展开。

std::forward 只改变值类别，不改变 const：const 左值转发后仍是 const 左值，不会突然变成可移动的右值。要移动一个 const 对象，必须先去掉 const，但那通常说明设计有问题；移动意味着“放弃所有权”，而 const 对象本来就不该被放弃。转发函数遇到 const 实参时，老老实实按 const 引用传下去，让下层决定拷贝还是拒绝。

转发的价值不是“性能技巧”，而是让包装层不改变实参的语义：调用方传左值，下层就看到左值；传右值，下层就能移动。包装层越多，越要保证每一层都用 std::forward 接力，任何一层漏掉，值类别就在这里退化成左值。

10.8 下一单元从哪继续

下一章 11.1 序列容器 会把“容器”从模板例子变成日常工具：vector 的扩容与迭代器失效、string 的短字符串优化、deque / list 的取舍。参数包与转发会以 emplace_back、vector::emplace 的形式继续出现；先确保你能解释“为什么左值经过转发包装后没有被搬空”，再去看容器的迭代器规则。

小结这一节要带走的五件事
  • typename... Ts 是类型包，Ts... args 是值包；包在编译期展开，sizeof...(Ts) 数元素。
  • 折叠表达式把包折叠成一个表达式；逗号折叠从左到右，+ 折叠不保证求值顺序。
  • 模板推导中的 T&& 是转发引用：左值推导为 U&，右值推导为 U；引用折叠决定最终类型。
  • std::forward<T> 保留值类别，std::move 强制右值；包装函数用 forward，不要用 move。
  • emplace_back 把参数转发给元素构造，少一次临时对象；是否更快取决于构造链与扩容。

  3. 为什么 invoke_all(take, target) 里 Args 推导为 Target&，而 invoke_all(take, Target{}) 里是 Target？

  5. emplace_back("b") 比 push_back(Widget("b")) 少做了什么？为什么不能保证一定更快？
注自测答案
  1. Ts 是类型参数包，args 是函数参数包；三个实参对应三个元素，sizeof...(Ts) 为 3。
  2. 逗号折叠（一元左折的常见形式），从左到右依次执行每个 std::cout << values << ' '，最后输出换行。
  3. 左值实参让 Args 推导为 Target&，转发引用的 && 与 & 折叠成 Target&；右值实参让 Args 推导为 Target，Args&& 是 Target&&。
  4. std::move 一律转成右值，左值实参会被下层移动构造搬空；std::forward<T> 按 T 的推导结果还原值类别，左值仍是左值，不会被搬空。
  5. emplace_back 把 "b" 直接转发给 Widget 的构造函数，在容器存储里就地构造，省掉临时 Widget 与一次移动；但如果构造链里还有 std::string 临时对象，或者容器扩容搬移元素，成本仍可能发生，所以不能笼统说一定更快。
