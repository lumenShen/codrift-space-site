普通函数在运行时执行；constexpr 函数多了一种可能——如果实参是编译期常量，编译器可以在编译期把它算完，直接把结果写进程序。consteval 更进一步：它必须在编译期求值，运行期调用直接编译失败。static_assert 把条件放进编译期，不成立就报错；if constexpr 让模板只实例化命中的分支。

这一单元用六个例子拆开编译期计算：先看同一个 constexpr 函数怎样既在编译期算、又在运行期算，再用 consteval 把“必须编译期”钉死；然后用 static_assert 检查类型与大小，用 if constexpr 写只在某个类型下合法的分支；最后看一个 consteval 的运行期调用反例，以及 C++20 起能在编译期使用的 std::vector。

学习目标看完这一单元，你应该能
  • 写 constexpr 函数与变量，说出“编译期求值”与“运行期调用”是两条路径；
  • 用 consteval 强制立即求值，并读懂“不是常量表达式”的编译错误；
  • 用 static_assert 在编译期检查条件，理解它检查的是当前目标平台；
  • 用 if constexpr 在模板里丢弃不匹配的分支，知道非模板环境下它仍会检查两个分支；
  • 说出编译期计算的边界：不能有未定义行为、不能读运行期输入、受实现限制；
  • 知道 C++20 起 constexpr 函数里可以用 std::vector 等容器做临时计算。

18.2 constexpr：能编译期算，也能运行期算

constexpr 函数没有承诺“一定在编译期执行”，它只是允许在常量表达式中使用。同一个 factorial，用字面量调用时可以常量求值，用运行期变量调用时就在运行期算。编译器可以选择在编译期折叠它，但语义上两条路径都合法。

constexpr int compiled = factorial(5); 要求 factorial(5) 是常量表达式，编译器在编译期算出 120；runtime_factorial(6) 的参数 6 虽然是字面量，但它经过普通函数调用，函数体在运行期执行，结果是 720。同一个 constexpr 函数，用在哪里决定它在哪算；constexpr 不是“把这个函数搬到编译期执行”的指令，而是“它具备在编译期执行的能力”。

constexpr 函数体在 C++14 起可以包含循环、局部变量、多个 return，比 C++11 的“单表达式”宽松得多。它仍然有约束：不能有未定义行为，不能调用非 constexpr 的函数（在常量求值路径上），不能读运行期输入。这些约束只在“常量求值”时检查；运行期调用时，它就是一个普通函数，可以有指针、可以分配内存（只要不要求在编译期算）。

constexpr 变量要求初始化器是常量表达式：constexpr int size = 10; 可以，constexpr int size = runtime_value(); 不行。constexpr 变量隐含 const，而且必须在编译期确定值；如果只是“运行期不再改”，用 const 就够了，不必强行 constexpr。

标准原文标准原文：constexpr 与 consteval 的声明

The constexpr specifier shall be applied only to the definition of a variable or variable template or the declaration of a function or function template. The consteval specifier shall be applied only to the declaration of a function or function template. A function or static data member declared with the constexpr or consteval specifier is implicitly an inline function or variable.

大意：constexpr 只能用于变量/变量模板的定义或函数/函数模板的声明；consteval 只能用于函数/函数模板的声明；带这两个说明符的函数或静态数据成员隐含 inline。

出处：N4950 §9.2.6「The constexpr and consteval specifiers」（[dcl.constexpr]）。

“隐含 inline”很实用：把 constexpr 函数定义在头文件里，被多个翻译单元包含也不会重复定义。这也是 constexpr 工具函数通常直接写在头文件里的原因；模板函数同理，二者都靠 inline 或模板规则避免 ODR 冲突。

18.3 consteval：必须编译期算

consteval 声明的是“立即函数”（immediate function）：每一次调用都必须在编译期求值，结果是一个常量。它比 constexpr 更严格——constexpr 可以运行期调用，consteval 不行。需要“这个值必须在编译期确定”时用它，例如生成固定表、检查配置、在编译期做断言。

constant_square() 是普通函数，在运行期被调用；但它里面的 square(5) 实参是常量，consteval 要求立即求值，编译器在编译期算出 25，运行期只是返回这个常量。square(4) 出现在 main 里，同样在编译期算出 16。consteval 的限制在“实参必须是常量表达式”，不在“调用点必须在常量上下文”；只要实参是常量，运行期函数里也能调用。

如果实参是运行期变量，consteval 调用就无法成立，编译器会报“不是常量表达式”。下一节的 constexpr_error/ 会看到真实诊断。这正是 consteval 的用途：把“必须在编译期”写成类型系统能检查的约束，而不是靠注释提醒。

consteval 函数不能声明为变量，也不能取地址后运行期调用；它的每一次调用都必须在编译期完成。constexpr 函数则可以取地址、可以运行期调用。二者不是“新代替旧”：constexpr 是“可以编译期”，consteval 是“必须编译期”，按需求选。

constexpr 与 const 容易混：const int n = runtime_value(); 只表示“运行期不再改”，初始化器不要求常量；constexpr int n = 42; 要求编译期常量，可以用于数组长度、模板实参。需要“编译期常量”时写 constexpr，只是“只读”写 const；反过来，把 const 当 constexpr 用，会在需要常量表达式的地方编译失败。

constinit 是 C++20 的另一个工具：它要求变量“在编译期完成初始化”，但不要求变量本身是 const，也不要求初始化器是常量表达式（只要初始化本身能静态完成）。constinit 解决的是“静态初始化顺序”问题，不是“运行期只读”；它常与全局/静态变量一起用，避免动态初始化的顺序不确定。本书只在边界里点到，不展开静态初始化顺序的细节。

constexpr 也可以出现在构造函数、析构函数、operator[] 等成员函数上，让对象在编译期构造/使用。C++20 起 constexpr 的限制进一步放宽（例如可以调用 new/delete，只要在常量求值内配对）；C++23 起 constexpr 函数里能用更多标准库设施。标准版本越高，能放进编译期的代码越多；写库时若要兼容旧标准，先查目标标准支持哪些 constexpr 设施。

constexpr 函数在运行期调用时就是普通函数，不要以为标了 constexpr 就“一定在编译期执行”。判断是否编译期求值，看调用上下文：constexpr 变量初始化、static_assert、模板实参、consteval 调用等要求常量表达式的地方才会强制编译期；普通运行期调用不会。“能编译期”与“已编译期”是两件事，性能分析时别把 constexpr 当成优化保证。

18.4 static_assert：条件不成立就编译失败

static_assert(条件, 消息) 在编译期检查条件；条件为假时，编译器报错并显示消息。它不需要运行程序，也不会产生运行期开销。条件必须是常量表达式，消息在 C++17 起可以省略，但建议总是写，因为它是给未来维护者看的线索。

第一个断言检查“本机的 int 是 4 字节”，第二个检查“long long 不小于 int”。第一条不是标准保证：C++ 只规定 int 至少 16 位，具体大小由实现决定；本书的本机是 4 字节，所以这个断言在本书工具链上成立，换一个平台可能直接编译失败。第二条同样是平台事实的检查；标准只保证 long long 至少 64 位（通常 8 字节），不保证一定不小于 int 的字节数（虽然实践中成立）。

static_assert 常用来检查模板参数、类型布局、常量配置：static_assert(std::is_copy_constructible_v<T>)、static_assert(sizeof(Header) == 16)。把“运行时才发现”的约定前移到编译期，是 C++ 模板库的常见手法；标准库大量用 static_assert 给出比模板报错更清楚的消息。

static_assert 与 if constexpr 的区别：前者检查一个条件，不成立就终止编译；后者在模板里选择分支，不满足条件的分支被丢弃。static_assert 是“必须成立”，if constexpr 是“按类型选路”；二者经常一起用：在某个分支里 static_assert 检查该分支的前提。

18.5 if constexpr：只实例化命中的分支

模板函数里，普通 if 的两个分支都会被编译；如果某个分支对当前类型不合法，即使运行期不会走到，也会编译失败。if constexpr 的条件必须是常量表达式；在模板中，条件为假的分支不会被实例化，因此可以写“只对某些类型合法”的代码。

kind_of(7) 让 T = int，只有第一个分支参与编译；kind_of(2.5) 让 T = double，只有第二个分支；kind_of("hi") 让 T = std::string，走 else。如果写成普通 if，std::to_string(value) 对 std::string 会报错，"text:" + value 对 int 也会报错；if constexpr 把不匹配的分支在实例化时丢掉，才让三种类型共存于一个模板。

第 1 帧只生成 int 版本，第 2 帧只生成 std::string 版本；每个 T 只看到自己那条路。这也是 if constexpr 与运行时多态的区别：它在编译期决定生成哪些代码，运行期没有分支判断，也没有虚调用。

需要提醒：在非模板函数里，if constexpr 的丢弃分支仍然会被完整检查。标准只在模板实例化时允许“不实例化丢弃的语句”；普通函数里写 if constexpr (false) { ... }，里面的代码仍然要语法正确、名字可查。想真正“按条件排除代码”，要么放进模板，要么用预处理宏。if constexpr 不是 #if 的替代品：前者是类型/常量分支，后者是文本替换；把平台相关、语法不同的代码塞进 if constexpr，通常得不到你想要的结果。

if constexpr 的条件必须是常量表达式，不能依赖运行期输入；条件为假的分支如果在模板里被丢弃，里面的 static_assert(false) 也可能不触发。不要把 static_assert(false) 放在模板的未命中分支里当“哨兵”，除非你确认它不会被实例化；需要“这个类型永远不支持”时，用 = delete 或约束，而不是依赖分支丢弃。

18.6 编译期计算的边界：不是所有东西都能算

constexpr / consteval 的常量求值有一条硬边界：不能有未定义行为。除零、越界、空指针解引用、有符号整数溢出，在运行期是“未定义”，在常量求值里则会让这个表达式“不是常量表达式”，编译失败。标准要求编译器诊断这种失败；实际消息可能很长，但根因通常是某一步不满足常量求值规则。

诊断会指出“调用 consteval 函数 square(value) 不是常量表达式”，并进一步指出 value 不是常量表达式。这不是 consteval 的缺陷，而是它的承诺：它只接受编译期能确定的值。要让运行期变量参与，就把函数改成 constexpr（允许运行期调用），或者把调用移到运行期路径。

另一个边界是“不能读运行期输入”：constexpr 函数不能调用 std::cin、不能读文件、不能取系统时间。编译期计算的输入只能来自源码里的常量、模板参数、sizeof、类型特征等编译期信息；这也是它可预测、可缓存的原因。

编译期计算还受实现限制：递归深度、步数、内存都有上限，超过会报“常量表达式过大/过深”。标准没有规定具体上限，由编译器决定；写 constexpr 算法时要避免无界递归，能写成循环就写循环，既省编译期资源，也更容易读。不同编译器版本对边界写法的接受程度也可能不同，跨平台项目要给编译期代码留出保守余量。

18.7 constexpr 容器：编译期也能用 vector

C++20 起，constexpr 函数里可以构造 std::vector、std::string 等动态容器，只要整个常量求值过程在结束时把分配的内存释放干净。这让“编译期建表、编译期解析、编译期校验”变得自然；下面的 sum_squares 在编译期建一个 vector，平方求和，再用 static_assert 检查结果。

static_assert(sum_squares(3) == 14) 要求在编译期完成整个 vector 的构造、push_back、遍历与析构；编译器在常量求值环境里分配临时存储，求值结束后释放。sum_squares(3) 在 main 里是常量表达式，得到 14；container_sum(4) 是运行期调用，得到 1²+2²+3²+4²=30。同一个函数，两条路径都成立；区别只是编译期路径不能依赖运行期输入。

编译期 vector 不是“把容器放进二进制常量区”，它只是常量求值期间的临时对象；求值结束后，结果是一个整数 14。别把“编译期能建 vector”误解成“运行时零成本容器”；运行期该分配还是要分配，constexpr 只影响常量求值那一次。

第 1 帧走编译期，第 2 帧走运行期，第 3 帧被 consteval 拒绝。constexpr 是“两扇门都开”，consteval 是“只开编译期这扇门”；选哪个取决于你是否允许运行期调用。

18.9 下一单元从哪继续

下一单元离开“纯计算”，进入文件与输出：<filesystem> 遍历目录、<format> 拼格式串、std::generator 逐次产出、ifstream / ofstream 读写文件。编译期计算会在那里再次出现——格式串检查、路径常量、生成器的惰性状态，都需要区分“编译期确定”与“运行期变化”。

小结这一节要带走的四件事
  • constexpr 函数既能在编译期求值，也能在运行期调用；consteval 只接受常量实参，必须立即求值。
  • static_assert 在编译期检查条件，条件不成立就编译失败；它检查的是当前目标平台，不是“所有平台都成立”。
  • if constexpr 在模板中只实例化命中的分支，让不同类型共用一份模板；非模板环境仍会检查两个分支。
  • 编译期计算不能有未定义行为、不能读运行期输入，并受实现的深度/步数限制；C++20 起可在 constexpr 里用 vector。
自测题自测题（先自己做，再对答案）
  1. constexpr int f(int); 的函数，在什么情况下会在编译期算，什么情况下在运行期算？
  2. consteval 与 constexpr 的核心区别是什么？运行期实参传给 consteval 会怎样？
  3. static_assert(sizeof(int) == 4) 在什么情况下会失败？这说明了 static_assert 检查的是什么？
  4. if constexpr 在模板里解决了什么问题？在非模板函数里，丢弃分支还会被检查吗？
  5. 为什么 constexpr 函数里不能有未定义行为？C++20 起 constexpr 里能用 vector 吗？
注自测答案
  1. 实参是常量表达式、且处于需要常量求值的上下文（如 constexpr 变量初始化、static_assert、模板实参）时，编译器在编译期算；实参是运行期变量或处于普通运行期调用时，在运行期算。
  2. constexpr 允许编译期也允许运行期；consteval 必须在编译期求值。运行期实参传给 consteval 会编译失败，诊断指出“不是常量表达式”。
  3. 在 int 不是 4 字节的平台上会失败；它检查的是当前编译目标的事实，不是标准对所有平台的保证。所以写这种断言时要清楚它绑定了平台。
  4. 它让模板只实例化与类型匹配的分支，避免其他分支对当前类型不合法而报错；在非模板函数里，丢弃分支仍然会被完整检查，不能当作 #if 使用。
  5. 常量求值要求每一步都有确定结果，未定义行为会让表达式不再是常量表达式，编译器必须诊断；C++20 起可以在 constexpr 函数里使用 std::vector，只要求值结束时释放所有分配。
