一个 .cpp 能跑，不代表工程能维护。真实项目由多个翻译单元组成：头文件放接口，源文件放实现，构建脚本把它们编译、链接成一个程序。多文件带来的第一个硬规则是 ODR（单一定义规则）：同一个函数或变量，在整个程序里只能有一个定义；头文件被多个 .cpp 包含时，写错位置就会重复定义。

这一单元是 C++ 分册的收尾。先用 multi_file/ 看“声明在头、定义在源”的标准分工，再用 odr_violation/ 看头文件里定义非 inline 函数的后果；然后用 inline_var/、anonymous_ns/、template_header/ 处理三个常见边界；最后用 final_app/ 把接口、实现、测试与 build.sh 串成一个可维护的小程序。

学习目标看完这一单元，你应该能
  • 说出翻译单元、声明、定义、链接之间的关系；
  • 解释 ODR 为什么禁止在头文件里定义非 inline 函数，以及链接期会看到什么；
  • 用 include guard（或 #pragma once）保护头文件，知道什么该放头、什么该放源；
  • 用 inline 变量在头文件里定义跨翻译单元共享的变量；
  • 用匿名命名空间给 .cpp 里的辅助函数内部链接，避免符号冲突；
  • 把模板定义放在头文件，理解实例化点为什么需要看到定义；
  • 用一条 g++ 或 build.sh 构建程序与测试，并按审查清单检查一个多文件工程。

20.1 先看工程长什么样

这一单元在 examples/ch09/ 下建六个例子，最后一个 final_app/ 是一个完整的小工程：两个头文件、三个实现文件、一个测试文件、一个构建脚本。前五个例子分别聚焦一个规则，避免把“多文件”一次性塞进一个例子。

第 1 帧的 multi_file/ 是“声明与定义分家”的正面样例，odr_violation/ 是头文件里定义非 inline 函数的反例，inline_var/ 展示跨翻译单元共享的 inline 变量。第 2 帧的 anonymous_ns/ 用匿名命名空间隔离两个 .cpp 里的同名 helper，template_header/ 把模板定义放在头文件里。第 3 帧的 final_app/ 把任务清单的接口、实现、格式化、测试与构建脚本组织成一个可运行的小工程。

20.2 翻译单元：编译器一次看到的东西

预处理之后，一个 .cpp 加上它包含的所有头文件，形成一个翻译单元（translation unit）。编译器一次处理一个翻译单元，生成一个目标文件；链接器再把多个目标文件与库合在一起。头文件本身不参与编译，它只是被 #include 复制进翻译单元；所以头文件里写定义，等于在每个包含它的翻译单元里都写了一遍。

math_ops.h 里只有函数声明，没有函数体；math_ops.cpp 里才有 add / multiply 的定义。main.cpp 包含头文件后，编译器知道“有这两个函数、签名是什么”，但不知道函数体在哪；链接器把 main.o 与 math_ops.o 接起来，才找到定义。声明让编译通过，定义让链接通过；缺声明是编译错误，缺定义是链接错误。

report.h 与 report.cpp 重复同样的分工：std::string describe(int) 的声明在头文件，定义在 report.cpp。一个头文件对应一组相关的接口，不要把所有声明塞进一个巨大的 all.h；头文件越具体，依赖越清楚，改一个模块时重编译的范围越小。

第 1 帧的 main.o 只有“引用”，没有定义；第 2 帧的实现文件提供定义；第 3 帧的链接器把引用与定义配对。这就是多文件工程的最小模型：编译按翻译单元并行，链接按符号全局配对。

20.3 ODR：同一个定义只能出现一次

ODR 有两条最常用的规则：一个翻译单元里，任何可定义实体只能有一个定义；整个程序里，非 inline、非模板的函数或变量只能有一个定义。头文件里的普通函数定义被两个 .cpp 包含，就同时踩中两条：每个翻译单元里有一份，整个程序里有多份。

这个头文件既没有 include guard，函数也不是 inline；main.cpp 包含它两次，同一个翻译单元里出现两份 twice 的定义，编译器直接报 redefinition of 'int twice(int)'。这是 ODR 在同一翻译单元里的表现：不需要链接，编译期就能抓住。

如果没有“包含两次”，而是让两个 .cpp 各包含一次，编译都能过；链接器会发现两个目标文件都导出 twice，报 multiple definition of 'twice(int)'。链接器能抓到的只是“同名符号重复”；如果两个定义分别放在不同翻译单元、又因为 inline 或模板被允许重复，链接器不一定能判断它们是否“相同”，这就是 ODR 违反常常“无诊断”的原因。

标准原文标准原文：ODR 的两条硬规则

No translation unit shall contain more than one definition of any definable item.

For any definable item D with definitions in multiple translation units, if D is a non-inline non-templated function or variable … the program is ill-formed; a diagnostic is required only if the definable item is attached to a named module and a prior definition is reachable at the point where a later definition occurs.

大意：一个翻译单元里，任何可定义实体只能有一个定义；如果一个非 inline、非模板的函数或变量在多个翻译单元里都有定义，程序是病态的（ill-formed）。标准只在特定模块场景要求诊断，普通多文件工程的重复定义常常由链接器发现。

出处：N4950 §6.3「One-definition rule」（[basic.def.odr]）第 2 段与第 14 段。

“ill-formed, no diagnostic required”不是“可以随便写”，而是“程序行为没有保证，编译器/链接器可以不报错”。ODR 违反是未定义行为的一种：可能链接失败，可能链接成功但调用到其中一个定义，也可能在不同优化级别下表现不同。工程上不能依赖“本机没报错”来判断合规。

修复方式很直接：头文件只放声明；函数定义移到 .cpp；如果确实要在头文件里定义（模板、inline 函数、constexpr 函数），就加 inline 或确保它是模板。“能在头文件里定义”的前提是允许重复定义，并且每份定义完全一致；普通函数不满足这个前提。

20.4 头文件卫生：guard、放什么、不放什么

头文件的第一道防线是 include guard：#ifndef / #define / #endif 包住整个文件，保证同一个翻译单元里只展开一次。#pragma once 更短，主流编译器都支持，但它不是标准；跨编译器、跨工具链的工程优先用标准 guard，或者两者都用（guard 为主，#pragma once 作为优化）。

头文件里应该放：

  • 函数、类的声明；
  • 类定义、枚举、类型别名、constexpr / inline 函数与变量；
  • 模板定义（实例化点需要看到）；
  • 必要的 #include，且尽量用前向声明减少依赖。

头文件里不应该放：

  • 普通函数的定义（除非 inline / constexpr / 模板）；
  • 普通变量的定义（除非 inline / constexpr）；
  • using namespace（会污染所有包含者的命名空间）；
  • 实现细节、平台相关的宏、内部 helper（放 .cpp 的匿名命名空间）。

“头文件是接口，源文件是实现”：接口要稳定、最小、可读；实现可以改，只要接口不变，调用方就不需要重编译（理想情况下）。这也是为什么 math_ops.h 只写两行声明，而把函数体放进 math_ops.cpp。

20.5 inline 变量：头文件里的共享变量

C++17 起，变量也能声明为 inline。inline 变量允许在多个翻译单元里出现相同定义，链接器把它们合并成一个实体；取地址在哪个翻译单元都得到同一个地址。这让“头文件里定义一个全局配置/计数器”变得合法，不必再写 extern 声明 + 一个 .cpp 定义。

main.cpp 里 ++shared_counter 把它从 0 加到 1；bump_in_module() 在另一个翻译单元里再加一次，返回 2；&shared_counter 在 main.cpp 与 inline_var.cpp 里取到的地址相同，所以 same=1。这不是“两个同名变量碰巧值一样”，而是链接器把它们合并成了同一个实体；inline 变量的地址一致性是标准要求。

inline 变量与 static 变量的区别：static 全局变量在每个翻译单元里各有一份（内部链接），地址不同、值也各自独立；inline 变量全程序一份。需要“全局唯一”用 inline，需要“每个文件私有”用匿名命名空间或 static；不要用 inline 表达“每个文件一份”，那是反的。

20.6 匿名命名空间：只在本翻译单元可见

.cpp 里的辅助函数如果不需要被别的翻译单元看到，放进匿名命名空间：namespace { ... }。匿名命名空间里的名字具有内部链接，每个翻译单元各有一份，不会与别的 .cpp 里的同名函数冲突。它比 static 函数更现代、对类型也适用（static 只能用于函数和变量，不能用于类定义）。

第二个翻译单元 second.cpp 里也有一个 helper()，返回 2；两个 helper 在各自的匿名命名空间里，链接器看到的是两个内部链接符号，不会冲突。main 调用 first_value() 与 second_value()，分别得到 1 和 2：

匿名命名空间是“文件私有的工具箱”：实现细节放进去，头文件只暴露必要的接口。这样改 helper 不会影响别的翻译单元，也不会制造符号冲突；代价是每个翻译单元各有一份代码，不能跨文件复用（需要复用时才放进头文件/公共模块）。

匿名命名空间与 static 的另一个差别是链接性规则的细节：匿名命名空间的名字具有内部链接，且它的成员可以被模板参数等使用；static 全局函数在 C++ 里仍可用，但现代代码更倾向匿名命名空间。两者都不要放在头文件里：头文件里的匿名命名空间会给每个包含者各生成一份，容易造成“看起来共享、实际各一份”的误解。

20.7 模板与头文件：实例化点要看到定义

模板不是普通函数：编译器在实例化点才生成具体代码，而实例化点需要看到模板定义。如果定义藏在 .cpp 里，调用方只看到声明，编译器无法生成 twice<int>，链接器就报 undefined reference。所以模板定义通常放头文件，除非你显式实例化并在头文件里 extern template 控制。

twice_int 与 twice_text 是两个普通函数，定义在 template_header.cpp 里；它们各自调用 twice<int> 与 twice<std::string>，实例化发生在那个 .cpp 里，而模板定义在头文件里可见。“模板定义放头文件”不是说所有实例都必须在使用点生成；你也可以在一个 .cpp 里显式实例化，让链接器找到，但那时要确保实例化覆盖所有调用类型。

extern template 可以抑制某些翻译单元的重复实例化：在头文件里写 extern template class Box<int>;，在一个 .cpp 里写 template class Box<int>;，其他翻译单元就不再生成。这是编译期/链接期的优化手段，不改变 ODR 要求；模板的每份实例化仍然必须一致。

20.8 构建：从一条命令到 build.sh

本机没有 make/cmake，构建就是一个 g++ 命令：-std=c++23、警告、-Iinclude、所有 .cpp、-o 输出。漏一个 .cpp 就是 undefined reference；多一个重复定义就是 multiple definition；链接命令里的源文件清单，就是工程的“参与编译的翻译单元”清单。

final_app/build.sh 把两条命令固定下来：一条构建程序，一条构建测试。两条都带 -Iinclude，都列全 src/task.cpp 与 src/report.cpp；测试多一个 test/tests.cpp，程序多一个 src/main.cpp。

set -euo pipefail 让脚本在任一命令失败时立刻退出，不会出现“编译失败但旧的可执行文件还在跑”的假成功。先编译再运行是构建脚本的基本顺序；更完整的脚本还会清理旧产物、区分 debug/release、把目标文件放到 build/，本单元只保留最小可用版本。

第 1 帧的接口只暴露“能做什么”，第 2 帧的实现负责“怎么做”，第 3 帧的测试只依赖接口、不依赖实现细节。测试通过接口验证行为，所以实现可以替换，只要接口与行为不变；build.sh 把“编译哪些文件”固定下来，避免手工命令漏文件。

20.9 final_app：一个能维护的小程序

final_app 是一个任务清单：TaskList 保存任务，add 追加，complete(id) 标记完成，render 输出清单与统计。接口在 task.h / report.h，实现在 task.cpp / report.cpp，main.cpp 只做驱动，tests.cpp 只做行为断言。

add 自动分配递增 id，complete(2) 把第二个任务标记完成，render 用 std::format 逐行拼出 [x] / [ ]，最后一行是完成数/总数。接口与实现分开后，main 只关心“加任务、完成任务、打印”，不关心 TaskList 内部用 vector 还是别的容器；以后换成 std::list 或数据库，只要接口不变，main 不用改。

测试只调用接口，检查三件事：初始大小为 3、complete(2) 成功且完成数为 1、对不存在的 id 返回 false。任何一条不成立，ok 变假，程序以非零退出：

ok = ok && ... 的写法保证前面的检查失败后不再执行后面的调用；如果想看每一步的结果，可以拆成多个 if 或输出中间值。测试的返回值很重要：return ok ? 0 : 1 让 CI 或 build.sh 能通过退出码判断失败，而不是靠人眼看输出。build.sh 里用 set -e，测试失败会让脚本以非零退出，构建就“红”了。

20.10 收尾：审查清单

把这一册的内容压成一份可执行的清单，提交前逐条过一遍：

  • 接口：头文件只有声明、类型、模板与 inline 定义；没有普通函数/变量的定义；有 include guard。
  • 实现：.cpp 里的 helper 放匿名命名空间；不把实现细节泄漏到头文件。
  • 链接：构建脚本列全所有 .cpp；新增文件后同步更新脚本；没有重复定义的全局符号。
  • 资源：裸 new / delete 是否被 RAII 取代；容器与智能指针是否表达了所有权；析构是否 noexcept 安全。
  • 错误：异常路径是否清理资源；是否区分“没有值”与“错误”；noexcept 是否诚实。
  • 模板：定义是否对实例化点可见；是否用 static_assert / concepts 给出清楚约束；是否避免无界递归。
  • 测试：是否只依赖接口；失败是否返回非零；是否覆盖边界（空容器、重复操作、不存在的 id）。
  • 构建：警告是否清零；-Wall -Wextra -Wpedantic 下是否干净；Debug/Release 是否有明确区分。

这份清单不是形式：每一条都对应前面单元里的一个真实坑。多文件工程的质量，往往不取决于你写了多少高级特性，而取决于接口是否清楚、资源是否有着落、失败是否被处理、构建是否可重复。

清单适合在提交前跑一遍，也适合在重构前跑一遍：先确认接口与所有权，再动实现；先让测试变红，再让它变绿。代码审查时，清单上的每一条都能对应到一个具体问题，比“看起来没问题”更可靠。把这份清单放进仓库的 CONTRIBUTING.md，下次换人维护时，他不必重新摸索这套工程约定；约定写下来，才算真正交付。如果只能记住三件事：头文件只放声明，所有权写进类型，失败必须被检查。先照着做一遍，再把它改成适合你们团队的版本；这份清单来自本册二十个单元的真实返工记录，不是从别处抄来的通用模板。

20.11 本机实测：七个读数

实验记录本机实测：多文件、ODR 与综合程序

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • multi_file 的 stdout 是 sum=7 product=12 text=result:19：三个 .cpp 链接后接口可用；
  • odr_violation 编译失败，诊断是 redefinition of 'int twice(int)'：头文件里的非 inline 定义在同一翻译单元里重复；
  • inline_var 的 stdout 是 same=1 counter=2：两个翻译单元取到同一个 inline 变量地址；
  • anonymous_ns 的 stdout 是 first=1 second=2：两个 .cpp 的同名 helper 互不冲突；
  • template_header 的 stdout 是 int=8 text=hihi：模板定义在头文件，两个包装函数分别实例化；
  • final_app 的 stdout 是 tasks=3 done=1 / 三行清单 / summary=1/3：综合程序按接口工作；
  • final_app_test 的 stdout 是 PASS size=3 done=1，退出码 0：测试通过。

20.12 下一站：算法与项目

C++ 分册到这里结束。你已经走过工具链、对象生命周期、继承与多态、模板、容器与算法、现代语法、错误处理、编译期、系统 I/O 与多文件工程；接下来是算法分册与项目实战分册。算法分册会用这些容器与迭代器做数据结构与算法分析；项目实战分册会把 final_app 这种“接口 + 实现 + 测试 + 构建”的结构扩展成真正的多模块项目。

下一步不是再学一个新语法，而是把已经会的东西组合起来：先读现有代码，再改一个小功能，再写一个测试，再让它通过。能维护，才算真的会。

小结这一节要带走的五件事
  • 翻译单元 = 一个 .cpp 加它包含的头文件；编译按翻译单元，链接按符号全局配对。
  • ODR 要求同一翻译单元内一个定义、全程序非 inline 非模板实体一个定义；头文件只放声明、模板与 inline 定义。
  • inline 变量跨翻译单元是同一实体，地址一致；匿名命名空间给 .cpp 内部链接，避免同名冲突。
  • 模板定义必须对实例化点可见，通常放头文件；extern template 可控制实例化位置。
  • 多文件工程用构建脚本列全源文件，测试只依赖接口并通过退出码报告结果。
自测题自测题（先自己做，再对答案）
  1. 声明与定义的区别是什么？为什么“编译通过”不代表“链接通过”？
  2. 为什么头文件里不能定义普通函数？inline 函数和模板为什么可以？
  3. inline 变量与 static 全局变量在多个翻译单元里的行为有什么不同？
  4. 匿名命名空间解决了什么问题？为什么不能把它放进头文件？
  5. final_app 的测试为什么只 #include "task.h"，而不包含 task.cpp？build.sh 为什么要把测试源文件也列进编译命令？
注自测答案
  1. 声明告诉编译器“名字与类型”，定义提供实体（函数体/存储）。编译只需要声明；链接需要定义，缺定义会 undefined reference。
  2. 头文件会被多个翻译单元包含，普通函数定义会在每个翻译单元各出现一次，违反 ODR；inline 函数与模板允许重复定义，但要求每份定义一致，链接器会合并。
  3. inline 变量全程序一个实体，各翻译单元地址相同；static 全局变量每个翻译单元各一份，地址与值都独立。
  4. 它给 .cpp 内的 helper 内部链接，避免与其他翻译单元的同名符号冲突；放进头文件会让每个包含者各生成一份，容易造成“看似共享、实际各一份”的误解。
  5. 测试只依赖接口，包含 task.h 就能声明 TaskList；task.cpp 是定义，必须由链接器与测试目标文件一起链接，所以 build.sh 要把它列进源文件清单。
