上一单元的异常适合“函数没法继续”的失败。但有些情况不是异常：查字典可能没有这个键，解析可能失败，一个格子可能暂时没有值。这些“没有”是正常结果，不该用异常来表达，也不该用 -1、空字符串、nullptr 这类哨兵值硬凑。C++17 的 std::optional、std::variant 与 C++23 的 std::expected 把“可能没有”“几种之一”“值或错误”写进类型，让编译器提醒调用者处理。

这一单元用六个例子拆开这三种类型：先看 optional 怎么表示“没有值”，再用一个编译错误说明它不能直接当 int 用；然后看 variant 的 index() 与 std::visit，用 overloaded 把多个分支写成一组重载；最后用 expected 表示“值或错误”，并用 and_then 把多步操作串起来。

学习目标看完这一单元，你应该能
  • 用 optional<T> 表示“可能有值、可能没有”，并正确选择 has_value / value_or / *；
  • 说出 optional 与“错误”的边界，不把错误信息塞进一个空 optional；
  • 用 variant 存“几种类型之一”，读 index()，用 std::visit 分派；
  • 用 overloaded 辅助器把多个 lambda 合成一个访问器，并知道漏掉分支会怎样；
  • 用 expected<T, E> 表示“值或错误”，用 and_then / transform 串联；
  • 根据“没有值 / 出错 / 多选一”选择正确的类型。

17.1 先看工程长什么样

这一单元在 examples/ch07/ 下新增六个例子。optional_basic/、variant_visit/、expected_basic/ 各展示一种类型的最小用法；optional_misuse/ 是编译期反例；variant_overload/ 展示 overloaded 访问器；expected_chain/ 展示多步错误传播。结构仍是“两个 .cpp + 一个 .h”。

第 1 帧的 optional_basic/ 用查分数演示“有/没有”，optional_misuse/ 直接把 optional<int> 赋给 int，让编译器拦下；variant_visit/ 用 index() 和 visit 处理三种类型。第 2 帧的 variant_overload/ 用 overloaded 写分支，expected_basic/ 用 expected<int, string> 表示成功或错误。第 3 帧的 expected_chain/ 把解析、校验、计算串成一条链，错误自动短路。

17.2 optional：有值或没有值

std::optional<T> 要么包含一个 T，要么为空。它自己管理内部值的构造与析构，不需要堆分配；标准明确说，实现不得用动态内存来放这个值。它表达的是“可能没有”，不是“出错了”：没有值本身就是一个正常结果，调用者应该决定“没有”意味着什么。

find_score("Ada") 返回包含 90 的 optional，has_value() 为真，value_or(-1) 返回 90；find_score("Bob") 返回 std::nullopt，has_value() 为假，value_or(-1) 返回备用值 -1。value_or 不会改原对象，它只是“有值就返回，没有就返回你给的默认值”。

访问内部值有几种方式，安全程度不同：

  • has_value() / operator bool：先问有没有；
  • value()：有值就返回，没有就抛 std::bad_optional_access；
  • value_or(default)：没有值时返回默认值；
  • *it / it->：不做检查，空的时候是未定义行为。

value() 比 * 安全，但也会抛异常；如果你的代码路径不允许异常，就先 has_value() 再解引用，或者用 value_or。optional 的 operator* 不检查，是因为它被设计成“你已经知道有值”时的零开销访问；把检查责任交给调用者，代价是调用者必须真的检查。

optional 不能直接存引用：std::optional<T&> 不是标准类型。需要“可能没有的引用”时，用 T*（空指针表示没有）、std::reference_wrapper<T> 的 optional，或者 std::optional<std::reference_wrapper<T>>。这不是标准库的疏忽，而是“引用必须绑定到对象”的语义决定的；引用一旦存在就必须指向某物，无法表示“没有”。需要可空引用时，指针更直接。

optional 也可以参与比较：两个 optional 都有值时比较内部值，空 optional 与有值对象比较时按“空小于有值”的规则；optional<T> == std::nullopt 用来判断空。这些比较规则在泛型代码里很有用，但不要用它们替代 has_value() 的可读性；明确写出“有没有值”比依赖隐式比较更清楚。

C++23 还给 optional 加了 monadic 操作：and_then、transform、or_else，语义与 expected 的对应操作类似——有值时继续，空时跳过。如果你的标准库支持，可以用它们把“有值才处理”的链拉平；不支持就手写 if (opt)，语义一样。不要把 monadic 操作当成“必须用的新风格”，可读性优先。

标准原文标准原文：optional 的存储与状态

An optional object is an object that contains the storage for another object and manages the lifetime of this contained object, if any. The contained object may be initialized after the optional object has been initialized, and may be destroyed before the optional object has been destroyed. The initialization state of the contained object is tracked by the optional object.

大意：optional 对象包含另一对象的存储并管理它的生命周期；内部值可以在 optional 之后初始化、之前销毁，是否初始化由 optional 自己跟踪。

出处：N4950 §22.5.1「In general」（[optional.general]）。

optional 也可以按值返回大对象，但要注意复制/移动成本：return std::optional<Big>{...} 会把 Big 构造进 optional 的存储；如果返回 optional<Big> 的副本，Big 也要复制。C++17 的强制复制消除不覆盖 optional 内部，所以大对象场景要考虑移动或 optional<Big> 的原地构造（emplace）。optional 省掉的是“堆分配 + 空指针”，不是所有复制。

17.3 optional 的边界：别把错误塞进去

optional 只有“有/没有”两种状态，没有地方放错误原因。如果把“解析失败”“文件打不开”“权限不足”都压成一个空 optional，调用者只知道“没有”，不知道“为什么”，也没法决定是重试、提示用户还是换路径。这是 optional 最常见的误用：把“错误”降级成“缺失”。

这个编译错误是好事：std::optional<int> 没有到 int 的隐式转换，编译器不允许你把“可能没有”悄悄当成“一定有”。类型系统在这里替你踩了刹车；如果你用 int 加 -1 当哨兵，编译器什么都不会说，-1 到底是“没有”还是“真实的 -1”只能靠约定。

设计上可以这样分：

  • 只是“可能没有”，调用者不关心原因：用 optional<T>；
  • 没有值就是错误，调用者需要原因：用 expected<T, E>，E 放错误码或错误信息；
  • “没有”与“错误”是两件事，且都要区分：用 variant<None, T, Error> 或自定义结果类型。

不要用 optional<T> 表示“出错了”，除非错误确实不需要原因、也不需要分类。optional 的名字就是“可选的值”，不是“可能失败的结果”；名字会误导维护者，也会让错误处理丢失信息。

17.4 variant：几种类型之一

std::variant<Ts...> 是一个类型安全的联合：它在任意时刻持有 Ts... 中的一个类型的值，或者在没有合适值时进入“无值”状态（valueless_by_exception，只在赋值/构造抛异常时出现）。它记住当前是哪一个类型，index() 返回这个下标，std::get<T> / std::get<I> 取对应值，取错类型会抛 std::bad_variant_access。

Value 是 variant<int, std::string, double>，三个类型按声明顺序对应下标 0、1、2。number.index() 是 0，text.index() 是 1，real.index() 是 2；render 用 std::visit 根据当前类型调用对应的分支。index() 是运行期读数，类型是编译期信息；两者配合，才能既知道“现在是什么”，又让编译器检查分支是否齐全。

variant 的大小通常等于“最大备选类型的大小 + 标签/对齐开销”，具体布局由实现决定。它不会为每个类型都分配一块存储，也不做堆分配；这是它与“基类指针 + 多态”的差别：variant 的值语义、无堆分配，但备选类型在编译期固定，运行期不能增加新类型。

std::visit 把 variant 当前持有的值传给访问器；这里的访问器是泛型 lambda，item 的类型随分支变化。std::decay_t<decltype(item)> 去掉引用与 const，得到 int / std::string / double，再用 if constexpr 在编译期选择分支。if constexpr 不满足条件的分支不会被实例化，所以 std::to_string(item) 不会对 std::string 报错；如果写成普通 if，三个分支都要能编译，std::to_string(std::string) 就会失败。

std::visit 要求访问器对每个备选类型都可调用；漏掉一个类型会编译失败，而不是运行期崩。这是 variant 相对“void + 手写标签”的最大好处*：类型清单在编译期已知，编译器能检查你是否处理了所有情况。泛型 lambda 自动覆盖所有类型；如果你用一组具体重载，就要显式覆盖每个类型（下一节的 overloaded）。

17.5 variant + overloaded：把分支写成重载

泛型 lambda + if constexpr 适合“分支逻辑相似”的场景；如果每个类型要写不同的函数体，用一组重载更清楚。std::visit 需要一个可调用对象，而多个 lambda 不能直接合成一个；overloaded 辅助器用继承把多个 lambda 的 operator() 聚到一起。

overloaded 继承三个 lambda 类型，并用 using Ts::operator()...; 把三个 operator() 都引入作用域；调用时按参数类型重载决议，选出匹配的那一个。这不是运行期查表，是编译期生成一个带三个重载的类；std::visit 仍然按 variant 的当前类型调用。

漏掉一个备选类型时，std::visit 会编译失败，因为访问器对那个类型不可调用。这是好事：新增一个备选类型，所有 visit 点都会被编译器找出来，你不得不处理新情况。如果用的是“整数标签 + switch”，新增类型时很容易漏掉某个 switch，运行期才暴露。

overloaded 的 deduction guide（overloaded(Ts...) -> overloaded<Ts...>;）让 overloaded{lambda1, lambda2} 自动推导出类型；没有它，模板参数无法从构造实参推导。C++20 起聚合类可以有隐式推导指引，但显式写出来兼容性更好、意图也更清楚；这段辅助器在大量 C++17/20 代码里都能见到。

第 1 帧的 optional 不需要堆；第 2 帧的 variant 用标签记录当前类型，存储大小至少能放下最大的备选类型。标签是运行期状态，备选类型清单是编译期信息；两者缺一不可。实际布局（bool 放哪、标签多大、对齐怎么排）由实现决定，标准只规定行为。

variant 有一个特殊状态：valueless_by_exception()。当赋值/构造过程中抛异常，导致原值已销毁、新值没构造成功时，variant 可能进入“无值”状态；此时 index() 返回 variant_npos，visit 会抛 std::bad_variant_access。这是异常安全的边界，不是正常状态；正常情况下不要依赖它，但读代码时要知道它的存在，尤其是对 variant 做赋值/交换的代码。

std::visit 的访问器对所有备选类型必须返回“兼容”的类型；如果不同分支返回 int 与 std::string，返回类型无法统一，编译失败。需要不同分支返回不同类型时，让它们返回 std::variant 或 std::any，或者把公共逻辑抽出来；不要指望 visit 自动做类型擦除。visit 的返回类型由所有分支共同决定，这也是它能在编译期检查分支完整性的原因。

variant 的备选类型不能重复：variant<int, int> 不合法，因为 get<int> 无法区分两个 int。需要“同类型但语义不同”时，用包装结构体（struct Meters { int value; }; 与 struct Seconds { int value; };）或不同的标签类型。类型系统靠“类型不同”区分分支；重复类型会让 visit 与 get 失去意义。

17.6 expected：值或错误

std::expected<T, E> 要么包含一个 T，要么包含一个 unexpected<E>。它和 optional 的区别是：空的时候有错误对象，调用者能读到原因；它和异常的区别是：错误在返回类型里，调用者必须面对，不需要 try / catch，也没有栈展开成本。

parse_positive(5) 返回包含 5 的 expected，has_value() 为真，value() 返回 5；parse_positive(-1) 返回 std::unexpected(std::string("negative"))，has_value() 为假，error() 返回 "negative"。value() 在错误状态下会抛 std::bad_expected_access<E>，所以读值前也要检查；error() 在成功状态下是未定义行为（标准要求先检查）；不确定时先看 has_value()，不要靠“应该不会成功”的假设。

标准原文标准原文：expected 保存值或错误

An expected<T, E> object holds an object of type T or an object of type unexpected<E> and manages the lifetime of the contained objects.

大意：expected<T, E> 持有 T 或 unexpected<E> 之一，并管理内部对象的生命周期。

出处：N4950 §22.8.1「In general」（[expected.general]）。

expected 的错误类型 E 是接口设计的一部分。用 std::error_code 能表达分类与系统错误，用 std::string 能带上下文但每次失败可能分配，用一个小的 enum class 最轻量。不要把 E 设计成“什么都能装”的大对象：expected 的存储要能放下 T 和 E 中较大的那个，错误类型太大，成功路径也要背这块空间；错误类型应当是“可枚举、可比较、可复制”的小对象。

expected<void, E> 用于“成功但没有返回值”的操作，例如 close()、flush()；成功时用 expected<void, E>{}，失败时返回 unexpected。它没有 value() 可读，通常用 has_value() 或直接 if (!result) 判断。这比返回 bool + 输出参数更清楚，因为错误原因在类型里，不会被忽略。

17.7 expected 链：错误自动短路

多步操作如果每步都可能失败，手写 if 嵌套会很深。expected 的 and_then（继续一个返回 expected 的操作）与 transform（对成功值做变换）把链拉平；任何一步返回 unexpected，后面的步骤都跳过，错误原样传下去。

parse_number("8") 得到 8，require_positive 通过，halve 得到 4.0，所以 value=4；parse_number("-3") 解析成功但校验失败，require_positive 返回 unexpected("must be positive")，后面的 halve 不再执行；parse_number("x") 一开始就失败，返回 unexpected("not a number")。and_then 的成功值类型可以变化：parse_number 与 require_positive 都是 expected<int, string>，halve 返回 expected<double, string>，链的最终类型是 expected<double, string>。

and_then 与 transform 的分工：and_then 接一个“返回 expected 的函数”，用于可能失败的一步；transform 接一个“普通函数”，只在成功时变换值，不会引入新错误。or_else 用于错误分支的恢复或转换。这三个是 C++23 的 monadic 操作，让错误处理像流水线；如果编译器/标准库不支持，可以手写 if，语义一样，只是更长。

第 1 帧的“没有”是正常结果；第 2 帧的“错误”需要原因；第 3 帧的“多种形态”不是错误，而是数据本身的可能性。先把问题归到这三类，再选类型，比“先选一个容器再想办法塞”要稳。

17.8 三者怎么选

  • 只关心“有没有值”，不关心原因，缺省值合理：optional<T>；
  • 关心失败原因，调用者需要分支处理，且不想用异常：expected<T, E>；
  • 值本身可以是几种类型之一，每种都是正常情况：variant<Ts...>；
  • 失败是真正的异常、当前层无法处理：抛异常，让上层 catch；
  • 失败极常见、性能敏感、且调用者就在附近处理：错误码或 expected，避免异常开销。

optional 不适合表达错误，expected 不适合表达“多选一”，variant 不适合表达“成功/失败”（虽然可以，但语义不如 expected 直接）。类型选对了，调用者的代码自然清楚；类型选错，后面会靠注释和约定补洞。

还有一种常见混用：用 optional<T> 表示“查不到”，用 expected<T, E> 表示“查到了但处理失败”。把两种失败塞进同一层，调用者就分不清该重试还是该报错；能区分的失败，尽量在类型上区分，这比在错误信息里写一句“可能是没找到”可靠得多。

17.9 本机实测：六个读数

实验记录本机实测：三种类型的真实输出

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • optional_basic 的 stdout 是 has=1 score=90 / has=0 fallback=-1：有值读值，无值走 value_or；
  • optional_misuse 编译失败，诊断是 cannot convert 'std::optional<int>' to 'int' in initialization：类型系统阻止“悄悄当 int 用”；
  • variant_visit 的 stdout 是 index=0 render=int:7 / index=1 render=text:hi / index=2 render=real:2.500000：下标与类型一一对应；
  • variant_overload 的 stdout 是 small-int / large-int / text:hi / real:2.500000：overloaded 按类型选分支；
  • expected_basic 的 stdout 是 ok=1 value=5 / ok=0 message=negative：成功读值，失败读错误；
  • expected_chain 的 stdout 是 ok=1 value=4 / error=must be positive / error=not a number：错误在链上短路。

17.10 下一单元从哪继续

下一单元进入编译期：constexpr 让函数在编译期求值，consteval 强制立即求值，static_assert 把条件变成编译错误，if constexpr 让模板只实例化命中的分支。这一单元的 variant 访问器已经用了 if constexpr；下一单元会把“编译期能做什么、不能做什么”系统讲清楚。

小结这一节要带走的四件事
  • optional<T> 表示“有值或没有”，用 has_value / value_or / * 访问；它不携带错误原因，别拿它当错误类型。
  • variant<Ts...> 是类型安全的联合，index() 给下标，std::visit 分派；漏掉备选类型会编译失败。
  • overloaded 用继承聚合多个 lambda 的 operator()，让 visit 的分支像重载一样书写。
  • expected<T, E> 表示“值或错误”，and_then / transform 把多步操作串成短路链；按“没有值 / 出错 / 多选一”选类型。

  1. value() 抛 std::bad_optional_access；value_or(-1) 返回 -1；*it 是未定义行为（空 optional 不做检查）。
  2. optional 没有到 T 的隐式转换，编译器不允许把“可能为空”当成“一定有值”；好处是强制调用者先检查，避免空值被静默使用。
  3. index() 返回当前备选类型在模板参数列表中的下标（从 0 开始）；访问器漏掉一个类型会编译失败，因为 visit 要求对每个备选类型都可调用。
  4. 它把多个 lambda 的 operator() 聚合到一个类里，让 visit 用一个对象接收多个分支；没有它也可以用泛型 lambda + if constexpr，或手写一个带多个 operator() 的类。
  5. optional 表示“可能没有值”（查字典没找到）；expected 表示“值或错误”（解析失败并带原因）；variant 表示“几种正常类型之一”（一个格子可以是数字、文本或实数）。
