上一单元证明了多态“能用”：基类指针调用虚函数，运行期选到派生实现。这一单元要回答“值不值得用”。虚函数不是免费的：对象里可能多一个虚表指针，调用要经过一次间接跳转，接口类的析构必须是虚的，dynamic_cast 是运行期检查而不是零成本转换。更重要的是设计代价：继承表达“是一种”，组合表达“有一个”；用继承复用实现，往往会在第二个需求到来时崩掉。

这一单元把“代价”拆成三类：对象大小、调用方式、设计耦合。对象大小用 sizeof 实测；调用方式只讲可观察的机制，不承诺性能数字；设计耦合用组合、variant 与 final 三个例子对照。

学习目标看完这一单元，你应该能
  • 写出一个只含纯虚函数与虚析构的接口类，并说清调用者为什么只依赖接口；
  • 用 sizeof 读数说明虚函数给对象增加了什么，以及这个数字为什么不是标准规定；
  • 说出虚调用与直接调用的机制差别，不把“有虚函数”当成“一定慢”；
  • 用 dynamic_cast 做安全的向下转换，并区分指针失败返回空、引用失败抛 bad_cast；
  • 判断一个复用场景该用继承还是组合，并说出 final 与 variant 各自解决什么问题。

7.1 先看工程长什么样

这一单元在 examples/ch03/ 下再加六个多文件小工程。接口类、对象大小、组合、转换、variant、final 各占一个目录；第 2 章起的硬规定③继续生效。

第 1 帧的 interface_shape/ 只有纯虚函数与虚析构，展示“接口类”最小形态；vtable_size/ 用四个空/非空、有/无虚函数的类型量 sizeof。第 2 帧的 composition_over_inheritance/ 把 Engine 作为 Car 的成员，而不是让 Car 继承 Engine；cast_cost/ 用 dynamic_cast 做指针与引用的向下转换。第 3 帧的 variant_dispatch/ 用 std::variant + std::visit 实现值语义的分派；final_demo/ 让一个 final 基类被继承，编译失败。

7.2 接口类：只依赖“能做什么”

Shape 没有数据成员、没有普通函数，只有三个虚函数：析构、name、area。调用者只写 shape->name() / shape->area()，不 include Circle 或 Square 的头文件；要加一种新形状，只要实现 Shape 并在工厂里注册，调用方不用改。这就是“依赖抽象”的实际收益：变化被关在实现文件里，调用方只面对稳定接口。

输出里的 drop circle 在 drop square 之前，是因为 vector 析构元素时按逆序进行：先构造的 Circle 后析构。done 在花括号结束后打印，说明 shapes 已经整体销毁；Shape 的虚析构让 unique_ptr<Shape> 能正确调用派生类析构，再调用 ~Shape()。

接口类的设计要点：析构必须是虚的（否则通过接口指针删除派生对象是未定义行为）；接口里尽量只放纯虚函数，不要把数据成员塞进基类；如果某个操作有默认实现，可以放在基类，但要想清楚它是否依赖派生类的细节。接口类不是“越纯越好”：一个没有任何数据的基类，通常意味着它只表达契约，不表达状态。

7.3 对象大小：虚函数增加了什么

Empty 是 1 而不是 0：标准要求同类型的两个不同对象有不同地址，空类必须至少占 1 字节。WithInt 是 4，正好一个 int。WithVirtual 是 8，多出来的 8 字节是一个指向虚表的指针（本机 64 位）；WithVirtualInt 是 16，因为虚表指针 8 字节 + int 4 字节，再按 8 字节对齐补齐到 16。

这些数字是“本机实测”，不是 C++ 标准规定。 标准只要求虚函数能动态绑定，不规定用虚表、也不规定指针大小；换一个 ABI、换一个编译器，布局可能不同。你能带走的结论是：多态对象通常要比非多态对象多存一份“怎么找到正确函数”的信息；具体多大，用 sizeof 量，不要背数字。

第 1 帧的 WithInt 只有数据；第 2 帧的 WithVirtualInt 在最前面放了 vptr，对象因此从 4 字节变成 16 字节（含对齐）。虚表本身是每个多态类一份，不是每个对象一份；对象里存的是“指向虚表”的指针。

7.4 虚调用的代价：一次间接跳转

虚调用与直接调用的差别在“地址从哪来”：直接调用在编译期就确定函数地址；虚调用要先读对象的 vptr，再从虚表里取对应槽位的地址，最后跳过去。本单元不承诺“虚调用比直接调用慢多少”的具体数字——那取决于 CPU、缓存、分支预测、优化档；我们只确认机制上的差别：多了一次内存读取与一次间接跳转。

这不意味着“有虚函数就一定慢”。如果一个循环里对同一个对象反复调用虚函数，分支预测会很准；如果虚函数体本身很重（例如做一次 I/O 或复杂计算），那点间接开销可以忽略。反过来，如果虚函数只是返回一个字段，而且被调用几百万次，间接开销就可能显现。优化前先量，别凭“虚函数慢”的传言改设计。

更值得警惕的是设计代价：虚函数把“调用哪份实现”推迟到运行期，编译器就不能内联、不能做跨过程的常量传播；接口越抽象，编译器能看到的细节越少。多态买的是“调用方与实现解耦”，付的是“运行期决策 + 优化空间”；这笔交易是否划算，取决于变化频率与性能预算。

编译器并非永远无法优化虚调用：如果对象类型在调用点确定（局部对象、final 类、去虚化分析），它可以把虚调用改成直接调用甚至内联。链接期优化（LTO）与基于性能分析的优化（PGO）也能提供更多类型信息。但这些是“可能发生”的优化，不是标准保证；写代码时不能假设编译器一定去虚化，性能敏感路径要靠测量确认。

接口类的设计也有成本边界：接口只放纯虚函数与虚析构，不放数据成员；数据放实现类，接口保持薄。这样每个实现对象只多一个 vptr，不会因为接口里的字段而膨胀。接口越“胖”，实现越难替换；把无关的便利函数塞进接口，会逼所有实现都去实现它们，反而降低多态的收益。

dynamic_cast 是另一种多态成本：它在运行期检查类型，失败时对指针返回 nullptr、对引用抛 std::bad_cast。它适合“确实需要按具体类型分支”的边界（例如插件加载、消息分发），不适合在热循环里做类型判断；能用虚函数表达的行为，不要用 dynamic_cast + if 模拟，那会把运行期类型检查散布到调用方，破坏封装，也让新增类型时更容易漏改；新增一个派生类，所有 if 分支都要跟着改。

第 1 帧的箭头从业务代码指向接口，业务代码不依赖任何具体形状；第 2 帧新增实现时，箭头从实现指向接口，业务代码不动。依赖方向决定改动范围：如果业务代码直接依赖 Circle，新增 Square 就要改业务代码；依赖接口，新增实现只改工厂/注册处。

7.5 组合优于继承：Car 有一个 Engine

Car 没有继承 Engine，而是持有一个 Engine engine_ 成员；drive() 调用 engine_.start() 与 engine_.stop()。这就是组合：“汽车有一个引擎”，不是“汽车是一个引擎”。 组合的好处是接口可控：Car 只暴露 drive()，Engine 的 start/stop 不必成为 Car 的公有接口；如果 Car 继承 Engine，Car 就会自动获得 start/stop，外部可以把汽车当引擎启动，语义上说不通。

继承复用的陷阱在于“为了省代码而继承”：class Stack : public std::vector<int> 看起来省了实现，但 std::vector 的所有操作都成了 Stack 的公有接口，用户可以下标越界、可以在中间插入、可以删除任意元素，栈的不变量被破坏。继承会把基类的接口与实现一起带进来；组合只带走你想要的那部分能力。 判断标准：派生类能不能在所有使用基类的地方替换基类，并且行为仍然正确？不能，就不要用 public 继承。

组合也有代价：要多写一层转发函数（Car::drive 调用 engine_.start），对象里多一个成员。但与“继承带来的接口污染”相比，这点成本通常更可控。工程上的默认策略是：先组合，确实需要“is-a”且需要运行期多态时，再继承。

大白话大白话：继承是“是”，组合是“有”

“苹果是一种水果”用继承；“汽车有一个引擎”用组合。你不会说“汽车是一种引擎”，所以不该让 Car 继承 Engine。继承会把父类的东西全继承下来，像把整套工具箱都搬进你家；组合只拿你需要的那把螺丝刀。需要“换引擎”时，组合还能把 Engine 换成接口/模板参数，继承则把类型关系焊死了。

7.6 dynamic_cast：运行期检查，失败有两条路

dynamic_cast<Beta*>(base) 在 base 实际指向 Beta 时返回 Beta*；在 other 实际指向 Alpha 时返回 nullptr，所以 ptr_null=yes。引用版本没有“空引用”可返回，转换失败时抛 std::bad_cast，被 catch 接住，输出 ref_caught=bad_cast。指针版适合“可能失败、失败后走另一条路”；引用版适合“失败就是异常，调用者必须处理”。

dynamic_cast 的前提是源类型必须是多态类型（至少有一个虚函数），因为它要读运行期类型信息；它也不能转走 const，不能做非公有/歧义基类的转换。它的成本是一次运行期检查，通常比 static_cast 高；不要用 dynamic_cast 做“类型 switch”：如果代码里排着一串 if (dynamic_cast<A*>(p)) ... else if (dynamic_cast<B*>(p)) ...，说明基类接口可能没设计好，或者应该用 variant / 访问者模式。

标准原文标准原文：dynamic_cast 失败怎么处理

If T is a pointer type, … The value of a failed cast to pointer type is the null pointer value of the required result type. A failed cast to reference type throws an exception of a type that would match a handler of type std::bad_cast.

大意：dynamic_cast 转指针失败时返回空指针；转引用失败时抛出 std::bad_cast，可以按这个类型捕获。

出处：N4950 §7.6.1.7「Dynamic cast」（[expr.dynamic.cast]）第 9 段。

陷阱用 `dynamic_cast` 串成类型 switch

你会看到：基类接口只有一个模糊的 process()，派生类各自需要不同参数；为了拿到具体类型，代码里排出一串 dynamic_cast，每加一种类型就要改这串 if。你会误判成“多态不够灵活，还是得知道具体类型”。真相是：这串转换把“类型集合”从编译期搬到了运行期，新增类型必须改所有分派点。要么把差异提炼成基类虚函数（让实现自己处理），要么用 variant + visit 把“类型集合”固定在一个地方，让编译器检查漏分支。

7.7 variant：值语义的类型集合

std::variant<Circle, Square> 是一个“安全的联合体”：它要么存 Circle，要么存 Square，同一时刻只有一个活动成员。std::visit 按当前活动类型调用访问者，不需要虚表，也不需要堆分配。

index=0 表示当前存的是 variant 的第一个替代类型 Circle，index=1 表示第二个 Square。std::visit 用泛型 lambda 接受任意替代类型，编译器为每种类型生成一份调用；如果新增一种类型，泛型 lambda 自动适配，但如果访问者里有 if constexpr 分支漏了类型，编译器在实例化时会报错。variant 把“类型集合”写进了类型系统，新增类型必须改 variant 的模板参数，编译器会检查所有 visit 是否覆盖。

variant 与继承的取舍：类型集合封闭、以值为主、希望避免堆分配时，用 variant；类型集合开放、需要运行期插件式扩展、对象可能很大且共享时，用继承 + 接口。variant 也可能“值过大”（存储最大替代类型的大小），并且 visit 的返回类型必须对所有替代类型一致；这些是它的代价。第 17 单元会再展开 variant 与 optional / expected。

7.8 final：明确关掉继承与重写

final 写在类名后面表示“这个类不能被继承”；写在虚函数后面表示“这个函数不能在派生类里重写”。它的作用不是“优化”，而是表达设计意图并让编译器执行：这个类不准备做基类，或者这个虚函数已经是最终实现。编译器看到 final 后，可以在某些情况下把虚调用去虚化（devirtualization），但那是优化结果，不是 final 的语义保证；不要把 final 当成性能开关，把它当成“此处禁止扩展”的契约。

final 与接口类不矛盾：接口类本身通常不标 final（它就是要被实现），但接口里的某个具体实现类可以标 final，防止别人再从它派生。一个类标了 final 之后，它的析构函数是否虚就不再影响“通过基类指针删除”的安全性——因为它不能被继承，也就不存在派生对象；但作为多态基类时，虚析构仍然必要。去虚化是否发生取决于编译器与优化选项，代码不能依赖它。

小结这一节要带走的五件事
  • 接口类只暴露纯虚函数与虚析构；调用方依赖接口，新增实现不改调用方。
  • 多态对象通常多存一个虚表指针；sizeof 的读数是本机事实，不是标准规定。
  • 虚调用多一次间接跳转，但不承诺具体性能差异；优化前先量。
  • dynamic_cast 转指针失败返回空，转引用失败抛 std::bad_cast；不要用它串类型 switch。
  • 组合表达“有一个”，继承表达“是一种”；类型集合封闭时 variant 可替代运行期多态，final 用于明确禁止扩展。
自测题自测题（先自己做，再对答案）
  1. 一个只含纯虚函数与虚析构的接口类，为什么析构函数必须是虚的？
  2. 本机 sizeof(Empty)=1、sizeof(WithVirtual)=8、sizeof(WithVirtualInt)=16，这些数字分别说明什么？哪些是标准规定？
  3. Car 持有 Engine 成员与 Car 继承 Engine，在使用上有什么本质差别？
  4. dynamic_cast<Beta*>(p) 与 dynamic_cast<Beta&>(*p) 在失败时分别怎样表现？为什么？
  5. variant 与继承各自适合什么样的“类型集合”？新增一种形状时，两者各要改哪里？
注自测答案
  1. 调用者可能通过 Shape* / unique_ptr<Shape> 删除派生对象；如果析构不是虚的，只会执行基类析构，派生部分不释放，且这是未定义行为。
  2. 空类至少占 1 字节；有虚函数的对象多一个虚表指针（本机 8 字节）；再加一个 int 后按 8 字节对齐到 16。1 字节是标准对“不同对象不同地址”的要求，8/16 是本机 ABI 的布局，不是标准规定。
  3. 继承会让 Car 自动获得 Engine 的公有接口，外部可以把汽车当引擎启动；组合只暴露 Car 想暴露的接口，Engine 可以替换/封装，语义更清楚。
  4. 指针版失败返回 nullptr，因为指针可以有空值；引用版失败抛 std::bad_cast，因为引用必须绑定对象，没有“空引用”可返回。
  5. variant 适合封闭、以值为主的类型集合，新增类型要改 variant 的模板参数并检查所有 visit；继承适合开放、运行期扩展的集合，新增类型只需实现接口并在工厂注册，调用方不用改。
