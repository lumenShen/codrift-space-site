前几章的例子大多用 std::vector，但“能装东西”不是容器的全部。vector 连续存储、随机访问快，扩容时要把元素搬到新块，迭代器全部失效；deque 两端插入便宜，中间插入仍要搬；list 每个节点单独分配，插入删除不搬元素，但没有随机访问；std::array 大小固定，不碰堆。选错容器，代码可能“能跑但很慢”，也可能在扩容后悄悄用着失效的迭代器。

这一单元用七个小实验把“容量、失效、两端插入、节点搬移、固定大小、越界检查”六件事钉住。性能数字不承诺，只讲可观察的行为与规则；本机 capacity() 的序列是 libstdc++ 的实现，不是标准规定。

学习目标看完这一单元，你应该能
  • 说出 vector 的 size() / capacity() / reserve() 各表示什么，并解释扩容为什么让指针/迭代器失效；
  • 用 data() 的前后比较证明一次扩容发生了，并说出失效后继续用旧迭代器的后果；
  • 说出 deque 与 list 在两端/中间插入上的差别，以及它们各自的迭代器稳定性；
  • 说出 std::array 与 std::vector 的存储差别，并按访问模式选容器；
  • 解释 push_back 与 emplace_back 的构造次数差异（上一单元已实测）。

11.1 先看工程长什么样

这一单元在 examples/ch05/ 下建七个多文件例子。每个例子仍然是 include/ + 两个 .cpp + 清单；容器类型与辅助函数分开，main.cpp 只做驱动与打印。

第 1 帧的 vector_growth/ 打印每次 push_back 后的 size/capacity；第 2 帧的 vector_invalidate/ 比较扩容前后的 data()，reserve_demo/ 展示预留后指针不变，deque_ends/ 与 list_splice/ 展示两端插入与节点搬移。第 3 帧的 container_choose/ 用 std::array 做固定大小求和，bounds_check/ 故意越界写入，用调试期断言展示“越界不是异常”。

11.2 vector 的容量：size 与 capacity 不是一回事

size() 是“现在有几个元素”，capacity() 是“在不重新分配的前提下最多能放几个”。输出里容量按 1 → 2 → 4 → 8 增长：第 3 个元素放不下 2 个的块，vector 分配一块更大的（这里是 4 个），把旧元素搬过去，再放新元素。这是本机 libstdc++ 的增长策略，不是标准规定的倍增；标准只要求 push_back 的摊还复杂度为常数，具体扩多少由实现决定。

reserve(n) 请求“至少能放 n 个”，但它不改变 size()，只改变 capacity()；如果 n 小于当前容量，什么也不做。resize(n) 才会改变元素个数：变大时补默认值，变小时销毁多余元素。reserve 是给容量提建议，resize 是改元素个数；把两者混用，通常会得到“容量够了但 size 还是 0”的意外。

第 1 帧的 data() 指向旧块；第 2 帧扩容后，元素被搬到新块，data() 返回新地址。旧块被释放，任何还指向旧块的指针、引用、迭代器都失效——即使旧地址上的字节“看起来还在”，解引用也是未定义行为。

11.3 扩容让迭代器失效

starting_values() 返回 {1, 2}，容量正好是 2；push_back(3) 触发扩容，before != values.data() 为真，输出 moved=yes。程序没有解引用 before，而是提前把 first_value 存下来，所以输出仍然正确。这段代码演示的是“扩容发生了”，不是“失效后还能用”；如果你在 push_back 之后写 *before，就是未定义行为。

reserve(8) 之后容量至少是 8；再 push 5 个元素不会超过容量，所以 data() 不变，same=yes。reserve 能在“你知道大概要放多少”时避免多次扩容，代价是可能预留过多内存；如果实际元素远少于预留值，浪费的是容量，不是 size。

标准原文标准原文：扩容使所有指针/引用/迭代器失效

Reallocation invalidates all the references, pointers, and iterators referring to the elements in the sequence, as well as the past-the-end iterator. [Note: If no reallocation happens, they remain valid.]

大意：vector 重新分配时，指向元素的引用、指针、迭代器以及尾后迭代器全部失效；没有重新分配时，它们保持有效。

出处：N4950 §24.3.11.5「Modifiers」（[vector.modifiers]），reserve 的 Remarks。

陷阱扩容后继续用旧迭代器

你会看到：循环里保存了 auto it = v.begin();，中间 v.push_back(...) 可能扩容，后面继续 ++it 或 *it，程序偶尔输出乱码、偶尔崩溃。你会误判成“迭代器语法用错了”。真相是：扩容把元素搬到新块，旧迭代器指向已释放的内存；标准明确说重新分配会让所有迭代器失效。在可能扩容的操作之后，重新取 begin()/end()，或者先用 reserve 把容量定下来；不要保存跨扩容的迭代器。

不同容器的失效规则不一样，不能把 vector 的规则套到所有容器上。vector 与 string：重新分配时全部失效；没有重新分配时，插入/删除点之后的迭代器、指针、引用失效（插入点之前的仍有效）。deque：在两端插入会让所有迭代器失效，但指向元素的引用/指针仍有效；在中间插入/删除会让全部失效。list：插入不使任何迭代器失效，删除只使被删元素的迭代器失效。array：大小固定，没有插入/删除，迭代器在对象生命周期内有效。记住“哪种操作、在哪个位置、让什么失效”，比背一句“vector 会失效”有用得多。

erase 的返回值是“被删元素之后的新迭代器”，这是为了安全地连续删除：it = v.erase(it); 而不是 v.erase(it); ++it;。后者在删除最后一个元素时会让 it 变成 end()，再 ++ 就是未定义行为。删除满足条件的元素，常用 erase-remove 惯用法：v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());；std::remove_if 只是把保留的元素往前挪，并不改变 size()，必须再 erase 才能真正删除。C++20 的 std::erase_if(v, pred) 把这两步封装成一个调用，能用在标准容器上。

std::vector<bool> 是特化版本：它把每个 bool 打包成一位，operator[] 返回的是代理对象，不是 bool&。所以 auto& bit = v[0]; 通常编译失败，bool* p = &v[0]; 也不行；auto bit = v[0] 会得到一个代理值。需要稳定地址或引用时，用 std::vector<char> 或 std::bitset；vector<bool> 省空间，但接口与普通 vector 不完全一样，泛型代码里要特别小心。

capacity() 不会自动缩小：clear() 只销毁元素，不释放存储；shrink_to_fit() 是“请求”缩小，标准不保证一定执行。不要为了“省内存”频繁调用 shrink_to_fit，它可能触发重新分配与搬移；如果确实要释放，考虑用 std::vector<T>(v).swap(v)（C++11 前的惯用法）或接受容量暂时偏大。front() / back() 在空容器上是未定义行为，调用前先检查 empty()；at() 会做边界检查并抛 std::out_of_range，但比 operator[] 多一次检查。

11.4 deque：两端插入，分段存储

deque（双端队列）在两端插入/删除都是摊还常数时间；它通常由多段连续块拼成，所以支持随机访问，但不是“整块连续”，data() 也没有 vector 那样的单一指针。push_front 在头部加元素，已有元素的迭代器通常不失效（标准对 deque 的失效规则比 vector 细：在两端插入不会使指向已有元素的引用/指针/迭代器失效，删除可能使被删元素的迭代器失效）。“通常”不是“永远”：中间插入/删除仍可能让迭代器失效，具体看操作与实现。

deque 适合“头尾都要进出”的队列/滑动窗口；如果你只需要尾部插入 + 随机访问，vector 通常更简单、缓存更友好。deque 的代价是分段存储带来的间接寻址，以及没有 reserve（你无法像 vector 那样一次性预留连续空间）。

deque 的“分段”通常是由一个指针数组（map）指向若干固定大小的块；块满时再分配新块。因此它的迭代器比 vector 迭代器更重（要记录当前块、块内位置、map 位置），随机访问也要多一次间接寻址。这些是实现细节，标准只规定行为与复杂度；但选容器时值得知道：deque 的“两端快”不是免费的，它的常数因子通常比 vector 大。

vector 的扩容策略也值得再看一眼：标准只要求 push_back 摊还常数时间，没规定每次扩多少；libstdc++ 按 2 倍增长，MSVC 的 vector 常见 1.5 倍增长。reserve 的实参是“元素个数”，不是字节数；resize(n) 会真正构造/销毁元素，reserve(n) 只改容量。把 reserve 当成“预分配对象”是常见误解：它只保证存储够，不保证 size() 变化。

11.5 list：节点稳定，但没有随机访问

list 是双向链表，每个元素一个节点；splice 把 second 的节点直接摘下来接到 first 的末尾，不复制元素，second 变成空。splice 的复杂度是常数时间（整条链）或与搬移节点数线性（单个/区间），而且指向被搬移元素的迭代器仍然有效——节点本身没动，只是换了链表。这是 list 相对 vector 的核心优势：插入/删除不搬元素，迭代器稳定。

list 的代价是每个节点多两个指针（前驱/后继），内存开销比 vector 大；节点分散在堆上，遍历时缓存不友好，随机访问是线性时间（没有 operator[]）。list 的 sort() 是成员函数，不是 std::sort：std::sort 要求随机访问迭代器，list 只有双向迭代器；成员 sort 通常用归并排序，能利用节点拼接。不要把 list 当“插入更快的 vector”；大多数场景 vector 的连续存储和缓存局部性更重要，只有明确的“中间插入/删除 + 迭代器稳定”需求才选 list。

forward_list 是单向链表，只支持向前遍历，节点更小，插入/删除接口也更“手工”（insert_after / erase_after）。没有特殊需求时，forward_list 比 list 更少见；先掌握 vector 与 list 的取舍，再看单向链表。

代价是：list 没有随机访问，std::sort 不能用（需要随机访问迭代器），要用 list::sort；每个节点都有前后指针，内存开销比 vector 大；遍历时节点分散，缓存局部性差。只有“频繁在中间插入/删除，并且需要迭代器稳定”时，list 才值得；只是“想少搬元素”而用 list，往往会输给 vector 的连续存储。

11.6 std::array：固定大小，不碰堆

std::array<int, 5> 的大小是编译期常量，对象直接包含 5 个 int，不分配堆内存；size() 是编译期常量，operator[] 不做边界检查（at() 才检查并抛异常）。它适合“元素个数固定、生命周期与对象一致”的场景：查表、固定维度向量、栈上小缓冲。std::vector 适合“元素个数运行期才知道、可能增长”的场景。array 不是“更快的 vector”，它是“带容器接口的 C 数组”；不能 push_back，也不能改变大小。

第 1 帧的 vector / array 适合随机访问；第 2 帧的 deque 适合两端进出；第 3 帧的 list 适合中间插入且要求迭代器稳定。选择顺序通常是：先 vector，不够再考虑 deque，只有明确的节点稳定性/中间插入需求才上 list。

std::array 是聚合类型，可以直接用花括号初始化：std::array<int, 3> a{1, 2, 3};；std::get<0>(a) 与 a[0] 都能访问元素，std::tuple_size_v<decltype(a)> 在编译期给出长度。它没有构造函数、没有 push_back，大小是类型的一部分；std::array<int, 3> 与 std::array<int, 4> 是不同类型，不能互相赋值。需要运行期长度就换 vector，需要固定长度且不想堆分配就用 array；两者不是“谁替代谁”，而是“长度在编译期还是运行期确定”的两种选择。

std::array 作为函数参数时，通常按 const std::array<T, N>& 传递，N 由模板参数或具体类型给出；如果函数想接受任意长度的 array，需要写成模板 template <std::size_t N> void f(const std::array<int, N>&)。array 的长度是类型的一部分，不会像 vector 那样隐式转换成长度可变的容器；需要运行期长度时，用 std::span（C++20）或指针 + 长度，而不是把 array 塞进 vector 再复制。

C++17 的类模板实参推导也能用于 std::array：std::array a{1, 2, 3}; 推导为 std::array<int, 3>。这很方便，但元素类型必须一致；std::array a{1, 2.5}; 推导会失败（int 与 double 冲突），需要显式写 std::array<double, 2>{1, 2.5}。花括号初始化 + CTAD 的组合要看清元素类型，别让编译器替你猜一个你并不想要的类型。

11.7 调试期边界检查：越界写入的护栏

operator[] 不做边界检查，越界是未定义行为；但在调试构建里，libstdc++ 的 _GLIBCXX_ASSERTIONS 会给容器的下标访问加断言，把越界变成一次可定位的终止。bounds_check/ 故意写 values[values.size()] = 9，让断言抓住这次越界。

清单把这个例子声明为 mode: detect，检测键是 glibcxx-assertions：正例用 -D_GLIBCXX_ASSERTIONS 编译，本机运行时以退出码 3 终止，stderr 含 Assertion '__n < this->size()' failed.；阴性对照用基线参数 -D_GLIBCXX_NO_ASSERTIONS 把机制关掉，断言不再出现。这是 libstdc++ 的调试期护栏，不是标准行为：换一个标准库、或关掉断言，越界仍然可能是静默破坏或访问冲突。生产代码处理不可信输入时，用 at()（标准规定越界抛 std::out_of_range）或显式检查，不要把安全寄托在 _GLIBCXX_ASSERTIONS 上。

11.8 string 与 SSO：只点到

std::string 在标准里不是“容器”，但它的接口与 vector<char> 很像：连续存储、可扩容、迭代器失效规则类似。主流实现有短字符串优化（SSO）：短字符串直接存在对象内部，不分配堆内存；长字符串才分配。SSO 让短字符串的构造/拷贝更便宜，但也意味着 data() 的地址、capacity() 的读数依赖实现与字符串长度。不要依赖 SSO 的具体阈值，也不要把 data() 的地址当成长期标识；需要稳定地址时，用 std::string 以外的方案或明确文档化。

std::string_view 是“指向一段字符的只读视图”，不拥有数据、不保证以 \0 结尾。它适合做只读参数，避免 const std::string& 逼调用方构造临时 string；但它不能延长数据的生命周期：std::string_view sv = make_string(); 之后源字符串已经销毁，sv 就是悬空视图。函数参数用 string_view，意味着调用方必须保证数据在调用期间活着；函数返回 string_view 时，要格外确认它指向的不是局部对象。

11.9 本机实测：六个读数

实验记录本机实测：容量、失效与两端插入

11.10 下一单元从哪继续

下一单元 11.2 关联容器与哈希 会把“按位置访问”换成“按键访问”：map / set 用比较器维持有序，unordered_* 用哈希分桶。map::operator[] 会插入、find 不会；自定义类型要提供比较或哈希。这一单元先确保你能说清“为什么 vector 扩容后不能再用旧迭代器”，下一单元再处理“键怎么比较、怎么哈希”。

小结这一节要带走的五件事
  • size 是元素个数，capacity 是不扩容能放的数量；reserve 只改容量，resize 改元素个数。
  • vector 扩容会重新分配并搬移元素，所有指针/引用/迭代器失效；不要跨扩容保存迭代器。
  • deque 两端插入便宜且支持随机访问；list 中间插入/删除不搬节点，但没有随机访问。
  • std::array 大小编译期固定、不碰堆；需要增长时用 vector。
  • 默认先选 vector；只有明确的两端/中间插入与迭代器稳定性需求，才考虑 deque / list。

  2. vector_invalidate 里 moved=yes 说明了什么？如果 push_back 之后解引用 before，会怎样？
  3. deque 与 list 都能在两端插入，主要差别是什么？list::splice 为什么不复制元素？
  4. std::array<int, 5> 与 std::vector<int> 的存储差别是什么？各自适合什么场景？

注自测答案
  1. size 是当前元素个数，capacity 是不重新分配时能容纳的元素个数；reserve(100) 只保证容量至少 100，size 仍是原来的值（通常是 0）。
  2. 说明 push_back 触发了重新分配，元素被搬到新块，data() 变了。解引用 before 会访问已释放的旧块，是未定义行为。
  3. deque 支持随机访问、分段存储，两端插入摊还常数；list 是双向链表，不支持随机访问，但节点插入/删除不搬元素，迭代器稳定。splice 直接改链表指针，把节点接过去，不复制元素。
  4. array 直接包含固定数量的元素，不分配堆，大小编译期固定；vector 在堆上管理连续存储，可增长。固定大小、小数据用 array；运行期大小可变用 vector。
  5. vector 连续存储、随机访问快、常数因子小；list 的节点分配与指针跳转成本通常更高。只有“频繁中间插入/删除且需要迭代器稳定”时，list 的优势才可能抵消这些成本。
