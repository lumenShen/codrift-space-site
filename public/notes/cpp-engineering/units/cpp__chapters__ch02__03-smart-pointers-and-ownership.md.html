上一单元的 FileHandle 与 Buffer 都在手写 new / delete。手写没有错，但它把“谁负责释放”藏在注释与约定里：拷贝一下就多一个释放者，传个指针就不知道对方会不会删。智能指针把所有权写进类型：unique_ptr 独占、shared_ptr 共享、weak_ptr 只观察不拥有。类型说清了所有权，析构函数就能按规则自动释放。

这一单元不教并发。智能指针常被当作“线程安全的万能药”，但 shared_ptr 只保证引用计数的更新是安全的，不保证它指向的对象线程安全；并发不在本书范围内，这里只把边界说清，不展开。

学习目标看完这一单元，你应该能
  • 说出独占、共享、观察三种所有权各自由哪个类型表达，以及它们各自能不能拷贝；
  • 用 unique_ptr 管理一个对象，解释 reset()、get()、移动与 make_unique 各做什么；
  • 用 use_count() 的读数证明 shared_ptr 的共享计数，并说清控制块与对象是两件事；
  • 画出一个 shared_ptr 循环引用，解释为什么析构计数不归零，并用 weak_ptr::lock 修好；
  • 为一个 C 风格资源写自定义删除器，并说出 shared_ptr 不该被当成默认选择的原因。

5.1 先看工程长什么样

这一单元继续在 examples/ch02/ 里加六个多文件小工程。每个目录仍然是 include/<例名>.h + src/<例名>.cpp + src/main.cpp + <例名>.json；第 2 章起硬规定③要求每个清单至少两个 .cpp，且至少一个 .h 被 #include。

第 1 帧的 unique_basic/ 用 make_unique 创建一个 Widget，reset() 之后立刻看到析构输出。第 2 帧的 unique_move/ 故意拷贝一个 unique_ptr，让编译失败成为“独占”的证据；shared_count/ 用 use_count() 展示共享计数。第 3 帧的 weak_cycle/ 先造一个循环引用（计数不归零），再用 weak_ptr 修好；factory_unique/ 用工厂函数返回 unique_ptr 并把它移进 vector；custom_deleter/ 用 malloc / free 展示删除器。

这六个例子各自回答一个问题：unique_basic 回答“独占指针什么时候释放”；unique_move 回答“为什么不能拷贝”；shared_count 回答“共享计数什么时候加减”；weak_cycle 回答“循环引用为什么泄漏、weak_ptr 怎么破”；factory_unique 回答“工厂怎样交出所有权”；custom_deleter 回答“不是 new 出来的资源怎么交给智能指针”。

5.2 所有权模型：独占、共享、观察

先看三种所有权在类型上的区别：

所有权 类型 能否拷贝 谁负责释放 典型场景
独占 std::unique_ptr<T> 不能，只能移动 指针的持有者 工厂返回值、容器里的对象、RAII 成员
共享 std::shared_ptr<T> 能，计数加一 最后一个持有者 多处共享同一对象
观察 std::weak_ptr<T> 能，不计数 不负责释放 打破循环、缓存、观察者

unique_ptr 的“独占”不是口头约定，而是类型系统强制的：它删除了拷贝构造与拷贝赋值，只保留移动。你把 unique_ptr 按值传给函数，必须写 std::move，所有权在代码里看得见。

make_widget 内部用 std::make_unique<Widget>("w") 创建对象；widget 独占它，widget->name() 通过 operator-> 访问成员。widget.reset() 释放当前对象（打印 dtor w），把指针置空；之后 widget 在布尔判断里为假，输出 empty=yes。reset() 是“立刻释放并接管新对象或置空”，不是“重置对象的值”。 如果你只想清空指针、保留对象，应该 release()，但 release() 会把释放责任交回给你，通常不是好主意。

get() 返回裸指针，用来传给只观察、不拥有的旧接口；它不转移所有权，也不延长生命周期。get() 的返回值只在你持有 unique_ptr 期间有效；把 get() 存起来，等 unique_ptr 析构后再用，就是悬空指针。

语法规则智能指针的最小语法
  • 创建：auto p = std::make_unique<T>(args...); / auto s = std::make_shared<T>(args...);
  • 访问：p->member、*p、p.get()（裸指针，不转移所有权）
  • 释放：p.reset()（立刻析构并置空）、p = nullptr;（等价于 reset()）
  • 转移：auto q = std::move(p);（p 变为空，q 独占）
  • 观察：std::weak_ptr<T> w = s;、w.lock()（成功返回 shared_ptr，失败返回空）

5.3 为什么不能拷贝：独占的代价与保证

诊断的核心是 use of deleted function：unique_ptr 的拷贝构造被显式删除了。为什么删除？如果允许拷贝，两个 unique_ptr 会持有同一个指针，两个析构函数都会 delete 它，结果就是我们上一单元看到的双重释放。“独占”不是性能优化，而是正确性约束：一个资源只能有一个释放者。 要转移所有权，写 std::unique_ptr<int> b = std::move(a);：移动之后 a 变为空，b 接管。

unique_ptr 的移动后状态是“空”，这一点与 std::string / std::vector 的“有效但未指定”不同——unique_ptr 不拥有任何东西时，布尔判断为假，get() 返回 nullptr。a 仍然是一个有效的 unique_ptr 对象，你可以对它赋值、reset()，或重新让它接管新对象；但不要在没有重新赋值前解引用它。

unique_ptr 还有一个数组特化 std::unique_ptr<T[]>，它会对数组调用 delete[]。用 std::make_unique<int[]>(n) 创建，不能对单个对象用数组特化，也不能混用 delete / delete[]。本书的例子不需要数组版本，但你应该知道它存在：删除器必须与分配方式匹配，这是自定义删除器要解决的问题。

所有权也应该写在函数签名上。要接管所有权，按值收 std::unique_ptr<T>：调用者必须 std::move，转移意图明确；函数内部负责释放。只观察不接管，收 T* 或 T&，不要收 const unique_ptr<T>& 再从中 get()——那会让接口看起来“拥有”，实际只是借用。要共享所有权，按值收 std::shared_ptr<T>，计数会加一；如果只是短期观察，收 const std::shared_ptr<T>& 可以避免计数增减，但不会延长对象寿命。

std::make_shared<T> 通常把对象与控制块放在一次分配里，比 std::shared_ptr<T>(new T) 少一次分配，也避免“对象构造成功、控制块分配失败”的异常安全问题。优先用 make_shared；只有需要自定义删除器、或对象已经存在时，才用 shared_ptr 的其它构造函数。shared_ptr 的引用计数是线程安全的，但指向的对象本身不是线程安全的；多线程读写同一个对象仍要加锁。

enable_shared_from_this<T> 让对象在“已经由 shared_ptr 管理”时，安全地产生指向自己的 shared_ptr。不要在构造函数里调用 shared_from_this()：那时对象还没交给 shared_ptr，控制块没建立，会抛 std::bad_weak_ptr。常见用法是在成员函数里返回 shared_from_this()，把 this 交给异步任务；如果对象不是由 shared_ptr 管理，应该用 weak_from_this() 检查，而不是假设。

5.4 shared_ptr：共享所有权与引用计数

shared_ptr 允许多个指针共享同一个对象。它内部有两个指针：一个指向对象，一个指向控制块；控制块里存引用计数与删除器。拷贝一个 shared_ptr 让计数加一，销毁一个让计数减一；计数归零时，控制块调用删除器销毁对象。

a=1 是唯一持有者；auto b = a; 之后 b=2；块内 auto c = b; 之后 c=3；块结束，c 析构，after=2；main 结束，b 与 a 依次析构，计数归零，对象销毁，打印 dtor shared。use_count() 是观察读数，不是同步原语；不要用它写“计数等于 1 就安全”的逻辑，因为别的线程/别的持有者随时可能改变它。

第 1 帧里对象与控制块是两个不同的内存块；第 2 帧的 b 复制了 a 的两个指针，计数从 1 变 2。“共享对象”不等于“共享指针变量”：a 与 b 各自有一个 shared_ptr 对象，它们只是都指向同一个控制块与同一个资源。控制块记录“还有几个强引用”，最后一个强引用离开时，对象析构；弱引用不增加强引用计数，但会让控制块多活一会儿（weak_ptr 要用它判断对象是否还在）。

std::make_shared<T> 通常把对象与控制块分配在同一块内存里，少一次分配；std::shared_ptr<T>(new T) 则是两次分配。这个差别是实现与性能层面的，不影响语义；本书的例子统一用 make_shared。shared_ptr 也可以接管 new 出来的裸指针，但不要用同一个裸指针构造两个独立的 shared_ptr——那会得到两个控制块，计数各算各的，最后还是双重释放。

5.5 循环引用：计数为什么不归零

shared_ptr 的计数只在“强引用”消失时减一。如果两个对象互相持有对方的 shared_ptr，它们就互为强引用：即使外部所有指针都离开作用域，两个对象的计数仍然各为 1，永远不会归零。

前半段先制造循环：两个 shared_ptr 成员互相指着对方。下面是同一份 main 的后半段，把强引用的那一条边换成 weak_next，其余结构不变。

第一段：a->next = b; b->next = a; 之后，a 与 b 的强引用计数各为 2（外部一个 + 对方一个）。块结束时，外部两个 shared_ptr 析构，计数各降到 1，两个对象仍然活着，所以 after_cycle=2——这就是内存泄漏：没有指针能再访问它们，但它们的析构函数不会执行。

第二段：weak_next 是 weak_ptr，赋值不增加强引用计数。块内 a->weak_next.lock() 成功，拿到一个临时的 shared_ptr，可以读 name()；块结束时 a、b 的强引用计数归零，两个对象析构，after_weak 回到 2（只剩第一段泄漏的两个），observer.expired() 为 1。weak_ptr 不延长对象寿命；它只是“知道对象在哪，需要时尝试升级为 shared_ptr”。

weak_ptr 的典型用途就是打破循环、实现缓存与观察者：父节点持有子节点的 shared_ptr，子节点持有父节点的 weak_ptr；缓存持有对象的 weak_ptr，对象被释放后缓存项自动失效。weak_ptr 不能直接解引用，必须先 lock() 或 shared_ptr 构造，因为对象可能已经不存在。

陷阱`shared_ptr` 能解决一切所有权问题

你会看到：只要把成员都改成 shared_ptr，代码就能编过，析构也“看起来正常”。你会误判成“共享指针是更安全的指针”，于是所有对象都用 shared_ptr。真相是：共享所有权把“谁负责释放”变成了“最后一个离开的人负责”，循环引用时没有人是最后一个；而且共享计数带来额外的控制块与原子操作。默认应该用 unique_ptr 或值语义；只有确实需要多处共享生命周期时，才用 shared_ptr，并想清楚谁持有谁、哪里需要 weak_ptr。

5.6 工厂与所有权转移

工厂函数返回 unique_ptr 是 C++ 的常见写法：调用者拿到独占所有权，不需要知道对象是怎么创建的，也不会忘记释放。

make_message 返回 std::unique_ptr<Message>，main 用 auto 接住；box.push_back(std::move(message)) 把所有权移进 vector，message 变为空，所以 moved=yes。vector 销毁时，它持有的 unique_ptr 析构，Message 打印 drop hello。容器里放 unique_ptr 而不是裸指针，容器的析构就自动负责释放所有元素；容器拷贝被禁止，但移动/emplace_back 仍然可用。

第 1 帧的所有权箭头从工厂指向 message；第 2 帧 message 变空，箭头改从 box 指向对象。移动不是“复制指针”，而是“把释放责任交给另一个对象，并让原对象置空”；这正是 unique_ptr 移动构造的语义。

5.7 自定义删除器：不是所有资源都来自 new

unique_ptr 的第二个模板参数是删除器。默认删除器 std::default_delete<T> 调用 delete；如果资源来自 malloc，就必须用 free，否则是未定义行为。

make_malloc_int 用 std::malloc 分配，返回的 unique_ptr 带着 FreeDeleter{freed}；离开作用域时删除器调用 free，freed 变成 1。删除器是 unique_ptr 类型的一部分：std::unique_ptr<int, FreeDeleter> 与 std::unique_ptr<int> 是两种不同的类型，不能互相赋值。这既是约束，也是好处——删除方式在编译期就固定了，不会出现“忘了用对应释放函数”的运行期错误。

shared_ptr 也接受自定义删除器，但删除器存在控制块里，类型擦除掉了；代价是控制块更大，且删除器的类型不影响 shared_ptr 的类型。make_shared 不支持自定义删除器，因为它要把对象与控制块一起分配。选择原则：资源来自 new 就用 make_unique / make_shared；来自 C API 就写删除器；不需要共享就用 unique_ptr。

5.8 边界：不要把所有东西都包成智能指针

智能指针解决“动态分配对象的生命周期”，不是“所有变量的默认容器”。下面这些情况不该用智能指针：

  • 对象是局部值、成员值、容器元素：直接用值语义，栈上分配，析构自动发生；
  • 函数只是观察参数：用 T& 或 const T&，不要为了“安全”传 shared_ptr；
  • 所有权明确且唯一：用 unique_ptr，不要用 shared_ptr 增加计数开销；
  • 需要多态容器：可以用 vector<unique_ptr<Base>>，但这是第 6 单元继承之后的话题。

接口里接收 shared_ptr，就等于向调用方宣告“我要参与共享所有权”；如果函数只是用完就走，应该改成 T& 或 const T&，否则调用方会被迫改变自己的生命周期管理方式。所有权语义要写在签名上，而不是藏在实现里，这样读接口的人不必猜。

shared_ptr 的线程安全边界也要说清：标准保证多个线程可以同时操作不同的 shared_ptr 对象，引用计数的更新是安全的；但它不保证同一个对象的内容线程安全，也不保证“先检查 use_count() 再使用”是原子的。并发不在本书范围内；这里只要求你不把 shared_ptr 当成“线程安全”的同义词。

还有一个常见的所有权误用：把 this 直接交给两个 shared_ptr 构造，会建立两个独立的控制块，最后双重释放。让对象自己产生 shared_ptr 时，用 enable_shared_from_this 或工厂函数；不要写 std::shared_ptr<T>(this)。所有权模型的价值就在于“释放者唯一且可追踪”，任何绕过控制块的写法都要先怀疑。

标准原文标准原文：unique_ptr 独占，shared_ptr 共享

A unique pointer is an object that owns another object and manages that other object through a pointer. … each such U is Cpp17MoveConstructible and Cpp17MoveAssignable, but is not Cpp17CopyConstructible nor Cpp17CopyAssignable.

The shared_ptr class template stores a pointer … shared_ptr implements semantics of shared ownership; the last remaining owner of the pointer is responsible for destroying the object.

大意：unique_ptr 独占一个对象，只可移动、不可拷贝；shared_ptr 实现共享所有权，最后一个持有者负责销毁对象。

出处：N4950 §20.3.1.1「General」（[unique.ptr.general]）与 §20.3.2.2.1「General」（[util.smartptr.shared.general]）。

shared_ptr 还有一个别名构造：它可以让新的 shared_ptr 指向对象的某个成员，同时与原对象共享同一个控制块。这在把成员地址交给外部、又要求宿主对象保持存活时很有用；但读代码的人容易误以为新指针拥有成员本身。所有权看控制块，不看指针指向哪里，别名指针不是独立的资源所有者。本书不展开别名构造的细节，只提醒一点：看到 shared_ptr 时，先问“控制块是谁创建的”，再问“指针指向什么”；两个问题分开，所有权就不会看错。

5.9 本机实测：四个读数

实验记录本机实测：独占、共享与循环引用

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • unique_basic 的 stdout 是 ctor w / name=w / dtor w / empty=yes：reset() 立刻析构；
  • unique_move 编译失败，诊断是 use of deleted function 'std::unique_ptr<...>::unique_ptr(const std::unique_ptr<...>&)'；
  • shared_count 的 use_count() 依次是 1、2、3、2，对象在最后一个持有者析构时打印 dtor shared；
  • weak_cycle 的真实读数是 cycle_alive=2、after_cycle=2、after_weak=2 expired=1：循环引用留下两个对象，weak_ptr 不延长寿命；
  • custom_deleter 的输出是 value=21 freed=0 → free 21 → after=1：删除器在作用域结束时执行。

5.10 下一单元从哪继续

下一章 6.1 继承与虚函数 会把“所有权”扩展到“多态”：基类指针指向派生对象，虚函数决定调用哪一份实现，虚析构决定删除时走哪条析构链。unique_ptr<Base> 持有派生对象时，基类的析构函数必须是虚的，否则删除只走基类析构，派生部分泄漏——这是第 6 单元的第一个坑。

小结这一节要带走的五件事
  • unique_ptr 独占、只能移动；shared_ptr 共享、计数归零时释放；weak_ptr 观察、不延长寿命。
  • unique_ptr 的拷贝被删除，所有权转移必须写 std::move；移动后原指针为空。
  • shared_ptr 的对象与控制块是两件事；use_count() 是读数，不是同步工具。
  • 循环引用会让强引用计数永不归零；把环中的一条边改成 weak_ptr，并用 lock() 临时提升。
  • 资源来自 new 用 make_unique / make_shared；来自 C API 写删除器；默认优先 unique_ptr，不要把所有对象都共享。
自测题自测题（先自己做，再对答案）
  1. unique_ptr 为什么禁止拷贝？如果允许拷贝，会发生什么？
  2. widget.reset() 与 widget.release() 的区别是什么？各自之后 widget 是什么状态？
  3. shared_ptr 的 use_count() 从 3 降到 2 时，对象会析构吗？什么时候才会析构？
  4. 两个对象互相持有 shared_ptr，为什么块结束后 alive 仍然是 2？把其中一条边改成 weak_ptr 后，expired() 为什么是 1？
  5. 为什么 malloc 出来的内存不能直接交给默认的 unique_ptr<int>？自定义删除器怎样解决？
注自测答案
  1. 如果允许拷贝，两个 unique_ptr 会持有同一个指针，两个析构函数都会释放它，造成双重释放。独占语义要求“一个资源只有一个释放者”，所以拷贝被删除，只能移动。
  2. reset() 释放当前对象并把指针置空；release() 放弃所有权并返回裸指针，unique_ptr 本身变为空，但对象不会被释放，释放责任交回调用者。
  3. 不会。use_count() 只表示还有几个强引用；计数降到 0 时，最后一个持有者离开，控制块调用删除器销毁对象。
  4. 因为两个对象互为强引用，外部指针离开后计数仍各为 1，析构不会发生。把一条边改成 weak_ptr 后，强引用计数能归零，对象析构；观察该对象的 weak_ptr 随即 expired() 为真。
  5. 默认删除器调用 delete，而 malloc 必须用 free 释放，混用是未定义行为。写一个调用 free 的删除器，并把它作为 unique_ptr 的第二个模板参数。
