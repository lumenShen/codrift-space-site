C 的结构体只是一组字段；C++ 的类在字段之外还带一组函数，其中两个最关键：构造函数负责把对象带到“可用”的状态，析构函数负责在对象消失时把资源还回去。把“资源的生命周期”绑到“对象的生命周期”上，这套做法叫 RAII（Resource Acquisition Is Initialization）。它不是语法糖，而是 C++ 管理内存、文件、锁、网络连接的默认方式。

这一单元从最小的 RAII 包装开始，依次看清四件事：构造/析构什么时候执行、成员按什么顺序初始化、默认拷贝为什么会把资源复制成两份指针、以及什么时候必须手写拷贝构造与拷贝赋值。最后用 explicit 把“隐式转换”这道门关上。

学习目标看完这一单元，你应该能
  • 写出一个 RAII 类，让构造函数获取资源、析构函数释放资源，并说清“确定性释放”发生在哪一刻；
  • 解释成员初始化顺序由声明顺序决定，而不是由初始化列表的书写顺序决定；
  • 说出默认拷贝构造对“拥有裸指针”的类做了什么，并用退出码证明双重释放；
  • 按 Rule of Three 写出拷贝构造、拷贝赋值与析构，并用 copy-and-swap 处理自赋值；
  • 解释 explicit 阻止了哪种隐式转换，并读懂对应的编译诊断。

3.1 先看工程长什么样

第 2 章起，硬规定③生效：每个清单至少两个 .cpp，并且至少一个 .h 被源文件 #include。这一单元的六个例子都按这个形状组织：include/<例名>.h 放声明，src/<例名>.cpp 放实现，src/main.cpp 只做驱动与打印，<例名>.json 固定编译命令。

第 1 帧只有 raii_file/：FileHandle 的构造函数接收一个 FILE*，析构函数负责 fclose；main.cpp 只负责拿临时文件、写一行、读回来。第 2 帧加上 ctor_order/（成员初始化顺序）、copy_shallow/（默认拷贝导致双重释放）与 copy_deep/（手写深拷贝）。第 3 帧加上 copy_elision_basic/（返回局部对象时的拷贝/移动计数）与 explicit_ctor/（隐式转换被拒绝）。

注意每个目录都把接口放在 include/、实现放在 src/：FileHandle 的用户只看得到头文件里的声明，不需要知道析构函数里调用了 fclose；Buffer 的用户只看得到 data() / set()，不需要知道内部用 new char[]。这不是为了“看起来工程化”，而是为了让“谁能看见什么”变成可检查的事实——头文件里没有定义，链接期就必须由某个 .cpp 补上。

3.2 类、构造与析构：对象的一生

class 与 struct 在 C++ 里只有一个语法差别：默认访问权限。struct 的成员默认 public，class 默认 private。本书的惯例是：只装数据的聚合用 struct，有不变量的类型用 class；这只是惯例，不是标准要求。FileHandle 有“必须持有有效文件、析构时必须关闭”的不变量，所以用 class，把 file_ 藏起来，只暴露 get()。

构造函数在对象创建时自动调用，析构函数在对象销毁时自动调用。所谓“自动”，指编译器在作用域结束时插入调用，不需要你手写 close()：

输出顺序是 open → read=hello → close。close 出现在 main 返回之后、file 离开作用域时，由析构函数打印。这就是确定性释放：对象的生命周期一结束，资源立刻归还，不依赖垃圾回收，也不依赖你记得写 fclose。 如果 main 中途 return 1，file 仍然会被析构，因为栈上的对象在函数返回时按构造的逆序销毁。

~FileHandle() 里判断 file_ != nullptr，是因为构造函数允许传入空指针；如果构造失败，对象仍然被构造出来（只是处于“没有资源”的状态），析构函数必须能处理它。更严格的写法是在构造函数里抛异常，让对象根本构造不出来；这属于第 16 单元“异常与异常安全”的内容，本单元先用“空指针 + 析构判空”的简化模型。

第 1 帧的构造调用发生在 FileHandle file(std::tmpfile()); 这一行；第 2 帧的析构调用不需要你写，编译器在 file 离开作用域时插入。两帧之间没有任何“手动关闭”的代码，fclose 只出现在析构函数体内——这就是 RAII 的调用链。

FileHandle(const FileHandle&) = delete; 与 FileHandle& operator=(const FileHandle&) = delete; 把拷贝构造与拷贝赋值删掉了。原因很直接：如果允许拷贝，两个 FileHandle 会持有同一个 FILE*，两个析构函数各 fclose 一次，第二次就是重复关闭。“拥有资源”的类型默认不应该可拷贝；要么禁止拷贝，要么写深拷贝。 这一条会在 3.5 与 3.6 节用两个例子分别展示“禁止”和“深拷贝”。

大白话大白话：RAII 就是“借东西的人负责还”

去图书馆借书，借的时候登记（构造函数），还的时候注销（析构函数）。你不需要每天想着“我借过书”，只要书还在你手上，登记就有效；你一离开（对象销毁），系统自动注销。RAII 把“还书”这件事绑在“你离开”这个事件上，而不是绑在“你记得”上。C++ 的析构函数就是那个“离开时自动执行”的钩子。

3.3 成员初始化：顺序看声明，不看列表

构造函数的初始化列表写在参数列表后面，用冒号开头。很多人以为“列表里先写的先初始化”，实际规则是：非静态数据成员按它们在类里的声明顺序初始化，跟列表顺序无关。

输出先 init first 再 init second，尽管初始化列表里写的是 second_ 在前。原因：编译器按声明顺序（first_、second_）逐个初始化成员，初始化列表只负责提供“用哪个值初始化”，不负责排序。如果你在列表里写 b_(a_)，而 b_ 声明在 a_ 前面，那么 b_ 会先初始化，此时 a_ 还没初始化，读它就是未定义行为。 编译器通常给 -Wreorder 警告，但警告不阻止编译，运行时可能“看起来正常”，换一个优化档就变。

-Wreorder 的诊断（本机编译 ctor_order 时真实出现）会指出“second_ 将先于 first_ 初始化”，并给出声明与初始化列表的位置。看到它不要关警告，改列表顺序或改声明顺序，让两者一致。初始化列表的最佳实践是：按声明顺序写，能在列表里初始化的就不要放进函数体。 放进函数体意味着成员先被默认构造一次，再被赋值一次，多一次构造/析构；对 const 成员与引用成员，函数体赋值甚至不合法，因为它们必须在初始化时绑定。

编译器视角编译器视角：`-Wreorder` 在说什么

这份代码在本机编译时，编译器给出 -Wreorder：它发现 Widget::second_ 会在 Widget::first_ 之前初始化（因为声明顺序），但初始化列表写的是 second_ 先出现，容易让读者误判。诊断不是“代码错了”，而是“你的书写顺序与执行顺序不一致”。修法只有两种：把列表改成 first_("first"), second_("second")，或把成员声明改成 second_ 在前。先让书写顺序与执行顺序一致，再谈其他优化。

3.4 默认拷贝：逐成员复制，指针只复制地址

如果类没有写拷贝构造，编译器会生成一个默认拷贝构造：逐个成员复制。成员是 int、std::string 这类值类型时，逐成员复制是对的；成员是裸指针时，逐成员复制只复制地址，两个对象指向同一块内存。

这份程序编译通过、没有警告；运行时的退出码是 3221226356（Windows 的堆损坏/双重释放异常码，本机 3/3 稳定），stderr 为空，stdout 也为空。原因是：Shallow b = a; 走默认拷贝构造，b.data_ 与 a.data_ 存的是同一个地址；main 返回时先析构 b，delete data_ 释放了那块内存；再析构 a，对同一地址再 delete 一次，堆管理器发现重复释放，进程终止。

第 1 帧的堆盒子只有一个；第 2 帧的 b.data_ 没有新建盒子，只是把 a.data_ 里的地址又抄了一份。所以“两个对象”在语言层面成立，“两份资源”却不成立——析构函数各删一次，第二次就删到了同一块已经归还的内存。

这个例子没有输出，所以正文用退出码作为证据。“编译通过”只说明类型正确，不说明所有权正确。 默认拷贝构造不知道你的 data_ 是“拥有的资源”还是“借来的观察指针”；它一律逐成员复制。要让它正确，只有两条路：禁止拷贝（像 FileHandle 那样 = delete），或手写深拷贝（像下一节的 Buffer）。

陷阱默认拷贝把“拥有”复制成“共享”

你会看到：一个持有 new 指针的类，按值传给函数、放进 vector、或写 T b = a; 之后，程序偶尔崩溃、偶尔“看起来正常”。你会误判成“new 用错了”或“编译器 bug”。真相是：默认拷贝构造只复制指针值，两个对象都以为自己拥有同一块内存；谁先析构谁释放，后析构的那个就是双重释放。判断标准不是“有没有写 new”，而是“这个类有没有复制一份资源的能力”。

3.5 深拷贝与 Rule of Three

要允许拷贝，就必须让新对象拥有自己的一份资源。Buffer 用 new char[] 保存字符串，手写拷贝构造分配新数组并逐字节复制；拷贝赋值用 copy-and-swap：先按源对象构造一个临时副本，再与自身交换，临时对象析构时释放旧资源。

a=alpha b=Alpha 证明两个对象各有自己的字符数组：改 b 的第一个字符，a 不变。拷贝构造里 data_(nullptr) 先占位，再在函数体分配；如果 new 抛异常，对象构造失败，析构函数不会执行，所以不会误删未分配的指针。拷贝赋值里的 if (this != &other) 处理自赋值；Buffer copy(other); swap(copy); 让旧资源随 copy 的析构释放，交换本身只交换两个指针与大小，不抛异常。

Rule of Three（三法则）：如果一个类需要手写析构函数、拷贝构造、拷贝赋值中的任何一个，通常三个都需要手写。原因是它们共同管理同一份资源：析构负责释放，拷贝构造负责复制，拷贝赋值负责“先释放旧的、再复制新的”。只写其中一个，另外两个会退化成编译器生成的默认版本，所有权模型就断了。C++11 之后还有移动构造/移动赋值，扩展成 Rule of Five，第 4 单元会讲。

swap 标了 noexcept，因为它只交换指针与整数，不会失败。copy-and-swap 的代价是多一次临时对象的构造与析构；收益是拷贝赋值只需要写一次资源释放逻辑（析构函数），并且天然处理自赋值与异常安全。这不是唯一写法，但它是“先正确、再优化”的稳妥写法。

3.6 返回值省略：为什么计数是 0

make_counter() 里明明有一个局部对象 local，main 里又有一个 result，为什么拷贝和移动都是 0？因为编译器做了返回值优化（NRVO，Named Return Value Optimization）：它直接在 result 的存储里构造 local，省掉了“构造局部对象 → 拷贝/移动到返回值 → 析构局部对象”这一串。C++17 起，返回纯右值（如 return Counter{};）的拷贝省略是强制的；NRVO（返回有名字的局部变量）仍然是可选的，只是主流编译器都会做。本机 g++ 在这个例子中做了 NRVO，所以计数为 0。

计数为 0 不代表“拷贝构造没写对”，也不代表“移动构造没用”。换一个编译器、换一个优化档、或在 return 里写 std::move(local)，计数就可能变成 1。第 4 单元会用 -fno-elide-constructors 把这条优化关掉，对照 copies / moves 的真实变化。现在的结论只有一条：返回值不一定发生拷贝；“计数为 0”是优化结果，不是语言保证。

3.7 explicit：关掉隐式转换的门

只有一个参数的构造函数，默认允许隐式转换：Meter distance = 42; 会把 42 转成一个 Meter。如果这个转换在语义上不合理（42 什么单位？米还是厘米？），就应该用 explicit 禁止它。

诊断的关键在 explicit conversion function was not considered：编译器看到了 Meter(int)，但因为它是 explicit，不参与这次隐式转换。把 Meter 的构造函数改成非 explicit，这行就能编过；但代价是任何 int 都能悄悄变成 Meter，包括函数传参、容器初始化、返回值。explicit 不是“更严格所以更好”，而是“这个转换是否应该由程序员显式写出来”的设计选择。 单参数构造函数默认加 explicit，需要隐式转换时再放开，是常见的工程惯例。

3.9 把 RAII 变成工程习惯

  1. 资源用对象管：文件、内存、锁、socket 都用 RAII 包装，构造获取、析构释放；不要让“打开”和“关闭”分散在两个函数里。
  2. 拥有资源的类先想拷贝：禁止拷贝（= delete）或写深拷贝；不要依赖默认拷贝。只读观察用引用/指针，不拥有就不负责释放。
  3. 三法则/五法则：写了析构、拷贝构造、拷贝赋值中的任何一个，就把另外两个一起检查；第 4 单元再加上移动构造/移动赋值。
  4. 单参数构造函数默认 explicit：除非你确实想要隐式转换（例如 std::string 从 const char* 构造是标准库的设计选择）。
  5. 成员按声明顺序初始化：列表与声明保持一致；能在列表里初始化就不要放进函数体。

std::unique_ptr 与 std::shared_ptr 会把“禁止拷贝/引用计数”做进标准库，下一单元会用它们替代手写 new / delete。但 RAII 的思想不变：所有权跟着对象走，析构负责归还。

3.10 下一单元从哪继续

下一单元 3.2 拷贝与移动 会把这一单元的“拷贝”扩展到“移动”：值类别、std::move、Rule of Five、noexcept 移动构造与 vector 扩容。本单元已经出现的 Counter、Buffer 与 FileHandle 会在那里以“可移动版本”再次出现；先确保你能独立写出 Buffer 的拷贝构造、拷贝赋值与析构，再往下走。

小结这一节要带走的五件事
  • 构造函数建立不变量，析构函数确定性释放资源；对象离开作用域时按构造的逆序析构。
  • 成员按声明顺序初始化，初始化列表的顺序不决定执行顺序；顺序不一致时 -Wreorder 会警告。
  • 默认拷贝构造逐成员复制；成员是裸指针时只复制地址，两个对象会重复释放同一块内存。
  • Rule of Three：析构、拷贝构造、拷贝赋值共同管理资源，写一个就要检查另外两个；copy-and-swap 是稳妥的拷贝赋值写法。
  • 单参数构造函数默认允许隐式转换，explicit 关掉它；explicit 的选择是接口设计，不是“越严格越好”。

  1. FileHandle 的 close 输出为什么出现在 read=hello 之后，而不是 main 里显式调用 fclose 时？
  2. Widget::Widget() : second_("second"), first_("first") {} 的执行顺序是什么？为什么？
  3. Shallow b = a; 之后，两个对象的 data_ 有什么关系？程序为什么以 3221226356 退出？
  4. Buffer 的拷贝赋值里，Buffer copy(other); swap(copy); 各自解决了什么问题？为什么不用先 delete[] data_ 再 new？
  5. Meter distance = 42; 为什么会编译失败？如果去掉 explicit，这行会发生什么？
注自测答案
  1. FileHandle 的析构函数在 file 离开 main 作用域时自动调用，fclose 与 close 输出都在那之后；程序没有显式调用 fclose，close 是 RAII 的确定性释放。
  2. 先 init first，再 init second：成员按声明顺序初始化（first_ 在 second_ 前），初始化列表只提供初值，不决定顺序。
  3. b.data_ 与 a.data_ 存的是同一个地址（默认拷贝只复制指针）。b 先析构释放该地址，a 再析构时对同一地址重复 delete，触发堆损坏，退出码 3221226356。
  4. Buffer copy(other); 先构造一份独立副本，失败时不会改动 this；swap(copy); 把旧资源换到临时对象里，随其析构释放。先 delete[] 再 new 的话，如果 new 抛异常，this 就留下一个已释放的指针；copy-and-swap 保证要么成功，要么原对象不变。
  5. Meter(int) 是 explicit，不参与隐式转换，所以 42 不能自动变成 Meter。去掉 explicit 后这行合法，42 会被隐式转换成一个 Meter 对象。
