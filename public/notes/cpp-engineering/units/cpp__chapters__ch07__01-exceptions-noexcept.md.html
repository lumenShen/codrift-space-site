函数发现“这件事做不成”时，有两种报告方式：返回一个错误码，或者抛出异常。错误码要求调用者每次都检查，漏一次就可能拿着无效结果继续算；异常把“成功路径”和“失败路径”分开，错误会沿着调用栈向上找 catch，中间的函数不必层层转交。代价是：控制流会突然跳走，路上必须把已经构造的对象清理干净。

这一单元讲三件事：异常怎么抛、怎么接，栈展开时析构函数做了什么；noexcept 承诺了什么，为什么它会影响 vector 扩容时选移动还是拷贝；以及“异常安全”的三个等级，怎么用 copy-and-swap 写出强保证。

学习目标看完这一单元，你应该能
  • 写 throw / try / catch，并说出异常对象按值抛出、按引用捕获的理由；
  • 画出栈展开路径，解释局部对象按什么顺序析构；
  • 说明析构函数默认为什么是 noexcept，以及析构中抛异常为什么危险；
  • 用 noexcept 标记移动构造，并解释 vector 扩容为什么偏爱不抛的移动；
  • 区分基本保证、强保证与不抛保证，用 copy-and-swap 实现强保证；
  • 判断什么时候用异常、什么时候用错误码或 expected。

16.1 先看工程长什么样

这一单元在 examples/ch07/ 下建六个例子，仍然保持“两个 .cpp + 一个 .h”的多文件结构：异常类型与辅助函数放头文件/实现文件，main.cpp 负责触发与打印。dtor_throw/ 是反例，它故意在析构函数里抛异常，靠编译器的 -Werror=terminate 在编译期拦下。

第 1 帧的 throw_basic/ 演示最小抛出与捕获，stack_unwind/ 用带打印的 Tracer 看析构顺序，catch_by_ref/ 对照按值与按引用捕获。第 2 帧的 noexcept_move/ 数 vector 扩容时的移动/拷贝次数，dtor_throw/ 是编译期反例。第 3 帧的 strong_guarantee/ 用 copy-and-swap 对照“先改再抛”的基本保证。

16.2 抛出与捕获：错误沿调用栈向上找

最小用法只有三块：可能失败的函数 throw 一个异常对象；调用方用 try 包住可能抛的语句；catch 按类型接住。异常一旦抛出，当前函数剩余语句不再执行，控制流开始向上找匹配的 catch。

checked_div(12, 3) 返回 4，打印 result=4；第二次调用分母为 0，checked_div 在除法之前 throw std::invalid_argument("division by zero")，int bad = ... 这条语句没有完成，后面的 std::cout << "result=" 也不会执行；控制流跳到 catch，打印异常对象的 what()。注意 throw 之后函数里剩下的代码不会运行，哪怕它只是 return。

std::invalid_argument 的构造函数接收一个字符串，what() 返回它。抛出的异常对象在标准里叫“异常对象”，它是一份按值保存的副本：throw 表达式里的对象会被复制（或移动）到一块由运行时管理的存储，catch 拿到的是这块存储的引用。按值抛出、按引用捕获是标准库和工程代码的常规组合：按值抛出保证异常对象活过抛出函数的作用域，按引用捕获避免再复制、也避免切片。

语法规则try / catch 的基本形状

形状是 try { ... } catch (const SomeError& error) { ... }：try 包住可能抛的语句，catch 的参数写异常类型。catch 的顺序要从“最具体”到“最一般”：catch (const std::exception&) 能接住所有派生自 std::exception 的异常，如果把它写在前面，后面的具体类型就永远轮不到。catch 只按类型匹配，不看值；同一个 try 里可以有多个 catch，第一个匹配的胜出。

throw;（不带表达式）只能在 catch 里用，表示“把当前异常继续往上抛”。如果 catch 里不想处理、只想记录一下，可以写 throw; 而不是 throw error;；后者会再复制一份，还可能因为静态类型变化而切片。重新抛出用 throw;，这是保持异常对象原样的方式。

catch (...) 能接住任何异常，但它拿不到异常对象，通常只用于“必须保证不泄漏”的边界（例如线程入口、回调边界）里做清理并重新抛出。不要用 catch (...) 吞掉异常：程序看起来继续跑了，实际问题被藏起来，后面的状态可能已经不可信。

16.3 栈展开：离开的每一层都要清理

异常从抛出点向上传播时，会依次退出沿途的函数。每退出一层，这一层已经构造完成的自动对象都要按构造的逆序析构。标准把这个过程叫“栈展开”（stack unwinding）。它不是“跳转”，而是一层一层地退，析构函数该跑的都跑。

outer 先构造，inner 后构造；抛出后 inner 先析构，outer 后析构，正好与构造顺序相反。两个析构都发生在 catch 之前，然后才打印 caught=boom，最后 main 继续执行到 done。异常不是“程序结束”；只要有人接住，程序就从 catch 之后继续。

第 2 帧的析构顺序是栈展开的核心：后构造的先析构，先构造的后析构。如果 run_with_throw 里还开了文件、锁、堆内存，这些资源的释放都写在析构函数里，栈展开就会自动完成清理——这就是 RAII 与异常能配合的原因。反过来说，如果资源是裸 new 出来的、析构函数又没管，栈展开不会替你 delete，泄漏就发生了。

标准原文标准原文：栈展开

As control passes from the point where an exception is thrown to a handler, objects are destroyed by a process, specified in this subclause, called stack unwinding.

Each object with automatic storage duration is destroyed if it has been constructed, but not yet destroyed, since the try block was entered. … The objects are destroyed in the reverse order of the completion of their construction.

大意：异常从抛出点走向处理器的过程中，自 try 块进入以来构造完成、尚未销毁的自动对象都会被销毁，顺序与构造完成的顺序相反。

出处：N4950 §14.3「Constructors and destructors」（[except.ctor]）。

“构造完成”很关键：如果对象的构造函数自己抛了，这个对象不算构造完成，它的析构不会运行；但它的基类与已完成的成员子对象会按规则清理。这也是为什么构造函数里分配资源后，后续步骤再抛异常时，要用 RAII 成员而不是裸指针。

16.4 按引用捕获：避免切片，也避免复制

catch 的参数写 Error 还是 const Error&，差别不只是“少复制一次”。如果抛出的实际类型是 AppError（Error 的派生类），catch (Error error) 会把异常对象切片成 Error 子对象，派生类部分丢失，虚函数也按 Error 的版本调用。

throw_app() 抛的是 AppError，它的 code() 覆盖为 7。第一次 catch (Error error) 按值接住，异常对象被复制成 Error，error.code() 调用的是 Error::code()，返回 0；第二次 catch (const Error& error) 按引用接住，动态类型仍是 AppError，code() 返回 7，what() 返回 "app failed"。切片不只发生在函数传参，也发生在按值捕获异常；这是“按引用捕获”最硬的理由。

按引用捕获还避免了复制异常对象。异常对象可能很大，复制可能再次抛异常（虽然少见），也可能有副作用；const & 既只读又不复制，是默认选择。只有当你确实需要一份独立副本、并且不关心动态类型时，才按值捕获——这种场景很少。

陷阱catch 顺序写反，具体异常永远接不到

如果try里抛出AppError，而先写catch (const Error& error)、后写catch (const AppError& error)，第一个处理器就把所有Error及其派生类接走了，后面的AppError处理器永远到不了，有的编译器会给 unreachable 警告。catch 按书写顺序匹配，第一个能接住的胜出。从派生到基类排列：先 AppError，再 Error，最后 std::exception。反过来写不会编译失败，但具体类型的处理器变成死代码，行为与你的预期不同。

16.5 noexcept：承诺不抛，影响容器选择

noexcept 是函数接口的一部分：它承诺“这个函数不会让异常逃出去”。如果函数真的抛了，程序不会正常传播异常，而是调用 std::terminate 直接结束。它不是优化提示，而是行为契约；写上去就要保证做到。

noexcept 最重要的实际影响之一是移动构造。std::vector 扩容时要把旧元素搬到新缓冲区；如果移动构造可能抛异常，搬到一半失败就会留下“旧缓冲区有一部分已被移走、新缓冲区还没建好”的烂摊子，连基本保证都难维持。所以标准库用 std::move_if_noexcept 做选择：移动构造是 noexcept 就移动，否则如果有拷贝构造就拷贝。

两个 vector 都装了 4 个元素，都发生了两次扩容（1→2、2→4），一共搬运 1+2=3 个旧元素。SafeMove 的移动构造标了 noexcept，3 次全是移动；UnsafeMove 的移动构造写的是 noexcept(false)，move_if_noexcept 判断“移动可能抛、拷贝可用”，于是 3 次全走拷贝。noexcept 在这里直接决定了性能路径：移动通常只是搬几个指针/整数，拷贝可能要分配内存、复制全部数据。

这里的 capacities=4,4 与“两次扩容”是 libstdc++ 的本机实测结果，不是标准规定。标准只要求 vector 的 push_back / emplace_back 均摊常数时间，具体扩容倍数由实现决定；换一个标准库，容量序列可能不同。但“移动是否 noexcept 会影响扩容选移动还是拷贝”是标准库算法的要求，换实现也成立。

第 2 帧的移动路径快，但如果移动到一半抛异常，vector 很难恢复；第 3 帧的拷贝路径慢，可一旦某个拷贝失败，旧缓冲区还完整，容器仍能保持基本保证。标准库选的是“先保证正确，再谈快”；你的移动构造如果确实不会抛，就应当标 noexcept，把快路径打开。

写 noexcept 要诚实：移动构造通常只搬指针/整数，标 noexcept 没问题；如果移动里要分配内存、调用可能抛的函数，就不能标。标了却抛，程序直接 terminate，比不标更糟。析构函数默认就是 noexcept，原因相同：栈展开时析构再抛，没法同时处理两个异常。

16.6 析构函数为什么不能抛

标准规定，析构函数默认带 noexcept(true)（除非基类或成员的析构可能抛，隐式声明才会变成可能抛）。如果析构函数里真的让异常逃出去，std::terminate 会被调用。更危险的是“栈展开过程中析构又抛”：运行时正在处理一个异常，又来了第二个，C++ 没有“异常嵌套传播”的机制，只能终止。

这个例子在清单里加了 -Werror=terminate，所以 GCC 的 -Wterminate 警告变成错误，编译失败。诊断会指出“throw 总会调用 terminate”，并提醒“C++11 起析构函数默认是 noexcept”。即使不加这个开关，代码也“能编译”，但一运行就会终止；编译期拦下比运行期崩溃好，这也说明编译器能识别这类必然终止的写法。

编译器视角本机诊断：`-Wterminate` 抓的是“必然终止”

GCC 的 -Wterminate 不需要运行就能看出：在一个 noexcept 函数（包括默认 noexcept 的析构）里写 throw，异常一定逃不出去，必然走到 std::terminate。它给的是警告而不是错误，因为标准没有禁止这种写法——标准只是规定运行时会发生什么。工程上通常把这类警告升级为错误（-Werror=terminate），让问题停在编译期。

如果确实需要“析构里的清理动作可能失败”，正确做法不是让异常逃出去，而是在析构内部捕获并记录/忽略，或者提供一个显式的 close() / commit() 让调用者在对象销毁前处理失败。析构函数的职责是释放资源，不是报告业务错误；把可能失败的逻辑放到显式接口里，是 RAII 设计的常见边界。

noexcept(false) 的析构函数可以写，但只在极特殊场景（例如析构需要调用可能抛的第三方接口，且你能保证不在栈展开中销毁）才考虑；即便写了，也要在内部 try / catch 兜住。默认让析构 noexcept，把失败前移到显式接口，这是更安全的工程惯例。

16.7 异常安全：基本、强、不抛

“异常安全”问的不是“会不会抛”，而是“抛了之后对象还能不能用”。工程上常分三档：

  1. 基本保证：异常后对象仍处于有效状态，可以继续使用或安全销毁，但具体内容可能已改变；
  2. 强保证：操作要么完全成功，要么回到操作前的状态，像事务一样；
  3. 不抛保证：操作承诺不抛异常（通常标 noexcept）。

vector::push_back 通常提供强保证（扩容失败时原容器不变），swap 通常提供不抛保证。自己写的多步修改，如果中途可能抛，就要想清楚停在哪一档。

append_strong 先把 data_ 复制到 next，往 next 追加，失败就抛；此时 data_ 完全没动，所以 strong_size=0。append_basic 直接往 data_ 追加，再抛；异常后 data_ 里已经多了一个 1，所以 basic_size=1。两者都“没有崩溃、对象仍可析构”，但强保证把“失败”变成了“什么都没发生”。

第 2 帧的 data_ 没有被碰过，所以强保证成立；第 3 帧的 swap 只交换内部指针，通常不抛，于是“交换”这一步不会破坏保证。copy-and-swap 的代价是每次操作都复制整个容器，适合“写少、要求强保证”的场景；如果数据很大、失败又很常见，就要权衡性能，可能退而求其次使用基本保证，或在操作前先做检查。

swap 本身是否 noexcept 取决于容器与分配器；标准库容器在同分配器下通常提供不抛的 swap，这是 copy-and-swap 能收尾的前提。如果你的类型没有不抛的 swap，最后一步也可能失败，强保证就不完整；实现时要检查这一点。

选择哪一档，取决于接口承诺与调用方需求：资源管理类的移动/交换操作应尽量做到不抛；修改多个字段的业务操作，如果调用方需要“重试”，强保证更有用；日志、清理这类“尽力而为”的操作，基本保证加上明确的返回值就够了。

16.8 异常还是错误码

异常适合“真正的异常”：文件打不开、内存耗尽、网络断开、参数违反前置条件。它们不常发生，发生后当前函数通常无法继续，必须由上层决定怎么办。异常的优势是不会被忽略——调用者不写 catch，异常就一路向上，直到有人处理或程序终止。

错误码适合“预期内的失败”：解析到文件末尾、查找键不存在、用户输入不合法。这些失败是正常流程的一部分，调用者通常就在附近处理。std::optional、std::expected 与错误码把失败放在返回值里，调用者必须显式检查，控制流是直的，没有隐藏跳转。

不要用异常做普通控制流：在一个循环里用 throw 表示“找到结尾”，会让读代码的人很难看出循环的正常出口，也会让性能不可预测。反过来，也不要用错误码掩盖真正的异常：如果内存分配失败、 invariant 被破坏，继续返回一个“空值”让上层猜，问题会更难查。

C++ 标准库自己两种都用：vector::at 越界抛 std::out_of_range，map::find 用 end() 表示没找到；std::stoi 抛异常，std::from_chars 用错误码。接口设计时先问“这个失败常见吗、调用方能在本地处理吗”，答案决定用哪种报告方式；下一单元的 optional / variant / expected 会把“不用异常的错误处理”展开。

16.9 本机实测：六个读数

实验记录本机实测：抛出、展开、捕获与保证

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • throw_basic 的 stdout 是 result=4 / caught=division by zero：抛出后剩余语句不执行，catch 接住；
  • stack_unwind 的 stdout 依次是 ctor=outer、ctor=inner、dtor=inner、dtor=outer、caught=boom、done：析构按构造逆序；
  • catch_by_ref 的 stdout 是 by_value=0 / by_ref=7 what=app failed：按值捕获切片，按引用保留动态类型；
  • noexcept_move 的 stdout 是 safe_moves=3 safe_copies=0 / unsafe_moves=0 unsafe_copies=3 / capacities=4,4：noexcept 移动走移动，可能抛的移动退回复制；
  • dtor_throw 在 -Werror=terminate 下编译失败，诊断指出 throw 必然调用 terminate；
  • strong_guarantee 的 stdout 是 strong_caught / strong_size=0 / basic_caught / basic_size=1 / final_size=2：强保证回到起点，基本保证留下部分修改。

16.10 下一单元从哪继续

下一单元换一种报告失败的方式：std::optional 表示“可能有值、可能没有”，std::variant 表示“几种类型中的一种”，std::expected 表示“成功值或错误值”。它们把失败放进返回类型，让调用者在类型系统里看到“这里可能没有结果”，而不是靠文档或约定。异常仍然会在真正异常的场景使用；两者不是替代关系，而是分工。

小结这一节要带走的四件事
  • 异常按值抛出、按引用捕获；catch 从具体到一般排列，重新抛出用 throw;。
  • 栈展开按构造逆序销毁局部对象，RAII 让清理自动发生；构造函数自己抛时，该对象不算构造完成。
  • 析构默认 noexcept，异常逃出会 terminate；noexcept 移动会让 vector 扩容选择移动而不是拷贝。
  • 异常安全分基本/强/不抛；copy-and-swap 用“副本上做完再交换”实现强保证，代价是复制。
自测题自测题（先自己做，再对答案）
  1. 抛出 AppError 后，catch (Error error) 与 catch (const Error& error) 调用虚函数 code() 的结果为什么不同？
  2. 栈展开时，局部对象按什么顺序析构？构造函数抛异常时，这个对象自己的析构会运行吗？
  3. 为什么析构函数默认是 noexcept？如果析构里真的抛了，会发生什么？
  4. noexcept 移动构造如何影响 std::vector 扩容？UnsafeMove 为什么走了拷贝？
  5. 强保证与基本保证的差别是什么？copy-and-swap 为什么能提供强保证，代价是什么？
注自测答案
  1. 按值捕获会把 AppError 切片成 Error 子对象，虚调用落到 Error::code()，返回 0；按引用捕获保留动态类型，调用 AppError::code()，返回 7。
  2. 按构造完成的逆序析构，后构造的先析构；构造函数自己抛异常时，该对象不算构造完成，它自己的析构不运行，但已完成的基类/成员子对象会按规则清理。
  3. 因为栈展开时不能再抛第二个异常，析构默认承诺不抛；异常真的逃出析构会调用 std::terminate，程序直接终止。
  4. vector 扩容用 move_if_noexcept：移动构造 noexcept 就移动，否则有拷贝构造就拷贝。UnsafeMove 的移动是 noexcept(false)，所以扩容选择拷贝，copies=3。
  5. 基本保证只要求对象仍有效，内容可能已改变；强保证要求失败后回到操作前。copy-and-swap 先在副本上完成修改，成功后才 swap，失败时原对象未动；代价是每次都要复制整个容器。
