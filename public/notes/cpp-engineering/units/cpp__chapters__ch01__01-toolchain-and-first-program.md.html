C 分册的第一个程序用 gcc 编译，C++ 分册的第一个程序换成 g++。这一步不只是「换一个命令」：C++ 多了一层标准库、多了名字修饰与链接约定，也多了 std::print 这类在 C 里没有的输出方式。本单元先把「源文件怎样变成一个能跑的程序」重新走一遍，再用三个最小的输出例子把 std::cout、std::format、std::print 的差别钉住。

学习目标看完这一单元，你应该能
  • 用一条 g++ 命令把单个源文件编成可执行文件，并说出 -std=c++23 在做什么；
  • 说出预处理、编译、汇编、链接四个阶段各产出什么，以及 C 与 C++ 在这一步的相同与不同；
  • 分别用 std::cout、std::format、std::print 输出同一组值，并解释三者的差别；
  • 解释本机 <print> 为什么需要 libs 里的 -lstdc++exp、运行时为什么还要固定 PATH；
  • 建起一个最小的多文件 C++ 工程（include/ + 两个 src/），说清声明与定义的分工。

1.1 先看工程长什么样

第 1 章仍然允许单文件工程：六个例子都在 examples/ch01/ 下，前五个是单文件，最后一个是多文件小工程。第 2 章起才强制每个清单至少两个 .cpp + 一个被 #include 的 .h；这一章先把「一个源文件也能跑」这件事看清楚。

第 1 帧的三个例子都只做一件事：打印一行固定文本，但分别走 std::cout、std::format、std::print 三条路。第 2 帧的 print_no_lib/ 故意不加 -lstdc++exp，让链接期失败成为可复现的证据；hello_types/ 用同一组不同类型的值验证格式化不会把类型弄错。第 3 帧的 hello_multi/ 第一次把 include/ 与 src/ 分开：hello_multi.h 只放声明，hello_multi.cpp 放定义，main.cpp 只调用。

这六个例子各自回答一个问题：hello_cout 证明「C++ 的流式输出能用」；hello_format 证明「格式化可以先得到一个字符串」；hello_print 证明「直接打印需要额外的链接与运行环境」；print_no_lib 把「少了那一步」变成可复现的链接错误；hello_types 证明「同一组值不会因为格式串写错而读错内存」；hello_multi 证明「声明与定义可以分家」。它们都不是「语法演示」，而是六个可以被闸门逐字对账的实验。

第 1 章允许单文件工程，所以前五个例子只有一个 src/main.cpp；第 2 章起硬规定③生效，每个清单至少两个 .cpp + 一个被 #include 的 .h。这不是说单文件「不专业」，而是说：从第二个项目开始，你要习惯「接口放头文件、实现放源文件、多个翻译单元一起链接」的工作方式。hello_multi 是这条路的起点。

编译命令是 g++ -std=c++23 -Wall -Wextra -Wpedantic -O0 -g hello.cpp -o hello.exe。这条命令既是编译也是链接：g++ 会在背后调用 cc1plus、as、collect2 / ld。

  • -std=c++23 选语言标准。C 分册用 -std=c17，C++ 分册用 -std=c++23；两者不是同一套标准。
  • -Wall -Wextra -Wpedantic 是本书的基础警告档；-O0 -g 让调试信息完整、优化关掉，便于对照。
  • -o hello.exe 指定目标文件名；不写时 Windows 默认是 a.exe。

先看最短的 std::cout 版本：

#include <iostream> 把 std::cout 的声明带进来；<< 是流插入运算符，把右边的字符串送进标准输出。\n 是换行字符，std::cout 不保证立刻刷新，但程序正常退出时会刷新。这个例子和 C 的 printf("hello\n") 输出一样，区别在于 << 的重载由类型决定，不需要你写格式串。

四个阶段可以画成一条链：

第 1 帧的 .ii 是预处理结果；第 2 帧的 .s 是汇编；第 3 帧的 .o 是目标文件，还缺 std::cout 的实现；第 4 帧把这些实现接上，才有可执行文件。C 与 C++ 的差别主要在第 4 帧：C++ 的标准库更大、名字经过修饰（mangling），链接器要按修饰后的名字找实现。「编译过了」不等于「链接过了」，后面的 std::print 例子就会在第 4 帧失败。

把四个阶段拆开看，每一段都有独立的失败方式：

  • 预处理只做文本替换：展开 #include、展开宏、处理条件编译。它不认识 C++ 语法，也不做类型检查；#include <iostream> 在这一步只是把几千行声明搬进你的源文件。预处理失败的典型原因是找不到头文件（fatal error: iostream: No such file or directory）或宏写错。
  • 编译把预处理结果翻成汇编或直接生成目标码。C++ 的类型检查、模板实例化、重载决议都在这一步；error: 与 warning: 大多来自这里。-std=c++23 会影响这一步接受哪些语法。
  • 汇编把汇编翻成机器码，产出 .o。这一步通常最安静；失败往往是内联汇编写错或目标架构不匹配。
  • 链接把多个 .o 与库接起来，解析符号。C++ 的函数名会被修饰成包含参数类型的名字（ABI 约定，不是 C++ 标准规定的具体拼法），所以 C 与 C++ 混编时要用 extern "C" 关掉修饰；标准库的实现也要在这一步接上。

这四段对应四种不同的错误：找不到头文件、语法/类型错误、汇编错误、undefined reference。先判断错误发生在哪一段，再决定去看什么；把链接错误当成语法错误去改源文件，是最常见的无效排查。

C 分册用 gcc，C++ 分册用 g++，这不是「换个名字」：gcc 也能识别 .cpp 并调用 C++ 前端，但它不会自动链接 C++ 标准库；g++ 会把 .cpp 当 C++ 编译，并在链接时自动加上 -lstdc++ 一类的参数。反过来，g++ 会把 .c 也当 C++ 编译，所以 C 代码要用 gcc 编、C++ 代码要用 g++ 编，别拿 gcc 去链接 C++ 程序。C 与 C++ 是两种语言：C 的 void* 可以隐式转成任意指针，C++ 不行；C 的 designated initializer 规则与 C++ 不同；这些差异会在你以后读「看起来像 C 的 C++」时冒出来。

C++ 与 C 混编时还要处理名字修饰：C++ 编译器会把 greeting 修饰成包含参数类型的内部名字，C 编译器不会。如果 C++ 要调用一个 C 库函数，C 头文件通常用 #ifdef __cplusplus extern "C" { ... } #endif 把声明包起来，关掉修饰。修饰规则是 ABI 约定，不是 C++ 标准规定的具体拼法；同一份源码在不同编译器/平台上修饰后的名字可能不同，所以不要手写修饰名，交给编译器。

1.3 三种输出方式：cout、format、print

std::cout：流式，类型安全，但拼接冗长

std::cout << a << b << c 的每个 << 都是一次重载调用，类型由编译器选；它不会像 printf 那样因为 %d 和 double 不匹配而读错内存。代价是格式化能力弱：对齐、进制、精度要配合 std::setw / std::hex / std::setprecision 等操纵符，代码容易变长。

std::cout 还有几个容易忽略的细节：<< 返回流本身，所以可以链式写；std::endl 在换行的同时强制刷新缓冲区，\n 只换行不刷新；程序正常退出时标准输出会刷新，但崩溃或 std::_Exit 不会。日志/崩溃前需要留下证据时，显式刷新（std::flush）比迷信 std::endl 更可靠；平时输出用 \n 就够了，不必每行都刷新。std::cout 与 C 的 printf 默认共享同一套缓冲区，混用时要注意刷新顺序，但这属于工程细节，本单元不展开。

std::format：先拼成字符串，再决定往哪写

std::format("format: {} {}\n", 42, "ok") 返回一个 std::string，你可以把它交给 std::cout、写进文件、放进日志。{} 是占位符，类型由实参推导；它不需要你手写 %d / %s，也不会因为格式串与参数不匹配而读错内存。

std::format 的 {} 不只是「占位」：你可以在花括号里写格式说明，例如 {:>6} 右对齐、{:.2f} 保留两位小数、{:#x} 十六进制带前缀。它返回一个 std::string，这意味着你可以先拼好再决定输出目标——写文件、进日志、放进异常消息都可以。代价是这次格式化会真的构造一个字符串对象；如果只是往终端打一行，std::print 可以少一次字符串构造。

std::format 的格式串在编译期会被检查（std::format_string 的 consteval 构造），参数数量/类型不匹配通常是编译错误；如果你把格式串作为运行期字符串传进去，就会走 std::vformat 那条路，检查退到运行期并可能抛 std::format_error。「编译期检查」不是无条件保证，取决于你用哪个入口。

std::print：直接写到标准输出，链接要额外库

std::println("hello, print: {}", 42) 直接输出并换行，不用先建字符串、也不用 std::cout <<。它是 C++23 的 <print> 设施；在本机 MSYS2 UCRT64 的 g++ 上，只写 #include <print> 能编译，但链接会失败，必须加 -lstdc++exp。

清单里因此多了 libs 与 env 两个字段：libs 写 ["-lstdc++exp"]，env 把 PATH 钉到 C:/msys64/ucrt64/bin;C:/msys64/usr/bin;C:/Windows/System32。libs 让闸门把库放在源文件之后再 -o，静态库顺序才正确；env 把 PATH 钉到干净的 MSYS2 路径，运行时才能加载到配套的 libstdc++ DLL。两件事缺一不可：只加库、不钉 PATH，本机会以 3221225785 退出（加载到别的 DLL）；只钉 PATH、不加库，链接期就过不去。

编译器视角编译器视角：为什么要看得懂链接错误

编译错误会告诉你「哪一行、哪个语法不对」；链接错误只会告诉你「哪个符号没找到」。undefined reference to 'std::__open_terminal(_iobuf*)' 里的名字虽然长，但它指向一个具体的实现，不是你的代码拼错了。看到 ld.exe / collect2 字样，先分清楚这是链接期，再去查「这个符号应该由哪个库提供」。C 分册的 nm 与 ld 那一节讲的就是这套排查方法；C++ 只是把符号名换成了修饰后的形式。

三种输出怎么选

方式 产出 格式能力 额外条件 适合
std::cout 直接写标准输出，返回流 基础，复杂格式靠操纵符 无 简单拼接、已有流对象
std::format 返回 std::string 强，{} + 格式说明 无 先拼字符串、写文件/日志
std::print 直接写标准输出 强，与 format 同语法 本机要 -lstdc++exp + PATH 终端输出、少一次字符串构造

这张表不是「谁更好」的排名，而是「你的输出目标是什么」的选择：要字符串就 format，要终端就 print，已经在用流就 cout。三种方式都依赖同一套 {} 格式化语法（cout 除外），学会一种，另外两种的格式说明可以直接迁移。

格式说明也不必背：{:>6} 右对齐到 6 列、{:<6} 左对齐、{:^6} 居中、{:.2f} 两位小数、{:#x} 十六进制带 0x、{:08.2f} 补零到 8 列。C 的 printf 用 %6d / %-6d / %.2f 表达同一组意图，但 C++ 的写法把「哪个参数」交给位置，格式说明只描述「这个参数怎么显示」。参数顺序由 {} 的顺序决定，不再靠格式串里 %d 的个数去对齐实参；这也是它更不容易错位的原因。

1.4 第一个多文件工程：声明与定义分家

单文件跑通之后，把 greeting() 拆到另一个 .cpp：

编译命令要把两个 .cpp 一起交给 g++：g++ -std=c++23 -Wall -Wextra -Wpedantic -O0 -g -Iinclude src/main.cpp src/hello_multi.cpp -o app.exe。-Iinclude 告诉编译器去哪里找 "hello_multi.h"。两个 .cpp 各自编译成一个 .o，链接器把 main.o 里对 greeting() 的调用接到 hello_multi.o 的定义上。声明让编译器知道「这个名字长什么样」，定义让链接器找到「它的实现在哪」；两者分开，才有「改一个文件、只重编一个文件」的可能。

头文件里的 #ifndef HELLO_MULTI_H / #define / #endif 是 include guard：同一个翻译单元里第二次 #include 同一份头文件时，宏已经定义，内容会被跳过去。没有 guard，一个 .cpp 里两次间接包含同一个头文件，就可能把同一个类/函数声明定义两遍。#pragma once 是常见替代，语义更简单，但它是编译器扩展，不是标准；本书统一用 guard，原因是 C 与 C++ 共用同一套头文件纪律，也方便你以后读别人的代码。

头文件里能放什么、不能放什么，也有边界：声明（函数、类、模板、extern 变量）可以放；inline 函数、constexpr 变量、类内定义的成员函数可以放；普通函数定义、普通全局变量定义不能放（会违反 ODR，链接期重复定义）。头文件会被多个翻译单元各包含一次，任何「只能有一份」的东西都不能直接写进去。 这条规则在第 9 单元会展开；本单元先记住 greeting() 的声明在 .h、定义在 .cpp，这是最常用也最不容易错的分工。

分开编译还可以用 -c 单独产出目标文件：g++ -c src/main.cpp -o main.o 与 g++ -c src/hello_multi.cpp -o hello_multi.o，最后 g++ main.o hello_multi.o -o app.exe。这正是构建脚本在做的事：编译是一份文件一份文件地做，链接是把所有 .o 与库接起来。改 hello_multi.cpp 只需重编它自己，main.cpp 的目标文件可以复用。代价是你要维护「哪些文件参与链接」这份清单，漏一个就 undefined reference，多一个就可能重复定义。

build.sh 的最小形态可以只有三行：删旧产物、逐个编译、链接。真正工程化的构建脚本还会加依赖检查、增量编译、错误即停（set -e）、清理目标等；本机没有 make/cmake，所以本书用脚本 + 清单固定命令，不引入额外构建系统。脚本的价值不是「少打几个字」，而是让「同一份源码怎样变成同一个可执行文件」可复现；这对后面讲 ODR、多模块、测试都是地基。

第 1 帧：两个 .cpp 都看见了声明，所以编译期都知道 greeting 的名字和签名。第 2 帧：定义只出现在 hello_multi.cpp 里，链接器把 main.cpp 的调用接过去。如果头文件里写函数定义（而不是声明），两个翻译单元就会各生成一份，链接期报重复定义——这是 C++ 分册第 9 单元（ODR）要展开的事。

1.5 类型安全：格式化不会把 double 读成 int

C 的 printf("%d", 3.5) 是未定义行为：格式串说「读一个 int」，实参却是一个 double，调用约定对不上。C++ 的 std::format / std::print 用 {} 占位符，类型由实参推导，不会出现「格式串说一套、实参是另一套」的错位。

本机输出 int=7 double=3.5 text=ok。7 是 int，3.5 是 double，"ok" 是字符串字面量；占位符按顺序绑定，编译器在编译期检查参数数量与格式串。这不是「C++ 比 C 聪明」，而是两套接口的契约不同：printf 把类型信息放在运行期的格式串里，std::format / std::print 把类型信息放在编译期的重载/模板里。

C 的 printf("%d", 3.5) 是未定义行为：格式串要求一个 int，实参却是 double，可变参数调用不会帮你转换，函数会按 int 的读法去取那 8 个字节的一部分，结果不可预测。编译器可能会给 -Wformat 警告，但它不是语言层面的类型检查；关掉警告或换一个调用点，程序照样能编出来。std::format / std::print 的 {} 不需要你声明类型，类型由实参推导；格式串写错（参数数量不对、占位符语法不对）通常在编译期就报错。这不是「C++ 更安全」的空话，是「类型信息放在哪一层」的直接结果。

但 std::format 也不是万能的：格式串里仍然可以写 {:d} 要求整数，传一个 std::string 就会编译失败；运行期格式串（std::vformat）会把检查推迟到运行期，可能抛 std::format_error。所以「用了 std::format 就绝不会格式错」是过度承诺；准确的说法是：在格式串是编译期常量、参数类型匹配的前提下，错误会在编译期暴露。

编译警告也值得单独说：-Wall 不是「所有警告」，-Wextra 补一批，-Wpedantic 再要求严格符合标准；三者都打开，仍然有警告不在其中。本单元不靠「记住每个开关」来写代码，而是靠闸门把基础档的真实输出钉住：同一份源码，警告要么出现、要么不出现，正文不能凭印象写。看到警告先读它指向的行与条件，不要用 -Wno-* 把它关掉；本书的清单也不允许关警告。

语法规则本单元的编译命令
  • 单个源文件：g++ -std=c++23 -Wall -Wextra -Wpedantic -O0 -g hello.cpp -o hello.exe
  • 多个源文件：g++ ... -Iinclude src/main.cpp src/hello_multi.cpp -o app.exe
  • 需要 <print>：在清单 libs 里写 ["-lstdc++exp"]，并用 env 固定 MSYS2 PATH
  • 只看预处理：g++ -std=c++23 -E hello.cpp -o hello.ii
陷阱`<print>` 不是「写了 include 就能跑」

新手最容易把「编译通过」当成「程序没问题」。#include <print> 只保证声明可见；std::println 的实现体在 libstdc++exp 里，链接期才需要它。本机的两个条件——-lstdc++exp 与干净 PATH——缺一个都跑不起来，而且报错位置完全不同：缺库是链接期 undefined reference，缺 PATH 是运行期 3221225785。看到 undefined reference 先查库；看到程序一启动就退出，先查运行环境。

工程惯例工程惯例：把编译命令固定下来

单文件时手敲 g++ 没问题；多文件时命令会越来越长，参数顺序、-I 路径、库名都容易漏。工程上的做法是把命令写进 build.sh 或清单，让「怎么编」成为可复现的事实，而不是某次终端里的记忆。C 分册第 7 章已经用过 build.sh；C++ 分册第 9 单元会把多文件、ODR 与构建脚本一起收口。

1.6 编译错误与链接错误怎么读

编译错误的形状是 文件:行:列: error: 说明，下面通常跟着一行源码和 ^ 指到具体位置。读它的顺序是：先看第一个 error（后面的错误经常是它的连锁反应），再看文件/行号是不是你改的那一处，最后看 error: 后面的动词（expected、no matching function、cannot convert）——它比整句英文更直接。修完一处就重编，不要一次改十处；否则新的错误会混进旧的噪音里。

链接错误的形状是 undefined reference to '符号' 或 multiple definition of '符号'。它没有行号，因为问题不在某一行，而在「所有目标文件与库的集合」。先看符号属于谁：greeting 是你自己的函数，就查「定义它的 .cpp 有没有参与链接」；std::__open_terminal 是库函数，就查「清单有没有写对应的 libs」。collect2.exe: error: ld returned N exit status 只是转述，不是根因；真正的根因在它上面的 undefined reference / multiple definition 行。

C 分册讲过：本机默认 PATH 下，ld 的诊断可能只剩 collect2 一行。C++ 的 <print> 例子用干净 PATH 把完整诊断钉住了；你以后遇到「只有一行 collect2」时，换干净 MSYS2 PATH 或直接看 nm，不要猜。

遇到看不懂的编译/链接错误，做一个最小复现：把出问题的代码删到只剩一个文件、一个函数、一个最小调用，确认错误还在；再逐项加回选项（-std、-Wall、-I、libs、env），看哪一项让错误出现/消失。最小复现不是「浪费时间删代码」，而是把「环境、选项、源码」三个变量分开；本单元 print_no_lib 就是这样一个最小复现：同一份源码，只差清单里的 libs。

1.7 本机工具链边界：标准、实现与实验条件

本书的 C++ 工具链是 MSYS2 UCRT64 的 g++ 16.1.0，标准 C++23。本机探测结果里有三条边界，写作者和读者都要知道：

  • <print> 需要 libs: ["-lstdc++exp"]，运行时还要用 env 固定干净的 MSYS2 PATH；这是本机实现的链接/运行条件，不是 C++ 标准的要求；
  • <modules> 在本机不可用（#include <modules> 直接报找不到头文件），所以本分册不教 modules，也不写「理论上可以」；
  • <stacktrace> 能链接（同样需要 -lstdc++exp）但本机只给 4 帧、首帧是 register_frame_ctor，符号质量不足以教学，只在工具链事实里记录，不放进正文例子。

标准要求 / 本机实测 / 工程惯例三分在这里第一次出现：std::print 是 C++23 标准设施（标准要求）；本机要加库、钉 PATH（本机实测）；把编译命令写进清单/脚本、头文件用 include guard（工程惯例）。三者不要混写成一句「C++ 就是这样」。

1.8 把第一个程序放进工程

单文件程序可以手敲命令，但工程里要固定下来。至少做三件事：

  1. 命令进脚本：把 g++ -std=c++23 -Wall -Wextra -Wpedantic -O0 -g ... 写进 build.sh 或清单，不要依赖终端历史；
  2. 头文件纪律：声明放 .h，定义放 .cpp；头文件用 include guard；不要在头文件里写 using namespace std;，也不要用 #include <bits/stdc++.h> 这种非标准汇总头；
  3. 入口简单：main 返回 int，正常结束写 return 0;（也可以省略，标准会隐式返回 0）；需要命令行参数时再用 int main(int argc, char** argv)。

#include <bits/stdc++.h> 在竞赛环境常见，但它不是标准头，换一个标准库就可能没有；本书不用它。using namespace std; 在 .cpp 里偶尔用可以，在头文件里会污染所有包含它的翻译单元，所以头文件里禁止。这些不是语法错误，而是「让别人能接手」的工程惯例；第 9 单元会把它们和 ODR 一起收口。

build.sh 的骨架可以写成：set -e（任何一步失败就停）、rm -f app.exe、g++ -std=c++23 ... src/main.cpp src/hello_multi.cpp -o app.exe。命令里的每个参数都有理由：-std 固定标准，-Wall -Wextra -Wpedantic 固定警告档，-Iinclude 固定头文件搜索路径，-O0 -g 固定调试档。不要用「上次能编过」当理由省略参数；换一台机器、换一个终端，默认值就可能不同。

这一单元只解决了「程序能编、能链、能输出」。下一单元 1.2 引用、const 与命名空间 会把注意力从工具链移到语言本身：C++ 的引用为什么必须初始化、const T& 为什么能接临时对象、命名空间怎样避免名字冲突。它们看起来是三个独立话题，其实都在回答同一个问题：一个名字在 C++ 里到底绑定到哪块存储、哪个作用域、哪份定义。

小结这一节要带走的五件事
  • C++ 与 C 共用预处理/编译/汇编/链接四阶段，但驱动换成 g++，链接期要接 C++ 标准库。
  • std::cout 是流式输出；std::format 先返回字符串；std::print 直接写标准输出。
  • 本机 <print> 需要 libs: ["-lstdc++exp"]，运行时还要用 env 固定干净的 MSYS2 PATH。
  • 多文件工程把声明放头文件、定义放 .cpp，-Iinclude 与「两个 .cpp 一起编」缺一不可。
  • std::format / std::print 的 {} 按实参推导类型，不会出现 printf 的格式串错位。
自测题自测题（先自己做，再对答案）
  1. g++ -std=c++23 hello.cpp -o hello.exe 这条命令里，编译与链接分别由谁完成？
  2. std::cout、std::format、std::print 三者的返回值/输出目标有什么不同？
  3. 本机 <print> 只写 #include <print> 时，编译能过吗？链接能过吗？为什么？
  4. print_no_lib 的 undefined reference 与「拼写错误」有什么区别？看到它应该先查什么？
  5. hello_multi 为什么要同时编译 src/main.cpp 与 src/hello_multi.cpp？只编 main.cpp 会怎样？
注自测答案
  1. g++ 是驱动程序：它先调用编译器前端/汇编器生成目标文件，再调用链接器把目标文件与 C++ 标准库接起来。你只敲一条命令，但两个阶段都发生了。
  2. std::cout << ... 直接写标准输出，返回流对象；std::format(...) 返回一个 std::string，不直接输出；std::print / std::println 直接写标准输出，返回 void（或流状态，随标准库实现）。
  3. 编译能过（头文件提供了声明），链接不能过：std::println 的实现需要 -lstdc++exp，否则报 undefined reference to std::__open_terminal / std::__write_to_terminal。再加上运行时的干净 PATH，才完整。
  4. 拼写错误是编译期「这个名字不存在」；undefined reference 是链接期「名字存在，但找不到实现」。先查「这个符号应该由哪个库提供」，而不是改源文件的拼写。
  5. 因为 greeting() 的定义在 hello_multi.cpp 里；只编 main.cpp 会得到「声明可见、定义缺失」的链接错误。两个 .cpp 一起交给 g++，链接器才能把调用接上。
