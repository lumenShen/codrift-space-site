C 分册里，函数想改调用者的变量，只能把地址传进去；C++ 多了一条更直接的路：引用。引用看上去像“自动解引用的指针”，但两者的规则并不一样——引用必须绑定、绑定后不能换、语言里没有“空引用”这个值。围绕引用，const 又引出一串新问题：const int* 和 int* const 锁住的到底是谁？const T& 为什么能接一个临时对象？临时对象能活多久？最后，这些名字都住在哪个作用域里，由命名空间回答。

这一单元不碰类，也不碰模板；它只把 C++ 最底层的四件事钉住：引用怎么绑定、const 锁住谁、临时对象活多久、名字在哪个作用域里找。这四件事在后面每一个单元都会出现，所以例子都尽量小，每个结论都用真实输出或真实诊断顶着。

学习目标看完这一单元，你应该能
  • 说出引用与指针的三条硬差别，并用 sizeof 与 &r == &a 的读数证明引用不是“另一个指针变量”；
  • 解释 const T& 的只读契约，并说清临时对象在“变量初始化”和“函数传参/返回”两种场景下活得一样不一样；
  • 分清 const int*、int* const、const int* const 各自锁住什么，能判断一行赋值该不该编译；
  • 解释返回局部变量引用的程序为什么在 C++23 下直接编译失败，并给出安全的替代写法；
  • 用命名空间与 using 声明组织同名函数，并说清头文件里为什么不该写 using namespace。

2.1 先看工程长什么样

这一单元仍然在 examples/ch01/ 里加例子。第 1 章允许单文件工程，所以六个例子都只有一个 src/main.cpp；到第 2 章，硬规定③才会要求每个清单至少两个 .cpp 加一个被 #include 的 .h。这里先把“一个源文件也能把规则讲清”这件事做扎实。

第 1 帧只有 ref_basics/，它把“引用传参”和“指针传参”放在同一个程序里对照：两者都能改到实参，但调用点的写法与可空性不同。第 2 帧加上 const_ref/（const T& 接临时对象）、const_ptr/（两种 const 位置）与 ref_return/（返回局部变量的引用，故意编不过）。第 3 帧加上 namespace_demo/（两个命名空间的同名函数）与 using_scope/（using 声明的作用域到哪里结束）。

这六个例子不是“语法清单”，而是六次对照实验：ref_basics 用地址比较回答“引用是不是独立变量”；const_ref 用构造/析构顺序回答“临时对象活多久”；const_ptr 用两行合法赋值回答“const 锁住谁”；ref_return 用真实诊断回答“为什么不能返回局部引用”；namespace_demo 与 using_scope 用两个同名函数和一个块作用域回答“名字在哪里找”。

2.2 引用不是指针：必须绑定，不能换绑

先看引用传参与指针传参的并排对照：

三行输出各回答一个问题。a=99 b=21 说明引用传参和指针传参都改到了调用者的变量；same=yes 说明 &r 取到的是 a 的地址，r 没有自己的存储；sizeof_ref=4 sizeof_ptr=8 说明 sizeof(int&) 量的是“被引用的 int”，不是“一个指针变量”。

引用在语言层面不是对象，是已有对象的另一个名字。 因此：

  • 声明引用时必须初始化：int& r; 直接编译失败；指针可以先声明后赋值；
  • 引用绑定后不能换绑：r = b; 不是“让 r 改指 b”，而是“把 b 的值写进 r 绑定的那个对象”，也就是写进 a；
  • 没有“空引用”这个值：引用必须绑定到一个对象或函数；指针可以是 nullptr。

这三条差别决定了接口设计。收引用 int& 的函数默认假设“你一定会给我一个对象”，所以函数里不需要判空；收指针 int* 的函数可以接受 nullptr，所以函数里必须先判空。反过来说，调用点看到 add_one_ref(a) 时，看不出 a 会不会被改；看到 add_one_ptr(&b) 时，& 明确提示“地址被交出去了”。引用更简洁，指针更显眼；选哪个，取决于你想让调用者看到什么契约。

第 2 帧的 r 不是“指向 a 的箭头”，而是“a 的别名”；&r == &a 是它最直接的证据。第 3 帧的 p 才是一个独立变量：它自己占 8 个字节，里面装 a 的地址，所以 p 可以被重新赋值去指别人。把这两帧摆在一起看，就不会再说“引用就是自动解引用的指针”——语法上像，语义上不是。

第 2 帧里 value 没有新增一个盒子，它只是 a 的另一个名字；所以 ++value 改的就是 a。这也是引用传参比指针传参少一次“解引用”动作的原因——编译器在背后仍然传地址，但语言把它包装成“直接使用对象”。

标准原文标准原文：引用必须初始化，且不能换绑

A variable whose declared type is “reference to T” shall be initialized. … A reference cannot be changed to refer to another object after initialization.

大意：声明为“T 的引用”的变量必须初始化；初始化之后，引用不能再改成指向另一个对象。给引用赋值，改的是被引用的那个对象。

出处：N4950 §9.4.4「References」（[dcl.init.ref]）。

陷阱把 `r = b` 当成“让 r 改指 b”

你会看到：int& r = a; r = b; 之后，a 变成了 b 的值，r 仍然和 a 绑定。新手会以为 r 现在指向 b，于是后面通过 r 修改时，意外改到了 a。真相是：引用初始化后不能换绑；这行赋值等价于 a = b;。要让“指向谁”可变，用指针；要让“这个名字永远指这个对象”，用引用。

2.3 const T&：只读契约与临时对象的寿命

const T& 是 C++ 里最常见的参数类型。它同时表达两件事：函数不会通过这个引用修改对象；它可以绑定临时对象。

const Tracker& bound = Tracker("bound"); 里，Tracker("bound") 先构造一个临时对象；const Tracker& 绑定它之后，这个临时对象的寿命被延长到 bound 的作用域结束。所以 name=bound 能读到名字，dtor bound 直到 main 结束才出现。如果写成非 const 的 Tracker& bound = Tracker("bound");，编译就过不去——非 const 引用不能绑定临时对象。

longer("hi", "longer") 更微妙：两个字符串字面量先各自构造一个临时 std::string，绑定到两个 const std::string& 形参；longer 返回其中一个的引用。这个引用在函数返回后仍然指向那个临时对象，而临时对象要活到“包含这次调用的完整表达式”结束——也就是这一整条 std::cout << ... << "\n"; 执行完。在同一个表达式里立刻用掉是安全的；一旦把它存进变量、留到下一行，就是悬空引用。

标准原文标准原文：函数参数的临时对象活到完整表达式结束

A temporary object bound to a reference parameter in a function call persists until the completion of the full-expression containing the call. … The lifetime of a temporary bound to the returned value in a function return statement is not extended; the temporary is destroyed at the end of the full-expression in the return statement.

大意：绑到函数引用参数上的临时对象，活到“包含这次调用的完整表达式”结束；绑到返回引用上的临时对象，寿命不会延长，返回语句所在的完整表达式一结束就销毁。

出处：N4950 §6.7.7「Temporary objects」（[class.temporary]）第 6.9、6.11 条。

这段标准原文解释了两件事。第一，longer("hi", "longer") 的两个临时实参在整条输出语句结束前都活着，所以 longer 返回的引用在这一刻有效。第二，如果 longer 返回的是“函数内部创建的临时对象”的引用，那个临时对象在 return 语句结束时就销毁了，调用者拿到的是悬空引用。“const 引用能接临时对象”和“临时对象能活很久”是两件事；前者是绑定规则，后者要看绑定发生在哪里。

第 1 帧的延长规则只适用于“用临时对象初始化一个引用变量”；第 2 帧的形参绑定只保证到完整表达式结束，不保证到函数返回之后。把这两帧分清，就不会写出“函数返回 const T&，调用者长期保存”的悬空代码。

const T& 的“只读”也不是装饰：它让函数体里对参数的修改直接编译失败，调用者不用读函数实现就能知道“这个参数不会被改”。代价是它可能绑定一个临时对象（多一次构造），也可能绑定一个长期对象（零拷贝）；函数内部无法假设参数一定指向长期存储。接口写 const T&，是在说“我只看，不拥有，也不保证你传进来的是长期对象”。

2.4 顶层 const 与底层 const：谁被锁住

const 放在 * 的哪一边，锁住的东西完全不同：

  • const int* p：p 是“指向 const int 的指针”。被锁住的是 *p——不能通过 p 写 a；但 p 自己可以改指 b。所以 p = &b; 合法，输出 *p=2。
  • int* const q：q 是“const 指针，指向 int”。被锁住的是 q 自己——不能改指别人；但可以通过 q 写 a。所以 *q = 5; 合法，输出 *q=5、a=5。

用“谁不能变”来判断最稳：const 紧挨着 int，锁的是被指对象；const 紧挨着变量名（在 * 右边），锁的是指针变量本身。两者都锁就是 const int* const p：既不能改指，也不能通过它写对象。读声明时从变量名往外读：q 是 const 的指针，指向 int；p 是指针，指向 const int。

顶层 const / 底层 const 是术语，记不住也没关系，记住“锁谁”就行。 顶层 const 修饰对象本身（如 int* const q 里的 q），底层 const 修饰指针/引用所指的类型（如 const int* p 里的 int）。函数重载、模板推导、auto 推导时，顶层 const 常常被丢掉，底层 const 会保留——这个差别在第 14 单元讲 auto 时会再出现。

大白话大白话：引用与 const 的“门牌”

把对象想成一间房，引用就是“这间房的另一个门牌”，钉上去之后不能换到别的房；指针是一张写着房间号的纸条，纸条可以换成别的号，也可以空着。const int* 是“纸条上的房间你不能改里面的东西”，int* const 是“纸条本身被胶水粘死了，不能换号”。两种限制互不替代；写代码前先问：我要锁的是房间，还是纸条？

诊断说的不是“局部变量不能返回”，而是“int& 不能绑定到一个右值”。C++23 的隐式移动规则要求：return 的表达式如果是一个局部变量，先按右值处理；返回类型是非 const 左值引用 int& 时，右值绑不上左值引用，于是编译失败。这条规则把一类悬空引用从“运行期才炸”提前到了编译期，是 C++23 相对早期标准的一个实际改进（规则见 N4950 §11.9.6，[class.copy.elision]）。

即使把返回类型改成 const int& 让编译通过，问题也没有消失：函数返回后 local 已经销毁，引用指向一块失效的栈内存；读它属于未定义行为。编译器可能给 -Wreturn-local-addr 警告，也可能什么都不说。判据不是“编过了”，而是“引用指向的对象在调用者使用时还活着吗”。

安全的返回方式只有三种：返回值（拷贝或移动，让调用者拥有自己的对象）；返回引用，但引用指向调用者传入的对象、全局对象或生命周期明确更长的对象；返回指针并明确约定所有权与空值。函数返回 const std::string& 时，如果它返回的是某个形参的引用，调用者只能在“包含这次调用的完整表达式”里用——这就是 2.3 节 longer 的边界。

编译器视角编译器视角：读“不能绑定”这类诊断

cannot bind non-const lvalue reference of type 'int&' to an rvalue of type 'int' 这句话可以拆成三段：int& 是函数声明的返回类型；local 在 return 里被当成右值；右值不能初始化非 const 左值引用。它没有说“local 生命周期结束”，因为编译器在类型检查阶段就拦住了，根本走不到生命周期分析。看到 cannot bind 先看两边的类型与值类别，不要先去改生命周期。

2.6 命名空间：同名函数怎样不打架

两个模块都想提供一个叫 code 的函数，一个把颜色编号翻成十六进制，一个把状态编号翻成 HTTP 码。直接放在全局作用域会重定义；放进两个命名空间就各自独立：

color::code 与 status::code 是两个不同的全名；using color::code; 只是把 color::code 这一个名字引进 main 的作用域，所以后面写 code(1) 等价于 color::code(1)。status::code(1) 仍然要写全名，因为 status::code 没有被引进来的话，code 在 main 里只指 color::code 这一个候选。

std::cout 也是同样的道理：std 是一个命名空间，cout 是里面的一个名字，<iostream> 把声明放进去。你写 std::cout 是“用全名”，写 using std::cout; 是“把这一个名字引进当前作用域”，写 using namespace std; 是“把 std 里的所有名字都放进查找范围”。三者不是一回事。

using 声明有明确的作用域边界：

块内的 using cfg::retries; 只在这个块里有效；出了块，retries 这个名字不再指向 cfg::retries，所以后面可以声明一个局部变量 int retries = 7;。如果 using 放在 main 的作用域（块外），再在同一个作用域声明同名局部变量就会冲突。using 不是“把名字复制过来”，而是“在当前作用域里增加一条查找路径”；路径随作用域结束而失效。

第 2 帧的 using 只加了一条从 main 到 color::code 的查找路径，没有把 status::code 也拉进来；所以 code(1) 没有歧义。若同时 using color::code; using status::code;，再写 code(1)，查找会同时命中两个声明，编译期报歧义——这不是“运行时选一个”，而是“编译期拒绝猜”。

工程惯例工程惯例：头文件里不写 `using namespace`

using namespace std; 放在 .cpp 的函数里，影响范围有限；放在头文件的全局作用域，会污染所有包含它的翻译单元，别人写 count、distance、size 时可能撞上 std 里的同名模板。这是惯例，不是标准禁令：标准没有禁止你写，但工程上通常禁止，因为头文件会被很多文件包含，影响面不可控。本书的规矩是：头文件里只用全名（std::string），源文件里可以在函数内用 using std::cout; 这类窄范围声明。

2.7 本机实测：四个读数

实验记录本机实测：引用、const 与命名空间

工具链：g++ 16.1.0，标准 C++23，固定 -Wall -Wextra -Wpedantic -O0 -g。

  • sizeof(int&) 输出 4，sizeof(int*) 输出 8：引用不是独立的指针变量；
  • &r == &a 输出 same=yes：引用与实参共享同一地址；
  • const Tracker& bound = Tracker("bound"); 的输出顺序是 ctor bound → name=bound → dtor bound：临时对象被延长到作用域结束；
  • ref_return 编译退出码非 0，诊断是 cannot bind non-const lvalue reference of type 'int&' to an rvalue：C++23 在编译期拒绝返回局部变量的非 const 引用。

2.8 把规则变成工程习惯

引用、const、命名空间这三件事，落到工程上就是几条可执行的约定：

  1. 只读参数用 const T&：大对象不复制；函数体不能改；能接临时对象。小标量（int、double、指针）直接按值传，引用不会更快，反而多一层间接。
  2. 要改实参用 T&，要可空用 T*：T& 的契约是“一定有对象”，T* 的契约是“可能为空”。不要把 T* 一律换成 T&，也不要用 T& 接一个可能不存在的对象。
  3. 不要返回局部变量或临时对象的引用：返回值让调用者拥有对象；返回引用就要求对象活得比调用长；两者不能兼得时，选返回值。
  4. 头文件里用全名，源文件里窄范围 using：头文件不写 using namespace；using std::string; 放在 .cpp 的函数里，影响面最小。
  5. 命名空间按模块分，不按“工具”分：color::、status:: 这种按领域分比 utils:: 更耐放；名字冲突时，先想“这个函数属于哪个概念”，再想“要不要改个名”。

const 与 constexpr 的区别这里只点到：const int n = 5; 表示“n 不可修改”，但 n 不一定能在编译期求值；constexpr int n = 5; 表示“n 是常量表达式”，可以用在 static_assert、数组长度等需要编译期常量的地方。第 18 单元会把 constexpr / consteval 单独讲透；现在只要不把两者当成同义词。

2.9 下一单元从哪继续

这一单元解决的是“名字绑定到哪、const 锁住谁、临时对象活多久”。下一单元 2.1 类与 RAII 会把这三件事放进一个类里：构造函数建立不变量、析构函数确定性地释放资源、拷贝构造决定“复制一个对象”到底复制什么。引用与 const 会以成员函数、const 成员函数、构造参数的形式再次出现；命名空间则用来给类与工厂函数分家。

小结这一节要带走的五件事
  • 引用必须初始化、不能换绑、没有空值；&r == &a 与 sizeof(int&) == sizeof(int) 证明它没有独立存储。
  • const T& 是只读契约；用临时对象初始化引用变量会延长寿命，函数参数的临时对象只活到完整表达式结束。
  • const int* 锁住被指对象，int* const 锁住指针本身；读声明时看 const 紧挨着谁。
  • 返回局部变量的非 const 引用在 C++23 下直接编译失败；安全的返回方式是返回值，或返回生命周期更长的对象的引用。
  • 命名空间给名字分组；using 声明只把指定名字引进当前作用域，头文件里不写 using namespace。

  1. int& r = a; r = b; 之后，a 和 r 分别变成什么？r 会改绑到 b 吗？
  2. 为什么本机 sizeof(int&) 是 4 而不是 8？这个读数说明了什么？
  3. const Tracker& bound = Tracker("bound"); 中临时对象的析构发生在什么时候？如果换成函数参数 f(Tracker("bound"))，析构又发生在什么时候？
  4. const int* p 与 int* const q 各自能不能改指、能不能通过它改写对象？用两行合法赋值证明。
  5. 返回 int& 指向局部变量的函数，为什么在本机 C++23 下编不过？如果改成 const int& 让编译通过，运行时还有没有问题？
注自测答案
  1. r 仍是 a 的别名，这行等价于 a = b;；所以 a 变成 b 的值，r 读到的也是这个新值。引用初始化后不能换绑。
  2. sizeof 作用于引用时，量的是被引用类型的大小；int 是 4 字节，所以结果是 4。指针变量本身是 8 字节（本机 64 位），但引用不是独立变量，没有自己的 8 字节。
  3. 绑定到引用变量的临时对象活到该引用的作用域结束，所以 bound 离开作用域时才析构；作为函数实参的临时对象活到包含这次调用的完整表达式结束，通常就是这条语句末尾。
  4. const int* p = &a; p = &b; 合法（改指），但 *p = 5; 非法；int* const q = &a; *q = 5; 合法（改写对象），但 q = &b; 非法。前者锁对象，后者锁指针。
  5. C++23 的隐式移动规则把 return local; 里的局部变量按右值处理，int& 不能绑定右值，所以编译失败。改成 const int& 后编译可能通过，但返回的引用指向已销毁的局部变量，运行时读它是未定义行为。
