这是 C++ 分册的第一个「对象生命周期」单元，也是全书第 4 单元。它要回答一个 C 语言里没有的问题：一个对象被复制、被搬走、被销毁时，到底发生了什么？ C 的 struct 赋值是逐字节复制；C++ 允许你在复制之外再定义一条「搬走」的路——移动。移动不是语法糖，它决定了资源（堆内存、文件句柄）归谁所有。

学习目标看完这一单元，你应该能
  • 说出拷贝构造与拷贝赋值各在什么时候调用，并用计数证明；
  • 解释 std::move 只是 static_cast<T&&>，并指出真正搬资源的是哪个函数；
  • 说出 moved-from 对象的标准状态，并给出一个「本机读数是空、但标准不保证」的例子；
  • 用 -Wpessimizing-move 解释 return std::move(local) 为什么反而阻止优化；
  • 按 Rule of Five 写出一个资源类的五个特殊成员函数，并说明 noexcept 移动构造对 vector 扩容的影响。

C 分册里，结构体赋值就是逐字节复制：b = a; 之后两个结构体各有一份字节，谁也不欠谁。这个模型在成员都是值、没有堆资源时够用；一旦成员是一个「拥有堆内存的指针」，逐字节复制就只复制了地址，两个对象会指向同一块内存。C++ 把「复制」与「搬走」拆成两个可编程的入口：拷贝构造 / 拷贝赋值负责「再要一份」，移动构造 / 移动赋值负责「把这一份交出去」。这一单元不追求把 C++ 的拷贝语义讲全，而是用八个可运行的对照实验，把「什么时候复制、什么时候搬、搬完源对象是什么状态」这三件事钉死。

4.1 先看工程长什么样

本单元的例子仍然在 examples/ch02/ 下。为了把「拷贝」与「移动」的每个侧面都单独验证，这里有 8 个多文件小工程，每个目录都是 include/<例名>.h + src/main.cpp + src/<例名>.cpp + <例名>.json。第 2 章起，硬规定③生效：不允许单文件工程——每个清单至少两个 .cpp，并且至少一个 .h 被某个源文件 #include 进来。

第 1 帧只有 copy_basics/，它用计数告诉你「拷贝构造」和「拷贝赋值」是两次不同的事件。第 2 帧加上 move_is_cast/（std::move 只是类型转换）、moved_from/（被搬走之后还剩什么）、rvo_counter/（返回值优化）与 pessimizing_move/（一个会让编译器警告的坏习惯）。第 3 帧加上 rule_of_five/（五个特殊成员函数）、shallow_copy_bug/（默认拷贝导致双重释放）与 vector_realloc/（noexcept 移动构造如何影响容器扩容）。每个目录里的 include/ 与 src/ 分家方式与 C 分册相同：声明放头文件，定义放源文件。

把这八个目录当成八次对照实验，每次只改变一个变量：

  • copy_basics/：只数拷贝构造与拷贝赋值的次数，证明它们是两个入口；
  • move_is_cast/：用两个 describe 重载证明 std::move 只改变值类别，不搬对象；
  • moved_from/：把 string 与 vector 搬走，观察源对象在本机还剩什么；
  • rvo_counter/：同一份源码，默认与 -fno-elide-constructors 两份清单，对照 RVO/NRVO 的计数；
  • pessimizing_move/：一个 return std::move(local)，让 -Werror=pessimizing-move 把它变成编译失败；
  • rule_of_five/：一个真正拥有 new char[] 的类，五个特殊成员函数各走一遍并计数；
  • shallow_copy_bug/：故意不写拷贝构造，让默认浅拷贝把程序送进双重释放；
  • vector_realloc/：noexcept 移动构造与不带 noexcept 的移动构造，对照 vector 扩容时选移动还是拷贝。

这八个例子都不靠「看代码猜结论」：每个结论都有一条真实输出或退出码在后面顶着。第 2 章起不允许单文件工程，所以每个例子都有 main.cpp 与一个实现 .cpp，头文件只放声明；这样你也能顺带看到「声明与定义分家」在 C++ 里是怎么落地的。

4.2 拷贝构造与拷贝赋值：两次不同的事件

先看一个最小的计数类。它只有一个 std::string 成员，不拥有堆资源，因此默认的拷贝行为是对的；我们只是把「拷贝构造」和「拷贝赋值」各自数出来。

语法规则拷贝与移动的五个签名
  • 拷贝构造：T(const T&)
  • 移动构造：T(T&&) noexcept（noexcept 不是语法要求，但资源类通常这么写）
  • 拷贝赋值：T& operator=(const T&)
  • 移动赋值：T& operator=(T&&) noexcept
  • 析构：~T()

Tracker b = a; 走的是拷贝构造：b 此时还不存在，构造函数负责把 b 建出来，所以 copies 加一。c = a; 走的是拷贝赋值：c 已经存在，赋值运算符负责把 a 的状态写进 c，所以 assignments 加一。两者签名不同、调用时机不同、要做的事也不同——拷贝赋值必须先处理「自己已经有资源」这件事（这里是 std::string 自己处理），否则就会泄漏或重复释放。

a=alpha b=alpha c=alpha 说明三个对象各自有一份名字；copies=1 assignments=1 说明两个入口各走了一次。注意 Tracker 的 name 是 std::string，它自己有深拷贝；如果成员是一个裸指针，默认拷贝就只复制指针值——这正是 4.7 节要看的 bug。

拷贝构造最常见的触发点有四个：用同类型对象初始化新对象（Tracker b = a; 或 Tracker b(a);）、按值传参、按值返回（没有被省略时）、把对象放进容器（vector 扩容或 push_back）。它们的共同点是「新对象还没有自己的资源」，所以拷贝构造必须把源对象的资源复制一份。拷贝赋值不同：目标对象已经存在，可能已经握着一块资源，所以它必须先处理「旧资源怎么办」，再复制新资源——顺序反了就会泄漏，忘了处理自赋值就会把自己的资源释放掉再读。

一个常见的写法是 copy-and-swap：先按源对象构造一个临时对象（复用拷贝构造），再把自己和临时对象交换，临时对象在析构时释放旧资源。这样拷贝赋值只需要写一次资源释放逻辑（析构函数），而且天然处理自赋值与异常安全——交换不会抛异常。代价是多了一次临时对象的构造与析构，本单元 4.6 节的 copy_ctors=2 就是这笔代价的读数。

为什么拷贝构造的参数是 const T&，不是 T？如果写成 T(T other)，为了把实参传进来，编译器又要调用一次拷贝构造，递归没有出口；const T& 直接绑定源对象，不复制。为什么加 const？因为拷贝不应该修改源对象，而且 const T& 能绑定临时对象（比如 Tracker b = Tracker("x");），非 const 引用绑定不了。拷贝赋值返回 T& 而不是 void，是为了支持 a = b = c 这样的链式赋值；返回 *this 是惯例，不是标准强制。

把「按值传参」单独拎出来看：void take(Tracker t) 调用时，实参会被复制进形参，触发一次拷贝构造；函数返回 Tracker 时，如果编译器不做省略，还会再触发一次拷贝或移动。这就是为什么大对象通常按 const T& 传参——不是为了「语法正确」，而是为了省掉一次真实的对象构造。反过来说，如果函数本来就要一份独立的副本（例如它要在内部修改），按值传参反而是更清晰的接口：调用者不用关心内部怎么改，函数自己拿到一份副本。传参方式的选择，取决于「你要不要一份自己的副本」，不是「引用看起来更高级」。

拷贝构造与移动构造的签名只差一个 &：T(const T&) 与 T(T&&)。这个 && 不是「两个地址」，而是右值引用类型；它让重载决议在实参是右值时优先选移动构造。拷贝赋值与移动赋值的签名同理，只是返回类型通常是 T&。注意：移动构造 / 移动赋值通常标 noexcept，拷贝构造 / 拷贝赋值通常不标——因为拷贝要分配资源，可能抛；移动只接管资源，通常不抛。这个差异在 4.8 节会变成 vector 的实际选择。

emplace_back 与 push_back 的区别也常和拷贝/移动一起问：v.push_back(T("x")) 先构造一个临时 T，再把这个临时对象移动/拷贝进容器；v.emplace_back("x") 把参数直接传给容器里的构造，在目标位置直接构造，少了一次临时对象与一次移动。少掉的那一次不是语法糖，是真实的构造/析构次数差异。但 emplace_back 不保证一定更快：如果容器扩容，已有元素仍然要被移动/拷贝；如果参数类型与构造函数不匹配，编译错误也会更难读。先写清楚语义，再谈省一次构造。

计数实验本身也有一个设计点：为什么用 static int 计数，而不是在每个构造函数里直接 std::cout？因为输出会与构造/析构的顺序纠缠在一起，读起来像一锅粥；把计数留到最后打印，得到的是一张干净的对照表。代价是你看不到「第几个对象、在什么时候」构造的——要看顺序，就换成在构造函数里打印指针/名字。证据的形式要跟着问题走：问次数用计数，问顺序用日志，问所有权用地址。

4.3 std::move 只是 static_cast<T&&>：它不搬任何东西

还要区分「拷贝构造」与「拷贝赋值」的语法位置：T b = a; 看起来像赋值，其实是初始化，调用拷贝构造；只有 b = a;（b 已经声明过）才是拷贝赋值。这个区别在写计数实验时最容易搞混——把 T b = a; 当成赋值，计数就会对不上。

4.3 std::move 只是 static_cast<T&&>：它不搬任何东西

新手最常见的误解是「std::move(x) 把 x 搬走了」。没有。std::move 的实现本质上就是一次类型转换：把左值表达式转换成右值引用，让重载决议有机会选中「移动」那条路。真正搬资源的是移动构造 / 移动赋值，不是 std::move。

输出里 lvalue overload 与 rvalue overload 各出现一次，说明重载决议确实按值类别选了不同的函数；same address: true 说明 r 和 s 指向同一个对象——std::move 没有创建新对象，也没有搬走字符。把这张图记住：

第 1 帧的 s 是左值；第 2 帧的 std::move(s) 是右值引用表达式，但它仍然指向 s 那块存储。右值引用是「允许被搬」的标签，不是「已经搬走」的事实。 std::move 本身不改变 s；只有真正发生移动构造 / 移动赋值后，源对象才进入「有效但未指定」状态。

值类别可以先用三句话记：左值有名字、能取地址；纯右值是临时结果、没有名字；将亡值是「有身份但马上要被搬走」的对象，std::move(x) 产生的就是它。T&& 是类型，不是值类别；一个声明出来的 T&& r = ...; 变量本身是左值（它有名字），所以把 r 再传给函数时，不写 std::move(r) 仍然按左值匹配。这就是为什么“右值引用”和“右值”不能混着说。

几个常见表达式的值类别可以列成一张小表：

表达式 值类别 说明
x 左值 有名字，能取地址
std::move(x) 将亡值（右值） 还是 x 那个对象，只是被标成「可搬」
T{} 纯右值 临时对象，没有名字
x++ 纯右值 返回旧值的副本
++x 左值 返回 x 本身

这张表说明：std::move(x) 并没有让 x 变成另一个对象，它只是改变了表达式的值类别。重载决议看的是表达式的值类别，不是变量声明时的类型。std::forward<T> 也是做类似的事，但它会按模板参数 T 保留原来的值类别——这是第 8 单元「完美转发」的内容，本单元只要记住：std::move 是无条件转成右值，std::forward 是有条件保留。

std::move 最常见的四个误用：

  • 对 const 对象调用：const std::string s = "x"; 之后 std::move(s) 得到 const std::string&&，移动构造要的是 std::string&&，匹配不上，最后还是拷贝；
  • 以为搬完源对象就空了：见 4.4，标准只保证有效但未指定；
  • 对指针调用：std::move(p) 只把指针本身当右值，指针指向的堆内存不会跟着搬；要让所有权转移，得移动拥有它的对象（例如 unique_ptr），不是移动裸指针；
  • 以为写了 std::move 就一定走移动构造：如果类型没有移动构造，或者移动构造被删除，重载决议会退回拷贝构造，std::move 只是白写。

所以判断「有没有搬」的正确方式不是看代码里有没有 std::move，而是看类型有没有可用的移动操作，以及计数 / 地址 / 输出给出的证据。本单元的 move_is_cast 用 same address: true 证明没有搬对象；4.5 的 rvo_counter 用计数证明移动发生了几次；4.8 的 vector_realloc 用 noexcept 对照证明容器会不会选移动。

4.4 moved-from：有效但未指定，不是「空」

std::string t = std::move(s); 之后，s 还在，类型还是 std::string，你仍然可以对它调用 size()、empty()、clear()，甚至重新赋值。但标准不保证它现在是空串：它只保证「有效但未指定」（valid but unspecified）。本机 libstdc++ 对短串（SSO）移动时复制内部缓冲区并把源串长度置 0；长串才可能接管堆缓冲区。所以 s 看起来是空的；换一个实现，s 可能保留一小段内容。

本机输出 t=hello s.size=0 s.empty=true、b.size=3 a.size=0 a.empty=true。这是本机 libstdc++ 的一次读数，不是标准保证。 标准库对 moved-from 对象的总则写在 [lib.types.movedfrom]：除非另有规定，被移动后的对象处于有效但未指定的状态。你可以对它做「不依赖具体值」的操作（析构、赋值、clear()），但不能假设它一定是空、一定保留原值、或者 size() 一定为 0。

把 moved-from 想成一个「已经交出家具有没有搬完不知道」的房间：房间本身还在，门锁、灯、地板都还能用（析构、赋值、clear() 都是安全的），但你不能根据房间里还剩什么做判断。「有效」保证的是「不会一碰就炸」，「未指定」说明「别读具体值」。 这也解释了为什么标准不规定成「一定为空」：不同实现有不同的优化空间（短串优化、缓冲区复用），强行规定为空反而会限制实现。

实际写代码时，moved-from 只适合做三件事：让它自然析构、给它赋新值、把它 clear() / swap() 掉。不要拿它当查询结果、不要把它当容器的键、不要在日志里打印它的内容并指望每次都一样。能读和能依赖读到的值是两回事。

标准原文标准原文：moved-from 不是「可以随便读」

C++ 标准对标准库对象的 moved-from 状态有一句总则：除非另有规定，被移动后的对象处于有效但未指定的状态（[lib.types.movedfrom]，N4950 §16.4.6.15）。注意：moved-from 对象的生命周期没有结束；[basic.life]（N4950 §6.7.3）管的是生命周期结束后的存储使用，和 moved-from 不是同一件事。两句话合起来：moved-from 不是空，也不是坏对象；它是「还能安全使用，但别猜内容」的对象。

moved-from 的规则不只影响 string / vector，它决定了「移动之后还能不能用源对象」这个接口问题。一个函数如果接受 T&& 并把参数搬走，调用者就必须知道「传进去的对象之后不能再用具体值」；如果函数只是借用（比如 const T&），就不该搬。这也是为什么标准库的 std::move 算法（std::move(first, last, out)）名字里虽然有 move，它做的是「把每个元素移动到输出区间」，源区间之后同样处于有效但未指定状态。移动是所有权转移，不是「读取一下再复制」；接口设计要把这件事说清楚。

如果确实需要保留源对象的值，就不要移动，老老实实拷贝；拷贝的代价是可见的、可预测的，而「移动之后偷偷读源对象」的 bug 往往在换实现或换优化档后才暴露。C++ 的移动语义把「我还要不要这个值」变成了一个必须由调用者回答的问题。

标准库各类型对 moved-from 的具体保证并不一样：std::unique_ptr 被移动后保证为空（它的规范明确写了 nullptr），std::string / std::vector 只给「有效但未指定」。「有效但未指定」是默认规则，不是所有类型的统一读数。 查一个类型的 moved-from 状态，要看它自己的条款，不要拿 string 的本机读数去套 unique_ptr。这也是为什么本单元把 moved_from 的读数标成「本机 libstdc++」，而不是「C++ 保证」。

调试时不要用 printf/cout 打印 moved-from 的值来判断「移动有没有成功」：打印本身是合法的，但打印出来的值没有规范意义，换一版标准库就可能变。判断移动是否发生，应该看目标对象（它拿到了什么）与计数/地址（移动构造调用了几次、两个对象是否指向同一块），而不是看源对象「看起来空不空」。源对象的状态是结果，不是证据；证据在目标和计数上。

这里要把三个名字分开：RVO（返回值优化）通常指返回一个临时对象时，直接在调用者的存储里构造；NRVO（具名返回值优化）指返回一个具名局部变量时做同样的事；强制拷贝省略是 C++17 起对「用同类型纯右值初始化对象」的硬性规定——Counted x = make_counted(); 的调用点不会再多构造一个临时对象。NRVO 不在强制之列，-fno-elide-constructors 关掉的正是这类可选省略。所以本机默认 move=0 是 GCC 的选择，不是标准欠你的；换一个不做 NRVO 的编译器，默认也可能 move=1。三种情况都不要和「std::move 一定会移动」混为一谈。

编译器怎么做到省略？它不需要「先构造一个对象再搬过去」，而是把返回槽（调用者为返回值预留的那块存储）的地址传给被调函数，让被调函数直接在那里构造 local。这不是运行期的优化技巧，而是编译器在生成代码时就把「返回对象」和「调用者的接收对象」当成同一块存储。C++17 的强制省略把这件事写进了语言规则：只要初始化表达式是同类型的纯右值，就不允许再产生一次拷贝/移动。NRVO 则取决于编译器是否愿意做这个分析——标准允许，但不强制。这也解释了为什么 -fno-elide-constructors 只影响可选省略，而 std::move 的误用会主动破坏它：你让返回表达式不再是「一个名字」，编译器就没有 NRVO 的入口了。

return std::move(local); 把 local 显式变成右值，编译器因此不能再对它做 NRVO（具名返回值优化要求返回的是一个名字，而不是一个转换后的表达式）。在本机默认档，结果是从 0 次构造退化成 1 次移动；换一个本来就不做 NRVO 的实现，默认也可能是一次移动。GCC 会在 -Wall 里直接报 -Wpessimizing-move；本书的清单再加 -Werror=pessimizing-move，让它变成编译失败，诊断原文由闸门从真实 stderr 回写：

编译器视角编译器视角：这条警告在说什么

-Wpessimizing-move 的触发条件是「在 return 语句里对一个局部对象调用 std::move」。编译器知道这个局部对象马上就要销毁，本来可以直接在调用者的存储里构造（RVO/NRVO），而 std::move 把这条零成本的路堵上了。诊断里的 moving a local object in a return statement prevents copy elision 就是字面意思：你阻止了拷贝省略。它不是「你写错了类型」，而是「你多写了一次移动」。

注意这个例子的清单模式是 compile_fail，不是 run：程序根本编不出来，所以没有运行时计数。证据就是编译器真实吐出的 stderr（上面那个块），而不是「我觉得它会慢」。这也是本书用 -Werror=pessimizing-move 的原因——把一条容易被忽略的警告升级成必须处理的编译失败，让例子在闸门里稳定复现。警告不是噪音，它是编译器把「你多写了一次移动」这件事直接说给你听。

第 1 帧是默认情况：本机 GCC 做了 NRVO，local 的构造发生在返回槽里，调用点又受强制省略保护，所以没有第二次构造。第 2 帧是关掉可选省略后的情况：编译器仍然先构造 local，返回时再移动构造一次。两张图只差一个开关，计数就从 move=0 变成 move=1——这就是「可选省略」与「移动」的区别。

RVO/NRVO 也有边界：如果 return 的表达式类型与函数返回类型不同（例如局部是 std::unique_ptr<Derived>，返回 std::unique_ptr<Base>），编译器不能直接省略，只能先完成类型转换，再移动/复制；如果返回的是成员变量、全局变量或函数参数，NRVO 也不适用，因为它们不是「函数内部的具名局部对象」。不要把 NRVO 当成「只要 return 局部变量就零拷贝」的保证；它是一条允许编译器优化的路径，不是语言强制。真正稳定的是「返回纯右值时调用点的强制省略」，以及「不要用 std::move 去堵 NRVO」。

那什么时候应该写 std::move？答案是「你确实想把所有权交出去」的时候：

  • 把一个即将销毁的对象塞进容器：v.push_back(std::move(s));，之后不再用 s；
  • 移动赋值：dst = std::move(src);，src 之后只做析构或重新赋值；
  • 实现移动构造 / 移动赋值时，对成员用 std::move（如果成员是资源拥有者）；
  • 泛型代码里转发参数用 std::forward<T>，不是 std::move（4.10 之外的第 8 章会展开）。

反过来，不要在 return 一个局部变量时写 std::move，不要对 const 对象写，不要在移动之后还依赖源对象的值。std::move 是「我确定不再需要这个值」的声明，不是「让代码变快」的咒语。

4.6 Rule of Five：资源类必须把五个特殊成员函数想清楚

Buffer 拥有 new char[]。它必须自己定义五个特殊成员函数：析构、拷贝构造、移动构造、拷贝赋值、移动赋值。不要假设「少写一个，编译器就会生成你想要的默认版本」：一旦你声明了析构、拷贝构造或拷贝赋值，移动构造 / 移动赋值就不会被隐式声明；隐式拷贝对裸指针只做浅拷贝，后果见 4.7。Rule of Five 的要点是「五个一起想清楚」，不是「五个都必须手写」。

标准原文标准原文：五个特殊成员函数

C++ 标准把拷贝构造、移动构造放在 [class.copy.ctor]（N4950 §11.4.5.3），把拷贝赋值、移动赋值放在 [class.copy.assign]（N4950 §11.4.6）。它们不是五个孤立的函数：编译器在没有被抑制的前提下生成默认版本，默认版本对每个成员做逐成员拷贝/移动；一旦你声明了析构、拷贝构造或拷贝赋值，移动操作就不再隐式生成。「Rule of Five」是工程惯例的总结，不是标准里的一个条款——标准只规定这五个函数各自的行为，不会强迫你全写。

工程惯例工程惯例：Rule of Five

「五个一起想清楚」是工程惯例，不是标准条款。标准不要求你手写五个；它只规定这五个函数各自的行为。真正的纪律是：资源类一旦自己管理资源，就把五个都检查一遍——缺哪个、为什么缺、缺了以后默认行为是什么，要能说出来。

先别急着看计数，先看 Buffer 的五个函数各自做了什么：

  • 析构：delete[] data_，只释放自己拥有的那块；
  • 拷贝构造：新分配一块，逐字节复制，源对象不动；
  • 移动构造：直接接管 other.data_，然后把 other 置空，保证它的析构不会重复释放；
  • 拷贝赋值：先构造临时对象（copy-and-swap），再交换，异常安全；
  • 移动赋值：先释放自己原有的块，再接管对方的块，把对方置空。

本机输出是 ctors=3 copy_ctors=2 move_ctors=1 copy_assigns=1 move_assigns=1 dtors=6。为什么 copy_ctors 是 2 而不是 1？因为拷贝赋值 d = b; 内部构造了一个临时 Buffer tmp(other)，它也是一次拷贝构造。计数表里多出来的那一次，不是 bug，而是 copy-and-swap 的代价。 这也说明「五个函数」不是五个孤立的函数：拷贝赋值可以复用拷贝构造，移动赋值要处理自赋值，析构要能接住所有路径。

把五个函数按「谁分配、谁释放、谁接管」重读一遍，逻辑就清楚了：析构函数只负责释放自己当前拥有的块，所以移动构造 / 移动赋值必须把源对象的指针置空，否则源对象析构时会再释放一次；拷贝构造负责新分配 + 复制，它不碰源对象；拷贝赋值要先处理「自己原来那块」，再复制对方的；移动赋值要先释放自己那块，再接管对方那块，最后把对方置空。五个函数的共同不变量是：每一个非空指针恰好有一个所有者。只要这个不变量成立，就不会 double free，也不会泄漏。

这也解释了「少写一个会怎样」：只写析构而不写拷贝构造，默认拷贝会复制指针，两个对象都以为自己拥有那块内存；只写拷贝构造而不写移动构造，std::move 会退回复制（因为移动构造没有被隐式声明时，重载决议选拷贝）；写了移动构造而不写移动赋值，移动赋值会退回复制赋值。编译器不会替你补齐你想要的那一个，它只会按语言规则生成或抑制某些默认版本。

自赋值是另一个容易漏掉的边界：a = a; 时，如果拷贝赋值先 delete[] data_ 再读 other.data_，源对象已经被自己释放了。Buffer 用 if (this != &other) 挡住自赋值；copy-and-swap 的写法则天然安全，因为临时对象先把源内容复制走，再交换。两种写法都可以，关键是你要意识到「源对象可能就是自己」。

如果资源已经由 std::string、std::vector、std::unique_ptr 这类 RAII 成员管理，通常不需要手写五个函数——编译器生成的默认版本会正确调用成员的拷贝/移动，这叫 Rule of Zero。Rule of Five 是「你自己管理裸资源」时的纪律；能交给 RAII 成员，就优先交给它们。

移动构造的成员初始化列表也有讲究：Buffer(Buffer&& other) noexcept : data_(other.data_), size_(other.size_) { other.data_ = nullptr; other.size_ = 0; }——初始化列表负责接管，函数体负责把源对象置空。这两步不能反过来：如果先置空源对象，初始化列表就拿不到指针了；如果忘了置空，源对象析构时会重复释放。移动赋值则是「先释放自己、再接管、再置空」，顺序同样不能错。拷贝构造没有「置空源对象」这一步，因为它不改变源对象。

移动赋值还要处理「自己移动给自己」：a = std::move(a); 在移动赋值里如果先 delete[] data_，再读 other.data_，而 other 就是 *this，读到的就是已经释放的指针。if (this != &other) 这一行看起来是防御性代码，实际上是正确性的一部分。拷贝赋值的自赋值同样危险：先释放自己的资源再读源对象，源对象已经被释放了。自赋值不是「没人会这么写」的边角料，它是赋值运算符必须成立的边界条件。

拷贝赋值有两种常见写法，各有代价：

  • 释放 + 复制：先 delete[] data_，再按源对象大小分配、复制。少一次临时对象，但如果复制过程中 new 抛异常，对象已经处于「旧资源没了、新资源没建好」的坏状态；
  • copy-and-swap：先按源对象构造临时对象（复用拷贝构造），再交换，临时对象析构时释放旧资源。多一次构造/析构，但交换不抛异常，异常安全更好，而且天然处理自赋值。

Buffer 选了 copy-and-swap，所以计数表里 copy_ctors=2。这不是唯一的正确写法，而是一次有意的取舍：用一次临时构造换异常安全与自赋值安全。 如果你的资源释放不会抛、复制逻辑简单，释放+复制也可以；关键是你要能说出「异常发生时对象处于什么状态」。这就是「异常安全」的三个档位：不泄漏（基本保证）、操作要么全成要么全不成（强保证）、承诺不抛（noexcept）。本单元的 Buffer 的目标是强保证。

析构函数什么时候该是虚的？本单元不展开多态，但先留一句：如果你会通过基类指针 delete 一个派生对象，基类析构必须是虚的，否则派生部分的析构不会被调用。Buffer 不是基类，所以它的析构不需要虚；第 6 单元会把这条规则和虚函数一起讲。不要因为「看到类就加 virtual」——虚析构有运行期开销，只有多态删除的场景才需要。

第 1 帧：a 的 data_ 指向一块堆内存。第 2 帧：b 拷贝构造后指向另一块内存，两个对象互不影响。第 3 帧：c 移动构造后直接接管 a 的指针，a.data_ 被置空；此后 a 的析构不会 delete[] 任何东西。本例的移动构造是「接管指针 + 源指针置空」；这是 Buffer 自己的约定。 标准库只承诺 moved-from 有效但未指定，用户类型的 moved-from 状态由它自己的移动操作规定。移动不是「把字节复制过去再删掉」。

为什么移动构造标了 noexcept，而拷贝构造没标？因为移动构造只做指针赋值与置空，不会分配内存，天然不会抛；拷贝构造要 new char[]，可能抛 std::bad_alloc。这个标注意味着「移动一定成功」，vector 扩容时才敢放心地移动；4.8 节会用 CopyFallback 演示不标 noexcept 的后果。

4.7 浅拷贝：默认拷贝构造会把两个对象绑在同一块内存上

把 Buffer 的五个函数全部删掉，只留下构造函数与析构函数，会得到什么？默认拷贝构造会逐成员复制——对 char* data_ 来说，复制的是指针值，不是它指向的字符。于是两个 Buffer 的 data_ 指向同一块内存，两个析构函数各 delete[] 一次。

本机退出码是 3221226356（Windows 的堆损坏），stderr 为空；程序在第二个 delete 时被杀掉，所以 after scope 不会打印。这是未定义行为：标准不保证它一定崩、也不保证崩在哪一行。你能依赖的只有「默认拷贝构造对裸拥有指针是浅拷贝」这一条语言规则，以及「两个析构函数都释放同一块内存」这个因果链。

为什么 before copy 和 b=7 能留下来？因为代码在这两行后面显式 std::flush 了；如果只写 \n，标准输出可能还在缓冲区里，进程被终止时整段丢失。崩溃程序的 stdout 不是可靠的证据，这也是本单元把退出码与输出分开记录的原因：退出码证明「它死了」，输出证明「死之前走到了哪一步」，两者不能互相替代。

修这个 bug 有三条路：一是按 Rule of Five 手写深拷贝（本单元 rule_of_five）；二是把 int* 换成 std::unique_ptr<int>，让所有权不可复制（第 5 单元）；三是明确禁止拷贝（Shallow(const Shallow&) = delete;），只允许移动。三条路的共同点是「让所有权关系在类型里显式化」，而不是靠调用者记得「这个对象不能复制」。默认拷贝构造不会替你思考所有权，它只会逐成员复制。

这个 bug 在容器里更隐蔽：std::vector<Shallow> v; v.push_back(a); 会拷贝构造元素；v 扩容时又会拷贝/移动已有元素。如果 Shallow 的拷贝是浅拷贝，容器里就会出现多个「拥有同一块内存」的对象，任何一个先析构都会让其余的变成悬空指针。容器不会替你修拷贝语义，它只是按类型提供的拷贝/移动操作行事。 所以在把自定义类型放进容器之前，先问一句：它的拷贝构造和移动构造到底做了什么？

接口设计也受这条规则影响：一个函数如果只是「看一眼」对象，用 const T&；如果它要保留一份自己的副本，用按值传参；如果它要接管调用者的资源，用 T&&（并在文档/命名里说清楚「调用后源对象不再使用」）。参数类型是所有权契约的一部分，不是随便挑一个能编过的写法。 你把参数写成 T&&，调用者就会以为可以 std::move 进来；你写成 const T&，调用者就知道你只是借用。C++ 的移动语义把「所有权」放到了签名里，读签名的人应该能看出这件事。

Rule of Three 是 Rule of Five 的前身：如果你需要自定义析构、拷贝构造、拷贝赋值中的任何一个，通常三个都要一起考虑；C++11 之后多了移动构造与移动赋值，变成 Rule of Five。Rule of Zero 则是「资源都交给 RAII 成员」的写法。三条规则不是三个教条，而是同一个问题的三种答案：谁拥有资源、谁负责释放、复制/移动时所有权怎么变。

陷阱`std::move` 不移动，moved-from 也不是空

两句话都反直觉，但都重要：

  1. std::move(x) 不移动任何东西。它只是把 x 转成右值引用；如果目标类型没有移动构造，或者重载决议选了拷贝构造，std::move 之后仍然是一次拷贝。判断「有没有移动」要看计数，不要看 std::move 这三个字。
  2. moved-from 不是空。本机 std::string 被移动后 size()==0，所以很多人以为「移动 = 清空」；标准只说「有效但未指定」。换一个标准库实现，moved-from 的 string 可能保留内容。不要依赖读到的值；读本身合法，值未指定。 要给对象赋新值之前，别拿旧值做判断。

4.8 noexcept 与 vector 扩容：为什么移动构造要标 noexcept

std::vector 扩容时要把旧元素搬到新缓冲区。标准给它的异常安全承诺有一个条件：如果搬移过程中抛异常，旧缓冲区要保持原样——但对不可拷贝且移动可能抛异常的类型，这个承诺不成立（没有安全退路）。libstdc++ 的做法是 std::move_if_noexcept：移动构造 noexcept 就移动；否则如果有拷贝构造就拷贝；如果只能移动，就只能移动。std::move_if_noexcept 是实现手法，不是标准强制。

本机输出三行：grow: moves=7 copies=0、reserve: moves=0 copies=0、fallback: moves=0 copies=7。本机 libstdc++ 按倍增扩容，grow 的 7 次移动来自容量 1→2→4→8 的三次扩容（1+2+4）；标准只保证 capacity() >= size()，换实现扩容次数可能不同。reserve 提前把容量留到 8，所以一次都不用搬；fallback 的移动构造没有 noexcept，vector 选择了拷贝，7 次移动变成 7 次拷贝。noexcept 不是装饰，它直接改变容器选择哪条路。

这里要小心不要把「noexcept 移动构造」当成无条件的好事。noexcept 是一个承诺：函数不会让异常逃出去。如果你的移动构造真的可能抛（例如它要分配内存、调用可能抛的函数），却硬标 noexcept，异常会直接触发 std::terminate，程序当场死掉——比「不标 noexcept、让 vector 选择拷贝」更糟。标准库容器的 noexcept 移动构造（std::string、std::vector、std::unique_ptr）之所以敢标，是因为它们内部只做指针/缓冲区的接管，不分配新资源。先保证移动构造真的不抛，再标 noexcept。

reserve 的对照也值得记住：grow 的 7 次移动不是因为「vector 喜欢搬」，而是因为容量不够、必须扩容。你提前 reserve(8)，vector 一次都不用搬。能预估大小时先 reserve，比事后怪移动构造更有效。 当然，reserve 也可能一次分配很大块内存，预估过大同样浪费；这是工程取舍，不是语法规则。

最后要分清「计数」与「性能」：本单元数的是构造/移动/拷贝调用了多少次，不是耗时。7 次移动可能比 7 次拷贝便宜，也可能因为对象很小而差不多；耗时随机器、负载、缓存状态变化，计数才是稳定、可复现的证据。要谈性能，先固定测量口径；本书的 experiment 只报计数、退出码、地址这类可复现读数，不写「快了多少倍」这种没有对照的结论。 这也是「标准要求 / 本机实测 / 工程惯例」三分里，本机实测只对自己这台机器负责的原因。

扩容还会让迭代器、指针、引用失效：vector 换了一块缓冲区，原来的迭代器指向旧内存，继续用就是悬空。reserve 只保证「在容量范围内不再重新分配」，不保证「已有的迭代器永远有效」；shrink_to_fit 则可能触发一次收缩，同样让迭代器失效。C 分册讲 realloc 时说过「地址可能变」，C++ 的 vector 是同一个道理，只是它把「搬元素」包装成了移动构造。任何可能导致扩容的操作之后，都不要假设旧迭代器还指着原来的元素。

那 noexcept 移动构造是不是越多越好？不是。它是「我保证不抛」的承诺，不是「写了就更快」的优化开关。只有当你确定移动构造不会抛（只做指针/句柄接管），才标 noexcept；不确定就不标，让 vector 走拷贝退路。把可能抛的移动硬标 noexcept，等于把异常变成 std::terminate，比拷贝更危险。

shrink_to_fit() 也值得提一句：它是「请求」而不是「命令」，实现可以忽略；即使实现接受，它也可能重新分配一块更小的缓冲区，让所有迭代器、指针、引用失效。不要因为「容量看起来太大」就随手 shrink_to_fit，先确认没有人在用旧迭代器，再确认这次收缩真的值得。 这是 C 分册 realloc 的同一个教训：地址变了，所有指向旧地址的东西都作废。

resize 与 reserve 也经常被混用：resize(n) 改变的是 size，会构造/析构元素，之后 v[n-1] 是合法元素；reserve(n) 改变的是 capacity，不构造任何元素，之后 v.size() 可能还是 0。要「提前留空间」用 reserve，要「真的有 n 个元素」用 resize。 这两个操作都可能触发重新分配（resize 超过当前 capacity 时），所以迭代器失效的规则同样适用。

4.9 两个 .cpp 都 include 同一个头文件：谁看得见什么

copy_basics 的 main.cpp 与 copy_basics.cpp 都 #include "copy_basics.h"。头文件里只有 run_copy_basics() 的声明，定义在 copy_basics.cpp 里。两个翻译单元各自编译，链接器把 main.cpp 里的调用接到 copy_basics.cpp 的定义上。

第 1 帧：两个 .cpp 都看见了声明，所以编译期都知道 run_copy_basics 这个名字和签名。第 2 帧：定义只出现在 copy_basics.cpp 里，链接器把 main.cpp 的调用接到它上面。如果头文件里写函数定义（而不是声明），两个翻译单元就会各生成一份，链接期报重复定义——这是 C++ 分册第 20 单元（ODR）要展开的事。本单元只要求你记住：头文件放声明，定义放 .cpp；模板是例外，它的定义必须让使用它的翻译单元看见。

为什么模板是例外？因为模板本身不是「一份可链接的代码」，它要等实参类型确定后才实例化；编译器在使用点必须看得见完整定义，才能生成那一份实例。C 分册的「声明放头文件、定义放 .cpp」在这里仍然成立，只是模板把「定义」也推到了头文件里。这个差异在第 8 单元（模板入门）会再用真实链接错误讲一次。

头文件里除了声明，还可以放 inline 函数、constexpr 变量、类定义、模板定义；不能放普通函数定义、普通全局变量定义（会违反 ODR，链接期重复定义）。C++17 起可以用 inline 变量在头文件里定义全局变量，这是第 9 单元（多文件工程与 ODR）的内容。本单元只要求你记住一条：头文件会被多个翻译单元各包含一次，任何「只能有一份」的东西都要小心。 这也是为什么 Buffer 的成员函数定义放在 .cpp，头文件里只有类定义与函数声明。

inline 在 C++ 里的含义和 C 不一样：C 的 inline 只是「建议内联」，C++ 的 inline 还附带「允许在多个翻译单元里出现同一份定义」的链接语义。所以头文件里的 inline 函数不会重复定义，普通函数会。这个区别在第 9 单元会展开；本单元只要记住：看到头文件里的函数定义，先问它是不是 inline / 模板 / 类内定义，否则链接期可能炸。

4.10 大白话：为什么 return std::move(x) 反而更慢

大白话用大白话说：搬家与打包

把返回局部对象想成搬家。默认的 RVO/NRVO 是「新房就是按你的旧房布局盖的，家具直接在新房摆好」——一次搬运都没有。std::move(local) 则是「先把家具打包，再搬到新房」——多了一次打包和拆包。编译器本来能直接在新房摆好，你非要在中间加一道打包工序，于是它只好移动一次。

再换个角度：std::move 不是「搬家公司的卡车」，它更像「在箱子上贴一张『可搬』的标签」。真正搬箱子的是移动构造。你在 return 里贴标签，等于告诉编译器「这个箱子可以搬」；可编译器本来就能把整个房间直接盖在新地址上，你贴标签反而让它只能搬箱子。标签不是搬运，别把手段当目的。

更反直觉的是：std::move 不保证「搬」。如果目标类型没有移动构造，std::move 之后仍然调用拷贝构造；如果编译器做了省略，std::move 甚至会让省略失效。判断有没有搬，不要看代码里写没写 std::move，要看计数（本单元的 rvo_counter 与 vector_realloc 就是干这个的）。标签贴得再多，也代替不了搬家公司的车；而 C++ 的「车」是移动构造，不是 std::move。

4.11 写自己的资源类时的检查清单

这一节没有新例子，只有一张可以带走的检查表。下次你写一个「拥有资源」的类，按顺序问自己：

  1. 它真的拥有资源吗？ 如果成员是 std::string、std::vector、std::unique_ptr 这类 RAII 类型，默认的拷贝/移动会正确调用成员的操作，通常不需要手写五个函数（Rule of Zero）。只有裸指针、文件描述符、锁这类「析构时必须手动释放」的成员，才需要你接管。
  2. 默认拷贝做了什么？ 对裸拥有指针，默认拷贝是浅拷贝：两个对象共用一个资源，析构两次就 double free。先写出这个反例，再决定是深拷贝、禁拷贝还是换 RAII 成员。
  3. 五个函数是否一致？ 析构释放资源；拷贝构造分配并复制；移动构造接管资源并把源对象置空；拷贝赋值处理旧资源与自赋值；移动赋值释放旧资源、接管、置空。五个函数共享一个不变量：每个非空资源只有一个所有者。
  4. 自赋值和异常安全怎么办？ a = a; 与 a = std::move(a); 都必须安全。copy-and-swap 用一次临时对象换取异常安全；手写释放/接管则要保证「先释放再读源对象」的顺序不会踩到自赋值。
  5. noexcept 是真实的吗？ 只有移动构造确实不抛（只接管指针/句柄）时才标 noexcept；标了却抛，异常会变成 std::terminate。不标 noexcept 的移动构造会让 vector 在可拷贝时退回拷贝，这是安全的选择，不是失败。
  6. 怎么验证？ 用计数（拷贝/移动/析构各几次）、地址（两个对象是否指向同一块）、退出码（double free 的本机退出码）和调试器（gdb 的 bt）拿证据。本机没有 ASan/UBSan，所以「我觉得不会泄漏」不算证据，能复现的计数/退出码才算。

这张表也可以反过来用：读别人的资源类时，按这六条逐一对照，缺哪条、为什么缺，通常就是 bug 或未定义行为的藏身处。

移动也不是默认选择：需要保留原值、源对象是 const、类型没有移动构造、移动构造其实会抛却标了 noexcept、或者你根本不确定所有权归谁——这些情况下拷贝或引用更安全。移动是优化，不是义务；先保证语义正确，再谈少一次构造。

小结这一节要带走的五件事
  • 拷贝构造与拷贝赋值是两个不同入口：前者建新对象，后者改写已有对象。
  • std::move 只是 static_cast<T&&>，不搬任何东西；真正搬资源的是移动构造 / 移动赋值。
  • moved-from 是「有效但未指定」，不是空；本机读数不能当标准保证。
  • 从 C++17 起，调用点的纯右值初始化有强制拷贝省略；NRVO 仍是可选优化。return std::move(local) 会阻止 NRVO，反而多一次移动，-Wpessimizing-move 会点名。
  • 资源类要按 Rule of Five 想清楚五个特殊成员函数；对可拷贝类型，移动构造标 noexcept 会让 vector 扩容选择移动而不是拷贝（只能移动的类型没有退路）。
