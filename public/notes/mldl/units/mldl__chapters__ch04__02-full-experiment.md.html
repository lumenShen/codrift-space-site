10.1 先看工程长什么样

上一个单元做的是对照：三种正则化配方在同一任务上比高低。那种实验关心的是「谁更好」，所以只报几个终点数字就够了。这一单元关心的是另一件事：一次训练实验怎么才能交给别人复现。这要多做几样东西——分层的训练数据、注入种子的清单、逐步打印的轨迹、保存参数的检查点，以及一张能照着排查的失败模式表。

工程上多了一个 experiment.py：三种种子的固定、三层数据的切分、小分类器、全量损失、准确率与检查点都在里面。main.py 只剩读种子、跑循环、打数字。种子仍然不写死在源码里，而是由闸门通过环境变量 ML_SEED 注入——写在源码里叫硬编码，写在清单里叫实验条件，后者才能被对照实验改变。

第 2 帧里带 + 的四行是本单元的全部新增。和上一单元比，地基模块从 reg.py 换成 experiment.py，职责从「三种配方」变成「整条链路」；清单从 mode=numerical 换成 mode=train，证据从六个黄金值变成一条收敛轨迹加三次运行。读这类图时只盯带 + 的行，就能把一个单元的增量和之前的积累分开。

工程惯例为什么把地基和流程分成两个文件

experiment.py 管「这个实验从哪里开始、每样东西长什么样」——种子、数据、网络、损失、评估；main.py 管「实验怎么走」——读种子、循环、打印。代价是职责略重，好处是改实验条件和改训练流程落在两个文件里，互不干扰。想换学习率只动 main.py 的常量；想换数据集只动 experiment.py 的 build_splits。这和上两个单元的分工一脉相承：真正会变的东西要放在容易找到的地方。

10.2 全链路六站：数据、模型、损失、优化器、循环、评估

一次训练实验拆开看，是六个首尾相接的站。第一站数据：造样本、切三层、装进 DataLoader。第二站模型：一个固定的网络结构，参数是待优化的对象。第三站损失：把「预测」和「答案」的差距压成一个标量。第四站优化器：拿着参数引用，按梯度更新。第五站循环：取数、前向、反向、更新四步反复走。第六站评估：在固定的数据上算 loss 与准确率，把模型好坏变成一个可打印的数。

第 1 帧里 数据 -> 模型 的边是小批量送入，不是全量——虽然本例的批大小恰好等于训练集大小，每步只看一批。第 2 帧强调损失只是给循环用的信号，优化器并不认识损失，它只认参数里的 .grad。第 3 帧的评估不建图，所以可以用固定的整套数据而不担心内存。六站里任何一站换了实现，其余五站的接口都不用动，这是流水线拆开的最大价值。

先看数据站。两团二维点分别以 (-1,-1) 与 (1,1) 为中心，标准差 0.45，一共四十八个；标签分别是零和一。用 torch.randperm 打乱后再切成 24/8/16 三段，对应 train、val、test。数据由一个专用生成器产生，种子写死 2024，因此不随实验种子变化——这样对照种子改变的就是纯粹的「训练起点与读取顺序」，而不是数据本身。

模型站是一个 2-8-1 的小网络，隐藏层用 tanh，输出一个 logit 而不是概率。为什么输出 logit？因为下一站的损失函数 binary_cross_entropy_with_logits 把 sigmoid 与交叉熵合并计算，数值上比「先 sigmoid 再算交叉熵」稳定得多——当 logit 很大时，先算概率会先溢出或下溢，合并版本则在 log 域里直接算，避开中间那一步。

10.2.1 损失函数为什么吃 logit 而不是概率

第三站有个容易忽略的选择：binary_cross_entropy_with_logits 接收的是 logit，不是先过 sigmoid 得到的概率。数学上两者等价，数值上差别很大。sigmoid 在 logit 绝对值大时会饱和到零或一，再取对数就得到无穷；把这两步合并以后，实现里用 -softplus(-z) 这类在 log 域稳定的公式直接算，避开了中间那次饱和。对分类任务而言，模型越自信越需要这个保护——恰恰在最该给出高置信度的时候，朴素写法最容易崩。

logit >= 0 等价于 sigmoid(logit) >= 0.5，所以评估时直接用零阈值判类，既省一次非线性计算，又避免浮点乘除引入的边界误差。本例的标签是精确的零和一，没有类别不平衡问题，因此损失没加权重；真实项目里正负样本比例悬殊时，要给少数类加权，否则模型学会「全猜多数类」就能拿到漂亮的准确率。这个改动落在第三站，流水线的其它五站一行都不用动——这正是六站拆开的好处。

评估站把 logit 过零阈值变成类别预测，再算准确率；全量损失则在整套训练数据上算，不去重也不抽样。检查点函数把 state_dict 写进内存字节流，返回字节数——真项目里把它换成 torch.save(state, path) 就是落盘检查点，这里用内存版是为了让实验不往工作目录里写文件。

10.3 train、val、test 三层：各管一段

三层数据不是把一份数据随便切成三块，而是三种不同的用途。训练集用来算梯度、更新参数——模型从它里面学。验证集不参与更新，用来选模型：超参数调到多少、训练到第几步停、要不要开早停，都看它。测试集留到最后只跑一次，用来报告「交给别人之后大概能到多少」。三者的界限一旦混了，你报告的数字就不再可信。

第 2 帧的两条边值得盯住：训练集不参与验证集的任何计算，验证集也不参与测试集的任何计算。常见的数据泄漏正好是这两条边被打破——比如先用全部数据做标准化再切分，统计量里就混进了验证与测试的信息；或者每跑一轮就拿测试误差调一下学习率，测试集事实上变成了验证集。本例的切分在造数据之后立刻完成，标准化根本没做，从结构上堵住了这条路。

陷阱用测试误差挑「最好的一轮」

训练十二步，每步都打印测试准确率，最后挑最高那一步报出去——这看起来很勤奋，实际上把测试集当成了验证集。挑出来的数字带着选择偏差：你是在十六个候选里挑最好的，它天然偏高。正确做法是训练时只打印训练 loss 与验证误差，用验证误差选定步数，然后在测试集上跑一次并且不再回头改。本例的 acc 只在十二步全部结束后算一次，正是这个纪律；它报的是最终模型的测试准确率，不是十二步里的最高值。

10.3.1 验证集在这一例里为何暂时没被用到

build_splits 切出了八点的验证集，main.py 也把它解包成了 val，却始终没拿它算任何东西。这不是遗漏，而是有意留白：这一单元的重点是把全链路与可复现检查跑通，不引入选型逻辑。一旦你要做早停，就应该在每步训练后算一次验证损失，连续若干步不再下降就停下并回滚参数；那时 val 立刻派上用场。

为什么不在本例里顺手把早停也写了？因为那会改变 loss 轨迹的终点与步数，清单里的十二行黄金值全部作废，而「早停防什么」已经在上一单元讲清楚了。一次实验只验证一件事，是这套书反复坚持的纪律。留白也有代价：读者可能以为切了不用的数据是 waste。恰好相反——先把接口留出来，将来加功能时不用改数据结构，只需在循环里多写几行。

验证集存在的另一个理由是防止数据泄漏。若拿全部四十八点先算均值方差做标准化，再切三层，那么验证与测试的统计量已经渗进了训练流程，报出的准确率偏乐观。正确顺序是先切分，再只用训练集拟合预处理，然后把同一变换施加到验证与测试上。本例的数据本来就是标准正态生成的，压根不需要标准化，从源头上绕开了这个坑。

10.4 种子：三条随机流与三次运行

随机来源不止一个。本例里至少有三处：random 模块、numpy 的随机功能，以及 PyTorch 的网络初始化与 DataLoader 打乱。只固定其中两个，剩下的那个照样能让轨迹漂移。

这五行是整个 train 模式成立的前提。闸门会用同一个种子跑两次程序，要求 stdout 逐值一致；只要有一条随机流漏掉，第二次就可能给出不同的 loss，报 train_nondeterministic。最后那行 torch.set_num_threads(1) 不属于随机流，但它把多线程归约的加法次序固定下来，避免同一份输入因为线程调度不同而末位有差——在容差只有 1e-4 的检查里，这类末位抖动也得挡住。

10.4.1 三条流各管一段

理解种子，关键是明白三条流彼此不知道对方的存在。random 是标准库的随机源，数据增强决定「翻不翻转」时常用它；numpy 的随机模块在采样与索引里无处不在；PyTorch 自己维护一条全局流，负责参数初始化、DataLoader 打乱与 Dropout 掩码。你连续调用三个 seeding 函数，得到的是三套互不相关的序列，第一条流吐出的数与另外两条毫无关系。所以「固定种子」不是一个动作，而是三个动作。

本例还有第四条流：torch.Generator() 造出来的专用生成器，种子写死为 2024。为什么不一起随 ML_SEED 变？因为它不随实验种子变，属于「实验条件的一部分」而不是「随机来源」。它用随机算法造了一组固定的假数据，本质上并不随机。把它和三条需要固定的流混为一谈，是初学时的常见混淆：前者保证两次看到同一批样本，后者保证换种子后能产生不同的训练轨迹。

闸门用环境变量而不是命令行参数注入种子，是因为 Python 运行器只调 python [flags] sources[0]，注入 env 最省事也最不容易被源码里的默认值掩盖。程序里若写 seed = 12345，闸门换种子也换不动它——seed_has_no_effect 会当场抓住。而 os.environ["ML_SEED"] 缺了就直接抛异常，逼着实验必须显式声明条件，不许悄悄用默认值蒙混过关。

种子不写死在源码里，而是由闸门通过 ML_SEED 注入。主种子 12345、对照种子 67890，都写在清单里。为什么不干脆写 seed = 12345？因为那样换种子就要改源码，等于把实验条件藏进了算法；写在清单里，任何人拿到清单就知道这条轨迹是在什么条件下得到的，也能一键换条件重跑。

第 2 帧验证确定性，第 3 帧验证数字真的来自种子。两条缺一不可：只跑两次同种子，一份把 loss 写死进列表的程序也能过；只跑一次对照种子，一个用时间当随机源的程序每次都不同，看起来「有变化」却无法复现。对照种子 67890 的首行是 0.441477、末行是 0.079013——整条轨迹都变了，说明这些数确实由种子驱动的网络初值与打乱顺序算出来，而不是一张硬编码的表。

实验记录为什么程序不打印种子

主种子真跑的 stdout 只有十二行 loss=、一行 acc=、一行 ckpt_bytes=，没有一行写 seed=12345。这是个有意的设计：如果打印了种子，换对照种子时这一行必然变化，seed_has_no_effect 这条检查就会平凡通过——哪怕十二行 loss 全是写死的。不打印种子，就逼着对照检查去看 loss 本身。这个很小的选择，直接决定了那条证据有没有牙。

10.5 训练循环四步：清账、前向、反向、更新

入口代码只有二十来行，但每一步都有明确职责。循环外层走十二步，内层把 DataLoader 的一批数据走一遍；每步开始先 zero_grad()，然后把当前批送进网络得到 logit，与标签算交叉熵，backward() 把梯度填进各参数的 .grad，最后 step() 按 w ← w - lr·g 更新。评估前后成对调用 eval() 与 train()，与上一个单元同样的纪律。

10.5.1 zero_grad 为什么必须

backward() 把梯度加进 .grad，而不是覆盖。在只反向一次的例子里这个性质不造成后果；到了循环里就成了头号陷阱。假设忘了 zero_grad()：第一步算出梯度 g₁，更新用 g₁；第二步算出 g₂，但 .grad 里已经是 g₁+g₂，更新步长用的是两者之和；第三步变成 g₁+g₂+g₃……梯度越积越大，参数很快被甩出去，loss 不降反升。闸门会报 train_loss_not_decreasing，因为前八步的非增判定被破坏。

为什么框架不自动清零？因为有些场景确实没法把几份损失合成一个标量再一次反向，比如梯度来自不同分支的采样估计。框架把这个决定权交给你：想常规训练就每步清一次，想做梯度累积就把清零挪到若干步之后。本例把 opt.zero_grad() 写在内层循环开头，每处理一批清一次，是最常规的位置。判断位置对不对有个简单办法：数一数每个 step() 之间调用了几次 backward()——常规训练是一次，梯度累积才是多次。

还有一个静默错误值得警惕：把 backward() 与 step() 调换顺序。step() 读的是 .grad，不会自己重新计算梯度；调换后它读到的是上一步的旧梯度，或第一次的 None 直接报错。参数按过时方向更新，轨迹看起来「像在收敛」却不对。这类错误不触发异常，只能靠四步顺序的纪律防止。

注意 batch_loss 与 print 里的 full_loss 是两个不同的量。前者是当前小批量上的损失，只用来反向；后者是固定训练集上的损失，只用来观察趋势。为什么分开？小批量 loss 每步喂的数据可能不同，数值天然跳动；把它打印出来，轨迹会抖得看不出趋势，前八步非增的判定根本过不了。全量 loss 是同一个函数在不同参数点上的值，才是「模型有没有变好」的度量。

第 3 帧里 模型 -> 全量损失 这条边不带梯度：full_loss 内部包了 torch.no_grad()，只是拿当前参数算一个数给我们看。这也是为什么它可以放心用整套数据——不建图，就不需要为每条样本保存中间量。val 变量在 main.py 里被解包出来却没有用到，这是有意的留白：下一个实验要加早停时，它就是那块用来判定的数据。

工程惯例批大小取二十四意味着什么

取 1 就是纯随机梯度下降：每步只看一条样本，噪声最大，轨迹抖得厉害。取 24 等于全批量：每步用全部训练数据，梯度精确、轨迹平滑。本例取后者，是为了让前八步非增的判定成立——目标函数虽然不是凸的，但从固定初值出发、用足够小的学习率，全量 loss 会平滑下降。改成小批量，轨迹会抖动，闸门的前八步判定就可能误报发散；那时要改成看移动平均的趋势，而不是逐点比较。批大小是实验条件，改了它就得重新取黄金阈值。

10.6 真跑：十二行轨迹与 train 闸门

主种子 12345 真跑得到的 stdout 如下。十二行 loss 从 0.508848 一路降到 0.075274，首尾差 0.433574，每一步都比上一步低；最后一行 acc=1.000000 说明这批玩具数据上模型把测试点全分对了，ckpt_bytes=2525 是 state_dict 序列化后的字节数。

清单 ml10-full.json 用 mode=train，seed_env 写 ML_SEED，seed=12345，seed_contrast=67890。expect.train 写：loss_key=loss、min_points=12、first_min=0.5、last_max=0.08、decline_min=0.43、monotone_window=8、slack=1e-4。四个阈值全部按真值取：首行 0.508848 高于 0.5，末行 0.075274 低于 0.08，首尾差 0.433574 大于 0.43，前八步严格非增。

实验记录四个阈值各自防什么

min_points=12 防「程序只跑三步就说收敛」；first_min=0.5 防「起点已经在最优附近，下降演示没有意义」；last_max=0.08 防「每步只走微不足道的一小步」；decline_min=0.43 防「起点低终点也低的平凡通过」；monotone_window=8 加 slack=1e-4 防「前几步来回震荡却自称收敛」。这五条彼此独立，少一条都能构造出骗过闸门的写法。阈值来自真跑，不能为了让绿字好看反过来放宽——若把 last_max 改成 1.0，闸门确实会过，但那条「必须真的收敛」的纪律被自己拆掉了。

10.6.1 阈值为什么按真值取，而不是取整

first_min=0.5 而首行实际是 0.508848，last_max=0.08 而末行是 0.075274——为什么不写成 0.6 和 0.1 这种整齐的数？因为阈值不是「你想要什么」，而是「真跑给出了什么、留多少余量」。首行留约 0.009 的余量，容得下浮点末位的小差异；末行留约 0.005 的余量同理；降幅 0.43 对实际 0.433574 留了不到百分之一的余量——若把学习率改小导致降幅只有 0.4，闸门就会拦下，这正是我们想要的。

monotone_window=8 的 slack=1e-4 是给浮点比较留的余地：判定是 loss[i] > loss[i-1] + slack 才算反弹，允许每步有极小的上浮。本例十二步严格递减，不用 slack 也过；但换成别的机器或别的浮点实现，末位可能出现微小的上跳，容差让判定稳在「趋势」上而不是末位数字上。这和上两个单元里 atol、rtol 的作用是同一类：把「合理波动」与「真的不对」分开。

工程惯例用三次运行拼出完整证据

把三次运行的角色摆在一起看：第一次带主种子，给收敛轨迹与黄金值，验证「训练确实在降低 loss」；第二次同种子，要求逐值一致，验证「程序是确定的」；第三次换对照种子，要求至少一个数值变化，验证「数字来自计算而不是硬编码」。单独任何一次都只能说明一部分——第一次可能被硬编码表格骗过，第二次无法区分硬编码与真计算，第三次无法证明可复现。只有三次合起来，才能说这个训练实验是真的。这也是 train 模式固定跑三次、不给开关让你自己选的原因。

陷阱把「闸门通过」当成「数学正确」

同种子两次一致，只说明程序是确定的；换种子有变化，只说明程序读了种子。两者都通过，也不能证明四步循环写对、损失函数选对、标签没写反。本单元的正确性来自三条独立证据：手算的收缩趋势与十二行轨迹吻合、train 闸门检查起点终点与单调性、对照种子改变整条轨迹。闸门查的是后两条，第一条要靠你自己看数字。把闸门绿灯当成数学证明，是这套书反复要破除的误解——尤其本例的测试准确率是 1.000000，漂亮得可疑时更要回头核对标签与数据是不是太容易了。

10.6.2 学习率零点五从哪里来

LR=0.5 是试出来的，不是推出来的。本例的目标不是凸二次函数，曲率沿轨迹变化，没法像前面概率优化册那样算出一个严格上界。工程上的办法很朴素：从保守值开始跑一次看十二行 loss，若平滑下降就保留，若反弹就减半，若下降太慢就加倍。取 0.5 时首行 0.508848、末行 0.075274，前八步严格递减，是个合适的值。改成 5.0 时前几步就会越过最低点反弹，闸门报 train_loss_not_decreasing；改成 0.005 时轨迹依旧单调，但末行远高于 0.08，报同一个码。

阈值不会替你选学习率，它只负责拦住不合适的选择。这是理解闸门定位的关键：它是纪律的执行者，不是参数的优化器。把绿字当成「学习率选对了」的好评，就等于把检查当成了目的——真正的目的是让实验可复现、可核对、可交接。每次调完学习率，都要重新跑一次取真值，再按真值改清单；反过来为了让绿字好看而放宽阈值，拆掉的是自己立的规矩。

学习率还与参数的尺度有关。本例输入是标准正态量级，两层线性层的权重初值也在同一个量级，因此一个固定的 0.5 能同时伺候所有参数。若某层权重典型取值是 1e-3、另一层是 1e3，同一个绝对步长对前者是巨步、对后者是微步。这就是合理初始化与输入标准化如此重要的原因——它们让各参数的可行尺度接近，固定学习率才有机会同时合适。

10.7 检查点、实验记录与失败模式

一次实验要能交给别人，光有 stdout 不够，还得留下三样东西：检查点、实验记录清单、失败模式表。检查点保存的是参数——state_dict 里是各层的权重与偏置，不是模型代码，也不是优化器状态（除非另外存）。恢复时要先按同样的结构建模型，再 load_state_dict。本例用内存字节流演示，ckpt_bytes=2525 就是这份状态的大小；真项目里换成写文件，并按步数或验证误差命名，比如 best_val_7.pt。

实验记录清单就是那份 JSON 清单。它记下 id、语言、源文件、模式、单元路径、输出块 id、种子环境变量与主对照种子，还有收敛判据。读者拿到清单就知道「这是在什么条件下跑出来的」，不需要翻源码找常量。反过来，源码里出现 seed = 12345 这种硬编码就破了这个约定——数字藏在算法里，别人无从知道它是实验条件。

失败模式表则把「症状—可能原因—怎么查」摆在一起，让出问题时不至于瞎调。

实验记录亲手制造一次「忘了清零」

把 main.py 里的 opt.zero_grad() 注释掉，重新用 ML_SEED=12345 python src/main.py 跑。梯度会逐轮累加，实际步长越迈越大，前八步的非增判定被破坏，闸门报 train_loss_not_decreasing。再试一次把 seed = int(os.environ["ML_SEED"]) 改成 seed = 12345，闸门会在第三次运行时发现换种子后十二行 loss 完全相同，报 seed_has_no_effect。做完把两处都改回去，程序必须重新打印清单里那十四行原始 stdout。这两个实验值得真做——它们是理解「累加而非覆盖」与「种子是证据」最快的方式。

10.7.1 检查点里到底存什么

state_dict 只含有可学习参数与缓冲区，按层名索引。本例两层各有一个权重和一个偏置，共四个张量；fc1.weight 的形状是 8×2，fc1.bias 是 8，fc2.weight 是 1×8，fc2.bias 是 1。加上序列化的头部信息，正好凑出 2525 这个字节数。注意它不存模型结构：恢复时若把 2-8-1 写成 2-16-1，load_state_dict 会直接报形状不匹配——这是好事，它让结构错误在加载时暴露，而不是等推理出错了再查。

工程惯例为什么不把优化器也存进去

只存参数适合「拿去推理」的场景；若中途中断要接着训练，还得存优化器状态与当前步数，否则动量的累积量丢失，续训的轨迹和不中断训练不同。本例没有动量，续训影响小，但纪律要提前立：检查点的命名要能区分「只含参数」与「含优化器状态」，别让人拿推理用的检查点去续训。代价只是多存一份状态，换来的是恢复行为可预期。

10.7.2 一份实验记录的十项自检

交付前照着清单过一遍，比事后追 bug 省事。第一，id 是否全局唯一；第二，lang 是否写了 python；第三，sources 是否至少两个 .py，且入口 import 了本地模块；第四，清单里有没有偷偷写 flags 或 libs——Python 运行器不接受这两样；第五，mode 与 expect 的证据类型是否对上，train 必须配 train 而不是 numbers；第六，unit 指向的 md 是否真实存在；第七，正文的 output 块 id 是否与清单的 output 字段一致；第八，种子是否来自 seed_env 而不是源码常量；第九，收敛阈值是否来自真跑并留了余量；第十，对照种子是否与主种子拉开距离，能看出明显差别。

这十项没有一项需要读懂框架源码，全是能在一次运行里核对的观察量。它们正好对应本单元几张图的层次：文件对应 tree，数据流对应流水线图，验证对应三次运行图，证据对应阈值表。养成按清单自查的习惯，比记住某条报错文本更值钱——报错文本会随版本变，这十个问题不会。

10.8 图元复盘与整章回望

这一单元画了五张图。tree 标出新增的工程文件；graph 画六站流水线，重点在「损失是信号、优化器只认梯度、评估不建图」；memory 把四十八个点切成三层，重点是两条不许跨越的边；graph 画三次运行，重点是同种子证明确定性、换种子证明非硬编码；最后一张 graph 画四步循环，重点是小批量 loss 用来反向、全量 loss 用来观察。

读多帧图守住三条纪律。每一帧自包含：渲染器不会把上一帧的节点带过来，仍成立的节点要重写一遍，第 2 帧里那些没带 * 的节点就是这么来的。节点文字不超过十八个字，长解释留在正文。箭头两边留空格，主一 -> 算法 才会画成边，主一->算法 只是文字。这些规矩让同一份围栏在网页、打印版和步进器里长得一样。

工程惯例把这一单元接到后续

下一册开始讲更多架构时，本单元的六站不会变：换的只是模型站的结构与数据站的输入形态。卷积网络把全连接换成卷积层，循环网络把一批样本换成一条序列，但清账、前向、反向、更新四步照旧，种子与对照的三次运行也照旧。理解本单元的流水线之后，那些新架构只是替换其中一个零件，不是推翻重来。

工程惯例用三个问题复盘任何一份训练报告

拿到别人的实验报告，先问三件事。第一，起点在哪：本例首行 0.508848，离最优还有明显距离，才有下降可演示；若首行已经接近零，整条轨迹平坦，什么也证明不了。第二，中间有没有异常：十二行 loss 一直下降，但你要同时看参数范数与梯度范数，才能排除「loss 降、参数在爆」的假收敛。第三，证据够不够：单看一次运行的轨迹，可能是硬编码；再看同种子复现与对照种子，三条证据合起来才算数。养成这三个问题的习惯，你读别人的实验报告时就不会只看「loss 降了」四个字，也不会把一次漂亮的截图当成可复现的结论。写报告时反过来用同样三问自查，读者关心的问题就都被回答过了。

  • 完整实验六站：数据、模型、损失、优化器、循环、评估；损失是反向信号，优化器只认 .grad，评估不建图；
  • train、val、test 三层各管训练、选型与最终报告，界限混了数字就不可信；
  • 三种随机源一起固定；train 闸门跑三次：同种子逐值一致、对照种子改变输出、轨迹满足起点终点降幅与前八步非增；

注自测题答案
  1. 损失把预测与标签的差距压成一个标量，交给反向填梯度；优化器不认识损失，只遍历参数读 .grad 做更新。full_loss 包在 torch.no_grad() 里，不建图，所以可以用整套数据而不必为每条样本保存中间量。
  2. 拿测试集选型会让报告数字带上选择偏差：你是在多个候选里挑最好的，它天然偏高。本例在十二步全部结束后只在测试集上算一次 acc，报的是最终模型，不是十二步里的最高值。真正挑模型应该用验证集。
  3. random、numpy、torch 三条流互不知情，漏掉任何一条都可能让第二次运行的轨迹漂移。多线程归约的加法次序可能因调度不同而使浮点末位有差，set_num_threads(1) 把次序固定下来，避免这类末位抖动触发误报。
  4. 同种子两次证明确定性，换对照种子证明数值不是硬编码。若打印了 seed=12345，换种子后这一行必然变化，seed_has_no_effect 会平凡通过——即便十二行 loss 全是写死的。
  5. first_min=0.5 对首行 0.508848，last_max=0.08 对末行 0.075274，decline_min=0.43 对降幅 0.433574，monotone_window=8 对前八步严格递减。把 last_max 放宽到 1.0，闸门是过了，但「必须真的收敛」的纪律被自己拆掉。
  6. state_dict 存各层权重与偏置，不存模型结构与优化器状态。恢复要先按同样结构建模型再 load_state_dict；拿只含参数的检查点续训会丢失优化器累积量，续训轨迹与不中断训练不同，若模型是含动量的优化器尤其明显。
