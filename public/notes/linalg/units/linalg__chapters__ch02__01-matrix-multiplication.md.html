3.1 先看工程长什么样

这是全书第二个项目：从第 2 章开始，examples/ 下不再只有一个目录。第 1 帧是这一节开始时的形态——上一章的两个例子还在，但 ch02/ 什么都还没有。第 2 帧标 + 的就是这一节新增的东西。请特别注意 src/ 和 include/ 分家这件事，从这一章起它成了规矩。

第 2 帧里 main.c 负责准备数据、调库、打印；matmul_local.c 放这一单元的两个手写算法——手写的矩阵乘向量和手写的矩阵乘矩阵；matmul_local.h 只放这两个函数的声明；清单把三个源文件（加上共用库）串成一条编译命令。共用库 common/ 这一节照旧不动，mat_get、mat_set、mat_vec、mat_mul 都从它来。

为什么要分家？三个理由：接缝可见（调用方只看头文件就知道有哪些算法可用，不必读实现）；各改各的（改手写循环的实现不会碰到打印格式）；能接手（别人接手时先读头文件，十秒钟就知道这个例子在做什么）。代价是要多写 include guard、多维护一份声明——声明和实现不一致时编译器会替你抓出来，这正是它的价值。注意清单的 sources 列了两个 .c 文件，flags 里有 -Iinclude，闸门从第二个项目起会检查这一点，防止退回到单文件工程。

3.2 矩阵乘向量：每一行都是一个点积

先给结论：Wx 就是把 W 的每一行分别拿出来，和向量 x 做一次点积，结果的行数等于输出的元素数。这一节取

  • W = [[1,2],[3,4]]，两行两列；
  • x = (2,1)；
  • 偏置 b = (0.5,-1)。

逐行算：

  • 第 0 行 (1,2)·(2,1) = 1×2 + 2×1 = 4；
  • 第 1 行 (3,4)·(2,1) = 3×2 + 4×1 = 10。

所以 h = Wx = (4,10)。再加上偏置 b 得到 y = h+b = (4.5,9)。这就是一层全连接网络（fully connected layer）最核心的计算，术语叫 forward（前向）：输入进来，线性变换，加上偏置，输出。

下面是手写版本的实现，来自 matmul_local.c 的第 5 到 17 行。注意内层循环里那一行 sum += mat_get(w, i, j) * x->v[j]——它就是你刚手算的 1×2 + 2×1，只不过让 j 从 0 跑到 cols-1 反复执行。

为什么外层循环走行、内层走列？因为输出 out 的第 i 个元素只依赖 W 的第 i 行，把 i 放外层可以让 sum 只用一个局部变量反复累加，不必先给输出数组清零再逐格追加。这也正好对应行主序的内存布局——第 i 行的 cols 个元素在内存里是连续的，内层循环顺着这个连续性往前走，缓存命中率最好。第 3.6 节会把这件事画出来。

再用上一单元的语言复述一遍：W 的每一行都是一个向量，Wx 的每一个输出都是「这一行与 x 的点积」。点积衡量的是方向是否一致，所以 h 的第 i 个分量可以理解为「输入 x 与第 i 个权重模式有多契合」。权重行 (1,2) 与输入 (2,1) 方向接近，点积就大；若某一行是 (1,-2)，与 (2,1) 点积为 2-2=0，输出就是零——这个神经元对当前输入「没有反应」。把权重想成一组探针，每层就是在问输入对这组探针的响应有多强，这是理解网络层很好用的画面。

你可能会问：共用库里已经有 mat_vec 了，为什么还要手写一遍？因为这一册的目的不是调库，而是让每一步数值都能追到具体的一行代码。mat_vec 的实现就在 common/src/linalg.c 里，它和这里的 matvec_manual 做的是同一件事；两份代码独立写出来再对拍，才构成证据。如果只调库不看实现，输出里那个 4 从哪来就成了一个黑箱。

3.3 数据流：x 经过 W，再加 b 变成 y

一层网络的数据流有五个角色：输入 x、权重 W、线性结果 h、偏置 b、输出 y。下面这张图按时间顺序拆成三帧，第 2 帧单独看矩阵乘，第 3 帧加上偏置。

第 1 帧只有两个演员。第 2 帧出现 h，箭头 W -> h 上标的是「逐行点积」——这一帧把上一节的公式变成了盒子里的一组数。第 3 帧把 b 加进来：h 和 b 各自有一条箭头指向 y，表示输出的两个分量分别是 4+0.5 和 10+(-1)。注意偏置是逐项加的，不是矩阵乘进去的；这是很多初学者第一次写网络层时最容易写错的地方。

把这张图压缩成一行，就是 x → W → h → b → y。以后看到更深的网络，无非是把这一行的 y 再接到下一层的 W 上，中间多插入一个非线性函数（比如 ReLU）。这一单元只讲线性部分，因为非线性不改变形状，也不改变矩阵乘法这件事本身。

再补一个容易忽略的细节：Wx 做的是线性变换，它满足 W(x₁+x₂)=Wx₁+Wx₂ 和 W(αx)=αWx。这意味着一批输入一起送进去，和逐个送进去再拼起来，数学上完全一样——这正是 3.4 节把多个输入按列排成 X 的理论依据。如果这一层在 Wx 之后接了非线性函数，这个可拆分性就不再成立，但形状规则不变。第 10 单元会从微分的角度再看这件事，那时你会知道反向传播里的转置就是从这些形状约束里长出来的。

陷阱你怎么会被坑到：把 Wx 和 xW 写反

你会看到代码里 mat_vec(&W, &x) 跑通了，于是以为把两个参数换个位置也行。真相是形状不答应：W 是 2×2 时恰好两种顺序都能编过，换个维度就露馅。假设 x 有 n 个输入、h 有 m 个输出，那么 W 必须是 m 行 n 列，Wx 才能给出 m 个数；写成 xW 要求 W 是 n×m，那是同一个权重的转置。更隐蔽的坑是偏置：有人把 b 也塞进矩阵乘里，给 W 多加一列、给 x 多加一个恒为 1 的分量——这确实能算出同样的数，但会让形状约定变复杂，调试时更难看清是哪一维出了错。本册一律用显式的 Wx+b，把线性部分和偏置分开。

3.4 矩阵乘矩阵：结果的每一列是列的线性组合

现在把「一个输入」推广到「一批输入」。假设有三个输入 x₁=(2,1)、x₂=(0,1)、x₃=(1,0)，把它们按列排成一个 2×3 的矩阵 X。那么 WX 是一个 2×3 的矩阵，它的三列分别是 Wx₁、Wx₂、Wx₃。换句话说，矩阵乘矩阵不是一种新的运算，而是把矩阵乘向量对每一列各做一次。

我们也可以从「列的线性组合」这个角度读它。W = [[1,2],[3,4]] 的两列是 c₁=(1,3)、c₂=(2,4)。对 x₁=(2,1) 而言，Wx₁ = 2c₁ + 1c₂ = (2,6)+(2,4) = (4,10)——正是上一节点积算出来的结果。这就是同一个乘法的第二种读法：行视角是点积，列视角是线性组合。上一单元讲的 αv+βw，在这里直接派上用场。

第 2 帧的标签「列 1 乘 2 加列 2 乘 1」就是 2c₁+1c₂。第 3 帧把三列结果 wb_col0=(4,10)、wb_col1=(2,4)、wb_col2=(1,3) 并排拼成 WX。这里三列的计算彼此独立，理论上可以并行——这是 GPU 擅长矩阵乘法的根本原因之一。

下面是手写版矩阵乘矩阵，来自 matmul_local.c 的第 19 到 35 行。它刻意选择了「列的线性组合」这条路径：每拿出一列 b，先复制成一个向量 col，再调用上一节的 matvec_manual，最后把结果写回输出矩阵的对应列。

为什么这里多了一步「把列复制成向量」？因为共用库的 vec_t 是一维结构，而矩阵 b 的列在 mat_t 里是竖着排的，拿它当 x 用之前得先装进一维数组。这一步不是数学需要，是数据结构接口的需要——读代码时要把这两类原因分开，才不会误以为矩阵乘法「多了一步」。

3.5 形状匹配：写代码之前先对一遍

矩阵乘法有一条铁律：(m×n)(n×p) = (m×p)。左边矩阵的列数 n 必须等于右边矩阵的行数 n；结果的形状是「左行数 × 右列数」。中间那个 n 被消掉，是因为它只是求和的下标——Wx 里每个输出都是对 n 个乘积求和，求和做完，n 就不出现在结果里了。

用这一节的数字核对一遍：

  • W 是 2×2，x 是 2×1（两行一列的列向量），所以 Wx 是 2×1，也就是两个数的向量；
  • W 是 2×2，X 是 2×3（三个输入按列排），所以 WX 是 2×3，对应三个输出、每个两维；
  • W 是 m×n，x 是 n×1，b 是 m×1，只有形状相同才能逐项加，所以偏置必须有 m 个分量。

这条规则不只是手写代码时的检查表，也是读框架报错的钥匙。看到 mat1 and mat2 shapes cannot be multiplied (2x3 and 4x2)，你立刻知道中间的 3 和 4 对不上——要么改输入维度，要么把其中一个矩阵转置。不需要去猜是哪一层的 bug。

再给一个批量场景的例子，帮你把按列排记牢。假设你要处理 32 个输入，每个 128 维，一层有 64 个输出神经元。那么输入矩阵 X 的形状是 128×32（每一列是一个样本），权重 W 是 64×128，偏置 b 是 64×1，输出 Y=WX+b 是 64×32——每一列对应一个样本的输出。如果你把样本按行排成 32×128，形状立刻对不上，框架就会报错。这个约定不是数学强制的，是框架的工程约定；一旦选定就要全项目一致，否则中间的转置会把你绕晕。

工程惯例这是工程惯例，不是标准

把偏置 b 单独存成一个与输出等长的向量、在矩阵乘之后逐项加，是深度学习框架的通行惯例，不是数学或 C 标准的规定。这样做的理由是形状直观、报错好定位——线性部分和偏置部分各自独立。代价是每一步都要多检查一次 b 的长度；有人为了省这一步，把偏置塞进权重矩阵（给输入多加一维常数 1），数学上等价，但形状约定变隐晦。本册选显式写法，因为我们要把每一步的数值来源讲清楚。

3.6 行主序：同样的数字，不同的内存顺序

C 的二维数组 double a[2][3] 在内存里是按行连续排放的：先存第 0 行的三个数，紧接着存第 1 行的三个数。这叫行主序（row-major）。共用库的 mat_t 里是 a[LA_MAX][LA_MAX]，mat_make 按 values[i*cols+j] 填格——i*cols+j 这个下标算式正是行主序的定义。

我们的 batch 矩阵 X = [[2,0,1],[1,1,0]]，六格连续内存如下。第 1 帧按行列坐标标出每一格的值，第 2 帧强调「下一行的起点 = 上一行起点 + cols」。

为什么要关心这个？因为缓存按「连续的块」搬数据。matvec_manual 的内层循环让 j 递增，访问 W 的第 i 行时地址是连续往前的，一次缓存加载就能喂饱好几次乘法；如果循环顺序写成内层走 i、j 放外层，每次访问都要跳过一整行，命中率骤降。矩阵规模小的时候你看不出差别，规模一大就是几倍的性能差距。这里用 -O0 编译，目的是让数值来源透明，不追求速度；但内存布局的道理在哪种优化级别下都成立。

反过来说，列主序语言（比如 Fortran）会把同一组数字竖着排，那里「内层走列」才是快的。数字相同，快的循环顺序相反——这就是「行主序」这条知识必须在写代码之前就知道的原因，否则你优化的方向可能是反的。

还有一个现实问题：定长数组会浪费内存。共用库的 mat_t 用 LA_MAX=8 开成 a[8][8]，哪怕这一节只用到 2×2，那 64 格也照占不误。换来的是代码简单——不用动态分配、不用释放、也不用处理分配失败。在这个量级浪费可以忽略；真实框架里矩阵可能上亿个元素，就必须用紧凑存储加尺寸信息，不能这么豪爽。理解这一节的数值时，记住 rows、cols 才是有效范围，后面的空槽不参与任何计算。

3.7 真跑：手写循环与库函数对拍

这一节的程序做了两次对拍：手写 matvec_manual 与共用库 mat_vec 比，手写 matmat_by_columns 与共用库 mat_mul 比。对拍的判据是两个结果矩阵（向量）对应元素绝对差的最大值——都是 0，说明两套独立写出来的算法给出完全一样的数。下面这段来自 main.c 的第 31 到 44 行，是全部输入与调用；它把实数直接写在数组里，没有随机数，所以任何人重跑都得到同一组数。

把输出逐行读一遍：h 是手算的 (4,10)，h_lib 是共用库算的，两者相同；y=(4.5,9) 是加了偏置的输出；WX 的三列是 (4,10)、(2,4)、(1,3)，与 3.4 节第 3 帧画的完全一致。数值行里 h0、h1、y0、y1 是黄金值，check 与 mm_check 是两次对拍的最大绝对差。

为什么坚持用 -O0 编译？因为优化级别会改变浮点运算的结合顺序，某些平台上 a*b + c*d 可能被融合成一次乘加，最后几位的舍入就不一样了。-O0 下代码和公式一一对应，屏幕上打出的 4.000000 你能立刻指到是哪一行乘出来的。等数值来源确认无误再谈优化也不迟——这也是调试数值 bug 的通用起手式：先关优化复现，再开优化比对。

实验记录闸门怎么证明这些数不是编的

清单 la03-matmul.json 用 mode=numerical，在 expect.numbers 里写了六个黄金值，各给 atol=1e-6。闸门按 sources 与 flags 真编译，真跑程序，再从 stdout 解析 h0=4.000000 这类行，与黄金值逐一在容差内比对。正文里那六个数受同一份容差约束——想把 y1 从 9 改成 10 让图好看，闸门会报数值不符。另外，因为这是第二个项目，闸门还会检查清单列了至少两个源文件、且头文件确实被源文件包含，防止把例子退化成单文件。

陷阱你怎么会被坑到：把对拍的零当成「永远不会错」

你会看到 check=0.000000、mm_check=0.000000，于是认为两套算法互相印证，结论绝对可靠。真相是：如果两套实现犯了同一个错（比如都把 x 的下标从 1 开始、都漏掉最后一列），对拍照样给出零。对拍证明的是「两套独立代码在这组输入上一致」，不是「数学上正确」。所以要再拿一组手算过的数当外部锚点——这里 h=(4,10) 就是我们在 3.2 节逐行点积算出来的，它不依赖任何程序。以后写梯度检查时也是同一条纪律：解析梯度与数值梯度对上，还要拿一个能手算的简单函数验证公式本身。

3.8 这一节新增了什么

回到 3.1 的第 2 帧：新增的是 ch02/ 这个项目和它的单元文件、清单；手写算法进了 src/matmul_local.c，声明进了 include/matmul_local.h，main.c 只负责摆数据、调用和打印。共用库一行没改，mat_vec 与 mat_mul 原样被拿来当对拍的参照。

这一节回答的问题是「为什么一层网络写成 Wx+b」。答案是：Wx 把每个输入按权重线性组合成输出，形状规则让流水线能一层层接下去，b 补上每个输出自己的基准。下一单元问反过来行不行——给定输出，能不能解回输入？那就是逆与高斯消元。

3.9 为什么矩阵乘法要这样定义

3.9.1 它是「复合线性变换」的算术版本

到目前为止我们把 Wx 当成「每行与 x 点积」的规则来用，但没回答一个根本问题：为什么偏偏是「行乘列求和」这个奇怪的规则，而不是逐格相乘？ 答案要从「线性变换的复合」说起。

设 A 是 n×m、B 是 m×p，它们各自代表一个线性变换：先把 p 维向量变成 m 维，再把 m 维变成 n 维。现在问：直接把 p 维变成 n 维的那个变换 C 是什么？

把 x 先过 B：(Bx)ᵢ = Σⱼ Bᵢⱼ xⱼ（结果第 i 个分量）。再把这个结果过 A：yₖ = Σᵢ Aₖᵢ (Bx)ᵢ = Σᵢ Aₖᵢ (Σⱼ Bᵢⱼ xⱼ)。交换求和顺序并提取 xⱼ：yₖ = Σⱼ (Σᵢ Aₖᵢ Bᵢⱼ) xⱼ。括号里那一串 Σᵢ Aₖᵢ Bᵢⱼ，正是「A 的第 k 行与 B 的第 j 列的点积」。我们把这个数定义成 Cₖⱼ，于是 y = Cx，而 C 就是 AB——矩阵乘法的定义，是被「先做 B 再做 A」这件事唯一逼出来的。它不是人为挑的方便规则，而是线性变换复合在坐标下的必然算术形式。

这也解释了形状规则为什么是 (n×m)(m×p)=(n×p)：中间的 m 是「中转站的维度」，先由 B 产生、再被 A 消费；求和下标 i 走完 m 项后被消掉，所以结果里不再有 m。

3.9.2 结合律的严格证明

现在证明 (AB)C = A(BC)。这件事在代码里几乎不用想（框架自动做），但证明它能让你明白「为什么可以任意结合」，以及浮点实现里为什么结合顺序仍会影响末位。

设 A 为 m×n、B 为 n×p、C 为 p×q。比较两边第 i 行第 j 列的元素。左边：

((AB)C)ᵢⱼ = Σₖ (AB)ᵢₖ Cₖⱼ = Σₖ (Σₗ Aᵢₗ Bₗₖ) Cₖⱼ

右边：

(A(BC))ᵢⱼ = Σₗ Aᵢₗ (BC)ₗⱼ = Σₗ Aᵢₗ (Σₖ Bₗₖ Cₖⱼ)

把左边的求和顺序交换，并利用实数的分配律与乘法结合律：

Σₖ Σₗ (Aᵢₗ Bₗₖ) Cₖⱼ = Σₗ Σₖ Aᵢₗ (Bₗₖ Cₖⱼ) = Σₗ Aᵢₗ (Σₖ Bₗₖ Cₖⱼ)

两边逐项相等，故矩阵乘法满足结合律。证明只用了三条实数性质：加法交换律（交换两个求和）、乘法结合律、分配律。有限求和可以换序是关键——这在数学上无条件成立，在浮点实现里却不严格成立（舍入顺序不同），这就是上一章说「优化级别会改变末位」的根源。

3.9.3 不满足交换律恰恰是信息的载体

AB ≠ BA 通常成立，初学者常把它当成缺陷。其实它承载了重要信息：先做 A 再做 B，与先做 B 再做 A，本来就是两个不同的操作。比如先旋转再平移，和先平移再旋转，结果当然不同。数组时代「乘法交换」的直觉在这里失效，是因为矩阵乘法描述的不是「两个数相乘」，而是「两个动作先后发生」。唯一的例外是标量（1×1 矩阵），那时退化为普通乘法。联想到深度学习：W₂(W₁x) 与 W₁(W₂x) 是两种不同深度的网络结构，不能随便交换——层的顺序就是计算图的顺序。

陷阱结合律成立，不代表代码里可以随便重排括号

数学上 (AB)C = A(BC) 精确相等，但浮点实现里 (A@B)@C 与 A@(B@C) 的舍入路径不同，末位会有差异；更严重的是，不同的括号顺序对应不同的中间矩阵大小，性能差别巨大。比如 A 是 10×10000、B 是 10000×10、C 是 10×10000，先算 AB 得到 10×10，再乘 C 只需十万次运算；先算 BC 得到 10000×10000，则要一亿次——结果数学上一样，耗时差了千倍。深度学习框架里的「算子融合」「矩阵链优化」就是在结合律允许的范围内挑最省力的括号顺序。数学的等号不保证性能相等。

3.10 失败模式：形状、广播与对拍盲区

3.10.1 形状不匹配：报错反而是好事

(m×n)(n×p) 中间两维对不上时，框架会直接抛错，比如 mat1 and mat2 shapes cannot be multiplied (2x3 and 4x2)。这种错误虽然中断程序，但定位极快：报错信息把两个形状都打出来了，你只需把中间的 3 和 4 对齐——要么改输入维度，要么转置其中一个矩阵。相比之下，C 版本的 mat_t 不做形状检查，传错维度会读出空槽或未初始化内存，程序照跑，结果却是一堆看着像模像样的小数。这类静默错误要靠清单的黄金值才能发现：正文若写了手算的 h=(4,10)，而程序因为形状错给出别的值，闸门报 numeric_value_mismatch。所以「用等号写黄金值」不只是排版选择，它是抓静默错误的网。

3.10.2 偏置广播：加错维度

偏置应当加到输出的每一行（或每一列），形状是 m。框架会自动「广播」：一个长度为 m 的向量加到 m×batch 的矩阵上，会沿 batch 维复制。初学者常把偏置写成形状 (batch,)，结果加到了错误的维度上——数学上完全不是一回事，但因为广播规则会「好心」地把它扩成可加的形状，程序不报错，只是结果悄悄错了。防御办法是在加偏置前后各打印一次形状，确认被广播的是你期望的那一维。这跟第 1 单元「维度不匹配是静默错误」是同一类问题，只是换到了矩阵维度上。

3.10.3 循环顺序写反：结果对，速度错

matvec_manual 外层走行、内层走列，是为了顺着行主序的连续内存。若把顺序写反（外层 j、内层 i），结果完全正确——求和顺序变了，数学不变；但缓存命中率骤降，矩阵一大就慢好几倍。这类 bug 不会被闸门发现（数值在容差内），只能靠性能测试或阅读代码发现。它提醒我们：数值正确只是底线，不是全部；内存布局的知识要在写循环之前就具备，否则优化方向可能是反的。

实验记录制造一次形状错误看闸门反应

把正文里 y=(4.5,9) 中的 9 改成 10（保留其余），然后跑单元渲染。闸门会报 numeric_value_mismatch：正文的黄金值与程序真跑的 y1=9 对不上。这说明正文里的每个等号数值都被清单的容差盯着。再想一步：如果连程序里的偏置也一起写错（比如把 bv 改成 (0.5,0)），真跑的 y1 就变成 10，此时正文与程序一致、闸门反而通过——所以闸门只能保证「文、程序、清单三者一致」，不能保证「数学正确」。数学正确要靠 3.2 节那次独立的手算 h=(4,10) 当外部锚点。

3.11 与深度学习的对应：注意力的四次矩阵乘

自注意力层是矩阵乘法最密集的地方。把输入 X 按列排成 d×n（n 个 token，每个 d 维），则：

  • Q = Wq X、K = Wk X、V = Wv X：三个投影矩阵（d×d）分别把输入变成 query、key、value，这三次都是 d×d 乘 d×n；
  • S = Qᵀ K：注意力的原始分数矩阵（n×n），第 i 行第 j 列是第 i 个 query 与第 j 个 key 的点积除以 √d——这是第 1 单元点积的批量版；
  • O = V · softmax(S)ᵀ：输出（d×n），每一列是 value 按注意力权重的线性组合——这是第 2 单元的 αv+βw 推广到 n 项。

一次注意力，把前三单元的工具全用上了：点积算分数、线性组合算输出、矩阵负责批量。读框架源码时看到 qkv = Wqkv @ x、attn = q @ k.transpose(-2,-1)、out = v @ attn，你要能立刻把每一行翻译成上面这三步。形状贯穿始终：Wq 是 d×d 才能把 d×n 的 X 变成 d×n 的 Q；QᵀK 是 (n×d)(d×n)=(n×n)，正好是每对 token 一个分数。这些形状不是约定俗成，是矩阵乘法规则逼出来的。

工程惯例手算一个小注意力

取两个 token，每个 1 维，设 q=(1,2)、k=(1,0)（列向量），V=[v₁ v₂] 为 1×2 矩阵 [[3,5]]。则 S = qᵀk = 1×1+2×0=1（这里只有一个分数，形状 1×1）。softmax([1])=[1]，输出 O = V·[1] = [3]。若有两个 key K=[[1,0],[0,1]]，则 S=qᵀK=(1,2)，softmax 后约为 (0.269,0.731)（用 e¹/(e¹+e²) 等计算），输出 O=3×0.269+5×0.731≈4.46。这个数完全由「点积定权重、线性组合定输出」两步算出，和你在本节手算 Wx 是同一套动作——只是规模大了些。

3.12 手算核对：2×2 乘 2×3 的每一格

取 W=[[1,2],[3,4]]（2×2）、X=[[2,0,1],[1,1,0]]（2×3），按列看 X 的三列是 x₁=(2,1)、x₂=(0,1)、x₃=(1,0)。逐列算：

  • 第一列：Wx₁=(1×2+2×1, 3×2+4×1)=(4,10)；
  • 第二列：Wx₂=(1×0+2×1, 3×0+4×1)=(2,4)；
  • 第三列：Wx₃=(1×1+2×0, 3×1+4×0)=(1,3)。

把三列横着拼起来，得到 WX=[[4,2,1],[10,4,3]]——与屏幕上的 WX:[4.000000,2.000000,1.000000;10.000000,4.000000,3.000000] 逐格一致。再用「列的线性组合」复算第一列：W 的两列是 c₁=(1,3)、c₂=(2,4)，2c₁+1c₂=(2,6)+(2,4)=(4,10)，一致。两种读法给出同一个结果，正是本节的核心结论。最后核对形状：(2×2)(2×3)=(2×3)，结果是 2 行 3 列，六个数，与拼出来的矩阵格数相符。

注深化自测答案

3.13 读图、精度与初始化的另外三件事

3.13.1 三张图各自在讲什么

这一单元的 tree 标记了第二个项目的诞生：注意 src/ 与 include/ 分家这一变化，它从第 3 单元起成了全册规矩。graph 里最关键的是第 2 帧的 W -> h 与第 3 帧的 h -> y、b -> y：前一条箭头是矩阵乘（线性），后两条是逐项加（偏置），画成不同的箭头就是为了提醒你「偏置不进矩阵乘」。memory 则把 X 的六格连续内存摊开，让你看到 a[1][0] 为什么紧接在 a[0][2] 后面。读图时把「数据在内存里怎么排」和「数学上怎么算」分成两条线：前者决定快不快，后者决定对不对。

3.13.2 内维越大，累加误差越明显

matvec_manual 的内层循环把 n 个乘积逐个加进 sum。每一项都有舍入，n 项累加的误差大致随 √n 或 n 增长——这就是深度网络里「内层维度很大时，矩阵乘的精度会悄悄变差」的根源。用一个小例子感受：取 x = (1e8, 1, -1e8)、w 的一行为 (1,1,1)，真结果是 1，但若先算 1e8+1 再减 1e8，单精度下 1e8+1 已经舍入成 1e8，结果变 0。double 有效位多，小例子还撑得住；当维度上千、量级参差不齐时，误差积累就需要关注。工程上的对策包括补偿求和、分块累加、以及近年流行的混合精度训练——用低精度算乘法（快）、用高精度累加（准）。

3.13.3 矩阵乘法决定了权重该怎么初始化

你可能好奇：为什么全连接层的权重常按 ±1/√n 的量级初始化？答案就藏在矩阵乘里。y = Wx 的每个输出是 n 项乘积之和，若 x 的分量均值为 0、方差为 1，W 的元素独立同分布且方差为 σ²，则由方差的可加性，y 的方差约为 nσ²。为了让信号在层间传播时方差不爆炸也不消失，应令 nσ² ≈ 1，即 σ ≈ 1/√n。这个「Xavier 初始化」的推导没有用到任何深奥理论，只是第 1 单元方差分析加上本单元「每行是 n 项求和」的直接结论。它再次说明：看似经验性的调参规则，往往能追溯到最朴素的算术性质。

工程惯例分块：把大矩阵乘拆成能塞进缓存的小块

行主序决定了「连续访问快」，但整个矩阵塞不进高速缓存时，光靠循环顺序还不够。工业级矩阵乘（如 BLAS 的 GEMM）会把 A、B、C 切成若干小块（tile），每次只把一小块搬进缓存，算完一块再换下一块。分块之所以合法，正是因为结合律允许我们改变求和的分组方式——(AB)C 与 A(BC) 数学上相等，所以可以按任何块边界累加。你在本节手算的 2×2 例子太小，看不出分块的价值；但当矩阵大到几万维时，分块与否就是「几秒」和「几分钟」的差别。理解这一点，你就明白为什么硬件友好的实现要同时懂内存布局和结合律。

3.14 为什么坚持写两遍：对拍的认识论

3.14.1 两份实现互为镜子，但需要第三只眼睛

这一单元的程序同时保留了 matvec_manual（手写）与共用库的 mat_vec（现成），还让它们对拍。有人觉得多余：库函数既然正确，直接用不就行了？对拍的意义不在于「证明其中一个对」，而在于让两个独立写出来的实现互相照见盲点。手写版本盯着公式，库版本盯着工程优化，两者犯同一个错误的概率远低于单独一个。但第 3.7 节的陷阱已经指出：若两者犯同一个错（比如下标从 1 开始），对拍仍然给出零。所以对拍提供的只是「一致性」，不是「正确性」。要得到正确性，必须引入第三只眼睛——一个不依赖任何实现的手算锚点，比如本节反复验算的 h=(4,10)。这套「两份实现 + 一个手算锚点」的三重结构，是后面所有数值单元（求逆、分解、微分）自查的模板。

3.14.2 选测试输入也有学问

对拍用的输入若太「乖」，会漏掉很多 bug。比如把 W 全填 1、x 全填 1，那么任何把某几行加错位置的实现都可能给出相同结果；把 x 全填 0，输出全为 0，几乎什么都测不出来。好的测试输入要故意包含：正负混合（测抵消）、非零非一（测缩放）、各分量不同（测下标是否写错）、以及形状边界（最小维度、最大维度）。本节的 W=[[1,2],[3,4]]、x=(2,1) 就满足这些条件——四个权重各不相同、有正有正的偏置、三列输入也互不相同。改变其中任何一个数，手算结果就会跟着变，从而让程序「无处藏身」。以后写梯度检查时，挑测试点也用同一原则：别只测 x=0 这种平凡点。

陷阱别让「对拍为零」替你做数学证明

check=0.000000 只说明两套实现在这这一组输入上一致。换一组输入，它们可能同时错。把这条纪律记牢：数值世界的证据总是分层的——对拍给一致性，手算给正确性，容差给合理性，三者各管一摊，谁也替代不了谁。闸门只核对正文、程序、清单三者一致；数学对不对，永远要由你自己用纸笔或独立的推导来背书。

小结这一节的要点
  • 矩阵乘向量 = 每行与向量点积；矩阵乘矩阵 = 结果每列是左矩阵列的线性组合；
  • 形状规则 (m×n)(n×p)=(m×p)，中间的 n 是求和下标，加偏置要求 b 与输出等长；
  • 一层 forward 的数据流是 x → W → h → b → y；偏置逐项加，不进矩阵乘；
  • mat_t 按行主序存储，下标 i*cols+j；内层循环顺着连续内存走，缓存才高效；
  • 手写循环与库函数两版对拍，再用一组手算值当外部锚点，才能同时排除实现错与公式错。

  5. 手写与库函数对拍结果全是 0。这能不能证明算法数学上正确？还需要什么？
注自测题答案
  1. 行视角：第 0 行 2×3+0×1=6，第 1 行 1×3+3×1=6，所以 Wx=(6,6)。列视角：W 的两列是 c₁=(2,1)、c₂=(0,3)，3c₁+1c₂=(6,3)+(0,3)=(6,6)，一致。
  2. AB 的形状是 3×2：左行数 3、右列数 2，中间的 4 被消掉。BA 要求 B 的列数 2 等于 A 的行数 3，不成立，所以形状不匹配，无法相乘。
  3. W 有 m 行，Wx 就有 m 个输出分量；偏置是逐项加到输出上的，必须等长才能加。W 的列数 n 对应输入维度，与偏置无关。
  4. 偏移是 1×3+2=5；它前面一格是偏移 4，也就是 a[1][1]。第二行紧接第一行末尾，中间没有空隙。
  5. 不能。对拍只能证明两套实现在这组输入上一致；若它们犯同一个错，残差仍是 0。还需要一个不依赖程序的外部锚点，比如手算过的 (4,10)，或者一个已知答案的小测试用例。
