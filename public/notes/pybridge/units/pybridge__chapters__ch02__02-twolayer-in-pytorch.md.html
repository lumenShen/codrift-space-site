3.1 先看工程长什么样

上一单元把 autograd 的记账机制讲透了，这一单元把它用到一个「真」网络上。所谓真，是指它有 13 个可调参数、有隐藏层、有非线性激活——和 dlmath 分册那个手写试点在结构上逐行对应。我们不做「换个更高级的模型」这种事，而是故意用同一个网络，这样两边的每一个数字都能摆在一起比。

证据口径也保持一致：输入 (0.5,-0.3)、目标 0.8、种子 12345。更严格的是，我们连 13 个初值都从 C 分册的 LCG 复刻过来，让两个实现从完全相同的起点出发。这样 y、loss、grad_b2 三个数就应该逐位一致——它们若不一致，一定是某一边写错了，没有「初始化不同」这个借口可找。

大白话先建立一个画面

把 C 版本的 net_t 想成一块木板，上面钉着 13 个旋钮：6 个连输入到隐层，3 个隐层偏置，3 个连隐层到输出，1 个输出偏置。前向就是顺着电线把信号从左边推到右边；反向就是拿一支笔从右边沿原路倒着描回去，在每个旋钮旁记下「动它一格，误差变多少」。

C 版本里那支笔是你自己拿的，13 个偏导数要一个个推。这一节把笔交给框架：你把电线接好、把误差递到最右端，剩下来的描线工作由 backward() 完成。

第 2 帧里带 + 的三行就是这一节的全部新增。net.py 收起网络结构与权重生成，main.py 负责前向、反向、对拍与打印，pb05-twolayer.json 钉住五个黄金值。和上一节一样，入口必须 from net import ...——这是 ch02 起的硬要求，也逼你把「网络定义」和「实验驱动」分开。

工程惯例为什么权重生成也放进 net.py

你可能觉得生成 13 个随机数放进 main.py 更省事。但权重初值属于「模型的一部分」，不属于「实验流程」；把它放进 net.py，以后换初始化方法只改一个文件。更重要的是，本例要在 Python 里复刻 C 的 LCG——这段代码的正确性直接决定两边能不能逐位对上。把它和前向、loss 放在一起，你读 net.py 就能看到完整的「这个网络是什么」；main.py 则只读出「这次实验跑了什么」。

3.2 13 个参数：把结构体翻译成四个张量

dlmath 的头文件里，net_t 有四个字段：w1[2][3]、b1[3]、w2[3]、b2。数量分别是 6、3、3、1，加起来 13。PyTorch 这边没有结构体，而是四个独立的叶节点张量：

第 2 帧里 b2 是零维张量而不是 Python 浮点数，这一点很关键。只有张量才能带 grad_fn 和 .grad；如果把 b2 写成普通 float，它一参与运算就会把 s 变成普通浮点，后面 torch.sigmoid 虽然还能调用，但 b2 这条支路上根本没有梯度可言。所以 torch.tensor(0.8) 和 0.8 看似一样，在计算图里是两回事。

四个张量放在一个元组 params 里传进函数。这是本例的取舍：真实项目会用 nn.Module 把它们注册成可遍历的参数列表（parameters()），那是 pb07 的内容。现在用元组，好处是你能一眼看到「这个网络就这四个东西」，代价是每次要解包一次 w1, b1, w2, b2 = params。

陷阱把参数元组当成不可变对象就不会出错

元组本身不可变，但里面的张量可变。中心差分那段会临时改参数值算两次 loss，如果不包在 torch.no_grad() 里，PyTorch 会报 a leaf Variable that requires grad is being used in an in-place operation。你会怎么误判？以为是元组不该被修改。真相是它是对的：叶节点不允许被原地改动，因为那会让已建好的计算图指向一个被改过的值。修法是把扰动整段放进 no_grad()，让这些修改不进图；算完再恢复原值。pb06 里优化器更新参数走的也是同一条规则。

3.2.1 为什么先用元组，而不是直接上 nn.Module

看到 params 这个四元组，熟悉 PyTorch 的人可能会问：为什么不写成 class TinyNet(nn.Module)，让框架自己注册参数？答案是教学顺序。本单元的目标是让你看清「13 个参数究竟是什么、反向到底落在谁身上」；一个四元组把这件事摊在桌面上，每个张量的形状、dtype、是否需要梯度都写在 make_params 里，一眼可查。

换成 nn.Module 之后，参数会被收进一个有序字典，parameters() 返回一个生成器；你不再是「看见」参数，而是「遍历」参数。这对大模型是必需的——一个 Transformer 有几百个张量，手写元组根本不现实——但它同时把 13 这个数字藏进了类的定义里。所以本书的顺序是先用元组把机制讲透，到 pb07 再引入模块类，那时你会清楚框架替你收走的到底是什么。

代价也要说清：元组不提供 parameters()，所以优化器暂时用不上；本单元没有训练，只需要手工读 .grad，这个缺口不妨碍教学。下一单元要训练时，我们会继续用一个轻量的参数列表，等到 pb07 才换成正式的模块接口。

工程惯例四个张量的顺序是契约

forward 里第一行就解包 w1, b1, w2, b2 = params，main.py 里又用 params[3].grad 取 b2 的梯度。这个顺序一旦改了而别处没跟着改，程序不会报错——四个张量的形状有重叠（长度三的 b1 和 w2 尤其像），解包错了照样能算出前向，只是结果毫无意义。工程上更稳的做法是给参数起名字、用字典存放，但那样要多写几行。本例选择元组，是用「顺序固定」换「代码短」，并在正文里把顺序反复写清楚。你要是自己改这个例子，务必同时改三处：make_params 的返回、forward 的解包、main.py 的下标。

3.3 前向：四行代码对应四个中间量

C 版本里 hidden() 算 z 和 h，net_forward() 算 s 和 y。PyTorch 版本把它们压进一个函数：

逐行对一下形状和含义：

  • z = x @ w1 + b1：x 是长度 2，w1 是 2×3，乘出来长度 3，再加长度 3 的 b1——三个隐元的加权和；
  • h = torch.tanh(z)：还是长度 3，把任意实数压到 (-1,1)，引入非线性；
  • s = h @ w2 + b2：长度 3 乘长度 3 得到标量，再加标量 b2——输出层的净输入；
  • torch.sigmoid(s)：把标量压到 (0,1)，得到预测 y。

损失写成 0.5*(y-target)²，和 dlmath 完全一样。前面那个 0.5 不是为了好看，而是让导数刚好消掉平方带来的因子 2：dL/dy = y-t。C 版本的手推从这里开始，PyTorch 则从记账本里直接读出同一条边。

工程惯例为什么保留手写 loss 而不直接调框架封装

框架当然提供现成的 MSELoss，写 torch.nn.functional.mse_loss(y, target) 更短。但本例刻意手写 0.5*(y-target)²，是为了让「loss 是前向后第一个被反向的量」这件事肉眼可见——你写的每一行运算都在图里，sum、*、**2 无一例外。换成封装好的损失函数，第一次读代码的人得跳进库里才能确认它到底算的是不是同一个东西。等你对这条链路熟了，再换封装不迟。代价是这几行代码以后每个例子都要重写一遍，但教学阶段「看得见」比「写得短」重要。

3.3.1 两个激活函数的链式因子各管什么

这个网络用了两种激活函数，它们各贡献一个最容易算错的局部导数。

隐层的 tanh 导数是 1-h²。它的形状很讨喜：输出 h 已经在 (-1,1) 里，所以 h² 在 [0,1)，导数落在 (0,1]，最大是 h=0 时的 1。当隐元饱和到接近 ±1 时导数趋近零，上游传来的误差被压扁，这个隐元就「学不动」了。本例的初值温和，三个 h 大约是 -0.51、-0.56、0.44，都不在饱和区，所以梯度健康。

输出层的 sigmoid 导数是 y(1-y)。同样地，y 在 (0,1)，导数最大是 y=0.5 时的 0.25，两端都趋近零。本例 y≈0.58，因子约 0.244，接近最大值，梯度传得回来。换一个目标让 s 很大，y 逼到 0.999，因子只剩千分之一，学习就慢下来了——这就是梯度消失在最简网络里的样子。

陷阱把激活函数的导数当成常数

有人看到 tanh 的导数是 1-h²，就随手写成 1-h；或者把 sigmoid 的 y(1-y) 记成 y。这类错误在手写版本里会直接让梯度表对不上，但在 autograd 版本里不会发生——框架从算子注册表里读出精确公式。这是否意味着你可以完全不懂这些因子？不是。当 loss 不下降、需要判断是不是饱和导致时，你还是得知道每个激活函数的导数长什么样。框架替你算，不替你诊断。

工程惯例为什么输出层选 sigmoid 而不是 tanh

因为任务被定义成「预测一个 0 到 1 之间的数」，目标 0.8 就在这个区间。sigmoid 把整个实数轴压进这个区间，输出天然可解释成概率或比例。隐层用 tanh 则是因为它以零为中心，均值接近零的激活更利于下一层学习——如果隐层也用 sigmoid，输出全为正，下一层的权重更新方向会高度相关，收敛变慢。这不是硬性规定，而是经验惯例：二分类输出常用 sigmoid，隐层常用 tanh 或 ReLU。代价是要记住两套导数公式。

3.4 同一组初值：把 C 的 LCG 复刻到 Python

要让两边的数字可比，必须让 13 个权重完全相同。C 版本用的是一个 32 位 LCG：

三个地方必须和 C 一模一样，错一个数字就全盘对不上。

第一，乘法常数 1664525 与加法常数 1013904223，以及每次都要 & 0xFFFFFFFF 模拟 32 位无符号回绕。Python 的整数是任意精度，不显式截断的话几步之后就会长成一个巨大的数，和 C 的 uint32_t 分道扬镳。

第二，取随机数的办法是 (state >> 8) / 16777216.0。右移八位等于砍掉低八位，留下 24 位，除以 2²⁴ 得到 [0,1) 区间的数；再乘 2 减 1 变成 (-1,1) 的权重。这里 >> 的位数和除法的分母是一对，改一个就得改另一个。

第三，也是最容易错的：调用顺序。C 版本先按 i 外层、j 内层填满六个 w1，然后循环三次、每轮依次取一个 b1[j] 和一个 w2[j]，最后取 b2。如果图省事把三个 b1 连续取完再取三个 w2，前面六个值不变，后面六个值就全错位了。本单元初写时就在这一处踩过坑：前向打出 y=0.797078，和 C 的 0.580931 差了一大截；逐值打印权重才发现 b1 和 w2 的取值交错被写成了分段。

实验记录对照两边的前向数字

C 版本真跑（种子 12345、输入 (0.5,-0.3)、目标 0.8）给出 y=0.580931、loss=0.023996。本节 Python 版本真跑给出完全相同的两个数，误差在打印的六位小数里为零。这不是巧合，而是上面三个细节都对上了的结果。想亲手验证，可以在 net.py 里把 c_lcg_weights 的返回值逐个打印，再去对照 C 版本 net_init 后的结构体——13 个数应当逐位相同。

陷阱用 torch.manual_seed 代替复刻 LCG 会怎样

有人会说：既然固定了 torch.manual_seed(12345)，直接用 torch.randn 初始化不也一样可复现吗？可复现是对了，可比性却没了。PyTorch 的随机数生成器是 Mersenne Twister 的一套实现，和 C 里那个 LCG 毫无关系；同种子给出的是另一组 13 个数，于是 y 变成另一个值，你没法判断差多少是「初始化不同」、差多少是「反向写错」。本例仍然调用 torch.manual_seed(12345)——那是纪律，保证未来加入的任何随机环节可复现——但 13 个权重由 LCG 显式给出，专门服务于逐位对照。

3.4.1 为什么不用 rand()：可复现的第一课

C 分册从一开始就拒绝 rand()，理由写得很直白：它的序列由 C 运行库决定，换个机器、换种编译器就可能不同。同一份源码在作者机器上跑出 y=0.580931，在读者机器上可能变成 0.61，而两边都「没错」——这种实验是没有价值的。LCG 只有五行代码，乘一个常数加一个常数再截断，任何语言都能逐位复刻。

Python 的 random 模块比 C 的 rand() 好一些，它用 Mersenne Twister，同种子跨机器通常一致；NumPy 与 PyTorch 也各有自己的生成器。问题在于三者互不相通：random.seed(12345)、np.random.seed(12345)、torch.manual_seed(12345) 各自初始化三条独立的随机流。pb03 立下的纪律就是「三种种子一起固定」，因为一个程序可能同时从三处取随机数，漏掉任何一处都会让结果漂移。

本例更进一步：干脆不靠任何库的随机源生成权重，而是把 C 的 LCG 逐行搬过来。这样连「PyTorch 版本升级后随机算法变了」这种风险都绕开了。代价是这段代码看起来和深度学习毫无关系——它的存在意义不是「怎么初始化权重」，而是「怎样让两个实现真的可比」。pb06 会回到常规做法：三种种子一起固定，让 DataLoader 的打乱顺序也可复现。

实验记录亲手验证跨实现的一致性

在 Python 里把 c_lcg_weights(12345) 的 13 个数打出来，再在 C 分册的 net_init 后面插一段 printf，把结构体的 13 个字段按同样顺序打出来。两边逐位对照，应该全部相同。若有任何一个不同，先查 >>8 与除数的配对，再查 b1/w2 的交错顺序——这两处占了此类错误的大多数。做完把 C 的调试代码删掉，不要污染参考实现。

3.5 loss.backward() 替你做了什么

把 13 个叶节点、四步前向、一个 loss 接好之后，只需要一句 loss.backward()。它做的事可以拆成三步：

  1. 从 loss 这个标量出发，找到它的 grad_fn；
  2. 沿 grad_fn 指向的运算一步步倒走，每条边乘上该运算的局部导数；
  3. 把最终落到每个叶节点的值累加进它的 .grad。

dlmath 分册里那一页手推，核心就是这四个偏导式子：∂L/∂y = y-t、∂L/∂s = (y-t)·y(1-y)、∂L/∂w2ⱼ = (∂L/∂s)·hⱼ、∂L/∂hⱼ = (∂L/∂s)·w2ⱼ，再乘 1-hⱼ² 分给 w1 和 b1。它们现在全部由框架从记账本里读出来，你一行都不用写。

第 2 帧里那条 loss -> s 的边乘的正是 y(1-y)——dlmath 分册反复强调「最容易漏的因子」。框架不会漏，因为它把 torch.sigmoid 的局部导数写在了算子里。但框架也不会替你检查 loss 是不是算对：如果你把 0.5*(y-t)² 写成 (y-t)²，backward() 照样精确地把梯度放大两倍，它忠实地给「错误的函数」求导。这就是下一节必须对拍的理由。

工程惯例一行代码省下的是什么

省下的不只是打字量。手推版本里，改一个激活函数就要重推所有下游导数，漏一项肉眼几乎看不出来；autograd 版本里，你把 torch.tanh 换成 torch.relu，反向自动跟着变。代价是可读性的转移：以前推导过程写在纸上、能逐行审；现在它藏在 grad_fn 链里，你只能靠对拍间接验证。本例保留中心差分那条独立路径，正是为了把这失去的一层补回来。

3.5.1 梯度会累加：为什么训练前必须清零

backward() 把算出的梯度加进 .grad，而不是覆盖它。本例只调了一次，看不出这个性质；但下一单元的训练循环会反复调用 backward()，如果不在每步之前清零，第二次的 .grad 就是两步梯度之和，更新步长翻倍，模型很快发散。

为什么要设计成累加？因为一个 batch 的损失常常由多个项组成，你可能想分别算它们的梯度再合并。比如主损失加正则项：先 loss_main.backward()，再 loss_reg.backward()，两者的梯度自然叠加进同一组参数。如果设计成覆盖，你就得自己把两项加进一个 loss 再一次反向——大多数时候这没问题，但有些场景（比如梯度来自不同计算分支、无法合成一个标量）就做不到了。

代价是每一轮训练都得记得清零。框架把它做成了显式操作 optimizer.zero_grad()，而不是悄悄替你做——因为「何时清零」本来就是实验设计的一部分，不该由库猜。pb06 会把这一步放进训练循环的四步里，并用固定种子的轨迹证明「忘了清零」和「清零了」给出两条不同的 loss 曲线。这个设计初看别扭，用久了你会发现它把一件容易出错的事摆到了明面上，反而比隐式清零更让人放心。

陷阱以为 backward 之前 .grad 是零

它在第一次反向之前是 None，不是零张量。如果你写 p.grad += something 就会在第一步崩掉。要判断有没有梯度，用 p.grad is not None；要清零，用 p.grad.zero_() 或更常见的 optimizer.zero_grad()。这个细节在 C 版本里不存在——那里梯度是一个每次都重新填满的数组，天然覆盖。从手写切到框架时，这种「语义沉默的差异」比语法错误更值得警惕。

3.6 对拍：中心差分再验一遍

机器算的梯度对不对，要靠一条不依赖链式法则的路来验。中心差分把第 i 个参数加减小量 ε=1e-5，看 loss 怎么变：斜率 (L₊-L₋)/(2ε) 就是偏导的近似。

这里有两个细节值得停一下。

第一，grads 用 torch.zeros_like(p, requires_grad=False) 创建。若省掉 requires_grad=False，新张量会继承 p 的记账标记，往里写数值时又要触发「叶节点不能原地改」的报错。第二，扰动必须在 torch.no_grad() 里做。这段函数一共要跑 26 次前向（13 个参数 × 加/减两次），每一次都建图的话既慢又危险——那些图指向的是被扰动过的参数，算完就失效了。关掉记账之后，每次前向只是纯数值计算，干净利落。

第 3 帧的 residual 是把 13 组偏差取最大绝对值得来的。它只有 1.485e-12，比中心差分本身的截断误差量级 ε²=1e-10 还小——说明 autograd 给出的确实是这条损失函数的正确导数，而不是一个碰巧接近的数。

陷阱只看 residual 小就宣布正确

这里有个隐含前提：中心差分的 ε 选得合适。ε 太大会引入二阶截断误差，太小则被浮点舍入淹没——双精度下 1e-5 是个稳妥的选择。更要紧的是，两条路径共用同一个 loss_value 函数；如果这个函数本身写错了（比如把平方写成绝对值），解析梯度和数值梯度会一起错，residual 照样接近零。所以 residual 只证明「框架求导和数值求导一致」，不证明「你的 loss 是你要的 loss」。后者要靠 y 与 loss 那两个黄金值来守。

3.7.1 读梯度表：符号、量级与它们的含义

虽然本例只打印了 b2 一个梯度，但 analytic 列表里装着全部 13 个。读梯度表时有三件事值得看。

第一是符号。grad_b2=-0.053332 为负，意思是「把 b2 增大一点，loss 会下降」。参数更新写成 b2 ← b2 - lr·grad_b2，负号乘负梯度得到正向位移——所以训练时 b2 会往增大方向走。dlmath 分册的梯度表里，13 行有正有负，正是这些符号合在一起决定了每一步往哪走。

第二是量级。grad_b2 大约 0.05，而隐层权重的梯度往往在 0.001 量级——因为上游误差连乘了 y(1-y) 和 1-h² 两个小于 1 的因子，越往前面传越小。这不是 bug，而是链式法则的必然结果；它也解释了为什么深层网络里靠近输入的层学得慢。

第三是零值。如果某个参数梯度恰好为零，可能是它真的不重要，也可能是它落进了饱和区或者根本没被用上。单看一次前向区分不了，要看训练轨迹：如果它的值一直不变而其他参数在动，八成是断链了。

工程惯例为什么把残差也做成黄金值

gradcheck_residual=1.485e-12 看起来小到没意义，为什么还要写进清单？因为它是「对拍这件事真的跑了」的证据。如果有人把 numerical_grad 改成直接返回 analytic，residual 会变成零——那反而更可疑，但清单只按 atol=1e-6 比较，0 和 1.485e-12 都通过。所以这条黄金值的真实作用不是判精度，而是让 stdout 里必须有这么一行、且数值落在合理量级；真正防「假对拍」的是代码审阅（两条路径确实不同）。把这一点写清楚，比假装一个数值能证明所有事更诚实。

3.8 双精度为什么是必需的

这一节有一行容易被跳过：torch.set_default_dtype(torch.float64)。PyTorch 的默认精度是单精度 float32，有效数字约 7 位十进制。本例的黄金值要求 6 位小数对上，看起来 7 位够用——其实不够。

原因在于对拍。中心差分要算 (L₊-L₋)/(2ε)，其中 L₊ 和 L₋ 都是接近 0.024 的数，相减之后只剩约 1e-6 量级。单精度下这两个数的末几位已经被舍入，相减会把有效位吃掉大半，算出来的数值梯度可能只准到 3～4 位。这时 gradcheck_residual 会从 1e-12 涨到 1e-4 甚至更大，对拍就失去了意义。双精度有约 16 位有效数字，做这种「大数相减」才有余量。

C 分册从头到尾用的都是 double，所以复刻时必须显式把默认精度设成 float64，不能指望框架替你选。这也解释了为什么 make_params 里每一行 torch.tensor(...) 都写了 dtype=torch.float64——默认精度是全局设置，显式写类型则是局部保险，两边都做才不会在某次重构里悄悄退化成单精度。

陷阱只改默认精度却忘了输入和目标

set_default_dtype 只影响之后不带 dtype 参数的张量构造。本例里 x、target 和四个参数都显式写了 dtype=torch.float64，所以即使删掉那行设置，结果仍然正确——那这行是不是多余的？不是。它是一道保护：以后有人加一个中间张量忘了写 dtype，默认精度就会是 float64 而不是悄悄退回 float32。这是一种防御性写法，代价是多一行代码，换来的是「加代码不容易破坏精度契约」。反过来，如果只写默认精度却在某处显式指定了 float32，那一处就会成为链条里最弱的一环。

3.9 从 13 行手推到一行 backward：成本搬去了哪里

把两种实现并排看，代码量的变化很直观：C 版本需要一个 net_backprop 函数逐行写四个偏导式子，加上一个 net_numerical_grad 做对拍；PyTorch 版本反向只有 loss.backward() 五个字符，对拍代码反而更长（因为要在 Python 里做原地扰动）。

省下的成本没有消失，而是换了位置。第一，它变成了框架内部的算子注册表：每个 torch 运算都得提供自己的局部导数，这份工作由库的维护者一次做完，所有用户共享。第二，它变成了运行时的图构建开销：每次前向都要分配节点、记录运算，小程序里可以忽略，大模型里就需要专门优化。第三，它变成了你的验证责任：以前推导写在纸上可以逐行审，现在必须自己搭一条独立路径来验。本例的中心差分就是这条路径。

工程惯例什么时候值得保留手写梯度

不是所有场景都该无脑上 autograd。如果你只要求一个闭式梯度、且调用次数极多（比如某些采样算法的内层循环里要算上百万次梯度和），手写公式可能比建图快一个数量级。另一个场景是自定义运算：你写了一个框架没有的算子，就得自己提供反向规则，否则它在计算图里是一堵墙。本书的目标是教你用框架做实验，所以默认选 autograd；但你要知道这个选择是有代价的，不是「免费升级」。

3.9.1 从 13 个参数到十亿个，什么变了

这个 2→3→1 的网络小得可以手算，但结构上和真正的大模型没有区别。Transformer 的一层注意力里有四个矩阵 Wq、Wk、Wv、Wo，本质都是「把一组向量线性映射到另一组向量」，和这里的 w1、w2 是同一件事，只是维度从 2→3 变成几千→几千。

放大的过程中，三条纪律一条不变。第一，前向要对：本例靠 y 与 loss 的黄金值守住，大模型靠端到端的小样本回归测试守住。第二，梯度要对：本例靠中心差分对拍守住，大模型靠框架的梯度检查工具在随机小批量上抽样验证。第三，实验要可复现：本例靠固定 LCG 种子守住，大模型靠固定全部随机源、记录依赖版本守住。变的只是规模与工具，不是方法论。

真正变化的是三件事。矩阵乘法从 Python 循环换成高度优化的底层核，因为朴素实现的复杂度不够用；初始化不再是简单均匀分布，而是 Xavier 或 He 这类按维度缩放的分布，保证前向方差不爆炸也不消失；训练要在海量数据上做小批量平均，还要记录动量、二阶矩等状态。这些正是后面三章的内容。

工程惯例为什么先练小网络再谈大模型

因为小网络的每个数字都能用另一种方法独立算出来。你能手推 grad_b2，能用中心差分验证它，能看着 LCG 权重解释 y 为什么是这个值。这种「三条独立证据互相印证」的体验，在几十亿参数的网络里根本无法获得——你只能看损失曲线和少量抽样。先在能完全掌控的小系统上把证据链建立起来，等系统大到看不清时，你至少知道该信什么、该怀疑什么。代价是这一段看起来「不实用」：没有一个真实任务需要 2→3→1 的网络。但教学的目的是建立判断力，不是交付产品。

3.10 图元怎么读，以及这一节的新增

这一节四张图的分工：memory 看 13 个参数在两边的布局，重点是 b2 必须是零维张量；tree 标出新增的三个文件；第一张 graph 画前向与反向共用一条链路，重点看 loss -> s 那条边乘的正是 y(1-y)；calltree 画两条独立路径如何在 residual 处汇合。

读图时记住每帧自包含：第 2 帧里仍然成立的节点要重写一遍，渲染器不会替你从上一帧带过来。节点文字不超过十八个字，箭头两边留空格——loss -> s 是边，loss->s 只是文字。这些约束让同一份围栏在屏幕步进器与打印 PDF 里长得一样。

四张图连起来读还有一条主线。memory 回答「参数长什么样」，tree 回答「代码放在哪」，graph 回答「信号怎么流」，calltree 回答「两条梯度路径怎么汇合」。这四个问题分别对应工程的四个层次：数据、文件、算法、验证。任何一次实验出问题，你都可以按这个顺序逐个排除——先确认参数形状对，再确认代码接线对，再确认前向流程对，最后确认对拍真的独立。

工程惯例把 13 这个数字当作第一道自检

读任何一个两层网络的源码，第一件事应该是数参数。本例是 2×3 + 3 + 3 + 1 = 13，程序也打印了 params=13。如果哪天你把隐层宽度从 3 改成 4 却忘了改别处，这个数字会变成 2×4 + 4 + 4 + 1 = 17，清单里的黄金值 params=13 立刻报不匹配。一个看起来很笨的计数，实际是结构变更的哨兵。换成更大的网络也一样：参数量是最便宜的一致性检查，比跑一遍完整前向还便宜。

回到 3.1 的第 2 帧：多了 net.py（结构、LCG、前向）、main.py（反向、对拍、打印）、pb05-twolayer.json（黄金值）。下一单元把这套机制接上训练循环：加上数据集、小批量、优化器与固定种子，打印 12 行 loss 轨迹。反向那一行还是 loss.backward()，但外面会多一圈 zero_grad() 和 step()——那一步忘了清零会怎样，正是 pb06 的核心陷阱。

小结这一节的要点
  • 13 个参数 = 6 个 w1 + 3 个 b1 + 3 个 w2 + 1 个 b2，四个叶节点张量，b2 必须是零维张量而非 Python 浮点数；
  • 前向四行对应 C 的 z → h → s → y；0.5*(y-t)² 让 dL/dy = y-t；
  • loss.backward() 沿图倒走并累加梯度到 .grad，但不会替你检查 loss 函数本身是否写对；
  • 复刻 C 的 LCG 时，常数、右移位数、以及 b1/w2 交错的调用顺序都必须一致；
  • 双精度下 y=0.580931、loss=0.023996、grad_b2=-0.053332 与 C 试点逐位相同，对拍残差 1.485e-12；
  • 「前向正确、求导正确、实验可复现」三条纪律在换框架之后一条都没变。
