1.1 先看工程长什么样

这个分册不再从零写数值库，而是把前几册手写的那些实验翻译成框架写法。第一步仍然是看清工程：每个例子都有自己的入口、本地模块和清单，三者缺一不可。入口负责把要展示的数打到屏幕上，模块负责提供可复用的函数，清单负责让流水线真跑一遍并把 stdout 对账。

第 2 帧里新增的是两个 .py 文件：src/main.py 是入口，src/demo.py 是本地模块。第 3 帧再新增 pb01-basics.json，闸门才知道该跑哪个脚本、该去正文的哪个 output 块里对账。注意清单里 sources 的顺序：第一个必须是入口，其余是被 import 的模块；流水线会先对这两个文件做 py_compile 语法检查，再真正执行第一个文件。

你可能会问：两个文件直接放在一个目录里不好吗，为什么非要 src/？这是工程惯例，不是语言规定。把入口和模块收进 src/ 之后，命令仍然是干净的一条 python src/main.py；由于入口脚本所在目录会自动进入 sys.path[0]，同一目录下的 demo.py 就能被直接找到，不需要额外设置路径。代价是你得记住「相对谁解析」这件事——从别的目录运行时要写全路径，或者先把工作目录切到例子目录。

1.2 一行代码背后：解释执行到底多了哪几步

先说结论：C 程序在运行之前已经被翻译成了机器指令，而 Python 程序每次运行都要先把自己翻译成一种中间形式再执行。这不是「Python 慢一点」这么轻描淡写，而是两套完全不同的执行路径。

大白话用大白话先说清这件事

你把同一句计算写在一张纸上。C 的做法是：先把整张纸交给一位翻译官，翻译官逐字读完、查好每个词的意思、把整张纸变成一份机器能直接照做的清单，然后机器拿着清单飞快地干活。Python 的做法是：每次运行时，先有人把这张纸匆匆扫一遍变成短一点的备忘条，然后另一个人拿着备忘条一条一条照做。第二个人每做一条都要再判断一次「这条是什么意思、要用哪个函数」。备忘条比原纸短，但「边看边做」这一步省不掉。严格说，Python 也做编译，只是编译的目标是字节码而不是机器码，而且这份字节码默认不落到你手里。

第 2 帧是 Python 这一侧：源码先被切成 token、建成语法树，再变成字节码，最后由虚拟机逐条取指执行。第 3 帧是 C 这一侧：类型检查、地址计算这些事在编译期就做完了，运行期基本只剩搬数据和算术。把两帧并排看，你就明白为什么同样是一行 printf 或 print，在 C 里是一次函数调用，在 Python 里却要穿过好几层间接。

这里的「虚拟机」不是另一台机器，而是解释器里的一段程序，它模拟出一台执行字节码的机器。字节码也不是给真实 CPU 的指令，而是给这段模拟程序的指令。这一层抽象换来了好处：同一份字节码可以跑在不同平台上，运行时也能改变量的类型、动态的添加属性。代价就是每一次算术都要多做一次分派——先判断对象是什么类型，再决定调用哪段实现。

1.3 动态类型：变量是便签，不是盒子

C 里写 int x = 3;，意思是在栈上划出四字节，把整数 3 的二进制填进去。这里 x 和那四字节是绑死的：盒子多大、里面能放什么，编译期就定了。Python 里写 a = 3，发生的是另一件事：先在堆上造出一个整数对象，再把名字 a 贴到这个对象上。名字不带类型，类型属于对象。

第 2 帧里 getsizeof 报的 28 字节不是「整数 3 占多少空间」的普遍真理，而是本机 CPython 的一个实测读数：对象头、引用计数、类型指针这些固定开销加上一个机器字的数据，凑成了这个数。换一种实现、换一个大整数，读数会变。程序里 int_bytes=28 与 big_bytes=36 两行把这个差异摆在屏幕上：后者是 2**64，超过一个机器字，需要多存一位数据。

这个模型解释了很多初看奇怪的现象。写 a = 3; b = a，在 C 里是把四字节复制到另一个盒子，在 Python 里是把同一张便签贴到同一个对象上——a 和 b 指向的是同一个东西。写一个可变对象（比如列表）时这个差别会咬人：b.append(4) 会同时改变 a 看到的内容，因为两者从头到尾只有一份列表。想真正复制一份，得显式调用 copy() 或切片，这不是「多余的一步」，而是你明确要求另造一个对象。

陷阱把可变对象当值传递，会被坑在哪

你会看到：函数里对参数列表 items.append(x)，函数外面那个列表也跟着多了 x。你的第一反应往往是「参数不是按值传的吗，怎么被调用方改了」；再一想又觉得「Python 是引用传递吧」，于是把所有东西都当成引用去解释。真相是：传进去的是那份引用的副本，函数内外两张便签指向同一个对象；改便签本身（重新赋值）互不影响，改便签指向的对象则双方都看得见。判断的办法只有一条：看操作发生在「便签」上还是「对象」上。

对象模型还带来一个实际后果：对象有生命周期。当最后一个便签被撕掉，对象就没人引用了，CPython 会用引用计数当场回收它。这意味着你可以随手创建临时对象而不必手写 free，但也意味着「看起来还活着」的对象可能随时消失——只要你没把它绑到任何名字上。后面用 NumPy 数组做切片时，这个「谁还引用着谁」的问题会以视图与拷贝的形式再次出现。

1.4 整数与浮点：两套完全不同的语义

现在看这一节最有意思的两个数。第一个是 int_max：程序里写的是 2 ** 64，打印出来是 18446744073709551616。如果你带着 C 的习惯，会以为它该回绕成 0——毕竟 64 位无符号整数装不下更大的数。Python 的 int 不是定宽的，它按需扩展，理论上只受内存限制。所以这里没有溢出，也没有回绕，就是一个精确的大整数。

第二个是 float_sum。程序把 0.1 和 0.2 累加，按六位小数打印是 0.300000；但旁边那行 float_raw:0.30000000000000004 把真面目露出来了。原因不在 Python，而在 IEEE 754 双精度：0.1 和 0.2 都不能被二进制浮点精确表示，它们各自被舍入成最接近的可表示数，相加之后再舍入一次，结果就比十进制的 0.3 多了一点点。这一点点误差在金额计算里会出事，在训练损失里通常被容差吸收。

陷阱拿 == 直接比浮点求和，会被坑在哪

你会看到：0.1 + 0.2 == 0.3 打印 False，而你刚刚手算明明等于 0.3。你可能会怀疑 Python 的加法实现有 bug，或者怀疑自己敲错了数字。真相是：等式两边根本不是同一个二进制数，0.3 这个字面量本身也被舍入过，两个舍入结果不同。正确做法是用容差比较，例如判断绝对值差是否小于一个很小的值——这正是闸门对账时 atol 的作用。注意也不要拿 abs(diff) < 0 这种写法，它永远为假。

这两套语义在深度学习里都有用武之地。任意精度整数让你写循环计数、索引、哈希时不必担心回绕；双精度浮点则是科学计算的主力，它的舍入误差可分析、可控制。真正要小心的是混用：把大整数转成浮点会丢精度，把浮点转成整数会截断而不是四舍五入。NumPy 的 dtype 会把这件事显式化——这是下一单元的主题。

还有一点值得单独说：type() 和 isinstance() 回答的是不同问题。前者问「这个对象的确切类型是什么」，后者问「它是不是某个类型或子类的实例」。在 Python 里，bool 是 int 的子类，所以 isinstance(True, int) 为真，但 type(True) is int 为假。写数值代码时这类细节偶尔会露出来，比如某个布尔值被当成 1 参与算术。读别人的代码时看到这种写法，别急着改，先确认作者是不是有意利用了这个关系。

1.5 缩进与作用域：花括号去哪了

C 用花括号划 block，Python 用缩进。这不是排版偏好，而是语法本身：缩进决定一条语句属于哪个 block，从而决定变量在哪一层可见。demo.py 里的 scoped_count 把这件事演示得很清楚。

第 2 帧里 total 属于 scoped_count 这一层；第 3 帧里 tick 想改它，就必须写 nonlocal total。如果不写，Python 会把 total += 1 里的 total 当成 tick 自己的局部变量，然后报「赋值前引用」。这是初学者几乎必踩的一次坑：读变量时可以向外层找，写变量时默认就在当前层新建。

_ 这个名字也有讲究。它仍然是一个合法变量，只是约定俗成表示「这个值我不用」。在 for _ in range(n) 里，循环变量确实没有被使用，用 _ 是给读者一个信号。别把它当成「丢弃」关键字——它照样绑定最后一个值，只是没人会去读。理解这一点，你就不会奇怪为什么后面写 for _ in values: 时缩进仍然算数。

缩进还有一个实践后果：复制粘贴代码时如果混进了不同宽度的空白，语法检查会在你完全没料到的地方报错。本书一律用四个空格，不用 Tab；ws=visible 这类工具能把空白显示出来，遇到诡异的缩进错误时值得打开看一眼。混用 Tab 与空格在 Python 里是真正的语法错误，不是风格问题。

1.7 慢在哪里：把「解释器开销」落到具体数字

很多人学 Python 的第一印象是「慢」。慢是真的，但笼统地说「慢」没有任何用处，我们要指出慢在哪一层。程序里的 loop_work 做了五十万次极简循环：每次只取一个整数的最低两位并累加。打印出来 loop_ops=500000、loop_odd=250000，前者是循环次数，后者是奇数个数。这两个数是固定的，因此可以作为黄金值对账。

为什么不打印毫秒？因为墙钟时间受机器负载、缓存、调度影响，同一份代码两次运行可能差出百分之几十。用 atol=1e-2 去对账几十毫秒的运行时间，等于什么都没对账；把噪声写进正文还违背了「数字必须可复现」的纪律。这里改用固定计数做证据：它精确、可复现，又足以说明「解释器要为每次循环做一次字节码分派」这个事实。

真实的耗时差异可以从结构上推出来。C 的 for (int i = 0; i < n; ++i) 编译后通常是几条机器指令加一个跳转，整数就放在寄存器里；Python 的 for i in range(n) 每次迭代都要取出下一个对象、判断类型、执行 & 对应的方法、再把结果加到一个新对象上。对象创建与分派是主要开销，算术本身反而是小头。所以优化 Python 数值代码的第一原则不是「少写几层循环」，而是「把循环搬到用 C 或 Fortran 写好的库里去」——这正是 NumPy 存在的理由。

工程惯例工程惯例：为什么先固定计数再谈计时

先把工作量固定成可复现的整数，再在需要性能结论时另做多次测量取中位数，这是数值实验的通行做法，不是语言规定。代价是你得维护两套数字：一套进闸门当黄金值，一套留在实验记录里当性能参考。好处是闸门永远稳定，不会因为某次机器繁忙就误报失败。本分册后续所有单元都遵循这条：耗时类指标一律不进 expect.numbers。

1.8 为什么科学计算仍然选 Python

既然纯 Python 循环这么慢，为什么深度学习领域几乎人手一份 Python？答案不在解释器，而在它背后。NumPy、PyTorch 这类库把真正的大循环写成了编译好的 C、C++ 或 Fortran，Python 这一层只负责描述「做什么」：分配多大的数组、对哪两维做乘法、梯度要不要保留。描述一次，底层跑几亿次。

这套分工的关键在于数据布局。当数据以连续的同类型数组存在时，底层代码可以用指针线性扫描，缓存命中率高，还能调用针对 CPU 指令集优化过的 BLAS。Python 的列表做不到这一点：列表里每个元素都是一个独立对象，类型可以不同，内存也不连续。所以从列表切到数组，不只是「换了个写法」，而是把数据从「一堆对象」变成「一块可以按字节算的内存」。

下一单元会把这件事讲透：数组的 shape、dtype、strides 三个属性分别回答「几维每维多长」「每格是什么类型」「跨一格要走多少字节」。理解了这三个词，你就知道为什么 A @ B 比双层循环快，也知道视图和拷贝的区别从哪来。今天这一节的 int_bytes 与 big_bytes 是铺垫：先看到对象有开销，才容易接受「把数据打包成连续数组」是个重要优化。

1.9 三个常见坑，逐个拆开

第一个坑是把 is 当成 ==。is 比较的是两个名字是不是指向同一个对象，== 比较的是内容是否相等。小的整数在 CPython 里会被缓存，所以 a is b 在小数值上常常为真；大整数不会，于是同一段判断换个数字结果就变。判断数值相等一律用 ==，判断是不是 None 才用 is。

第二个坑是可变对象作为默认参数。写 def f(items=[]): 时，那个空列表在函数定义时就造好了，所有调用共享同一个对象；第一次调用往里加东西，第二次调用就带着旧东西进来。正确写法是默认 None，进函数再造新列表。这个坑之所以隐蔽，是因为它只在多次调用之间才显形，单次测试永远看不出来。

第三个坑是以为异常会自己消失。除零、索引越界、类型不匹配都会抛异常；如果不捕获，程序就带着栈回溯结束，退出码非零，闸门会报 exit_mismatch。本书的例子刻意不捕获异常——让错误当场暴露比悄悄兜住更有利于建立证据纪律。真正要处理异常时，捕获的范围越窄越好，别用一个巨大的 except 把八种错误全吞掉。

陷阱把 print 当成调试终点，会被坑在哪

你会看到：屏幕上打出了 loop_odd=250000，于是认定循环没问题。你的第一反应是「数值对上了，收工」。真相是：打印出来的数只是你让程序打印的数，它可能对，也可能因为索引写错而碰巧对。闸门的价值在于它拿同一份 stdout 与清单黄金值对账，并且用固定种子排除偶然。想真正建立信心，得再问一句「这个数能不能手算核对」——下一节就带你把四个数逐个手算一遍。

1.11 手算核对：四个数不用程序也能验

先看 int_max。2 ** 64 就是 2 自乘 64 次，十进制写开是 18446744073709551616。你可以在纸上用 2**10=1024 做分段：2**60 = (2**10)**6 = 1024**6 = 1152921504606846976，再乘 16 得到上数。过程繁琐但没有任何跳步，所以它是一个合格的黄金值。

再看 loop_odd。range(500000) 产生从 0 到 499999 的整数，其中奇数正好一半，也就是 250000。loop_ops 就是循环次数 500000，两者相加是 500000 的一半与全体，比例刚好一半。float_sum 的手算稍微绕一点：把 0.1 与 0.2 的二进制展开写到足够多位，相加后再舍入，得到比 0.3 略大的那个数；用六位小数打印则两者都显示 0.300000。

int_bytes 与 big_bytes 不能纯手算，它们是 CPython 的实现细节，只能实测。但它们的差有道理：小整数用一个机器字存数据，2**64 需要两个，于是对象多出 8 字节。这个 8 与 28、36 的差正好吻合，说明我们对对象布局的理解没有跑偏。能解释实测数字的差异，比背住数字本身更有价值。

实验记录把黄金值改错一次，看闸门怎么报

建议做一次受控破坏：把清单里 float_sum 的 value 从 0.3 改成 0.5，然后跑 node build/run.js --unit pb01-basics。你会看到 numeric_value_mismatch，日志里同时写出真实 stdout 的值和清单黄金值。再把正文 output 块里 loop_odd=250000 改成别的值，重跑同一条命令，会看到正文与实际对不上。做完记得改回来。这两次失败比十次通过更能说明「正文里的数受清单约束」。

1.12 读图指引：四张图分别该盯什么

这一单元出现四种图元。tree 看带 + 的行，它们标出本节新增的两个源文件与清单；graph 逐帧比较状态差异，第 2 帧比第 1 帧多了解析器和字节码，第 3 帧换成编译路径；memory 看便签与对象的边界，第 3 帧里老对象还在但已经没人引用；calltree 看调用方向，第 3 帧多出的那条边对应 tick 里的 nonlocal。

每一帧都是自包含的。渲染器不会把上一帧的节点自动带到下一帧，打印版里每一帧是独立的一张图，所以第 3 帧里照样把 main() 与 scoped_count(5) 重写一遍。节点文字也刻意压短，因为同一句话在几帧里要重复出现。把图当成分步动画的步骤看，而不是三张互不相干的插图，才能读出「变化」。

最后强调一次证据的分工。正文里的解释负责回答「为什么」，清单和 stdout 负责回答「是多少」。程序自报的任何 PASS 都不算数；exec_mode:interpreted 这行也只是给人看的文字。下一单元我们会把同样的纪律搬到数组上：先看 shape、dtype、strides，再用循环版与向量化版对拍，残差进黄金值。工具变了，纪律没变。

1.13 再看一眼字节码：解释器视角的证据

前面说「源码先变成字节码」，这句话不能只停留在比喻上。本机自带 dis 模块，能把一个文件里的函数反汇编成人能读的字节码指令。在例子目录下执行 python -m dis src/demo.py，就会看到一份逐行对应的指令清单。

编译器视角解释器视角：字节码到底长什么样
  • 命令：在 examples/ch01/py_basics/ 下执行 python -m dis src/demo.py；
  • 观察：文件级代码以 RESUME 开头，紧接着 LOAD_CONST 取出文档字符串、STORE_NAME 把它绑到 __doc__；import sys 被拆成 LOAD_SMALL_INT、LOAD_CONST、IMPORT_NAME、STORE_NAME 四条指令；
  • 每个函数体单独成为一个代码对象，MAKE_FUNCTION 把它变成函数对象再 STORE_NAME 绑到名字上；这就是「函数也是一等对象」在字节码层面的样子；
  • 这段反汇编是解释器生成出来的中间表示，不是机器码；它证明了 1.2 节第 2 帧里「先翻译再执行」这一步真的存在。

把这份清单和 C 的汇编对照，会看到一个有趣的区别：LOAD_SMALL_INT 0 这种指令带着「小整数常量」的语义，而机器码里只有寄存器和立即数。解释器每条指令都要查一遍对象的类型信息，才能知道该怎么解释操作数。这正是 1.7 节说的分派开销的来源——它不是某一行代码的错，而是这套执行模型的固有成本。

你不需要记住任何一条字节码助记符。这里给出命令和观察结果，目的只有一个：让「解释执行」四个字落到一条可复现的命令上，而不是停留在课堂上的示意图。以后看到别人说「Python 慢」，你可以追问一句「慢在字节码分派还是慢在算法复杂度」，这个问题比笼统的快慢有用得多。

语法规则f-string 的取值格式只记这一处

形式：f"标签={值:.6f}" 生成数值行，f"标签:{值!r}" 生成说明行。前者按六位小数格式化，适合进闸门对账；后者调用 repr 保留完整精度，适合给人看精确打印值。花括号内还能写表达式，例如 f"a_shape:[{a.shape[0]},{a.shape[1]}]"，会在打印时求值。整行不带等号时就是普通文字，不会被当成数值行解析。

1.14 布尔、None 与整数：类型系统的三个边角

第一处边角是布尔值。Python 的 bool 是 int 的子类，True 和 False 在算术里分别表现成 1 和 0。所以 True + True 等于 2，sum([True, False, True]) 等于 2。这不是 bug，而是有意的设计：布尔判断常常和计数混在一起用。写数值代码时如果你不确定某个变量到底是布尔还是整数，用 type() 看一眼，比猜更可靠。

第二处边角是 None。它表示「没有值」，is None 是判断它的标准写法。不要用 == None——自定义类型可以重载相等判断，让一个并非 None 的对象和 None 比出相等。None 在布尔上下文里被当成假，但「被当成假」和「就是假」不是一回事：0、空字符串、空列表同样被当成假，它们彼此之间并不相等。把「是否为 None」和「真值真假」混为一谈，是读代码时容易看漏的一层。

第三处边角是整数除法的分裂。/ 永远返回浮点数，// 才做向下取整的整数除法，% 给出余数。三个数满足 a == (a // b) * b + a % b，对负数也成立，因为 // 是向下取整而不是向零截断。从 C 迁移过来的人最容易在这里踩空：C 里两个 int 相除得到 int，Python 里得到 float。写循环步长或数组索引时，这个差别会让下标变成浮点数，进而在索引时才报错。

工程惯例工程惯例：把类型意图写在变量名和注释里

Python 不要求声明类型，但读者需要知道一个变量大致是什么。给变量起名 n_rows、loss_sum、is_training，比起名 n、s、flag 更能说明意图；关键函数用一行文档字符串写清输入输出，本书的例子都这么做。这是惯例而非语言规定，代价是多敲几个字符，收益是别人（包括几周后的你自己）不用把整个函数读完才能猜出类型。后面用 Tensor 时，shape 与 dtype 会把一部分类型意图显式化，但命名习惯仍然管用。

1.15 把这一单元接到下一单元

这一单元的主线是「同样的数值程序，Python 慢在哪、快在哪」。慢在解释器的逐条分派，快在它能把真正的大循环交给底层库。今天看到的 loop_odd 是一个纯 Python 循环的结果，下一单元会把同一类计算写成数组运算：循环版依旧保留， NumPy 版用 @ 一次算完，两份结果相减得到残差。残差进黄金值，循环次数只作说明。

在读下一单元之前，先带着三个问题：第一，为什么列表里的元素必须各带一个对象头，而数组可以把数据紧紧挨着放？第二，shape 与 strides 之间是什么关系，为什么同一个数组转置之后 strides 会变而数据没动？第三，切片得到的视图和 copy() 得到的副本，改哪一个会动到原数组？这三个问题都能在本节的便签模型和对象开销里找到根：把数据从「一堆对象」变成「一块连续内存」，再让名字以不同方式指向它。

证据纪律也会一起带过去。下一单元的输出里，数组照样用冒号打印成 v:[...]，残差、求和、元素个数这些可复现的量写成 key=value 并进清单；毫秒数仍然不进黄金值。种子固定、真跑取数、黄金值对账这三件事，从 C 分册一路延续到 autograd，只是被对账的对象从点积换成了梯度。

小结这一节的要点
  • Python 每次运行都要先把源码变成字节码再交给虚拟机执行，C 的翻译工作大部分在编译期完成；
  • 变量是贴到对象上的便签，类型属于对象；可变对象被多个名字引用时，改对象大家都看见；
  • int 任意精度不会回绕，float 仍是 IEEE 754，0.1 + 0.2 的精确打印值不是 0.3；
  • 缩进决定作用域，读变量向外找、写变量默认在当前层，nonlocal 用来跨层修改；
  • 数值行走 key=value，数组与说明行走 key:文字，黄金值和容差只写在清单。

注自测题答案
  1. a 仍然是 3。第一次赋值把 a 和 b 两张便签贴到同一个整数 3 上；第二次赋值只把 b 这张便签改贴到新造的 4 上，并没有改动对象 3，所以 a 的指向不变。这正是「便签」与「对象」分离的好处：重新绑定不会误伤别人。
  2. 因为两个字面量各自被舍入成最接近的二进制近似值，相加后再次舍入，结果与字面量 0.3 的近似值不同。正确写法是判断绝对差是否小于容差，例如 abs((0.1 + 0.2) - 0.3) < 1e-9；闸门用的是同样的思路，只是把容差写在清单的 atol 里。
  3. 不写 nonlocal 时，total += 1 里的 total 会被当成 tick 的局部变量，赋值前读取它就会抛 UnboundLocalError。读变量不需要声明，是因为 Python 的作用域查找规则会沿着外层一路向外找名字；而赋值规则默认在当前层新建绑定，两条规则不对称，nonlocal 就是用来显式改写这条规则的。
  4. 因为那行是给人看的精确打印值，不是要被数值对账的项；冒号让它成为普通文字行，逐字比较即可。若写成 float_raw=0.30000000000000004，等号左边会被当成数值行的键，而右侧虽然也是合法十进制数，这行就会被当成第二个数值项参与对账；若右侧换成带方括号的内容，则会报 numeric_value_invalid。本单元统一把说明与数组写成冒号行，就是为了避免这类歧义。
  5. 墙钟时间受机器负载、缓存和调度影响，同一份代码两次运行的毫秒数可能差出百分之几十；把它写成黄金值，闸门会频繁误报，正文里的数也无法复现。固定计数精确、可复现，又足以说明解释器每层分派的工作量，所以更适合当证据。要谈性能时另做多次测量取中位数，那份数字不进闸门。
  6. 依赖的是「入口脚本所在目录自动进入 sys.path[0]」这条规则，所以同目录的 demo.py 能被直接找到。把入口挪到别的目录后，除非把模块也一起挪过去，或者显式把模块所在目录加进 sys.path，否则 import 会失败；更稳妥的做法是保持入口与模块同目录，并且始终在例子目录里执行 python src/main.py。
