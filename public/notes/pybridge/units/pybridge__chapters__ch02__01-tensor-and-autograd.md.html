2.1 先看工程长什么样

这一章是全书的分水岭。前四册里所有梯度都是手推出来的：先写前向，再在纸上链式求导，最后把十几行导数塞回 C 代码。从这一单元起，求导这件事交给框架，我们负责的是让它算对，并且证明它算对。

证据纪律一点没变：真运行、真实 stdout、黄金值写在清单里、容差只能写在 expect。变的只是被测对象——现在被测的不是某个 C 函数，而是一张由框架临时搭出来的计算图。

大白话先建立一个画面

把 autograd 想成一个随身记账的会计。你每做一次乘法、每一次加法，它都在小本子上记一笔：「这个数是由哪两个数算出来的，当时用的什么运算」。等你喊一声 backward()，它就顺着这本账倒着走一遍，把「最终结果对每一步中间量的敏感度」算出来。

关键是：它记的是运算，不是公式。你不用提前推导链式法则，只要把前向写对，反向就自动跟着来了。

第 2 帧里带 + 的四行就是这一节的全部新增。manual.py 故意不写一行 PyTorch：它用纯 Python 循环把前向和梯度各算一遍，充当「独立的那把尺子」。main.py 才用张量建图、反向、打印。pb04-autograd.json 把四个黄金值钉在清单里，正文里的数字受它约束。

工程惯例为什么手算模块要单独放一个文件

如果把手算和 autograd 写进同一个函数，很容易出现一种隐蔽的污染：你改了手算公式，顺手也改了张量表达式，两边一起错，对账却照样通过。拆成两个文件之后，manual.py 里没有一个 import torch，它想错都错不到框架那边去。代价是多了两行 from manual import ...，以及 import 路径要对——入口脚本所在的 src/ 会自动进 sys.path[0]，所以同目录的模块直接按名字引就行。

2.2 Tensor：ndarray 穿上三件外套

如果你写过 NumPy，Tensor 的第一眼几乎一模一样：一块连续的内存，按 shape 解释成多维数组，dtype 决定每格几位。torch.tensor([1.0, 2.0, 3.0]) 和 np.array([1.0, 2.0, 3.0]) 打出来的东西看不出差别。差别藏在三件外套里。

第一件是 shape 参与运算语义。NumPy 的广播规则宽松，(3,) 和 (1,3) 经常能混着用；PyTorch 在矩阵乘法这类运算上更严格，@ 要求维度对得上，错了当场抛异常而不是悄悄广播出一个你没想到的形状。这不是挑剔，而是把「我到底在算什么」提前暴露出来。

第二件是 dtype 会一路传染。整数张量除以整数张量在 PyTorch 里会得到整数结果（或者报错），不会像 Python 标量那样自动升级成浮点。本例里 xs、ws、ts 全部写成带小数点的字面量，就是为了让 dtype 从第一步起就是浮点；否则 w*x-t 的平方会走整数路径，梯度根本无从谈起。

第三件是 device 决定谁来计算。同一份代码在 CPU 张量和 CUDA 张量上写法一样，但两者不能直接相加。本例只用 CPU，你暂时感受不到这件外套的重量；等到模型搬到显卡上，忘记 .to(device) 报错的就是它。

语法规则本单元只用的四种写法
  • torch.tensor(xs, requires_grad=True)：从 Python 列表建张量，并申请「请替我记账」；
  • y = torch.sum((w * x - t) ** 2)：普通算术，但每一步都被记进计算图；
  • y.backward()：从标量 y 出发反向走图，把梯度填进各个叶节点的 .grad；
  • with torch.no_grad():：临时关掉记账，块内运算不进图。
陷阱把 Tensor 当成「能自动求导的 ndarray」就完了

这么想会在两处栽跟头。第一，只有 requires_grad=True 的张量才被记账；你从它派生出来的中间结果自动带 requires_grad，但一个一开始就用普通列表建出来的张量不会有梯度，即使后来参与了运算。第二，浮点 dtype 不会自己升级：torch.tensor([1, 2, 3]) 是整型，对它做 ** 2 仍然是整型，backward() 会直接拒绝——因为整数上不存在导数。你会看到什么？一句 RuntimeError: Only Tensors of floating point and complex dtype can require gradients。你会怎么误判？以为是计算图断了，其实是 dtype 在建张量那一刻就没选对——报错甚至发生在反向之前。真相是：建张量时写 1.0 而不是 1，比事后补 .float() 更不容易漏。

2.2.1 dtype 为什么会一路传染

上一节的 trap 只说了「整型不能求导」，但没说清这件事为什么会发生。PyTorch 的算术运算有一条简单规则：结果 dtype 由参与运算的张量决定，不会像 Python 标量那样自动往「更宽」的方向升级。torch.tensor([1,2,3]) 是 torch.int64，两个 int64 相乘还是 int64，torch.sum 也返回 int64。整条链路上没有一步会偷偷变成浮点。

这条规则在深度学习里是必要的。混用 dtype 意味着每次运算前都要插入隐式转换，既拖慢速度又让内存布局难以预测；框架选择把决定权交给写作者，代价就是你得在建张量那一步想清楚。本例里 xs、ws、ts 三个列表的元素全带小数点，建出来的张量 dtype 就是默认的 torch.float32，从源头上避免了问题。

实验记录亲手触发一次整型报错

把 main.py 里的 xs = [1.0, 2.0, 3.0] 改成 xs = [1, 2, 3]，然后跑 python src/main.py。你会拿到一句 RuntimeError: Only Tensors of floating point and complex dtype can require gradients，而且它发生在 torch.tensor(...) 那一行，反向还没开始。你会怎么误判？以为是计算图写错了、或者 .grad 没分配。真相是整型张量压根不允许 requires_grad，框架在建张量时就拒绝了。修法只有一条：建张量时写 1.0，或者在构造时显式给 dtype=torch.float32。做完把文件改回来，否则清单里的黄金值全对不上。

工程惯例这个坑在真实项目里长什么样

真实项目里 dtype 出错很少这么直白。更常见的是：数据加载器吐出的标签是 int64（分类任务本来就该是），你顺手把它和 float32 的模型输出一起送进损失函数，框架可能报类型不匹配，也可能在某个内部转换后照常跑出一个「看起来还行」的 loss。后者更危险。养成习惯：在模型入口处打印一次 x.dtype 和 y.dtype，确认它们是你以为的样子；本单元的例子虽然小，仍然把 dtype 的选择写死在带小数点的字面量里，就是为了让这件事一眼可见。

2.3 requires_grad：一句话把张量变成变量

requires_grad=True 不是给张量贴个标签，而是给框架一道指令：「从这个张量开始，所有以它为祖先的运算都要留痕」。本例里只有 x 开了这个开关：

w 和 t 没开开关，所以它们是常数：参与运算，但不需要为它们准备梯度槽。这一节刻意这么安排，是为了让对账只盯一个变量。真训练时权重 w 也会开 requires_grad=True，因为要学的正是它——那是下一单元的事。

注意 .grad 在反向之前是 None，不是 0。反向结束后它才变成一个与 x 同形状的张量。这个细节很重要：如果你在循环里反复 backward() 却不清零，梯度会累加。loss.backward() 算出 ∂L/∂x 之后把结果加到已有的 .grad 上，而不是覆盖它。为什么这样设计？因为一次前向可能对应多个损失项，你需要把它们各自的梯度先加起来再做一次更新。代价是训练循环里必须显式 zero_grad()——pb06 会专门讲这一步忘了会怎样。

第 1 帧和第 2 帧的差别只有一处：运算发生之后，小本子上多了 r 与 sq 两条记录。第 3 帧把三维向量压成一个标量 loss——这一步看似平淡，却是 backward() 能工作的前提。框架要求反向的起点是个标量，因为「一个向量对另一个向量求导」在数学上是个雅可比矩阵，框架不会替你默认把它压扁。

陷阱对非标量直接 backward() 会当场拒绝

你可能会想：既然 sq 是个三维向量，为什么不直接 sq.backward()？运行一下会得到 RuntimeError: grad can be implicitly created only for scalar outputs。你会怎么误判？以为是图建错了、中间节点没有 grad_fn。真相是框架不知道你想把三个分量的梯度「合成」成一个数：是求和？加权？还是各算各的？它拒绝猜测，要求你先 torch.sum(sq) 明确写出这个合成方式。所以本例里那句 torch.sum(...) 不只是为了得到 loss，也是在告诉反向「从哪个标量开始走」。

2.3.1 动态图：每次前向都重新搭一遍

PyTorch 的计算图是动态的：它不是在编译期定死的一张网，而是每次执行前向代码时现搭，反向走完之后就被丢弃。同一个变量下一次进前向，会生成一张全新的图，节点编号和上次毫无关系。这一点和 C 手写梯度形成鲜明对照——后者把导数公式编译进可执行文件，想改结构就得重新编译。

动态带来两个直接好处。第一，你的前向代码里可以写 Python 的 if、for、甚至打印语句，图会照着这次实际走的那条分支搭出来。一个按 batch 大小改变层数的网络，在静态图框架里要写两套符号表达，在这里只是普通的 Python 分支。第二，调试时你可以随时在某个中间节点上 print(y.shape)，看到的正是即将被记账的那个张量，不需要借助专门的调试器。

代价也有两条。第一是开销：每一次前向都要重新申请节点、记录运算，这部分时间在小程序里可以忽略，在每层都被调用上千次的模型里却很可观。第二是「图用完即弃」带来的纪律：你不能把上一次前向留下的 y 或 grad_fn 留到下一次用，因为它们指向的是旧图。训练循环里每一轮都从零开始算前向、算 loss、调 backward()，正是这个原因。

工程惯例动态图对实验意味着什么

对写实验的人而言，动态图最大的价值是「所见即所得」。本单元里 y 是什么、y.grad_fn 长什么样，你在 backward() 之前打一行 print 就能看到；不像静态图那样要先建会话、再喂数据、最后取结果。本书坚持让每个例子都把中间量打到 stdout，正是借了这个便利——正文里每一个数字都能在一次普通脚本运行里复现，不需要额外的图执行器。代价是这套机制依赖 Python 解释器实时跑，性能上限不如预先编译好的静态图，这也是后续工程里要用 torch.compile 之类工具的根本原因。

2.4 前向怎么记，反向就怎么走

现在把账本倒着读一遍。前向是 x → r → sq → loss，反向就是从 loss 出发，沿着相反的边一步步把敏感度传回去。每一步用的规则，恰好是前向那一步的局部导数。

记 r = w·x - t，sq = r²，loss = Σ sq。从后往前三句话就能推完：

  • ∂loss/∂sq = 1：求和函数对每个输入的偏导都是 1，这是 sum 这条边的局部导数；
  • ∂sq/∂r = 2r：平方的导数是两倍自身，所以传回残差的敏感度是 1 × 2r = 2r；
  • ∂r/∂x = w：因为 w 是常数，w·x-t 对 x 的导数是 w，逐元素相乘。

乘起来就是 ∂loss/∂x = 2·w·(w·x - t)。注意每一条边的局部导数只依赖前向时的输入值，不需要重新跑一遍函数——这正是计算图省下的东西。

第 3 帧的 x_grad 就是最终答案。对照第 2.3 节的前向图你能看到一件很舒服的事：反向完全照着前向的边走，只是方向相反、乘的因子换成局部导数。这条对称性不是巧合，链式法则本来就是这么说的。

工程惯例为什么中间结果不直接存梯度

你可能会问，既然 r 和 sq 也有 requires_grad，为什么程序只打印 x.grad？因为框架默认只为叶节点保留 .grad。中间节点的梯度算完就传下去，用完即弃，省内存。如果你真的想看某一层中间量的梯度，得显式调用 r.retain_grad()。在几层的小网络里这点内存无所谓，但真实模型有上亿个中间量，全都存下来会直接撑爆显存——这是框架做这个取舍的原因。

还有一层考虑：保留中间梯度会诱导你把它当成「可以拿去更新」的东西，但真正需要更新的只有参数。框架把 .grad 限制在叶节点上，等于用接口提醒你「该动的是谁」。本例里 x 恰好是需要求导的输入；换成训练时，叶节点会是权重和偏置。想清楚这一点，你读 optimizer.step() 的代码时就不会奇怪它为什么只遍历 parameters()。

2.5 手算那把尺子：为什么敢说 autograd 算对了

现在轮到 manual.py。它不知道 PyTorch 的存在，只按上一节推出来的公式逐项算：

这段代码把「手算梯度」落实成了一行列表推导。它和 autograd 的来源完全不同：一个是人从链式法则写死的公式，一个是框架从记账本倒推出来的结果。两条路互不引用，所以它们对上是一件有分量的事。

把具体数字代进去。x=(1,2,3)、w=(0.5,-1,2)、t=(1,0,2)。先算残差 w·x - t：

  • 第一项 0.5×1 - 1 = -0.5
  • 第二项 (-1)×2 - 0 = -2
  • 第三项 2×3 - 2 = 4

平方后求和：0.25 + 4 + 16 = 20.25。再算梯度 2w·(w·x-t)：

  • 第一项 2×0.5×(-0.5) = -0.5
  • 第二项 2×(-1)×(-2) = 4
  • 第三项 2×2×4 = 16

梯度向量是 (-0.5, 4, 16)，它的范数 √(0.25+16+256) = √272.25 = 16.5——恰好是个有限小数，这不是巧合，而是这组数据挑得好。正文里打印的 manual 和 auto 都是这个范数：把一个向量压成标量，才好放进清单做数值对账。

实验记录为什么对账要用范数而不是整个向量

清单的 expect.numbers 只能声明标量黄金值。梯度是个三维向量，直接打印成 g:[-0.5,4,16] 会被闸门当成普通文字行逐字比较——那也能查错，但查不出「差了一点点」这种数值漂移。所以程序额外把向量压成范数打印成 manual= 和 auto=，让闸门按 atol=1e-6 做真正的数值对账；向量本身那行留着给人眼看方向。两种证据各管一件事，谁也替代不了谁。

工程惯例换一组数亲手验一遍

建议把 ts 改成 (0, 0, 0) 再跑一次。此时残差就是 w·x=(0.5,-2,6)，梯度变成 2·w·(w·x)=(0.5,4,24)，范数 √(0.25+16+576)≈24.336187。手算完真跑一遍，看 manual 与 auto 是否仍然相等。改完记得把 pb04-autograd.json 里的四个黄金值同步改掉，否则闸门会报 numeric_value_mismatch——这正是纪律：黄金值来自真跑，不能反过来迁就正文。

2.5.1 三种梯度来源，三种可信度

把视野拉开一点，求梯度其实有三条独立的路，它们的可信度和代价各不相同。

第一条是解析梯度：人根据链式法则推导出闭式公式，再照着写进代码。manual.py 的 grad_x 就是这一类。它的优点是精确、快，缺点是公式一复杂就容易漏项——dlmath 分册里那个漏掉的 y(1-y) 因子就是活生生的例子。它适合当「参照答案」，但不适合独立承担正确性。

第二条是数值梯度：把第 i 个分量加一个很小的扰动 ε，算一次损失；再减 ε，算一次；斜率 (L₊-L₋)/(2ε) 就是偏导的近似。它不需要任何链式法则，思路简单到几乎不可能推错，所以常被叫作「明显正确的暴力版」。代价是慢：每个参数要跑两次前向，13 个参数就是 26 次；并且 ε 选得太小会被浮点舍入淹没，太大又引入截断误差。

第三条是autograd：沿计算图反向走，每条边乘上局部导数。它把前两条的优点合起来——比数值梯度快得多，又不需要人手写公式。但它不是独立的证据：如果前向写错了，它照样忠实地给错梯度的梯度。这就是为什么本单元要保留 manual.py。

实验记录为什么清单里写 diff 而不是写 PASS

把三条路的角色对上清单你就能看出设计意图：manual 是解析梯度，auto 是 autograd 结果，diff 是两者之差，黄金值都是真跑读数。闸门检查的是 |manual-auto| ≤ atol，也就是两条独立路径必须重合到小数点后六位。如果程序自己在末尾打一句 PASS，闸门看都不会看——它只认 stdout 里的数值行。这条「程序自报不算证据」的纪律在 dlmath 分册就立下了，Python 这边原样继承。

2.6.1 打印格式的纪律：等号、冒号与有效位

这一节的输出块看起来不起眼，其实每一行都是按规则设计过的。标量一律 key=0.123456：键名只含字母、数字、点、方括号、下划线与连字符，值必须是有限十进制数。这样的行才会被闸门解析成数值行，才有资格谈 atol。张量一律 v:[...]，冒号让整行落到「普通文字」通道，逐字比较即可。

为什么要分两条通道？因为数值对账需要知道「哪个数是哪个量」以及「允许多大误差」，而一个向量同时包含方向和大小，把它拆成三个 g_0=...、g_1=...、g_2=... 当然也能对账，但读者就看不到「这是一个三维梯度」的结构了。冒号行保留了结构，范数行保留了精度，二者互补。

有效位数也有讲究。程序统一用 %.6f 打印，而不是 Python 默认的 str(float)。原因有三：一是格式稳定，不会因为某个值恰好是整数就打 16.5 而另一个打成 16.5000001；二是stdout 里每行长度一致，便于逐行对账和日志阅读；三是六位小数对 atol=1e-6 的量级刚好够用——再多就是噪音，再少就掩盖差异。记住这条：打印精度要和容差配套，容差 1e-6 却只打三位小数，对账就成了摆设。

陷阱把布尔值也打进数值行会怎样

有人会把 x.is_leaf 直接写成 print("leaf=", x.is_leaf)，stdout 变成 leaf= True。前面那个键是合法的，但值 True 不是合法有限小数，闸门会报 numeric_value_invalid，整条清单失败。本例把三个布尔量塞进 flags:[leaf=1,...] 这个冒号行里，就是为了让它们走文字通道；%d 把 True 转成 1、False 转成 0，读起来仍然清楚。你会怎么误判？以为是闸门太严格。真相是闸门必须拒绝一切无法比较的「数值」，否则 nan、inf、布尔值混进来，|actual-expected| 的比较就失去意义。

2.7 叶节点、非叶节点与 no_grad

最后一行 flags:[leaf=1,nonleaf=0,frozen=0] 挤进了三个布尔事实，值得单独拆开。x 是你亲手建出来的，requires_grad=True，没有 grad_fn——它是叶节点。y 是算出来的，带着 grad_fn=<SumBackward0>——它是非叶节点。而 frozen 是在 with torch.no_grad(): 里由 y*2 得到的，既没有 grad_fn，requires_grad 也是假。

这三身份的区分不是学术分类，它直接决定你会不会踩坑。只有叶节点的 .grad 会被填充；对非叶节点读 .grad 会得到 None。而 no_grad() 的用处有两条：一是做推理时省掉记账开销——你不打算反向，记那些账纯属浪费时间和内存；二是明确告诉框架「这几个量当常数看」，避免它们意外把梯度一路传回你不能更新的东西。

陷阱以为 no_grad 里的结果还能反向

最常见的误用是这样：先 with torch.no_grad(): z = x * 2，出了块之后想 z.backward()。你会看到 RuntimeError: element 0 of tensors does not require grad。你会怎么误判？以为是 x 的 requires_grad 被块改掉了。真相是 x 一点没变，变的是 z——块内所有运算都不记账，z 从出生起就不带 grad_fn，反向链路在它这里断了。要修就得把 z 放回块外重新算。这个错在推理代码里尤其常见：有人为了省内存把预处理也塞进 no_grad，结果发现模型根本学不动。

工程惯例什么时候该用 no_grad，什么时候不该

一个简单判据：这一步的结果要不要参与反向。训练时的前向、loss 计算、反向都在记账范围内，不能包 no_grad；而验证集上的 loss 统计、把张量转成 NumPy 打印、构造不需要学习的常数标签，都该包进去。代价是你要多写一行 with，换来的是显存与速度。别为了「看起来专业」到处加 no_grad——加错位置的症状是梯度莫名其妙变成 None，排查起来比重写一行费劲得多。

2.8 图元怎么读：四张图分工不同

这一节用了四张图元，它们的分工不能互换。tree 看带 + 的行，那是本单元新增的工程文件；第一张 graph 画前向，重点看「每做一次运算，账本上就多一条记录」；第二张 graph 画反向，重点看「反向的边和前向一一对应，只是乘的因子换成局部导数」；memory 画三种身份，重点看 .grad 与 grad_fn 分别长在谁身上。

读多帧图时有两条硬规矩。第一，每一帧自包含：渲染器不会把上一帧的节点自动带过来，所以第 2 帧里仍然成立的 x、w 都要重写一遍，纸面上每帧都是独立的图。第二，节点文字不超过十八个字，箭头两边必须留空格——x -> r 才会被画成一条边，写成 x->r 就只是普通文字。这些约束看着繁琐，但它们保证同一份围栏在单页 HTML、合书、打印 PDF 里长得一模一样。

陷阱把「图」当成静态插图看

如果只盯着第 3 帧，你会以为前向和反向是两件独立的事。其实图元的正确读法是比较相邻两帧的状态差异：第 2 帧比第 1 帧多了哪两条记录，第 3 帧又多了哪一个节点。打印版没有动画，所以每帧都把旧节点重画一遍——那是约束，不是啰嗦。把四张图连起来读，你会得到一条完整叙事：建图、记账、倒走、落梯度。

2.9 与那一册手写梯度的对照：代价换来了什么

回头看 dlmath 分册的试点：13 个参数，反向传播写了满满一页，其中最容易漏的是 sigmoid 的链式因子 y(1-y)。漏了它程序照跑、loss 照降，肉眼几乎看不出来。现在把这些交给 autograd，那一行再也不会漏——因为框架直接从运算记录里读出局部导数，不存在「人忘了写某项」。

但天下没有白吃的午餐。第一笔代价是可见性变差：手推时每一步导数都摊在纸上，现在它们藏在 grad_fn 链里，初学者看到 loss 不降能改的只剩学习率。所以这一节坚持保留 manual.py 这条独立路径——不是为了重复劳动，而是为了让梯度仍然「有一把外面的尺子」。第二笔代价是调试对象变了：以前查的是公式写没写错，现在查的是图建没建对——dtype 是不是浮点、有没有误进 no_grad、是不是对非标量调了 backward()。这三类错本单元都专门展开过。

工程惯例把三道体检平移过来

dlmath 那册立了三条规矩：数值黄金值查前向、梯度对拍查导数、种子与收敛查训练。这一单元完成了前两条：前向的 loss 是黄金值，梯度的 manual 与 auto 互为对拍。第三条要等到 pb06 的训练循环才齐。注意本单元没用 mode=gradient——那是 C/C++ 专用，靠编译期注入错误梯度的阴性对照来判别；Python 这边把解析梯度、autograd 梯度和残差都当黄金值对账，阴性对照的角色改由「手算模块完全不 import torch」这层独立性来承担。

2.9.1 当梯度变成 nan：三种典型原因

真正上手之后，你迟早会遇到 loss 打出 nan 的时刻。数值行里出现 nan 会被闸门判成 numeric_value_invalid，因为 NaN 不是有限十进制数——这是好事，它逼你停下来查，而不是让一张看似正常的表格混过去。这里先列出三种最常见的原因，方便你按图索骥。

第一种是数据里本来就有非有限数。输入含 nan 或 inf，任何运算都会把它传染下去：nan 参与加法还是 nan，inf - inf 也是 nan。查法是在建张量之后立刻打一行 torch.isfinite(x).all()，别等到 loss 出来才追。第二种是除零或开方负数。比如自己写 softmax 时分母可能为零，或者手写方差时 x 全相等导致标准差为零。PyTorch 对整数除零会抛异常，对浮点除零则安静地给出 inf——后者更危险。第三种是学习率过大导致参数爆炸：权重指数增长直到溢出成 inf，接着 inf - inf 把 loss 变成 nan。这种情况通常出现在训练若干步之后，而不是第一步。

工程惯例用最小脚本定位非有限数

怀疑某个张量有问题时，不要整套重跑。把前向拆开，在每个中间量后面插一句 print(name, torch.isfinite(t).all().item(), t.dtype)，先跑一次。输出会告诉你第一次出现 False 的位置。若连输入都是 False，问题在数据源；若输入正常而某个中间量变 False，问题就在那一步运算或它前面的运算。非有限数具有传染性，定位要找最早出现的位置，而不是最后打印出的 loss=nan 那一行。

陷阱用等号判断 nan 永远不成立

有人会写 if x == float('nan'): 来判断，结果永远进不去分支——IEEE754 规定 nan != nan。要用 torch.isnan(x) 或 math.isnan(x)。同样地，inf 虽然能用 == 比，但更稳的是 torch.isinf。这个坑在 C 分册讲浮点时就出现过，到了 Python 加上张量之后并没有消失，只是换了一层 API。闸门的 numeric_value_invalid 正是替你把最后一道关：只要 stdout 里出现 nan=... 或 loss=nan，整份证据直接作废。

2.10.1 一张可以照着做的排查清单

把这一节所有纪律压缩成六步，下次梯度不对时按顺序过一遍，能省掉大量瞎猜。

第一步，确认 dtype：所有要进计算图的浮点张量都应是 torch.float32 或更高，别让整型混进来。第二步，确认起点：打印 requires_grad 与 is_leaf，你要反向的那个量必须是叶节点且开关打开。第三步，确认图没断：在 loss 之前打印 y.grad_fn，它是 None 说明中间某处被 no_grad 包住了。第四步，确认反向起点是标量：打印 y.shape，它是 () 或含一维才安全，三维向量必须先 sum。第五步，确认梯度不是累加的结果：在 backward() 前打印 x.grad，第一次应为 None；若在循环里，先清零。第六步，拿独立尺子量：manual.py 那种纯 Python 实现给出的范数应当和 auto 在六位小数上一致。

这六步没有一步需要读框架源码，全是能在一次普通脚本运行里验证的观察量。把它们写进习惯，比记住某个报错文本更有用——报错文本会随版本变，但这六个问题不会。

工程惯例为什么把排查写成清单而不是讲原理

原理层面，「梯度不对」永远可以归结为「前向写错」或「图没建对」两句话，听完还是不知道该敲哪条命令。清单的价值在于把它翻译成可执行的动作，每步都有一个能打印的量和一个明确的预期。这也是本书反复坚持「数字要真跑、输出要贴原文」的原因：一个能打印出来的中间量，比一段口头解释更能定位问题。代价是你得多写几行 print，但比起追一整个下午的 bug，这点成本可以忽略。

下一单元把这套机制用到一个真正的两层网络上：2→3→1，tanh 加 sigmoid，13 个参数全交给 autograd。你会看到 loss.backward() 一行取代了那一页手推公式，同时 gradcheck_residual 仍然把梯度数值摆出来给人看——框架接管了求导，但证据纪律一点没松。

小结这一节的要点
  • Tensor 是带 shape、dtype、device 的 ndarray；建张量时写 1.0 而不是 1，避免整数路径上无法求导；
  • requires_grad=True 让运算留痕形成计算图；叶节点保留 .grad，非叶节点只持有 grad_fn；
  • backward() 必须从标量出发，梯度累加而非覆盖，所以训练循环里要显式清零；
  • 手算 ∂L/∂x = 2w(wx-t) 与 autograd 逐项相符：manual=auto=16.5、diff=0；
  • 标量打印成 key=value 才享受容差，张量打冒号 g:[...] 走逐字对账；容差只写在清单。

注自测题答案
  1. 因为梯度沿着「以 x 为祖先的运算」回传，w、t 只是常数系数，参与运算但不需要梯度槽。给 w 也开开关后，w.grad 会被填上 2x(wx-t)，而 x.grad 不变——两个变量各自独立求导，互不影响。

  3. sum 把向量压成标量，明确告诉框架「反向从哪些分量的加权和开始」。省掉它对三维向量调 backward() 会报 RuntimeError: grad can be implicitly created only for scalar outputs，框架拒绝替你猜合成方式。
