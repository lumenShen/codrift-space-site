2.1 先看工程长什么样

上一单元把数字打成了 key=value，这一单元换成数组。例子仍然守着同一套骨架：一个入口、一个本地模块、一个清单。模块里放四件事——三层循环版矩阵乘法、@ 版矩阵乘法、广播加法、视图与拷贝的检测；入口负责造数据、调用它们、打印对账用的数。

第 2 帧新增的 vectorize.py 是本单元的核心：循环版和框架版放在同一个模块里，才能公平对拍。第 3 帧新增清单，九个黄金值将由它声明。注意入口用 from vectorize import ...，与上一单元 from demo import ... 是同一条规则：入口脚本所在目录自动进入模块搜索路径，所以同目录的模块可以直接导入。

这一单元还有一处与上一单元不同：入口顶部固定了随机数生成器的种子，末尾才用它抽四个数。种子固定是为了让 seed_sum 成为可复现的黄金值；放在末尾是为了让前面那些手算例子不被随机数干扰。真正重要的实验里，种子要在最开始就固定，并且三种随机源一起固定——那是第三单元的主题。

2.2 ndarray 与 C 数组：同一块内存，多了一份说明

C 里写 double a[6]，拿到的是六个连续的 double，编译器知道每个占八字节，数组名在多数场合会退化成指向首元素的指针。NumPy 的 ndarray 把这件事拆成两层：一块连续的数据区和一份描述这块数据该怎么解释的元数据。元数据里最要紧的三项是 shape、dtype、strides。

大白话用大白话先说清这三层元数据

把数组想成一排格子。dtype 告诉你每格里装的是什么、占多宽，比如 float64 就是八字节的浮点数；shape 告诉你这排格子要怎么折成多维，比如 (2,3) 就是两行三列；strides 告诉你「在同一行里往右走一格要跨几个字节」以及「换到下一行要跨几个字节」。C 数组把这些写死在类型里，所以不需要另存；NumPy 的维度是运行时决定的，所以必须把它们显式记下来。同一块数据，换一份 shape 就能换个看法——这正是后面视图与转置的基础。

第 1 帧是物理视角：六个 float64 连续排列，第 k 格距离起点 8k 字节。第 2 帧把 shape=(2,3) 套上去，于是「往右一格」跨 8 字节，「往下一行」跨 24 字节——因为一行有三格，三乘八等于二十四。程序真跑打印的 a_strides:[24,8] 正是这两个数。第 3 帧是转置：数据区还是那六格，但「行」和「列」的解释互换了，所以 strides 变成 (8,24)。

理解 strides 之后，很多看似神秘的现象都变简单了。切片 a[:, ::2] 不复制数据，只把列方向的步长从 8 改成 16；转置不复制数据，只交换两个步长；把数组传给一个 C 扩展时，对方真正需要知道的就是「数据在哪、每维多长、步长多少」。所谓「零拷贝视图」，全部建立在这份元数据可以被改写的前提上。

陷阱以为 strides 一定等于 dtype 大小乘以维度，会被坑在哪

你会看到：一个数组的 shape 是 (3,4)，于是你推断它的第二维步长一定是 8（假设 float64）。你的第一反应是「 stride 还能不是 8 吗」。真相是：只有当数组在内存里连续存放时，这个推断才成立。转置、步长切片、或者从别的数组里取出来的视图，都可能让步长变大、变小，甚至为负。判断办法只有一条：直接打印 a.strides，别拿 shape 反推。本单元把 a_strides 打进 stdout，就是为了让这条判断有证据。

2.3 向量化：把循环交给底层

现在看矩阵乘法。三层 Python 循环版逐格算：外层遍历结果的行，中层遍历结果的列，内层做点积。框架版只写 a @ b。两行代码算的是同一件事，区别在于循环发生在哪一层。

第 1 帧里 py_loop -> scalar 这条边每发生一次，解释器就要判断一次对象类型、分派一次乘法实现；第 2 帧把整段循环压到底层的 BLAS 里，Python 只负责发起和收结果。第 3 帧是对拍：两个版本都算完，逐元素相减，最大绝对差写进 diff。真跑得到 diff=0.000000，说明在这个尺寸上两条路给出的结果一致。

这里要克制一个冲动：别从 diff=0.000000 推出「底层算法和我们的循环完全一样」。浮点求和顺序不同，结果可能差最后几位；这组数字能精确对上，是因为我们选的小整数恰好能被 float64 精确表示。换成随机小数，残差通常是一个极小的非零值——那时它照样能进金色值，只要固定种子保证可复现。

实验记录为什么本单元不打印毫秒
  • 命令：python src/main.py，输出里打印的是 ops_loop=12、ops_np=12 与 diff=0.000000；
  • 12 来自 2×2×3：结果矩阵两行两列，内层各做三次乘加，两个版本算的是同样多的标量运算；
  • 墙钟时间不计入黄金值：同一份代码两次运行的毫秒数会随机器负载、缓存与调度波动，把它写进清单会让闸门频繁误报；
  • 想看性能差异时，另做多次测量取中位数，把数字留在实验记录里，不进 expect.numbers。这是证据纪律，不是回避测量。

2.4 广播：形状不同也能相加

第三个函数演示广播。数据 a 的形状是 (2,3)，偏置 bias 的形状是 (3,)。两者维度数不同，NumPy 仍然允许相加：它把短形状在左侧补 1，变成 (1,3)，再按「对应维相等或其中一个是 1」的规则逐维对齐，长度为 1 的那一维被当成可沿该轴复制。结果是 (2,3)：偏置被加到每一行上。

第 2 帧里那条边是广播规则的要点：维度长度一个是 2、一个是 1，不冲突，长度为 1 的那维只是「可以复制」。如果换成 (2,) 的偏置去加 (2,3) 的数据，最后一维 2 对 3 既不相等也不是 1，就会立刻抛错。广播不是魔法，它是一组可以逐维检查的规则。

bias_sum=141.000000 可以手算核对。原矩阵六个元素之和是 1+2+3+4+5+6=21，偏置三个数之和是 10+20+30=60，两行各加一次偏置，所以总和是 21 + 2×60 = 141。这个手算把「偏置沿第 0 轴复制了两次」这件事变成了一个可验证的整数。如果你的程序打出别的数，先检查偏置的形状是不是被写成了 (2,)。

工程惯例工程惯例：把广播写成显式形状更稳

库代码里常见 x + bias.reshape(1, -1) 这种写法，虽然 x + bias 也能跑。显式 reshape 的好处是把「我希望沿哪一维复制」写进代码，读的人不用在脑子里跑一遍广播规则；代价是多一行代码，而且在维度变化时可能不再适用。本书例子保留隐式广播，是为了让读者一次看清规则；真实项目里两种写法都常见，选哪种取决于团队更看重简洁还是明确。

2.5 视图与拷贝：改一个会不会动到另一个

切片 a[:, :2] 得到的不是新数组，而是一个视图：它有自己的形状和步长，但数据指针仍指向原来的六个格子。在视图上写 view[0,0] = -999.0，原数组的 [0,0] 也跟着变。调用 .copy() 才会另开一块数据区，此后两边互不影响。

第 2 帧的视图只有两张元数据卡，没有自己的数据；第 3 帧的副本才有独立数据区。真跑打印 view_hit=1 与 copy_safe=1：前者说明改视图确实动到了原数组，后者说明副本里的值仍是原值。两个 1 都是整数黄金值，不受浮点容差影响。

陷阱把切片结果当独立数组，会被坑在哪

你会看到：一段代码先 v = a[:2]，再对 v 做归一化或填充，随后发现 a 里的值莫名其妙变了。你的第一反应是「我只改了局部变量 v，怎么会动到 a」。真相是：v 是视图，它和 a 共享数据；你改的是那块数据本身。判断办法是看 v.base is a 是否为真，或者更简单——需要独立数组时就显式 .copy()。这类 bug 特别难查，因为赋值语句看起来人畜无害，症状却在很远的下游才出现。

2.7 手算核对：四个数不用程序也能验

先算矩阵乘法。a 第一行点乘 b 第一列：1×7 + 2×9 + 3×11 = 7+18+33 = 58。第一行点乘第二列：1×8 + 2×10 + 3×12 = 8+20+36 = 64。第二行第一列：4×7 + 5×9 + 6×11 = 28+45+66 = 139。第二行第二列：4×8 + 5×10 + 6×12 = 32+50+72 = 154。四个数正好是 stdout 里那两行数组的内容。

再算总和：58 + 64 + 139 + 154 = 415，与 loop_sum 和 numpy_sum 一致。广播那一组：偏置是 [10,20,30]，加完两行之后全部元素之和是 21 + 2×60 = 141，与 bias_sum 一致。循环次数：2×2×3=12，两个版本都是 12，说明它们做的标量乘加次数相同，差别只在「这些乘加发生在哪一层」。

seed_sum=2.844317 不能手算，它是固定种子下的抽样结果。它的作用不是展示随机数有多随机，而是证明「同一种子必得同一串数」：把这个数写进黄金值，任何人重跑这份代码都该得到同一个值。若种子没固定，这一行每次都在变，闸门就会失去一个可靠的对账点。

实验记录把黄金值改错一次，看闸门怎么报

把清单里 diff 的 value 从 0.0 改成 0.1，跑 node build/run.js --unit pb02-numpy。闸门会报 numeric_value_mismatch，因为真实 stdout 的 diff 与黄金值差了 0.1，远超 1e-6。再把正文里 a_strides:[24,8] 改成 [8,24]，重跑同一条命令，会报逐字不一致——因为那不是数值行，闸门按文字对账。做完记得改回原值。

2.8 从 C 的数组到 ndarray：概念对照

C 里数组的长度信息常常要额外传一个变量，函数签名写成 void f(const double *x, int n)；NumPy 把长度放进对象里，函数直接读 x.shape。这个差别看似小事，却决定了两层工程实践：C 里维度不匹配往往是静默错误，NumPy 里形状不匹配通常当场抛异常。异常比静默错误好，因为它逼你停下来看。

C 里数组名在传参时退化成指针，函数内部拿不到「这是不是一个独立副本」的信息；NumPy 的视图带着 base 属性，能追出它从哪块数据来。这也是为什么本单元专门用两个整数 view_hit 与 copy_safe 把这件事钉死。把「谁改了谁」写成可复现的数值，而不是一句口头提醒，是这套书从第一册延续下来的证据纪律。

计算路径的差别更根本。C 的循环被编译成机器指令，循环本身就在最快的一层；Python 的循环留在解释器层，只有把数据交给底层库才能跨到快的一层。所以写 Python 数值代码的正确姿势不是「把 C 循环逐行翻译过来」，而是「先想清楚数据布局，再找库里现成的批量操作」。loop_matmul 保留下来是为了对拍和教学，真实项目里应当写 a @ b。

2.9 常见坑与读图指引

第一个坑是用 dtype 猜步长，前面已经用 a_strides 这行证据驳回。第二个坑是把视图当副本，第 2.5 节的两帧图给出了判断办法。第三个坑是广播方向搞反：偏置形状 (3,) 配数据 (2,3) 是合法的，配 (3,2) 就不合法；别靠试，按「右侧对齐、逐维检查」的规则推一遍。

这一单元有四张图元，读法各不相同。tree 看 + 行，确认本单元新增的两个源文件与清单；第一张 memory 看数据区与步长的对应，重点是第 3 帧转置只改元数据；graph 看循环版与框架版的执行路径差异，重点是第 1 帧那条「一次乘加一次分派」的边；第二张 memory 看视图与拷贝指向几块数据，重点是第 3 帧原数组已经被改。每帧都自包含，打印版里每一帧是独立的图，所以关键节点在几帧里重复出现是刻意的。

最后把这一单元接回第一单元。第一单元说「把循环搬到 C 或 Fortran 写好的库里」，本单元给出了第一份实物：a @ b 一次调用背后是底层库在按块遍历，dtype/shape/strides 则是 Python 与底层之间那份共同的约定。下一单元会把工程纪律补齐——模块、种子、输出格式怎么钉死；再往后，Tensor 登场时你会发现它就是把 ndarray 添上 device 与 requires_grad 两个字段。数组的这三个属性不会消失，只会换一层外衣。

2.10 dtype 不是装饰：宽度、精度与溢出

dtype 决定每格占几个字节、按什么规则解释这些字节。本单元选的是 float64，也就是 IEEE 754 双精度：八字节、约十五到十六位十进制有效数字。把它改成 float32 之后，每格只占四字节，同样一块内存能装下两倍的数据，代价是有效数字降到七位左右，而且累加误差更容易积累。深度学习里 float32 是常态，因为训练对速度敏感、对最后几位不敏感；科学计算里 float64 更常见，因为解的精度本身就是要研究的对象。

整数类型更直接。int8 只有一字节，能表示 -128 到 127；把 100 加 100，结果是 -56，因为它按补码回绕了。NumPy 不会像 Python 的任意精度整数那样自动扩展类型——这一点是 C 的习惯，不是 Python 的习惯。写索引时通常用系统默认的整数类型，宽度足够；但如果你为了省内存把索引数组压成 int8，一旦元素个数超过 127，就会静默错乱。判断是否需要收窄类型，要看数据的取值范围，而不是看内存够不够。

陷阱把 Python 整数的安全感带进 NumPy 数组，会被坑在哪

你会看到：x = np.array([100], dtype=np.int8); y = x + 100 打出 [-56]。你的第一反应是「加法写错了」，或者觉得是打印格式问题。真相是：dtype 一旦定下，运算就按这个宽度做，超出范围按补码回绕；Python 标量的任意精度保护在这里不生效。判断办法是打印 x.dtype 与 x.max() 这类边界值，先确认范围再算。真要避免回绕，就把数组建成更宽的类型，例如 dtype=np.int64。

dtype 还影响跨库交互。把这些数组交给 PyTorch 时，类型要对得上：float64 的 NumPy 数组变成 Tensor 后依然是双精度，而很多网络层默认期待单精度。类型不一致不会总是报错，有时只是悄悄做一次拷贝转换，让性能下降一半却看不出原因。养成习惯：在数据入口处统一打印一次 dtype，就像本单元打印 a_dtype:float64 那样，把约定摆到明面上。

2.11 索引的两种身份：共享数据还是另开一块

索引看起来只有一种写法，实际上分成两类。用整数或切片索引，例如 a[0]、a[:, :2]，得到的是视图：元数据变了，数据还指着原来那块。用整数数组或布尔数组索引，例如 a[[0,1], [0,1]]、a[a > 3]，得到的是新的数组：数据被抽出来重排到一块新内存里。两类结果用起来几乎一样，改起来却完全不同。

实验记录本机实测：三种索引的步长与 base
  • 命令：在本机 python -c 里对 a = np.arange(6, dtype=np.float64).reshape(2,3) 逐项观察；
  • a.strides 是 (24,8)，a.T.strides 是 (8,24)，说明转置只改元数据；
  • a[:, ::2].strides 是 (24,16)，列步长翻倍，说明步长切片同样不复制数据；
  • a.flags.c_contiguous 为真而 a.T.flags.c_contiguous 为假，说明转置后不再按行连续；
  • 花式索引 a[[0,1],[0,1]] 的结果 base 为 None，它确实拿到了一块新数据。

为什么这件事值得写进正文？因为「改一个会不会动到另一个」是数据管道里最常见的隐式耦合。把特征矩阵切片送进归一化函数，函数里就地减去均值，结果原矩阵也被改了——训练时前一批样本的统计量被后一批破坏，这种 bug 极难定位。防御手段不是记住所有规则，而是建立习惯：凡是准备就地修改的数组，先问一句「它是视图吗」，不确定就 .copy()。

负步长切片也值得知道。a[::-1] 得到的视图步长是负的，数据没动，只是从尾部往头部走。很多库对负步长支持不佳，传给 C 扩展时可能被迫复制一份。这不是错误，只是性能上的隐含代价；读到「为什么这段数据突然慢了」时，检查步长是不是负数，往往比看算法更有用。

2.12 内存顺序：C 连续与 F 连续

shape 与 strides 一起决定了数据在内存里的走法。按行存放的数组叫 C 连续，最后一维变化最快；按列存放的叫 F 连续，第一维变化最快。本单元的 a 是 C 连续的，strides=(24,8) 就是证据；转置之后第一维变化最快，变成 F 连续。NumPy 的大多数操作不关心顺序，但把数组交给底层库时，顺序会决定是否要先复制一遍。

这不是抽象的性能焦虑。矩阵乘法里访问 b 的某一列时，如果 b 是 C 连续的，那一列的元素在内存里隔着整行距离，缓存命中差；如果 b 是 F 连续的，那一列恰好连续，访问快得多。底层 BLAS 会针对这一点选择不同的内核，或者要求调用方先做一次转置拷贝。你在 Python 里只写了一行 a @ b，但这些决定已经在底下发生了。

工程惯例工程惯例：在边界处统一内存布局

数据从文件读进来、经过若干切片和转置之后，布局可能已经七零八落。稳妥做法是在交给底层库之前统一一次布局，例如用 np.ascontiguousarray，让拷贝发生在一个可控的位置；代价是多一次内存复制，收益是后续每一步都不必为奇怪的步长付隐性成本。本书例子规模小，看不出差别；真实数据管道里，这一步经常是性能分水岭。

把内存顺序和上一单元的便签模型连起来看，会更清楚：ndarray 的名字、元数据、数据区是三个不同的东西。视图只换元数据，副本才换数据区；转置换的是元数据的解释顺序，内存顺序标志随之改变。一旦你习惯把这三者分开想，广播、切片、转置、拷贝四类操作就不再是四条要背的规则，而是同一套模型的四种用法。

2.13 广播的边界：规则推演而不是试错

广播规则只有两条：短形状在左侧补 1；逐维比较时，长度相等或其中一个为 1 才合法，结果取较大的那个。把这两条写成推演步骤，任何形状组合都能当场判定，不必敲代码试。

例如 (2,1,3) 加 (4,3)：先把后者补成 (1,4,3)；第一维 2 对 1 合法、结果 2；第二维 1 对 4 合法、结果 4；第三维 3 对 3 相等、结果 3；最终形状是 (2,4,3)。再例如 (2,3) 加 (2,)：补成 (1,2)，第一维 2 对 1 合法，第二维 3 对 2 冲突，报错。注意「补 1 在左侧」这条：偏置写到右边才是列向量式的对齐，写到左边往往得到完全不同的结果。

陷阱把广播当成自动纠错，会被坑在哪

你会看到：a + bias 在 bias 形状 (3,) 时成功，换成 (2,) 时抛异常，而两段代码看起来只差一个数字。你的第一反应是「NumPy 怎么有时宽容有时严格」。真相是：广播按规则推演，合法就做、不合法就报，它从不会猜你的意图。判断办法是打印两个形状，按本节两步规则逐维推一遍。若推演发现冲突，就显式 reshape 到期望形状，让错误在 reshape 那一步暴露得更清楚。

广播也不复制数据。它让运算在读取短数组时重复读取同一块内存，逻辑上像复制了若干份，物理上并没有。这个细节在内存紧张时很重要：给一个巨大的矩阵加一个长度为列数的偏置，不会凭空多出一大块内存。但如果后续对这个结果做就地修改，就要小心——结果的形状可能是新的，数据区却是由广播逻辑生成的，某些情况下仍会被底层做成副本。需要确定时，看 np.shares_memory 的判断，不要用肉眼猜。

2.14 求和顺序：残差为什么不一定为零

diff=0.000000 很容易被误读成「两条路完全等价」。浮点加法不满足结合律：(a+b)+c 与 a+(b+c) 可能差最后一位。循环版按 k=0,1,2 的顺序累加；BLAS 可能分块、可能用向量寄存器并行累加，顺序不同。这次残差为零，是因为我们的整数输入都能被双精度精确表示，任何顺序都得到同一个结果。

把输入换成固定种子抽出来的小数，残差通常会变成一个极小的非零值。那时它同样能作为黄金值——只要种子固定，这个残差每次都一样。这正是第三单元要强调的种子纪律：不是让随机数消失，而是让随机过程可复现，从而让噪声也能被对账。想进一步减小误差，可以用 pairwise 求和或补偿求和，但那属于数值分析的专门话题，本册只在需要时点到。

实验记录把输入换成小数后会发生什么

建议自己改一次：把 a、b 的元素改成带小数的值，例如 1.1、2.2，重跑 python src/main.py。你会看到 diff 大概率不再是零，但每次运行仍是同一个值——因为代码里 rng 的种子固定，且输入是写死的常量。然后把清单里 diff 的黄金值改成这次的真实读数，闸门应该重新通过。做完记得把输入和清单都改回来。这个练习能让你亲身体会「残差也是可复现的证据」。

2.15 一个完整的排查故事

假设你改完代码，发现 bias_sum 从 141 变成了别的数。第一步别急着改黄金值，先回到手算：矩阵和 21、偏置和 60、两行各加一次，理论值就是 141。理论值没变而程序变了，说明改动引入了 bug 或对输入动了手脚。第二步读 stdout 的 a_shape:[2,3] 与 a_strides:[24,8]，确认数据布局没被改坏。第三步检查 bias 的形状，看广播是不是把偏置加到了错误的轴上。

如果这些都正常，再看 view_hit 与 copy_safe。这两个整数专门用来发现「某个函数偷偷改了原数组」：如果 view_hit 从 1 变成 0，说明视图共享关系被破坏了，可能是有人在不该 .copy() 的地方复制了；如果 copy_safe 从 1 变成 0，说明副本变成了视图，原数组被写入的风险出现了。把这类关系写成数值并进黄金值，就是把隐式的工程约定变成可机器检查的证据。

最后才轮到改黄金值。只有在你确认数值变化来自「有意修改输入或算法」时，才应该用真跑读数更新清单。顺序反过来——先改黄金值让闸门变绿——等于把证据关掉。这套流程在 C 分册里用来对付点积和范数，在这里用来对付数组与残差，到了 autograd 还会用来对付梯度。工具一直在换，顺序一次都没变。

2.16 把这一单元接到下一单元

这一单元把数据从「一堆对象」变成了「一块连续内存加元数据」，并用三个属性把这块内存解释清楚。下一单元要做的是工程收尾：模块怎么分、种子怎么一起固定、输出怎么只留能对着账的数。你会在那里看到同一条打印纪律再次出现——数组用冒号，数值用等号，黄金值只写在清单。

再往后，Tensor 登场。它保留 shape 与 dtype，添上 device 与 requires_grad。本单元练的 strides 在 Tensor 里仍在，视图与拷贝的陷阱仍在，广播规则也仍在。所以这里的图元不是一次性的插图：第 2 帧那句「换行走 24、换列走 8」，到了 GPU 上只是把内存地址换成显存地址，解释方式一模一样。

2.17 从列表到数组：开销到底省在哪

回到上一单元的 getsizeof。把一千个浮点数装进 Python 列表，再把同样一千个数装进 float64 数组，观察两者。列表本身报约 8856 字节，数组报约 8112 字节——看起来差不多，但这是个陷阱式的读数：sys.getsizeof 数的是列表里那一千个指针加上表头，并不包括指针指向的那些浮点对象。每个浮点对象另外占 24 字节，一千个就是约 24000 字节。数组则是实打实的一块 8000 字节数据区加一点元数据，没有额外的对象。

把三块加起来，列表方案约三万多字节，数组方案约八千字节，差距接近四倍。真正的损失还不只是内存：指针随机指向堆上零散的对象，遍历时要到处跳，缓存命中差；数组是一段连续内存，底层可以按固定步长线性扫描，甚至交给硬件做向量化。这就是「为什么科学计算仍能用 Python」的完整答案——Python 这一层只负责描述意图，数据以适合机器的形态躺在内存里。

陷阱拿 sys.getsizeof 比较容器大小，会被坑在哪

你会看到：一万个元素的列表和同长度的数组，getsizeof 报出的字节数相差不大，于是你认定「列表并不比数组费内存」。你的第一反应是「数组的优势被夸大了」。真相是：getsizeof 对容器只算指针数组本身，不算它引用的对象；而数组把数据内嵌在对象里，所以数字看起来接近。判断办法是分开算：列表要加上每个元素的对象开销，数组只需要看 nbytes。想知道共享关系，还要看 base 与 nbytes，单看一个数字容易得出反向结论。

这个对照也解释了为什么 dtype 一旦选定就不该频繁改。数组的数据区是按宽度紧密排布的，想从 float64 换成 float32 必须重新分配并逐元素转换；列表里每个元素本来就是独立对象，换类型只是重新绑定便签。数组用「不可变的布局约定」换来了连续与快速，这个交换在数值计算里几乎总是划算的，但它要求你在建数组时就想清楚类型。

实验记录本机实测：自己把这笔账算一遍
  • 命令：python -c "import sys,numpy as np; lst=[float(i) for i in range(1000)]; arr=np.arange(1000,dtype=np.float64); print(sys.getsizeof(lst), sys.getsizeof(arr), sys.getsizeof(0.0), arr.nbytes)"；
  • 观察：getsizeof(lst) 约 8856，getsizeof(arr) 约 8112，单个浮点对象 24 字节，arr.nbytes 正好 8000；
  • 结论：列表的真实占用要把一千个浮点对象算进去，而 nbytes 给出的才是数组数据区的大小；
  • 这组数字只用于建立直觉，不进清单黄金值——不同解释器实现下对象头大小会变，写进正文当证据即可。

最后提醒一句：nbytes 只算数据区，不算元数据，也不算视图共享的那块原始数据。对视图调用 nbytes 得到的是「看进去的那一块有多少字节」，不是「另外占用了多少内存」。一个覆盖了整个大数组的视图，nbytes 可以很大，实际新增占用却几乎为零；反过来，一个很小的花式索引结果，nbytes 虽小，却是实实在在的新数据。把这层区别记牢，读性能剖析工具的输出时才不会把「看到的字节数」误读成「分配的字节数」。

小结这一节的要点
  • ndarray 是连续数据区加元数据：dtype 定每格宽度，shape 定怎么折成多维，strides 定跨一格要走多少字节；
  • (2,3) 的 float64 数组 strides 是 (24,8)；转置只交换元数据，数据不动；
  • 广播先给短形状左侧补 1，再逐维检查「相等或为 1」，(3,) 的偏置能沿 (2,3) 的第 0 轴复制；
  • a @ b 把循环压到底层库；本单元用固定乘加次数与残差做证据，毫秒数不进黄金值；
  • 切片是视图、.copy() 是副本；改视图会动到原数组，黄金值 view_hit、copy_safe 把这件事钉死。

注自测题答案
  1. float32 每格 4 字节，连续数组按行存放，换一列跨 4 字节、换一行跨 5×4=20 字节，所以 strides 是 (20,4)。转置后形状变成 (5,4)，步长为 (4,20)；数据区一个字节都没有移动，改变的只是元数据里「哪一维算行、哪一维算列」的解释。
  2. 不会成功。(2,) 补成 (1,2) 后与 (2,3) 逐维对齐：第一维 2 对 1 可以复制，第二维 2 对 3 既不相等也不是 1，冲突，NumPy 会抛出形状不匹配的错误。要让它成功，得先把偏置改成 (3,) 或 (1,3)。
  3. 矩阵乘法四项是 1×7+2×9+3×11=58、1×8+2×10+3×12=64、4×7+5×9+6×11=139、4×8+5×10+6×12=154；四项相加得 58+64+139+154=415，即 loop_sum。bias_sum：原矩阵和 21，偏置和 60，两行各加一次，所以 21+2×60=141。ops_loop 是结果四格乘以每格三次乘加，4×3=12。
  4. 不加 copy() 时变，因为切片返回的是视图，view 与原数组共享同一块数据，view[0,0] 写入的就是那块数据的第 0 格。加 copy() 后不变，因为副本另开了数据区，写入只影响新数组。判断方法还可以看 view.base is a，视图为真、副本为假。
  5. 因为浮点加法不满足严格结合律，不同的求和分组与顺序可能让最后几位不同；这次残差恰好为零，是因为选的整数能被 float64 精确表示，任何顺序都得到同一个结果。换成随机小数，残差通常是极小的非零值。diff 只能证明「在这组输入上两条路结果一致」，不能证明实现细节相同。
  6. 因为那行是结构说明，要按文字逐字对账，不是待对账的数值；冒号让它成为普通文字行。写成 a_strides=[24,8] 时，等号左边 a_strides 是符合语法的数值键，而右边 [24,8] 不是合法十进制数，闸门会报 numeric_value_invalid。本单元所有数组与形状一律用冒号打印，就是为了避开这个坑。
