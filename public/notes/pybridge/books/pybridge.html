1.1 先看工程长什么样

这个分册不再从零写数值库，而是把前几册手写的那些实验翻译成框架写法。第一步仍然是看清工程：每个例子都有自己的入口、本地模块和清单，三者缺一不可。入口负责把要展示的数打到屏幕上，模块负责提供可复用的函数，清单负责让流水线真跑一遍并把 stdout 对账。

第 2 帧里新增的是两个 .py 文件：src/main.py 是入口，src/demo.py 是本地模块。第 3 帧再新增 pb01-basics.json，闸门才知道该跑哪个脚本、该去正文的哪个 output 块里对账。注意清单里 sources 的顺序：第一个必须是入口，其余是被 import 的模块；流水线会先对这两个文件做 py_compile 语法检查，再真正执行第一个文件。

你可能会问：两个文件直接放在一个目录里不好吗，为什么非要 src/？这是工程惯例，不是语言规定。把入口和模块收进 src/ 之后，命令仍然是干净的一条 python src/main.py；由于入口脚本所在目录会自动进入 sys.path[0]，同一目录下的 demo.py 就能被直接找到，不需要额外设置路径。代价是你得记住「相对谁解析」这件事——从别的目录运行时要写全路径，或者先把工作目录切到例子目录。

1.2 一行代码背后：解释执行到底多了哪几步

先说结论：C 程序在运行之前已经被翻译成了机器指令，而 Python 程序每次运行都要先把自己翻译成一种中间形式再执行。这不是「Python 慢一点」这么轻描淡写，而是两套完全不同的执行路径。

大白话用大白话先说清这件事

你把同一句计算写在一张纸上。C 的做法是：先把整张纸交给一位翻译官，翻译官逐字读完、查好每个词的意思、把整张纸变成一份机器能直接照做的清单，然后机器拿着清单飞快地干活。Python 的做法是：每次运行时，先有人把这张纸匆匆扫一遍变成短一点的备忘条，然后另一个人拿着备忘条一条一条照做。第二个人每做一条都要再判断一次「这条是什么意思、要用哪个函数」。备忘条比原纸短，但「边看边做」这一步省不掉。严格说，Python 也做编译，只是编译的目标是字节码而不是机器码，而且这份字节码默认不落到你手里。

第 2 帧是 Python 这一侧：源码先被切成 token、建成语法树，再变成字节码，最后由虚拟机逐条取指执行。第 3 帧是 C 这一侧：类型检查、地址计算这些事在编译期就做完了，运行期基本只剩搬数据和算术。把两帧并排看，你就明白为什么同样是一行 printf 或 print，在 C 里是一次函数调用，在 Python 里却要穿过好几层间接。

这里的「虚拟机」不是另一台机器，而是解释器里的一段程序，它模拟出一台执行字节码的机器。字节码也不是给真实 CPU 的指令，而是给这段模拟程序的指令。这一层抽象换来了好处：同一份字节码可以跑在不同平台上，运行时也能改变量的类型、动态的添加属性。代价就是每一次算术都要多做一次分派——先判断对象是什么类型，再决定调用哪段实现。

1.3 动态类型：变量是便签，不是盒子

C 里写 int x = 3;，意思是在栈上划出四字节，把整数 3 的二进制填进去。这里 x 和那四字节是绑死的：盒子多大、里面能放什么，编译期就定了。Python 里写 a = 3，发生的是另一件事：先在堆上造出一个整数对象，再把名字 a 贴到这个对象上。名字不带类型，类型属于对象。

第 2 帧里 getsizeof 报的 28 字节不是「整数 3 占多少空间」的普遍真理，而是本机 CPython 的一个实测读数：对象头、引用计数、类型指针这些固定开销加上一个机器字的数据，凑成了这个数。换一种实现、换一个大整数，读数会变。程序里 int_bytes=28 与 big_bytes=36 两行把这个差异摆在屏幕上：后者是 2**64，超过一个机器字，需要多存一位数据。

这个模型解释了很多初看奇怪的现象。写 a = 3; b = a，在 C 里是把四字节复制到另一个盒子，在 Python 里是把同一张便签贴到同一个对象上——a 和 b 指向的是同一个东西。写一个可变对象（比如列表）时这个差别会咬人：b.append(4) 会同时改变 a 看到的内容，因为两者从头到尾只有一份列表。想真正复制一份，得显式调用 copy() 或切片，这不是「多余的一步」，而是你明确要求另造一个对象。

陷阱把可变对象当值传递，会被坑在哪

你会看到：函数里对参数列表 items.append(x)，函数外面那个列表也跟着多了 x。你的第一反应往往是「参数不是按值传的吗，怎么被调用方改了」；再一想又觉得「Python 是引用传递吧」，于是把所有东西都当成引用去解释。真相是：传进去的是那份引用的副本，函数内外两张便签指向同一个对象；改便签本身（重新赋值）互不影响，改便签指向的对象则双方都看得见。判断的办法只有一条：看操作发生在「便签」上还是「对象」上。

对象模型还带来一个实际后果：对象有生命周期。当最后一个便签被撕掉，对象就没人引用了，CPython 会用引用计数当场回收它。这意味着你可以随手创建临时对象而不必手写 free，但也意味着「看起来还活着」的对象可能随时消失——只要你没把它绑到任何名字上。后面用 NumPy 数组做切片时，这个「谁还引用着谁」的问题会以视图与拷贝的形式再次出现。

1.4 整数与浮点：两套完全不同的语义

现在看这一节最有意思的两个数。第一个是 int_max：程序里写的是 2 ** 64，打印出来是 18446744073709551616。如果你带着 C 的习惯，会以为它该回绕成 0——毕竟 64 位无符号整数装不下更大的数。Python 的 int 不是定宽的，它按需扩展，理论上只受内存限制。所以这里没有溢出，也没有回绕，就是一个精确的大整数。

第二个是 float_sum。程序把 0.1 和 0.2 累加，按六位小数打印是 0.300000；但旁边那行 float_raw:0.30000000000000004 把真面目露出来了。原因不在 Python，而在 IEEE 754 双精度：0.1 和 0.2 都不能被二进制浮点精确表示，它们各自被舍入成最接近的可表示数，相加之后再舍入一次，结果就比十进制的 0.3 多了一点点。这一点点误差在金额计算里会出事，在训练损失里通常被容差吸收。

陷阱拿 == 直接比浮点求和，会被坑在哪

你会看到：0.1 + 0.2 == 0.3 打印 False，而你刚刚手算明明等于 0.3。你可能会怀疑 Python 的加法实现有 bug，或者怀疑自己敲错了数字。真相是：等式两边根本不是同一个二进制数，0.3 这个字面量本身也被舍入过，两个舍入结果不同。正确做法是用容差比较，例如判断绝对值差是否小于一个很小的值——这正是闸门对账时 atol 的作用。注意也不要拿 abs(diff) < 0 这种写法，它永远为假。

这两套语义在深度学习里都有用武之地。任意精度整数让你写循环计数、索引、哈希时不必担心回绕；双精度浮点则是科学计算的主力，它的舍入误差可分析、可控制。真正要小心的是混用：把大整数转成浮点会丢精度，把浮点转成整数会截断而不是四舍五入。NumPy 的 dtype 会把这件事显式化——这是下一单元的主题。

还有一点值得单独说：type() 和 isinstance() 回答的是不同问题。前者问「这个对象的确切类型是什么」，后者问「它是不是某个类型或子类的实例」。在 Python 里，bool 是 int 的子类，所以 isinstance(True, int) 为真，但 type(True) is int 为假。写数值代码时这类细节偶尔会露出来，比如某个布尔值被当成 1 参与算术。读别人的代码时看到这种写法，别急着改，先确认作者是不是有意利用了这个关系。

1.5 缩进与作用域：花括号去哪了

C 用花括号划 block，Python 用缩进。这不是排版偏好，而是语法本身：缩进决定一条语句属于哪个 block，从而决定变量在哪一层可见。demo.py 里的 scoped_count 把这件事演示得很清楚。

第 2 帧里 total 属于 scoped_count 这一层；第 3 帧里 tick 想改它，就必须写 nonlocal total。如果不写，Python 会把 total += 1 里的 total 当成 tick 自己的局部变量，然后报「赋值前引用」。这是初学者几乎必踩的一次坑：读变量时可以向外层找，写变量时默认就在当前层新建。

_ 这个名字也有讲究。它仍然是一个合法变量，只是约定俗成表示「这个值我不用」。在 for _ in range(n) 里，循环变量确实没有被使用，用 _ 是给读者一个信号。别把它当成「丢弃」关键字——它照样绑定最后一个值，只是没人会去读。理解这一点，你就不会奇怪为什么后面写 for _ in values: 时缩进仍然算数。

缩进还有一个实践后果：复制粘贴代码时如果混进了不同宽度的空白，语法检查会在你完全没料到的地方报错。本书一律用四个空格，不用 Tab；ws=visible 这类工具能把空白显示出来，遇到诡异的缩进错误时值得打开看一眼。混用 Tab 与空格在 Python 里是真正的语法错误，不是风格问题。

1.7 慢在哪里：把「解释器开销」落到具体数字

很多人学 Python 的第一印象是「慢」。慢是真的，但笼统地说「慢」没有任何用处，我们要指出慢在哪一层。程序里的 loop_work 做了五十万次极简循环：每次只取一个整数的最低两位并累加。打印出来 loop_ops=500000、loop_odd=250000，前者是循环次数，后者是奇数个数。这两个数是固定的，因此可以作为黄金值对账。

为什么不打印毫秒？因为墙钟时间受机器负载、缓存、调度影响，同一份代码两次运行可能差出百分之几十。用 atol=1e-2 去对账几十毫秒的运行时间，等于什么都没对账；把噪声写进正文还违背了「数字必须可复现」的纪律。这里改用固定计数做证据：它精确、可复现，又足以说明「解释器要为每次循环做一次字节码分派」这个事实。

真实的耗时差异可以从结构上推出来。C 的 for (int i = 0; i < n; ++i) 编译后通常是几条机器指令加一个跳转，整数就放在寄存器里；Python 的 for i in range(n) 每次迭代都要取出下一个对象、判断类型、执行 & 对应的方法、再把结果加到一个新对象上。对象创建与分派是主要开销，算术本身反而是小头。所以优化 Python 数值代码的第一原则不是「少写几层循环」，而是「把循环搬到用 C 或 Fortran 写好的库里去」——这正是 NumPy 存在的理由。

工程惯例工程惯例：为什么先固定计数再谈计时

先把工作量固定成可复现的整数，再在需要性能结论时另做多次测量取中位数，这是数值实验的通行做法，不是语言规定。代价是你得维护两套数字：一套进闸门当黄金值，一套留在实验记录里当性能参考。好处是闸门永远稳定，不会因为某次机器繁忙就误报失败。本分册后续所有单元都遵循这条：耗时类指标一律不进 expect.numbers。

1.8 为什么科学计算仍然选 Python

既然纯 Python 循环这么慢，为什么深度学习领域几乎人手一份 Python？答案不在解释器，而在它背后。NumPy、PyTorch 这类库把真正的大循环写成了编译好的 C、C++ 或 Fortran，Python 这一层只负责描述「做什么」：分配多大的数组、对哪两维做乘法、梯度要不要保留。描述一次，底层跑几亿次。

这套分工的关键在于数据布局。当数据以连续的同类型数组存在时，底层代码可以用指针线性扫描，缓存命中率高，还能调用针对 CPU 指令集优化过的 BLAS。Python 的列表做不到这一点：列表里每个元素都是一个独立对象，类型可以不同，内存也不连续。所以从列表切到数组，不只是「换了个写法」，而是把数据从「一堆对象」变成「一块可以按字节算的内存」。

下一单元会把这件事讲透：数组的 shape、dtype、strides 三个属性分别回答「几维每维多长」「每格是什么类型」「跨一格要走多少字节」。理解了这三个词，你就知道为什么 A @ B 比双层循环快，也知道视图和拷贝的区别从哪来。今天这一节的 int_bytes 与 big_bytes 是铺垫：先看到对象有开销，才容易接受「把数据打包成连续数组」是个重要优化。

1.9 三个常见坑，逐个拆开

第一个坑是把 is 当成 ==。is 比较的是两个名字是不是指向同一个对象，== 比较的是内容是否相等。小的整数在 CPython 里会被缓存，所以 a is b 在小数值上常常为真；大整数不会，于是同一段判断换个数字结果就变。判断数值相等一律用 ==，判断是不是 None 才用 is。

第二个坑是可变对象作为默认参数。写 def f(items=[]): 时，那个空列表在函数定义时就造好了，所有调用共享同一个对象；第一次调用往里加东西，第二次调用就带着旧东西进来。正确写法是默认 None，进函数再造新列表。这个坑之所以隐蔽，是因为它只在多次调用之间才显形，单次测试永远看不出来。

第三个坑是以为异常会自己消失。除零、索引越界、类型不匹配都会抛异常；如果不捕获，程序就带着栈回溯结束，退出码非零，闸门会报 exit_mismatch。本书的例子刻意不捕获异常——让错误当场暴露比悄悄兜住更有利于建立证据纪律。真正要处理异常时，捕获的范围越窄越好，别用一个巨大的 except 把八种错误全吞掉。

陷阱把 print 当成调试终点，会被坑在哪

你会看到：屏幕上打出了 loop_odd=250000，于是认定循环没问题。你的第一反应是「数值对上了，收工」。真相是：打印出来的数只是你让程序打印的数，它可能对，也可能因为索引写错而碰巧对。闸门的价值在于它拿同一份 stdout 与清单黄金值对账，并且用固定种子排除偶然。想真正建立信心，得再问一句「这个数能不能手算核对」——下一节就带你把四个数逐个手算一遍。

1.11 手算核对：四个数不用程序也能验

先看 int_max。2 ** 64 就是 2 自乘 64 次，十进制写开是 18446744073709551616。你可以在纸上用 2**10=1024 做分段：2**60 = (2**10)**6 = 1024**6 = 1152921504606846976，再乘 16 得到上数。过程繁琐但没有任何跳步，所以它是一个合格的黄金值。

再看 loop_odd。range(500000) 产生从 0 到 499999 的整数，其中奇数正好一半，也就是 250000。loop_ops 就是循环次数 500000，两者相加是 500000 的一半与全体，比例刚好一半。float_sum 的手算稍微绕一点：把 0.1 与 0.2 的二进制展开写到足够多位，相加后再舍入，得到比 0.3 略大的那个数；用六位小数打印则两者都显示 0.300000。

int_bytes 与 big_bytes 不能纯手算，它们是 CPython 的实现细节，只能实测。但它们的差有道理：小整数用一个机器字存数据，2**64 需要两个，于是对象多出 8 字节。这个 8 与 28、36 的差正好吻合，说明我们对对象布局的理解没有跑偏。能解释实测数字的差异，比背住数字本身更有价值。

实验记录把黄金值改错一次，看闸门怎么报

建议做一次受控破坏：把清单里 float_sum 的 value 从 0.3 改成 0.5，然后跑 node build/run.js --unit pb01-basics。你会看到 numeric_value_mismatch，日志里同时写出真实 stdout 的值和清单黄金值。再把正文 output 块里 loop_odd=250000 改成别的值，重跑同一条命令，会看到正文与实际对不上。做完记得改回来。这两次失败比十次通过更能说明「正文里的数受清单约束」。

1.12 读图指引：四张图分别该盯什么

这一单元出现四种图元。tree 看带 + 的行，它们标出本节新增的两个源文件与清单；graph 逐帧比较状态差异，第 2 帧比第 1 帧多了解析器和字节码，第 3 帧换成编译路径；memory 看便签与对象的边界，第 3 帧里老对象还在但已经没人引用；calltree 看调用方向，第 3 帧多出的那条边对应 tick 里的 nonlocal。

每一帧都是自包含的。渲染器不会把上一帧的节点自动带到下一帧，打印版里每一帧是独立的一张图，所以第 3 帧里照样把 main() 与 scoped_count(5) 重写一遍。节点文字也刻意压短，因为同一句话在几帧里要重复出现。把图当成分步动画的步骤看，而不是三张互不相干的插图，才能读出「变化」。

最后强调一次证据的分工。正文里的解释负责回答「为什么」，清单和 stdout 负责回答「是多少」。程序自报的任何 PASS 都不算数；exec_mode:interpreted 这行也只是给人看的文字。下一单元我们会把同样的纪律搬到数组上：先看 shape、dtype、strides，再用循环版与向量化版对拍，残差进黄金值。工具变了，纪律没变。

编译器视角解释器视角：字节码到底长什么样
  • 命令：在 examples/ch01/py_basics/ 下执行 python -m dis src/demo.py；
  • 观察：文件级代码以 RESUME 开头，紧接着 LOAD_CONST 取出文档字符串、STORE_NAME 把它绑到 __doc__；import sys 被拆成 LOAD_SMALL_INT、LOAD_CONST、IMPORT_NAME、STORE_NAME 四条指令；

语法规则f-string 的取值格式只记这一处

形式：f"标签={值:.6f}" 生成数值行，f"标签:{值!r}" 生成说明行。前者按六位小数格式化，适合进闸门对账；后者调用 repr 保留完整精度，适合给人看精确打印值。花括号内还能写表达式，例如 f"a_shape:[{a.shape[0]},{a.shape[1]}]"，会在打印时求值。整行不带等号时就是普通文字，不会被当成数值行解析。

1.14 布尔、None 与整数：类型系统的三个边角

第一处边角是布尔值。Python 的 bool 是 int 的子类，True 和 False 在算术里分别表现成 1 和 0。所以 True + True 等于 2，sum([True, False, True]) 等于 2。这不是 bug，而是有意的设计：布尔判断常常和计数混在一起用。写数值代码时如果你不确定某个变量到底是布尔还是整数，用 type() 看一眼，比猜更可靠。

第二处边角是 None。它表示「没有值」，is None 是判断它的标准写法。不要用 == None——自定义类型可以重载相等判断，让一个并非 None 的对象和 None 比出相等。None 在布尔上下文里被当成假，但「被当成假」和「就是假」不是一回事：0、空字符串、空列表同样被当成假，它们彼此之间并不相等。把「是否为 None」和「真值真假」混为一谈，是读代码时容易看漏的一层。

第三处边角是整数除法的分裂。/ 永远返回浮点数，// 才做向下取整的整数除法，% 给出余数。三个数满足 a == (a // b) * b + a % b，对负数也成立，因为 // 是向下取整而不是向零截断。从 C 迁移过来的人最容易在这里踩空：C 里两个 int 相除得到 int，Python 里得到 float。写循环步长或数组索引时，这个差别会让下标变成浮点数，进而在索引时才报错。

工程惯例工程惯例：把类型意图写在变量名和注释里

Python 不要求声明类型，但读者需要知道一个变量大致是什么。给变量起名 n_rows、loss_sum、is_training，比起名 n、s、flag 更能说明意图；关键函数用一行文档字符串写清输入输出，本书的例子都这么做。这是惯例而非语言规定，代价是多敲几个字符，收益是别人（包括几周后的你自己）不用把整个函数读完才能猜出类型。后面用 Tensor 时，shape 与 dtype 会把一部分类型意图显式化，但命名习惯仍然管用。

1.15 把这一单元接到下一单元

这一单元的主线是「同样的数值程序，Python 慢在哪、快在哪」。慢在解释器的逐条分派，快在它能把真正的大循环交给底层库。今天看到的 loop_odd 是一个纯 Python 循环的结果，下一单元会把同一类计算写成数组运算：循环版依旧保留， NumPy 版用 @ 一次算完，两份结果相减得到残差。残差进黄金值，循环次数只作说明。

在读下一单元之前，先带着三个问题：第一，为什么列表里的元素必须各带一个对象头，而数组可以把数据紧紧挨着放？第二，shape 与 strides 之间是什么关系，为什么同一个数组转置之后 strides 会变而数据没动？第三，切片得到的视图和 copy() 得到的副本，改哪一个会动到原数组？这三个问题都能在本节的便签模型和对象开销里找到根：把数据从「一堆对象」变成「一块连续内存」，再让名字以不同方式指向它。

证据纪律也会一起带过去。下一单元的输出里，数组照样用冒号打印成 v:[...]，残差、求和、元素个数这些可复现的量写成 key=value 并进清单；毫秒数仍然不进黄金值。种子固定、真跑取数、黄金值对账这三件事，从 C 分册一路延续到 autograd，只是被对账的对象从点积换成了梯度。

小结这一节的要点
  • Python 每次运行都要先把源码变成字节码再交给虚拟机执行，C 的翻译工作大部分在编译期完成；
  • 变量是贴到对象上的便签，类型属于对象；可变对象被多个名字引用时，改对象大家都看见；
  • int 任意精度不会回绕，float 仍是 IEEE 754，0.1 + 0.2 的精确打印值不是 0.3；
  • 缩进决定作用域，读变量向外找、写变量默认在当前层，nonlocal 用来跨层修改；
  • 数值行走 key=value，数组与说明行走 key:文字，黄金值和容差只写在清单。

2.1 先看工程长什么样

上一单元把数字打成了 key=value，这一单元换成数组。例子仍然守着同一套骨架：一个入口、一个本地模块、一个清单。模块里放四件事——三层循环版矩阵乘法、@ 版矩阵乘法、广播加法、视图与拷贝的检测；入口负责造数据、调用它们、打印对账用的数。

第 2 帧新增的 vectorize.py 是本单元的核心：循环版和框架版放在同一个模块里，才能公平对拍。第 3 帧新增清单，九个黄金值将由它声明。注意入口用 from vectorize import ...，与上一单元 from demo import ... 是同一条规则：入口脚本所在目录自动进入模块搜索路径，所以同目录的模块可以直接导入。

2.2 ndarray 与 C 数组：同一块内存，多了一份说明

C 里写 double a[6]，拿到的是六个连续的 double，编译器知道每个占八字节，数组名在多数场合会退化成指向首元素的指针。NumPy 的 ndarray 把这件事拆成两层：一块连续的数据区和一份描述这块数据该怎么解释的元数据。元数据里最要紧的三项是 shape、dtype、strides。

大白话用大白话先说清这三层元数据

把数组想成一排格子。dtype 告诉你每格里装的是什么、占多宽，比如 float64 就是八字节的浮点数；shape 告诉你这排格子要怎么折成多维，比如 (2,3) 就是两行三列；strides 告诉你「在同一行里往右走一格要跨几个字节」以及「换到下一行要跨几个字节」。C 数组把这些写死在类型里，所以不需要另存；NumPy 的维度是运行时决定的，所以必须把它们显式记下来。同一块数据，换一份 shape 就能换个看法——这正是后面视图与转置的基础。

第 1 帧是物理视角：六个 float64 连续排列，第 k 格距离起点 8k 字节。第 2 帧把 shape=(2,3) 套上去，于是「往右一格」跨 8 字节，「往下一行」跨 24 字节——因为一行有三格，三乘八等于二十四。程序真跑打印的 a_strides:[24,8] 正是这两个数。第 3 帧是转置：数据区还是那六格，但「行」和「列」的解释互换了，所以 strides 变成 (8,24)。

理解 strides 之后，很多看似神秘的现象都变简单了。切片 a[:, ::2] 不复制数据，只把列方向的步长从 8 改成 16；转置不复制数据，只交换两个步长；把数组传给一个 C 扩展时，对方真正需要知道的就是「数据在哪、每维多长、步长多少」。所谓「零拷贝视图」，全部建立在这份元数据可以被改写的前提上。

陷阱以为 strides 一定等于 dtype 大小乘以维度，会被坑在哪

你会看到：一个数组的 shape 是 (3,4)，于是你推断它的第二维步长一定是 8（假设 float64）。你的第一反应是「 stride 还能不是 8 吗」。真相是：只有当数组在内存里连续存放时，这个推断才成立。转置、步长切片、或者从别的数组里取出来的视图，都可能让步长变大、变小，甚至为负。判断办法只有一条：直接打印 a.strides，别拿 shape 反推。本单元把 a_strides 打进 stdout，就是为了让这条判断有证据。

2.3 向量化：把循环交给底层

现在看矩阵乘法。三层 Python 循环版逐格算：外层遍历结果的行，中层遍历结果的列，内层做点积。框架版只写 a @ b。两行代码算的是同一件事，区别在于循环发生在哪一层。

第 1 帧里 py_loop -> scalar 这条边每发生一次，解释器就要判断一次对象类型、分派一次乘法实现；第 2 帧把整段循环压到底层的 BLAS 里，Python 只负责发起和收结果。第 3 帧是对拍：两个版本都算完，逐元素相减，最大绝对差写进 diff。真跑得到 diff=0.000000，说明在这个尺寸上两条路给出的结果一致。

这里要克制一个冲动：别从 diff=0.000000 推出「底层算法和我们的循环完全一样」。浮点求和顺序不同，结果可能差最后几位；这组数字能精确对上，是因为我们选的小整数恰好能被 float64 精确表示。换成随机小数，残差通常是一个极小的非零值——那时它照样能进金色值，只要固定种子保证可复现。

2.4 广播：形状不同也能相加

第三个函数演示广播。数据 a 的形状是 (2,3)，偏置 bias 的形状是 (3,)。两者维度数不同，NumPy 仍然允许相加：它把短形状在左侧补 1，变成 (1,3)，再按「对应维相等或其中一个是 1」的规则逐维对齐，长度为 1 的那一维被当成可沿该轴复制。结果是 (2,3)：偏置被加到每一行上。

第 2 帧里那条边是广播规则的要点：维度长度一个是 2、一个是 1，不冲突，长度为 1 的那维只是「可以复制」。如果换成 (2,) 的偏置去加 (2,3) 的数据，最后一维 2 对 3 既不相等也不是 1，就会立刻抛错。广播不是魔法，它是一组可以逐维检查的规则。

bias_sum=141.000000 可以手算核对。原矩阵六个元素之和是 1+2+3+4+5+6=21，偏置三个数之和是 10+20+30=60，两行各加一次偏置，所以总和是 21 + 2×60 = 141。这个手算把「偏置沿第 0 轴复制了两次」这件事变成了一个可验证的整数。如果你的程序打出别的数，先检查偏置的形状是不是被写成了 (2,)。

2.5 视图与拷贝：改一个会不会动到另一个

切片 a[:, :2] 得到的不是新数组，而是一个视图：它有自己的形状和步长，但数据指针仍指向原来的六个格子。在视图上写 view[0,0] = -999.0，原数组的 [0,0] 也跟着变。调用 .copy() 才会另开一块数据区，此后两边互不影响。

第 2 帧的视图只有两张元数据卡，没有自己的数据；第 3 帧的副本才有独立数据区。真跑打印 view_hit=1 与 copy_safe=1：前者说明改视图确实动到了原数组，后者说明副本里的值仍是原值。两个 1 都是整数黄金值，不受浮点容差影响。

陷阱把切片结果当独立数组，会被坑在哪

2.8 从 C 的数组到 ndarray：概念对照

C 里数组的长度信息常常要额外传一个变量，函数签名写成 void f(const double *x, int n)；NumPy 把长度放进对象里，函数直接读 x.shape。这个差别看似小事，却决定了两层工程实践：C 里维度不匹配往往是静默错误，NumPy 里形状不匹配通常当场抛异常。异常比静默错误好，因为它逼你停下来看。

C 里数组名在传参时退化成指针，函数内部拿不到「这是不是一个独立副本」的信息；NumPy 的视图带着 base 属性，能追出它从哪块数据来。这也是为什么本单元专门用两个整数 view_hit 与 copy_safe 把这件事钉死。把「谁改了谁」写成可复现的数值，而不是一句口头提醒，是这套书从第一册延续下来的证据纪律。

计算路径的差别更根本。C 的循环被编译成机器指令，循环本身就在最快的一层；Python 的循环留在解释器层，只有把数据交给底层库才能跨到快的一层。所以写 Python 数值代码的正确姿势不是「把 C 循环逐行翻译过来」，而是「先想清楚数据布局，再找库里现成的批量操作」。loop_matmul 保留下来是为了对拍和教学，真实项目里应当写 a @ b。

2.10 dtype 不是装饰：宽度、精度与溢出

dtype 决定每格占几个字节、按什么规则解释这些字节。本单元选的是 float64，也就是 IEEE 754 双精度：八字节、约十五到十六位十进制有效数字。把它改成 float32 之后，每格只占四字节，同样一块内存能装下两倍的数据，代价是有效数字降到七位左右，而且累加误差更容易积累。深度学习里 float32 是常态，因为训练对速度敏感、对最后几位不敏感；科学计算里 float64 更常见，因为解的精度本身就是要研究的对象。

整数类型更直接。int8 只有一字节，能表示 -128 到 127；把 100 加 100，结果是 -56，因为它按补码回绕了。NumPy 不会像 Python 的任意精度整数那样自动扩展类型——这一点是 C 的习惯，不是 Python 的习惯。写索引时通常用系统默认的整数类型，宽度足够；但如果你为了省内存把索引数组压成 int8，一旦元素个数超过 127，就会静默错乱。判断是否需要收窄类型，要看数据的取值范围，而不是看内存够不够。

陷阱把 Python 整数的安全感带进 NumPy 数组，会被坑在哪

你会看到：x = np.array([100], dtype=np.int8); y = x + 100 打出 [-56]。你的第一反应是「加法写错了」，或者觉得是打印格式问题。真相是：dtype 一旦定下，运算就按这个宽度做，超出范围按补码回绕；Python 标量的任意精度保护在这里不生效。判断办法是打印 x.dtype 与 x.max() 这类边界值，先确认范围再算。真要避免回绕，就把数组建成更宽的类型，例如 dtype=np.int64。

dtype 还影响跨库交互。把这些数组交给 PyTorch 时，类型要对得上：float64 的 NumPy 数组变成 Tensor 后依然是双精度，而很多网络层默认期待单精度。类型不一致不会总是报错，有时只是悄悄做一次拷贝转换，让性能下降一半却看不出原因。养成习惯：在数据入口处统一打印一次 dtype，就像本单元打印 a_dtype:float64 那样，把约定摆到明面上。

2.11 索引的两种身份：共享数据还是另开一块

索引看起来只有一种写法，实际上分成两类。用整数或切片索引，例如 a[0]、a[:, :2]，得到的是视图：元数据变了，数据还指着原来那块。用整数数组或布尔数组索引，例如 a[[0,1], [0,1]]、a[a > 3]，得到的是新的数组：数据被抽出来重排到一块新内存里。两类结果用起来几乎一样，改起来却完全不同。

实验记录本机实测：三种索引的步长与 base
  • 命令：在本机 python -c 里对 a = np.arange(6, dtype=np.float64).reshape(2,3) 逐项观察；
  • a.strides 是 (24,8)，a.T.strides 是 (8,24)，说明转置只改元数据；
  • a[:, ::2].strides 是 (24,16)，列步长翻倍，说明步长切片同样不复制数据；
  • a.flags.c_contiguous 为真而 a.T.flags.c_contiguous 为假，说明转置后不再按行连续；
  • 花式索引 a[[0,1],[0,1]] 的结果 base 为 None，它确实拿到了一块新数据。

为什么这件事值得写进正文？因为「改一个会不会动到另一个」是数据管道里最常见的隐式耦合。把特征矩阵切片送进归一化函数，函数里就地减去均值，结果原矩阵也被改了——训练时前一批样本的统计量被后一批破坏，这种 bug 极难定位。防御手段不是记住所有规则，而是建立习惯：凡是准备就地修改的数组，先问一句「它是视图吗」，不确定就 .copy()。

负步长切片也值得知道。a[::-1] 得到的视图步长是负的，数据没动，只是从尾部往头部走。很多库对负步长支持不佳，传给 C 扩展时可能被迫复制一份。这不是错误，只是性能上的隐含代价；读到「为什么这段数据突然慢了」时，检查步长是不是负数，往往比看算法更有用。

2.12 内存顺序：C 连续与 F 连续

shape 与 strides 一起决定了数据在内存里的走法。按行存放的数组叫 C 连续，最后一维变化最快；按列存放的叫 F 连续，第一维变化最快。本单元的 a 是 C 连续的，strides=(24,8) 就是证据；转置之后第一维变化最快，变成 F 连续。NumPy 的大多数操作不关心顺序，但把数组交给底层库时，顺序会决定是否要先复制一遍。

这不是抽象的性能焦虑。矩阵乘法里访问 b 的某一列时，如果 b 是 C 连续的，那一列的元素在内存里隔着整行距离，缓存命中差；如果 b 是 F 连续的，那一列恰好连续，访问快得多。底层 BLAS 会针对这一点选择不同的内核，或者要求调用方先做一次转置拷贝。你在 Python 里只写了一行 a @ b，但这些决定已经在底下发生了。

工程惯例工程惯例：在边界处统一内存布局

数据从文件读进来、经过若干切片和转置之后，布局可能已经七零八落。稳妥做法是在交给底层库之前统一一次布局，例如用 np.ascontiguousarray，让拷贝发生在一个可控的位置；代价是多一次内存复制，收益是后续每一步都不必为奇怪的步长付隐性成本。本书例子规模小，看不出差别；真实数据管道里，这一步经常是性能分水岭。

把内存顺序和上一单元的便签模型连起来看，会更清楚：ndarray 的名字、元数据、数据区是三个不同的东西。视图只换元数据，副本才换数据区；转置换的是元数据的解释顺序，内存顺序标志随之改变。一旦你习惯把这三者分开想，广播、切片、转置、拷贝四类操作就不再是四条要背的规则，而是同一套模型的四种用法。

2.13 广播的边界：规则推演而不是试错

广播规则只有两条：短形状在左侧补 1；逐维比较时，长度相等或其中一个为 1 才合法，结果取较大的那个。把这两条写成推演步骤，任何形状组合都能当场判定，不必敲代码试。

例如 (2,1,3) 加 (4,3)：先把后者补成 (1,4,3)；第一维 2 对 1 合法、结果 2；第二维 1 对 4 合法、结果 4；第三维 3 对 3 相等、结果 3；最终形状是 (2,4,3)。再例如 (2,3) 加 (2,)：补成 (1,2)，第一维 2 对 1 合法，第二维 3 对 2 冲突，报错。注意「补 1 在左侧」这条：偏置写到右边才是列向量式的对齐，写到左边往往得到完全不同的结果。

陷阱把广播当成自动纠错，会被坑在哪

你会看到：a + bias 在 bias 形状 (3,) 时成功，换成 (2,) 时抛异常，而两段代码看起来只差一个数字。你的第一反应是「NumPy 怎么有时宽容有时严格」。真相是：广播按规则推演，合法就做、不合法就报，它从不会猜你的意图。判断办法是打印两个形状，按本节两步规则逐维推一遍。若推演发现冲突，就显式 reshape 到期望形状，让错误在 reshape 那一步暴露得更清楚。

广播也不复制数据。它让运算在读取短数组时重复读取同一块内存，逻辑上像复制了若干份，物理上并没有。这个细节在内存紧张时很重要：给一个巨大的矩阵加一个长度为列数的偏置，不会凭空多出一大块内存。但如果后续对这个结果做就地修改，就要小心——结果的形状可能是新的，数据区却是由广播逻辑生成的，某些情况下仍会被底层做成副本。需要确定时，看 np.shares_memory 的判断，不要用肉眼猜。

2.14 求和顺序：残差为什么不一定为零

diff=0.000000 很容易被误读成「两条路完全等价」。浮点加法不满足结合律：(a+b)+c 与 a+(b+c) 可能差最后一位。循环版按 k=0,1,2 的顺序累加；BLAS 可能分块、可能用向量寄存器并行累加，顺序不同。这次残差为零，是因为我们的整数输入都能被双精度精确表示，任何顺序都得到同一个结果。

把输入换成固定种子抽出来的小数，残差通常会变成一个极小的非零值。那时它同样能作为黄金值——只要种子固定，这个残差每次都一样。这正是第三单元要强调的种子纪律：不是让随机数消失，而是让随机过程可复现，从而让噪声也能被对账。想进一步减小误差，可以用 pairwise 求和或补偿求和，但那属于数值分析的专门话题，本册只在需要时点到。

2.15 一个完整的排查故事

假设你改完代码，发现 bias_sum 从 141 变成了别的数。第一步别急着改黄金值，先回到手算：矩阵和 21、偏置和 60、两行各加一次，理论值就是 141。理论值没变而程序变了，说明改动引入了 bug 或对输入动了手脚。第二步读 stdout 的 a_shape:[2,3] 与 a_strides:[24,8]，确认数据布局没被改坏。第三步检查 bias 的形状，看广播是不是把偏置加到了错误的轴上。

如果这些都正常，再看 view_hit 与 copy_safe。这两个整数专门用来发现「某个函数偷偷改了原数组」：如果 view_hit 从 1 变成 0，说明视图共享关系被破坏了，可能是有人在不该 .copy() 的地方复制了；如果 copy_safe 从 1 变成 0，说明副本变成了视图，原数组被写入的风险出现了。把这类关系写成数值并进黄金值，就是把隐式的工程约定变成可机器检查的证据。

最后才轮到改黄金值。只有在你确认数值变化来自「有意修改输入或算法」时，才应该用真跑读数更新清单。顺序反过来——先改黄金值让闸门变绿——等于把证据关掉。这套流程在 C 分册里用来对付点积和范数，在这里用来对付数组与残差，到了 autograd 还会用来对付梯度。工具一直在换，顺序一次都没变。

2.16 把这一单元接到下一单元

这一单元把数据从「一堆对象」变成了「一块连续内存加元数据」，并用三个属性把这块内存解释清楚。下一单元要做的是工程收尾：模块怎么分、种子怎么一起固定、输出怎么只留能对着账的数。你会在那里看到同一条打印纪律再次出现——数组用冒号，数值用等号，黄金值只写在清单。

再往后，Tensor 登场。它保留 shape 与 dtype，添上 device 与 requires_grad。本单元练的 strides 在 Tensor 里仍在，视图与拷贝的陷阱仍在，广播规则也仍在。所以这里的图元不是一次性的插图：第 2 帧那句「换行走 24、换列走 8」，到了 GPU 上只是把内存地址换成显存地址，解释方式一模一样。

2.17 从列表到数组：开销到底省在哪

回到上一单元的 getsizeof。把一千个浮点数装进 Python 列表，再把同样一千个数装进 float64 数组，观察两者。列表本身报约 8856 字节，数组报约 8112 字节——看起来差不多，但这是个陷阱式的读数：sys.getsizeof 数的是列表里那一千个指针加上表头，并不包括指针指向的那些浮点对象。每个浮点对象另外占 24 字节，一千个就是约 24000 字节。数组则是实打实的一块 8000 字节数据区加一点元数据，没有额外的对象。

把三块加起来，列表方案约三万多字节，数组方案约八千字节，差距接近四倍。真正的损失还不只是内存：指针随机指向堆上零散的对象，遍历时要到处跳，缓存命中差；数组是一段连续内存，底层可以按固定步长线性扫描，甚至交给硬件做向量化。这就是「为什么科学计算仍能用 Python」的完整答案——Python 这一层只负责描述意图，数据以适合机器的形态躺在内存里。

陷阱拿 sys.getsizeof 比较容器大小，会被坑在哪

你会看到：一万个元素的列表和同长度的数组，getsizeof 报出的字节数相差不大，于是你认定「列表并不比数组费内存」。你的第一反应是「数组的优势被夸大了」。真相是：getsizeof 对容器只算指针数组本身，不算它引用的对象；而数组把数据内嵌在对象里，所以数字看起来接近。判断办法是分开算：列表要加上每个元素的对象开销，数组只需要看 nbytes。想知道共享关系，还要看 base 与 nbytes，单看一个数字容易得出反向结论。

这个对照也解释了为什么 dtype 一旦选定就不该频繁改。数组的数据区是按宽度紧密排布的，想从 float64 换成 float32 必须重新分配并逐元素转换；列表里每个元素本来就是独立对象，换类型只是重新绑定便签。数组用「不可变的布局约定」换来了连续与快速，这个交换在数值计算里几乎总是划算的，但它要求你在建数组时就想清楚类型。

实验记录本机实测：自己把这笔账算一遍
  • 命令：python -c "import sys,numpy as np; lst=[float(i) for i in range(1000)]; arr=np.arange(1000,dtype=np.float64); print(sys.getsizeof(lst), sys.getsizeof(arr), sys.getsizeof(0.0), arr.nbytes)"；
  • 观察：getsizeof(lst) 约 8856，getsizeof(arr) 约 8112，单个浮点对象 24 字节，arr.nbytes 正好 8000；
  • 结论：列表的真实占用要把一千个浮点对象算进去，而 nbytes 给出的才是数组数据区的大小；
  • 这组数字只用于建立直觉，不进清单黄金值——不同解释器实现下对象头大小会变，写进正文当证据即可。

最后提醒一句：nbytes 只算数据区，不算元数据，也不算视图共享的那块原始数据。对视图调用 nbytes 得到的是「看进去的那一块有多少字节」，不是「另外占用了多少内存」。一个覆盖了整个大数组的视图，nbytes 可以很大，实际新增占用却几乎为零；反过来，一个很小的花式索引结果，nbytes 虽小，却是实实在在的新数据。把这层区别记牢，读性能剖析工具的输出时才不会把「看到的字节数」误读成「分配的字节数」。

  • (2,3) 的 float64 数组 strides 是 (24,8)；转置只交换元数据，数据不动；
  • 广播先给短形状左侧补 1，再逐维检查「相等或为 1」，(3,) 的偏置能沿 (2,3) 的第 0 轴复制；

3.1 先看工程长什么样

这一单元给前两节补工程纪律。例子仍然只有两个 .py，但它们承担的角色更清楚：main.py 是入口，负责读环境变量、调用模块、按固定格式打印；seedutil.py 是本地模块，负责固定种子、抽样、报告依赖版本。清单则把种子钉成环境变量，让闸门每次都在同一个条件下运行。

第 3 帧的清单与前面两个单元有一处关键不同：它多了一个 env 字段，把 PY_SEED 固定为 2024。种子不写在程序里硬编码，而是由闸门注入——这样同一份代码可以跑不同种子，闸门也能用对照种子验证「输出确实来自随机数，而不是写死的常数」。程序里仍然留了默认值 2024，方便你直接执行 python src/main.py 得到同样结果。

这一节的工程结构是后面所有单元的底版。从 PyTorch 那一章起，例子只会更多：同一个模块里既要固定种子，又要搭网络、跑训练循环。但现在把「入口 / 模块 / 清单 / 种子」四件事的位置摆清楚，后面就不会在地上盖楼时才发现地基歪了。

3.2 模块与 import 路径：谁能看见谁

Python 导入模块时，会按一套固定顺序搜索：先查内置模块，再查 sys.path 列出的目录。sys.path 的第一项在脚本直接运行时就是入口脚本所在目录。本单元入口是 src/main.py，于是 src/ 自动进搜索路径，from seedutil import draw 就能找到同目录的 seedutil.py。

第 2 帧的三条边方向一致：入口可以拿本地模块，也可以拿第三方库。第 3 帧特意画出一条不该有的边——模块去导入入口。如果 seedutil.py 里写 from main import SEED，而 main.py 又导入 seedutil，就形成循环导入；轻则拿到一个还没初始化完的值，重则当场报错。正确做法是把种子当参数传进模块函数，让依赖方向保持单向。

大白话用大白话解释 import

把 import 想成「按名字去图书馆借书」。图书馆有几个书架，按固定顺序找：先找随身带的小册子（内置模块），再找当前脚本旁边的书架（sys.path[0]），最后找系统书架（环境里安装的第三方库）。找到就把书里的名字借到当前文件里用。你不会把整本书抄一遍，Python 也不会——它会把加载过的模块缓存起来，第二次 import 直接拿缓存。所以模块里的顶层代码只跑一次，这个性质在固定种子时很重要。

模块缓存还解释了一个实践细节：模块顶层的随机状态只在首次导入时初始化。如果在 seedutil.py 顶层写一句 random.seed(...)，它在导入时就执行了，后续调用 draw 再想换种子，必须重新调用设置函数。本单元把 set_all_seeds 写成显式函数，并在 draw 开头调用它——每次抽样都重新设置，种子从参数来，不依赖导入时机。

3.3 __main__ 守卫：一个文件的两种身份

main.py 最后几行是熟悉的形状：if __name__ == "__main__": main()。它的意思是「只有当这个文件被直接执行时，才调用 main」。当它被别的文件导入时，__name__ 是模块名而不是字符串 "__main__"，守卫里的语句就不执行。

第 1 帧里 stdout 有内容，因为 main() 被调用；第 2、3 帧里没有打印，因为守卫挡住了入口逻辑。这不是文体偏好，而是可复用模块的前提：如果模块顶层直接打印，任何导入它的脚本都会被迫看到那些输出，闸门对账的 stdout 也会被污染。

陷阱把打印语句写在模块顶层，会被坑在哪

你会看到：只是 import seedutil，屏幕上就冒出几行数字；你明明还没调用任何函数。你的第一反应是「导入居然会执行代码」，然后开始怀疑解释器。真相是：模块顶层本来就是可执行代码，import 会把它跑一遍；你写的 print 恰好在那里。判断办法是把所有副作用（打印、写文件、发起网络请求）都收进函数，只在 __main__ 守卫里调用。这样导入是纯的，测试与对账才可控。

守卫还有一个隐藏好处：它让入口文件可以被测试工具导入，然后单独调用 main() 检查行为。虽然本单元没有写测试文件，但结构上已经留出了口子。后面写训练循环时，你会庆幸自己一开始就遵守了这条纪律——否则每次导入模块都会启动一轮训练，调试根本没法进行。

3.4 三种种子一起固定：少一条都不够

本单元的核心纪律在 seedutil.py 里。程序用到了三条随机源：Python 标准库的 random、NumPy 的全局随机状态、PyTorch 的随机状态。只固定一条，其余两条仍然会从系统熵里取初值，每次运行都不一样。

三条设置语句的取模范围不同：numpy 的全局种子常见上限是 2 的 32 次方减一，torch.manual_seed 接受更宽的整数范围。取模保证传入的种子落在合法区间里，即使将来有人从环境变量塞进一个大数也不会报错。函数每次调用都重新设置一遍，这叫「把随机状态握在自己手里」——不管之前谁动过全局状态，抽出来的数都只取决于传入的种子。

第 2 帧的措辞要留意：同一个数字被写进三条独立的状态，但三条流彼此不相干。种子相同不意味着抽出的数相同——py_draw、np_draw、torch_draw 三个数分别是 0.470091、0.588015、0.531716，明显不同。要保证的是「同一种子下三个数各自可复现」，而不是「三条流给出同一个数」。

陷阱只固定一条随机源，会被坑在哪

你会看到：第一次跑出的损失是 0.69，第二次变成 0.71，你怀疑模型不稳定或者学习率太大。你的第一反应是去调超参数，甚至改网络结构。真相是：初始化走 PyTorch 的随机源，数据打乱可能走 NumPy 或 random，少固定一条就多一个漂移来源。判断办法是连续跑两次同种子，逐行比对 stdout；若有差异，先检查三条源是否都固定了，再谈模型。本单元把三个抽样值都打出来，正是为了让这种漂移当场显形。

3.5 种子怎么进程序：环境变量与闸门

种子由环境变量 PY_SEED 传进来。入口第一行从 os.environ 读它，转成整数；如果没设置，就用默认值 2024。清单里的 env 字段保证闸门运行时一定注入 2024，所以无论你本机环境里是否设置过这个变量，闸门的条件都一样。

这条路线有个重要性质：程序不硬编码种子。把它写死成 SEED = 2024 也能得到同样的 stdout，但那样就无法用对照种子验证输出是否真来自随机过程。闸门可以换一个种子再跑一次，要求至少一个数值变化；若结果纹丝不动，说明种子没起作用，程序里的数很可能是常量。这种「对照实验」是把随机数变成证据的关键一步。

  • 命令一：python src/main.py；命令二：PY_SEED=2024 python src/main.py；两次输出逐行一致；
  • 命令三：PY_SEED=7 python src/main.py；py_draw 从 0.470091 变成 0.323833，np_draw 从 0.588015 变成 0.076308，torch_draw 从 0.531716 变成 0.534923；

  • 清单用 env 把 PY_SEED 固定为 2024，所以闸门的对账条件与上面前两条命令一致。

3.6 输出格式：只留能对着账的数

前两节已经反复出现过同一条纪律，这里把它写全。stdout 的每一行要么是 key=value 数值行，要么是普通文字行。数值行的键必须符合简单标识符规则，值必须是有限十进制数；文字行建议写成 key:文字，用冒号与内容隔开。数组、形状、版本号统统走冒号。

语法规则本单元用到的两种行

形式一：py_draw=0.470091。等号左边是合法键，右边是有限小数，闸门按容差对账。形式二：deps:python=...,numpy=...,torch=...。这一行虽然内部有等号，但第一个等号左边的键包含冒号，不符合数值键规则，因此整行按文字逐字比较。要打印数组就写 v:[...]，不要写 v=[...]——后者会被当成数值行，方括号不是合法数值，闸门报 numeric_value_invalid。

check=0.000000 这一行值得多说一句。它的值是 b - (py + npv + tv)，理论上恒为零。它存在的意义不是凑一个黄金值，而是给「浮点加法顺序」留一个自检：如果哪天有人改动了求和顺序，让这个数偏离零，闸门会立刻报变化。一个恒等于零的量也能当证据，前提是它由程序真算出来，而不是写死的 print("check=0.000000")。

依赖版本行 deps: 走的也是同一套逻辑：把三个版本拼成一行文字，逐字对账。为什么不用等号？因为版本号不是十进制数，写成 python=3.14.3 会被当成非法数值行。为什么要有这一行？因为「同一种子在同一版本下才复现」——换了解释器或库版本，随机算法可能变化，同样的种子会抽不同的数。把版本打进 stdout，等于给每次实验贴上标签。

3.7 为什么依赖版本必须记录

随机数是算法，不是玄学。random.random() 用的是 Mersenne Twister，numpy 的全局随机状态有自己的生成器，torch 又有自己的一套。这些实现在库升级时可能调整，甚至同一个版本号在不同编译选项下也有细微差别。只记录种子而不记录版本，等于只记住了「哪一天」而没记住「用哪台机器」——别人拿你的种子复现不出结果，你也无法判断是代码改了还是环境变了。

工程惯例工程惯例：把版本当实验的一部分

写实验记录时，把解释器版本、关键库版本、种子、命令四样东西放在一起，这是可复现研究的基本做法，不是某个框架的规定。代价是每次输出多一行，配置文件多几个字段；收益是半年后回头看，还能知道那串数字是在什么条件下产生的。本单元把版本拼成 deps: 行并进 stdout，就是让这件事自动化：版本变了，这一行先变，闸门的对账会提醒你重新确认黄金值。

版本不只是复现问题，还关系到 API 语义。底层库升级后，某个函数默认参数可能改变，导致数值结果漂移；这种漂移不会报错，只会让黄金值悄悄失配。把版本写进输出之后，你至少能把「失配」与「版本变化」对应起来，而不是盲目怀疑自己的代码。真遇到这种情况，正确做法是先确认版本差异，再重新跑一遍真值并更新清单——绝不能直接改黄金值让它变绿。

本单元的工具链事实写在 build/toolchain.json 的 runners.python 里：解释器的版本写作 3.14.3，由构建期注入正文，不手写数字。程序打印的版本行来自运行时的 __version__ 属性，两者应当一致；如果出现不一致，说明你跑的解释器不是工具链约定的那个，先解决环境问题再谈对账。

后半段只做一件事：按固定顺序打印。顺序也是契约的一部分——闸门按行配对，换了顺序就算数值没变也会报逐字不一致。

3.9 手算核对与对照实验

先核对加法。py_draw + np_draw = 0.470091 + 0.588015 = 1.058106，而程序打出 a=1.058105。这 0.000001 的差不是 bug：程序里先把未舍入的完整精度相加，最后才格式化成六位小数；我们用已经舍入的六位数手算，末位自然可能差一。这正是清单给 atol=1e-6 的原因——容差不是「允许算错」，而是给「先算后舍入」与「先舍入后算」的差别留空间。

再核对 b。用完整精度算出来约 1.589821，与屏幕一致。check 恒为零，因为 b 与括号里的表达式在 Python 里都是同一种左结合顺序；如果把其中一个改成先加后两项，残差可能变成 1e-16 量级，仍在容差内。想亲眼看这个差别，可以把 check 的表达式改成 round(tv + (py + npv) - b, 12)，重跑后会发现它仍然是零——因为 十二位取整把微小残差抹掉了；把 12 改成 16 才会露出来。

实验记录对照种子应该怎样用

把环境变量换成 PY_SEED=7 再跑一次，七个数里除了 check 都会变：种子变成 7，三个抽样值分别是 0.323833、0.076308、0.534923，a 与 b 随之变成 0.400141 与 0.935064。check 不变是合理的，它测的是加法顺序，与种子无关。这个实验说明两件事：第一，种子真的进入了三条随机源；第二，不是所有输出都必须随种子变化，闸门只要求「至少一个数值变化」。如果想把对照实验也纳入自动闸门，可以使用 mode=train 的 seed_contrast 字段，那是后面单元的做法。

3.10 常见坑：从路径到随机状态

第一个坑是在错误的目录运行。清单的工作目录是它自己所在的例子目录，所以 python src/main.py 要在 py_project/ 下执行；从工作区根执行时，要写全路径，并且模块搜索路径会随入口脚本所在目录走。路径问题最阴险的地方是：有时它能跑出结果，只是导入了同名的另一个模块。给模块起通用名字（比如 utils.py）会增加这种风险，本单元用 seedutil.py 这种专名来降低它。

第二个坑是把种子写死在模块顶层。set_all_seeds 必须在每次需要复现的抽样前调用，否则中间若有其他代码消耗了随机数，后续结果就会漂移。本单元在 draw 开头调用它，保证「给我一个种子，我就给你一组确定的数」，与调用历史无关。这种写法在函数式语境里叫显式状态管理，在这里就是一句朴素的建议：不要依赖全局状态碰巧没被改过。

第三个坑是忽略版本行。看到 deps: 变了就以为只是文本变化，不去复核黄金值，等于放弃了版本带来的预警。数值实验里最贵的错误不是程序崩了，而是结果悄悄漂移却没人发现。把版本当信号，是这一节想养成的习惯。

陷阱拿同一个种子跨机器复现，会被坑在哪

你会看到：同事用同样的种子、同样的代码，抽出的三个数与你的不同，于是怀疑他抄错了代码。你的第一反应是「种子明明一样啊」。真相是：种子只固定算法里的初值，算法本身由解释器和库的版本决定；版本不同，同一初值可能走出不同的序列。判断办法是先对比 deps: 行，确认环境一致；再逐行对比 stdout，找出从哪一步开始分叉。这也解释了为什么本单元坚持把版本打进输出，而不是只在文档里写一句「建议版本一致」。

3.11 与前后单元的衔接

回看这一章的三节：第一节回答「Python 为什么会慢、快在哪里」，第二节回答「怎样把数据变成适合机器的形态」，第三节回答「怎样让每次运行都留下可核对的证据」。三节合起来，构成了后面所有框架写法的基础——先把数值算对，再把数据结构摆对，最后把证据钉死。

下一章的 Tensor 会把这三件事接起来。它保留 shape 与 dtype，添上 device 与 requires_grad；随机初始化要用本节的种子纪律，参数更新会产出梯度，而梯度要和手算结果逐项对账。你会发现输出格式仍然一样：张量用冒号打印成 v:[...]，残差、范数、梯度值写成 key=value 进黄金值。换的是被验证的对象，不换的是验证的方式。

如果现在要动手做一个小练习，最好的一个是：把 PY_SEED 换成自己的学号，跑出三个抽样值，再用同种子跑第二遍确认逐值一致；然后把清单里的黄金值改成自己那次读数，跑 node build/run.js --unit pb03-project 看闸门是否通过。这个练习只改几行 JSON，却能让你亲手完成一次「固定种子 → 真跑取数 → 更新证据 → 闸门确认」的完整循环。

3.12 三条随机源各自的脾气

random 模块用的是梅森旋转算法，状态很大但只适合一般用途，不适合密码学。numpy.random.seed 设置的是旧式全局随机状态，历史包袱最重：同一个进程里任何代码调用 np.random.rand() 都会推进它，所以「调用顺序」本身就是实验条件的一部分。较新的写法是创建 np.random.default_rng(seed) 生成器对象，把状态装进对象里，避免全局共享；本单元为了把三条源摆在一起看，保留了全局写法，但你要知道还有更稳的选择。

PyTorch 的 manual_seed 会同时设置 CPU 与所有设备上的随机状态。如果程序用了 CUDA，还需要考虑 cuda 特有的确定性开关；本机的工具链事实只列了 CPU 版本，例子也只在 CPU 上跑，所以暂时不展开。但可以先把原则立住：种子设置要在任何随机初始化之前完成，且要在每次重复实验之前重新设置——只设一次然后连跑两轮，第二轮的状态已经被第一轮消耗掉了。

陷阱在循环外面设置一次种子，会被坑在哪

你会看到：一个训练脚本在循环外调用 set_all_seeds(42)，然后跑五轮实验，五轮的初始损失逐渐变化。你的第一反应是「学习率是不是太大了」，或者怀疑数据里有随时间变化的因素。真相是：种子只在开头设置了一次，每轮实验都会推进三条随机状态，下一轮拿到的初值已经不是 42 对应的那个。判断办法是把设置调用挪进循环内部，或在每轮开始前重新调用一次；本单元的 draw 函数把设置放在函数开头，就是这个道理。

随机状态也是一种全局状态，和 3.2 节说的模块缓存有相似之处：导入模块只执行一次顶层代码，但模块里的全局随机对象会被后续调用不断推进。想写出可复现的程序，最有效的办法是让随机性成为显式输入——函数接收种子，返回确定结果，而不是偷偷读一个藏在模块里的状态。本单元的 draw(seed) 就是这个形状。

3.13 环境变量：字符串、默认值与注入时机

os.environ 里的一切都是字符串。int(os.environ.get("PY_SEED", "2024")) 做了两件事：先取值，取不到就用字符串 "2024" 兜底；再把字符串转成整数。如果环境变量里是空串或字母，转换会抛 ValueError，程序以非零码退出，闸门报 exit_mismatch。想让错误更友好，可以自己写一段检查，把非法值明确报出来；本例子刻意保持极简，让错误当场暴露。

工程惯例工程惯例：默认值与注入并存

程序里留一个默认种子，方便手工执行；清单里用 env 显式注入同一个值，保证闸门条件稳定。这不是重复，而是两道保险：默认值让 python src/main.py 直接可跑，注入让不同机器上跑闸门得到同样的输入。代价是你要在两处维护同一个数字，一旦改了默认值却忘了改清单，闸门就会报数值不符——这其实是好事，它逼你显式确认变更。

注入时机也值得说清。闸门启动子进程时把环境变量写进去，子进程里的 os.environ 就能看到；程序开始运行之后，外部环境再怎么变都不影响这个进程。所以「种子由闸门注入」不是一句抽象的话，而是操作系统层面的一次拷贝：清单里的 JSON 字段变成子进程环境里的一对键值，入口再把它读出来。理解这条链路之后，你就不会奇怪为什么程序不需要任何命令行参数也能拿到种子。

实验记录让注入失败一次，看会发生什么

把清单里 env 的值从 "2024" 改成 "7"，保持程序与正文不动，跑 node build/run.js --unit pb03-project。闸门会报数值不符，因为真实 stdout 里的种子和三个抽样值全变了，而清单黄金值仍是 2024 那一套。这个失败说明清单的 env 真的是实验条件的一部分，不是可有可无的装饰。做完把值改回 "2024"，闸门应恢复通过。

3.14 stdout 是一份接口，不是日志

初学者常把打印当成随手写的调试信息，本单元反过来要求你把它当接口设计。接口有三条约束：行顺序固定、键不重复、数值可解析。行顺序固定是因为闸门按行配对，交换两行就算数值没变也会报不一致；键不重复是因为重复的键会被判为 numeric_key_duplicate，即使两次数值相同也不行；数值可解析是因为方括号、中文、布尔字面量都不是合法数值。

语法规则打印之前先问三个问题

第一问：这一行要不要被闸门对账？要，就用 key=有限小数；不要，就用 key:文字。第二问：这个键在前面出现过吗？出现过就换个名字，或者把多次出现改成训练轨迹那样的专门模式。第三问：值在不同运行里会变吗？会变就先固定种子或改用固定计数，别让噪声进 stdout。三问都过了再写 print，能省掉大量闸门报错后的返工。

check 这行还示范了另一种用法：用它检查程序内部结构是否如你所想。一个恒等于零的量，如果被写成常量打印，闸门照样通过——所以它不能单独作为证据，必须和三个抽样值一起看。三个抽样值来自三条独立随机源，若它们都在变而 check 恒为零，说明加法顺序没被改动；若某个抽样值不再随种子变化，对照实验就会抓住。证据之间互相牵制，比单个数字更重要。

版本行则是「元证据」：它不验证计算结果，而验证计算条件。把条件写进输出，等于给这次实验签名。以后别人拿来一组数字问你「这怎么复现」，你只需把 stdout 与清单一起交出去，条件、结果、容差三样都在。这套纪律在 C 分册里靠工具链占位符与清单实现，到这里多了一行运行时版本，形式变了，目的没变。

3.15 种子与并行：为什么会重新引入不确定性

单线程程序里固定三条随机源已经足够，但真实训练常用多进程数据加载。每个工作进程会从父进程复制随机状态；若所有进程用同一个种子，它们会抽出相同的打乱序列，破坏数据多样性；若各自用系统熵，又失去复现性。常见做法是用基础种子加工作编号派生子种子，例如 seed + worker_id，并在每个工作进程里重新设置三条源。

陷阱以为设了主种子就万事大吉，会被坑在哪

你会看到：主进程种子固定了，但每次训练的损失仍有小幅波动，尤其在使用多进程加载数据时。你的第一反应是「模型对初始化敏感」或者「学习率该调小」。真相是：工作进程各自持有复制来的随机状态，若没有独立派生种子，它们的抽样顺序会随进程调度变化。判断办法是先关掉多进程，看结果是否稳定；稳定就说明问题在数据加载层。本单元不涉及并行，但把三条源显式管理的习惯，到了那里会直接派上用场。

设备差异也会重新引入不确定性。同一份代码在 CPU 与 GPU 上跑，算术顺序、并行归约方式可能不同，最后一几位有差别；某些算子如果不强制确定性算法，甚至会有更明显的差异。本机的工具链事实只列了 CPU 版本的 PyTorch，所以例子里不涉及设备切换。原则仍然适用：换了设备就要重新确认黄金值，别假设种子能抹平所有差异。

3.16 把三节串起来：一份可复现实验的最小骨架

回头看，一个能进闸门的 Python 数值实验只需要四样东西。第一，两个 .py：入口管输入输出，模块管逻辑，依赖单向。第二，一个清单：指定入口、模块、模式、黄金值与容差，必要时用 env 固定外部条件。第三，一段按纪律打印的 stdout：数值行走等号，数组与元信息走冒号。第四，一份正文：把代码从真实文件注入，把输出从真实运行贴入，再用图元和语义块解释「为什么」。

少任何一样都不完整。少了模块，工程无法成长；少了清单，输出没人核对；少了格式纪律，对账会把文字当数值；少了正文，数字即使正确也没人看得懂。这三节分别把四样东西逐件装上，现在它们拼成了一套可以一直用到 autograd 的骨架。下一章的张量实验不会另起炉灶，只会往模块里添函数、往清单里添黄金值、往正文里添图元。

2.1 先看工程长什么样

这一章是全书的分水岭。前四册里所有梯度都是手推出来的：先写前向，再在纸上链式求导，最后把十几行导数塞回 C 代码。从这一单元起，求导这件事交给框架，我们负责的是让它算对，并且证明它算对。

证据纪律一点没变：真运行、真实 stdout、黄金值写在清单里、容差只能写在 expect。变的只是被测对象——现在被测的不是某个 C 函数，而是一张由框架临时搭出来的计算图。

大白话先建立一个画面

把 autograd 想成一个随身记账的会计。你每做一次乘法、每一次加法，它都在小本子上记一笔：「这个数是由哪两个数算出来的，当时用的什么运算」。等你喊一声 backward()，它就顺着这本账倒着走一遍，把「最终结果对每一步中间量的敏感度」算出来。

关键是：它记的是运算，不是公式。你不用提前推导链式法则，只要把前向写对，反向就自动跟着来了。

第 2 帧里带 + 的四行就是这一节的全部新增。manual.py 故意不写一行 PyTorch：它用纯 Python 循环把前向和梯度各算一遍，充当「独立的那把尺子」。main.py 才用张量建图、反向、打印。pb04-autograd.json 把四个黄金值钉在清单里，正文里的数字受它约束。

2.2 Tensor：ndarray 穿上三件外套

如果你写过 NumPy，Tensor 的第一眼几乎一模一样：一块连续的内存，按 shape 解释成多维数组，dtype 决定每格几位。torch.tensor([1.0, 2.0, 3.0]) 和 np.array([1.0, 2.0, 3.0]) 打出来的东西看不出差别。差别藏在三件外套里。

第一件是 shape 参与运算语义。NumPy 的广播规则宽松，(3,) 和 (1,3) 经常能混着用；PyTorch 在矩阵乘法这类运算上更严格，@ 要求维度对得上，错了当场抛异常而不是悄悄广播出一个你没想到的形状。这不是挑剔，而是把「我到底在算什么」提前暴露出来。

第二件是 dtype 会一路传染。整数张量除以整数张量在 PyTorch 里会得到整数结果（或者报错），不会像 Python 标量那样自动升级成浮点。本例里 xs、ws、ts 全部写成带小数点的字面量，就是为了让 dtype 从第一步起就是浮点；否则 w*x-t 的平方会走整数路径，梯度根本无从谈起。

第三件是 device 决定谁来计算。同一份代码在 CPU 张量和 CUDA 张量上写法一样，但两者不能直接相加。本例只用 CPU，你暂时感受不到这件外套的重量；等到模型搬到显卡上，忘记 .to(device) 报错的就是它。

语法规则本单元只用的四种写法
  • torch.tensor(xs, requires_grad=True)：从 Python 列表建张量，并申请「请替我记账」；
  • y = torch.sum((w * x - t) ** 2)：普通算术，但每一步都被记进计算图；
  • y.backward()：从标量 y 出发反向走图，把梯度填进各个叶节点的 .grad；
  • with torch.no_grad():：临时关掉记账，块内运算不进图。
陷阱把 Tensor 当成「能自动求导的 ndarray」就完了

这么想会在两处栽跟头。第一，只有 requires_grad=True 的张量才被记账；你从它派生出来的中间结果自动带 requires_grad，但一个一开始就用普通列表建出来的张量不会有梯度，即使后来参与了运算。第二，浮点 dtype 不会自己升级：torch.tensor([1, 2, 3]) 是整型，对它做 ** 2 仍然是整型，backward() 会直接拒绝——因为整数上不存在导数。你会看到什么？一句 RuntimeError: Only Tensors of floating point and complex dtype can require gradients。你会怎么误判？以为是计算图断了，其实是 dtype 在建张量那一刻就没选对——报错甚至发生在反向之前。真相是：建张量时写 1.0 而不是 1，比事后补 .float() 更不容易漏。

2.2.1 dtype 为什么会一路传染

上一节的 trap 只说了「整型不能求导」，但没说清这件事为什么会发生。PyTorch 的算术运算有一条简单规则：结果 dtype 由参与运算的张量决定，不会像 Python 标量那样自动往「更宽」的方向升级。torch.tensor([1,2,3]) 是 torch.int64，两个 int64 相乘还是 int64，torch.sum 也返回 int64。整条链路上没有一步会偷偷变成浮点。

这条规则在深度学习里是必要的。混用 dtype 意味着每次运算前都要插入隐式转换，既拖慢速度又让内存布局难以预测；框架选择把决定权交给写作者，代价就是你得在建张量那一步想清楚。本例里 xs、ws、ts 三个列表的元素全带小数点，建出来的张量 dtype 就是默认的 torch.float32，从源头上避免了问题。

实验记录亲手触发一次整型报错

把 main.py 里的 xs = [1.0, 2.0, 3.0] 改成 xs = [1, 2, 3]，然后跑 python src/main.py。你会拿到一句 RuntimeError: Only Tensors of floating point and complex dtype can require gradients，而且它发生在 torch.tensor(...) 那一行，反向还没开始。你会怎么误判？以为是计算图写错了、或者 .grad 没分配。真相是整型张量压根不允许 requires_grad，框架在建张量时就拒绝了。修法只有一条：建张量时写 1.0，或者在构造时显式给 dtype=torch.float32。做完把文件改回来，否则清单里的黄金值全对不上。

工程惯例这个坑在真实项目里长什么样

真实项目里 dtype 出错很少这么直白。更常见的是：数据加载器吐出的标签是 int64（分类任务本来就该是），你顺手把它和 float32 的模型输出一起送进损失函数，框架可能报类型不匹配，也可能在某个内部转换后照常跑出一个「看起来还行」的 loss。后者更危险。养成习惯：在模型入口处打印一次 x.dtype 和 y.dtype，确认它们是你以为的样子；本单元的例子虽然小，仍然把 dtype 的选择写死在带小数点的字面量里，就是为了让这件事一眼可见。

requires_grad=True 不是给张量贴个标签，而是给框架一道指令：「从这个张量开始，所有以它为祖先的运算都要留痕」。本例里只有 x 开了这个开关：

w 和 t 没开开关，所以它们是常数：参与运算，但不需要为它们准备梯度槽。这一节刻意这么安排，是为了让对账只盯一个变量。真训练时权重 w 也会开 requires_grad=True，因为要学的正是它——那是下一单元的事。

注意 .grad 在反向之前是 None，不是 0。反向结束后它才变成一个与 x 同形状的张量。这个细节很重要：如果你在循环里反复 backward() 却不清零，梯度会累加。loss.backward() 算出 ∂L/∂x 之后把结果加到已有的 .grad 上，而不是覆盖它。为什么这样设计？因为一次前向可能对应多个损失项，你需要把它们各自的梯度先加起来再做一次更新。代价是训练循环里必须显式 zero_grad()——pb06 会专门讲这一步忘了会怎样。

第 1 帧和第 2 帧的差别只有一处：运算发生之后，小本子上多了 r 与 sq 两条记录。第 3 帧把三维向量压成一个标量 loss——这一步看似平淡，却是 backward() 能工作的前提。框架要求反向的起点是个标量，因为「一个向量对另一个向量求导」在数学上是个雅可比矩阵，框架不会替你默认把它压扁。

陷阱对非标量直接 backward() 会当场拒绝

你可能会想：既然 sq 是个三维向量，为什么不直接 sq.backward()？运行一下会得到 RuntimeError: grad can be implicitly created only for scalar outputs。你会怎么误判？以为是图建错了、中间节点没有 grad_fn。真相是框架不知道你想把三个分量的梯度「合成」成一个数：是求和？加权？还是各算各的？它拒绝猜测，要求你先 torch.sum(sq) 明确写出这个合成方式。所以本例里那句 torch.sum(...) 不只是为了得到 loss，也是在告诉反向「从哪个标量开始走」。

2.3.1 动态图：每次前向都重新搭一遍

PyTorch 的计算图是动态的：它不是在编译期定死的一张网，而是每次执行前向代码时现搭，反向走完之后就被丢弃。同一个变量下一次进前向，会生成一张全新的图，节点编号和上次毫无关系。这一点和 C 手写梯度形成鲜明对照——后者把导数公式编译进可执行文件，想改结构就得重新编译。

动态带来两个直接好处。第一，你的前向代码里可以写 Python 的 if、for、甚至打印语句，图会照着这次实际走的那条分支搭出来。一个按 batch 大小改变层数的网络，在静态图框架里要写两套符号表达，在这里只是普通的 Python 分支。第二，调试时你可以随时在某个中间节点上 print(y.shape)，看到的正是即将被记账的那个张量，不需要借助专门的调试器。

代价也有两条。第一是开销：每一次前向都要重新申请节点、记录运算，这部分时间在小程序里可以忽略，在每层都被调用上千次的模型里却很可观。第二是「图用完即弃」带来的纪律：你不能把上一次前向留下的 y 或 grad_fn 留到下一次用，因为它们指向的是旧图。训练循环里每一轮都从零开始算前向、算 loss、调 backward()，正是这个原因。

工程惯例动态图对实验意味着什么

对写实验的人而言，动态图最大的价值是「所见即所得」。本单元里 y 是什么、y.grad_fn 长什么样，你在 backward() 之前打一行 print 就能看到；不像静态图那样要先建会话、再喂数据、最后取结果。本书坚持让每个例子都把中间量打到 stdout，正是借了这个便利——正文里每一个数字都能在一次普通脚本运行里复现，不需要额外的图执行器。代价是这套机制依赖 Python 解释器实时跑，性能上限不如预先编译好的静态图，这也是后续工程里要用 torch.compile 之类工具的根本原因。

2.4 前向怎么记，反向就怎么走

现在把账本倒着读一遍。前向是 x → r → sq → loss，反向就是从 loss 出发，沿着相反的边一步步把敏感度传回去。每一步用的规则，恰好是前向那一步的局部导数。

记 r = w·x - t，sq = r²，loss = Σ sq。从后往前三句话就能推完：

  • ∂loss/∂sq = 1：求和函数对每个输入的偏导都是 1，这是 sum 这条边的局部导数；
  • ∂sq/∂r = 2r：平方的导数是两倍自身，所以传回残差的敏感度是 1 × 2r = 2r；
  • ∂r/∂x = w：因为 w 是常数，w·x-t 对 x 的导数是 w，逐元素相乘。

乘起来就是 ∂loss/∂x = 2·w·(w·x - t)。注意每一条边的局部导数只依赖前向时的输入值，不需要重新跑一遍函数——这正是计算图省下的东西。

第 3 帧的 x_grad 就是最终答案。对照第 2.3 节的前向图你能看到一件很舒服的事：反向完全照着前向的边走，只是方向相反、乘的因子换成局部导数。这条对称性不是巧合，链式法则本来就是这么说的。

工程惯例为什么中间结果不直接存梯度

你可能会问，既然 r 和 sq 也有 requires_grad，为什么程序只打印 x.grad？因为框架默认只为叶节点保留 .grad。中间节点的梯度算完就传下去，用完即弃，省内存。如果你真的想看某一层中间量的梯度，得显式调用 r.retain_grad()。在几层的小网络里这点内存无所谓，但真实模型有上亿个中间量，全都存下来会直接撑爆显存——这是框架做这个取舍的原因。

还有一层考虑：保留中间梯度会诱导你把它当成「可以拿去更新」的东西，但真正需要更新的只有参数。框架把 .grad 限制在叶节点上，等于用接口提醒你「该动的是谁」。本例里 x 恰好是需要求导的输入；换成训练时，叶节点会是权重和偏置。想清楚这一点，你读 optimizer.step() 的代码时就不会奇怪它为什么只遍历 parameters()。

梯度向量是 (-0.5, 4, 16)，它的范数 √(0.25+16+256) = √272.25 = 16.5——恰好是个有限小数，这不是巧合，而是这组数据挑得好。正文里打印的 manual 和 auto 都是这个范数：把一个向量压成标量，才好放进清单做数值对账。

2.5.1 三种梯度来源，三种可信度

把视野拉开一点，求梯度其实有三条独立的路，它们的可信度和代价各不相同。

第一条是解析梯度：人根据链式法则推导出闭式公式，再照着写进代码。manual.py 的 grad_x 就是这一类。它的优点是精确、快，缺点是公式一复杂就容易漏项——dlmath 分册里那个漏掉的 y(1-y) 因子就是活生生的例子。它适合当「参照答案」，但不适合独立承担正确性。

第二条是数值梯度：把第 i 个分量加一个很小的扰动 ε，算一次损失；再减 ε，算一次；斜率 (L₊-L₋)/(2ε) 就是偏导的近似。它不需要任何链式法则，思路简单到几乎不可能推错，所以常被叫作「明显正确的暴力版」。代价是慢：每个参数要跑两次前向，13 个参数就是 26 次；并且 ε 选得太小会被浮点舍入淹没，太大又引入截断误差。

第三条是autograd：沿计算图反向走，每条边乘上局部导数。它把前两条的优点合起来——比数值梯度快得多，又不需要人手写公式。但它不是独立的证据：如果前向写错了，它照样忠实地给错梯度的梯度。这就是为什么本单元要保留 manual.py。

实验记录为什么清单里写 diff 而不是写 PASS

把三条路的角色对上清单你就能看出设计意图：manual 是解析梯度，auto 是 autograd 结果，diff 是两者之差，黄金值都是真跑读数。闸门检查的是 |manual-auto| ≤ atol，也就是两条独立路径必须重合到小数点后六位。如果程序自己在末尾打一句 PASS，闸门看都不会看——它只认 stdout 里的数值行。这条「程序自报不算证据」的纪律在 dlmath 分册就立下了，Python 这边原样继承。

2.6.1 打印格式的纪律：等号、冒号与有效位

这一节的输出块看起来不起眼，其实每一行都是按规则设计过的。标量一律 key=0.123456：键名只含字母、数字、点、方括号、下划线与连字符，值必须是有限十进制数。这样的行才会被闸门解析成数值行，才有资格谈 atol。张量一律 v:[...]，冒号让整行落到「普通文字」通道，逐字比较即可。

为什么要分两条通道？因为数值对账需要知道「哪个数是哪个量」以及「允许多大误差」，而一个向量同时包含方向和大小，把它拆成三个 g_0=...、g_1=...、g_2=... 当然也能对账，但读者就看不到「这是一个三维梯度」的结构了。冒号行保留了结构，范数行保留了精度，二者互补。

有效位数也有讲究。程序统一用 %.6f 打印，而不是 Python 默认的 str(float)。原因有三：一是格式稳定，不会因为某个值恰好是整数就打 16.5 而另一个打成 16.5000001；二是stdout 里每行长度一致，便于逐行对账和日志阅读；三是六位小数对 atol=1e-6 的量级刚好够用——再多就是噪音，再少就掩盖差异。记住这条：打印精度要和容差配套，容差 1e-6 却只打三位小数，对账就成了摆设。

陷阱把布尔值也打进数值行会怎样

有人会把 x.is_leaf 直接写成 print("leaf=", x.is_leaf)，stdout 变成 leaf= True。前面那个键是合法的，但值 True 不是合法有限小数，闸门会报 numeric_value_invalid，整条清单失败。本例把三个布尔量塞进 flags:[leaf=1,...] 这个冒号行里，就是为了让它们走文字通道；%d 把 True 转成 1、False 转成 0，读起来仍然清楚。你会怎么误判？以为是闸门太严格。真相是闸门必须拒绝一切无法比较的「数值」，否则 nan、inf、布尔值混进来，|actual-expected| 的比较就失去意义。

2.7 叶节点、非叶节点与 no_grad

最后一行 flags:[leaf=1,nonleaf=0,frozen=0] 挤进了三个布尔事实，值得单独拆开。x 是你亲手建出来的，requires_grad=True，没有 grad_fn——它是叶节点。y 是算出来的，带着 grad_fn=<SumBackward0>——它是非叶节点。而 frozen 是在 with torch.no_grad(): 里由 y*2 得到的，既没有 grad_fn，requires_grad 也是假。

这三身份的区分不是学术分类，它直接决定你会不会踩坑。只有叶节点的 .grad 会被填充；对非叶节点读 .grad 会得到 None。而 no_grad() 的用处有两条：一是做推理时省掉记账开销——你不打算反向，记那些账纯属浪费时间和内存；二是明确告诉框架「这几个量当常数看」，避免它们意外把梯度一路传回你不能更新的东西。

陷阱以为 no_grad 里的结果还能反向

最常见的误用是这样：先 with torch.no_grad(): z = x * 2，出了块之后想 z.backward()。你会看到 RuntimeError: element 0 of tensors does not require grad。你会怎么误判？以为是 x 的 requires_grad 被块改掉了。真相是 x 一点没变，变的是 z——块内所有运算都不记账，z 从出生起就不带 grad_fn，反向链路在它这里断了。要修就得把 z 放回块外重新算。这个错在推理代码里尤其常见：有人为了省内存把预处理也塞进 no_grad，结果发现模型根本学不动。

工程惯例什么时候该用 no_grad，什么时候不该

一个简单判据：这一步的结果要不要参与反向。训练时的前向、loss 计算、反向都在记账范围内，不能包 no_grad；而验证集上的 loss 统计、把张量转成 NumPy 打印、构造不需要学习的常数标签，都该包进去。代价是你要多写一行 with，换来的是显存与速度。别为了「看起来专业」到处加 no_grad——加错位置的症状是梯度莫名其妙变成 None，排查起来比重写一行费劲得多。

读多帧图时有两条硬规矩。第一，每一帧自包含：渲染器不会把上一帧的节点自动带过来，所以第 2 帧里仍然成立的 x、w 都要重写一遍，纸面上每帧都是独立的图。第二，节点文字不超过十八个字，箭头两边必须留空格——x -> r 才会被画成一条边，写成 x->r 就只是普通文字。这些约束看着繁琐，但它们保证同一份围栏在单页 HTML、合书、打印 PDF 里长得一模一样。

2.9 与那一册手写梯度的对照：代价换来了什么

工程惯例把三道体检平移过来

dlmath 那册立了三条规矩：数值黄金值查前向、梯度对拍查导数、种子与收敛查训练。这一单元完成了前两条：前向的 loss 是黄金值，梯度的 manual 与 auto 互为对拍。第三条要等到 pb06 的训练循环才齐。注意本单元没用 mode=gradient——那是 C/C++ 专用，靠编译期注入错误梯度的阴性对照来判别；Python 这边把解析梯度、autograd 梯度和残差都当黄金值对账，阴性对照的角色改由「手算模块完全不 import torch」这层独立性来承担。

2.9.1 当梯度变成 nan：三种典型原因

真正上手之后，你迟早会遇到 loss 打出 nan 的时刻。数值行里出现 nan 会被闸门判成 numeric_value_invalid，因为 NaN 不是有限十进制数——这是好事，它逼你停下来查，而不是让一张看似正常的表格混过去。这里先列出三种最常见的原因，方便你按图索骥。

第一种是数据里本来就有非有限数。输入含 nan 或 inf，任何运算都会把它传染下去：nan 参与加法还是 nan，inf - inf 也是 nan。查法是在建张量之后立刻打一行 torch.isfinite(x).all()，别等到 loss 出来才追。第二种是除零或开方负数。比如自己写 softmax 时分母可能为零，或者手写方差时 x 全相等导致标准差为零。PyTorch 对整数除零会抛异常，对浮点除零则安静地给出 inf——后者更危险。第三种是学习率过大导致参数爆炸：权重指数增长直到溢出成 inf，接着 inf - inf 把 loss 变成 nan。这种情况通常出现在训练若干步之后，而不是第一步。

工程惯例用最小脚本定位非有限数

怀疑某个张量有问题时，不要整套重跑。把前向拆开，在每个中间量后面插一句 print(name, torch.isfinite(t).all().item(), t.dtype)，先跑一次。输出会告诉你第一次出现 False 的位置。若连输入都是 False，问题在数据源；若输入正常而某个中间量变 False，问题就在那一步运算或它前面的运算。非有限数具有传染性，定位要找最早出现的位置，而不是最后打印出的 loss=nan 那一行。

陷阱用等号判断 nan 永远不成立

有人会写 if x == float('nan'): 来判断，结果永远进不去分支——IEEE754 规定 nan != nan。要用 torch.isnan(x) 或 math.isnan(x)。同样地，inf 虽然能用 == 比，但更稳的是 torch.isinf。这个坑在 C 分册讲浮点时就出现过，到了 Python 加上张量之后并没有消失，只是换了一层 API。闸门的 numeric_value_invalid 正是替你把最后一道关：只要 stdout 里出现 nan=... 或 loss=nan，整份证据直接作废。

2.10.1 一张可以照着做的排查清单

把这一节所有纪律压缩成六步，下次梯度不对时按顺序过一遍，能省掉大量瞎猜。

第一步，确认 dtype：所有要进计算图的浮点张量都应是 torch.float32 或更高，别让整型混进来。第二步，确认起点：打印 requires_grad 与 is_leaf，你要反向的那个量必须是叶节点且开关打开。第三步，确认图没断：在 loss 之前打印 y.grad_fn，它是 None 说明中间某处被 no_grad 包住了。第四步，确认反向起点是标量：打印 y.shape，它是 () 或含一维才安全，三维向量必须先 sum。第五步，确认梯度不是累加的结果：在 backward() 前打印 x.grad，第一次应为 None；若在循环里，先清零。第六步，拿独立尺子量：manual.py 那种纯 Python 实现给出的范数应当和 auto 在六位小数上一致。

这六步没有一步需要读框架源码，全是能在一次普通脚本运行里验证的观察量。把它们写进习惯，比记住某个报错文本更有用——报错文本会随版本变，但这六个问题不会。

工程惯例为什么把排查写成清单而不是讲原理

原理层面，「梯度不对」永远可以归结为「前向写错」或「图没建对」两句话，听完还是不知道该敲哪条命令。清单的价值在于把它翻译成可执行的动作，每步都有一个能打印的量和一个明确的预期。这也是本书反复坚持「数字要真跑、输出要贴原文」的原因：一个能打印出来的中间量，比一段口头解释更能定位问题。代价是你得多写几行 print，但比起追一整个下午的 bug，这点成本可以忽略。

下一单元把这套机制用到一个真正的两层网络上：2→3→1，tanh 加 sigmoid，13 个参数全交给 autograd。你会看到 loss.backward() 一行取代了那一页手推公式，同时 gradcheck_residual 仍然把梯度数值摆出来给人看——框架接管了求导，但证据纪律一点没松。

小结这一节的要点
  • Tensor 是带 shape、dtype、device 的 ndarray；建张量时写 1.0 而不是 1，避免整数路径上无法求导；
  • requires_grad=True 让运算留痕形成计算图；叶节点保留 .grad，非叶节点只持有 grad_fn；
  • backward() 必须从标量出发，梯度累加而非覆盖，所以训练循环里要显式清零；
  • 手算 ∂L/∂x = 2w(wx-t) 与 autograd 逐项相符：manual=auto=16.5、diff=0；
  • 标量打印成 key=value 才享受容差，张量打冒号 g:[...] 走逐字对账；容差只写在清单。

四个张量放在一个元组 params 里传进函数。这是本例的取舍：真实项目会用 nn.Module 把它们注册成可遍历的参数列表（parameters()），那是 pb07 的内容。现在用元组，好处是你能一眼看到「这个网络就这四个东西」，代价是每次要解包一次 w1, b1, w2, b2 = params。

陷阱把参数元组当成不可变对象就不会出错

元组本身不可变，但里面的张量可变。中心差分那段会临时改参数值算两次 loss，如果不包在 torch.no_grad() 里，PyTorch 会报 a leaf Variable that requires grad is being used in an in-place operation。你会怎么误判？以为是元组不该被修改。真相是它是对的：叶节点不允许被原地改动，因为那会让已建好的计算图指向一个被改过的值。修法是把扰动整段放进 no_grad()，让这些修改不进图；算完再恢复原值。pb06 里优化器更新参数走的也是同一条规则。

3.2.1 为什么先用元组，而不是直接上 nn.Module

看到 params 这个四元组，熟悉 PyTorch 的人可能会问：为什么不写成 class TinyNet(nn.Module)，让框架自己注册参数？答案是教学顺序。本单元的目标是让你看清「13 个参数究竟是什么、反向到底落在谁身上」；一个四元组把这件事摊在桌面上，每个张量的形状、dtype、是否需要梯度都写在 make_params 里，一眼可查。

换成 nn.Module 之后，参数会被收进一个有序字典，parameters() 返回一个生成器；你不再是「看见」参数，而是「遍历」参数。这对大模型是必需的——一个 Transformer 有几百个张量，手写元组根本不现实——但它同时把 13 这个数字藏进了类的定义里。所以本书的顺序是先用元组把机制讲透，到 pb07 再引入模块类，那时你会清楚框架替你收走的到底是什么。

代价也要说清：元组不提供 parameters()，所以优化器暂时用不上；本单元没有训练，只需要手工读 .grad，这个缺口不妨碍教学。下一单元要训练时，我们会继续用一个轻量的参数列表，等到 pb07 才换成正式的模块接口。

工程惯例四个张量的顺序是契约

forward 里第一行就解包 w1, b1, w2, b2 = params，main.py 里又用 params[3].grad 取 b2 的梯度。这个顺序一旦改了而别处没跟着改，程序不会报错——四个张量的形状有重叠（长度三的 b1 和 w2 尤其像），解包错了照样能算出前向，只是结果毫无意义。工程上更稳的做法是给参数起名字、用字典存放，但那样要多写几行。本例选择元组，是用「顺序固定」换「代码短」，并在正文里把顺序反复写清楚。你要是自己改这个例子，务必同时改三处：make_params 的返回、forward 的解包、main.py 的下标。

3.3.1 两个激活函数的链式因子各管什么

这个网络用了两种激活函数，它们各贡献一个最容易算错的局部导数。

隐层的 tanh 导数是 1-h²。它的形状很讨喜：输出 h 已经在 (-1,1) 里，所以 h² 在 [0,1)，导数落在 (0,1]，最大是 h=0 时的 1。当隐元饱和到接近 ±1 时导数趋近零，上游传来的误差被压扁，这个隐元就「学不动」了。本例的初值温和，三个 h 大约是 -0.51、-0.56、0.44，都不在饱和区，所以梯度健康。

输出层的 sigmoid 导数是 y(1-y)。同样地，y 在 (0,1)，导数最大是 y=0.5 时的 0.25，两端都趋近零。本例 y≈0.58，因子约 0.244，接近最大值，梯度传得回来。换一个目标让 s 很大，y 逼到 0.999，因子只剩千分之一，学习就慢下来了——这就是梯度消失在最简网络里的样子。

陷阱把激活函数的导数当成常数

有人看到 tanh 的导数是 1-h²，就随手写成 1-h；或者把 sigmoid 的 y(1-y) 记成 y。这类错误在手写版本里会直接让梯度表对不上，但在 autograd 版本里不会发生——框架从算子注册表里读出精确公式。这是否意味着你可以完全不懂这些因子？不是。当 loss 不下降、需要判断是不是饱和导致时，你还是得知道每个激活函数的导数长什么样。框架替你算，不替你诊断。

工程惯例为什么输出层选 sigmoid 而不是 tanh

因为任务被定义成「预测一个 0 到 1 之间的数」，目标 0.8 就在这个区间。sigmoid 把整个实数轴压进这个区间，输出天然可解释成概率或比例。隐层用 tanh 则是因为它以零为中心，均值接近零的激活更利于下一层学习——如果隐层也用 sigmoid，输出全为正，下一层的权重更新方向会高度相关，收敛变慢。这不是硬性规定，而是经验惯例：二分类输出常用 sigmoid，隐层常用 tanh 或 ReLU。代价是要记住两套导数公式。

3.4 同一组初值：把 C 的 LCG 复刻到 Python

要让两边的数字可比，必须让 13 个权重完全相同。C 版本用的是一个 32 位 LCG：

三个地方必须和 C 一模一样，错一个数字就全盘对不上。

第一，乘法常数 1664525 与加法常数 1013904223，以及每次都要 & 0xFFFFFFFF 模拟 32 位无符号回绕。Python 的整数是任意精度，不显式截断的话几步之后就会长成一个巨大的数，和 C 的 uint32_t 分道扬镳。

第二，取随机数的办法是 (state >> 8) / 16777216.0。右移八位等于砍掉低八位，留下 24 位，除以 2²⁴ 得到 [0,1) 区间的数；再乘 2 减 1 变成 (-1,1) 的权重。这里 >> 的位数和除法的分母是一对，改一个就得改另一个。

第三，也是最容易错的：调用顺序。C 版本先按 i 外层、j 内层填满六个 w1，然后循环三次、每轮依次取一个 b1[j] 和一个 w2[j]，最后取 b2。如果图省事把三个 b1 连续取完再取三个 w2，前面六个值不变，后面六个值就全错位了。本单元初写时就在这一处踩过坑：前向打出 y=0.797078，和 C 的 0.580931 差了一大截；逐值打印权重才发现 b1 和 w2 的取值交错被写成了分段。

实验记录对照两边的前向数字

C 版本真跑（种子 12345、输入 (0.5,-0.3)、目标 0.8）给出 y=0.580931、loss=0.023996。本节 Python 版本真跑给出完全相同的两个数，误差在打印的六位小数里为零。这不是巧合，而是上面三个细节都对上了的结果。想亲手验证，可以在 net.py 里把 c_lcg_weights 的返回值逐个打印，再去对照 C 版本 net_init 后的结构体——13 个数应当逐位相同。

陷阱用 torch.manual_seed 代替复刻 LCG 会怎样

有人会说：既然固定了 torch.manual_seed(12345)，直接用 torch.randn 初始化不也一样可复现吗？可复现是对了，可比性却没了。PyTorch 的随机数生成器是 Mersenne Twister 的一套实现，和 C 里那个 LCG 毫无关系；同种子给出的是另一组 13 个数，于是 y 变成另一个值，你没法判断差多少是「初始化不同」、差多少是「反向写错」。本例仍然调用 torch.manual_seed(12345)——那是纪律，保证未来加入的任何随机环节可复现——但 13 个权重由 LCG 显式给出，专门服务于逐位对照。

3.4.1 为什么不用 rand()：可复现的第一课

C 分册从一开始就拒绝 rand()，理由写得很直白：它的序列由 C 运行库决定，换个机器、换种编译器就可能不同。同一份源码在作者机器上跑出 y=0.580931，在读者机器上可能变成 0.61，而两边都「没错」——这种实验是没有价值的。LCG 只有五行代码，乘一个常数加一个常数再截断，任何语言都能逐位复刻。

Python 的 random 模块比 C 的 rand() 好一些，它用 Mersenne Twister，同种子跨机器通常一致；NumPy 与 PyTorch 也各有自己的生成器。问题在于三者互不相通：random.seed(12345)、np.random.seed(12345)、torch.manual_seed(12345) 各自初始化三条独立的随机流。pb03 立下的纪律就是「三种种子一起固定」，因为一个程序可能同时从三处取随机数，漏掉任何一处都会让结果漂移。

本例更进一步：干脆不靠任何库的随机源生成权重，而是把 C 的 LCG 逐行搬过来。这样连「PyTorch 版本升级后随机算法变了」这种风险都绕开了。代价是这段代码看起来和深度学习毫无关系——它的存在意义不是「怎么初始化权重」，而是「怎样让两个实现真的可比」。pb06 会回到常规做法：三种种子一起固定，让 DataLoader 的打乱顺序也可复现。

实验记录亲手验证跨实现的一致性

在 Python 里把 c_lcg_weights(12345) 的 13 个数打出来，再在 C 分册的 net_init 后面插一段 printf，把结构体的 13 个字段按同样顺序打出来。两边逐位对照，应该全部相同。若有任何一个不同，先查 >>8 与除数的配对，再查 b1/w2 的交错顺序——这两处占了此类错误的大多数。做完把 C 的调试代码删掉，不要污染参考实现。

3.5 loss.backward() 替你做了什么

把 13 个叶节点、四步前向、一个 loss 接好之后，只需要一句 loss.backward()。它做的事可以拆成三步：

  1. 从 loss 这个标量出发，找到它的 grad_fn；
  2. 沿 grad_fn 指向的运算一步步倒走，每条边乘上该运算的局部导数；
  3. 把最终落到每个叶节点的值累加进它的 .grad。

dlmath 分册里那一页手推，核心就是这四个偏导式子：∂L/∂y = y-t、∂L/∂s = (y-t)·y(1-y)、∂L/∂w2ⱼ = (∂L/∂s)·hⱼ、∂L/∂hⱼ = (∂L/∂s)·w2ⱼ，再乘 1-hⱼ² 分给 w1 和 b1。它们现在全部由框架从记账本里读出来，你一行都不用写。

第 2 帧里那条 loss -> s 的边乘的正是 y(1-y)——dlmath 分册反复强调「最容易漏的因子」。框架不会漏，因为它把 torch.sigmoid 的局部导数写在了算子里。但框架也不会替你检查 loss 是不是算对：如果你把 0.5*(y-t)² 写成 (y-t)²，backward() 照样精确地把梯度放大两倍，它忠实地给「错误的函数」求导。这就是下一节必须对拍的理由。

工程惯例一行代码省下的是什么

省下的不只是打字量。手推版本里，改一个激活函数就要重推所有下游导数，漏一项肉眼几乎看不出来；autograd 版本里，你把 torch.tanh 换成 torch.relu，反向自动跟着变。代价是可读性的转移：以前推导过程写在纸上、能逐行审；现在它藏在 grad_fn 链里，你只能靠对拍间接验证。本例保留中心差分那条独立路径，正是为了把这失去的一层补回来。

3.5.1 梯度会累加：为什么训练前必须清零

backward() 把算出的梯度加进 .grad，而不是覆盖它。本例只调了一次，看不出这个性质；但下一单元的训练循环会反复调用 backward()，如果不在每步之前清零，第二次的 .grad 就是两步梯度之和，更新步长翻倍，模型很快发散。

为什么要设计成累加？因为一个 batch 的损失常常由多个项组成，你可能想分别算它们的梯度再合并。比如主损失加正则项：先 loss_main.backward()，再 loss_reg.backward()，两者的梯度自然叠加进同一组参数。如果设计成覆盖，你就得自己把两项加进一个 loss 再一次反向——大多数时候这没问题，但有些场景（比如梯度来自不同计算分支、无法合成一个标量）就做不到了。

代价是每一轮训练都得记得清零。框架把它做成了显式操作 optimizer.zero_grad()，而不是悄悄替你做——因为「何时清零」本来就是实验设计的一部分，不该由库猜。pb06 会把这一步放进训练循环的四步里，并用固定种子的轨迹证明「忘了清零」和「清零了」给出两条不同的 loss 曲线。这个设计初看别扭，用久了你会发现它把一件容易出错的事摆到了明面上，反而比隐式清零更让人放心。

陷阱以为 backward 之前 .grad 是零

它在第一次反向之前是 None，不是零张量。如果你写 p.grad += something 就会在第一步崩掉。要判断有没有梯度，用 p.grad is not None；要清零，用 p.grad.zero_() 或更常见的 optimizer.zero_grad()。这个细节在 C 版本里不存在——那里梯度是一个每次都重新填满的数组，天然覆盖。从手写切到框架时，这种「语义沉默的差异」比语法错误更值得警惕。

3.6 对拍：中心差分再验一遍

机器算的梯度对不对，要靠一条不依赖链式法则的路来验。中心差分把第 i 个参数加减小量 ε=1e-5，看 loss 怎么变：斜率 (L₊-L₋)/(2ε) 就是偏导的近似。

这里有两个细节值得停一下。

第一，grads 用 torch.zeros_like(p, requires_grad=False) 创建。若省掉 requires_grad=False，新张量会继承 p 的记账标记，往里写数值时又要触发「叶节点不能原地改」的报错。第二，扰动必须在 torch.no_grad() 里做。这段函数一共要跑 26 次前向（13 个参数 × 加/减两次），每一次都建图的话既慢又危险——那些图指向的是被扰动过的参数，算完就失效了。关掉记账之后，每次前向只是纯数值计算，干净利落。

第 3 帧的 residual 是把 13 组偏差取最大绝对值得来的。它只有 1.485e-12，比中心差分本身的截断误差量级 ε²=1e-10 还小——说明 autograd 给出的确实是这条损失函数的正确导数，而不是一个碰巧接近的数。

陷阱只看 residual 小就宣布正确

这里有个隐含前提：中心差分的 ε 选得合适。ε 太大会引入二阶截断误差，太小则被浮点舍入淹没——双精度下 1e-5 是个稳妥的选择。更要紧的是，两条路径共用同一个 loss_value 函数；如果这个函数本身写错了（比如把平方写成绝对值），解析梯度和数值梯度会一起错，residual 照样接近零。所以 residual 只证明「框架求导和数值求导一致」，不证明「你的 loss 是你要的 loss」。后者要靠 y 与 loss 那两个黄金值来守。

3.7.1 读梯度表：符号、量级与它们的含义

虽然本例只打印了 b2 一个梯度，但 analytic 列表里装着全部 13 个。读梯度表时有三件事值得看。

第一是符号。grad_b2=-0.053332 为负，意思是「把 b2 增大一点，loss 会下降」。参数更新写成 b2 ← b2 - lr·grad_b2，负号乘负梯度得到正向位移——所以训练时 b2 会往增大方向走。dlmath 分册的梯度表里，13 行有正有负，正是这些符号合在一起决定了每一步往哪走。

第二是量级。grad_b2 大约 0.05，而隐层权重的梯度往往在 0.001 量级——因为上游误差连乘了 y(1-y) 和 1-h² 两个小于 1 的因子，越往前面传越小。这不是 bug，而是链式法则的必然结果；它也解释了为什么深层网络里靠近输入的层学得慢。

第三是零值。如果某个参数梯度恰好为零，可能是它真的不重要，也可能是它落进了饱和区或者根本没被用上。单看一次前向区分不了，要看训练轨迹：如果它的值一直不变而其他参数在动，八成是断链了。

工程惯例为什么把残差也做成黄金值

gradcheck_residual=1.485e-12 看起来小到没意义，为什么还要写进清单？因为它是「对拍这件事真的跑了」的证据。如果有人把 numerical_grad 改成直接返回 analytic，residual 会变成零——那反而更可疑，但清单只按 atol=1e-6 比较，0 和 1.485e-12 都通过。所以这条黄金值的真实作用不是判精度，而是让 stdout 里必须有这么一行、且数值落在合理量级；真正防「假对拍」的是代码审阅（两条路径确实不同）。把这一点写清楚，比假装一个数值能证明所有事更诚实。

3.8 双精度为什么是必需的

这一节有一行容易被跳过：torch.set_default_dtype(torch.float64)。PyTorch 的默认精度是单精度 float32，有效数字约 7 位十进制。本例的黄金值要求 6 位小数对上，看起来 7 位够用——其实不够。

原因在于对拍。中心差分要算 (L₊-L₋)/(2ε)，其中 L₊ 和 L₋ 都是接近 0.024 的数，相减之后只剩约 1e-6 量级。单精度下这两个数的末几位已经被舍入，相减会把有效位吃掉大半，算出来的数值梯度可能只准到 3～4 位。这时 gradcheck_residual 会从 1e-12 涨到 1e-4 甚至更大，对拍就失去了意义。双精度有约 16 位有效数字，做这种「大数相减」才有余量。

C 分册从头到尾用的都是 double，所以复刻时必须显式把默认精度设成 float64，不能指望框架替你选。这也解释了为什么 make_params 里每一行 torch.tensor(...) 都写了 dtype=torch.float64——默认精度是全局设置，显式写类型则是局部保险，两边都做才不会在某次重构里悄悄退化成单精度。

陷阱只改默认精度却忘了输入和目标

set_default_dtype 只影响之后不带 dtype 参数的张量构造。本例里 x、target 和四个参数都显式写了 dtype=torch.float64，所以即使删掉那行设置，结果仍然正确——那这行是不是多余的？不是。它是一道保护：以后有人加一个中间张量忘了写 dtype，默认精度就会是 float64 而不是悄悄退回 float32。这是一种防御性写法，代价是多一行代码，换来的是「加代码不容易破坏精度契约」。反过来，如果只写默认精度却在某处显式指定了 float32，那一处就会成为链条里最弱的一环。

3.9 从 13 行手推到一行 backward：成本搬去了哪里

把两种实现并排看，代码量的变化很直观：C 版本需要一个 net_backprop 函数逐行写四个偏导式子，加上一个 net_numerical_grad 做对拍；PyTorch 版本反向只有 loss.backward() 五个字符，对拍代码反而更长（因为要在 Python 里做原地扰动）。

省下的成本没有消失，而是换了位置。第一，它变成了框架内部的算子注册表：每个 torch 运算都得提供自己的局部导数，这份工作由库的维护者一次做完，所有用户共享。第二，它变成了运行时的图构建开销：每次前向都要分配节点、记录运算，小程序里可以忽略，大模型里就需要专门优化。第三，它变成了你的验证责任：以前推导写在纸上可以逐行审，现在必须自己搭一条独立路径来验。本例的中心差分就是这条路径。

工程惯例什么时候值得保留手写梯度

不是所有场景都该无脑上 autograd。如果你只要求一个闭式梯度、且调用次数极多（比如某些采样算法的内层循环里要算上百万次梯度和），手写公式可能比建图快一个数量级。另一个场景是自定义运算：你写了一个框架没有的算子，就得自己提供反向规则，否则它在计算图里是一堵墙。本书的目标是教你用框架做实验，所以默认选 autograd；但你要知道这个选择是有代价的，不是「免费升级」。

3.9.1 从 13 个参数到十亿个，什么变了

这个 2→3→1 的网络小得可以手算，但结构上和真正的大模型没有区别。Transformer 的一层注意力里有四个矩阵 Wq、Wk、Wv、Wo，本质都是「把一组向量线性映射到另一组向量」，和这里的 w1、w2 是同一件事，只是维度从 2→3 变成几千→几千。

放大的过程中，三条纪律一条不变。第一，前向要对：本例靠 y 与 loss 的黄金值守住，大模型靠端到端的小样本回归测试守住。第二，梯度要对：本例靠中心差分对拍守住，大模型靠框架的梯度检查工具在随机小批量上抽样验证。第三，实验要可复现：本例靠固定 LCG 种子守住，大模型靠固定全部随机源、记录依赖版本守住。变的只是规模与工具，不是方法论。

真正变化的是三件事。矩阵乘法从 Python 循环换成高度优化的底层核，因为朴素实现的复杂度不够用；初始化不再是简单均匀分布，而是 Xavier 或 He 这类按维度缩放的分布，保证前向方差不爆炸也不消失；训练要在海量数据上做小批量平均，还要记录动量、二阶矩等状态。这些正是后面三章的内容。

工程惯例为什么先练小网络再谈大模型

因为小网络的每个数字都能用另一种方法独立算出来。你能手推 grad_b2，能用中心差分验证它，能看着 LCG 权重解释 y 为什么是这个值。这种「三条独立证据互相印证」的体验，在几十亿参数的网络里根本无法获得——你只能看损失曲线和少量抽样。先在能完全掌控的小系统上把证据链建立起来，等系统大到看不清时，你至少知道该信什么、该怀疑什么。代价是这一段看起来「不实用」：没有一个真实任务需要 2→3→1 的网络。但教学的目的是建立判断力，不是交付产品。

这一节四张图的分工：memory 看 13 个参数在两边的布局，重点是 b2 必须是零维张量；tree 标出新增的三个文件；第一张 graph 画前向与反向共用一条链路，重点看 loss -> s 那条边乘的正是 y(1-y)；calltree 画两条独立路径如何在 residual 处汇合。

工程惯例把 13 这个数字当作第一道自检

读任何一个两层网络的源码，第一件事应该是数参数。本例是 2×3 + 3 + 3 + 1 = 13，程序也打印了 params=13。如果哪天你把隐层宽度从 3 改成 4 却忘了改别处，这个数字会变成 2×4 + 4 + 4 + 1 = 17，清单里的黄金值 params=13 立刻报不匹配。一个看起来很笨的计数，实际是结构变更的哨兵。换成更大的网络也一样：参数量是最便宜的一致性检查，比跑一遍完整前向还便宜。

回到 3.1 的第 2 帧：多了 net.py（结构、LCG、前向）、main.py（反向、对拍、打印）、pb05-twolayer.json（黄金值）。下一单元把这套机制接上训练循环：加上数据集、小批量、优化器与固定种子，打印 12 行 loss 轨迹。反向那一行还是 loss.backward()，但外面会多一圈 zero_grad() 和 step()——那一步忘了清零会怎样，正是 pb06 的核心陷阱。

小结这一节的要点
  • 13 个参数 = 6 个 w1 + 3 个 b1 + 3 个 w2 + 1 个 b2，四个叶节点张量，b2 必须是零维张量而非 Python 浮点数；
  • 前向四行对应 C 的 z → h → s → y；0.5*(y-t)² 让 dL/dy = y-t；

  • 「前向正确、求导正确、实验可复现」三条纪律在换框架之后一条都没变。

4.1 先看工程长什么样

前两个单元都是「跑一次前向、求一次梯度」。真正的训练不一样：同一组运算要重复几十次、几百次、几百万次，每次喂进去的数据可能还不一样。这一节把 autograd 接上数据流，凑出一个完整的训练循环。

工程上多了一个 loop.py：三种种子的固定、数据集与小批量的构造、网络类、整套数据上的 loss 都在里面。main.py 只剩入口与四步循环。种子仍然不写死在源码里，而是由闸门通过环境变量 PY_SEED 注入——写在源码里叫硬编码，写在清单里叫实验条件，后者才能被对照实验改变。

大白话先建立一个画面

把训练想成一条流水线。最左边是数据集，像一摞打好标签的卡片；DataLoader 负责每次抽几张递给工人；工人是网络，拿到卡片算出预测；预测和答案一比得到误差；误差沿原路倒着传回去，告诉每个旋钮该往哪拧一点。拧完一轮，再抽下一摞卡片。

四个动作——取数、前向、反向、更新——构成训练循环的四步。第四步之前还有个不起眼的清账动作：把上一轮留下的梯度擦干净。忘掉它，工人就会拿着两轮的账一起拧，步子越迈越大。

第 2 帧里带 + 的三行是这一节的全部新增。loop.py 管「实验条件是什么」——种子、数据、网络、评估用的 loss；main.py 管「实验流程怎么走」——读种子、循环、打印；pb06-trainloop.json 则是实验记录：用哪个环境变量、主种子和对照种子各是多少、怎样的轨迹才算收敛。

工程惯例为什么把种子与数据放进同一个模块

4.2.1 三条随机流的边界

理解种子，关键要明白「三条流各管一段」。random 是 Python 标准库的随机源，常被数据增强、采样策略拿来决定「翻不翻转」「抽哪个索引」；numpy 的随机模块在科学计算代码里无处不在，从打乱数组到初始化参数都可能用到；PyTorch 自己又维护一条全局流，负责张量的随机初始化、DataLoader 的打乱、Dropout 的掩码等等。

这三条流彼此不知道对方的存在。你在 Python 里连续调用 random.seed(1)、np.random.seed(1)、torch.manual_seed(1)，得到的是三套完全独立的序列，第一条流吐出的第一个数和另外两条毫无关系。所以「固定种子」不是一个动作，而是三个动作。

本例还有第四条流：torch.Generator() 造出来的专用生成器。它有自己独立的状态，专门用来生成数据。为什么不再多固定一次？因为它不随实验种子变——它的 2024 是写死在代码里的，属于「实验条件的一部分」而不是「随机来源」。换句话说，它根本不是随机的，只是用了随机算法来造一组固定的假数据。把它和三条需要固定的流混为一谈，是初学时常见的混淆。

工程惯例种子是实验条件，不是超参数

种子写在清单里而不是源码里，这件事的意义值得多说一句。超参数（学习率、批大小）是你要调到最好的东西；种子不是——它只是让实验可重复的编号。你从不「优化」种子，但你必须记录它。train 闸门把种子通过环境变量注入，等于把它从代码里拎出来变成表格里的一列：主实验 12345、对照实验 67890，任何人拿到清单都能复现这两条轨迹。若把种子写死在源码里，读者看到的数字就没有「这是在什么条件下得到的」这个信息。

4.3 数据集、DataLoader 与小批量

训练数据长什么样？本例造一个最小的回归问题：16 个二维输入 X，真实权重 [1.5,-0.5]，目标 y = X·w_true + 0.2。没有噪声，所以理论上 loss 可以降到零——这让我们能专心看收敛过程，不被数据本身的噪音干扰。

这里有个容易被忽略的设计：数据由一个专用生成器产生，种子固定为 2024。为什么要另起一个生成器，而不是直接用 torch.randn(16,2)？因为后者会消耗全局随机流，把网络初始化的序列往后推。我们把数据和随机初始化解耦——数据恒定，只有网络初值和打乱顺序随 PY_SEED 变。这样对照种子改变的那部分就是纯粹的「训练起点不同」，解释起来干净。

generator 的 2024 是固定的，不随 PY_SEED 变。这不是疏漏，而是有意为之：如果数据也随主种子变，你就分不清轨迹变化来自数据还是来自初始化。固定数据是可控实验的基本功。

DataLoader 做两件事：batch_size=8 把 16 条样本切成两摞；shuffle=True 每轮打乱顺序。打乱用的是全局 torch 随机流（没有传 generator 参数），因此受 torch.manual_seed 控制——同种子两次的打乱顺序相同，对照种子则不同。

第 2 帧强调两批加起来恰好是 16 条、没有重叠——DataLoader 的切分是划分，不是抽样。第 3 帧则点出小批量的本质：每步只看一半数据，梯度是对「真实梯度」的一个带噪声的估计。噪声既是缺点（loss 轨迹抖动），也是优点（噪声能把参数从鞍点附近踢走，这一点在概率优化分册讲过）。

工程惯例为什么 batch_size 选八而不是一或十六

取 1 就是纯随机梯度下降：每步只看一条样本，噪声最大，轨迹抖得厉害。取 16 就是全批量：每步用全部数据，梯度精确、轨迹平滑，但每次更新的计算量翻倍。取 8 是折中——两批各占一半，既保留了噪声的逃逸能力，又不至于抖到看不出趋势。这个数字是经验选择，不是定律；你改成 4 或 16，轨迹会变，但闸门只要求前 8 步非增，一样能过。代价是你要重新写黄金值，因为轨迹数字全变了。

4.3.1 小批量的噪声既是麻烦也是资源

全批量梯度下降每步都朝「真正的最陡下降方向」走，轨迹平滑得像教科书插图。小批量却只看一部分样本，估计出来的梯度带着噪声：这一批碰巧把某个方向放大，下一批又把它压小。本例每步走两批，噪声已经小了很多，但如果你把批大小改成 1，就会看到 loss 曲线上下跳动。

噪声不是纯粹的坏事。概率优化分册讲过，高维非凹问题里的随机驻点大多是鞍点；纯梯度下降正好落在鞍点上时梯度为零，会永远停在那里，而小批量的噪声能不断扰动参数，把它从不稳定方向推走。批量越小，噪声越大，逃逸能力越强，代价是收敛后参数会持续抖动。学习率衰减的作用之一就是前期靠噪声逃逸、后期压低噪声稳定下来。

这也解释了一个常见现象：训练 loss 曲线抖动时，有经验的工程师不会立刻调学习率，而是先画出移动平均。移动平均滤掉的是采样噪声，留下的是趋势。如果趋势仍在下降，模型就好好的；只有趋势掉头向上才需要干预。train 模式之所以能对本例要求前 8 步逐点非增，是因为这里用的是确定性数据、固定打乱顺序、并且打印的是全量 loss——换成真实随机训练，这样的逐点判定就太苛刻了。

陷阱把 loss 抖动一律当成发散

你会看到什么：loss 从第 5 步到第 6 步突然升高一点点。你会怎么误判：学习率太大，赶紧减半。真相可能只是这一批样本碰巧更难，下一批就降回来了。判据是看窗口而不是单点——取最近若干步的移动平均，或者像闸门那样看一段窗口的整体趋势。反过来也要警惕另一种错：loss 连续下降但参数范数在爆炸，只看 loss 会把发散前夜误判成健康收敛。两种误判都源于「只看一个标量」，所以真实训练里要同时监控 loss、梯度范数和参数范数。

四步依次是：

  • pred = model(xb)：前向，得到这一批的预测；

注意循环结构：外层走 12 步，内层把 DataLoader 的两批各走一遍。也就是说每一步训练其实做了两次参数更新，12 步共 24 次。每次更新前都清零——这是关键。

还有一处细节：batch_loss 是当前小批量上的损失，用来反向；但打印的是 full_loss(model, X, y)，即整套数据上的损失。为什么分开？因为小批量 loss 每步喂的数据不同，数值天然上下跳；把它打印出来，轨迹会抖得看不出趋势，前 8 步非增的判定根本过不了。整套数据的 loss 是同一个函数在不同参数点的值，才是「模型有没有变好」的度量。

第 3 帧里那条 model -> full_loss 的边不带梯度——full_loss 内部包了 torch.no_grad()，只是拿当前参数算一个数给我们看，不参与反向。这也是为什么它可以用整套数据而不担心内存：不建图，就不需要为 16 条样本保存中间量。

陷阱把小批量 loss 当成全量 loss 打印

如果你把 print 改成 print("loss=%.6f" % batch_loss.item())，打出来的是每批的 8 条样本上的损失。由于两批交替、顺序还被打乱，相邻两步看的样本不同，loss 会上下跳动——不是模型变差了，是尺子换了。你会怎么误判？以为学习率太大导致震荡，于是把它调小，结果收敛变慢。真相是：评估必须在固定的数据集上做，否则你比较的不是同一个量。train 闸门的 monotone_window=8 也正是靠这一点才判得准。

4.4.1 opt.step() 替你做了哪一行

pb05 里我们亲手用过 SGD 更新；这一节把它换成了 opt.step()。两者做的事情完全一样：对每个参数执行 w ← w - lr·g。差别只在「谁拿着参数列表」。手写时你要自己写 for p in params: p.data -= lr * p.grad；现在 opt 在创建时就收下了 model.parameters()，之后每步只需喊一声。

优化器并不神秘。本例的 torch.optim.SGD 内部只存了学习率和参数引用，step() 就是遍历参数、做一次减法。它的价值在于统一接口：以后换成 Adam，step() 这行不变，只是内部改成按动量和二阶矩缩放的更新式。这就是框架收走的样板代码——你不必为每种优化器重写一遍循环。

有一点必须注意：step() 读的是 .grad，不会自己重新计算梯度。所以四步的顺序不能乱——必须先 backward() 填上梯度，再 step() 用它。如果把两者调换，step() 会读到上一步的旧梯度（或第一次的 None 直接报错），参数按过时的方向更新，loss 轨迹变得莫名其妙。这个错误不会触发异常，只会给出一条看起来「像在收敛」但其实不对的曲线，属于典型的静默错误。

工程惯例学习率零点一从哪里来

LR=0.1 是试出来的，不是推出来的。本例的目标是二次型，理论上可以按曲率算出一个安全上界；但真实网络里曲率未知，工程上就是从保守值开始试。试的办法很朴素：跑一次看 12 行 loss，若平滑下降就保留，若反弹就减半，若下降太慢就加倍。本例取 0.1 时首行 0.746848、末行 0.008668，前 8 步严格递减，是个合适的值。改成 0.5 时前几步就会越过最低点反弹，闸门报 train_loss_not_decreasing。阈值不会替你选学习率，它只负责拦住不合适的选择。

4.5 zero_grad 为什么必须

backward() 把梯度加进 .grad，而不是覆盖。pb05 已经讲过这个性质，但在只反向一次的例子里它不造成后果；到了循环里就成了头号陷阱。

假设忘了 zero_grad()：第一步算出梯度 g₁，更新用 g₁；第二步算出 g₂，但 .grad 里已经是 g₁+g₂，更新步长用的是两者之和；第三步变成 g₁+g₂+g₃……梯度越积越大，参数很快被甩出去，loss 不降反升。闸门会报 train_loss_not_decreasing，因为前 8 步的非增判定被破坏。

实验记录亲手制造一次「忘了清零」

把 main.py 里的 opt.zero_grad() 那一行注释掉，跑 PY_SEED=12345 python src/main.py。你会看到 loss 不再平滑下降，前几步就可能反弹。再跑 node build/run.js --unit pb06-trainloop，闸门报 train_loss_not_decreasing。你会怎么误判？以为是学习率太大。真相是梯度累加让实际步长逐轮放大。做完把注释去掉，否则清单里的黄金值对不上。这个实验值得真的做一遍——它是理解「累加而非覆盖」最快的方式。

工程惯例为什么框架不自动清零

如果 backward() 自己先清零，那么「把主损失和正则损失的梯度加起来」就做不到——你只能先把两个损失合成一个标量再一次反向。有些场景确实没法合成，比如梯度来自不同分支的采样估计。框架把这个决定权交给你，代价是每轮都要写一行。习惯之后你会发现这行代码反而是一种提醒：它在每次更新前强制你意识到「现在的梯度从哪来」。

4.5.1 累加不是缺陷，是一种接口

把「梯度累加」单纯当成坑，会错过它有用的那一面。考虑一个常见的训练技巧：梯度累积。显存只够放 2 条样本，但你希望等效批大小是 8。做法是连续跑 4 个小批，每批都做前向和反向但不清零，让梯度累加四次；等攒够了再调一次 step()，然后清零。数学上，四个梯度的和除以 4 就等于大批量的平均梯度。

这个技巧能成立，正是因为 backward() 设计成累加而非覆盖。如果框架自作主张在每次反向前清零，你就没法实现它。本例没用到梯度累积，但把 zero_grad() 写在明确的位置，等于给这条路留了口子：你想累积时把这一行挪到循环外面即可。

代价是学习者必须理解「清零是自己的责任」。框架选择把复杂性暴露出来，而不是藏起来——这和它坚持「标量才能 backward」「叶节点才能读 grad」是同一种哲学。本书从 pb04 起就反复讲这些边界，正是为了让你在需要变形时知道哪些动作是安全的。

陷阱清零的位置比清零本身更重要

写 opt.zero_grad() 不难，难的是放在哪。本例放在内层循环开头——每处理一批就清一次，这是常规做法。若你想做梯度累积，就得放到外层、攒够若干批再清。放错位置的症状很隐蔽：训练照跑、loss 照降，只是等效批大小和你想的不一样，调出来的学习率不再合适。判断办法是数一数每个 step() 之间调用了几次 backward()——常规训练应该是 1 次，梯度累积才是多次。

4.6 eval 模式：本例里没差别，但必须写

每步训练结束后，代码先 model.eval()，算完全量 loss 再 model.train()。eval() 把模块切到评估模式：带 Dropout 的层会关闭随机丢弃，BatchNorm 会用累积统计量而不是当前批次的统计量。本例的 TinyReg 只有一个 nn.Linear，既没有 Dropout 也没有 BatchNorm，所以切换在数值上没有任何差别。

那为什么还要写？因为这是习惯。真实模型几乎一定有对训练/评估敏感的层；如果你在验证时忘了切到 eval()，测出来的 loss 会带随机性，看起来像模型不稳定，实际只是 Dropout 还在开。eval() 与 train() 成对出现，是让别人一眼看出「这里在评估」的信号。

陷阱在 eval 模式下反向更新参数

有人为了「评估时不建图」，把整个验证循环放进 model.eval() 之后就再没切回来，接着又开始训练。结果训练时也处于评估模式，Dropout 永远不工作，模型悄悄失去了正则化。症状很隐蔽：训练 loss 漂亮地下降，验证 loss 却卡住不动。修法就是本例的写法——评估算完立刻 model.train() 切回。本例数值上看不出差别，恰恰是最危险的地方：你没法靠数字发现漏了切回，只能靠成对书写的纪律。

min_points=12 防「程序只跑了三步就说收敛」；first_min=0.7 防「起点已经在最优附近，下降演示没有意义」；last_max=0.01 防「每步只走微不足道的一小步」；decline_min=0.7 防「起点低终点也低的平凡通过」；monotone_window=8 加 slack=1e-4 防「前几步来回震荡却自称收敛」。这五条彼此独立，少一条都能构造出骗过闸门的写法。阈值来自真跑，不能为了让绿字好看反过来放宽。

4.7.1 阈值为什么按真值取，而不是取整

first_min=0.7 而首行实际是 0.746848，last_max=0.01 而末行是 0.008668——为什么不干脆写成 0.75 和 0.005 这种整齐的数？因为阈值不是「你想要什么」，而是「真跑给出了什么，留多少余量」。

留余量的原则是：既要容得下合理波动，又不能宽到失去判别力。首行留约 0.047 的余量是因为不同机器上浮点末位可能差一点；末行留约 0.0013 的余量同理。decline_min=0.7 对实际降幅 0.738180 留了约 5% 的余量——若把学习率改小导致降幅只有 0.6，闸门就会拦下，这正是我们想要的。

反过来的错误做法更常见：为了让失败的实验变绿，把 last_max 从 0.01 放宽到 1.0。闸门确实过了，但那条「必须真的收敛」的纪律被自己拆掉了。本套书所有数值实验的共同底线就是这一句：黄金值和阈值来自真跑，不能反过来迁就。你已经知道哪些动作不该做，剩下的交给纪律。

工程惯例用三次运行拼出完整证据

把三次运行的角色摆在一起看：第一次给收敛轨迹与黄金值，验证「训练确实在降低 loss」；第二次同种子逐值一致，验证「程序是确定的」；第三次换种子轨迹改变，验证「数字来自计算而不是硬编码」。单独任何一次都只能说明一部分——第一次可能被硬编码表格骗过，第二次无法区分硬编码与真计算，第三次无法证明可复现。只有三次合起来，才能说这个训练实验是真的。这也是为什么 train 模式固定跑三次，而不是给你一个开关让你自己选。

4.8 种子复现：为什么要跑三次

train 模式一共跑三次程序。第一次带 seed=12345，抓 stdout 并检查收敛；第二次还是 12345，要求逐值一致，否则报 train_nondeterministic；第三次换成 seed_contrast=67890，要求至少一个数值变化，否则报 seed_has_no_effect。

对照种子 67890 真跑的结果是：首行 0.502193，末行 0.003293，中间十行也全部不同——整条轨迹都变了。主种子首行 0.746848、末行 0.008668；对照种子首行 0.502193、末行 0.003293。这说明数字确实由种子驱动的网络初值与打乱顺序算出来，而不是一张硬编码的表。

这里只把对照的两个端点写进正文，没有为它另开一个 output 块。原因很简单：每个 output 块都必须被某个清单的 output 字段声明，而一个清单只声明一个 id。把对照数字写在 experiment 块的叙述里，既保留了证据，又不制造无人认领的输出块。

现在回答 4.7 留下的问题：为什么程序不打印 seed=12345？因为那样的话，换种子后这一行必然变化，seed_has_no_effect 就会平凡通过——哪怕 12 行 loss 全是写死的。不打印种子，就逼着对照检查去看 loss 本身。这是一个很小的设计选择，却直接决定这条证据有没有牙。

第 2 帧验证确定性，第 3 帧验证数值真的来自种子。两条缺一不可：只跑两次同种子，一个硬编码 loss 表的程序也能过；只跑一次对照种子，一个用时间当随机源的程序每次都不同，看起来「有变化」却无法复现。

陷阱复现性不等于正确性

同种子两次一致，只说明程序是确定的；换种子有变化，只说明程序读了种子。两者都通过，也不能证明四步循环写对、loss 函数选对。本单元的正确性来自三条独立证据：手算的收敛趋势与 12 行轨迹吻合、train 闸门检查起点终点与单调性、对照种子改变整条轨迹。train 闸门查的是后两条，第一条要靠你自己看数字。把「闸门通过」当成「数学正确」，是这套书反复要破除的误解。

4.8.1 为什么对照种子是必需的

最容易跳过的是第三次运行：既然同种子两次已经逐值一致，为什么还要换种子？因为「确定」和「真算」是两回事。把 12 个 loss 写死进一个列表，程序每次都打同一串数字——确定性满分，可它根本没有训练。seed_has_no_effect 就是专门抓这种骗法的：换一个种子，写死的表不会变，闸门立刻报失败。

反过来，只跑对照种子而不跑同种子，也挡不住另一类问题。用当前时间、内存地址或系统熵当随机源的程序，每次跑都有变化，看上去「种子起了作用」，实际上完全不可复现。两次同种子一致正是要堵这个口。两次与一次，各自防一种骗法，缺一不可。

对照种子取 67890 而不是 12346，是因为要拉开距离——两个相近种子可能碰巧给出相近轨迹，虽然不会完全相同，但读数不直观。取一个明显不同的数，第一条 loss 就从 0.746848 变成 0.502193，一眼能看出「种子确实换了」。

实验记录亲眼看到 seed_has_no_effect

想确认这道检查真的有牙，可以把 main.py 里读环境变量那行改成硬编码 seed = 12345，其他不动，跑 node build/run.js --unit pb06-trainloop。闸门会在第三次运行时发现：换种子 67890 后 12 行 loss 与主种子完全相同，于是报 seed_has_no_effect。这证明它检查的是 loss 本身，而不是某个被打印出来的种子字样。做完把那行改回去，程序必须重新从 os.environ["PY_SEED"] 读种子。

7.1 先看工程长什么样

前面两个单元里，参数是我们自己捧在手里的几个张量：w、b 各自活着，梯度要手动清零，更新要手写一行 w -= lr * w.grad。那种写法对理解反向传播有好处，但只要你把网络从两层加到二十层，麻烦就来了——你得自己记住每一层的参数、自己遍历它们、自己把优化器的状态（比如 Adam 的一阶矩和二阶矩）跟着参数一起存下来。nn.Module 与 torch.optim 就是专门收走这批样板代码的框架部件：前者替你登记参数，后者替你更新参数，调度器再替你改学习率。

这一单元仍然只用一台机器、一个 CPU、两个源文件。我们先把工程形状画出来，再一层层拆开框架替你做的事。

第 1 帧是讲故事用的起点，不是说你的磁盘上真的空着。第 2 帧里冒出来一个 torch_module/，三个新增文件各有分工：main.py 只负责编排和打印，model.py 放模型与训练循环，pb07-module.json 是闸门读的清单。第 3 帧把目录外壳去掉，专门看运行时关系——入口那行 from model import ... 把本地模块拉进来，这也是 ch03 起硬规定③在 Python 侧的落地方式：从第二个项目开始，不许再用一个单文件脚本糊到底。

为什么非要拆两个文件？表面理由是闸门要求，真正的理由是接缝：你想换优化器，只动 main.py；你想换网络结构或训练循环，只动 model.py。代价是多一层 import 路径要操心——python src/main.py 时 Python 把 src/ 放进模块搜索路径，所以 from model import ... 能找到同目录的 model.py；如果你在别的目录里执行 python main.py，路径就变了。这条坑我们后面还会再提一次。

大白话三个名字先分清楚

nn.Module 是账本：你把 nn.Linear(2, 1) 赋给它的属性，它就记下「这里有两个参数」。Optimizer 是搬运工：它拿着账本上参数的引用，每步按梯度和自己的规则搬一下。LRScheduler 是调音师：它不改参数，只改搬运工手里的学习率。三者各管一段，所以你能在不动网络定义的前提下换优化器、换调度策略。

7.2 把网络写成类：nn.Module 到底替你管了什么

先看模型本体。它能做的事情只有一件：把两维输入变成一维输出，也就是一个线性层。mse 故意不调用 nn.MSELoss，因为我们这一册的纪律是「先把损失写成看得见的式子，再允许框架替你写」。

第 24 行的继承不是装饰：只有挂上 nn.Module，框架才会在你给属性赋值时自动登记参数。第 28 行把 nn.Linear(2, 1) 存成 self.linear，于是这个线性层内部的 weight 和 bias 自动进入账本；super().__init__() 必须早点调用，否则登记表还没建好，赋值时就会报错。第 31 行的 forward 只写数学，不写梯度——梯度由 autograd 在调用发生时现建计算图。第 37 行把平方损失摊开：先算预测与目标的差，平方，再对全部元素取平均。

下面三帧把「你写类、框架记账、优化器拿账」这条链画出来。看的时候盯住带星号的节点：星号表示这一帧新出现的东西。

第 1 帧到第 2 帧是「赋值即注册」：你并没有手写一张参数清单，nn.Module 的 __setattr__ 在赋值时把 Parameter 收进内部字典。第 2 帧到第 3 帧是「账本交给搬运工」：torch.optim.SGD(model.parameters(), lr=...) 拿到的是生成器吐出的引用，所以 optimizer.step() 能直接改张量的数值，不需要把新值塞回模型。

陷阱先把优化器建好，再把参数换成新对象，会静默失效

你会看到：代码照跑、损失照打印，可模型参数一动不动，或者 loss 卡在初始值为你误以为是数据没准备好。你会怀疑是学习率太小、梯度是零。真相是：优化器在构造时记住的是那几个张量对象本身。如果你之后写 model.linear = nn.Linear(2, 1)，账本里换成了新张量，旧优化器还攥着旧引用，更新的对象跟前向用的已经不是同一个。正确做法是先换结构、再建优化器；或者原地改参数数值（load_state_dict 就是原地拷贝），这样引用不变。这个坑不报错，是它最危险的地方。

7.3 parameters() 与 state_dict：优化器真正看到的东西

账本有两个出口。parameters() 给优化器用，吐的是参数张量本身；state_dict() 给保存和加载用，吐的是键名到张量的字典。先看我们怎么给账本拍快照。

第 42 行做了三件事：state_dict().items() 取出所有键值，detach() 把张量从计算图上摘下来，clone() 复制一份独立存储。少掉 clone() 会怎样？两个模型的参数会指向同一块内存，SGD 走一步，Adam 的起点也跟着动了，所谓「同一条起跑线」就成了骗局。少掉 detach() 呢？字典里带着图信息，保存和比较都可能出问题。

真跑输出的 sd_keys:['linear.weight', 'linear.bias'] 把键名摆出来了。它不是随便起的名字，而是**「注册时的属性路径 + 参数名」**：linear 是你在 __init__ 里给属性起的名字，weight 和 bias 是 nn.Linear 内部的名字。改属性名，键名跟着改；用 nn.Sequential 包一层，键名会变成 0.weight 这种带编号的形状。

第 1 帧强调键和值是分开的两类东西：键决定「加载时往哪儿塞」，值决定「塞进去的数是多少」。第 2 帧强调深拷贝后的存储是新的——这正是 sgd 和 adam 能从同一起点出发、互不干扰的原因。

工程惯例保存检查点时要不要连优化器一起存

只存模型的 state_dict，文件小、兼容性好，够你继续推理或微调；但恢复训练时优化器的动量、Adam 的二阶矩都会丢，等于换了个优化器重新起步。工程惯例是把 model.state_dict()、optimizer.state_dict()、scheduler.state_dict() 和当前步数打成一个检查点。代价是文件变大、框架版本升级后旧状态可能读不回来；换来的是断点续训能接上原来的轨迹。这是惯例，不是标准，你完全可以只存模型再从头热身几个 step。

7.4 训练四步曲：框架把哪三行收走了

训练循环本身还是你自己写的——框架没有替你决定「训练多少步」，只替你完成了每步里的更新动作。

第 49 行的 zero_grad() 是PyTorch 与很多手写框架最不同的地方：梯度默认是累加的，不是每步自动清空。这个设计让「多个 loss 累加反向」变得容易，代价就是你每步都得记得清零。第 52 行前向时 autograd 现场建图；第 53 行反向把梯度写进每个参数的 .grad；第 55 行 optimizer.step() 读 .grad 改参数。注意第 54 行的 scheduler.step() 在 optimizer.step() 之后——顺序反了会让第一步就用错学习率。

losses.append(loss.item()) 里的 item() 把单元素张量取成 Python 浮点数。少了它，列表里存的是带图信息的张量，图会一直挂在内存里，训练几千步后你会看到内存条慢慢涨满。这是零基础最容易忽视的一处样板代码。

陷阱忘了 zero_grad，loss 会先降后炸

你会看到：前几步 loss 降得挺快，然后突然反弹、甚至变成 NaN。你会误判成学习率太大，于是把它调小，结果只是把爆炸推迟。真相是：.grad 一直没清零，第 t 步的梯度实际是前 t 步梯度之和，等效学习率被悄悄放大了 t 倍。判断方法很简单——把第一步和第二步的 .grad 打印出来，第二步若约等于第一步的两倍（在损失曲面近似不变时），就是这里忘了清零。本例把 zero_grad() 写在循环开头，正是为了把这个坑堵死。

第 39 行的 p.sub_(LR * p.grad) 就是全部秘密：sub_ 是原地减法，学过 C 的你完全可以把它读成 w[i] -= lr * g[i]。第 46 行的 step() 内部对 SGD 而言做的也是这件事（不带动量、不带权重衰减时）。我们用 torch.no_grad() 包住手写更新，避免更新动作本身被记进计算图——这一步不是训练，只是改数。

7.6 SGD 与 Adam：同一条起跑线上的 30 步

两条训练路径的代码几乎一样，唯一差别是优化器对象，以及 Adam 这边多挂了一个调度器。

两个模型都先 load_state_dict(init_state)，所以起点逐位相同；都跑 30 步，步数也相同。差别在第 25 行和第 30 行构造的优化器：SGD 只需记住参数和学习率，Adam 还为每个参数多存两个同形状的张量。输出到第 30 步时，sgd_loss=0.004384、adam_loss=0.003682，两者差 diff=0.000701——Adam 略微领先。

为什么领先？SGD 对所有参数用同一个步长 lr；Adam 给每个参数单独算一个有效步长。把第 t 步的梯度记成 g_t，Adam 维护一阶矩 m_t = β₁m_{t−1} + (1−β₁)g_t 与二阶矩 v_t = β₂v_{t−1} + (1−β₂)g_t²，再做偏差修正 m̂_t = m_t/(1−β₁ᵗ)、v̂_t = v_t/(1−β₂ᵗ)，最后更新 w_t = w_{t−1} − lr·m̂_t/(√v̂_t + ε)。分母里的 √v̂_t 是「这个参数过去梯度有多大的滑动平均」：梯度长期大的参数步长被压小，梯度长期小的参数步长被放大。本例两个输入特征的量级不同， Adam 的这个逐坐标归一化正好派上用场。

但别把「Adam 更快」当成语录。学习率 0.1 是这对数据的合适档位；换成更小的学习率，SGD 可能反超，因为 Adam 的自适应步长在小梯度方向上会把步子迈得过大。框架给了你两种搬运工，选哪个是实验问题，不是信仰问题。这也是我们把 diff 单独打印并写进清单的原因：比较必须落到一对可复现的数字上，而不是一句「通常更好」。

第 1 帧的两个星号是两条分支的诞生；第 2 帧的星号是差距本身。两帧合起来读，你看到的是同一个实验的两个时刻，而不是两条毫不相干的程序。

7.7 学习率调度与状态快照：把 step 之后的那件事接上

StepLR(step_size=10, gamma=0.5) 的意思很朴素：每过 10 次 scheduler.step()，学习率乘 0.5。30 步里会在第 10、20、30 步各触发一次，于是 0.1 → 0.05 → 0.025 → 0.0125，这就是 lr_end=0.012500 的来历。

调度的意义在于「先大步探路、再小步收尾」。如果从第 1 步就用 0.0125，前期下坡会慢得多；如果一直用 0.1，后期容易在最优点附近来回震荡。调度器把这条经验写成了三行配置，代价是训练循环里多了一次 scheduler.step() 调用，以及检查点里多了一份调度器状态。

快照与恢复这段代码同样短。

load_state_dict 默认是 strict=True：键名必须一一对应，多一个少一个都报错。这看似麻烦，实则是好事——它把「你换了网络结构却忘了改检查点」这类错误变成显式失败，而不是悄悄加载了一半。restored_diff=0.000000 说明加载后的模型与源模型算出的损失在六位小数上一致；注意 restored_loss 是重新前向算出来的，不是从快照里读的旧数字，因此这条对账有独立计算支撑。

陷阱恢复训练只 load 模型会丢掉动量

你会看到：断点续训之后 loss 突然跳高，然后重新慢慢下降。你会怀疑数据打乱出了问题。真相是：模型的 weight/bias 回来了，但 Adam 的 m、v 和步数没回来，第一步的矩估计从零开始，步长分布和中断前完全不同。正确做法是连 optimizer.state_dict()、scheduler.state_dict() 一起存。另一个相邻陷阱是保存时用了 model.state_dict() 的浅引用又继续训练，文件里记的其实是张量的实时值——写盘前应该先 detach().clone() 或让框架立即序列化。本例的 clone_state 就是把这件事摆到明面上。

大白话为什么「同一起点」要深拷贝而不是复用同一个模型

两个优化器不能同时训练同一个模型：它们会往同一批 .grad 和同一批参数上写，谁先谁后完全取决于调用顺序。这不是并行，是互相踩脚。本例的做法是造三个模型：sgd、adam、one（还有手写的 manual），每个都从 init_state 加载一份独立参数。看起来多写了几行，换来的是实验可以逐项对账——否则你根本说不清 diff 是两个优化器的差别，还是调用顺序的差别。

7.9 反例与代价：这些写法不是等价的

第一处反例是「先反向再清零」。有人觉得 zero_grad() 放在 step() 之后更省事，反正下一步开始前都会清。单看一个 step 没问题；一旦你中途插入梯度累加（例如两个 loss 各反向一次再更新），清空的时机会决定累加是否成立。本例把清零写在循环开头，语义是「每一步从干净的梯度开始」，这也最常见。

第二处反例是「用 loss.item() 当收敛判据」。本例的 sgd_first=0.071775 是第 1 步的损失，它等于 init_loss，因为 train() 里记录的是更新之前算出的 loss。而 sgd_loss=0.004384 是训练结束后独立重算的更新之后的损失。两者不是同一个量，混用会让「降了多少」算错。想比较起点和终点，要么都用更新前记录，要么都像本例这样在训练后重新算一次。

第三处反例是「state_dict 等于全部训练状态」。它只是模型参数。优化器有自己的状态，调度器也有（当前步数、上次的学习率）。 checkpoint 少存一样，恢复出来的轨迹就不一样。代价是文件更大、版本耦合更强；收益是断点续训真的能续上。

第四处反例是「调度器调用放在 optimizer.step() 前面」。那样第一步起作用的就不是初始学习率，而是折半后的值；30 步结束时会少触发一次折半，lr_end 从 0.012500 变成 0.025000。框架不会报错，数字却全变了——这正是清单黄金值的用武之地。

工程惯例把常数写成具名变量

SEED、STEPS、LR 都在文件开头具名，而不是散落在代码里的 0.1、30。这是工程惯例不是标准：它让「改一个档位重跑」变成一次编辑，也让实验记录能一句话说清配置。代价是多几行声明，换来的是复现实验时不用全文搜索数字。本例若把 LR 改成别的值，sgd_loss 与 adam_loss 都会变，清单黄金值必须跟着真跑结果更新，不能手改正文去迁就旧数字。

7.10 从损失曲面到 w -= lr*g：那一行从哪来

第 39 行的 p.sub_(LR * p.grad) 看着像咒语，其实它和前面几册手推的梯度下降是同一件事。把本例的损失写开：L(w, b) = (1/n) Σᵢ (xᵢw + b − yᵢ)²，其中 n = 4，xᵢ 是两维输入，yᵢ 是那个线性式算出的标量。对 w 求偏导，链式法则把平方的 2、残差、以及 xᵢ 依次带出来：

∂L/∂w = (2/n) Σᵢ xᵢ (xᵢw + b − yᵢ)，∂L/∂b = (2/n) Σᵢ (xᵢw + b − yᵢ)。

写成矩阵形式就是 ∇w = (2/n) Xᵀ(Xw + b − y)。你在 dlmath 分册里手推过同样的式子，区别只是那时把每个分量写出来、这里让 autograd 现场建图算。所以 p.grad 不是什么神秘产物，它就是上面这个偏导数在 w 和 b 两个位置上的取值；p.sub_(lr * p.grad) 则是把参数沿负梯度方向挪一小步。

为什么沿负方向？在一阶近似下，L(w + Δ) ≈ L(w) + gᵀΔ，其中 g 是当前梯度。如果想让 L 变小，就要让 gᵀΔ 为负；取 Δ = −lr·g 时，gᵀΔ = −lr‖g‖² ≤ 0，只要 lr 为正且够小，下降就有保证。这一句话把「学习率不能太大」也说清楚了：一阶近似只在小邻域里成立，步子迈出邻域，线性近似失效，损失反而可能上升。

对二次函数还能给出更具体的稳定条件。若损失在某一维上近似为 L(w) = a(w − w*)²，梯度是 2a(w − w*)，一步更新后离最优点的距离变成原来的 (1 − 2a·lr) 倍。要收敛就要 |1 − 2a·lr| < 1，也就是 0 < lr < 1/a。曲率 a 越大，允许的步长越小。本例输入被压在 0.1 到 0.4 的量级，曲率温和，lr = 0.1 才落在这个窗口里；把输入整体放大十倍，同一个学习率就会越界，loss 会先降后炸。这不是框架的行为，是损失曲面本身的性质。

第 1 帧到第 2 帧是建图与走图，第 3 帧特意把 torch.no_grad() 的效果画出来：更新本身不再产生新节点，否则你每训练一步，图就再长一层，显存和内存都会被拖垮。手写循环时这条纪律靠 no_grad 保证，框架版的 optimizer.step() 内部也做了同样的事。

大白话梯度是「往哪走」，学习率是「走多大」

把损失想成一座山谷，你站在山坡上看不见谷底，只能摸到脚下坡度的方向和陡峭程度。p.grad 告诉你「最陡的下坡朝哪个方向、有多陡」，但它不告诉你迈多大的步子；lr 就是步长。坡很陡时小步慢慢挪，坡很缓时可以迈大点——Adam 的 √v̂ 分母做的正是「按坡度记忆自动调步长」这件事。

7.11 Adam 多存的东西：两个矩、两次修正、三份状态

SGD 的账本上只有参数本身；Adam 为每个参数额外存了 m 和 v 两个同形状的张量。本例参数是 weight(1, 2) 和 bias(1,)，于是 Adam 的状态里也有一份 (1, 2) 的 m、一份 (1, 2) 的 v，以及 bias 的对应两份。参数量小的时候看不出差别；换成一个几千万参数的模型，优化器状态会占掉检查点的大头——这是工程上选择 SGD 与 Adam 时要算的账，不是信仰问题。

偏差修正为什么非要不可？看第一步就明白了。取默认 β₁ = 0.9、β₂ = 0.999，第一步 m₁ = (1 − β₁)g₁ = 0.1 g₁，只有真实梯度的十分之一；v₁ = (1 − β₂)g₁² = 0.001 g₁²，只有千分之一。若直接用 m₁/√v₁，分子分母的缩小幅度不同，步长会被放大约 √10 倍，起步就过猛。除以 1 − β₁ᵗ 与 1 − β₂ᵗ 正好把这两处缩小抵消掉，所以 m̂₁ = g₁、v̂₁ = g₁²，第一步的有效步长回到 lr 的量级。随 t 增大，修正因子趋近 1，偏差自然消失。

ε 的作用是防止除零：某个参数如果长期没有梯度，v̂ 可能非常小，分母 √v̂ + ε 里的 ε 给了一个下限。本例取的是框架默认值，你可以在构造 Adam 时用 eps= 改它，但改完必须重跑真跑、更新黄金值——正文里写「应该差不多」不构成证据。

陷阱中途中止再续训，阶梯数比参数更要命

你会看到：检查点明明存了 optimizer.state_dict()，恢复后前几步 loss 还是有一个小跳。你会怀疑是 load_state_dict 写错了键名。真相常常是调度器的 last_epoch 没恢复：参数与动量都在，学习率却从初始值重新开始，或者跳过了本该折半的那一次。本例的 lr_end=0.012500 就是一条可以钉死这条链的黄金值——只要次序或恢复状态错一步，这个数字就变。另一个相邻陷阱是训练中途改了 step_size，这让调度器的内部计数与新配置不再对应，框架同样不会报错。

工程惯例AdamW 与权重衰减不是同一件事

在 SGD 里把权重衰减写成「梯度上加 λw」很自然；到了 Adam，那个被逐坐标归一化的分母会把衰减项也一起缩放，效果就变味了。AdamW 把权重衰减从梯度里拆出来，直接在参数上做 w ← (1 − lr·λ)w，于是衰减强度不再被 √v̂ 扰动。这是工程惯例而非标准条款：本例没有用权重衰减，免得多一个变量干扰对账；你做真实训练时若发现 Adam 的正则行为怪异，先检查是不是该换 AdamW。代价是要多理解一个优化器，收益是正则强度可预测。

7.12 逐个拆开 stdout：13 行里每一行的来路

最后把输出块按用途归堆，你以后设计自己的数值实验也可以照这个清单来。

第一组是起点证据：init_loss=0.071775、sgd_first=0.071775、adam_first=0.071775 三行相等。前一行来自 main.py 第 20–21 行，在 torch.no_grad() 里对 base 重新前向；后两行来自 train() 里第一步更新前记录的损失。三者相等才说明 sgd 与 adam 真的从同一份参数出发；只要有一行不同，后面所有关于优化器差别的结论都不成立。

第二组是单步对账：manual_loss=0.045673 是手写 w -= lr*g 之后的损失，manual_step_diff=0.000000 是它与框架 SGD.step() 路径的差。注意比较的不是梯度张量本身，而是两条路径各自前向算出的损失——这样即便内部实现细节不同，只要数学等价，数值就该一致。这也是我们说「框架优化器等价于手写更新」的实验含义。

第三组是终点比较：sgd_loss=0.004384、adam_loss=0.003682、diff=0.000701。三行都来自训练结束后的独立前向，与 train() 里记录的最后一步损失不是同一个量。Adam 在这个配置下略好；把学习率或步数改掉，领先关系可能反转，所以 diff 必须与 LR=0.1、STEPS=30 一起读。

第四组是状态与配置：restored_diff=0.000000 证明 state_dict 往返无损；lr_end=0.012500 钉死调度器的折半次数；sd_keys:['linear.weight', 'linear.bias'] 把账本键名摆出来；w:[0.075538, 0.462384] 与 b:[0.396496] 则给出 Adam 最终停在什么位置。后三行里只有 lr_end 参与容差对账，另外两行是冒号文本——闸门对它们做的是逐字比较，任何空格或顺序变化都会被抓住。

把四组连起来，这个实验的论证链是闭合的：起点相同 → 单步等价 → 多步分化 → 状态可恢复 → 配置可复现。少掉任何一组，你都无法排除「差别来自别处」这个解释。这也解释了为什么清单里要写十个黄金值而不是一个：单个数字吻合可能是巧合，十个数字同时吻合才构成证据。

你若要把这套办法搬到自己的实验里，可以先问一句「哪一行变了我会怀疑程序坏了」，把那一行单独打成六位小数写进清单；再问「哪一行只是给人看的说明」，把它写成冒号文本逐字对账。前者进 expect.numbers，后者留在 output 块里，两种待遇不要混。黄金值不是把答案抄进清单就算完——它必须来自一次真实运行，并且能在代码改动后敏感地失败。一个永远不会失败的黄金值，和一个没有黄金值一样，都证明不了任何东西。

最后提醒一句关于时间的账：框架替你收走的是样板代码，不是计算。30 步训练在这台机器上几秒就跑完，换成几百万步、几亿参数，优化器状态与自动建图的开销就会成为主要成本。理解每一步到底做了什么，才能在成本失控时知道该动哪里，而不是只会改学习率碰运气。

7.13 三个变体：怎样设计能抓住错误的对照

实验的可信度不来自「跑通了一次」，而来自「某些写法一改就会失败」。这里给出三个你马上可以动手做的变体，每一个都指向一条具体的错误链。

第一个变体是把两份 load_state_dict(init_state) 改成同一个模型对象。你会看到程序仍然打印出两个损失，但它们的差不再只来自优化器：两个优化器交替改同一批参数，后跑的 Adam 接手的是已经被 SGD 推过 30 步的位置。diff 依然是个有限的数，看不出异常；但 adam_first 不再等于 sgd_first 与 init_loss，起点证据那一组三行会立刻分岔。所以清单里同时钉三个起点值不是冗余——它是这条对照的探测器。

第二个变体是把 zero_grad() 注释掉。前几步 loss 确实会下降，甚至比正常情况更快，这正是它有欺骗性的原因。跑满 30 步后，sgd_loss 与 adam_loss 会明显偏离黄金值，闸门报 numeric_value_mismatch。注意闸门不会告诉你「忘了 zero_grad」，它只说数值不符；把现象翻译成原因，靠的是你理解梯度累加这条机制。机器负责发现不一致，人负责解释不一致。

第三个变体是把 StepLR 的 scheduler.step() 从更新后挪到更新前。程序照跑、sd_keys 不变、w 与 b 变了，lr_end 从 0.012500 变成 0.025000。这一行的黄金值就是专门钉调度次序的。若你只钉最终 loss，调度次序改了但 loss 偶然接近，闸门会漏判；多钉一个配置量，就把这条漏判堵上了。

实验记录变体实验怎么做才有证据

  • 用 node build/run.js --unit pb07-module 看失败码：黄金值超差是 numeric_value_mismatch，行数变了是 numeric_line_mismatch；
  • 只改正文 output 块去迁就新数字会报 stale_output，因为正文必须与真实 stdout 逐字一致；
  • 改动后若决定保留新行为，先重跑程序拿真实 stdout，再更新清单的黄金值，最后重跑 render 与 run 两条闸门。
大白话为什么「跑通」不等于「正确」

程序退出码 0 只说明它没有崩溃。梯度累加、起点不同、调度次序错位，这些错误都不会让 Python 抛异常，它们只会悄悄改变数字。数值模式的清单正是为这类沉默错误准备的：把关键中间量和最终量都写成黄金值，让「数字变了」这件事变成机器能看见的失败。你负责挑哪些数字值得钉，闸门负责每次都替你核对。

把这一单元和下一单元接起来：这里我们已经会让框架登记参数、更新参数、调度学习率，但网络仍然是普通矩阵乘法。下一单元转向注意力：把 Q Kᵀ / √d 的softmax 乘 V 用框架写出来，并与线性代数分册的 Wq/Wk/Wv 对上号。两件事的共同点是：先手写一遍看清数值从哪来，再让框架接管重复的样板。

小结这一节的要点
  • 继承 nn.Module 后，赋值给属性的 nn.Linear 会自动登记进 parameters()；优化器拿的是参数引用，不是快照；
  • state_dict() 的键名来自「属性路径 + 参数名」，本例是 linear.weight 与 linear.bias；深拷贝才能保证两条训练路径同起点；
  • SGD 的一步等价于 p.sub_(lr * p.grad)，manual_step_diff=0.000000 是两条独立路径对账出来的证据；
  • Adam 多存一阶矩与二阶矩，逐坐标归一化步长；本例 sgd_loss=0.004384、adam_loss=0.003682、diff=0.000701，领先关系依赖具体学习率；
  • StepLR(step_size=10, gamma=0.5) 在 30 步里折半三次，lr_end=0.012500；训练后重新前向得到的 restored_diff=0.000000 证明快照加载无误；
  • 三种随机源一起固定、入口 import 本地模块、数值与张量分行打印，是可复现实验的三根钉子。

注自测题答案
  1. nn.Module 的赋值钩子会把注册过的 Parameter 收进内部字典，parameters() 按注册顺序遍历它。漏掉 super().__init__()，登记表还没初始化，注册会失败；靠继承拿到登记能力，而不是靠类名字里带 Module。
  2. detach() 把张量从计算图摘下来，避免快照带着前向图；clone() 复制出独立存储，避免两个模型共用同一块内存。只 detach() 不 clone()，两个模型参数同源，SGD 一走 Adam 的起点也变了；只 clone() 不 detach()，克隆体仍挂在图上，保存与比较都可能出问题。
  3. 它是从 stdout 解析出的数值，闸门拿清单里的黄金值 0.0 与 atol=1e-6 重算差值，超差报 numeric_value_mismatch；两条独立计算路径给出同一个数，才排除了「同一公式自己验证自己」。自报 PASS 只是字符串，不携带可复算的数值与容差。

  5. 0.1 × 0.5³ = 0.012500，因为第 10、20、30 步各触发一次折半。若顺序颠倒，第一步就用折半后的学习率，30 步只折两次，lr_end 会变成 0.025000；框架不报错，只有黄金值对账能抓住。
  6. 模型参数回来了，但 Adam 的一阶矩、二阶矩和步数没回来，第一步的矩估计从零开始，步长分布与中断前不同。检查点还应包含 optimizer.state_dict()、scheduler.state_dict() 与当前步数；代价是文件更大、与框架版本耦合更强。

从矩阵到注意力：softmax(QKᵀ/√d)V 用框架怎么写

学习目标看完这一单元，你应该能

  • 手写缩放点积注意力的五步：点积、除以 √d、掩码、softmax、乘 V；
  • 解释 √d 缩放为什么能防止 softmax 饱和，以及掩码为什么用负无穷而不是零；

  • 推导注意力的 O(n²d) 复杂度，说清长序列为什么贵；
  • 用真跑的 stdout 对账 out00、out01、attn00、diff，知道黄金值只能写在清单里。

8.1 先看工程长什么样

线性代数分册里已经把注意力拆成过矩阵：输入 X 分别乘 Wq、Wk、Wv 得到 Q、K、V，再算 QKᵀ、做 softmax、乘回 V。那时我们只关心「这些矩阵乘出来是什么」。这一单元要做的是同一件事的工程版：把每一步用 PyTorch 写出来，再让框架自己的 nn.MultiheadAttention 从旁边跑一遍，看两条路给出的数字是否一致。

例子仍然只有两个源文件。attn.py 装手写实现与固定的投影矩阵，main.py 负责调框架、打印数值。两个 token、四维嵌入——小到能逐格手算，又足够撑起所有形状关系。

第 1 帧是讲故事用的起点。第 2 帧里多了 torch_attention/，结构与上一单元刻意保持一致：入口编排流程，本地模块提供可复用的函数，清单声明证据。第 3 帧把目录外壳去掉，只看 from attn import ... 这条边——本地模块放在 src/ 下，靠 python src/main.py 时自动加入的模块搜索路径找到它。

大白话注意力一句话在说什么

给序列里每个位置发一张问询卡（Q）、一张身份证（K）和一份可提取的内容（V）。某个位置拿着自己的问询卡去和所有位置的身份证做匹配，匹配分数越高，就从那个位置的内容里取越多。所谓「注意力权重」就是这份取用的比例，加起来等于 1。softmax 负责把它们变成合法比例，√d 负责让分数别太夸张。

8.2 先有 Wq/Wk/Wv：输入被复制成三个角色

注意力的输入 X 是一张 n×d 的表：n 行是 token，d 列是嵌入维度。同一份 X 要扮演三种角色，所以要乘三张不同的矩阵。本例把三张矩阵写死成常量，避免随机初始化把对账弄脏。

第 19 行的注释「行是输出维、列是输入维」是理解整套约定的钥匙：矩阵 wq[i, j] 说的是「第 j 个输入分量对第 i 个输出分量的贡献」。线性代数分册习惯写 Q = XWq，那是把 Wq 存成「列是输出维」的形状；PyTorch 的 nn.Linear 存的是「行是输出维」的形状，于是前向写成 XWᵀ。两者是同一张矩阵的不同摆放方式，不是两套数学。

第 43 行的 @ 是矩阵乘法，x @ wq.T 把 2×4 的 X 变成 2×4 的 Q。三张矩阵都用 torch.tensor([...]) 直接给出，没有随机性；种子照样固定，是为了让整个工程保持可复现的纪律，而不是因为这里真的用到了随机数。

第 1 帧强调投影矩阵是 4×4：输入四维、输出也四维，所以形状不变。第 2 帧强调 Q、K、V 都从同一个 X 来——它们不是三份独立数据，而是同一份数据的三种看法。若你把 d_q 与 d_k 设成不同维度，前三步的矩阵形状仍能对上，只是那时要为每个 head 单独记维度；本例为了手算方便让它们相等。

陷阱把 Wq/Wk/Wv 存反了，数字全变但程序不报错

你会看到：程序正常退出，输出也是漂亮的六位小数，只是与线性代数分册手算的结果对不上。你会怀疑 softmax 写错了，或者怀疑浮点精度。真相是：把 Wq 当成「列是输出维」直接写 x @ wq，等于用了 Wqᵀ，投影结果整体转置了一项。框架里 nn.MultiheadAttention.in_proj_weight 按 [Wq; Wk; Wv] 纵向拼接，每一块都是「行是输出维」。本例把矩阵写死并在注释里钉死这个约定，就是为了让这种错位一眼能查出来：拿第 0 行的 Q 手算一遍，看是否等于 q00=0.750000。

8.3 手写五步：从分数到输出

投影做完，剩下的就是注意力的核心。代码把「算分数」和「分数变输出」拆成两个函数，好处是掩码可以单独插进第一步，而 softmax 与乘 V 的逻辑不需要改。

第 49 行的 k.transpose(-2, -1) 把 K 从 2×4 变成 4×2，于是 Q(2×4) 乘 Kᵀ(4×2) 得到 2×2 的分数表——第 i 行第 j 列就是「第 i 个 token 对第 j 个 token 的匹配分」。除以 math.sqrt(d) 就是 √d 缩放，本例 d = 4，所以除以 2。第 51 行把掩码位置填成负无穷，softmax(-∞) = 0，这些位置从此不参与取用。第 57 行的 dim=-1 指定沿最后一维做 softmax：每一行独立归一化，行的和等于 1。第 58 行用权重乘 V，2×2 乘 2×4 得 2×4 的输出。

为什么非要除以 √d？假设 q 和 k 的每个分量是独立同分布、均值为 0 方差为 1 的随机数，那么点积 q·k = Σᵢ qᵢkᵢ 的方差随 d 线性增长。d 大时，分数的量级会很大，softmax 进入饱和区：最大值几乎吃掉全部概率，其余位置接近 0。饱和的 softmax 梯度极小，反向传播几乎传不回去，训练就卡住了。除以 √d 把分数的方差拉回 1 附近，既保留区分度，又让梯度活着。这不是为了好看，是为了反向传播能工作。

第 1 帧的节点名 scores(2,4→2) 是在说形状从 2×4 与 4×2 的乘法收缩成 2×2；第 2 帧只换了一样东西——分数变成权重；第 3 帧把 V 拉进来，输出才出现。三帧合起来读，你就得到了那句熟悉的公式：softmax(QKᵀ/√d)V。

大白话负无穷不是「一个很大的负数」

掩码的实现写的是 float("-inf")，这不只是偷懒。softmax 的分母要算 e 的幂次，任何有限的负数都会给出一个虽然很小但非零的概率；只有负无穷的指数严格为 0。换句话说，用 −1e9 当掩码在数学上只是「几乎屏蔽」，用 −∞ 才是「完全屏蔽」。本例输出 mask01=0.000000，六位小数上两者看不出差别，但语义差了一层。

8.4 掩码：让某些位置「不可见」

掩码是一张布尔表，形状通常和分数表一样是 n×n。本例的 mask = [[False, True], [False, False]] 表示：第 0 个 token 不许看第 1 个，第 1 个 token 两个都能看。这是因果掩码的最小版本——预测第 t 个词时只能看到它自己与之前的词。

第 45 行的布尔值含义要记牢：在 PyTorch 的 attn_mask 里，True 表示这个位置不允许被注意。这与某些库里「1 表示保留」的约定正好相反，是新手最常踩的反直觉点。第 46 行把同一张表交给手写实现，masked_fill 对 True 的位置填负无穷，语义一致。第 48 行交给框架，第 49 行取最大绝对差当证据。

真跑给出 mask00=1.000000、mask01=0.000000：第 0 个 token 只能看自己，于是它的全部权重都落在第 0 列。mask_diff=0.000000 说明手写与框架在掩码情形下也一致。注意这只覆盖了布尔掩码；浮点掩码（在分数上加一个偏置）语义不同，别混着用。

陷阱把掩码当成「给分数乘零」

你会想当然地以为「屏蔽就是把这个位置的分数乘 0」，于是写出 scores = scores * (~mask)。你会看到输出确实变了，但权重不再满足每行和为 1，而且被屏蔽位置得到一个等于 e⁰ = 1 的未归一化贡献——它在 softmax 分母里照样占一份。真相是：屏蔽必须发生在 softmax 之前，且要让该位置的指数严格为 0，所以填负无穷而不是乘零。另一个相邻陷阱是掩码形状写反：[[True, False], [False, False]] 屏蔽的是第 0 行第 1 列以外的位置，语义完全变了。

8.5 框架版：把同一组 Wq/Wk/Wv 塞进 MultiheadAttention

nn.MultiheadAttention 默认自己随机初始化投影矩阵。如果我们直接调用它，输出当然和手写版对不上——那样的比较毫无信息量。正确做法是把本例写死的 Wq/Wk/Wv 拷贝进框架，再把输出投影设成单位阵，让两条路唯一可能的差别只剩实现细节。

第 20 行把头数设成 1，这样框架的注意力权重就是一张 2×2 的表，和手写版形状一致；batch_first=True 让输入形状写成 (batch, 序列长度, 嵌入维)。第 22 行的 torch.cat([wq, wk, wv], dim=0) 按行把三张 4×4 拼成 12×4，这正是框架内部的存法。第 24 行把输出投影设为单位阵：如果留着随机初始化，框架输出会再乘一张随机矩阵，差自然很大，但你根本分不清差来自输入投影还是输出投影。

调用部分也很短。

第 31 行是两行四列的输入；第 34 行手写版直接吃二维张量，第 36 行框架版要一个 batch 维，所以第 39 行 unsqueeze(0) 把它变成 (1, 2, 4)，算完再 squeeze(0) 收回二维。第 41 行的三个 xb 分别是 query、key、value——本例是自注意力，三者同源；换成编码器—解码器注意力，query 来自目标序列、key 与 value 来自源序列。第 43 行的 diff 取所有输出元素里最大的绝对差，比只看某一个元素更严格。

8.6 复杂度：为什么长序列贵在 n²

注意力的成本可以数乘法次数。设序列长 n、嵌入维 d：

  • QKᵀ：矩阵 (n×d) 乘 (d×n)，每个输出元素要做 d 次乘加，共 n² 个元素，所以约 n²d 次运算；
  • softmax：对每个分数做指数与归一化，约 n² 次，不含大矩阵乘法；
  • 权重乘 V：(n×n) 乘 (n×d)，同样是 n²d 次运算。

合计是 O(n²d)。本例 n = 2、d = 4，前一步 2×2×4 = 16 次乘加，后一步也是 2×2×4 = 16 次，总共 32 次——小到你能在纸上数完。把序列长度从 2 加到 2000，其他不变，成本不是涨 1000 倍，而是涨约一百万倍；这就是长上下文模型的注意力层成为瓶颈的原因。

第 2 帧是本单元最该记住的一张图：QKᵀ 产生一张 n×n 的表，序列里任意两个位置都有一格，这就是「二次」的来源。第 3 帧把信息压回 n×d，形状回到输入的样子，所以注意力层能一层层堆起来。

工程惯例为什么生产环境不直接物化这张 n×n 表

n = 4096 时，一张 float32 的分数表约 64 MB，仅一层的一个 head 就占这么多；几十层、几十个 head 会把显存吃光。工程惯例是用 FlashAttention 这类「分块计算、不落盘整张表」的实现：数学上还是 softmax(QKᵀ/√d)V，但只在片上算一小块就立刻累积结果，省掉显存往返。这是惯例而非标准，代价是实现复杂、对硬件依赖强；收益是长序列能跑得动。本例故意把整张表算出来，因为它只有 2×2，正好能看清每一步。

8.7 手算核对：从 q00 到 out00 的完整链路

这一节把 stdout 里的每个数字用手算对一遍，证明框架没有在背后偷偷改公式。

x₀ = [1.0, 0.5, −0.5, 1.0]。按第 43 行的 x @ wq.T，q₀ 的第 0 个分量是 x₀ 与 Wq 第 0 行的点积：1.0×1.0 + 0.5×0 + (−0.5)×0.5 + 1.0×0 = 0.75，正是 q00=0.750000。同法可得 q₀ = [0.75, 1.0, 0, 1.25]；再从 Wk 得 k₀ = [0.75, 0.25, 0, 1.5]，所以 k00=0.750000。

点积 q₀·k₀ = 0.75×0.75 + 1.0×0.25 + 0×0 + 1.25×1.5 = 2.6875。第 49 行除以 √4 = 2，得 score00=1.343750。这一除不是装饰：不除的话分数是 2.6875，softmax 会更尖锐，权重会从 0.737 推向更接近 1 的位置，小梯度的风险随之上升。

再算第 0 行第二个分数：q₀·k₁ = 0.75×0.5 + 1.0×1.5 + 0×0.5 + 1.25×(−1.0) = 0.625，除以 2 得 0.3125。于是第 0 行的两个分数是 [1.343750, 0.3125]，指数后归一化给出 attn00=0.737158、attn01=0.262842，两者相加为 1（六位小数上恰好 1.000000）。

V 的第 0 行是 [0.5, 1.0, 0, 0.75]，第 1 行是 [1.0, 0, 0.5, −0.5]。按第 58 行加权求和：out₀₀ = 0.737158×0.5 + 0.262842×1.0 = 0.631421，正是 out00=0.631421；out₀₁ = 0.737158×1.0 + 0.262842×0 = 0.737158，正是 out01=0.737158。两格都对上，再加上 manual:[...] 与 fw:[...] 四格全同，这条从输入到输出的链就闭合了。

陷阱手算时最容易在转置和归一化上翻车

第一种错：算 q₀·k₀ 时用 Wk 的列而不是行，得到的不是身份证匹配分，而是另一组投影的组合。记住第 43 行投影完的 Q、K 已经是 2×4，分数是这两张表的行向量点积，不需要再回头碰 Wq/Wk。第二种错：softmax 沿错了维度。dim=-1 是让每一行独立地归一化；若写成 dim=0，归一化发生在列上，第 0 行的两个数不再和为 1，attn00 + attn01 = 1 这条手算核对立刻失败。第三种错：忘了缩放，直接拿 2.6875 和 0.625 去 softmax；程序照样跑，但 score00 对不上，闸门会报 numeric_value_mismatch。

8.8 多头、批量与形状：框架多做了什么

本例把头数设成 1，是为了让手写与框架的权重表能一一对齐。多头注意力做的事情并不神秘：把 d 维切成 h 份，每份用自己的一组 Wq/Wk/Wv 独立算注意力，最后把 h 份输出拼起来再乘一张输出投影矩阵。h = 1 时这套机制退化成我们手写的版本——这就是为什么本例能把 diff 做到 0。

框架的输入输出形状也值得钉死。batch_first=True 时输入是 (N, L, E)，N 是批量、L 是序列长度、E 是嵌入维；输出同形状。need_weights=True 才会返回注意力权重，形状是 (N, h, L, L)。本例 unsqueeze(0) 造出 N = 1，squeeze(0) 又去掉它，所以你看到的 attn:[...] 只是第 0 个 batch、第 0 个 head 的那一行。若把 average_attn_weights 打开（默认行为之一），多头的权重会被平均成 (N, L, L)，这在多头情形下只是一张摘要表，不再是某个 head 的真实权重。

大白话为什么输出还要再乘一张 W_o

注意力输出是多头结果的拼接，每个头学到的「取什么信息」未必在同一个坐标系里。乘一张输出投影 W_o 相当于给它们换到统一的坐标，让下一层能统一处理。本例把它设成单位阵，等于宣布「这一步不重要，别让它干扰对账」。真实模型里 W_o 是学出来的，不能随便丢。

8.9 打印纪律：张量走冒号，标量走等号

这一单元的 stdout 有 15 行，其中十行是 key=0.123456 形状的标量，三行是 attn:[...] 这类冒号文本。分界不是审美问题，而是闸门的解析规则：它把形如 key=value 且 value 是有限十进制数的行当数值行，拿清单里的 atol=1e-6 重算差值；其它行按文本逐字对账。张量里带逗号，若写成 out=0.631421, 0.737158, ... 会被判成 numeric_value_invalid。

标量里也分两类。q00、score00、attn00、out00 是手写路径的中间量与输出；fw00 是框架路径的输出；diff 与 mask_diff 是两条路径的差距；mask00、mask01 是掩码后的权重。清单为每一行都写了黄金值，所以改任何一步实现，闸门都能指出是哪一类量先变了。正文里写「大约相等」没有精度承诺，只有清单里的 atol 才是机器可执行的证据。

选这些量还有一层考虑：它们分布在计算链的不同位置。q00 在最上游，score00 在缩放前后之间，attn00 在 softmax 之后，out00 在最下游，diff 横跨两种实现。中间的某一步写错时，下游数字当然也会错，但上游黄金值先失败能帮你少走很多弯路。设计自己的实验时，也别只钉最终 loss——沿链路每隔几步钉一个量，排查成本会低得多。

8.10 softmax 的数值稳定：框架替你减了最大值

第 57 行调用的 F.softmax 看着只是「指数、求和、相除」，但框架在里面多做了一步保命的操作。朴素写法是 exp(xᵢ)/Σⱼ exp(xⱼ)：当某个分数大到几百，exp(500) 会溢出成正无穷，分子分母都是无穷，结果变成 NaN；当所有分数都很负，exp(−1000) 全部下溢成 0，分母为零，同样得到 NaN。注意力分数经过 √d 缩放后一般落在几到几十的量级，离溢出很远，但你也见过那些因为一行坏数据就把 loss 打成 NaN 的训练——softmax 往往是第一个倒下的地方。

稳定写法先减去这一行的最大值：m = maxⱼ xⱼ，然后算 exp(xᵢ − m)/Σⱼ exp(xⱼ − m)。数学上分子分母同乘 exp(−m)，结果完全不变；数值上最大的那个指数变成 exp(0) = 1，其余都是小于等于 1 的数，永远不会溢出，至少有一项不为零，分母也不会下溢成 0。F.softmax 内部正是这么做的。

拿本例第 0 行核对一遍：分数是 [1.343750, 0.3125]，最大值 m = 1.343750。减去最大值后变成 [0, −1.03125]，指数约是 [1, 0.3568]，归一化得 1/1.3568 ≈ 0.737 与 0.3568/1.3568 ≈ 0.263，正是 attn00=0.737158、attn01=0.262842。减与不减在数学上是同一件事，但只有减了之后这套计算对大数也是安全的。

陷阱手写 softmax 时漏掉减最大值

你会看到：小输入的测试全过，一旦换成量级大一点的分数，输出突然全是 NaN，你可能怀疑是 learning rate 爆炸或者数据里有 inf。真相常常是自己写的 softmax 直接对原始分数取指数，溢出之后 0/0 变成 NaN，再传到损失里一路污染。判断方法是把这行的最大分数打印出来：如果它已经到了几百的量级，先给 softmax 减最大值。本例直接调用 F.softmax，这层保护已经替你做了——这也是为什么我们说「框架收走了样板代码」有时还包括你根本想不到的数值防御。

8.11 三种掩码：同一个位置，三种「不许看」

掩码不是一个单一概念。按用途分，最常见的有三类，它们的形状和取值约定各有讲究。

第一类是因果掩码，本例用的就是它。第 t 个位置只能看 0 到 t 位置，不能看未来。n×n 的布尔表里，上三角（不含对角线）为 True，本例 n = 2 时就是 [[False, True], [False, False]]。它让自回归生成成为可能：预测第 t 个词时，模型看不到后面的答案。

第二类是填充掩码。一个 batch 里句子长短不一，短句尾部要补占位符，这些位置不该被注意。常见写法是生成一个长度为 n 的布尔表，占位位置为 True，再广播成 n×n——每个 query 都不能看占位位置。它与因果掩码可以叠加：逻辑或起来就是「既不能看未来，也不能看占位」。广播这一步很容易写错形状，尤其当框架要求掩码形状是 (N, h, L, L) 时，少一个维度就会报形状错或悄悄按错误方向广播。

第三类是自定义块掩码。比如图结构数据里只让相连节点互相注意，或者文档里只让同一段落的 token 互看。这类掩码不再是简单的三角形状，而是一张由业务规则算出来的 n×n 表；本例的 masked_fill 照样适用，只要布尔语义一致。

还要区分布尔掩码与浮点掩码。本例传的是布尔表，True 表示屏蔽；有些接口接受浮点表，直接把它加到分数上，此时 0 表示不屏蔽，一个很大的负数表示屏蔽。两者语义相反，混用会让「加掩码」变成「只注意被屏蔽的位置」，而且不一定报错。本例在两个路径里都使用布尔语义，并用 mask_diff=0.000000 把这条约定钉死。

大白话掩码为什么要作用在分数上，而不是输出上

输出是「从 V 里按权重取内容」，权重由 softmax 决定。想让某个位置完全不被取用，就要让它的权重严格为 0；权重是 softmax 算出来的，所以必须在 softmax 之前动手。填负无穷正是让指数严格为 0 的办法。若等输出出来再把那一格乘 0，权重本身仍然不对，你只是把错误的取用结果抹掉了——训练时的梯度依然会告诉模型「去看那个位置」，下一次它还会犯错。

8.12 从单头到多头：形状账本再推一遍

本例用 num_heads=1，是为了让手写与框架的权重能一一对齐。多头做了什么？把嵌入维 d 切成 h 份，每份 d_k = d/h，每个头用自己那一份 Wq/Wk/Wv 独立算注意力，最后把 h 份输出拼起来再乘输出投影。

形状账是这样的：输入 X 是 (N, L, d)；in_proj_weight 形状 (3d, d)，一次乘出 Q、K、V 各 (N, L, d)。接着把最后一维拆成 (N, L, h, d_k) 并转置成 (N, h, L, d_k)，让每个头单独算。分数是 (N, h, L, L)；权重同形状；每个头的输出是 (N, h, L, d_k)。最后转置回 (N, L, h, d_k)、摊平 h 与 d_k 两维得到 (N, L, d)，再乘 out_proj 的 (d, d) 矩阵。

算一笔复杂度账：每个头的 QKᵀ 约 L²d_k 次乘加，h 个头合起来是 h·L²d_k = L²d，与单头同阶；权重乘 V 同理。多头并没有省掉二次项，它省的是「所有信息只能挤在一个 d 维空间里做匹配」的限制：不同头可以关注不同关系，比如一个头盯句法相邻，另一个头盯指代回指。本例的 d = 4、h = 1 只有一个头，所以手写版与框架版的权重表都是 2×2，能直接相减。

框架还有一处细节值得知道：batch_first=True 决定输入的最前面一维是 batch；老代码里常见 batch_first=False，形状变成 (L, N, E)。本例手写版吃二维 (L, E)，框架版吃三维 (1, L, E)，靠 unsqueeze(0) / squeeze(0) 来回切换。这两个函数不复制数据，只改视图的 shape，所以没有额外成本；但形状写错时错误信息往往指向矩阵乘法而不是入口，调试时要从输入形状查起。

工程惯例为什么教学例子要把头数设成 1

因为多头会把权重表变成 (N, h, L, L)，手写版只实现单头，两者没法逐格相减。设成 1 之后，in_proj_weight 的三块与我们的 Wq/Wk/Wv 一一对应，out_proj 设成单位阵后输出也不再被二次混合，diff 才真的在衡量「手写数学对不对」。代价是你学不到多头 reshape 的细节——所以我们在正文里把形状账写清楚，而不是假装它不存在。做真实项目时，头数、隐藏维、层数都要通过实验定，不能照抄本例。

8.13 变体实验：哪些改动会让闸门变红

和上一单元一样，真正让实验可信的是「一改就失败」。这里列出四个你马上能做的变体，以及闸门会给出的具体码。

8.14 反向也能走通：注意力不是只能前向

本例在调用手写与框架注意力时都包了 torch.no_grad()，因为我们在做数值对账，不需要梯度，也就没必要为计算图付内存。可一旦把注意力放进真正的训练，这些包围圈就得去掉：Q、K、V 来自可学习的 Wq/Wk/Wv，softmax 的权重也是由它们算出来的，损失对投影矩阵的梯度必须沿着「输出 → 权重 → 分数 → Q/K → Wq/Wk」这条链一路传回去。

这条链上的每一步都是可微的。矩阵乘法 QKᵀ 对 Q 的导数是 K，对 K 的导数是 Qᵀ；除以 √d 只是乘常数；softmax 有自己的雅可比矩阵，PyTorch 已经实现好；乘 V 对 V 的导数就是权重表。你不需要手推这些导数，上一册手推的链式法则在这里由 autograd 自动完成——但要知道它们确实存在，否则「为什么 attention 层的参数能被训练」就成了一个黑箱。

陷阱为了让数字稳定，把 no_grad 包在了整个训练前向

你会看到：loss 打出来很正常，跑几百步也不降，检查参数发现 .grad 全是 None。你会怀疑数据标签错位、怀疑学习率。真相是前向被 no_grad() 包住，计算图根本没建，反向时无图可走。本例包 no_grad 只在「比较两个固定权重的实现」这个场景成立；写训练代码时，正确做法是先正常前向拿 loss、反向、更新，只在评估或计算指标时包 no_grad。判断方法很简单：在 loss 后打印 loss.requires_grad，训练路径应该是 True，推理路径才是 False。

工程惯例什么时候手写，什么时候调框架

手写一遍的价值在于你能指着 score00=1.343750 说清它从哪来，能在结果异常时定位到「是缩放漏了还是转置反了」。框架的价值在于它把多头 reshape、数值稳定、不同后端的高效算子都收走了，生产环境自己重写一遍既慢又容易错。本例的策略是「教学时手写一遍、对账时用框架复核」：两条路给出同一个 diff=0.000000，你既拿到了理解，也拿到了可以放心调用框架的证据。代价是要多写一个本地模块和多做一次对账，换来的是以后看到注意力变体时知道该改哪一步。

8.15 注意力在 Transformer 层里只占一块

学会了注意力，你可能以为它就是 Transformer 的全部。其实一层标准的 Transformer 编码器通常由几块拼成：先是多头自注意力，然后残差连接与层归一化，再过一个逐位置的前馈网络（通常是两层线性加激活），最后再来一次残差与归一化。注意力负责「让不同位置交换信息」，前馈网络负责「对每个位置单独加工」，残差负责让梯度有直达通道，层归一化负责稳住数值尺度。

本例只实现了第一块，原因很实际：其余部件不涉及新的数学思想，而且会把对账链条拉长。你可以把注意力输出 manual:[0.631421, ...] 想成第一块交出的结果；下游的残差会把它与原来的 X 相加，前馈网络再对每个四维向量单独处理。所有后续操作的形状仍然是 (n, d)，所以本单元建立的形状账本能一直用下去。

这也解释了为什么复杂度讨论要盯住 n²：前馈网络的成本是 O(nd²)，与序列长度线性相关；注意力的 O(n²d) 才会随着上下文变长反超。短序列时前馈甚至可能是大头，长序列时注意力必然成为瓶颈。任何「优化 Transformer」的说法都要先说明优化的是哪一块、在什么长度下成立，否则就是空话。

判断一个性能改进是否真的有效，也要落到数字上：固定批量、序列长度与头数，记录前向耗时与显存峰值，再改一处重测。只看「感觉更快了」很容易被测量噪声误导；把配置与结果写进实验记录，别人才复现得出你的结论。本单元的小例子跑不出有意义的性能数字，它的任务是把形状与数值链讲清，为以后读懂那些优化留出抓手。

大白话为什么要残差与归一化

深层网络里，梯度从最后一层往回传时要连乘很多 Jacobian，容易越乘越小（消失）或越乘越大（爆炸）。残差连接给梯度开了一条「绕过这一层」的直路，像给山路修了一条平缓的辅路。层归一化则把每一层的输出拉回相近的量级，让后面的层不必反复适应新的尺度。两者都不是注意力的一部分，但缺了它们，几十层注意力很难训得动。

把这一单元与线性代数分册接起来：那边教的是「注意力就是三组投影加两次矩阵乘加一次 softmax」，这边教的是「同一套数学写成 PyTorch 会长什么样，以及框架替你做了哪些形状搬运」。真正的新东西只有 √d 缩放、掩码语义和 O(n²d) 的成本意识；矩阵乘法与 softmax 还是你早就认识的那两个操作。

小结这一节的要点
  • X 乘 Wq/Wk/Wv 的转置得到 Q、K、V；三张表形状都是 n×d，PyTorch 的存法是「行是输出维」，与线性代数分册的写法差一次转置；
  • 手写五步是点积、除以 √d、掩码、softmax、乘 V；缩放把分数方差拉回 1 附近，避免 softmax 饱和吞掉梯度；
  • 布尔掩码里 True 表示禁止注意，靠 masked_fill(-inf) 让 softmax 给出严格的 0；本例 mask00=1.000000、mask01=0.000000；
  • 把同一组投影矩阵拷进 nn.MultiheadAttention 并把输出投影设为单位阵后，两条独立路径给出相同结果：out00=fw00=0.631421、diff=0.000000；
  • 分数表是 n×n，所以注意力复杂度是 O(n²d)；本例 n = 2、d = 4，共约 32 次乘加；
  • 标量用 key=0.123456、张量用冒号文本，黄金值与容差只写在清单，diff 这类比较量必须来自真跑。

注自测题答案
  1. PyTorch 的 nn.Linear 把矩阵存成「行是输出维、列是输入维」，所以前向是 xWᵀ；线性代数分册把 Wq 存成「列是输出维」，写法是 XWq。两者是同一张矩阵转置后的两种摆放，投影结果相同，但把矩阵元素抄错位置会让结果整体转置。
  2. x₀ = [1.0, 0.5, −0.5, 1.0]，Wq 第 0 行是 [1.0, 0, 0.5, 0]，点积为 1.0 − 0.25 = 0.75，即 q00=0.750000。k₀ = [0.75, 0.25, 0, 1.5]，q₀·k₀ = 0.5625 + 0.25 + 1.875 = 2.6875；除以 √4 = 2 得 1.343750，与 score00 一致。
  3. q 与 k 的点积方差随 d 增长，d 大时分数很极端，softmax 进入饱和区，几乎把所有概率给一个位置，其余位置的梯度趋近于零，训练就传不回梯度。除以 √d 把方差拉回 1 附近，保留区分度也让梯度存活。
  4. True 表示这个位置禁止被注意。softmax(-∞) = 0 是严格为零；乘零只会让分数变成 0，指数 e⁰ = 1 仍在分母里占份额，权重不再和为 1。本例掩码后第 0 行权重是 [1.000000, 0.000000]。
  5. 框架默认随机初始化投影与输出投影。若只调用而不拷贝，输出会经过另一组随机矩阵，差来自初始化而非实现，对照没有信息量；拷贝同一组 Wq/Wk/Wv、把输出投影设成单位阵后，两条路的唯一差别才是实现细节，diff 才是对账证据。
  6. QKᵀ 是 (n×d)(d×n) → n×n，约 n²d 次乘加；权重乘 V 是 (n×n)(n×d) → n×d，也约 n²d 次；softmax 是 n² 量级。总成本 O(n²d)，序列长扩大 10 倍、d 不变时成本约涨 100 倍。
  7. 闸门把 key=value 当数值行解析，张量那一串逗号不是有限十进制数，会报 numeric_value_invalid。冒号文本按字面量逐字对账；真正参与容差比较的标量单独打成六位小数，例如 attn00=0.737158。
