1.1 先讲动机：为什么需要一条工具链

写一个 Rust 程序，表面上看只是「把文本变成能运行的二进制」。但真正让人头疼的从来不是语法本身，而是依赖怎么管、不同机器怎么保持一致、代码风格怎么统一、常见错误能不能早点被发现。Rust 的答案是把这些问题交给一条配套的工具链，而不是让你自己拿一堆脚本去拼。

对初学者来说，最大的认知负担往往来自「我到底该敲哪条命令」。rustc、cargo、rustfmt、clippy 这四个名字会反复出现，它们不是互相竞争的替代品，而是分工明确的协作者。先记住一句话：rustc 负责把源码编译成程序，cargo 负责组织项目和依赖，rustfmt 负责排版，clippy 负责挑刺。剩下都是细节。

大白话先用直觉把它讲通

把写程序想成开一家小饭馆。rustc 是灶台，真正把食材做熟；cargo 是店长，管进货、排班、下单；rustfmt 负责把桌子擦得整整齐齐；clippy 像一位挑剔的美食评论家，专门提醒你「这样写能吃，但不够好」。你不用亲自当灶台，但要认识每位伙计。

安装 Rust 时通常会用到 rustup，它是工具链的安装与切换器，负责把上面这些工具装到你的机器上，并让你在不同版本之间切换。注意 rustup 本身不是编译器，它只是「装工具的工具」。真正决定代码语义的是「edition（版本）」：Rust 从 2015 到 2021（再到更新的版本）经历过几次语言级演进，edition 用来标记一套语义规则。新项目几乎都该选 2021，这也是本系列默认使用的版本。

为什么要在命令里显式写 edition？因为省略时，不同版本的 rustc 可能采用不同的默认 edition，导致同一份代码在不同机器上的行为有细微差别。编译期把这个选择写死，是一种很便宜的「可复现性」投资。尤其在团队里或者 CI（持续集成）环境中，可复现比「在我机器上能跑」重要得多。

1.2 rustc：把源码变成可执行文件

rustc 是 Rust 的编译器，它接收一个 .rs 文件，输出可执行文件或库。最小的一段程序只需要一个 main 函数——它是程序执行的入口，程序从这里开始、在这里结束。注意 Rust 用 println! 结尾的感叹号表示这是一个宏（macro），而不是普通函数。宏在编译期展开，能做一些函数做不到的事，比如接受可变数量的参数、对格式字符串做静态检查。

下面这段代码不依赖任何外部库，只用标准库 std，可以直接交给 rustc 编译。试着把它存成 main.rs，然后编译运行。标准库是随语言一起分发的，任何符合规范的 Rust 环境都自带它，不需要额外下载。

rustRust · 标准库6 行
fn main() {
println!("Hello, Rust!");
let a = 7;
let b = 9;
println!("{a} + {b} = {}", a + b);
}

编译和运行的过程如下。这里显式写 --edition 2021，是为了锁定语言版本；-o hello 指定输出文件名。如果不写 edition，rustc 会用默认的 edition（新版本工具链通常是 2021 或更高），显式声明能让行为更可预期。

终端真跑一遍
$ rustc --edition 2021 main.rs -o hello
$ ./hello
Hello, Rust!
7 + 9 = 16

{a} 这种写法叫「格式化参数隐式捕获」，编译器会从当前作用域里找同名变量填进去，从 Rust 1.58 起就稳定可用。它比 println!("{} {}", a, b) 更好读，因为变量名直接写在字符串里，改代码时不容易对错位置。还有一个细节：格式字符串里的 {} 会在编译期被检查，如果占位符数量和传入参数对不上，编译器直接报错，而不是等到运行时才打出奇怪的结果。这种「把错误挡在编译期」的思路，是 Rust 一贯的风格。

编译器的错误信息也值得专门提一句。Rust 的错误提示以详细著称，它不仅告诉你哪一行出错，还常常给出修改建议，甚至用彩色箭头标出问题位置。初学时不要害怕报错，把报错当成一对一的辅导老师：读懂它、按它说的改，往往比到处搜答案更快的提升方式。

1.3 cargo：项目管家与构建系统

单个文件用 rustc 足够，但项目一旦有依赖、有多个源文件、有测试和构建配置，手敲 rustc 命令就会迅速失控。你要记住每个依赖的版本、文件路径、编译参数，还要保证同事的机器上命令完全一致。cargo 是 Rust 的包管理器和构建系统，它约定了一套目录结构，你只要把文件放对位置，剩下的交给它。

下面是四个工具的职责对照，建议先有个整体印象。

工具 角色 你最常敲的命令
rustc 编译器，把源码变成二进制 rustc --edition 2021 main.rs
cargo 包管理器与构建系统 cargo new、cargo build、cargo run、cargo check
rustfmt 格式化工具，统一排版 cargo fmt
clippy 静态检查，给出改进建议 cargo clippy

用 cargo new 创建项目，cargo 会帮你生成目录和一个能跑的「Hello, world!」。注意项目名里如果带连字符，例如 hello-rust，生成的目标名会换成下划线 hello_rust，这是 Rust 标识符的规则所致。如果是在已有目录里初始化，用 cargo init 而不是 cargo new，区别只在于是否新建一层文件夹。

终端真跑一遍
$ cargo new hello_rust
Created binary (application) `hello_rust` package
$ cd hello_rust
$ cargo run
Compiling hello_rust v0.1.0 (.../hello_rust)
Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.42s
Running `target/debug/hello_rust`
Hello, world!

上面 cargo run 的输出里，编译耗时和具体路径因机器而异，属于示意输出。目录结构里，Cargo.toml 是清单文件，记录项目名、版本和依赖；Cargo.lock 锁定依赖的具体版本，保证每次构建拿到同样的依赖树；src/main.rs 是二进制入口；target/ 放编译产物，通常不用手动碰，也能随时删掉让 cargo 重新生成。cargo check 只做类型检查不生成二进制，日常开发里它比 cargo build 快得多，适合频繁调用；确认无误后再用 cargo build 或 cargo run 生成程序。

依赖写在 Cargo.toml 的 [dependencies] 段落里，cargo 会从官方仓库拉取并解析版本。版本号遵循语义化版本规范，cargo 在兼容范围内选择最新可用版本，而 Cargo.lock 把最终选择固定下来。这套机制让「升级一个依赖可能悄悄破坏构建」的概率大大降低。

1.4 rustfmt 与 clippy：让代码更地道

能编译不代表写得好。rustfmt 会按社区统一风格重排代码，clippy 则在上百条规则上给你建议，比如提醒你某个手写循环其实有更惯用的写法。两者都不改变语义，可以放心当作「免费体检」。统一风格的意义在团队里尤其明显：当所有人都用同一套排版，代码评审就能把注意力放在逻辑上，而不是花时间争论缩进和大括号位置。

rustfmt 的开箱即用配置已经覆盖绝大多数场景，你几乎不需要调参数。运行 cargo fmt 会格式化整个包，运行 cargo fmt --check 则只检查不修改，常用于 CI 里强制风格。如果确实要定制，可以在项目根目录放一个 rustfmt.toml，但初学阶段不建议急着改——先接受社区默认值，往往比「我觉得这样更好看」更靠谱。

clippy 的建议分等级：有些是 warning，不阻碍编译；有些在严格模式下会成为 error。初学阶段不必追求清零所有警告，但每条警告都值得读一遍，因为它往往对应着一个真实存在的坏习惯。比如下面这段程序用 iter().sum() 求和，而不是手写累加循环——这正是 clippy 会「建议你考虑」的惯用写法，它更短，也不容易在边界条件上出错。

rustRust · 标准库10 行
fn add(a: i32, b: i32) -> i32 {
a + b
}
fn main() {
let numbers = [1, 2, 3, 4, 5];
let sum: i32 = numbers.iter().sum();
println!("{} + {} = {}", 7, 9, add(7, 9));
println!("数组 {:?} 的和是 {}", numbers, sum);
}
终端真跑一遍
$ cargo fmt
$ cargo clippy
Checking hello_rust v0.1.0 (.../hello_rust)
Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.31s

一个实用的节奏是：写完一段就用 cargo check 快速确认类型没问题，阶段性完成后跑 cargo clippy 看看有没有更地道的写法，提交前用 cargo fmt 统一排版。把工具用成习惯，而不是等到「代码丑得看不下去」才想起来，收益会大得多。

1.5 workspace 初见

当项目变大，你可能需要把代码拆成多个包（crate）。cargo 的 workspace 机制允许一组包共享同一个 Cargo.lock 和目标目录，统一构建。你不必现在就掌握它，只要知道长什么样：根 Cargo.toml 里列出 members，每个成员是独立的包，有自己的 Cargo.toml 和 src/。

这种结构的好处是，修改一个公共库后，所有依赖它的成员能一起重新编译、一起测试，版本不会各自漂移。举个例子，一个项目里有「核心逻辑库」「命令行前端」「网页后端」三个成员，它们共享同一份依赖锁定文件；你在核心库里改了一个函数签名，一次 cargo check --workspace 就能把所有受影响的地方找出来，而不是等上线后才发现某个成员还在用旧签名。

什么时候该拆 workspace？经验法则是：当一块代码被两个以上的成员复用，或者不同部分需要独立发布、独立测试时，拆分才划算。过早拆分会带来额外的目录与配置复杂度，反而拖慢开发。本单元只要建立印象即可，等后面讲到模块、可见性和包管理时，我们再回来细看其中的门道。

2.1 变量：默认不可变，且是绑定

很多语言里写 x = 5 是「把 5 这个数装进名为 x 的盒子」。Rust 里写 let x = 5; 的语义更接近「给 5 这个值起个名字叫 x」，这叫绑定（binding）。之所以强调这一点，是因为接下来讲 move 时你会发现：值本身只有一份，变量名只是指向它的标签，标签可以被转移。

Rust 默认变量不可变。这不是为了为难你，而是因为「这个变量之后会不会变」是阅读代码时极其重要的信息。当编译器保证一个绑定不会被重新赋值，它就能更放心地优化，你读代码时也少一层心智负担。如果确实需要变化，显式加 mut，把可变性变成一处醒目的声明，而不是藏在几百行之后的心照不宣。

还有一种常见写法叫「遮蔽」（shadowing）：先 let x = 5;，再 let x = x + 1;，第二个 let 会创建一个新绑定，把旧名字遮住。它和 mut 的区别在于，遮蔽改变了类型也可以——你可以先用 String 存一个字符串，再用 let s = s.len(); 把它变成 usize。这在「分几步把数据加工成另一种形态」时特别顺手，而且每一步都不需要想新名字。

下面这段程序把变量、类型注释、元组和数组放在一起，全是标准库内容，可以直接编译。注意 let y: f64 = 3.14; 里的冒号：这是显式类型注释，告诉编译器 y 是双精度浮点数。元组用 (1, 2.5, 'a') 这样的小括号表示，元素类型可以各不相同；数组用方括号，长度固定且元素类型必须一致。

rustRust · 标准库12 行
fn main() {
let x = 5;
let y: f64 = 3.14;
let flag = true;
let c = '中';
let tuple = (1, 2.5, 'a');
let arr = [10, 20, 30];
println!("x={x}, y={y}, flag={flag}, c={c}");
println!("tuple=({},{},{})", tuple.0, tuple.1, tuple.2);
println!("arr[1]={}", arr[1]);
}

2.2 标量类型与复合类型

Rust 的类型分两大族：标量（scalar）和复合（compound）。标量是单个值，复合是把多个值组合在一起。先记住常见标量类型，读编译器报错时会轻松很多。

类别 类型 说明 字面量示例
整数 i8/i16/i32/i64/i128、u8/u16/u32/u64/u128 有符号与无符号，位数固定 42、1_000、0xff
整数 isize/usize 与平台指针宽度一致，常用于索引 arr.len() 返回 usize
浮点 f32、f64 单精度与双精度，默认推断为 f64 3.14、2.0f32
布尔 bool 只有 true 和 false true
字符 char 一个 Unicode 标量值，占四个字节 'a'、'中'

复合类型里最常见的是元组和数组。元组长度和元素类型都可以不同，用 .0、.1 这样的下标访问；数组则要求所有元素同类型且长度在编译期确定，用 [下标] 访问。超过范围的下标不会在编译时报错，但运行时会直接 panic（程序崩溃退出），这是 Rust 对越界访问的明确态度：宁可立刻停下，也不偷偷读到别的内存。

usize 值得单独说一句。它是「无符号、大小与平台指针宽度一致」的整数类型，在 64 位机器上是 64 位。数组长度、Vec 的长度以及所有索引操作都用它，所以当你用 for i in 0..v.len() 遍历时，i 的类型自然也是 usize。把索引写成 i32 经常会在比较或运算时触发类型不匹配的报错，这不是编译器的挑剔，而是在提醒你「索引不该是负数」。

2.3 类型推断：编译器替你做填空题

Rust 是静态强类型语言：每个值在编译期都必须有确定的类型，类型不匹配的代码根本编译不过。但它又不需要你处处写类型，因为编译器有类型推断能力。你写 let x = 5;，编译器看字面量是整数，就推断出 i32——这是 Rust 整数的默认类型。你写 let y = 3.14;，它推断为 f64。

推断不是「猜」，而是根据上下文做约束求解。比如 let mut v = Vec::new(); v.push(1u8); 这两行，编译器从 push 的参数类型倒推出 v 是 Vec<u8>。当上下文信息不足时，编译器会明确报错，让你补上注释。这种「能推就推、推不出就问你」的策略，让代码既简洁又不失严谨。

类型推断有边界：函数签名里的参数类型必须写出来。这是因为 Rust 要求函数有明确接口，不能让调用方猜测它接受什么——这既是对读代码的人负责，也让编译错误信息更可定位。

2.4 move、copy、clone：值是怎么交出去的

现在进入 Rust 最有辨识度的部分。先看三条所有权规则：一，每个值都有一个所有者（owner）；二，同一时刻只能有一个所有者；三，所有者离开作用域时，值被丢弃（drop）。大部分让人困惑的编译错误，追根溯源都是这三条规则在起作用。

区分 move 和 copy 的关键是「这个类型能否在栈上按位复制且不需要额外资源」。像 i32、bool、char 这类固定大小、没有堆上资源的类型，实现了 Copy trait，赋值时只是复制几个字节，原变量照样能用。而 String、Vec 这类拥有堆上数据的类型没有 Copy：赋值会把所有权整个转走（move），原变量随即失效，避免两个变量都以为自己负责释放同一块内存——那会导致重复释放（double free），是 C/C++ 里经典的内存安全漏洞。

下面的程序把三种情况放在一起。第二行注释掉的那句如果打开，编译器就会报「use of moved value」：a 的所有权已经交给 b 了。clone() 则是显式请求深拷贝，它会真正复制堆上的数据，代价更高，但两个变量各自独立。

rustRust · 标准库14 行
fn main() {
let a = String::from("hello");
let b = a; // move：a 不再可用
// println!("{a}"); // 打开这行会编译失败
println!("b={b}");
let x = 42;
let y = x; // copy：x 依然可用
println!("x={x}, y={y}");
let s1 = String::from("hi");
let s2 = s1.clone(); // 深拷贝，s1 与 s2 各自独立
println!("s1={s1}, s2={s2}");
}

需要强调的是，move 是 Rust 的默认行为，不是性能优化的小技巧，而是安全模型的核心。编译器会在编译期静态追踪所有权的流转，一旦检测到某个值被使用两次或没人释放，就直接拒绝编译。这套检查没有任何运行时开销，这正是 Rust 敢宣称「内存安全且高效」的底气。报错信息里的 E0382 是错误码，你可以用 rustc --explain E0382 查看官方解释，遇到不熟悉的错误码时这是个很实用的办法。

2.5 栈与堆，以及函数传参

理解 move，最好有一点栈与堆的直觉。栈是一块后进先出的连续内存，分配和释放只是移动栈指针，极快；函数里的局部变量、固定大小的标量都放在栈上。堆则是一块更大更自由的内存区域，分配需要寻找空闲块、记录元数据，更慢；String 的内容、Vec 的元素放在堆上，而指向它们的指针、长度、容量这些「描述符」放在栈上。

当 String 被 move 时，真正被复制走的只是栈上的描述符（指针、长度、容量），堆上的数据原地不动，只是换了负责人。这解释了为什么 move 很便宜：它本质上是按位复制描述符，只是语言层面禁止你再用旧变量，从而保证「只有一个人负责释放堆数据」。

把值传给函数时，同样的规则生效。下面这个程序里，take(name) 把 String 的所有权移进了函数，函数结束时 s 离开作用域，String 被 drop，堆内存随之释放。回到 main 后 name 已失效，不能再用。如果想「借一下而不交出」，就得用引用——那是下一个单元的主题。

rustRust · 标准库11 行
fn take(s: String) {
println!("函数内拿到: {s}");
}
fn main() {
let name = String::from("Rust");
take(name);
// println!("{name}"); // name 已被移走，打开会报错
let again = String::from("again");
println!("again={again}");
}

最后留一个小规律：如果一个函数内部没有拿走所有权，只是读取值，那调用方通常仍然拥有它；一旦参数类型是 String 而不是 &str，就要警惕所有权是不是被转移了。读函数签名时先看参数有没有 &，这是判断 move 还是 borrow 最快的办法。

3.1 动机：不想交出所有权怎么办

上一个单元里，把 String 传给函数就会把它 move 进去，调用方随后再也用不了。这在很多场景下太浪费了：一个函数只是想读一读字符串的长度，凭什么要把它吞掉？更麻烦的是，如果函数用完了也想「还回来」，你就得设计返回值把所有权再传回来，签名变得啰嗦。

Rust 的解法是借用（borrowing）：你可以把一个值的引用交给函数，函数用完就还，所有权始终留在原处。引用就是一个指向数据的指针，但它不是「随便什么指针」，而是被编译器严格检查过的指针——它必须指向有效的、类型正确的数据。这种「有规则约束的指针」正是 Rust 既能避免悬垂指针、又不需要垃圾回收的关键。

引用还有一个容易被忽视的好处：它不复制数据。传一个 &String 给函数，传递的只是栈上那个小小的指针，堆上的字符串内容原地不动。对于大对象，这比 clone 便宜得多。另外，Rust 的引用不可能为空——想表达「可能没有」，请用 Option<&T>，而不是像 C 那样用空指针。把「有没有」显式写进类型，是 Rust 减少 bug 的又一手段。

大白话先用直觉把它讲通

所有权像是把书送人，送出去你手上就没了。借用则是把书借给朋友看：书还是你的，他看完要还。规则也很像现实——你可以把书同时借给好几个人看（大家只读），但如果其中一个人要在书上涂改，那段时间里就绝不能有别人在看，否则大家看到的版本就不一致了。

3.2 不可变引用与可变引用

引用分两种，区别全在一个 mut 上。不可变引用写 &T，表示「我只读，不改」；可变引用写 &mut T，表示「我要改」。函数参数里用哪种，直接决定了调用方能不能同时做别的事。

先看只读的写法。length(&name) 把 name 的引用传进去，函数签名写 &String，函数体内 s.len() 只是读取长度。调用结束后 name 依然完好，还能照常打印。这里的 & 是「取引用」操作符，println! 里直接用 name 而不是 &name，是因为格式化宏会自动按引用捕获——不过写清楚 &name 也不会错。

rustRust · 标准库9 行
fn length(s: &String) -> usize {
s.len()
}
fn main() {
let name = String::from("Rust");
let n = length(&name);
println!("name={name}, 长度={n}");
}

再看可变引用。函数参数写 &mut String，函数体里就能调用 push 修改内容；调用方必须把变量声明成 mut，并用 &mut msg 传参。两处的 mut 缺一不可——这是 Rust 在提醒你「修改的权力」需要双方共同确认，而不是某个函数偷偷获得。

rustRust · 标准库9 行
fn push_exclaim(s: &mut String) {
s.push('!');
}
fn main() {
let mut msg = String::from("hello");
push_exclaim(&mut msg);
println!("{msg}");
}

写函数签名时，你可能纠结参数该写 &String 还是 &str。经验法则是：如果函数不需要调用 String 独有的能力，优先写 &str。因为 &String 会自动解引用（deref coercion）成 &str，所以传 &name 给一个接受 &str 的函数完全没问题；反过来接受 &String 的函数却没法接收字符串字面量。参数越宽泛，函数越通用。

一个小建议：写函数时优先考虑 &T，只在确实需要修改时才升级到 &mut T。因为不可变引用更「宽容」，调用方更容易满足借用规则，函数的适用范围也更广。方法调用时也有自动借用：对 String 调用 len()，实际等价于编译器自动帮你取了引用，所以你不需要手动写 (&s).len()。

3.3 借用规则：编译器是你的图书管理员

借用规则可以浓缩成两条：第一，同一时刻，要么有任意多个不可变引用，要么有且仅有一个可变引用，二者不能同时存在；第二，引用必须始终有效，不能指向已经被释放的数据。第二条会在下一个单元讲生命周期时展开，这里先盯住第一条。

为什么可变引用必须独占？想象一个向量 v，你手里拿着 &v[0] 指向第一个元素，这时如果允许 v.push(4)，向量可能因容量不足而重新分配内存，你手里的引用就变成了悬垂指针，指向一块已经被释放的区域。Rust 直接在编译期禁止这种组合：只要还有不可变引用活着，就不能取得可变引用；反过来也一样。

引用类型 写法 同一时刻数量 典型用途
不可变引用 &T 可以有多个 读取、遍历、计算长度
可变引用 &mut T 只能有一个 修改内容、追加元素
不可变切片 &[T] 可以有多个 只读地访问一段连续元素
可变切片 &mut [T] 只能有一个 原地修改一段连续元素

试着同时持有一个不可变引用和一个可变引用，编译器会给出类似下面的报错（示意输出，行号因文件而异）：

终端真跑一遍
$ rustc --edition 2021 main.rs -o main
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
--> main.rs:4:5
|
3 | let first = &v[0];
| - immutable borrow occurs here
4 | v.push(4);
| ^^^^^^^^^ mutable borrow occurs here
error: could not compile `main` (bin "main") due to 1 previous error

初学者常被这条规则「卡住」，但它其实是好事：这类并发与内存错误在其他语言里往往要等到线上偶发崩溃才暴露，而 Rust 让你在敲代码时就撞上它。

这条规则还是 Rust 并发安全的基础。所谓数据竞争，指的是两个线程同时访问同一份数据，其中至少一个在写，且没有同步措施。借用规则在编译期就排除了「同时有多个写入者」或「一边读一边写」的可能，于是 Rust 敢说「如果代码能编译通过，共享可变状态就受到约束」。这正是它不靠垃圾回收也能保证安全的另一半答案：所有权管释放，借用规则管并发与别名。

3.4 NLL：借用没你想的那么长

早期的 Rust 里，借用的有效期严格跟随变量的作用域（从声明到花括号结束）。这带来了一些反直觉的失败：明明最后一次使用引用之后你已经不再碰它了，编译器却认为借用还活着。后来的改进叫 NLL（Non-Lexical Lifetimes，非词法作用域生命周期）：借用的有效期从「变量作用域」缩短为「最后一次使用引用之前」。

下面的例子就是 NLL 的典型受益者。first 引用了 v 的第一个元素，打印一次之后就不再使用；紧接着 v.push(4) 取得可变借用。按老规则这会冲突，但在 NLL 下，编译器看到 first 之后没再用，就判定不可变借用已经结束，于是放行。

rustRust · 标准库7 行
fn main() {
let mut v = vec![1, 2, 3];
let first = &v[0];
println!("first={first}");
v.push(4); // first 不再使用，借用到此结束
println!("v={v:?}");
}

理解 NLL 的一个实用技巧是：把借用的有效期想象成「从取引用到最后一次使用这段区间」，而不是整个大括号。写代码时如果遭遇借用冲突，先看看能不能把某次使用提前，或者把引用的作用域用一对额外的小括号缩紧，很多问题就迎刃而解。

要注意，NLL 只看「引用有没有被使用」，不看变量是否还在作用域里。所以像 let r = &mut v; println!("{r}"); v.push(1); 这种顺序能过编译，因为 r 在 push 之前就最后一次出现了。但如果你在 push 之后又用了 r，借用就重新「活」到了那里，冲突立刻出现。把这点想清楚，大部分借用报错都能自己推断出原因。

3.5 as_ref 与 as_mut：从容器里借出引用

有些类型既持有所有权，又需要「借用里面的内容」，Option<T> 是最常见的例子。Option<String> 里的字符串是被 Some 包着的，直接 map 会把所有权 consume 掉；如果你只是想读长度、还想保留原来的 Option，就该用 as_ref()——它把 Option<T> 变成 Option<&T>，借用里面的值而不是拿走它。

对应的 as_mut() 把 Option<T> 变成 Option<&mut T>，让你在 Some 里修改内容。下面这段程序同时演示了两者：show 用 as_ref().map(...) 读长度而不消耗参数；main 里用 as_mut() 拿到可变引用，往字符串后面追加一个字符。

rustRust · 标准库15 行
fn show(opt: Option<String>) -> Option<usize> {
opt.as_ref().map(|s| s.len())
}
fn main() {
let a = Some(String::from("hi"));
let b: Option<String> = None;
println!("{:?}, {:?}", show(a), show(b));
let mut c = Some(String::from("x"));
if let Some(s) = c.as_mut() {
s.push('y');
}
println!("{c:?}");
}

as_ref / as_mut 不是 Option 的专利，Box、Rc 等智能指针也提供类似方法，套路是一致的：当你手上有「拥有者」，但下游只需要「借用」时，就找找有没有 as_ref 这类转换。养成这个习惯，能省掉大量不必要的 clone。

生命周期

4.1 动机：引用也可能悬垂

所有权保证「谁负责释放」，借用规则保证「不能乱改」，但还缺一块拼图：引用本身可能比它指向的数据活得更久。想象一个函数在函数体内部创建一个字符串，然后返回它的引用。函数一结束，那个字符串就被 drop 了，返回的引用却指向一块已经失效的内存——这就是悬垂引用（dangling reference），在 C/C++ 里是经典的 use-after-free 漏洞。

Rust 不允许这种情况发生。下面这段「坏代码」会在编译期被拦下，这里只展示它的报错（它不是可编译代码，不要照着写）：

终端真跑一遍
$ rustc --edition 2021 main.rs -o main
error[E0515]: cannot return value referencing local variable `s`
--> main.rs:2:9
|
2 | let s = String::from("hi");
| ----------------- `s` is borrowed here
3 | &s
| ^^ returns a value referencing data owned by the current function
error: could not compile `main` (bin "main") due to 1 previous error

（示意输出，具体行号与格式因 rustc 版本而异。）编译器是怎么知道 &s 会出问题的？靠的是生命周期检查：它会比较引用的生命周期和被引用数据的生命周期，只有当前者不超过后者时才放行。大多数时候编译器能自己推断，不需要你写任何标注——这也是为什么很多人写了很久 Rust 都没碰过 'a。

这种自动推断不仅发生在函数签名上，也发生在局部变量上。你写 let r = &s;，编译器会根据 s 的作用域给 r 安排一个合适的有效期，并保证 r 不会在 s 之后还被使用。换句话说，生命周期检查是无处不在的，标注只是你在少数「编译器猜不出来」的场合主动提供的提示。把这件事想通，就不难理解为什么生命周期被称作零成本抽象：它不产生运行时代码，只是编译期的一道校验。

大白话先用直觉把它讲通

生命周期就是「引用的保质期」。数据像一盒牛奶，引用像贴在上面的便签。便签的有效期不能超过牛奶本身：牛奶过期（被释放）了，便签还留着就是废纸。生命周期标注不是给牛奶写生产日期，而是告诉编译器「这张便签和那盒牛奶是同一批的，会一起到期」。

4.2 标注语法：'a 到底标的是什么

生命周期标注长这样：'a、'b、'static，读作「撇 a」「撇 static」。它出现的位置是引用类型上，比如 &'a str 表示「这个引用的生命周期是 'a」。关键要理解：生命周期标注描述的是多个引用之间的相对关系，而不是让某个值活得更久。写 'a 不会延长任何东西的寿命，它只是给编译器一张「关系图」。

下面的 longest 函数演示了最典型的场景：两个输入引用，返回一个引用。编译器必须知道返回值借用的是哪一个——如果两个输入的生命周期各不相同，就可能返回 shorter 的那个，导致悬垂。写成 <'a>(x: &'a str, y: &'a str) -> &'a str，意思是「两个参数和返回值共享同一个生命周期 'a，返回值的有效范围不会超过两个输入中较短的那个」。

rustRust · 标准库10 行
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
if x.len() >= y.len() { x } else { y }
}
fn main() {
let a = String::from("abcd");
let b = "xy";
let result = longest(a.as_str(), b);
println!("最长的是 {result}");
}

这里有一个常见困惑：既然 'a 是两个参数生命周期中较短的那个，那函数返回后还能用 result 吗？可以，只要 result 的使用发生在 a 和 b 都还活着的作用域内。借用检查器会把 result 的有效期限制在较短的那个输入之内，超出就报错。'a 不是某个具体的秒数，而是一段由调用点决定的作用域区间。

如果把两个参数写成不同的生命周期，比如 <'a, 'b>(x: &'a str, y: &'b str)，返回值就必须明确说自己跟谁走。通常做法是加一个约束 -> &'a str，再在代码里保证只返回 x（或者要求 'b: 'a，即 b 活得至少和 a 一样久）。编译器不会替你做这种「选哪个」的决定，因为这是程序逻辑的一部分——它只负责检查你的承诺有没有兑现。

4.3 省略规则：为什么你很少写生命周期

既然生命周期这么重要，为什么日常代码里几乎看不到 'a？因为编译器有三条生命周期省略（elision）规则，能自动为多数函数签名补上标注。规则如下：每个引用参数各自获得一个生命周期；如果只有一个输入生命周期，所有输出都用它；如果有多个输入生命周期，但其中一个出现在 &self 或 &mut self 上，那么所有输出都用 self 的生命周期。

写法 含义 何时需要
&'a T 对 T 的共享引用，生命周期为 'a 需要标注引用之间的关系时
&'a mut T 对 T 的可变引用，生命周期为 'a 同上，且需要修改数据时
fn f<'a>(x: &'a str) -> &'a str 输出借用自输入 多个输入且无 self 时
T: 'a 类型 T 里的所有引用都至少活到 'a 泛型与 trait 约束中
&'static str 整个程序期间都有效 字符串字面量、全局常量

把这三条规则套到 longest 上：它有两个输入引用，又都不是 self，所以编译期无法决定返回值该用哪个生命周期，必须手写。而像 fn first(s: &str) -> &str 这种只有一个输入引用的写法，编译器自动把输出生命周期设成和输入一样，于是你可以完全不写标注。理解省略规则的最大好处是：当你真的遇到「编译器要求写生命周期」的报错时，能立刻明白是自己的签名触发了哪条规则的例外。

4.4 结构体与 impl 上的生命周期

当结构体字段是引用时，结构体本身也要带生命周期参数，否则编译器不知道这个字段借的是谁。写法是 struct Excerpt<'a> { text: &'a str }，表示 Excerpt 实例不能比 text 引用的数据活得久。注意生命周期参数写在尖括号里、名字前面带撇号，和泛型参数并列出现。

在 impl 块里也要写出 <'a>，否则编译器不认识这个参数。下面这个例子里，first_word 用 &self 借用结构体，并返回 &'a str——因为字段 text 本身就是 &'a str，从它切出来的子串自然也带着 'a。

rustRust · 标准库15 行
struct Excerpt<'a> {
text: &'a str,
}
impl<'a> Excerpt<'a> {
fn first_word(&self) -> &'a str {
self.text.split_whitespace().next().unwrap_or("")
}
}
fn main() {
let story = String::from("rust lifetime basics");
let ex = Excerpt { text: story.as_str() };
println!("第一个词是 {}", ex.first_word());
}

如果你把方法签名改成返回 &str（不带 'a），生命周期会按省略规则绑定到 &self，表达的是「返回值的有效期不超过这个 Excerpt 实例」。两种写法都能编译，但语义不同：前者强调「和原始文本同寿」，后者强调「和结构体实例同寿」。实际项目里，只要你想清楚返回值实际借用的是谁，选对应的那个即可。

4.5 'static：最长但常被误解

'static 表示「整个程序运行期间都有效」。最常见的例子是字符串字面量：它们被编译进二进制文件，从程序启动到退出都存在，所以类型是 &'static str。下面的函数只接受 'static 引用，传入字面量完全没问题。

rustRust · 标准库8 行
fn print_static(s: &'static str) {
println!("{s}");
}
fn main() {
let literal = "我是字符串字面量";
print_static(literal);
}

但 'static 不等于「永远不变」，也不等于「必须写成字面量」。通过 Box::leak 把堆数据泄露出去，也能得到 &'static mut T——代价是这块内存直到程序结束都不会被释放。所以 'static 更像一个承诺：「我保证这份数据活得比任何借用都久」。在函数签名里要求 &'static str，会让函数拒绝一切指向局部变量的引用，只接受真正长命的数据；写之前要想清楚自己是否真的需要这么强的约束。

生命周期还会出现在泛型约束里。写 T: 'a 的意思是「类型 T 内部包含的所有引用都至少活到 'a」。这在写泛型容器时很重要：如果你把 T 存进一个活得很长的结构体，就必须保证 T 里没有「短命」的引用，否则整个结构体会变成悬垂的。初学阶段遇到这种约束，先把它读成「T 里不能藏短命引用」就够了。

一个实用的判断顺序是：先什么都不写，让编译器推断；只有当它明确报错、或你发现省略规则的表达能力不够时，再引入 'a。生命周期不是用来「炫技」的，它是你向编译器解释引用关系的工具——能把关系讲清楚就够了，不必给每个引用都起名字。

5.1 枚举：把状态变成类型

很多语言用一组布尔变量或整数常量表示状态：是不是在加载、加载成功了没有、失败的原因是什么。问题是这些标志可能同时为「真」，也可能全都漏掉，非法状态在类型系统里畅通无阻。Rust 的枚举（enum）把每一种可能的状态变成类型的变体（variant），一个值只能是其中一个变体，非法状态从源头就不存在。

枚举的变体可以带数据，而且形式灵活：可以像 Running(u32) 那样带一个元组，可以像 Done { code: i32 } 那样带命名字段，也可以像 Pending 那样什么都不带。这让枚举同时承担了「状态」和「状态附带信息」两件事，不需要再额外维护几个可能不同步的变量。

大白话先用直觉把它讲通

枚举像一个带标签的抽屉柜。每个抽屉上贴着不同的标签，有的抽屉是空的，有的里面装着东西。你从外面一眼就知道拿的是哪个抽屉，不可能出现「一半是 A 一半是 B」的怪东西。模式匹配就是打开抽屉取东西的动作——标签对上了才能取，取到的东西类型也确定。

从内存角度看，枚举占用空间的大小由「最大的变体」加上一个用于区分变体的标签决定。比如上面的 Status，因为要容纳 u32 和带字段的结构，它的大小至少跟最大的那个变体相当。Rust 会做布局优化，但核心思想不变：用一份空间表达多种可能，且任何时刻只有一种可能成立。

下面的程序定义了一个任务状态枚举，并用 match 给每个变体生成描述。match 的每一条分支叫一个「匹配臂」，用 => 连接模式和结果。这里用 &Status 作为输入，匹配臂里的 p 和 code 会被自动解引用绑定，不需要手动写 *p。

rustRust · 标准库24 行
enum Status {
Pending,
Running(u32),
Done { code: i32 },
}
fn describe(s: &Status) -> String {
match s {
Status::Pending => "等待中".to_string(),
Status::Running(p) => format!("运行中，进度 {p}%"),
Status::Done { code } => format!("完成，退出码 {code}"),
}
}
fn main() {
let items = [
Status::Pending,
Status::Running(42),
Status::Done { code: 0 },
];
for item in &items {
println!("{}", describe(item));
}
}

5.2 Option 与 Result：标准库里的两个明星枚举

Rust 没有 null。表示「可能没有」用标准库的 Option<T>，它只有两个变体：Some(T) 和 None。表示「可能失败」用 Result<T, E>，变体是 Ok(T) 和 Err(E)。它们本质就是普通枚举，编译器对它们一视同仁，没有任何魔法——但整个标准库和社区生态都围绕它们建立了统一的约定，所以你几乎到处都会遇到。

类型 变体 表达的含义 常见操作
Option<T> Some(T) / None 可能有一个值，也可能没有 unwrap_or、map、as_ref
Result<T, E> Ok(T) / Err(E) 可能成功，可能带着错误信息失败 ?、map_err、unwrap_or_else

为什么不用异常？因为异常让控制流变得隐式：一个函数会不会抛异常，光看签名常常看不出来。Result 把「会失败」写进返回类型，调用方必须面对它——要么处理，要么显式地 unwrap（意为「我确信不会失败，崩了算我的」）。这种「错误是值」的设计，让错误处理成为可静态检查的普通代码。

Option 和 Result 还能互相配合。比如在一个返回 Option 的函数里调用返回 Result 的操作，可以用 .ok() 把 Result 转成 Option，失败就变成 None；反过来 Option 也可以用 ok_or 转成 Result，并附带一个自定义错误。这种转换是标准库里大量存在的小工具，用熟了能少写很多 match。

5.3 match：穷尽检查是最大的保护

match 最有价值的地方不是「分支」，而是穷尽检查（exhaustiveness）：编译器会验证你有没有覆盖枚举的所有变体，漏掉一个就拒绝编译。这意味着将来给枚举新增一个变体时，所有 match 它的地方都会立刻报错，逼你逐个确认新情况该怎么处理——而不是等到线上遇上新状态才发现没写对应逻辑。

当然，你也可以写一条 _ => ... 通配符分支来兜底，但那等于主动放弃穷尽检查。它适合「确实有几十种情况、只有少数需要特殊处理」的场合；如果枚举只有三五个变体，老老实实逐个写出来，未来新增变体时编译器才会提醒你。这个提醒的价值，往往超过省下那几行代码。

终端真跑一遍
$ rustc --edition 2021 main.rs -o main

`Status::Done { .. }` not covered
--> main.rs:6:11
|
6 | match s {
| ^ patterns `Status::Running(_)` and `Status::Done { .. }`
| not covered

下面的程序演示了 Result 的典型用法：解析端口字符串。这里用 map_err 把标准库的解析错误转换成自己的描述字符串，再用 ? 提前返回（下一节细讲）。返回类型写成 Result<u16, String>，调用方只要 match 一下就能同时拿到成功值和失败原因。

rustRust · 标准库19 行
fn parse_port(s: &str) -> Result<u16, String> {
let n = s
.parse::<u16>()
.map_err(|e| format!("解析失败: {e}"))?;
if n == 0 {
Err("端口不能为 0".to_string())
} else {
Ok(n)
}
}
fn main() {
match parse_port("8080") {
Ok(p) => println!("端口 {p}"),
Err(e) => println!("错误: {e}"),
}
let opt = Some(7);
println!("缺失时取默认值: {}", opt.unwrap_or(0));
}

5.4 if let 与 let else：只关心一种情况

有时候你只想处理 match 里的某一种分支，其他情况一概忽略。这时 if let 更简洁：if let Some(n) = opt { ... } 读作「如果 opt 恰好是 Some，就把里面的值绑成 n」。它等价于一个只有一条有效分支、其他分支写 _ => () 的 match，但省掉了噪音。

let else 则解决相反的需求：先解开一个模式，解不开就提前返回或跳出。写法是 let Some(n) = opt else { return; };，注意 else 块里的代码必须以发散表达式（如 return、break、panic!）结尾，因为类型系统要求它在模式匹配失败时也能「走下去」——而它选择的是直接不往下走。这个语法从 Rust 1.65 起稳定可用。

rustRust · 标准库24 行
fn first_even(v: &[i32]) -> Option<i32> {
for &x in v {
if x % 2 == 0 {
return Some(x);
}
}
None
}
fn main() {
let nums = [1, 3, 4, 5];
if let Some(n) = first_even(&nums) {
println!("第一个偶数是 {n}");
} else {
println!("没有偶数");
}
let nums2 = [1, 3, 5];
let Some(n) = first_even(&nums2) else {
println!("确实没有偶数");
return;
};
println!("居然有偶数 {n}");
}

选择建议是：需要覆盖所有分支时用 match，只关心一种时用 if let，「拿不到就尽早退出」时用 let else。三者不是替代关系，而是同一套模式匹配能力在不同场景下的表达。

写法 适合场景 能否处理其他分支
match 枚举变体都要分别处理 能，且强制穷尽
if let 只关心某一种情况 可选 else
let else 匹配失败就提前退出 失败时必须发散

一个容易踩的坑是 if let 的「遮蔽」错觉：模式里的变量名只在成功分支里有效，出了大括号就消失了。如果你需要在后面继续用，记得在分支里把它赋给一个更外层的变量，或者干脆改用 match。

5.5 ? 运算符与自定义错误

? 只能用在返回 Option 或 Result 的函数里。它检查当前值：如果是 Ok，就把里面的值取出来继续；如果是 Err，就立刻从当前函数返回那个错误。这样你就不用层层写 match，错误会沿着调用链自动向上冒泡。? 还带有自动类型转换：只要错误类型之间定义了 From 转换，它就能帮你转好。

下面的例子用标准库的 ParseIntError 作为错误类型，演示一次解析两个整数。split(',') 把字符串切开，? 在任一次解析失败时立即返回，调用方用 match 统一处理。

rustRust · 标准库15 行
use std::num::ParseIntError;
fn parse_pair(s: &str) -> Result<(i32, i32), ParseIntError> {
let mut parts = s.split(',');
let a = parts.next().unwrap_or("").trim().parse::<i32>()?;
let b = parts.next().unwrap_or("").trim().parse::<i32>()?;
Ok((a, b))
}
fn main() {
match parse_pair("3, 4") {
Ok((a, b)) => println!("a={a}, b={b}"),
Err(e) => println!("出错: {e}"),
}
}

写错误处理时有个实用原则：在底层保留足够的错误细节，在靠近用户的一层再把它翻译成人话。底层直接 unwrap 会让调用方失去判断的依据，而把所有错误都压成一句「操作失败」又丢掉了排查线索，两头都不是好选择。

实际项目里，你往往需要自己的错误类型，把「文件读不到」「配置格式错」「网络超时」这些不同原因归到一个枚举里。手写时要为它实现 Display 和 std::error::Error，还要为底层错误实现 From，样板代码不少。社区里的 thiserror 思路正是为此而生：用派生宏自动帮你生成这些实现，你只要写出错误枚举和每个变体上的提示文本即可。这里只讲思路，不引入任何外部 crate——你完全可以先手写一个简化版体会其中的结构，等项目真的复杂起来再考虑用宏省事。

最后提醒一个度的问题：unwrap() 和 expect() 在示例和测试里很方便，但在可能失败的生产路径上滥用，等于把错误又变回了「运行时崩溃」。能用 ? 传上去就传上去，让错误在最有上下文的那一层被解释和处理。

结构体、trait 与泛型

目标这一单元要带走什么

  • 会写泛型函数与 trait bound，知道编译期单态化意味着什么

6.1 结构体：给一组数据起名字

到目前为止我们用的大多是零散的值。真实项目里，数据往往成组出现：一个点有 x 和 y，一个用户有名字、年龄和邮箱。结构体（struct）把命名字段打包成一个新类型，让「这些字段属于同一个概念」这件事在类型系统里成立。和元组相比，结构体的字段有名字，读代码时不用猜 .0 是什么。

定义结构体时，字段默认也是私有的（对其他模块而言）——不过在同一个模块里可以直接访问。加 #[derive(Debug)] 让编译器自动实现 Debug trait，这样你就能用 {:?} 打印整个结构体；这是派生宏最常见的一个用途，不需要手写格式化逻辑。derive 不是继承，也不是运行时反射，而是「编译期帮你生成一段实现代码」。

结构体还有几种变体：元组结构体 struct Point(i32, i32); 没有字段名，适合包装单个值；单元结构体 struct Marker; 没有字段，常用来标记某种状态。当两个结构体大部分字段相同、只有少数不同时，还可以用结构体更新语法 let b = Config { debug: true, ..base }; 复用旧值——不过要留意被复用的字段如果是 String 这类没有 Copy 的类型，所有权会被移走，旧结构体就不能整体再用了。

大白话先用直觉把它讲通

结构体像一张表格的表头，规定了「每行有哪些列、每列叫什么」。trait 则像一份岗位说明书：它不告诉你这个人长什么样，只规定他必须会做什么。泛型是「先写好模板，等用到的时候再填类型」——像是可调节的模具，倒进去的是铁就是铁件，倒进去的是塑料就是塑料件。

下面的程序定义了矩形，并在 impl 块里写了三个函数。new 没有 self 参数，是关联函数，用 Rectangle::new(...) 调用，扮演构造器的角色；area 和 can_hold 第一个参数是 &self，是方法，用 big.area() 调用。Self 是 impl 块所针对类型的别名，写 Self { ... } 比重复 Rectangle 更耐改。

rustRust · 标准库27 行
#[derive(Debug)]
struct Rectangle {
width: u32,
height: u32,
}
impl Rectangle {
fn new(width: u32, height: u32) -> Self {
Self { width, height }
}
fn area(&self) -> u32 {
self.width * self.height
}
fn can_hold(&self, other: &Rectangle) -> bool {
self.width >= other.width && self.height >= other.height
}
}
fn main() {
let big = Rectangle::new(30, 50);
let small = Rectangle::new(10, 20);
println!("面积: {}", big.area());
println!("能否装下: {}", big.can_hold(&small));
println!("{big:?}");
}

6.2 枚举也能有方法

上一单元定义了枚举，其实枚举同样能写 impl 块。方法内部用 match self 区分变体，为每个变体给出不同实现。这是 Rust 里表达「一组相关但行为不同的东西」的常见手法：与其写一堆散落的 if，不如把行为挂在类型上，让调用方只面对一个统一的方法名。

下面的程序定义了 Shape 枚举，圆形用半径算面积，矩形用宽高算面积。调用方拿到的是 &Shape，不需要知道内部是哪个变体，只要调用 area() 就好。将来新增三角形时，只需在 match 里补一条分支，编译器会帮你找出所有遗漏的地方。

一个类型可以有多个 impl 块，只要它们不重复定义同一个方法。项目里常见的组织方式是：把构造器放一个块，把核心行为放一个块，把实现的 trait 各放一个块。这样每个块的职责清晰，读起来比把所有方法塞进一个大块舒服得多。

rustRust · 标准库20 行
enum Shape {
Circle(f64),
Rect(f64, f64),
}
impl Shape {
fn area(&self) -> f64 {
match self {
Shape::Circle(r) => std::f64::consts::PI * r * r,
Shape::Rect(w, h) => w * h,
}
}
}
fn main() {
let shapes = [Shape::Circle(2.0), Shape::Rect(3.0, 4.0)];
for s in &shapes {
println!("面积 {:.2}", s.area());
}
}

6.3 trait：定义行为契约

trait 描述「某种类型必须提供哪些能力」。它只给出方法签名，可以把实现留给具体类型；也可以提供默认实现，让实现者按需覆盖。trait 和接口（interface）的概念很像，但 Rust 的 trait 没有运行时查找的开销——调用在编译期就确定下来，这叫静态分发。

下面的 Summary trait 要求实现者提供 summarize，同时给 author 提供了默认实现。Article 实现它时，只覆盖了 author，沿用了 summarize 之外的默认行为。notify 函数的参数写成 &T 并加上 T: Summary 约束，意思是「任何实现了 Summary 的类型都能传进来」，而函数体内可以放心调用 trait 里的方法。

rustRust · 标准库33 行
trait Summary {
fn summarize(&self) -> String;
fn author(&self) -> &str {
"匿名"
}
}
struct Article {
title: String,
author: String,
}
impl Summary for Article {
fn summarize(&self) -> String {
format!("《{}》", self.title)
}
fn author(&self) -> &str {
&self.author
}
}
fn notify<T: Summary>(item: &T) {
println!("新摘要: {} by {}", item.summarize(), item.author());
}
fn main() {
let a = Article {
title: "Rust 入门".to_string(),
author: "张三".to_string(),
};
notify(&a);
}

默认实现还有一个妙用：它能让 trait 渐进式演进。发布后给 trait 新增一个带默认实现的方法，已有的实现者无需改代码也能继续编译；如果新增的是没有默认实现的方法，所有实现者都会被迫更新。设计公共 API 时，这是个很实际的兼容性考量。trait 也可以作为类型使用（trait object），像 Box<dyn Summary> 这样，代价是运行时动态分发——不过这属于进阶话题，本单元先记住「泛型是编译期确定，dyn 是运行时确定」的区别就够了。

6.4 泛型与 trait bound

泛型让函数或类型摆脱对具体类型的绑定。下面的 largest 接受任意类型的切片，返回其中最大的元素。T: PartialOrd + Copy 是 trait bound：前者保证值之间能用 > 比较，后者保证按值返回时是复制而不是 move（如果换成 String 这种没有 Copy 的类型，函数体里的 best = item 就会触发所有权问题）。多个约束用 + 连接。

rustRust · 标准库14 行
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
let mut best = list[0];
for &item in list {
if item > best {
best = item;
}
}
best
}
fn main() {
println!("最大整数 {}", largest(&[1, 9, 3]));
println!("最大字符 {}", largest(&['a', 'z', 'm']));
}

泛型在运行时没有额外开销：编译器会为用到的每种具体类型生成一份 specialized 代码，这叫单态化（monomorphization）。代价是编译时间变长、生成物变大，但运行时和普通代码一样快。这和某些语言用装箱、虚表实现的泛型不同——理解这一点，你就明白为什么 Rust 社区把泛型称为零成本抽象。

泛型不只属于函数，结构体和枚举也能带泛型参数，比如标准库的 Vec<T> 和 Option<T>。定义 struct Wrapper<T> { value: T } 后，特定实例的类型就写成 Wrapper<i32>。调用泛型函数时，类型参数通常由编译器推断，但偶尔需要显式指定，写法是 largest::<i32>(&v)——两个连续冒号加尖括号，社区里戏称「涡轮鱼」（turbofish）。

trait bound 也可以写在 where 子句里，当约束较多时可读性更好，例如 fn f<T>(x: T) where T: Summary + Clone { }。两种写法语义相同，纯粹是排版选择。真正要留意的是约束的松紧：要求越多，函数能接受的类型越少，但函数体内能用的能力也越多。按需加约束，是泛型设计的基本功。

6.5 orphan rule：谁能给谁实现 trait

Rust 有一条 orphan rule（孤儿规则）：实现 impl Trait for Type 时，trait 和类型至少有一个必须定义在你自己的 crate 里。换句话说，你不能给外部库的类型实现外部库的 trait。这条规则的目的，是保证任意两个 trait 实现不会「撞车」——如果大家都去给 String 实现外部的 Display，编译器就不知道该选哪一个。

直觉上可以这样记：trait 和类型就像插头和插座，至少有一头是你家生产的，你才能合法地接线。想给第三方类型加能力，常见做法是定义一个自己的新类型把它包起来（newtype 模式），再为这个新类型实现 trait；反之，想给自己的类型加上第三方 trait 的能力，直接实现即可。

举个具体场景：你用外部库提供的 Point，又想让它支持自己定义的 Printable trait。因为 trait 是你自己的，可以直接写 impl Printable for Point。但如果是外部库的 trait 和外部库的类型，你就得包一层 struct MyPoint(Point);，再为 MyPoint 实现那个 trait。多写这一层看似麻烦，却换来了「实现不会在互不知晓的两个库之间冲突」的确定性。

struct、enum、trait、泛型四者各有分工，用一张表对照会更清楚。

概念 描述什么 关键写法
struct 有名字的字段集合 struct Point { x: i32, y: i32 }
enum 互斥的若干种变体 enum Status { Ok, Err(String) }
trait 类型必须提供的行为 trait Draw { fn draw(&self); }
泛型 对具体类型不绑定的模板 fn f<T>(x: T)、Vec<T>

什么时候该引入 trait？经验法则是：当你发现多个类型都有「同一件事的不同做法」，而调用方并不关心具体是哪种类型时，就把这件事抽成 trait。相反，如果只有一个类型会用，老老实实写方法就好，过早抽象只会增加理解成本。

7.1 闭包：可以当值传递的函数

函数只能定义一次、名字固定；闭包（closure）则像「匿名函数 + 它能看见的周围环境」，可以存进变量、当作参数传递、从函数里返回。语法是 |参数| 表达式，参数类型通常可以省略，因为编译器会从调用方式推断出来。下面的 add 明确写了类型，而 |n| n * 2 则让编译器从 iter() 产出的元素类型推断出 n 是 &i32。

闭包最特别的能力是捕获（capture）：它可以引用定义时所在作用域里的变量。let x = 10; let plus_x = |n| n + x; 里的 x 并没有通过参数传进来，而是被闭包「顺手带走」了。捕获的方式取决于闭包体怎么用这个变量：只读就按引用捕获，要修改就按可变引用捕获，要拿走所有权就用 move 关键字。

大白话先用直觉把它讲通

闭包像一个随身带着行李的小帮手。普通函数只能用它手里临时的东西，闭包却能把「当时桌上的东西」一起打包带走。迭代器则像一条传送带：你在传送带旁挂上几个工位（map、filter），东西只有被推到最后要用到时才真正加工——这叫惰性求值，好处是不用先造出一堆中间产物。

下面的程序把三种场景放在一起：一个纯粹的二元闭包、一个捕获了 x 的闭包，以及闭包作为 map 参数的使用。最后一个 collect() 会把迭代器收集成 Vec<i32>，目标类型由变量注释决定。

rustRust · 标准库12 行
fn main() {
let add = |a: i32, b: i32| a + b;
println!("3 + 4 = {}", add(3, 4));
let x = 10;
let plus_x = |n: i32| n + x;
println!("5 + x = {}", plus_x(5));
let nums = [1, 2, 3];
let doubled: Vec<i32> = nums.iter().map(|n| n * 2).collect();
println!("{doubled:?}");
}

闭包的类型是编译器为它匿名生成的，你写不出「闭包的类型名」。正因如此，接收闭包的函数必须写成泛型 F: Fn...，而不能写具体类型。这也是理解下一节三个 trait 的入口。

编译器推断闭包参数类型的方式很实用：第一次调用时看到你传了整数，就确定参数是整数；如果一直不调用、上下文也没有类型信息，它就会报错，这时给参数补上类型即可。另外，move 关键字不只是「把变量搬进闭包」的语法糖——在把闭包交给另一个线程时，它几乎是必需的，因为新线程的生命周期可能超过当前栈帧，闭包不能依赖对局部变量的借用。

7.2 Fn、FnMut、FnOnce：按「怎么用」分类

Rust 用三个 trait 描述闭包能怎样被调用，它们的约束强度依次递减：Fn 最宽松（可以重复调用，不消耗任何东西），FnMut 次之（可以重复调用，但需要可变引用来修改状态），FnOnce 最弱（只能调用一次，因为会消耗捕获的值）。

trait 调用次数 对捕获值的操作 典型例子
Fn 任意多次 只读借用 || x，|a, b| a + b
FnMut 任意多次 可变借用、修改状态 计数器 || { count += 1; count }
FnOnce 仅一次 取得所有权并消耗 move || drop(s)

这套分类的价值在于：函数在签名里声明 F: Fn，就向调用方保证「我不会拿走你的闭包，也不会修改它」；声明 F: FnMut 则需要把闭包声明成 mut。如果参数写成 F: FnOnce，调用函数时闭包本身会被消耗掉——它最适合那些「只跑一次」的回调场景。

三者之间是包含关系：所有 Fn 闭包都自动是 FnMut，所有 FnMut 又都是 FnOnce。所以写 F: FnOnce 是对调用方最宽松的约束（几乎任何闭包都能传进来），而写 F: Fn 最严格。设计 API 时有个实用原则：按「你实际需要的最弱能力」来选——只要调用一次就够，就别要求 Fn；这样调用方能传进来的闭包类型更多。

下面的程序分别写了三个接收者。call_mut 的形参必须写 mut f，否则调用 f() 时会报「不可变地借用可变闭包」的错误。call_once 里用 move 把 String 的所有权移进闭包，闭包被调用后 s 就被 drop 了。

fn call_once<F: FnOnce() -> i32>(f: F) -> i32 {

fn call_mut<F: FnMut() -> i32>(mut f: F) -> i32 {

count += 1;

7.3 迭代器：惰性求值的数据流

迭代器（iterator）是对「一串可以逐个取出的值」的抽象。它的核心只有一个方法 next()，返回 Option<Item>——有元素就给 Some(值)，取完了给 None。for 循环其实就是迭代器的语法糖：for x in v 会把 v 转成迭代器，反复调用 next() 直到结束。

迭代器最重要的性质是惰性（lazy）：光创建它不会做任何计算，只有真正调用 next()（或者被 collect、sum 这类消费器驱动）时才逐步产出值。这意味着你可以把多个步骤串成一条流水线，而中间结果不需要先存成完整的 Vec，既省内存又能早停。

下面的程序先算一个「偶数平方和」，链上 filter 和 map，最后由 sum() 消费。第二半段用一个带打印的 map 演示惰性：创建之后什么都没打印，直到调用 next() 才看到输出。

rustRust · 标准库16 行
fn main() {
let nums = [1, 2, 3, 4, 5, 6];
let result: i32 = nums
.iter()
.filter(|&&n| n % 2 == 0)
.map(|&n| n * n)
.sum();
println!("偶数平方和 = {result}");
let mut lazy = nums.iter().map(|n| {
println!("正在计算 {n}");
n * 2
});
println!("此刻还没有任何计算发生");
println!("第一个结果: {:?}", lazy.next());
}

注意 iter() 产出的是引用 &i32，所以 filter 的闭包收到 &&i32、map 的闭包收到 &i32。用 |&n| 这样的模式可以把引用解构掉，直接拿到值。如果你拿到的是迭代器本身而不是切片，比如 .into_iter() 产出的是 i32，闭包参数就不用带 & 了。三种常见入口的区别值得记牢：iter() 借用集合，iter_mut() 可变借用（可以原地修改元素），into_iter() 消耗集合、把所有权逐个交出。选哪个取决于你之后还想不想继续使用原集合。

7.4 适配器：map、filter、fold

适配器（adapter）是「接收一个迭代器、返回另一个迭代器」的方法，可以无限串联。map 做一对一转换，filter 按条件保留元素，take(n) 只取前 n 个，enumerate() 给元素配上下标。它们都是惰性的，不会立即遍历数据。

fold 则是消费器：它带一个初始累加值，把闭包依次应用到每个元素上，最后返回累加结果。下面的程序用 fold 实现字符串拼接，同时演示 take 和 enumerate 的惰性链条。

rustRust · 标准库16 行
fn main() {
let nums = [1, 2, 3, 4, 5];
let txt = nums
.iter()
.take(3)
.map(|n| n.to_string())
.fold(String::from("结果:"), |acc, n| {
format!("{acc} {n}")
});
println!("{txt}");
for (i, n) in nums.iter().enumerate() {
println!("下标 {i} -> 值 {n}");
}
}

这里要提醒一点：fold 的闭包里用 format! 每次生成新字符串，数据量很大时会有额外分配。追求性能时可以改成可变累加器，或者用 write! 直接写入 String。这属于优化层面的考虑，初学阶段先用最直观的写法把逻辑写对更重要。先跑通，再优化，永远是比较稳妥的顺序。

7.5 collect 与类型推断

collect() 把迭代器收集成集合，是迭代器世界里最常用的「出口」。它之所以能工作，是因为 FromIterator trait：Vec、BTreeSet、HashMap 等类型都实现了它，知道怎么从一个迭代器构造自己。正因为如此，collect() 的返回类型必须由上下文给出——变量注释、函数返回值或后续用法都可以，但如果完全没有类型信息，编译器就会报错。

下面的程序把同一组单词分别收集成 Vec、BTreeSet 和 HashMap。注意 Vec<usize> 的注释是必需的；而 BTreeSet 会自动去重；HashMap 的构造稍微特殊，这里用 entry API 手动统计词频，展示迭代器与常规写法的配合。

rustRust · 标准库17 行
use std::collections::{BTreeSet, HashMap};
fn main() {
let words = ["rust", "go", "rust", "c"];
let lens: Vec<usize> = words.iter().map(|w| w.len()).collect();
println!("长度列表 {lens:?}");
let unique: BTreeSet<&str> = words.iter().copied().collect();
println!("去重后 {unique:?}");
let mut counts: HashMap<&str, i32> = HashMap::new();
for &w in &words {
*counts.entry(w).or_insert(0) += 1;
}
println!("词频 {counts:?}");
}

collect() 还有一个进阶用法：如果迭代器的元素本身是 Result<T, E>，你可以把它收集成 Result<Vec<T>, E>——遇到第一个 Err 就整体失败，否则得到装满成功值的向量。这在「批量解析、任一失败就报错」的场景里非常顺手，因为类型系统会自动帮你把错误冒泡出来。

什么时候该用迭代器、什么时候写普通循环？一个简单判断：如果是在「对一串数据做连续的变换和筛选」，迭代器链通常更短、更不容易写出边界错误；如果逻辑里充满了提前返回、复杂状态机或需要修改多个外部变量，for 循环往往更清晰。两者不是高低之分，而是工具箱里的不同工具。迭代器链会消耗原始迭代器，收集完想再用一遍，记得重新调用 iter() 建一条新链，不能直接拿旧链重复收集。

8.1 Cargo.toml 关键字段

一个仓库的构建元数据几乎全部集中在 Cargo.toml 里。初学时最容易混淆的是 package 与 workspace：前者描述「这一个包怎么构建、怎么发布」，后者描述「哪些包共享同一次依赖解析与同一个产物目录」。[package] 中必须给出 name、version、edition；edition 决定语法特性和 lint 的默认集合，升级 edition 是一次需要评审的迁移，而不是顺手改掉一个数字。

dependencies 只声明「我需要什么」，并不声明「最终用哪个具体版本」——后者由解析器和 Cargo.lock 共同决定。version = "1.2" 表示兼容 1.x 的最新版本，~1.2 表示限定在 1.2.x，=1.2.3 才是精确锁定。只在测试里用到的依赖写进 [dev-dependencies]，它不会进入发布产物；可选能力写进 [dependencies] 并标记 optional = true，再由 feature 决定是否真正编译。

下面的片段把这几类字段放在一起。dep:serde 是 1.60 之后推荐的写法，它明确告诉 Cargo「这里的 feature 只是开关依赖，不要额外生成一个同名的隐式 feature」，这是多年踩坑后形成的约定。

还有几个容易忽略的字段值得提前认识：[[bin]] 用于声明额外的可执行文件，[lib] 可以改名或关闭库目标，build = "build.rs" 指定构建脚本，而 [package.metadata] 留给第三方工具存放自己的配置，Cargo 本身并不解读它。一个包同时拥有库目标和二进制目标是完全正常的，库接口才是复用的正确入口，main.rs 应当尽可能薄。字段记不全并不可怕，关键是知道「哪一类信息该写进清单」，而不是把配置散落在脚本和文档里。

把 Cargo.toml 想成一张快递单。package 写「我是谁、送到哪」，workspace 写「这几个包裹一起发货」，dependencies 写「我需要哪些零件」，而 Cargo.lock 是当天真正装车的零件清单。你声明的是需求，锁文件记录的是结果，两者各司其职，谁也替代不了谁。

Rust 代码里读取特性有两种方式，它们的时机完全不同：cfg! 是布尔表达式，两个分支都要通过类型检查；#[cfg] 则在编译前直接删除条目，未选中的代码甚至不会被解析成有效实现。需要「同一接口、两套实现」时，应当用后者，让不相关依赖彻底不进入编译单元。

rustRust · 标准库17 行
#![allow(dead_code, unexpected_cfgs)]
/// 根据编译时特性选择后端名称。
fn backend_name() -> &'static str {
if cfg!(feature = "json") { "json" } else { "minimal" }
}
#[cfg(feature = "json")]
fn parse_hint() -> &'static str { "启用结构化解析，支持嵌套输入" }
#[cfg(not(feature = "json"))]
fn parse_hint() -> &'static str { "仅内置格式，产物更小" }
fn main() {
println!("backend = {}", backend_name());
println!("hint = {}", parse_hint());
}

用 rustc 直接编译时没有 Cargo 注入的 feature，因此走 minimal 分支；用 cargo 编译时默认特性 json 被打开，走另一条分支。这种「编译期分叉、运行期零成本」是 Rust 处理平台差异和功能裁剪的基本手段，但代价是组合数量会膨胀，必须有意识地收敛。

8.2 workspace 拆分与目录约定

当仓库里出现多个互相依赖的包时，workspace 让它们共享一份 lockfile 和一个 target 目录。根 Cargo.toml 用 [workspace] 列出成员，每个成员自身仍是完整的 package，可以独立测试与发布。拆分的判据不是「代码行数到了多少」，而是「能否用一条清晰的依赖方向描述它们」：底层库不认识上层应用，上层应用可以组合若干底层库，过程宏单独成包。

tomlRust · 标准库10 行
[workspace]
resolver = "2"
members = ["crates/core", "crates/cli", "crates/e2e"]
[workspace.package]
edition = "2021"
license = "MIT"
[workspace.dependencies]
core = { path = "crates/core", version = "0.3.0" }

成员通过 version.workspace = true、edition.workspace = true 继承公共字段，避免十几个包各自漂移。典型目录如下，注意跨包测试应当放在专门的 e2e 包里，而不是工作区根目录——根目录不是任何 crate 的源目录，放在那里的测试不会被 cargo 自动发现。

8.3 feature 组合与默认特性

feature 的第一条工程原则是保持可叠加：打开某个 feature 不应该让已有 API 的语义发生变化，否则两个库同时打开它时就会产生冲突。第二条原则是让默认特性覆盖「大多数用户开箱即用」的路径，把重型或平台相关的能力留给用户显式开启；default = [] 适合作为底层库的选择，default = ["json"] 适合作为应用的选择。

组合 启用内容 适用场景 代价
默认（default = ["json"]） 结构化解析与日志 本地开发、常规发布 依赖较多，编译较慢
--no-default-features --features minimal 仅内置逻辑 轻量产物、受限环境 缺少结构化输入

8.4 依赖版本与 lockfile

语义化版本把变更分成三类：主版本号变化意味着不兼容的 API 改动，次版本号变化意味着向后兼容的新增，修订号变化意味着向后兼容的修复。Cargo 的默认 ^ 策略允许次版本与修订号自动升级，这让你能拿到安全修复，也意味着两台机器在不同时间构建可能得到不同结果。Cargo.lock 记录每个依赖的精确版本与校验和，正是为了消除这种不确定性。

应用仓库必须提交 lockfile；库仓库如今也建议提交，并用 cargo update -p <name> 显式升级，而不是让每个使用者各自解析。CI 中使用 cargo build --locked，可以在锁文件与清单不一致时直接失败，防止有人改了 Cargo.toml 却忘记更新锁文件。需要定点回退时用 cargo update -p serde --precise 1.0.188，它只动一个包，比全量 cargo update 可控得多。

还有一个容易踩的坑是「最低版本」与「实际版本」的差别。清单写 serde = "1" 只约束了下界，真正在锁文件里的可能是 1.0.219； CI 若想验证声明的下界是否真的可用，需要单独用最小版本解析跑一遍。反过来，锁文件里的版本不会因为清单放宽而自动变化，必须显式 cargo update 才会移动。理解这一点，就能解释「为什么我改了版本号但构建结果没变」以及「为什么同事拉代码后依赖突然升级了」这两类经典疑问。

版本字符串的处理看着简单，却是很多工具的隐藏 bug 来源。下面这个小例子只演示 std 下的手写解析思路：真实项目应当使用专门的版本解析库，而不是自己拼字符串，因为预发布标签、构建元数据与比较规则远比这里复杂。

rustRust · 标准库20 行
#[derive(Debug, PartialEq, Eq)]
struct Ver { major: u64, minor: u64, patch: u64 }
impl Ver {
fn parse(s: &str) -> Option<Ver> {
let mut it = s.split('.');
let major = it.next()?.parse().ok()?;
let minor = it.next()?.parse().ok()?;
let patch = it.next()?.parse().ok()?;
if it.next().is_some() { return None; }
Some(Ver { major, minor, patch })
}
}
fn main() {
let a = Ver::parse("1.2.3").unwrap();
let b = Ver::parse("1.3.0").unwrap();
println!("a={:?} b={:?}", a, b);
println!("跨次版本: {}", a.minor != b.minor);
}

8.5 工程边界与迁移策略

workspace 的边界应当与团队的代码所有权边界大致对齐。把十几个小包塞进一个 workspace 会让编译图难以理解；把强耦合的模块拆成五个互相引用的包则会让每次改动都触发连锁发布。一个实用的判据是：如果两个模块永远一起改、一起发布，它们就属于同一个包。

迁移现有仓库时不必一次到位。先把可执行文件的业务逻辑挪到 lib.rs，让 main.rs 只剩装配；再把被多个应用复用的部分抽成内部库包；最后把发布节奏独立的部分拆出去。每一步都能单独验证，比「大爆炸式重构」安全得多。

需要提醒的是，workspace 内所有成员共享一次依赖解析。这意味着某个成员引入的高版本依赖可能抬高整个工作区的统一版本，进而影响其他成员；cargo tree -d 可以查看重复版本，cargo tree -i <crate> 能反向找出是谁把它带进来的。掌握这两个命令，比凭记忆猜测依赖来源可靠得多。

目标这一单元要带走什么
  • 能判断一个失败该用 Result 返回还是该 panic，并说明取舍理由
  • 理解 ? 的展开语义，知道何时该用 match 接住错误、何时该继续传播
  • 能用标准库实现自定义错误类型：Display、Error 与 source 错误链
  • 能让 main 返回 Result，并在正确的层级补充上下文、避免重复日志

9.1 Result 是边界，不是装饰

Rust 把失败分成两类：调用方有可能处理的叫「可恢复错误」，用 Result<T, E> 表达；程序状态已经被破坏、继续运行没有意义的叫「不可恢复错误」，用 panic 表达。库代码面对用户输入、文件缺失、网络断开时应当返回 Result，因为库作者并不知道调用方是否愿意降级处理；相反，越是应用内部的「绝不可能发生」的不变量，越适合用断言或 panic，让 bug 在测试阶段就暴露。

Option 和 Result 的差别在于信息量：前者只说「没有」，后者说明「为什么没有」。配置缺一个字段时返回 None 会让排查者无从下手，返回 Err(Missing("database.url")) 则直接指出问题。工程上的默认选择应当是「不确定就用 Result，除非缺失本身是正常业务状态」。

选择错误类型时有两条路线。枚举把每种失败变成一个变体，调用方可以 match 后分别处理，适合库与需要精细分支的模块；trait object 则把不同来源的错误统一成 Box<dyn Error>，写起来省事，但具体类型被擦除，只能靠字符串或 downcast 区分。经验法则是「库返回具体类型，应用在边界汇聚成 trait object」，这样既不牺牲调用方的判断能力，也不必在每个上层函数里重复写一长串错误枚举。

下面的例子把三类要素放在一起：用枚举分类错误、为它实现 Display 与 Error、用 From 让 ? 自动转换 io 错误，最后让 main 返回 Result。这是 std-only 项目里的最小完整骨架，后续引入 anyhow 或 thiserror 时也改变不了这套结构，只是省掉样板代码。

rustRust · 标准库47 行
use std::error::Error;
use std::fmt;
use std::fs;
#[derive(Debug)]
enum ConfigError {
Missing(String),
Io(std::io::Error),
}
impl fmt::Display for ConfigError {
fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
match self {
ConfigError::Missing(key) => write!(f, "缺少配置项: {}", key),
ConfigError::Io(e) => write!(f, "读取配置失败: {}", e),
}
}
}
impl Error for ConfigError {
fn source(&self) -> Option<&(dyn Error + 'static)> {
match self {
ConfigError::Io(e) => Some(e),
ConfigError::Missing(_) => None,
}
}
}
impl From<std::io::Error> for ConfigError {
fn from(e: std::io::Error) -> Self { ConfigError::Io(e) }
}
fn read_config(path: &str) -> Result<String, ConfigError> {
let text = fs::read_to_string(path)?;
if text.is_empty() {
return Err(ConfigError::Missing("content".into()));
}
Ok(text)
}
fn main() -> Result<(), Box<dyn Error>> {
match read_config("/definitely/not/here") {
Ok(text) => println!("内容: {}", text),
Err(e) => println!("捕获: {} / source: {:?}", e, e.source().map(|s| s.to_string())),
}
Ok(())
}

Result 就像快递的签收单。成功时里面有货，失败时里面是一张写明原因的退货单。? 的作用是你不想拆开每张单子细看时，直接把退货单往上游递；只有到了能真正处理问题的柜台，才需要拆包判断该怎么处置。

9.2 错误分类与 ? 的传播

? 并不是魔法，它大致展开成「成功就取出内部值，失败就 return Err(From::from(e))」。这意味着两件事：当前函数的返回类型必须能容纳那个错误，而且 From 转换必须存在。上面例子里为 std::io::Error 实现 From，正是为了让一次 read_to_string 的失败能自动升级成 ConfigError::Io。

传播不等于放弃处理。经验做法是「谁有信息谁加上下文」：底层知道「文件读取失败」，中间层知道「这是在加载用户配置时」，顶层知道「程序因此无法启动」。每一层只补自己知道的部分，错误链才既有细节又不啰嗦。反过来，在每一层都 eprintln! 一次会造成同一错误刷屏，排查时反而找不到真正的源头。

io::Error::kind() 是分类的典型例子。比起比较字符串，用 kind 判断是可移植且稳定的做法；map_err 则负责在不改变控制流的前提下改写错误类型，常用于把第三方错误包进本模块的错误枚举。

rustRust · 标准库24 行
use std::io::{self, ErrorKind};
fn classify(e: &io::Error) -> &'static str {
match e.kind() {
ErrorKind::NotFound => "可恢复：资源缺失，可提示用户",
ErrorKind::PermissionDenied => "需人工介入：权限不足",
ErrorKind::Interrupted => "可重试：系统调用被打断",
ErrorKind::InvalidData => "数据问题：上游内容不合法",
_ => "未知：保留原始错误向上抛出",
}
}
fn double(s: &str) -> Result<i32, String> {
s.parse::<i32>()
.map_err(|e| format!("解析 {:?} 失败: {}", s, e))
.map(|n| n * 2)
}
fn main() {
let e = io::Error::new(ErrorKind::NotFound, "no such file");
println!("分类: {}", classify(&e));
println!("成功: {:?}", double("21"));
println!("失败: {:?}", double("abc"));
}

下表给出几个常见决策点。注意「失败频率」比「失败严重程度」更影响选择：一个每秒发生百万次的可预期失败不适合用 panic 或生成堆栈；而一个一生只会发生一次的不变量破坏，panic 反而更合适。

ok_or 与 ok_or_else 也是同一类决策：前者立即构造错误值，后者延迟到真的失败时才调用闭包。如果错误信息里包含格式化或分配操作，用 ok_or_else 可以让成功路径完全不付这笔成本。类似地，let Some(x) = ... else { return Err(...) }; 在需要从 Option 提前返回时比嵌套 match 更易读。这些细节单独看都很小，累积起来却决定了错误处理代码是清爽还是臃肿。

场景 推荐做法 理由
用户输入不合法 返回 Result，描述具体字段 调用方可提示并重试
配置文件缺失 返回 Result 并补路径上下文 运维需要定位到文件
内部不变量被破坏 assert! 或 panic! 这是 bug，应尽早终止
可选资源不存在 返回 Option 缺失属于正常状态

9.3 自定义错误类型的取舍

小项目用一个枚举就能覆盖全部错误来源；大项目则常按子系统划分多个错误枚举，再用 #[from] 式的转换把它们串起来。无论哪种，都要保证 Display 面向人、Debug 面向开发者：Display 应写清楚「发生了什么、涉及哪个对象」，Debug 则保留字段结构供日志系统采集。

Error::source 是标准库提供的错误链入口。它让上层错误能指向底层错误，形成「加载配置失败 → 读取文件失败 → 权限被拒绝」这样的链条。实现它几乎不花成本，却让排查效率产生质变。需要包装第三方错误且不愿自定义枚举时，Box<dyn Error> 作为返回类型是可接受的应用层选择；但它会擦除具体类型，调用方无法再按类型分支，因此更适合作为最外层的汇聚点，而不是库 API。

thiserror、anyhow 等 crate 能消除大量样板，但它们只是「用宏生成我们刚才手写的 impl」，并不改变错误处理的原则。即便项目最终引入它们，也要能回答：错误在哪一层被分类，在哪一层被补充上下文，在哪一层被记录日志。

错误类型本身也值得测试。至少要覆盖两类断言：一是「失败时返回的是预期的变体」，二是「Display 文本包含关键信息」。前者保证调用方能可靠分支，后者保证日志可读。这类测试不需要复杂框架，用 matches! 与 to_string().contains(...) 就足够，却能防止重构时误改错误分类。

9.4 main 返回 Result 与错误链打印

fn main() -> Result<(), E> 是稳定特性，其中 E 需要实现 Debug。这让示例程序与小型工具能把错误直接交给运行时输出，省去手写 match。但要注意这种输出调用的是 Debug，样式偏机器化；面向用户的 CLI 仍应在顶层用 Display 格式化，并统一决定退出码。返回 Result 时，运行时打印的是 Debug 形式，还会带上一句类似 Error: ... 的前缀；它适合快速验证想法，但正式工具往往需要把错误映射到整数退出码，让脚本能够判断失败类型。日志与用户输出也要分开：诊断细节写进日志，用户看到的是一句可行动的提示，两者混在一起会让非技术用户无所适从。

下面的例子演示如何沿 source() 遍历整条错误链。实践中这正是日志框架打印错误的方式：第一行是业务语义，后续缩进行给出根因。把这段逻辑放在应用的最外层一次，比散落在各层更可控。

rustRust · 标准库30 行
use std::error::Error;
use std::fmt;
#[derive(Debug)]
struct StepError(&'static str);
impl fmt::Display for StepError {
fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
write!(f, "步骤失败: {}", self.0)
}
}
impl Error for StepError {}
fn run() -> Result<(), Box<dyn Error>> {
Err(StepError("加载配置").into())
}
fn main() {
match run() {
Ok(()) => println!("运行成功"),
Err(e) => {

  • 库 API 不返回 Box<dyn Error>，保留具体类型供调用方分支。
  • 自定义错误的 Display 不换行、不夹杂内部字段名，字段名交给 Debug。
  • 需要重试的错误必须能按类型或 kind 识别，不能依赖解析字符串。
  • 错误类型新增变体属于破坏性变更，库发布时要计入 semver。

10.1 测试分层：单元、集成与文档测试

Rust 的测试天然分成三层，区别不在写法而在「可见性」。单元测试和被测试代码放在同一个文件里，通过 #[cfg(test)] 模块引入，能访问私有实现；集成测试放在包根目录的 tests/ 下，每个文件都是独立的 crate，只能调用公开 API；文档测试藏在文档注释的代码片段里，由 rustdoc 编译并运行。

三层各自解决不同问题。单元测试适合覆盖内部状态机与边界条件，成本最低；集成测试验证「从外部看这个库是否真的好用」，能捕捉公开 API 设计缺陷；文档测试保证示例代码不会随重构悄悄失效。一个常见误区是只写单元测试：它全绿并不代表用户能正确调用你的库。

大白话先用直觉把它讲通

单元测试像检查发动机零件，集成测试像试驾，文档测试像照着说明书装家具。零件合格不等于车能开，车能开不等于说明书没写错，三样都过了才算交付。

测试类型 位置 可见范围 主要目标
单元测试 源码文件内的 #[cfg(test)] mod tests 可访问私有项 算法与边界条件
集成测试 tests/*.rs 仅公开 API 跨模块组合与使用体验
文档测试 文档注释中的代码块 仅公开 API 示例不过期

测试默认并行运行，每个用例都在独立线程上执行。这要求测试之间不共享可变全局状态，也不能依赖执行顺序；需要串行化的场景应当重新设计，而不是靠睡眠碰运气。极少数耗时很长的用例可以标 #[ignore]，让它退出默认集合，再由 cargo test -- --ignored 单独运行。调试失败时用 cargo test -- --nocapture 让 println! 输出不被捕获，往往比反复加断点更快。

10.2 assert 宏与表驱动测试

assert_eq! 失败时会同时打印期望值与实际值，assert! 只给出布尔结果，因此比较值一律优先用前者。assert_ne!、matches! 在处理枚举状态时更贴切；预定会失败的用例用 #[should_panic(expected = "片段")]，expected 写的是 panic 消息的子串，不要依赖完整文本。

表驱动测试把「输入—期望」放进数组，用一个循环跑完所有用例。好处是新增场景只需加一行，失败信息里还能带上输入，定位速度远快于复制粘贴出的十个测试函数。下面这个例子同时演示了表驱动、assert_eq! 的自定义消息和 should_panic。

rustRust · 标准库33 行
#![allow(dead_code)]

s.trim().to_lowercase()
}
#[cfg(test)]
mod tests {

}

浮点比较是个常见陷阱：由于精度误差，assert_eq!(0.1 + 0.2, 0.3) 会失败。正确做法是断言差值小于一个明确的 epsilon，或比较近似相等的整数倍。同理，涉及时间与随机数的测试要把「随机源」作为参数注入，才能在测试中传入固定值；否则今天全绿的套件明天就可能随机失败。

断言要检查真正重要的性质，而不是照抄实现。例如测试排序函数时，断言「结果有序且是原集合的重排」比断言某个固定输出更抗重构；测试缓存时，断言「第二次没有重新计算」比断言最终值更能抓住回归。

10.3 可见性、目录约定与测试成本

tests/ 下每个 .rs 文件都会被编译成独立的测试 crate，因此它们之间不共享私有辅助函数；如果需要复用，把公共辅助代码放进 tests/common/mod.rs 并由各测试文件 mod common;。这个细节经常让初学者困惑：直接放在 tests/ 根目录的 common.rs 会被当成一个独立的测试目标，而不是模块。

测试成本也要纳入设计。启动进程、访问网络、依赖真实时钟的测试会拖慢反馈速度，应当限制数量，并保证可重复。把「纯逻辑」和「副作用」分开，让绝大多数用例落在纯逻辑层，是让测试套件长期保持可用的关键。集成测试尽量用临时目录与本地数据，不依赖外部服务状态。

第三个 rust 块展示集成测试的常见写法：只依赖公开函数，并用 Result 的匹配来断言失败分支。这类测试对重构最友好，因为它不关心内部实现怎么变。

测试命名也值得投入一点心思。像 parse_positive_rejects_negative 这样的名字能直接说明「被测对象 + 场景 + 期望结果」，失败时无需读代码就知道回归了什么。表驱动用例则应在消息里带上输入，正如前面的例子那样。一个维护良好的测试套件，读测试名就能大致画出模块的公开行为清单，这份清单比过时的设计文档可靠得多。

}

10.4 rustdoc 与文档注释

文档注释用 ///，面向库的读者；普通注释用 //，面向维护者。rustdoc 会把 Markdown 渲染成网页，并把文档注释里的代码块当作文档测试执行。这意味着示例不是装饰，而是会被 CI 验证的契约：API 改名后，示例代码编译失败会直接让测试套件变红。

好的模块文档先回答「这个模块解决什么问题」，再给出最小可运行示例，最后说明不适用场景。函数文档则写清参数含义、边界条件、失败方式与复杂度。值得注意的是 panic 与 unsafe 的文档义务：可能 panic 的函数应说明触发条件，unsafe 函数必须有 # Safety 段落描述调用契约。

rustRust · 标准库15 行
#![allow(dead_code)]
/// 把摄氏度转换为华氏度。
///
/// 公式为 `F = C * 9 / 5 + 32`。调用方需保证输入处于合理物理范围，
/// 本函数不做校验，也不处理非有限数。
///
/// 语义示例：`c_to_f(100.0)` 返回 `212.0`。

cargo doc --no-deps --open 只构建当前项目的文档，适合本地检查排版；cargo test --doc 单独运行文档测试。CI 里两者都应执行：前者保障可读性，后者保障示例正确性。

文档结构也有惯例可循：# Examples 给出可运行示例，# Panics 说明触发 panic 的条件，# Errors 列出可能的失败与含义，# Safety 则专属于 unsafe 函数。rustdoc 支持用 [Type] 这样的 intra-doc 链接指向其他项目，让类型说明互相可达。写出这类文档的成本不高，但它把「读源码才能理解」的隐性知识搬到了公开页面上，对库的采用率影响很大。

10.5 基准测试概念与边界

基准测试回答的是「性能有没有退化」，与功能测试回答的「行为对不对」是两件事。标准库提供 #[bench]，但它只在 nightly 通道可用；稳定版通常借助第三方基准框架，或干脆写独立的可执行程序手工计时。把基准测试与功能测试混在同一条流水线里，容易让耗时波动造成误报，因此基准更适合在专用环境按需运行。

  • 先有功能测试，再考虑基准；没有正确性保障的性能数字没有意义。
  • 基准要固定输入规模与编译配置，通常在 release 配置下测量。
  • 比较的是数量级与趋势，不要追逐个位数百分比的噪声。
  • 优化前记录基线，优化后在同一台机器上复测，并保留结论文档。

需要强调：基准测试衡量的是「同样输入下耗时是否变化」，它不会告诉你算法是否选对。复杂度高一个数量级的实现，在小输入上可能反而更快；只看单点数字容易得出错误结论。稳妥做法是覆盖多个输入规模，观察增长趋势，并把结论连同硬件与编译配置一起记录。稳定的基准通常借助专门的框架完成统计分析，标准库自带的 nightly 设施只适合了解原理。

11.1 线程与 move 闭包：所有权就是安全边界

thread::spawn 要求传入的闭包满足 Send + 'static。前者表示「这个类型的值可以跨线程转移」，后者表示「它不借用任何比线程寿命更短的栈数据」。这两条约束把数据竞争最常见的来源挡在编译期：你不可能不小心把一个指向局部变量的引用交给新线程。

满足约束的直接方式是 move 闭包：它把捕获的变量按值搬进闭包。需要注意 move 移动的是变量本身，对于 Vec 这类所有权类型意味着整个缓冲区被转移；对于 &T 这类引用类型，移动的只是引用，仍然受生命周期约束。下面每个线程各拿一份克隆的数据，因此互不干扰。

rustRust · 标准库18 行
use std::thread;
fn main() {
let data = vec![1, 2, 3];
let handles: Vec<_> = (0..3)
.map(|i| {
let owned = data.clone();
thread::spawn(move || {
let sum: i32 = owned.iter().sum();
println!("worker {} sees sum={}", i, sum);
})
})
.collect();
for handle in handles {
handle.join().unwrap();
}
}
大白话先用直觉把它讲通

把线程想成外包团队。你交给它的资料必须是一份完整的复印件（move 转移所有权），不能是一张写着「去我办公桌上拿」的便条（借用局部变量）。等团队干完活要签收（join），否则主程序可能先收工走人。

线程与异步不是非此即彼：线程适合 CPU 密集型且数量可控的任务，异步适合大量等待 IO 的连接。线程由操作系统调度，上下文切换成本较高但使用直观；异步任务由运行时调度，单线程上可以挂起成千上万个等待中的任务。选择时先看「任务是计算多还是等待多」，再看团队对调试复杂度的承受能力，而不是盲目追随性能数字。

11.2 Arc<Mutex>：共享可变状态

当确实需要多个线程改动同一份数据时，Arc<Mutex<T>> 是标准库给出的基本组合：Arc 提供原子引用计数，让同一个值有多个所有者；Mutex 保证同一时刻只有一个线程能拿到内部数据的可变访问。锁的获取返回 Guard，它在离开作用域时自动释放，因此不会因为忘记解锁而死锁——但「拿着锁调用可能等待的操作」仍然会造成死锁或长时间阻塞。

计数器是最典型的例子。循环内每次只锁住极短的临界区，累加后立刻释放；用 Arc::clone 而不是直接克隆数据，确保共享的是同一个计数器。

rustRust · 标准库22 行
use std::sync::{Arc, Mutex};
use std::thread;
fn main() {
let counter = Arc::new(Mutex::new(0u64));
let mut handles = Vec::new();
for _ in 0..8 {
let shared = Arc::clone(&counter);
handles.push(thread::spawn(move || {
for _ in 0..1000 {
let mut guard = shared.lock().unwrap();
*guard += 1;
}
}));
}
for handle in handles {
handle.join().unwrap();
}
println!("counter = {}", *counter.lock().unwrap());
}

lock() 返回 Result，因为持锁线程 panic 后锁会处于「中毒」状态。示例里用 unwrap() 是假设工作线程不会 panic；生产代码应当根据业务决定是恢复中毒锁、记录错误还是终止流程。还要警惕锁的粒度：锁太少导致竞争，锁太细导致逻辑碎片化，两者都要靠实际数据判断。

另一个实用细节是 try_lock：它不等待，拿不到锁立即返回，适合「能做就做、不能就跳过」的刷新类任务。死锁的经典成因是多个线程以不同顺序获取两把锁；约定全局加锁顺序，或干脆把两把锁合成一把保护同一个结构体，通常比事后排查更省事。还要避免跨 await 持有标准库的锁：wait 期间线程可能被运行时切换去执行别的任务，而 MutexGuard 并不适合跨任务传递，应改用异步运行时提供的锁。

11.3 mpsc channel：以通信代替共享

共享内存不是并发的唯一答案。mpsc channel 让发送端持有 Sender、接收端持有 Receiver，数据通过队列传递，所有权随之转移。当所有发送端都被丢弃时，通道关闭，for msg in rx 自然结束——这个特性让「工作线程完成即退出」的协作变得非常简洁。

选择经验：需要多方修改同一份状态时用 Arc<Mutex<T>>；需要把任务或数据从生产者交给消费者时用 channel。后者把同步点集中在消息传递上，通常更容易推理，也更容易改成多消费者或加缓冲。

rustRust · 标准库16 行
use std::sync::mpsc;
use std::thread;
fn main() {
let (tx, rx) = mpsc::channel::<String>();
let producer = thread::spawn(move || {
for word in ["alpha", "beta", "gamma"] {
tx.send(word.to_string()).unwrap();
}
});
for msg in rx {
println!("received: {}", msg);
}
producer.join().unwrap();
}

同步通道与异步通道是两个概念：这里的 mpsc::channel 是同步的，send 会阻塞直到接收端准备好；异步运行时提供的通道则把等待交给调度器，不应混用。

标准库还提供 sync_channel，它可以设置有限容量，让发送方在队列满时阻塞，从而形成天然的反压；try_recv 则让接收方在没有消息时立即返回，适合轮询式的工作循环。错误类型 SendError 会带回没能发出的消息，这对「队列关闭后如何回收数据」很有用。设计数据流时，先明确「消息丢了能不能接受」「生产者会不会比消费者快很多」，再决定用无界通道还是有界通道。

11.4 Send / Sync 的直觉与边界

Send 表示「值可以安全地转移到另一个线程」，Sync 表示「值的引用可以安全地共享到另一个线程」。Mutex<T> 只要 T: Send 就同时满足两者，因为它负责串行化访问；Rc<T> 使用非原子计数，因此既不是 Send 也不是 Sync，跨线程使用会被编译器拒绝。

类型 Send Sync 原因
i32、String 是 是 无内部共享状态
Rc<T> 否 否 引用计数非原子
Arc<T> 取决于 T 取决于 T 计数原子，数据仍需安全
Mutex<T> T: Send 时是 T: Send 时是 通过锁串行化

这些 trait 大多是自动派生的：一个类型若所有字段都 Send，它自身就自动是 Send。手写 unsafe impl Send 属于高级操作，只有在你能证明类型内部的不变量在跨线程时依然成立才可做，例如某些自带同步机制的自制容器。错误的手动实现会把数据竞争带进安全代码，责任完全由实现者承担，因此任何这样的 impl 都应附带详细的安全论证。

把约束写进函数签名能让错误出现在调用点，而不是深处的某个 spawn：

rustRust · 标准库14 行
use std::thread::JoinHandle;
fn run_on_thread<F>(f: F) -> JoinHandle<()>
where
F: FnOnce() + Send + 'static,
{
std::thread::spawn(f)
}
fn main() {

11.5 async/await 状态机与运行时概念

async fn 并不会直接创建一个线程。编译器把它改写成一个实现 Future 的匿名状态机：每次遇到 .await，若被等待的 Future 返回 Pending，状态机保存当前进度并让出；恢复时从断点继续。所以 Future 本身是惰性的，没有任何轮询就不会前进。

轮询由执行器驱动，而真正处理「何时可继续」的是反应器与任务调度器，这些合起来就是运行时。运行时负责把就绪的唤醒投回队列、管理定时器与 IO，它的取舍直接决定吞吐量与延迟。下面用 std 手写一个最小的轮询器，目的不是替代运行时，而是让「Future 需要被 poll 才会动」这件事变得可见。

rustRust · 标准库26 行
use std::future::Future;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};
struct NoopWaker;
impl Wake for NoopWaker {
fn wake(self: Arc<Self>) {}
}
fn block_on<F: Future>(fut: F) -> F::Output {
let waker = Waker::from(Arc::new(NoopWaker));
let mut cx = Context::from_waker(&waker);
let mut fut = Box::pin(fut);
loop {
match fut.as_mut().poll(&mut cx) {
Poll::Ready(value) => return value,
Poll::Pending => std::thread::yield_now(),
}
}
}
async fn answer() -> i32 { 40 + 2 }
fn main() {
println!("answer = {}", block_on(answer()));
}

这里的 NoopWaker 什么也不做，因此真正会 Pending 的 Future 会一直空转。这恰恰说明了运行时的价值：它实现复杂的唤醒机制，让等待中的任务在条件满足时才被重新调度。不要在生产代码中手工轮询 Future，也不要在 async 代码里执行长时间阻塞调用，那会卡住整个工作线程。

Pin 之所以出现，是因为自引用的状态机在被移动后可能让内部指针失效；它保证 Future 一旦被轮询就不会再被搬走，而 Box::pin 是最简单的固定方式。另一个常被忽略的概念是取消：丢弃一个 Future 就等于取消它，析构函数仍会运行，但「操作是否已生效」必须由业务层设计，例如写入前先生成幂等键。至于运行时选择，单线程运行时适合大量 IO 且任务轻量的场景，多线程运行时能利用多核但要处理共享状态，两者都应通过压测决定。

12.1 unsafe 是契约，不是开关

unsafe 并不关闭借用检查器，它只额外允许五件事：解引用裸指针、调用 unsafe 函数、访问可变静态变量、实现 unsafe trait、读取 union 字段。类型系统的其余部分照常工作。因此「编译器报错就加 unsafe」是彻底的误解——unsafe 不能修复类型错误，它只是把一部分安全责任从编译器转移到人。

真正的风险在于未定义行为（UB）。一旦触发 UB，编译器对程序的任何假设都不再成立，优化器可能把看似无关的分支优化掉，问题往往在远离现场的地方才暴露。写 unsafe 的正确姿势是把它当成一个需要书面合同的特权操作：谁调用、满足了什么前提、为什么这段实现成立，都必须写清楚。

大白话先用直觉把它讲通

unsafe 像医院里的特殊药品。它不会让你变成医生，只是允许你在有明确处方时使用；处方上必须写适用条件和剂量，否则出了事没人能帮你追溯。安全 Rust 是「编译器替你守门」，unsafe 是「你亲自签名守门」。

未定义行为的危险之处在于它不留痕迹。触发 UB 的代码可能在测试环境完全正常，却在优化后的发布版本里产生错误结果；编译器有权基于「程序不会 UB」这一前提做激进优化。因此 unsafe 代码的审查标准是「能否在纸上证明契约」，而不是「跑起来没崩」。这也是为什么标准库里的 unsafe 实现往往配有大量注释：它们记录的是证明过程，而不是操作说明。

12.2 裸指针与 unsafe 块：最小包围

裸指针 *const T / *mut T 与引用不同：它不保证非空、不保证对齐、不保证指向有效内存、也不参与生命周期检查。这些保证全部由程序员承担。as_ptr() 从切片或数组得到裸指针是安全的，但一旦解引用就需要 unsafe。

工程原则是「最小包围」：unsafe 块只包住真正需要特权的那一行，把空指针检查、长度计算、边界判断留在安全代码里。这样审查者只需盯住极短的一段，并能对照紧邻的 SAFETY 注释验证契约。

rustRust · 标准库20 行
#![allow(dead_code)]
/// 对一段连续的 i32 求和。
/// 调用方必须保证 ptr 指向至少 len 个已初始化的 i32，且期间不被并发写入。
fn sum_slice(ptr: *const i32, len: usize) -> i64 {
if len == 0 { return 0; }
assert!(!ptr.is_null(), "ptr 不能为空");
assert!(ptr.align_offset(std::mem::align_of::<i32>()) == 0, "指针未对齐");
let mut total = 0i64;
for i in 0..len {
// SAFETY: 调用方契约保证 ptr..ptr+len 已初始化且有效
unsafe { total += *ptr.add(i) as i64; }
}
total
}
fn main() {
let data = [1i32, 2, 3, 4];
println!("sum = {}", sum_slice(data.as_ptr(), data.len()));
}

align_offset 在这里用于演示概念；实际代码更常见的是直接让类型系统保证对齐（例如从 &[i32] 取指针），而不是运行时补救。记住：检查能挡住一部分错误，但挡不住「指针指向已经释放的内存」这类时序问题。

裸指针还涉及「来源」（provenance）：一个由已释放的 Vec 得到的指针，即使数值地址看起来仍合理，也不再可用于访问。安全的做法是在函数参数里直接接收 &[T]，让借用检查器替你保证有效期；只有在与硬件或外部库交互时才退回到裸指针。另一个常被忽视的点是 usize 与指针的整数转换：把指针转成整数再转回来，语言并不保证在所有平台上保持有效，跨 FFI 时尤其要小心。

12.3 unsafe fn 与 # Safety 文档

把裸指针逻辑包进 unsafe fn，可以把契约集中到一处，让调用点只需证明一次。函数文档里的 # Safety 段落是行业惯例，rustdoc 会把它渲染成醒目的警告区，clippy 的 missing_safety_doc lint 也会检查它。契约应写成可验证的条件，而不是「使用时小心」这种空话。

下面的 first_byte 即使内部做了空指针与长度检查，仍标记为 unsafe：因为仅凭一个裸指针无法证明它指向的内存有效可读。调用方必须来自可信来源，例如有效切片的 as_ptr()。

rustRust · 标准库20 行
#![allow(dead_code)]
/// 读取缓冲区的首字节。
///
/// # Safety
/// `ptr` 必须是非空、正确对齐、且至少可读 `len` 个字节的指针；
/// 调用期间该内存不得被其他线程写入。
unsafe fn first_byte(ptr: *const u8, len: usize) -> Option<u8> {
if ptr.is_null() || len == 0 {
return None;
}
// SAFETY: 调用方已保证指针有效且 len > 0
Some(unsafe { *ptr })
}
fn main() {
let buf = b"rust";
let byte = unsafe { first_byte(buf.as_ptr(), buf.len()) };
println!("{:?}", byte);
}

理想目标是把 unsafe 收敛进薄薄一层安全封装，对外只暴露普通的安全 API。例如用 &[u8] 作参数，内部再转裸指针；这样调用方不需要写 unsafe，也不再有机会违反契约。这也是标准库自身的组织方式。

与之相对的是 unsafe trait，例如 Send、Sync 或自行定义的「实现者必须满足某不变量」的 trait。实现它们意味着你向整个类型系统作出承诺，编译器会据此在别处省略检查。因此除非你完全掌控类型的内部表示并能证明该承诺，否则不要手写实现；遇到编译器提示「类型不满足 Send」时，优先修正设计（换用 Mutex 或原子类型），而不是加一行 impl 让错误消失。

12.4 FFI 与 extern "C"

跨语言调用必须统一 ABI（调用约定、参数传递、名称修饰）。extern "C" 表示使用 C 的 ABI，是 FFI 的默认选择；Rust 自身的 ABI 不稳定，绝不能跨语言边界使用。结构体跨越边界时要用 #[repr(C)] 固定字段布局，否则编译器可以自由重排字段，另一端的 C 代码会读到错误偏移。

rustRust · 标准库18 行
#![allow(dead_code)]
#[repr(C)]
pub struct CPair {
pub x: i32,
pub y: i32,
}
/// 导出给 C 侧调用的函数，使用 C ABI 与未修饰符号名。
#[no_mangle]
pub extern "C" fn c_add(a: i32, b: i32) -> i32 {
a.wrapping_add(b)
}
fn main() {
let pair = CPair { x: 2, y: 3 };
println!("size={} sum={}", std::mem::size_of::<CPair>(), c_add(pair.x, pair.y));
}

从 Rust 调用 C 函数时写法是 unsafe extern "C" { fn name(...); }，因为编译器无法验证外部函数的契约。字符串与集合尤其危险：Rust 的 String、Vec 布局不保证与 C 一致，应转换成 *const c_char 加长度，或由 C 侧分配的缓冲区，并明确谁负责释放。注意 edition 2024 起 #[no_mangle] 需要写成 #[unsafe(no_mangle)]，本单元统一用 2021。

字符串是最容易出错的边界。C 侧期待的是以零结尾的字节序列，Rust 的 String 不保证这一点；标准库提供了 std::ffi::CString 用于构造、CStr 用于借用查看，对应类型是 c_char。反过来，从 C 拿回字符串时不能凭空造出 &str：必须验证 UTF-8 有效性、知道长度，并明确缓冲区由谁释放。分配器也必须一致——在一侧 malloc 的内存要在同一侧 free，跨边界传递所有权前先写清协议。

13.1 release profile 与产物取舍

同一个 crate 在 cargo build 与 cargo build --release 下会产生截然不同的二进制。debug 配置追求编译速度和调试体验：优化级别低、保留符号与调试信息、打开溢出检查。release 配置追求运行效率：默认 opt-level = 3、剥离部分调试信息、关闭 debug_assertions。把「只在开发时检查」的逻辑挂到 debug_assertions 上，可以让发布版省掉开销而不丢失开发期保护。

下面的片段展示最常见的自定义 profile。lto 做跨 crate 内联，能减小体积并提升速度，代价是链接时间显著变长；codegen-units = 1 让优化器看到更大的整体，同样以编译时间为代价；panic = "abort" 让 panic 直接终止进程，可以去掉展开表，但会跳过析构函数，不能随便打开。

tomlRust · 标准库9 行
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
strip = true
# panic = "abort" # 只在确认不需要展开时用
[profile.dev.package."*"]
opt-level = 2 # 只优化依赖，提升开发期运行速度

代码侧也能感知构建配置。cfg!(debug_assertions) 在 cargo 的 debug 构建中为真、release 构建中为假；option_env! 读取的环境变量若不存在则返回 None，因此在 rustc 直接编译时也安全。下面这个小程序演示了如何让同一份源码输出不同的渠道标识。

rustRust · 标准库8 行
fn build_channel() -> &'static str {

}
fn main() {
println!("channel = {}", build_channel());

}

在 cargo 构建中，CARGO_PKG_VERSION、CARGO_PKG_NAME 等变量由 Cargo 自动注入；用 env! 读取则会在变量缺失时直接编译失败，适合「必须存在」的元数据。option_env! 适合可选信息。

strip = true 会去掉符号表，让产物明显变小，但线上崩溃时的回溯信息也会变得难读。折中方案是保留符号、在发布流水线里单独生成并归档调试符号文件，排查时再用它还原栈帧。profile 还可以按包细分：[profile.release.package."*"] 单独控制依赖的优化级别，让项目代码保持激进优化而依赖不至于拖慢构建。改动这些配置后要用真实负载复测，体积数字好看不代表性能一定更好。

13.2 feature 开关与发布渠道

给不同渠道发布不同产物时，最忌讳复制整份代码库。更好的做法是把差异表达成 feature：默认关闭重型能力，发布时按渠道显式开启。这样所有渠道共享同一套测试与代码审查，差异集中在 Cargo.toml 的几行配置里。

feature 应当保持可叠加，且不要在打开时改变已有函数的语义。展示层的能力（遥测、实验性开关）很适合用 feature 控制；会改变数据格式的能力则应谨慎，因为它可能让两个渠道产生互不兼容的产物。下面的模板用 feature 决定是否编译遥测上报，report 在未启用时退化成空函数，调用方代码完全不用改。

rustRust · 标准库14 行
#![allow(dead_code, unexpected_cfgs)]
#[cfg(feature = "telemetry")]
fn report(event: &str) {
println!("[telemetry] {}", event);
}
#[cfg(not(feature = "telemetry"))]
fn report(_event: &str) {}
fn main() {
report("startup");
println!("startup done");
}

  • cargo fmt --all -- --check：格式门禁，失败时提示运行 cargo fmt --all。

  • cargo build --release --locked：验证锁文件与清单一致且发布配置可构建。

13.5 semver、变更日志与交付纪律

语义化版本是库作者与使用者之间的契约：0.x 阶段任何次版本都可能破坏兼容，进入 1.0 后主版本号变化才代表不兼容变更。新增公开 API、放宽约束属于兼容变更；删除或改名公开项、改变 trait 实现要求、给公开枚举加变体都可能破坏下游，应当计入主版本号。

变更日志不是发布时补写的流水账，而是开发过程中持续记录「用户能感知的变化」。按 Added、Changed、Fixed、Removed 分类，每条说明影响范围与迁移方式。它与 semver 互为表里：日志解释「为什么升这个版本号」，版本号告诉使用者「该不该升级」。

  • 每次合并请求都包含测试或文档变更，门禁才有意义。
  • CI 失败时先修主干，不要靠重试掩盖偶发问题。
  • 发布后立刻打 tag 并记录产物哈希，便于事后追溯。
  • 对已发布版本做修复时，选择向后兼容的补丁版本，避免 downstream 被迫跟随破坏性升级。

把变更日志当作面向用户的沟通渠道，而不是提交记录的复制粘贴。一次破坏性改动应写清「谁会受影响、需要怎么改」，几句话的迁移示例往往比一长串内部实现说明更有价值。版本号、tag、变更日志条目与发布公告应当指向同一个提交，这条一致性纪律在出了问题需要回滚时尤其有用。

交付链的最后一步是验证，而不是上传成功。发布后立刻在一个干净环境中安装该版本、跑一遍最小示例，能够发现「本地能编译但漏了文件」「feature 组合与文档不符」这类问题。把这一步自动化并纳入发布后检查清单，交付才算真正闭环。

14.1 复杂度速查与估算手法

big-O 描述的是输入规模 n 趋向无穷时增长速度的量级，它刻意忽略常数系数与低阶项。刷题时真正有用的不是精确推导，而是看到一个循环结构就能立刻判断量级：一层循环是线性，两层嵌套通常是平方，每次把规模减半是对数，分治加合并是 n log n。

复杂度又分时间与空间两侧，两者经常可以互相交换。用一张哈希表把查找降到 O(1)，代价是 O(n) 的额外内存；用 bitset 标记状态能省下布尔数组的开销，却要求值域不能太大。面试与笔试里更常见的是最坏情况复杂度：快速排序平均 O(n log n)，但有序输入下退化成 O(n²)，所以在要求稳定上界的场景要改用归并排序，或先打乱输入。空间复杂度要连递归调用栈一起算：一个深度为 n 的递归 DFS，即便每层只存一个变量，也占用 O(n) 的栈空间，这正是后面强调迭代写法的理由。

复杂度 典型场景 n = 10³ n = 10⁶ 判断要点
O(1) 下标访问、哈希查询 1 1 与 n 无关
O(log n) binary search、堆调整 ≈10 ≈20 每轮规模减半
O(n) 单层循环、前缀和 10³ 10⁶ 每元素常数次

O(2ⁿ) 子集枚举 天文数字 不可行 状态爆炸
O(n!) 全排列 不可行 不可行 阶乘增长

估算时有三个容易踩的坑。第一，对数的底不重要：log₂n、log₁₀n 只差一个常数，所以统一写成 log n。第二，均摊复杂度要单独记：Vec 的 push 在扩容时是 O(n)，但按倍增扩容，均摊下来是 O(1)；并查集的路径压缩加按秩合并也是均摊近乎 O(1)。第三，复杂度要算到输入读取：读入一百万个整数本身就是 O(n)，一个 O(n log n) 的算法配上 O(n²) 的字符串拼接，整体依旧是平方级。

反推法是更实用的技巧：先看 n 的范围，再倒推所需的复杂度。n ≤ 20 暗示子集枚举或状态压缩，n ≤ 500 允许 O(n³) 的区间 DP，n ≤ 2000 大致是 O(n²) 的天下，n ≥ 10⁵ 则必须 O(n log n) 甚至 O(n)。看到 n ≤ 10⁶ 且内存限制 256 MB，就要警觉一个 Vec<i64> 已经吃掉 8 MB，若干个矩阵式数组很容易超限。把约束翻译成复杂度，再把复杂度翻译成数据结构，这一步比背模板更能决定解题速度。

大白话先用直觉把它讲通

复杂度就是在问"数据量翻十倍，程序会不会慢到没法用"。O(n) 大致慢十倍，O(n²) 大约慢一百倍，O(log n) 几乎感觉不到变化。写算法前先花十秒估一下量级，能帮你早早放弃那些注定超时的朴素想法。

14.2 输入输出与整数解析

Rust 标准库没有 scanf，竞赛里通行的做法是一次性把 stdin 读成字符串，再用 split_whitespace 切成词元。这样做有两个好处：系统调用次数少，且不必关心换行符是 \n 还是 \r\n。下面的 Scanner 用泛型 + FromStr 统一解析所有整数类型，是后面各单元的通用零件。

rustRust · 标准库34 行
use std::io::{self, Read};
use std::str::FromStr;
struct Scanner {
tokens: Vec<String>,
pos: usize,
}
impl Scanner {
fn new() -> Self {
let mut s = String::new();
io::stdin().read_to_string(&mut s).unwrap();
let tokens = s.split_whitespace().map(|t| t.to_string()).collect();
Scanner { tokens, pos: 0 }
}
fn next<T: FromStr>(&mut self) -> T {
// 先解析再自增 pos，彻底避开对 self 的借用冲突
let val = self.tokens[self.pos].parse::<T>().ok().expect("parse failed");
self.pos += 1;
val
}
}
fn main() {
let mut sc = Scanner::new();
let n: usize = sc.next();
let mut v: Vec<i64> = Vec::with_capacity(n);
for _ in 0..n {
v.push(sc.next::<i64>());
}
let sum: i64 = v.iter().sum();
println!("{} {}", n, sum);
}

注意 parse::<T>().ok().expect(...) 的写法：T::Err 未必实现 Debug，直接 unwrap() 可能编译不过，而 .ok() 先转成 Option<T>，expect 就不再需要错误类型可打印。另外 tokens 存的是 String，每个词元一次分配；如果追求极致，可以改成保存 &str 切片（需要让 Scanner 持有字符串本体），但日常刷题这点开销可以忽略。

输出侧同样有讲究。println! 每次调用都可能触发一次系统调用，输出上万行时应当先把结果攒进 String 或 Vec<String>，最后一次性 print!。Rust 的格式化宏支持与 C 类似的对齐语法，例如 {:>8} 表示右对齐占八格，{:.2} 表示保留两位小数。整数解析要注意前导零与正负号：parse::<i64>() 能正确处理 -12，但把负数解析成 usize 会直接失败，所以读入可能带负号的数据时一定用 i64，只在确认非负且需要当下标时再转换。

14.3 Rust 算法工程约定

Rust 写算法与 C++ 最大的差别集中在三个地方。

其一，预分配与容量。 已知元素个数时先 Vec::with_capacity(n)，避免反复扩容时的数据搬运。下文的前缀和数组预分配 n + 1 个位置，多出来的 pref[0] 作为哨兵，能把"区间和"统一成一次减法。

其二，usize 是下标唯一合法类型。 它的代价是不能为负：写下 i - 1 而 i == 0 时，debug 构建会直接 panic，release 构建则回绕成天文数字。正确做法是先判断 i > 0，或者把下标转成 isize 做减法后再转回来。其三，避免递归爆栈。 Rust 默认主线程栈只有几 MB，深达十万层的 DFS 会 stack overflow。把递归改写成显式栈（用 Vec 当栈）既安全又可控。

借用检查器是另一个分水岭。C++ 里常见的"遍历容器的同时修改容器"在 Rust 中被严格禁止：不能在持有元素不可变引用的同时改动整个容器。算法代码里更典型的冲突是"遍历 Vec 的同时往同一个 Vec 里 push"，编译器会直接拒绝。破解办法有三种：把索引范围先算出来，用 for i in 0..n 驱动循环；先把要写入的值收集到临时 Vec，循环结束后统一 extend；或者用 std::mem::take 把容器换出，处理完再放回去。习惯这些模式之后，Rust 的严格反而成了安全网：它把"遍历时修改导致迭代器失效"这类经典 bug 拦在编译期，而不是留到线上。

rustRust · 标准库24 行
fn main() {
let n = 100_000usize;
// 约定一：预分配 + 哨兵，前缀和多开一格
let mut pref: Vec<i64> = Vec::with_capacity(n + 1);
pref.push(0i64);
for i in 0..n {
pref.push(pref[i] + (i as i64) * 2);
}
// 约定二：左闭右开区间 [l, r)，减法方向保证 r >= l
let (l, r) = (3usize, 9usize);
let sum = pref[r] - pref[l];
// 约定三：迭代替代递归，绝不触碰调用栈上限
let mut acc = 0i64;
for x in 1..=n {
acc += x as i64;
}
println!("sum[{}..{}) = {}", l, r, sum);
println!("1..={} = {}", n, acc);
println!("len = {}, cap = {}", pref.len(), pref.capacity());
}

这段代码还演示了另一个细节：i as i64 是有意的显式转换。Rust 不会在 usize 与 i64 之间隐式转换，把转换写在明面上，能立刻暴露"这里可能出现负数"的设计意图。

还有一个反复出现的细节：用下标而不是持有可变引用。假设要同时访问 a[i] 和 a[i - 1] 并修改其中一个，写成 let x = &mut a[i]; let y = &a[i - 1]; 会被拒绝，因为编译器无法静态证明两个下标不同。改用 let (left, right) = a.split_at_mut(i); 就能拿到两段互不重叠的可变切片，或者干脆先读出需要的旧值到局部变量，再写回原处。另一个实践是用 .get(i) 返回 Option 来替代直接下标访问，在边界不确定的地方把 panic 变成显式的 if let，调试时定位问题会快很多。这几个小习惯累积起来，能省下大量与借用检查器搏斗的时间。

14.4 对拍：让暴力算法当裁判

优化算法写完后最难的是确认它真的对。对拍的思路是：准备一个绝对正确的朴素版本和一个待验证的快速版本，用随机数生成成千上万组小数据，逐个比对输出，一旦不一致就打印现场。小数据下 O(n²) 跑得飞快，正好当裁判。

rustRust · 标准库45 行
fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
fn max_subarray_slow(a: &[i64]) -> i64 {
let mut best = i64::MIN;
for i in 0..a.len() {
let mut s = 0i64;
for j in i..a.len() {
s += a[j];
best = best.max(s);
}
}
best
}
fn max_subarray_fast(a: &[i64]) -> i64 {
let mut best = i64::MIN;
let mut cur = 0i64;
for &x in a {
cur = x.max(cur + x);
best = best.max(cur);
}
best
}
fn main() {
let mut seed = 42u64;
for t in 0..500 {
let n = (lcg(&mut seed) % 20 + 1) as usize;
let a: Vec<i64> = (0..n)
.map(|_| (lcg(&mut seed) % 21) as i64 - 10)
.collect();
let slow = max_subarray_slow(&a);
let fast = max_subarray_fast(&a);
if slow != fast {
println!("MISMATCH case {}: {:?} slow={} fast={}", t, a, slow, fast);
return;
}
}
println!("all 500 cases passed");
}

这里的随机数发生器是线性同余（LCG），必须用 wrapping_mul / wrapping_add，否则 debug 构建下乘法溢出会 panic。对拍的价值在于它把"我觉着对了"变成"五百组数据都对了"；尤其是二分边界、单调栈的弹出条件这类极易错一两个位置的代码，对拍能在几秒内抓出漏洞。

对拍还有两个进阶习惯。一是固定随机种子并打印它：一旦发现错误用例，把种子记下来就能稳定复现，而不是靠运气再撞一次。二是缩小用例：找到出错的小数组后，尝试逐个删掉元素，只要删除后两个版本仍然不一致就继续删，最后得到一个极小的反例，往往一眼就能看出是哪行边界写错。做题时把暴力解法保留在代码里并用注释开关，比写完就删更划算——它既是正确性保险，也是理解题意的镜子。大量刷题之后你会发现，真正的难点很少是模板记不住，而是边界条件与循环不变量；把对拍当常规武器，这类细节错误会越来越早地暴露。

15.1 数组模拟栈与队列

栈只在一端进出，用 Vec 的末尾当栈顶再自然不过：入栈是 push，出栈是 pop，两者都是均摊 O(1)。队列则必须支持头部出队，普通 Vec 的 remove(0) 要搬动后面所有元素，是 O(n)，所以标准库提供了双端队列 VecDeque，它的 push_back / pop_front 都是 O(1)。如果题目固定容量，也可以手写一个环形数组队列：用 head 指向队首下标，用 len 记录元素个数，写入位置是 (head + len) % cap。

结构 推荐实现 入队/入栈 出队/出栈 关键陷阱
栈 Vec<T> push 均摊 O(1) pop O(1) 栈顶在尾部，别反向遍历
队列 VecDeque<T> push_back O(1) pop_front O(1) 别用 Vec::remove(0)
定长队列 手写环形数组 取模定位 O(1) 移动 head O(1) head 回绕、len 与 cap 相等

手写环形队列时最妙的一点是永远不要写 head - 1：那在 head = 0 时会触发 usize 下溢。改用 head + len 表示下一个写入位置，配合取模，既避免了负数，也让"队满"的判断变成 len == cap。这个思路在后面所有涉及下标的算法里都会反复出现。

实际刷题时，如果题目没有明确要求固定容量，直接用 VecDeque 是更省心的选择：它会自动扩容，with_capacity 只是提前预留而不是硬上限。手写环形队列的价值主要在于理解"逻辑下标"与"物理下标"的分离——head 会随着出队一直增长并回绕，len 才是真实元素数，任何关于队满、队空的判断都必须基于 len。把这套心智模型掌握后，后续实现单调队列、BFS 队列乃至循环缓冲区都会轻松很多。另外 while let Some(v) = q.pop_front() 是 Rust 里 drain 一个容器的惯用写法，比 while !q.is_empty() 更简洁，也把"取不到就停"的语义写在了类型里。

struct ArrayQueue {
buf: Vec<i32>,
head: usize,
len: usize,
}
impl ArrayQueue {
fn new(cap: usize) -> Self {
ArrayQueue { buf: vec![0; cap], head: 0, len: 0 }
}
fn push_back(&mut self, v: i32) -> bool {
if self.len == self.buf.len() {
return false;
}
let pos = (self.head + self.len) % self.buf.len();
self.buf[pos] = v;
self.len += 1;
true
}
fn pop_front(&mut self) -> Option<i32> {
if self.len == 0 {
return None;
}
let v = self.buf[self.head];
self.head = (self.head + 1) % self.buf.len();
self.len -= 1;
Some(v)
}
}
fn main() {
let mut q = ArrayQueue::new(4);
for x in 1..=6 {
if !q.push_back(x) {
println!("full at {}", x);
break;
}
}
while let Some(v) = q.pop_front() {
print!("{} ", v);
}
println!();
}

栈像一摞盘子，只能从顶上拿；队列像排队买票，先来的先走。单调栈和单调队列则是在这两个容器上加了一条规矩：里面的值必须按大小排好队，一旦有人破坏了规矩就把队尾不合格的请出去。这样队首永远是当前最优解，查询就是 O(1)。

15.2 单调栈：每日温度与最大矩形

单调栈的核心不变量是：栈中下标对应的值保持单调（递增或递减），新元素到来时不断弹掉破坏单调性的栈顶，直到满足单调性再入栈。因为每个下标最多入栈一次、出栈一次，总时间是 O(n)，而不是乍看之下的 O(n²)。这个"每个元素只进出各一次"的摊还论证是单调结构的灵魂：内层的 while 看起来像嵌套循环，但表面上多出来的工作量被分摊到了整趟遍历上，所以千万不能想当然地把它判成平方复杂度。

"每日温度"要求找出右边第一个更高的温度。维护一个下标栈，栈中温度严格递减。遍历到位置 i、温度 t 时，只要栈顶下标 j 的温度低于 t，说明 i 就是 j 要等的"更暖和的一天"，弹出 j 并记录距离 i - j。这里存下标而非温度是必要的：答案要的是天数差，只有下标才能算距离。由于弹出时必然有 i > j，i - j 不会下溢。

rustRust · 标准库22 行
fn daily_temperatures(t: &[i32]) -> Vec<usize> {
let n = t.len();
let mut ans = vec![0usize; n];
let mut st: Vec<usize> = Vec::with_capacity(n); // 栈中温度严格递减
for (i, &temp) in t.iter().enumerate() {
while let Some(&j) = st.last() {
if temp > t[j] {
let j = st.pop().unwrap();
ans[j] = i - j; // i > j，减法安全
} else {
break;
}
}
st.push(i);
}
ans
}
fn main() {
let t = [73, 74, 75, 71, 69, 72, 76, 73];
println!("{:?}", daily_temperatures(&t));
}

注意 while let Some(&j) = st.last() 里的 &j：它把下标复制出来，而不是持有对栈顶的引用。如果写成 Some(j)，j 是个 &usize 引用，紧接着调用 st.pop() 需要可变借用，与它冲突，编译不过。这是 Rust 写单调结构最常遇到的借用冲突，解法就是先 copy 出标量再修改容器。

"柱状图最大矩形"是单调栈的另一经典应用。枚举每根柱子作为高度，需要知道它向左向右能延伸多远——也就是左右两侧第一个比它矮的位置。遍历时用递增栈，遇到比栈顶矮的柱子就弹出，此时弹出柱子的"右边界"是当前位置 i，"左边界"是弹出后新的栈顶加一。为了让栈中所有柱子在结束时都被弹出结算，在末尾追加一个高度为 0 的哨兵。

rustRust · 标准库26 行
fn largest_rectangle(heights: &[i32]) -> i32 {
let mut h = Vec::with_capacity(heights.len() + 1);
h.extend_from_slice(heights);
h.push(0); // 哨兵：强制清空栈
let mut st: Vec<usize> = Vec::with_capacity(h.len());
let mut best = 0i32;
for (i, &cur) in h.iter().enumerate() {
while let Some(&top) = st.last() {
if h[top] <= cur {
break; // 保持栈中高度严格递增
}
let idx = st.pop().unwrap();
let height = h[idx];
let left = st.last().map_or(0, |&j| j + 1);
let width = i - left; // i 一定大于 left
best = best.max(height * (width as i32));
}
st.push(i);
}
best
}
fn main() {
let a = [2, 1, 5, 6, 2, 3];
println!("{}", largest_rectangle(&a));
}

这里的弹出条件写成 h[top] <= cur 而不是 <：相同高度时弹出旧的、保留新的，能让左边界计算更干净，也避免重复结算。哨兵必须是 0 而不是 -1，因为高度非负；若输入可能含负数，要改用 -1 或显式循环清空栈。

拿 [2, 1, 5, 6, 2, 3] 走一遍：当 i 走到下标 4（高度 2）时，栈顶是高度 6 的下标 3，6 > 2 被弹出，此时新栈顶是高度 5 的下标 2，左边界为 3，宽度为 4 - 3 = 1，面积 6；继续弹出高度 5，左边界变成下标 1 之后，宽度为 4 - 2 = 2，面积 10，这就是答案。注意"左边界 = 弹出后新栈顶下标 + 1"这一步：新栈顶是最后一个比当前柱矮的柱子，矩形自然只能从它右边开始。这种在脑中手动模拟两三个元素的能力，比死记模板更能帮你定位边界错误。

15.3 单调队列：滑动窗口最大值

滑动窗口最大值要不断回答"当前窗口里谁最大"。单调队列的做法是：队列里只保存可能成为未来最大值的下标，并保证它们对应的值从队首到队尾严格递减。于是队首永远是答案。每次新元素 x 到来要做两件事：先把已经滑出窗口的过期下标从队首弹掉；再从队尾弹掉所有不大于 x 的下标——因为它们既比 x 小又比 x 早出窗，永远不可能再成为最大值。

rustRust · 标准库35 行
use std::collections::VecDeque;
fn sliding_max(a: &[i32], k: usize) -> Vec<i32> {
if k == 0 || k > a.len() {
return Vec::new();
}
let mut dq: VecDeque<usize> = VecDeque::with_capacity(a.len());
let mut out = Vec::with_capacity(a.len().saturating_sub(k) + 1);
for (i, &x) in a.iter().enumerate() {
while let Some(&front) = dq.front() {
if front + k <= i {
dq.pop_front();
} else {
break;
}
}
while let Some(&back) = dq.back() {
if a[back] <= x {
dq.pop_back();
} else {
break;
}
}
dq.push_back(i);
if i + 1 >= k {
out.push(a[*dq.front().unwrap()]);
}
}
out
}
fn main() {
let a = [1, 3, -1, -3, 5, 3, 6, 7];
println!("{:?}", sliding_max(&a, 3));
}

过期判断写成 front + k <= i 而不是 front == i - k + 1，是为了绕开 usize 减法下溢：循环初期 i 可能小于 k，此时 i - k + 1 会回绕。同样地，预分配输出容量用 saturating_sub(k) + 1，避免 k > a.len() 时 a.len() - k 下溢。这两个小写法是 Rust 下标运算的标志性防御动作。

为什么队尾弹出条件用 <= 也能正确处理相等元素？假设两个相等的值先后入队，旧的那个先过期，而新的一直留在队列里；弹出旧的不损失信息，反而让队列更短。如果题目要求同时保留相等元素的计数信息，才需要改成 < 并在别处单独处理。把单调队列想象成"去掉了所有被支配候选者的候选名单"：一个候选被支配，当且仅当存在更靠后且不小于它的元素——这正是 a[back] <= x 的含义。

15.4 复杂度与调试清单

三种结构的复杂度可以总结如下：普通栈与队列的每次操作都是 O(1)；单调栈与单调队列虽然内层有 while，但每个元素最多进出各一次，摊还仍是 O(n)，空间 O(n)。真正会退化成 O(n²) 的写法是"对每个元素都扫描一遍窗口"，那正是单调结构要消灭的冗余。

调试这类代码时建议逐项核对：栈或队列里存的到底是值还是下标；单调方向是递增还是递减，与题目求"更大"还是"更小"是否一致；弹出条件该用 <= 还是 <；过期判断的下标关系是否正确；哨兵值是否会与真实数据冲突；所有减法是否满足被减数大于减数。把不变量写成注释放在循环上方，比事后单步调试更快。

如果写错了单调方向，程序往往不会崩溃，而是给出"看起来差不多"的错误答案，这类 bug 最危险。一个有效的自检办法是在纸上画三列：当前位置 i、栈（或队列）内容、本轮产生的答案，然后手工推进五到六个元素。手工模拟能验证不变量是否真的成立，比如每日温度里栈中温度是否始终递减、最大矩形里新栈顶是否一定比弹出柱矮。等手工推演与程序输出一致，再交给随机对拍做大范围验证，两套手段配合起来基本能根除这一类边界错误。

16.1 并查集：路径压缩与按秩合并

并查集维护一组不相交集合，支持两个操作：判断两个元素是否属于同一集合，以及把两个集合合并。实现方式是给每个元素一个 parent 指针，每棵树的根代表整个集合。核心不变量很简单：沿着 parent 一路向上走必然到达根，同集合元素的根相同；合并时只改一个根的 parent，不碰其他节点。

裸的 find 在链状树上可能退化成 O(n)，所以必须加两个优化。路径压缩：find 过程中把沿途所有节点直接挂到根下，使树高度趋近于 1。按秩合并：始终让节点数少（或高度小）的树挂到另一棵下面，避免长链。两者叠加后，单次操作的摊还复杂度是反阿克曼函数 α(n)，在实际数据规模下可以当作常数。

Rust 里要把 find 写成迭代而不是递归。递归版在深链上会占用大量栈帧，虽然路径压缩后链很短，但在压缩发生之前仍可能很深；迭代版用两个 while 循环，第一趟找根，第二趟把沿途节点改挂到根，完全不碰调用栈。注意第二趟里要先用 let next = self.parent[cur]; 把下一个节点存到局部变量，再写 self.parent[cur] = root，否则既读又写同一个 Vec 的位置，虽然编译器未必报错，逻辑上也容易把链路改乱。

struct UnionFind {

rank: Vec<u32>,
comps: usize,
}
impl UnionFind {
fn new(n: usize) -> Self {
UnionFind {
parent: (0..n).collect(),
rank: vec![0; n],
comps: n,
}
}
fn find(&mut self, x: usize) -> usize {
let mut root = x;
while self.parent[root] != root {
root = self.parent[root];
}
let mut cur = x;
while self.parent[cur] != cur {
let next = self.parent[cur];
self.parent[cur] = root;
cur = next;
}
root
}
fn union(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
if ra == rb {
return false;
}
if self.rank[ra] < self.rank[rb] {
self.parent[ra] = rb;
} else if self.rank[ra] > self.rank[rb] {
self.parent[rb] = ra;
} else {
self.parent[rb] = ra;
self.rank[ra] += 1;
}
self.comps -= 1;
true
}
fn connected(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
ra == rb
}
}
fn main() {
let mut uf = UnionFind::new(6);
for (a, b) in [(0usize, 1usize), (1, 2), (3, 4), (4, 5)] {

}

println!("0~2 connected = {}", uf.connected(0, 2));
println!("0~5 connected = {}", uf.connected(0, 5));
}

选择并查集还是 DFS/BFS，取决于"查询是静态的还是动态的"。如果所有边一次性给定、只问一次连通性，DFS 或 BFS 更直接；如果边是逐条加入的、中间要随时回答"这两个点是否已连通"，并查集才是正解。rank 字段用 u8 就够了，因为树的高度最多 log₂(n)，即使 n 取 10⁹ 也不会超过 31，省下的内存对大规模节点很可观。另外务必统一编号约定：如果题目给的是 1 到 n 的编号，读入后要么整体减一转成 0 基，要么把数组开成 n + 1 并浪费 0 号位，两种做法都行，但绝不能混用。

16.2 并查集的应用：连通块计数

并查集最常见的使用场景是"动态连通性"：一开始每个元素自成一团，随着边或相邻关系不断加入，问最后剩几团。一个直接的做法是维护计数器 count，初值为元素个数；每次 union 返回 true 就把 count 减一，因为一次有效合并恰好消灭一个连通块。这比最后遍历所有元素收集不同的根更省事，也不依赖 HashSet。

网格类题目需要把二维坐标 (r, c) 压成一维下标：id = r * cols + c。这样 Vec 只需一维，缓存局部性也更好。危险在于反推邻居时容易出现 r - 1 或 c - 1，而 usize 在 r = 0 或 c = 0 时会下溢 panic。务必把边界判断写在减法之前：先 if r > 0 再算 (r - 1) * cols + c。Rust 不会像 C 那样悄悄回绕，这反而是好事——错误会当场暴露。

这里只检查上和左两个方向，而不是上下左右四个方向。因为并查集合并是对称操作，每对相邻陆地只会被访问一次；若同时检查四个方向，同一组相邻格会被重复合并，虽然结果不变，但多做了无用功。这个"只向右和向下扩展"的剪枝在很多网格搜索题里都成立。

并查集还有个高频用法是检测环：按顺序加入无向图的每条边，如果它连接的两个端点已经在同一个集合里，说明这条边构成环。这能在不建完整邻接表的情况下找出"多余的一条边"，复杂度只需 O(m α(n))。相比之下，用 DFS 检测环要额外维护访问状态和父节点，代码更长。记住这个判别式——union 返回 false 即代表遇到环——很多看起来不同的题目（冗余连接、等式方程矛盾、最小生成树判环）都能归到它上面。

16.3 BinaryHeap：标准库的最大堆

std::collections::BinaryHeap 是最大堆，peek 返回最大元素，插入与弹出都是 O(log n)。求第 k 大时，维护一个大小不超过 k 的小堆思想：用最大堆保存当前见过的 k 个最小元素，堆顶是这 k 个里最大的；新元素只有比堆顶还大才替换。最终堆顶就是第 k 大。

需要小根堆时用 std::cmp::Reverse<T> 包一层，它会把所有比较方向反转，是标准库正式提供的类型，不依赖任何外部 crate。堆里也可以放自定义结构体，只要为它实现 Ord 与 PartialOrd（通常 derive 即可，字段顺序决定优先级）。

fn kth_largest(a: &[i32], k: usize) -> Option<i32> {

return None;
}

if heap.len() < k {
heap.push(x);
} else if x > *heap.peek().unwrap() {
heap.pop();
heap.push(x);
}
}
heap.peek().copied()
}
fn merge_stones(stones: &[i32]) -> i32 {

}

heap.push(Reverse(merged));
}

}

关于 table 里的 peek：它返回 Option<&T>，空堆时不要直接 unwrap()，除非你能用 len 或循环条件保证非空。上面的 top-k 代码里，else 分支能走到说明堆已经装了 k 个元素且 k > 0，所以 peek().unwrap() 是安全的。另外 BinaryHeap 可以从 Vec 直接 collect 或用 BinaryHeap::from(vec) 构造，标准库会在 O(n) 时间内完成建堆，比逐个 push 的 O(n log n) 更高效。若要在堆里放自定义类型，注意 Ord 必须与 PartialOrd 的语义一致，否则标准库可能表现出违反直觉的行为。

16.4 手写二叉堆与复杂度小结

手写堆的价值不在于替代标准库，而在于理解它的下标不变量。用数组按层序存放完全二叉树：下标 i 的左孩子是 2i + 1，右孩子是 2i + 2，父节点是 (i - 1) / 2。这些公式在 i = 0 时都会出问题，所以上浮循环必须写成 while i > 0，先判断再算父节点。下沉时用 l = 2i + 1、r = l + 1，先检查 l < len 再决定是否比较 r。

struct MinHeap {
data: Vec<i32>,
}
impl MinHeap {
fn new() -> Self {
MinHeap { data: Vec::new() }
}
fn push(&mut self, v: i32) {
self.data.push(v);
let mut i = self.data.len() - 1;
while i > 0 {
let p = (i - 1) / 2;
if self.data[p] <= self.data[i] {
break;
}
self.data.swap(p, i);
i = p;
}
}
fn pop(&mut self) -> Option<i32> {
if self.data.is_empty() {
return None;
}
let ret = self.data[0];
let last = self.data.pop().unwrap();
if !self.data.is_empty() {
self.data[0] = last;
let mut i = 0usize;
loop {
let l = 2 * i + 1;
let r = l + 1;
if l >= self.data.len() {
break;
}
let mut smallest = l;
if r < self.data.len() && self.data[r] < self.data[l] {
smallest = r;
}
if self.data[i] <= self.data[smallest] {
break;
}
self.data.swap(i, smallest);
i = smallest;
}
}
Some(ret)
}
fn len(&self) -> usize {
self.data.len()
}
}
fn heap_sort(a: &[i32]) -> Vec<i32> {
let mut h = MinHeap::new();
for &x in a {
h.push(x);
}
let mut out = Vec::with_capacity(a.len());
while h.len() > 0 {
out.push(h.pop().unwrap());
}
out
}
fn main() {
let a = [5, 3, 8, 1, 9, 2];
println!("{:?}", heap_sort(&a));
}

把数组所有元素依次 push 进堆再逐个 pop，就得到升序序列，这是 O(n log n) 的堆排序。若改用原地建堆（从最后一个非叶节点开始下沉），建堆可以做到 O(n)，整体仍为 O(n log n)，但常数更小。堆最常见的用途是优先队列：Dijkstra 取当前距离最小的点、合并 K 路有序序列取最小头元素、以及在海量数据里维护 top-k。它们共同的模式都是"插入一个候选、弹出一个最优"，这正是堆擅长的事。

上浮与下沉都用 swap 而不是逐个赋值，是因为 Vec::swap 一次完成两个位置的交换，不需要先克隆出临时值；对 i32 这类 Copy 类型差别不大，但换成 String 或自定义结构体时就能省下分配。正确性方面，上浮终止时父节点不大于当前节点，且原本的堆性质未被破坏；下沉终止时当前节点不大于两个孩子，两边子树递归地满足堆性质。这两个局部性质合起来就是全局不变量。写完代码后，用小数组跑一次堆排序并检查结果是否有序，是最省事的自检。

17.1 Rust 排序 API 与比较器

Vec 和切片都提供了三个常用排序方法：sort 稳定排序，相等元素保持原有相对顺序，需要额外的临时内存，最坏 O(n log n) 比较、O(n) 额外空间；sort_unstable 不保证稳定性，通常更快且只用地毯式堆排与插入排的混合实现，额外空间 O(log n)；sort_by_key 按提取出的关键字排序。判断标准很简单：相等元素是否需要保留输入顺序——按分数排序后还要按名字排第二关键字时用稳定排序，或者干脆把两个关键字写进一个比较器里。

比较器接收两个 &T，返回 Ordering。降序不是把结果取负（Rust 的 Ordering 没有取负运算），而是把参数顺序反过来写：b.cmp(a)。多关键字用 then_with 串联：q.1.cmp(&p.1).then_with(|| p.0.cmp(q.0)) 表示分数降序、同分时名字升序。注意闭包参数名字 p 和 q 的顺序，写反了会得到完全相反的结果，这是排序题最常见的低级错误。

排序浮点数时要格外小心：IEEE 754 的 NaN 与任何值比较都返回 false，不满足 Ord 要求的全序关系，所以 f64 没有实现 Ord，直接 sort() 编译不过。竞赛数据通常不含 NaN，这时可以用 partial_cmp(...).unwrap()；若数据可能含 NaN，要先把 NaN 过滤掉或映射到无穷大再排。

切片本身还带一个 binary_search 方法，返回 Result<usize, usize>：找到时是 Ok(下标)，没找到时是 Err(应插入位置)，这个"应插入位置"正好等于 lower_bound。若数组里存在重复元素，binary_search 返回的是其中某一个，不保证是第一个或最后一个，所以题目要找边界时还是自己写 lower_bound / upper_bound 更可靠。类似的还有 partition_point，它接受一个谓词，返回第一个使谓词为 false 的位置——把二分模式的意图直接写进名字里，可读性更好。

大白话先用直觉把它讲通

排序就是把一堆东西按规则排队。sort 是"讲礼貌的排队"，分数相同的人保持原来的先后；sort_unstable 是"只关心分数"的排队，同分谁在前都行，所以更快。比较器就是告诉程序"谁该站前面"的那句话，降序只要把两个参数换个位置说一遍。

17.2 归并排序与逆序对

归并排序把数组对半分，分别排好两个半区，再做一次线性合并。它的时间复杂度稳定为 O(n log n)，不像快速排序那样有退化风险，代价是需要一个等长的临时数组。逆序对定义为下标 i < j 但 a[i] > a[j] 的二元组的个数，它衡量数组的"无序程度"。

巧妙之处在于：在合并两个已经有序的半区时，如果右半区的 rbuf[j] 小于左半区的 lbuf[i]，那么 rbuf[j] 不仅小于 lbuf[i]，还小于左半区中从 i 到末尾的所有元素（因为左半区递增），于是逆序对数一次性增加 left_len - i。这样统计逆序对不需要额外的嵌套循环，归并排序的 O(n log n) 复杂度原封不动地继承下来。

Rust 写归并排序的难点不在算法而在借用。递归调用 &mut a[..mid] 和 &mut a[mid..] 是两段互不重叠的可变切片，合法；合并前要先把两半拷进临时数组，用 a.split_at(mid) 拿不可变切片、tmp.split_at_mut(mid) 拿可变切片，拷贝完成后用一个花括号块主动结束这些借用，之后才能写回 a[k]。如果借用没结束就写 a[k] = ...，编译器会报"cannot borrow a as mutable"。另外，把 left.len() 事先存成 left_len 这样的标量，也能减少对借用的依赖。

fn merge_sort_count(a: &mut [i64], tmp: &mut [i64]) -> i64 {

if n <= 1 {
return 0;
}

let mut inv = merge_sort_count(&mut a[..mid], &mut tmp[..mid]);
inv += merge_sort_count(&mut a[mid..], &mut tmp[mid..]);

let right_len = n - mid;
{

let (lbuf, rbuf) = tmp.split_at_mut(mid);
lbuf[..left_len].copy_from_slice(left);
rbuf[..right_len].copy_from_slice(right);

i += 1;
} else {

j += 1;
}
k += 1;
}

a[k] = tmp[i];
i += 1;
k += 1;

合并条件写成 <= 而不是 <，保证相等元素先取左边的，因此这个排序是稳定的，也避免把相等元素误计为逆序对。临时数组只分配一次，由递归各层复用；若在每层递归里都新建 Vec，总分配量会上升，性能明显变差。

递归深度是 log₂n，远小于递归爆栈的阈值，所以归并排序用递归是安全的，这与后面图中的深链 DFS 不同。若数据的值域不大（例如都在 10⁶ 以内），统计逆序对还有另一种做法：从右往左扫描，用树状数组（Fenwick tree）统计已出现过且小于当前值的元素个数，复杂度同样是 O(n log n)，内存只需一个计数数组。两种方法的结果应当一致，互为对拍的参照很合适。归并排序的额外好处是天然稳定，如果题目同时要求"按值排序且同值保持原序"，它就是首选。

17.3 二分的四种边界写法

二分查找的 bug 几乎都出在区间约定上。推荐全程使用左闭右开 [l, r)：初始 l = 0, r = len，循环条件是 while l < r，中点 m = l + (r - l) / 2。这写法的好处是循环结束时 l == r，答案就是 l，不需要讨论"最后 l 和 r 谁大"。中点用 l + (r - l) / 2 而不是 (l + r) / 2，可以避免两个大下标相加溢出。

四种常见需求只差一个判定条件：找第一个大于等于 target 的位置（lower_bound）用 a[m] < target 时右移；找第一个大于 target 的位置（upper_bound）用 a[m] <= target 时右移。"第一个等于"是先做 lower_bound 再校验，"最后一个等于"是先做 upper_bound 再减一——而减一之前必须判断 i > 0，否则 i = 0 时会触发 usize 下溢。

l = m + 1;

}

上界减下界就是某个值出现次数，这是 lower_bound / upper_bound 最实用的组合。注意所有返回类型都是 usize，"找不到"用 a.len() 表示，而不是 -1；想表达"不存在"的语义就用 Option<usize>，让类型系统替你记账。

还有一个常被忽略的要点：二分的前提是数组有序。如果题目给的是无序数据，别忘了先排序，并记得排序会打乱原始下标——若答案需要输出原位置，就要先和值一起打包成结构体或二元组再排。二分本身只要求"谓词单调"，不要求数组严格递增：对于形如"前半段满足某条件、后半段不满足"的判定序列，同样可以用同样的框架找分界点。把二分理解为"在一个单调布尔序列里找 true/false 的交界"，比死记四种模板更通用。

17.4 二分答案：从判定到最优

当题目要求"最大化最小值"或"最小化最大值"时，答案往往具有单调性：如果某个上限 limit 可行，那么比它更大的上限一定也可行；如果不可行，更小的也不可行。有了单调性，就能对答案本身二分，把在巨大值域上的搜索压缩到 O(log V) 次判定。

"把数组切成 m 段、最小化最大段和"是标准范例。判定函数 feasible(limit) 贪心地从左往右累加，一旦加上当前元素超过 limit 就另起一段；若段数超过 m 则不可行。二分时 lo 取数组最大值（任何一段至少装得下最大的单个元素），hi 取全数组之和（一段装下全部），循环写法同样用 lo + (hi - lo) / 2，可行就把 hi 压到 mid，否则把 lo 抬到 mid + 1。

rustRust · 标准库38 行
fn feasible(a: &[i64], pieces: usize, limit: i64) -> bool {
let mut used = 1usize;
let mut sum = 0i64;
for &x in a {
if x > limit {
return false;
}
if sum + x > limit {
used += 1;
sum = x;
if used > pieces {
return false;
}
} else {
sum += x;
}
}
true
}
fn minimize_largest_sum(a: &[i64], pieces: usize) -> i64 {
let mut lo = *a.iter().max().unwrap();
let mut hi: i64 = a.iter().sum();
while lo < hi {
let mid = lo + (hi - lo) / 2;
if feasible(a, pieces, mid) {
hi = mid;
} else {
lo = mid + 1;
}
}
lo
}

println!("answer = {}", minimize_largest_sum(&a, 2));
}

写二分答案前必须先证明单调性，否则二分会悄悄给出错误答案。一个快速验证办法是拿几组小数据穷举所有切分，再把结果与判定函数对照；建立直觉后再推广到大数据。还要注意 lo 和 hi 的初值必须分别落在"一定不可行/一定可行"或包含答案的区间内：若 lo 设得太大，真正的答案会被排除在外；若 hi 设得太小，二分永远收敛不到可行解。

二分答案的题目形形色色，但套路高度一致："求最大的最小距离"可以判定为能否放下至少 k 个物品，"求最小的最大耗时"可以判定为能否在限定时间内完成所有任务，"求最少天数"可以判定为限定天数能否运完。判定函数几乎都是贪心：从左到右尽可能塞，塞不下就新开一组。写完判定函数后，先用极端数据自检——limit 取最大值时应恰好可行，limit 取最小值时通常不可行——再交给二分，能省掉大量调试时间。

18.1 前缀和：一维与二维

前缀和数组的不变量是：pref[i] 等于原数组前 i 个元素之和，也就是 [0, i) 的和。为了省掉对 i == 0 的特判，预分配 n + 1 个位置并让 pref[0] = 0 作哨兵。建表用一次循环完成，之后任意区间 [l, r) 的和都是 pref[r] - pref[l]，把 O(n) 的区间查询降到 O(1)。注意区间统一用左闭右开：长度直接是 r - l，两个相邻区间的边界不会重叠。

rustRust · 标准库13 行
fn main() {
let a = [1i64, 3, 5, 7, 9, 11];
let mut pref = Vec::with_capacity(a.len() + 1);
pref.push(0i64);
for &x in &a {
let last = *pref.last().unwrap();
pref.push(last + x);
}
let pairs = [(0usize, 3usize), (1, 4), (2, 2), (0, 6)];
for (l, r) in pairs {
println!("[{}, {}) = {}", l, r, pref[r] - pref[l]);
}
}

这里没有写 pref.push(pref[pref.len() - 1] + x)，而是先用 last() 取出旧值再 push。虽然 Rust 的两阶段借用通常允许前者，但先取值的写法意图更明确，也避免了在循环中反复索引 len() - 1。如果原数组元素可能很大，前缀和要用 i64 累加，否则 i32 在一百万个 10⁹ 元素上必然溢出。

另一种常见变体是原地前缀和：直接把 a[i] 改成前 i 项之和，不再分配新数组，省内存但会破坏原数据。刷题时若后面还要用原数组，就别这么做。涉及取模的题目（例如统计子数组和能被 k 整除的个数）要在每次累加后立即取模，并用 HashMap<i64, usize> 统计每个余数出现次数，核心思想仍是"两个前缀同余则其差能被 k 整除"。把前缀和看成"压缩的信息"，很多看似无关的题型都能归入这个框架。

二维前缀和把同样的思想扩展到矩阵。ps[r][c] 表示左上角 (0,0) 到右下角 (r-1,c-1) 的矩形和。递推式是 ps[r][c] = a[r-1][c-1] + ps[r-1][c] + ps[r][c-1] - ps[r-1][c-1]，也就是"自己加上方加左方，再把重复算的左上角减一次"。查询 [r1, r2) × [c1, c2) 用同样的容斥：ps[r2][c2] - ps[r1][c2] - ps[r2][c1] + ps[r1][c1]。

关键技巧是把所有下标整体加一：原矩阵 m × n 存进 (m+1) × (n+1) 的前缀数组，让第 0 行和第 0 列全为 0。这样递推里的 r - 1、c - 1 都变成合法的 r、c，彻底绕开 usize 下溢。如果在 0 基数组里硬写 ps[i-1][j]，那么 i = 0 时程序会当场 panic。

fn build_prefix_2d(grid: &[Vec<i64>]) -> Vec<Vec<i64>> {
let rows = grid.len();
let cols = if rows == 0 { 0 } else { grid[0].len() };
let mut ps = vec![vec![0i64; cols + 1]; rows + 1];
for r in 0..rows {
for c in 0..cols {
ps[r + 1][c + 1] = grid[r][c]
+ ps[r][c + 1]
+ ps[r + 1][c]
- ps[r][c];
}
}
ps
}

}

18.2 差分：区间加与单点查询

差分是前缀和的逆运算。diff[i] 定义为 a[i] - a[i-1]（令 a[-1] = 0），对 diff 做前缀和就还原出 a。这个性质带来一个极强的操作：要把区间 [l, r] 整体加 delta，只需 diff[l] += delta、diff[r+1] -= delta 两处修改，因为前缀和扫到 l 时开始生效，扫过 r 后被抵消。多次区间加可以全部 O(1) 处理，最后统一 O(n) 还原。

需求 工具 单次修改 单次查询
区间和 前缀和 建表 O(n) O(1)
区间加、单点值 差分 O(1) 还原后 O(1)
区间加、区间和 差分 + 两层前缀 O(1) 还原后 O(1)
单点加、区间和 树状数组 O(log n) O(log n)

下面的实现预分配 n + 1 个位置，让 r + 1 == n 时仍能安全写入差分边界；只有 r + 1 >= diff.len() 才跳过，而这个判断在合法输入下通常不会发生。还原时维护滚动变量 cur，避免真的去改差分数组本身——这让差分数组保持"只记录修改"的纯粹语义，便于多次复用。

rustRust · 标准库22 行
fn range_add_diff(n: usize, ops: &[(usize, usize, i64)]) -> Vec<i64> {
// 每个三元组 (l, r, delta) 表示对闭区间 [l, r] 加 delta
let mut diff = vec![0i64; n + 1];
for &(l, r, delta) in ops {
diff[l] += delta;
if r + 1 < diff.len() {
diff[r + 1] -= delta;
}
}
let mut cur = 0i64;
let mut out = Vec::with_capacity(n);
for i in 0..n {
cur += diff[i];
out.push(cur);
}
out
}
fn main() {
let ops = [(0usize, 2usize, 3i64), (1, 3, -1), (2, 4, 5)];
println!("{:?}", range_add_diff(5, &ops));
}

差分与前缀和经常组合使用：先对原数组建一次差分，执行若干次区间加，再对差分求前缀得到新数组，最后对新数组求前缀得到区间和查询表，整体仍是 O(n + m)。二维差分同理，区间加 [x1,x2] × [y1,y2] 变成四个角点的符号修改，公式与二维前缀和互为镜像。

要注意差分的"离线"属性：上面的代码必须先把所有修改收集完，才能统一还原出最终数组。如果题目要求"每做一次区间加就立刻回答一次查询"，纯差分就力不从心了，需要改用树状数组或线段树，把每次修改与查询都降到 O(log n)。区分在线与离线是选择数据结构的第一步：能在读入阶段一次性拿到全部操作时，离线算法往往更简单也更快。另外差分值为负数完全合法，用 i64 存储即可，不必特殊处理。

18.3 双指针与滑动窗口

双指针有两大流派。相向双指针：左指针从开头、右指针从结尾出发，根据当前和与目标的大小关系移动其中一个，典型是排序数组的两数之和。它要求数组有序，每次移动都单调地缩小搜索范围，因此 O(n)。同向双指针（滑动窗口）：左右指针都只向右走，右指针负责扩大窗口，左指针负责在窗口"不合法"时收缩，典型是求最短子数组或无重复最长子串。

滑动窗口的正确性依赖两个不变量：其一，窗口 [left, right] 始终满足题目对右端的扩展要求；其二，每轮收缩后窗口恰好是"以 right 结尾的最优窗口"。左指针绝不回退是关键——如果某个左端位置被排除，那么以更靠右的 right 结尾时它也不可能重新变优。这个单调性一旦不成立（例如窗口合法性与 right 不单调），双指针就会失效，必须换用别的方法。

rustRust · 标准库34 行
fn min_subarray_sum(a: &[i64], target: i64) -> usize {
let (mut left, mut sum, mut best) = (0usize, 0i64, usize::MAX);
for (right, &x) in a.iter().enumerate() {
sum += x;
while sum >= target && left <= right {
best = best.min(right - left + 1);
sum -= a[left];
left += 1;
}
}
if best == usize::MAX { 0 } else { best }
}
fn longest_unique(s: &str) -> usize {
let bytes = s.as_bytes();
let mut last = [usize::MAX; 256];
let mut left = 0usize;
let mut best = 0usize;
for (right, &b) in bytes.iter().enumerate() {
let idx = b as usize;
if last[idx] != usize::MAX && last[idx] >= left {
left = last[idx] + 1;
}
last[idx] = right;
best = best.max(right - left + 1);
}
best
}
fn main() {
let a = [2i64, 3, 1, 2, 4, 3];
println!("min len = {}", min_subarray_sum(&a, 7));
println!("longest unique = {}", longest_unique("abcabcbb"));
}

longest_unique 用定长数组 [usize::MAX; 256] 记录每个字节最后出现的位置，用 usize::MAX 表示"从未出现"，省掉 Option 的判断开销。它只适用于 ASCII 字节串；处理中文要用 char 与 HashMap<char, usize>，因为 UTF-8 下一个汉字占多个字节。判断重复时用 last[idx] >= left 而不是 != usize::MAX，是为了只在"上次出现位置仍在当前窗口内"时才移动左端。

相向双指针的经典例子是三数之和：先排序，再固定一个数，用 l = i + 1、r = n - 1 从两侧夹逼。三数之和大于目标就让 r 左移，小于目标就让 l 右移；遇到重复元素要跳过，否则结果里有大量重复三元组。排序 + 双指针把原本 O(n³) 的暴力枚举压到 O(n²)，这也再次说明"有序"是双指针能工作的重要前提。写这类代码时，l < r 的循环条件要保证 i + 1 不超过 n - 1，把固定元素的循环上界设为 n - 2 最省心。

18.4 边界、不变量与调试清单

这一类题目出错往往不是算法想错，而是边界处理不细。逐项核对能省很多时间：区间是闭区间还是左闭右开；前缀数组是否多开了一格作哨兵；二维递推是否已经整体右移一位以避开 i - 1；差分修改的右端点是 r 还是 r + 1；收缩窗口时 left 是否会越过 right 导致 r - l + 1 下溢；累加和是否需要 i64。"宁可多判断一次，也不要让 usize 偷偷回绕"是这里的黄金准则。

另一个好习惯是写出并维护不变量注释。例如在滑动窗口里注明"窗口内和小于 target，且 left 是满足条件的最小位置"，在差分里注明"diff 的前缀等于当前增量"。每次循环体内只做保持不变量的事，代码就很难错。调试时先用小规模输入手工模拟两三轮，再和程序输出比对；若有对拍环境，用暴力枚举所有子数组的答案与双指针结果比较，往往几十行代码就能覆盖全部边界。

前缀和与差分这对工具一个负责查询、一个负责修改，理解它们的互逆关系后，面对区间类问题就能先在纸上画出前缀或差分的草图，再决定用哪种结构，而不是上来就套模板。特别提醒一个 Rust 专属陷阱：usize::MAX 是合法的哨兵值，但它加一就会回绕成 0。上面 longest_unique 里先判断 last[idx] != usize::MAX 再执行 left = last[idx] + 1，顺序绝不能颠倒。同理，right - left + 1 只有在 right >= left 时才有意义，循环条件里加一道 left <= right 的防线几乎不花成本。把这些防御动作写成肌肉记忆，才能在 debug 构建下避免突如其来的 panic。

19.1 邻接表建图与 BFS / DFS

树是一种特殊的稀疏图，所以下面所有建图与遍历技巧对树同样适用；把树问题先转成"无向图 + 根节点"，是求解 LCA 等问题的通用起点。图的存储首选邻接表：Vec<Vec<usize>>，第 u 个 Vec 存放 u 的所有邻居。无向图每条边要往两个方向各加一次，有向图只加一次。相比邻接矩阵，邻接表的空间是 O(n + m)，稀疏图下优势巨大。若边带权，把元素类型换成 (usize, i64) 的元组即可。读入边时如果题目给的是 1 基编号，一定要先整体减一转成 0 基，否则会访问越界并浪费 0 号位置；编号转换的 bug 往往在样例上就能暴露，但如果不看输出很容易漏掉。

BFS 用 VecDeque 当队列，按层推进，dist[v] = -1 表示未访问。它在无权图上给出最短路径，也是很多图算法（拓扑排序、Dijkstra 的初始化）的基础。DFS 通常用递归写，但 Rust 主线程栈有限，深链会导致 stack overflow。稳妥做法是手写栈：用一个 Vec<usize> 模拟递归栈，配合 seen 数组保证每点只入栈一次。

DFS（迭代） Vec 当栈 O(n + m) 拓扑序、连通块
Dijkstra BinaryHeap O((n + m) log n) 非负权最短路

use std::collections::VecDeque;
fn build_undirected(n: usize, edges: &[(usize, usize)]) -> Vec<Vec<usize>> {
let mut g = vec![Vec::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
g
}
fn bfs(g: &[Vec<usize>], start: usize) -> Vec<i32> {
let mut dist = vec![-1i32; g.len()];
let mut q = VecDeque::new();
dist[start] = 0;
q.push_back(start);
while let Some(u) = q.pop_front() {
for &v in &g[u] {
if dist[v] == -1 {
dist[v] = dist[u] + 1;
q.push_back(v);
}
}
}
dist
}
fn dfs_iter(g: &[Vec<usize>], start: usize) -> Vec<usize> {
let mut seen = vec![false; g.len()];
let mut order = Vec::with_capacity(g.len());
let mut st = vec![start];
seen[start] = true;
while let Some(u) = st.pop() {
order.push(u);
for &v in &g[u] {
if !seen[v] {
seen[v] = true;
st.push(v);
}
}
}
order
}
fn main() {
let g = build_undirected(6, &[(0, 1), (1, 2), (1, 3), (3, 4), (3, 5)]);
println!("dist = {:?}", bfs(&g, 0));
println!("dfs = {:?}", dfs_iter(&g, 0));
}

注意 BFS 里"入队时就置 dist"：这样即使同一层的多个节点都指向 v，v 也只会被入队一次。如果等到出队才标记，就会重复入队，复杂度退化。DFS 的 seen 同理，在入栈时就标记，而不是出栈时。

Vec<Vec<usize>> 的内存并不连续：每个内层 Vec 各自分配一块，遍历时缓存命中率不如扁平数组。若图的边数达到百万级，可以用"前向星"式的扁平存储——一个 to 数组加一个 head / next 数组，把所有邻接边连续存放。对多数笔试题而言邻接表已经够用，但知道这个优化的存在有助于在卡性能时快速切换。另外上面的 BFS 和 DFS 都只从第 0 号点出发；若图不连通，要对每个未访问的点再跑一次，才能覆盖全部节点。迭代 DFS 的访问顺序与递归版本可能不同（因为栈是后进先出），但只要是合法的遍历顺序就不影响连通块计数这类与顺序无关的问题。

19.2 Dijkstra：BinaryHeap 与 Reverse

Dijkstra 解决非负权图上的单源最短路。它每次从尚未确定的点里取当前距离最小的那个，用它去松弛邻居。标准库 BinaryHeap 是最大堆，而我们需要最小堆，于是用 std::cmp::Reverse<(i64, usize)> 把比较方向翻转。元组里放 (距离, 点号)，距离相同时按点号排，行为确定。

关键细节是过期堆项：同一个点可能被多次压入堆（每次距离变小就压一次），弹出旧记录时它的 d 已经大于 dist[u]，必须 continue 跳过，否则会用过时距离去做松弛，得到错误结果。这个判断也可以写成 if Reverse(d) != ...，但直接比较 d > dist[u] 最直观。无限大用 i64::MAX / 4，给加法留出余量，避免溢出成负数。

为什么不能用 visited 数组代替跳过判断？因为 Dijkstra 的点在第一次弹出时距离确实已经确定，理论上可以标记 visited；但那需要在压堆前排除重复项，代码反而更绕。直接允许重复入堆、弹出时惰性丢弃，是更简洁也更常用的写法，代价只是堆里多几条记录。把这个模式记住，后面所有"优先队列 + 松弛"的算法都能套用。

use std::cmp::Reverse;
use std::collections::BinaryHeap;
fn dijkstra(n: usize, edges: &[(usize, usize, i64)], src: usize) -> Vec<i64> {
let mut g = vec![Vec::<(usize, i64)>::new(); n];
for &(u, v, w) in edges {
g[u].push((v, w));
g[v].push((u, w));
}
let inf = i64::MAX / 4;
let mut dist = vec![inf; n];
let mut pq: BinaryHeap<Reverse<(i64, usize)>> = BinaryHeap::new();
dist[src] = 0;
pq.push(Reverse((0, src)));
while let Some(Reverse((d, u))) = pq.pop() {
if d > dist[u] {
continue; // 过期记录，跳过
}
for &(v, w) in &g[u] {
let nd = d + w;
if nd < dist[v] {
dist[v] = nd;
pq.push(Reverse((nd, v)));
}
}
}
dist
}

let edges = [
(0usize, 1usize, 4i64), (0, 2, 1), (2, 1, 2),
(1, 3, 5), (2, 3, 8),
];

}

Dijkstra 要求所有边权非负，这是因为它的贪心依赖"距离一旦确定就不会再变小"。若存在负权边，需改用 SPFA 或 Bellman-Ford。另外不要把"取出最小值"写成每次线性扫描 dist 数组，那样是 O(n²)，在 n 达十万级时会超时；堆把这一步降到 O(log n)。

跑完算法后，仍为 inf 的点表示从源点不可达，输出时要按题目要求转成 -1 或忽略。堆里最多会积累 O(m) 个记录（每条边松弛成功一次就可能压入一项），所以空间复杂度是 O(n + m)，不必担心。对于边权全为 1 的特殊情况，BFS 就能给出最短路，比 Dijkstra 更快更简单；只有当权值不全相等时才需要动用堆。把这一点写进选择题的判断清单，能避免杀鸡用牛刀。

19.3 拓扑排序

拓扑排序针对有向无环图（DAG），输出一个序列使得每条边 u → v 都满足 u 排在 v 前面。Kahn 算法从入度为 0 的点开始：把它们全部入队，依次弹出并记录，每弹出一个点就把它的所有后继入度减一，减到 0 的点再入队。若最终输出的点数不足 n，说明图中存在环。

rustRust · 标准库37 行
use std::collections::VecDeque;
fn topo(n: usize, edges: &[(usize, usize)]) -> Option<Vec<usize>> {
let mut g = vec![Vec::<usize>::new(); n];
let mut indeg = vec![0usize; n];
for &(u, v) in edges {
g[u].push(v);
indeg[v] += 1;
}
let mut q = VecDeque::new();
for i in 0..n {
if indeg[i] == 0 {
q.push_back(i);
}
}
let mut order = Vec::with_capacity(n);
while let Some(u) = q.pop_front() {
order.push(u);
for &v in &g[u] {
indeg[v] -= 1;
if indeg[v] == 0 {
q.push_back(v);
}
}
}
if order.len() == n {
Some(order)
} else {
None
}
}
fn main() {
let edges = [(0usize, 1usize), (0, 2), (1, 3), (2, 3), (3, 4)];
println!("{:?}", topo(5, &edges));
println!("{:?}", topo(3, &[(0, 1), (1, 2), (2, 0)]));
}

indeg[v] -= 1 在 usize 上是安全的，因为 v 出现在 u 的后继列表里，就说明它有一条来自 u 的入边尚未被扣减；而 u 只会被弹出一次，所以不会重复扣。返回 Option<Vec<usize>> 把"有环"这个失败状态编码进类型，比返回一个空 Vec 更不容易被误用。

拓扑排序的结果通常不唯一：只要存在多个入度为 0 的点，它们的先后顺序就随意，题目若要求"字典序最小的拓扑序"，只需把普通队列换成 BinaryHeap<Reverse<usize>>。另一种实现是 DFS 后序遍历：每访问完一个点就把它压入结果栈，最后整体反转。DFS 版本代码更短，但递归深链有爆栈风险，迭代 Kahn 更稳妥。平行边（同一对 u、v 出现多次）会让 indeg 多加也多减，结果依然正确，无需去重。

19.4 倍增 LCA：binary lifting

LCA 是最近公共祖先。朴素做法是一步步把较深的点往上抬，直到两点深度相同，再一起往上走，每次查询 O(n)。binary lifting 用预处理把"往上走"变成按 2 的幂跳跃：令 up[k][v] 表示 v 的第 2ᵏ 代祖先，k 最多 log₂n 层。预处理时 up[k][v] = up[k-1][up[k-1][v]]，即跳 2ᵏ 等于先跳 2ᵏ⁻¹ 再跳一次。

查询分三步：先把深度较大的点 a 抬到与 b 同深——计算差值 diff，按二进制位逐次跳；若此时 a == b，答案就是它；否则从最大的 k 往下枚举，只要 up[k][a] != up[k][b]，就让两点同时跳 2ᵏ，最后它们的父节点就是 LCA。最后一步之所以不能直接返回 up[0][a]，是因为当两点同层且相邻时已经相等，需要先区分再取父节点。

深度对齐用 depth[a] - depth[b] 时已经保证 a 更深（前面用 swap 换过），所以减法不会下溢。枚举二进制位用 (diff >> k) & 1 而不是反复取模，既直观又高效。若根不一定是 0 号点，只需把 root 作为参数传入并把 parent 数组的哨兵设成一个合法范围外的值，其余代码无需改动。

fn lca_all(
n: usize,
edges: &[(usize, usize)],
root: usize,
queries: &[(usize, usize)],
) -> Vec<usize> {
let mut g = vec![Vec::<usize>::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
let mut log = 1usize;
while (1usize << log) <= n {
log += 1;
}
let mut up = vec![vec![root; n]; log];
let mut depth = vec![0usize; n];
let mut parent = vec![n; n];
parent[root] = root;
let mut st = vec![root];
while let Some(u) = st.pop() {
for &v in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
up[0][v] = u;
st.push(v);
}
}
for k in 1..log {
for v in 0..n {
up[k][v] = up[k - 1][up[k - 1][v]];
}
}
let mut ans = Vec::with_capacity(queries.len());
for &(mut a, mut b) in queries {
if depth[a] < depth[b] {
std::mem::swap(&mut a, &mut b);
}
let diff = depth[a] - depth[b];
for k in 0..log {
if ((diff >> k) & 1) == 1 {
a = up[k][a];
}
}
if a == b {
ans.push(a);
continue;
}
for k in (0..log).rev() {
if up[k][a] != up[k][b] {
a = up[k][a];
b = up[k][b];
}
}
ans.push(up[0][a]);
}
ans
}
fn main() {
let edges = [(0usize, 1usize), (1, 2), (1, 3), (3, 4), (3, 5)];
let q = [(2usize, 4usize), (0, 5), (4, 5)];
println!("{:?}", lca_all(6, &edges, 0, &q));
}

预处理 O(n log n)，单次查询 O(log n)。注意 up 表用 vec![vec![root; n]; log] 初始化，让根的祖先始终是根自己，这样跳到根以上也不会越界；这正是避免 usize 减法和越界检查的巧妙做法。第一次 DFS 写成迭代，依旧是为了规避深树爆栈——一条十万节点的链会让递归版直接崩溃。

计算层数 log 时，while (1usize << log) <= n 要在 n 很大时确保移位不溢出；对常规 n ≤ 10⁶ 完全安全。若查询量特别大且树是静态的，还可以用欧拉序 + RMQ（稀疏表）把查询压到 O(1)，预处理变成 O(n log n)；但 binary lifting 代码更短、更不易错，是刷题时的默认选择。另一个常见变体是"带权 LCA"——在抬升过程中累加路径长度，只需多维护一个 dist_up[k][v] 表，就能顺带求出任意两点的树上距离：dist(a) + dist(b) - 2 * dist(lca)。把这几套模板放在同一份笔记里对照记忆，比孤立背诵效果好得多。

20.1 DP 的本质：状态、转移与不变量

动态规划（DP）不是一种固定模板，而是一种消重思想：当问题具有最优子结构（大局最优由子问题最优组合而来）和重叠子问题（同一子状态被反复用到）时，可以把每个子状态的答案存起来，避免重复计算。写 DP 的第一步永远是定义状态——用一句话说清 dp[i]（或 dp[i][j]）代表什么，包括"范围"和"目标"两个要素，例如"只考虑前 i 个元素、以 i 结尾的最大和"。

第二步是转移：从已知状态推出当前状态，通常是在若干种决策里取 max 或 min。转移方程要写得能自圆其说：每种决策对应一种实际可行的选择，不能漏也不能重复。第三步是初始化与计算顺序：base case 必须覆盖最小的子问题，循环顺序要保证"转移时依赖的状态已经算好"。把这三步的不变量写成注释贴在代码上方，是调试 DP 最有效的手段。

实现上有两种路线。自顶向下用递归加备忘录，思路贴近状态定义，但深递归有爆栈风险；自底向上用数组填表，顺序明确、性能更好，是竞赛默认选择。Rust 里填表常用 Vec<T> 或 Vec<Vec<T>>，下标统一为 usize，并在需要"前一项"时多开一格哨兵，避免 i - 1 下溢。

估算 DP 复杂度有个简单公式：状态总数乘以每个状态的转移数。线性 DP 是 O(n × k)，背包是 O(n × cap)，区间 DP 是 O(n² × n) = O(n³)。用这个公式能在写代码前就判断方法是否可行。若状态只依赖有限的前几项，可以用滚动数组压缩空间；若依赖跨度很大（例如区间 DP），就只能保留整张表。状态里带一维"是否已选择"的布尔标记时，常用 0/1 下标的二维数组表示，比嵌套 Option 更省事也更易调试。

大白话先用直觉把它讲通

DP 就是"把算过的答案记在小本本上"。面对一个大问题，先把它拆成规模更小的同类问题，把每种小问题的答案记下来，大问题只要查小本本再做一次选择就行。关键是小本本上每条记录都要写清楚"它管的是哪一段"，不然查错行就全盘皆输。

20.2 线性 DP 与状态转移表

线性 DP 的状态沿一维下标推进，dp[i] 依赖前面的若干项。"打家劫舍"是典型：沿街房屋排成一行，不能偷相邻两家。定义 dp[i] 为"偷完前 i 家所得的最大金额"，那么对第 i 家只有两种选择——不偷，答案是 dp[i-1]；偷，答案是 dp[i-2] + a[i]。转移即 dp[i] = max(dp[i-1], dp[i-2] + a[i])。

为了少写边界判断，把数组多开两格：dp 长度 n + 2，dp[i + 2] 对应原问题的"前 i + 2 家"？更直接的约定是让 dp[k] 表示前 k 家的答案，于是 dp[0] = dp[1] = 0，循环里算 dp[i + 2] = max(dp[i + 1], dp[i] + a[i])。这样 i = 0 时访问 dp[0] 完全合法，不必特判。完整转移表建议先保留，打印出来对照手工推演；确认无误后再改成只留两个变量的滚动数组，把空间从 O(n) 降到 O(1)。

fn rob(a: &[i64]) -> (i64, Vec<i64>) {
let n = a.len();
let mut dp = vec![0i64; n + 2];
for i in 0..n {
dp[i + 2] = dp[i + 1].max(dp[i] + a[i]);
}
(dp[n + 1], dp)
}
fn rob_rolling(a: &[i64]) -> i64 {
let (mut prev2, mut prev1) = (0i64, 0i64);
for &x in a {
let cur = prev1.max(prev2 + x);
prev2 = prev1;
prev1 = cur;
}
prev1
}
fn main() {
let a = [2i64, 7, 9, 3, 1];
let (ans, dp) = rob(&a);
println!("answer = {}", ans);
println!("dp = {:?}", dp);
println!("rolling = {}", rob_rolling(&a));
}

滚动数组更新顺序是易错点：必须先用旧的 prev2 和 prev1 算出 cur，再依次把 prev2 ← prev1、prev1 ← cur。若先把 prev2 = prev1 写下去，prev2 + x 就不是两步之前的值了。这种"旧值被覆盖导致转移错误"的 bug 在 DP 里非常常见，改成滚动前一定要先把完整表的版本验证通过。

同类的线性 DP 还有最长递增子序列（LIS）：定义 dp[i] 为以 i 结尾的 LIS 长度，转移是枚举所有 j < i 且 a[j] < a[i] 的位置取最大值，复杂度 O(n²)。若用 tail 数组维护每个长度的最小结尾值，配合二分查找可以压到 O(n log n)，但那已经不属于朴素填表。初学阶段建议先把 O(n²) 版本写对，再用随机数据与优化版对拍，这样既能保证正确性，也能理解优化究竟省掉了什么。

20.3 背包：0/1 与完全

背包是 DP 最重要的一族。0/1 背包：每件物品最多选一次；定义 dp[c] 为"容量不超过 c 时能取得的最大价值"，对每件物品更新一遍容量。关键在容量必须倒序枚举：从 cap 递减到 weight[i]，这样 dp[c - weight[i]] 还是"上一件物品处理完"的值，保证当前物品只用一次。若正序枚举，dp[c - weight[i]] 可能已经包含当前物品，就会重复选取——那恰好是完全背包的行为。

完全背包每件物品可以选任意多次，容量改为正序枚举，让新算出的 dp[c - weight[i]] 立即被更大的 c 复用，等价于允许无限次选择。两个模板只差一个 .rev()，但含义天差地别，务必用自己的话解释一遍再写。

fn knap01(weight: &[usize], value: &[i64], cap: usize) -> i64 {
let mut dp = vec![0i64; cap + 1];
for i in 0..weight.len() {
for c in (weight[i]..=cap).rev() {
dp[c] = dp[c].max(dp[c - weight[i]] + value[i]);
}
}
dp[cap]
}

for i in 0..weight.len() {
for c in weight[i]..=cap {
dp[c] = dp[c].max(dp[c - weight[i]] + value[i]);
}
}
dp[cap]
}

当 weight[i] > cap 时，weight[i]..=cap 是空区间（Rust 的 RangeInclusive 在起点大于终点时不产生任何元素），循环自然跳过，不需要额外判断。若题目要求"恰好装满"，把 dp 初始化为负无穷、只保留 dp[0] = 0，最后输出 dp[cap] 即可区分无解。价值可能很大时用 i64 累加。

如果题目还限制"每组至少选一件"或"分给两个人"，往往要把状态扩展成二维甚至三维，例如 dp[i][j] 表示处理前 i 件、给第一个人分配容量 j 时的最优值。维度增加会让复杂度成倍上升，动手前先用"状态数 × 转移数"算一遍。把 dp 数组按行存成 Vec<Vec<T>> 时，注意内层 Vec 的长度是 cap + 1，访问 dp[i][c - weight[i]] 的减法只有在 c >= weight[i] 时才合法，循环起点正是为了守住这个前提。

20.4 区间 DP 入门

区间 DP 的状态是 dp[l][r]，表示闭区间 [l, r] 上的最优值。它的计算顺序不能按 l 或 r 的字典序，而要按区间长度从小到大：先算所有长度为 2 的区间，再算长度为 3 的，以此类推。因为长度为 len 的区间要由两个更短的区间合并而来，长度递增天然保证依赖已就绪。

"石子合并"是标准例题：一排石子两两合并，每次代价是两堆总数，求全部合成一堆的最小总代价。枚举断点 k，把 [l, r] 拆成 [l, k] 和 [k+1, r]，转移是 dp[l][r] = min(dp[l][k] + dp[k+1][r] + sum(l, r))。区间和用前缀和 O(1) 取得，避免每次累加。复杂度 O(n³)，n 通常不超过几百。

fn merge_stones(a: &[i64]) -> i64 {
let n = a.len();
if n <= 1 {
return 0;
}
let mut pref = vec![0i64; n + 1];
for i in 0..n {
pref[i + 1] = pref[i] + a[i];
}
let inf = i64::MAX / 4;
let mut dp = vec![vec![0i64; n]; n];
for len in 2..=n {
for l in 0..=n - len {
let r = l + len - 1;
let sum = pref[r + 1] - pref[l];
let mut best = inf;
for k in l..r {
best = best.min(dp[l][k] + dp[k + 1][r] + sum);
}
dp[l][r] = best;
}
}
dp[0][n - 1]
}
fn main() {
let a = [4i64, 3, 3, 4];
println!("{}", merge_stones(&a));
}

for l in 0..=n - len 中 n - len 恒为非负（len 最大取 n），不会下溢；r = l + len - 1 最大为 n - 1，访问 dp[k+1][r] 安全。区间 DP 的调试建议打印二维表：先确认所有 dp[l][l] = 0 的边界，再逐层检查长度为 2、3 的值是否与手工计算一致。

20.5 树形 DP 与调试清单

树形 DP 在树上定义状态，典型形态是"以 u 为根的子树内的最优值"。因为子树之间互不影响，可以先分别算出每个孩子的答案再合并。树上没有自然的循环顺序，所以要先做一次遍历得到节点的后序，再倒序处理，保证算 u 时所有孩子已算好。与第一单元的 DFS 一样，这里也用显式栈避免深树爆栈。

"树的最大独立集"需要两个状态：take[u] 表示选 u 时子树的最大收益，skip[u] 表示不选 u 时的最大收益。转移是 take[u] = 1 + Σ skip[v]，skip[u] = Σ max(take[v], skip[v])，其中 v 遍历 u 的所有孩子。两个状态互相依赖但层次不同，正是树形 DP 的经典结构。

fn tree_mis(n: usize, edges: &[(usize, usize)]) -> i64 {
let mut g = vec![Vec::<usize>::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
let mut parent = vec![n; n];
let mut order = Vec::with_capacity(n);
let mut st = vec![0usize];
parent[0] = 0;
while let Some(u) = st.pop() {
order.push(u);
for &v in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
st.push(v);
}
}
let mut take = vec![0i64; n];
let mut skip = vec![0i64; n];
for &u in order.iter().rev() {
take[u] = 1;
skip[u] = 0;
for &v in &g[u] {
if v == parent[u] {
continue;
}
take[u] += skip[v];
skip[u] += take[v].max(skip[v]);
}
}
take[0].max(skip[0])
}
fn main() {
let edges = [(0usize, 1usize), (0, 2), (1, 3), (1, 4), (2, 5)];
println!("{}", tree_mis(6, &edges));
}

树形 DP 的变化很多，例如换根 DP 需要两次遍历：第一次自底向上求子树答案，第二次自顶向下把父方向的贡献传递下来，合起来得到以每个点为根的最优值。掌握"后序合并"这一核心后，再学换根只是多加一次前序传递。调试 DP 有一套固定流程：先在纸上写出状态定义，再用最小的两三个例子手推转移表；把完整表打印出来与手工结果逐格对照；确认转移正确后再考虑滚动优化；最后用暴力搜索或随机对拍验证大数据。绝大多数 DP 错误都出在状态定义含糊、边界初始化错误或循环顺序颠倒，而不是转移方程本身。把"状态是什么、依赖谁、何时算好"这三句话写在代码注释里，排查时就能快速定位。
