18.1 栈与队列：从 Vec 到手写环形数组

问题定义：栈要求后进先出（LIFO），队列要求先进先出（FIFO）。两者都是"只在端点操作"的容器，核心诉求是插入与删除都接近常数时间。栈用 Vec 的尾部当栈顶再自然不过：入栈 push、出栈 pop 都是均摊 O(1)。队列则必须支持头部出队，普通 Vec 的 remove(0) 要搬动后面所有元素，是 O(n)，所以标准库提供双端队列 VecDeque，它的 push_back/pop_front 都是 O(1)。

如果题目固定容量，也可以手写一个环形数组队列：用 head 指向队首元素的物理位置，用 len 记录当前元素个数，下一个写入位置是 (head + len) % cap。这里有一条铁律：永远不要写 head - 1，那在 head = 0 时会触发 usize 下溢。改用 head + len 表示写入位置，配合取模，既避免负数，也让"队满"判断变成 len == cap。出队时只把 head 前移一位再取模，len 减一；所有关于队满队空的判断都必须基于 len，而不是 head 的值。

为什么 VecDeque 能同时做到两端 O(1)？它内部也是环形缓冲区，只是把"逻辑下标"与"物理下标"的映射藏在了标准库里，并会在容量不足时自动扩容搬移。Vec::remove(0) 之所以慢，是因为它必须把后面所有元素向前搬一格，这是数组连续存储的固有代价，而非实现偷懒。理解这一点后就能做出正确取舍：需要频繁头部删除时用 VecDeque，只在尾部操作时用 Vec，后者缓存局部性更好、常数更小。环形缓冲区的另一个好处是内存可以复用——出队后那块空间会留给后来的入队元素，不会像"每次 remove(0) 再 push"那样反复分配。这也是第 17 单元"预分配"约定在队列上的具体体现。

结构 推荐实现 入栈/入队 出栈/出队 关键陷阱
栈 Vec<T> push 均摊 O(1) pop O(1) 栈顶在尾部，别反向遍历
队列 VecDeque<T> push_back O(1) pop_front O(1) 别用 Vec::remove(0)
定长队列 手写环形数组 取模定位 O(1) 移动 head O(1) head 回绕、len 与 cap 相等

下面的程序先用 Vec 演示栈，再运行手写的 ArrayQueue。当队列容量为 4、连续入队 6 个数时，第 5 次入队返回 false 并打印 full at 5；随后把队列排空，得到 1 2 3 4。while let Some(v) = q.pop_front() 是 Rust 里 drain 一个容器的惯用写法，比 while !q.is_empty() 更简洁，也把"取不到就停"的语义写在了类型里。

struct ArrayQueue {
buf: Vec<i32>,
head: usize,
len: usize,
}
impl ArrayQueue {
fn new(cap: usize) -> Self {
ArrayQueue { buf: vec![0; cap], head: 0, len: 0 }
}
fn push_back(&mut self, v: i32) -> bool {
if self.len == self.buf.len() {
return false;
}
let pos = (self.head + self.len) % self.buf.len();
self.buf[pos] = v;
self.len += 1;
true
}
fn pop_front(&mut self) -> Option<i32> {
if self.len == 0 {
return None;
}
let v = self.buf[self.head];
self.head = (self.head + 1) % self.buf.len();
self.len -= 1;
Some(v)
}
}
fn main() {
// Vec 当栈：栈顶在尾部
let mut st: Vec<i32> = Vec::with_capacity(4);
st.push(1);
st.push(2);
println!("stack push/pop: {:?} {:?}", st.pop(), st.pop());
let mut q = ArrayQueue::new(4);
for x in 1..=6 {
if !q.push_back(x) {
println!("full at {}", x);
break;
}
}
while let Some(v) = q.pop_front() {
print!("{} ", v);
}
println!();
}
大白话先用直觉把它讲通

栈像一摞盘子，只能从顶上拿；队列像排队买票，先来的先走。单调栈和单调队列则是在这两个容器上加了一条规矩：里面的值必须按大小排好队，一旦有人破坏了规矩就把队尾不合格的请出去。这样队首永远是当前最优解，查询就是 O(1)。

18.2 单调栈的不变量：存下标、摊还线性

问题定义：给定数组，求每个位置右边第一个比它大的元素的位置（"每日温度"求的是天数差）。

不变量：维护一个下标栈，栈中下标对应的值保持严格递减。新元素 t[i] 到来时，不断弹掉栈顶那些值小于 t[i] 的下标，直到栈顶的值不小于它（或栈空），再把 i 入栈。弹出时，i 就是被弹下标 j 要等的"更暖和的一天"，答案是 i - j。

为什么必须存下标而不是值？因为答案要的是距离，只有下标才能算 i - j；只存温度值就丢失了位置信息。为什么 i - j 不会下溢？因为栈里的下标都是已经遍历过的位置，必有 i > j，减法方向天然安全。这是 Rust 写单调结构时少有的"不需要额外判断"的减法，原因值得记住：数据结构的不变量本身保证了边界。

摊还 O(n) 的论证是单调结构的灵魂。内层 while 看似嵌套在 for 里，容易误判成 O(n²)；但每个下标最多入栈一次、出栈一次，整个遍历过程中弹栈操作的总次数不超过 n。把内层循环的总工作量摊到 n 个元素上，每份是常数，因此总时间是 O(n)。用第 17 单元的术语说，这是聚合分析：先算总量再除以次数。判断一个看起来嵌套的结构是不是单调结构，就问"同一个元素会不会被反复弹入弹出"——若答案是否定的，基本可以放心判线性。

严格性与相等值是另一个需要提前约定的细节。上面用 temp > t[j] 弹出，意味着"必须严格更暖"才算找到答案；如果题目问的是"第一个不低于当前温度的日子"，弹出条件要改成 temp >= t[j]。差一个等号，相等元素的行为完全不同：前者会把相等温度留在栈里继续等，后者会立即弹出并结算为距离 0。没有对错之分，只有是否符合题意。写完代码后，用一组含大量重复值的数组（例如全 20）跑一遍，看输出是否符合题目对相等情况的规定，是验证这个细节最快的办法。

rustRust · 标准库22 行
fn daily_temperatures(t: &[i32]) -> Vec<usize> {
let n = t.len();
let mut ans = vec![0usize; n];
let mut st: Vec<usize> = Vec::with_capacity(n); // 栈中温度严格递减
for (i, &temp) in t.iter().enumerate() {
while let Some(&j) = st.last() {
if temp > t[j] {
let j = st.pop().unwrap();
ans[j] = i - j; // i > j，减法安全
} else {
break;
}
}
st.push(i);
}
ans
}
fn main() {
let t = [73, 74, 75, 71, 69, 72, 76, 73];
println!("{:?}", daily_temperatures(&t));
}

while let Some(&j) = st.last() 里的 &j 不能省略。st.last() 返回 Option<&usize>，模式 Some(j) 会把 j 绑定为 &usize 引用，而紧接着的 st.pop() 需要可变借用 st——一个不可变引用与一个可变引用同时存在，编译器拒绝。写成 Some(&j) 则是把下标复制成标量，引用在模式匹配结束时就消失了，后面可以放心 pop。这是 Rust 写单调结构最常遇到的借用冲突，解法统一为"先 copy 出标量再修改容器"。

18.3 柱状图最大矩形：哨兵、弹出结算与左右边界

问题定义：给定非负整数数组表示柱状图各柱高度，求矩形面积的最大值。

不变量与正确性：维护高度严格递增的下标栈。当遇到高度 cur 小于栈顶高度时，栈顶柱 idx 的"右边界"就是当前位置 i（再往右第一根柱子比它矮），"左边界"是弹出后新栈顶下标加一（新栈顶是左边最后一根比它矮的柱子）。于是以 h[idx] 为高的最大矩形宽度是 i - left，面积立即结算。每根柱子只在被弹出时结算一次，不会遗漏也不会重复。

为了让遍历结束时栈中所有柱子都被结算，在数组末尾追加一个高度为 0 的哨兵：它比所有真实高度都小，能一次性清空整个栈。哨兵必须是 0 而不是 -1，因为题目保证高度非负；若输入可能含负数，要改用 -1 或显式循环清空栈。

坑这里最容易踩

弹出条件写成 h[top] <= cur 而不是 <：遇到相同高度时弹出旧的、保留新的。若写成 <，相同高度会全部留在栈里，既不错误但左边界计算会变得啰嗦，且容易在多次相等时重复结算。另一个坑是把哨兵写成 -1 却用 Vec<i32> 装非负高度，看似可行，但一旦题目数据含 0 就会与哨兵冲突；更稳妥的做法是显式追加一个"逻辑哨兵"下标，用一个额外的循环把栈排空，而不是往数据里塞特殊值。

rustRust · 标准库26 行
fn largest_rectangle(heights: &[i32]) -> i32 {
let mut h = Vec::with_capacity(heights.len() + 1);
h.extend_from_slice(heights);
h.push(0); // 哨兵：强制清空栈
let mut st: Vec<usize> = Vec::with_capacity(h.len());
let mut best = 0i32;
for (i, &cur) in h.iter().enumerate() {
while let Some(&top) = st.last() {
if h[top] <= cur {
break; // 保持栈中高度严格递增
}
let idx = st.pop().unwrap();
let height = h[idx];
let left = st.last().map_or(0, |&j| j + 1);
let width = i - left; // i 一定大于 left
best = best.max(height * (width as i32));
}
st.push(i);
}
best
}
fn main() {
let a = [2, 1, 5, 6, 2, 3];
println!("{}", largest_rectangle(&a));
}

left = st.last().map_or(0, |&j| j + 1) 用 map_or 把"栈空"和"有栈顶"两种情况压成一个表达式：栈空时左边界是 0，否则是新栈顶下标加一。|&j| 同样是在复制下标，避免持有引用干扰后续操作。

还有一个容易被忽视的数值边界：height * (width as i32) 在高度达到 10⁹、宽度达到 10⁵ 时会溢出 i32。本单元示例代码用的是小数据，所以 i32 够用；实际题目若声明高度可达 10⁹，要先把 height 转成 i64 再相乘，即 height as i64 * width as i64，并把 best 也声明为 i64。Rust 在 debug 构建下会当场报告整数溢出，这反而是好事——它逼你在上线前就把类型选对，而不是像某些语言那样静默回绕。记住：下标用 usize，计数与求和用 i64，这是算法里最稳妥的默认选择。

拿 [2, 1, 5, 6, 2, 3] 走一遍：当 i 走到下标 4（高度 2）时，栈顶是高度 6 的下标 3，6 > 2 被弹出，此时新栈顶是高度 5 的下标 2，左边界为 3，宽度 4 - 3 = 1，面积 6；继续弹出高度 5，左边界变成下标 1 之后，宽度 4 - 2 = 2，面积 10，这就是答案。注意"左边界 = 弹出后新栈顶下标 + 1"这一步：新栈顶是最后一个比当前柱矮的柱子，矩形自然只能从它右边开始。在脑中手动模拟两三个元素的能力，比死记模板更能帮你定位边界错误。

18.4 单调队列：滑动窗口最大值的候选淘汰

问题定义：给定数组与窗口大小 k，求每个长度为 k 的滑动窗口中的最大值。

不变量与正确性：队列里只保存可能成为未来最大值的下标，且它们对应的值从队首到队尾严格递减。于是队首永远是当前窗口答案。这个"候选名单"的删减依据是支配关系：若下标 p < q 且 a[p] <= a[q]，那么只要 q 还在窗口内，p 就永远不可能成为最大值——q 更靠后（活得更久）且不小于它。所以 p 被 q 完全支配，可以从名单里删掉。

每次新元素 x = a[i] 到来要做三件事，顺序不能乱：第一，把已经滑出窗口的过期下标从队首弹掉；第二，从队尾弹掉所有值 <= x 的下标（它们被 x 支配）；第三，把 i 入队。当 i + 1 >= k 时，队首就是当前窗口最大值。先过期再淘汰，能保证被淘汰判断的候选都还在窗口内；反过来先淘汰再过期虽然结果相同，但会让"支配关系"的语义变得不清晰。

rustRust · 标准库35 行
use std::collections::VecDeque;
fn sliding_max(a: &[i32], k: usize) -> Vec<i32> {
if k == 0 || k > a.len() {
return Vec::new();
}
let mut dq: VecDeque<usize> = VecDeque::with_capacity(a.len());
let mut out = Vec::with_capacity(a.len().saturating_sub(k) + 1);
for (i, &x) in a.iter().enumerate() {
while let Some(&front) = dq.front() {
if front + k <= i {
dq.pop_front();
} else {
break;
}
}
while let Some(&back) = dq.back() {
if a[back] <= x {
dq.pop_back();
} else {
break;
}
}
dq.push_back(i);
if i + 1 >= k {
out.push(a[*dq.front().unwrap()]);
}
}
out
}
fn main() {
let a = [1, 3, -1, -3, 5, 3, 6, 7];
println!("{:?}", sliding_max(&a, 3));
}

队尾弹出用 <= 也能正确处理相等元素：两个相等的值先后入队，旧的先过期，新的留在队列里，弹出旧的不损失信息，反而让队列更短。只有当题目要求"同时保留相等元素的计数"时，才需要改成 < 并在别处单独处理。把单调队列想象成"去掉了所有被支配候选者的名单"，a[back] <= x 正是支配关系的直译。

从摊还角度看，滑动窗口的每一步里，每个下标入队一次、出队最多一次（可能从队首过期出去，也可能从队尾被淘汰出去），所以总操作次数是 O(n)，而非表里的 O(nk) 暴力扫描。空间上队列最多装 k 个候选人，是 O(k)。相比之下，用堆维护窗口需要同时保存值和下标，并在过期时做懒删除，单次操作 O(log n)，代码也更长；单调队列的优势正是把"过期"与"最值"这两件事合并进同一个数据结构，用简单的下标比较取代了复杂的删除逻辑。代价是它只适用于"最大值/最小值"这类可由支配关系刻画的问题，换成"中位数"就不再成立。

方案 单次查询 总复杂度 适用条件
每个窗口扫一遍 O(k) O(nk) 仅作暴力对照
单调队列 摊还 O(1) O(n) 任意数组，窗口固定
堆 + 懒删除 O(log n) O(n log n) 窗口可变、需支持删除

18.5 过期判断与 usize 防御：两处细节定生死

单调队列的代码不长，却集中了 Rust 下标运算最典型的两个防御动作，值得单独拆开讲。

第一处是过期判断 front + k <= i，而不是 front == i - k + 1。那种写法在数学上等价，但循环初期 i 可能小于 k - 1，此时 i - k + 1 会发生 usize 下溢——debug 构建当场 panic，release 构建回绕成天文数字，导致队列永远不被清空。改成加法形式后，等式两边都不会出现负数，front + k 只有在 i 真正越过窗口右端时才成立。这再次印证第 17 单元的准则：让减法永远发生在"被减数更大"的前提下。

第二处是输出预分配 a.len().saturating_sub(k) + 1。当 k > a.len() 时，普通减法 a.len() - k 会下溢；虽然前面已经用 if k == 0 || k > a.len() { return Vec::new(); } 挡住了这种情况，但把 saturating_sub 写上是一层额外的保险，也表达了"容量最坏为 0"的意图。类似地，柱状图里的 left = st.last().map_or(0, |&j| j + 1)，j + 1 在 j 接近 usize::MAX 时理论上会溢出，但 j 是真实数组下标，远小于上限，所以这里安全——区分"理论上溢出"与"实践中不可能"同样是工程判断力。

18.6 随机对拍：三个单调算法一起验

单调结构的 bug 往往"看起来差不多"，不会崩溃，只是边界错一两个位置。把暴力解法当裁判，能在几秒内抓出来。本节的测试同时验证三种实现：每日温度、柱状图最大矩形、滑动窗口最大值。

暴力解法分别是：对每个位置向右扫描直到找到更大值；枚举每根柱子的起点终点并维护区间最小高度；对每个窗口扫描 k 个元素取最大值。它们分别是 O(n²)、O(n²)、O(nk)，在 n ≤ 12 的小数据上瞬间完成。随机数由 LCG 生成，乘法与加法都用 wrapping_* 避免 debug 构建溢出 panic。固定种子并打印，一旦发现不一致就能稳定复现。

fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
fn daily_fast(t: &[i32]) -> Vec<usize> {
let n = t.len();
let mut ans = vec![0usize; n];
let mut st: Vec<usize> = Vec::with_capacity(n);
for (i, &temp) in t.iter().enumerate() {
while let Some(&j) = st.last() {
if temp > t[j] {
let j = st.pop().unwrap();
ans[j] = i - j;
} else {
break;
}
}
st.push(i);
}
ans
}
fn daily_slow(t: &[i32]) -> Vec<usize> {
let n = t.len();
let mut ans = vec![0usize; n];
for i in 0..n {
for j in i + 1..n {
if t[j] > t[i] {
ans[i] = j - i;
break;
}
}
}
ans
}
fn rect_fast(heights: &[i32]) -> i32 {
let mut h = Vec::with_capacity(heights.len() + 1);
h.extend_from_slice(heights);
h.push(0);
let mut st: Vec<usize> = Vec::with_capacity(h.len());
let mut best = 0i32;
for (i, &cur) in h.iter().enumerate() {
while let Some(&top) = st.last() {
if h[top] <= cur {
break;
}
let idx = st.pop().unwrap();
let height = h[idx];
let left = st.last().map_or(0, |&j| j + 1);
best = best.max(height * ((i - left) as i32));
}
st.push(i);
}
best
}
fn rect_slow(h: &[i32]) -> i32 {
let n = h.len();
let mut best = 0i32;
for i in 0..n {
let mut min_h = i32::MAX;
for j in i..n {
min_h = min_h.min(h[j]);
best = best.max(min_h * ((j - i + 1) as i32));
}
}
best
}
fn slide_fast(a: &[i32], k: usize) -> Vec<i32> {
if k == 0 || k > a.len() {
return Vec::new();
}
let mut dq: VecDeque<usize> = VecDeque::with_capacity(a.len());
let mut out = Vec::with_capacity(a.len().saturating_sub(k) + 1);
for (i, &x) in a.iter().enumerate() {
while let Some(&front) = dq.front() {
if front + k <= i {
dq.pop_front();
} else {
break;
}
}
while let Some(&back) = dq.back() {
if a[back] <= x {
dq.pop_back();
} else {
break;
}
}
dq.push_back(i);
if i + 1 >= k {
out.push(a[*dq.front().unwrap()]);
}
}
out
}
fn slide_slow(a: &[i32], k: usize) -> Vec<i32> {
if k == 0 || k > a.len() {
return Vec::new();
}
let mut out = Vec::with_capacity(a.len() - k + 1);
for s in 0..=a.len() - k {
let mut m = i32::MIN;
for &x in &a[s..s + k] {
m = m.max(x);
}
out.push(m);
}
out
}
fn main() {
let seed0 = 20240501u64;
let mut seed = seed0;
let mut bad = 0usize;
for t in 0..3000 {
let n = (lcg(&mut seed) % 12 + 1) as usize;
let temps: Vec<i32> = (0..n).map(|_| (lcg(&mut seed) % 71) as i32 + 30).collect();
let heights: Vec<i32> = (0..n).map(|_| (lcg(&mut seed) % 10) as i32 + 1).collect();
let vals: Vec<i32> = (0..n).map(|_| (lcg(&mut seed) % 21) as i32 - 10).collect();
let k = (lcg(&mut seed) % n as u64 + 1) as usize;
let (df, ds) = (daily_fast(&temps), daily_slow(&temps));

if df != ds || rf != rs || sf != ss {
bad += 1;
println!(

);

}
}
if bad == 0 {
println!("diff seed={}: 3000 cases x 3 algorithms passed", seed0);
}
}

18.7 变体、取舍与常见误用

单调方向的反转是最常见的变体。每日温度求"下一个更大"，栈保持递减；若要求"下一个更小"，栈就保持递增，弹出条件改成 temp < t[j]。柱状图求最大矩形用递增栈；若求"每个位置左边第一个更高"，同样改成递减栈。判断方向有个简单口诀：弹出条件要能淘汰"不可能成为答案"的元素——求更大时，比当前小的元素被淘汰；求更小时，比当前大的被淘汰。

相等元素的处理决定了弹出条件是 < 还是 <=。求"下一个严格更大"时，相等元素不能互相弹出，用 temp > t[j]（严格大于才弹）；求"下一个不小于"时，用 >=。柱状图最大矩形用 <= 弹出相等高度，是为了把重复的宽度合并到最右边的柱子上，避免重复结算。滑动窗口用 <= 淘汰相等值，是因为旧的下标必定先过期，留新的更划算。把"为什么要这样比较"写成注释放在 if 上方，比事后单步调试快得多。

单调结构不是万能的。它要求被维护的量具有单调性，且每个元素只需进出各一次。如果查询是"窗口内第 k 大"而非最大，单调队列就无能为力，需要切换到堆或平衡树；如果"最优候选"会因为某个未来事件重新变优（左指针需要回退），滑动窗口的前提就被破坏，必须换方法。还有一个典型误用：把单调栈用于无序数据的"全局最值"查询——栈只能回答"到当前位置为止"的局部问题，全局最值用一次扫描就够了，栈反而多余。

与优先队列的取舍可以归结为一句话：单调结构用"信息淘汰"换取线性时间，堆用"全量保留"换取通用性。单调栈里被弹出的元素永远不会再回来，因为它的答案已经确定；堆里的元素即使过期也要等到弹出时才能判断，所以堆必须保留全部候选。当问题能证明"一旦被淘汰就永不再需要"时，单调结构严格优于堆；当这个证明不成立时，强行套单调结构只会得到错误答案。竞赛中"每日温度""滑动窗口最大/最小值"属于前者，"动态维护第 k 大"属于后者，分界线相当清晰。

18.8 调试清单与不变量注释

这一类题目出错往往不是算法想错，而是边界处理不细。逐项核对能省很多时间：栈或队列里存的到底是值还是下标；单调方向是递增还是递减，与题目求"更大"还是"更小"是否一致；弹出条件该用 <= 还是 <；过期判断的下标关系是否用了加法形式；哨兵值是否会与真实数据冲突；所有减法是否满足被减数大于减数；usize 转换是否显式写出。把不变量写成注释放在循环上方，例如"栈中下标对应高度严格递增，弹出即结算以该高度为高的最大矩形"，每次循环体内只做保持不变量的事，代码就很难错。

写错单调方向时，程序往往不会崩溃，而是给出"看起来差不多"的错误答案，这类 bug 最危险。一个有效的自检办法是在纸上画三列：当前位置 i、栈（或队列）内容、本轮产生的答案，然后手工推进五到六个元素。手工模拟能验证不变量是否真的成立，比如每日温度里栈中温度是否始终递减、最大矩形里新栈顶是否一定比弹出柱矮。等手工推演与程序输出一致，再交给随机对拍做大范围验证，两套手段配合起来基本能根除这一类边界错误。

以每日温度的 [73, 74, 75, 71] 为例手工推演：i=0 时栈空，73 入栈；i=1 时 74 弹出 73，记录距离 1，再入栈；i=2 时 75 弹出 74，记录距离 1，再入栈；i=3 时 71 不大于 75，直接入栈，栈内变成 [2, 3]，对应温度 [75, 71]，依然递减。四步走完，输出开头是 [1, 1, ...]，与程序真实结果一致。这种"每轮都能用一句话解释不变量为何保持"的推演，是把模板变成自己东西的最短路径。
