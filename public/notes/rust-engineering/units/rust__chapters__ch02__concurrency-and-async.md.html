12.1 线程与 move 闭包：为什么是 Send + 'static

thread::spawn 的签名要求闭包满足 F: Send + 'static，返回值满足 T: Send + 'static。这两个约束不是随意加的，而是把数据竞争最常见的来源挡在编译期。Send 表示「这个值可以安全地转移到另一个线程」，'static 表示「它不借用任何比新线程寿命更短的栈数据」。操作系统不知道 Rust 的生命周期，一旦新线程拿着指向已销毁栈帧的引用运行，结果就是未定义行为；编译器用这两条约束在源头阻止了它。

满足约束的直接方式是 move 闭包：它把捕获的变量按值搬进闭包。要注意 move 移动的是变量本身：如果变量是 Vec<String>，整个缓冲区被转移；如果变量是 &String，移动的只是这个引用，它仍然指向原来的栈数据，依旧过不了 'static 这一关。很多人以为写了 move 就万事大吉，结果错误变成「borrowed data escapes outside of closure」，原因正在这里。

Rust 1.63 起提供的 thread::scope 是另一种答案：它允许子线程借用当前栈上的数据，因为 scope 会在返回前强制 join 所有子线程，借用的生命周期因此被严格约束在作用域内。下面这个 std-only 例子把两种形态放在一起：前半段用 scoped 线程借用 names，后半段用 spawn 时把数据克隆进每个线程，最后按 (编号, 和) 排序输出，避免打印顺序受调度影响。

rustRust · 标准库31 行
use std::thread;
fn main() {
let names = vec!["alpha".to_string(), "beta".to_string()];
// scoped thread：允许借用当前栈上的数据，因为 scope 保证子线程先结束。
thread::scope(|s| {
for name in &names {
s.spawn(move || println!("scoped worker sees {}", name));
}
});
println!("scope 结束后 names 仍可用: {}", names.len());
// spawn 要求 'static：这里把所有权克隆进线程，互不干扰。
let data = vec![1i64, 2, 3];
let handles: Vec<_> = (0..3)
.map(|i| {
let owned = data.clone();
thread::spawn(move || {
let sum: i64 = owned.iter().sum();
(i, sum)
})
})
.collect();
let mut results = Vec::new();
for h in handles {
results.push(h.join().unwrap());
}
results.sort_unstable();
println!("results = {:?}", results);
}

scoped worker sees beta
scope 结束后 names 仍可用: 2

线程与异步不是非此即彼。线程由操作系统调度，上下文切换成本较高但使用直观，适合 CPU 密集且数量可控的任务；异步任务由运行时调度，单线程上可以挂起成千上万个等待 IO 的连接。选择时先看「任务是计算多还是等待多」，再看团队对调试复杂度的承受能力，而不是盲目追随性能数字。join 返回的 Result 也别忽略：工作线程 panic 时，join() 会返回 Err，不检查它就会把失败悄悄吞掉。

大白话先用直觉把它讲通

把线程想成外包团队。你交给它的资料必须是一份完整的复印件（move 转移所有权），不能是一张写着「去我办公桌上拿」的便条（借用局部变量）；后者等你下班回家就失效了。thread::scope 相当于你站在办公室等团队干完活再走，所以便条暂时有效。普通 spawn 没人等你，只能给复印件。

12.2 Arc<Mutex>：共享可变状态、中毒与锁粒度

当确实需要多个线程改动同一份数据时，Arc<Mutex<T>> 是标准库给出的基本组合。Arc 用原子引用计数让同一个值有多个所有者，Mutex 保证同一时刻只有一个线程能拿到内部数据的可变访问。锁的获取返回一个 guard，它在离开作用域时自动释放，因此不会因为忘记解锁而死锁——但「拿着锁调用可能等待的操作」仍会造成死锁或长时间阻塞，这一点编译器帮不了你。

计数器是最典型的例子。循环内每次只锁住极短的临界区，累加后立刻释放；用 Arc::clone 而不是直接克隆数据，确保共享的是同一个计数器。八个工作线程各加一千次，最终值精确等于 8000——这同时演示了 Mutex 的互斥语义：*guard += 1 看似一条语句，实际是读—改—写三步，没有锁就会丢失更新。

rustRust · 标准库26 行
use std::sync::{Arc, Mutex, TryLockError};
use std::thread;
fn main() {
let counter = Arc::new(Mutex::new(0u64));
let mut handles = Vec::new();
for _ in 0..8 {
let shared = Arc::clone(&counter);
handles.push(thread::spawn(move || {
for _ in 0..1000 {
let mut guard = shared.lock().unwrap();
*guard += 1;
}
}));
}
for h in handles {
h.join().unwrap();
}
println!("counter = {}", *counter.lock().unwrap());
match counter.try_lock() {
Ok(_) => println!("try_lock: 拿到锁"),
Err(TryLockError::WouldBlock) => println!("try_lock: 锁被占用，立即返回"),
Err(TryLockError::Poisoned(_)) => println!("try_lock: 锁已中毒"),
};
}

$ rustc --edition 2021 block_u12_2.rs -o bu12_2.exe && ./bu12_2.exe
counter = 8000
try_lock: 拿到锁

lock() 返回 Result，因为持锁线程 panic 后锁会处于「中毒（poisoned）」状态：此时内部数据可能只被改了一半。示例里 unwrap() 的前提是工作线程不会 panic；生产代码应当根据业务决定是恢复中毒锁、记录错误还是终止流程。若判断数据仍可用，可以用 err.into_inner() 从 PoisonError 中取回 guard，但必须确认被中断的操作没有留下半成品。另一个实用细节是 try_lock：它不等待，拿不到锁立即返回，适合「能做就做、不能就跳过」的刷新类任务。死锁的经典成因是多个线程以不同顺序获取两把锁；约定全局加锁顺序，或干脆把两把锁合成一把保护同一个结构体，通常比事后排查更省事。

当读多写少时 RwLock<T> 可以减少竞争：多个读者可同时进入，写者独占。但它的实现比 Mutex 复杂，在写竞争激烈时反而更慢，且同样有中毒问题——先用测量决定，不要凭「读多写少」四个字就直接引入。锁粒度也需要权衡：把整个大结构体塞进一把锁，逻辑简单但所有字段互相阻塞；每个字段一把锁，并发度高却容易在「需要同时更新两个字段」时忘记顺序。一个折中方案是让单个任务独占某个对象（通过通道移交），从根本上消除锁，这正是 12.3 的主题。

坑这里最容易踩

坑：跨 .await 持有标准库的 MutexGuard。等待期间任务可能被运行时切换出去，而 guard 会一直占着锁；若另一个任务恰好也要这把锁，就可能形成「自己等自己」的死锁。MutexGuard 不是 Send，编译器在 spawn 的任务里通常能拦住，但普通 async 函数里未必报错。 async/tokio 代码中应使用运行时提供的异步锁（tokio::sync::Mutex），并且只在真正读写共享数据的极短临界区内持有它。

12.3 mpsc 与交叉光束：以通信代替共享

共享内存不是并发的唯一答案。mpsc（multi-producer, single-consumer）通道让发送端持有 Sender、接收端持有 Receiver，数据通过队列传递，所有权随之转移。当所有发送端都被丢弃时通道关闭，for msg in rx 自然结束——这个特性让「工作线程完成即退出」的协作变得非常简洁，不需要额外的停止标志。

下面的例子分两段：前半段是无界通道，生产者发送三个字符串后函数结束、tx 被丢弃，接收端的 for 循环自然收尾；后半段用容量为 1 的 sync_channel 演示反压——队列满时 try_send 立即返回 Full，而不会阻塞。接收端关闭后再 send，SendError 会把没能发出的消息还回来，这对「队列关闭后如何回收数据」很有用。

rustRust · 标准库23 行
use std::sync::mpsc;
use std::thread;
fn main() {
let (tx, rx) = mpsc::channel::<String>();
let producer = thread::spawn(move || {
for word in ["alpha", "beta", "gamma"] {
tx.send(word.to_string()).unwrap();
}
});
for msg in rx {
println!("received: {}", msg);
}
producer.join().unwrap();
let (tx2, rx2) = mpsc::sync_channel::<u32>(1);
tx2.send(1).unwrap();
println!("队列满时 try_send = {:?}", tx2.try_send(2));
drop(rx2);
let err = tx2.send(3).unwrap_err();
println!("队列关闭后未发出的消息 = {}", err.0);
}

$ rustc --edition 2021 block_u12_3.rs -o bu12_3.exe && ./bu12_3.exe

received: beta
received: gamma
队列满时 try_send = Err(TrySendError::Full(..))
队列关闭后未发出的消息 = 3

选择经验可以压缩成一句话：需要多方修改同一份状态时用 Arc<Mutex<T>>；需要把任务或数据从生产者交给消费者时用 channel。后者把同步点集中在消息传递上，通常更容易推理，也更容易改成多消费者或加缓冲。设计数据流前先回答两个问题：消息丢了能不能接受？生产者会不会比消费者快很多？前者决定错误处理方式，后者决定用无界还是有界通道。

场景 推荐工具 理由
多个工作线程累加同一个计数器 Arc<Mutex<T>> 或原子 共享的是同一份状态
任务分发给工作线程池 mpsc / sync_channel 所有权随消息移动，天然解耦
生产者远快于消费者 有界 sync_channel 队列满时形成反压
只需一个布尔标志的跨线程通知 AtomicBool 无需锁，开销最低
大量独立 IO 等待 async 任务 + 异步通道 由运行时调度，不占线程

要注意同步通道与异步通道是两个概念：标准库的 mpsc::channel 在 send 时可能阻塞当前线程，tokio 的 mpsc 则把等待交给调度器。两者不应混用——在 async 任务里调用标准库的阻塞 send，会卡住执行器的工作线程。

12.4 原子与内存序直觉：从 Relaxed 到 SeqCst

AtomicUsize 这类原子类型提供的操作由硬件的原子指令支持，不需要锁。真正难的是内存序（Ordering）：它描述的不只是「这个操作本身不可分割」，还包括「这个操作对其他线程的可见性与其他操作的先后关系」。初学者常把所有地方都写成 SeqCst，它最安全但可能最慢；理解几档语义的差别，才能在热路径上做有依据的选择。

Relaxed 只保证原子性，不保证顺序。它适合「只关心最终计数，不关心中间先后」的场景：fetch_add 是一次读—改—写原子操作，四个线程各加十万次，最终结果精确等于 400000，即使各线程看到的中间值顺序完全不同。把这种场景写成 SeqCst 通常没有正确性收益，在某些架构上却会带来额外的内存屏障成本。

SeqCst 提供全局顺序：所有线程观察到所有 SeqCst 操作的一致性顺序。下面的第二段代码用它传递「数据已就绪」这一事实：写线程先 store(42) 再 store(ready)，读线程自旋等待 ready 后读取 data，必然看到 42。如果两处都换成 Relaxed，原子性仍然成立，但读线程可能先看到 ready 的更新却没看到 data 的更新——在 x86 上往往碰巧没问题，在 ARM 上就会翻车。这就是为什么内存序问题「测不出来不等于不存在」。

rustRust · 标准库34 行
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;
fn main() {
let count = Arc::new(AtomicUsize::new(0));
let mut hs = Vec::new();
for _ in 0..4 {
let c = Arc::clone(&count);
hs.push(thread::spawn(move || {
for _ in 0..100_000 {
c.fetch_add(1, Ordering::Relaxed);
}
}));
}
for h in hs {
h.join().unwrap();
}
println!("Relaxed 计数 = {}", count.load(Ordering::Relaxed));
let data = Arc::new(AtomicUsize::new(0));
let ready = Arc::new(AtomicUsize::new(0));
let d = Arc::clone(&data);
let r = Arc::clone(&ready);
let writer = thread::spawn(move || {
d.store(42, Ordering::SeqCst);
r.store(1, Ordering::SeqCst);
});
while ready.load(Ordering::SeqCst) == 0 {
std::hint::spin_loop();
}
println!("读到 data = {}", data.load(Ordering::SeqCst));
writer.join().unwrap();
}
终端真跑一遍
$ rustc --edition 2021 block_u12_4.rs -o bu12_4.exe && ./bu12_4.exe
Relaxed 计数 = 400000
读到 data = 42

介于两者之间的 Acquire/Release 提供了更精细的配对语义：写线程用 Release 发布数据，读线程用 Acquire 观察标志，就能建立单向的可见性保证，而不必付出全局顺序的代价。经验法则是：不确定就用 SeqCst，用基准与论证证明热路径需要更弱的序时再降；自旋等待时记得调用 std::hint::spin_loop() 提示 CPU 让出流水线资源，否则会空耗。

大白话先用直觉把它讲通

原子操作保证的是「这一下动作不会被切成两半」，而内存序保证的是「别人什么时候能看见这一下」。Relaxed 像默默记账，账目最终对得上，但别人什么时候看到不保证；SeqCst 像在所有人的日历上写同一件事，大家看到的顺序一致，代价是更费劲。只在真正需要「先看到 A 才允许看 B」的地方买这份保险。

12.5 Send / Sync：自动 trait 与编译器错误

Send 与 Sync 是标记 trait，没有方法，只有语义。T: Send 表示 T 的所有权可以转移到另一个线程；T: Sync 表示 &T 可以共享到另一个线程。两者的关系可以这样记：如果 T 是 Sync，那么 &T 就是 Send——因为共享引用本身可以被搬走，而它指向的数据允许被并发读取。

大多数类型不需要手写这两个 trait：一个结构体若所有字段都 Send，它就自动是 Send；所有字段都 Sync，它就自动是 Sync。标准库里的反例很有教育意义：Rc<T> 用非原子引用计数，多线程同时增减计数会破坏它，因此既不是 Send 也不是 Sync；Cell<T> 允许通过共享引用修改内部值，没有同步机制，所以不是 Sync；Mutex<T> 只要 T: Send 就同时满足两者，因为它串行化了访问。

类型 Send Sync 原因
i32、String 是 是 无内部共享状态
Rc<T> 否 否 引用计数非原子
Cell<T> T: Send 时是 否 共享引用可改值，无同步
Arc<T> T: Send + Sync 时是 同上 计数原子，数据仍需安全
Mutex<T> T: Send 时是 T: Send 时是 通过锁串行化访问

把约束写进函数签名，能让错误出现在调用点而不是深处的某个 spawn。下面这段代码把「可跨线程执行的闭包」写成了显式 bound，这样 API 的使用者在传入捕获了 Rc 的闭包时会立即得到提示。

rustRust · 标准库14 行
use std::thread::JoinHandle;
fn run_on_thread<F>(f: F) -> JoinHandle<()>
where
F: FnOnce() + Send + 'static,
{
std::thread::spawn(f)
}
fn main() {
let name = String::from("worker");
let handle = run_on_thread(move || println!("{} 满足 Send + 'static", name));
handle.join().unwrap();
}

自动派生的传播规则也值得留意：Vec<T>、Option<T>、Box<T> 等容器只要 T 满足条件，容器本身也满足；Arc<T> 则要求 T: Send + Sync，因为它可能被克隆到不同线程再解引用。这也解释了 anyhow 等库为什么要求错误类型满足 Send + Sync + 'static——错误可能跨线程传播到日志或任务边界。理解这条链，就能从「某个字段不是 Send」一路推到「整个结构体为什么过不了 spawn」。

手写 unsafe impl Send / unsafe impl Sync 属于高级操作：只有在你能证明类型内部的不变量跨线程仍成立时才可做，例如某些自带同步机制的自制容器。错误的手动实现会把数据竞争带进安全代码，责任完全由实现者承担，因此每个这样的 impl 都应附带详细的安全论证（第 13 单元展开）。

12.6 async fn 状态机：poll、Waker 与 Pin

async fn 并不会直接创建线程。编译器把它改写成一个实现 Future 的匿名状态机：每个 .await 都是一个状态切换点。当被等待的 Future 返回 Pending，状态机保存当前进度并让出执行权；恢复时从断点继续。所以 Future 是惰性的——没有任何人轮询它，它就永远停在第一个状态，连函数体第一行都不会执行。

Future::poll 的签名是 poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<T>。Context 里最关键的是 Waker：当 Future 无法立刻完成（比如等待 socket 可读），它应把 waker 注册到感兴趣的事件上，然后返回 Pending；事件就绪时，反应器调用 waker，执行器把任务重新放回就绪队列。忘记唤醒的 Future 会永远沉睡——这是手写 Future 最常见的 bug。

Pin 之所以出现，是因为这个状态机是自引用结构：某个字段可能持有指向自身另一个字段的指针。如果状态机被移动，指针就会悬空。Pin<&mut T> 保证一旦被固定，值就不会再被搬走；Box::pin 是最简单的固定方式。不要在 async 函数里对固定后的值做移动操作，编译器会拦住你。

下面的小程序用 std 手写了一个最小的轮询器。OncePending 第一次被轮询时调用 cx.waker().wake_by_ref() 并返回 Pending，第二次返回 Ready；执行器只是循环 poll，直到拿到结果。真跑输出 polls = 2, wakes = 1，把「轮询—唤醒—再轮询」的循环变成了可观察的数字。

rustRust · 标准库46 行
use std::future::Future;
use std::pin::Pin;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};
struct CountingWaker(AtomicUsize);
impl Wake for CountingWaker {
fn wake(self: Arc<Self>) { self.0.fetch_add(1, Ordering::SeqCst); }
fn wake_by_ref(self: &Arc<Self>) { self.0.fetch_add(1, Ordering::SeqCst); }
}
struct OncePending { polls: usize }
impl Future for OncePending {
type Output = &'static str;
fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
self.polls += 1;
if self.polls == 1 {
cx.waker().wake_by_ref();
Poll::Pending
} else {
Poll::Ready("done")
}
}
}
fn block_on<F: Future>(fut: F) -> (F::Output, usize, usize) {
let wakes = Arc::new(CountingWaker(AtomicUsize::new(0)));
let waker = Waker::from(Arc::clone(&wakes));
let mut cx = Context::from_waker(&waker);
let mut fut = Box::pin(fut);
let mut polls = 0;
loop {
polls += 1;
match fut.as_mut().poll(&mut cx) {
Poll::Ready(v) => return (v, polls, wakes.0.load(Ordering::SeqCst)),
Poll::Pending => continue,
}
}
}
fn main() {
let (value, polls, wakes) = block_on(OncePending { polls: 0 });
println!("value = {}, polls = {}, wakes = {}", value, polls, wakes);
}

async 函数里的局部引用可以跨越 .await 保存：编译器会在状态机里把它们作为字段存下来，因此 let r = &x; foo().await; use(r); 是合法的。代价是这类 future 通常不是 Send——引用指向的类型若不满足 Sync，跨线程迁移就不安全。async move 关键字强制把捕获的变量按值搬入状态机，常用于需要 'static 的任务。理解这一点后，tokio::spawn 要求 async move 块满足 Send + 'static 就不再是一条莫名其妙的限制，而是状态机能够安全跨线程调度的必要条件。

这个执行器里的 waker 只增加计数，不做真正的调度，因此真正会 Pending 的 IO Future 在这里会一直空转。这恰恰说明了运行时的价值：tokio 的 reactor 把 waker 与定时器、socket 就绪事件绑定，调度器负责把被唤醒的任务放回队列。不要在生产代码里手工轮询 Future，也不要在 async 代码里执行长时间阻塞调用——那会卡住整个工作线程，让同线程上的其他任务一起饿死。

12.7 tokio 实战：运行时、select! 与取消

验证工程 u12-async 用了真实的 tokio 运行时。依赖只开启需要的 feature：多线程运行时、宏、同步原语与定时器，避免把整个 full 拉进来。

#[tokio::main(flavor = "multi_thread", worker_threads = 2)] 展开后，大致是「构造一个多线程运行时，然后在它上面 block_on 主 future」。运行时内部有两类关键部件：每个工作线程维护一个可窃取（work stealing）的任务队列，空闲线程可以从别的线程那里偷活；还有一个 IO 驱动与定时器轮，负责在 socket 可读或时间到期时调用对应任务的 Waker。任务被唤醒后重新进入就绪队列，由某个工作线程 poll。理解这个模型后就能明白：阻塞工作线程的代价不只是慢，而是会让它无法去 poll 队列里其他任务；这与线程池里「一个线程卡住只影响自己的任务」很不一样。

tomlRust · 标准库2 行
[dependencies]
tokio = { version = "1", features = ["rt-multi-thread", "macros", "sync", "time"] }

主程序做三件事：生产者任务通过有界 mpsc 发送四个数字；消费者用 tokio::select! 同时等待消息与超时；最后用一个慢任务演示取消语义。消费者里的 Arc<tokio::sync::Mutex<u32>> 保存累加结果——注意这是异步锁，可以在 .await 前后持有而不会阻塞工作线程。

rustRust · 标准库59 行
use std::sync::Arc;
use std::time::Duration;
use tokio::sync::{mpsc, Mutex};
use tokio::time::{sleep, timeout, Instant};
async fn producer(tx: mpsc::Sender<u32>) {
for i in 1..=4u32 {
tx.send(i).await.unwrap();
sleep(Duration::from_millis(20)).await;
}
}
#[tokio::main(flavor = "multi_thread", worker_threads = 2)]
async fn main() {
let (tx, mut rx) = mpsc::channel::<u32>(8);
let p = tokio::spawn(producer(tx));
let counter = Arc::new(Mutex::new(0u32));
let c = Arc::clone(&counter);
let consumer = tokio::spawn(async move {
loop {
tokio::select! {
maybe = rx.recv() => match maybe {
Some(v) => {
let mut guard = c.lock().await;
*guard += v;
println!("recv {}", v);
}
None => {
println!("channel closed");
break;
}
},
_ = sleep(Duration::from_millis(300)) => {
println!("consumer timeout -> 退出");
break;
}
}
}
});
p.await.unwrap();
consumer.await.unwrap();
println!("total = {}", *counter.lock().await);
let mut slow = tokio::spawn(async {
sleep(Duration::from_millis(500)).await;
99
});
let start = Instant::now();
match timeout(Duration::from_millis(50), &mut slow).await {
Ok(res) => println!("slow finished: {:?}", res),
Err(_) => println!("timeout after {}ms", start.elapsed().as_millis()),
}
slow.abort();
println!("abort() 后立刻查询: {}", slow.is_finished());
sleep(Duration::from_millis(10)).await;
println!("让出一次后查询: {}", slow.is_finished());
}

最后三行是取消语义的核心。timeout 超时只意味着「不再等待这个任务」，并不自动终止它；必须调用 abort() 才会真正取消。abort() 发出请求后，任务要在下一次被调度时才真正结束，所以立刻查询 is_finished() 仍是 false，让出一次后才变成 true。更隐蔽的是取消安全：丢弃一个 Future 等于取消它，析构函数会运行，但「操作是否已生效」由业务决定——写文件写到一半被取消，可能留下半条记录。稳妥做法是先生成幂等键再写入，或用 tokio::select! 的 biased; 形式明确分支优先级，让取消点出现在可预期的位置。

坑这里最容易踩

坑：把 tokio::spawn 的 JoinHandle 直接丢弃就以为任务被取消了。实际上任务会继续在运行时里跑到结束，除非调用 abort()。另一个相关陷阱是在 async 任务里使用标准库的 std::sync::Mutex：临界区里的 .await 会阻塞工作线程，应当换成 tokio::sync::Mutex，或者更好的做法是重新设计数据流，让任务通过通道把结果交给单一所有者，干脆不需要锁。

12.8 并发代码的审查清单与取舍

并发 bug 往往只在特定调度交错下出现，一次绿灯不能说明任何问题。审查顺序建议固定为：先找共享点，再确认每个共享点由谁负责同步，最后检查所有等待路径是否会形成环。join 的 panic 传播、lock 的中毒状态、通道关闭后的收尾逻辑，都是极易遗漏的环节。测试方面，关键用例要在 CI 中多次重复运行，并结合压力测试观察，而不是靠一次通过就放心。

选择同步原语时，可以按下面的顺序自问：能不能通过消息传递把状态交给单一所有者？如果能，优先用通道，推理成本最低。如果不能，共享的是不是一个简单值？是的话用原子，按需要选择最弱但正确的内存序。只有当临界区里涉及多个字段、需要保持复合不变量时，才使用 Mutex。每升级一档，调试难度与死锁风险都会上升，而性能未必更好——锁争用严重时，原子或通道方案往往反而更快。

线程模型的选择同样要基于测量：多线程运行时能利用多核，适合 CPU 与 IO 混合的负载；单线程运行时没有跨线程共享开销，适合大量轻量 IO 任务。无论哪种，都要用真实负载压测后再定，而不是凭「多线程听起来更快」。
