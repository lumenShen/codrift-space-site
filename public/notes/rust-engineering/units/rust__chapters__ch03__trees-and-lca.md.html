22.1 树问题的图论化：邻接表、选根与迭代 DFS

树只是边数恰好为 n−1 的连通无向图，所以处理树的第一步与处理图完全一样：建邻接表。Vec<Vec<usize>> 的第 u 个内层向量存 u 的所有邻居，无向边要往两个方向各 push 一次。树的编号若来自题目的 1 基输入，读入时统一减一转成 0 基，否则 0 号位置浪费、n 号位置越界。与邻接矩阵相比，邻接表是 O(n+m) 空间，在树上就是 O(n)，这是后面所有线性预处理的前提。

为什么一定要"选根"？树本身没有父子，但祖先、深度、子树这些概念都依赖一个固定的根。一旦选定 root，把每条边按"离根更近的一端是父"定向，树就变成一棵有根树。实现上不需要真的改邻接表，只要一个 parent 数组：从 root 出发遍历，遇到未访问的点 v 就记 parent[v] = u。root 自己的父设成它自己（哨兵），这样往上跳永远不会越界，这是后面倍增表能直接用下标访问的关键技巧。

遍历必须写成迭代版。Rust 主线程栈默认只有几 MB，一条十万节点的链用递归 DFS 会直接 stack overflow，而且这是发布模式也躲不掉的运行时崩溃。迭代版用一个 Vec<usize> 当栈：弹出 u 就算访问，把 u 的所有"非父邻居"入栈并在入栈时写好父与深度。注意标记时机——在入栈时确定 parent[v]，而不是出栈时再判断，否则同一节点的多个邻居可能把它重复入栈。

建表阶段还有两个容易被忽略的工程细节。其一，vec![Vec::new(); n] 会为 n 个内层 Vec 各做一次分配，边数很大时这些小块在堆上分散，遍历邻居时缓存命中率不如扁平数组；若边数达到百万级，可改用前向星——一个 to 数组加一个 next/head 数组把所有邻接边连续存放。对 n 不过十万的树题，邻接表的简洁性更值钱，知道优化存在即可。其二，若输入给的是 1 基编号，读入时统一 u -= 1; v -= 1，不要在算法内部到处减一：内部下标约定保持 0 基，能让所有 parent/depth 的哨兵与循环边界保持统一，减少一类最常见的越界错误。

大白话先用直觉把它讲通

树就是一张没有环的地图。先随便挑一个"首都"（根），每个城市就天然有了"上级"和"下级"。迭代 DFS 像派人挨个下乡登记户口：每到一个城市就写下它归谁管、离首都多远。用显式栈而不是递归，是因为递归相当于让派人的人一层层站在前一个人肩膀上，链太长就站不下去了。

fn build_tree(n: usize, edges: &[(usize, usize)]) -> Vec<Vec<usize>> {
let mut g = vec![Vec::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
g
}
struct Rooted {
parent: Vec<usize>,
depth: Vec<usize>,
order: Vec<usize>,
size: Vec<usize>,
}
fn root_tree(g: &[Vec<usize>], root: usize) -> Rooted {
let n = g.len();
let mut parent = vec![n; n];
let mut depth = vec![0usize; n];
let mut order = Vec::with_capacity(n);
parent[root] = root;
let mut st = vec![root];
while let Some(u) = st.pop() {
order.push(u);
for &v in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
st.push(v);
}
}
let mut size = vec![1usize; n];
for &u in order.iter().rev() {
if u != root {
size[parent[u]] += size[u];
}
}
Rooted { parent, depth, order, size }
}
fn main() {
let edges = [(0usize, 1usize), (1, 2), (1, 3), (3, 4), (3, 5)];
let g = build_tree(6, &edges);
let r = root_tree(&g, 0);
println!("parent = {:?}", r.parent);
println!("depth = {:?}", r.depth);
println!("order = {:?}", r.order);
println!("size = {:?}", r.size);
}

22.2 一次遍历的四份产物：父指针、深度、后序与子树大小

上面的 root_tree 同时产出四样东西，理解它们的依赖关系比背代码更重要。parent 与 depth 在入栈时就能确定；order 是出栈顺序，它是一份合法的先序（根在孩子前），因为只有先弹出 u 才会把 u 的孩子压栈。子树大小 size 则相反，必须等孩子都算完才能累加：把 order 倒过来遍历，size[u] 已经包含 u 的所有后代，此时把它加给 parent[u] 即可。这种"先正序收集、再逆序汇总"的两段式是树上聚合的标准套路。

正确性来自归纳：对 order 逆序的位置 i，假设所有在 i 之后出现的点（即 u 的后代）的 size 已正确，那么把每个孩子的 size 累加进 u 就得到完整子树大小。根没有父，if u != root 这个判断同时避免了给哨兵 parent[root] = root 重复计数。若题目需要在树上做"子树求和"，只要把 size 换成 value[u] += Σ value[child] 即可。

下面的图把样例树和四份产物放在一起看。注意 order 不是唯一的：栈是后进先出，把邻居入栈的顺序不同会得到不同的 order，但只要满足"父在孩子前"，逆序汇总就一定正确。

复杂度上，每个点入栈一次、出栈一次，每条边在两个端点各被检查一次，建表和遍历都是 O(n)；order 用 Vec::with_capacity(n) 预分配，避免中途扩容搬移。若输入不保证连通（严格说 n 个点 n−1 条边的图若连通才是树），需要先判断 order.len() == n，否则应报错而不是默默给出错误的 size。

把 size 换成一般聚合时，同样要注意运算是否满足交换律与结合律：求和、计数、最大值都可以直接套用"孩子结果合并到父"的框架，而涉及"必须先知道父的取值再算孩子"的问题（例如换根 DP）就需要两遍遍历。order 这份先序序列在两遍遍历里都能复用：第一遍用它的逆序做自底向上的子树聚合，第二遍再按它的正序把父方向的贡献传递下去。这也是为什么 22.3 的倍增表构造坚持用显式栈收集遍历顺序，而不是只维护一个父指针数组。

坑这里最容易踩

坑：迭代 DFS 里"跳过父节点"依赖 parent[u] 已经填好。如果图里存在环（比如误把普通图当树处理），同一个非父邻居会被从两条路径重复入栈，parent 被覆盖、size 累加两次。树的输入应当在建图时校验边数为 n−1 且遍历覆盖全部节点；对一般图必须另加 visited 数组，不能只靠 parent 判重。

22.3 倍增表的不变量：为什么跳 2ᵏ 能拆成两次跳 2ᵏ⁻¹

最近公共祖先（LCA）的朴素做法是"较深的点一步步上抬到同深，再一起一步步走"，单次查询 O(n)。倍增（binary lifting）把"一步步走"预计算成"按 2 的幂跳"：定义 up[k][v] 为 v 的第 2ᵏ 代祖先。这个定义的不变量是：k=0 时 up[0][v] 就是父节点；对 k≥1，先跳 2ᵏ⁻¹ 到达 m = up[k-1][v]，再从 m 跳 2ᵏ⁻¹，正好是 2ᵏ 代祖先，即 up[k][v] = up[k-1][up[k-1][v]]。

层数 log 取满足 2^log > n 的最小值，循环写成 while (1usize << log) <= n { log += 1 }。up 表初始化为 vec![vec![root; n]; log]，让所有"跳过了根"的位置都落在根上——这消掉了边界判断：即使从深度 2 的点跳 8 步，也不会越界访问不存在的祖先。第一次 DFS 填 up[0] 和 depth，之后按 k 从小到大填表，因为 up[k] 只依赖已经算好的 up[k-1]。预处理 O(n log n)，空间 O(n log n)；对 n=10⁵，log≈17，两张表各约 1.7×10⁶ 个 usize，十几 MB，完全可接受。

正确性可以用对 k 的归纳严格写出：k=0 时 up[0][v] 是父，跳 1=2⁰ 步成立；假设对所有小于 k 的层成立，则从 v 先跳 2ᵏ⁻¹ 到 m，再从 m 跳 2ᵏ⁻¹ 到 up[k-1][m]，两次合计 2ᵏ 步，且第二次起点 m 的祖先信息由归纳假设保证正确。填表顺序恰好与归纳顺序一致，这就是循环必须让 k 从 1 递增到 log−1 的原因；若反过来从大到小填，up[k-1] 还未就绪，会读到初始化值 root，整张表就全错了。

倍增的本质是二进制分解：任意不超过 n 的步数都能写成若干个 2 的幂之和，于是"走 diff 步"最多只需 log 次表查询。这与快速幂的思想同源，up 表就是"幂"的预计算版本。层数 log 的循环用移位而不是 n.ilog2()，好处是对 n=1 也得到 log=1：此时表中只有一层，根的自环哨兵保证查询不会访问不存在的层。若 n 接近 usize::BITS 的上限，1usize << log 会溢出，但竞赛与工程中 n 通常远小于 2⁶³，这个循环是安全的。预处理两重循环的复杂度是 O(log n × n)，把外层 k 放外面、内层 v 放里面，是按行连续访问 up[k]，对缓存更友好。

struct Lca {
up: Vec<Vec<usize>>,
depth: Vec<usize>,
}
impl Lca {
fn new(n: usize, edges: &[(usize, usize)], root: usize) -> Self {
let mut g = vec![Vec::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
let mut log = 1usize;
while (1usize << log) <= n {
log += 1;
}
let mut up = vec![vec![root; n]; log];
let mut depth = vec![0usize; n];
let mut parent = vec![n; n];
parent[root] = root;
let mut st = vec![root];
while let Some(u) = st.pop() {
for &v in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
up[0][v] = u;
st.push(v);
}
}
for k in 1..log {
for v in 0..n {
up[k][v] = up[k - 1][up[k - 1][v]];
}
}
Lca { up, depth }
}
fn lca(&self, mut a: usize, mut b: usize) -> usize {
if self.depth[a] < self.depth[b] {
std::mem::swap(&mut a, &mut b);
}
let diff = self.depth[a] - self.depth[b];
for k in 0..self.up.len() {
if ((diff >> k) & 1) == 1 {
a = self.up[k][a];
}
}
if a == b {
return a;
}
for k in (0..self.up.len()).rev() {
if self.up[k][a] != self.up[k][b] {
a = self.up[k][a];
b = self.up[k][b];
}
}
self.up[0][a]
}
}
fn main() {
let edges = [(0usize, 1usize), (1, 2), (1, 3), (3, 4), (3, 5)];
let lca = Lca::new(6, &edges, 0);
for &(a, b) in &[(2usize, 4usize), (0, 5), (4, 5), (2, 2)] {
println!("lca({}, {}) = {}", a, b, lca.lca(a, b));
}
}

22.4 LCA 查询的两阶段：先对齐深度，再同步上跳

查询分两阶段，每阶段都有清晰的不变量。第一阶段把深度大的点抬到与另一个同深：先交换保证 depth[a] >= depth[b]，于是 diff = depth[a] - depth[b] 在 usize 上不会下溢；再把 diff 按二进制拆开，第 k 位为 1 就让 a 跳 2ᵏ。因为每次跳都精确消耗 diff 的一个二进制位，循环结束时 depth[a] == depth[b] 必然成立。若此时 a == b，说明其中一个点就是另一个的祖先，答案直接是 a。

第二阶段从最大的 k 往下枚举：若 up[k][a] != up[k][b]，说明还处于 LCA 之下（甚至已经跳过它但两边祖先不同），可以让两点同时跳 2ᵏ；若相等，说明这一跳会越过或正好落到 LCA，必须保守地不跳。循环结束后 a、b 同深且是兄弟（或同点），它们的父就是 LCA。为什么最后返回 up[0][a] 而不是 a？因为第二阶段保持了"a、b 始终不是同一点"的不变量（相等时已提前返回），而它们的父第一次汇合，正是 LCA；若直接返回 a，会把 LCA 的孩子误当答案。

坑这里最容易踩

坑：depth[a] - depth[b] 必须先用 swap 保证 a 更深，否则 usize 下溢会 panic；枚举 k 时必须从大到小，若从小到大则 up[k] 的"大步"信息会被过早用过的小步破坏，结果不再是最小跳跃组合。样例里 lca(2,2)=2 覆盖了"提前返回"分支，别漏测。

把样例中的 lca(4,5) 手推一遍能巩固不变量：深度都是 3，diff=0，第一阶段不动；k 从大到小尝试，k=1 时两者的祖父都是 0，相等跳过；k=0 时 up[0][4]=3、up[0][5]=3 也相等，继续跳过；循环结束返回 up[0][4]=3，正确。再看 lca(2,4)：先把 4 抬到深度 2 得到 3，此时 2 与 3 深度相同但不是同点；k=1 时两者的祖父都是 0，相等跳过；k=0 时 up[0][2]=1、up[0][3]=1 相等跳过；返回 up[0][2]=1。注意"相等就跳过"看起来保守，却保证了不会误降到 LCA 以下，这正是算法正确性的核心。这两次手推还说明，第一阶段只移动较深的那个点，不会改变两点真正的公共祖先；若实现里把两点同时抬升，就会破坏这个前提。

22.5 带权树的距离：把边权一起倍增

若树边带权，树上两点距离公式是 dist(a,b) = d(a) + d(b) − 2·d(lca)，其中 d(v) 是根到 v 的带权距离。这个公式把问题归约回 LCA：只要能求 LCA，再维护每个点到根的距离即可。但还有一个常见需求是"从 v 向上走 k 步的边权和"，例如在路径上加数据时，这时需要把 up_w[k][v] 也倍增：up_w[k][v] = up_w[k-1][v] + up_w[k-1][up[k-1][v]]，含义是先跳 2ᵏ⁻¹ 的代价加上后半段的代价。

up_w 的初始化在建树 DFS 时完成：up_w[0][v] = w(u,v)，同时 dist_root[v] = dist_root[u] + w。三种信息同一次遍历得到，没有额外复杂度。distance 用根距离公式；climb 用与 LCA 相同的二进制拆解，只是每跳一步把对应 up_w[k][v] 累加进 cost。注意 usize 下标与 i64 权值混用时，增量先加到 i64 变量上再更新 v，顺序不能颠倒——否则会拿新位置的 up_w 去索引，得到错误代价。

大白话先用直觉把它讲通

带权树上问"两点相距多远"，不用真的把路径走一遍。从根到 a、从根到 b 各有一条路，它们前面一段是重合的，重合段正好走到 LCA。把两段全长相加、再减去两倍重合段，剩下的就是 a 到 b 的独有部分，也就是答案。倍增表多存一份"每跳 2ᵏ 步累计多少路费"，就能顺带回答"往上走若干步花了多少"。

struct WeightedLca {
up: Vec<Vec<usize>>,
up_w: Vec<Vec<i64>>,
depth: Vec<usize>,
dist_root: Vec<i64>,
}
impl WeightedLca {
fn new(n: usize, edges: &[(usize, usize, i64)], root: usize) -> Self {
let mut g = vec![Vec::<(usize, i64)>::new(); n];
for &(u, v, w) in edges {
g[u].push((v, w));
g[v].push((u, w));
}
let mut log = 1usize;
while (1usize << log) <= n {
log += 1;
}
let mut up = vec![vec![root; n]; log];
let mut up_w = vec![vec![0i64; n]; log];
let mut depth = vec![0usize; n];
let mut dist_root = vec![0i64; n];
let mut parent = vec![n; n];
parent[root] = root;
let mut st = vec![root];
while let Some(u) = st.pop() {
for &(v, w) in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
dist_root[v] = dist_root[u] + w;
up[0][v] = u;
up_w[0][v] = w;
st.push(v);
}
}
for k in 1..log {
for v in 0..n {
up[k][v] = up[k - 1][up[k - 1][v]];
up_w[k][v] = up_w[k - 1][v] + up_w[k - 1][up[k - 1][v]];
}
}
WeightedLca { up, up_w, depth, dist_root }
}
fn lca(&self, mut a: usize, mut b: usize) -> usize {
if self.depth[a] < self.depth[b] {
std::mem::swap(&mut a, &mut b);
}
let diff = self.depth[a] - self.depth[b];
for k in 0..self.up.len() {
if ((diff >> k) & 1) == 1 {
a = self.up[k][a];
}
}
if a == b {
return a;
}
for k in (0..self.up.len()).rev() {
if self.up[k][a] != self.up[k][b] {
a = self.up[k][a];
b = self.up[k][b];
}
}
self.up[0][a]
}
fn distance(&self, a: usize, b: usize) -> i64 {
let c = self.lca(a, b);
self.dist_root[a] + self.dist_root[b] - 2 * self.dist_root[c]
}
// 沿父链向上走 steps 步，返回落点与累计边权（展示 up_w 的用法）
fn climb(&self, mut v: usize, steps: usize) -> (usize, i64) {
let mut cost = 0i64;
for k in 0..self.up.len() {
if (steps >> k) & 1 == 1 {
cost += self.up_w[k][v];
v = self.up[k][v];
}
}
(v, cost)
}
}
fn main() {
let edges = [
(0usize, 1usize, 3i64), (1, 2, 4), (1, 3, 2),
(3, 4, 5), (3, 5, 1),
];
let t = WeightedLca::new(6, &edges, 0);
for &(a, b) in &[(2usize, 4usize), (0, 5), (2, 5), (4, 4)] {
println!("dist({}, {}) = {}", a, b, t.distance(a, b));
}
println!("climb(4, 2) = {:?}", t.climb(4, 2));
}

手验一条：dist(2,4) 中 LCA 是 1，d(2)=3+4=7，d(4)=3+2+5=10，d(1)=3，所以 7+10−2×3=11，与输出一致。负值边权在这个框架里同样成立（只要不溢出 i64），这是它比"依赖深度差"的朴素做法更通用之处。

为什么不用每次查询现爬父链累加边权？那是 O(n) 的，而 up_w 把累加也倍增了，单次 O(log n)。需要留意两点：一是 dist_root 与 up_w 都要用 i64，若权值总和可能超过 2³¹ 甚至 2⁶³，必须先估算上界再选类型；二是题目若要求"路径上的最大边权"而非总和，把递推里的加法换成 max 即可，up_w[k][v] = max(up_w[k-1][v], up_w[k-1][up[k-1][v]])，框架完全不变。这个"把运算符换掉、结构照搬"的特性，是倍增表比欧拉序 RMQ 更通用之处：RMQ 只能回答最小值查询，倍增却能承载任意可结合运算。

22.6 欧拉序 + 稀疏表：O(1) 查询的代价是 2n−1 长的数组

另一条 LCA 路线建立在欧拉序上：从根出发 DFS，第一次到达 v 时记 first[v]，此后每次从某个孩子返回到 v 时再记一次 v；整条序列长度恰为 2n−1。直觉是：在 first[a] 与 first[b] 之间的欧拉子序列里，深度最小的点恰好是 LCA(a,b)——因为 DFS 走到 a 子树再走到 b 子树，必然在两处之间"浮"到它们汇合的最高处。于是 LCA 查询变成区间最小值（RMQ）。

RMQ 用稀疏表：预处理 st[k][i] 为欧拉序区间 [i, i+2ᵏ) 内深度最小的下标，合并两段用 min(深度) 比较。lg[i] = lg[i/2] + 1 一次性预处理，查询 [l,r] 取 k = lg[r−l+1]，答案是两段重叠区间的最小值之一。预处理 O(n log n)，单次查询 O(1)。注意欧拉序数组下标是 usize，r - (1<<k) + 1 在 Rust 里先算减法会下溢，必须写成 r + 1 - (1<<k)，这是真实会 panic 的坑。

坑这里最容易踩

坑有两处，笔者实跑都踩到过。其一：迭代模拟 DFS 的欧拉序时，父节点必须在每从一个孩子返回时追加一次；如果只在整帧弹出时追加，序列里会缺失中间的父节点，LCA 结果偏深。其二：稀疏表查询的下标 r - len + 1 要用加法优先的写法。两个 bug 都不会被编译期发现，靠 22.7 的随机对拍才稳。

稀疏表的构造同样可用归纳验证：st[0][i] 就是单点；st[j][i] 覆盖长度 2ʲ 的区间，拆成左右两个长度 2ʲ⁻¹ 的区间，取两者深度较小者即整体最小，因为两个区间恰好拼成原区间且互不重叠。查询时取长度为 2ᵏ 的两段覆盖 [l,r]（允许重叠），重叠不影响最小值结果。lg 数组的递推 lg[i] = lg[i/2] + 1 只依赖更小的 i，一趟从 2 扫到 m 即可；避免对每个查询调用浮点 log2 再取整，既快又无精度隐患。若查询多到还要压缩常数，可进一步用 Cartesian 树加 ±1 RMQ 把空间降到 O(n)，但实现复杂度陡增，除非确实卡内存否则不建议。

struct EulerLca {
node: Vec<usize>,
euler_depth: Vec<usize>,
first: Vec<usize>,
lg: Vec<usize>,
st: Vec<Vec<usize>>,
}
impl EulerLca {
fn new(n: usize, edges: &[(usize, usize)], root: usize) -> Self {
let mut g = vec![Vec::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
let mut depth = vec![0usize; n];
let mut parent = vec![n; n];
parent[root] = root;
let mut node = Vec::with_capacity(2 * n - 1);
let mut first = vec![0usize; n];
first[root] = 0;
node.push(root);
// 帧 (当前点, 下一个孩子下标)，显式模拟递归的进入/返回
let mut frames: Vec<(usize, usize)> = vec![(root, 0)];
while let Some((u, idx)) = frames.last_mut() {
let (u, idx) = (*u, *idx);
if idx < g[u].len() {
frames.last_mut().unwrap().1 += 1;
let v = g[u][idx];
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
first[v] = node.len();
node.push(v);
frames.push((v, 0));
} else {
frames.pop();
if let Some(&(p, _)) = frames.last() {
node.push(p); // 每从一个孩子返回，就记录一次父节点 p
}
}
}
let m = node.len();
let euler_depth: Vec<usize> = node.iter().map(|&v| depth[v]).collect();
let mut lg = vec![0usize; m + 1];
for i in 2..=m {
lg[i] = lg[i / 2] + 1;
}
let k = lg[m] + 1;
let mut st = vec![vec![0usize; m]; k];
st[0] = (0..m).collect();
for j in 1..k {
let half = 1usize << (j - 1);
let len = half * 2;
for i in 0..=m - len {
let x = st[j - 1][i];
let y = st[j - 1][i + half];
st[j][i] = if euler_depth[x] <= euler_depth[y] { x } else { y };
}
}
EulerLca { node, euler_depth, first, lg, st }
}
fn lca(&self, a: usize, b: usize) -> usize {
let l = self.first[a].min(self.first[b]);
let r = self.first[a].max(self.first[b]);
let k = self.lg[r - l + 1];
let x = self.st[k][l];
let y = self.st[k][r + 1 - (1usize << k)];
let idx = if self.euler_depth[x] <= self.euler_depth[y] { x } else { y };
self.node[idx]
}
}
fn main() {
let edges = [(0usize, 1usize), (1, 2), (1, 3), (3, 4), (3, 5)];
let e = EulerLca::new(6, &edges, 0);
println!("euler = {:?}", e.node);
println!("first = {:?}", e.first);
for &(a, b) in &[(2usize, 4usize), (0, 5), (4, 5)] {
println!("lca({}, {}) = {}", a, b, e.lca(a, b));
}
}

欧拉序的稀疏表比倍增多占约一倍内存（m≈2n，且要存下标与深度），但查询是常数时间。若树是静态且查询极多（几十万次），这个交换很划算；若树会动态加点，倍增表尚可增量维护，RMQ 则基本要重做，这时应选倍增。

22.7 随机对拍：xorshift 生成树与暴力爬树互证

LCA 的正确性很难靠几个样例穷尽，尤其是"一个是另一个祖先""两点同点""深链跳越根"这些分支。随机对拍的思路：用一个 std-only 的 xorshift 生成器造随机树——令节点 i 的父节点在 [0, i) 中随机选，i 从 1 到 n−1，这样必然得到一棵以 0 为根的连通树；再随机出查询对，把倍增实现与"一步步爬父链"的暴力实现对照。暴力实现的正确性几乎显然，所以两者不一致时几乎一定是倍增实现有 bug。

xorshift 的核心是三个异或移位，种子必须非零；below(n) 用取模映射到 [0,n)，对测试足够均匀。对拍规模设为 3000 棵树、每棵 20 个查询、n 在 2..=30：树小意味着暴力便宜，数量多意味着分支覆盖广。每棵树只用一次预处理、多次查询，正好符合真实使用场景。任何不一致都会打印细节，最后用计数器汇总。

生成器的正确性值得单独说明：令第 i 个点的父节点从 [0,i) 中选，i 从 1 递增，则每个新点都连向一个已存在的点，不可能成环，且最终所有点都与 0 连通，边数恰为 n−1，因此必然是一棵树。随机性只体现在树的形状上，不破坏这个结构保证。种子固定为常数让每次运行结果可复现——对拍一旦失败，你能用同一个种子重现现场再打印细节，而不是靠运气碰 bug。若要把带权距离也纳入对拍，只需在生成边时附带小随机权值，再用"暴力沿父链累加"的对照实现即可，框架不变。

struct Rng(u64);
impl Rng {
fn next(&mut self) -> u64 {
let mut x = self.0;
x ^= x << 13;
x ^= x >> 7;
x ^= x << 17;
self.0 = x;
x
}
fn below(&mut self, n: usize) -> usize {
(self.next() % n as u64) as usize
}
}
fn build_lca(n: usize, edges: &[(usize, usize)]) -> (Vec<Vec<usize>>, Vec<usize>) {
let mut g = vec![Vec::new(); n];
for &(u, v) in edges {
g[u].push(v);
g[v].push(u);
}
let mut log = 1usize;
while (1usize << log) <= n {
log += 1;
}
let mut up = vec![vec![0usize; n]; log];
let mut depth = vec![0usize; n];
let mut parent = vec![n; n];
parent[0] = 0;
let mut st = vec![0usize];
while let Some(u) = st.pop() {
for &v in &g[u] {
if v == parent[u] {
continue;
}
parent[v] = u;
depth[v] = depth[u] + 1;
up[0][v] = u;
st.push(v);
}
}
for k in 1..log {
for v in 0..n {
up[k][v] = up[k - 1][up[k - 1][v]];
}
}
(up, depth)
}
fn lca(up: &[Vec<usize>], depth: &[usize], mut a: usize, mut b: usize) -> usize {
if depth[a] < depth[b] {
std::mem::swap(&mut a, &mut b);
}
let diff = depth[a] - depth[b];
for k in 0..up.len() {
if ((diff >> k) & 1) == 1 {
a = up[k][a];
}
}
if a == b {
return a;
}
for k in (0..up.len()).rev() {
if up[k][a] != up[k][b] {
a = up[k][a];
b = up[k][b];
}
}
up[0][a]
}
fn brute(parent: &[usize], depth: &[usize], mut a: usize, mut b: usize) -> usize {
while depth[a] > depth[b] {
a = parent[a];
}
while depth[b] > depth[a] {
b = parent[b];
}
while a != b {
a = parent[a];
b = parent[b];
}
a
}
fn main() {
let mut rng = Rng(0x9E3779B97F4A7C15);
let mut trees = 0usize;
let mut queries = 0usize;
let mut bad = 0usize;
for _ in 0..3000 {
let n = 2 + rng.below(29); // 2..=30
let mut parent = vec![0usize; n]; // parent[0] 占位
let mut edges = Vec::with_capacity(n - 1);
for i in 1..n {
let p = rng.below(i);
parent[i] = p;
edges.push((i, p));
}
let (up, depth) = build_lca(n, &edges);
for _ in 0..20 {
let a = rng.below(n);
let b = rng.below(n);
let fast = lca(&up, &depth, a, b);
let slow = brute(&parent, &depth, a, b);
queries += 1;
if fast != slow {
bad += 1;
if bad <= 3 {
println!("MISMATCH n={} ({},{}) fast={} slow={}", n, a, b, fast, slow);
}
}
}
trees += 1;
}
println!("trees={} queries={} mismatches={}", trees, queries, bad);
if bad == 0 {
println!("RESULT: PASS");
}
}

6 万组随机查询零分歧，覆盖了链、星形与随机分叉树。读对拍结果时不要只看最后的 PASS：若出现 MISMATCH，打印的 n 与两点编号能让你用同一随机种子重放现场，先把最小复现规模缩小，再逐步打印 up 表与深度去定位是建表错还是查询错。对拍的价值在于：它不需要你事先知道正确答案，只需要一个"慢但显然对"的对照。把同样的方法用在 22.6 的欧拉序实现上（把 lca 换成该实现的查询），就能在改代码时持续守住正确性。

22.8 工程取舍：预计算 log、内存布局与方法选择

三种方案没有绝对优劣，只有场景匹配。倍增胜在代码短、可在线扩展、附带"跳 k 步"能力；欧拉序加 RMQ 胜在查询 O(1)；朴素爬树胜在零预处理，适合一次性查询。下表把关键维度列在一起，实际选型先看查询量与树的静态性。

还有一个常被问到的取舍是"是否把查询并行化"。倍增表构造完成后是只读的，Lca 结构体不含可变引用，可以安全地用 std::thread::scope 把查询切片分给多个线程，各自调用 lca 再汇总；Rust 的类型系统在这里替你守住了数据竞争防线。相比之下，欧拉序方案的稀疏表同样是只读的，也能并行。真正的瓶颈往往是建表而非查询，所以除非查询量极大，先把单线程版本写对更实际。

方案 预处理 单次查询 额外空间 动态加点 适合场景
朴素爬父链 O(n) O(n) O(n) 容易 查询极少
倍增 O(n log n) O(log n) O(n log n) 较容易 通用默认
欧拉序 + RMQ O(n log n) O(1) O(n log n) 困难 静态树海量查询

实现层面还有三点值得固化成习惯。第一，log 层数一次性算好并作为参数传入，避免每次查询重新算 ilog2 或在循环边界反复调用；Rust 的 usize::ilog2 可用，但把层数存下来更直观。第二，up 用 Vec<Vec<usize>> 时外层是 k、内层是 v，查询时对固定 k 访问不同 v 会跨内层跳转；若追求极致缓存，可换成扁平 Vec<usize> 按 k*n+v 索引，代价是可读性下降。第三，根不一定总是 0：把 root 作为构造函数参数，所有哨兵用 root 而非硬编码 0，代码换场景时无需改动。
