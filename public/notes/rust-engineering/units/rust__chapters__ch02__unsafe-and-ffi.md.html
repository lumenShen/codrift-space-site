13.1 unsafe 解锁了什么，又没解锁什么

很多初学者把 unsafe 理解成"关闭借用检查器的开关"，这是最危险的误解。准确的说法是：unsafe 只额外允许五件事——解引用裸指针、调用 unsafe 函数、访问可变静态变量、实现 unsafe trait、读取 union 字段。类型系统的其余部分照常工作：类型检查、trait 解析、生命周期检查、模式匹配的穷尽性一个都不会少。写 unsafe 不能让一个类型错误凭空消失，它只是把一部分安全责任从编译器转移到人身上。在 2021 edition 里，整个 unsafe 函数体默认处于"特权模式"；从 2024 edition 起，函数内部也必须逐个写出 unsafe 块，目的就是让每一处特权操作都留痕。

真正需要敬畏的是未定义行为（undefined behavior，UB）。安全 Rust 的承诺是"良构程序不会触发 UB"，编译器和优化器都建立在这个前提上。一旦违约，优化器就有权做任意事情：删掉它认为不可能走的分支、把两次读取合并成一次、甚至让整个函数在数学上等价于任意结果。举个具体的例子：如果你先通过裸指针写入，又用一个已经失效的 &mut 读取，优化器可以依据"可变引用独占"这条前提推断两次访问不可能重叠，于是把你的写入重排到读取之后——程序在测试机上看似正常，发布版却给出错误答案。更麻烦的是 UB 常常不在现场暴露：栈回溯往往指向完全无关的位置，因为破坏发生在优化阶段而非运行阶段。

大白话先用直觉把它讲通

unsafe 像医院里的特殊药品。它不会让你变成医生，只是允许你在有明确处方时使用；处方上必须写适用条件和剂量，否则出了事没人能帮你追溯。安全 Rust 是"编译器替你守门"，unsafe 是"你亲自签名守门"，签名意味着出事时第一个被追问的是你。

这里还要区分两个词：unsafe 代码和 unsound 代码。unsafe 只是"编译器不替你证明"，unsound 才是"实际上违反了前提"。一段 unsafe 代码可以完全 sound，标准库里到处都是；一个没有写任何 unsafe 的 safe 函数也可能因为逻辑错误产生错误结果，但那只是 bug，不是 UB。判断标准是抽象的边界：一个模块如果对外只暴露安全 API，且无论调用方怎么调用都不会触发 UB，那它就是可靠的安全抽象。编写 unsafe 的目标，就是尽快回到这个状态——把危险关进盒子，给外面一个普通的函数签名。

因此审查 unsafe 代码的标准不是"测试通过了没有"，而是"能否在纸上证明它的前提成立"。标准库里大量 unsafe 实现都配有长篇注释，那些注释记录的不是操作说明，而是证明过程：为什么这里的指针一定有效、为什么此刻不存在别名、为什么这段内存一定已初始化。写不出这种注释，通常说明抽象层次选错了，应当退回安全 API 重新设计。

一个实用的心智模型是"责任账本"：每出现一个 unsafe 块，就相当于向账本借了一笔，借款人必须在注释里写明还款计划，也就是前提由谁保证。审计时顺着账本往前追，任何一笔找不到保证来源的借款都算坏账。这个模型也解释了为什么在 unsafe 函数里嵌套多层 unsafe 块是坏味道——借款人变成了模糊的"整个函数"，责任被摊薄后没人能说清哪条前提对应哪次使用。

13.2 裸指针、别名规则与来源

裸指针 *const T 和 *mut T 与引用有本质区别：引用是一个保证——非空、对齐、指向有效值、遵守别名规则；裸指针只是一个地址，这些保证一个都不带。你可以对裸指针做加减、比较、判空，但解引用必须进入 unsafe。裸指针也不参与生命周期检查，因此一个指向已释放内存的指针在类型层面没有任何异常，这正是它危险的地方。

别名规则是理解 UB 的关键。共享引用 &T 允许同时存在很多个，但同一时刻不能有任何可变引用指向同一位置；&mut T 保证独占，因此不能与别的引用重叠。裸指针本身不受这套规则约束，但一旦解引用，就必须像对应的引用一样满足独占性。经典错误是同时持有两个 *mut 并交错写入，或者在一个 &mut 还活着时通过裸指针写入——优化器会依据"可变引用独占"做重排，于是你的写入可能被认为"不可能发生"而被优化掉。别名模型的细节（Stacked Borrows / Tree Borrows）至今仍在演进，这也提醒我们：不要写"踩在规则边缘"的代码，要给优化器留出明确的余地。

还有一个容易被忽视的概念叫来源（provenance）。指针不只是整数地址，它还携带着"从哪个分配而来"的信息。一个由已释放的 Vec 得到的指针，即使数值地址看起来仍然合理、甚至恰好指向一块新分配的内存，也不能再用来访问——它的来源已经失效。这也是为什么把指针转成 usize 再转回来在很多平台上并不可靠，跨 FFI 边界时尤其如此。实践中的防线很简单：尽量让函数参数接收 &[T] 或 &mut [T]，让借用检查器替你守住有效期，只有在与硬件或外部库交互时才退回到裸指针。

另一个实用细节是 ptr::addr_of! 与 addr_of_mut!：它们可以在不创建引用的前提下取得字段的裸指针。这一点对未初始化内存至关重要，因为"取一个引用"本身就要求目标已经是有效值，即使你并不解引用它。需要用裸指针读写 MaybeUninit 的字段时，应当用这两个宏而不是 &/&mut。至于指针运算，add 以元素为单位且要求结果仍在同一个分配内（否则 UB），offset 以字节为单位；越过分配末尾即使不解引用也可能 UB，因此边界判断必须在指针运算之前完成。

标准库还提供 NonNull<T>，它是"非空裸指针"的包装，既保留了裸指针的灵活性，又把判空这件事交给类型系统。很多安全抽象内部都用它来表示"我持有指向有效对象的指针，但暂不借用"。需要表达"可能为空"的外部指针时，用 Option<NonNull<T>> 让空值显式化，而不是在裸指针上到处写 is_null()。这种写法能把一部分契约从注释提升到类型，是减少审查负担的有效手段。指针转换方面，cast 用于改变指向类型，as_ptr/as_mut_ptr 用于从切片或 MaybeUninit 取指针；跨类型 reinterpret 要特别小心对齐，因为 cast 不会替你检查目标类型的对齐要求。

坑这里最容易踩

这里是坑："长度为零就跳过空指针检查"看似优化，实则埋雷。很多 C API 约定空指针加零长度是合法的，但 Rust 侧 slice::from_raw_parts 要求指针即使长度为零也必须非空且对齐。正确做法是对零长度单独返回空切片常量，不要把一个判空失败后仍继续走通用路径的指针传下去。另一个坑是用 align_offset 在运行时"补救"对齐：它只能检测，不能把未对齐的指针变对齐；真正的对齐保证应该来自类型系统（例如从 &[i32] 取指针），而不是运行时补丁。

13.3 最小包围：把特权压到一行

工程上最重要的纪律是最小包围：unsafe 块只包住真正需要特权的那一行，空指针检查、长度校验、边界判断全部留在安全代码里。这样审查者只需要盯住极短的一段，并能对照紧邻的 SAFETY 注释逐条验证契约。下面这段求和函数来自本单元的真实验证项目，编译与运行结果稍后给出。

rustRust · 标准库26 行
#![allow(dead_code)]
/// 对一段连续的 i32 求和。
/// 调用方必须保证 ptr 指向至少 len 个已初始化的 i32，且调用期间不被并发写入。
fn sum_slice(ptr: *const i32, len: usize) -> i64 {
if len == 0 {
return 0;
}
assert!(!ptr.is_null(), "ptr 不能为空");
let mut total = 0i64;
for i in 0..len {
// SAFETY: 调用方契约保证 ptr..ptr+len 已初始化且期间不被并发写入
unsafe { total += *ptr.add(i) as i64; }
}
total
}
/// 安全外壳：把裸指针藏在参数边界里，调用方无需写 unsafe。
fn sum_slice_safe(data: &[i32]) -> i64 {
sum_slice(data.as_ptr(), data.len())
}
fn main() {
let data = [1i32, 2, 3, 4];
println!("sum_slice = {}", sum_slice_safe(&data));
}

注意 sum_slice_safe 的价值：它把"指针有效"这件事变成调用方无需操心的事实。外部只看到普通的安全函数，unsafe 被收敛在一层薄薄的封装里。这正是标准库自身的组织方式——Vec、String 内部有大量 unsafe，但使用者几乎接触不到。审查这种代码时可以采用固定流程：先列出 unsafe 块依赖的全部前提，再逐条追问"谁保证它成立、在哪一行可能被破坏"，最后确认这些前提不会因重构而失效。

重构时最容易出现的问题是"顺手把 unsafe 块撑大"：为了少写几行类型转换，把原本放在外面的计算也挪进 unsafe 块。这样审查面积会悄悄膨胀，注释却没跟着更新。一个有效的纪律是让 SAFETY 注释与 unsafe 块一一对应，且注释里提到的每个条件都能在紧邻的安全代码里找到对应的检查。工具上可以配合 -W unsafe_op_in_unsafe_fn、cargo clippy -- -W unsafe_op_in_unsafe_fn 以及 clippy::undocumented_unsafe_blocks，把"写注释"变成流水线要求而不是自觉行为。

13.4 unsafe fn 与 # Safety 契约

把裸指针逻辑包进 unsafe fn，可以把契约集中到一处，让调用点只需证明一次，而函数内部可以多次使用这份证明。函数文档里的 # Safety 段落是行业惯例：rustdoc 会把它渲染成醒目的警告区，clippy 的 missing_safety_doc lint 也会检查它。契约必须写成可验证的条件，"使用时小心"这种话不算契约，因为它无法被审查。

下面的 first_byte 即使内部做了空指针和长度检查，仍然标记为 unsafe：因为仅凭一个裸指针，无法证明它指向的内存有效可读。调用方必须能提供可信来源，比如有效切片的 as_ptr()。注意这里的安全外壳只做了一件事——把"来源可信"从调用方的责任变成类型系统的责任。

rustRust · 标准库23 行
#![allow(dead_code)]
/// 读取缓冲区首字节。
///
/// # Safety
/// `ptr` 必须非空、正确对齐，且至少可读 `len` 个字节；
/// 调用期间该内存不得被其他线程写入。
unsafe fn first_byte(ptr: *const u8, len: usize) -> Option<u8> {
if ptr.is_null() || len == 0 {
return None;
}
// SAFETY: 调用方已保证指针有效且 len > 0
Some(unsafe { *ptr })
}
fn first_byte_safe(buf: &[u8]) -> Option<u8> {
unsafe { first_byte(buf.as_ptr(), buf.len()) }
}
fn main() {
println!("first = {:?}", first_byte_safe(b"rust"));
println!("empty = {:?}", first_byte_safe(b""));
}

写契约时建议采用固定句式：先写"谁负责什么"，再写"在什么时间范围内成立"，最后写"违反会怎样"。例如"调用方保证 ptr 在本次调用期间不被其他线程写入"比"注意线程安全"强得多，因为它把责任主体和时间窗口都明确了。同时要避免在契约里重复实现细节：契约描述的是调用方的义务，不是函数内部做了什么。

启用 unsafe_op_in_unsafe_fn lint 后，unsafe 函数内部的每个特权操作都必须显式写出 unsafe 块，这正是上面代码刻意保留的写法。它让特权操作在代码里"看得见"，避免读者误以为什么都没发生。

与 unsafe fn 相对的是 unsafe trait，例如 Send、Sync 或自定义的"实现者必须满足某不变量"的 trait。实现它们意味着你向整个类型系统作出承诺，编译器会据此在别处省略检查。除非你完全掌控类型的内部表示并能证明承诺，否则不要手写实现。遇到"类型不满足 Send"时，优先修正设计——换用 Mutex 或原子类型——而不是加一行 unsafe impl Send 让错误消失。这类"让错误消失"的改动会把一个编译期问题转化为运行期 UB，代价通常要在几周后才显现。

13.5 MaybeUninit：让"还没初始化"成为合法状态

Rust 要求所有变量在使用前必须初始化，但很多 C API 采用"调用方分配空间、被调方填充"的模式。直接写 let mut p: T; 然后传给 C 是不合法的；MaybeUninit<T> 才是表达这种状态的正确工具：它占用的空间与 T 相同、对齐与 T 相同，但不要求里面存在有效的 T。读写它需要通过 as_ptr/as_mut_ptr 取得裸指针，确认初始化完成后再用 assume_init 取出值。

rustRust · 标准库19 行
#![allow(dead_code)]
use std::mem::MaybeUninit;
/// 演示 C 风格 out 指针：写入完成后才 assume_init。
fn uninit_pair() -> (i32, i32) {
let mut raw = MaybeUninit::<(i32, i32)>::uninit();
// SAFETY: 下面两次写入覆盖了全部字段，之后才读取
unsafe {
let p = raw.as_mut_ptr();
(*p).0 = 7;
(*p).1 = 9;
raw.assume_init()
}
}
fn main() {
println!("pair = {:?}", uninit_pair());
}
大白话先用直觉把它讲通

MaybeUninit 就是"先占好座位，人还没到"。座位必须留够，但在人坐稳之前不能告诉别人"这里有人"。assume_init() 相当于正式宣布"人到了"，宣布早了就是 UB。

assume_init 是另一个 unsafe 操作，因为编译器无从得知你是否真的写完了。特别注意部分初始化的陷阱：如果 T 有析构函数，而你只初始化了其中一部分字段就调用 assume_init，析构时会读取未初始化内存。稳妥的写法是先写满所有字段，或者用 MaybeUninit 数组逐个元素初始化后再整体转换。另一个反直觉的细节是：对 MaybeUninit<T> 用普通赋值 x = value 会先丢弃旧值，而旧值可能是未初始化的——正确做法是用 MaybeUninit::write，它直接写入而不读取旧内容。

还要警惕 MaybeUninit::zeroed：全零字节并不等于所有类型的有效值。引用、Box、NonNull、NonZeroU*、fn 指针都禁止全零，bool 的零值虽然是 false 但依赖具体实现约定，枚举更是如此。只有当你明确知道 C API 会写入有效位模式，或者类型是 u8/[u8; N] 这类全零合法的类型时，zeroed 才安全。标准库的 Vec 内部正是用 MaybeUninit 管理容量与长度之间的"已分配但未初始化"区间，这是理解它设计动机的最好例子。

13.6 extern "C" 与 repr(C)：跨语言边界的形状

跨语言调用必须统一 ABI：调用约定、参数传递方式、名称修饰、返回值处理都要一致。extern "C" 表示使用 C 的 ABI，是 FFI 的默认选择；Rust 自身的 ABI 不稳定，绝不能跨语言边界使用。结构体跨越边界时必须用 #[repr(C)] 固定字段布局，否则编译器可以自由重排字段，另一端的 C 代码会读到错误偏移。类似地 #[repr(transparent)] 适合"只包一个字段的新类型"，它能保证包装层不改变布局。

下面是本单元真实验证过的完整程序：C 侧提供一个求和函数、一个交换字段的函数和一个填充函数，Rust 侧用 unsafe extern "C" 声明并调用。声明之所以 unsafe，是因为编译器无法验证外部函数的契约；调用点必须自己保证参数有效。

rustRust · 标准库54 行
#![allow(dead_code)]
use std::ffi::{c_char, CStr, CString};
use std::mem::MaybeUninit;
#[repr(C)]
#[derive(Debug, Clone, Copy)]
pub struct CPair {
pub x: i32,
pub y: i32,
}
unsafe extern "C" {
fn c_add(a: i32, b: i32) -> i32;
fn c_sum(ptr: *const i32, len: usize) -> i64;
fn c_pair_flip(p: *mut CPair);
fn c_fill_pair(out: *mut CPair);
fn c_greeting() -> *const c_char;
}
fn pair_from_c() -> CPair {
let mut raw = MaybeUninit::<CPair>::uninit();
// SAFETY: c_fill_pair 会完整写入 CPair 的全部字段
unsafe {
c_fill_pair(raw.as_mut_ptr());
raw.assume_init()
}
}
fn sum_slice(ptr: *const i32, len: usize) -> i64 {
if len == 0 { return 0; }
let mut total = 0i64;
for i in 0..len {
// SAFETY: 调用方契约保证 ptr..ptr+len 已初始化
unsafe { total += *ptr.add(i) as i64; }
}
total
}
fn main() {
let data = [1i32, 2, 3, 4];
println!("sum_slice = {}", sum_slice(data.as_ptr(), data.len()));
println!("c_sum = {}", unsafe { c_sum(data.as_ptr(), data.len()) });
println!("c_add = {}", unsafe { c_add(2, 3) });
let mut pair = CPair { x: 2, y: 3 };
unsafe { c_pair_flip(&mut pair) };
println!("flipped = {:?}", pair);
println!("filled = {:?}", pair_from_c());
println!("size_of CPair = {}", std::mem::size_of::<CPair>());
let greeting = unsafe { CStr::from_ptr(c_greeting()) };
println!("greeting = {}", greeting.to_str().unwrap());
let owned = CString::new("rust -> c").unwrap();
println!("owned = {}", owned.to_str().unwrap());
}

对应的 C 侧实现只有十来行，核心是固定布局的结构体和按约定写入的 out 指针。两侧共享同一个 CPair 定义：C 用 typedef struct { int32_t x; int32_t y; } CPair;，Rust 用 #[repr(C)] 保证同样的偏移。真实编译与运行输出如下（宿主 rustc 1.96.0，MinGW gcc 编译 C 目标文件后由 MSVC 链接器链接）。

$ rustc --edition 2021 -W unsafe_op_in_unsafe_fn main.rs -C link-arg=clib.o -o ffi-demo.exe

还有几个平台层面的边界要记住：usize 对应 C 的 size_t，在 32 位与 64 位目标上宽度不同，因此用固定宽度的 u32/u64 交换数据更稳妥；带数据的 Rust 枚举即便加了 repr(C) 也不是 C 的 union/tagged struct，需要手工定义标签加联合；函数指针在 Rust 里默认非空，可以用 Option<extern "C" fn()> 表达可空的函数指针，这与 C 的 NULL 自然对应。

坑这里最容易踩

这里是坑：在 edition 2024 中 #[no_mangle] 要写成 #[unsafe(no_mangle)]，本单元统一用 2021。更隐蔽的问题是传递 Rust 集合：String、Vec、HashMap 的布局不受跨语言承诺，Box 也依赖 Rust 分配器。把它们直接交给 C 等于让两端对同一块内存各执一套解释。正确做法是转换成裸指针加长度，或由 C 侧分配、按明确的协议交还，并在文档里写清"谁分配、谁释放、用什么函数释放"。

13.7 字符串与所有权：FFI 最容易出错的边界

C 侧期待的是以零结尾的字节序列，Rust 的 String 并不保证结尾有 NUL。标准库提供 CString 用于构造、CStr 用于借用查看，对应类型是 c_char。CString::new 会拒绝内部含 NUL 的字符串并返回 NulError——这不是麻烦，而是防止 C 侧提前截断的护栏。反过来，从 C 拿回字符串时不能凭空造出 &str：必须知道长度、验证 UTF-8 有效性，并明确缓冲区由谁释放。上面例子里的 c_greeting 返回静态字符串常量，因此可以用 CStr::from_ptr 借用；如果 C 侧返回的是 malloc 出来的缓冲区，Rust 侧必须在合适的时机调用同一个分配器的释放函数，否则就是内存泄漏或者跨分配器释放。

所有权边界还包括不透明句柄模式。C 库常把内部状态藏在 void* 后面，Rust 侧可以定义零大小标记类型，用 *mut Opaque 持有句柄，并在 Drop 里调用 C 的析构函数。这样借用检查器无法追踪的生命周期，被转换成了一个正常的 RAII 对象。关键是保证 Drop 只执行一次、句柄不会被复制后双重释放——这也是为什么这类封装通常要显式禁止 Clone，或者用 Arc 加引用计数来共享。

异常边界同样重要：panic 不允许跨越 extern "C" 函数传播到 C 侧，现代 Rust 会直接 abort。如果 C 回调可能触发 Rust 的 panic，必须用 std::panic::catch_unwind 在边界内接住，转换成错误码返回。回调设计也有固定套路：extern "C" fn 签名里带一个 void* userdata，Rust 侧把上下文盒子转成裸指针传进去，回调内部再转回引用。这里又回到来源与别名问题——回调执行期间不能有其他可变别名指向同一上下文。

字符串转换的错误处理也要明确：CString::new 失败时返回 NulError，它带有内部字节与 NUL 的位置，适合直接转成领域错误；CStr::to_str 失败说明 C 侧给了非 UTF-8 字节，此时可以用 to_string_lossy 做日志展示，但不要把它当作合法数据继续处理。反过来，把 Rust 字符串交给 C 之前要确认生命周期：as_ptr 得到的指针只在原字符串存活且未被修改期间有效，把它存进 C 侧长期持有的结构体是典型的悬垂来源。工程上更稳妥的做法是在边界处复制一份到 C 侧分配的内存，并配套提供释放函数。

13.8 Miri、sanitizer 与 soundness 清单

即使做了上述所有事情，unsafe 代码仍然需要工具辅助验证。Miri 是 Rust 的解释器，能在执行时检查别名违规、越界、未初始化读取、指针来源错误等问题；它比测试慢得多，但能抓到普通测试发现不了的问题。宿主没有安装 Miri（本单元实测 cargo miri --version 无输出），所以下面的命令作为工作流说明，输出标记为示意。sanitizer 是另一种选择，需要 nightly 工具链，能在真实硬件上以较低开销检查内存错误；它覆盖的面不如 Miri 全，但速度快得多，适合放进日常 CI。

终端真跑一遍
$ cargo +nightly miri test # 示意：宿主未安装 Miri，未真实执行
$ RUSTFLAGS="-Z sanitizer=address" cargo +nightly test
（示意输出；实际可用性取决于工具链与平台）

工具之外还有流程。cargo geiger 可以统计项目与依赖里 unsafe 的分布，帮你判断审查重点；proptest 或 fuzz 能对安全外壳做随机输入压力测试，虽然不能证明 soundness，却能把"明显违反契约"的调用暴露出来。最重要的一条是：新增 unsafe 代码必须随附契约说明和针对性测试，评审时不接受"先合进去以后再补注释"。测试设计上也要刻意覆盖边界：空指针、零长度、最大长度、对齐边界、重复调用与并发调用。这些输入在安全 Rust 里往往由类型系统直接排除，但在 unsafe 边界上它们都是合法可构造的状态，必须逐个验证封装真的把它们挡住了。

最后给出一份可以贴在代码评审里的 soundness 清单。它不承诺证明正确性，但能迫使作者把隐含前提写出来。每次修改 unsafe 代码后逐条核对，比事后追查 UB 便宜得多。

检查项 典型后果 正确做法
解引用空指针或悬垂指针 立即 UB 用引用或有效切片作为参数
