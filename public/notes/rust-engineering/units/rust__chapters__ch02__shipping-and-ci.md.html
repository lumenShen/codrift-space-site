13.1 release profile 与产物取舍

同一个 crate 在 cargo build 与 cargo build --release 下会产生截然不同的二进制。debug 配置追求编译速度和调试体验：优化级别低、保留符号与调试信息、打开溢出检查。release 配置追求运行效率：默认 opt-level = 3、剥离部分调试信息、关闭 debug_assertions。把「只在开发时检查」的逻辑挂到 debug_assertions 上，可以让发布版省掉开销而不丢失开发期保护。

下面的片段展示最常见的自定义 profile。lto 做跨 crate 内联，能减小体积并提升速度，代价是链接时间显著变长；codegen-units = 1 让优化器看到更大的整体，同样以编译时间为代价；panic = "abort" 让 panic 直接终止进程，可以去掉展开表，但会跳过析构函数，不能随便打开。

tomlRust · 标准库9 行
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
strip = true
# panic = "abort" # 只在确认不需要展开时用
[profile.dev.package."*"]
opt-level = 2 # 只优化依赖，提升开发期运行速度

代码侧也能感知构建配置。cfg!(debug_assertions) 在 cargo 的 debug 构建中为真、release 构建中为假；option_env! 读取的环境变量若不存在则返回 None，因此在 rustc 直接编译时也安全。下面这个小程序演示了如何让同一份源码输出不同的渠道标识。

rustRust · 标准库8 行
fn build_channel() -> &'static str {
if cfg!(debug_assertions) { "debug" } else { "release" }
}
fn main() {
println!("channel = {}", build_channel());
println!("version = {:?}", option_env!("CARGO_PKG_VERSION"));
}

在 cargo 构建中，CARGO_PKG_VERSION、CARGO_PKG_NAME 等变量由 Cargo 自动注入；用 env! 读取则会在变量缺失时直接编译失败，适合「必须存在」的元数据。option_env! 适合可选信息。

strip = true 会去掉符号表，让产物明显变小，但线上崩溃时的回溯信息也会变得难读。折中方案是保留符号、在发布流水线里单独生成并归档调试符号文件，排查时再用它还原栈帧。profile 还可以按包细分：[profile.release.package."*"] 单独控制依赖的优化级别，让项目代码保持激进优化而依赖不至于拖慢构建。改动这些配置后要用真实负载复测，体积数字好看不代表性能一定更好。

大白话先用直觉把它讲通

debug 像试衣间，灯全开、处处方便检查；release 像正式上台，多余的道具全部撤掉。同一件衣服，两种准备方式。你写的是同一份代码，Cargo 负责按场合换装。

13.2 feature 开关与发布渠道

给不同渠道发布不同产物时，最忌讳复制整份代码库。更好的做法是把差异表达成 feature：默认关闭重型能力，发布时按渠道显式开启。这样所有渠道共享同一套测试与代码审查，差异集中在 Cargo.toml 的几行配置里。

feature 应当保持可叠加，且不要在打开时改变已有函数的语义。展示层的能力（遥测、实验性开关）很适合用 feature 控制；会改变数据格式的能力则应谨慎，因为它可能让两个渠道产生互不兼容的产物。下面的模板用 feature 决定是否编译遥测上报，report 在未启用时退化成空函数，调用方代码完全不用改。

rustRust · 标准库14 行
#![allow(dead_code, unexpected_cfgs)]
#[cfg(feature = "telemetry")]
fn report(event: &str) {
println!("[telemetry] {}", event);
}
#[cfg(not(feature = "telemetry"))]
fn report(_event: &str) {}
fn main() {
report("startup");
println!("startup done");
}

CI 至少验证三种组合：默认特性、--no-default-features、--all-features。若某些特性互斥，还需显式列出合法组合。--all-features 全绿不代表默认配置可用，反过来也一样，这两个方向不能互相替代。把每个组合的用途写进 README 也很重要：使用者最常问的不是「有哪些 feature」，而是「我该开哪个」。给出两三条典型命令，比罗列全部开关更有效。feature 命名要表达能力而非实现细节，例如 json 比 use_serde_v1 更耐久，因为实现可以被替换而能力通常不会。

13.3 cargo publish 流程概念

发布到 crates.io 前有几项硬约束：包必须有唯一的 name、合法的 license 或 license-file、description，以及能找到源码的 repository。cargo publish --dry-run 会执行打包、校验清单并做一次试构建，但不会真正上传，是发布前必做的一步；它能抓到「本地能编译但漏提交了文件」这类问题。

发布流程通常是：确认 semver 版本号变更 → 更新变更日志 → 本地跑通全部测试与文档测试 → cargo publish --dry-run → 打 git tag → cargo publish。发布是不可撤销的，crates.io 不允许用相同版本号重新上传，即使 yank 也只是让新项目不再选用它，已锁定的使用者不受影响。工作区里发布多个相互依赖的包时，还要注意顺序：被依赖的包先发布，发布期间路径依赖要临时切换到版本依赖，否则 crates.io 会拒绝带有未发布路径依赖的包。这个过程机械但容易出错，最好在流水线里固化成脚本，而不是每次手工改动清单。<arg_key:6124c78e>replace_all<arg_value:6124c78e>false

发布内部库时不一定上传到公共仓库，可以用路径依赖、git 依赖或私有注册中心。但「内部库也要有版本号和变更日志」这条纪律应当保留，否则依赖方无法判断升级是否安全。

13.4 GitHub Actions CI 要素

CI 的价值在于把「记得做」变成「做不到就合不进去」。一条最小可用的流水线包含四个环节：格式检查、静态检查、测试矩阵、文档构建。它们应当按成本从低到高排列，让最廉价的反馈最先到达开发者。

  • cargo fmt --all -- --check：格式门禁，失败时提示运行 cargo fmt --all。
  • cargo clippy --all-targets -- -D warnings：把 lint 当错误，防止警告堆积。
  • cargo test --workspace --all-features：覆盖所有成员与特性组合。
  • cargo doc --no-deps --document-private-items：确保文档注释可渲染。
  • cargo build --release --locked：验证锁文件与清单一致且发布配置可构建。

流水线的触发条件也要设计：合并请求跑完整门禁，推送到主干再额外跑发布构建，避免每个临时提交都消耗昂贵的交叉编译资源。发布凭证放进 CI 的 secrets 而不是仓库文件，并限制只有受保护分支可以使用。构建产物（可执行文件、符号文件）应当上传归档，事后若需紧急回滚，有现成的二进制可用，不必重新构建当时的提交。

缓存是 CI 提速的关键：缓存 ~/.cargo/registry 与 target 目录可以省掉大量重复下载和编译。跨平台检查同样重要，至少覆盖一个 Linux 与一个 Windows 目标；FFI 或 unsafe 代码尤其容易在平台差异上翻车。

门禁 拦截的问题 失败成本
fmt 风格分歧与无意义 diff 极低
clippy 可疑写法与潜在 bug 低
test 行为回归 中
doc 文档示例失效 低
release + --locked 配置漂移与锁文件不一致 中

13.5 semver、变更日志与交付纪律

语义化版本是库作者与使用者之间的契约：0.x 阶段任何次版本都可能破坏兼容，进入 1.0 后主版本号变化才代表不兼容变更。新增公开 API、放宽约束属于兼容变更；删除或改名公开项、改变 trait 实现要求、给公开枚举加变体都可能破坏下游，应当计入主版本号。

变更日志不是发布时补写的流水账，而是开发过程中持续记录「用户能感知的变化」。按 Added、Changed、Fixed、Removed 分类，每条说明影响范围与迁移方式。它与 semver 互为表里：日志解释「为什么升这个版本号」，版本号告诉使用者「该不该升级」。

  • 每次合并请求都包含测试或文档变更，门禁才有意义。
  • CI 失败时先修主干，不要靠重试掩盖偶发问题。
  • 发布后立刻打 tag 并记录产物哈希，便于事后追溯。
  • 对已发布版本做修复时，选择向后兼容的补丁版本，避免 downstream 被迫跟随破坏性升级。

把变更日志当作面向用户的沟通渠道，而不是提交记录的复制粘贴。一次破坏性改动应写清「谁会受影响、需要怎么改」，几句话的迁移示例往往比一长串内部实现说明更有价值。版本号、tag、变更日志条目与发布公告应当指向同一个提交，这条一致性纪律在出了问题需要回滚时尤其有用。

交付链的最后一步是验证，而不是上传成功。发布后立刻在一个干净环境中安装该版本、跑一遍最小示例，能够发现「本地能编译但漏了文件」「feature 组合与文档不符」这类问题。把这一步自动化并纳入发布后检查清单，交付才算真正闭环。
