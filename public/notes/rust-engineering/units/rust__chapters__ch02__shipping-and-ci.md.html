14.1 release profile：每一项配置都有代价

同一个 crate 在 cargo build 和 cargo build --release 下会产生截然不同的二进制。debug 配置追求编译速度和调试体验：优化级别低、保留符号与调试信息、打开溢出检查与 debug_assert!。release 配置追求运行效率：默认 opt-level = 3、关闭 debug_assertions、剥离部分调试信息。把"只在开发时检查"的逻辑挂到 debug_assertions 上，可以让发布版省掉开销而不丢失开发期保护——这是成本最低的一项工程优化。

下面的片段来自本单元真实验证的项目。lto = "thin" 做跨 crate 内联，能减小体积并提升速度，代价是链接时间显著变长；codegen-units = 1 让优化器一次看到更大的代码整体，同样以编译时间为代价；strip = true 去掉符号表，让产物变小，但线上崩溃时的回溯会变得难读。

tomlRust · 标准库9 行
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
strip = true
# panic = "abort" # 只在确认不需要展开时用
[profile.dev.package."*"]
opt-level = 2 # 只优化依赖，提升开发期运行速度

panic = "abort" 值得单独说：它让 panic 直接终止进程，从而去掉展开表、进一步减小体积，但会跳过栈上对象的析构函数。如果你的代码依赖 Drop 释放文件锁、刷写缓冲或归还连接池，打开它就会造成资源泄漏。默认保持 "unwind" 是稳妥选择，只有确认整个依赖图都不依赖析构时才切换。

本单元在同一台机器上做了对照构建：一个是默认式配置（lto=false、codegen-units=16、strip=false），一个是上面的激进配置。结果如下。

终端真跑一遍
$ CARGO_TARGET_DIR=target-default cargo build --release \
--config 'profile.release.lto=false' \
--config 'profile.release.codegen-units=16' \
--config 'profile.release.strip=false'
$ stat -c %s target-default/release/rust-notes-ship-demo-2026.exe
135168
$ stat -c %s target/release/rust-notes-ship-demo-2026.exe
134656

这个只有标准库的小程序只省下 512 字节，说明"配置好看"不等于"收益真实"。在依赖多、代码量大的项目上 LTO 的收益可能明显得多，但必须用自己的真实负载复测。体积数字尤其容易产生错觉：strip 去掉的是符号表，不影响代码逻辑，真正的性能变化来自内联与代码布局。

profile 还支持按包细分。[profile.release.package."*"] 单独控制所有依赖的优化级别，[profile.release.package.my_crate] 则只针对某个包。常见组合是让项目代码保持激进优化而依赖用较低级别，以缩短构建时间；反过来，如果瓶颈在依赖里（例如数值计算库），就只把那一个依赖提到 opt-level = 3。opt-level = "z" 与 "s" 分别以体积为第一目标，适合嵌入式或 WASM 场景，但可能明显变慢。调试信息也有独立开关 debug = true：它可以在发布版里保留行号信息，配合分离符号使用，比"整体 strip"更灵活。改动任何 profile 字段后都要重跑基准与体积测量，因为不同字段之间会互相影响。

还有一个容易混淆的点：cargo build --release 使用的是 release profile，而 cargo bench 默认使用 bench profile，它继承 release 但有自己的覆盖项。基准测试如果与真实发布构建用了不同配置，测出来的数字就没有参考价值。让两者保持一致的最简单办法是在清单里显式声明 [profile.bench]，把关键字段写成与 release 相同。cargo test --release 则使用 release profile，适合在接近发布的条件下跑耗时测试。理解这些映射关系，才能确信"测的是将要发布的那份代码"。

大白话先用直觉把它讲通

debug 像试衣间，灯全开、处处方便检查；release 像正式上台，多余的道具全部撤掉。同一件衣服，两种准备方式。你写的是同一份代码，Cargo 负责按场合换装，而换装效果好不好要自己上台量一遍才知道。

14.2 构建元数据与条件编译

代码可以感知构建配置。cfg!(debug_assertions) 在当前构建中为真或为假；env!("CARGO_PKG_VERSION") 在编译期读取环境变量，缺失时直接编译失败，适合"必须存在"的元数据；option_env! 缺失时返回 None，适合可选信息。下面这个程序来自验证项目，两次运行的输出也一并记录。

rustRust · 标准库19 行
use std::env;
fn channel() -> &'static str {
if cfg!(debug_assertions) {
"debug"
} else {
"release"
}
}
fn main() {
let args: Vec<String> = env::args().skip(1).collect();
println!(
"channel={} version={} args={:?}",
channel(),
env!("CARGO_PKG_VERSION"),
args
);
}
终端真跑一遍
$ cargo run -q -- foo
channel=debug version=0.2.0 args=["foo"]
$ ./target/release/rust-notes-ship-demo-2026.exe hello world
channel=release version=0.2.0 args=["hello", "world"]

Cargo 会自动注入 CARGO_PKG_NAME、CARGO_PKG_VERSION、CARGO_PKG_DESCRIPTION 等变量。直接用 rustc --edition 2021 编译时这些变量不存在，env! 会让编译失败，而 option_env! 会退化成 None——这正是两者最重要的区别。

rustRust · 标准库4 行
fn main() {
println!("opt = {:?}", option_env!("CARGO_PKG_DESCRIPTION"));
println!("ver = {:?}", option_env!("CARGO_PKG_VERSION"));
}
终端真跑一遍
$ rustc --edition 2021 opt_env_check.rs -o opt_env_check && ./opt_env_check
opt = None
ver = None

条件判断还有另一种写法 #[cfg_attr(...)]，它按条件应用属性。例如测试专用模块可以在 cfg(test) 时加上 #[allow(dead_code)]，发布时属性消失。需要同时满足多个条件时用 #[cfg(all(...))]，任一满足用 #[cfg(any(...))]，取反用 #[cfg(not(...))]。这些组合在跨平台代码里很常见，例如 #[cfg(all(unix, not(target_os = "macos")))]。要注意 rustc 从 1.80 起默认检查未知 cfg 名，自定义名称必须通过 Cargo.toml 的 [lints.rust] unexpected_cfgs 或 build.rs 的 rustc-check-cfg 登记，否则会收到警告。

需要更丰富的构建信息时（例如 git 提交号、构建时间），可以用 build.rs。它在主 crate 编译之前运行，通过标准输出与 Cargo 通信：

rustRust · 标准库12 行
use std::env;
fn main() {
// 把构建时的 git 描述写进编译期环境变量
let desc = env::var("GIT_DESC").unwrap_or_else(|_| "unknown".into());
println!("cargo:rustc-env=BUILD_DESC={desc}");
// 自定义 cfg：通知主程序有某项构建能力
println!("cargo:rustc-check-cfg=cfg(has_build_stamp)");
println!("cargo:rustc-cfg=has_build_stamp");
// 环境变量变化时重新构建
println!("cargo:rerun-if-env-changed=GIT_DESC");
}
坑这里最容易踩

这里是坑：自定义 cfg 只写 cargo:rustc-cfg=has_build_stamp 而不写 cargo:rustc-check-cfg=...，Cargo 会在编译主程序时发出 unexpected_cfgs 警告，在 clippy -- -D warnings 的流水线里直接变红。本单元实测过两种版本：缺少 check-cfg 时输出一整屏警告；补上之后 cargo run -q 干净通过。另一个坑是忘记 rerun-if-env-changed：环境变量改了但 Cargo 认为构建脚本没变，产物里会留着旧戳记。

14.3 feature 矩阵与发布渠道

给不同渠道发布不同产物时，最忌讳复制整份代码库。更好的做法是把差异表达成 feature：默认关闭重型能力，发布时显式开启。这样所有渠道共享同一套测试与代码审查，差异集中在 Cargo.toml 的几行里。下面的 report 在未启用时退化成空函数，调用方代码完全不用改。

rustRust · 标准库23 行
#[cfg(feature = "telemetry")]
fn report(event: &str) {
println!("[telemetry] {event}");
}
#[cfg(not(feature = "telemetry"))]
fn report(_event: &str) {}
fn check_invariant(x: usize) {
debug_assert!(x > 0, "debug 构建才检查");
assert!(x < 100, "两种构建都检查");
}
fn main() {
report("startup");
check_invariant(7);
#[cfg(has_build_stamp)]
println!("build stamp = {}", env!("BUILD_DESC"));
println!(
"channel = {}",
if cfg!(debug_assertions) { "debug" } else { "release" }
);
}
终端真跑一遍
$ GIT_DESC=abc123 cargo run -q
build stamp = abc123
channel = debug
$ GIT_DESC=abc123 cargo run -q --features telemetry
[telemetry] startup
build stamp = abc123
channel = debug
$ GIT_DESC=abc123 cargo run -q --release
build stamp = abc123
channel = release

CI 至少验证三种组合：默认特性、--no-default-features、--all-features。如果某些特性互斥，还要显式列出合法组合。--all-features 全绿不代表默认配置可用，反之亦然，两者不能互相替代。feature 命名要表达能力而非实现细节：json 比 use_serde_v1 耐久，因为实现可以被替换而能力通常不会。给使用者的文档里，最有效的不是罗列全部开关，而是给出两三条典型命令，例如"日常使用默认配置""嵌入式用 --no-default-features --features core"。

补一句值得记住的细节

补一句：feature 应该是可叠加的。如果打开某个 feature 会改变已有函数的语义，那它更像"另一个 crate"而不是 feature。会改变数据格式的能力尤其要谨慎，因为它可能让两个渠道产生互不兼容的产物。

理解 feature 还要知道统一（unification）现象：同一个依赖被多个包以不同 feature 引用时，Cargo 会把这些 feature 合并，最终只编译一份启用所有请求能力的版本。这意味着"A 关掉的功能"可能因为 B 打开了而实际存在，单测某个 feature 组合时不要假设它是隔离的。resolver = "2" 改变了构建依赖与开发依赖的 feature 传播方式，新项目应当显式声明它。可选依赖通常写成 serde = { version = "1", optional = true }，再用 json = ["dep:serde"] 暴露成对外能力；dep: 前缀的作用是避免 Cargo 自动生成一个同名隐式 feature，让命名空间保持干净。这些细节决定了 feature 矩阵是否真的可预测。

14.4 cargo package：.crate 里到底装了什么

cargo publish 的第一步是打包。.crate 是一个 tar.gz 归档，默认包含清单、锁文件、README、源码与许可证文件。发布前必须用 cargo package --list 看一眼真实清单，因为它会暴露"本地能编译但漏提交了文件"以及"把构建产物打进包里"这类问题。本单元验证项目里最初把 CARGO_TARGET_DIR 指向了包目录内部，结果如下。

终端真跑一遍
$ cargo package --allow-dirty --list
Cargo.lock
Cargo.toml
Cargo.toml.orig
README.md
src\main.rs

上面这份清单看起来正常，但 cargo package 真正打出来的包却是 12 个文件、2.7MiB，因为 target-default/ 目录被递归收了进去。解压列表直接证明了这一点。

终端真跑一遍
$ tar -tf target/package/rust-notes-ship-demo-2026-0.2.0.crate
rust-notes-ship-demo-2026-0.2.0/Cargo.lock
rust-notes-ship-demo-2026-0.2.0/Cargo.toml
rust-notes-ship-demo-2026-0.2.0/Cargo.toml.orig
rust-notes-ship-demo-2026-0.2.0/README.md
rust-notes-ship-demo-2026-0.2.0/src/main.rs
rust-notes-ship-demo-2026-0.2.0/target-default/release/deps/rust_notes_ship_demo_2026.exe
...（其余为 target-default 下的 .d / .pdb 等构建产物）
$ stat -c %s target/package/rust-notes-ship-demo-2026-0.2.0.crate
710633

修复方式是在清单里显式排除，或者把构建目录放到仓库之外。加上 exclude = ["target-default/", "target/"] 后重新打包，数字变成了 5 个文件、1.2KiB 压缩、1209 字节。

tomlRust · 标准库9 行
[package]
name = "rust-notes-ship-demo-2026"
version = "0.2.0"
edition = "2021"
license = "MIT OR Apache-2.0"
description = "用于验证发布流程的最小示例包"
repository = "https://example.invalid/rust-notes-ship-demo"
readme = "README.md"
exclude = ["target-default/", "target/"]
终端真跑一遍
$ cargo package --allow-dirty # 加 exclude 后
Packaged 5 files, 2.0KiB (1.2KiB compressed)
$ tar -tf target/package/rust-notes-ship-demo-2026-0.2.0.crate
rust-notes-ship-demo-2026-0.2.0/Cargo.lock
rust-notes-ship-demo-2026-0.2.0/Cargo.toml
rust-notes-ship-demo-2026-0.2.0/Cargo.toml.orig
rust-notes-ship-demo-2026-0.2.0/README.md
rust-notes-ship-demo-2026-0.2.0/src/main.rs
$ stat -c %s target/package/rust-notes-ship-demo-2026-0.2.0.crate
1209

注意 --list 本身没列出 target-default/ 的内容，而真正打包时却收了进去——这说明不能只看 --list 的输出就以为万事大吉，最终还要检查归档本身。这也是为什么"dry-run 价值很高但仍不能替代干净环境验证"：它验证的是打包与构建流程，不是包里内容的业务正确性。

打包规则可以概括为三条：遵守 .gitignore（在 git 仓库里）、遵守 exclude、遵守 include。include 是白名单，一旦指定就只收列出的文件，适合"只发必要内容"的库；exclude 是黑名单，适合"除了这个临时目录都发"的场景。两者都支持 glob 模式。仓库之外的文件一律不会被打包，所以不要指望用相对路径把父目录的资产带进来。打包后 Cargo 还会做一次"验证构建"：在一个临时目录里解包并编译，确保包是自包含的。这一步能抓到"引用了仓库里存在但未纳入包的文件"这类错误，但对运行时才发现的问题无能为力。把 tar -tf 检查加进发布脚本，成本极低而收益很高。

包里还有一个容易被忽略的文件：Cargo.toml.orig，它是你手写的原始清单的副本，而包内的 Cargo.toml 是 Cargo 规范化后的版本。规范化的目的是让包在不同 Cargo 版本上行为一致：它会补全元数据、展开 workspace 继承字段、去掉路径依赖。因此阅读包内清单时看到"和自己写的不一样"是正常现象，真正需要核对的是 Cargo.toml.orig 与 Cargo.lock。锁文件对库 crate 通常不生效（下游会重新解析），但对可执行 crate 很重要，能保证构建时依赖版本可复现。

14.5 cargo publish 与不可变发布

发布到 crates.io 前有几项硬约束：包必须有唯一的 name、合法的 license 或 license-file、description，以及能找到源码的 repository。cargo publish --dry-run 会执行打包、校验清单并做一次试构建，但不会真正上传，是发布前必做的一步。本单元真实执行了它（版本号刻意选用了不会冲突的名字），输出如下。

终端真跑一遍
$ cargo publish --dry-run --allow-dirty
Updating crates.io index
Packaging rust-notes-ship-demo-2026 v0.2.0
Packaged 12 files, 2.7MiB (694.0KiB compressed)
Verifying rust-notes-ship-demo-2026 v0.2.0
Compiling rust-notes-ship-demo-2026 v0.2.0
Finished `dev` profile [unoptimized + debuginfo] target(s) in 1.64s
Uploading rust-notes-ship-demo-2026 v0.2.0
warning: aborting upload due to dry run

发布是不可撤销的：crates.io 不允许用相同版本号重新上传，即使 yank 也只是让新项目不再选用它，已经锁定该版本的使用者不受影响。因此在点下发布按钮前要把版本号、变更日志、git tag 三者对齐。工作区里发布多个相互依赖的包时还要讲究顺序：被依赖的包先发布，发布期间路径依赖要临时切换成版本依赖，否则注册中心会拒绝带未发布路径依赖的包。这个过程机械但容易出错，最好固化成脚本，而不是每次手工改清单。

内部库不一定要上传到公共仓库，可以用路径依赖、git 依赖或私有注册中心。但"内部库也要有版本号和变更日志"这条纪律应当保留，否则依赖方无法判断升级是否安全。发布凭证放进 CI 的 secrets 而不是仓库文件，并限制只有受保护分支可以使用；一旦泄露，攻击者可以抢注同名包或发布恶意版本。

版本号的另一条纪律是"先改版本，再打 tag，最后发布"，顺序反了就会出现 tag 指向的提交里版本号还是旧值的情况。cargo publish 成功后 crates.io 上的包与 git tag 应当指向同一份内容，可以用归档哈希做交叉校验。如果确实需要撤回，优先用补丁版本修复并发布说明，而不是 yank——yank 会让正在解析新版本的项目跳过它，但已经锁定旧版本的用户无从得知原因。只有在包会造成严重问题（例如包含恶意代码或完全不可用）时才考虑 yank，并在变更日志里写明替代版本。发布顺序在多包 workspace 里尤其关键：被依赖的包先发布且要等索引同步完成，再发布依赖方，否则校验阶段会找不到对应版本。

14.6 GitHub Actions 门禁矩阵

CI 的价值在于把"记得做"变成"做不到就合不进去"。一条最小可用的流水线包含五个环节，按成本从低到高排列，让最廉价的反馈最先到达开发者。

门禁 典型命令 拦截的问题 失败成本
格式 cargo fmt --all -- --check 风格分歧与无意义 diff 极低
静态检查 cargo clippy --all-targets -- -D warnings 可疑写法与潜在 bug 低
测试 cargo test --workspace --all-features 行为回归 中
文档 cargo doc --no-deps --document-private-items 文档示例失效 低
发布构建 cargo build --release --locked 配置漂移与锁文件不一致 中

流水线的触发条件也要设计：合并请求跑完整门禁，推送到主干再额外跑发布构建，避免每个临时提交都消耗昂贵的交叉编译资源。缓存 ~/.cargo/registry 与 target 目录能省掉大量重复下载和编译，缓存键应当包含 Cargo.lock 的哈希与工具链版本，否则缓存命中后反而可能掩盖依赖变化。跨平台检查同样重要，至少覆盖一个 Linux 与一个 Windows 目标；FFI 或 unsafe 代码尤其容易在平台差异上翻车。构建产物（可执行文件、符号文件）应当上传归档，事后若需紧急回滚，有现成的二进制可用，不必重新构建当时的提交。

矩阵策略要克制。三个平台乘三个 feature 组合就是九次构建，再加三个 Rust 版本就变成二十七次，等待时间会迅速超出团队耐心。更好的做法是分层：默认配置在所有平台跑，完整 feature 矩阵只在一个平台跑，稳定版工具链跑全部门禁，最小支持版本只跑编译与测试。这样既覆盖主要风险，又不让 CI 成为瓶颈。失败时先看是不是环境差异（平台缺库、路径分隔符、行尾换行），再怀疑代码本身；把"只在某平台失败"的用例单独标记，能省下大量排查时间。

大白话先用直觉把它讲通

CI 不是"跑测试的机器"，而是"不让坏东西混进来的门卫"。门卫越早发现越省事——格式问题两秒就能拦下，等发布构建失败再回头查，往往已经浪费了半小时。把门禁按便宜到昂贵排队，是最朴素也最有效的优化。

14.7 semver、变更日志与制品归档

语义化版本是库作者与使用者之间的契约：0.x 阶段任何次版本都可能破坏兼容，进入 1.0 后主版本号变化才代表不兼容变更。新增公开 API、放宽约束、修复 bug 属于兼容变更；删除或改名公开项、改变 trait 实现要求、给公开枚举加变体都可能破坏下游，应当计入主版本号。理解"为什么"很重要：下游的代码在高版本约束下会自动升级，如果破坏性改动只升次版本，下游会在毫无察觉的情况下编译失败。

0.x 的特殊规则常被误读。Crates.io 把 0.2.3 的次版本号当作主版本看待，也就是说 0.2 到 0.3 是破坏性升级，而 0.2.3 到 0.2.4 应当保持兼容。如果你的库还在快速演进，长期停在 0.x 是合理的，但要意识到下游的 0.2 约束不会自动跨到 0.3。另一个细节是预发布版本（1.0.0-beta.1）：它不满足 ^1.0.0 约束，因此适合用来收集反馈而不影响稳定用户。把何时发布 1.0 写进项目路线图，能让使用者对稳定性有明确预期。

变更日志不是发布时补写的流水账，而是开发过程中持续记录"用户能感知的变化"。按 Added、Changed、Fixed、Removed 分类，每条说明影响范围与迁移方式。它与 semver 互为表里：日志解释"为什么升这个版本号"，版本号告诉使用者"该不该升级"。一次破坏性改动应写清"谁会受影响、需要怎么改"，几句话的迁移示例往往比一长串内部实现说明更有价值。

  • 每次合并请求都包含测试或文档变更，门禁才有意义。
  • CI 失败时先修主干，不要靠重试掩盖偶发问题。
  • 发布后立刻打 tag 并记录产物哈希，便于事后追溯。
  • 对已发布版本做修复时选择向后兼容的补丁版本，避免下游被迫跟随破坏性升级。

版本号、tag、变更日志条目与发布公告应当指向同一个提交，这条一致性纪律在需要回滚时尤其有用。制品归档则解决另一个问题：源码可以重建，但当时的编译器版本、依赖解析结果与环境变量未必能精确复现。把二进制与符号文件一起归档，并记录构建戳记，才能让"线上这个包到底是哪次提交产出的"成为一个可以回答的问题。

变更日志的写法也有讲究。好的条目以用户视角描述变化："现在可以用 --config 指定配置文件"比"重构了配置加载模块"有用得多。按 Added、Changed、Fixed、Removed 分类能让读者快速扫到自己关心的部分；每个破坏性变更都附上迁移示例，能显著降低支持成本。日志应当在合并请求里逐条累加，而不是发布前翻 git log 补写——后者容易漏掉细节，也容易把内部重构写进去。一个实用的纪律是：没有变更日志条目的合并请求不算完成，哪怕它只是修了一个 bug。

14.8 交付闭环：在干净环境里验证最后一步

交付链的最后一步是验证，而不是上传成功。发布后立刻在一个干净环境中安装该版本、跑一遍最小示例，能够发现"本地能编译但漏了文件""feature 组合与文档不符""系统缺少某个动态库"这类问题。把这一步自动化并纳入发布后检查清单，交付才算真正闭环。

干净环境验证的关键在于"干净"二字：不要用开发机上已有的缓存、环境变量或全局安装的工具。容器是理想载体——从一个最小镜像开始，只安装目标平台的运行时，执行 cargo install <your-crate> 再跑一个 hello world。如果产物依赖系统库（例如 OpenSSL 或 C 运行时），这一步会把缺失依赖暴露出来，而这在开发机上往往被掩盖。

回滚预案也要提前准备。发布后发现严重问题时，最短路径是让使用者退回到上一个版本：变更日志里应当明确写出"已知问题与建议版本"，并让包管理器能顺利降级。如果问题出在某个 feature 组合，修复应当以补丁版本发布，同时保持旧版本的 API 不变。把回滚步骤写成一段可执行命令放进发布清单，比出事时临时商量要可靠得多。交付链是否真正闭环，看的不是"发布成功"那一刻，而是"出问题后能否在十分钟内恢复到可用状态"。

动手动脑

  • 给验证项目加上 [profile.release] 的 panic = "abort"，重新构建并对比二进制大小；再把一个带 Drop 的结构体加入程序，确认析构确实没有执行，据此写一段说明何时可以打开该选项。
  • 在 build.rs 里增加 println!("cargo:rustc-env=BUILD_TIME=...")（用系统时间），在主程序打印它。连续运行两次，观察是否触发重编译；再用 touch build.rs 验证 rerun-if-changed 的行为。
  • 仿照本单元的做法，故意在包目录里创建一个 scratch/ 目录并放入临时文件，先观察 cargo package 的体积，再用 exclude 修复，记录修复前后的真实字节数。
