11.1 三层测试的可见性边界

Rust 的测试天然分成三层，区别不在写法而在「能看见什么」。单元测试与被测试代码放在同一个文件里，通过 #[cfg(test)] mod tests 引入，能访问私有函数与内部状态；集成测试放在包根目录的 tests/ 下，每个文件都被编译成独立的 crate，只能调用公开 API；文档测试藏在文档注释的代码块里，由 rustdoc 编译并运行，同样只能看到公开 API。

三层各自解决不同问题。单元测试覆盖内部状态机与边界条件，成本最低、反馈最快；集成测试验证「从外部看这个库是否真的好用」，能捕捉公开 API 设计缺陷；文档测试保证示例代码不会随重构悄悄失效。只写单元测试是最常见的误区：它全绿并不代表用户能正确调用你的库，因为单元测试可以用私有后门绕过那些用户必须面对的构造步骤。

测试类型 位置 可见范围 主要目标
单元测试 源码内的 #[cfg(test)] mod tests 可访问私有项 算法细节与边界条件
集成测试 tests/*.rs，各自独立 crate 仅公开 API 跨模块组合与使用体验
文档测试 文档注释中的代码块 仅公开 API 示例不过期、可复制运行

验证工程的目录把这套约定落成了文件。注意 tests/common/mod.rs 放在子目录里：如果直接写成 tests/common.rs，Cargo 会把它当成一个独立的测试目标编译，而不是可被其他测试文件 mod common; 引入的模块。

测试默认并行运行，每个用例在独立线程上执行，因此用例之间不应共享可变全局状态，也不能依赖执行顺序。需要串行化时应当重新设计——把共享状态收进一个显式的对象，或把有状态的部分隔离成单独的进程，而不是靠 sleep 碰运气。极少数耗时很长的用例可以标 #[ignore]，让它退出默认集合，再由 cargo test -- --ignored 单独运行；调试失败时用 cargo test -- --nocapture 让 println! 输出不被捕获，往往比反复加断点更快。

11.2 表驱动断言、should_panic 与失败信息

assert_eq! 失败时会同时打印期望值与实际值，assert! 只给出布尔结果，因此比较值一律优先用前者。assert_ne! 与 matches! 在处理枚举状态时更贴切；预定会失败的用例用 #[should_panic(expected = "片段")]，expected 写的是 panic 消息的子串，不要依赖完整文本。验证工程里就踩过一次这个坑：assert_eq! 的实际消息是 assertion + 反引号包裹的 left == right 加上两行值，写 expected = "assertion failed" 会让用例失败——宏的文本会随 Rust 版本变化，稳定的是表达式部分。

表驱动测试把「输入—期望」放进数组，用一个循环跑完所有用例。新增场景只需加一行，失败信息里还能带上输入，定位速度远快于复制粘贴出的十个测试函数。下面这个 std-only 例子同时演示了表驱动、assert_eq! 的自定义消息和 should_panic；用 rustc --test 编译即可直接运行测试框架。

rustRust · 标准库33 行
#![allow(dead_code)]
fn normalize(s: &str) -> String {
s.trim().to_lowercase()
}
#[cfg(test)]
mod tests {
use super::*;
#[test]
fn table_driven_with_input_in_message() {
let cases = [
(" Hello ", "hello"),
("RUST", "rust"),
("\tGo\t", "go"),
("", ""),
];
for (input, want) in cases {
assert_eq!(normalize(input), want, "输入: {:?}", input);
}
}
#[test]
#[should_panic(expected = "boom")]
fn panic_expected() {
panic!("boom: 用于演示 should_panic");
}
}
fn main() {
println!("请用 rustc --test 编译以运行测试");
}
终端真跑一遍
$ rustc --edition 2021 --test block_u11_1.rs -o bu11_1.exe && ./bu11_1.exe
running 2 tests
test tests::table_driven_with_input_in_message ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

debug_assert! 系列宏在 debug 构建里检查、在 release 构建里被完全移除，适合「验证内部前提但不愿为发布产物付成本」的场景。它不能替代普通断言：如果检查失败意味着数据已经损坏，就该用 assert!，哪怕发布版本也宁可崩溃。测试代码里几乎总该用普通断言，因为测试本来就不进发布产物。

浮点比较是另一个常见陷阱：由于精度误差，assert_eq!(0.1 + 0.2, 0.3) 会失败。正确做法是断言差值小于一个明确的 epsilon，或把两边放大成整数后比较。涉及时间与随机数的测试要把「随机源」「时钟」作为参数注入，才能在测试中传入固定值；否则今天全绿的套件明天就可能随机失败。断言还要检查真正重要的性质：测试排序函数时，断言「结果有序且是原集合的重排」比断言某个固定输出更抗重构；测试缓存时，断言「第二次没有重新计算」比断言最终值更能抓住回归。断言失败时若需要额外上下文，assert_eq!(a, b, "第 {} 轮, 配置={:?}", i, cfg) 的自定义消息会被一起打印，这比在测试里到处加 println! 更精确。

11.3 集成测试与共享辅助：目录约定与测试成本

集成测试的价值在于强迫你站在用户视角。tests/integration.rs 只能 use u11_testing::...，因此如果某个功能必须依赖私有函数才能调用，测试会立刻暴露这个 API 设计问题。验证工程里的辅助函数放在 tests/common/mod.rs，通过 mod common; 引入，避免被 Cargo 当成独立测试目标。

rustRust · 标准库24 行
mod common;
use u11_testing::{format_list, normalize, parse_list, sum};
#[test]
fn public_api_contract() {
let parsed = parse_list(common::sample_input()).unwrap();
assert_eq!(parsed, vec![10, 20, -30]);
assert_eq!(sum(&parsed), 0);
assert_eq!(format_list(&parsed), "10,20,-30");
}
#[test]
fn normalize_is_idempotent_on_samples() {
let once = normalize(" HeLLo ");
assert_eq!(once, "hello");
assert_eq!(normalize(&once), once);
}
#[test]
#[should_panic(expected = "left == right")]
fn assert_message_shape_is_stable() {
assert_eq!(1, 2);
}

测试成本也要纳入设计。启动进程、访问网络、依赖真实时钟的测试会拖慢反馈速度，应当限制数量并保证可重复。把「纯逻辑」和「副作用」分开，让绝大多数用例落在纯逻辑层，是让测试套件长期保持可用的关键；集成测试尽量用临时目录与本地数据，不依赖外部服务状态。需要临时目录时用 tempfile 之类的 crate 在用例结束时自动清理，不要复用 /tmp 下的固定路径——并行执行的另一个用例可能正在写同一个文件。测试命名同样值得投入：parse_positive_rejects_negative 这样的名字直接说明「被测对象 + 场景 + 期望结果」，失败时无需读代码就知道回归了什么。一个维护良好的测试套件，读测试名就能画出模块的公开行为清单，这份清单比过时的设计文档可靠得多。

大白话先用直觉把它讲通

单元测试像在车间里检查零件，能拿到卡尺和内部图纸；集成测试像客户试驾，只能摸方向盘和油门；文档测试像照着说明书装家具，说明书少写一步就装不起来。零件合格不等于车能开，车能开不等于说明书没写错——三样都过了才算交付。

为什么单元测试要放进源码文件而不是单独目录？因为它需要访问私有实现来验证内部状态机，而 #[cfg(test)] 让这份访问权只在测试构建里存在，发布产物中不会多出任何代码。反过来说，集成测试如果频繁需要通过 pub 才能访问的内部函数来完成准备工作，通常说明公开 API 缺了一个合适的构造入口，应当修补 API 而不是放宽可见性。

坑这里最容易踩

坑：把 CI 上偶发失败的用例改成 sleep(100ms) 再重试。这只会把竞态藏得更深，下一次失败可能在更关键的时刻出现。正确做法是找到共享点并消除它：用临时目录取代固定路径，用依赖注入取代全局随机源，用消息传递取代全局可变状态。确实无法消除的外部依赖，应标 #[ignore] 并放进单独的定期任务，而不是污染每次提交的主反馈环。

11.4 proptest：从例子走向性质

表驱动测试回答「这些输入对不对」，属性测试回答「这一类输入满不满足某条性质」。proptest 的工作方式是：先根据你的策略生成大量随机输入，运行断言；一旦失败，它会**收缩（shrink）**输入，找到一个更小的反例。这个收缩步骤是属性测试比「自己写个随机循环」更有价值的地方——你拿到的是 [0, -1] 这样的最小反例，而不是一个巨大的随机向量。

验证工程里写了三条性质：序列化再解析应当回到原值；normalize 满足幂等性；纯字母串一定被拒绝。策略由 prop::collection::vec、any::<i64>() 与正则字符串生成器组合而成。注意 format_parse_round_trip 覆盖的不只是「常见数字」，还包括 i64::MIN、空向量与负值——这些正是手写测试用例容易漏掉的边界。

tomlRust · 标准库3 行
[dev-dependencies]
proptest = "1"
criterion = "0.5"
rustRust · 标准库21 行
use proptest::prelude::*;
use u11_testing::{format_list, normalize, parse_list};
proptest! {
#[test]
fn format_parse_round_trip(xs in prop::collection::vec(any::<i64>(), 0..24)) {
let text = format_list(&xs);
prop_assert_eq!(parse_list(&text).unwrap(), xs);
}
#[test]
fn normalize_is_idempotent(s in "[ -~]{0,40}") {
let once = normalize(&s);
prop_assert_eq!(normalize(&once), once);
}
#[test]
fn garbage_is_always_rejected(s in "[a-zA-Z]{1,6}") {
prop_assert!(parse_list(&s).is_err());
}
}

proptest 的断言宏与标准库不同：prop_assert_eq! 失败时会返回 TestCaseError，让框架知道可以开始收缩；用普通的 assert_eq! 也能工作，但会直接 panic，收缩效果会打折扣。默认每个性质跑 256 个用例，可以用 PROPTEST_CASES 环境变量调整；CI 上跑得多一些，本地迭代时调少一些。失败时框架会打印用于生成该用例的 RNG 种子，设置 PROPTEST_RNG_SEED 可以在本地精确重放——把它写进 bug 报告，排查就不再是碰运气。

生成策略的组合方式决定了性质测试的可信度。prop::collection::vec(any::<i64>(), 0..24) 会同时覆盖空集合与长度上界；正则策略 "[ -~]{0,40}" 生成可打印 ASCII，刻意避开 Unicode 的复杂大小写映射，让「幂等性」这条性质保持清晰。若策略过窄（例如只生成正数），性质测试会给你虚假的安全感；过宽则可能让测试跑上几分钟。一个实用的迭代方式是：先写小范围策略快速反馈，发现反例后逐步扩大范围，直到耗时与覆盖达到平衡。对于有内部状态的对象，proptest 还提供状态机测试接口，可以生成一系列操作并验证模型与实际实现一致，这是表驱动测试难以表达的另一类性质。

真跑结果如下，三条性质共 3 个用例在 0.02 秒内通过。注意属性测试的时间与输入规模相关，若某条性质突然从毫秒级涨到秒级，往往说明生成策略无意间包含了极大输入，这本身就是一个值得检查的信号。

单元测试像抽查几个乘客，属性测试像在安检口装了一台机器，凡是符合条件的人全查一遍，查出问题还会把问题人物「压缩」成一个最典型的样本给你看。前者快，后者能发现你根本没想到的组合。两种都要有。

11.5 criterion：真实数字、噪声与趋势

功能测试回答「行为对不对」，基准测试回答「同样输入下耗时有没有变化」。这是两件事：一个复杂度高一个数量级的实现，在小输入上可能反而更快，只看单点数字会得出错误结论。因此基准要覆盖多个输入规模，观察增长趋势，并把结论连同硬件与编译配置一起记录。

标准库的 #[bench] 只在 nightly 可用，稳定版通常用 criterion。它会自动做预热、采集多个样本、用统计方法给出置信区间并标记离群点。验证工程的基准覆盖了两组：求和在 64 与 1024 个元素上的耗时，以及 128 个整数的序列化与解析。为了让本单元的验证快速完成，代码里显式缩短预热与测量时间并把样本数降到 10；正式项目应保留默认值，数字才足够稳定。

rustRust · 标准库27 行
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use std::time::Duration;
use u11_testing::{format_list, parse_list, sum};
fn bench_sum(c: &mut Criterion) {
for n in [64usize, 1024] {
let xs: Vec<i64> = (0..n as i64).collect();
c.bench_function(&format!("sum_{}", n), |b| b.iter(|| sum(black_box(&xs))));
}
}
fn bench_round_trip(c: &mut Criterion) {
let xs: Vec<i64> = (0..128).collect();
let text = format_list(&xs);
c.bench_function("format_128", |b| b.iter(|| format_list(black_box(&xs))));
c.bench_function("parse_128", |b| b.iter(|| parse_list(black_box(&text)).unwrap()));
}
fn fast_config() -> Criterion {
Criterion::default()
.sample_size(10)
.warm_up_time(Duration::from_millis(120))
.measurement_time(Duration::from_millis(250))
}
criterion_group!(name = benches; config = fast_config(); targets = bench_sum, bench_round_trip);
criterion_main!(benches);

black_box 很关键：它告诉编译器「这个值会被使用，别把它优化掉」。没有它，对常量输入的求和可能被完全折叠成一条立即数返回，测出来的是优化器的本事而不是函数的耗时。另一个常见错误是在基准里包含输入构造：那测的是分配与填充，不是被测函数；应把数据准备放在闭包外。

真跑数字如下（release profile，10 个样本，Windows x64，本机实测）。sum_1024 大约是 sum_64 的 14 倍，与数据量 16 倍的增长基本吻合，说明这里主要受线性扫描支配；format_128 明显慢于 parse_128，因为前者为每个整数分配一个 String 再拼接，而解析走的是原地扫描。这个结论是「分配次数比字符数量更影响这段路径」，只有比较了同规模的两组数字才看得出来。

坑这里最容易踩

坑：把基准测试放进每次提交的 CI 流水线。共享 CI 机器上的噪声（邻居任务、CPU 降频、页面换入）会让数字上下浮动，导致误报。基准应当在专用环境按需运行，或只比较数量级与趋势；追逐个位数百分比的「优化」通常只是噪声。另外，基准通过的前提是功能测试全绿——没有正确性保障的性能数字没有意义。

11.6 rustdoc 与文档测试：示例即契约

文档注释用 ///，面向库的读者；普通注释用 //，面向维护者。rustdoc 把 Markdown 渲染成网页，并把文档注释里的 Rust 代码块当作文档测试编译运行。这意味着示例不是装饰，而是会被 CI 验证的契约：API 改名后，示例代码编译失败会直接让测试套件变红。

验证工程的 parse_list 文档包含可运行示例与 # Errors 段落。示例里用 use u11_testing::parse_list; 显式导入，是因为文档测试会被编译成独立的外部 crate——它看不到库内部的私有项，这一点与集成测试一致。文档注释里还支持 intra-doc 链接，例如 [parse_list] 会变成指向该函数的可点击链接，让类型说明互相可达。

rustRust · 标准库29 行
/// 把逗号分隔的整数列表解析成 `Vec<i64>`，容忍两侧空白与空串。
///
/// # Examples
///
/// ```
/// use u11_testing::parse_list;
/// assert_eq!(parse_list("1, 2,3").unwrap(), vec![1, 2, 3]);
/// assert_eq!(parse_list("").unwrap(), Vec::<i64>::new());
/// ```
///
/// # Errors
///
/// 任一分段不是合法整数时返回带原文的错误信息。
pub fn parse_list(s: &str) -> Result<Vec<i64>, String> {
if s.trim().is_empty() {
return Ok(Vec::new());
}
s.split(',')
.map(|p| {
p.trim()
.parse::<i64>()
.map_err(|e| format!("无法解析 {:?}: {}", p, e))
})
.collect()
}
fn main() {
println!("{:?}", parse_list("1,2,3"));
}

文档的结构有惯例可循：# Examples 给可运行示例，# Panics 说明触发 panic 的条件，# Errors 列出失败与含义，# Safety 专属于 unsafe 函数。可能 panic 的函数若不写 # Panics，调用方就无法在不读源码的情况下判断风险。rustdoc 还能用 #![warn(missing_docs)] 把缺失文档变成编译警告，配合 CI 的 -D warnings 形成门禁。

并非所有示例都该被真正执行。```no_run 表示只编译不运行，适合启动服务器这类有副作用的示例；```ignore 完全跳过，只应用于确实无法在 CI 环境运行的片段，并尽量配一个可运行的替代示例；```compile_fail 则断言代码必须编译失败，可用来测试类型系统的约束，例如「把错误的类型传给函数应当报错」。默认代码块既编译又运行，是最强的契约，应当作为文档示例的首选。

rustdoc 还有几个影响文档质量的开关。#![warn(rustdoc::broken_intra_doc_links)] 让拼错的 [Type] 链接变成警告，配合 -D warnings 能防止链接悄悄失效；#[doc(hidden)] 把公开但不希望用户依赖的项藏起来；cargo doc --document-private-items 在本地生成包含私有项的文档，适合维护者自查，但发布给用户的仍是公开视图。文档开头的 //! 用于模块级说明，适合回答「这个模块解决什么问题、什么时候不该用它」——这类信息放在函数文档里太碎，放在 README 里又容易与代码脱节。

文档测试失败时说明什么？通常有三种：示例引用的 API 已改名、示例展示了错误用法、示例依赖了文档里没声明的 feature。它覆盖的维度与功能测试不同：功能测试验证实现，文档测试验证「用户照着抄能不能跑」。一个库可以功能测试全绿但文档测试全红——那意味着它的说明已经落后于代码。

11.7 覆盖率与 CI 门禁：哪些指标值得守

覆盖率回答的是「哪些代码行从未被执行」，它只能发现明显的测试空白，不能证明断言质量。一行被覆盖但什么也没断言的代码，对可靠性的贡献仍然为零。因此覆盖率适合当作发现缺口的工具，不适合当作 KPI：把覆盖率从 80% 推到 95% 的成本，往往不如把剩余 20% 里真正高风险的路径补上断言。

CI 门禁应当分成两层。「必须绿」的是确定性的检查：格式化、lint、全量测试、--locked 构建、文档构建。「只汇报」的是有噪声或需要人工判断的指标：覆盖率百分比、基准数字、依赖安全公告。把后者也设为硬门禁，会诱使开发者写「为了覆盖率而覆盖率」的空测试，反而降低套件质量。

门禁 命令示例 守护什么
格式 cargo fmt --all -- --check 风格漂移与无意义 diff
Lint cargo clippy --all-targets -- -D warnings 常见误用与可疑写法
测试 cargo test --workspace --locked 行为回归、文档示例过期
构建 cargo check --workspace --all-targets 所有目标可编译
覆盖率 cargo llvm-cov 等第三方工具 发现从未执行的路径，建议不设硬阈值

覆盖率工具的选择也受工具链影响：稳定版 Rust 不内置 cargo test --coverage，需要借助 cargo-llvm-cov 等第三方工具。把它装进 CI 镜像并在 PR 上贴出增量覆盖率报告，比追求全局百分比更有用——你真正关心的是这次改动有没有留下未测试的新分支。若想进一步衡量断言质量，可以看变异测试（mutation testing）：工具自动把实现里的 > 改成 >=、把常量换掉，再跑测试套件；如果套件仍然全绿，说明对应分支缺少有效断言。它比覆盖率更接近「测试到底有没有用」，代价是运行时间长得多，适合在关键模块上按需执行。

偶发失败（flake）是另一个需要主动治理的问题。定位时可以用 cargo test -- --test-threads=1 把套件串行化：如果串行后不再失败，几乎可以确定是共享状态或顺序依赖。找到根因后修复它，而不是在 CI 失败时点一下重跑。并发代码的用例尤其要在 CI 上多次重复执行，-- --test-threads=8 与不同 seed 组合能覆盖更多调度交错。工具层面，cargo-nextest 为每个用例分配独立进程，能从机制上消除进程内全局状态的串扰，并给出更清晰的失败摘要。

11.8 可重复性：随机源注入与时间边界

最后一节把前面反复出现的「可重复性」落成具体写法。核心原则是：不要在被测函数内部调用全局随机源或读取系统时间，而把它们作为参数传进去。这样测试可以传入固定种子，生产代码传入真实随机源，两者跑的是同一套逻辑。

下面的 std-only LCG 用一个 64 位状态生成 32 位伪随机数。被测函数 sample_sum 接收 &mut Lcg，而不是自己调用 rand()。真跑结果证明同一 seed 得到同一结果，不同 seed 得到不同结果——这正是「随机测试可复现」的最小实现。生产项目可以直接用 rand crate 的 StdRng::seed_from_u64，但注入的形态不变。

rustRust · 标准库27 行
/// 32 位 LCG：std-only 的可重现随机源，用于让「随机测试」变得可复现。
struct Lcg(u64);
impl Lcg {
fn new(seed: u64) -> Self { Lcg(seed) }
fn next_u32(&mut self) -> u32 {
self.0 = self.0.wrapping_mul(6_364_136_223_846_793_005)
.wrapping_add(1_442_695_040_888_963_407);
(self.0 >> 32) as u32
}
fn below(&mut self, n: u32) -> usize {
(self.next_u32() as u64 * n as u64 / u32::MAX as u64) as usize
}
}
/// 被测逻辑接收随机源作为参数，而不是自己调用全局随机函数。
fn sample_sum(rng: &mut Lcg, len: usize) -> i64 {
let xs: Vec<i64> = (0..len).map(|_| rng.below(100) as i64).collect();
xs.iter().sum()
}
fn main() {
for seed in [42u64, 42, 7] {
let mut rng = Lcg::new(seed);
println!("seed={} -> sum={}", seed, sample_sum(&mut rng, 5));
}
}

时间边界同理：涉及超时的逻辑应接收一个「现在是什么时间」的抽象，测试里传入可控时钟，才能可靠地覆盖「刚好到期」「已经过期」这类边界，而不必真的 sleep。同理，proptest 失败时打印的 seed 应当记录在案，让任何一次红测都能被本地重放。可重复性不是额外的工程奢侈，而是让测试在半年后仍能被信任的前提。
