16.1 运行时模型：任务、worker 与 work stealing

async fn 本身不会运行任何东西。调用它只是构造一个 future，它需要被某个执行器反复 poll 才会前进。tokio 就是这样一个执行器：它维护一个任务队列，由若干 worker 线程从队列里取任务、poll 一次、再把未完成的任务放回。理解这个模型，很多现象就不再神秘——例如为什么在 async 函数里调用 std::thread::sleep 会拖垮整个系统，因为那个 worker 线程被占住了，队列里其他任务都得不到 poll。

本单元的真实验证用的是多线程运行时，配置两个 worker 线程。程序打印了宿主的逻辑核数，并并发跑六个模拟请求：偶数 id 给 100ms 预算，奇数 id 只给 30ms，而每个请求本身需要 60ms 才能完成。

rustRust · 标准库36 行
use std::time::Duration;
use tokio::time::Instant;
async fn fake_fetch(id: u32, ms: u64) -> String {
tokio::time::sleep(Duration::from_millis(ms)).await;
format!("result-{id}")
}
async fn with_timeout(id: u32, fetch_ms: u64, budget_ms: u64) -> Option<String> {
tokio::select! {
v = fake_fetch(id, fetch_ms) => Some(v),
_ = tokio::time::sleep(Duration::from_millis(budget_ms)) => None,
}
}
#[tokio::main(flavor = "multi_thread", worker_threads = 2)]
async fn main() {
println!("逻辑核数: {:?}", std::thread::available_parallelism());
let t0 = Instant::now();
let mut handles = Vec::new();
for i in 0..6 {
let budget = if i % 2 == 0 { 100 } else { 30 };
handles.push(tokio::spawn(async move {
let r = with_timeout(i, 60, budget).await;
(i, r)
}));
}
let mut results = Vec::new();
for h in handles {
results.push(h.await.unwrap());
}
for (i, r) in results {
println!("任务 {i}: {:?}", r.as_deref());
}
println!("6 个任务墙钟: {:?}", t0.elapsed());
}

真实输出如下。六个任务只花了约 73ms，而不是串行的 360ms——等待发生在 reactor 上，worker 在请求睡眠期间可以去 poll 别的任务。偶数任务拿到结果，奇数任务超时返回 None，与预算设置完全吻合。

大白话先用直觉把它讲通

把运行时想成一家餐厅。worker 线程是服务员，任务是餐桌。服务员不会守在一桌旁边等菜上齐，而是把订单交给厨房（reactor），转身去服务别的桌；菜好了再回来。这样几个服务员就能照看几十桌，但前提是没人把服务员按住聊天——那正是阻塞调用干的事。

work stealing 指的是：每个 worker 有自己的本地队列，本地队列空了就去别的 worker 那里"偷"任务。这比全局单一队列更少争用，同时又能自动平衡负载。理解它对配置线程数很关键——线程数不是越多越好，超过物理并行度会增加上下文切换与偷取开销。I/O 密集型负载通常用默认（等于逻辑核数）就够；CPU 密集型混合计算时，可以考虑把重计算 spawn_blocking，避免长期占用 worker。

#[tokio::main] 是一个宏，它把被标注的 async main 改写成同步 main：创建一个 Runtime，调用 block_on。参数 flavor 与 worker_threads 直接传给运行时构建器。需要更细的控制时（例如自定义 thread_name、设置 max_blocking_threads、启用 enable_all 的部分能力），可以不用宏，手写 Runtime::new() 再 block_on。宏的便利在于代码短，代价是配置只能通过参数表达。理解这个展开过程，也能解释为什么 main 里的 panic 与普通同步程序一样——真正异步的部分都在 block_on 内部。

16.2 async 状态机与 poll：为什么不能阻塞

编译器把每个 async fn 变换成一个状态机，每个 .await 是一个可挂起点。poll 一次，状态机运行到下一个未完成的 await，把控制权还给执行器；下次 poll 从断点继续。这意味着两件事：第一，future 很小，只保存跨越 await 仍然活跃的变量；第二，两次 poll 之间执行器可以跑别的任务，但同一次 poll 内部的代码必须很快返回。

std::thread::sleep 或同步文件 I/O 会让当前 worker 线程睡住，期间它无法去 poll 其他任务。如果所有 worker 都被睡住，整个运行时就卡死了，即使有成千上万个就绪任务。这就是 "async 函数里不要写阻塞代码" 的真正原因——不是风格问题，而是调度模型决定的。

状态机的视角还解释了 Send 约束。一个 future 要被 spawn 到别的线程，它保存的所有跨 await 变量都必须能安全跨线程移动，因此编译器要求整个 future 实现 Send。如果你在 await 之间持有 Rc 或 MutexGuard，future 就不是 Send，spawn 会拒绝。这不是编译器故意刁难，而是因为下次 poll 可能在另一个 worker 上进行——状态机必须能整体搬家。理解了这一点，看到 "future is not Send" 的错误时就知道该去找哪个跨 await 持有的变量，而不是盲目加 Arc<Mutex<>>。

rustRust · 标准库16 行
#![allow(dead_code)]
// 错误示范：会把 worker 线程睡住，拖垮同运行时里的其他任务
async fn bad() {
std::thread::sleep(std::time::Duration::from_secs(1));
}
// 正确示范：让出线程，reactor 负责唤醒
async fn good() {
tokio::time::sleep(std::time::Duration::from_secs(1)).await;
}
#[tokio::main(flavor = "current_thread")]
async fn main() {
good().await;
}

如果确实要做阻塞操作（同步数据库驱动、CPU 密集压缩、DNS 查询），用 tokio::task::spawn_blocking 把它移到专门的阻塞线程池。这样 worker 线程保持空闲，阻塞任务在另一个池子里慢慢跑。注意 spawn_blocking 返回的 JoinHandle 同样可以 await，因此它既能保持异步调用风格，又不会污染调度。

坑这里最容易踩

这里是坑：在 async fn 里持有 std::sync::MutexGuard 跨越 .await。这会让 future 变成非 Send（标准库的 MutexGuard 不是 Send），tokio::spawn 会直接编译失败。更隐蔽的后果是：如果同一个任务在另一个线程被 poll，锁的持有线程与释放线程不一致，可能死锁。正确做法是用 tokio::sync::Mutex，并且只在必要的临界区内持有锁，绝不让 guard 活到 await 点之后。

16.3 select!：竞速、偏置与 drop 时机

select! 同时 poll 多个分支，谁先完成就执行谁的处理逻辑，其余分支被丢弃。它是表达超时、竞速、取消的瑞士军刀。上面 with_timeout 已经用过一次：把网络请求与一个定时器竞速，定时器先完成就意味着取消请求。

下面的 demo 专门观察 drop 时机。两个 future 各自持有一个 Guard，Drop 时打印名字。慢任务 100ms，快任务 20ms，必定是快任务胜出。输出会告诉我们败者的资源何时被释放。

rustRust · 标准库29 行
use std::time::Duration;
struct Guard(&'static str);
impl Drop for Guard {
fn drop(&mut self) {
println!(" Drop 守卫: {}", self.0);
}
}
async fn phase(name: &'static str, ms: u64) -> u32 {
let _g = Guard(name);
tokio::time::sleep(Duration::from_millis(ms)).await;
1
}
async fn cancellation_demo() {
println!("-- select! 取消演示（败者 future 被立即丢弃）--");
tokio::select! {
v = phase("慢任务 100ms", 100) => println!(" 慢任务胜出: {v}"),
v = phase("快任务 20ms", 20) => println!(" 快任务胜出: {v}"),
}
tokio::time::sleep(Duration::from_millis(110)).await;
}
#[tokio::main(flavor = "current_thread")]
async fn main() {
cancellation_demo().await;
}

真实输出出乎很多人的意料：两条 Drop 守卫 都打印在处理逻辑之前。原因是 select! 在拿到胜出分支的值后，会先清理所有分支的 future（包括胜者自身），再执行胜出分支的处理器。所以写在处理器里的日志，一定发生在资源释放之后。

终端真跑一遍
$ cargo run --release
-- select! 取消演示（败者 future 被立即丢弃）--
Drop 守卫: 快任务 20ms
Drop 守卫: 慢任务 100ms
快任务胜出: 1

当多个分支在同一轮 poll 里都就绪时，select! 默认随机选择，以避免饥饿。需要确定性顺序时写 biased;，它按代码顺序 poll——适合优先级明确的场景，例如先检查取消信号再处理正常数据。但要小心偏置带来的饥饿：如果高优先级分支总是就绪，低优先级分支可能永远得不到执行。

select! 还支持传入 &mut future，让分支在 select 结束后仍然存活，可以再次参与下一轮竞速。这在"循环中反复等待多个事件"的场景里很常用，例如每一轮都同时等取消信号和一条消息，处理完消息后继续下一轮。用值传入会每次重建 future，可能丢失内部状态；用 &mut 传入则保留进度。需要 pin 的未来（例如包含自引用的 async 块）配合 Box::pin 使用，因为 &mut 需要稳定地址。选择哪种写法，取决于"这个 future 是一次性的还是可恢复的"。

16.4 取消安全：什么能安全取消，什么不能

取消一个 future，就是在它尚未完成时丢弃它。安全与否取决于"丢弃时是否会留下不一致的状态"。一次 sleep 被丢弃是绝对安全的，因为它没有外部副作用；一次"先写半条记录再 await 再写另外半条"被丢弃，则会留下损坏的数据。

判断标准是：这个 future 被丢弃后，调用方重新创建一个执行同样的操作，会不会产生重复或残缺的副作用？写文件、发请求、更新共享状态这几类操作尤其危险。典型的不安全模式是用 &mut buf 在循环里分段读取，每轮 select! 一次取消信号：取消发生在两段之间时，缓冲区里已经有一部分新数据、一部分旧数据，调用方无法区分。

大白话先用直觉把它讲通

取消就像把正在进行的作业撕掉一页。撕掉的是单纯的计算草稿没关系；撕掉的是"已经寄出的包裹存根"就麻烦了——包裹已经上路，你却以为没发。取消安全的核心就是"被撕掉时，要么什么都没发生，要么完整地发生了"。

工程上有三种常规对策。第一种是把整个操作放进 tokio::spawn，select! 只等待 JoinHandle；丢弃句柄不会取消后台任务，它会继续跑到完成。第二种是引入取消令牌（tokio_util::sync::CancellationToken），让任务自己在安全的检查点主动退出。第三种是把操作设计成一次性提交：先在内存里构造完整结果，最后一次调用完成写入。

rustRust · 标准库21 行
use std::time::Duration;
struct Guard(&'static str);
impl Drop for Guard {
fn drop(&mut self) { println!(" Drop 守卫: {}", self.0); }
}
async fn detached_demo() {
println!("-- 分离任务演示（丢掉 JoinHandle 也不取消）--");
tokio::spawn(async {
let _g = Guard("后台任务");
tokio::time::sleep(Duration::from_millis(20)).await;
println!(" 后台任务完成");
}); // 不 await → 任务继续跑
tokio::time::sleep(Duration::from_millis(40)).await;
}
#[tokio::main(flavor = "current_thread")]
async fn main() {
detached_demo().await;
}
终端真跑一遍
-- 分离任务演示（丢掉 JoinHandle 也不取消）--
后台任务完成
Drop 守卫: 后台任务

这个模式也有代价：spawn 出来的任务不再与调用方的生命周期绑定，错误无法用 ? 传回，必须自己设计通道或状态来传递结果。选择哪种对策，取决于业务上"取消"到底意味着什么——是"我不关心结果了但事情该做完"，还是"立刻停止一切副作用"。

还要区分"等待被取消"与"任务被取消"。上一节 with_timeout 里被丢弃的是等待本身，后台请求可能仍在 reactor 中；而 task.abort() 才会真正终止一个已 spawn 的任务，且终止同样发生在下一个 await 点。若任务正在 spawn_blocking 的计算里，abort 无法打断已经运行的同步代码。理解这两个层次，才能正确解释"明明超时了，服务端却收到了请求"这类线上现象——超时只取消了客户端的等待，没有取消已经发出的网络操作。想要端到端取消，需要协议层面的支持，例如 gRPC 的 deadline 传播。

16.5 AsyncDrop 引子与替代方案

同步代码里 Drop 是确定性的：离开作用域就执行。异步世界里资源释放可能需要 await——例如关闭一个连接要 flush 缓冲区、归还池化连接要通知池子。Rust 目前还没有稳定的 AsyncDrop trait，因此这类清理必须显式调用 close().await 之类的函数，不能指望 Drop 帮你完成。这是取消安全问题的另一面：即使future 被正常丢弃，Drop 里也只能做同步清理。

社区常见的替代方案有两种。一种是把资源封进 Arc，Drop 只负责把"需要异步清理"的标志位置位，由后台任务观察标志并执行 await；另一种是提供显式的 shutdown 方法，并在类型上用 #[must_use] 或 lint 提醒调用方。两者都不完美，但共同点是"不要假装 Drop 能 await"。

场景 推荐做法 理由
取消一次网络请求 select! + 超时 future 请求未完成即丢弃，无副作用
取消一次数据库写入 spawn + 通道回报 保证事务完整提交
关闭连接并 flush 显式 close().await Drop 不能 await
停止后台循环 CancellationToken 在安全点主动退出

设计异步 API 时，最好把"清理是否需要 await"写进文档，并让类型名或方法名体现出来。例如 ConnectionGuard 暗示 RAII，而 Connection::close(self).await 明确要求调用方参与。含糊的 API 会让使用者在 Drop 里等待一个永远不会发生的清理。

还有一个与取消紧密相关的话题：超时预算应当贯穿整条调用链，而不是只在最外层设一个。最外层 500ms 超时、内层数据库又设 5s 超时，结果就是外层已经放弃而内层还在跑，浪费资源。正确做法是把剩余预算用 tokio::time::Instant 计算后向下传递，每一层用自己的 deadline。这个模式在微服务里叫 deadline 传播，它的实现不需要特殊 crate，只需要统一的时间源与参数约定。本单元的 with_timeout 是最小版本：预算作为参数传入，而不是在函数内部硬编码。

16.6 真实基准：criterion 数字与解读

性能结论必须来自测量。本单元在 _verify/async-bench/ 下用 criterion 0.5.1 跑了两组基准：一组是 current_thread 运行时里 spawn 不同数量任务并等待完成的开销，另一组是 select! 在立即就绪分支上的开销。每组预热 3 秒、采集 100 个样本、测量 5 秒，全部在 release profile（LTO thin、codegen-units = 1）下运行。项目清单如下，harness = false 是 criterion 基准的必要设置，否则 cargo 会用默认测试框架运行它，得不到统计结果。

tomlRust · 标准库18 行
[package]
name = "async-bench"
version = "0.1.0"
edition = "2021"
[dependencies]
tokio = { version = "1", features = ["full"] }
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }
[[bench]]
name = "runtime"
harness = false
[profile.release]
lto = "thin"

rustRust · 标准库26 行
use criterion::{black_box, criterion_group, criterion_main, BenchmarkId, Criterion};
fn bench_spawn(c: &mut Criterion) {
let rt = tokio::runtime::Builder::new_current_thread()
.enable_all().build().unwrap();
let mut group = c.benchmark_group("spawn_tasks");
for n in [1usize, 16, 256] {
group.bench_with_input(BenchmarkId::from_parameter(n), &n, |b, &n| {
b.iter(|| {
rt.block_on(async {
let mut handles = Vec::with_capacity(n);
for i in 0..n {
handles.push(tokio::spawn(async move { black_box(i) }));
}
for h in handles {
black_box(h.await.unwrap());
}
})
})
});
}
group.finish();
}
criterion_group!(benches, bench_spawn);
criterion_main!(benches);

criterion 输出的三列分别是下界、估计值与上界，通常取中列作为结果。区间很窄说明测量稳定；select_timeout 的 19 个 mild 离群点来自系统调度抖动，属于正常现象，不必惊慌，但如果离群点是 high severe 就要检查是不是测试里混入了偶发的系统调用。读数时还要看迭代次数：spawn_tasks/256 只收集了 146k 次迭代，单次成本更高，但绝对时间仍然只有几十微秒——这个量级告诉我们，任务创建开销在真实网络请求（毫秒级）面前几乎可以忽略。

测量方法本身也要写进结论。本单元的具体条件是：宿主逻辑核数 32、rustc 1.96.0、tokio 1.54.1、criterion 0.5.1、release profile 开启 thin LTO 与单代码生成单元、每组预热 3 秒后采样 100 次共 5 秒。换一台机器、换一个 tokio 版本，这些数字都可能变化，因此它们是用来说明"量级与相对关系"的，不是用来当性能契约的。如果要做版本间的性能回归检测，更稳妥的办法是把基准结果提交为基线，用 criterion 的 --save-baseline 与 --baseline 对比，而不是每次人工读数字。另外，Gnuplot not found, using plotters backend 是 criterion 在宿主上的真实提示：没有 gnuplot 时它改用 plotters 生成报告，不影响测量本身。

坑这里最容易踩

这里是坑：在没有预热、没有固定硬件环境的机器上跑一次就宣布"快了 20%"。criterion 的默认配置已经包含预热与统计，但仍要求测量期间别跑别的重负载。另外不要在 debug 构建上跑基准——opt-level = 0 的数字与发布版毫无关系。本单元所有数字都来自 cargo bench，它使用 bench profile，并显式在清单里把它与 release 的关键字段对齐。

16.7 perf、flamegraph 与剖析流程

基准告诉你"多快"，剖析告诉你"时间花在哪"。Linux 上的典型流程是：用 perf record 采集调用栈，再用 perf report 或 cargo flamegraph 生成火焰图。火焰图从下往上读：底部是调用栈的根，宽度代表采样占比；越宽的横条越值得优化。优化的目标是让"业务函数"占据的宽度变大，让"调度与序列化"变窄。

本单元宿主是 Windows，实测没有 perf、flamegraph 或 cargo-flamegraph（which perf flamegraph 无输出，cargo flamegraph --version 返回未知子命令），因此下面只能给出工作流命令，并把输出明确标为示意，不编造任何采样数字。

终端真跑一遍
$ perf record --call-graph dwarf -g ./target/release/my-app # 示意：宿主无 perf
$ perf report --stdio | head -40
$ cargo install flamegraph && cargo flamegraph --bin my-app # 示意：宿主无 flamegraph
（示意命令；未在宿主执行，故不提供采样数字）

如果拿到真实火焰图，判读分三步：先看最宽的栈顶是不是预期函数；再找"宽而平"的区域，那通常是无用的辅助开销；最后对比优化前后的同一负载，确认热点确实缩小。异步程序的火焰图还有一层特殊之处：大量时间可能落在 park 或 epoll_wait 上，那是空闲等待而非 CPU 消耗，不要把它误判为瓶颈。真正该关注的是运行 worker 上的业务栈。

采样剖析与基准是互补的。基准回答"改动有没有让数字变好"，剖析回答"为什么变好或为什么还不够好"。只做基准容易陷入盲目调参：把线程数从 2 改到 4，数字好了 5%，却不知道是缓存命中率提升还是调度开销下降。只做剖析则无法确认改动是否真的端到端有效。两者结合的流程是：先用基准锁定可复现的性能差异，再用火焰图定位热点，改动后重跑基准验证。本单元刻意把无法真实执行的部分标为示意，就是为了让读者清楚地区分"测出来的"与"讲方法的"。

16.8 工程取舍：runtime 配置、阻塞池与背压

运行时配置没有万能答案。worker_threads 默认等于逻辑核数，适合 I/O 密集且计算很轻的服务；如果任务里有较多 CPU 计算，线程数可以保持默认，但要把计算移到 spawn_blocking。current_thread 运行时只有一个线程，开销更低、行为更可预测，适合客户端程序或单线程嵌入式场景——本单元基准就选了它，以减少测量噪声。max_blocking_threads 控制阻塞池上限，太小会让阻塞任务排长队，太大会浪费线程资源。

背压是异步系统里比"快不快"更重要的问题。当生产者快于消费者时，队列会无限增长，最终耗尽内存。tokio 的 mpsc::channel(capacity) 用固定容量解决这一点：send().await 在通道满时会挂起，把压力传回生产者。相反，unbounded_channel 只在你能证明生产者不会失控时才使用。这个设计哲学与同步世界一致，但异步版本多了"等待期间不占线程"的优势。

容量取值没有公式，通常从"消费者每秒能处理多少 × 可接受的最大排队延迟"倒推。例如消费者每秒处理 1000 条、允许排队 100 毫秒，容量就从 100 起步，再用真实负载压测调整。容量太小会让生产者频繁挂起，吞吐下降；太大则延迟不可控，故障时会堆积大量即将过期的请求。把它做成可配置参数并观测队列长度，比拍脑袋定一个常数更可靠。

动手动脑

  • 把验证程序的 worker 线程数从 2 改成 1 和 8，各跑一次，对比六个任务的墙钟时间；解释为什么差异不符合"线程越多越快"的直觉。
  • 给 with_timeout 加一个 biased; 分支，让取消信号成为最高优先级；构造一个取消信号与数据同时就绪的场景，观察输出顺序并解释偏置的影响。
  • 在 criterion 基准里增加一组 spawn_tasks/1024，记录中位数与离群点数量；结合 1/16/256 三组的真实数字，画出任务数与单次开销的关系图。

把这些机制串起来看，异步性能的本质是"让等待不占用稀缺资源，让副作用在明确的边界上提交"。运行时、任务、取消与安全退出都是这个原则的不同侧面，缺一不可，也值得反复推敲。
