8.1 编译期大小：Sized、?Sized 与 unsized 的边界

Rust 的类型系统默认一切类型都有编译期已知的大小。这个假设渗透在语言的每个角落：值能按值传递、能放进栈帧、能作为结构体最后一个之前的字段、能通过 mem::size_of 查询。为了表达这个假设，编译器给每个类型参数悄悄加了一个 T: Sized 约束——你写 fn f<T>(x: T)，编译器看到的是 fn f<T: Sized>(x: T)。

但有些类型天然没有固定大小：[T]（长度未知的切片）、str、dyn Trait，以及最后一个字段为 unsized 的自定义结构体。它们统称 DST（dynamically sized type，动态大小类型）。要让泛型函数接受它们，必须显式写 T: ?Sized 来取消默认约束。代价是：unsized 类型只能出现在「间接层」后面——引用、Box、Rc 等指针类型——而且不能用 size_of::<T>() 查询，只能用 size_of_val(&x) 查询运行时实际大小。

rustRust · 标准库23 行
#![allow(dead_code)]
use std::mem::{size_of, size_of_val};
fn needs_sized<T: Sized>(x: T) -> usize { size_of::<T>() + size_of_val(&x) * 0 }
fn accepts_unsized<T: ?Sized>(x: &T) -> usize { size_of_val(x) }
fn main() {
let arr = [1u8, 2, 3];
let slice: &[u8] = &arr;
let text: &str = "hi";
let debug: &dyn std::fmt::Debug = &42i32;
println!("u8={} [u8;3]={}", size_of::<u8>(), size_of::<[u8; 3]>());
println!("&[u8]={} &str={} &dyn Debug={}",
size_of::<&[u8]>(), size_of::<&str>(), size_of::<&dyn std::fmt::Debug>());
println!("Box<[i32]>={} Box<dyn Debug>={}",
size_of::<Box<[i32]>>(), size_of::<Box<dyn std::fmt::Debug>>());
println!("size_of_val: slice={} text={} debug={}",
size_of_val(slice), size_of_val(text), size_of_val(debug));
println!("needs_sized(u32)={}", needs_sized(1u32));
println!("accepts_unsized: slice={} text={} debug={}",
accepts_unsized(slice), accepts_unsized(text), accepts_unsized(debug));
}

注意两组数字的对照：[u8; 3] 是 3 字节而 [u8] 根本没有大小；指向它们的引用都是 16 字节，因为它们都是胖指针。size_of_val 回答的是「这个引用指向的数据实际多大」，slice 是 3 字节、"hi" 是 2 字节、dyn Debug 背后的 i32 是 4 字节。为什么引用本身是 16 字节而不是 8？多出来的 8 字节是元数据，下一节展开。

默认 Sized 还会影响 trait 的定义。像 trait Clone 隐含要求 Self: Sized（因为要按值返回 Self），所以 dyn Clone 不可用；而 trait Debug 没有这个要求，于是 dyn Debug 合法。这就把「能否做成 trait 对象」与「大小是否已知」两条线索接在了一起：动态分派依赖胖指针，而胖指针要求 trait 本身不要求具体大小。类似地，函数参数写成 fn f(x: str) 会被直接拒绝，因为参数必须按值传递、必须有已知大小；想处理字符串请用 &str。

大白话先用直觉把它讲通

Sized 类型是「量好尺寸装箱」的货物，仓库按固定格子摆放；unsized 类型是「一卷布」或「一袋子散装零件」，你没法说它占几个格子，只能记「从哪个位置开始、有多长」。所以指向它们的指针得带一张小票（长度或 vtable），这就是胖指针那额外的 8 字节。

8.2 DST 与胖指针：元数据的来源与未size化 coercion

胖指针的第二部分是 metadata（元数据），它的内容由目标类型决定：切片是元素个数，str 是字节长度，dyn Trait 是指向 vtable 的指针。元数据让编译器在只有静态类型信息的情况下，依然能正确回答「这个引用指向多少数据」「该调用哪个方法」「怎么释放这块内存」。它同时也解释了为什么 Box<dyn Trait> 能正确 drop——析构所需的 size/align 信息就在 vtable 里。

从固定大小类型到 DST 的转换叫 unsized coercion（未定长强制转换），由 CoerceUnsized trait 在标准库内部支持。最常见的形式是 Box<[T; N]> -> Box<[T]> 与 &[T; N] -> &[T]，Box<Concrete> -> Box<dyn Trait> 也属于同一机制。转换后数据本身不变，只是指针的元数据从「无」变成「有」。

rustRust · 标准库24 行
#![allow(dead_code)]
use std::mem::size_of;
struct Wrapper<T: ?Sized> {
data: Box<T>,
}
impl<T: ?Sized> Wrapper<T> {
fn new(data: Box<T>) -> Self { Self { data } }
}
fn main() {
let boxed_array: Box<[i32]> = Box::new([1, 2, 3]);
println!("Box<[i32]> fat ptr = {}", size_of::<Box<[i32]>>());
println!("array data = {}, slice len = {}", size_of::<[i32; 3]>(), boxed_array.len());
let w1 = Wrapper::new(boxed_array);
let w2 = Wrapper::new(Box::<str>::from("hello"));
let w3: Wrapper<dyn std::fmt::Display> = Wrapper::new(Box::new(7i32));
println!("w1 len = {}", w1.data.len());
println!("w2 = {}", w2.data);
println!("w3 = {}", w3.data);
}

Wrapper<T: ?Sized> 允许 T 是 [i32]、str 或 dyn Display，因为它只通过 Box<T> 间接持有数据。这正是 ?Sized 的主要用途：让容器抽象不无谓地排除 unsized 类型。标准库里 Box<T>、Rc<T>、Arc<T> 都是这样定义的。

元数据的大小不是固定的 8 字节，而是由目标类型的元数据种类决定；在当前实现里，切片长度和 vtable 指针恰好都是一个字长，所以胖指针都是 16 字节。标准库内部用 Pointee::Metadata 这样的机制把「指针类型 → 元数据类型」的关系表达出来，普通代码不需要直接依赖它，但知道元数据是类型系统的一部分，就能理解为什么胖指针不能随便转成裸指针再转回来——转换中必须保留元数据。

自定义 DST 也有规则可循：结构体最后一个字段可以是 unsized 类型，但前面的字段必须都是 sized，且 unsized 字段必须真的在末尾（否则编译器无法用「固定前缀 + 变长尾部」布局）。例如 struct Packet { len: usize, data: [u8] } 是合法的 DST；由于它的构造通常需要手工分配变长内存，实践中更常见的写法是 struct Packet { len: usize, data: Vec<u8> }，把变长部分交给标准库管理。除非你在写类似 Rc 的底层设施，否则不该自己造 DST。值得注意的是，指向 DST 的 Box 在释放时必须知道总字节数，这个信息来自元数据；元数据丢失就意味着无法正确释放——这也是 unsize 转换必须编译期可知的原因。

指针类型 目标 sized? 指针大小 元数据
&i32 / Box<u8> 是 8 无
&[T] 否 16 元素个数
&str 否 16 字节长度
&dyn Trait 否 16 vtable 指针
指向自定义 DST 的指针 否 16 由 unsized 字段决定
坑这里最容易踩

坑：?Sized 具有传染性。一旦某个泛型参数写成 ?Sized，所有以它为参数的结构体和函数都必须跟着写 ?Sized，而且不能再对它调用 size_of::<T>()、不能按值传递。另一点是 unsized 字段必须是最后一个——把它放在中间会直接编译失败。日常代码里 ?Sized 几乎只出现在标准库式的容器抽象中，普通业务类型不用刻意追求它。

8.3 Pin/Unpin：自引用结构为什么需要地址稳定

考虑一个结构体，它内部有一个指针指向自己的另一个字段：

textRust · 标准库1 行
SelfRef { value: String, ptr: *const String } ptr 指向 self.value

如果把这个结构体按值移动（赋值、作为函数参数传递、放进 Vec 后 Vec 扩容），整个结构体的地址变了，但 ptr 里存的还是旧地址，于是得到一个悬垂指针。这就是**自引用结构（self-referential struct）**的核心难题，也是 async/await 生成的状态机必须面对的问题：一个 future 常常持有对自身其他字段的引用，而 Future::poll 又需要能反复调用。

Pin<P> 给出的解法是「固定住被指向的对象」：一旦一个 !Unpin 类型被 pin 住，安全代码就再也不能把它移走。Unpin 是一个自动 trait，绝大多数类型都实现它（移动它们无害）；显式放入 PhantomPinned 字段的类型则变成 !Unpin，从而受到 pin 约束。Pin<Box<T>> 是最常用的形式——堆上地址天然稳定，把 Box 交给 Pin 就等于承诺「里面的值不再搬家」。

rustRust · 标准库34 行
use std::marker::PhantomPinned;
use std::pin::Pin;
struct SelfRef {
value: String,
ptr: *const String,
_pin: PhantomPinned,
}
impl SelfRef {
fn new(v: &str) -> Self {
Self { value: v.to_string(), ptr: std::ptr::null(), _pin: PhantomPinned }
}
fn init(self: Pin<&mut Self>) {
// SAFETY: 这里只写入 pointer 字段，不移动整个 SelfRef；
// 之后也不会提供任何能移出字段的接口。
let this = unsafe { self.get_unchecked_mut() };
this.ptr = &this.value as *const String;
}
fn value_ptr(self: Pin<&Self>) -> &str {
unsafe { &*self.ptr }
}
}
fn main() {
let mut sr = Box::pin(SelfRef::new("hello"));
sr.as_mut().init();
println!("value = {}", sr.as_ref().value_ptr());
let moved = sr;
println!("after moving the Pin<Box>: {}", moved.as_ref().value_ptr());
}
终端真跑一遍
$ rustc --edition 2021 u08_b3.rs -o u08_b3 && ./u08_b3
value = hello
after moving the Pin<Box>: hello

两处 unsafe 都需要解释。get_unchecked_mut() 之所以安全，是因为我们只改写了 ptr 字段，没有把 SelfRef 本身移出 pin；value_ptr 里解引用裸指针之所以安全，是因为 pin 保证 value 的地址在初始化之后不再变化，且该结构体没有提供任何移动它的安全接口。Pin 不是一个运行时检查，而是一组编码在类型里的承诺；unsafe 代码的职责就是维护这个承诺。

Pin 的常用入口有三种。Pin::new 只对 Unpin 类型可用，是安全构造；Box::pin 在堆上分配并固定，适用于所有类型；Pin::new_unchecked 是 unsafe，调用者必须自己保证地址稳定。Future::poll 的签名 fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<T> 正是这套机制的应用点：async 块生成的状态机被 pin 后，才能安全地在字段之间持有自引用。业务代码几乎不需要手写 Pin——pin! 宏和 Box::pin 覆盖了绝大多数需求，自己写 unsafe pin projection 则是库作者的任务。

坑这里最容易踩

坑：不要把 Pin 误解成「让对象绝对不能动」。对于 Unpin 类型，Pin::get_mut 可以直接拿到 &mut T 并移走它——pin 对它们没有约束力。只有当类型是 !Unpin 时，pin 才真正锁死移动；这也是 PhantomPinned 存在的意义。另一个常见错误是「pin projection」：想对 pin 住的某个字段取 Pin<&mut Field>，需要 pin-project 这类工具或手写 unsafe，直接 &mut self.field 会破坏 pin 的承诺。

8.4 方差深入：协变、逆变与不变

生命周期可以像类型一样构成子类型关系：'static 比任何局部生命周期都长，记作 'static : 'a（「'static outlives 'a」），也可以说 'static <: 'a。方差（variance） 描述的是：当一个类型里的生命周期变短时，整个类型是变得「更一般」还是「更特殊」，抑或完全不能变。

三种方差的直觉如下。协变（covariance）：&'a T、Vec<T>、Option<T> 对 'a 或 T 协变——能接受 'static 的地方也能接受更长的生命周期，反过来不行。逆变（contravariance）：函数参数类型 fn(&'a T) 对 'a 逆变——一个能处理「任意生命周期引用」的函数，可以当作只处理 'static 的函数用，反过来不行。不变（invariance）：&'a mut T 对 T 不变，Cell<T>、UnsafeCell<T> 对 T 不变——因为读写操作要求类型参数精确一致。

rustRust · 标准库13 行
fn shorten<'a>(long: &'static str, short: &'a str) -> &'a str {
if long.len() < short.len() { long } else { short }
}
fn main() {
let local = String::from("hi");
println!("covariant result = {}", shorten("static", &local));
let mut binding = String::from("mutable");
let r: &mut String = &mut binding;
let len = r.len();
println!("&mut String len = {len}");
}
终端真跑一遍
$ rustc --edition 2021 u08_b4.rs -o u08_b4 && ./u08_b4
covariant result = hi
&mut String len = 7

shorten 能编译，正是因为 &'static str 协变：返回值需要 &'a str，而 'static 比 'a 长，可以作为更短生命周期的子类型返回。换个方向就不行——下面的例子试图把局部字符串的引用写进一个 &'static str 的槽位，编译器拒绝：

方差不是手写出来的，而是编译器根据类型定义推导出来的：它检查每个参数出现在什么位置（只读、只写、既读又写），据此赋予协变、逆变或不变。自定义类型若推导结果不符合预期，可以用 PhantomData<fn() -> T>（协变）、PhantomData<fn(T) -> ()>（逆变）或 PhantomData<Cell<T>>（不变）来「声明」期望的方差——这种技巧主要出现在 unsafe 代码和底层库中，用来防止误用。

为什么需要不变性？考虑 &mut &'a str：如果它对 'a 协变，就可以把 &mut &'static str 当作 &mut &'short str 传入函数，函数往里写入一个短命引用，调用方却以为里面还是 'static——悬垂引用就产生了。因此 &mut T 对 T 必须不变；同理 Cell<T> 因为提供 set，也必须对 T 不变。这是方差规则背后的核心动机：不让写操作破坏类型系统对生命周期的承诺。

类型构造子 对生命周期/参数的方差 原因
&'a T 对 'a 和 T 协变 只读
&'a mut T 对 'a 协变、对 T 不变 可写会破坏别名安全
fn(&'a T) 对 'a 逆变 参数位置反转方向
Cell<T> / UnsafeCell<T> 对 T 不变 内部可变性
Vec<T> / Option<T> 对 T 协变 只拥有值，不提供写入借出引用
大白话先用直觉把它讲通

协变像「长绳可以当短绳用」——你有一根十米绳，需要一米绳时当然够；逆变像「能修所有型号机器的师傅，可以派去只修 A 型号」；不变像「专门装 A 型号零件的盒子，不能塞 B 型号进去」，因为一旦塞错，以后取出来的人会按 A 型号的用法用它，就要出事。

8.5 trait solver 直觉：impl 匹配是一次证明搜索

写 x.foo() 或给函数加 T: Trait 约束时，编译器要做的事可以看成一次证明搜索：目标是证明 Type: Trait 成立。它遍历所有可见的 impl，尝试把 impl 的头部与当前目标统一（unify）；匹配成功后，再把 impl 的 where 子句变成新的子目标，递归求解。只有找到唯一成功的证明路径，调用才被接受。

rustRust · 标准库18 行
#![allow(dead_code)]
trait Marker { fn tag(&self) -> &'static str; }
impl<T: std::fmt::Debug> Marker for T {
fn tag(&self) -> &'static str { "debug-value" }
}
struct Plain;
fn main() {
println!("{}", 7.tag());
println!("{}", vec![1, 2].tag());
println!("{}", need_marker(7i32));
// need_marker(Plain); // 取消注释会报错：Plain 不满足 Marker 的 blanket impl 前提
}
fn need_marker<T: Marker>(x: T) -> &'static str { x.tag() }
终端真跑一遍

debug-value

parse() 对任何实现 FromStr 的类型都能工作，候选有无数个；unwrap() 又要求错误类型实现 Debug。求解器既不能枚举无穷候选，也不愿随便选一个（选择必须是确定的），于是报 E0284。补上 let n: i32 = ... 就给了它唯一的锚点。

这个模型解释了前面几节的许多规则：coherence 保证 impl 集合无重叠，所以候选唯一；orphan rule 保证不同 crate 的 impl 能拼成全局一致的集合；而「更具体的 impl 优先」不被支持，是因为在泛型上下文里「具体」无法判定。当递归 impl 形成环时，求解器还有深度上限，超出会报 E0275「overflow evaluating the requirement」。读懂错误里 note 的「required by」链条，基本就能定位是哪一个子目标断了。

还有一个实用概念叫「where 子句的传递」。在 fn f<T: Marker>(x: T) 里调用 x.tag()，编译器把约束 T: Marker 当作已知事实，不再继续展开它；只有真正要调用时，才在调用点检查具体类型能否满足。这解释了一个常见困惑：泛型函数体里看似「没有 impl」也能编译，因为约束本身就是承诺；而错误总是在具体调用点出现。Rust 的 trait 系统之所以能在缺乏完整类型信息时仍给出有意义的检查，靠的就是这种「定义处验证结构、实例化处验证事实」的两阶段分工。

8.6 macro_rules!：在 token 层写生成规则

macro_rules! 是 Rust 的声明式宏，工作在 token 层而非字符串层：它把输入按 token 树匹配，再按模板展开成新的 token 树。这与 C 预处理器拼接文本有本质区别——宏不会破坏语法结构，也不会把标识符错误地粘在一起。语法由两部分组成：=> 左边是 matcher（匹配模式），右边是 transcriber（展开模板）。

matcher 里 $(...),* 表示「逗号分隔、重复零次或多次」，$(;)* 换成任意分隔符，$(,)? 表示可选尾随逗号。transcriber 里的 $(...)* 必须与 matcher 中的重复层级对应，否则编译器会报「变量仍然重复」之类的错误。匹配片段还可以指定类型：expr（表达式）、ty（类型）、ident（标识符）、path（路径）、literal（字面量）、block（块）等；选得越精确，宏展开后越不容易破坏语法结构。例如下面的 $t:ty 保证调用方写的是类型，$label:expr 保证是表达式。

rustRust · 标准库4 行
macro_rules! identity {
($e:expr) => { $e };
}
fn main() { println!("{}", identity!(1 + 2)); }

这个最小例子说明宏必须接收完整的 token 树：若写成 identity!(1 +)，matcher 会在解析阶段就拒绝，而不是等到展开后产生语法错误。下面的宏一次性为多种类型生成 trait impl，展示了「宏能做的事函数做不到」——函数在运行时工作，宏在编译期生成代码。

rustRust · 标准库30 行
trait Describe { fn describe(&self) -> String; }
macro_rules! impl_describe {
($($t:ty => $label:expr),+ $(,)?) => {
$(
impl Describe for $t {
fn describe(&self) -> String {
format!("{} = {}", $label, self)
}
}
)+
};
}
impl_describe!(u32 => "整数", i64 => "大整数", String => "字符串");
macro_rules! double {
($x:expr) => {{
let tmp = $x;
tmp + tmp
}};
}
fn main() {
println!("{}", 7u32.describe());
println!("{}", 9i64.describe());
println!("{}", String::from("hi").describe());
let tmp = 100;
println!("double = {}, tmp = {}", double!(21), tmp);
}
终端真跑一遍
$ rustc --edition 2021 u08_b6.rs -o u08_b6 && ./u08_b6
整数 = 7
大整数 = 9
字符串 = hi
double = 42, tmp = 100

double! 演示了 hygiene（卫生性）：宏内部引入的局部变量 tmp 与调用方作用域里的 tmp 属于不同的语法上下文，不会互相遮蔽或冲突，所以 tmp 仍然是 100。对于路径，$crate 提供类似的卫生性——在宏里引用自己 crate 的项时写 $crate::foo，就能在下游 crate 中正确解析，而不是误指向下游同名项。

坑这里最容易踩

坑：宏展开后的错误信息通常指向调用点，而且类型推断能被宏打断，调试体验远不如普通函数。不要用它做「本来用函数就能解决」的事。适合宏的场景是：变长参数列表、需要生成 impl/struct 定义、需要接受标识符作为语法片段、需要把重复样板压缩成一行。写复杂宏时，先写一份展开后的目标代码，再倒推 matcher，比直接写宏容易得多。

8.7 const generics：把值提升到类型参数

泛型参数传统上只能是类型或生命周期。const generics 让值也能成为类型参数，条件是它的类型受限于整数、bool、char 等编译期可知的类别。最典型的例子是数组：[T; N] 里的 N 就是一个 const 参数。fn sum<const N: usize>(a: [i32; N]) 让同一个函数能服务于所有长度，同时保持编译期长度信息。

rustRust · 标准库22 行
fn sum<const N: usize>(a: [i32; N]) -> i32 {
a.iter().sum()
}
#[derive(Debug)]
struct Matrix<T, const R: usize, const C: usize> {
data: [[T; C]; R],
}
impl<T: Default + Copy, const R: usize, const C: usize> Matrix<T, R, C> {
fn new() -> Self {
Self { data: [[T::default(); C]; R] }
}
}
fn main() {
println!("sum3 = {}", sum([1, 2, 3]));
println!("sum4 = {}", sum([0; 4]));
let m: Matrix<i32, 2, 3> = Matrix::new();
println!("matrix = {:?}", m);
println!("shape = {}x{}", m.data.len(), m.data[0].len());
}
终端真跑一遍
$ rustc --edition 2021 u08_b7.rs -o u08_b7 && ./u08_b7
sum3 = 6
sum4 = 0
matrix = Matrix { data: [[0, 0, 0], [0, 0, 0]] }
shape = 2x3

和类型泛型一样，const 泛型在单态化时按值展开：sum::<3> 与 sum::<4> 是不同的机器码实例，因此长度信息能被优化器利用。注意 sum([0; 4]) 可以——数组表达式 [0; 4] 的长度是字面量，编译器能推断 N = 4。

const generics 的边界也很明确。min const generic expressions（最小 const 泛型表达式） 尚未稳定，所以不能写「把泛型值当表达式计算」这样的签名：

textRust · 标准库1 行
fn grow<const N: usize>(a: [i32; N]) -> [i32; N + 1] { ... } // 目前不稳定

因为 N + 1 需要编译器对泛型 const 求值，这牵涉到溢出、相等性判断等复杂语义。目前的替代方案是返回 Vec<T>、把长度运算放到运行时，或者使用类型级别的技巧（如 typenum）。另外，const 参数要求的值必须是「结构相等」可用的类型——浮点数和自定义结构体一般不能作为 const 泛型参数。const 参数也能出现在 trait 与 impl 上：trait Storage<const N: usize> 让不同容量的存储实现同一套接口，impl<const N: usize> Storage<N> for [u8; N] 一次覆盖所有长度。这类写法在嵌入式与密码学代码里很常见，因为它能把「缓冲区必须恰好 32 字节」这样的约束写进类型，越界使用直接编译失败，而不是留到运行时检查。代价是类型名变长、错误信息更难读，而且每个不同的 N 都会单态化出一份代码——与类型泛型一样，要留意代码体积。

机制 参数是什么 何时确定 典型用途

8.8 把这些机制放回工程语境

这一单元讲的六件事，出现的频率并不相同。方差与 trait solver 你不会「主动使用」，但它们每天都在解释编译器的行为：为什么这个借用报错、为什么类型推断不出来。DST 与 ?Sized 多数时候藏在标准库背后；Pin 由 async 生态替你打理；宏与 const generics 则是库作者在明确收益时才拿出的工具。

判断是否需要动用它们的标准也很朴素：先让类型表达清楚，再看编译器报什么。遇到「类型必须已知」「借用不够长」「trait 未实现」这类错误时，用本单元的模型倒推：信息不足就补类型标注（solver）；生命周期不够长就检查协变/不变的转换是否合法（方差）；自引用解决不了就让对象待在堆上（Pin）。反之，为了「显得高级」而在业务代码里引入宏或自定义 DST，往往得不偿失。

特别值得强调的是 unsafe 的边界。Pin 与 DST 的底层构造都涉及裸指针和 unsafe，但本单元给出的用法把 unsafe 限制在极小的局部：两处 unsafe 都有明确的不变量说明，且 unsafe 之外仍然是安全接口。这是 Rust 处理底层机制的典型方式——把危险封装成安全抽象，并用类型系统维护抽象的边界。理解边界在哪，比掌握某个具体技巧更能决定代码质量。

最后，把这八节连起来看：从枚举的 niche 布局到第 3 节的借用检查、从单态化/vtable 到闭包捕获与迭代器优化，再到本单元的 DST/Pin/方差/求解器，Rust 的类型系统始终围绕同一个目标运转——把尽可能多的程序性质变成编译期可验证的事实，并把确实无法静态决定的部分，用显式的、局部的、有契约的机制（胖指针、Pin、unsafe 块）安放好。这套一致性，才是它值得深入学习的原因。
