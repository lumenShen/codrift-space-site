15.1 项目全貌与依赖取舍

这一单元不再讲孤立的概念，而是把前面几编的工程机制落到一个能真正运行的小工具上。目标是一个极简的笔记管理器：支持新增、列出、标记完成，配置文件决定数据文件位置与日志级别。刻意保持功能小，是为了让每个 crate 的职责边界看得清楚——参数解析归 clap，配置反序列化归 serde，可观测性归 tracing，错误上下文归 anyhow。

选这四个 crate 还有一层考虑：它们都是各自领域的事实标准，文档与社区资源丰富，遇到问题容易查到答案。Rust 生态里有不少功能相似的库，但"能跑起来"和"长期可维护"是两回事。对工程开发者而言，依赖的稳定性、维护活跃度、与工具链的兼容性往往比某个 API 更漂亮更重要。本单元刻意不引入数据库、HTTP 客户端或配置中心，因为这些会把主线淹没在基础设施细节里。

目录结构如下。这是 _verify/cli-app/ 下真实验证过的布局，不是示意。

对应的依赖清单如下。clap 打开 derive feature 才能用 #[derive(Parser)]；serde 同样需要 derive；serde_json 负责把配置与数据落盘；tracing-subscriber 的 env-filter feature 让日志级别可以通过字符串配置。

tomlRust · 标准库12 行
[package]
name = "notes-cli"
version = "0.1.0"
edition = "2021"
[dependencies]
anyhow = "1"
clap = { version = "4", features = ["derive"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }

依赖取舍上有一条经验：应用可以直接依赖高层 crate（anyhow、tracing-subscriber），库则应尽量只依赖最小集合并把错误类型暴露给上层。本项目里 config.rs 与 store.rs 虽然也用了 anyhow，但它们都在同一个二进制 crate 内，不涉及对外 API 稳定性。如果拆成库，就应该改用 thiserror 定义领域错误。

四个 crate 的职责边界可以用一张表固定下来。表里"失败时的表现"一列尤其有用：它提醒我们参数错误应该在进程启动阶段就被拦下，而数据损坏必须作为可恢复错误交给 main 处理。

crate 负责 不负责 失败时的表现
clap 参数建模、帮助文本、类型校验 业务逻辑、配置 打印用法并退出
serde 结构与 JSON 的双向转换 文件定位、错误解释 返回解析错误
tracing 事件采集、级别过滤、格式化 业务决策 静默降级
anyhow 附加上下文、组织错误链 定义领域错误变体 打印 Caused by 链

版本约束都写成主版本号（clap = "4"、serde = "1"），这是 crates.io 上最常见的做法，既允许兼容性更新，又避免意外跨越大版本。Cargo.lock 会锁定实际解析出的版本，二进制项目应当把它提交进仓库；本单元的真实构建解析到 clap 4.6.9、serde 1.0.229、tracing-subscriber 0.3.23 等版本，全部记录在项目目录里。库项目通常不提交锁文件，因为下游需要自行解析；这个差别经常让初学者困惑，记住"二进制要锁，库不锁"就够了。

cargo build --release 的真实输出显示整个依赖图在 16.30 秒内编译完成，其中 clap 的派生宏与 tracing-subscriber 的过滤器占了相当一部分。这个数字不是重点，重点是它说明"引入四个高层 crate"在现代 Rust 工程里是很轻的决定——编译成本可以接受，换来的是大量经过实战检验的基础设施。

大白话先用直觉把它讲通

写 CLI 就像开一家小餐馆。clap 是点菜单，客人怎么点都被整理成固定的格式；serde 是进货单，把外面送来的原始材料变成厨房认识的样子；tracing 是监控摄像头，出事时能回看；anyhow 是事故报告，把"哪一步、因为什么失败"写在一起。四个角色各管一摊，谁也不抢谁的活。

15.2 clap：把命令行变成类型

clap 的 derive API 核心是"结构体即接口"。#[derive(Parser)] 把字段映射成选项或位置参数，#[command(subcommand)] 字段映射成子命令。下面这段是 src/main.rs 的完整内容，已经用 cargo build --release 真编译通过。

rustRust · 标准库67 行
mod config;
mod store;
use anyhow::Result;
use clap::{Parser, Subcommand};
use config::Config;
use std::path::PathBuf;
use store::Store;
use tracing_subscriber::EnvFilter;
#[derive(Debug, Parser)]
#[command(name = "notes", version, about = "真实 CLI：clap + serde + tracing + anyhow")]
struct Cli {
/// 配置文件路径
#[arg(long, global = true)]
config: Option<PathBuf>,
/// 覆盖日志级别，例如 debug
#[arg(long, global = true)]
log: Option<String>,
#[command(subcommand)]
command: Command,
}
#[derive(Debug, Subcommand)]
enum Command {
/// 新增一条笔记
Add { title: String },
/// 列出所有笔记
List,
/// 标记完成
Done { id: usize },
}
fn main() -> Result<()> {
let cli = Cli::parse();
let cfg = Config::load(cli.config.as_deref())?;
let level = cli.log.as_deref().unwrap_or(&cfg.log_level);
tracing_subscriber::fmt()
.with_env_filter(EnvFilter::new(level))
.with_target(false)
.with_ansi(false)
.init();
tracing::debug!(?cli, "命令行参数解析完成");
tracing::info!(store = %cfg.store, "配置已加载");
let mut store = Store::open(&cfg.store)?;
match cli.command {
Command::Add { title } => {
let note = store.add(title)?;
println!("added #{} {}", note.id, note.title);
}
Command::List => {
let notes = store.list();
if notes.is_empty() {
println!("(empty)");
}
for n in notes {
println!("{} [{}] {}", n.id, if n.done { "x" } else { " " }, n.title);
}
}
Command::Done { id } => {
store.finish(id)?;
println!("done #{}", id);
}
}
Ok(())
}

几个设计点值得展开。global = true 让 --config 与 --log 可以写在子命令前后任意位置，这对使用者很友好；如果省掉它，选项就必须紧跟在主命令之后。Option<PathBuf> 表达"可给可不给"，usize 让 clap 自动拒绝负数与非法字符串——参数校验在解析阶段就完成，业务代码拿到的一定是合法类型。文档注释直接变成帮助文本，因此不需要再维护一份说明。注意 Cli::parse() 在参数非法时会自动打印帮助并退出进程，这是 CLI 的正确行为，库代码不应模仿。

参数解析的失败路径也值得验证。给 done 传一个非数字时，clap 会打印带具体错误原因的提示，并指出期望的类型；这比让业务代码用 parse::<usize>() 再自己拼错误信息可靠得多。真正的工程收益在于：参数错误的处理代码完全不需要写，clap 把它统一成一致的体验。需要自定义校验时，优先用 value_parser 把约束前移到解析阶段，而不是在 match 分支里返回错误——前者的失败发生在程序做任何其他事情之前，不会产生半成品状态。

还看到一个细节：#[command(name = "notes", version, ...)] 决定了 --version 输出的是 notes 0.1.0，但可执行文件名仍是 notes-cli.exe（由包名决定）。帮助文本里的 Usage: 用的是真实文件名。这种"展示名与文件名不同"是允许的，但文档里要说清，否则使用者会困惑。

derive 宏还解决了另一类问题：参数命名为 CLI 风格而字段命名为 Rust 风格。--log-level 会自动映射到字段 log_level，不需要手写转换。需要限制取值范围时可以用 value_parser，例如把 id 字段声明为 usize 已经排除负数，再配合枚举类型就能把字符串限制在固定集合内。子命令用枚举表示还带来一个额外好处：穷尽性检查保证新增子命令时编译器会提示你补上对应的 match 分支，不会出现"帮助里显示了但执行时什么都没做"的功能。这种"类型系统替你检查 UI 完整性"的体验，是 derive API 最值得保留的部分。

15.3 serde：配置加载与默认值

配置文件是最容易被低估的部分。下面这段 src/config.rs 展示了三个关键决定：#[serde(default)] 让缺失字段回落到 Default 实现，with_context 给 IO 与解析错误加上"是哪个文件"的上下文，日志事件放在加载之后——因为日志订阅器还没初始化时发出的事件会丢失。

rustRust · 标准库37 行
use anyhow::{Context, Result};
use serde::Deserialize;
use std::path::Path;
#[derive(Debug, Deserialize)]
#[serde(default)]
pub struct Config {
pub store: String,
pub log_level: String,
}
impl Default for Config {
fn default() -> Self {
Self {
store: "notes.json".into(),
log_level: "info".into(),
}
}
}
impl Config {
pub fn load(path: Option<&Path>) -> Result<Self> {
match path {
None => {
tracing::debug!("未指定配置文件，使用默认值");
Ok(Self::default())
}
Some(p) => {
let text = std::fs::read_to_string(p)
.with_context(|| format!("读取配置文件 {} 失败", p.display()))?;
let cfg: Config = serde_json::from_str(&text)
.with_context(|| format!("解析配置文件 {} 失败", p.display()))?;
Ok(cfg)
}
}
}
}

#[serde(default)] 放在结构体上表示"任何缺失字段都用 Default::default() 对应字段"。如果只给某个字段加，就写成 #[serde(default = "default_store")] 并单独提供函数。两者的取舍在于：结构体级默认简洁，但新增字段时必须同步更新 Default 实现；字段级默认更显式，适合字段之间相对独立的配置。

配置格式的另一个选择是 TOML。如果用 toml crate，清单会变成 toml = "0.8"，反序列化代码完全不变——这正是 serde 抽象的价值。JSON 的优势是生态通用、容易用其他语言生成；TOML 的优势是可读性与注释。本项目选 JSON 是因为数据文件也用它，减少一个依赖。

serde 的常用属性还有几个值得记住。#[serde(rename_all = "kebab-case")] 让 Rust 的 log_level 对应 JSON 的 log-level；#[serde(flatten)] 把嵌套结构摊平到同一层；#[serde(skip_serializing_if = "Vec::is_empty")] 在序列化时省略空数组。反序列化失败时的错误信息会包含行号与列名，这正是前面错误链里那段 key must be a string at line 1 column 2 的来源。配置结构应当尽量扁平且只包含基本类型：嵌套越深，用户手写配置时越容易出错，而 serde 能给出的定位信息也越有限。最后一点：默认值与显式零值要区分清楚，缺失字段走 Default，写了 0 就按 0 处理，不要混淆两者。

坑这里最容易踩

这里是坑：把日志初始化放在配置加载之后，会导致配置加载过程中的日志事件丢失。本项目里 Config::load 在没有配置文件时发出的 debug! 就落在订阅器初始化之前，因此 --log debug 也看不到它。这是真实现象：只有 main 里初始化之后的那条 debug!(?cli, ...) 会出现。解决办法是先用一个最小订阅器初始化，再根据配置重新配置；或者在解析命令行后先初始化一个临时订阅器。对多数 CLI 来说，把关键信息放到初始化之后的事件里更简单。

15.4 tracing：结构化日志而不是 println

println! 与日志的差别不只是"能不能关掉"。日志带级别、目标、结构化字段，并且可以被过滤与聚合。下面的初始化链做了几件事：EnvFilter::new(level) 把字符串（如 debug）转成过滤规则；with_target(false) 隐藏模块路径让输出短一些；with_ansi(false) 关闭颜色，保证 CI 日志与重定向到文件时没有转义序列；init() 把它设为全局默认订阅器。关闭 ANSI 是本单元在真实运行中刻意加入的调整：最初的日志带有彩色转义序列，直接贴进文档或 CI 报告会变成乱码，关掉之后输出干净且可复现。

tracing::info!(store = %cfg.store, "配置已加载") 是一条结构化事件：消息是固定的，变量以键值对形式单独携带。这样日志系统可以按字段过滤、聚合，而不是靠正则去解析文本。% 表示用 Display 格式化，若换成 ? 则用 Debug；对 PathBuf 这类类型通常用 Display 更易读。

tracing 还有 span 这一层，它表示"一段时间范围"而不是单个事件。例如把一次 Store::open 包成 #[tracing::instrument]，进入与退出时都会自动记录事件，并带上耗时。事件在 span 内部发生时会自动携带 span 的字段，因此同一个请求的所有日志可以串起来。本项目功能简单，只用事件就够；一旦引入并发或多步骤流程，span 的价值会迅速显现。

用 --log debug 覆盖配置里的 warn，可以立刻看到更多信息——这在排查线上问题时非常有用，因为不需要重新编译或改配置文件。下面是真实运行输出，时间戳来自 tracing-subscriber 的默认格式。

日志级别的选择本身也有工程含义。error 只记录必须处理的问题，warn 记录可疑但不致命的情况，info 记录关键生命周期事件（启动、配置加载、任务完成），debug 记录排查用的细节，trace 记录高频内部状态。CLI 的默认级别通常设为 warn 或 info：太吵会淹没业务输出，太安静会让使用者不知道程序在做什么。把级别做成命令行选项，等于把决定权交给使用者。

15.5 anyhow：错误链与边界

anyhow::Result 是 Result<T, anyhow::Error> 的别名。Error 类型内部保存一个错误链：最外层是我们用 with_context 添加的解释，里层是真正的 IO 错误或解析错误。当 main 返回 Result<()> 时，Rust 会用 Debug 打印错误，而 anyhow 的 Debug 实现会把整条链漂亮地展开。

下面这段来自 src/store.rs。ok_or_else 把"找不到 id"转换成领域错误，with_context 给文件操作加上下文。注意 save 用 serde_json::to_string_pretty 而非 to_string：数据文件会被人打开查看，可读性比几个字节更重要。

rustRust · 标准库65 行
use anyhow::{anyhow, Context, Result};
use serde::{Deserialize, Serialize};
use std::path::{Path, PathBuf};
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Note {
pub id: usize,
pub title: String,
pub done: bool,
}
#[derive(Debug, Default, Serialize, Deserialize)]
struct Db {
next_id: usize,
notes: Vec<Note>,
}
pub struct Store {
path: PathBuf,
db: Db,
}
impl Store {
pub fn open(path: impl AsRef<Path>) -> Result<Self> {
let path = path.as_ref().to_path_buf();
let db = if path.exists() {
let text = std::fs::read_to_string(&path)
.with_context(|| format!("读取存储 {} 失败", path.display()))?;
serde_json::from_str(&text)
.with_context(|| format!("解析存储 {} 失败", path.display()))?
} else {
Db::default()
};
Ok(Self { path, db })
}
pub fn add(&mut self, title: String) -> Result<Note> {
if title.trim().is_empty() {
return Err(anyhow!("标题不能为空"));
}
self.db.next_id += 1;
let note = Note { id: self.db.next_id, title, done: false };
self.db.notes.push(note.clone());
self.save()?;
Ok(note)
}
pub fn list(&self) -> &[Note] {
&self.db.notes
}
pub fn finish(&mut self, id: usize) -> Result<()> {
let note = self.db.notes.iter_mut()
.find(|n| n.id == id)
.ok_or_else(|| anyhow!("没有 id={} 的笔记", id))?;
note.done = true;
self.save()
}
fn save(&self) -> Result<()> {
let text = serde_json::to_string_pretty(&self.db)?;
std::fs::write(&self.path, text)
.with_context(|| format!("写入存储 {} 失败", self.path.display()))
}
}

15.6 错误链在终端上长什么样

错误链的价值只有在真实失败时才看得出来。下面是三种失败路径的真实输出：配置文件不存在、配置 JSON 损坏、目标 id 不存在。每一行 Caused by 都对应链上的一层，最内层保留了操作系统原始错误或 serde 的具体位置。

$ ./target/release/notes-cli.exe --config settings.json done 99
Error: 没有 id=99 的笔记

注意第三条没有 Caused by：它是用 anyhow! 直接构造的领域错误，没有更底层的原因。这种分层很合理——领域错误本身已经足够表达问题，强行再包一层只会让输出变噪。

错误链可以从代码里遍历：anyhow 的 Error::chain() 返回一个迭代器，从最外层依次走到最内层；downcast_ref::<io::Error>() 则尝试取出某个具体类型。CLI 通常只需要打印，但库代码可能需要根据底层错误做恢复——例如区分"文件不存在"和"权限不足"时，链遍历就派上用场。日志里打印错误链时要用 {:#} 格式（Debug 的替代展示），否则只会看到最外层一句话。本项目依赖 main 的默认打印行为，所以没有额外写日志错误的代码。

库与应用的分工在这里体现得很清楚：如果 config.rs 是一个独立库，它应该定义 ConfigError::{Io, Parse} 这样的 thiserror 枚举，让调用方可以按变体匹配；作为应用内部的模块，用 anyhow 加上下文更省事。选择标准是"有没有人需要以编程方式区分错误"——有就用领域错误，没有就用 anyhow。

错误处理的另一条纪律是"尽早失败，但不要在底层 panic"。Store::add 对空标题返回错误而不是 assert!，因为用户输入是外部数据；Store::open 对损坏的文件返回带上下文的错误，而不是让 serde 的 panic 冒出来。相对地，程序内部的逻辑不变量（例如 next_id 不应倒退）可以用 assert!，因为它们反映的是代码 bug 而非输入问题。把这个边界画清楚，日志与错误就不会互相打架：错误链负责解释"为什么这次操作失败"，日志负责记录"发生了什么"，二者不要互相替代。

坑这里最容易踩

这里是坑：anyhow! 与 Context 很方便，但不要在库 API 里把 anyhow::Error 作为公开返回类型。它没有结构化变体，调用方只能打印字符串，无法针对不同错误做恢复。另一个坑是在循环里反复 with_context，会让错误链变得很长且重复；只在跨越模块边界的地方加一次上下文通常就够了。

15.8 测试与工程化收尾

一个能跑的 CLI 还不足以称为工程化产物，测试是下一步。下面这段集成测试直接调用 Store 的公开方法，验证"新增后 id 递增"与"标记完成后可从列表看到"两个行为。它用临时目录避免污染开发数据，是文件型存储测试的标准做法。

rustRust · 标准库25 行
#[cfg(test)]
mod tests {
use super::*;
use std::fs;
fn temp_db(name: &str) -> std::path::PathBuf {
let mut p = std::env::temp_dir();
p.push(format!("notes-cli-test-{name}.json"));
let _ = fs::remove_file(&p);
p
}
#[test]
fn add_and_finish() {
let path = temp_db("add");
let mut store = Store::open(&path).unwrap();
let a = store.add("A".into()).unwrap();
let b = store.add("B".into()).unwrap();
assert_eq!((a.id, b.id), (1, 2));
store.finish(1).unwrap();
assert!(store.list()[0].done);
assert!(!store.list()[1].done);
let _ = fs::remove_file(&path);
}
}

测试分层要清楚：clap 的参数解析通常靠向二进制传参的集成测试验证；serde 的配置与数据往返适合单元测试；main 里的日志初始化使用全局状态，不适合在单元测试里反复调用。把逻辑下沉到 config.rs 与 store.rs，会让大部分行为都能在不启动进程的情况下测试。CI 里至少跑 cargo test --all-features 与 cargo clippy --all-targets -- -D warnings；前者覆盖所有路径，后者防止警告堆积。上面这段测试已经在本项目中真实运行通过，输出为 test result: ok. 1 passed; 0 failed。

临时文件测试有个常见坑：不同测试并行运行时如果共用同一个文件名，会互相删除对方的数据。用测试名做文件名前缀只是权宜之计，更稳妥的做法是让每个测试创建独立临时目录，或用 tempfile crate 自动管理生命周期。另一个细节是测试结束后的清理：即使断言失败也要删除临时文件，否则连续运行几次后 temp_dir() 会积累一堆垃圾。把这些基础工作做好，测试才会成为可信赖的门禁而不是偶发失败的来源。

动手动脑

  • 给 CLI 增加 search <关键词> 子命令：用 Iterator::filter 在 Store::list() 上筛选标题，返回匹配项；为它写一条集成测试。
  • 把配置格式从 JSON 换成 TOML：只改 Cargo.toml 与 config.rs 的反序列化调用，观察其他模块是否完全不用改。记录真实编译输出。
  • 让 Store::save 先写临时文件再原子重命名，避免进程中断留下半个 JSON。用一次人工中断测试验证旧文件仍然可读。

把四层职责分开之后，代码评审也变得更容易：参数问题只看 main.rs 的类型定义，配置问题只看 config.rs，数据问题只看 store.rs。这种"按关注点切分"的习惯，比把所有事情塞进一个 main 函数要耐久得多。随着功能增长，这个好处会越来越明显，重构时也不容易牵一发而动全身。
