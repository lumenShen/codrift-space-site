19.1 并查集的不变量与迭代 find

问题定义：维护一组不相交集合，支持判断两个元素是否属于同一集合（查询），以及把两个集合合并（更新）。典型场景是动态连通性：边逐条加入，随时要回答"这两个点连通吗"。

不变量：给每个元素一个 parent 指针，每棵树的根代表整个集合。沿着 parent 一路向上走必然到达根，同集合元素的根相同。合并时只改一个根的 parent，不碰其他节点——这是并查集高效的根本原因：一次操作只动 O(1) 个指针。

裸的 find 在链状树上可能退化成 O(n)，所以必须做两件事。路径压缩：find 过程中把沿途所有节点直接挂到根下，让树高度趋近 1。按秩合并：始终让节点数少（或高度小）的树挂到另一棵下面，避免长链。两者叠加后，单次操作的摊还复杂度是反阿克曼函数 α(n)，在实际数据规模下不超过 5，可以当作常数。

Rust 里要把 find 写成两趟迭代而非递归。第一趟顺着 parent 找根；第二趟把沿途节点改挂到根下。第二趟里必须先用 let next = self.parent[cur]; 把下一个节点存到局部变量，再写 self.parent[cur] = root，否则链路会被提前改乱，导致后续节点找不到原来的根。递归版在深链上会占用大量栈帧，虽然路径压缩后链很短，但在压缩发生之前仍可能很深；迭代版完全不碰调用栈。

struct UnionFind {
parent: Vec<usize>,
rank: Vec<u32>,
comps: usize,
}
impl UnionFind {
fn new(n: usize) -> Self {
UnionFind {
parent: (0..n).collect(),
rank: vec![0; n],
comps: n,
}
}
fn find(&mut self, x: usize) -> usize {
let mut root = x;
while self.parent[root] != root {
root = self.parent[root];
}
let mut cur = x;
while self.parent[cur] != cur {
let next = self.parent[cur];
self.parent[cur] = root;
cur = next;
}
root
}
fn union(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
if ra == rb {
return false;
}
if self.rank[ra] < self.rank[rb] {
self.parent[ra] = rb;
} else if self.rank[ra] > self.rank[rb] {
self.parent[rb] = ra;
} else {
self.parent[rb] = ra;
self.rank[ra] += 1;
}
self.comps -= 1;
true
}
fn connected(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
ra == rb
}
}
fn main() {
let mut uf = UnionFind::new(6);
for (a, b) in [(0usize, 1usize), (1, 2), (3, 4), (4, 5)] {
uf.union(a, b);
}
println!("components = {}", uf.comps);
println!("0~2 connected = {}", uf.connected(0, 2));
println!("0~5 connected = {}", uf.connected(0, 5));
}

connected 里刻意把两次 find 的结果先存进局部变量再比较。写成 self.find(a) == self.find(b) 通常也能编译，但拆开写能避免"同一表达式里两次可变借用 self"的隐患，意图也更清楚。union 返回 bool 表示这次合并是否真的发生——这个返回值非常有用，下一节就靠它统计连通块数量。

一个初学者常问的问题是：为什么 find 需要 &mut self？因为路径压缩会修改 parent 数组——查询本身也是一次"写操作"。这与很多语言里"查询就是只读"的直觉不同，但在 Rust 里反而顺理成章：类型签名准确反映了副作用，调用方一眼就知道这个方法会动内部结构。如果确实需要只读查询（例如在同一个表达式里对两个不同元素调用），可以写一个不压缩的 find_readonly(&self) -> usize 作为补充，但代价是可能遇到深链，通常没必要。编号约定也要统一：题目给出 1 到 n 的编号时，要么读入后整体减一转成 0 基，要么把数组开成 n + 1 并浪费 0 号位，两种做法都行，但绝不能混用。

大白话先用直觉把它讲通

并查集就像给一堆人分小组，每组选一个组长。要问两个人是不是同组，就顺着"我的组长是谁"一路问上去，看最后是不是同一个组长；要合并两组，让人少的那组组长认人多的那组当组长。路径压缩就是问过一次之后直接把组长名字改掉，下次一秒出答案。

19.2 摊还要点：路径压缩与按秩合作为何接近 O(1)

两种优化解决的是不同问题。路径压缩解决"查询慢"：反复查询同一个深链时，第一次走完整条路，之后所有节点都直接指向根。按秩合并解决"合并慢"：即使不做路径压缩，也保证树高是 O(log n)，因为只有秩相等时树高才加一，而秩翻倍需要指数多次合并。单独用任何一个都能改善性能，但都会有退化场景；叠加起来才有 α(n) 的强保证。

rank 字段语义是"树高的上界"，不是精确高度——路径压缩会让真实高度下降，但不更新 rank，这没关系，因为上界依然成立。它用 u8 就足够：树的高度最多 log₂(n)，即使 n 取 10⁹ 也不会超过 31。省下的内存对大规模节点很可观——一百万个节点，Vec<u32> 要 4 MB，Vec<u8> 只要 1 MB。更激进的做法是只存一个 i32 size 字段做按大小合并，语义更直观：让节点少的树挂到节点多的树下，合并后更新根的大小。

反阿克曼函数 α(n) 增长慢到什么程度？对于任何实际可测的 n（哪怕 n 等于宇宙中原子的数量级），α(n) 都不超过 5。也就是说，"摊还 O(α(n))"在实践中就是 O(1)。这个结论来自势能分析：定义势能为所有节点的"高度贡献"之和，路径压缩虽然让单次查询的实际代价可能较高，却大幅降低势能，从而摊还代价很小；按秩合并则保证势能的总增量有限。理解"实际代价 + 势能变化 = 摊还代价"这个等式，是读懂摊还分析证明的钥匙，也是区分"我背下了结论"和"我理解为什么"的分界线。

操作 朴素实现 加路径压缩 再加按秩合并
查询连通 O(n) 摊还 O(log n) 摊还 O(α(n))
合并集合 O(n) 摊还 O(log n) 摊还 O(α(n))
空间 O(n) O(n) O(n)
坑这里最容易踩

两个高频错误。其一，把 find 写成递归：在故意构造的深链上，递归深度可达 n，Rust 主线程默认栈只有几 MB，会直接 stack overflow。其二，合并时不比较秩，直接 parent[rb] = ra：如果每次都把大树挂到小树下，会造出长度 n 的链，路径压缩也救不回来，单次操作退化到 O(n)。还有一种隐蔽错误是只压缩被查询节点本身而不压缩沿途节点，这样链的其他部分依旧很深，效果大打折扣——两趟迭代的写法正是为了把整条路径都压平。

选择并查集还是 DFS/BFS，取决于"查询是静态的还是动态的"。如果所有边一次性给定、只问一次连通性，DFS 或 BFS 更直接；如果边是逐条加入的、中间要随时回答"这两个点是否已连通"，并查集才是正解。注意并查集只支持合并不支持拆分，一旦需要"删除一条边"，就得换用更高级的动态连通结构，或者离线倒过来处理（先算最终状态，再逆向拆边）。认清这个能力边界，比记住模板更重要。

19.3 应用：连通块计数与网格压维

问题定义：给定一个二维网格，'1' 表示陆地、'0' 表示水，求岛屿（水平或垂直相邻的陆地构成的连通块）数量。

不变量：count 等于当前已确认的连通块数。初始把所有陆地格子的数量计入 count；每发生一次真正有效的合并（两个原本不同的集合被合并），连通块数恰好减一。union 返回的 bool 正是"是否真的合并"的信号，用它来驱动 count -= 1，比最后遍历收集不同的根更省事，也不依赖 HashSet。

网格类题目需要把二维坐标 (r, c) 压成一维下标：id = r * cols + c。这样 Vec 只需一维，缓存局部性也更好。危险在于反推邻居时容易出现 r - 1 或 c - 1，而 usize 在 r = 0 或 c = 0 时会下溢 panic。务必把边界判断写在减法之前：先 if r > 0 再算 (r - 1) * cols + c。Rust 不会像 C 那样悄悄回绕，这反而是好事——错误会当场暴露。

struct UnionFind {
parent: Vec<usize>,
rank: Vec<u8>,
}
impl UnionFind {
fn new(n: usize) -> Self {
UnionFind { parent: (0..n).collect(), rank: vec![0; n] }
}
fn find(&mut self, x: usize) -> usize {
let mut root = x;
while self.parent[root] != root { root = self.parent[root]; }
let mut cur = x;
while self.parent[cur] != cur {
let next = self.parent[cur];
self.parent[cur] = root;
cur = next;
}

}
fn union(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
if ra == rb { return false; }
if self.rank[ra] < self.rank[rb] {
self.parent[ra] = rb;
} else {
self.parent[rb] = ra;
if self.rank[ra] == self.rank[rb] { self.rank[ra] += 1; }
}
true
}
}
fn num_islands(grid: &[Vec<char>]) -> usize {
let rows = grid.len();
if rows == 0 { return 0; }
let cols = grid[0].len();
if cols == 0 { return 0; }
let mut uf = UnionFind::new(rows * cols);
let mut count = 0usize;
for r in 0..rows {
for c in 0..cols {
if grid[r][c] == '1' { count += 1; }
}
}
for r in 0..rows {
for c in 0..cols {
if grid[r][c] == '0' { continue; }
let id = r * cols + c;
if r > 0 && grid[r - 1][c] == '1'
&& uf.union(id, (r - 1) * cols + c)
{
count -= 1;
}
if c > 0 && grid[r][c - 1] == '1'
&& uf.union(id, r * cols + (c - 1))
{
count -= 1;
}
}
}
count
}
fn main() {
let g = vec![
vec!['1', '1', '0', '0', '0'],
vec!['1', '1', '0', '0', '0'],
vec!['0', '0', '1', '0', '0'],
vec!['0', '0', '0', '1', '1'],
];
println!("{}", num_islands(&g));
}

这里只检查上和左两个方向，而不是上下左右四个方向。因为并查集合并是对称操作，每对相邻陆地只会被访问一次；若同时检查四个方向，同一组相邻格会被重复合并，虽然结果不变，但多做了无用功。这个"只向右和向下扩展"的剪枝在很多网格搜索题里都成立。

并查集还有个高频用法是检测环：按顺序加入无向图的每条边，如果它连接的两个端点已经在同一个集合里，说明这条边构成环。判别式是 union 返回 false，很多看起来不同的题目（冗余连接、等式方程矛盾、最小生成树判环）都能归到它上面。

复杂度方面，设网格大小为 rows × cols，建表与扫描各一遍，总时间是 O(rows · cols · α(rows · cols))，实践中就是线性；空间是一个长度为 rows · cols 的 parent 数组加一个同样长的 rank 数组。相比之下，用 BFS 求岛屿数也是线性，但需要额外的访问标记队列。并查集的优势在于"边"是逐条给出的场景——如果陆地格子会动态增加，BFS 每次都要重跑，而并查集只需对新格子与邻居做合并。静态网格上两者势均力敌，选择哪一个更多取决于代码习惯。

19.4 BinaryHeap：标准库最大堆与 Reverse 小根堆

问题定义：维护一个动态集合，支持插入元素与取出当前最值。堆用完全二叉树实现，根节点永远是最值，插入与弹出都是 O(log n)。

std::collections::BinaryHeap 是最大堆，peek 返回最大元素。求第 k 大时，维护一个大小不超过 k 的"小根堆"思想：用最大堆保存当前见过的 k 个最小元素，堆顶是这 k 个里最大的；新元素只有比堆顶还大才替换。最终堆顶就是第 k 大。这个技巧的价值在于把堆的空间从 O(n) 压到 O(k)，在海量数据流场景尤其重要。

需要真正的小根堆时用 std::cmp::Reverse<T> 包一层，它会把所有比较方向反转，是标准库正式提供的类型。堆里也可以放自定义结构体，只要为它实现 Ord 与 PartialOrd（通常 derive 即可，字段顺序决定优先级）。

操作 BinaryHeap 方法 复杂度 说明
建空堆 BinaryHeap::new() O(1) with_capacity(n) 可预分配
看堆顶 peek() O(1) 返回引用，可能为空
插入 push(x) O(log n) 上浮调整
弹最值 pop() O(log n) 下沉调整，堆空返回 None
变长 len() / is_empty() O(1) 循环终止条件

use std::cmp::Reverse;
use std::collections::BinaryHeap;
fn kth_largest(a: &[i32], k: usize) -> Option<i32> {
if k == 0 || k > a.len() {
return None;
}
let mut heap: BinaryHeap<i32> = BinaryHeap::with_capacity(k);
for &x in a {
if heap.len() < k {
heap.push(x);
} else if x > *heap.peek().unwrap() {
heap.pop();
heap.push(x);
}
}
heap.peek().copied()
}
fn merge_stones(stones: &[i32]) -> i32 {
let mut heap: BinaryHeap<Reverse<i32>> = BinaryHeap::new();
for &s in stones {
heap.push(Reverse(s));
}
let mut cost = 0;
while heap.len() >= 2 {
let Reverse(a) = heap.pop().unwrap();
let Reverse(b) = heap.pop().unwrap();
let merged = a + b;
cost += merged;
heap.push(Reverse(merged));
}
cost
}
fn main() {
let a = [3, 2, 1, 5, 6, 4];
println!("kth largest = {:?}", kth_largest(&a, 2));
println!("merge cost = {}", merge_stones(&[1, 2, 3, 4]));
}

merge_stones 演示了堆的经典应用：每次取当前最小的两块合并，再把结果放回。用 Reverse 把最大堆翻成小根堆，循环里解构 let Reverse(a) = heap.pop().unwrap(); 直接拿到内部值。这个"反复合并最小两项"的贪心结构是 Huffman 编码等问题的基础。关于 peek：它返回 Option<&T>，空堆时不要直接 unwrap()，除非你能用 len 或循环条件保证非空。top-k 代码的 else 分支能走到，说明堆已经装了 k 个元素且 k > 0，所以 peek().unwrap() 安全。

自定义类型入堆时，优先级由 Ord 决定，而 Ord 必须与 PartialOrd 的语义保持一致，否则标准库可能表现出违反直觉的行为。多关键字排序可以 derive 结构体后按字段顺序自然比较，也可以手写 cmp 实现"先按优先级、再按时间戳"这类规则；后一种情况下务必注意比较的对称性：a.cmp(b) 与 b.cmp(a) 必须互为反向，否则堆的内部调整会破坏不变量。Reverse 本身是一个零成本的包装类型，只在比较时翻转方向，不会带来额外分配或间接访问，所以"用小根堆"不需要任何外部 crate。

大白话先用直觉把它讲通

堆像一个自动排好队的取号机，永远把"最重要"的那个放在最前面让你取。它不保证整个队列有序，只保证队首是最优的——这个克制的承诺换来 O(log n) 的插入和弹出。如果你需要"第 k 大"而不是全部有序，堆比排序更省时省空间。

19.5 手写二叉堆：下标公式与上浮下沉

手写堆的价值不在于替代标准库，而在于理解它的下标不变量。用数组按层序存放完全二叉树：下标 i 的左孩子是 2i + 1，右孩子是 2i + 2，父节点是 (i - 1) / 2。这些公式在 i = 0 时都会出问题（(0 - 1) / 2 下溢），所以上浮循环必须写成 while i > 0，先判断再算父节点。下沉时用 l = 2i + 1、r = l + 1，先检查 l < len 再决定是否比较 r。

rustRust · 标准库72 行
struct MinHeap {
data: Vec<i32>,
}
impl MinHeap {
fn new() -> Self {
MinHeap { data: Vec::new() }
}
fn push(&mut self, v: i32) {
self.data.push(v);
let mut i = self.data.len() - 1;
while i > 0 {
let p = (i - 1) / 2;
if self.data[p] <= self.data[i] {
break;
}
self.data.swap(p, i);
i = p;
}
}
fn pop(&mut self) -> Option<i32> {
if self.data.is_empty() {
return None;
}
let ret = self.data[0];
let last = self.data.pop().unwrap();
if !self.data.is_empty() {
self.data[0] = last;
let mut i = 0usize;
loop {
let l = 2 * i + 1;
let r = l + 1;
if l >= self.data.len() {
break;
}
let mut smallest = l;
if r < self.data.len() && self.data[r] < self.data[l] {
smallest = r;
}
if self.data[i] <= self.data[smallest] {
break;
}
self.data.swap(i, smallest);
i = smallest;
}
}
Some(ret)
}
fn len(&self) -> usize {
self.data.len()
}
}
fn heap_sort(a: &[i32]) -> Vec<i32> {
let mut h = MinHeap::new();
for &x in a {
h.push(x);
}
let mut out = Vec::with_capacity(a.len());
while h.len() > 0 {
out.push(h.pop().unwrap());
}
out
}
fn main() {
let a = [5, 3, 8, 1, 9, 2];
println!("{:?}", heap_sort(&a));
}

上浮与下沉都用 swap 而不是逐个赋值，是因为 Vec::swap 一次完成两个位置的交换，不需要先克隆出临时值；对 i32 这类 Copy 类型差别不大，但换成 String 或自定义结构体时就能省下分配。正确性方面，上浮终止时父节点不大于当前节点，且原本的堆性质未被破坏；下沉终止时当前节点不大于两个孩子，两边子树递归地满足堆性质。这两个局部性质合起来就是全局不变量。把数组所有元素依次 push 进堆再逐个 pop，就得到升序序列，这是 O(n log n) 的堆排序。

上面内存图里那棵树的数组表示也说明了一个工程事实：堆不占用额外的指针空间，父子关系完全靠下标算术推导，缓存局部性远优于显式链式树。这也是为什么 Dijkstra 这类算法喜欢用堆——它的"插入候选、取出最优"操作模式与堆的实现天然契合。若需要在堆中修改某个已存在元素的值（Dijkstra 的减小距离），标准库没有提供索引接口，做法是插入新值并在取出时懒删除旧值，或者自己维护一个 pos 数组实现支持 decrease_key 的索引堆。这两个方案是时间与代码复杂度的取舍：懒删除写起来简单，但堆里可能堆积无效元素；索引堆精确但代码量翻倍。

19.6 建堆的线性时间与 BinaryHeap 内部

逐个 push n 个元素建堆，总代价是 O(n log n)——因为每个元素最多上浮 log n 层。但标准库的 BinaryHeap::from(vec) 或 collect() 能在 O(n) 时间内完成建堆，做法是 Floyd 建堆：从最后一个非叶节点 (n - 2) / 2 开始，下标递减到 0，逐个执行下沉。

为什么这样是线性的？关键在求和而不是逐点估计。高度为 h 的节点最多有 n / 2^(h+1) 个，每个下沉最多走 h 层，所以总代价不超过 Σ h · n / 2^(h+1)，这个级数收敛到 2n，因此是 O(n)。直觉是：绝大多数节点都在树的底部，它们下沉的距离很短；真正需要走 log n 层的根节点只有一个。把"每个节点都花 log n"误算成 O(n log n)，是忽视了对数高度的节点数量呈指数递减。

O(n) 建堆 + n 次 O(log n) 弹出，总体仍是 O(n log n)，但常数比"n 次 push"更小。这也解释了为什么堆排序在需要原地建堆的场景有优势。实际工程中很少手写建堆——直接用 BinaryHeap::from(vec) 即可——但理解这个证明能让你在别人问"为什么是 O(n)"时讲得清楚，也是分析其他"自底向上"算法的基础。另一个细节是 BinaryHeap::pop 的实现：它把最后一个元素移到根，然后下沉，这正是上面手写 pop 的写法；BinaryHeap 内部就是一个 Vec<T>，所有下标公式与手写版完全一致。

需要提醒的是，Floyd 建堆要求从后往前处理，顺序反过来（从根到叶子）就会失效——因为下沉依赖两棵子树已经是堆，从后往前正好保证这一点。这个"自底向上"的依赖顺序与动态规划里的拓扑序是同一个思想。如果改成从前往后对每个节点上浮，得到的仍是正确堆，但复杂度退回 O(n log n)。理解"为什么必须这个方向"，比记住"从最后一个非叶节点开始"这个结论更重要：它让你在遇到变体（例如最大堆改成小根堆、数组下标从 1 开始）时，能自己推导出正确的起点。

19.7 随机对拍：并查集对 BFS、手写堆对标准库

两个数据结构都容易出"看起来对但边界错"的 bug，对拍是最可靠的验证手段。本节用固定种子 777 的 LCG 同时验证两套实现：

并查集对照组：维护邻接矩阵，每次成功合并就同步置位；查询时用 BFS 在矩阵上判断可达性，这就是绝对正确的暴力解法。最后再对比"不同根的数量"与"BFS 数出的连通块数"。

手写堆对照组：把同一组随机数据分别塞进 MinHeap 与标准库 BinaryHeap<Reverse<i32>>，把两者的弹出序列与 sort_unstable 的结果三方比对。标准库实现本身就是一份可信参照。

use std::cmp::Reverse;
use std::collections::{BinaryHeap, VecDeque};
fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
struct UF {
parent: Vec<usize>,
rank: Vec<u8>,
}
impl UF {
fn new(n: usize) -> Self {
UF { parent: (0..n).collect(), rank: vec![0; n] }
}
fn find(&mut self, x: usize) -> usize {
let mut root = x;
while self.parent[root] != root { root = self.parent[root]; }
let mut cur = x;
while self.parent[cur] != cur {
let next = self.parent[cur];
self.parent[cur] = root;
cur = next;
}
root
}
fn union(&mut self, a: usize, b: usize) -> bool {
let ra = self.find(a);
let rb = self.find(b);
if ra == rb { return false; }
if self.rank[ra] < self.rank[rb] {
self.parent[ra] = rb;
} else {
self.parent[rb] = ra;
if self.rank[ra] == self.rank[rb] { self.rank[ra] += 1; }
}
true
}
}
fn reachable(adj: &[Vec<bool>], s: usize, t: usize) -> bool {
let n = adj.len();
let mut vis = vec![false; n];
let mut q = VecDeque::new();
q.push_back(s);
vis[s] = true;
while let Some(u) = q.pop_front() {
if u == t { return true; }
for v in 0..n {
if adj[u][v] && !vis[v] {
vis[v] = true;
q.push_back(v);
}
}
}
vis[t]
}
struct MinHeap {
data: Vec<i32>,
}
impl MinHeap {
fn new() -> Self { MinHeap { data: Vec::new() } }
fn push(&mut self, v: i32) {
self.data.push(v);
let mut i = self.data.len() - 1;
while i > 0 {
let p = (i - 1) / 2;
if self.data[p] <= self.data[i] { break; }
self.data.swap(p, i);
i = p;
}
}
fn pop(&mut self) -> Option<i32> {
if self.data.is_empty() { return None; }
let ret = self.data[0];
let last = self.data.pop().unwrap();
if !self.data.is_empty() {
self.data[0] = last;
let mut i = 0usize;
loop {
let l = 2 * i + 1;
let r = l + 1;
if l >= self.data.len() { break; }
let mut smallest = l;
if r < self.data.len() && self.data[r] < self.data[l] { smallest = r; }
if self.data[i] <= self.data[smallest] { break; }
self.data.swap(i, smallest);
i = smallest;
}
}
Some(ret)
}
}

19.8 工程取舍、调试清单与练习

两种数据结构的适用边界值得总结。并查集的强项是只增不减的等价关系：合并与查询都近乎常数，但不支持拆分；一旦题目要求"撤销合并"或"删除边"，就要改用可撤销并查集（用栈记录修改）或整体离线处理。堆的强项是动态最值：插入与取最值都是 O(log n)，但只能回答最值，查第 k 大需要配套技巧，删除任意元素需要额外的索引映射。两者都属于"用不变量换效率"的典范：并查集靠"只认根"压平查询，堆靠"只保父不大于子"压低维护成本。

调试这类代码时逐项核对：并查集的 find 是否为迭代两趟、第二趟是否先存 next；union 是否比较了秩、是否只在真正合并时减少计数；网格压维后是否把边界判断写在减法之前；手写堆的上浮循环是否以 i > 0 为条件、下沉是否先检查 l < len；所有 unwrap() 是否都有长度或循环条件作为前提。写完先小规模手工推演，再用随机对拍大范围验证，这类摊还数据结构最怕的就是"某个罕见路径下不变量被破坏"。

还要注意验证数据的分布。并查集在"所有元素一开始就连通"或"所有操作都是查询"的极端输入下，很多分支根本走不到；堆在全相等数据上，比较器的 Tie 处理是否正确也测不出来。因此对拍时要刻意混合递增、递减、全相等、只有两个不同值等退化样本，再叠加随机数据。第 19.7 节生成的并查集测试数据同时包含合并与查询，堆测试数据横跨正负值，正是出于这个考虑。把"对拍通过"当成必要而非充分条件，才是对正确性负责的态度。
