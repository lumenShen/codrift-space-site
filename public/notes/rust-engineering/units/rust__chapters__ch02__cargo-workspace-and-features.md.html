9.1 从单包到 workspace：拆包判据与目录约定

一个仓库只有一个 Cargo.toml 时，所有问题都简单：清单描述这一个包，锁文件记录一次解析，产物躺在同一个 target/。当代码增长到出现「可被多个可执行文件复用的库」「只在测试里使用的辅助程序」「过程宏」这三类目标时，把它们放进同一个 crate 会让依赖方向变成一团乱麻。workspace 不是为了「看起来模块化」，而是让若干个独立的包共享一次依赖解析和一个产物目录。

拆包的判据不是代码行数，而是能否用一条清晰的有向无环图描述依赖：底层库不认识上层应用，上层应用组合若干底层库，e2e 包从外部视角测试整条链路。若两个模块永远一起改、一起发布，它们就属于同一个包；把它们拆成两个只会制造连锁发布。反过来，若一个过程宏和它的运行时库必须互相引用，也要先解决循环依赖再谈拆分。

真实验证工程的目录如下。注意 notes-e2e 是一个完整的 package，而不是根目录里随手放的 tests/——工作区根目录本身不是任何 crate 的源目录，放在那里的测试不会被 Cargo 自动发现。

目录约定真正解决的是「新人该把代码写在哪」：src/lib.rs 放可复用接口，src/main.rs 只解析参数与装配，tests/ 放从外部调用的集成测试，benches/ 放基准，examples/ 放可运行示例。把业务实现写进 main.rs，等第二个二进制需要复用时再大规模搬运，是最常见的返工来源。

大白话先用直觉把它讲通

把 workspace 想成一个物流园区。每家公司（包）都有自己的招牌和业务，但共用同一个仓库（target/）和同一张采购总表（Cargo.lock）。这样园区里不会有人买了两个不同版本的同一零件还互相不知道；谁要改采购清单，得在园区级的会议上说清楚。

9.2 根清单与成员继承：把公共字段写一次

根 Cargo.toml 只负责声明「哪些包属于这个工作区」和「大家共用的默认值」，它本身不构成一个可发布的包。成员的 version.workspace = true、edition.workspace = true 表示继承根清单的 [workspace.package]；依赖里的 workspace = true 表示继承 [workspace.dependencies]。继承的价值不只是少写几行：当十几个包各自写 edition = "2018"，升级 edition 就变成一场排查游戏；集中声明后一次修改全军同步。

下面是验证工程真实使用的清单骨架。注意 notes-core 在 [workspace.dependencies] 里同时给出 path 和 version：前者让本工作区内的引用走本地路径，后者是发布到 crates.io 后其他项目看到的版本约束，两者缺一不可。

tomlRust · 标准库17 行
[workspace]
resolver = "2"
members = ["crates/notes-core", "crates/notes-cli", "crates/notes-e2e"]
[workspace.package]
version = "0.3.0"
edition = "2021"
license = "MIT"
[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
notes-core = { path = "crates/notes-core", version = "0.3.0" }
[profile.release]
lto = "thin"
strip = "symbols"

成员的依赖声明则写成 { workspace = true, optional = true } 这种形式。特别要看 dep:serde 这个语法：它明确告诉 Cargo「json 这个 feature 只是打开 serde 依赖，不要再额外生成一个同名的隐式 feature」。在 1.60 之前，写 json = ["serde"] 会顺带暴露一个叫 serde 的 feature，导致下游能绕过你的抽象直接开关它；dep: 前缀消除了这个隐患。

tomlRust · 标准库13 行
[package]
name = "notes-core"
version.workspace = true
edition.workspace = true
[dependencies]
serde = { workspace = true, optional = true }
serde_json = { workspace = true, optional = true }
[features]
default = ["std"]
std = []
json = ["dep:serde", "dep:serde_json"]

还有几个字段在小型仓库里看不出价值，一旦包数上来了就变得关键。default-members 决定在根目录直接敲 cargo build 时构建哪些成员：把正在迭代的一两个包写进去，可以避免每次都编译整套 e2e；exclude 则列出「目录里有 Cargo.toml 但不属于本工作区」的路径，常见于 vendored 子模块或刻意独立的示例。判断一个目录是否真的成为成员，不要靠肉眼扫清单，用 cargo metadata --no-deps 看工具链给出的 JSON 图——IDE 和 CI 脚本也都靠它定位工作区根目录。

目标（target）的声明同样有讲究。[lib] 可以给库改名或关闭库目标，[[bin]] 声明额外可执行文件，required-features 让某个示例或基准只在指定 feature 下才有意义——这样 --all-targets 不会把需要可选依赖的例子拉进来。构建脚本用 build = "build.rs" 指定，它生成的 OUT_DIR 里可以放生成代码；[package.metadata] 则是留给第三方工具的抽屉，Cargo 自己完全不解读。把这些约定集中在清单里，而不是写在 README 的「请先手动执行某脚本」中，是构建可重复的前提。

回到 main.rs：它应当尽可能薄，只负责解析参数、装配依赖、调用库函数。原因不是审美，而是可测试性——库目标可以被集成测试直接依赖，二进制目标不能被别的 crate use。一旦业务逻辑写在 main.rs 里，第二个二进制想复用时只能复制文件，复制出来的一份很快就会与原版分叉。

日常检查整个工作区用 cargo check --workspace，它比逐个 cd 进成员目录再构建更快，也更能暴露跨成员的链接问题。本次真跑的结果如下，Cargo 解析出 11 个包并逐个检查通过；版本号是 crates.io 在本次验证时的真实状态，不是写死在示例里的数字。

9.3 resolver 2 与 feature 统一：一次解析，不是各算各的

Cargo 的核心机制之一叫 feature 统一（feature unification）：同一个包在一次构建中只编译一份，它启用的 feature 是所有依赖路径上请求的并集。这不是实现偷懒，而是类型系统的必然——如果 serde 被编译成「带 derive」和「不带 derive」两份，它们的类型身份就会分裂，下游传错类型时错误会变得无法理解。

从 resolver 1 到 resolver 2，最实质的变化正是统一的范围：resolver 1 会把 build-dependencies 和 dev-dependencies 请求的 feature 也算进正常依赖，导致「仅为测试启用的 serde/derive」污染了发布产物；resolver 2 把构建依赖、开发依赖与目标依赖分开统一，并让目标平台相关的依赖只在对应平台生效。新项目没有理由不选 2。

feature 的引用还可以写成弱依赖形式，这是 resolver 2 带来的一处细节。serde?/derive 的含义是「如果 serde 已经因为别的路径被启用，那么顺带打开它的 derive，但不要为了这个 feature 而把 serde 拉进来」。与之对照，serde/derive 是无条件打开依赖并转发 feature。弱依赖让可选依赖的能力透传变得精确：一个库可以提供 json 输出，但当且仅当调用方自己已经需要 serde 时才对齐其配置，避免为「可能用得上」付编译成本。注意 dep: 前缀与 ? 解决的是两个不同问题：前者消除隐式 feature，后者抑制依赖启用。

反向排查同样重要。正向的 cargo tree -e features -p notes-cli 回答「这个包打开了什么」，而 cargo tree -e features -i serde 回答「是谁把 serde 带进来的」——后者在几十个传递依赖的工程里往往更快定位问题。两种视角结合，才能判断某个 feature 是设计意图还是意外泄漏。

为了把这个机制看得更清楚，下面用 std-only 代码模拟「并集求解」。真实 Cargo 还要处理 feature 之间的依赖闭包（json 打开 dep:serde）、target-specific 依赖与 resolver 分组，但核心直觉就是这段两次 insert 的循环。

rustRust · 标准库25 行
use std::collections::{BTreeMap, BTreeSet};
/// 把多条依赖路径上的 feature 声明合并成一个并集，模拟 Cargo 的 feature 统一。
fn resolve(requests: &[(&str, &[&str])]) -> BTreeMap<String, BTreeSet<String>> {
let mut unified: BTreeMap<String, BTreeSet<String>> = BTreeMap::new();
for (pkg, feats) in requests {
let set = unified.entry((*pkg).to_string()).or_default();
for f in *feats {
set.insert((*f).to_string());
}
}
unified
}
fn main() {
let requests: &[(&str, &[&str])] = &[
("notes-core", &["std"]),
("notes-core", &["json"]),
("serde", &["derive", "std"]),
];
for (pkg, feats) in resolve(requests) {
let list: Vec<_> = feats.iter().cloned().collect();
println!("{} -> {:?}", pkg, list);
}
}
终端真跑一遍
$ rustc --edition 2021 block_u09_3.rs -o b3.exe && ./b3.exe
notes-core -> ["json", "std"]
serde -> ["derive", "std"]
坑这里最容易踩

坑：以为「我没有启用 json，所以产物里不会有 serde」。在 workspace 里，只要有任何一个成员或任何一条传递依赖请求了 json，整个构建中的 notes-core 就带上了它，serde 也随之进入编译图。排查时不要凭清单猜测，用 cargo tree -e features -p <包名> 看真实的 feature 来源；这条命令会画出「谁请求了哪个 feature」的反向路径。

9.4 feature 矩阵：可叠加、默认路径与编译期互斥

feature 的第一条工程原则是可叠加：打开一个 feature 不应该改变已有 API 的语义。如果两个库各自请求了不同的 feature，Cargo 会把它们并起来；只要其中一个是「把 parse 的返回类型换掉」这种破坏性开关，另一个库立刻编译失败。所以 feature 只能做「增加能力」，不能做「替换行为」。

第二条原则是让默认特性覆盖「大多数用户开箱即用」的路径。底层库通常选 default = []，让用户为每份能力付费；应用则可以把常用组合设为默认。我们的 notes-cli 把 json 设为默认，因此 cargo run 会输出结构化结果；显式关闭后走轻量分支。

Rust 代码里读取 feature 有两个入口，时机完全不同。cfg! 是布尔表达式，两个分支都要通过类型检查；#[cfg] 在解析前直接删除条目，未选中的代码里即使引用了不存在的 crate 也不会报错。需要「同一接口、两套实现」时必须用后者，才能让不相关依赖彻底不进入编译单元。

rustRust · 标准库16 行
#![allow(dead_code, unexpected_cfgs)]
fn backend_name() -> &'static str {
if cfg!(feature = "json") { "json" } else { "minimal" }
}
#[cfg(feature = "json")]
fn parse_hint() -> &'static str { "启用结构化解析，支持嵌套输入" }
#[cfg(not(feature = "json"))]
fn parse_hint() -> &'static str { "仅内置格式，产物更小" }
fn main() {
println!("backend = {}", backend_name());
println!("hint = {}", parse_hint());
}

}

9.5 语义化版本与 lockfile：需求不等于结果

SemVer 把变更分成三类：主版本号变化是不兼容的 API 改动，次版本号变化是向后兼容的新增，修订号变化是向后兼容的修复。Cargo 默认使用 ^ 策略：serde = "1" 允许 1.x 的所有兼容升级，~1.2 限定在 1.2.x，=1.2.3 才是精确锁定。你声明的是需求的下界，真正使用哪个版本由求解器与 lockfile 共同决定。

理解这一点就能解释两类经典疑问。「为什么同事拉代码后依赖突然升级了」——因为他那边没有 lockfile 或锁文件没提交，求解器按最新兼容版本重新算了一遍；「为什么我改了版本号但构建结果没变」——因为 lockfile 里的版本仍满足新约束，Cargo 不会主动移动它，必须显式 cargo update -p serde --precise 1.0.188。

lockfile 本身也值得读一遍。当前格式以 # This file is automatically @generated by Cargo. 开头，每个 [[package]] 记录名称、版本、来源与校验和；注册表来源带 registry+... 与 checksum，本地路径来源则没有校验和。这个结构解释了三件事：--locked 为什么能发现清单与锁文件不一致——Cargo 会重算图并比对；cargo update -p serde --precise 1.0.188 为什么只动一个包——它只重写该包及其必要的依赖边；以及为什么删掉 lockfile 是一次「重新求解」而不是「重新下载」——版本选择会重新发生，下载缓存仍在。

还有一个容易误判的点：Cargo 选的是最高兼容版本，不是最低版本。清单写 serde = "1" 表示接受任何 1.x，求解器就会挑当前最新的 1.x。这意味着「声明的下界能不能编译」从未被验证过——如果你的库声称支持 1.0.100，而 CI 一直用 1.0.229 构建，两者之间被用掉的 API 就是潜在坑。较新的 Cargo 提供 resolver.incompatible-rust-versions = "fallback" 配置，让求解器优先选择声明的 rust-version 能接受的版本；更严格的项目则单独跑一次最小版本构建。这两种手段解决的都是「下界失真」，但都不如真的在 CI 里跑一遍来得可靠。

版本字符串的比较规则比看上去复杂，尤其预发布标签：1.2.3-rc.1 小于 1.2.3。下面这个 std-only 的小实现给出核心比较逻辑，用于说明「为什么不能自己写字符串比较」——真实项目要用专门的版本解析库，因为构建元数据、比较优先级与数字标识符的边界远比这里多。

rustRust · 标准库52 行
#[derive(Debug, Eq, PartialEq)]
struct Ver {
major: u64,
minor: u64,
patch: u64,
pre: Option<String>,
}
impl Ord for Ver {
fn cmp(&self, other: &Self) -> std::cmp::Ordering {
use std::cmp::Ordering::*;
let core = (self.major, self.minor, self.patch)
.cmp(&(other.major, other.minor, other.patch));
if core != Equal {
return core;
}
match (&self.pre, &other.pre) {
(None, None) => Equal,
(None, Some(_)) => Greater,
(Some(_), None) => Less,
(Some(a), Some(b)) => a.cmp(b),
}
}
}
impl PartialOrd for Ver {
fn partial_cmp(&self, other: &Self) -> Option<std::cmp::Ordering> {
Some(self.cmp(other))
}
}
fn parse(s: &str) -> Option<Ver> {
let (core, pre) = match s.split_once('-') {
Some((c, p)) => (c, Some(p.to_string())),
None => (s, None),
};
let mut it = core.split('.');
Some(Ver {
major: it.next()?.parse().ok()?,
minor: it.next()?.parse().ok()?,
patch: it.next()?.parse().ok()?,
pre,
})
}
fn main() {
let stable = parse("1.2.3").unwrap();
let rc = parse("1.2.3-rc.1").unwrap();
let newer = parse("1.3.0").unwrap();
println!("stable < rc ? {}", stable < rc);
println!("rc < newer ? {}", rc < newer);
}

大白话先用直觉把它讲通

Cargo.toml 像点菜单，写的是「来一份不辣的」；Cargo.lock 像厨房小票，写的是「实际端上来的是 1 号厨师做的那份」。只要小票在，第二个人照着做结果一样；没有小票，厨师今天心情好就可能换种做法。所以应用仓库一定要把小票（lockfile）交上去。

排查依赖膨胀时优先看 cargo tree -e features，而不是凭记忆猜。本次验证里 notes-cli 的树形输出明确显示 notes-core 的 json feature 来自 notes-cli，并把 serde/derive、serde_json/default 一路带进来；cargo tree -d 则用来发现同一包的多个重复版本。

终端真跑一遍
$ cargo tree -e features -p notes-cli
notes-cli v0.3.0
└── notes-core feature "default"
├── notes-core v0.3.0
│ ├── serde feature "default"
│ │ └── serde v1.0.229
│ ├── serde feature "derive"

│ └── serde_json v1.0.154

（为篇幅做了裁剪，真实输出包含 proc-macro2/syn/quote 等完整子树）

9.6 target/ 目录与增量构建：产物到底去了哪

工作区共享一个 target/，这是「同一份依赖只编译一次」的物理基础。成员不再各自拥有 target/，因此从一个成员切到另一个成员时不会重新编译公共依赖。目录按 profile 和 target triple 分层，理解这个布局能帮你回答「我明明没改代码，为什么又全量重编」：通常是换了 profile、换了 target、或改了会污染全局的 feature 组合。

“同一个包” 在工作区里有唯一身份标识，cargo pkgid 会把路径与版本拼在一起打印出来。下面的输出也解释了为什么 [workspace.dependencies] 里必须写 version：本地开发时 path 生效，发布后包身份变成注册表中的版本。

终端真跑一遍
$ cargo pkgid -p notes-core
path+file:///C:/Users/Administrator/Documents/Study/.scratch/rust-notes-src/_verify/u09-workspace/crates/notes-core#0.3.0
$ cargo build -q --release -p notes-cli && ls -l target/release/notes-cli.exe
-rwxr-xr-x 2 Administrator 197121 133632 Nov 23 20:28 target/release/notes-cli.exe

增量构建的判定靠一组指纹，而不是文件时间戳。target/debug/.fingerprint/ 下每个包都有记录编译器版本、feature 集合、RUSTFLAGS、环境变量与依赖哈希的文件；任何一项变化都会让该包及其下游重新编译。这解释了一个常见困惑：「我只改了 feature，怎么半个项目都重编了」——因为 feature 是类型身份的一部分，必须重编才能保证 ABI 一致。cargo clean -p notes-core 只清一个包，适合排查「疑似缓存污染」；CARGO_TARGET_DIR 则可以把缓存搬到仓库外甚至团队共享路径，配合 sccache 使用效果更明显。交叉编译时 --target x86_64-pc-windows-msvc 会在 target/ 下再分一层目录，不同 triple 的产物互不覆盖。想找编译慢的元凶，用 cargo build --timings 生成按 crate 排序的耗时报告，比凭感觉猜要准。

release profile 里的 lto = "thin" 让跨 crate 的链接期优化可以内联掉边界，strip = "symbols" 去掉符号表；两者都让产物变小，但会让崩溃栈更难读，通常配合单独的符号制品一起发布（第 14 单元展开）。开发期不要盲目套用这些配置，lto 会显著拖慢链接。

9.7 patch、replace 与私有源：接管依赖的三种手段

真实工程里经常需要临时接管某个依赖：上游有一个还没发版的修复，或公司要求所有依赖走私有镜像。三种手段的侵入性依次递增。

[patch.crates-io] 最常用：它告诉 Cargo「当有人请求注册表中的 serde 1.x 时，改用我指定的 git 分支或本地路径」。被 patch 的版本号必须满足原依赖的约束，否则 Cargo 会忽略它并打印警告。它适合短期救急，合并 upstream 后要第一时间删除。

tomlRust · 标准库6 行
[patch.crates-io]
# 临时使用带修复的分支；版本号仍需满足依赖声明的约束
serde = { git = "https://github.com/serde-rs/serde.git", branch = "master" }
# 本地覆盖（调试时更直接）
# serde = { path = "../vendor/serde" }

[replace] 是更老的机制，可以替换任意来源的依赖，但它会改变依赖图的身份，容易和 lockfile 打架，Cargo 文档已不推荐新项目使用。私有源则通过 .cargo/config.toml 的 [source] 定义，可以把 crates.io 整体替换为公司镜像，也可以同时声明多个注册源并用 [source.<name>] 的 registry 指向地址。配置层级也值得注意：Cargo 会从当前目录向上逐级寻找 .cargo/config.toml，越靠近项目的优先级越高；嵌套 workspace 若要隔离配置，就要在被嵌套的目录里放自己的文件。写错 replace-with 的典型症状是「本地能编，CI 拉不到包」，因为开发者机器上残留了镜像配置。

tomlRust · 标准库6 行
# .cargo/config.toml：把默认源整体指向公司镜像
[source.crates-io]
replace-with = "company-mirror"
[source.company-mirror]
registry = "sparse+https://crates.example.com/index/"

还有一条更彻底的路是 cargo vendor：它把所有依赖源码下载到 vendor/ 目录，并打印一段可直接粘进配置的 [source] 片段，让完全离线的构建成为可能。它适合对供应链有硬性要求的场景，代价是仓库体积与升级人工成本。三种手段的选择顺序应当是：优先 patch 临时救急，长期方案推回上游；私有镜像只解决网络与合规，不改变版本选择；vendor 是最后手段。

坑这里最容易踩

坑：把 patch 当成永久分叉留在仓库里。patch 只对当前工作区生效，发布到 crates.io 的包不会携带 patch；依赖你的下游会重新解析到上游原版，于是「本地测试通过、用户那边行为不同」。正确做法是把修复推回上游并发版，或在等待期间给依赖写死 git 修订并明确记录这是一笔技术债。

9.8 把矩阵固化成 CI 门禁

工作区的价值只有在机器上也成立时才算兑现。CI 至少要跑四件事：cargo check --workspace --all-targets 保证所有目标可编译；cargo test --workspace 跑全量测试；cargo build --locked --release 验证 lockfile 与清单一致且发布配置可用；feature 矩阵按列分别验证。--locked 能防住「改了 Cargo.toml 忘了更新锁文件」，但防不住「有人手改 lockfile 里的校验和」——后者要靠代码评审与依赖审计工具。

门禁命令 守护的问题 不能守护的问题
cargo check --workspace --all-targets 所有成员、测试与基准都能编译 运行时行为
cargo test --workspace 跨包公开 API 契约 性能退化
cargo build --locked --release 清单与锁文件一致、发布配置可用 传递依赖里已有漏洞
cargo tree -d 重复版本导致的类型分裂风险 feature 互斥组合

发布边界也要在清单里写清：publish = false 标记内部包，license、description、repository 是发布到 crates.io 的必填元数据，exclude 可以把测试数据挡在 .crate 包之外。真要发布之前，先用 cargo package --list 看一遍将要被打进压缩包的文件，再用 cargo publish --dry-run 完整走一遍打包与校验流程——它不会上传，却会执行构建并从包内容重新编译一次，因此能抓到「本地能编是因为引用了仓库里未提交的文件」这类问题。.crate 里包含规范化后的 Cargo.toml、原始清单 Cargo.toml.orig、Cargo.lock、源码、README 与许可证文件；路径依赖必须带 version 字段才能通过校验，这正是 9.2 里强调写作 path + version 的原因。

对于要长期维护的库，再加两道门禁是划算的：cargo semver-checks 对比上一个发布版本，自动识别公开 API 的破坏性变更；cargo deny check 同时审查许可证兼容性与已知安全公告。MSRV（最低支持 Rust 版本）也要写进 rust-version 字段并纳入 CI 矩阵，否则「我们用最新稳定版都能编」不等于用户能用他机器上那版编过。把这些约定写进根清单与 CI 配置，而不是口口相传，是每个工作区都值得投入的十分钟。

动手动脑

  • 在验证工程的 notes-cli 里再加一个 feature upper，让它把 summarize 的输出转成大写；要求 default 不含它，并用 cargo run -p notes-cli --features upper 验证两种输出。
  • 给 notes-core 增加一个 #[cfg(all(feature = "std", feature = "json"))] 下的函数，然后用 cargo tree -e features -p notes-e2e 观察单独构建 e2e 时 feature 是否变化，解释差异。
  • 修改根清单的 resolver = "1"，重新运行 cargo tree -e features -p notes-cli，记录与 resolver 2 的差异后改回。

  • 某个依赖只在测试中出现时应该写进哪个字段？为什么不能图省事写进 [dependencies]？
  • 为什么 feature 必须可叠加？如果两个 feature 互斥，应当用什么机制在编译期报错？
