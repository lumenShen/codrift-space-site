31.1 从前缀和到区间结构：问题定义与边界

前缀和把"静态区间和"压到 O(1)，但一旦允许修改，前缀数组就要整体重算，代价退化为 O(n)。本单元要处理三类典型冲突：既改又查（区间加、区间求和）、二维点改矩形查（网格上的增量与区域和）、不可改但查得复杂（静态区间第 k 小）。它们分别对应线段树、二维 BIT、主席树。

问题定义必须精确到下标语义。线段树处理长 n 的数组 a，支持 add(l,r,v) 把 [l,r] 每个元素加 v，以及 sum(l,r) 返回区间和；二者都要 O(log n)。二维 BIT 处理 n×m 的矩阵，支持单点加与 [x1,x2]×[y1,y2] 的矩形和，复杂度 O(log n log m)。主席树处理静态数组，支持 kth(l,r,k) 返回 [l,r] 内第 k 小，预处理 O(n log n)，单次查询 O(log n)。

大白话先用直觉把它讲通

前缀和像一本算好总账的账本，改一笔就要重印整本。线段树把账本拆成层级，某一段涨价了只在那一页贴个"待补款"便条，查账时才把便条摊给下面。二维 BIT 是给表格的行列都编了二进制页码，顺着页码跳就能把一片格子汇总。主席树则像给每一次"拍照"只重拍被改动的那一条走廊，其余走廊直接复用上一张照片。

在动手写结构之前，先看清一个常被忽略的前提：线段树与 BIT 能工作，是因为"求和"构成一个交换幺半群——有结合律、有单位元 0、且与顺序无关。结合律允许我们把大区间切成若干节点区间再合并；单位元允许空区间返回 0 而不破坏结果；交换律让左右子树的合并次序不影响答案。换成"最大值""按位或""异或"同样成立，换成"字符串拼接"或"浮点数求和"就要小心：前者虽结合但分配内存代价高，后者因舍入误差不再严格结合，对拍时可能出现"同一批数不同合并顺序得到不同末位"的假 mismatch。理解这一点，比背模板更能决定你何时该用、何时不该用这些结构。

三者共享一个工程约定：用闭区间还是半开区间必须从头到尾一致。本单元线段树用闭区间 [l,r]，二维 BIT 用 1-based 闭区间，主席树用 1-based 下标。混用是调试噩梦的源头，所以在函数签名处就要固定下来。闭区间的额外好处是空区间判断简单（l > r 直接返回单位元），半开区间 [l,r) 则在二分与切片转换时更自然；两种都能用，唯一不能接受的是"建树用闭区间、查询用半开区间"这种半途换语义。

再从问题模型上看，"在线"与"离线"也决定了结构选择。线段树和 BIT 都支持读到一条操作就立刻处理、立刻回答，属于在线结构；主席树要求先把整批数组读入、离散化、再建版本树，属于离线预处理结构。若题目边读边问且答案依赖后续修改，主席树根本无从下手；反过来，若数组全程不变而要回答上万次区间排名查询，用线段树维护计数再逐值二分会很慢，主席树的 O(log m) 才是正解。把"是否修改""查什么""何时知道全部输入"三个问题按顺序问完，结构通常就唯一确定了。

31.2 线段树的形状与不变量

线段树把 [0,n-1] 递归二分：节点 p 覆盖区间 [l,r]，左孩子 2p 覆盖 [l,mid]，右孩子 2p+1 覆盖 [mid+1,r]。用数组存树时，深度约 log₂n，节点总数不超过 4n，所以预分配 vec![0; 4*n+4] 是安全的上界，也避免动态扩容带来的借用麻烦。

节点不变量有两条。sum[p] 恒等于节点覆盖区间当前的元素和；lazy[p] 记录"已经计入 sum[p]、但尚未下发给两个孩子"的加值。注意 lazy 的语义是"子树每个元素都要加 v"，不是"sum 要加 v"——这个区分决定了 push 时乘的是区间长度。

建树时叶子直接取 a[l]，内部节点 sum[p] = sum[2p] + sum[2p+1]。由于 Rust 不允许同时持有 &mut self.sum[p] 和递归调用 &mut self，实现里用 self.sum[p] = self.sum[p*2] + self.sum[p*2+1] 这种"先读后写"的单语句形式，让两次不可变借用结束后再可变借用，绕开借用冲突。这正是两阶段借用（two-phase borrow）在实践中的样子：赋值号右侧的两次索引先完成不可变读取，左侧的可变借用直到真正写入才生效。若把同一个意思拆成 let s = &mut self.sum[p]; *s = self.sum[p*2] + self.sum[p*2+1];，编译就会失败——因为 s 的生命周期横跨了右侧读取。

为什么用数组而不是 Box<Node> 指针树？因为完全二叉形态让父子关系变成纯算术 2p / 2p+1，无需存指针，缓存局部性也更好。4n 这个上界可以这样估算：深度 d 的节点数不超过 2^d，最坏情况下最后一层不满但编号仍连续，最大下标小于 2^(h+1)，而 2^h ≤ n < 2^(h+1)，故最大下标 < 4n。多开 4 个是防御性余量，避免边界处越界。另一处细节是 mid = l + (r-l)/2 而非 (l+r)/2：后者在 l、r 都接近 usize::MAX 时相加溢出，虽然本单元 n 不会那么大，但写成安全形式没有代价，应该形成习惯。

补一句值得记住的细节

迭代式线段树（把叶子排成 2 的幂长度的数组，自底向上合并）代码更短、无递归，但懒标记下推需要额外的"标记高度"技巧，可读性反而下降。本单元选递归版，是因为它让不变量与区间一一对应，便于讲清正确性；工程里若追求极限常数再换迭代版也不迟。

#![allow(dead_code)]
/// 线段树：区间加、区间求和，懒标记向下传递。
struct SegTree {
n: usize,
sum: Vec<i64>,
lazy: Vec<i64>,
}
impl SegTree {
fn new(a: &[i64]) -> Self {
let n = a.len();
assert!(n > 0, "线段树至少需要一个元素");
let mut st = Self { n, sum: vec![0; 4 * n + 4], lazy: vec![0; 4 * n + 4] };
st.build(1, 0, n - 1, a);
st
}
fn build(&mut self, p: usize, l: usize, r: usize, a: &[i64]) {
if l == r {
self.sum[p] = a[l];
return;
}
let m = l + (r - l) / 2;
self.build(p * 2, l, m, a);
self.build(p * 2 + 1, m + 1, r, a);
self.sum[p] = self.sum[p * 2] + self.sum[p * 2 + 1];
}
fn apply(&mut self, p: usize, len: usize, v: i64) {
self.sum[p] += v * len as i64;
self.lazy[p] += v;
}
fn push(&mut self, p: usize, l: usize, r: usize) {
if self.lazy[p] != 0 && l < r {
let m = l + (r - l) / 2;
let v = self.lazy[p];
self.apply(p * 2, m - l + 1, v);
self.apply(p * 2 + 1, r - m, v);
self.lazy[p] = 0;
}
}
fn add(&mut self, ql: usize, qr: usize, v: i64) {
if ql > qr { return; }
self.add_rec(1, 0, self.n - 1, ql, qr, v);
}
fn add_rec(&mut self, p: usize, l: usize, r: usize, ql: usize, qr: usize, v: i64) {
if ql <= l && r <= qr {
self.apply(p, r - l + 1, v);
return;
}
self.push(p, l, r);
let m = l + (r - l) / 2;
if ql <= m { self.add_rec(p * 2, l, m, ql, qr, v); }
if qr > m { self.add_rec(p * 2 + 1, m + 1, r, ql, qr, v); }
self.sum[p] = self.sum[p * 2] + self.sum[p * 2 + 1];
}
fn query(&mut self, ql: usize, qr: usize) -> i64 {
if ql > qr { return 0; }
self.query_rec(1, 0, self.n - 1, ql, qr)
}
fn query_rec(&mut self, p: usize, l: usize, r: usize, ql: usize, qr: usize) -> i64 {
if ql <= l && r <= qr { return self.sum[p]; }
self.push(p, l, r);
let m = l + (r - l) / 2;
let mut res = 0;
if ql <= m { res += self.query_rec(p * 2, l, m, ql, qr); }
if qr > m { res += self.query_rec(p * 2 + 1, m + 1, r, ql, qr); }
res
}
}
fn main() {
let a = vec![1i64, 2, 3, 4, 5, 6, 7, 8];
let mut st = SegTree::new(&a);
println!("init sum[0..8] = {}", st.query(0, 7));
st.add(2, 5, 10);
println!("after add[2,5]+10: sum[0..8] = {}", st.query(0, 7));
println!("sum[2..5] = {}", st.query(2, 5));
println!("sum[0..1] = {}", st.query(0, 1));
st.add(0, 7, -3);
println!("after add[0,7]-3: sum[3..6] = {}", st.query(3, 6));
let mut one = Vec::new();
for i in 0..8 { one.push(st.query(i, i)); }
println!("point values = {:?}", one);
}

31.3 懒标记：apply、push、pull 三件套

懒标记的全部机制可以拆成三个动作。apply(p,len,v) 把加值挂到节点 p：更新 sum[p] += v*len，累加 lazy[p] += v。push(p,l,r) 在下探之前把标记发给两个孩子：对左孩子传长度 mid-l+1，对右孩子传 r-mid，然后清空 lazy[p]。pull 在递归返回后重算 sum[p] = sum[2p] + sum[2p+1]。

正确性论证依赖一个归纳不变量：对任意节点 p，sum[p] 等于覆盖区间真实和，且 lazy[p] 是尚未应用到子孙的加值总量。形式化地说，设节点 p 覆盖区间 I_p，叶子真实值为 a[x]，则 sum[p] = Σ_{x∈I_p} a[x] + lazy[p] · |I_p| 对所有祖先路径上的节点成立，而 a[x] 只在本节点被完全覆盖或下推到底时才更新。apply 保持不变量：它让 sum 增加 v·len、lazy 增加 v，等式两边同步变化；push 让 lazy 清零并把 v 分别写入左右孩子，父节点 sum 不变，但子节点的 sum + lazy·len 各增加 v·len_child，等式仍成立；pull 在孩子变化后用子节点和重算父节点 sum，由于子节点 sum 已包含各自的 lazy 贡献，父节点无需再叠加自己的 lazy（它已被清空）。三条动作都不破坏不变量，归纳即得正确性。

调用顺序同样重要：必须先 push 再递归，再 pull。若先递归后 push，孩子会将基于旧值的部分结果与父节点尚未下推的标记混合，pull 出来的 sum 必然偏小；若递归后忘了 pull，父节点 sum 停留在修改前，下一次整段命中查询就会返回陈旧值。这两个错误在对拍里都表现为"部分覆盖操作之后才出现 mismatch"，而全区间操作恰好能绕过它们——这也是为什么对拍要同时包含全区间与零散区间。整段命中时直接 apply、不进入孩子，所以单次更新只经过 O(log n) 个节点：每层至多处理两个边界节点加若干整段节点，总数是深度的常数倍。

坑这里最容易踩

这里是坑：查询路径也必须 push。如果 query 遇到部分覆盖时直接读孩子的 sum，而父节点的 lazy 还没下推，读到的就是旧值。上面代码里 query_rec 在递归前无条件调用 push，正是为此。另一个坑是 n=0：new 里 n-1 会在 usize 下溢并 panic，所以显式 assert!(n>0)。第三个坑是 v * len as i64：若 v 与 n 都很大，i64 可能溢出，竞赛场景常改 i128，工程场景应在入口约束数据范围。

再补一个更隐蔽的坑：懒标记的可交换性并非总是成立。若把操作换成"区间赋值 + 区间和"，标记必须覆盖旧值而不是累加；若换成"先乘后加"，push 时必须按复合顺序应用，写反会得到完全不同的结果。本单元的加标记之所以简单，正是因为"加 v"与"加 w"可交换且可合并为"加 v+w"。设计新操作时先问：两个标记能否合成一个？合成是否保序？答不上来就别急着套懒标记模板。前文演示序列里，先对 [2,5] 加 10、再对 [0,7] 减 3，最后逐点结果是 [-2,-1,10,11,12,13,4,5]：第 2 到 5 项确实同时含两次更新，而第 0、1、6、7 项只含后者。这种"人工可核对"的小样例，应当作为对拍之外的第一道防线。

复杂度：建树 O(n)，单次 add / query 访问 O(log n) 个节点，空间 O(n)（4n 上界）。相比"每次 add 用差分再前缀重建"的 O(n)，当操作数 q 远大于 n 时收益是数量级的。

31.4 二维 BIT：lowbit 的秘密与容斥

二维树状数组把一维 lowbit 技巧搬到矩阵上。定义 lowbit(x) = x & x.wrapping_neg()，它取出 x 的最低置位。节点 tree[i][j] 维护的矩形是 (i-lowbit(i)+1 ..= i) × (j-lowbit(j)+1 ..= j)。于是单点加 (x,y) 要沿着 i += lowbit(i)、j += lowbit(j) 向上更新所有包含它的矩形；前缀和 prefix(x,y) 则沿 i -= lowbit(i)、j -= lowbit(j) 向下汇总。

矩形和用容斥分解为四个前缀：rect(x1,y1,x2,y2) = P(x2,y2) - P(x1-1,y2) - P(x2,y1-1) + P(x1-1,y1-1)。这里下标必须从 1 开始：若 x=0，lowbit(0)=0，i += 0 会让你原地打转直到超时；1-based 让所有前缀查询自然以 i -= lowbit(i) 收敛到 0。代码里 tree 开成 (n+1)×(m+1)，第 0 行第 0 列恒为 0，正好作为容斥的哨兵。

tree[i][j] 覆盖的区间为什么恰好是 (i-lowbit(i)+1 ..= i)？把 i 写成二进制，减去最低置位相当于清掉那个 1，得到 i'；区间 (i'..=i] 的长度就是 lowbit(i)。所有落在这个区间内的点 x 满足 x-lowbit(x) < i'，因此它们向上跳 lowbit 时都会经过 i。反过来，一个点 x 向上更新时覆盖的节点集合，恰好是所有满足"节点下标 j ≥ x 且 j-lowbit(j) < x"的 j，这正好是一组互不相交、层层放大的矩形。前缀和 prefix(x,y) 沿着 i 减 lowbit 走，把这些矩形拼成 [1..x]×[1..y] 而不重不漏——这就是不变量。二维情形只是把同样的推理对行、列各做一遍，两个方向的区间独立，故复杂度相乘而非相加。

#![allow(dead_code)]
fn lowbit(x: usize) -> usize { x & x.wrapping_neg() }
/// 二维树状数组：下标从 1 开始，单点加 + 前缀和 + 矩形和。
struct Bit2D {
n: usize,
m: usize,
tree: Vec<Vec<i64>>,
}
impl Bit2D {
fn new(n: usize, m: usize) -> Self {
Self { n, m, tree: vec![vec![0i64; m + 1]; n + 1] }
}
fn add(&mut self, x: usize, y: usize, delta: i64) {
let mut i = x;
while i <= self.n {
let mut j = y;
while j <= self.m {
self.tree[i][j] += delta;
j += lowbit(j);
}
i += lowbit(i);
}
}
fn prefix(&self, x: usize, y: usize) -> i64 {
let mut res = 0i64;
let mut i = x;
while i > 0 {
let mut j = y;
while j > 0 {
res += self.tree[i][j];
j -= lowbit(j);
}
i -= lowbit(i);
}
res
}
/// [x1,x2] x [y1,y2] 的闭区间和，输入均从 1 开始。
fn rect_sum(&self, x1: usize, y1: usize, x2: usize, y2: usize) -> i64 {
if x1 > x2 || y1 > y2 { return 0; }
self.prefix(x2, y2) - self.prefix(x1 - 1, y2)
- self.prefix(x2, y1 - 1) + self.prefix(x1 - 1, y1 - 1)
}
}
fn main() {
let mut bit = Bit2D::new(6, 6);
bit.add(2, 3, 5);
bit.add(4, 4, 7);
bit.add(2, 3, -2);
println!("rect[1..6,1..6] = {}", bit.rect_sum(1, 1, 6, 6));
println!("rect[1..3,1..4] = {}", bit.rect_sum(1, 1, 3, 4));
println!("rect[2..2,3..3] = {}", bit.rect_sum(2, 3, 2, 3));
println!("rect[4..6,4..6] = {}", bit.rect_sum(4, 4, 6, 6));
println!("rect[5..6,1..2] = {}", bit.rect_sum(5, 1, 6, 2));
}

单点 (2,3) 先加 5 再加 -2，净值 3，所以 rect[2..2,3..3]=3；左上 3×4 区域恰好包含这个点，结果同为 3；右下角只包含 (4,4)=7。这些数字与直觉一致，说明容斥的四个前缀方向没有写反。复杂度：add 与 prefix 各 O(log n · log m)，空间 O(nm)；若 n、m 都到 1e5，Vec<Vec<i64>> 的开销不可接受，应换一维压扁数组或稀疏哈希。

工程上还有两个细节值得点明。第一，Vec<Vec<i64>> 的每一行单独分配，遍历时指针跳跃较多；若矩阵规模固定且不大（如几百乘几百），把它压成 Vec<i64> 并用 i*(m+1)+j 索引，常数会明显下降，代价是代码可读性变差。第二，delta 允许为负（上面演示就有 -2），所以 tree 元素必须是有符号整数；若用 u64 存计数，减去一个较大值就会下溢 panic。lowbit 用 wrapping_neg 而不是 -x，是因为标准库对无符号数的一元负号会触发溢出检查，而位模式取反加一正是我们要的低位提取，用 wrapping 语义既安全又表达准确。

31.5 主席树：把每个前缀都存成一张"快照"

主席树（可持久化线段树）解决的问题是：静态数组上查 [l,r] 的第 k 小。做法是把值离散化到 1..m，对前缀 a[1..i] 建一棵值域线段树 root[i]，节点计数表示"该值域区间里出现了多少个数"。关键技巧是路径复制：插入一个值时只复制从根到叶的 log m 个节点，其余子树直接沿用旧版本的编号。这样 root[i] 与 root[i-1] 共享大部分节点，空间从 O(nm) 降到 O(n log m)。

举个具体例子帮助建立图像：若值域 m=8，前缀版本 root[3] 已经在 rank 5 和 rank 7 上各有一个计数，现在要插入 rank 7。路径从根 [1,8] → 右子 [5,8] → 右子 [7,8] → 叶 [7,7]，共 4 个节点被复制；[5,6] 这段子树完全没变，因此 root[4] 的 [5,6] 孩子编号直接复用 root[3] 的对应编号。两个版本加起来只多出 4 个节点，而不是重建整棵 15 节点的树。节点 0 被设为 (0,0,0) 哨兵：空孩子的计数恒为 0，孩子编号恒为 0，这样"不存在的子树"也满足同一套不变量，查询时无需特判 null——这正是用哨兵换掉分支判定的典型手法。

不变量有两条。nodes[cur].2 等于该节点值域区间在当前版本中的计数；root[r] 减去 root[l-1] 得到 [l,r] 的计数直方图（对应节点逐相减）。第二条是查询正确性的核心：root[r] 含 a[1..r] 的计数，root[l-1] 含 a[1..l-1] 的计数，两棵结构相同的值域树逐节点相减，剩下的正是 a[l..r] 中各值出现次数，因为前缀差满足可减性。查询时若左孩子计数 ≥ k，答案在左半值域，否则去右半并把 k 减去左计数；走到叶子即排名，映射回离散化前的原值。注意"第 k 小"按出现次数计数：重复值各占一名，所以 [5,5,7] 的第 2 小仍是 5，这与 sort_unstable 后取下标 k-1 完全一致，也是对拍选用的暴力基准。

Rust 实现里，update 先 let old = self.nodes[prev]; let cur = self.nodes.len(); self.nodes.push(old); 取出旧节点并复制，再对计数加一，然后递归只修改一侧孩子并回写编号。这里 Vec 的引用在 push 之后会失效，所以必须先把旧节点拷贝成局部值，不能持有 &self.nodes[prev] 跨过 push——这是主席树实现最常见的借用错误。

#![allow(dead_code)]
/// 主席树（可持久化线段树）：静态区间第 k 小。
/// nodes[i] = (左孩子, 右孩子, 该节点覆盖区间内的计数)，0 号为哨兵空节点。
struct PersistentSegTree {
nodes: Vec<(usize, usize, usize)>,
roots: Vec<usize>,
m: usize,
}
impl PersistentSegTree {
fn new(m: usize, n: usize) -> Self {
Self { nodes: vec![(0, 0, 0)], roots: vec![0; n + 1], m }
}
fn update(&mut self, prev: usize, l: usize, r: usize, pos: usize) -> usize {
let old = self.nodes[prev];
let cur = self.nodes.len();
self.nodes.push(old);
self.nodes[cur].2 += 1;
if l != r {
let mid = l + (r - l) / 2;
if pos <= mid {
let child = self.update(old.0, l, mid, pos);
self.nodes[cur].0 = child;
} else {
let child = self.update(old.1, mid + 1, r, pos);
self.nodes[cur].1 = child;
}
}
cur
}
fn query(&self, right_root: usize, left_root: usize, l: usize, r: usize, k: usize) -> usize {
if l == r { return l; }
let mid = l + (r - l) / 2;
let left_count = self.nodes[self.nodes[right_root].0].2
- self.nodes[self.nodes[left_root].0].2;
if k <= left_count {
self.query(self.nodes[right_root].0, self.nodes[left_root].0, l, mid, k)
} else {
self.query(self.nodes[right_root].1, self.nodes[left_root].1, mid + 1, r, k - left_count)
}
}
/// 在原始数组 a（下标 1..n）上查询区间 [l,r] 的第 k 小，返回原始值。
fn kth(&self, l: usize, r: usize, k: usize, sorted_unique: &[i64]) -> i64 {
let rank = self.query(self.roots[r], self.roots[l - 1], 1, self.m, k);
sorted_unique[rank - 1]
}
}
fn build_from(a: &[i64]) -> (PersistentSegTree, Vec<i64>) {
let n = a.len();
let mut vals: Vec<i64> = a.to_vec();
vals.sort_unstable();
vals.dedup();
let m = vals.len();
let mut pst = PersistentSegTree::new(m, n);
for i in 0..n {
let rank = vals.binary_search(&a[i]).unwrap() + 1;
let root = pst.update(pst.roots[i], 1, m, rank);
pst.roots[i + 1] = root;
}
(pst, vals)
}
fn main() {
let a = vec![4i64, 1, 5, 2, 7, 3, 5, 8];
let (pst, vals) = build_from(&a);
println!("sorted unique = {:?}", vals);
for (l, r, k) in [(1usize, 5usize, 3usize), (2, 7, 2), (3, 8, 6), (1, 8, 1)] {
println!("a[{}..{}] k={} -> {}", l, r, k, pst.kth(l, r, k, &vals));
}
}

31.6 三种结构的复杂度与工程取舍

把三种结构放在同一张表里，可以看清"维护什么、牺牲什么"。线段树换来了通用性（区间加、区间乘、区间最值都能套同一个框架），但每个节点要维护 sum / lazy 两个量；二维 BIT 代码最短、常数最小，却只支持"点改 + 可减区间查"，一旦更新变成"子矩阵加"就得换二维线段树或二维差分；主席树空间换时间，适合离线静态查询，不能原地修改。

大白话先用直觉把它讲通

选结构其实就是问三个问题——会不会改？查的是"总和"还是"排名"？数据是一维还是二维？会改且查总和选线段树；二维点改查区域选 BIT；不改却要查排名选主席树。把这三个问题答完，结构自然就定了，不必背模板。

结构 支持的操作 单次复杂度 空间 能否修改
懒标记线段树 区间加、区间和 O(log n) O(n) 能，在线
二维 BIT 单点加、矩形和 O(log n · log m) O(nm) 能，仅点改
主席树 静态区间第 k 小 O(log m) O(n log m) 不能，需重建

工程取舍还涉及数值范围与内存层级。线段树的 sum 在 n 较大时要考虑 i64 是否够：n=1e5、元素绝对值 1e9，总和 1e14，i64 游刃有余；若元素到 1e18 则必须 i128，且 len as i128 的转换要显式写出。二维 BIT 的矩阵若是稀疏的（绝大多数格子为 0），用稠密 Vec<Vec> 会浪费上百倍内存，此时应改用哈希映射存非零节点，或用"动态开点"的树状数组。主席树的节点数上限约为 n*(log₂m+1)，n=1e5、m=1e5 时约 1.7e6 个三元组，按每个三元组 24 字节算约 40 MB，仍在可接受范围；但把三元组换成三个独立 Vec<usize> 的 SoA 布局，往往因缓存友好而更快，这是性能敏感场景的后续优化方向，不影响算法正确性。

坑这里最容易踩

这里是坑：主席树的 k 必须先校验 1 <= k <= r-l+1。query 假设 k 合法，若传入 0 会一路走左分支并在叶子返回错误排名；若大于区间长度则在右分支越界。另外离散化用 binary_search 前要对 vals 排序去重，否则同一原值可能对应不同 rank，计数值不会被正确聚合。

31.7 随机对拍：给每个结构找一个"第二实现"

对拍的核心不是"多跑几遍"，而是让两个独立实现在同一随机输入上给出同一答案。下面程序用 xorshift64 生成可复现的随机数据：种子固定为 20261123，因此任何人重跑都得到逐字相同的输出。三个对照分别是：线段树对"逐元素累加的数组"、二维 BIT 对"直接遍历网格求和"、主席树对"截取子数组排序取第 k 个"。任何一次 mismatch 都会让计数增加，最终全为 0 才算通过。

为什么强调"独立实现"？如果对照版复用了被测版的 push / lowbit / 差分逻辑，那么一个错误会同时污染两边，对拍永远绿。真正的暴力版必须笨到不可能错：逐元素加、遍历网格、排序取下标——这些代码的正确性几乎不证自明，才能充当裁判。xorshift64 相比标准库的 rand 无需外部依赖，且状态只有一个 u64，便于在失败时把种子写入日志复现；代价是它不是密码学安全随机源，但对算法对拍完全够用。若担心低位随机性偏差，可以把输出右移若干位再取模，本单元数据量小，直接取模不影响覆盖。

测试规模也有讲究：线段树用 n=40、300 次操作，既覆盖全区间更新也覆盖零散区间；BIT 用 8×8 网格、100 次加 + 200 次查，保证矩形组合足够多样；主席树用 n=60、值域 0..59，重复值必然出现，才能验证"重复计数"的语义。若把规模设成 1 或 2，很多边界分支根本走不到；若设成 1e6，暴力对照又慢到跑不完。对拍规模应取"暴力还能秒出结果、但组合数量足够覆盖分支"的甜点区。真出现 mismatch 时，下一步是缩小用例（delta debugging）：固定随机种子后逐段删操作，只要仍然失败就保留删除，最终得到一个最小反例——第 34 单元会把这套流程做成通用工具。

}

// ---- segment tree ----
struct SegTree { n: usize, sum: Vec<i64>, lazy: Vec<i64> }
impl SegTree {
fn new(a: &[i64]) -> Self {
let n = a.len();
let mut st = Self { n, sum: vec![0; 4*n+4], lazy: vec![0; 4*n+4] };
st.build(1, 0, n-1, a); st
}
fn build(&mut self, p: usize, l: usize, r: usize, a: &[i64]) {
if l == r { self.sum[p] = a[l]; return; }
let m = l + (r-l)/2;
self.build(p*2, l, m, a); self.build(p*2+1, m+1, r, a);
self.sum[p] = self.sum[p*2] + self.sum[p*2+1];
}
fn apply(&mut self, p: usize, len: usize, v: i64) { self.sum[p] += v*len as i64; self.lazy[p] += v; }
fn push(&mut self, p: usize, l: usize, r: usize) {
if self.lazy[p] != 0 && l < r {
let m = l + (r-l)/2; let v = self.lazy[p];
self.apply(p*2, m-l+1, v); self.apply(p*2+1, r-m, v); self.lazy[p] = 0;
}
}
fn add(&mut self, ql: usize, qr: usize, v: i64) { if ql <= qr { self.add_rec(1, 0, self.n-1, ql, qr, v); } }
fn add_rec(&mut self, p: usize, l: usize, r: usize, ql: usize, qr: usize, v: i64) {
if ql <= l && r <= qr { self.apply(p, r-l+1, v); return; }
self.push(p, l, r);
let m = l + (r-l)/2;
if ql <= m { self.add_rec(p*2, l, m, ql, qr, v); }
if qr > m { self.add_rec(p*2+1, m+1, r, ql, qr, v); }
self.sum[p] = self.sum[p*2] + self.sum[p*2+1];
}
fn query(&mut self, ql: usize, qr: usize) -> i64 { if ql > qr { 0 } else { self.query_rec(1, 0, self.n-1, ql, qr) } }
fn query_rec(&mut self, p: usize, l: usize, r: usize, ql: usize, qr: usize) -> i64 {
if ql <= l && r <= qr { return self.sum[p]; }
self.push(p, l, r);
let m = l + (r-l)/2; let mut res = 0;
if ql <= m { res += self.query_rec(p*2, l, m, ql, qr); }
if qr > m { res += self.query_rec(p*2+1, m+1, r, ql, qr); }
res
}
}
// ---- 2D BIT ----
fn lowbit(x: usize) -> usize { x & x.wrapping_neg() }
struct Bit2D { n: usize, m: usize, t: Vec<Vec<i64>> }
impl Bit2D {
fn new(n: usize, m: usize) -> Self { Self { n, m, t: vec![vec![0; m+1]; n+1] } }
fn add(&mut self, x: usize, y: usize, v: i64) {
let mut i = x;
while i <= self.n { let mut j = y; while j <= self.m { self.t[i][j] += v; j += lowbit(j); } i += lowbit(i); }
}
fn prefix(&self, x: usize, y: usize) -> i64 {
let mut r = 0; let mut i = x;
while i > 0 { let mut j = y; while j > 0 { r += self.t[i][j]; j -= lowbit(j); } i -= lowbit(i); } r
}
fn rect(&self, x1: usize, y1: usize, x2: usize, y2: usize) -> i64 {
if x1 > x2 || y1 > y2 { return 0; }
self.prefix(x2,y2) - self.prefix(x1-1,y2) - self.prefix(x2,y1-1) + self.prefix(x1-1,y1-1)
}
}
// ---- persistent seg tree ----
struct Pst { nodes: Vec<(usize,usize,usize)>, roots: Vec<usize>, m: usize }
impl Pst {
fn new(m: usize, n: usize) -> Self { Self { nodes: vec![(0,0,0)], roots: vec![0;n+1], m } }
fn update(&mut self, prev: usize, l: usize, r: usize, pos: usize) -> usize {
let old = self.nodes[prev]; let cur = self.nodes.len(); self.nodes.push(old); self.nodes[cur].2 += 1;
if l != r { let mid = l+(r-l)/2;
if pos <= mid { let c = self.update(old.0,l,mid,pos); self.nodes[cur].0 = c; }
else { let c = self.update(old.1,mid+1,r,pos); self.nodes[cur].1 = c; }
} cur
}
fn query(&self, rr: usize, lr: usize, l: usize, r: usize, k: usize) -> usize {
if l == r { return l; }
let mid = l+(r-l)/2;
let lc = self.nodes[self.nodes[rr].0].2 - self.nodes[self.nodes[lr].0].2;
if k <= lc { self.query(self.nodes[rr].0, self.nodes[lr].0, l, mid, k) }
else { self.query(self.nodes[rr].1, self.nodes[lr].1, mid+1, r, k-lc) }
}
fn kth(&self, l: usize, r: usize, k: usize, vals: &[i64]) -> i64 {
vals[self.query(self.roots[r], self.roots[l-1], 1, self.m, k) - 1]
}
}

31.8 自检与练习

三种结构看似毫不相干，实则共享同一条方法论：先写不变量，再写操作，最后用不变量解释每一行代码。线段树的不变量是"sum 含 lazy 记账、push 只搬运记账"，二维 BIT 的不变量是"tree[i][j] 覆盖 lowbit 矩形"，主席树的不变量是"版本差即区间计数直方图"。调试时不要一上来打日志，而应先问：哪条操作破坏了哪条不变量？整段命中是否漏了 push？1-based 是否被某处 0-based 污染？版本差是否把 l-1 写成了 l？把问题定位到具体不变量，修复往往只有一行；反之盲目改代码，常常按下葫芦浮起瓢。这也解释了为什么对拍必须打印操作计数与抽样细节——它们是把"哪一步出错"缩小到"哪一类操作出错"的线索。下一单元开始处理数论，其中的 exgcd 与快速幂同样依赖"每步保持什么不变"的推理方式，本单元练就的思路会直接复用。

自检合上书之前问自己
  • 线段树里 apply 为什么要乘以区间长度，而 push 要给左右孩子传不同长度？
  • 二维 BIT 的下标如果从 0 开始，lowbit(0)=0 会让哪个循环卡死？怎么改才安全？
  • 主席树的 root[r] - root[l-1] 为什么恰好得到 [l,r] 的计数直方图？
  • 为什么线段树查询也必须调用 push，而主席树查询完全不需要修改节点？

动手动脑

  • 练习 1：给线段树再加"区间乘 + 区间和"，提示：节点需要两个标记（乘标记、加标记），push 时先乘后加；把 300 次随机操作与数组暴力对拍，报告 mismatch。
  • 练习 2：把二维 BIT 改成"子矩阵加 + 单点查"，提示：用二维差分 + 四次前缀更新，仍然 1-based；用 8×8 网格与暴力对拍 200 次。
  • 练习 3：给主席树加上 count(l,r,x)——返回 [l,r] 中 ≤ x 的元素个数，提示：在值域线段树上按 rank 边界累加计数；用排序子数组 + partition_point 对照。
  • 练习 4：把对拍种子改成你自己的学号，重跑 v31_cross.rs，确认三个 mismatch 仍为 0；若出现不为 0，打印失败时的 l、r、k 并定位是不变量写错还是随机数据越界。
