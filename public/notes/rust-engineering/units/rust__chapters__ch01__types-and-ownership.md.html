2.1 类型的三重身份：尺寸、对齐与内存布局

学类型时最容易被忽略的是：类型首先是一段内存布局的描述。编译器需要知道每个类型占多少字节（size_of）、起始地址必须满足什么对齐（align_of），才能正确地在栈上开空间、在结构体里排布字段、生成读写指令。u8 是 1 字节 1 对齐，u64 在常见的 64 位平台上是 8 字节 8 对齐；引用（&str、&[u8]）是胖指针，占两个机器字，因为除了地址还要带长度或元数据；String 和 Vec<T> 都是三个机器字：指向堆缓冲区的指针、长度、容量。这三个字本身在栈上，真正的数据在堆上——所谓「String 在堆上」是简略说法，准确说法是「String 的句柄在栈上，句柄指向的缓冲区在堆上」。

结构体字段的排布由 repr 决定。默认的 repr(Rust) 不保证字段顺序与源码一致，编译器可以重排以减少填充；repr(C) 则严格按声明顺序排布，用于 FFI。Mixed { a: u8, b: u64, c: u8 } 在默认布局下是 16 字节（编译器把两个 u8 挪到一起），加上 #[repr(C)] 后变成 24 字节（中间要插 7 字节填充）。这个差异不是实现细节的八卦：它提醒你不要依赖结构体字段的内存顺序，除非明确写了 repr(C)。

下面的程序把上述结论变成可观察的输出。show::<T>() 是泛型函数，泛型参数只用在 size_of::<T>() 这类类型级位置，所以调用时必须写 turbofish 语法 ::<T>——编译器没法从参数反推出 T。

rustRust · 标准库23 行
#![allow(dead_code)]
use std::mem::{align_of, size_of};
struct Mixed { a: u8, b: u64, c: u8 }
#[repr(C)]
struct CMixed { a: u8, b: u64, c: u8 }
fn show<T>(name: &str) {
println!("{name:<12} size={:>3} align={:>2}", size_of::<T>(), align_of::<T>());
}
fn main() {
show::<u8>("u8");
show::<i32>("i32");
show::<u64>("u64");
show::<&str>("&str");
show::<String>("String");
show::<Vec<u8>>("Vec<u8>");
show::<()>("()");
show::<[u8; 0]>("[u8;0]");
show::<Mixed>("Mixed");
show::<CMixed>("#[repr(C)] Mixed");
}

在本机（64 位）跑出的真实结果如下。注意 () 和 [u8; 0] 是零大小类型（ZST）：占 0 字节，但对齐仍为 1。ZST 很有用——它们可以当状态标记、当 trait 的标记类型，Vec<()> 不会为元素分配任何堆内存，push 只是把长度加一。

类型先是一张「占地说明」。栈上放的是句柄（几个机器字），堆上放的是真正的大块数据。ZST 像一张写着「占地为零」的说明：东西存在，但不占地方。结构体字段的顺序编译器可以悄悄调整，除非你用 repr(C) 明确要求按源码顺序摆。

2.2 Copy 的精确边界：什么才能被安全地按位复制

Copy 是一个标记 trait：它没有任何方法，只是告诉编译器「这个值可以按位复制，复制完两份都有效」。i32、bool、char、浮点数是 Copy；由 Copy 字段组成的元组、数组、结构体也是 Copy；不可变引用 &T 永远是 Copy，无论 T 是什么；函数指针也是 Copy。反过来，String、Vec<T>、Box<T> 不是 Copy，因为它们拥有堆资源，简单复制位模式会造成两次释放同一块内存。&mut T 也不是 Copy——它代表独占访问权，复制一份就违反独占性。

Copy 与 Clone 的关系是单向的：Copy 要求 Clone，所以能 Copy 的类型一定能显式 Clone；但 Clone 不一定是 Copy。手写 Clone 可以做任意深拷贝，Copy 只能是浅的按位复制。还有一个硬约束：实现了 Drop 的类型不能实现 Copy，因为编译器不允许一个类型既有自定义析构逻辑、又能被无声地按位复制——那样析构会被调用几次就说不清了。这解释了为什么给一个 struct 加上 Drop 实现后，原本 #[derive(Copy)] 的代码会突然编译失败。

理解 Copy 的关键不是背类型清单，而是问一个问题：「如果我把这段位模式原样复制一份，两份之间会不会互相干扰、会不会有资源被重复释放？」对 u64 答案是否定的，对 String 答案是肯定的（两个句柄指向同一块缓冲区，drop 时会 double free）。Cell<T> 和 RefCell<T> 这类内部可变性容器也都不是 Copy，因为复制共享的状态会破坏它们的语义。泛型代码里可以用 T: Copy 约束表达「我需要能廉价复制这个参数」，这比无条件 .clone() 更精确，也向调用方传达了真实需求。

大白话先用直觉把它讲通

Copy 就是「复印一张纸，两份都能独立用」，比如复印一张写着数字的便签；Clone 是「照着菜谱重新做一份」，可能要重新买菜、重新下锅。字符串像一张写着仓库地址的钥匙卡：把卡片复印一张，两个人拿同一把钥匙去开同一个仓库，还都以为自己负责锁门——这就乱了。所以字符串只能 Clone 不能 Copy。

2.3 move 不是搬运：按位复制加失效标记

新手常把 move 想象成「把数据从旧变量搬到新变量，旧位置被清空」。更接近真相的模型是：move 在机器层面通常就是一次按位复制，随后编译器把源变量标记为「已初始化失效」。旧位置的内存可能还残留着原来的字节，但你再也不能通过源变量访问它——编译器会阻止你。所有权不是运行时机制，而是编译器的静态记账：let b = a; 之后，a 在类型检查器眼里就是未初始化状态。

结构体可以部分移动（partial move）：把 String 字段移走后，其余 Copy 字段仍然可用，因为编译器按字段粒度追踪初始化状态。下面的程序演示这一点，并给出数组为什么不能按索引移动。数组下标 arr[0] 是一个「位置表达式」，但编译器无法证明它只被求值一次、也不会在循环里产生重复移动，所以禁止从非 Copy 数组里按索引移出元素（错误码 E0508）；用解构 let [a, b] = arr; 一次性拿走全部元素则是合法的。

rustRust · 标准库16 行
#[derive(Debug)]
struct User { id: u64, name: String }
fn take_name(name: String) -> usize { name.len() }
fn main() {
let u = User { id: 7, name: String::from("Ada") };
let id = u.id; // Copy：u.id 之后仍可读
let name = u.name; // move：name 字段失效
println!("id = {id}, u.id 仍可读 = {}", u.id);
println!("name 长度 = {}", take_name(name));
let arr = [String::from("x"), String::from("y")];
let [first, second] = arr; // 解构可以整体移出
println!("解构数组: {first}, {second}");
}

如果把 println!("{}", u.name); 加回去，编译器会给出下面这样的诊断（省略了「n 未使用」的附带警告）。注意它明确指出「move occurs because u.name has type String, which does not implement the Copy trait」——错误信息把所有权规则的因果链完整写了出来，而不是冷冰冰地说「变量已移动」。

move 在函数调用和闭包里也遵循同样的记账规则：把一个非 Copy 的值传给函数，所有权就转移给形参，调用结束后原变量不能用；闭包捕获外部变量时，如果捕获方式是按值（move 或编译器推断为移动），同样会让原变量失效。靠「我之后还会用」的直觉写代码行不通，必须看最后一次使用发生在哪里——这正是下一单元借用检查器要做的数据流分析。

2.4 Drop 的时机与顺序：像剥洋葱一样确定

当一个值离开作用域，编译器会插入对 Drop::drop 的调用（如果类型实现了 Drop）。顺序是可预测的：局部变量按声明的相反顺序 drop；结构体的字段在 Drop::drop 执行完毕后按声明顺序 drop；Vec 的元素则从前到后依次 drop。把「局部变量后进先出」和「字段先进先出」区分开很重要——前者像栈，后者是结构体内存布局的线性扫描。

下面的程序用 Guard 在析构时打印自己的名字，把顺序变成可见事实。Pair 自己实现了 Drop，所以你会先看到 drop Pair，再看到两个字段按声明顺序被释放。

rustRust · 标准库16 行
#![allow(dead_code)]
struct Guard(&'static str);
impl Drop for Guard {
fn drop(&mut self) { println!("drop {}", self.0); }
}
struct Pair { first: Guard, second: Guard }
impl Drop for Pair {
fn drop(&mut self) { println!("drop Pair"); }
}
fn main() {
let _p = Pair { first: Guard("first"), second: Guard("second") };
let _g = Guard("local");
println!("--- 作用域结束 ---");
}

$ rustc --edition 2021 drop_order.rs -o drop_order && ./drop_order

drop local
drop Pair
drop first
drop second

drop 顺序不是学究式的细节，它决定资源释放的正确性。考虑一个持有文件句柄和内存缓冲区的结构：如果缓冲区先释放、文件句柄后释放，写盘逻辑还能正常工作；反过来就可能出问题。Rust 用确定的顺序消除了这类不确定性。另一个边界是部分移动后的析构：一个结构体即使有字段被移走，它的 Drop::drop 仍会被调用，但你在 drop 里不能访问已移走的字段（编译器会拒绝）——所以实现 Drop 的类型通常避免在 drop 里读取自己的字段内容。

需要提前释放时，用 std::mem::drop(value)（它只是把值当作形参接收，函数结束时触发析构），或 std::mem::take / std::mem::replace 把值换出来再处理。std::mem::take(&mut s) 会用 Default 值把原值换走，对 String 来说就是拿走内容、留下空串，这比手写「先 clone 再清空」高效得多。若想彻底禁止自动析构，可以用 std::mem::ManuallyDrop<T> 包一层——代价是你自己承担释放责任，通常只在实现底层容器或 FFI 边界时才需要。

Drop 与异常安全也有关：Rust 的 panic 会触发栈展开（unwind），沿途所有局部变量照样按序 drop，这就是 RAII（资源获取即初始化）的保障来源。反过来说，如果编译配置选了 panic = "abort"，程序会立刻终止、不再展开栈，操作系统仍会回收进程占用的资源，但你自己写的 Drop 逻辑不会执行——涉及落盘、释放外部锁这类副作用时，这个差别必须想清楚。

坑这里最容易踩

坑：给一个已经 #[derive(Copy)] 的结构体添加 Drop 实现，编译会报「cannot implement both Drop 和 Copy」。原因是 Copy 会让同一份位模式出现多个「所有者」，析构时无法决定谁负责释放。正确做法是二选一：如果这个类型真的拥有资源，就去掉 Copy 并手写 Clone（深拷贝资源）；如果只是普通的值类型，就不要加 Drop。另一个坑是以为 drop(x) 之后 x 还能用——drop 的参数按值传入，调用后 x 已被移动，编译器会禁止后续访问。

2.5 整数溢出：同一段代码，两套语义

Rust 的整数溢出是个刻意设计的「分裂」行为：debug 构建默认开启溢出检查，溢出时直接 panic；release 构建默认关闭检查，溢出时按二进制补码回绕（wrap）。同一行 a + b，在 cargo run 和 cargo run --release 下可能一个崩溃、一个悄悄给出错误结果。这不是 bug，而是在「开发期尽早暴露错误」与「发布后少一次分支判断」之间做的权衡；构建 profile 里的 overflow-checks 设置可以改变默认值，对正确性敏感的服务端程序应当在 release 里也打开它。

为了避免依赖构建模式，标准库提供了四组显式方法。checked_* 溢出时返回 None；wrapping_* 永远回绕；saturating_* 钳位到类型边界（上溢取 MAX，下溢取 MIN）；overflowing_* 同时返回结果和「是否溢出」的布尔值。它们都是普通函数，不受 profile 影响，是写健壮代码时的首选。下面的程序用 u8 把四种行为跑一遍，并展示 as 转换的截断语义。

rustRust · 标准库10 行
fn main() {
let max = u8::MAX;
println!("max + 1: checked={:?}", max.checked_add(1));
println!("max + 1: wrapping={}", max.wrapping_add(1));
println!("max + 1: overflowing={:?}", max.overflowing_add(1));
println!("1 - 3(u8): checked={:?}", 1u8.checked_sub(3));
println!("1 - 3(u8): wrapping={}", 1u8.wrapping_sub(3));
println!("1 - 3(u8): saturating={}", 1u8.saturating_sub(3));
println!("300u16 as u8 = {}", 300u16 as u8);
}

$ rustc --edition 2021 overflow.rs -o overflow && ./overflow

max + 1: wrapping=0
max + 1: overflowing=(0, true)

1 - 3(u8): wrapping=254

回绕并不总是错误：哈希函数、环形缓冲区索引、部分密码学算法本来就定义在模 2ⁿ 的算术上，wrapping_add 正是为这些场景准备的，它让意图在代码里显式可见，也避免因为 profile 切换而改变结果。真正的危险是「本来不该溢出，却因为回绕悄悄算错」——比如统计计数超过 u32::MAX 后变小，导致缓存淘汰逻辑判断失误。对这类业务数值，checked_add 加 expect("计数溢出") 或直接用更宽的 u64 才是稳妥选择。

300u16 as u8 = 44 来自 300 的低 8 位（300 = 256 + 44）。as 的数值转换永远是截断或按补码解释，不会 panic 也不会报错——这是它和 try_into() 的根本区别。工程里有一条简单纪律：只要值可能超出目标类型范围，就用 TryFrom / try_into() 拿到 Result 并处理失败，别用 as 蒙混过关。还有一个高频坑是 usize 下溢：循环里写 for i in (0..n).rev() 没问题，但手写 while i >= 0 { i -= 1; } 时 i 是无符号数，0 - 1 会变成巨大的数，导致死循环或越界——这类边界在算法编会反复遇到。

2.6 类型推断与 never type：编译器在解一组约束方程

Rust 的类型推断不是「看右边猜类型」这么简单，它更像把整个函数体里的类型约束收集起来解方程组。let x = 5; 里 5 可以是任何整型，没有别的约束时编译器采用默认规则回落到 i32；一旦出现 let y: u8 = x;，约束立刻把 x 定成 u8。collect() 是经典例子：let v = iter.collect(); 无法推断目标容器类型，必须写 let v: Vec<i32> = ... 或 iter.collect::<Vec<i32>>()。这种「约束不足就报错」的行为不是编译器笨，而是拒绝在有多种合理答案时替你随机选一个。

! 是 never type（永不类型），表示「这个表达式永远不会产生值」。return、break、panic!()、无限循环 loop {} 的类型都是 !。关键性质是 ! 可以强制转换成任意类型：于是 let n: i32 = panic!(); 能通过类型检查——因为右边根本不会返回，把它当 i32 用不会带来任何运行时不一致。std::convert::Infallible 是 ! 在类型库里的替身，表示一个「不可能被构造出来」的错误类型，常用于「这个操作理论上不会失败」的泛型签名。

rustRust · 标准库15 行
use std::convert::Infallible;
fn first_or<T>(items: &[T]) -> Result<&T, Infallible> {
Ok(&items[0])
}
fn main() {
let data = [10, 20, 30];
let r: &i32 = first_or(&data).unwrap(); // 错误分支是 Infallible，等价于永不会发生
println!("first = {r}");
let parsed = "42".parse::<i32>().unwrap(); // parse 的错误类型由目标类型决定
println!("parsed = {parsed}");
let empty: Vec<String> = Vec::new(); // 空容器必须标注元素类型
println!("empty len = {}", empty.len());
}

这段程序里藏着两处推断："42".parse() 的错误类型由赋值目标 i32 决定（写成 parse::<u8>() 就会走另一条实现）；Vec::new() 完全没有任何类型线索，只能靠标注。理解推断的约束本质，能让你在看到「type annotations needed」时立刻补上正确的标注，而不是乱试 turbofish。另一个常见现象是「整数字面量在比较时才定型」：1 + 2 单独出现时是 i32，放进 let x: u8 = 1 + 2; 就整段变成 u8 运算——约束会沿着表达式反向传播。

闭包参数也是推断的高频现场：let f = |x| x + 1; 里的 x 类型要等第一次调用才确定，如果在那之前没有任何线索，编译器会报「type annotations needed」。这时可以写 let f = |x: i32| x + 1;，或者给变量一个函数指针类型标注。还有一类「默认类型回落」值得记住：浮点字面量没有约束时回落到 f64 而不是 f32。这些默认规则是语言为了少写标注做出的务实妥协，但一旦你把它当成「类型永远是这样」，就会在泛型代码里摔跤——泛型参数没有默认回落，约束不足就是错误。

2.7 内部可变性引子：共享引用也能改数据

借用规则说「有 &mut T 就不能有 &T」，但有些场景需要「大家共享一个引用，同时又能修改里面的计数器」。Rust 用**内部可变性（interior mutability）**解决：把可变性从引用类型挪到类型内部。Cell<T> 提供 get / set，set 接收 &self，所以通过一个共享引用就能改值；get 要求 T: Copy，因为要复制一份出来。RefCell<T> 放宽到任意 T：它返回一个 Ref<T> / RefMut<T> 守卫，借用期间借用标志由运行时维护，违反规则时 borrow_mut() 会 panic，而 try_borrow_mut() 返回 Result 让调用方自己处理。

下面的程序先把 &Cell<i32> 传给函数并调用 set，再演示 RefCell 的运行时借用检查：持有一个共享借用时尝试 try_borrow_mut() 会被拒绝，释放守卫后才成功追加元素。

rustRust · 标准库22 行
use std::cell::{Cell, RefCell};
fn bump(c: &Cell<i32>) { c.set(c.get() + 1); }
fn main() {
let c = Cell::new(0);
let r = &c;
bump(r);
bump(r);
println!("Cell = {}", c.get());
let rc = RefCell::new(vec![1, 2, 3]);
let guard = rc.borrow();
println!("共享借用 len = {}", guard.len());
match rc.try_borrow_mut() {
Ok(_) => println!("拿到可变借用"),
Err(e) => println!("借用被拒: {e}"),
}
drop(guard);
rc.borrow_mut().push(4);
println!("追加后 = {:?}", rc.borrow());
}

$ rustc --edition 2021 cell.rs -o cell && ./cell

共享借用 len = 3
借用被拒: RefCell already borrowed
追加后 = [1, 2, 3, 4]

内部可变性不是「绕过借用检查」的后门，而是把检查从编译期挪到运行期：RefCell 内部有一个借用状态计数器，borrow() 递增共享计数，borrow_mut() 要求计数为零，否则报错。代价有三条：违规变成运行时 panic 而非编译错误；Cell / RefCell 都不是 Sync，不能跨线程共享（线程安全版本是 Mutex / RwLock）；RefCell 的守卫会延长借用存活期，忘记 drop 就容易触发意外冲突。它们的底层都建立在 UnsafeCell<T> 之上——语言把「允许通过共享引用修改」的唯一合法入口封装在这一类型里，标准库再用它构建安全的抽象。这正是下一单元要展开的借用检查器视角的反面：编译期管不住的地方，就用类型把规则编码进 API。

2.8 工程取舍：值语义的收益与成本

所有权系统最终要回答一个工程问题：数据到底归谁、复制的代价有多大。一个简单的判断顺序是：能借用就不转移，能 Copy 就不 Clone，必须 Clone 时让代价可见。对 i32 这类 Copy 类型，传值和传引用差别不大，直接传值反而让签名更简单；对 String 和 Vec，按值传递会转移所有权，适合「函数要消费它」的场景，而借用更适合「只读一下」。泛型函数里用 impl AsRef<str> 或 &str 接收字符串，可以让调用方自由选择传 String 还是字面量，避免不必要的分配。

场景 首选方式 代价 误用的后果
小型标量/Copy 类型 直接传值 按位复制，几乎为零 无
大结构只读访问 &T 借用 一次间接寻址 生命周期标注变复杂
函数需要接管数据 按值 move 无额外分配 调用方失去使用权
双方都要保留副本 .clone() 深拷贝资源 热路径上可能成为瓶颈
共享引用下的修改 Cell/RefCell 运行期检查 违规时 panic、非线程安全

把这张表和前面几节的机制对照起来看：Copy 的边界决定「复制是否安全」，Drop 的顺序决定「释放是否可靠」，整数溢出语义决定「计算是否可信」，内部可变性决定「共享与修改如何共存」。这些都不是孤立的语法点，而是同一个设计目标的不同侧面——用编译期信息换掉运行时的不确定性。下一单元我们进入借用检查器内部，看它如何在控制流图上判断一次借用究竟活到哪儿。

所有权还有一个常被追问的问题：这些检查有运行时成本吗？绝大多数情况下没有。&T 和 T 的机器表示往往相同（都是一个地址或直接是值本身），move 通常是按位复制，Drop 的插入点由编译器静态决定，Copy 的开销等同于赋值。所谓的「零成本抽象」在这里体现得很直白：你得到的是内存安全保证，付出的主要成本是编译期分析和偶尔一次必要的 .clone()。真正需要权衡的是设计层面——把数据设计成值语义还是引用语义、是否需要共享可变性、要不要为方便而多分配一次。这些取舍没有通用答案，但你可以用本单元给出的机制去估算代价，而不是凭感觉猜。
