1.1 先讲动机：为什么需要一条工具链

写一个 Rust 程序，表面上看只是「把文本变成能运行的二进制」。但真正让人头疼的从来不是语法本身，而是依赖怎么管、不同机器怎么保持一致、代码风格怎么统一、常见错误能不能早点被发现。Rust 的答案是把这些问题交给一条配套的工具链，而不是让你自己拿一堆脚本去拼。

对初学者来说，最大的认知负担往往来自「我到底该敲哪条命令」。rustc、cargo、rustfmt、clippy 这四个名字会反复出现，它们不是互相竞争的替代品，而是分工明确的协作者。先记住一句话：rustc 负责把源码编译成程序，cargo 负责组织项目和依赖，rustfmt 负责排版，clippy 负责挑刺。剩下都是细节。

大白话先用直觉把它讲通

把写程序想成开一家小饭馆。rustc 是灶台，真正把食材做熟；cargo 是店长，管进货、排班、下单；rustfmt 负责把桌子擦得整整齐齐；clippy 像一位挑剔的美食评论家，专门提醒你「这样写能吃，但不够好」。你不用亲自当灶台，但要认识每位伙计。

安装 Rust 时通常会用到 rustup，它是工具链的安装与切换器，负责把上面这些工具装到你的机器上，并让你在不同版本之间切换。注意 rustup 本身不是编译器，它只是「装工具的工具」。真正决定代码语义的是「edition（版本）」：Rust 从 2015 到 2021（再到更新的版本）经历过几次语言级演进，edition 用来标记一套语义规则。新项目几乎都该选 2021，这也是本系列默认使用的版本。

为什么要在命令里显式写 edition？因为省略时，不同版本的 rustc 可能采用不同的默认 edition，导致同一份代码在不同机器上的行为有细微差别。编译期把这个选择写死，是一种很便宜的「可复现性」投资。尤其在团队里或者 CI（持续集成）环境中，可复现比「在我机器上能跑」重要得多。

1.2 rustc：把源码变成可执行文件

rustc 是 Rust 的编译器，它接收一个 .rs 文件，输出可执行文件或库。最小的一段程序只需要一个 main 函数——它是程序执行的入口，程序从这里开始、在这里结束。注意 Rust 用 println! 结尾的感叹号表示这是一个宏（macro），而不是普通函数。宏在编译期展开，能做一些函数做不到的事，比如接受可变数量的参数、对格式字符串做静态检查。

下面这段代码不依赖任何外部库，只用标准库 std，可以直接交给 rustc 编译。试着把它存成 main.rs，然后编译运行。标准库是随语言一起分发的，任何符合规范的 Rust 环境都自带它，不需要额外下载。

rustRust · 标准库6 行
fn main() {
println!("Hello, Rust!");
let a = 7;
let b = 9;
println!("{a} + {b} = {}", a + b);
}

编译和运行的过程如下。这里显式写 --edition 2021，是为了锁定语言版本；-o hello 指定输出文件名。如果不写 edition，rustc 会用默认的 edition（新版本工具链通常是 2021 或更高），显式声明能让行为更可预期。

终端真跑一遍
$ rustc --edition 2021 main.rs -o hello
$ ./hello
Hello, Rust!
7 + 9 = 16

{a} 这种写法叫「格式化参数隐式捕获」，编译器会从当前作用域里找同名变量填进去，从 Rust 1.58 起就稳定可用。它比 println!("{} {}", a, b) 更好读，因为变量名直接写在字符串里，改代码时不容易对错位置。还有一个细节：格式字符串里的 {} 会在编译期被检查，如果占位符数量和传入参数对不上，编译器直接报错，而不是等到运行时才打出奇怪的结果。这种「把错误挡在编译期」的思路，是 Rust 一贯的风格。

编译器的错误信息也值得专门提一句。Rust 的错误提示以详细著称，它不仅告诉你哪一行出错，还常常给出修改建议，甚至用彩色箭头标出问题位置。初学时不要害怕报错，把报错当成一对一的辅导老师：读懂它、按它说的改，往往比到处搜答案更快的提升方式。

1.3 cargo：项目管家与构建系统

单个文件用 rustc 足够，但项目一旦有依赖、有多个源文件、有测试和构建配置，手敲 rustc 命令就会迅速失控。你要记住每个依赖的版本、文件路径、编译参数，还要保证同事的机器上命令完全一致。cargo 是 Rust 的包管理器和构建系统，它约定了一套目录结构，你只要把文件放对位置，剩下的交给它。

下面是四个工具的职责对照，建议先有个整体印象。

工具 角色 你最常敲的命令
rustc 编译器，把源码变成二进制 rustc --edition 2021 main.rs
cargo 包管理器与构建系统 cargo new、cargo build、cargo run、cargo check
rustfmt 格式化工具，统一排版 cargo fmt
clippy 静态检查，给出改进建议 cargo clippy

用 cargo new 创建项目，cargo 会帮你生成目录和一个能跑的「Hello, world!」。注意项目名里如果带连字符，例如 hello-rust，生成的目标名会换成下划线 hello_rust，这是 Rust 标识符的规则所致。如果是在已有目录里初始化，用 cargo init 而不是 cargo new，区别只在于是否新建一层文件夹。

终端真跑一遍
$ cargo new hello_rust
Created binary (application) `hello_rust` package
$ cd hello_rust
$ cargo run
Compiling hello_rust v0.1.0 (.../hello_rust)
Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.42s
Running `target/debug/hello_rust`
Hello, world!

上面 cargo run 的输出里，编译耗时和具体路径因机器而异，属于示意输出。目录结构里，Cargo.toml 是清单文件，记录项目名、版本和依赖；Cargo.lock 锁定依赖的具体版本，保证每次构建拿到同样的依赖树；src/main.rs 是二进制入口；target/ 放编译产物，通常不用手动碰，也能随时删掉让 cargo 重新生成。cargo check 只做类型检查不生成二进制，日常开发里它比 cargo build 快得多，适合频繁调用；确认无误后再用 cargo build 或 cargo run 生成程序。

依赖写在 Cargo.toml 的 [dependencies] 段落里，cargo 会从官方仓库拉取并解析版本。版本号遵循语义化版本规范，cargo 在兼容范围内选择最新可用版本，而 Cargo.lock 把最终选择固定下来。这套机制让「升级一个依赖可能悄悄破坏构建」的概率大大降低。

1.4 rustfmt 与 clippy：让代码更地道

能编译不代表写得好。rustfmt 会按社区统一风格重排代码，clippy 则在上百条规则上给你建议，比如提醒你某个手写循环其实有更惯用的写法。两者都不改变语义，可以放心当作「免费体检」。统一风格的意义在团队里尤其明显：当所有人都用同一套排版，代码评审就能把注意力放在逻辑上，而不是花时间争论缩进和大括号位置。

rustfmt 的开箱即用配置已经覆盖绝大多数场景，你几乎不需要调参数。运行 cargo fmt 会格式化整个包，运行 cargo fmt --check 则只检查不修改，常用于 CI 里强制风格。如果确实要定制，可以在项目根目录放一个 rustfmt.toml，但初学阶段不建议急着改——先接受社区默认值，往往比「我觉得这样更好看」更靠谱。

clippy 的建议分等级：有些是 warning，不阻碍编译；有些在严格模式下会成为 error。初学阶段不必追求清零所有警告，但每条警告都值得读一遍，因为它往往对应着一个真实存在的坏习惯。比如下面这段程序用 iter().sum() 求和，而不是手写累加循环——这正是 clippy 会「建议你考虑」的惯用写法，它更短，也不容易在边界条件上出错。

rustRust · 标准库10 行
fn add(a: i32, b: i32) -> i32 {
a + b
}
fn main() {
let numbers = [1, 2, 3, 4, 5];
let sum: i32 = numbers.iter().sum();
println!("{} + {} = {}", 7, 9, add(7, 9));
println!("数组 {:?} 的和是 {}", numbers, sum);
}
终端真跑一遍
$ cargo fmt
$ cargo clippy
Checking hello_rust v0.1.0 (.../hello_rust)
Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.31s

一个实用的节奏是：写完一段就用 cargo check 快速确认类型没问题，阶段性完成后跑 cargo clippy 看看有没有更地道的写法，提交前用 cargo fmt 统一排版。把工具用成习惯，而不是等到「代码丑得看不下去」才想起来，收益会大得多。

1.5 workspace 初见

当项目变大，你可能需要把代码拆成多个包（crate）。cargo 的 workspace 机制允许一组包共享同一个 Cargo.lock 和目标目录，统一构建。你不必现在就掌握它，只要知道长什么样：根 Cargo.toml 里列出 members，每个成员是独立的包，有自己的 Cargo.toml 和 src/。

这种结构的好处是，修改一个公共库后，所有依赖它的成员能一起重新编译、一起测试，版本不会各自漂移。举个例子，一个项目里有「核心逻辑库」「命令行前端」「网页后端」三个成员，它们共享同一份依赖锁定文件；你在核心库里改了一个函数签名，一次 cargo check --workspace 就能把所有受影响的地方找出来，而不是等上线后才发现某个成员还在用旧签名。

什么时候该拆 workspace？经验法则是：当一块代码被两个以上的成员复用，或者不同部分需要独立发布、独立测试时，拆分才划算。过早拆分会带来额外的目录与配置复杂度，反而拖慢开发。本单元只要建立印象即可，等后面讲到模块、可见性和包管理时，我们再回来细看其中的门道。
