5.1 枚举：把状态变成类型

很多语言用一组布尔变量或整数常量表示状态：是不是在加载、加载成功了没有、失败的原因是什么。问题是这些标志可能同时为「真」，也可能全都漏掉，非法状态在类型系统里畅通无阻。Rust 的枚举（enum）把每一种可能的状态变成类型的变体（variant），一个值只能是其中一个变体，非法状态从源头就不存在。

枚举的变体可以带数据，而且形式灵活：可以像 Running(u32) 那样带一个元组，可以像 Done { code: i32 } 那样带命名字段，也可以像 Pending 那样什么都不带。这让枚举同时承担了「状态」和「状态附带信息」两件事，不需要再额外维护几个可能不同步的变量。

大白话先用直觉把它讲通

枚举像一个带标签的抽屉柜。每个抽屉上贴着不同的标签，有的抽屉是空的，有的里面装着东西。你从外面一眼就知道拿的是哪个抽屉，不可能出现「一半是 A 一半是 B」的怪东西。模式匹配就是打开抽屉取东西的动作——标签对上了才能取，取到的东西类型也确定。

从内存角度看，枚举占用空间的大小由「最大的变体」加上一个用于区分变体的标签决定。比如上面的 Status，因为要容纳 u32 和带字段的结构，它的大小至少跟最大的那个变体相当。Rust 会做布局优化，但核心思想不变：用一份空间表达多种可能，且任何时刻只有一种可能成立。

下面的程序定义了一个任务状态枚举，并用 match 给每个变体生成描述。match 的每一条分支叫一个「匹配臂」，用 => 连接模式和结果。这里用 &Status 作为输入，匹配臂里的 p 和 code 会被自动解引用绑定，不需要手动写 *p。

rustRust · 标准库24 行
enum Status {
Pending,
Running(u32),
Done { code: i32 },
}
fn describe(s: &Status) -> String {
match s {
Status::Pending => "等待中".to_string(),
Status::Running(p) => format!("运行中，进度 {p}%"),
Status::Done { code } => format!("完成，退出码 {code}"),
}
}
fn main() {
let items = [
Status::Pending,
Status::Running(42),
Status::Done { code: 0 },
];
for item in &items {
println!("{}", describe(item));
}
}

5.2 Option 与 Result：标准库里的两个明星枚举

Rust 没有 null。表示「可能没有」用标准库的 Option<T>，它只有两个变体：Some(T) 和 None。表示「可能失败」用 Result<T, E>，变体是 Ok(T) 和 Err(E)。它们本质就是普通枚举，编译器对它们一视同仁，没有任何魔法——但整个标准库和社区生态都围绕它们建立了统一的约定，所以你几乎到处都会遇到。

类型 变体 表达的含义 常见操作
Option<T> Some(T) / None 可能有一个值，也可能没有 unwrap_or、map、as_ref
Result<T, E> Ok(T) / Err(E) 可能成功，可能带着错误信息失败 ?、map_err、unwrap_or_else

为什么不用异常？因为异常让控制流变得隐式：一个函数会不会抛异常，光看签名常常看不出来。Result 把「会失败」写进返回类型，调用方必须面对它——要么处理，要么显式地 unwrap（意为「我确信不会失败，崩了算我的」）。这种「错误是值」的设计，让错误处理成为可静态检查的普通代码。

Option 和 Result 还能互相配合。比如在一个返回 Option 的函数里调用返回 Result 的操作，可以用 .ok() 把 Result 转成 Option，失败就变成 None；反过来 Option 也可以用 ok_or 转成 Result，并附带一个自定义错误。这种转换是标准库里大量存在的小工具，用熟了能少写很多 match。

5.3 match：穷尽检查是最大的保护

match 最有价值的地方不是「分支」，而是穷尽检查（exhaustiveness）：编译器会验证你有没有覆盖枚举的所有变体，漏掉一个就拒绝编译。这意味着将来给枚举新增一个变体时，所有 match 它的地方都会立刻报错，逼你逐个确认新情况该怎么处理——而不是等到线上遇上新状态才发现没写对应逻辑。

当然，你也可以写一条 _ => ... 通配符分支来兜底，但那等于主动放弃穷尽检查。它适合「确实有几十种情况、只有少数需要特殊处理」的场合；如果枚举只有三五个变体，老老实实逐个写出来，未来新增变体时编译器才会提醒你。这个提醒的价值，往往超过省下那几行代码。

如果漏写一个分支，报错大致如下（示意输出）：

终端真跑一遍
$ rustc --edition 2021 main.rs -o main
error[E0004]: non-exhaustive patterns: `Status::Running(_)` and
`Status::Done { .. }` not covered
--> main.rs:6:11
|
6 | match s {
| ^ patterns `Status::Running(_)` and `Status::Done { .. }`
| not covered
= note: the matched value is of type `Status`

下面的程序演示了 Result 的典型用法：解析端口字符串。这里用 map_err 把标准库的解析错误转换成自己的描述字符串，再用 ? 提前返回（下一节细讲）。返回类型写成 Result<u16, String>，调用方只要 match 一下就能同时拿到成功值和失败原因。

rustRust · 标准库19 行
fn parse_port(s: &str) -> Result<u16, String> {
let n = s
.parse::<u16>()
.map_err(|e| format!("解析失败: {e}"))?;
if n == 0 {
Err("端口不能为 0".to_string())
} else {
Ok(n)
}
}
fn main() {
match parse_port("8080") {
Ok(p) => println!("端口 {p}"),
Err(e) => println!("错误: {e}"),
}
let opt = Some(7);
println!("缺失时取默认值: {}", opt.unwrap_or(0));
}

5.4 if let 与 let else：只关心一种情况

有时候你只想处理 match 里的某一种分支，其他情况一概忽略。这时 if let 更简洁：if let Some(n) = opt { ... } 读作「如果 opt 恰好是 Some，就把里面的值绑成 n」。它等价于一个只有一条有效分支、其他分支写 _ => () 的 match，但省掉了噪音。

let else 则解决相反的需求：先解开一个模式，解不开就提前返回或跳出。写法是 let Some(n) = opt else { return; };，注意 else 块里的代码必须以发散表达式（如 return、break、panic!）结尾，因为类型系统要求它在模式匹配失败时也能「走下去」——而它选择的是直接不往下走。这个语法从 Rust 1.65 起稳定可用。

rustRust · 标准库24 行
fn first_even(v: &[i32]) -> Option<i32> {
for &x in v {
if x % 2 == 0 {
return Some(x);
}
}
None
}
fn main() {
let nums = [1, 3, 4, 5];
if let Some(n) = first_even(&nums) {
println!("第一个偶数是 {n}");
} else {
println!("没有偶数");
}
let nums2 = [1, 3, 5];
let Some(n) = first_even(&nums2) else {
println!("确实没有偶数");
return;
};
println!("居然有偶数 {n}");
}

选择建议是：需要覆盖所有分支时用 match，只关心一种时用 if let，「拿不到就尽早退出」时用 let else。三者不是替代关系，而是同一套模式匹配能力在不同场景下的表达。

写法 适合场景 能否处理其他分支
match 枚举变体都要分别处理 能，且强制穷尽
if let 只关心某一种情况 可选 else
let else 匹配失败就提前退出 失败时必须发散

一个容易踩的坑是 if let 的「遮蔽」错觉：模式里的变量名只在成功分支里有效，出了大括号就消失了。如果你需要在后面继续用，记得在分支里把它赋给一个更外层的变量，或者干脆改用 match。

5.5 ? 运算符与自定义错误

? 只能用在返回 Option 或 Result 的函数里。它检查当前值：如果是 Ok，就把里面的值取出来继续；如果是 Err，就立刻从当前函数返回那个错误。这样你就不用层层写 match，错误会沿着调用链自动向上冒泡。? 还带有自动类型转换：只要错误类型之间定义了 From 转换，它就能帮你转好。

下面的例子用标准库的 ParseIntError 作为错误类型，演示一次解析两个整数。split(',') 把字符串切开，? 在任一次解析失败时立即返回，调用方用 match 统一处理。

rustRust · 标准库15 行
use std::num::ParseIntError;
fn parse_pair(s: &str) -> Result<(i32, i32), ParseIntError> {
let mut parts = s.split(',');
let a = parts.next().unwrap_or("").trim().parse::<i32>()?;
let b = parts.next().unwrap_or("").trim().parse::<i32>()?;
Ok((a, b))
}
fn main() {
match parse_pair("3, 4") {
Ok((a, b)) => println!("a={a}, b={b}"),
Err(e) => println!("出错: {e}"),
}
}

写错误处理时有个实用原则：在底层保留足够的错误细节，在靠近用户的一层再把它翻译成人话。底层直接 unwrap 会让调用方失去判断的依据，而把所有错误都压成一句「操作失败」又丢掉了排查线索，两头都不是好选择。

实际项目里，你往往需要自己的错误类型，把「文件读不到」「配置格式错」「网络超时」这些不同原因归到一个枚举里。手写时要为它实现 Display 和 std::error::Error，还要为底层错误实现 From，样板代码不少。社区里的 thiserror 思路正是为此而生：用派生宏自动帮你生成这些实现，你只要写出错误枚举和每个变体上的提示文本即可。这里只讲思路，不引入任何外部 crate——你完全可以先手写一个简化版体会其中的结构，等项目真的复杂起来再考虑用宏省事。

最后提醒一个度的问题：unwrap() 和 expect() 在示例和测试里很方便，但在可能失败的生产路径上滥用，等于把错误又变回了「运行时崩溃」。能用 ? 传上去就传上去，让错误在最有上下文的那一层被解释和处理。
