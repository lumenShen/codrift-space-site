34.1 为什么需要随机化与对拍工程

前 33 个单元里，每个算法都配了"随机数据 + 朴素裁判"对拍。本单元把这套做法本身当作主题讲透。原因很简单：手写测试用例只能覆盖你想到的情况，而 bug 往往藏在你没想到的地方；随机数据能以极低成本探索输入空间，性质测试则把"正确答案是什么"这个难题换成"答案应满足哪些不变量"这个容易回答的问题。再加上一个可复现的随机源与失败用例缩小器，你就拥有一条完整的自动化流水线：生成 → 检验 → 缩小 → 复现。

这套流水线与工程编第 11 单元的测试分层是互补关系。单元测试适合验证"已知输入的精确输出"，集成测试验证模块间协作，而性质测试与对拍擅长发现"没想到的输入"。三者不能互相替代：性质测试发现 bug 后，仍要把它固定成一个单元测试防止回归；单元测试覆盖不到的组合爆炸，才交给随机探索。本单元聚焦第三层，因为算法代码的核心风险正是输入组合而非模块接口。标准库之外虽有 proptest、criterion 等成熟工具，但理解其背后的生成—缩小—计时机制，才能正确使用它们，也才能在无依赖场景里自己搭一套。

问题定义如下。随机源：给定非零 64 位种子，产生确定性但看起来随机的 u64 序列，同种子必须逐字复现。随机化算法：在算法关键决策处（如快排主元）引入随机性，使坏输入不再固定地触发最坏情况。性质测试：对函数 f 与输入 x，检验谓词 P(x, f(x)) 是否对所有随机 x 成立，无需知道 f(x) 的精确值。缩小器：给定失败输入 x，找尽可能小的 x' 仍使 P 失败。计时：在受控条件下测量 f 的墙钟时间，避免被编译器优化掉。

大白话先用直觉把它讲通

对拍就是请一个"笨但绝对可靠"的裁判，让它和你的聪明实现同时答题，答案不一致就是你有错。随机源决定题目从哪来，性质测试决定裁判怎么判，缩小器负责把一道长题目砍成最短的仍会做错的那道，计时负责告诉你谁跑得快。四件事凑齐，调试就从"盯着屏幕猜"变成"机器替你找反例"。

34.2 可复现随机源：xorshift64 与种子纪律

xorshift64 的状态只有一个 u64，推进只需三步移位异或：x ^= x << 13; x ^= x >> 7; x ^= x << 17。种子为 0 时状态永远为 0，所以代码里用黄金比例常数 0x9E3779B97F4A_7C15 替换。它的周期是 2^64-1，对算法测试足够；不是密码学安全随机源，不能用来生成密钥。

可复现性是对拍的生命线。程序用种子 42 生成前五个数，两个独立实例给出完全相同的序列；换成种子 43，第一个数立刻不同。这意味着任何一次失败都可以通过"种子 + 用例编号"精确重放，而不需要保存整份输入。相比之下，用系统时间做种子虽然每次跑不同数据，看似覆盖更广，但一旦失败就无法复现，只能靠打印大量日志碰运气。正确的做法是：常规回归用固定种子，额外探索用一组预设种子批量跑，两者结合。

均匀性也要粗查。程序把 10000 次 below(10) 的结果分进 10 个桶，理想每桶 1000，实测最大偏差 26。这个偏差在随机波动的合理范围内，说明低位取模没有明显偏斜。若你的算法对分布敏感（例如随机化快排的主元），应优先用高位或乘缩放（next() >> 32）来降低低位相关性；本单元数据规模小，直接取模不影响结论。

与另一种常见选择线性同余生成器（LCG）相比，xorshift 的优势是只需要移位与异或，没有乘法，因而在 32 位平台也快；LCG 的低位有明显周期性，s % 2 常呈 0、1 交替，用它取模小范围会得到严重偏斜的分布。xorshift64 的低位虽然不是密码学级别，但对算法测试已经够用。若需要更强的统计质量，可以换成 SplitMix64（一次乘法加三次移位异或），它常被用作标准库随机源的种子扩展器。选随机源的判据不是"越高级越好"，而是"是否满足当前测试的统计需求且可复现"。另外，below(n) 用取模实现会带来轻微的模偏差：当 2^64 不能被 n 整除时，余数较小的桶略多。对 n≤200 的测试规模，偏差不足 2^-54，可以忽略；若做严谨的蒙特卡洛统计，应使用拒绝采样消除偏差。

/// xorshift64：一个 u64 状态，周期 2^64-1（种子非 0）。
struct Rng { s: u64 }
impl Rng {
fn new(seed: u64) -> Self {
Self { s: if seed == 0 { 0x9E37_79B9_7F4A_7C15 } else { seed } }
}
fn next(&mut self) -> u64 {
let mut x = self.s;
x ^= x << 13;
x ^= x >> 7;
x ^= x << 17;
self.s = x;
x
}
fn below(&mut self, n: u64) -> u64 { self.next() % n }
}
fn main() {
// 可复现性：同种子产生完全相同的序列。
let mut a = Rng::new(42);
let mut b = Rng::new(42);
let sa: Vec<u64> = (0..5).map(|_| a.next()).collect();
let sb: Vec<u64> = (0..5).map(|_| b.next()).collect();
println!("seed=42 seq[0..5] = {:?}", sa);
println!("reproducible = {}", sa == sb);
// 粗略均匀性：10000 次取模落入 10 个桶，理想每桶 1000。
let mut rng = Rng::new(20261123);
let mut buckets = vec![0u32; 10];
for _ in 0..10000 { buckets[rng.below(10) as usize] += 1; }
println!("buckets(10000 draws, expect 1000 each) = {:?}", buckets);
let mut max_dev = 0i64;
for &c in &buckets { max_dev = max_dev.max((c as i64 - 1000).abs()); }
println!("max deviation = {}", max_dev);
// 不同种子给出不同序列。
let mut c = Rng::new(43);
println!("seed=43 first = {}, seed=42 first = {}", c.next(), sa[0]);
}

34.3 随机化算法：随机主元快排的期望复杂度

确定性快排若总取最后一个元素作主元，遇到已排序输入时每次划分只缩小 1，递归深度 n，总时间 O(n²)。随机化把主元下标改成 rng.below(len)，任何固定输入都不再能预先命中最坏划分；期望比较次数是 2n·ln n 左右，期望递归深度 O(log n)。注意随机化不改变最坏情况（仍可能是 O(n²)，只是概率极低），它改变的是坏输入的分布：对手无法构造一个固定序列让你每次都退化。

划分不变量是：Lomuto 扫描结束后，a[..i] 全部 < pivot，a[i+1..] 全部 >= pivot，a[i] 是主元最终位置。循环里 i 指向"下一个小于主元的元素该放的位置"，j 扫描整个区间；遇到 a[j] < pivot 就交换 a[i] 与 a[j] 并递增 i。重复元素全部落入右半，所以全等数组会退化为深度 n——这是随机化也救不了的场景，因为主元无论选哪个都相同；工程上应改用三路划分（< / == / >）。演示里全等数组仍返回 true，只是性能不佳，正确性没问题。

期望复杂度的直觉可以写成递推：设 T(n) 是随机主元快排的期望时间，主元落在第 k 个位置的概率均为 1/n，于是 T(n) = (n-1) + (1/n)·Σ(T(k)+T(n-1-k))。用归纳法可解出 T(n) ≤ 2n·ln n，即 O(n log n)。这个推导同时说明递归深度的期望也是 O(log n)：随机主元把数组大致对半分，层数约为 log₂n。深度不只是性能指标——每层递归消耗栈帧，n=2000 的固定主元版本深度 1999，接近栈上限；若 n 再大一个数量级就会栈溢出，这是随机化在工程上的额外收益。生产环境的 sort_unstable 还会在递归深度超限时切换到堆排序（introsort），彻底消除栈溢出风险。

struct Rng { s: u64 }
impl Rng {
fn new(seed: u64) -> Self { Self { s: if seed == 0 { 1 } else { seed } } }
fn next(&mut self) -> u64 {
let mut x = self.s;
x ^= x << 13; x ^= x >> 7; x ^= x << 17;
self.s = x; x
}
fn below(&mut self, n: u64) -> u64 { self.next() % n }
}
/// 随机化快排：随机选主元，Lomuto 划分。
/// 不变量：划分后 a[..i] 的元素都 < pivot，a[i+1..] 的元素都 >= pivot。
fn quicksort(a: &mut [i64], rng: &mut Rng) {
if a.len() < 2 { return; }
let p = rng.below(a.len() as u64) as usize;
a.swap(p, a.len() - 1);
let pivot = a[a.len() - 1];
let mut i = 0;
for j in 0..a.len() - 1 {
if a[j] < pivot { a.swap(i, j); i += 1; }
}
a.swap(i, a.len() - 1);
quicksort(&mut a[..i], rng);
quicksort(&mut a[i + 1..], rng);
}
fn main() {
let mut rng = Rng::new(7);
let v: Vec<i64> = (0..20).map(|_| rng.below(50) as i64).collect();
let mut a = v.clone();
quicksort(&mut a, &mut rng);
let mut b = v.clone();
b.sort_unstable();
println!("input = {:?}", v);
println!("sorted = {:?}", a);
println!("matches std::sort_unstable = {}", a == b);
let mut c = vec![5i64; 20];
quicksort(&mut c, &mut rng);
println!("all-equal case ok = {}", c == vec![5i64; 20]);
let mut e: Vec<i64> = Vec::new();
quicksort(&mut e, &mut rng);
println!("empty case ok = {}", e.is_empty());
}

34.4 性质测试：用不变量代替正确答案

性质测试的关键转变是：不再问"排序结果是否等于某个预先算好的数组"，而是问"结果是否满足排序应有的性质"。本单元为排序定义三个性质：有序性（相邻元素非降）、保多重集（输入输出排序后逐项相等）、幂等性（对输出再排一次不变）。三者合起来足以排除绝大多数排序 bug，而且不需要手写任何预期输出。

这三条性质各自堵住一类错误：只检查有序性，一个"把所有元素改成 0"的函数会蒙混过关；加上保多重集，就能抓住丢元素或凭空造元素的 bug；加上幂等性，能抓住"输出局部有序但再排一次又变"的不稳定实现。保多重集的判定方式是把输入输出各自 sort_unstable 再比较——这里用标准库排序作为裁判，是刻意选择的独立实现：若被测函数就是标准库排序，则应换用哈希表计数，避免裁判与被测同源。性质的选择没有万能公式，原则是"每条性质独立排除一类错误，且实现比被测函数更简单"。写性质时还要防止性质本身过弱：例如只检查首尾有序就无法发现中间乱序，windows(2) 全对检查才是正确写法。

程序用种子 20261125 跑 1000 组随机数组（长度 0..59，元素 0..29，大量重复），正确实现失败 0 次；故意植入的 bug 版（只排序前半段）失败 955 次。注意不是 1000 次：当数组本来就有序，或后半段恰好不需要调整时，bug 版也能蒙混过关——这正是随机测试的现实：它给出的是高概率发现bug，不是形式化证明。报告里要如实写出 955 而非 1000，否则就是在伪造覆盖率。

/// 故意有 bug 的排序：只排序前半段。用来展示性质测试如何抓 bug。
fn buggy_sort(a: &mut [i64]) {
let h = a.len() / 2;
a[..h].sort_unstable();
}
fn properties_ok(input: &[i64], output: &[i64]) -> bool {
if input.len() != output.len() { return false; }
let sorted = output.windows(2).all(|w| w[0] <= w[1]);
let mut a = input.to_vec(); a.sort_unstable();
let mut b = output.to_vec(); b.sort_unstable();
let same_multiset = a == b;
let mut once_more = output.to_vec();
once_more.sort_unstable();
let idempotent = once_more == output;
sorted && same_multiset && idempotent
}
fn main() {
let seed = 20261125u64;

for _ in 0..1000 {
let n = rng.below(60) as usize;
let data: Vec<i64> = (0..n).map(|_| rng.below(30) as i64).collect();

if !properties_ok(&data, &g) { good_fail += 1; }
let mut b = data.clone();
buggy_sort(&mut b);
if !properties_ok(&data, &b) {
bad_fail += 1;
if first_bad.is_none() { first_bad = Some(data.clone()); }
}
}
println!("[property] seed={} cases=1000 correct_impl_failures={}", seed, good_fail);
println!("[property] buggy_impl_failures={}", bad_fail);

}
}

34.5 缩小失败用例：delta debugging 实战

第一个失败用例往往很长，直接打印出来难以分析。缩小器的目标是删掉尽可能多的元素，同时保持失败。本程序实现的是简化版 delta debugging：按 8、4、2、1 的块大小从数组中删除连续片段，只要删除后 fails 仍为真就接受，任何删除都失败时停止。判据 fails(v) 定义为"buggy_sort 后数组不非降"。

块大小从大到小是有讲究的：先用大块快速砍掉无关部分，再用小块精细修剪；若一上来就逐个删除，遇到"必须同时删掉相隔较远的两个元素才仍失败"的情况就会卡在局部最小。完整的 ddmin 算法会在无法删除时把块进一步二分，本程序的 8→4→2→1 序列近似了这一过程，对排序这类失败判据单调的问题足够。所谓单调，是指"失败用例的任意超集也失败"——对 buggy_sort 而言，往一个降序对里加元素不会让它突然变有序，所以单调性成立，缩小才有意义。若失败判据不单调（例如"数组长度恰好为 7 时才失败"），缩小器会把你引向完全无关的用例，此时应先改造判据而不是迷信工具。

程序实测从 12 项缩到 2 项 [22,18]，并且验证极小性：对这个 2 项数组分别删除任一元素后，fails 都不再成立，removals_that_still_fail = 0。这个验证步骤不能省——很多"缩小器"只做到局部最小就停手，却误称"最小反例"。有了最小反例，bug 原因一目了然：buggy_sort 取 h = len/2 = 1，只排序第一个元素，于是降序对永远无法被纠正。

impl Rng {
fn new(seed: u64) -> Self { Self { s: if seed == 0 { 1 } else { seed } } }
fn next(&mut self) -> u64 {
let mut x = self.s;
x ^= x << 13; x ^= x >> 7; x ^= x << 17;
self.s = x; x
}
fn below(&mut self, n: u64) -> u64 { self.next() % n }
}
fn buggy_sort(a: &mut [i64]) {
let h = a.len() / 2;
a[..h].sort_unstable();
}
/// 失败判据：有 bug 的排序不能把数组排好序。
fn fails(v: &[i64]) -> bool {
let mut out = v.to_vec();
buggy_sort(&mut out);
!out.windows(2).all(|w| w[0] <= w[1])
}
/// delta debugging：按从大到小的块尝试删除，只要删除后仍失败就接受。
fn shrink(mut v: Vec<i64>) -> Vec<i64> {
loop {
let mut changed = false;
for chunk in [8usize, 4, 2, 1] {
let mut i = 0;
while i < v.len() {
let end = (i + chunk).min(v.len());
let mut cand = v.clone();
cand.drain(i..end);
if fails(&cand) {
v = cand;
changed = true;
} else {
i += 1;
}
}
}
if !changed { break; }
}
v
}
fn main() {
let mut rng = Rng::new(20261125);
let mut found: Option<Vec<i64>> = None;
for _ in 0..1000 {
let n = 5 + rng.below(20) as usize;
let data: Vec<i64> = (0..n).map(|_| rng.below(30) as i64).collect();
if fails(&data) { found = Some(data); break; }
}
let original = found.expect("未找到失败用例");
println!("[shrink] original len={} case={:?}", original.len(), original);
let minimal = shrink(original.clone());
println!("[shrink] minimal len={} case={:?}", minimal.len(), minimal);
// 验证极小性：再删任意一个元素都不再失败。
let mut still_fails_on_removal = 0usize;
for i in 0..minimal.len() {
let mut cand = minimal.clone();
cand.remove(i);
if fails(&cand) { still_fails_on_removal += 1; }
}
println!("[shrink] removals_that_still_fail = {}", still_fails_on_removal);
let mut out = minimal.clone();
buggy_sort(&mut out);
println!("[shrink] buggy output of minimal case = {:?}", out);
}

坑这里最容易踩

这里是坑：缩小器必须把"失败判据"与"被测函数"严格分开。若 fails 里复用了被测代码的内部逻辑（比如直接调用同一个划分函数），一个 bug 会让两边同时失效，缩小过程可能永远停在原地或缩出一个与 bug 无关的反例。本单元的 fails 只用"输出是否非降"这个外部可观察性质，与 buggy_sort 的实现细节无关，所以结果可信。另一个坑是用 Option<Vec<i64>> 而不是 unwrap() 直接取第一个失败用例：若随机数据恰好没触发 bug，程序会 panic 而不是给出"未发现失败"的明确结论；显式处理让自动化流水线能区分"通过"与"没跑到"。

34.6 计时与剖析：Instant、black_box 与 -O

正确性过关后，性能数字必须真测。std::time::Instant 提供单调时钟，elapsed() 返回 Duration，打印时保留实际精度，不要自己四舍五入成"大约 50 毫秒"。std::hint::black_box(&a) 告诉编译器"这个值真的被使用了"，防止它把整段计算当成无用代码优化掉。编译必须加 -O（等价于 release 优化级别），否则测到的是未优化代码，数字没有参考价值。

程序对 n=1000000 的随机数组分别跑随机快排与 sort_unstable，并把 results identical 打印出来——性能比较必须建立在结果一致的前提上，否则"快 10 倍"可能只是"算错了所以快"。实测随机快排 54.7907ms、标准库 12.526ms、比值 4.37。这个比值只在本机本次运行有效，换个 CPU 或换批数据会变；把它写进笔记时要注明"实测于本机、-O 编译、n=1000000、种子 99"，不能当成普适真理。

大白话先用直觉把它讲通

计时最容易骗自己的地方有两个——调试编译下慢得离谱，以及编译器发现"结果没用到"干脆把计算删了。-O 与 black_box 就是专门治这两样的。打印时把真实耗时原样贴出来，别写"大约"，因为数字一旦被四舍五入，读者就无法判断它是否来自真跑。

标准差库快排经过多年优化（introsort、插入排序小数组特化、模式防御），手写的教学版慢 4.37 倍完全正常。这里的意义不是"比标准库快"，而是建立一个可重复的测量方法：固定输入、固定种子、预热、black_box、真实输出。

测量方法本身也要写进笔记：本次编译命令是 rustc --edition 2021 -O，输入是种子 99 生成的 100 万个 0..999999 的整数，先对前 1000 个元素预热再开始计时，两次测量各自 clone 一份相同输入，最后校验结果一致。缺了其中任何一项，数字都可能失真——不预热会把首次页缺失算进去，不 clone 会测到已排序数组，不校验一致性则可能把错误结果当成快速结果。若要把这组数字用于正式对比，还应重复多次取中位数；本单元为保持终端记录简洁只跑一次，读者须清楚它的统计意义有限。

34.7 综合对拍：把随机化收益量化

前面的性质测试验证了"对不对"，还需要一个实验回答"随机化到底防住了什么"。程序做两件事：第一，1000 组随机数组（含大量重复）加 4 组对抗输入（升序、降序、全等、锯齿），把随机主元快排与 sort_unstable 逐项比较，结果 1004 组、0 处不一致；第二，对 n=2000 的升序输入，分别记录随机主元版与固定主元版的最大递归深度。

四组对抗输入各有针对性：升序触发固定主元的最坏划分，降序触发另一种单调退化，全等检验 Lomuto 对重复值的处理，锯齿（0/1 交替）检验大量重复下的划分平衡性。它们都是几行代码就能构造的确定性用例，却比随机数据更容易击中特定分支——这也是"随机测试之外必须保留手写对抗样例"的理由。程序最后打印 both sorted = true / true，强调深度差异不是以正确性为代价换来的：两个版本都排好了，只是路径长短不同。若只比较深度而不校验结果，一个"直接返回空数组"的函数也能得到深度 0 的漂亮数字。

实测随机主元最大深度 21，固定主元 1999。两者都把数组排好了，但固定主元版本几乎退化成一条链：每层只排掉一个元素，递归深度与 n 同阶，既慢又有栈溢出风险。随机主元的深度约为 2·log₂2000≈22，与 21 吻合。这个数字把"期望 O(n log n)"从公式变成可观察的事实，也说明随机化不是玄学——它把对手构造最坏输入的难度从"给个有序数组"提升到"猜中每一步的随机下标"。若把 n 加大到 20000，固定主元版很可能耗尽栈空间，而随机版深度只增长到约 29；这种"同样正确但资源曲线完全不同"的差异，正是算法分析要量化的东西。

/// 随机主元快排，同时记录最大递归深度。
fn quicksort(a: &mut [i64], rng: &mut Rng, depth: usize, max_depth: &mut usize) {
*max_depth = (*max_depth).max(depth);
if a.len() < 2 { return; }
let p = rng.below(a.len() as u64) as usize;
a.swap(p, a.len() - 1);
let pivot = a[a.len() - 1];
let mut i = 0;
for j in 0..a.len() - 1 { if a[j] < pivot { a.swap(i, j); i += 1; } }
a.swap(i, a.len() - 1);
quicksort(&mut a[..i], rng, depth + 1, max_depth);
quicksort(&mut a[i + 1..], rng, depth + 1, max_depth);
}
/// 固定主元（总取最后一个）快排：有序输入会退化成 O(n^2)。
fn fixed_quicksort(a: &mut [i64], depth: usize, max_depth: &mut usize) {
*max_depth = (*max_depth).max(depth);
if a.len() < 2 { return; }
let pivot = a[a.len() - 1];
let mut i = 0;
for j in 0..a.len() - 1 { if a[j] < pivot { a.swap(i, j); i += 1; } }
a.swap(i, a.len() - 1);
fixed_quicksort(&mut a[..i], depth + 1, max_depth);
fixed_quicksort(&mut a[i + 1..], depth + 1, max_depth);
}

34.8 工程约定与取舍

把五段程序放在一起看，能提炼出一套可复用的测试工程约定：种子写在常量里、每组用例打印实际计数、裁判与被测代码不共享内部逻辑、失败样本要能缩小到最小、性能数字要注明编译选项与输入规模。这些约定不依赖任何外部 crate，std-only 就能落地。

环节 做法 为什么
随机源 固定种子 xorshift64 失败可复现，无外部依赖
性质测试 有序/保多重集/幂等 无需预先知道正确答案
缩小 按 8/4/2/1 块删除 + 极小性验证 把长反例砍成可一眼看懂的短反例
计时 -O + black_box + Instant 避免未优化与死代码消除
对照 独立朴素实现 + 对抗用例 防止两边共享同一个 bug

这张表里的每一行都对应本单元一个可运行的程序，而不是抽象建议。例如"种子写在常量里"在五段程序里分别体现为 42、20261123、7、20261125、99 与 20261126；它们不是随意选的幸运数字，而是固定下来便于读者逐字复现输出。若把种子改成环境变量或命令行参数，记得同时把实际使用的值打印进日志，否则终端记录将失去可核对性。同理，对抗用例（升序、降序、全等、锯齿）应作为常量表长期保留，而不是每次临时手写——它们是一次性成本、长期收益的回归资产。

坑这里最容易踩

这里是坑：不要把"跑了多少次"当成"覆盖了多少情况"。本单元属性测试跑 1000 次、buggy 版失败 955 次，说明仍有 45 次漏网；综合对拍的 1004 组里也包含大量相似的随机数组。真正提高覆盖的是输入模式的多样性：随机数组之外要显式加入升序、降序、全等、空、单元素、锯齿等对抗模式，34.7 的四组对抗输入就是为此。另一个坑是计时只跑一次：机器负载、缓存状态都会带来波动，正式基准应重复多次取中位数，本单元为保持输出简洁只跑一次，读者在真实项目里应改用 criterion 等工具（见工程编第 11、16 单元）。

34.9 自检与练习

把五段程序串起来看，随机化与对拍工程的本质是把"我希望它是对的"变成"机器反复检验后仍找不到反例"。随机源提供可复现的输入，性质断言提供不依赖标准答案的裁判，缩小器把反例压缩到人类可理解的规模，计时器把性能主张变成可核查的数字。这四者都不需要额外依赖，std-only 就能完整实现；理解其机制后，再引入 proptest、criterion 只是工程便利，而非能力上的跃迁。本单元也是整套算法编的收尾：前 33 个单元里每一篇的对拍，用的都是这里系统化的方法。
