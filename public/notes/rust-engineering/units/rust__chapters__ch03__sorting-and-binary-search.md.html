20.1 排序 API 的选择：稳定性、空间与比较器

Vec 和切片都提供了三个常用排序方法。sort 是稳定排序：相等元素保持原有相对顺序，代价是额外的 O(n) 临时内存，最坏 O(n log n) 次比较；sort_unstable 不保证稳定性，通常更快，只占用 O(log n) 额外空间；sort_by_key 按提取出的关键字排序，也是稳定的。判断标准很简单：相等元素是否需要保留输入顺序。按分数排序后还要按名字排第二关键字时，用稳定排序可以做两次（先按名字、再按分数）；或者干脆把两个关键字写进一个比较器，一次排完。

降序不是把比较结果取负——Rust 的 Ordering 没有取负运算——而是把参数顺序反过来写：b.cmp(a)。多关键字用 then_with 串联：q.1.cmp(&p.1).then_with(|| p.0.cmp(q.0)) 表示分数降序、同分时名字升序。注意闭包参数名字 p 和 q 的顺序，写反了会得到完全相反的结果，这是排序题最常见的低级错误。更稳妥的写法是先给比较器写一行注释说明"谁该排前面"，再写代码。

方法 稳定性 额外空间 适用场景
sort() 稳定 O(n) 相等元素需保留原序
sort_unstable() 不稳定 O(log n) 默认首选，更快
sort_by(cmp) 由底层决定 同上 自定义规则、降序
sort_by_key(f) 稳定 O(n) 单一关键字
rustRust · 标准库17 行
fn main() {
let mut a = vec![5, 2, 9, 1, 5, 6];
let mut stable = a.clone();
stable.sort();
println!("ascending: {:?}", stable);
a.sort_unstable();
println!("unstable asc: {:?}", a);
let mut desc = vec![3, 1, 4, 1, 5];
desc.sort_unstable_by(|x, y| y.cmp(x));
println!("descending: {:?}", desc);
let mut v = vec![("tom", 80), ("ana", 95), ("bob", 80)];
v.sort_unstable_by(|p, q| q.1.cmp(&p.1).then_with(|| p.0.cmp(q.0)));
println!("by score: {:?}", v);
}

输出里 by score 把 95 分的 ana 排在最前，两个 80 分的 tom 和 bob 按名字升序排列，正是比较器想要的效果。sort_unstable 的内部是模式消除快速排序与堆排序的混合：正常情况下接近 O(n log n) 且常数很小，一旦递归深度过大就切换到堆排序以保证最坏 O(n log n) 上界，因此不必担心有序输入导致退化。这正是标准库"默认就用它"的底气——除非你真的需要稳定性，否则没有理由为此多付 O(n) 内存。切片本身还带一个 binary_search 方法，返回 Result<usize, usize>：找到时是 Ok(下标)，没找到时是 Err(应插入位置)，这个"应插入位置"正好等于 lower_bound。若数组里存在重复元素，binary_search 返回的是其中某一个，不保证是第一个或最后一个，所以题目要找边界时还是自己写二分更可靠。

大白话先用直觉把它讲通

排序就是把一堆东西按规则排队。sort 是"讲礼貌的排队"，分数相同的人保持原来的先后；sort_unstable 是"只关心分数"的排队，同分谁在前都行，所以更快。比较器就是告诉程序"谁该站前面"的那句话，降序只要把两个参数换个位置说一遍。

20.2 归并排序与逆序对：借用如何被精确控制

问题定义：逆序对是下标 i < j 但 a[i] > a[j] 的二元组个数，衡量数组的"无序程度"。归并排序在合并两个已经有序的半区时，如果右半区的 rbuf[j] 小于左半区的 lbuf[i]，那么它不仅小于 lbuf[i]，还小于左半区中从 i 到末尾的所有元素（因为左半区递增），于是逆序对数一次性增加 left_len - i。这样统计不需要额外的嵌套循环，归并排序的 O(n log n) 复杂度原封不动地继承下来。

Rust 写归并排序的难点不在算法而在借用。递归调用 &mut a[..mid] 和 &mut a[mid..] 是两段互不重叠的可变切片，完全合法；合并前要先把两半拷进临时数组，用 a.split_at(mid) 拿不可变切片、tmp.split_at_mut(mid) 拿可变切片，拷贝完成后用一个花括号块主动结束这些借用，之后才能写回 a[k]。如果借用没结束就写 a[k] = ...，编译器会报 "cannot borrow a as mutable"。把 left.len() 事先存成 left_len 这样的标量，也能减少对借用的依赖。

坑这里最容易踩

一个常见错误是把临时数组 tmp 也按层递归地重新分配：let mut tmp = vec![0; mid]; 写在递归函数内部，每层都新建。这样总分配量是 O(n log n)，性能明显变差，而且大量小分配会拖慢速度。正确做法是在 main 里分配一次长度等于原数组的 tmp，所有递归层共享它的不同切片——代码里 &mut tmp[..mid] 和 &mut tmp[mid..] 正是这个意思。另一个坑是合并条件写成 < 而不是 <=：相等元素先取右半，虽然结果仍然有序，但会把相等元素误计为逆序对（因为 lbuf[i] > rbuf[j] 不成立时反而进入了统计分支），同时破坏稳定性。

rustRust · 标准库49 行
fn merge_sort_count(a: &mut [i64], tmp: &mut [i64]) -> i64 {
let n = a.len();
if n <= 1 {
return 0;
}
let mid = n / 2;
let mut inv = merge_sort_count(&mut a[..mid], &mut tmp[..mid]);
inv += merge_sort_count(&mut a[mid..], &mut tmp[mid..]);
let left_len = mid;
let right_len = n - mid;
{
let (left, right) = a.split_at(mid);
let (lbuf, rbuf) = tmp.split_at_mut(mid);
lbuf[..left_len].copy_from_slice(left);
rbuf[..right_len].copy_from_slice(right);
}
let (mut i, mut j, mut k) = (0usize, 0usize, 0usize);
while i < left_len && j < right_len {
if tmp[i] <= tmp[mid + j] {
a[k] = tmp[i];
i += 1;
} else {
inv += (left_len - i) as i64;
a[k] = tmp[mid + j];
j += 1;
}
k += 1;
}
while i < left_len {
a[k] = tmp[i];
i += 1;
k += 1;
}
while j < right_len {
a[k] = tmp[mid + j];
j += 1;
k += 1;
}
inv
}
fn main() {
let mut a = vec![2i64, 4, 1, 3, 5];
let mut tmp = vec![0i64; a.len()];
let inv = merge_sort_count(&mut a, &mut tmp);
println!("sorted = {:?}, inversions = {}", a, inv);
}

归并排序递归深度是 log₂n，远小于递归爆栈的阈值，所以这里用递归是安全的——这与深链 DFS 不同。copy_from_slice 在这里也很关键：它把一段连续内存整体复制，编译器会生成高效的批量拷贝指令，比逐元素循环快得多；而且它要求两边长度相等，lbuf[..left_len] 这个切片表达式把长度约束写在了类型里，写错长度会直接 panic 而不是悄悄漏拷。

若数据的值域不大（例如都在 10⁶ 以内），统计逆序对还有另一种做法：从右往左扫描，用树状数组统计已出现过且小于当前值的元素个数，复杂度同样是 O(n log n)，内存只需一个计数数组。两种方法的结果应当一致，互为对拍的参照非常合适。归并排序的额外好处是天然稳定，如果题目同时要求"按值排序且同值保持原序"，它就是首选；树状数组版本虽然在值域小时常数更小，但只能给出逆序对数量，不能顺带产出有序数组。按需求选择，不要只盯着复杂度数字。

20.3 二分的四种边界：左闭右开统一天下

二分查找的 bug 几乎都出在区间约定上。推荐全程使用左闭右开 [l, r)：初始 l = 0, r = len，循环条件是 while l < r，中点 m = l + (r - l) / 2。这写法的好处是循环结束时 l == r，答案就是 l，不需要讨论"最后 l 和 r 谁大"。中点用 l + (r - l) / 2 而不是 (l + r) / 2，可以避免两个大下标相加溢出——第 17 单元已经详细解释过这一点。

四种常见需求只差一个判定条件。下表把它们归纳在一起，记忆时只要抓住"何时右移 l"这一条即可。

需求 右移条件（l = m + 1） 不右移时 找不到时
lower_bound（第一个 >= target） a[m] < target r = m 返回 len
upper_bound（第一个 > target） a[m] <= target r = m 返回 len
first_equal 先 lower_bound 校验 a[i] == target 返回 None
last_equal 先 upper_bound 校验 a[i-1] == target 返回 None
rustRust · 标准库51 行
fn lower_bound(a: &[i32], target: i32) -> usize {
let (mut l, mut r) = (0usize, a.len());
while l < r {
let m = l + (r - l) / 2;
if a[m] < target {
l = m + 1;
} else {
r = m;
}
}
l
}
fn upper_bound(a: &[i32], target: i32) -> usize {
let (mut l, mut r) = (0usize, a.len());
while l < r {
let m = l + (r - l) / 2;
if a[m] <= target {
l = m + 1;
} else {
r = m;
}
}
l
}
fn first_equal(a: &[i32], target: i32) -> Option<usize> {
let i = lower_bound(a, target);
if i < a.len() && a[i] == target {
Some(i)
} else {
None
}
}
fn last_equal(a: &[i32], target: i32) -> Option<usize> {
let i = upper_bound(a, target);
if i > 0 && a[i - 1] == target {
Some(i - 1)
} else {
None
}
}
fn main() {
let a = [1, 2, 2, 2, 3, 4];
println!("lower=({}, {})", lower_bound(&a, 2), lower_bound(&a, 5));
println!("upper=({}, {})", upper_bound(&a, 2), upper_bound(&a, 5));
println!("first={:?} last={:?}", first_equal(&a, 2), last_equal(&a, 2));
println!("count={}", upper_bound(&a, 2) - lower_bound(&a, 2));
}

上界减下界就是某个值出现的次数，这是 lower_bound / upper_bound 最实用的组合。last_equal 里先判断 i > 0 是必须的：若 i = 0，i - 1 会在 debug 构建下直接 panic。所有返回类型都是 usize，"找不到"用 a.len() 表示；想表达"不存在"的语义就用 Option<usize>，让类型系统替你记账。二分的前提严格来说是判定谓词单调，数组有序只是最常见的表现形态：对于形如"前半段满足条件、后半段不满足"的任何序列，同一套框架都能找分界点，而不要求元素本身递增。把二分理解为"在一个单调布尔序列里找 true/false 的交界"，比死记四种模板更通用，也更容易迁移到第 20.4 节的二分答案。

若给的是无序数据，别忘了先排序，并记得排序会打乱原始下标——若答案需要输出原位置，就要先和值一起打包成结构体或二元组再排。还有一种常见做法是排序时保留原下标作为第二关键字：把 (值, 原下标) 一起排序，二分命中后直接读出原下标。这样既利用了有序性，又不丢失位置信息，是"排序 + 二分"类题目的标准套路。

20.4 二分答案：从判定到最优

当题目要求"最大化最小值"或"最小化最大值"时，答案往往具有单调性：如果某个上限 limit 可行，那么比它更大的上限一定也可行；如果不可行，更小的也不可行。有了单调性，就能对答案本身二分，把在巨大值域上的搜索压缩到 O(log V) 次判定。"把数组切成 m 段、最小化最大段和"是标准范例。

判定函数 feasible(limit) 贪心地从左往右累加，一旦加上当前元素超过 limit 就另起一段；若段数超过 m 则不可行。这里有个隐蔽的正确性要点：这个贪心用的是"尽可能塞满当前段"，它使段数最少——若连最省段的切法都超过 m 段，任何别的切法只会用更多段，所以判定正确。二分边界 lo 取数组最大值（任何一段至少装得下最大的单个元素），hi 取全数组之和（一段装下全部），循环写法同样是 lo + (hi - lo) / 2，可行就把 hi 压到 mid，否则把 lo 抬到 mid + 1。

rustRust · 标准库38 行
fn feasible(a: &[i64], pieces: usize, limit: i64) -> bool {
let mut used = 1usize;
let mut sum = 0i64;
for &x in a {
if x > limit {
return false;
}
if sum + x > limit {
used += 1;
sum = x;
if used > pieces {
return false;
}
} else {
sum += x;
}
}
true
}
fn minimize_largest_sum(a: &[i64], pieces: usize) -> i64 {
let mut lo = *a.iter().max().unwrap();
let mut hi: i64 = a.iter().sum();
while lo < hi {
let mid = lo + (hi - lo) / 2;
if feasible(a, pieces, mid) {
hi = mid;
} else {
lo = mid + 1;
}
}
lo
}
fn main() {
let a = [7i64, 2, 5, 10, 8];
println!("answer = {}", minimize_largest_sum(&a, 2));
}

写二分答案前必须先证明单调性，否则二分会悄悄给出错误答案。快速验证办法是拿几组小数据穷举所有切分，再把结果与判定函数对照；建立直觉后再推广到大数据。还要检查 lo 和 hi 的初值：若 lo 设得太大，真正的答案会被排除在外；若 hi 设得太小，二分永远收敛不到可行解。极端数据自检也很有效——limit 取最大值时应恰好可行，limit 取最小值时通常不可行。

二分答案的题目形形色色，套路高度一致："求最大的最小距离"可以判定能否放下至少 k 个物品，"求最小的最大耗时"可以判定能否在限定时间内完成所有任务，"求最少天数"可以判定限定天数能否运完。判定函数几乎都是贪心：从左到右尽可能塞，塞不下就新开一组。写完判定函数先用极端数据自检，再交给二分，能省掉大量调试时间。

20.5 partition_point 与切片自带二分：标准库的抽象

标准库还提供了 slice::partition_point，它接受一个谓词，返回第一个使谓词为 false 的位置——要求谓词在序列上是"先 true 后 false"的单调形式。lower_bound 可以写成 a.partition_point(|&x| x < target)，upper_bound 则是 a.partition_point(|&x| x <= target)。把二分模式的意图直接写进方法名里，可读性明显更好；而且这个方法对任何支持索引的切片都可用，不必自己写区间约定。

binary_search_by 是另一个有用的接口：它接受自定义比较闭包，适合结构体数组的二分。例如对 Vec<(String, i32)> 按第一字段二分，可以写 v.binary_search_by(|p| p.0.as_str().cmp(key))。注意它返回的是 Result<usize, usize>，Err(pos) 表示插入位置——语义上等价于 lower_bound。若数组含重复元素且需要第一个或最后一个匹配位置，还是要自己在 Err/Ok 之后用 lower/upper_bound 精确定位，或者用 partition_point 直接表达意图。还有 binary_search_by_key，它接受一个取关键字的闭包，是 sort_by_key 在二分侧的对应物，适合按结构体的某个字段查找。这几个接口共享同一个前提：元素按比较规则单调排列，否则结果未定义——标准库不会检查数组是否有序，把责任完全交给调用方。

选择自己写二分还是用标准库，取决于两点：一是否需要非标准的区间约定（例如闭区间 [l, r] 或需要同时返回多个量），二是否要对二分过程做统计（例如记录比较次数用于复杂度实测）。只是普通查找时，优先用标准库——它久经考验，能避免手写边界错误。闭包形式的比较器在 Rust 里会被单态化，调用开销通常能被内联消除，所以 binary_search_by 的性能与手写循环相当，不必因为"闭包可能慢"而回避它。真正影响性能的往往是数据结构本身：在链表上做二分是 O(n) 而非 O(log n)，因为无法用下标直接访问中点；这也是为什么 Rust 把二分方法定义在切片上而不是迭代器上——它需要随机访问能力。

20.6 浮点排序与 Ord 的契约

排序浮点数时要格外小心：IEEE 754 的 NaN 与任何值比较都返回 false，不满足 Ord 要求的全序关系（全序要求任意两个值可比且满足传递性），所以 f64 没有实现 Ord，直接 sort() 编译不过。f64::partial_cmp 返回 Option<Ordering>，遇到 NaN 就是 None。竞赛数据通常不含 NaN，这时可以用 a.partial_cmp(b).unwrap()；若数据可能含 NaN，要先把 NaN 过滤掉或映射到无穷大再排，或者用 Rust 1.62 起提供的 f64::total_cmp——它定义了一个把所有 NaN 排在最后、区分 +0 与 -0 的全序，可以直接传给 sort_by。

更一般地，Ord 与 PartialOrd 必须保持一致：若 a.cmp(b) == Ordering::Less，那么 a.partial_cmp(b) 必须是 Some(Less)。手动实现时若违反这个契约，排序、二分、堆的行为都会变得不可预测——它们默认比较关系是一致的、可传递的。这也是为什么给自定义类型 derive PartialOrd 与 Ord 时，字段顺序必须完全相同：derive 会按字段声明顺序逐个比较，两者顺序不同就会破坏一致性。工程上更推荐只 derive Ord（它要求同时实现 Eq），再让 PartialOrd 由 derive 自动推导，杜绝手写不一致的可能。

total_cmp 的具体规则值得记住：它先把浮点数按 IEEE 754 的位模式解释为整数，再做一次符号变换，使得排序结果满足"-NaN < -inf < 负数 < -0 < +0 < 正数 < +inf < +NaN"。换句话说，所有 NaN 被归到两端（负 NaN 最小、正 NaN 最大），零的正负号也纳入比较。这样定义的全序虽然与数学上的数轴不完全一致，但满足 Ord 的契约，可以直接用于 sort 与 BinaryHeap。处理传感器数据这类可能混入 NaN 的输入时，用 sort_by(f64::total_cmp) 比 partial_cmp().unwrap() 安全得多——后者遇到 NaN 会直接 panic。

20.7 随机对拍：排序、边界、二分答案一起验

二分边界和归并条件都极易错一两个位置，对拍能把"我觉着对了"变成"几千组数据都对了"。本节用固定种子 314159 的 LCG 一次验证三组实现：归并排序与逆序对、四种二分边界、二分答案。

对照组设计：逆序对用二重循环暴力计数；二分边界用线性扫描找第一个 < target 与第一个 <= target 的位置；二分答案枚举所有切分方案——用 n - 1 个间隙的位掩码表示在哪里切，只保留恰好 pieces - 1 个断点的方案，取所有方案中最大段和的最小值。小数据下这些暴力解法瞬间完成，当裁判正合适。

fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
fn merge_sort_count(a: &mut [i64], tmp: &mut [i64]) -> i64 {
let n = a.len();
if n <= 1 { return 0; }
let mid = n / 2;
let mut inv = merge_sort_count(&mut a[..mid], &mut tmp[..mid]);
inv += merge_sort_count(&mut a[mid..], &mut tmp[mid..]);
let (ll, rl) = (mid, n - mid);
{
let (left, right) = a.split_at(mid);
let (lbuf, rbuf) = tmp.split_at_mut(mid);
lbuf[..ll].copy_from_slice(left);
rbuf[..rl].copy_from_slice(right);
}
let (mut i, mut j, mut k) = (0usize, 0usize, 0usize);
while i < ll && j < rl {
if tmp[i] <= tmp[mid + j] {
a[k] = tmp[i]; i += 1;
} else {
inv += (ll - i) as i64;
a[k] = tmp[mid + j]; j += 1;
}
k += 1;
}
while i < ll { a[k] = tmp[i]; i += 1; k += 1; }
while j < rl { a[k] = tmp[mid + j]; j += 1; k += 1; }
inv
}
fn inv_slow(a: &[i64]) -> i64 {
let mut c = 0i64;
for i in 0..a.len() {
for j in i + 1..a.len() {
if a[i] > a[j] { c += 1; }
}
}
c
}
fn lower_bound(a: &[i32], t: i32) -> usize {
let (mut l, mut r) = (0usize, a.len());
while l < r {
let m = l + (r - l) / 2;
if a[m] < t { l = m + 1; } else { r = m; }
}
l
}
fn upper_bound(a: &[i32], t: i32) -> usize {
let (mut l, mut r) = (0usize, a.len());
while l < r {
let m = l + (r - l) / 2;
if a[m] <= t { l = m + 1; } else { r = m; }
}
l
}
fn lb_slow(a: &[i32], t: i32) -> usize {
let mut i = 0;
while i < a.len() && a[i] < t { i += 1; }
i
}
fn ub_slow(a: &[i32], t: i32) -> usize {
let mut i = 0;
while i < a.len() && a[i] <= t { i += 1; }
i
}
fn feasible(a: &[i64], pieces: usize, limit: i64) -> bool {
let mut used = 1usize;
let mut sum = 0i64;
for &x in a {
if x > limit { return false; }
if sum + x > limit {
used += 1;
sum = x;
if used > pieces { return false; }
} else { sum += x; }
}
true
}
fn minimize_largest_sum(a: &[i64], pieces: usize) -> i64 {
let mut lo = *a.iter().max().unwrap();
let mut hi: i64 = a.iter().sum();
while lo < hi {
let mid = lo + (hi - lo) / 2;
if feasible(a, pieces, mid) { hi = mid; } else { lo = mid + 1; }
}
lo
}
fn brute_min_largest(a: &[i64], pieces: usize) -> i64 {
let n = a.len();
let mut best = i64::MAX;
for mask in 0u32..(1u32 << (n - 1)) {
if mask.count_ones() as usize != pieces - 1 { continue; }
let mut cur = 0i64;
let mut seg_max = 0i64;
for i in 0..n {
cur += a[i];
if i < n - 1 && (mask & (1u32 << i)) != 0 {
seg_max = seg_max.max(cur);
cur = 0;
}
}
seg_max = seg_max.max(cur);
best = best.min(seg_max);
}
best
}
fn main() {
let seed0 = 314159u64;
let mut seed = seed0;
let mut bad = 0usize;
// 测试一：归并排序 + 逆序对 vs 暴力
for _ in 0..2000 {
let n = (lcg(&mut seed) % 12 + 1) as usize;
let a: Vec<i64> = (0..n).map(|_| (lcg(&mut seed) % 21) as i64 - 10).collect();
let expected_inv = inv_slow(&a);
let mut expected_sorted = a.clone();
expected_sorted.sort_unstable();
let mut work = a.clone();
let mut tmp = vec![0i64; n];
let inv = merge_sort_count(&mut work, &mut tmp);
if inv != expected_inv || work != expected_sorted {
bad += 1;
println!("SORT MISMATCH: a={:?} inv={} exp={} sorted={:?}", a, inv, expected_inv, work);
break;
}
}
// 测试二：四种二分边界 vs 线性扫描
if bad == 0 {
for _ in 0..3000 {
let n = (lcg(&mut seed) % 15 + 1) as usize;
let mut a = Vec::with_capacity(n);
let mut v = (lcg(&mut seed) % 10) as i32;
for _ in 0..n {
a.push(v);
v += (lcg(&mut seed) % 3) as i32; // 0/1/2 保证非降且有重复
}
let t = (lcg(&mut seed) % 20) as i32;
if lower_bound(&a, t) != lb_slow(&a, t) || upper_bound(&a, t) != ub_slow(&a, t) {
bad += 1;
println!("BOUND MISMATCH: a={:?} t={} lb={} lbs={} ub={} ubs={}",
a, t, lower_bound(&a, t), lb_slow(&a, t), upper_bound(&a, t), ub_slow(&a, t));
break;
}
let fe = {
let mut r = None;
for (i, &x) in a.iter().enumerate() { if x == t { r = Some(i); break; } }
r
};
let le = {
let mut r = None;
for (i, &x) in a.iter().enumerate() { if x == t { r = Some(i); } }
r
};
let i = upper_bound(&a, t);
let my_le = if i > 0 && a[i - 1] == t { Some(i - 1) } else { None };
let j = lower_bound(&a, t);
let my_fe = if j < a.len() && a[j] == t { Some(j) } else { None };
if fe != my_fe || le != my_le {
bad += 1;
println!("EQUAL MISMATCH: a={:?} t={}", a, t);
break;
}
}
}
// 测试三：二分答案 vs 枚举所有切分
if bad == 0 {
for _ in 0..1500 {
let n = (lcg(&mut seed) % 9 + 2) as usize;
let pieces = (lcg(&mut seed) % (n as u64 - 1) + 1) as usize + 1;
let a: Vec<i64> = (0..n).map(|_| (lcg(&mut seed) % 15) as i64 + 1).collect();
let fast = minimize_largest_sum(&a, pieces);
let slow = brute_min_largest(&a, pieces);
if fast != slow {
bad += 1;
println!("ANSWER MISMATCH: a={:?} pieces={} fast={} slow={}", a, pieces, fast, slow);
break;
}
}
}
if bad == 0 {
println!("diff seed={}: sort 2000 + bounds 3000 + answer 1500 cases passed", seed0);
}
}

测试数据的构造也有讲究：二分测试用"每步加 0/1/2"的方式生成非降且有大量重复的数组，专门压测相等边界；二分答案的数组元素全为正，满足"每段和为正"的前提。一旦出现不一致，程序立刻打印完整现场并停止，把种子和数组记下来就能稳定复现。

对拍还有一个容易被忽略的价值：它同时验证了暴力解法本身。如果 inv_slow 或 brute_min_largest 写错了，对拍会报出大量不一致，促使你回到问题定义重新检查——这恰恰是暴露理解偏差的机会。反过来，如果对拍一直通过，也要警惕"两个实现共享同一个错误假设"的可能：例如把"非空子段"误理解成"可空子段"，两种实现可能一起偏离题意。因此除了对拍，还要用手工构造的边界样例（空数组、单元素、全相等、已排序、逆序）直接核对题意，双重保险才放心。

大白话先用直觉把它讲通

二分边界就像在一排排好队的人里找"第一个分数达到 80 的人"和"第一个分数超过 80 的人"。两者只差一个判断符号，但差之毫厘谬以千里。对拍就是让一个从队头一个个看的笨办法当裁判，几千组随机数据都一致，你才敢说边界写对了。

20.8 调试清单、练习与自检

这一类题目的自检可以逐项核对：排序时稳定性是否满足题意、比较器的参数顺序是否写反、合并条件是否用了 <=；二分时区间约定是否全程统一为左闭右开、中点公式是否防溢出、last_equal 是否先判断了 i > 0；二分答案时单调性是否证明、lo/hi 是否落在正确区间、判定贪心是否真的最小化段数。slice::binary_search 的 Err(pos) 是插入位置而非"找不到"，这个语义常被误用，要特别留意。

排序和二分是后续几乎所有算法的基础设施：双指针之前要排序、DP 之前要排序、图论里的离散化也依赖排序 + 二分。把这一单元的比较器、边界和单调性打扎实，后面遇到"先排序再处理"的题目时就能把注意力放在算法本身，而不是反复纠结边界。对拍依旧是最后的保险——尤其在二分答案这种"写错也能跑出个数"的场景，没有暴力对照很难发现答案偏了一格。

复杂度方面，排序是 O(n log n)，归并排序统计逆序对额外是 O(n) 空间，四种二分边界各是 O(log n) 时间、O(1) 空间，二分答案的总代价是 O(log V · 判定代价)。把这几个量级与第 17 单元的速查表对照，就能在数据规模给定时快速判断方案是否可行。例如值域 V 达到 10⁹ 时，二分答案只需约三十次判定，而枚举值域绝无可能——这正是"对答案二分"的价值所在。这些数字本身不难，难的是把它们与具体约束对应起来：当数组长度达到 10⁶ 时，O(n log n) 的排序约需两千万次比较，在 Rust 的 release 构建下通常在一两秒内完成；而一次 O(log n) 的二分只有二十步左右，几乎可以忽略。因此在"排序一次、查询多次"的场景，把排序成本摊到每次查询上非常划算，这正是离线算法常用的优化思路。
