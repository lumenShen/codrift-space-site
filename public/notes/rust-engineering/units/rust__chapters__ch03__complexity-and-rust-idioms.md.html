17.1 从输入规模倒推算法：复杂度是第一道闸门

拿到一道算法题，第一件事不是想模板，而是看数据范围。复杂度分析真正的用途，是在写第一行代码之前就砍掉注定超时的思路。一个 n ≤ 20 的问题可以放心枚举子集，n ≤ 500 容得下三重循环的区间 DP，n ≤ 2000 通常是平方算法的天下，而 n ≥ 10⁵ 就必须把目标锁定在 O(n log n) 甚至 O(n)。这种"由约束反推复杂度，再由复杂度反推数据结构"的思路，比背十套模板更能决定解题速度。

big-O 描述的是 n 趋向无穷时增长速度的量级，刻意忽略常数系数与低阶项。刷题时不必逐条做极限推导，但要形成对结构的条件反射：一层循环是线性，两层嵌套通常是平方，每轮规模减半是对数，分治加线性合并是 n log n，而状态数随输入指数膨胀的问题基本不可解。空间一侧同样要算，尤其是递归调用栈——一个深度为 n 的递归函数，即使每层只存一个整数，也占用 O(n) 的栈空间，这正是后面反复强调"用显式栈替代递归"的理由。

大白话先用直觉把它讲通

复杂度就是在问"数据量翻十倍，程序会不会慢到没法用"。O(n) 大致慢十倍，O(n²) 大约慢一百倍，O(log n) 几乎感觉不到变化。先花十秒估一下量级，能让你早早放弃那些注定超时的朴素想法，把精力花在正确方向上。

复杂度 典型场景 n = 10³ n = 10⁶ 判断要点
O(1) 下标访问、哈希查询 1 1 与 n 无关
O(log n) 二分、堆调整 ≈10 ≈20 每轮规模减半
O(n) 单层循环、前缀和 10³ 10⁶ 每元素常数次
O(n log n) 归并排序、堆排序 ≈10⁴ ≈2·10⁷ 分治或堆
O(n²) 二重循环、朴素 DP 10⁶ 10¹² 两层嵌套
O(2ⁿ) 子集枚举 天文数字 不可行 状态爆炸

估错复杂度的常见原因有三类。第一，把"看起来嵌套"误判成平方：单调栈的 while 弹栈写在 for 循环里面，看似嵌套，但每个元素最多进出各一次，摊仍是线性。第二，忘了把输入和输出算进去：读入一百万个整数本身就是 O(n)，一个 O(n log n) 的排序配上 O(n²) 的字符串拼接，整体依旧是平方级。第三，忽视内存：在 256 MB 限制下，一个 Vec<i64> 装一百万个数就吃掉 8 MB，几个二维 Vec<Vec<i64>> 轻松超限，复杂度正确却因内存爆炸而失败。

反推法在具体题型上有稳定的对应关系：看到"子数组"想到前缀和与滑动窗口，看到"子序列"想到动态规划，看到"连通性"想到并查集或图遍历，看到"最值"想到堆或单调结构。这些对应不是死记硬背的结论，而是复杂度约束筛选后的结果——子序列的数量是指数级，所以只能用 DP 在多项式状态上转移；连通性查询若需要动态合并，逐次重跑 BFS 是 O(mn)，而并查集把它压到近乎线性。把"为什么选这个结构"讲给自己听一遍，才算真正掌握了复杂度分析。内存估算同样要养成习惯：先数清数组个数与元素宽度，再乘以规模，最后加上调用栈与临时缓冲，和限制一对比就知道该不该换更紧凑的表示。

17.2 渐进符号的严格含义：O、Ω、Θ 与四种"复杂度"

严格地说，O(f(n)) 只给出上界，Ω(f(n)) 给出下界，两者同时成立才写作 Θ(f(n))。日常语境里大家把"大 O"当成"精确量级"来用，这是约定俗成的简化；写证明时若被追问，要能说清自己给的是上界还是紧确界。对数的底同样无关紧要：log₂n 与 log₁₀n 只差一个常数因子，所以统一写成 log n；唯独 log log n 与 log²n 不能混为一谈，前者增长极慢，后者是平方对数。

同一份代码在不同输入下表现可能天差地别，因此要区分四种口径。最坏情况是竞赛默认口径，保证任何输入都不超时；平均情况假设输入随机分布，快速排序平均 O(n log n) 但有序输入会退化成 O(n²)；均摊情况看一串操作的平均代价，Vec::push 在扩容那一次是 O(n)，但按倍增扩容，连续 n 次 push 的总代价是 O(n)，摊下来每次 O(1)；摊还分析的另一种典型是并查集的路径压缩加按秩合并，单次操作的摊还代价是反阿克曼函数 α(n)，在实践中可以当作常数。把口径写清楚，比争论"到底是 O(n) 还是 O(n²)"更有意义。

证明摊还复杂度有三种常用手法。聚合分析直接算出 n 次操作的总代价再除以 n，适合 Vec 扩容这类场景：容量依次为 1、2、4、8……，总搬移次数不超过 2n。势能法给数据结构定义一个势能函数 Φ，把每次操作的摊还代价记作实际代价加势能变化；并查集的势能取决于树的高度与秩，路径压缩虽然单点代价高，却大幅降低势能，从而摊还下来接近常数。记账法可以理解为势能法的具象版本：给每次操作发"虚拟币"，预先为将来可能的昂贵操作存钱。理解这三种手法后，看到"摊还 O(1)"的结论就不会只停留在背诵层面，也能自己论证单调栈里内层 while 为何不破坏线性上界。

坑这里最容易踩

从小到大跨越下标边界时，usize 的回绕是 debug 构建下的 panic、release 构建下的静默错误，而后者更可怕。在 i = 0 时写 i - 1，debug 会当场报错，release 却悄悄变成 18446744073709551615，继而越界访问或者死循环。防御办法是让减法永远在"被减数大于减数"的前提下发生：先 if i > 0 判断，或用 saturating_sub，或把下标转成 isize 做减法。不要把类型检查和边界判断的责任推给运行时。

复杂度还要算到常数与缓存这一层。两个同为 O(n) 的实现，一个是顺序扫描 Vec，另一个频繁随机跳转访问 HashMap，实测可能差十倍——这源于 CPU 缓存行与分支预测，而非渐进量级。渐进分析回答"规模变大时趋势如何"，实测回答"在这台机器上到底多快"，两者互补而非替代。一个实用的原则是：先把渐进量级选对，再用实测确认常数没有夸张到越界；反过来只测小规模数据、不做量级分析，很容易被"某个常数较小的平方算法在小数据上更快"误导。

17.3 输入输出：一次性读入与 split_whitespace 解析

Rust 标准库没有 scanf。竞赛里通行的做法是一次性把 stdin 读进一个 String，再用 split_whitespace 切成词元序列。这么做有两个好处：系统调用次数少，且不必关心换行符是 \n 还是 \r\n。下面的 Scanner 用泛型加 FromStr 统一解析所有整数类型，是后续各单元的通用零件。

rustRust · 标准库34 行
use std::io::{self, Read};
use std::str::FromStr;
struct Scanner {
tokens: Vec<String>,
pos: usize,
}
impl Scanner {
fn new() -> Self {
let mut s = String::new();
io::stdin().read_to_string(&mut s).unwrap();
let tokens = s.split_whitespace().map(|t| t.to_string()).collect();
Scanner { tokens, pos: 0 }
}
fn next<T: FromStr>(&mut self) -> T {
// 先解析再自增 pos，彻底避开对 self 的借用冲突
let val = self.tokens[self.pos].parse::<T>().ok().expect("parse failed");
self.pos += 1;
val
}
}
fn main() {
let mut sc = Scanner::new();
let n: usize = sc.next();
let mut v: Vec<i64> = Vec::with_capacity(n);
for _ in 0..n {
v.push(sc.next::<i64>());
}
let sum: i64 = v.iter().sum();
println!("n={} sum={}", n, sum);
}

这里有两处值得细看。其一，next 里先解析再自增 pos：如果写成 let val = self.tokens[self.pos].parse...; self.pos += 1;，看上去也没问题，但把自增和借用拆开能避免"同一表达式里既有不可变借用又有可变借用"的隐患——编译器通常能处理，养成明确顺序的习惯更省心。其二，parse::<T>().ok().expect(...) 不是多此一举：T::Err 未必实现 Debug，直接 unwrap() 可能编译不过，而 .ok() 先把 Result<T, E> 转成 Option<T>，expect 就不再要求错误类型可打印。

输出侧同样有讲究。println! 每次调用都可能触发一次系统调用，输出上万行时应先把结果攒进 String 或 Vec<String>，最后一次性 print!。批处理输出可以写成：先用 String::with_capacity 预留空间，循环里用 push_str 追加片段，最后单次 print! 把整块内容交给 stdout。相比之下，循环里每次 println! 都可能陷入一次系统调用，上十万行时差距非常明显。格式化宏本身也有成本，format! 会分配一个新的 String，所以极热路径上可以直接用 write! 配合 out 的可变引用，把中间分配也省掉。格式化宏支持类似 C 的对齐语法，{:>8} 右对齐占八格，{:.2} 保留两位小数。整数解析要注意符号：parse::<i64>() 能正确处理 -12，但把负数解析成 usize 会直接失败，所以读入可能带负号的数据时一定用 i64，只在确认非负且要当下标时再显式转换。下面的终端记录是真实编译运行的结果。

17.4 三条实现约定：预分配、哨兵与左闭右开

Rust 写算法与 C++ 最大的差别集中在三个地方。预分配：已知元素个数时先 Vec::with_capacity(n)，避免反复扩容时的数据搬运。哨兵：在数组前端或后端多开一格，省掉边界特判。左闭右开：区间统一写成 [l, r)，长度直接是 r - l，相邻区间不会在端点重叠。

下面的程序把这三条落在同一段代码里：前缀和多开一格，让 pref[0] = 0 当哨兵，于是"前 i 个元素之和"统一为 pref[i]；区间查询用 [l, r)，答案就是 pref[r] - pref[l]；最后用迭代累加替代递归，避开调用栈上限。注意 i as i64 是有意写出的显式转换——Rust 不会在 usize 与 i64 之间隐式转换，把转换写在明面上，能立刻暴露"这里可能出现负数"的设计意图。

rustRust · 标准库24 行
fn main() {
let n = 100_000usize;
// 约定一：预分配 + 哨兵，前缀和多开一格
let mut pref: Vec<i64> = Vec::with_capacity(n + 1);
pref.push(0i64);
for i in 0..n {
pref.push(pref[i] + (i as i64) * 2);
}
// 约定二：左闭右开区间 [l, r)，减法方向保证 r >= l
let (l, r) = (3usize, 9usize);
let sum = pref[r] - pref[l];
// 约定三：迭代替代递归，绝不触碰调用栈上限
let mut acc = 0i64;
for x in 1..=n {
acc += x as i64;
}
println!("sum[{}..{}) = {}", l, r, sum);
println!("1..={} = {}", n, acc);
println!("len = {}, cap = {}", pref.len(), pref.capacity());
}

len 与 capacity 的关系也值得说明：with_capacity 保证至少能装下指定数量的元素，实际容量由分配器决定；上面这次运行恰好相等，但程序不应依赖这一点。真正依赖的是 pref[i] 的下标范围——它只到 n，而容量不小于 n + 1，所以写入永远安全。把"逻辑长度"和"物理容量"分开理解，是后续手写栈、队列、堆的基础。

补一句值得记住的细节

为什么递归在 Rust 算法里格外危险？主线程默认栈只有几 MB，深达十万层的 DFS 会直接 stack overflow，而且这种崩溃无法用 catch_unwind 可靠恢复。改成显式栈（用 Vec 当栈）后，内存来自堆，只受可用内存限制；递归只有在深度可证明为 O(log n) 时才安全，比如归并排序——它的递归深度是 log₂n，几十层而已。

17.5 usize 下溢与整数回绕：Rust 算法最隐蔽的敌人

usize 是下标唯一合法的类型，代价是不能为负。它的回绕有两个层次：下标减法如 0usize - 1，debug 构建 panic、release 构建回绕成最大值；算术溢出如两个大 u64 相乘，行为类似。随机数的线性同余生成器（LCG）必须显式使用 wrapping_mul 与 wrapping_add，否则 debug 构建下第一次乘法就会溢出 panic。下面的程序集中演示了四种防御姿势。

rustRust · 标准库27 行
fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
fn main() {
let mut s = 1u64;
println!("lcg x3 = {} {} {}", lcg(&mut s), lcg(&mut s), lcg(&mut s));
let i = 0usize;
// 安全写法一：先判断再减
let safe = if i > 0 { i - 1 } else { usize::MAX };
println!("guarded i-1 = {}", safe);
// 安全写法二：isize 中转，保留负数语义
let j: isize = i as isize - 1;
println!("isize i-1 = {}", j);
// 安全写法三：标准库提供的饱和减与受检减
println!("saturating = {}, checked = {:?}", i.saturating_sub(1), i.checked_sub(1));
// 大下标相加可能溢出，用中点公式规避
let (l, r) = (usize::MAX - 2, usize::MAX);
println!("mid = {}", l + (r - l) / 2);
}

四种写法各有适用场合。if i > 0 最直接，适合"前面就是边界"的语义；isize 中转保留了 -1 的数学含义，适合需要负数的推导；saturating_sub 把下溢钳到 0，适合表示"最多减到空"；checked_sub 返回 Option，适合把越界显式暴露给调用方。二分中点写成 l + (r - l) / 2 而不是 (l + r) / 2：当 l、r 都是接近 usize::MAX 的大下标时，后者会在相加那一刻溢出，而前者先减后加，差值一定不溢出。输出里 mid = 18446744073709551614 正是这个公式在极端输入下的正确结果。

大白话先用直觉把它讲通

usize 像一个只能显示非负数的里程表，往回拨一格不会显示 -1，而是跳到最大数。程序不会当场告诉你错了，只会拿着这个荒唐的大数继续跑。所以每次要写减法前，都先在脑子里问一句："减数会不会比被减数大？"如果会，就必须先挡一道。

17.6 借用冲突的四把钥匙：从 split_at_mut 到 mem::take

C++ 里司空见惯的"遍历容器的同时修改容器"，在 Rust 中被严格禁止；算法代码里最典型的冲突是"遍历 Vec 的同时往同一个 Vec 里 push"。编译器拒绝这类代码，是因为迭代器持有容器的借用，而 push 需要可变借用。化解的办法不是关闭检查，而是换一种表达，让"互不重叠"或"先后关系"在类型层面变得可见。

rustRust · 标准库30 行
fn main() {
let mut a = vec![1i32, 2, 3, 4, 5];
// 模式一：split_at_mut 拿到两段互不重叠的可变切片
{
let (left, right) = a.split_at_mut(2);
left[0] += right[0];
}
println!("split_at_mut: {:?}", a);
// 模式二：mem::take 把容器换出，处理完再放回去
let mut buf = vec![10, 20, 30];
let taken = std::mem::take(&mut buf);
for x in taken {
buf.push(x * 2);
}
println!("take: {:?}", buf);
// 模式三：先读旧值到局部变量，再写回
let i = 1;
let old = a[i];
a[i] = old * 10;
println!("read-then-write: {:?}", a);
// 模式四：用 get 把越界 panic 变成显式的 Option 判断
match a.get(100) {
Some(v) => println!("a[100] = {}", v),
None => println!("a[100] out of range"),
}
}

split_at_mut(k) 返回 [0, k) 与 [k, n) 两段互不重叠的可变切片，编译器能证明它们不交叉，因此可以同时持有两个 &mut。写单调栈、归并排序这类"同时读左半写右半"的代码时，它是首选。mem::take 用 Default 值换走原容器，让你可以自由消费那份数据，再把结果写回——BFS 里"取出当前层的节点、生成下一层"就是典型场景。模式三看似朴素，却最常用：同时访问 a[i] 和 a[i-1] 并修改其一时，先读出旧值到局部变量，再写回原处，借用自然消失。模式四用 .get(i) 返回 Option，在边界不确定的地方把 panic 变成显式的 if let，调试时定位问题会快很多。

这四把钥匙背后是同一个思想：把"我确信这两块内存不冲突"翻译成编译器能证明的形式。习惯之后，Rust 的严格反而是安全网——它把"遍历时修改导致迭代器失效"这类经典 bug 拦在编译期，而不是留到线上。

还有一个高频变体是"先收集再合并"：遍历时不能直接改目标容器，就把待写入的值收进一个临时 Vec，循环结束后用 extend 一次性写入。它比 mem::take 更直白，代价是多一次数据搬运。选择哪一招可以遵循一个简单的判断：如果新旧内容完全无关，用 take 最干净；如果只是要追加若干元素，用临时 Vec 更省事；如果两段数据天然分居下界两侧，用 split_at_mut 表达力最强。编译器拒绝的代码往往正因为语义含糊，换成这几种写法后，意图反而清楚了。

17.7 随机对拍：让暴力解法当裁判

写出优化算法后最难的，是确认它真的对。对拍的思路是：准备一个绝对正确的朴素版本和一个待验证的快速版本，用随机数生成成千上万组小数据，逐个比对输出，一旦不一致就打印现场。本节用一个完整案例讲清这套框架——最大子数组和。

问题定义：给定整数数组 a，求所有连续子数组之和的最大值（允许空子数组时答案为 max(0, ...)，本题要求非空）。

不变量与正确性：Kadane 算法维护 cur 为"以当前位置结尾的最大子数组和"。处理新元素 x 时，要么把 x 接在之前的段后面得到 cur + x，要么从 x 重新开始，取两者较大者即 cur = max(x, cur + x)；全局答案 best 取历史 cur 的最大值。这个转移覆盖了所有以当前位置结尾的子数组，因此不变量成立，best 就是答案。

复杂度：暴力枚举所有起点终点是 O(n²)，Kadane 是单趟扫描 O(n)，两者都为 O(1) 额外空间。

use std::time::Instant;
fn lcg(state: &mut u64) -> u64 {
*state = state
.wrapping_mul(6364136223846793005)
.wrapping_add(1442695040888963407);
*state >> 33
}
fn max_subarray_slow(a: &[i64]) -> i64 {
let mut best = i64::MIN;
for i in 0..a.len() {
let mut s = 0i64;
for j in i..a.len() {
s += a[j];
best = best.max(s);
}
}
best
}
fn max_subarray_fast(a: &[i64]) -> i64 {
let mut best = i64::MIN;
let mut cur = 0i64;
for &x in a {
cur = x.max(cur + x);
best = best.max(cur);
}
best
}
fn main() {
let seed0 = 42u64;
let mut seed = seed0;
let mut failed = false;
for t in 0..2000 {
let n = (lcg(&mut seed) % 30 + 1) as usize;
let a: Vec<i64> = (0..n)
.map(|_| (lcg(&mut seed) % 201) as i64 - 100)
.collect();
let slow = max_subarray_slow(&a);
let fast = max_subarray_fast(&a);
if slow != fast {
println!("MISMATCH t={} n={} a={:?} slow={} fast={}", t, n, a, slow, fast);
failed = true;
break;
}
}
if !failed {
println!("diff seed={}: 2000 cases passed", seed0);
}
let n = 4000usize;
let mut s = 7u64;
let a: Vec<i64> = (0..n)
.map(|_| (lcg(&mut s) % 2001) as i64 - 1000)
.collect();
let t0 = Instant::now();
let f = max_subarray_fast(&a);
let tf = t0.elapsed();
let t1 = Instant::now();
let sl = max_subarray_slow(&a);
let ts = t1.elapsed();
println!("n={} fast={} in {:?}; slow={} in {:?}", n, f, tf, sl, ts);
}

对拍有三个进阶习惯。一是固定并打印种子：发现错误用例时记下种子就能稳定复现，而不是靠运气再撞一次。二是控制数据规模：小数据下 O(n²) 的暴力解法跑得飞快，正好当裁判；上面用 n ≤ 30，两千组数据瞬间跑完。三是构造有区分度的分布：数据全为正或全为负时，很多错误分支根本走不到，所以这里用 % 201 - 100 生成正负混合的值。找到反例后还可以缩小用例：逐个删除元素，只要删除后两种实现仍不一致就继续删，最后得到一个极小反例，往往一眼就能看出是哪行边界写错。

对拍也不是万能的。它只能验证"两个实现在生成的分布上一致"，如果暴力解法本身有 bug，或者随机分布永远覆盖不到某类边界（比如空数组、全相等、极端值），对拍就会给出虚假的安心。因此生成数据时要有意识地混入退化样本：n = 1、全 0、全负、已排序、逆序，以及值域上下界。把这些固定用例与随机用例混合，才是完整的验证策略。此外，对拍验证的是"实现符合暴力版本"，而非"实现符合题意"——如果题意理解错了，两个实现可能一起错，这时唯一可靠的办法是回到问题定义，用不变量重新推导一遍。

17.8 计时与实测：常数、缓存与"看起来更快"

上一节的输出里，n = 4000 时 Kadane 用了约 20 微秒，暴力解法用了约 45 毫秒，差了约两千倍——这正是 O(n) 与 O(n²) 在规模放大后的真实差距。计时数字每次运行都会略有波动（取决于机器负载与调度），终端块里贴的是某一次真实运行的结果，重点看量级倍数而非精确小数。Instant::now() 与 elapsed() 是标准库提供的单调时钟，适合测量这类短区间耗时；它不受系统时间调整影响，但会受机器负载、CPU 频率与编译器优化影响，因此数字只能在同一台机器、同一构建模式下横向比较。

计时要注意三点。第一，用 release 构建测性能，debug 构建没有优化，数字没有参考价值；但本文所有代码块都用 rustc --edition 2021 默认（debug）编译以证明"可直接编译通过"，计时数字同样来自该构建，所以只用于展示量级差异而非绝对值。第二，避免测量被优化掉：如果结果完全没被使用，优化器可能删掉整段计算；把结果 println! 出来，或存入一个外部可见的变量，能防止这种"虚假加速"。第三，多次运行取稳定值：单次测量可能撞上系统调度抖动，跑三五次取中位数更可靠。

测量要点 错误做法 正确做法
构建模式 用 debug 数字下结论 性能结论基于 release
结果使用 算完就丢，可能被优化掉 打印结果或逃逸到外部
噪声处理 只跑一次 多次运行取中位数
跨机比较 直接对比不同机器的耗时 比较同机同配置下的相对倍数

实测数字还要放在正确的语境里解读。上面 n = 4000 的对比中，暴力解法约 45 毫秒、Kadane 约 20 微秒，倍数接近两千；如果把 n 缩小到 100，倍数会跌到几十，因为平方算法的常数项和循环开销在低规模时占主导。这说明"渐进优势"只有在规模足够大时才显现，小规模数据上选错算法未必立刻暴露——这也是对拍必须覆盖较大随机输入的原因之一。另一个常见误区是拿不同语言的数字互相比较：Rust 的 debug 构建比 C++ 的 -O2 慢很多，但 release 构建加上单态化后的性能通常接近 C++，离开构建模式谈快慢没有意义。

复杂度分析与实测是互补的：前者告诉你"规模翻十倍会怎样"，后者告诉你"在这台机器上到底多快"。把随机对拍当作正确性保险，把计时当作性能体检，再配上"先算量级、再选结构"的决策流程，就构成了后续所有算法单元的工程底座。下面两道练习把这套底座真正用起来。
