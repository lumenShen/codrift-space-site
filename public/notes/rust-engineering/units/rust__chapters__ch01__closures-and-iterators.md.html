7.1 闭包是匿名结构体：捕获模式决定布局

闭包（closure）看起来像「一段能当值传递的代码」，但在编译后的世界里它是一个匿名结构体：结构体里若干字段保存被捕获的环境值，编译器再为它生成一个 call 方法执行函数体。一个闭包表达式就对应一个独一无二的类型，哪怕两段代码长得完全一样，它们的类型也不同——这是理解后续所有行为的起点。

捕获模式不是由 move 关键字单独决定的，而是编译器先看函数体怎么用变量，再推导捕获方式：只读就按共享引用捕获，需要修改就按可变引用捕获，需要转移所有权就按值捕获。move 的作用是强制「所有捕获都按值进行」，即使函数体只读也复制/移动到闭包里。下面的程序用 size_of_val 把三种捕获的实际大小打出来：

rustRust · 标准库15 行
use std::mem::size_of_val;
fn main() {
let a = 1u32;
let mut b = 2u32;
let s = String::from("hi");
let borrow = || a;
let mut borrow_mut = || { b += 1; b };
let owned = move || s.len();
println!("borrow={} borrow_mut={} owned={}",
size_of_val(&borrow), size_of_val(&borrow_mut), size_of_val(&owned));
println!("values: {} {} {}", borrow(), borrow_mut(), owned());
}
终端真跑一遍
$ rustc --edition 2021 u07_b1.rs -o u07_b1 && ./u07_b1
borrow=8 borrow_mut=8 owned=24
values: 1 3 2

borrow 和 borrow_mut 都是 8 字节，因为环境里只有一个引用；owned 是 24 字节，因为 String 被整个搬进了闭包（3 个字：指针、长度、容量）。注意 owned 只调用了 s.len()，并没有消耗 s，所以它仍然实现 Fn——move 改变的是捕获方式，不是 call 方法需要 &self 还是 self。

不捕获任何变量的闭包大小为 0 字节（ZST），编译器可以直接用类型本身当值，不占存储空间。捕获字段的排列顺序是编译器的自由选择，不要依赖它；能依赖的只有「捕获得越多、闭包越大」这个总体规律。

edition 2021 还引入了 disjoint capture（精确捕获）：闭包只使用结构体的一个字段时，编译器只捕获那个字段，而不是整个结构体。这直接减少了借用冲突——下面的例子在 2018 edition 下会报错（整个 d 被借用），在 2021 下却能编译，因为 d.b 完全没进入闭包：

rustRust · 标准库8 行
struct Data { a: i32, b: String }
fn main() {
let d = Data { a: 1, b: String::from("s") };
let c = || d.a; // edition 2021：只捕获 d.a 这一个字段
println!("c() = {}", c());
println!("d.b = {}", d.b); // b 未被捕获，仍可正常使用
}
终端真跑一遍
$ rustc --edition 2021 u07_b8.rs -o u07_b8 && ./u07_b8
c() = 1
d.b = s

这个机制对异步代码尤其重要：async 块本质上也是一种闭包式捕获，精确捕获让「只用到 self 的一个字段」的 future 不会把整个 self 借走，从而减少 Send/Sync 约束传播和借用冲突。

闭包的参数类型通常可以省略，因为编译器会结合上下文推断：直接调用 let f = |x| x + 1; f(1u32); 时，x 被推断为 u32；传给 map 时，x 的类型由迭代器的 Item 决定。但「先定义、后传给多个不同签名的函数」会让推断失去唯一解，此时必须显式标注 |x: i32| ...。这也是闭包不如普通函数「独立」的一个表现——它的类型与上下文紧密绑定。

大白话先用直觉把它讲通

闭包像一个随身带着工具的小工人。只看一眼桌上的尺子（共享借用），兜里只装一把「尺子在哪」的纸条；要挪动桌子（可变借用），兜里装的是「桌子在哪」的纸条；老板说「这桌子归你了」（move），他就把整张桌子扛走。工人干的活一样，但兜里东西的多少决定了他的「体积」。

7.2 Fn、FnMut、FnOnce：一层套一层的三个 trait

三个调用 trait 形成严格的层级关系：FnOnce: FnMut: Fn。它们分别对应三种调用方式：

trait 调用方法 需要的接收者 能做什么
FnOnce call_once self（按值） 可以消耗捕获的值，只能调用一次
FnMut call_mut &mut self 可以修改捕获的环境，可多次调用
Fn call &self 只读环境，可多次调用且无副作用要求

层级是「子 trait 自动获得父 trait 的能力」：Fn 一定是 FnMut，也一定是 FnOnce；但反过来不成立。因此当一个函数泛型参数是 F: FnOnce 时，传进来的闭包即使只读取变量也没问题；反过来若参数是 F: Fn，却传了一个消耗 String 的闭包，编译器就会拒绝。标准库里的 &F 在 F: Fn 时实现 Fn，&mut F 在 F: FnMut 时实现 FnMut——这让「借用着调用」变得自然。

rustRust · 标准库18 行
fn call_once<F: FnOnce() -> String>(f: F) -> String { f() }
fn call_mut<F: FnMut() -> i32>(mut f: F) -> i32 { f() }
fn call<F: Fn() -> i32>(f: F) -> i32 { f() }
fn main() {
let x = 10;
let f = || x; // 只读借用，实现 Fn + FnMut + FnOnce
println!("Fn: {}", call(f));
let mut n = 0;
let mut fm = || { n += 1; n }; // 可变借用，实现 FnMut + FnOnce
println!("FnMut #1: {}", call_mut(&mut fm));
println!("FnMut #2: {}", call_mut(&mut fm));
let s = String::from("bye");
let fo = move || s; // 按值移动，只实现 FnOnce
println!("FnOnce: {}", call_once(fo));
}
终端真跑一遍
$ rustc --edition 2021 u07_b2.rs -o u07_b2 && ./u07_b2
Fn: 10
FnMut #1: 1
FnMut #2: 2
FnOnce: bye

这里有两个值得停下来的细节。其一，call_mut(&mut fm) 每次都能继续累加，说明可变引用的闭包「记住了」上次修改后的状态——状态在闭包结构体里，不在函数调用栈上。其二，call_once(fo) 之所以只实现 FnOnce，是因为闭包体把捕获的 String 直接返回（移动出 self），这样的闭包无法提供 &self 版本。想让它变成 FnMut 或 Fn，就得返回引用或克隆值。

FnOnce 是实际上唯一「必须实现」的 trait：任何闭包都至少能被调用一次。写泛型代码时遵循「最低要求原则」——只要调一次就写 FnOnce，要改状态写 FnMut，完全只读才写 Fn。约束越松，API 能接受的可调用对象越多。

标准库里这条原则随处可见：Option::map 接受 FnOnce，因为它对每个元素只调一次；Iterator::map 接受 FnMut，因为适配器可能被反复调用；thread::spawn 接受 FnOnce + Send + 'static，因为新线程只执行一次闭包且闭包必须拥有自己的数据。看懂这些签名，就能反推出库作者预期的使用方式。

还有一点容易混淆：闭包实现哪些 Fn trait，是编译器根据闭包体对捕获值的使用方式自动推导的，没有任何手动 impl 的入口。想改变它，只能改变捕获方式（move）或函数体（是否消耗捕获值）。函数指针 fn(i32) -> i32 也实现这三个 trait，而且作为 ZST 值可以无条件复制——这让接受 impl Fn 的 API 同样能接收普通函数，参数设计得当时非常灵活。

7.3 闭包类型不可名状：impl Fn 与 dyn Fn

因为闭包类型是编译器生成的匿名类型，你无法在源码里写出它的名字。想把它存进结构体、作为参数或返回值，只有三条路：用泛型参数 F: Fn(...)；用 impl Fn(...)（参数位置的泛型糖、返回位置的不透明类型）；或者擦除成 dyn Fn(...) 指针。

rustRust · 标准库13 行
fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
move |x| x + n
}
fn apply_static(f: &impl Fn(i32) -> i32, x: i32) -> i32 { f(x) }
fn apply_dynamic(f: &dyn Fn(i32) -> i32, x: i32) -> i32 { f(x) }
fn main() {
let add = make_adder(5);
println!("static = {}", apply_static(&add, 3));
println!("dynamic = {}", apply_dynamic(&add, 4));
println!("direct = {}", add(10));
}
终端真跑一遍
$ rustc --edition 2021 u07_b3.rs -o u07_b3 && ./u07_b3
static = 8
dynamic = 9
direct = 15

make_adder 必须写 move：否则 n 只是对栈上局部变量的引用，函数返回后就成了悬垂引用。返回 impl Fn 时，调用方知道「有个实现了 Fn 的类型」，但不知道它是谁，因此不能写 let f: 具体类型 = make_adder(5);，也不能要求它实现额外的 trait（除非在返回类型里显式写出，如 impl Fn(i32)->i32 + Send）。

坑这里最容易踩

坑：返回闭包时忘记 move 是新手最常遇到的编译错误（「captured variable escapes the closure / returns a value referencing local variable」）。反过来也要警惕 move 的滥用：若一个闭包捕获了 Rc 或大 Vec 又只被短暂调用，按值移动会无谓地转移所有权和分配。记住判断标准——闭包要活得比捕获的变量久，就必须按值拥有它。

dyn Fn 把具体类型擦除成函数指针式的胖指针，适合把不同闭包放进同一个容器（如 Vec<Box<dyn Fn(i32) -> i32>>），代价是一次间接调用且无法内联；impl Fn 则保持静态分派和零成本。Fn、FnMut、FnOnce 都是 object safe 的，所以 dyn Fn 形式合法；但带泛型方法的 trait 就不能这么做，这与 trait 对象那一节的规则一致。

事件回调、GUI 信号槽这类「异构且需要存起来」的场景常用 dyn Fn，而 map 的谓词、sort_by 的比较器这类立即使用的场景几乎总是泛型/impl Fn。若一个 API 需要在两种模式间切换，可以提供两个入口：内部泛型版本保留性能，对外再包一层接受 Box<dyn Fn> 的便捷函数。还要注意生命周期：Box<dyn Fn()> 默认等价于 Box<dyn Fn() + 'static>，若闭包借用了局部变量，必须写成 Box<dyn Fn() + '_> 并把生命周期参数显式传给函数。选择哪种形态还有一个语调上的信号：impl Fn 暗示「这是一个实现细节，不需要关心具体类型」，dyn Fn 则明确告诉读者「这里存在运行期多态，可能有间接调用开销」。

7.4 迭代器惰性：构造适配器不等于执行

v.iter().map(f).filter(g) 看起来像一串函数调用，实际发生的是构造一个嵌套的适配器结构体：Filter 持有 Map，Map 持有 Iter。每一步只是记录「将来要做什么」，没有任何元素被处理。真正驱动计算的是 next()——collect、for 循环、sum 等消费者不断调用它，数据才像水流一样从源头经过每层适配器流出来。

rustRust · 标准库18 行
fn main() {
let v = vec![1, 2, 3, 4];
let it = v
.iter()
.map(|x| { println!(" map {}", x); x * 2 })
.filter(|x| { println!(" filter {}", x); *x > 4 });
println!("适配器链已构造，还没执行");
let r: Vec<_> = it.collect();
println!("结果 {:?}", r);
let short: Vec<_> = v
.iter()
.map(|x| { println!(" visit {}", x); *x })
.take(2)
.collect();
println!("take(2) = {:?}", short);
}
终端真跑一遍
$ rustc --edition 2021 u07_b4.rs -o u07_b4 && ./u07_b4
适配器链已构造，还没执行
map 1
filter 2
map 2
filter 4
map 3
filter 6
map 4
filter 8
结果 [6, 8]
visit 1
visit 2
take(2) = [1, 2]

输出把惰性讲得非常直白：println 出现在「构造之后」之后；map 1 → filter 2 成对出现，说明每个元素完整地穿过整条链，而不是先把所有元素 map 完再统一 filter；take(2) 只打印了 visit 1 和 visit 2，说明它在拿到两个元素后立即停止，后续元素连 map 都不会执行。

适配器之所以能层层嵌套，是因为每个适配器自身也实现了 Iterator：它的 next() 内部调用上游的 next()，对拿到的值做变换，再交给下游。Iterator trait 的核心只有一个必须实现的方法 fn next(&mut self) -> Option<Self::Item>——&mut self 说明迭代器是有状态的游标，Option 的 None 表示流结束。所有其他方法（map、fold、find……）都是在这个方法之上用默认实现搭出来的。理解这一点，就可以把任意自定义数据源接进同一套生态。

这种「按需拉取（pull-based）」模型带来两个直接好处：短路天然成立（take、find、any 不必处理剩余元素），以及中间结果不必分配（map 不会创建一个新 Vec）。代价是副作用难以预测——在 map 里写 println! 或改全局状态，调用次数取决于下游消费者，换一个 take 或 collect 就变了。把副作用放进 for 循环体，通常是更诚实的选择。

另一个实际影响是「被消耗之后不能再用」：collect 会按值消耗迭代器，同一个 it 不能收集两次。想复用同一批数据，要么重新调用 v.iter() 构造新迭代器，要么先把结果收集成集合。这与「迭代器是游标而不是集合」的心智模型一致——它不代表数据本身，只代表一次遍历的过程。

7.5 适配器链如何消失：从 map/filter 到一个循环

迭代器之所以被称为「零成本抽象」，是因为适配器链在优化构建里会被完全内联掉。下面两个函数做同样的事：一个用迭代器链，一个手写循环。我们把它们编译成汇编，再数一数调用指令：

rustRust · 标准库21 行
#![crate_type = "lib"]
#![allow(dead_code)]
#[inline(never)]
pub fn iter_sum(v: &[i32]) -> i64 {
v.iter()
.copied()
.map(|x| x as i64 * 2)
.filter(|x| *x > 4)
.sum()
}
#[inline(never)]
pub fn loop_sum(v: &[i32]) -> i64 {
let mut s = 0i64;
for &x in v {
let y = x as i64 * 2;
if y > 4 { s += y; }
}
s
}
终端真跑一遍
$ rustc --edition 2021 -O --emit asm u07_b5.rs -o u07_b5.s
$ grep -c 'call' u07_b5.s
0
$ grep -c 'Map\|Filter\|next' u07_b5.s
0
$ grep -c '^\.LBB' u07_b5.s
12

三个数字合在一起说明问题：汇编里没有任何 call 指令，也没有 Map、Filter、next 这样的符号残留，只剩下本地跳转标签（循环与分支）。迭代器适配器的每个 next() 都被内联展开，闭包体被直接嵌进循环体，最终产物与手写循环同一量级——LLVM 甚至可能对其中一版做自动向量化，导致两边指令数不完全相同，但两者都不再有适配器开销。

适配器之所以能被内联，根源还是上一节讲的单态化：Map<I, F>、Filter<I, P> 都是泛型结构体，单态化后迭代器类型、闭包类型全都具体化，LLVM 能看到完整的调用图。#[inline] 提示在标准库里被大量使用，但多数情况下即使没有它，优化器也会因为「函数体很小且调用点固定」而自动内联。反过来说，若把谓词写成 &dyn Fn 或手工装箱，就重新引入了间接调用，零成本优势随之消失。

要复现这个实验，必须用 -O 或 Cargo 的 release 构建；debug 构建默认关优化，会保留大量 next() 调用，看起来「迭代器很慢」。这提醒我们：性能结论必须来自与实际发布配置一致的构建，而不是 debug 下的直觉。另一个测量陷阱是编译器可能把整个计算常量折叠掉——基准测试应当让输入来自运行时（例如命令行参数），并检查汇编里确实保留了循环。

大白话先用直觉把它讲通

适配器链像一条流水线，但 Rust 编译器在发布时会把整条流水线「压平」成一个工人从头做到尾——流水线上的站点（map、filter）只是源码里的描述，机器码里它们已经融进了同一个循环。所以你写的是「数据流」，机器跑的是「循环」，两全其美。

7.6 collect 与 FromIterator：目标类型驱动收集

collect() 是迭代器世界里的「出口」，但它的能力不来自 Iterator，而来自目标类型实现的 FromIterator。写法 let x: Target = iter.collect(); 中，类型是从赋值目标反推出来的；同一个迭代器可以收集成 Vec、HashSet、BTreeMap、String，甚至 Result——只要目标类型实现了对应 Item 的 FromIterator。

rustRust · 标准库27 行
use std::collections::HashMap;
#[derive(Debug)]
struct Pair(char, i32);
impl FromIterator<Pair> for HashMap<char, i32> {
fn from_iter<T: IntoIterator<Item = Pair>>(iter: T) -> Self {
let mut map = HashMap::new();
for Pair(k, v) in iter {
map.entry(k).and_modify(|acc| *acc += v).or_insert(v);
}
map
}
}
fn main() {
let pairs = vec![Pair('a', 1), Pair('b', 2), Pair('a', 3)];
let m: HashMap<char, i32> = pairs.into_iter().collect();
println!("a={:?} b={:?}", m.get(&'a'), m.get(&'b'));
let doubled: Vec<i32> = (1..=4).map(|x| x * 2).collect();
println!("doubled = {:?}", doubled);
let mixed: Vec<Result<i32, &str>> = vec![Ok(1), Err("x"), Ok(3)];
let short: Result<Vec<i32>, &str> = mixed.into_iter().collect();
println!("short-circuit = {:?}", short);
}
终端真跑一遍
$ rustc --edition 2021 u07_b6.rs -o u07_b6 && ./u07_b6
a=Some(4) b=Some(2)
doubled = [2, 4, 6, 8]
short-circuit = Err("x")

FromIterator 的签名决定了「一次调用完成聚合」，所以实现里通常用 fold 或循环累积状态，而不是在每次 next 时都分配新集合。自定义的 FromIterator<Pair> 把同字符的值累加，a 得到 1 + 3 = 4。这条 impl 之所以合法，是因为本地类型 Pair 出现在 trait 的类型参数位置，且它前面没有未覆盖的泛型参数——这正是孤儿规则所要求的「至少一个本地类型作为锚点」。它与标准库已有的 FromIterator<(K, V)> for HashMap<K, V> 不冲突，因为 Pair 和元组 (K, V) 是不同的 Item 类型。

FromIterator 的完整签名是 fn from_iter<T: IntoIterator<Item = A>>(iter: T) -> Self：它不要求传入的必须是 Iterator，任何能转成迭代器的容器都行。这个细节让 collect 的调用极其灵活，也带来一个常见困惑——当目标类型无法从上下文推断时，编译器会报「type annotations needed」，此时用 turbofish 写 collect::<Vec<i32>>() 或 collect::<BTreeSet<_>>() 即可消歧。

标准库里还有几个值得记住的实现：String: FromIterator<char> 与 String: FromIterator<&str> 让字符流直接拼成字符串；Option<V>: FromIterator<Option<A>>（其中 V: FromIterator<A>）在任一项为 None 时整体返回 None，是 Result 短路行为的 Option 版本；Iterator::unzip 则依赖 (A, B): FromIterator<(X, Y)>，把成对元素拆成两个集合。看到这些实现，就能理解为什么 collect 几乎能「变出」任何容器。

Result 的 FromIterator 尤其有用：它内部用 try_fold，遇到第一个 Err 就停止，所以 short-circuit = Err("x")，后面的 Ok(3) 根本没被收进结果。如果你在 collect::<Result<Vec<_>, _>>() 之后还手动过滤错误，说明没利用好这个机制。反过来说，若确实需要「收集全部成功项并列出所有错误」，就不能依赖这个短路行为，得自己分区处理——例如用 partition::<Result<_, _>, _> 拆成两个 Vec，或者手写循环同时累加。理解 FromIterator 的短路语义，也能解释为什么 try_fold 是迭代器家族里如此核心的方法：它是 find、try_for_each、collect::<Result<_,_>>() 等一众适配器的共同底座，内部用 ControlFlow 表达「继续」与「提前结束」。

7.7 size_hint、FusedIterator 与自定义迭代器

实现 Iterator 时只需提供 next()，但还有几个可选方法会影响性能与语义。size_hint() 返回 (下界, 上界)，collect 用它预分配容量；ExactSizeIterator 表示上下界精确等于剩余元素数；FusedIterator 承诺「一旦返回 None，以后永远返回 None」，让 last()、find() 等适配器能安全优化。

rustRust · 标准库28 行
struct Counter(u32);
impl Iterator for Counter {
type Item = u32;
fn next(&mut self) -> Option<u32> {
if self.0 < 3 {
let v = self.0;
self.0 += 1;
Some(v)
} else {
None
}
}
fn size_hint(&self) -> (usize, Option<usize>) {
let n = (3 - self.0) as usize;
(n, Some(n))
}
}
impl std::iter::FusedIterator for Counter {}
fn main() {
let c = Counter(0);
println!("size_hint = {:?}", c.size_hint());
println!("collect = {:?}", Counter(0).collect::<Vec<_>>());
println!("sum = {}", Counter(0).sum::<u32>());
println!("after 3 next = {:?}", Counter(0).last());
}

Counter 的 size_hint 上下界都是 3，因此 collect 可以一次分配好 3 个槽位。last() 之所以能直接一路 next 到底并记住最后一个值，与 FusedIterator 的承诺有关——不保证融合的迭代器在第一次 None 之后可能又吐出值，DoubleEndedIterator 等适配器需要区别对待。

写自定义迭代器时还有两个常见方法。DoubleEndedIterator 增加 next_back()，让 rev() 成为可能；它要求前后两个游标不会交叉，否则会重复或漏掉元素。ExactSizeIterator 是 Iterator 的子 trait，增加 len()，它要求 size_hint 的上下界相等且准确。实现这些方法能解锁更多适配器，但每个都是必须遵守的语义契约。

另外，示例里的 3 - self.0 在类型 u32 下有下溢风险：如果 next 在返回 None 之后又被误调用（或状态被外部破坏），表达式会 panic（debug）或回绕（release）。更稳健的写法是 (3u32).saturating_sub(self.0)。算法编里会大量遇到这类整数边界问题——usize 的下溢尤其隐蔽，因为代码看起来完全合理。自定义迭代器的另一个常见义务是「融合性」：标准迭代器在耗尽后再次调用 next 通常仍返回 None，你的实现也应如此，否则会在 zip、chain 等组合里出现意外行为。写单元测试时，除了验证元素序列，还要专门验证耗尽后的重复调用。

坑这里最容易踩

坑：size_hint 是给优化器的提示，不是正确性承诺。标准库不会因为下界是 3 就假定一定有 3 个元素，但你的 collect 性能会直接受它影响；写错上界只会让预分配不准，不会让结果出错。真正危险的是谎称实现了 FusedIterator 或 ExactSizeIterator：那是在向标准库承诺语义性质，违反它属于错误契约（尽管 trait 本身是 safe 的），会导致依赖该承诺的适配器行为异常。

7.8 工程取舍：迭代器、循环与借用冲突

用了这么多节讲迭代器，最后要回答的是「到底什么时候用它」。先说一个底层事实：for x in coll 会展开成 let mut it = IntoIterator::into_iter(coll); while let Some(x) = it.next() { ... }。所以 for 循环本身就是迭代器协议的使用者，二者不是对立关系——争的只是「要不要把处理步骤写成适配器链」。

一个高频坑是借用冲突：遍历 Vec 的同时往里 push，或者同时持有 iter() 和 iter_mut()，都会被借用检查器拒绝。这不是迭代器的限制，而是别名的硬规则——可变迭代要求对元素的独占访问，任何其他路径都不能同时活着。解决办法有三类：收集要新增的元素后一次性 extend；用索引循环（下标是整数，不借 Vec）；或者把需要修改的元素用 iter_mut() 一次遍历完成。

场景 推荐写法 理由
纯变换/过滤后收集 迭代器链 意图清晰，惰性且零成本
需要在循环里 ? 提前返回 for + ? 闭包里 ? 的类型和返回路径较绕
需要同时修改容器结构 索引循环或先收集再合并 绕开借用冲突
带复杂副作用/日志 for 循环 执行时机与次数一目了然
需要复用一段「处理流程」 自己实现 Iterator 把逻辑封装成可组合的适配器

还有一个性能上的细粒度考量：filter 之后紧跟 map 与 map 之后紧跟 filter，语义相同但闭包调用次数不同（对不满足谓词的元素是否执行 map）。在热路径上，把廉价筛选放在昂贵变换之前通常更快；但只有在剖析数据支持时才值得为此牺牲直觉。更一般的做法是相信优化器，先写清楚，再测瓶颈。

还有一条关于可读性的经验：一条链超过三四个适配器、或者闭包体超过两行，就该考虑拆成中间变量或独立函数。迭代器的优势在于「每一步都在说做什么」，一旦闭包里塞满控制流，这层清晰度就消失了。相反，简单到 iter().sum() 这种程度时，手写循环的样板代码反而成了噪音。迭代器的更大价值其实在于可组合性：一旦数据以 Iterator 形式流动，就能无缝切换到 rayon 的并行迭代器、接入 serde 的序列化流程，或用同一套适配器处理来自文件、网络、内存的不同来源——这是手写循环难以提供的抽象红利。

把整节串起来看，闭包提供了「把行为当值传递」的能力，捕获规则让它安全地携带环境；Fn 家族提供了调用能力的分层，使 API 能按需约束；迭代器则把「遍历」抽象成一个惰性状态机，让 map/filter 这类别名能够像乐高一样组合，又在优化后消融成最朴素的循环。三者共同构成 Rust 里最基本也最高频的抽象层——理解它们的机制，比记住几十个适配器方法有用得多。
