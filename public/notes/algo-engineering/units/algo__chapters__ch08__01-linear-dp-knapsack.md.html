8.1 先看工程长什么样

这一单元有四个例子工程。别急着看公式，先看文件：本节新增的是 examples/ch08/ 下的四个目录，以及三个清单、三份真实终端会话。第 1 帧是这一章开始时的草稿形态，第 2 帧是四个例子落地的形态，第 3 帧是补完清单与会话后的最终形态。

大白话先建立一个画面，再谈状态

把 DP 想成填一张表。表的每一格是一个小问题：「走到这一步、用掉这么多资源，最好能到什么程度」。你不可能凭空填出最后一格，但你可以从「已经填好的格子」推下一格。所谓状态定义，就是回答三件事：表格按什么顺序填（阶段）、每一格记什么（状态）、这一格从哪些格子抄过来（决策）。整套背包模板，本质上都是这张表的三种填法。

第 2 帧的四个目录对应四种「同一张表、不同填法」：LIS 的表按元素下标填；01 背包的表按「物品 × 容量」填但压成一行；多重背包把一件物品拆成几捆再压一行；方案数把「最大值」换成「计数」。第 3 帧里多出来的 session-*.txt 不是装饰——耗时每次都抖，进不了 output 块，只能抓成会话文件再用 file= 注入正文。注意第 3 帧里 knapsack_cpp 那一组：它是一份完整的 C++/STL 应用层程序，也参与 200 组对拍。

工程惯例工程惯例：为什么每个例子都要一个头文件

标准没有规定一个程序分几个文件。这里每个目录都把声明放进 include/*.h、定义放进 src/*.c（或 .cpp），驱动 main.c 只负责造数据、调用、打印。这么分有两个实打实的好处：一是你抄模板时只抄实现那一份，不会把实验代码带进赛场；二是头文件就是接缝，读一眼就知道算法「能做什么、不能做什么」。代价是多一次 #include 和 -Iinclude。本单元四个目录全部遵守，所以每个清单都列出至少两个源文件、并真的包含了项目内的头文件。

这一单元还故意把「错的版本」一起编进工程：knapsack_01 里有一份 trap_forward.c，它和正解只差一个循环方向；knapsack_scheme 同时算 long long 与 32 位回绕。为什么要留错版？因为正确性不能靠「我看着像对的」来保证。你在赛场上写出的代码，编译通过、样例过了，仍然可能是错的——本书第 2 单元讲过对拍的三件套，这里把它用起来：每一份正解都要有一份明显正确的暴力做裁判，200 组随机数据一组一组地比。读这一节时，建议你先看 main.c 弄清每组在比什么，再去看正解和暴力，最后才看注释里的论证。顺序反了，你会像背模板一样把结论记下来，却不知道它什么时候会失效。

八份清单里，五份输出 OK 200：LIS 两版与暴力、01 背包与子集枚举、完全与多重背包对三重循环、C++ 应用层对递归枚举、方案数对子集枚举。另外三份是性能与反例实验：它们不报 OK，而是把耗时打进 stderr，把可复现的结论留在 stdout——因为耗时每次都会抖，写进输出块会让逐字对账天天失败。这一层工程纪律和算法本身一样重要：它让你明天还能相信今天跑出来的数。

8.2 状态定义三件事：阶段、状态、决策

很多人背了一堆 DP 模板，碰到新题还是不会——问题不在模板，在于没把「状态」这事想清楚。任何一个线性 DP，动笔前先回答三句话。

语法规则状态定义的形式：三件事缺一不可
  1. 阶段：表的填表顺序是什么？通常是一个下标 i 从 1 走到 n，或者容量 c 从 0 走到 C。阶段必须保证「算当前格时，它依赖的格子已经算好」。
  2. 状态：dp[i]（或 dp[i][c]）里的那个数到底是什么？必须能一句话说完，而且是「到目前为止的最优值/方案数」，不能是「当前这一段的」。
  3. 决策：最后一刀怎么切？也就是「当前格从哪些已算好的格子转移过来，取 max 还是求和」。决策决定转移方程。

拿 LIS 举例。阶段是「扫描到第 i 个元素」；状态 f[i] 是「必须选 a[i] 结尾的最长上升子序列长度」；决策是「上一个被选的元素是谁」——枚举 j < i 且 a[j] < a[i]，于是 f[i] = 1 + max(f[j])。注意「必须结尾」这四个字：少了它，f[i] 就变成「前 i 个元素里的最优」，你再也写不出转移——因为你不知道那条最优序列是不是用到了 a[i]。

再看背包。阶段是「处理到第 i 件物品」；状态 dp[c] 是「容量不超过 c 时能拿到的最大价值」；决策是「第 i 件选还是不选」，于是 dp[c] = max(dp[c], dp[c - w[i]] + v[i])。把状态定义在「不超过」而不是「恰好」上，是初值能全填 0 的原因：装不满也算合法，价值 0 就是「什么都不选」。

写不出转移方程时，八成是状态定义出了问题，而不是数学不够。这里有三个能动手自查的信号。

第一，你没法用一句话说清 dp[i] 是什么。如果你发现自己在解释时说「它是这一步的最优，但也可能是那一步的最优」，那状态就混了。LIS 里必须补上「以 a[i] 结尾」这几个字，背包里必须补上「容量不超过 c」，少一个限定词，转移就会凭空多出你没算过的格子。

第二，转移里出现了还没算过的格子。比如你把 f[i] 定义成「前 i 个元素的 LIS 长度」，想写 f[i] = f[i-1] + 1，可当 a[i] 不能接在最优序列后面时这个式子是错的——你根本不知道 f[i-1] 那条序列的结尾是什么。把状态改定义为「必须以 i 结尾」，依赖就全部落在 j<i 上，方程立刻成立。这种「改一个限定词，方程从错变对」的经历，比背十个模板都管用。

第三，状态和循环方向互相打架。压缩空间时尤其明显：01 背包压成一行靠倒序，完全背包压成一行靠正序，两者代码只差一个符号。可见状态不只是数组里存什么，还包括你打算按什么顺序更新它。把这两件事一起写进注释，才不会在赛后复盘时看不懂自己写的代码。

回头看 8.2 第 1 帧的 DAG：箭头方向就是阶段顺序，拓扑序就是填表顺序。如果你画不出那张图，或者画出来的图有环，那基本可以断定状态定义要重来。LCS 的二维表为什么能滚成两行？因为它的箭头只从第 i-1 行与本行左边格指向当前格，所有箭头朝同一个方向。方案数为什么要留整张表？因为你要沿箭头反向走回去还原方案，箭头走过就找不到了。

8.3 LIS：两版答案与 lower_bound 的真正含义

最长上升子序列（LIS）是理解「状态」与「优化」关系的最好例子：同一道题，状态定义不变，只换一种「表格压缩方式」，复杂度就从 O(n²) 掉到 O(n log n)。

大白话LIS 到底在找什么

给你一串数，从里面挑出一些（可以不连续，但顺序不能变），要求后面的严格比前面的大，问最多能挑几个。比如 2 2 3 1 3 4：严格版本只能挑 3 个（2 3 4 或 1 3 4），因为两个 2 不能同时要；如果把「上升」放宽成「不下降」，就能挑 5 个（2 2 3 3 4）。「严格」和「非严格」的差别，全在能不能接受相等的那一下，这一下会改变你用的是 lower_bound 还是 upper_bound。

现在看对数版。它把「以 i 结尾」这个状态压缩掉了：不再给每个 i 留一格，而是维护一个短得多的 tails 数组。

语法规则lower_bound 与 upper_bound 在这里到底找什么
  • lower_bound(tails, len, x) 返回第一个 >= x 的位置；严格 LIS 用它，因为相等的元素不能接在后面，必须顶掉那个相等值。
  • upper_bound(tails, len, x) 返回第一个 > x 的位置；非严格 LIS 用它，因为相等的元素可以接在后面，必须跳过所有相等值、找一个更大的来替换。
  • 记法：strict ? (t[mid] < x) : (t[mid] <= x)。条件为真就把左端点右移；两个版本只差「< 还是 <=」这一个字符，但答案可以差很多（演示里的 3 与 5）。

现在写正确性论证。这是本单元最该认真读的一段，因为 tails 的写法太短，短到很多人背下来却讲不出为什么对。

不变式：处理完前 i 个元素后，对任意 k（0 ≤ k < len），tails[k] 等于「在前 i 个元素中，所有长度为 k+1 的合法上升子序列里，末尾元素的最小可能值」。

初始化：i=0 时 len=0，不变式对空集合平凡成立。

归纳步：来了一个新元素 x = a[i]，设 pos = lis_bound(tails, len, x)。

  • 若 pos > 0：由二分定义，tails[pos-1] 是「第一个不小于（或大于）x 的位置的前一格」，严格版里 tails[pos-1] < x。于是把 tails[pos-1] 对应的那条长度 pos 的子序列接上 x，得到一条长度 pos+1 的子序列，末尾是 x。而 tails[pos] 原本是长度 pos+1 里末尾最小值，现在 x <= tails[pos]（严格版由 lower_bound 定义保证；非严格版由 upper_bound 保证 x < tails[pos]），所以用 x 覆盖 tails[pos] 只会让末尾更小，不变式保持。
  • 若 pos == 0：说明 x 比所有已有末尾都小（或都不大于），它自己就能构成长度 1 的子序列，且末尾最小，覆盖 tails[0] 正确。
  • 若 pos == len：说明 x 比所有已有末尾都大（严格版）或都不小于（非严格版），它接在长度 len 的那条最优序列后面，构成长度 len+1 的新序列，于是 len 加一。

还要证明 tails 始终是升序的（否则二分不成立）。覆盖发生在 pos，而 tails[pos-1] < x <= tails[pos+1]（严格版）或 tails[pos-1] <= x < tails[pos+1]（非严格版），所以覆盖后仍有 tails[pos-1] < tails[pos] <= tails[pos+1]。归纳成立。

终止：len 就是整个数组里合法上升子序列的最大长度。为什么不会漏？因为不变式说的是「每个长度只保留末尾最小的那一条」，而末尾越小越容易被后面的元素接上——丢掉的那些「同长度但末尾更大」的序列，不可能产生比保留下来的更长的答案。∎

这个证明里最容易被跳过的一步，是「tails 为什么升序」。不妨单独拎出来讲：二分的前提是数组有序，若 tails 不是升序的，lis_bound 找到的位置就没有意义，整套 O(n log n) 会静默给出错误答案。上面的归纳步里，覆盖发生在 pos，而 pos 的定义保证 tails[pos-1] < x（严格版）与 x <= tails[pos+1]，两个不等式夹住新值，所以覆盖之后局部仍然有序，其他位置没动，全局有序。实践里把严格版与非严格版的判定写反，第一处破坏的就是这条升序性质——这也是对拍用重复值能立刻抓到它的原因。

再看一个常被问到的问题：既然 tails 只存末尾最小值，它自己是一条真实的子序列吗？答案是 tails 这个数组通常不是原数组的合法子序列，它只是若干个「长度为 k 的最优末尾」的摘要。例如 a = 2 1 3，处理完三个数后 tails = [1, 3]，恰好是子序列；换一组数据就未必。所以别试图从 tails 里读出方案——要方案就得像 8.7 那样另外记 pre。这和 LCS 的滚动数组是同一条纪律：压掉的是还原方案所需的信息，不是算答案所需的信息。

工程惯例工程惯例：n=1e5 时别再写平方版

复杂度表不是背的，是拿来反推写法的。n=1e5 时 O(n²) 要做 5e9 次量级的操作，本机实测 n=8e3 已经要 36 ms，按平方外推到 1e5 就是秒级甚至更差，而 O(n log n) 实测只要 2.80 ms，差了三个数量级，不是常数能补回来的。反过来，n≤20 时暴力枚举 2^n 反而最省事：写错的风险最低，跑完只要几毫秒。正确的工程判断是「看 n 选写法」，而不是「永远写最优复杂度」。

为什么暴力版不能省？因为它是唯一不依赖「我对状态的理解」的裁判。平方版和对数版都建立在同一个状态定义上：如果我把「上升」理解成「不下降」，两版会一起给出偏大的答案，而且彼此完全一致——对到这里谁也发现不了错。暴力版直接枚举所有子序列，它不关心你怎么定义状态，只认题目原话。本单元把值域压到 0..12 再跑 200 组，就是为了制造大量相等相邻值，让「严格与不严格」的分歧频繁出现。写对拍时请记住：裁判和选手不能共享同一个可能出错的前提，否则两千组 OK 也只是共同犯错。

三份 output 块与三份 term 块的分工再强调一次：output 是程序 stdout 的逐字副本，由清单在闸门里逐行对账，所以它只能放确定量；term 是真实终端记录的副本，命令那一行以 $ 开头，耗时、编译诊断这类会抖的东西放这里。你若把毫秒数塞进 output，明天重跑时闸门就会报 stale_output；你若把输出编造出来而不从真跑的程序回写，同样过不了对账。本单元所有数字都按这个纪律处理，写作者能做的只剩「跑、抓、填」。

边界也别放过：n = 0 时三版都应该返回 0，而不是崩溃或返回 1。平方版与对数版在源码里显式处理了空数组，暴力版因为 dfs 一开始 i == n == 0 也会正确返回 0。但如果你把状态写成「以 i 结尾」却让循环从 1 开始、数组按 1 基存，很容易在读 a[0] 时越界。本单元所有实现统一用 0 基，只有输出给读者看的方案编号才转成 1 基——一个程序里只能选一种下标口径，混用是比写错方程更常见的静默错误。

陷阱你怎么会被坑到：把 lower_bound 和 upper_bound 用反了

你会看到什么？样例里有一串带重复的数，你写的「严格 LIS」却把两个相同元素都选了进去，答案比暴力版大 1。你会怎么误判？多半会怀疑边界条件写错，或者去改 < 的方向。真相是：严格版该用 lower_bound（第一个 >= x），非严格版该用 upper_bound（第一个 > x）。用反了，严格版会放过相等元素、非严格版会拒绝相等元素，恰好反过来。本单元的对拍把值域故意压到 0..12，让重复成为常态——这就是为什么 200 组能揪出这个只差一个字符的 bug。

8.4 LCS：二维表与滚动数组

LCS（最长公共子序列）是「二维状态 + 可以压成一维」的标准样本。给你两个串 A 和 B，问最长的、同时在两者中按顺序出现的子序列有多长。

状态定义照 8.2 的三件事走：阶段是「A 的前 i 个字符、B 的前 j 个字符」；状态 dp[i][j] 是「这两个前缀的 LCS 长度」；决策看最后一个字符——

  • 若 A[i-1] == B[j-1]，那么这两个字符可以配对，dp[i][j] = dp[i-1][j-1] + 1；
  • 否则它们不可能同时被用上，dp[i][j] = max(dp[i-1][j], dp[i][j-1])。

边界是 dp[0][*] = dp[*][0] = 0：空串和任何串的 LCS 都是 0。这里不能把不可达写成别的含义，因为 0 本来就是正确答案。

这张表用一张小图看一眼就懂。取 A = "ab", B = "ba"，答案应该是 1：

第 1、2 帧是二维表：每格只从「左上、上、左」三个方向来，所以按行从左到右填就行。第 3 帧是滚动数组的关键——因为第 i 行只依赖第 i-1 行和本行左边那一格，dp 的两维完全可以压成两行 old 与 cur。空间从 O(|A||B|) 降到 O(|B|)，代价是你再也拿不回完整表格。

于是有一条判断准则：只问长度，可以滚动；要还原具体方案，就得留二维表（或者额外记 pre）。8.7 的字典序方案就是留了整张后缀表才还原出来的。LCS 这里不建独立工程，用上面这张小图验证转移即可；你若想自己确认，把 A="ab"、B="ba" 手算一遍，答案必为 1。

LCS 的递推为什么成立，值得补一句交换论证。若 A[i-1] == B[j-1]，这两个字符一定能同时出现在某条最优解里：取任意一条最优公共子序列，若它没用这对相等字符，就把对应位置的值换成这个相等字符，长度不变且仍合法，所以存在一条用到它们的解，长度就是 dp[i-1][j-1]+1。若两者不等，它们不可能同时被用上——子序列要保序，一旦 A[i-1] 被选，它在 A 里已经是最后一个，B[j-1] 在其后却不可能配对；于是最优解要么不用 A[i-1]（长度不超过 dp[i-1][j]），要么不用 B[j-1]（长度不超过 dp[i][j-1]），取两者最大即可。

把 A="ab"、B="ba" 手填一遍能验证图里的四格：dp[1][1]=0（a 与 b 不等，取 dp[0][1] 与 dp[1][0] 的最大值 0）；dp[1][2]=1（a 与 a 相等，dp[0][1]+1=1）；dp[2][1]=1（b 与 b 相等）；dp[2][2]=1（b 与 a 不等，两个候选都是 1）。所以答案是 1，任何声称是 2 的实现都把「子序列」当成了「子集」——子序列必须保序，a 在 A 里排在 b 前面，在 B 里却排在后面，不能同时选。这个例子很小，却把 LCS 与 LIS 的根本区别钉住了：LIS 只排自己的顺序，LCS 要同时照顾两个顺序。 滚成两行时最容易踩的坑是覆盖顺序。算当前行第 j 格要读 old[j]（上一行同列）与 cur[j-1]（本行左邻），所以 j 必须从左到右更新；若写成倒序，cur[j-1] 还是上一轮的旧值，答案会静默变小。另一个坑是忘记在每行开始把 cur[0] 置 0，上一行遗留的值会被当成合法前缀。这两处都不会让程序崩，只会让答案偏小一两格，靠样例很难发现，最好的防线是拿小数据跟二维版逐格比对。

什么情况下不能滚动？三种：要还原具体方案；要查询任意 (i,j) 的历史值；转移依赖不止上一行（比如依赖 dp[i-2][j]，或者既要 i-1 行又要 i-2 行）。8.7 属于第一种——它要沿 pre 走回整条方案，所以老老实实留了 (n+1) × (target+1) 的表。空间换的是可还原性，不是浪费。

8.5 01 背包：倒序为什么每件只选一次

现在进入背包。先把最核心的一句话记住：01 背包的倒序不是风格问题，是正确性本身。

大白话01 背包在问什么

有一堆物品，每件有重量 w[i] 和价值 v[i]，每件事至多拿一次，背包容量 C，问最多能装多少价值。把「每件事至多一次」翻译成 DP，就是状态 dp[c] = 「容量不超过 c 能拿到的最大价值」。关键在更新顺序：同一件物品，你不能让自己刚算出来的结果再去帮自己一次。

正确性论证（不变式）。设 dp_old[c] 是开始处理第 i 件物品之前数组里的内容，它只由前 i-1 件物品决定。循环从 c = cap 递减到 w[i]。当处理某个 c 时，比 c 小的容量 c - w[i] 还没被本轮碰到（因为我们是从大到小走的），所以 dp[c - w[i]] 此刻等于 dp_old[c - w[i]]。于是这一行更新恰好是

dp_new[c] = max(dp_old[c], dp_old[c - w[i]] + v[i]),

前者对应「不选第 i 件」，后者对应「选第 i 件」。两个候选都只用旧值，所以第 i 件在整个第 i 轮里只被考虑一次。归纳完成：处理完第 i 件后，dp[c] 是「前 i 件里容量不超过 c 的最优值」。∀ i 成立，故最后 dp[cap] 就是答案。∎

陷阱陷阱三连：容量 0、-INF 与「不可达」

你会看到什么？同样是背包，dp 初值有时全填 0，有时全填 -INF，填错了样例还能过。你会怎么误判？以为这只是两种风格。真相是它们在回答两个不同的问题：

  • 容量 0：dp[0] 必须是 0（什么都不选），循环里 w[i] > 0 时它不会被更新。本例演示里容量 0 输出 0，就是这条边界在起作用。若你有一个重量为 0 且价值为正的物品，倒序循环 for (c = cap; c >= 0; c--) 会把它加一次（正确），但循环写成 c > 0 就会漏掉 c=0——另一个静默 bug。
  • 「不超过」用 0：dp[c] 表示容量不超过 c 的最大价值，装不满也算合法，所以全 0 是对的。
  • 「恰好装满」用 -INF：如果题目要求「重量必须恰好等于 C」，那么 dp[c] 全 0 会把「装不满的 0」误当成「装满且价值 0」。正确做法是 dp[0] = 0、其余 -INF，转移前先判 dp[c-w[i]] 是否可达。8.7 的方案数用 long long 装真值、用 -1 表示不可达，正是同一条纪律。
陷阱你怎么会被坑到：1 基题面遇上 0 基数组

题目给的编号常常是 1..n，C 数组却是 0..n-1。三种写法都合法：读入时统一减一、数组开 n+1 保留 0 空着、或者全程序按题面写。但一个程序只能选一种。 本单元的正解、暴力、对拍驱动全部 0 基，只在打印方案时把内部编号 i 写成 i+1。混用的症状很讨厌：结果有时对有时错，加一行打印就变好，因为内存布局被改了。若在方案还原里把 pre 记录的容量当成物品编号读，也会得到一串看似合理却完全错误的序列——对拍比三个维度（计数、价值、序列）正是为了堵住这种错。

8.6 完全背包、多重背包与分组背包

把 8.5 的循环方向反过来，01 背包就变成了完全背包——同一份代码，语义完全相反。

记忆这三种背包有个对偶的抓手：倒序是「不许回头」，正序是「允许回头」。01 背包里每件物品只有一份，用掉就没有了，所以算大容量时不能去读刚被自己改过的小容量；完全背包里每件物品有无限份，算大容量时读小容量里那份「已经含了本件」的结果，恰好等于再拿一件。多重背包卡在中间，要么把有限份拆成若干「不许回头」的捆，要么用窗口把有限份直接限制住。把这句话写在模板旁边，比死记循环方向可靠。

大白话三种背包的差别只有一句话

01：每件至多一次；完全：每件无限次；多重：第 i 件至多 cnt[i] 次。既然状态 dp[c] 一模一样，差别只能落在「第 i 件被允许用几次」上，而这件事恰好由容量循环的方向控制：倒序读旧值 → 一次；正序读新值 → 可以无限次。

为什么正序对完全背包是对的？设处理第 i 件时，dp[c - w[i]] 已经在本轮被更新，它可能是「选了 k 次第 i 件的最优值」，那么再加一次 v[i] 就得到「选了 k+1 次」；由于 c 从小到大走，k 可以一直累加到容量装不下为止。不变式改成「处理完第 i 件后，dp[c] 是前 i 件各取任意次的最优值」即可，证明与 8.5 同构，只是「旧值」换成了「本轮已含本件的值」。

多重背包介于两者之间。最朴素的写法是给第 i 件真的枚举「选 k 件」（0 ≤ k ≤ cnt[i]），再做一次 01 更新：

for i: copy dp → prev; for k ≤ cnt[i]: for c 从 cap 倒序: dp[c] = max(dp[c], prev[c-k*w]+k*v)

这里有个容易忽略的坑：必须从上一层的 prev 读。如果直接从本层 dp 读，k=1 和 k=2 两次更新会叠加成「选了三件」，计数直接越限——我在写这个对拍基准时就踩了一次，200 组第 0 组就报出 三重=450 / 二进制=355，追下去才发现是基准在骗自己。暴力版必须写得明显正确，否则对拍只会把两个人一起带沟里。

语法规则二进制拆分：把 cnt 件拆成几捆 01 物品

把 cnt 写成 1 + 2 + 4 + ... + 余数：例如 cnt = 13 拆成 1, 2, 4, 6，cnt = 5 拆成 1, 2, 2。每一捆看成「一件新物品」，重量 k*w、价值 k*v，然后跑 01 背包的倒序循环。 为什么够用？因为 1,2,4,...,2^m 能拼出 0..2^(m+1)-1 的任意整数，最后一捆把剩下的余数补上，就覆盖了 0..cnt 的所有取法。捆数从 cnt 降到 O(log cnt)。

陷阱你怎么会被坑到：二进制拆分丢了余数

你会看到什么？cnt 是 2 的幂减一时一切正常（7 = 1+2+4），换成 cnt = 5 答案就偏小。你会怎么误判？以为拆分公式写错了。真相是：循环写成 for (p = 1; p <= cnt; p <<= 1) 会把 p=8 > 5 那一档也做进去，或者写成「只拆完整的 1,2,4」把剩下的 1 丢掉——两种情况都覆盖不到 0..cnt。正解就是上面第 14 行那句 k = (p < left) ? p : left：不够一整块时，把剩下的全部作为最后一捆。

二进制拆分已经够快，但它是 O(n * cap * log cnt)。多重背包还有 O(n * cap) 的单调队列优化。把容量按 w 取模分成若干类，在同一类里令 c = r + j*w，转移可以改写成：

dp[r+j*w] = max_{t ∈ [j-cnt, j]} ( dp[r+t*w] - t*v ) + j*v

括号里那一坨只依赖 t，j*v 是常量。于是对每个余数类维护一个「最大值在队首」的双端队列，j 每前进一格就入队一个新值、把过期下标弹掉，每个 j 进出各一次：

注意第 28 行读的是本轮更新前的 dp[r+j*w]（因为 j 递增，当前格还没被写过），这是这个写法成立的前提。另外 cnt[i] * w[i] >= cap 时件数已经足够，直接退化成完全背包的正序写法更快（实现里就是这个分支）。

分组背包是另一种常见变体：物品被分成若干组，每组至多选一件。做法是把阶段改成「处理到第 g 组」，状态仍是 dp[c]，决策变成「这一组选哪一件、或者不选」：

for g: for c 从 cap 倒序: for 每件 i 属于 g: if c>=w[i]: dp[c] = max(dp[c], dp[c-w[i]]+v[i])

容量循环必须在物品循环外面且倒序——否则同一组的两件会被先后选上。记住这个形状就行，它本质上还是 01 背包的「倒序保旧值」。

单调队列那段的式子值得多写两句，否则很容易变成背模板。把 c = r + j*w（0 ≤ r < w）代入转移，得到 max_{k ≤ j} ( dp[r+k*w] - (j-k)*v )，再限制 j-k ≤ cnt。拆开括号就是 max_{k ∈ [j-cnt, j]} ( dp[r+k*w] - k*v ) + j*v。左边那一坨只跟 k 有关，是关于 k 的一个滑动窗口最大值，窗口右端随 j 右移，左端是 j-cnt。于是用双端队列维护候选 k：新元素进来前，把队尾所有不大于新值的弹掉（它们永远不可能成为最大值），再把下标小于 j-cnt 的队首弹掉（过期）。每个 k 最多进队一次、出队一次，这一层是 O(cap/w)，所有余数类加起来 O(cap)，与 cnt 无关。这正是它比二进制拆分快的根源——二进制拆分的代价里有个 log cnt。

陷阱你怎么会被坑到：单调队列里读了本轮已改的值

你会看到什么？单调队列版在小数据上对拍全过，容量一大答案就偏大。你会怎么误判？以为窗口边界写错了。真相是上面代码里计算 val = dp[r+j*w] - j*vi 的那一行：如果那个格子已经被本轮某次更新写过，你读到的就不是上一层的值，窗口最大值会被自己刚写的结果抬高。正确写法是 j 递增、同一余数类从前往后扫，当前格在被写之前先读。另一个细节：cnt*w >= cap 时件数已经足够，直接按完全背包正序做即可，省掉队列的常数——这条分支在完整实现里，别漏掉。

分组背包再补一句：它的「每组至多一件」用一维数组实现时，容量循环必须在物品循环外面。写成「每组 → 组内每件 → 容量倒序」会让同一组的多件被依次选上，因为下一件读到的 dp[c-w] 已经含了上一件。正确顺序是「每组 → 容量倒序 → 组内每件」，这样更新当前组时读到的 dp[c-w] 还是进入本组之前的值——和 01 背包的倒序不变式是同一件事，只是多了一层枚举。

8.7 方案数与字典序最小方案

最后一类问题不问「最大是多少」，而问「有几种方案」以及「哪套方案字典序最小」。这两问各有一个新坑。

方案数：把 DP 的 max 换成 +。ways[c] 表示「恰好装到重量 c 的方案数」，初值 ways[0] = 1（什么都不选是装到 0 的唯一方案），其余 0；每件物品倒序累加 ways[c] += ways[c-w[i]]。倒序的理由与 8.5 完全相同：同一件不能贡献两次。

陷阱你怎么会被坑到：int 装不下方案数

你会看到什么？小规模上 int ways[] 和暴力数出来的方案数一模一样，规模稍微上去，方案数突然变成一个莫名其妙的小正数甚至负数。你会怎么误判？以为是倒序写错。真相是方案数增长比价值快得多：40 件重量为 1 的物品，恰好装满 20 的方案数是组合数 C(40,20) = 137846528820，早已超过 32 位有符号上限。示例里特意同时算了 long long 与 32 位无符号两版：真值 137846528820，截断到 32 位后回绕成 407575348——把无符号按有符号读就是错的。这里用无符号回绕演示是因为无符号溢出是标准定义好的；int 溢出是未定义行为，编译器有权假设它不发生，连「回绕成某个值」都不能保证。方案数、组合数一律 long long 起步，必要时取模。

字典序最小方案：先用后缀 DP 算出 f[i][c]（只用第 i..n-1 件、恰好装到 c 的最大价值），再贪心从编号小的物品往大走：只要「取第 i 件」仍能达到最优值，就取它。这给出的是编号序列字典序最小的一套——因为越早的编号进了方案，序列的第一处差异就越小。平局时也要取（代码里的 cand >= b），这正是字典序的要求。

方案数的初始化为什么是 ways[0] = 1 而不是 0？用归纳看最清楚：处理完 0 件物品时，恰好装到重量 0 的方案只有一种——什么都不选；恰好装到其他重量的方案数是 0。每加入一件重量 w 的物品，新的 ways[c] 由两部分组成：不选它（ways[c] 原值）与选它（ways[c-w] 原值），两者相加。倒序更新保证第二部分读到的还是加入这件之前的数，于是新方案恰好计入一次。这个递推和组合数的杨辉三角是同一回事：40 件重量 1 的物品装满 20，方案数就是 C(40,20)，也就是杨辉三角第 40 行第 20 列。理解到这一层，你就不用背「方案数把 max 换成 +」这句口诀了。

pre 数组还有个容易忽略的细节：它记的是「取这件之前的容量」，不是「上一件物品的编号」。还原时每一步都要用当前 c 去查 pre[i][c]，再把 c 更新成查到的值；如果误把它当成前驱编号直接跳，你会跳过中间的容量，得到一条不存在的方案。另外平局判定必须用 cand >= b 而不是 cand > b：只有平局时也选「取」，才能保证越小的编号越早进方案，这正是字典序最小的来源。把这两个细节写进注释，比事后对着错误序列调试便宜得多。

target=5 恰好装满的两套方案是「1+4」和「2+3」，价值都是 50。字典序更小的是 1 4——第一处差异就赢在编号 1 上，这正是平局时取小编号的效果。

把 8.7 的两件事合起来看，会发现它们其实是同一张状态表的三种问法。最大价值版问「最优是多少」，方案数版问「有多少条路达到目标」，字典序版问「这些路里哪条字典序最小」。三者的阶段与状态完全一样，只把决策的合并方式从 max 换成 + 或「记录选择」。所以真正要练的不是背三套模板，而是看到题目问法时能迅速决定用哪种合并。

字典序贪心为什么对，补一个简短证明。设 S 是所有能达到最优价值且恰好装满 target 的方案集合，把每个方案的编号序列按升序写好。从编号 0 开始：若存在某个 S 中的方案包含它，就固定下来，只在剩余后缀里继续；否则跳过。这个决策不会降低最优值，因为「包含它」的前提就是仍有最优方案；而任何不包含它的方案，在第一处与包含它的方案比较时必然更大，因为当前编号比后面能取到的任何编号都小。归纳下去得到的就是字典序最小的一套。pre[i][c] 只是把「是否包含 i」这个判定记下来，还原时不必重算。

小结这一节的要点
  • 状态定义三件事：阶段（填表顺序）、状态（每格记什么）、决策（从哪些格转移）；状态必须一句话说完；
  • LIS 对数版的 tails[k] 是「长度 k+1 的合法子序列里末尾最小的值」，用归纳法证明它始终升序、且不会产生更差的答案；严格用 lower_bound、非严格用 upper_bound；
  • LCS 的二维表只依赖上一行和本行左边，可以滚成两行；要还原方案就得留二维表或 pre；
  • 01 背包倒序的不变式：c 递减时 dp[c-w] 还是旧值，所以每件只选一次；正序把同一段代码变成完全背包，真反例算出 12 而不是 6；
  • 多重背包二进制拆分必须带余数；单调队列把转移写成窗口最大值，复杂度从 O(n·C·log cnt) 降到 O(n·C)；分组背包的容量循环要在物品循环外且倒序；
  • 方案数把 max 换成 +，int 装不下（C(40,20) 真值 137846528820，32 位回绕成 407575348）；字典序最小方案用后缀 DP + pre，平局时取小编号；
  • 不可达用 -INF 而不是 0；「不超过」的初值全 0、「恰好装满」的初值只有 dp[0]=0；
  • 三份 OK 200 与三份真抓会话构成本单元的对拍与实测证据。

注自测题答案
  1. 严格用 lower_bound（第一个 >= x），因为相等元素不能接在后面，必须顶掉相等值；非严格用 upper_bound（第一个 > x），因为相等元素可以接，要跳过所有相等值找更大的替换。用反会让严格版接受相等、非严格版拒绝相等。
  2. 不变式：处理第 i 件前 dp[c] 只含前 i-1 件。倒序时 c-w[i] < c 尚未被本轮改写，读到的仍是旧值，于是 dp[c] = max(旧 dp[c], 旧 dp[c-w]+v) 恰好是「不选/选第 i 件」两个互不重叠的候选。正序时 dp[c-w] 已含第 i 件，再加一次 v 就是选两次；真反例是单件 w=2、v=6、容量 4，正解 6、错解 12。
  3. tails[k] 是「目前见过的、长度 k+1 的合法上升子序列里，末尾元素的最小可能值」。末尾越小越容易被后续元素接上，所以同长度里末尾更大的序列不可能导出更长的答案，丢掉它们不会损失最优性；同时这个最小性保证 tails 升序，二分才合法。
  4. 13 = 1 + 2 + 4 + 6，拆成重量为 1w, 2w, 4w, 6w 的四捆。只拆 1,2,4,8 会超出 cnt（8 > 13 的余数处理不对），或者只取 1,2,4,8 中会拼出超过 13 件的组合，覆盖的取法集合不再是 0..13。
  5. LCS 只问长度，第 i 行只依赖第 i-1 行和本行左边一格，可以滚成 old/cur 两行；字典序方案要沿 pre[i][c] 从后往前还原整套编号，一旦丢掉中间行的 pre 就走不回去了。
  6. 方案数增长极快：40 件重量 1 的物品恰好装满 20 的方案数是 C(40,20)=137846528820，超过 2^31-1；int 溢出是未定义行为，连回绕值都不保证。本单元用无符号 32 位安全演示回绕成 407575348，把它按有符号读或直接塞进 int 都是错的。
  7. 「不可达」必须用 -INF：0 会被当成「可达且价值 0」，与「装不满也算合法」混淆。但「容量不超过 c 的最大价值」这个问题里，装不满本来就是合法方案、价值 0，所以初值全 0 正确；只有「恰好装满」才需要 dp[0]=0、其余 -INF。
