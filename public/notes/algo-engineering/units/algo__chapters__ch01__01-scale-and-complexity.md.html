1.1 先看工程长什么样

从这一单元起，你进入《算法》分册。这个分册回答的问题只有一类：同一道题，为什么有人 2 秒跑完、有人 2 秒跑不完。答案不在语法里，在「工作量随 n 怎么长」里。但空谈 O(n)、O(n²) 没有意义——本分册的规矩是：每一个复杂度结论，都要落到本机真实耗时上。所以第 1 单元不教算法，先教两件事：把「时间」变成可测量的东西，把「能过」变成一张对得上的表。

这一单元是后面 27 个单元的地基，值得花整节课的力气。学法只有一条：每个数字都是跑出来的，每个数字你都能自己重跑。三个探针程序就躺在仓库里，正文引用它们的每一行耗时，你都可以用同一份代码、同一条命令在机器上复现——这正是「算法」这门课和「背模板」的区别：模板告诉你怎么做，规模表告诉你什么该做、什么做了一定死。

工程惯例工程惯例：耗时为什么永远打 stderr，不进 stdout

三个探针都守同一条纪律：stdout 只放跨次逐字稳定的量（校验和、计数、OK 200），耗时一律打到 stderr。原因是流水线对账：正文里的 output 块要和程序 stdout 逐字一致，耗时每次差几毫秒，混进去对账天天失败。代价是你看耗时要多敲一个重定向——./app 2>&1 >/dev/null——换来的是「输出块永远干净」。这条纪律后面每个单元都用。

1.2 时间的单位：一秒能做多少次基本运算

所有「能不能过」的判断，最后都要折算成一句话：这道题的工作量，乘上每一步的成本，够不够 1 秒。所以先把尺子造出来：本机做一次「最便宜的操作」要多久。

大白话基本运算是什么

把 CPU 想成一个手速极快但一次只干一件小事的工人：把两个数相加、比较大小、从内存搬一个数，各算一件小事。「基本运算」就是这件小事的计量单位。复杂度分析里「这条算法要做 1e8 次基本运算」，意思就是「工人要干 1 亿件小事」。工人一秒能干几件小事？不同的小事手速不一样——这正是本节要量出来的。

为什么选「乘加」当标尺，而不是「一条指令」？因为「一条指令」根本不是一把稳定的尺子：同样是一次加法，操作数在寄存器里和在内存里价格不同；一次除法比一次加法贵几十倍；现代 CPU 一条 SIMD 指令一口气算 8 个 int。「指令」这个词太杂，量不出统一的价。乘加的立场是：它是所有算法里最普通、最常见的那件小事——每一次比较、每一次状态转移、每一次循环体，折开看都是一两件这种量级的事。标尺的意义不在精确，在可比：所有复杂度都折成「乘加的倍数」，彼此就能比较了。

尺子有三个要求：够便宜（它是最普通的操作，别用特殊指令）、结果被使用（否则编译器有权把整个循环删掉）、可重复（同一份数据跑一万次结果一样）。probe_muladd 就是这把尺子：

「1 秒 ≈ 10 亿」这条标尺值得单独交代来历。十年前的教材普遍写「1 秒 ≈ 1 亿次」——那是老评测机的实测；今天的家用机器轻轻松松越过 10 亿，评测机也跟着水涨船高。本分册取 10 亿这条中间线：本机实测（17 亿乘加/秒）比它乐观，但它留了三层保险——评测机单核比你本机慢、题目往往有多组数据（预算要除以组数）、你的算法每步比探针重。标尺宁紧勿松：按 10 亿估出来「勉强能过」的写法，实际就是过不了。

两个心算例题，把标尺用起来。例一：n=1e6 的双重循环（n² = 1e12 次）——1e12 ÷ 1e9 = 1000 秒，必死，平方档最多撑到 n≈3e4；例二：n=1e6 的「每层一个 log」的循环（约 2e7 次）——2e7 ÷ 1e9 = 0.02 秒，随便过，甚至 n=1e8 都还有富余。两道除法做完，「该写什么复杂度」就不是感觉了。附一张体感表，把时间单位换成本机的「能做的事」：

还有最后一件事要交代：为什么后面所有实验都写「三次取值」而不是单个数。这台机器上跑着的杀毒扫描、系统更新、别的进程随时会来抢几毫秒 CPU，一次运行撞上了，读数就虚高；CPU 还会在冷热之间漂（刚开机和跑热了频率不同）。单个读数会撒谎，区间不会——所以本分册每个耗时都给三次运行的区间，会话文件里存的是其中一次的原文。你复现时如果落在区间之外（比如慢了一个量级），先查后台，再怀疑代码。

工程惯例工程惯例：-O2 是默认优化级，实测必须带它

本分册所有清单的 flags 都带 -O2——竞赛评测机的真实环境就是开优化的。不开优化的实测数字会比真实情况慢 2~4 倍（1.7 有逐项对照），拿它去套规模表会误判一批「其实能过」的算法。代价是：开优化之后，编译器有权改写甚至删掉你「没用到结果」的代码——所以探针的校验和必须真的被打印，这句话后面每个实验都适用。

1.3 从 n 反推算法：规模表是怎么量出来的

大白话复杂度在数什么

复杂度不问「一步要几纳秒」，只问「步数随 n 怎么长」。n 翻 10 倍，如果步数也翻 10 倍，它是线性 O(n)；如果翻 100 倍，它是平方 O(n²)；如果只翻一点点（约 1.1 倍不到），它带 log。数清楚了步数，再拿 1.2 的标尺一除，「能不能过」就出来了。

大 O 记号还有一条隐藏条款要知道：它扔掉常数。O(2n) 写成 O(n)，O(4n²) 写成 O(n²)——在「步数怎么长」这个问题上 2 倍、4 倍不重要，长法才重要。这条条款让复杂度分析变得清爽（不用纠结循环里到底几句话），但也埋下本单元反复出现的主题：复杂度相同，实测可以差 20 倍——被扔掉的常数没有消失，它们在 1.4 和 1.7 排队等你。所以本分册的口号是：大 O 负责「选型」，实测负责「验收」，两张纸缺一不可。

每一档的边界都不是随手画的，逐档看一眼为什么：

  • n ≤ 20 → 状压与搜索。2²⁰ = 1048576，一个 int 的 20 个位刚好一枚举一状态；配上每个状态 O(n) 或 O(n²) 的转移，工作量在几百万到几亿之间——标尺量得动，指数算法在这里是「正解」不是「暴力」。n=21 时 2²¹ 翻倍、n=22 再翻倍，1e6 级别的状态数一下顶到 4e6、8e6，配上重转移就开始贴预算线——所以指数算法的身份证就是 n ≤ 20（个别 22）。
  • n ≤ 500 → 三方。500³ = 1.25 亿次判定，实测 24.5–25.0 ms，睡得香；600³ 就是 2.16 亿、1000³ 是 10 亿——后者只留 0.05 秒余量，翻车只在弹指间。
  • n ≤ 5000 → 平方。5000² 的一半是 1250 万对，实测 4.8–5.2 ms；n=1e4 就 1 亿对（约 20 ms），n=1e5 是 50 亿对——2 秒出头，必死（本节末尾实测为证）。
  • n ≤ 1e5 → n log n。1e5 次「分半」只叠 17 层，工作量 1e5×17 ≈ 170 万次比较——比平方档便宜 15 倍。排序、分治、堆、平衡树全是这一档的住户。
  • n ≤ 1e6 → 线性。1e6 次访问实测 0.2 ms；连 1e7 都只要 2.2 ms——线性算法是唯一「n 越大越敢写」的档。

拿一道真实场景把「反推」走一遍。题目说 n ≤ 3000，要你判断每对点之间是否满足某个关系。三步：第一步查表——n=3000 落在平方档（n≤5000）；第二步算账——3000² 的一半是 450 万对，按标尺 0.0045 秒，就算每步成本是探针的 20 倍也只有 0.09 秒，平方写法能过；第三步想更好的——如果这个问题有单调性或可排序结构，双指针能压到线性；没有的话，平方就是正解，不必强求。反过来，如果题目给 n ≤ 1e6，三步的结论就变成：平方是 5000 亿对必死、n log n 是 2e7 次从容——必须想出 log 级的做法。同一道题，n 一变，答案从「暴力也行」翻脸成「暴力必死」，这就是这张表存在的意义。

你会看到有人说「1 秒能跑 1e8 次，所以 n=1e4 的平方能过」——然后你在自己的机器上交了一发 TLE。你会怎么误判：怀疑标尺错了，或者怀疑机器。真相是：规模表给的是安全档，不是边界。1 秒的真实预算在不同评测机上能差好几倍；真实算法每步的成本是探针的好几倍（探针只做一次比较，你的算法每步要比较、要下标、要写答案）；题目经常一组输入里塞多个 n。所以本分册的表永远留出几倍到几十倍余量——「n≤5000 平方」的意思是平方档在这个规模下睡得着觉，不是「n=5001 必死」。

这张表还有第二个用法：TLE 排查的第一反应。交了一发超时，别急着卡常，先做题：读题面的 n 和时限定档位（n=1e6？线性或 nlogn），再估算你的写法工作量（两层循环套一层 map？工作量 1e6×log×每步几条指针），一除——差 10 倍以上的，卡常救不了，换算法；差 2 倍以内的，才轮到 1.7 的常数手段。这个顺序的反面教材是：在平方写法上花两小时卡常，而 n=1e6 的平方根本不可能过——账没算，方向就是错的。本分册后面每个单元都会给出它那个算法的档位和实测，就是在帮你把这张表一格格填厚。

1.4 缓存行：机器按 64 字节搬，不按 int 搬

1.2 的标尺里藏着一个没解释的怪事：乘加每步 0.58 ns，顺序读 int 每步只要 0.22 ns——读内存比做乘法还便宜？ 对，只要你是「顺序」读。这一节把内存的真实价格表量出来。

先把这台机器的内存层级摆出来。离 CPU 计算单元最近的叫寄存器，零距离，和计算同速；外面套一层 L1 缓存，再外面 L2、L3，最外圈才是内存条。越近的越小越快，越远的越大越慢——L1 通常几十 KB、L3 几 MB 到几十 MB、内存以 GB 计，价格差从几倍到上百倍。你的数组 99% 的时间躺在内存条里，CPU 能这么快地用它们，全靠中间这几层缓存提前把数据搬近。本单元不背各级时延的教科书数字（每个机型都不同），只量两件可复现的事：顺序访问的真实价格和乱序访问的真实价格——上一节那个 0.22 ns 就是顺序价格的实测。

大白话缓存行是什么

CPU 和内存之间隔着一层小仓库（缓存）。仓库进货不按个进，按箱进：一箱固定 64 字节，叫一条缓存行。你要 1 个 int（4 字节），机器把含着它的整条 64 字节都搬进来。如果你接着用旁边的 int，它们已经在箱子里了，白送；如果你跳走了，刚才那一箱等于白搬。顺序访问为什么 0.22 ns？因为 16 个 int 共享一条搬运。

填充也讲究：数组不是 memset 清零随便糊弄的——全 0 的数组会让某些访问模式「看起来」比真实快（分支可预测、值全是同一个，硬件的各种猜测全中）。所以探针用固定种子的 LCG 把 64 MB 填成真随机值：每个分支、每次访存都要面对不可预测的数据，量出来的才是算法自己的成本。这也是所有基准测试的第一戒律：数据像真的，数字才像真的。

还有一处要诚实交代：gather 的 5.7–7.2 ns 看起来仍然「太快了」——体系结构教科书上「去内存取一个数」的裸延迟常写上百纳秒，为什么这里只要 6 ns？因为 CPU 是乱序执行的：这一批随机访问之间谁也不等谁，硬件同时挂着十几条在途的访问，单条的裸延迟被十几条并行摊薄了。什么时候教科书数字才会现出原形？访问之间有依赖的时候——链表沿指针走、树从根往下摸、map 一层层比较，每一次访问的地址都由上一次的结果决定，想并行也并行不了，那一跳就是实打实的裸延迟。1.7 讲 map 的账时用的是「每跳 ≈ 一次随机访问」的保守折算，理由就在这里：独立的随机访问便宜，依赖的随机访问贵——写算法时能改成前者就别写成后者。

三个推论值得单独立正：① 复杂度数的是「访问次数」，机器收钱按「缓存行条数」——两个账本对不上时，以机器的为准；② 同样是 O(n) 的两个算法，访问模式不同，实测能差 20 倍，这就是 1.7「常数」的第一个来源；③ 一切「指针跳来跳去」的结构（链表、树、map）每次都是一次随机访问，起步价 6 ns 左右——后面讲数据结构选型时，这个数是判决书。

推论 ③ 还有一个更日常的化身：vector 和普通数组赢在内存连续。1e6 个 int 存在数组里是 4 MB 连续内存，顺序扫一遍 0.2 ms；存在 map（红黑树）里是 100 万个散落在堆各处的节点，每个节点还要带三个指针——就算都是「遍历一遍」，前者按行流水搬运，后者一百万次随机访问。这就是为什么本分册反复强调「数组是第一数据结构」：不是它功能强，是它天生坐在缓存友好的位置上。后面各单元大量「数组模拟 X」的写法（数组栈、数组堆、链式前向星），全部出自这一个理由。

「数据摆放」落到写法上就是两个字母的选择：AoS（结构体数组，每个点的 x、y、权值挨在一起）还是 SoA（每个字段一个数组）。如果算法每次只用一个字段扫全表，SoA 的每条缓存行装的全是有用数据；AoS 的一行里三个字段只有你要的那个有用，等于每行浪费三分之二搬运。反过来，如果每次都要一个点的全部字段，AoS 一行全到位、SoA 要跳三处。判据永远是一句话：让一条 64 字节的缓存行里装满这一次访问真正要用的东西。竞赛代码的绝大多数场景是「整表扫描单字段」（vis 数组、dist 数组），所以分册默认把字段拆成独立数组——现在你知道这不是代码洁癖，是在给 1.4 的价格表省钱。

陷阱你怎么会被坑到：「我访问的元素少，所以快」

你会看到：把循环从「每步 +1」改成「每步 +64」，访问次数少 64 倍，心想这下快了。跑起来发现几乎没快（本机：3.67 ms 对 1.11 ms，只快三倍）——你会怎么误判：以为优化无效、编译器偷懒。真相是：你省下的是 63 次白送的访问，留下的是每一次最贵的搬运。缓存行的世界里，省时间靠的是「把相关的数据放在一起」，不是「少碰几个数」。体现在写法上：优先顺序扫描、下标数组连续存放、别把大数组按列跳着访。

1.5 均摊：把扩容的大账摊到每次压入

规模表回答「选什么复杂度」，但有一类结论它给不了：vector.push_back 单次最多要搬整个数组，为什么书上敢标 O(1)？这类「单次很贵、平均很便宜」的账，叫均摊。

大白话均摊是什么

均摊就是分期还贷。买房一次性掏 100 万掏不起，摊到 30 年每月几千块就付得起。vector 扩容也一样：第 2、4、8、16…次压入时「搬一次家」，单次最贵；但把全部搬家的总账摊到每一次压入头上，每次平均只摊到一两件搬运。均摊 O(1) 说的是长期平均，不是每一次都便宜。

「均摊」和「平均」是两回事，值得花一句话分清。平均是对随机输入取期望——快排的平均复杂度 O(n log n) 说的就是「随机数据下期望这么快，特定数据可以把它拖到平方」；均摊是对最坏输入序列把总账除以操作数——不管你的压入序列多倒霉，n 次压入的总搬运就是不到 2n，谁也拖不坏它。所以「快排平均 O(n log n)」前面要挂「随机」两个字，而「vector 均摊 O(1)」不需要任何前提。赛场上前者要警惕构造数据，后者可以闭眼信。

第二条路径不开缓冲，从 n 直接推公式。推导只有两步：容量从 1 开始翻倍，扩容发生在 size 等于 0、1、2、4、…、2^(k−1) 的时刻，所以总拷贝是 1+2+4+…+2^(k−1)；等比数列求和，等于 2^k − 1，其中 2^k 是不小于 n 的最小的 2 的幂。等比求和有个一看就懂的记法：最后一项占了一半——1+2+4+…+2^(k−1) 里，2^(k−1) 一项就等于前面所有项的总和加 1，所以总和永远不到 2^k。这条「最后一段占一半」的直觉值得留下，后面分析堆的建堆复杂度、并查集的摊还时全是它的变体。

因为 2^k < 2n（它是「不小于 n 的最小 2 的幂」，至多是 n 的两倍不到），所以总拷贝 2^k − 1 < 2n——这就是「均摊 O(1)」的完整证明：n 次压入至多搬不到 2n 个元素，摊下来每次不到 2 次。第三条路径是反例策略：容量不够就 +16。它的总账也有闭式：扩容发生在 size = 16, 32, 64, … 处，共约 n/16 次，每次搬走全部旧元素，总拷贝 ≈ n²/(2×16)——平方级。n=20000 时两条账分别是 32767 对 12490000，差 381 倍，等下在 stdout 里见：

reserve 那两行值得多说一句。reserve(n) 的含义是「我知道我要装 n 个，现在就把缓冲一次开够」——之后的所有 push_back 都不再触发扩容，账本上那一列「搬运」直接清零。实测里它把 1e7 次 push_back 从 21.7–24.4 ms 压到 11.8–13.1 ms：省掉的不是理论，是真金白银的一次性搬运。什么时候该用？只要 n 在压入之前已知（读完了数据、题目给了上限），先 reserve 是免费的保险；什么时候不能帮上忙？n 只能边走边知道时（比如 BFS 逐层发现新点），那就靠翻倍策略自己兜底——好在它的均摊保证够硬。注意 reserve 只管容量不管大小，reserve 之后 size() 还是 0，要用下标访问的话先 resize——两个函数名字长得像，干的活差一层。

陷阱你怎么会被坑到：公式背对了，n=1 时算错

账本公式 2^k − 1 背起来很顺，一上手就在边界翻车。n=1 时 k=0，总拷贝是 0 不是 1——第一次扩容从 0 到 1，没有旧元素可搬；n=0 时连扩容都不会发生，三项统计全是 0。你会怎么误判：写验证时发现「模拟 0、公式 1」对不上，以为模拟错了，其实公式忘了 n=1。另一个方向更隐蔽：均摊 O(1) 不等于每次 O(1)——第 2^k 次压入那一发要搬整个数组，单次最坏 O(n)。写实时性敏感的代码（比如中断处理）别用它，老老实实 reserve 或者用定长数组。同样的账本第 5 单元还会再算一次：并查集的路径压缩也是「单次最坏、均摊近似常数」，证明结构一模一样。

1.6 空间：256MB 能开多少个 int

时间表立完了，还有半张表：空间。绝大多数题目的内存限制是 256MB，它限的不是「你的数组多大」，是你同时活着的所有东西加起来多大——数组、递归栈、标准库容器全算在内。三个 1e7 的 int 数组各自合法，挤在一个进程里就是 120 MB，再叠两个 1e7 的 long long 就贴线了——MLE 的判罚对象是总量，不是最大的那个数组。

大白话空间复杂度在数什么

和时间一样，空间复杂度不数「多少字节」，数「格子数随 n 怎么长」。一维 dp 数组是 O(n)，二维表是 O(n²)，递归每层占一个栈帧、深度为 n 的递归是 O(n) 的栈空间。数完格子乘上每格的字节（int 4 字节、long long 8 字节），才落到「多少 MB」——所以空间账永远比时间账多一步乘法，也多一类错误：忘乘字节。

算术只有一步：256MB = 256×1024×1024 字节 = 268435456 字节。它和 1.4 的实测互相印证：cache_effect 那 64 MB 数组就是 16777216 个 int——16M×4B 正好 64 MB，sizeof(int)=4 在本机不是查书查来的，是探针真开出来的。

你想开的东西 占用 256MB 限额下
int（4 字节，本机实测） 1e7 个 = 40MB 最多约 6.7e7 个
long long（8 字节） 1e7 个 = 80MB 最多约 3.3e7 个
两个 1e7 的 int 数组 80MB 从容（本单元最大数组 64MB，占限额 1/4）
1e8 个 int 400MB 必炸，还没开始算就已经 MLE
pair<int,int>（8 字节） 1e6 个 = 8MB 便宜，1e7 个也才 80MB

三个推论：① n≤1e7 的 int 数组随便开，1e8 就要想想滚动数组或离线；② 把 int 换成 long long，能开的个数立刻减半——别给不需要 9 位数的量用 long long；③ 递归也吃内存：本机可执行文件默认栈保留 2MB，递归深度几万层就会把进程杀死（第 5 单元会实测这个边界）。

两个实战演算，把表格用熟。演算一：DP 题给 n=5000，想开二维 dp[5005][5005] 的 int——5005×5005×4 字节 ≈ 1 亿字节 = 100 MB，256MB 限额下放得下，但再叠一个同尺寸数组就 200MB，贴着天花板；改 long long 直接 200MB 一个——所以二维 DP 的类型选择是空间题，不是时间题。演算二：图论题 n=1e6、m=5e6，链式前向星的三个数组（to、next 各 int 4 字节 + head）——(2×5e6+1e6)×4 = 44 MB，安全；如果手滑把边数组开成 long long 的 pair（16 字节一条），就是 80 MB——没炸，但预算被吃掉三分之一，后面再加 dist 数组就开始紧张。字节是攒出来的，也是省出来的。

陷阱你怎么会被坑到：用 int 存「1e18」级别的中间量

你会看到：算 n×(n−1)/2（比如数点对），n=1e5 时答案是 4999950000——你用 int 接，打印出来是个负数。你会怎么误判：以为乘法写错了。真相是 int 的上限只有约 2.1e9（2³¹−1），4999950000 早爆了。这类「中间量」到处都是：平方档的工作量（n=1e6 时 5e11 对）、估算耗时的「次数×纳秒」（1e8 次×1e4ns = 1e12ns）、大题的答案本身。规矩只有一条：只要数字可能超过 21 亿，一律 long long；long long 的上限约 9.2e18，n(n−1)/2 在 n=1e9 时约 5e17，装得下；1e18 本身也装得下——但再往上（比如两数相乘各自 1e9）就该想想取模了。mid = (l + r) / 2 里的 l+r 是同一类坑，第 8 单元展开。

陷阱你怎么会被坑到：memset 0x3f 当无穷大，一加就溢出

「求最小值时把数组 memset 成无穷大」是标准操作，常见写法是 memset(dp, 0x3f, sizeof dp)——它给每个字节填 0x3f，一个 int 就变成 0x3f3f3f3f = 1061109567。选 0x3f 不选 0x7f 是算过账的：两个 0x3f3f3f3f 相加等于 2122219134，还没越过 int 的上限 2147483647，INF + w 这类式子安全；但三个相加就变成 3183328701，溢出成负数 −1111638595——最短路里「松弛两次」的路径一对，负数会一路污染后面的答案。你会怎么误判：样例能过（样例里路径短，攒不出三个 INF），大数据上答案莫名其妙偏小。真相是：0x3f 只担保「加两次」，转移式里可能出现 INF+INF+w 的题（如 Floyd 三重取 min）要么用 long long 装 0x3f3f3f3f3f3f3f3f，要么把松弛写成 if (INF + w < 0) 跳过。顺带：0x7f7f7f7f = 2139062143，两个相加就溢出，比 0x3f 危险得多。

空间和时间是唯一能互相兑换的一对货币，两种方向的兑换都要认得。拿空间换时间：前缀和多开一个 n 的数组，把每次区间求和从 O(n) 压到 O(1)——多花 4 MB，省下的是每次查询百万次加法（第 4 单元的主角）；拿时间换空间：滚动数组只留两行，把 O(n²) 空间压到 O(n)，代价是写法上多一轮覆盖逻辑、且丢掉了「中间各行」的复用可能。竞赛里前一种更常见（内存限制宽松、时间紧），后一种在 n 特别大、DP 表格只依赖上一行时是救命的。判断顺序永远是：先按 1.3 选复杂度（时间），再用本节的算术检查空间装不装得下（空间），装不下才动兑换的手术——顺序反了会为了省 40 MB 把 O(n log n) 硬改成 O(n²)，得不偿失。

工程惯例工程惯例：开数组之前，先写注释算字节数

竞赛代码里最便宜的保险，是在数组声明旁边写一行字节数注释：int dp[5005][5005]; // 100MB。写不出这个数的题，说明你还没想清规模——那正是出错的前夜。代价是多写一行注释，收益是「声明即自检」：一看注释超了 256MB，立刻回头想滚动数组，而不是在评测机上等一个 MLE。

1.7 常数：同一个复杂度为什么能差好几倍

到 1.4 为止你已经见过两个 O(n) 差 20 倍（0.2 ns 对 4.2 ns）。复杂度相同、实测不同的差距叫常数。它不是玄学，来源可以列全——本机实测逐个对号。

第一个来源是优化等级。同一份 scale_probe，把 -O2 摘掉换 -O0 再跑：

两件事值得看：乘加几乎没快——它每一步依赖上一步的 h，属于「延迟瓶颈」，优化器再聪明也得等乘法算完；线性扫描快了 3.6 倍——顺序求和能被向量化成一路算 8~16 个 int。qsort 只快 1.5 倍是因为排序本体在运行库里，早就编译好了，你的代码只有比较器。结论：优化级平均值在 2~4 倍，但瓶颈在依赖链上的代码优化帮不上忙——这也解释了为什么「换个更快的公式」往往比「卡常」有用。

第二个来源是 1.4 的内存访问模式（实测最高 20 倍）：顺序 0.2 ns、步长 64 是 4.1–4.8 ns、完全随机 5.7–7.2 ns。写算法时每一步「访问什么」是自己选的——先排序再扫描、把相邻的量放进同一个数组、用连续的 vector 代替节点链，都是在给这一项打折。

第三个来源是间接层数。用 map 存 1e6 个数和用数组存，账面复杂度是「查询 O(log n) 对 O(1)」，真实差距更大：map 的底层是红黑树，一次查询要跳两三层指针，每一跳都是 1.4 实测过的一次随机访问（5.7–7.2 ns 起步），一次查询 20 ns 打不住；数组一次顺序命中 0.2 ns——同一件事上百倍。这不是说 map 不该用（键不是连续整数时它是首选），而是说：键明明是 0 到 n−1 的整数时，用 map 是在白白给每个查询加两层指针。第 2 单元起你会反复看到「数组模拟」替代各种花哨结构的写法，判决书就是这个数。

第四个来源是分支预测。CPU 执行指令走流水线：第一条还没算完，第二条已经在路上。遇到 if，它不等你算完就猜一个方向先往下走，猜对了流水线满速，猜错了整段推倒重来。所以同一段代码，分支走向「有规律」（比如数据已排序，if (a[i] < x) 前半段全真后半段全假）和「完全乱跳」，实测能差出数倍——编译器看不到数据，帮不了你；第 3 单元讲排序时会在「随机/有序/全相同」三种数据上把这个差距量成表。

第五个来源是包装层的间接调用，代表人物是 std::function。它是个「能装下任何可调用物」的盒子：装函数指针、装 lambda、装带捕获的闭包都行。方便的代价在看不见的地方——每次调用要经过一层间接跳转，闭包带捕获时数据可能被搬到堆上，一次「调用」背后藏着一两次 1.4 量过的随机访问。在只会被调用几次的地方，这些成本无所谓；把它塞进内层循环（比如「每次比较都调一个 function」的排序比较器），一百万次间接调用就是实打实的几毫秒。竞赛代码的写法要么直接写函数，要么用模板把类型在编译期定死——间接层留给真正需要它的接口处。

  1. 因为两件事的「每一步」根本不是一回事。乘加的下一步依赖上一步的结果（h 要先算出来才能算下一个 h），是一条串行依赖链，每步都要等乘法延迟；顺序求和被编译器向量化，一条指令算 8~16 个 int，还和预取配合。所以「复杂度相同」只保证步数同阶，每步的价格由依赖结构和访存模式决定。
  2. n 从 5000 到 8000 乘 1.6，平方档时间乘 1.6² = 2.56，5 ms×2.56 ≈ 13 ms。依据是平方律：工作量 ∝ n²。用另一对实测数据也能验证：n=1e4 是 19.5–20.5 ms，正好是 n=5000 的 4 倍。
  3. 缓存行，64 字节，装 16 个 int。你只用了 4 字节，机器为它搬了整条 64 字节——步长 64 的每一次访问都强制一条新缓存行，中间 15 个 int 的位置全部白搬。
  4. 从 12490000 降到 32767，约 381 倍。+16 的总拷贝 ≈ n²/32（O(n²) 量级，千万级）；倍增的总拷贝是 2^k−1 = 32767（O(n) 量级，几万级），因为 1+2+4+…+2^(k−1) 被「最后一段占一半」的等比结构压住了。
  5. 不保证。均摊 O(1) 是长期平均：恰好在容量翻倍的那一次（size 等于 2 的幂时），这一发要搬走全部旧元素，单次最坏 O(n)。n=1e7 的扩容那一发要搬约 800 万个元素。要每次都快，先 reserve。
  6. 三个 0x3f3f3f3f 相加是 3183328701，超过 int 上限 2147483647，溢出成负数 −1111638595，这个「比 0 还小」的假无穷大会在后续取 min 时污染答案。两个相加是 2122219134，刚好没越界——0x3f 的设计初衷就是「只担保两次相加」。要加三次以上，换 long long 的 0x3f3f3f3f3f3f3f3f，或者改写转移避免 INF 参与加法。
