4.1 先看工程长什么样

上一单元（前缀和与差分）解决的是「静态数组上反复问区间」；这一单元换成「一段活着的区间上反复问」——区间在动，答案跟着动。双指针的全部内容可以压缩成一句话：两个下标都不回头，每个下标一生至多被扫两次，所以是线性。这句话反过来也是它的死穴：一旦「不回头」会丢解（有负数、数组无序、窗口里的量不单调），这套招就不能用。本单元用三个例子把「什么时候能用、什么时候会错」讲透，每个例子都是「正解 + 暴力 + 对拍」三件套，另配一份 C++ STL 应用层（4.7）。

三个例子各占一种「指针形态」，合起来是这类题的完整地图：

  • 相向双指针（两数之和）：两个指针从两端往中间走，每一步丢掉「被证明没戏」的一端——它对数组有序性有硬要求；
  • 收缩窗口（无重复最长子串）：右端扩张、左端条件触发收缩，两端都不回头——它对窗口摘要的可增量维护有要求；
  • 计数窗口（最小覆盖子串）：同上，但合法条件是「需要的字符凑够个数」，摘要从「计数 ≤1」升级成「两张计数表加一个 missing 计数器」。

看懂这三个，赛场上再遇到「最长 / 最短的一段」「成对出现」「覆盖要求」之类的题，你先问自己的就不是「套哪个模板」，而是「我的摘要能不能 O(1) 增量维护、我的指针凭什么敢不回头」——这两个问题答不上来，模板就是空中楼阁。

大白话这一节想让你先建立一个画面

把窗口想成一条橡皮筋套在数组上，右端被人拉着往右走：

  • 右端扩张：每吞进一个新元素，用 O(1) 的时间更新窗口的摘要（计数、和、最值……）；
  • 左端收缩：橡皮筋太松（多装了没用的东西）或者破了（出现重复、缺了必需品），左端就往右退，把不要的元素吐出去；
  • 每吞一次、吐一次，答案就抄一次。

「双指针」听起来像两根指针在跳舞，其实是一根在前面探路、一根在后面打扫——前面进多少，后面总共出多少，谁也不回头。

三个例子里的「摘要」各不相同，看清这一点，窗口题就不再是一堆模板：两数之和的摘要最省事——就两个数本身（窗口的两端），和直接可读；无重复窗口的摘要是一张计数表，合法条件「全 ≤1」；覆盖窗口的摘要是两张表加一个 missing 整数。摘要越贵，每格的常数越大——但只要摘要能 O(1) 增量维护，线性就不受影响。

工程惯例工程惯例：暴力必须「不看任何性质」

三个例子的暴力都有一个共同点：不利用任何有序性、不变式或数学性质——两数之和的暴力把每一对 (i, j) 都比一遍，窗口两题的暴力从每个左端老实数到不合法为止。这是对拍可信的前提：如果暴力也偷偷用了「窗口无重复」这条性质，那正解和暴力共享同一个假设，假设错了它们一起错。

代价是暴力慢（本节三份暴力分别在 n=3e4、n=2e4、n=1e6 上量过耗时，见 4.6 的表），所以对拍数据要小——alg02 的结论在这里原样成立：对拍找反例，不做压测。另一个代价是写暴力也要认真：它不能「随手写个大概」，下标范围、边界条件（n=0、m=0、空窗口）都得经得起推敲——裁判自己先错，整场对拍就是空转。本节三份暴力都通过了同一套 200 组数据的检验，而它们彼此的实现路径完全不同，这正是「两个证人比一个证词可信」的工程化表达。

六帧连起来看有两个值得注意的节奏。第一，两个指针加起来只动了六次，跟「每轮区间严格缩一格」的论证完全吻合——没有任何一步是试探性的「先动一下看看」，每一步的方向都被当前和与 target 的大小关系唯一决定。第二，帧 2 与帧 3 之间有个容易忽略的转折：和从「偏小」变成「偏大」的那一轮，移动的指针从 l 换成了 r——同一轮里只有一个指针动，不存在「两边都动一步试试」的犹豫，这正是引理给我们的底气：偏小说明左端没戏（动 l），偏大说明右端没戏（动 r），两件事不会同时成立。

为什么对。把「丢弃」写成一条引理，正确性就是一步归纳。设当前窗口是 [l, r]（数组升序）：

  • 若 a[l] + a[r] < target 而 l 右移：对窗口里任何 j ≤ r，a[l] + a[j] ≤ a[l] + a[r] < target——a[l] 与窗口里谁也配不成对，丢它不丢解；窗口右边（下标 > r）的元素在更早的轮次里被丢过，每一次丢弃当时都带着同样的证明。
  • 若 a[l] + a[r] > target 而 r 左移：对称地，对任何 i ≥ l，a[i] + a[r] ≥ a[l] + a[r] > target——a[r] 与谁也配不成。

于是不变式是：每一轮开始时，「若原数组存在解，则解（或一对解）仍落在当前窗口 [l, r] 内」。按归纳的三段式把它说全：

  • 基础步：第一轮之前窗口是整个数组，若解存在它当然在窗口里——显然成立；
  • 保持步：从一轮到下一轮，被移出窗口的恰好是那一个下标（l 或 r），丢弃引理保证了「它不属于任何解」——窗口里剩下的解（如果原来有）不会少；
  • 终止态：l < r 不再成立时窗口里至多剩一个元素，配不成对；由不变式反证——若原数组有解，此刻它应当还在窗口里，但窗口装不下两个下标，矛盾。所以报 0（无解）也不会错。

再看复杂度，这笔账比直觉更硬：每轮循环 r - l 严格减 1（要么 l 加一、要么 r 减一，不可能原地打转），初值 n - 1，所以循环至多 n - 1 轮，每轮常数次操作——扫描是 O(n)。加上前面的排序 O(n log n)，整个算法 O(n log n)，瓶颈在排序而不在指针。左指针只前进不回退，就是线性扫描的全部秘密：它把「枚举所有对」的 O(n²) 变成了「每个元素至多被看常数次」。这个论证模式值得记住——4.3、4.4 的窗口收缩用的是同一招，只是「窗口」从两个端点换成了一条橡皮筋，「严格减 1」换成了「两端合计至多走 2n 格」。

把这个判断标准推广成一张自查清单——「这道题敢不敢用双指针」，问三个问题：一问单调性：我的丢弃引理依赖什么性质？两数之和靠「两端是窗口最值」（排序给的），窗口收缩靠「合法性可以增量修复」（计数给的）——性质不存在，指针就不敢动。二问摘要：窗口从 r-1 到 r，我的摘要（和、计数、最值）能 O(1) 更新吗？求和可以（加减一个数），计数可以（增减一格），最值不行（元素离开窗口时，次大值不知道是谁——那要单调队列，第 4 单元的活）。三问负向元素：窗口里的量有负数吗？「和为 target 的滑动窗口最短子串」在含负数的数组上，左端收缩的条件不再单调（去掉一个负数反而让和变大），左右指针都会失去「只进不退」的依据——这道题的正确解法是前缀和加单调队列，第 9 单元会讲到工具，这里先记住结论：有负数的窗口最短和，不是滑动窗口的菜。

陷阱你怎么会被坑到：样例全对、随机数据一片 WA

忘排序的双指针有个阴险的性格：样例经常能过。样例数据往往比较「巧」——比如全正数且大致递增，乱序双指针也能撞上答案。你会误判成「边界写错了」「下标搞混了」，把 l < r 改成 l <= r、把初值 n - 1 改成 n，越改越乱。真相是：丢弃引理依赖「两端分别是窗口的最小值和最大值」，这一条只有排序才给得了。查法只有一条：拿一组带负数的乱序数据对拍，比如本节的 5 -9 4 12 3，暴力说有解而你说无解，一眼定位。修法也是一条：进函数之前先 qsort，或者把「已排序」写进接口注释当前置条件——本单元的 tps.h 第 3 行就是这么写的。比「忘了排序」更隐蔽的变体是「排了，但排的是副本」：函数里 qsort 传进去的是另一个数组的指针，原数组纹丝没动——对拍的数据是每个现造的还看不出来，一旦数据被多个函数共享就当场穿帮。把「谁负责排序」固定在一个位置（读入后立刻排，或接口契约里写死），两种变体一起防住。

语法规则滑动窗口循环的三个约定
  1. 右端每轮前进一格：for (r = 0; r < n; r++)，扩张永远是主循环——左端不是循环变量，是被收缩推着走的。
  2. 收缩到「恰好合法」为止：while (cnt[c] > 1) 的退出条件就是「不合法刚被修好」。多收一格浪费，少收一格窗口带着病继续走，后面全错。
  3. 收缩时计数同步递减：离开窗口的字符要把 cnt 减回去——窗口的摘要必须始终反映窗口里真实的东西。

为什么对，为什么是 O(n)。 不变式两条，先把它们写成能检验的句子：I1——收缩完成后，窗口 [l, r] 内无重复（cnt 全部 ≤ 1）；I2——l 是「以 r 为右端的无重复窗口」里最靠右的合法左端，也就是「再往左一格就一定有重复」。

按归纳三段式过一遍。基础步：r = 0 时窗口 [0, 0] 只有一个字符，无重复，l = 0 也是唯一可能的左端——I1、I2 成立。保持步：r 前进一格，先扩张后收缩。扩张可能引入重复（而且至多引入一个：只有新来的 c 计数变 2），收缩循环把多余副本逐格挤出去——每收一格，离开窗口的那个字符计数减一，摘要始终如实反映窗口；退出时 cnt[c] 回到 1，I1 恢复。I2 呢？收缩停在「c 的计数恰好回到 1」的那一格——注意重复的来源只有 c 自己（窗口里其他字符的计数都没动过、仍 ≤ 1），所以退出时的 l 再往左一格，c 就会回到 2，窗口必坏：这个 l 是不能再往左的合法左端，I2 保持。终止态：所有 r 都处理完，best 是逐个 r 的 r - l + 1 的最大值，而每个 r - l + 1 由 I2 保证是「以 r 结尾的无重复子串里最长的」。

漏解问题最后堵一次口：任何无重复子串都有某个右端点 r0，而「以 r0 结尾的无重复子串」中最长的那个长度就是 r0 - l(r0) + 1——它 ≥ 我们要找的那条子串的长度。所以对每个 r 取最大值不会漏掉全局答案。帧 1 到帧 4 里每一次收缩，都是 I2 在说「这一格不能再让了」。

复杂度是均摊的账，记到每个字符头上：一个字符一生只有两件事——进窗一次（r 扫到它，cnt 加一）、出窗一次（l 收缩越过它，cnt 减一）。r 严格前进 n 格没有悬念；l 看起来被 while 推着走很多次，但 l 从不清零、从不回退，一生也走不过 n 格——合计 ≤ 2n 次指针移动，每格常数次计数操作，O(n)。帧 4 里那两个数字（r 走 8 格、l 走 6 格）就是这笔账在 abcabcbb 上的实数。「左端不回退」在这里的作用与 4.2 的相向双指针完全同构：4.2 里 r - l 每轮严格减 1，这里 l 与 r 合计走 ≤ 2n 格——两笔账合起来就是这句话：双指针的线性，来自「每个下标至多被扫常数次」。

两个版本怎么选？复杂度同阶（都是 O(n)，跳跃版把「收缩一段」折成「跳一步」，均摊常数更小——4.6 实测里跳跃版 ≤1 ms、收缩版 3~4 ms），差异不在快慢在风险：收缩版的正确性几乎「看得见」（每一步摘要都同步），跳跃版多了一个 last 表和一处 max 判断，边界更容易漏。赛场上两个都能过；先写收缩版把不变式立稳，回头想省常数再换跳跃版，是性价比最高的顺序。还有第三种写法在某些题里会见到：while 改成「收缩到窗口重新合法」但用 if 只收一格——那就是带病前进的 bug 版，I1 每轮都被破坏，样例常常看不出错，随机对拍一炸一个准。对拍的主循环不长，三方逐组比对：

陷阱你怎么会被坑到：收缩时忘了递减计数

4.4 滑动窗口之二：窗口 + 计数，最小覆盖子串

题目（LeetCode 76 原形）：给 s 和 t，找 s 里最短的连续子串，使它包含 t 的全部字符——按个数计。t 里有重复字符时，子串里该字符的个数不能少于 t 里要求的个数：t = "aab" 时，窗口里必须有两个 a 和一个 b，「出现过」没用，「凑够数」才算。这一题和无重复最长子串是同一个骨架，只换了两样东西：合法条件从「计数全 ≤ 1」变成「需要的字符计数 ≥ 需要量」；答案从「每个 r 的窗口长度取最大」变成「取最小」。但「按个数计」这个要求让朴素的布尔标记失效——「每个字符一个 seen 位」答不出「装了几个」——必须上真正的计数表，而且要能回答一个更难的问题：窗口现在离「合法」还差多少，这个差值必须 O(1) 可读，不能每轮扫一遍表。

样例两行读出两个信息：长度 4 与起点 9——合起来就是子串 [9..12] = BANC。它比人工第一直觉（从 A 开头的 ADOBEC，长度 6）短一半，短出来的部分全是收缩的功劳：ADOBEC 里 D、O、E 是 t 不要的「闲人」，B 又有第二个副本顶上——收缩把闲人全挤出去、把 A 换成窗口内更靠后的那个，剩下的才是最短覆盖。正解与暴力从完全不同的路径（计数器 vs 逐左端重开表）落到同一个 (9, 4)，这是样例层的第一次对齐；OK 200 是随机数据层的最终结论，200 组里 t 可能是 aaa 这类重字符（考按个数计）、也可能 s 里根本没有需要的字符（考无解返回 -1）。

missing 是这一题的点睛之笔，值得把它的机制拆到每个条件上。它把「窗口是否覆盖 t」从「每轮扫 256 格对表」变成一个整数的 O(1) 判断，前提是每个字符对它的贡献至多一次减、一次加：扩张时 cnt[c]++ 之后，条件 need[c] > 0 && cnt[c] <= need[c] 成立才 missing--——意思是「刚装进来的是 t 需要的字符，而且这个个数是第一次到位」（第 1 个 a 让 missing 减，第 2 个多余的 a 不减）；收缩时 cnt[d]-- 之后，条件 need[d] > 0 && cnt[d] < need[d] 成立才 missing++——意思是「刚丢掉的是 t 需要的字符，而且丢的这个刚好是最后一个富余」（丢多余的 a 不加，丢到不够了才加）。两个条件互为镜像，missing == 0 就是「每个需要的字符都够数」。没有这两个 need[c] > 0 的守卫，s 里成千上万个 t 不要的字符也会来动 missing，计数器立刻失真。经典样例的四帧：

  • 记录值不会小于真答案：missing == 0 才进收缩循环、才记录，所以每个被记录的窗口都真的覆盖 t，长度自然 ≥ 全局最小。
  • 记录值不会大于真答案：看 l 什么时候前进——只在「当前窗口覆盖」时前进一格，且前进的前提是「被丢的那个左端与当时的 r 组成的窗口覆盖」。由此归纳：r 到达 r* 时 l 还没越过 l*（若 l 已经到了 l*+1，说明某个 r0 ≤ r* 时窗口 [l*, r0] 覆盖，长度 r0 - l* + 1 ≤ r* - l* + 1，与「[l*, r*] 是最优」矛盾，除非 r0 = r*——那也正是此刻）。于是 r = r* 时窗口 [l, r*] ⊇ [l*, r*] 覆盖，收缩循环逐格记录，退出前的最后一次记录就是「以 r 为右端的最短覆盖窗口」*，长度 ≤ r* - l* + 1。

两半夹住，算法记录的就是全局最优。注意「收缩到恰好不满足为止」在代码里的落点：while (missing == 0) 的退出态是「窗口刚丢了第一个必需字符」——此刻的 l 减 1 正是「以当前 r 为右端的最短覆盖窗口」的左端点。帧 3 里那串 7、6、5、4，就是退出前最后一轮的记录轨迹。

几处边界也顺手交代：m > n 时窗口根本装不下 t，直接报 -1（m == n 时最多有一个候选窗口——整个 s）；t 里某个字符 s 里根本没有，missing 永远到不了 0，收缩循环从不触发，best 保持 n + 1、返回 -1——「无解」不是特判出来的，是计数器自然走出来的；n = 1、m = 1 时窗口就是一个字符，匹配就记 1，不匹配循环走完报 -1。空间是两张 256 格的 int 表加常数变量，约 2 KB——字符串窗口题的空间全部花在「摘要」上，与 n 无关，这比 4.2 那种要整个数组副本的算法宽裕得多；暴力版每个左端重开一张 have[256]（1 KB，栈上），代价同样与 n 无关，贵的是时间不是空间。

陷阱你怎么会被坑到：字符集假设

最顺手的写法是 int cnt[26]——「题目说只有小写字母」。坑有三层：其一，题目的话只约束样例，隐藏数据里混进一个大写字母或数字，cnt[c - 'a'] 就是负下标写，症状是结果时对时错（堆上越界的经典表现）；其二，本机 char 是有符号的，字节值 128..255 存进 char 是负数，cnt[c] 直接写穿到数组前面——lnr.h 的注释特意写了这一点，三份工程的计数数组全部开 256 格、下标一律过 (unsigned char)；其三，t 的字符集和 s 的字符集是两个集合，你给 s 开了 128 格、顺手给 t 开了 26 格，t 一超就错。判据只有一条：计数数组按「输入可能出现的全部字节值」开——char 只有 256 个取值，256 格的 int 才 1 KB，这 1 KB 买断一整类错误，是最便宜的保险。

这张表有两处值得停下来读。其一，暴力的成本不由 n 单独决定：同样是 n=1e6，两数之和的暴力（数对结构，真 O(n²)）外推要 96 秒；无重复子串的暴力只有 6~128 ms——因为它的成本是「到下一个重复的距离之和」，被字符集大小封了顶。判断暴力能不能「直接跑」要看问题的结构，不是背一句「暴力是平方所以不能跑」。其二，窗口三题的正解全部 ≤4 ms，差距全在排序（两数之和的 90 ms 是 qsort 的）——双指针类算法的线性扫描本身就是「免费」的那一层，这也是为什么赛场上这类题的成败几乎全在正确性，不在时限。

空间也记一笔，虽然这类算法从不在这里出事：三份正解的摘要都是固定大小的计数表（256 格 int ≈ 1 KB），与 n 无关；perf 里 1e6 个 long long 的数组占 8 MB、1e6 字符的串占 1 MB，都在 256 MB 限制内绰绰有余。真正值得留意的是暴力的栈：mw_brute 每个左端在栈上开 have[256]（1 KB）——它不在递归里，栈深恒定，没有 2.8 那种爆栈风险；但如果你把暴力写成递归枚举（比如枚举所有子串），深度跟着 n 走，本机 2 MB 的栈到几万层就死——这就是「迭代收缩」与「递归枚举」之间除了速度之外的又一条分界线。

这张表怎么用：拿到题先看 n 和「问题结构」两件事。n ≤ 5000 上下，暴力都是候选（对拍的参照物也是它）；n 到 1e5~1e6，数对/枚举结构的暴力出局，窗口类正解随便过；n 到 1e8，就要开始抠常数——先换掉 unordered_map 这类哈希容器（本机实测差 7 倍），再考虑把 qsort 换成基数排序或手写快排。表里每一行都有出处（perf 的 stderr、四次 experiment 块），换一台机器读同数量级即可——逐字对账只认结论行（OK 200、校验和、一致性），耗时不进对账，这条纪律在 4.5 就立下了。

顺带拆一下那 90 ms 的排序花在哪。qsort 对 1e6 个 long long 做比较排序，90 ms 折合每秒约 1100 万次比较——比理论内存带宽能支撑的慢了好几倍，慢在两处：比较器是函数指针回调，每次比较都是一次间接调用，编译器没法内联也没法向量化；元素 8 字节、随机访问模式让缓存的预取预测一直落空。手写一个针对 long long 的三路快排（或者 std::sort，编译器能把比较内联成一条指令），同规模通常能压到 40~60 ms；基数排序能再往下走一档。这笔账的意义在于：「排序 + 双指针」类算法的常数大头在排序，双指针扫描本身几乎不要钱——优化先动排序，别去抠那个 1 ms 的扫描循环。

4.7 应用层：std::unordered_map 的最小覆盖子串

原理层手写数组是为了看懂每一步；应用层的问题是：字符集不设上限时，计数表还能不能开成数组？ 256 格是 char 的答案；若 key 是任意字符串（比如「覆盖这些单词」），数组开不了，就轮到 std::unordered_map：

骨架与 C 版逐行对应（count 代替「need 是否非零」，operator[] 代替数组下标），差异全在容器。std::unordered_map 是一张哈希表：每个键被哈希函数映射进一个桶，查、插、删平均 O(1)，最坏退化成一条链（哈希全撞或被恶意构造时）。本题的键是 char，256 个取值、哈希分布极散，退化不会发生——7 倍常数差全在「每次操作都要算哈希、走桶、摸堆上节点」上。两处 C++ 细节：其一，s.size() 返回无符号的 size_t，与有符号 int 直接比较时编译器会把 int 提升成无符号，m 一旦是负数（参数给错）就变成天文数字、边界检查整个失灵，static_cast<int> 把这个坑摁死在写法上——ch02 讲 std::deque 时说过同一件事；其二，big_s.reserve 先把内存一次要够，让 1e6 次 push_back 不在中途反复扩容搬运——实测里它省的是几十万次重分配，不是正确性，是常数。

这是惯例，不是标准。判据一句话：key 的取值范围能不能预算出来。字符（256 个字节值）→ 数组，1 KB 买断，常数最小；单词、ID、任意字符串 → unordered_map，来什么装什么，代价是哈希常数（本机实测 7 倍）与最坏退化的风险。中间地带（值域大但稀疏，比如 1e9 范围里的 1e5 个数）先排序离散化再开数组，还是比 map 快。赛时顺序照旧：先写对（哪个顺手写哪个），确认卡常数再换——但这一题的 n 到 1e8 才需要操心，1e6 上两个版本都绰绰有余。

最后一条惯例写给读书的人：看到别人代码里的「窗口 + 计数」，先问两句——摘要是什么（几张表、几个计数器）、收缩的触发条件是什么（while 的退出态）。问完这两句，那份代码对你的透明度就够了；剩下的行都是这两句的展开。本单元三个例子你都能按这个句式复述一遍，就算真的拿下了。

陷阱你怎么会被坑到：operator[] 会把「查一下」变成「建一个」

把第 17 行的 need.count(c) > 0 && win[c] < need[c] 顺手写成 need[c] > 0 && win[c] < need[c]——编译过、样例对，看起来是「等价简化」。真相：need[c] 对不存在的键会插入一个 0 再返回引用，于是每个 s 里出现过、但 t 里不需要的字符都会在 need 表里建出条目。本题里 char 只有 256 种，插入的 0 条目碰巧无害（0 > 0 仍为假），你会带着这个习惯一直写下去；哪天 key 换成字符串——比如「窗口里覆盖哪些单词」——每次扩张都往 map 里塞新键，内存和哈希成本随 n 涨上去，还会把 need.size() 这类基于条目数的统计全部污染。判读的方法是盯住语义：只读用 count/find，确定要写才用 operator[]。C++23 里 at() 与 find 返回迭代器都是只读的合法选择。

这一节还有一个没点破的对照：第 4 单元的单调队列也在「滑动窗口」上干活，但它干的是窗口最值（队内单调，弹头弹尾）；本节的两个窗口（无重复、覆盖）只需要计数（合法条件是「全 ≤1」或「≥ 需要量」），没有单调性可言，所以左端收缩靠条件触发、不靠弹队头。判据记一句话：要窗口的最值找单调队列，要窗口的合法性找计数收缩。两类窗口还有一个隐藏的组合：最小覆盖子串里若再要「窗口里出现次数最多的字符」，摘要就得同时养一张计数表和一个「最值摘要」——那是两类技巧在同一根橡皮筋上合作的样子，竞赛题里并不罕见。

下一单元进入树——指针从「数组上的两个下标」变成「父子之间的边」，不变式的写法会换一套，但「每步只丢被证明没用的东西」这条论证纪律，从今天起随身带着。

小结这一节的要点
  • 双指针的正确性全部押在「每一步只丢被证明没用的元素」上：相向双指针的丢弃引理靠排序（两端分别是窗口最值），窗口收缩的合法性靠计数摘要；
  • 左指针（或左端）只前进不回退 ⇒ 总移动 ≤ 2n ⇒ O(n)；「收缩到恰好不满足为止」对应 while 的退出态，多收浪费、少收带病前进；
  • 「和为 target 的两数」必须先排序：乱序时 a[l]+a[r] < target 说明不了「a[l] 跟谁都配不成」——本节真跑的反例漏掉 5+4=9，200 组乱序数据漏 117 组；负数不是问题，无序才是；
  • 窗口 + 计数的两件套：need（要多少）与 cnt（有多少），missing 把「是否覆盖」变成 O(1) 整数判断；收缩时计数同步递减——忘了递减不是答错，是死循环加越界；
  • 计数数组开 256 格、下标过 (unsigned char)：char 在本机有符号，字符集假设是这类题最便宜的保险；key 是任意字符串时才轮到 unordered_map（本机实测比数组慢 7 倍）；
  • 对拍比「存在性」不比「下标相等」（数对可能不唯一），外加正解自检；随机数固定种子自实现，200 组只花几毫秒；
  • 暴力的真实成本由问题结构决定：数对暴力是真 O(n²)（n=3e4 全扫 88 ms），字符串暴力被字符集封顶（周期 250 的 1e6 串也只要 128 ms）——量它之前先构造能让它露出真面目的数据。

注自测题答案
  1. 每轮循环要么 l++ 要么 r--，r - l 每轮严格减 1，初值是 n - 1，减到 0（l == r）为止，所以至多 n - 1 轮。若两边一起动：某轮和偏小其实该只动 l，你把 r 也左移了——r 这个位置可能与后面的某个元素配成对，从此再无人检查它，不变式「解仍在窗口内」被破坏，漏解；而且「每轮区间严格缩一格」的 O(n) 论证也还在，错得又快又无声。
  2. 手推（排序后 -3 -1 2 4）：l=0、r=3：1 == 1，直接命中，一步就完。换 target=3：l=0、r=3：-3+4=1 < 3 → l++；-1+4=3 命中。负数的作用体现在第 2 步：和偏小是因为左边是负数拖了后腿，恰好说明该换左端——算法对负数毫无特殊处理，它只依赖「两端是窗口最值」这个排序给的性质。所以负数不影响正确性，它影响的是「你不能用无序版的双指针」这件事；无序才是错误之源。
  3. 三种表现按顺序：先是 while 退不出去（cnt[c] 永远是 2），表现为程序卡住不退出；随后 l 一路 ++ 越过 r、冲出字符串，读 s[l] 越界内存；最终被 Windows 按访问违例杀死（退出码 3221225477）或在堆上安静地污染别人的数据（时对时错）。最先出现的是卡死。
  4. abba：r=2 撞上旧 b（位置 1），l 跳到 2；r=3 撞上旧 a（位置 0），不做判断的话 l 会从 2 往回跳到 0 + 1 = 1，窗口 [1..3] = bba 含重复的 b，错报长度 3（正确答案是 2）。判断 last[c] + 1 > l 不成立就保持 l 不动，窗口留在 [2..3] = ba。
  5. 退出时窗口 [l, r] 恰好不覆盖 t——刚丢了第一个把覆盖撑住的必需字符（cnt[d] < need[d] 让 missing 回 1 的那一步）。此时「以 r 为右端的最短覆盖窗口」的左端点是 l - 1（退出前的最后一次记录就发生在 l 还是 l - 1 的那一轮，长度 r - (l - 1) + 1）。
  6. key 的取值范围无法预算时值得付：t 与 s 的「字符」其实是单词、ID、任意字符串，256 格数组无从开起，哈希的 7 倍常数是「能写出来」的价格；n 不大（比如 1e5 级）时 7 倍也仍然在几毫秒量级，先写对再说。连 unordered_map 都不够用的场景：n 到 1e8 量级、key 又必须任意字符串——那时要先做哈希离散化（把字符串映射成整数）再回到数组计数，或者干脆换双哈希等概率结构；本机实测的 22 ms 在 n=1e6 上无所谓，外推到 1e8 就是 2 秒级，超出多数题的时限。
