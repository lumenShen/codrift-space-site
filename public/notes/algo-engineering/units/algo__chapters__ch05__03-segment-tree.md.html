5.1 先看工程长什么样

线段树是本册到现在工程量最大的一棵树：三个例子目录、每个都是「头文件 + 实现 + 驱动」的三文件工程，其中两个还各带一份暴力对照、一份性能驱动。坑也最密——空间、下标、递归、溢出，每一类都在这棵树上摔过跤。所以照本书的规矩，先看文件。

第 2 帧是三个例子的分工：seg_range_add_sum 讲「区间加 + 区间和」——懒标记的主场；seg_range_max_pos 讲「区间最值 + 位置」——节点上存两个量怎么合并；seg_dynamic 讲「动态开点」——值域 1e9 时树怎么活下来。第 3、4 帧是这本书的加码：每个例子都有一份暴力对照（对拍 200 组）、一份性能驱动（M12 的表全靠它们），第 3 帧里还有三个特殊角色：bit.c（树状数组对照组，5.10 同数据比武）、death_main.c（递归深度的死亡演示，5.9）、segsum.cpp + cpp_main.cpp（C++ 应用层，5.11）。三份 session-*.txt 是真实抓下来的耗时与崩溃会话，正文逐字引用。

5.2 从分治到树：什么样的信息能挂上去

大白话用大白话说线段树

把数组从中间劈一刀，两半各自再劈，一直劈到每个节点只管一个元素。每个节点管一段区间，节点上写着「这一段的答案」——问的是和就写和，问的是最大值就写最大值。于是问任意一段 [l,r]，都等于把树上「能整段拿走的几个节点」拼起来：不用碰区间里的每个元素，只用碰 log n 个节点。改也一样：改一个元素，只需重算它到根这条路上的 log n 个节点。

这句话成立有一个前提，也是线段树唯一的准入条件：节点的答案必须能由两个孩子的答案直接算出来。这叫「可合并」：sum[x] = sum[左孩子] + sum[右孩子]，一行，O(1)。最大值可以（两边取大）、最小值可以、最大公约数可以、区间「最大值加次大值」也可以（两个二元组拼一个新的）。反过来，「区间众数」不行——左半的众数和右半的众数拼不出整段的众数（真正的众数可能两边都不占优）；「区间开根号」不能直接懒标记，因为对「整段」生效的变换推不出来。拿到题先问这一句：孩子的信息能不能 O(1) 拼出我的信息？不能，线段树就不是白给的。

建树自身的边界也顺手交代清。n=1：根就是叶子，build(1, 1, 1) 第一层判断直接命中，树只有 4 个数组格被用到；空树不该建：seg_sum_init 对 n <= 0 返回 −1，接口层挡住，递归永远见不到空区间；递归的终止就是 nl == nr——它与查询的「整段包含」是两回事：前者是「树长到头」，后者是「问题被整段覆盖」，混为一谈的人会把叶子判断写进查询里，单点区间就查错了。

5.3 查询：三种覆盖关系与对拍

查询只认三种关系，每种都有明确动作：整段包含（l <= nl && nr <= r）——节点管的区间整个落在 [l,r] 里，它的 sum 正是你要的一段，直接拿；不相交——本实现里没有专门的 if，靠 l <= mid 和 r > mid 两个判断挡在门外：不相交的孩子根本不会被调用；部分覆盖——劈开，两半各问各的，回来把结果相加。查询的边界就这么多，难的不是写，是边界常数：<= 与 < 错一个，答案就在样例上时对时错。

用具体区间把边界走一遍（n=8，查 [3,6]）：根 [1,8] 部分覆盖，下钻；左孩子 [1,4] 部分覆盖，mid=2，l=3 <= 2 为假——左孙 [1,2] 不进，右孙 [3,4] 整段包含，拿走；右孩子 [5,8] 部分覆盖，mid=6，r=6 > 6 为假——右孙 [7,8] 不进，左孙 [5,6] 整段包含，拿走。答案 = [3,4] + [5,6]，只碰 5 个节点。两次「不进」各由一个 if 条件独立完成，这就是「无交不写 if」的实操形状。你若更喜欢显式三段式（先 if (r < nl || nr < l) return 0; 再判包含、再下钻），也对——多两次比较、少一分对 if 条件的依赖，两派都常见，别混着写。

语法规则语法规则：递归线段树的函数签名
  1. 私有递归带四个区间参数：node（当前节点编号）与 nl, nr（它管辖区间的左右端点）同行进、同行出；查询/修改自己的 l, r 单独一份。树的区间是「递归自己带着走的」，问题的区间是「调用给的」，两份参数永远不混。
  2. 入口只有一行：query(t, 1, 1, t->n, l, r)——根编号 1、根管 [1, n]，与接口的 1..n 重合是刻意的；5.7 的动态开点会看到「值域 [1, U]」接替 [1, n]。
  3. mid 每层现算：nl + (nr - nl) / 2。缓存整张 mid 数组省两次减法、多一个 4n 数组——本机量不出能感知的差别，不值。
陷阱你怎么会被坑到：闭区间与左闭右开混用

题面（或你从 Python 抄来的思路）给的是左闭右开 [l, r)，C 的习惯是闭区间 [l, r]，而你两个都写过：查 [l,r] 时手一滑写成 query(l, r+1)——多算一个元素；写差分树状数组时又是 add(l, r+1, -v)——这里却必须 +1。两种约定在同一份代码里各对一半，症状是：所有样例都对，随机对拍第一次区间端点相碰时就错 1。定死一条规矩并写进头文件注释：线段树的接口一律闭区间 [l, r]，r+1 只出现在树状数组的差分里。本单元所有例子遵守这条，对拍里专门撒「l == r」「r == n」的端点数据让它无处躲。

5.4 懒标记：整段记账，下推才落地

大白话用大白话说懒标记

给 [1,1000] 每个数加 5，犯不着跑 1000 步——在管这整段的节点上记一笔账：「我这一整段欠 +5」，走人。账记着，但孩子还没真的加。什么时候必须进孩子（比如下一次操作只问到 [1,500]），才把账下推给孩子，自己销账。懒标记的全部思想就一句：整段都加的操作先记账，下推的时候才落账。

为什么这样是对的：归纳论证一句话说全。不变式是——任何时刻，sum[x] 已包含 x 自己身上的账，但没包含祖先身上的账；于是「x 的真实区间和 = sum[x] + 各祖先 lazy 之和 × 区间长」。三个动作各自保持不变式：整段覆盖时 sum 与 lazy 同时加（sum 立刻对、账也记下，将来下推不重不漏）；pushdown 是把「祖先的账」原样转移给直接孩子（总账守恒）；回溯时的 sum[x] = sum[左] + sum[右] 用的孩子 sum 都已含各自及以下的账。而查询敢直接返回 sum[node]，靠的是路上所有部分覆盖节点都先下推了——它到根之间不可能还有没落地的账。

为什么是均摊 O(log n)：拆成两半看。整段覆盖的节点，记账是 O(1)——这就是懒标记省下的部分，没有它，一次区间加要走到叶子，O(n)；部分覆盖的节点才花钱：下推 O(1)、下钻 O(1)、回溯重算 O(1)，而部分覆盖的节点一次操作至多出现 O(log n) 个（下一节证明）。所以每次操作的总代价 = O(log n) 个 O(1)，均摊成立。「完整覆盖时记账、部分覆盖才下推」不是两个实现细节，是这条复杂度的两根支柱：少了记账，区间加退化成 O(n)；少了「部分覆盖才下推」，每次操作都要把全树账推平，也是 O(n)。

拿 5.10 那份数据粗走一遍账：深度 18、每层至多 2-3 个节点被访问，一次操作的上界不过几十个节点；其中「整段覆盖、记账收工」的占大头，真正下推的只有边界链上的那几个。1e5 次操作就是几百万次 O(1) 动作，对应 5.10 里 27ms 的量级。暴力逐点加呢？区间长度的期望是 n/3 ≈ 3.3 万，1e5 次就是 33 亿次元素操作——两个数量级的差距，也是对拍只能用 n≤300 小数据的原因：暴力证明正确性，perf 证明复杂度，各管各的规模。

pushdown 的时机其实有两种写法，本书选了第一种：

  1. 进节点先下推（本单元）：update 与 query 遇到部分覆盖，先 pushdown 再下钻。好处是想得简单——任何时候你看到的节点，它到根的账都清了；坏处是只读的查询也写内存（孩子的 sum、lazy 被改），5.10 会看到这笔账在缓存上多少钱。
  2. 标记永久化，永不下推：update 只在自己这层记账；query 从根往下走时把路径上的 lazy 累加进一个「随身账」，整段包含时答案 = sum[node] + 随身账 × 区间长。代码更短（没有 pushdown），查询零写入，可持久化线段树几乎必须用它；代价是每个操作的式子都得自己带账，写错更隐蔽。

懒标记是个框架，不专属于加法。区间赋值：账从「+v」换成「赋 c」，下推时孩子 sum = c × 长度、lazy = c——注意赋值是「覆盖」语义，下推要顶掉孩子原来的账，与加法的「累加」不同。乘加混合：两种标记同时挂时，下推顺序必须「先乘后加」（(a×m)+c 的展开），顺序反一次，整棵子树答案全歪——这是懒标记体系里最经典的坑题。能不能做成标记，判据仍是 5.2 那句：变换能对整段批处理，且连续两次变换能折叠成一个（+a 再 +b 折叠成 +(a+b)，赋 c1 再赋 c2 折叠成赋 c2）。

陷阱你怎么会被坑到：忘 pushdown

你会看到的现象高度一致：做了一串区间加之后，查出来的和「缺了一截」——缺的恰好是某段还没落地的账。最常见的两种错法：add 里记了账、却忘了在进孩子前 pushdown（孩子读到的 sum 是旧的）；或者照抄了别人的 query、而那份 query 是配「标记永久化」写的，两套约定混在一起。特征性的坑：操作序列很短时全对（账还没来得及穿过查询路径），序列一长就错。查法也简单：对拍数据里先来一次全区间加、再来一次单点查——这个组合专抓没下推的账。

顺带回答「下推为什么写成递归内联、不抽成独立的一次性推平」：因为下推的需求永远是局部的——本次操作只走进边界链上的那几个节点，把它们各自的账推一层就够了；「一次性推平全树」是把 O(log n) 的活干成 O(n)。同理也别想着把 pushdown 挪到操作开头「统一做一遍」：懒标记的全部收益就来自「账能欠着不还」，先推平等于自废武功。账只在「必须进孩子」的那一刻、只推当前这一层，这条纪律贯穿所有懒标记变体（赋值、乘加、区间最值都一样）。

5.5 为什么一次查询恰好碰 O(log n) 个节点

5.4 把复杂度押在一个断言上：一次 update/query 访问的节点数是 O(log n)。这个断言值得完整证一遍，因为它同时也是「区间拆分为什么漂亮」的答案。

先证一个引理：部分覆盖的节点，要么包含 l，要么包含 r。设节点管 [nl,nr]，与查询 [l,r] 相交但不被包含。若它既不含 l 也不含 r，则交集里的点 x 满足 l < x < r 且 nl ≤ x ≤ nr——若 nl > l 且 nr < r，则 [nl,nr] 整个落在 (l,r) 内，节点被包含，矛盾；否则 nl ≤ l 或 nr ≥ r，交上的是端点，即包含 l 或包含 r。引理成立。

而包含 l 的节点，从根到叶恰好构成一条链（每一层至多一个节点同时含 l——节点的区间互不重叠），包含 r 的同理。所以：每一层的部分覆盖节点至多 2 个（l 链上一个、r 链上一个），树高是 ⌈log2 n⌉，部分覆盖节点总数 ≤ 2⌈log2 n⌉ + 2。整段包含的节点只在部分覆盖节点的孩子处被直接拿走，每个部分覆盖节点至多带 2 个这样的孩子，总访问数 ≤ 3 × (2⌈log2 n⌉ + 2) + 1——n=1e6 时上界 123，实测 5.9 会看到递归深度只有 21 层。

第 4 帧里那三个「整段在查询里，拿走」的节点（[2]、[3..4]、[5..6]）各有各的来历：[3..4] 是 l 链节点 [1..2] 之外的兄弟被整体拿走，[5..6] 是 r 链上的兄弟——它们不是「碰巧」整段覆盖，而是被边界链的结构保证整段覆盖。这也是为什么区间拆分出来的节点总能拼回 [l,r] 无重无漏：拿走的节点互不相交（树结构保证），并起来恰好盖住 [l,r]（下钻只在部分覆盖处发生）。

大白话用大白话收住这一节

把 [l,r] 的两个端点想成两只手从根往下摸。两只手每层各走一个节点，手上经过的节点才可能「半截在查询里」；别的节点要么整段被手盖住（直接拿），要么离得远（不看）。所以花的钱只跟「手的深度」有关——树的深度是 log n，花的钱就是 log n。

回看 5.2 第 4 帧就多了一层意思：那帧里「部分覆盖，下钻」的三个节点（[1..8]、[1..4]、[5..8]）全部站在 l 链与 r 链上，三个「拿走」的节点全是链节点的兄弟——图上省略的 [1] 与 [7..8] 正是「不交不看」的那两个 if 挡掉的。一次查询的全部行为，帧里一画，引理一证，两边严丝合缝。

5.7 动态开点：值域 1e9 怎么办

大白话用大白话说动态开点

前几节的树要 4n 空间，前提是 n 是数组长度。可如果操作发生在值域 [1, 1e9] 上——位置本身就是 1e9 以内的数——4e9 个节点谁也开不起。但你一共只做 q 次操作，每次只穿过约 30 个节点：那就别预建，走到哪一段才建哪一段。没走过的区间根本不存在，自然不占内存。

与普通线段树相比有三处本质不同：孩子编号不再有 2i/2i+1 的算术关系，必须真的存下来；编号 0 固定空着，当「这个孩子不存在」的判据；查询遇到 0 号孩子，答案直接是 0——没建过的区间和一定是 0。

先算一笔反账，看动态开点省的是什么。值域 1e9 的静态线段树要 4×1e9 个节点，long long 的 sum 加 int 的孩子指针约 16B 一节——640 亿字节，64GB，题目内存直接爆炸。而 q=1e5 的操作每个只穿过 ⌈log2 1e9⌉ ≈ 30 个节点，全程被碰到的节点最多 300 万个——是 4e9 的千分之一量级。走到哪、建到哪，省下的就是「用不到的那千分之九百九十九」。

普通线段树的编号是算出来的：根是 1，孩子 2i/2i+1，全树没有「空孩子」这个概念。动态开点的编号是存出来的，而 0 还兼任「不存在」的判据——两件事挤在同一个数上。你若让 new_node 从 0 起领号，根就成了 0 号：第一次判 lc == 0 会把「根本身」误判成「没建过」，然后新建节点顶掉根。症状是查询集体返回 0 或答案缺一大块。规矩一句话：0 永远空着，真节点从 1 起，并把这句话写在结构体注释里（本单元就是这么写的）。

陷阱你怎么会被坑到：一行「顺手」的写法，撞上 realloc 和求值顺序

写 dyn_add 时，最顺手的写法是一行：t->lc[node] = new_node(t);——本单元第一版就是这么写的，然后 -O2 下对拍第 3 组 FAIL、性能程序直接访问违例倒下（本机退出码 3221225477，即 0xC0000005；Git Bash 的 $? 折成 127）。真相：new_node 里 realloc 会搬家，而 C 语言不规定 t->lc[node] = new_node(t) 里左边「取 t->lc 的地址」与右边「调函数」谁先算——这台机器的 gcc 先取了旧地址，realloc 一搬走，写入落在已经释放的旧块上。2.4 节那句「有副作用的调用别和读同一状态的调用放进同一个表达式」在这里换了个马甲。修法就是现在代码里的三行：先领编号存进局部变量，函数返回后再写回 t->lc[node]。

陷阱你怎么会被坑到：mid = (nl + nr) / 2 在值域上溢出

数组线段树里 n ≤ 1e6，nl + nr 顶多 2e6，怎么写都行。值域线段树不一样：值域 [1, 1e9] 时最深处的 nl + nr 可到约 2e9——距离 int 的上界 2147483647 只差一步，侥幸不炸；一旦题目坐标有负数、平移成 [1, 2e9]，nl + nr 直奔 4e9，有符号溢出是未定义行为，mid 变负数，递归走进不存在的区间。nl + (nr - nl) / 2 一劳永逸，本单元两棵树都用它。

动态开点不是唯一出路。离线知道所有位置时，把位置排序去重，用二分映射到 1..q——值域瞬间缩成 q 个点，普通线段树（甚至树状数组）就够了，空间还从 O(q log U) 降到 O(q)。三步是固定套路：① 把所有会出现的位置（操作的位置、查询的左右端点）收进一个数组；② 排序、去重；③ 每个位置用它在新数组里的下标当新坐标。此后普通线段树的深度从 31 掉到 17，常数也跟着小。代价是离线：必须先读完全部操作。反过来，「强制在线」的题（下一个位置依赖之前查询的结果）只能动态开点。判据就一条：位置集合能不能提前拿到。

两条路线还能组合：动态开点 + 懒标记——区间加 + 区间和搬上值域，lc/rc/sum 之外再加一条按需扩建的 lazy 数组，pushdown 与 5.4 逐行相同，唯一的区别是「孩子不存在时先建再推」。复杂度不变（还是每操作 O(log U)），空间照样按需。竞赛里的「权值线段树」（对值域开树、统计每个值出现几次）就是这套组合的常客：单点加一个数、查全局第 k 小，二分着往下走，靠左孩子的计数决定往哪边——你已经具备读懂它的全部零件。

动态开点的空间账与 5.8 的 4n 完全不同源：它按需领编号，上界是「操作数 × 每操作新建节点数」= q × ⌈log2 U⌉ + 1——听着吓人（5 万次 × 31 ≈ 155 万），实际远少于此：路径会共享。同一子树里的位置共用祖先，实测 770378 个节点、约 15.4 节点/操作；按上界预留数组也不亏（155 万格 × 16B ≈ 25MB），按实测比例估算 1e6 次操作约 1550 万节点、250MB——到了这个量级，先想想 5.7 开头的离散化。

5.8 空间账：为什么开 4n

sum 和 lazy 都开 4n 个格子，不是「乘 4 图吉利」，是一个能写出来的上界。树的最大深度（根算第 0 层）是 D = ⌈log2 n⌉——劈 ⌈log2 n⌉ 刀必然劈到单点。节点编号的规律是：第 d 层的编号落在 [2^d, 2^(d+1) − 1]（根 1 号、第二层 2、3 号，以此类推，2i/2i+1 的直接推论）。所以最大编号 ≤ 2^(D+1) − 1 < 2^(⌈log2 n⌉ + 1) ≤ 2^(log2 n + 2) = 4n。第二处不等号用到了「上取整 ≤ 值 + 1」——n 不是 2 的幂时，最深层其实稀稀拉拉没几个节点，但编号照样走到那么远，这才是 4n 的来源：它不是节点数的 4 倍，是「最深一层最右那个节点的编号」的上界。

n=4 时开 4n=16 格，实际只用 7 格。先补一句常被问的：建树为什么是 O(n) 而不是 O(n log n)？节点总数是 2n − 1（n 个叶子加 n − 1 个内部节点，满二叉树的个数守恒），build 在每个节点上只做一次加法，总功 O(n)。「每个元素要爬 log n 层」的直觉错在把「层」当成了「工作量」——同一层的兄弟是并列建出来的，不是串行，量度该数节点个数而不是层数乘法。

第 3 帧是 4n 的关键：浪费不在「用不到的节点」，在「用不到的编号」。n=1e5 时实测递归深度 18（5.9 的 perf 输出），编号上界 2^19 − 1 = 524287——而实际节点只有不到 2×1e5 个。4n = 400000 卡在两者之间，是紧的上界：再小就真会越界。

陷阱你怎么会被坑到：开 2n 或 3n「省内存」

你会看到的现象：样例全对、随机测试几千组全对，某天换个 n（特别是 2 的幂加减一，比如 n=65537）直接访问违例，退出码 3221225477——或者更糟，不崩，答案时对时错，因为越界写到的恰好还是自己进程的堆。拿 5.9 的数算一遍就死心：n=1e5、深度 18、最坏编号 524287，而 2n=200000、3n=300000 都小于它——开 2n 的树在「左半细劈、右半大块」的形状上必然越界。4n 不是迷信，是把「编号上界 2^(⌈log2 n⌉+1)」换成的好记近似。真要省空间，用 5.7 的动态开点——按需领编号，一个都不浪费。

还有一笔账与空间无关、与这棵树的每个 long long 有关：求和会溢出。本单元 perf 程序的校验和是 4367209619784——单次区间和就可能到 1e5 个元素 × 每个几百万 ≈ 2.5e11，早已越过 int 的 2.1e9；用 int 存 sum，跑到一半答案就变负数，而且样例照样全对（小数据碰不到上界）。规矩：区间和一类的节点值、加值、累加器，全部 long long；v * 区间长 在乘之前把长度转型（代码里的 (long long)(nr - nl + 1) 就是干这个的——两个 int 相乘先溢出再转型就晚了）。

还有一条纪律来自机器事实篇：换程序要重测。「4.4 万帧」是并查集递归 find 的边界，本单元 walk_chain 的帧更小、query 的帧更大，具体数字都会漂；编译器、优化档、局部变量的多少都在改帧大小，漂多少没法照搬。不变的只有两件事：量级（log n 的递归离死亡线几个数量级；深度 = n 的递归必死）与判据（每层规模减半还是减一）。所以本节报的所有帧数只在这台机器、这份代码上成立，换机器只能参考量级，随身带走的是判据，不是数字。

陷阱你怎么会被坑到：把「深度 = log n」的自信平移给所有递归

线段树、二分、堆调整这类递归，每层规模减半，深度 O(log n)，本机随便跑。但「用递归」这个动作本身不提供任何保证：链上 DFS、递归 find、错误的终止条件（比如把「完全覆盖」的 <= 写成 <，单点查询在叶子上永远停不下来）都能把深度推到 n。本地小数据全对、大数据 RE，八成是这一类。对策按序：改迭代；改不了就把递归改「显式栈」；都来不及，至少在本地用最大规模的边界数据跑一次——栈溢出这种死法，样例永远探不出来。

可能有人要问：既然递归这么挑，为什么不干脆写迭代版线段树？迭代版（非递归、自底向上）确实存在，单点改 + 区间查的形态只要十几行、常数还更小；但懒标记很难搬进迭代版——pushdown 的时机依赖「从根下来」的方向，自底向上的循环要额外维护一遍「下行路径」，代码反而更长更绕。所以竞赛的默认分工是：无懒标记的简单树可以迭代，带懒标记的一律递归——递归的安全线（深度 ⌈log2 n⌉ + 1）已经在本节用实测钉死了，用放心用。

顺带把「帧大小」说破：一个栈帧多大，取决于函数里有多少局部变量、寄存器怎么分——query 带六个参数和三个局部量，一帧几十字节；walk_chain 更小。所以「深度多少会死」永远是个乘法：深度 × 帧大小对上 2MB 的保留量。深度这一头你写代码时就能算（log n 还是 n），帧大小那一头编译器说了算——这正是「判据随身带、数字重测」的原因。

把选择流程压成赛场上 30 秒能走完的三问。第一问：操作集合里有没有「和」以外的东西（最值、赋值、第 k 小）？有——线段树，讨论结束。第二问：只有和，改动是不是「单点改 + 前缀查」的形态？是——普通 BIT 甚至差分数组就够。第三问：剩下「区间加 + 区间和」——双 BIT 起步，只有题目额外要求可持久化、强制在线这类本事时才让线段树上场。偶尔还有第四问反向否决：空间。256MB 限制、n=1e6 时，long long 的 4n 线段树（sum + lazy 两条数组）要 64MB，双 BIT 只要 16MB——题目若还有别的大家伙（图、DP 表），16MB 与 64MB 的差别就是过与不过。

5.11 应用层：C++ 怎么写这一棵树

C++ 标准库里没有线段树——STL 给你的是 partial_sum（静态前缀和）和有序集合，区间改区间查都得自己来。所以 C++ 选手的线段树也是手写模板，值得学的是封装的边界：内存交给 std::vector，深度观测交给 RAII，接口对调用者隐藏节点编号。

小结这一节的要点
  • 线段树的准入条件只有一条：孩子的信息能 O(1) 拼成本节点的信息（可合并）；和、最值、gcd 都行，众数不行；
  • 查询/修改只认三种覆盖关系：整段包含直接拿、不相交被 l<=mid/r>mid 挡住、部分覆盖劈开下钻；
  • 懒标记一句话：整段覆盖时记账 O(1)，部分覆盖才下推；不变式是「sum 已含自身账、未含祖先账」，两条合起来才是均摊 O(log n)；
  • pushdown 两种时机：进节点先下推（直观，查询也写内存）与标记永久化（查询零写入，账随参数下传）；混用两套约定是最常见的错法；
  • 部分覆盖节点每层至多 2 个（l 链 + r 链），所以一次操作访问 O(log n) 个节点，无重无漏拼回 [l,r]；
  • 动态开点三件事：孩子编号显式存、0 号当「不存在」、没建过的和为 0；t->lc[node] = new_node(t) 这种一行写法会撞上 realloc 与求值顺序；
  • 4n 是「最深一层最右编号」的上界 2^(⌈log2 n⌉+1) 的好记近似，不是节点数的 4 倍；开 2n/3n 在特定 n 上真会越界；
  • 本机实测：懒标记线段树 27–28 ms、双 BIT 3 ms（同数据 n=q=1e5）、区间最值 14–16 ms、动态开点 33–35 ms；线段树递归深度 21 层（n=1e6）离 2MB 栈差三个数量级，链式递归 100 万步当场被杀。

注自测题答案
  1. 众数不满足「可合并」：知道左半的众数和右半的众数，拼不出整段的众数——真正的众数可能在两边都只是少数派。能挂上去的信息必须能由两个孩子的信息 O(1) 组合出来，例如和、最值、gcd、「最大值 + 次大值」这种补充了上下文的二元组。
  2. 靠两个下钻判断挡住：if (l <= mid) 保证「与左孩子相交才进左」，if (r > mid) 保证「与右孩子相交才进右」。不相交的孩子根本不会被调用，不需要显式的无交返回。
  3. 不变式：任何时刻 sum[x] 已包含 x 自己 lazy 的影响，但未包含祖先的 lazy；x 的真实区间和 = sum[x] + 各祖先 lazy 之和 × 区间长。整段覆盖时把 v×区间长 加进 sum、同时把 v 加进 lazy——sum 仍然「含自身账」，lazy 记下「欠孩子的」，将来下推时恰好补齐，不重不漏。
  4. 标记永久化：查询从根走到节点时，把路径上所有 lazy 累加成「随身账」，整段包含时答案是 sum[node] + 随身账 × 区间长。换来的是没有 pushdown——查询零写入、代码更短、天然支持可持久化；牺牲的是每个操作的式子都得自己带账，写错更隐蔽，且没有「下推后孩子干净」的简单心智模型。
  5. 因为 0 兼任「这个孩子不存在」的判据（lc[x] == 0 表示没建过）。根若占 0 号，第一次判 lc[根] == 0 会把根本身误判成「没建过的新节点」，新建节点顶掉根，查询集体失效。真节点从 1 起，0 永远空着，判据与编号就不再相撞。
  6. 选双 BIT：5.10 的实测里同数据（n=q=1e5）线段树 27–28 ms、双 BIT 3 ms，差一个数量级，而 1e6 规模对 BIT 也只是 30 倍工作量，1 秒预算内绰绰有余。改成「区间加 + 区间最大值」就必须换线段树：最大值没有差分结构（5.6 开头的论证），双 BIT 表达不了，懒标记线段树是标准解。
