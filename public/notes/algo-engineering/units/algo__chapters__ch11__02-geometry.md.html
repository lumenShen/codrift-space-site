27.1 先看工程长什么样

计算几何在赛场上有个坏名声：样例全过，一交就 WA。原因几乎从不在公式，而在约定：叉积的符号意思是左还是右？共线点算不算顶点？矩形的边界算不算被覆盖？这些约定编译器一个字都不会提醒你，只有对拍能和把约定写死的代码救你。照本书的规矩，先看清文件，再谈算法。

大白话先建立一个画面

把叉积想成「两个人并排走，看第二个人拐向哪边」。你站在 O 点，先看向 A，再看向 B：如果 B 落在你视线的左手边，叉积是正的；落在右手边，是负的；三点连成一条直线，是零。这个「左/右/直」的三态判断，是这一单元的原子操作——凸包在用它，线段相交在用它，点在多边形内也在用它。

第 1 帧是动笔前的样子。第 2 帧一次给出本节新增的三个目录，每个都是「正解 + 暴力 + 对拍」三件套：正解负责快，暴力负责一眼能看出对，两者不共享任何计算代码；include/ 放约定与类型，main.c 只造数据、调用、比对、打印。第 3 帧是应用层与实验：一份完整的 C++/STL 程序（M14 要求的那一层）和两份性能探针，探针的 stderr 被抓进 session-perf.txt，正文里的会话块逐字来自它。

工程惯例工程惯例：为什么暴力要单独写一个文件

这不是标准规定，是对拍的纪律。如果正解和暴力共享一个「公共子函数」，它们就会在同一个地方一起错，对拍打出 OK 200 也毫无意义。本单元三套例子的 _brute 文件都把计算重新写了一遍：cross_basic_brute.c 用浮点斜率与有向面积，convex_hull_brute.c 用礼物包裹法加极点枚举，scanline_area_brute.c 用单位格积分。代价是多写几百行；收益是每一声 OK 200 都有分量。

27.2 叉积：一个乘法定左右

先把最要紧的结论放在前面：叉积的符号就是转向，绝对值就是有向平行四边形的面积。给定 O、A、B 三个点，令 OA = (a.x−o.x, a.y−o.y)，OB = (b.x−o.x, b.y−o.y)，则 OA × OB = ax·by − ay·bx。结果为正，B 在 OA 的左侧；为负，在右侧；为零，三点共线。注意这个「左」是从 O 看向 A 时的左，不是纸面上的左——这一点会让很多人第一次写凸包时把整条链翻过来。

大白话用大白话说叉积

把 OA 和 OB 想成两根木条，从同一点 O 伸出去。它们夹出来的平行四边形有多大，就是叉积的绝对值；而叉积的正负，记着「从 OA 转到 OB 是往哪边转」。所以叉积一次回答两个问题：转了多少面积，以及往哪边转。凸包只关心后半句：如果转的方向不对（右转或不动），中间那个点就不是顶点，扔掉。

第 9 行是整个模块的核心：两个乘积都在 long long 里算完再相减，不经过 double。坐标是整数时，这一步完全精确——没有舍入、没有比较 eps、没有「差一点点算成零」的玄学。cb_sgn 把任意整数压成 1 / 0 / −1 三态，后面所有判断都只认这三个值。

第 1 帧里 4×5 − 2×1 = 18，是正的：从 OA 转向 OB 是左转。第 2 帧换成 B=(2,−1)，4×(−1) − 2×2 = −7，变成右转；面积仍是 7，符号单独记录方向。第 3 帧 B=(3,3) 与 A=(2,2) 在同一条射线上，2×3 − 2×3 = 0，平行四边形压成一条线。三帧合起来就是那句口诀：符号定方向，绝对值是面积。

把叉积和另一个熟悉的东西接上：多边形面积。顶点按逆时针给出的多边形，其有向面积的两倍等于所有相邻顶点叉积之和 ∑(xᵢ·yᵢ₊₁ − xᵢ₊₁·yᵢ)——这就是鞋带公式。每一项都是一次叉积，所以「面积为正 = 逆时针」与「叉积为正 = 左转」是同一套符号约定的两个侧面。凸包输出逆时针顺序，正是为了让后续算面积时这个和天然为正；若你把两条链拼反，面积会变成负数，对拍里的顶点序列也会整个翻过来。

语法规则语法规则：三步把叉积用对
  1. 先平移到同一起点：叉积算的是 OA 与 OB，所以两个向量都要减掉 O 的坐标；直接拿三点坐标做差时别漏掉这一步；
  2. 符号只认三态：正数、零、负数分别对应左转、共线、右转，不要在整数版判断里写 cross > 1e-9 这种浮点条件；
  3. 顺序不可交换：OA×OB = −OB×OA，把 A、B 写反符号整条翻过来——凸包弹栈条件写反，得到的就会是一个凹多边形。

前 3 行与上面三帧一一对应，可以直接心算验算。第 4 行是「点在线段上」：先叉积为零再查包围盒。第 5 行是溢出边界的实测数字——坐标放到 1e9，叉积已经到 2×10¹⁸，离 long long 的上界 9.22×10¹⁸ 只剩四倍多一点的余量。最后两行是对拍结论：200 组随机点，整数叉积的结果与两套独立写出的浮点几何定义逐组一致。

这套对拍的生成器也值得看一眼。方向测试每次随机造三个 −40..40 的整点；在线段测试里，偶数组走一条特殊路径：先随机方向向量 D 与倍数 den，再令 B = A + den·D、P = A + num·D（num 从 0 到 den 任取），于是 P 保证落在线段 AB 上，而且坐标全是整数，不引入任何舍入。奇数组则完全随机，P 大多数不共线，偶尔共线但落在延长线上——正好覆盖「共线却不在段上」这个分支。两边分别用整数包围盒判据与浮点参数 t 判据，结论必须一致；若哪天把包围盒的四行漏掉两行，奇数组里那些共线错位的点就会把错误抓出来。

cb_orient_area_brute 用「有向面积」这条路：t1 = ax·by、t2 = ay·bx，差就是平行四边形的有向面积。它与斜率版互为印证——一个走除法、一个走乘法，都在 long double 里带相对 eps。两份暴力同时与整数版一致，才敢说「符号 = 转向」这件事在整数域里是被机器证实过的，而不只是我们抄来的公式。

27.3 能用整数就别用浮点：eps 的两头风险

既然浮点斜率也能算方向，为什么还要写整数叉积？因为浮点把「精确的三态」变成了「带误差的近似三态」。判断两条射线是否共线，本质上是在问 k1 == k2 或 ax*by == ay*bx；浮点里这两边都可能是 1.0000000000000002 对 1.0。你要引入 eps：差小于 eps 就算相等。于是 eps 本身成了一个必须选对的常数。

语法规则语法规则：浮点比较的三条纪律
  1. 几乎相等用 fabs(a-b) < eps，不用 a == b；eps 取 1e−9 到 1e−12 这一档，取决于坐标量级和运算次数；
  2. 共线判断用相对误差更稳：fabs(cross) <= eps * (fabs(t1) + fabs(t2) + 1)，大坐标和小坐标用同一把尺子；
  3. 整数输入就用整数叉积：坐标是整数、乘积装得下 long long 时，整数版没有 eps、没有舍入、没有争议。

这份暴力版把竖直线单独列出，其余情形比较斜率 k1、k2，最后乘上两个分母的符号还原成转向。它和整数叉积在 200 组随机整数数据上一致（第 27.2 节 output 的最后两行），这正说明两条路算的是同一个几何量；区别只在：这条路要背 eps，整数路不用。

eps 该取多少没有放之四海皆准的数：它取决于坐标量级、运算次数和题目给的精度。坐标在 1e3 以内、只做几次加减乘，1e−12 通常够用；坐标到 1e9、中间又做了几十次浮点运算，误差可能累积到 1e−7 量级，这时 1e−9 都可能太小。更稳妥的写法是始终把判定写成相对量——fabs(v) <= eps * (|t1| + |t2| + 1)，让尺子随数据大小自动伸缩。还有一种常见的自欺：在整数数据上用浮点算，结果「大部分时候对」，于是把偶尔的临界错误归咎于「数据太刁」；正确态度是看到临界错误就回头检查：这个量能不能用整数精确算？

工程惯例工程惯例：整数输入就用整数几何

坐标、边长、面积若为整数，优先把判定改写成整数乘积比较：点在线段上用叉积为零加包围盒，共线用两个整数乘积相等，点在圆内用距离平方比较。这不只是「避免浮点麻烦」，它还让对拍的结论变得可证：整数运算没有舍入，两个独立实现若给出同一个整数，就没有精度灰色地带。代价是偶尔要自己处理倍数与溢出——但这比在 eps 上赌运气划算得多。

陷阱你怎么会被坑到：eps 选大错判，选小死循环

（你会看到什么）用浮点做「点是否在多边形边上」时，你把 eps 从 1e−10 调到 1e−6，原本 WA 的临界数据过了；可另一些离边界很近的点也开始被判成「在边上」，答案悄悄偏掉。反过来，把 eps 设成 0 或 1e−18，本该共线三点因为 1e−16 的舍入差被判成不共线，射线法在顶点上反复横跳，某些二分/迭代写法还会因为永远达不到收敛条件而卡死。 （你会怎么误判）你会以为 eps 是「越小越精确」的万能旋钮，或者干脆抄一个 1e−8 到处用。 （真相）eps 是尺子：比坐标量级和运算累积误差小一个合适倍数才对。1e−6 在坐标 1e9 的题里会把 1000 单位以内的点全算重合；1e−18 小于 long double 在百万次运算后的误差，等于没设。正确做法只有两条：整数输入就走整数几何，根本不需要 eps；非用浮点不可时，用相对误差并把 eps 与题目精度要求绑定，同时在临界数据上实测。

陷阱你怎么会被坑到：坐标 1e9，叉积 2e18，离上界只剩四倍

（你会看到什么）题目说坐标绝对值 ≤ 1e9，你放心地写 (a.x-o.x)*(b.y-o.y) - (a.y-o.y)*(b.x-o.x)，还用 int 存中间结果。样例坐标小，全过；大数据上输出一堆看似随机的数。 （你会怎么误判）你以为「坐标 1e9，long long 有 9e18，肯定装得下」。 （真相）装的是叉积不是坐标。单个乘积是 1e18，两个乘积相减最坏到 2e18；更要命的是若中间用 int，1e18 这一乘法本身就已经溢出。output 第 5 行是实测：坐标 ±1e9 时叉积 2×10¹⁸，long long 上界 9.22×10¹⁸。规则：点坐标用 long long，叉积也用 long long，并在乘之前确认量级；若坐标到 1e18，就要 __int128 或换思路。

万一题目给的坐标是实数怎么办？这时整数几何用不上，只能走 long double，并接受「共线」永远是一个带 eps 的近似判断。两条纪律能降低翻车概率：第一，全程只用一种容差，把 EPS 写成常量而不是散落的 1e−9、1e−10；第二，尽量把判定化成不需要开方、不需要三角函数的乘积式，每多一次超越函数就多一份误差。还有一条经验：若实数只有有限位小数（例如三位），可以整体乘以 1000 化成整数再算，最后再缩放回去——这是「能用整数就别用浮点」在工程上最实用的一种变形，代价只是要确认放大后的叉积仍在 long long 上界内。

27.4 点在线段上、线段相交、点在多边形内

叉积一旦能判方向，三个常见判定就都是它的组合。先把最基础的「点在线段上」写死：

为什么不能只查共线？因为共线只说明 P 落在直线 AB 上，可能远在 A 的左边或 B 的右边。四行包围盒把 P 钉在 A、B 之间。程序里另一半随机数据故意只生成共线但在线段外的点，专门打这个坑（见 main.c 的偶数/奇数组分工）。

线段相交判定是叉积的第二次出场。记 d1 = orient(A,B,C)、d2 = orient(A,B,D)、d3 = orient(C,D,A)、d4 = orient(C,D,B)：若 d1·d2 < 0 且 d3·d4 < 0，两线段严格相交（互相穿过内部）；只要出现 0，就有端点落在对方所在直线上。把这四种方向值逐个看一遍，坑就很清楚了：

  • d1·d2 < 0 且 d3·d4 < 0：C、D 在 AB 两侧，同时 A、B 在 CD 两侧，两线段从内部穿过——这是最干净的相交；
  • 某个 d 为 0：例如 C 落在直线 AB 上。此时 C 可能在线段 AB 上（真的接触），也可能在延长线上（不算相交）。只有再调一次 cb_on_segment(A,B,C) 才能分辨；
  • 四个 d 全为 0：两线段共线。它们可能部分重叠、完全包含，也可能错开——方向值全是 0，单靠符号完全分不清，必须退化成「共线上的区间是否有交集」；
  • d1·d2 = 0 但 d3·d4 > 0：一个端点在对方直线上，但另一条线段堵不住它，通常不相交。
语法规则语法规则：线段相交的完整判据

先算四个方向值 d1..d4。第一步快速筛：d1*d2 <= 0 && d3*d4 <= 0 不成立就一定不相交。第二步逐项补漏：对每个等于 0 的 dᵢ，调用点在线段判定确认那个端点真的落在对方线段上；若四个 d 全为 0，改为判断两条线段在共线方向上的投影区间是否相交。只写第一步不写第二步，会把「共线但错开」误判成相交；只写第二步不写第一步，则退化情形漏不完。

注意这里的 d1*d2 也是整数乘法，不过 d 只有 −1/0/1 三态，乘积不会溢出——真正会溢出的是算 d 的那一步，仍然是 1e18 量级的叉积。

语法规则语法规则：点在多边形内的射线法

从待判点 P 向右水平射一条射线，数它与多边形边的交点个数：奇数在内，偶数在外。实现时只统计「边跨过射线所在水平线，且交点在 P 右侧」的那些边，典型条件是 (yi > py) != (yj > py) 且 px < xi + (py−yi)·(xj−xi)/(yj−yi)。整数实现把后一个分式通分，用叉积避免除法。射线恰好穿过顶点时，用「上开下闭」（yi > py 与 yj > py 一真一假）保证每个顶点只被数一次。

大白话射线法的直觉，以及转角法为什么等价

想象你站在 P 点，朝右边看，数眼前有多少条边挡着你。从很远处一路走到 P，每穿过一条边，你在「内/外」之间翻一次；翻奇数次说明 P 在里头，翻偶数次说明你在外面。转角法换了个说法：把多边形每条边对 P 张的有向角加起来，绕满一圈是 ±2π 就在内，是 0 就在外。两者是同一件事的两种计数——射线法数穿越次数，转角法数绕了几圈；整数实现里用叉积符号累加「上下穿越」，不必真的算 atan2。

第 2 帧是新手最容易错的地方：射线恰好经过多边形顶点，两条相邻的边都会被算一次，交点数虚增，奇偶性翻转。上开下闭规则 (yi > py) != (yj > py) 把「顶点在上」与「顶点在下」分成两种情形，保证每条跨过射线的边只贡献一次；水平边两端 y 相同，自然被排除。整数实现把交点横坐标的通分写成叉积，于是整个过程又回到本单元的原子操作。

射线法的两个退化点必须单独处理：射线穿过顶点（上面用上开下闭规则解决）和 P 恰好在边上（先用 cb_on_segment 判掉，直接返回「在边界上」）。竞赛题若把边界算作「在内」，这一步不能省。转角法在整数上更省心：从 P 出发依次看向各顶点，用叉积符号记录每次跨越正 x 轴的方向，累加「向上穿越」减「向下穿越」，只看结果是否为零；它不需要除法，也没有交点是否在线段上的麻烦。两种方法的结论必然一致——都在回答「P 被多边形绕了几圈」。

27.5 Andrew 单调链：排序之后，栈里为什么恰好是凸包

凸包是这一单元的重头戏。先把问题说清：给 n 个点，求最小的凸多边形，使所有点都在它内部或边上。Andrew 单调链的做法只有四步：按 (x, y) 排序 → 去重 → 从左往右建下链 → 从右往左建上链，两条链拼起来就是凸包。

大白话先建立一个画面

把所有点按横坐标排成一排，想象一根橡皮筋从最左点绕到最右点，贴着所有点的「下沿」走。它每遇到一个新点，就检查最后两段是不是「左转」；如果是右转或直行，中间那个点就被橡皮筋弹开。下沿走完再从右往左走一遍上沿。栈里留下的，正是橡皮筋真正碰到的那些点。

排序后立刻去重是第一个纪律：重复点若不去掉，弹栈条件会把它当成「拐点」，把链搞出莫名其妙的锯齿。n=0、1、2 单独返回：这些情形没有「凸多边形」可言，顶点就是它们自己（全部共线时两个端点）。第 42 行那个 int t = k + 1 是第二个纪律，上链必须给下链的最后一个端点留位置，否则收尾时会把它弹掉。

弹栈条件是 cross3(...) <= 0，注意是非严格：右转（负）和共线（零）都弹。共线被弹掉，意味着边上的中间点不进凸包——这正是本题约定的「共线点只留两端」。最后 return k - 1 是因为起点被写了两次，收尾要把重复的那一份去掉。

第 2 帧的 (0,2) 是竖边上的中间点，共线被弹；第 3 帧的 (0,4) 是右转被弹；第 4 帧看两条链如何衔接；第 5 帧是最终结果——图里 9 个点只剩 4 个顶点，与 output 第一行的演示对得上。

大白话极角排序与字典序排序是同一个故事的两种讲法

大纲里常说「按极角排序后栈里留下的是凸包」，那是 Graham scan：取最左下角为极点，把其余点按绕它转过的极角从小到大排，再用同一个「左转保留、右转弹出」的栈扫一遍。Andrew 把这件事拆成两条链：按 (x, y) 字典序排好后，下链从最左走到最右，上链从最右走回最左。极角排序要算 atan2，有浮点误差，共线时还要按距离补排序；字典序只用整数比较，所以竞赛里几乎都写 Andrew。两条路径维护的是同一个不变式：栈内相邻三点始终左转，任何破坏左转的新点都会把中间点顶出去。

极角排序为什么能行？把极点放在原点，其余点按极角排队后，从极点看出去的射线扫过整个点集。假设栈里已经是一段凸包边界，新点按极角顺序到来：若它与栈顶两点构成左转，它就在边界外侧，可以接上去；若构成右转或共线，它在当前这条边的内侧，栈顶点被这条新弦盖住，永远不可能成为最终凸包的顶点，弹掉它再检查前一对外壳——直到左转恢复。这个「新弦盖住旧顶点」的几何事实，就是弹栈正确的全部理由。Andrew 的字典序排序等价于把极角扫描拆成「上半平面」和「下半平面」两段：下链对应极角从 −90° 到 +90° 的那一段，上链对应剩下的那一段，两段在左右极值点处接上。

为什么对。 分两半论证。下链的不变式：处理完排序后的前 i 个点，栈里恰好是前缀的凸包下沿，且相邻三点都严格左转。初始 i=0、1 显然成立。处理新点 v[i] 时，若栈顶两点与它不构成左转，那么栈顶那个点落在「新点与前一点连线」的上方或线上，它不可能是整个前缀下沿的顶点，弹掉不会丢答案；重复弹到左转出现为止，再把新点压入，不变式恢复。上链同理，只是扫描方向反过来，保证上沿也严格左转。两条链在左右两个极值点处相接，拼成的闭合折线每个顶点都左转，因而是凸的；又因为没有点落在它外面（每个被弹的点都被证明在某条弦的内侧），它就是包含全部点的最小凸多边形。共线处用 <= 0 把中间点弹掉，得到的正好是「只留两端」的约定。

为什么快。 排序 O(n log n) 是主导项；扫描部分每个点至多进栈一次、出栈一次，while 的弹栈总次数不超过 n，所以是 O(n)。记忆口诀：** Andrew 是「排序 + 线性扫描」，n=1e5 的耗时几乎全在 qsort 上**。

陷阱你怎么会被坑到：忘了去重、弹栈写成 <、收尾多留一个点

（你会看到什么）三个坑的表现各不相同：重复点没去掉时，凸包顶点列表里冒出几乎重合的点；弹栈条件写成 < 0 时，边上的共线点全被保留，凸包顶点数比正确答案多；收尾忘了 k-1 时，输出第一个顶点出现两次。 （你会怎么误判）你会以为「多几个顶点也还是凸包」，因为画出来肉眼看不出区别。但下游算法（点在多边形内、多边形面积）会因此报错，或者对拍时顶点序列对不上。 （真相）这三个地方都是约定，必须写死：先按 (x,y) 排序并去重；弹栈用 <= 0（共线弹中间，只留两端）；上链从 m-2 开始扫、用 t=k+1 保端点；返回 k-1 去掉重复起点。全共线数据是最狠的试金石——正确答案只有两个端点，错一处的版本会给出三四个「顶点」。

共线点的处理策略要按题目要求切换，不能一律照抄。本单元采用「只留两端」：弹栈条件 <= 0，凸包顶点数最少，后续算面积、判包含都最省事。若题目要求「输出边界上的所有点」，改成 < 0（共线保留），但要在输出前把同一条边上的点按距离排好；若要求「顺时针输出」，把两条链的拼接顺序反过来即可。三种策略的正确性论证完全一样，变的是「哪些点算顶点」这个约定——所以务必把约定写在函数注释里，output 第一行那种「含共线点只剩 4 个顶点」的演示就是给接手的人看的证据。

边界规模也逐个扫过了：n=0 返回 0；n=1 直接返回那一个点；n=2 不论是否重合，去重后返回 1 或 2 个点；全部共线返回最左与最右两个端点（此时没有面积可言）。这些分支看着琐碎，却是评测数据里最爱放的东西——main.c 的单点演示和全共线演示正对着它们。忘了 n≤2 分支时，m<=2 之后的扫描会把同一个点反复压栈，输出里出现重复顶点，对拍的第一组就会炸。

27.6 凸包对拍：两个独立算法加一份枚举校验

只看凸包顶点画出来「像 convex」不算证据。本单元的对拍做了三重保险：Andrew 的结果与礼物包裹法给出的顶点序列逐点比对，再用枚举校验独立检查凸性、覆盖、极点三件事。礼物包裹法（ch_jarvis）每步扫所有点，挑出让所有点都在左侧的最极端一点，共线取最远——它慢，但正确性是「一步挑最极端」这句话本身，正适合当裁判。

校验函数 ch_verify 更直白：逐段查 cross3(h[i], h[i+1], h[i+2]) > 0（严格凸），逐点查它在每条边的左侧（覆盖），再对每个顶点枚举所有点对，找一个支撑方向使其余点全在一侧（极点）。全共线是单独分支：只有最左与最右两个端点算顶点。

固定种子 LCG、n 从 1 到 60、坐标 −30..30（小值域制造大量共线），三组演示分别是含边上点与内部点的点集、全共线、单点。任何一组不一致就打印轮次与两边顶点数并退出。

前六行是三个边界演示，第 7、8 行是对拍结论与观测到的最大顶点数。OK 200 是 M13 要的那一行：200 组随机点集，两个独立算法加枚举校验全部一致。

实验记录本机实测：三套对拍各自的规模与结果
  • 工具链：本机 gcc 16.1.0（C17，清单 flags 追加 -O2）；应用层另用本机 g++ 16.1.0（C++23，-O2）；
  • 命令（在各自例子目录）：gcc -std=c17 -Wall -Wextra -Wpedantic -O2 -g -Iinclude src/main.c src/<例名>.c src/<例名>_brute.c -o app，三套都零警告、退出码 0；
  • 数据：cross_basic 200 组三点与线段（坐标 −40..40，偶数组保证点落在线段上），convex_hull 200 组点集（n=1..60、坐标 −30..30），scanline_area 200 组矩形（n=1..30、坐标 −12..12）；全部使用固定种子 20261122u 的自实现 LCG；
  • 结果：三份 stdout 的最后一行都是 OK 200，stdout 连跑三次逐字一致、stderr 为空、退出码全 0，所以三行才敢进 output 块参与逐字对账。

这里有三条值得单独说的对拍纪律。第一，两条路必须真的不同：Andrew 是「排序 + 栈」，礼物包裹是「每步全扫取最极端」，它们没有任何共享的几何子过程；如果只把 Andrew 的弹栈条件从 <= 0 改成 < 0 当暴力，两边会在同一个共线坑里一起错。第二，数据形状要主动制造边界：凸包对拍的坐标只取 −30..30，60 个点挤在 61×61 的格子里，共线、重合、全共线频繁出现；若用 1e9 的大值域随机点，共线几乎不会发生，那个坑就永远测不到。第三，失败要能复现：一旦打印 FAIL 第 k 组，固定种子 20261122u 让你重跑同一组数据，把那组点单独抄进演示数组即可定位。

还要承认对拍的边界：它验证的是「两个实现在这 200 组数据上一致」，不是数学证明。正确性论证（上一节的不变式）与随机对拍是互补的两条腿——论证覆盖所有输入，对拍抓住你论证时没想到的约定错误。只靠其中一个都不稳。

为什么是 200 组而不是 2 组？因为几何错误往往是「条件组合」式的：共线且点在线段外、共线且点在线段上、重合点、全共线、单点、空输入……单独造一个演示数组只能覆盖你想到的那种，随机数据却会把条件搅在一起。200 组在小规模下几乎不花时间，却能把这些组合撞出来。反过来，也不必把对拍数据放大到 1e5：那里跑的是同一份算法，只是规模更大，不会暴露新的约定错误。对拍要「小而密」，压测要「大而少」，两种实验目的不同，别混成一份程序。

27.7 扫描线：把二维面积变成一维覆盖长度的积分

现在换一个维度上的思路。求 n 个矩形的面积并，暴力是「每个单位格问有没有矩形盖住它」——坐标小的时候能用，坐标到 1e9 就彻底没戏。扫描线做的事，是把二维区域切成若干竖条，每条竖条里「被覆盖的部分」只是一条 y 方向区间的并集。

大白话用大白话说降维

拿一把竖直的尺子从左到右扫过去。每碰到矩形的左边界，就把这个矩形的 y 区间「加上」；碰到右边界，就「减去」。两根相邻扫描线之间，哪些 y 被盖住是不变的，于是那一竖条的面积 = 被盖住的 y 总长度 × 竖条宽度。把每个竖条的面积加起来，就是整个并集面积。二维面积 = 一维覆盖长度对 x 的积分——这就是扫描线的全部秘密。

扫描线的两个数据结构都很朴素。事件：每个矩形拆成 (x1, y1, y2, +1) 与 (x2, y1, y2, −1)；线段树：维护每个 y 区间被多少个矩形盖着（cover），以及由此得到的实际覆盖长度（len）。节点 p 管压缩后的第 l..r 个区间，也就是 y 轴上的 [ys[l], ys[r+1])：

注意线段树这里不存区间和，也不下传懒标记：每个节点只需要知道「这一段有没有被盖住」。cover > 0 时整段长度都算；否则叶子长度为 0、内部节点由两个儿子相加。这是扫描线专用线段树与普通区间和线段树最大的区别。

第 1 帧先把事件钉死；第 2、3 帧是「一竖条一竖条积分」的过程：x=0 到 x=2 贡献 4，x=2 到 x=4 再贡献 4；第 4 帧收尾。两个矩形只共享一条边，并集面积是 8，与 output 第 2 行一致。

同一根 x 上的事件先一次性全部应用，再算到下一根扫描线之间的面积；最后一根扫描线之后没有竖条，所以不贡献。lower_idx 用二分把 y 端点换成压缩下标，qr = lower_idx(y2) − 1 是因为节点管的是相邻两条 y 线之间的区间，而不是端点本身。

为什么对。 关键观察是：在两根相邻扫描线 x_i 与 x_{i+1} 之间，没有任何矩形的边界穿过，所以每个 y 点「是否被覆盖」恒定，覆盖长度 L_i 是一个常数。这一段里的并集正好是 [x_i, x_{i+1}) × (被覆盖的 y 集合)，由积分的可加性，它的面积就是 L_i × (x_{i+1} − x_i)。线段树维护的 st[1].len 恰恰是 L_i：每个被覆盖的 y 区间在树里 cover > 0，整段计入；重叠区间由 cover 计数而不是重复累加，所以不会把交集算两次。把所有竖条求和就得到整个并集面积。事件排序保证每根扫描线上的加减在同一次访问中全部完成，不会把中间状态算进面积。

主循环里那个「先按 x 分组、组内全部应用、再算一块面积」的写法，是这套论证的代码化。若改成每处理一个事件就算一次面积，同一根 x 上的中间状态会参与计算；虽然零宽竖条贡献为零、面积值侥幸不错，但逻辑上已经偏离了「相邻扫描线之间」这个前提。分组写法让每一块面积都对应一个明确的开区间 (x_i, x_{i+1})，日后换成数格点或求周长时也不会埋雷。

不用线段树行不行？最朴素的办法是每到一个 x 就把所有 y 区间重新合并一次，每次 O(n log n)，总共 O(n² log n)——n=1e5 完全没戏。线段树的作用就是把「重新合并」摊到每次事件更新里：一次更新 O(log n)，根节点永远是当前的覆盖长度。这是典型的「用数据结构把重复计算缓存起来」，和第 5 章线段树的思路一脉相承，区别只是节点里存的不是区间和，而是覆盖计数与覆盖长度。

暴力版把包围盒切成 1×1 小格，逐格问「有没有矩形盖住它」。它显然正确，但复杂度与坐标范围成正比——只能当对拍的裁判，不能当正解。

大白话为什么普通线段树在这里不够用

如果每个节点只存「区间和」，合并两个儿子的和会把重叠部分算两次——而矩形面积并最怕的就是重叠算两次。扫描线专用线段树靠 cover 计数解决这个问题：只要这一段还被至少一个矩形盖着，整段长度就一次性计入，管它盖了一层还是五层。换句话说，普通线段树合并的是「数值」，这里合并的是「集合的并」，所以 pull 里必须先看 cover 是否为零，再决定用整段长度还是两个儿子的长度。不需要懒标记也是这个原因：更新从来不是「整段加一个数再下推」，而是「这一层覆盖数增减一」，覆盖关系只在当前节点上记账。

扫描线的内存也很好估：事件数是 2n，压缩后的 y 数组最多 2n，线段树开 4×(2n) 个节点，每个节点两个 long long，n=1e5 时约 12.8 MB，加上事件与矩形数组约 6 MB，远低于常见 256 MB 限制。真正需要注意的是递归深度：线段树深度是 log₂(2n)，n=1e5 时不到 18 层，完全安全；但如果你把它改成「按原始坐标建树、区间长度 1e9」，深度会变成 30 层，数组规模却直接爆掉——又一次说明坐标压缩不是可选优化，而是算法能跑的前提。

27.8 扫描线的两个硬坑：开闭区间与坐标压缩

陷阱你怎么会被坑到：同 x 处先加后减，边界被算重

（你会看到什么）把事件排序写成「先按 x，再按 delta 从大到小」，也就是左边界 (+1) 排在右边界 (−1) 前面。在纯面积并里你多半看不出差别——因为同一根 x 上的事件被一次性应用，零宽竖条贡献 0。 （你会怎么误判）你会以为「顺序无所谓，反正矩形边界是零测集」。这句话在面积并里侥幸成立，但同一套事件一旦拿去数覆盖的整数格点、求并集周长或统计恰好被盖 k 次的长度，顺序反了就立刻出错：共享边的两个矩形会把公共边算重或算漏。 （真相）把约定钉死：矩形用半开区间 [x1,x2) × [y1,y2)，事件排序时 delta = -1 的右端点排在 delta = +1 的左端点前面。实现就是 cmp_event 里那一行 if (a->delta != b->delta) return a->delta < b->delta ? -1 : 1;。这样无论下游问题怎么改，事件流都保持「先离开再进入」的一致语义。

陷阱你怎么会被坑到：直接用原始 y 当下标，线段树当场爆掉

（你会看到什么）坐标到 1e9，你照搬「下标 1..n」的线段树模板，把 y 值直接当数组下标——程序连编译都过，一运行就访问违例；或者你开了一个 1e9 大小的数组，直接 MLE。 （你会怎么误判）你会以为「线段树开 4n 就行」，却没想过这个 n 是区间个数，而 y 坐标只是一些稀疏的端点。 （真相）必须先做坐标压缩：把所有矩形的 y1、y2 收集起来排序去重，得到长度 m 的数组 ys；线段树节点 p 管的是第 l..r 个相邻端点区间 [ys[l], ys[r+1])，数组只开 4m。事件更新前用二分把 y 端点换成下标（lower_idx）。好处是树大小只和矩形个数有关（m ≤ 2n），与坐标量级无关——这正是扫描线能处理 1e9 坐标的原因。

开闭区间的约定不只在 x 方向。矩形写成 [x1,x2) × [y1,y2) 时，y 方向的端点也被压缩成「相邻两条 y 线之间的区间」：事件给的是 y1、y2 两个端点，更新的是 lower_idx(y1) 到 lower_idx(y2)−1 这一段区间下标。若把端点也当成区间，一个高为 0 的「矩形」会凭空盖住一条线段；虽然面积为 0，但下游的覆盖次数统计会错。半开半闭还带来一个好处：两个共边矩形不会共享任何面积，公共边只在其中一侧被计入，所以 output 里 [0,2) 与 [2,4) 的并集恰好是 8，而不是 8 加一条边。

如果题目换成「数被覆盖的整数点个数」，同一套事件仍然能用：把每个矩形看作覆盖格子 [x1,x2−1] × [y1,y2−1] 的整数点，在压缩后的每条 y 区间上额外维护「 Covered 的整数点数」，面积公式里的长度换成点数即可。这时同 x 处先减后加的约定就从「无所谓」变成「必须」——共享边上的那一列点到底算谁的，完全由事件顺序决定。把约定写在比较器里，下游换题时不必重写事件流。

原理层讲完了，按本书的双层写法，还要给出应用层。下面这份 C++/STL 程序把同样的算法重写了一遍：容器换成 std::vector、排序换成 std::sort、去重换成 std::unique、二分换成 std::lower_bound，并且它自己也跑 200 组对拍（M14 要求的应用层程序参与对拍）。

reserve 一次把内存备好，避免 vector 扩容时的搬移；sort + unique + erase 三行就是坐标压缩的 STL 写法。手写版本里那二十行 qsort、去重、二分，在这里缩成了几行标准算法——这就是应用层的价值：逻辑不变，样板代码交给标准库。

相交的面积 14 = 9 + 9 − 4，共边的是 8，包含关系的面积是大矩形 100。这些演示专门打「重叠不算两次」「共边不算重」「空输入」三个边界，后面才是主菜 OK 200。

应用层给出与 C 版相同的 14 和 8，并自己完成 200 组对拍。两份 OK 200 合在一起说明：算法对、约定也对——C 版证明实现，C++ 版证明换个写法结论不变。

27.9 复杂度表：n、耗时与能过的规模对得上

这张表是本单元最该带走的东西。复杂度、能过的 n、本机实测耗时三者必须放在同一行读，只写「O(n log n)」等于没写完。「能过的 n」不等于「理论内存装得下的 n」：它还要算上时限、常数和这道题的输入形状。比如凸包在随机点上几乎顶点很少，栈操作次数固定是 n；但若数据特意造出全部点到凸包上（例如圆上的整点），扫描部分的弹栈次数也不变，复杂度不会退化——这是与快排那种「最坏形状会变慢」的算法不同的地方。面积并则相反，矩形重叠越多，线段树里 cover 的计数越大，但更新次数不变，所以重叠形状不改变复杂度，只改变 len 的计算结果。理解了这一点，表中的耗时列才不是一堆孤立的数字。

两张探针的 stdout 只放校验和、顶点数和面积——这些量跨次逐字一致，才好对账；耗时在 stderr 里。读数怎么理解？凸包 n=1e5 只要约 10 ms，主要花在 qsort；扫描线 n=1e5 要约 140 ms，慢一个数量级，原因是每个矩形产生两个事件、每次更新走 log(2n) 层线段树，还要排两次序（y 与事件）。所以同样是 O(n log n)，常数差距可以到一个数量级：题目给 n=1e5、时限 1 秒时两者都过，n 涨到 1e6 时凸包仍有余量，扫描线就要先看常数与内存了。

对照 alg01 的规模表：O(n²) 的暴力凸包在 n=1e4 就是 1e8 量级的叉积比较，基本出局；Andrew 的 10 ms 与扫描线的 140 ms 才是 n=1e5 这个量级能谈的选项。用 n 反推算法，落在这张表上就是两行读数。

两张探针也顺带回答了「原理层与应用层怎么选」。C 版手写线段树、qsort、二分，每个数组多大、哪一行会溢出都看得见，适合讲清每一步为什么在；C++/STL 版把同样的逻辑压缩成 vector、sort、unique、lower_bound，代码短、改需求快，但扩容策略、比较器开销都藏在标准库背后。实测两者同量级，说明 STL 在这里不是性能瓶颈；真正决定选择的是你要的是可审计的每一步，还是要的是快速落地的应用层。本书要求两层都写，正是因为它们回答的问题不同。

再把 n 往外推一格，图中读数的意义更清楚。n 从 1e5 涨到 1e6（10 倍），Andrew 的 qsort 比较次数涨约 20 倍，实测大致是 0.1–0.2 秒，仍在 1 秒线内；扫描线因为事件排序与线段树更新都带 log，且常数本来就大十倍，10 倍规模下就要按 1.5–2 秒估，得先看时限再决定要不要卡常。n 到 1e7 时两者都开始吃内存：凸包光点数组就是 1e7×16 字节 = 160 MB，扫描线的事件与树节点接近 500 MB——256 MB 的题这关就过不去了。复杂度告诉你曲线形状，实测常数和内存估算告诉你横轴能走多远，两者缺一不可。

工程惯例工程惯例：几何模板上场前先写死三件事

把叉积、弹栈条件、事件比较器这三处写成模板里的固定行，别临场改：叉积一律 long long 并在注释里写坐标上界；Andrew 的弹栈条件固定 <= 0 并配去重；扫描线事件比较器固定「x 升序、同 x 时 −1 在 +1 前」。代价是失去一点灵活性（想要保留共线点的题要另写版本），收益是赛场上不会因为三态判断的符号写反丢掉整道题。这三条都写进本单元的 quiz，上场前过一遍。

小结这一节的要点
  • 叉积 OA×OB 的符号是转向（正左、负右、零共线），绝对值是平行四边形面积；坐标是整数且装得下时，整数叉积完全精确，不需要 eps；
  • eps 是把尺子：选大错判、选小死循环；非用浮点不可时用相对误差并在临界数据上实测；坐标 1e9 时叉积到 2e18，long long 只剩四倍余量，中间量必须用 long long；
  • Andrew 单调链 = 排序 + 去重 + 下链 + 上链；弹栈条件 <= 0 弹掉右转与共线中间点，t = k+1 保住端点，收尾 k-1 去重复；每个点至多进出栈一次，扫描部分 O(n)；
  • 点在多边形内用射线法（奇数在内）或转角法，上开下闭避开顶点、先判边界；线段相交先看四个方向符号，出现 0 必须补共线上的连线判定；
  • 扫描线把二维面积变成一维覆盖长度对 x 的积分：每个矩形拆成两个事件，y 坐标压缩后由线段树维护覆盖长度，竖条面积 = len × 宽度；同 x 处右端点先于左端点，坐标压缩让树大小与坐标量级无关；
  • 三套 200 组对拍都输出 OK 200，其中一份是完整的 C++/STL 应用层程序；实测 n=1e5 凸包 10.0–11.0 ms、扫描线 137.0–140.0 ms。

注自测题答案
  1. 叉积 = 2×5 − 3×4 = 10 − 12 = −2，是负数，所以从 OA 看向 OB 是右转，B 在右侧。坐标到 1e9 时，单个乘积就到 1e18，远超 int 的 2.1e9；int 乘法先截断，再赋给 long long 也救不回来。点坐标与叉积都必须用 long long，且两个乘积相减最坏 2e18，仍在上界 9.22e18 之内。
  2. 叉积为零只说明 P 落在直线 AB 上，可能远在线段之外。还要检查 P 的坐标落在 A、B 的包围盒内（对每个坐标分量，P 介于 A 与 B 之间），两步同时成立才在线段上。暴力版用「共线 + 参数 t ∈ [0,1]」的另一种写法验证同一件事。
  3. <= 0 把右转和共线都弹掉：共线时中间点不是凸包顶点，只保留两端；写成 < 0 会把边上的点全留下，顶点数虚多。t = k + 1 保证上链开始时不把下链的最右端点弹掉；return k - 1 去掉被写了两次的起点，否则输出里第一个顶点重复一次。
  4. 当某条线段的端点恰好落在另一条线段所在直线上时，相应方向值为 0，乘积判据会放行，但两条线段可能根本不相交（共线但错开、端点在延长线上）。补法是对每个为 0 的方向值调用点在线段判定：确认这个端点真的落在对方线段上，才算相交。
  5. 因为面积并里同一根 x 上的事件被一次性全部应用，两个事件之间的「竖条」宽度为 0，对面积的贡献是 0，所以顺序不影响最终答案。但同一套事件若拿去数覆盖的整数格点、求并集周长或统计恰好覆盖 k 次的长度，共享边会被算重或算漏；把「右端点先于左端点」写死在比较器里，能让约定在所有下游问题里保持一致。
  6. 坐标压缩把所有矩形的 y1、y2 收集、排序、去重，压成一个长度 m ≤ 2n 的有序数组 ys，线段树用下标 0..m−2 对应这些区间。因为被覆盖的是两条相邻 y 线之间的一整段，端点本身只是区间边界；用 lower_idx(y2) − 1 得到最后一个区间的下标，才能正确覆盖 [y1, y2) 内的全部区间。
