24.1 先看工程长什么样

这一单元讲的是字符串，但一半的坑不在算法里，在「你以为字符串比对很便宜」这个错觉里。比较两个长度 1e6 的串，暴力要逐字符看一百万次；把每个前缀压成一个整数之后，任意两段是否相等只剩一次减法。KMP 走的是另一条路：它不压字符串，而是让文本指针永不后退，靠一张 next 表在失配时把模式串滑到正确位置。两条路都在做同一件事——把「逐字符比」变成「查一个整数或跳一个下标」。照本书的规矩，先打开工程看文件，再谈公式。

字符串题在竞赛里还有一个特点：题意看着简单，边界却特别多。n=1、m=1、模式串比文本长、全相同字符、周期串、空串——这些情形在小样例上往往碰不到，评测机却专挑它们。所以本单元每份对拍都把 n 从 1 起、让模式串长度上限随文本走，并在小值域里制造大量重复；每份正解都在入口检查空指针与长度关系。你写模板时也该这么做：先把边界约定写成注释，再写循环。哈希、KMP、Z 三者解决的其实是同一个问题的三种形态——「已知一段文本，问某个模式或子串在哪、等不等」——读懂它们的差异，比背下三份模板更有用。

大白话先建立一个画面

把字符串想成一串珠子，每颗珠子有一个编号。多项式哈希就是给这串珠子算一个「加权总和」：越靠前的珠子乘的权重越大，像多项式里 x 的幂次。两串珠子如果加权总和一样，它们大概率是同一串——这就是用整数代替逐字符比对的全部想法。KMP 的画面不同：你拿一把梳子（模式串）在布（文本）上从左往右梳，梳齿卡住时，你不是把梳子拿回起点重来，而是利用「刚才梳过的那一段自己跟自己很像」这个事实，把梳子往后挪一点点。挪多少，就是 next 表告诉你的。

第 1 帧是动笔前的空目录。第 2 帧一次标出三套「正解 + 暴力 + 对拍」：include/ 放声明与约定，src/ 里正解与暴力互不共享任何函数，main.c 只负责造数据、跑两版、逐组比对、打印 OK 200。第 3 帧补的是本单元的两层写法与实验证据：kmp_stl.* 是 C++/STL 应用层（M14 要求），两份 perf_main.c 是 n=1e6 的计时探针，session-perf.txt 是真抓下来的终端记录。

工程惯例工程惯例：为什么哈希、KMP、Z 各自都要一份暴力

对拍有一条铁律：两版不许共享逻辑。本单元三份暴力分别是 strncmp 逐位置（hash_substring_brute.c）、strstr 式双层循环（kmp_match_brute.c）、以及独立的 z_brute_first。它们与正解没有一行公共代码，所以 OK 200 才有分量——它证明的是两个互不相信对方的实现，在同一批随机数据上给出了同一个答案。代价是三份重复劳动：写暴力要老实、要慢、要一眼能看出正确，不允许「优化」成另一个正解。

24.2 多项式哈希：把一串字符压成一个整数

先给定两个参数：底数 B 和每个字符的编号 val(c)。长度为 L 的串 s 的哈希定义为（注意哈希值里不存长度，长度是查询时由调用方另行给出的参数）

H(s) = val(s[0])·B^(L-1) + val(s[1])·B^(L-2) + … + val(s[L-1])

这就是「多项式」三个字的来历：把字符编号当成系数，拼出一个 B 进制数。实现里选 B = 911382323、字符编号用 unsigned char 的值，再配两套算术：一套在 unsigned long long 上自然溢出（等价于 mod 2^64），一套在 1000000007 上取模。

还有两个参数之外的提醒：把 val 记成字符本身还是记成 1..26 的编号，不影响正确性，但必须在同一个程序里统一。模式串与文本要用同一套哈希函数，本例两者都走 hash_ull_of / hash_mod_of；如果一边用 0..255、另一边用 1..26，所有比较都会错，而对拍的第一组就会 FAIL。这也是为什么头文件把哈希配置集中成两个宏——改一处，两边一起变。长度不进哈希值这件事也有后果："a" 与 "\0a" 在只按字符编号算的系统里可能同哈希（若把 \0 编成 0），所以比较前必须明确「比的是固定长度的子串」，这正是前缀公式里 len 参数不可省的原因。

两个哈希共用同一个底数、同一批字符编号，只是算术不同。单串哈希的递推式是 h = h * B + val(c)——每来一个字符，先把已有结果整体左移一位（乘 B），再把新字符放到最低位。

注意第 18 行的 unsigned long long：unsigned 乘法溢出不是未定义行为，而是按 2^64 取模回绕，这是 ULL 哈希能用的前提。如果写成 long long，溢出就是 UB，编译器可以在 -O2 下把它优化成你料不到的结果。第 25 行先乘到 unsigned long long 再取模，是为了避免 32 位乘法先截断——这与直方图那一单元「乘法前转 long long」是同一条纪律。

先把底数 B 的选择说透，因为这里藏着一个新手容易忽略的前提。我们要求 B 严格大于所有字符编号的最大值：若把字母编号成 0、1、2 而取 B=2，那么串 "ab" 的值是 0×2+1=1，串 "b" 的值也是 1——两个不同的串算出同一个整数，这不是概率碰撞，而是编码本身有歧义，就像十进制里不补前导零时 01 和 1 没法区分。本例 val(c) = (unsigned char)c 最大 255，而 B = 911382323，远大于 255，第一位就不会「进位」到别处。第二个要求是 B 不能是模数的倍数，也不能模 M 等于 0 或 1：B≡0 时所有长度 ≥2 的串哈希只由最后一个字符决定，B≡1 时哈希退化成字符编号之和，任意两个字母相同的重排串都会撞。第三，B 要足够大，让不同长度的串在多项式次数上就有区分度；太小会让短串的高位与长串的低位凑出同一个值。取一个接近 M 的大素数级别的数，是最省心的做法。

还要强调一个容易被忽略的事实：哈希相等对于相等的串是必然的，不是概率的。只要两个串逐字符相同、用同一套 B 和 val，递推式算出来的整数一定逐位相等——这是确定性。概率只出现在反方向：两个不同的串可能算出同一个整数。所以哈希可以用作「快速排除」：一旦哈希不等，立刻能断定字符串不等，不需要再比字符；只有哈希相等时才需要担心是不是撞了。双哈希做的就是把「担心」的概率压到可以忽略。

语法规则语法规则：哈希配置的三条固定写法
  1. val(c) = (unsigned char)c：先把 char 转成无符号，否则字节值 ≥128 时会变成负数；
  2. 递推恒为 h = h * B + val(c)，前缀数组写成 h[i+1] = h[i] * B + val(s[i])；
  3. 两套算术并行维护：ULL 那路直接乘，mod 那路每步取模；比较时两路都相等才算相等。

24.3 子串哈希的前缀公式：代数推导

单串哈希只会算整串。要支持任意子串 O(1) 比较，得先把所有前缀的哈希存成数组。定义 h[0] = 0，h[i+1] = h[i] * B + val(s[i])，于是 h[i] 是 s 的前 i 个字符的哈希。这跟「前缀和」的形态几乎一样，只是加法换成了「乘 B 再加」。

下面把前缀公式真正推一遍，不靠背。先用归纳证明 h[i] = Σ(k=0..i-1) val(s[k])·B^(i-1-k)：i=0 时两边都是 0；设 i 成立，则 h[i+1] = h[i]·B + val(s[i]) = Σ(k=0..i-1) val(s[k])·B^(i-k) + val(s[i])，正好是 i+1 项的展开式。现在拆 h[l+len]：

h[l+len] = Σ(k=0..l+len-1) val(s[k])·B^(l+len-1-k)
         = Σ(k=0..l-1) val(s[k])·B^(l+len-1-k) + Σ(k=l..l+len-1) val(s[k])·B^(l+len-1-k)
         = B^len · Σ(k=0..l-1) val(s[k])·B^(l-1-k) + Σ(j=0..len-1) val(s[l+j])·B^(len-1-j)
         = B^len · h[l] + H(s[l..l+len-1])

最后一步就是定义：第二个求和是子串自己的多项式。移项得到前缀公式

H(s[l..l+len-1]) = h[l+len] − h[l]·B^len

在 mod M 的算术里，减法可能出负数，写成 (h[l+len] + M − h[l]·B^len % M) % M；在 ULL 里，无符号减法按 2^64 回绕，直接减就是正确结果。B^len 用快速幂或循环预处理，本例长度最多 20，循环即可。

拿一个能心算的小例子把公式落住。取 B=10、val('a')=1、val('b')=2、val('c')=3，串 abca 的前缀数组是 h[0]=0、h[1]=1、h[2]=12、h[3]=123、h[4]=1231。现在要 s[1..3] = bca：按公式 h[4] − h[1]×10³ = 1231 − 1000 = 231，而 bca 按定义展开正是 2×100+3×10+1 = 231，两边对上。这个例子还顺手解释了为什么必须先乘 B^len：h[1]=1 是「a」在个位上的值，要把它挪回千位变成「a」在 abca 里的贡献，必须乘 10³。

模运算下的同一笔账也走一遍。取 M=101、B=10，串 abca 的 h 数组逐项取模：h[0]=0、h[1]=1、h[2]=12、h[3]=123−101=22、h[4]=22×10+1=221，221−202=19。要取 s[1..3]：10³ mod 101 = 1000−909=91，h[1]×91 = 91，于是 (19 + 101 − 91) % 101 = 29。直接算 bca = 231，231 mod 101 = 231−202 = 29，一致。注意这里每一步都把中间值收窄到 0..100，若等到最后才取模，乘积会先溢出 int——这正是 24.2 里强调过的「乘法前转换」在模世界里的翻版。

第 4 帧是全节的核心画面：要 substr，就是把右端前缀拿出来，减去左端前缀被放大后的那一份。一次减法，与子串长度无关。代码里 hash_equal 同时比较两路哈希，任意一路不同就判不等。

陷阱你怎么会被坑到：把减法的顺序写反

（你会看到什么）把 h[l+len] - h[l]*B^len 写成 h[l]*B^len - h[l+len]，短串上「好像也没错」，一旦做子串搜索就全线找不到匹配，打印的命中位置永远是 -1。 （你会怎么误判）你会去查底数与模板，怀疑模式串没算对，甚至怀疑暴力版有 bug——因为暴力版明明白白能找到。 （真相）前缀公式的被减项是右端前缀，减项是左端前缀放大后的值。顺序一反得到的是相反数，ULL 里是 2^64 减原值，mod 里是 M 减原值，绝不会相等。判断办法很简单：拿长度 1 的子串试一下，h[l+1] - h[l]*B 必须等于 val(s[l])，反了就是负数。

24.4 双哈希、模数选择与冲突概率

哈希是概率工具，不是确定性相等。两串不同却哈希相同，叫碰撞。要判断风险，先算数量级。

单哈希 mod 1e9+7：模数空间 M ≈ 1e9。对一对固定的不同串，碰撞概率约 1/M，看起来很小。但竞赛里你往往要比较两个串的所有子串：长度 1e5 的串有约 n²/2 = 5e9 个子串，量级已经超过 M。哪怕数据随机，按生日悖论，任意两子串撞上的概率约 1 − exp(−n²/(2M))，代进去 n²/(2M) ≈ 5，结果超过 99%。所以对 1e5 规模，单哈希 mod 1e9+7 不是"几乎不会撞"，而是"几乎一定存在某对子串撞了"——只是你不一定恰好查到那一对。这就是大纲里说的现实风险。

把「一对固定串」的概率说严谨一点也有好处。两个不同串的哈希之差是 Σ d_k · B^k 形式的非零多项式（d_k 是对应位置的字符编号之差），次数不超过串长 L−1。若底数 B 在模 M 下均匀随机取，这个多项式最多有 L−1 个根，于是碰撞概率 ≤ (L−1)/M；L=1e5、M=1e9 时约 1e-4。本例 B 是写死的，不属于随机底数模型，所以这个上界只作直觉参考；真实系统里两种风险叠加：随机数据下的生日碰撞，加上对手针对固定 B 的构造。ULL 那路把 M 换成 2^64，同样的上界变成约 1e5/1.8e19 ≈ 5e-15，小到可以忽略；但前面说过，2^64 不是素数，专门构造另当别论——这正是要把素数模一起叠上的理由。

双哈希把两个独立空间叠起来：ULL 提供 2^64，素数模提供 1e9+7，合起来约 2^94 ≈ 2e28。刚才那 5e9 个子串里存在碰撞的概率降到 5e9 / 2e28 ≈ 2.5e-19，可以放心当作不会。注意这里的前提是两套算术要真的独立：共用一个底数是可以的，只要模数互素、运算不同，碰撞需要同时满足两个方程。

为什么 1e9+7 这个数这么常见？因为它是素数，且 2×1e9+14 < 2^31 使得 a+b 在 int 范围内不会溢出（乘之前仍要转 64 位）。1e9+9 也是素数，常被拿来当第二个模。两个素数模当然也能构成双哈希，代价是每次递推两次取模——取模指令比乘法慢一个数量级；ULL 那路把其中一次取模换成自然回绕，同样的抗碰撞效果，常数更小。这里有个细节值得记住：底数必须同时小于两个模数，否则它在其中一个模下等于 0，那一整路就废了。本例底数 911382323 小于 1e9+7 也小于 2^64，安全。

还有一个初学者常犯的错：以为「模数越大越安全，所以随便选个大数就行」。模数必须是素数，否则环里的零因子会让多项式方程出现意外的根；随便找一个大合数，碰撞概率可能比 1e9+7 还差。同理，不要自己拿 rand() 在运行时随机底数却不做任何记录——底数随机确实能防针对，但程序输出不再可复现，对拍与 output 对账都会失效；赛场上的折中是「底数写死、两个模写死、再加一路 ULL」，靠空间量级而不是靠秘密性取安全性。

大白话用大白话说双哈希

单哈希像只给每串发一张「指纹卡」，卡上只有一个号码。号码位数有限，串一多，总有两个人的号码撞车。双哈希就是发两张卡：一张号码特别长（64 位），一张号码来自另一套编号规则。要让两个不同的串同时把两张卡都撞对，概率小到你在赛场上遇不到。所以双哈希不是「更精确的哈希」，而是「把碰撞概率从能感觉到的量级压到感觉不到的量级」。

生日悖论的账可以手算：把 N 个球丢进 M 个桶，某一对落进同一桶的期望数量约为 N(N−1)/(2M)。本例 N=20 万、M≈1e9，代进去得约 20——也就是说这 20 万个随机串里，平均能找到二十对 mod 哈希相同的串，找到一对几乎是必然事件。样本量取 20 万不是随手写的，而是 sqrt(2M)≈44721 的几倍，留足余量。排序之后相邻两项哈希相同就说明撞了，再用 strcmp 确认字符串不同（相同的字符串不算碰撞，那本来就该同哈希）。整个过程没有碰 ULL 那一路，所以找到的这一对是单哈希的受害者。

为什么不用两个素数模（比如 1e9+7 和 1e9+9），非要配一个 ULL？两条路都能把空间叠起来，取舍在常数与结构上。ULL 那路的乘法溢出由 CPU 直接完成，一条指令，不用除法取模——取模是慢操作，在 n=1e6、m=32 的探针里，双哈希只比单哈希慢 0～1 ms（见 24.10），这 1 ms 就是多算一路 ULL 的代价。而 ULL 的弱点也正是它的结构：模数是 2^64，不是素数，环里存在零因子；底数若是奇数，乘以底数在 mod 2^64 下是一个 GF(2) 上的线性变换，把 128 个 0/1 向量做一次高斯消元就能找出两个不同串使 ULL 哈希相同。所以 ULL 单独用不能抵抗刻意构造，必须配一个素数模；反过来素数模单独用又撞得太多。两者互补，才叫双哈希。

程序里真造了一组碰撞。做法是生日攻击：固定种子造 20 万个长度 7 的随机小写串，只按 mod 1e9+7 的哈希排序，找出哈希相同而字符串不同的一对。若双哈希有用，这一对在 ULL 那路必然分开。

接着排序并扫描相邻等哈希的项，把找到的那一对按三种哈希分别打印出来。随机数发生器是自己实现的 LCG，种子写死，所以重跑逐字一致——输出块才能参与对账。

前四行是那组真碰撞：oxuzvpb 与 wczmtdk 在 mod 1e9+7 下哈希同为 43429415，单哈希会把它们当成同一串；换成 ULL 那路，两个值差了一个数量级都不止，双哈希一比就分开。这就是「双哈希为什么更稳」最直接的证据。

陷阱你怎么会被坑到：模数选得太小

（你会看到什么）把模数从 1e9+7 换成 101、底数取 100（在 mod 101 下等于 −1）。算 "aa" 得 1×100+1 = 101 ≡ 0，算 "bb" 得 2×100+2 = 202 ≡ 0，两个明显不同的串哈希一模一样。输出块第五行就是这条实测。 （你会怎么误判）你会觉得「模数小只是碰撞多，数据随机就没事」——可底数 ≡ −1 时，任何由同一个字符重复偶数次组成的串哈希都是 0，"aa"、"bb"、"cc" 全撞，与随机性无关。 （真相）模数决定哈希值的取值空间，也决定多项式的代数结构。小模数不只是空间小，还会让底数的幂次很快循环，构造碰撞易如反掌。选模数的规矩：用大素数（1e9+7、1e9+9 这种量级），底数不要选 0、1 或模数的倍数；用 ULL 那路时别把「自然溢出」当免费午餐——2^64 是 2 的幂，环里有零因子，专门构造的话可以在约 128 个位置上解出一组 0/1 串使 ULL 哈希相等（思路是把溢出看成 GF(2) 上的线性映射，做一次高斯消元）。双哈希之所以稳，是因为攻击者要同时满足两套算术，难度陡增。

陷阱你怎么会被坑到：用 char 当下标，负号从哪来

（你会看到什么）写一张 256 项的计数表 cnt[256]，遍历原始字节时写 cnt[c]++，其中 c 的类型是 char。数据里一旦出现字节 0xFF，程序要么悄悄写到内存前面去，要么在边界检查打开时直接崩。输出块第六行是本机实测：(char)0xFF 是 −1，而 (unsigned char)0xFF 是 255。 （你会怎么误判）你会盯着「0xFF 不是 255 吗」想半天，或者以为这是编译器 bug——毕竟你从键盘输入的都是可见字符，哪来 0xFF。 （真相）本机 char 是有符号的，字节值 ≥128 时转成负数，数组下标 −1 落在数组前面，属于未定义行为。修法只有一条：凡是拿字符当数值或下标，先 (unsigned char)c。本单元数据只用 'a'..'d'，所以这个坑不会自己冒出来——正因为不会冒出来，才值得提前写在这里。

24.5 哈希加二分：把 LCP 变成二十次比较

两个后缀 A[i..] 与 B[j..] 的最长公共前缀（LCP），暴力要一个字符一个字符比，最坏 O(n)。有了前缀哈希，可以二分答案：设 ok(k) 表示「两段长度为 k 的前缀哈希相等」，若 ok(k) 为真则所有更短的 k' 也为真（相等串的前缀当然相等），这就是单调性；二分出最大的 k 即可。每次 ok 是两次减法，复杂度 O(log n)。

注意二分上界取两边剩余长度的较小值；用 mid = lo + (hi-lo+1)/2 取上整，配合 lo=mid / hi=mid-1，才能在没有答案时收敛到 0 而不是死循环。输出块最后一行 lcp(A,0,B,0)=2 lcp(A,3,B,3)=7 来自 A = abcdefghij、B = abqdefghij：第 0 位起比到 'c' 与 'q' 就分叉（长度 2），第 3 位起两串都是 defghij（长度 7）。

把单调性写严谨一点，免得你以后自己写二分时把方向搞反。设 P(k) 为「长度 k 的两段哈希相等」。若 P(k) 为真且 k'>k，P(k') 不一定真；但若 P(k') 为真，则 P(k) 必真——因为两个长度 k' 的串如果逐字符相等，它们各自的前 k 个字符也逐字符相等，而前缀公式保证相等串的哈希相等。所以 P 的真值序列形如 真 真 真 … 真 假 假 …，分界点就是 LCP。二分要找的是最后一个真的位置，上界取两边剩余长度的较小值是自然的：超过这个长度根本不存在对应的子串。循环不变式是「答案在 [lo, hi] 里」，取上整的 mid 保证 lo<hi 时 mid>lo，于是 lo=mid 一定推进，不会出现 lo 原地不动的死循环；hi=mid-1 则保证区间严格缩小。这两条合起来才让 log₂(1e6)≈20 次迭代必然结束。

LCP 是很多串算法的通用零件：后缀数组里相邻后缀的 LCP 数组能回答「任意两个后缀的最长公共前缀」；求一个串里最长重复子串时，对后缀排序后看相邻 LCP 的最大值；比较两个后缀的字典序时，先求 LCP 再比较后面第一个不同字符。本单元只用到「哈希加二分」这一把钥匙，你以后在别的章节见到 LCP，可以直接把它当成一个 O(log n) 的黑盒。代价要记牢：黑盒依赖前缀哈希，所以它是概率的；而 KMP/Z 给出的匹配结果是确定的，两者不能混为一谈。

陷阱哈希相等的语义不能当成字符串相等

这里必须说清一条边界：哈希相等只是「极可能相等」，不是证明。做 LCP 二分时，若两串在某长度哈希相同但字符其实不同，二分会给出一个偏大的 k。双哈希把这个概率压到约 2^-94，赛内可以接受；但如果题目是交互式、裁判能根据你的查询动态构造字符串（对抗性输入），固定底数的哈希就可能被针对——那种场合要么用 KMP/Z 这种确定性算法，要么在赛前随机化底数并把底数写进程序（代价是输出不可复现，对拍要固定种子另行处理）。

24.6 next 数组：最长相等真前后缀

现在换一条完全不靠概率的路。KMP 的核心是 next 表，先把它定义死：

next[j] = 模式串前缀 p[0..j-1] 中，最长的「既是前缀又是后缀」的真子串长度

「真」指长度严格小于 j，否则自己等于自己没意义。例如 p = ababaca：p[0..4] = ababa，它的真前后缀里 aba 最长（前面三个字符与后面三个字符相同），所以 next[5] = 3；next[0] 特殊，规定为 −1，当哨兵用。

把 p = ababaca 的 next 逐格手推一遍，比看十遍模板管用：

j p[0..j−1] 真前后缀候选 next[j]
0 空串 无 −1（哨兵）
1 a 只有空串 0
2 ab a≠b，只有空串 0
3 aba 前 1 位 a = 后 1 位 a 1
4 abab 前 2 位 ab = 后 2 位 ab 2
5 ababa 前 3 位 aba = 后 3 位 aba 3
6 ababac a≠c、ab≠ac、aba≠bac 0

表里最容易错的是 j=5：真前后缀有 a（长 1）和 aba（长 3），取最长的 3；后面证明不漏解时，正是这个「取最长」在起作用。另一个极端是周期性模式 p = aaaa：next = −1 1 2 3。它说明「a 有多少个，就有多长的可复用前缀」，这类模式在暴力匹配里最费时（每个起点都要比到最后一个 a 才发现不对），恰好是 KMP 最划算的场合。

这段代码和匹配过程长得几乎一样——因为求 next 就是「拿模式串的前缀当文本，模式串自己当模式」做了一次 KMP。理解它的关键在于 i 是已经处理到的位置，j 是当前候选真前后缀的长度：字符相等就把两个指针一起往前推，失配就让 j 沿 next 回退，直到 j == -1（从头开始）或再次相等。因为 i 只增不减，构造 next 也是 O(m)：j 每次回退都沿 next 跳到严格更小的值，而 j 的增加全靠 ++i 顺带加一，总增加不超过 m，于是总回退次数也不超过 m。这是与单调栈同款的均摊分析——循环里套着 while，却仍是线性。

陷阱你怎么会被坑到：next[0] 写成 0

（你会看到什么）把 next[0] = -1 改成更「自然」的 0。程序编译通过，在无匹配的数据上偶尔输出正确答案，但在模式的第一个字符反复失配时卡死，CPU 占用 100%，程序再也不打印下一行。 （你会怎么误判）你会以为死循环出在主匹配的 while 上，于是去检查文本下标有没有前进——文本下标确实没前进，但根因在 next[0]。 （真相）失配处理是 j = next[j]。当 j=0 且字符不等时，若 next[0]=0，赋值后 j 还是 0，下一次比较还是同一对字符，永远卡住。写成 −1 后，j 变成 −1，if (j == -1 || ...) 直接进分支让 i、j 同时加一，文本下标前进一格，循环才有出口。口诀：−1 是「这里没有可复用前缀」的哨兵，不是可以省掉的细节。

陷阱失配写 next[j] 还是 next[j-1]：先把定义对清楚

（你会看到什么）从两份教程各抄一半：next 数组按 next[0]=-1、next[j] 表示 p[0..j-1] 的真前后缀来构造，却在失配时写成 j = next[j-1]；或者 next 按另一种约定（下标从 1 起，next[1]=0）构造，却照抄 j = next[j]。前者每次跳得比能跳的短，极端数据上退化到接近暴力；后者可能让 j 卡在 0 反复比较，甚至读到 next[0] 的垃圾值。 （你会怎么误判）你会以为「next 表嘛，差一格没关系」，把两种约定混着调试，越调越乱。 （真相）只有一条判据：看你的 next[j] 定义里包不包含当前比较的那个字符 p[j]。本书的定义是 next[j] 描述 p[0..j-1]（不含 p[j]），所以失配直接写 j = next[j]；代码里 next 数组多开一格（m+1），因为构造过程会顺手写一次 next[m]。若换成「next[j] 描述 p[0..j]」的约定，失配就得写 j = next[j-1]，初始化与数组长度也要跟着换。约定本身没有对错，混用才是灾难：抄模板时先把这两件事对齐。

24.7 KMP 匹配：文本指针为什么不回退

有了 next，匹配就是同一个循环再走一遍。文本下标 i 从 0 走到 n，模式下标 j 表示「当前已经匹配了前 j 个字符」。

换个角度能把这段代码看得更透：把 KMP 想成一台状态机。状态就是 j——「已经匹配了模式的前 j 个字符」；输入是下一个文本字符。若输入字符等于 p[j]，状态变成 j+1；否则查 next[j] 跳到新状态。j=m 是接受状态，表示找到一次出现。状态数只有 m+1，每读入一个字符做一次转移，所以 O(n) 是状态机的自然结果，不是什么巧妙的优化。next 表就是这台状态机的转移表在失配那一列的内容。这个视角在实现 AC 自动机时会原样复用——那里模式串从 1 个变成多个，next 表变成 fail 树上的转移。

还有一个常被问到的边界：找到一次匹配之后怎么办。本例只要首次位置，所以 if (j == m) { ans = i - m; break; } 直接返回。若题目要所有出现（包括重叠），命中后不能 break，而要 j = next[j] 再继续扫描。为什么要这样写？因为命中时 p[0..m−1] 与文本某段完全相同，这段文本自己的最长真前后缀长度正是 next[m]，把它当成新的 j，就等于把模式串滑到「尾部与开头重叠」的位置——重叠的那段已经确认相等，不用重比。例如文本 aaaaa 中找 aaa，命中位置 0 后令 j=next[3]=2，接着扫描就能拿到位置 1 和 2；若命中后直接令 j=0，位置 1 就会漏掉。

把演示数据 t = ababababaca、p = ababaca 走一遍，盯着失配那一刻 j 怎么跳。模式 p 的 next 是 -1 0 0 1 2 3 0。

第 2 帧是戏眼：失配发生在 p[5]，next[5]=3 说的是「p 的前三个字符 aba 和结尾三个字符 aba 一样，所以结尾那三个不用再比了，直接当新开头」。起点从 0 挪到 2，文本指针 i 一步没退。第 4 帧同样的事再来一次，起点挪到 4，最终在第 5 帧命中位置 4。两帧跳转合起来，把暴力需要「回起点重扫」的活全省了。

边界情形也逐个过一遍，免得模板一到 n=1 就翻车。m=1 时 next 数组只有 −1 0（构建过程会写 next[1]=0，所以分配 m+1=2 格）；匹配循环里 j=0，若首字符不等则 j=next[0]=−1，下一轮靠 j==−1 分支把 i、j 一起加一，文本正常前进一格。n<m 时入口直接返回 −1，不会进循环。文本全相同、模式末尾不同这种最坏形状，前面已经用量测说明它不退化。空模式（m=0）在竞赛题里通常按约定返回 0，本例直接返回 −1；两种约定都可以，但要和对拍的暴力版保持一致——这也是为什么三份暴力都独立写了入口检查。

为什么不会漏解：归纳证明

这一步必须真写，不能拿「经典算法肯定对」糊弄。记匹配开始时循环顶部的不变式为：

存在起点 s = i − j，使得 t[s..i−1] = p[0..j−1]（前 j 个字符已经在 s 处对齐）。

初始：i=0、j=0、s=0，长度 0 的前缀相等，成立。

字符相等分支：t[i] = p[j]，由不变式 t[s..i−1] = p[0..j−1]，两边各接一个相等字符，得 t[s..i] = p[0..j]，于是 (i+1, j+1, s) 满足不变式，且 s 不变。

失配分支：设 k = next[j]（k < j，因为 next 是真前后缀）。由 next 定义 p[0..k−1] = p[j−k..j−1]；由不变式 t[s+j−k..s+j−1] = p[j−k..j−1]。两式拼起来得 t[s+j−k..s+j−1] = p[0..k−1]。令新起点 s′ = s + j − k、新 j′ = k，则 t[s′..i−1] = p[0..k−1]，不变式恢复。由于 k < j，有 s′ > s，起点严格右移，所以 j 的回退次数有限，不会死循环。

关键是「被丢掉的起点不可能成为答案」。设 s < u < s′ 是某个被丢弃的起点，记 L = i − u（它在 i 之前已经能对齐的字符数）。由 s′ = s+j−k 且 u < s′，得 L > k；又由 i − s = j 得 L < j，所以 k < L < j。若 u 真能匹配出一个完整出现，那么在 i 之前它必须已经对齐 L 个字符，即 t[u..i−1] = p[0..L−1]；而由不变式，t[s+j−L..s+j−1] = p[j−L..j−1]。同一段文本的后 L 个字符，既等于 p[0..L−1] 又等于 p[j−L..j−1]，于是 p[0..L−1] = p[j−L..j−1]，说明 L 是 p[0..j−1] 的真前后缀长度。可是 L > k，这与 k 是最大的真前后缀长度矛盾。因此所有 s < u < s′ 的起点都不可能匹配，丢弃它们是安全的。

复杂度：i 全程只增不减，共 n 次；j 每次失配至少回退一步，但 j 的每次增长都伴随 i 的增长，所以 while 的迭代次数是 O(n)。代价是 next 构造 O(m)，总 O(n+m)。若要求所有出现位置，命中后写 j = next[j] 而不是 break，让模式串继续往后滑——重叠的出现也能拿到。

大白话把这一段证明压缩成一句话

失配时，你已经知道「模式串的前 k 个字符」和「刚匹配过那段文本的末尾 k 个字符」是同一串。把模式串滑到让这 k 个字符重新对齐，就不用回头重比；而 next 取的是最大的 k，所以夹在中间那些更短的滑动位置根本不可能配出答案——它们要是能配，k 就不是最大的了。一句话：最大可复用前缀既保证了省事，也保证了不漏。

24.8 Z 函数：另一条线性路

KMP 的 next 描述的是「模式串的每个前缀，自己有多长的一段首尾相同」。Z 函数换个角度：对串 s，z[i] 是 s[0..] 与 s[i..] 的最长公共前缀长度，约定 z[0] = n。z[i] 直接回答「从 i 开始的子串和整串开头像不像、像多长」。

维护「目前找到的最右 z-box」[l, r]：若 i 落在盒子内部且 z[i-l] 没越过盒子右端，就能直接抄答案；否则从 k = r-i+1（或 0）开始暴力往后比，比完更新盒子。每个位置要么被抄一次，要么把 r 往右推一次，所以总 O(n)。严格说法：进入 else 分支时，内层 while 的起点是 r-i+1（i 在盒子内）或 0（i 在盒子外，此时更新 l=i、r=i+k−1），每一次成功比较都让 r 增大 1；r 全程单调不减且不超过 n−1，所以内层比较的总次数 ≤ n。外层循环 n 次，加起来 O(n)。这与 KMP 的「i 不回退」是同一种均摊思路，只是这里不回退的是盒子右端。

看一组小数据的 z 值找感觉：s = abacaba，z[0]=7（约定），z[1]=0（开头是 a，s[1] 是 b），z[2]=1（从 2 开始 acaba 与开头 ab... 只有首字母 a 相同），z[3]=0（c 对 a 不等），z[4]=3（从 4 开始 aba 正好是开头三个字符），z[5]=0（b 对 a 不等），z[6]=1（末尾 a 等于开头 a）。写成数组是 7 0 1 0 3 0 1。中间那个 3 就是最右的 z-box：它让后面几个位置可以直接抄 z[i-l]，省掉重复比较。

Z 与 next 的等价关系也能用这组数验证。对 p = ababaca，逐位算得 z(p) = 7 0 3 0 1 0 1。按 next[j] = max{k<j : z[j−k] ≥ k} 算 next[5]：试 k=3，z[5−3]=z[2]=3 ≥ 3，成立；k=4 需 z[1]≥4，但 z[1]=0，不成立，所以 next[5]=3，与手推一致。这个公式不只是数学玩具：有些模板先用 Z 求出 z 数组，再 O(m) 推出 next，这样同一份 z 既能做整串匹配又能做单串前缀匹配；代价是 Z 需要 O(m) 额外空间，而直接构造 next 只要 O(1) 额外空间（除 next 本身）。

陷阱你怎么会被坑到：把 i+z[i] 的边界写成 z[i]

（你会看到什么）把第 15 行改成 while (k < n && s[k] == s[i+k]) k++;。短串上照样输出，长串靠近末尾时突然读到数组外面，轻则 z[i] 算出离谱大数，重则访问违例退出码 3221225477。 （你会怎么误判）你会去检查数组开得够不够大，甚至把 n 再加 10 试试——加完还是崩，因为越界的是 s[i+k] 的下标 i+k，不是 z 数组。 （真相）比较的两个下标是 k 和 i+k，两个都不能越过 n−1。写成 k < n 只管住了左边，右边 i+k 在 i>0 时更早越界。正确写法是 i + k < n，它同时约束了两边（因为 i≥0 时 i+k ≥ k）。同一个陷阱在 KMP 里对应「先判 j==−1 再访问 p[j]」——凡是两个下标一起走，检查的必须是较大的那个。

Z 与 KMP 的关系有两层。第一层是信息等价：next[j] 是 p[0..j−1] 的最长真前后缀，而 z 数组的 z[j−k] ≥ k 恰好表达 p[0..k−1] = p[j−k..j−1]，于是 next[j] = max{k<j : z[j−k] ≥ k}——next 能从 z 算出来。第二层是用法不同：KMP 带着一个状态 j 从左到右扫文本，状态之间有依赖；Z 函数把模式串和一个分隔符拼成 pat#text，对整串一次性算出每个文本起点的匹配长度，位置之间没有依赖。把 text[i] 对应的 z[m+1+i] ≥ m 全部收集起来，就得到所有出现位置——与 KMP 完全相同的集合。

分隔符 s[m] = '#' 必须选一个不出现在模式和文本中的字符。本单元数据只用 'a'..'d'，所以 '#' 安全；如果处理的是任意字节流，就不能靠一个字符做分隔，得改成分别算 z 或用 int 序列。这也是 Z 函数相对 KMP 的一个小代价：它需要额外 O(n+m) 内存放拼接串和 z 数组，KMP 只要 next（O(m)）。

分隔符的作用值得多说一句：它挡住的是「从模式串内部开始、一路匹配进文本」这种假命中。假如没有分隔符，拼接串是 pat+text，在 i∈[1,m−1] 的位置可能算出 z[i] ≥ m（模式的某个后缀恰好等于模式前缀又接上文本），扫描循环若从 1 开始就会返回负的下标或错误位置。本实现从 i = m+1 才开始看，其实已经避开了模式区，但分隔符仍然必要——它保证 z[i] 在文本区不会「穿过模式边界继续匹配」，从而 z[i] 的长度恰好对应从文本该位置起能匹配的字符数。用 int 序列处理任意字节时，把分隔符换成一个数据里不可能出现的整数（例如 −1）即可，逻辑不变。

z[0] 的约定也要说清：本例取 z[0]=n，因为「整串与自身的最长公共前缀」就是整串长度；有的模板把 z[0] 设成 0 当作无用位，此时搜索循环与 next 推导的公式都要跟着调整。两种约定都自洽，错的是从一种模板抄了构建、从另一种抄了使用。Z 函数什么时候比 KMP 更顺手？当你需要的不是「第一个匹配位置」，而是每个文本位置开始能匹配多长——比如统计以每个位置开头的 LCP、求最短循环节、做字符串周期分析——Z 一次算完全部位置，KMP 则要配额外的状态记录。反过来只要首次出现，KMP 省内存、写起来也短。

24.9 对拍：三份 OK 200 与一层 C++ 应用

三份对拍工程的结构完全同构：固定种子 LCG 造 n∈[1,200]、m∈[1,20] 的小数据，偶数组把文本的一段抄进模式（制造命中），奇数组纯随机（制造失配），然后分别调用正解与暴力，任何一个位置不一致就打印组号并退出 1，全过才打印 OK 200。小值域 'a'..'d' 是故意的：它让 abab 这类强周期性模式频繁出现，专打 next 的边界与 z-box 的复制逻辑。

具体说，这套数据能逮住哪些 bug？第一，next[0] 写成 0 会让含 a 开头且首字符失配的组卡死——对拍有超时保护，卡死就是失败，不会悄悄放过。第二，失配写成 next[j-1]（约定混用）在周期串上跳得不够，虽然答案可能仍对，但某些构造会让文本指针反复回退（如果实现里手滑把 i 也退了），立即产生错误位置。第三，Z 函数写成 k < n 时，长度接近 220 的组有可能读到拼接串外，输出离谱的命中位置，与暴力一比就露馅。第四，哈希减法写反的组会全部返回 -1，而偶数组里明明植入了命中，第一组就会 FAIL。对拍的价值不是「证明正确」，而是「把错误变成可复现的那一组」：FAIL 行打印组号，改完源码重跑，同一组必然还在同一个位置——因为种子固定。

为什么是 200 组而不是 2000？这里是对拍，不是压测。n≤200、m≤20、值域 4，暴力每组的代价微不足道，200 组毫秒级跑完；种子固定在源码里，重跑逐字一致，所以 stdout 才能进 output 块参与对账。上一章的规模表已经说明：找反例靠的是数据形状（小值域、周期性、植入命中），不是数量堆砌。真正的大数据交给 24.10 的探针，两者分工不同。

Z 工程多比一路：它同时调用 KMP 实现，要求 Z、KMP、暴力三者给出同一个位置。这样「Z 与 KMP 结果一致」不再是口头断言，而是 200 组随机数据的逐组结论。

原理层用 C 手写是为了看清每一步为什么在；应用层该用标准库就用。C++ 的 std::string::find 本身就是一套优化过的串搜索（实现可能用 Boyer–Moore 或两路算法），赛题里如果只是「找一次模式串」，直接 find 比手写 KMP 省事且常数不差。真正需要自己写 KMP 的场合是：要在匹配过程中挂额外的状态（比如统计所有出现、配合自动机、作为 AC 自动机的一部分），或者要复用 next 数组的结构信息。本单元的应用层把三种写法放在同一份对拍里比：std::vector<int> 存 next 的手写 KMP、std::string::compare 的暴力、std::string::find 的标准库实现，三者对 200 组随机数据给出一致答案。代价是应用层多引入一层类型转换（size_t 与 ptrdiff_t），但换来的是不用自己管内存。这里顺带说清一个真会踩的坑：C++ 的 std::string::size() 与 find() 返回的是无符号 size_t，没找到时返回 npos（一个很大的无符号数）。若你直接把它赋给 int 再和 −1 比较，可能得到 0 或别的数，判断全错；正确写法是先判 == std::string::npos，再转成 std::ptrdiff_t 这种能表示 −1 的有符号类型（源码第 32 行就是这么写的）。另一个坑是把 int j 与 p[i] 的 size_t i 混着比，j==−1 时若先算 p[j] 会被隐式转成巨大的无符号下标，直接越界——所以 C++ 版每次访问都写 p[static_cast<std::size_t>(j)]，并且把 j == -1 放在 || 的左边靠短路保命。手写 C 版本用 int 下标没这事，但代价是自己确保长度不超 INT_MAX。

先交代「能过的 n」这一列怎么定。假设时限 1 秒、本机实测的毫秒数按上表，O(n²) 的暴力在 m=32 时每多一个数量级就多两个数量级的比较：n=1e6 是 6 ms，n=1e7 就是约 600 ms，n=3e7 接近 5 秒——所以暴力只在 n≤1e7 且模式很短时侥幸可行，一旦 m 也涨到 1e5，n·m = 1e11，直接出局。O(n) 的 KMP 在 n=1e6 只要 1–2 ms，即便 n=1e8 也只是百毫秒量级，瓶颈会从算法转到内存带宽。哈希的预处理 O(n) 与 KMP 同档，但它的强项是多次查询：预处理一次，之后每个子串比对 O(1)、每次 LCP O(log n)；若只有一次匹配，哈希并不比 KMP 省，反而多了碰撞概率这个心理负担。选择口诀：一次匹配用 KMP 或 Z，多次子串比对与 LCP 用哈希，模式串很多用 AC 自动机（下一单元）。

表里最该盯的是最后两行的对比。暴力在这个最坏形状下每个起点要比 32 次，1e6 起点就是约 3.2e7 次字符比较，实测 6.0 ms；KMP 的文本指针只走一遍，实测 1.0–2.0 ms。把 m 从 32 放大到 1e5、文本换成全 a，暴力会涨到 O(1e10) 直接超时，而 KMP 与哈希仍在一两毫秒——用 n 和 m 反推算法，落在这张表上就是两行读数。单哈希那一行的「1.0 ms」不能单独看：它快，但它在一个 1e5 串的所有子串里几乎必然有碰撞；双哈希多算一路仍只要 1.0–2.0 ms，这点常数换来碰撞概率从「必然」降到「2e-19」，是这场交易里最划算的一笔。

24.11 工程检查清单：上场前你要能答的六个问题

知识要能变成反应速度才有价值。下面六问是从这一节的坑里提炼出来的，合上书先自己答一遍，答不上来就回对应小节看证据。

第一问：给你 n 和 m，怎么选工具？ 先看查询次数。只问一次「模式串在不在文本里」，KMP 或 Z 函数是确定性的首选，O(n+m)，不怕对抗数据；如果同一份文本要反复问上千个不同子串是否相等、或者反复求 LCP，就先花 O(n) 建前缀哈希，之后每次 O(1) 或 O(log n)，这时候哈希的优势才发挥出来。模式串有成百上千个，别在 KMP 上叠循环，那是下一单元 AC 自动机的活。再看内存：双哈希前缀数组约 12n 字节（n=1e6 时 12 MB），KMP 的 next 约 4m 字节，Z 函数约 5(n+m) 字节；32 MB 环境里要先算这笔账。

第二问：数据全是同一个字符，会不会让 KMP 退化？ 不会。这是 KMP 与暴力最重要的分水岭。全 a 文本里找 a^31 + b，暴力的每个起点要比 32 次才发现末尾不同，是 n·m；KMP 的 j 在 0..31 之间来回，文本指针 i 只增不减，内层 while 的总迭代次数仍是 O(n)。实测那一行 6.0 ms 与 1.0–2.0 ms 的差距，就是在这个最坏形状下量出来的。哈希也不退化，但注意全相同串的所有子串都有相同哈希，比较时会「看似都相等」——这在概率模型下是对的（它们真的相等），对抗模型下则要警惕构造。

第三问：我就是想把 next[0] 设成 0，行不行？ 行，但整套约定要一起改。本书用 next[0]=−1、失配写 j=next[j]；若你用 next[0]=0、next[1]=0 的约定，失配必须写 j=next[j-1]，而且要保证 j=0 失配时有别的办法推进 i（通常写成 if (j==0) i++ 或把 −1 藏在别处）。两种写法都能正确工作，混用才会死循环或漏解。抄模板时先做一件事：拿 p=aaaa 在文本 aaab 上手推三步，看 j 有没有卡住。

第四问：对拍为什么要固定种子、还要打印组号？ 固定种子是为了让 stdout 逐字可复现，这样才能写进 output 块参与闸门对账；打印组号是为了把错误变成可复现实验。本单元三份 LCG 种子分别是 20261122、20261123、20261125，重跑结果一模一样。若你用系统时间做种子，程序每次输出都不同，output 块永远对不上，闸门会报 stale_output——这不是闸门苛刻，而是「不可复现的结论不是证据」。

第五问：时间紧，单哈希能不能凑合？ 看数据会不会被对手控制。如果输入是随机生成的、题目也不是交互式，单哈希 mod 1e9+7 在只比较少量子串时够用，快 0～1 ms；但如果题目允许构造数据，或者你要枚举一个 1e5 串的全部子串，单哈希几乎必然有碰撞，WA 会来得毫无征兆。双哈希多付的常数只有约 1 ms（24.10 的探针），换来的碰撞概率从「几乎必然」降到 2.5e-19，这笔交易在赛内几乎总是划算的。

第六问：Z 函数总是越界，先查哪里？ 先查内层 while 的比较条件是不是 i + k < n——只写 k < n 时，i>0 的 s[i+k] 会先越界。再查分隔符：拼接 pat#text 时 '#' 必须不出现在数据里，否则 z 值会穿过分隔符把模式串和文本连成一片，命中位置乱掉；处理任意字节流时不能用单字符分隔。最后查 z[0] 的约定：本例 z[0]=n，若模板里 z[0]=0，搜索循环与 next 推导都要跟着改，不能只改一处。

下一单元讲 Trie 与 AC 自动机：KMP 是一个模式串在文本上跳，AC 自动机把多个模式串的 next 挂到一棵 fail 树上——你在这里推的「最长相等前后缀」，到那里会换个名字再出现一次。

小结这一节的要点
  • 多项式哈希 H(s)=Σ val(s[k])·B^(L-1-k)，前缀数组满足 h[i+1]=h[i]·B+val(s[i])，于是 H(s[l..l+len-1]) = h[l+len] − h[l]·B^len；ULL 里直接相减（mod 2^64 回绕），mod 里补一个 M 再取模；
  • 单哈希 mod 1e9+7 在 1e5 串的全部子串上几乎必然碰撞（子串数 5e9 已超过 M）；双哈希把空间叠到约 2^94，实测碰撞概率降到 2.5e-19；程序里真造出一组单哈希碰撞，ULL 那路成功分开；
  • next[j] 是 p[0..j−1] 的最长相等真前后缀，next[0]=−1 是哨兵；匹配时失配写 j=next[j]（配套 next[0]=−1 的约定），文本下标 i 永不回退，总 O(n+m)；
  • 不漏解的归纳核心：k=next[j] 是最大可复用前缀，任何夹在旧起点与新起点之间的候选起点都会推出一条更长的真前后缀，与 k 的最大性矛盾；
  • Z 函数 z[i] 是 s[0..] 与 s[i..] 的 LCP，边界必须写 i+k < n；next[j]=max{k<j : z[j−k]≥k}，Z 与 KMP 在 200 组随机数据上结果一致；
  • 哈希加二分求 LCP 靠「哈希相等的长度集合是前缀闭合的」这一单调性，单次 O(log n)；
  • 实测 n=1e6、m=32：双哈希 1.0–2.0 ms、单哈希 1.0 ms、KMP 1.0–2.0 ms、最坏形状暴力 6.0 ms；三份对拍各打印 OK 200。

  1. 设 B=10、val('a')=1、val('b')=2。写出 s="abab" 的 h[0..4]，并用前缀公式求 s[1..3]="bab" 的哈希。如果减法的两项写反，会得到多少？

  3. p="aaaa" 的 next[0..3] 是多少？若把 next[0] 写成 0，在哪一种输入上会卡死？说出失配写 next[j] 还是 next[j-1] 的判据。
  4. 在 KMP 的失配归纳证明里，为什么要强调 next[j] 是「最大」的真前后缀？如果 next 里存的是次长值，证明的哪一步会断？
  5. Z 函数为什么必须写 i + k < n 而不是 k < n？Z 与 KMP 在信息上有什么等价关系？哈希加二分求 LCP 依赖的单调性是什么？
注自测题答案
  1. h[0]=0，h[1]=1，h[2]=1×10+2=12，h[3]=12×10+1=121，h[4]=121×10+2=1212。"bab" 的哈希 = h[4] − h[1]×10^3 = 1212 − 1000 = 212，展开验证 2×100+1×10+2=212。写反成 h[1]×10^3 − h[4] 得到 1000−1212=−212（ULL 里是 2^64−212），绝不等于 212。
  2. 长度 1e5 的串约有 n²/2=5e9 个子串，超过模数空间 1e9；按生日悖论任意两子串撞上的概率 1−exp(−n²/(2M))，代入后超过 99%，所以几乎必然存在某对碰撞。双哈希叠上 ULL 的 2^64 后总空间约 2^94，5e9 个子串里出现碰撞的概率约 5e9/2^94≈2.5e-19。程序那组碰撞只在 mod 1e9+7 下相同（43429415），ULL 哈希是 4599547993657720442 与 766217907938825628，明显不同。
  3. next[0]=−1；p[0..1]="aa" 的真前后缀 "a" 长 1，故 next[1]=1；同理 next[2]=2、next[3]=3，即 −1 1 2 3。若 next[0] 写成 0，当 j=0 且文本字符与 p[0] 不等时，j=next[0] 仍是 0，下一次还是同一对字符，i 不前进，死循环。判据：看 next[j] 的定义是否包含 p[j]；本书 next[j] 描述 p[0..j−1]（不含），故失配写 j=next[j]；若 next[j] 描述 p[0..j]，则要写 j=next[j−1]。
  4. 失配分支证明新起点 s′=s+j−k 后，要排除夹在 s 与 s′ 之间的起点 u。设 L=i−u，可推出 k<L<j 且 p[0..L−1]=p[j−L..j−1]，即 L 也是真前后缀长度；正因为 k 是最大的，才与 L>k 矛盾。若 next 存的是次长值，这个矛盾消失，无法排除被丢弃的起点，证明就断了——这也说明「最大」不是优化，而是正确性的一部分。
  5. 两个比较下标是 k 和 i+k，最大的是 i+k，所以要用 i+k < n 同时管住两边；只写 k<n 时，i>0 的 i+k 更早越界，long 数据上会读到数组外。等价关系：next[j] = max{k<j : z[j−k] ≥ k}，因为 z[j−k]≥k 正好说明 p[0..k−1] 等于 p[j−k..j−1]。LCP 二分的单调性是：若长度 k 的两段哈希相等，则所有更短长度 k'<k 的两段也相等（相等串的前缀相等），所以「相等」对 k 是前缀闭合的，可以二分。
