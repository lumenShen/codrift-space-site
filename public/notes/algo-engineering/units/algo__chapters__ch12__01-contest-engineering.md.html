28.1 先看工程长什么样

前面每个算法单元都有正解与暴力，验收门天天打 OK 200。这一节是收尾，没有「正解对暴力」的对象可打：它要交付的是三样工程制品——耗时对照（读得快不快、模得省不省）、模板库（能不能直接抄进考场）、排查清单（出错时按什么顺序动手）。所以三个目录的形态与前几章不同：fast_io 同一份 1e6 输入上跑三种读法，mod_cost 比较取模次数对耗时的影响，template_lib 是一份自包含的头文件加一个演示程序。先看它们怎么落进仓库。

第 1 帧是动笔前的形态：ch12 连目录都还没有。第 2 帧把三个例子一次摆齐——注意每个例子都不是单文件：哪怕只是测个读入速度，也按本册硬规定分成 include/ 与 src/，头文件写约定、源文件写实现，这样「换一种读法」时不动驱动。第 3 帧是四份清单：两份 C、一份 C++、一份模板演示；它们把正文里那些 output 块接上了真编译真运行的对账链。

本单元不强制每份清单都跑 200 组对拍——没有「正解 vs 暴力」的对象，硬凑一个反而是自我欺骗。全书累计的 M13 加码（每个算法单元一份 mode: run、输出 OK 200、n≥200）已经由前二十七节满足；这里只要求至少一份清单输出确定校验和，而且每份清单里的耗时都不进 stdout。这条纪律看个例子就懂：fast_io 的程序把校验和打到 stdout、把三种读法的毫秒数打到 stderr——校验和逐字稳定，可以对账；毫秒数每次不同，只进正文的实验块与终端会话。把这两类东西分开，是这个单元全部工程纪律的起点。

你也许会问：收尾这一节讲的东西这么「琐碎」，值得单独占一个单元吗？值得，因为竞赛里的失分大多不发生在「不会算法」，而发生在这些琐碎处——读入慢了半秒、取模多了一层、下标错了一位、关同步后混用了两套输出、卡在一题上忘了另一题。这些东西没有一条需要新算法知识，却每一条都能把一道本来会做的题变成零分。工程收益的特点是单次很小、累计很大：快读省下的几十毫秒在单题上不显眼，但四道题、每道题都少犯一个低级错误，总分就完全不一样。把纪律写成清单，就是让这些小收益不再依赖你当天的心情。

28.2 赛时时间分配：把五小时切成五段

大白话用大白话说时间分配

竞赛不是「谁算法懂得多谁赢」，是「谁在截止时间前把会做的都写对了谁赢」。你的脑子有三种状态：读得懂、想得出、写得对。它们不是同一时刻都能用——刚开赛时你读得快但还没进入状态，两小时后你写得熟但读题已经开始漏条件。时间分配就是把最贵的脑力留给最需要它的那一段：先花一点时间把题读准，再花整块安静时间想清楚，最后才是敲键盘和查错。

以常见的五小时四题赛制为例，把它切成五段，每段给一个能执行的分钟数：

段落 建议用时 这一段唯一的产出 超时信号
读题 15–25 分钟（四题通读） 每题一句话题意 + 数据规模 + 特殊约束 读第三遍还在纠结同一句话
想 每题 10–20 分钟 一个复杂度与 n 对得上的算法 + 正确性论证要点 想了 20 分钟还在换做法
写 每题 15–30 分钟 能编译、过样例的完整程序 边写边改设计超过两次
调 每题 5–15 分钟 样例全过 + 边界数据过 同一处改了三遍仍红
对拍 每题 5–10 分钟（有余力） 小数据暴力互打一轮，或至少手造三组边界 对拍本身写成了一个新 bug

四题乘下来大约 4 小时 40 分钟，留 20 分钟机动。这张表不是规矩，是默认值：你某一题读完就「哦，这是裸的并查集」，那就把想的十分钟省下来给难题；反过来，某题卡了 25 分钟还没写出第一版，就该强制切走。把决策画成流程图，赛场上你不需要回忆这张表，只需要按帧往下走。

把这张表摊到真实的一场比赛里，它长这样：开场二十分钟四题全读一遍，在题面边上写 n 和「看着像什么」；接着挑最稳的那题，十分钟想清楚、二十分钟写完、十分钟调完、五分钟手造三组边界，用时约五十五分钟。这时你手上有了一道确定能拿的分，心态就稳了。第二道略难的照同样流程走，花掉约七十分钟。剩下两小时二十分钟给剩下的两题——这时你已经没有「必须全做出来」的压力，可以放心在一道题上多想一会儿，也可以果断承认某题超出当前能力，把时间砸在另一题的卡常上。很多新手把四题平均分配时间，结果每道都写到一半；高手的时间分配是不均匀的，因为他们对不同题的信心本来就不均匀。记住一件事：评委按通过的题数算分，不按你写了多少行代码算分，一道写完的题胜过三道半成品。

第 1 帧的关键动作是排序，不是按题号顺序做：你最该先写的是「稳拿且分高」的那题，它给你信心与缓冲；难题留到最后，因为难题的多做十分钟，边际收益远低于稳拿题的十分钟。第 2 帧的「换题」箭头是整张图最值钱的一条：它是唯一一个允许你放弃当前思路的出口。第 3 帧把「写」和「调」分开，是为了防止你边写边调——那会把一段连续的 25 分钟切碎成十次上下文切换。第 4 帧把对拍放在最后，是因为它没有正解就不成立；先有能过样例的正解，对拍才有意义。

陷阱你怎么会被坑到：死磕一道题，把会做的题带进坟墓

（先说你会看到什么）开赛四十分钟，你还在第二题上改第五版代码，心里想着「马上就想出来了」；交卷后才发现第三题是你会的裸前缀和，根本没动过。

（再说你会怎么误判）你会把原因归给「那天状态不好」或者「题太毒」，然后下次照旧。

（最后说真相）你缺的不是算法，是一个硬超时闹钟：第 2 帧里那条「想 → 换题」的箭头没有被执行。对策只有一条写进流程的动作——想满 20 分钟还没写出复杂度与 n 对得上的方案，就把这题压到队尾，立刻开下一题；等你把会的都写完回来，经常会发现卡住的那题只是少看了一个条件。在时间分配上，「放弃」不是一个情绪决定，是一个预设阈值触发的机械动作。

工程惯例工程惯例：先写能过的版本，再写更快的版本

很多高手第一遍故意用最直白、最不容易错的写法（哪怕 O(n²)），确认题意和边界没问题之后，再把它换成复杂度对得上的版本，并对拍两版。这是工程惯例、不是标准：代价是写两遍、多花十分钟；收益是「题意理解错」和「实现写错」这两类错误被拆开——前者在第一版就暴露，后者由对拍兜住。时间紧时至少保留「先写对的、再想快的」这个顺序，别反过来。

28.3 卡常清单之一：输入输出的那一刀

卡常（卡常数）说的是同一复杂度下把常数因子压小。顺序永远是先证明算法对，再压常数；一个 O(n) 但写错的程序，快到 0 毫秒也是零分。输入输出是最常见于「我都 O(n) 了为什么还 TLE」的一刀：n 到 1e6 时，每个数多花 100 纳秒，总量就是 100 毫秒。

三种读法的差异集中在「把字符变成整数」这一步。getchar 快读自己写一个循环吞字符；scanf 每次调用都要解释一遍格式串；cin 默认为了让 cout 与 printf 混用不出乱子，每次读都要与 C stdio 同步一次缓冲。先看手写快读的最小形态。

这十行里有两件值得记住的事。第一，它不判 EOF：竞赛输入里 n 是给定的，读满 n 个就停，省掉每一次的流状态检查；自己写通用库时才需要补上 c != EOF。第二，它比 scanf 快的原因不是「getchar 本身快」，而是没有格式串解释——scanf("%d") 每次要把格式串推进一遍、处理空白字符、再处理可选符号。继续看同一份数据上两种 C 读法怎么并排跑。

make_data 用固定种子 20261122 生成 data.txt，这件事看着不起眼，却是整个对照实验能成立的前提：三种读法读的是同一串数，校验和才可能逐字相同；换一次种子，三份校验和一起变，但「谁快谁慢」的结论不该跟着变。如果你把种子换成 time(NULL)，今早跑出的 93 ms 和明早跑出的 96 ms 就没法放进同一张表里——数据变了，比较的基础也变了。可复现的数据 + 三次取值 + 只把稳定量写进 stdout，这三条合起来才是「实验」而不是「随口一测」。第 2 单元讲生成器时说过「种子写死在代码里」，这里正是那条纪律的延续。

这个结果值得说两句，因为它和很多人的印象相反。本机 getchar 是带线程安全锁的，逐字符调用有一点点额外开销；scanf 的格式串解释是实打实的负担；而关同步后的 cin 用的是自己的缓冲区，读整数时并没有传说中那么慢。别背结论，背方法：把同一份输入喂给三种写法，各自计时，看的是你这台机器、你这个输入规模下的数。顺带一句，若还嫌慢，下一步是把整个输入用 fread 一次性读进缓冲区再解析——那是「快读模板」的完全体，本例刻意保留 getchar 形态，是为了让你看清「跳过非数字 + 逐位拼接」这两层循环。

为什么要跑三次而不只跑一次？程序内 clock() 的分辨率是 1 毫秒，单次测量里夹着进程启动、文件缓存冷热、操作系统调度这些你控制不了的抖动；三次取值画成一个区间，比一个孤零零的数字诚实得多。实验块里写「93–95 ms」而不是「93 ms」，是因为前者描述了这台机器在这三天里真实的表现范围。还有一条容易忽略的纪律：耗时绝不进 output 块。output 块每次验收都要和真实 stdout 逐字对账，而毫秒数每次都不同，写进去等于给自己埋一颗定时炸弹；所以它只走 stderr、只进会话文件、只被正文引用。这条纪律在本册每一节都成立，你在自己的工程里也应该把「结论通道」和「观测通道」分开。

陷阱你怎么会被坑到：关了同步还用 printf

（先说你会看到什么）你按教程写了 ios::sync_with_stdio(false)，程序大部分时候正常，偶尔输出顺序乱掉：先 printf 的一行跑到后 cout 的一行后面，甚至读到的数和写出的数对不上。

（再说你会怎么误判）你以为是缓冲区没刷新、多线程、或者评测机有问题，开始到处加 fflush。

（最后说真相）关同步的语义就是「C++ 流与 C stdio 各管各的缓冲，互不同步」，从此两套函数混用不再保证顺序与一致性。修法只有两条路，二选一：全程只用 cin/cout（本例的做法），或全程只用 scanf/printf。中间态「只关同步不改风格」是最坏的——它把一个确定性问题变成了偶发问题。

工程惯例工程惯例：先写 cin，卡到 TLE 再换快读

竞赛里输入输出改写的代价很低、收益不一定高，所以惯例是先用最省心的写法把算法写完，等真正因为输入 TLE 了再换。代价是你要在代码里留一个容易替换的读入层（本例的 next_int 就是这样一个接缝）；收益是绝大多数题你不必为了「听说 cin 慢」而多写二十行还引入 bug。反过来，输入量到 1e6 以上、且你确认瓶颈就在读入时，别犹豫——三种写法在本例里只差几十毫秒，但放到时限 1 秒的题上就是过与不过。

28.4 卡常清单之二：少一次取模就是少一条除法

取模 % 在整数运算里是贵操作：编译成 64 位除法，延迟远高于加减乘。如果一段循环每轮都取模，n 一大，这些除法就排成了队。省取模的核心依据是模运算对加法、乘法都可分配：(a+b) % M == ((a%M)+(b%M)) % M，于是「每步取模」与「最后取一次模」在数学上等价——前提是你的累加器装得下中间和。

第 27 行的类型选择是整个技巧的命门：乘积最大 1e10，n=2000 万时总和约 2e17，unsigned long long 上限约 1.8e19，装得下；换成 int 早就溢出了。所以「延迟取模」不是无脑删掉 %，而是先算清楚中间量的上界，再用更宽的类型托住它。

分配律本身值得推一遍，免得你只记住「可以省」却不知道边界：对任意整数 a、b 与正模数 M，写 a = qM + r，那么 (a + b) % M 与 ((a % M) + (b % M)) % M 必然相等，因为 qM 这一整块对 M 取模为零。把这条性质从两个数推广到 n 个数，就是你眼前的循环。乘法同理，但更容易溢出：两个接近 1e9 的数相乘已经贴近 64 位边界，想用乘法延迟取模就得上更宽的类型甚至 __int128，不是所有题都划算。所以实战里「省取模」主要用在加法型累加上，乘法型要格外小心。

还有一个折中档位值得写进清单：当中间和装不下、但每步取模又太慢时，用「每 K 轮取一次模」。K 的选法有章可循——设单项上界 p、每轮累加 p、累加器上限 U，那么只要 K × p ≤ U 就安全，取满足条件的最大 K 即可。K 越大除法越少，但要留足余量给还没取模的尾巴；把 K 写成常量并在注释里记下推导，半年后你还能看懂为什么是这个数。本例算下来 K 可以取到整个 n，所以直接只取一次。

大白话用大白话说延迟取模

28.5 卡常清单之三：inline、循环展开与缓存局部性

剩下三项卡常有个共同点：它们大多是编译器的活，你只负责别挡路。inline 是给编译器的建议而非命令——现代编译器在 -O2 下会自己决定把小函数内联，手写 inline 的主要价值是把定义放进头文件而不触发重复定义（本册模板头的 static 就是这个用法）。循环展开同理，-O2 会自动展开规整的小循环；只有当你用 -fno-unroll-loops 做过对照、并确认瓶颈就在循环控制上时，手写展开才值得。

缓存局部性则是你真正能控制的：int a[1000][1000] 按行遍历是顺序访问，按列遍历是每次跳 1000 个 int（4000 字节）——后者会把缓存行反复冲掉。第 1 单元的 cache_effect 例子在本机实测过这组对照（顺序访问 vs 大步长访问），那里的读数可以直接拿来用：同一份数据、同一种运算，只改访问顺序，耗时能差出好几倍。这里不重复造数，只把结论接到卡常清单上。

机制说穿了不复杂：CPU 从内存取数不是一次取一个 int，而是一次取一条 64 字节的缓存行，大约是 16 个 int。按行扫描时，你刚取进来的 16 个数接下来全都要用，这一趟缓存行就值回票价；按列扫描时，你用掉这一行的第一个数，接着跳到 4000 字节之外取另一条缓存行，循环一圈回来时最初那条早被挤走了——每条缓存行只用一个数，带宽全浪费在搬运上。这就是「数组与缓存的局部性」这一条的全部故事。落到写法上有三件即刻能做的事：二维数组按行遍历；结构体数组优于数组的结构体（你要的是每个元素的几个字段，不是所有元素的同一个字段）；能用数组就别用指针串联的容器，因为 std::map 的节点散落在堆上，每次跳转都是一次缓存失效。最后一条也解释了 28.9 表里「n ≤ 1e6 别用 std::map 替代数组」——那不只是复杂度常数大，更是局部性差。

工程惯例工程惯例：先量后改，一次只改一处

卡常最容易犯的错是「一把梭」：同时改读入、改类型、改循环写法，快了不知道是哪一项的功劳，慢了也不知道是哪一项拖累。惯例是每次只动一处，跑三次取区间，记进实验块，再决定留不留。代价是迭代次数多；收益是每一条经验都能归因，下次换题时你知道该抄哪一条。-O2 是竞赛默认优化档，本册所有例子清单都追加它——先让编译器把能做的做完，你再去压它做不了的。卡常还有一条隐性成本别忘了：每一次改写都可能引入新 bug，所以每改一处都要重跑对拍；省下的那几十毫秒如果换来一次 WA，这笔账就彻底亏了。

编译器视角编译器视角：`inline` 是建议，`-O2` 是主力

在 C++ 里 inline 的语义是「允许同一函数在多个翻译单元各有一份定义」，编译器是否真的把它展开到调用点是另一回事；在 C17 里 static 函数放在头文件则天然每个翻译单元一份。本册模板头全用 static + 头文件实现，正是为了让编译器能在 -O2 下自由内联，同时避免链接期的重复定义。至于循环展开与向量化，参数由优化档决定：本机 gcc -S 可以观察 -O0 与 -O2 产出的汇编差异，但不要把「我写了 inline」当成「它一定被展开了」——要看汇编、看计时，不要看心愿。

28.7 调试套路：小数据对拍、输出中间量、assert

算法的 bug 分两种：编译期就死（语法、类型、链接）与跑起来才错。前者编译器替你找，后者才需要套路。三招按成本从低到高排：assert 最便宜，对拍最贵也最可靠。

第一招 assert：把「我认为一定成立」的东西写成断言，让它替你盯着不变式。比如二分里 assert(l <= r)、线段树递归里 assert(1 <= l && l <= r && r <= n)、并查集压缩前 assert(0 <= x && x < n)。断言失败会当场打出一个具体位置，比你在几百行之后看到一个错答案强得多。本机 C 的 assert 来自 <assert.h>，-O0 默认生效；-DNDEBUG 会把它编译掉——交付版别带这个宏，调试版也别把断言当错误处理。

第二招输出中间量：把循环里某个关键变量打到 stderr，看它是怎么一步步走到错的。为什么是 stderr 而不是 stdout？因为 stdout 常常是对账的「结论通道」，掺进调试行会污染证据链——这正是 fast_io 把校验和与耗时分开的原因。输出中间量最容易自我欺骗的一点是「看了等于懂了」：一定要预测「这一轮它应该等于几」再打印，预测与实测的差才是线索。

第三招小数据对拍：第 2 单元讲透的三件套，这里只强调它在收尾阶段的用法——规模要小、维度要刁。n 取 1、2、3、全相同、极端值，让暴力版一眼能算完、你能手算验证；再随机跑 200 组覆盖常规路径。对拍的输出必须是可判定的量（计数、校验和、合法性），不能是「看起来差不多」。

三招怎么配合？拿一个二分答案的例子走一遍：你先在判定函数里写 assert(l <= r) 和 assert(mid >= l && mid < r)，让越界的区间当场炸出来；样例错了就在每次二分后把 l、r、mid、check(mid) 四个值打到 stderr，看区间是不是按你预期的方向收缩；样例过了仍不放心，就写个 O(n²) 的暴力版，用第 2 单元的生成器跑 200 组小数据比对答案。三层防线各管一段：断言管「不变式被破坏」，中间量管「怎么走到错的」，对拍管「我没想到的路径」。注意断言与对拍不是一回事——断言只能证明你写下的那个条件成立，如果你连条件都写错了，断言也帮不上忙；对拍则拿一个独立实现当裁判，能抓到你根本没想到的错误类型。

调试实录调试实录：把「偶尔错」变成「必现」

间歇性 WA 最难查，因为它不给你稳定的现场。解法不是盯着代码看，而是把随机性赶走：固定种子让失败组号永远停在同一处。下面这份会话是真抓下来的，里面编译、运行、退出码一条不缺。读法三步：先看第一条命令怎么把三份源文件编成一个程序；再看 stdout 的第二行 OK 200 表示 200 组逐位比对全过；最后看 echo $? 的 0 表示进程正常退出。若你把种子改成 time(NULL)，第二行每次都不同——那份「偶发」就回来了。

陷阱你怎么会被坑到：用 print 大法debug，改完忘了删

（先说你会看到什么）你在循环里加了十几行 printf 找 bug，找到之后心满意足地提交——评测机报 Presentation Error，输出里多了一堆调试行。

（再说你会怎么误判）你会以为评测机对格式要求变态，或者怀疑自己漏看了某个换行。

（最后说真相）调试输出该走 stderr（评测通常只看 stdout），而且应该跟着一个能一键关掉的开关。把调试输出留在 stdout 里，等于把内部状态当成答案交了出去。修法：从第一行调试打印起就写 fprintf(stderr, ...)，收工时用 grep -n stderr 扫一遍，或者把这些打印包在 #ifdef LOCAL 里——本地编译时加 -DLOCAL，交付编译时自然消失。

28.8 RE / WA / TLE / MLE：四种症状的排查顺序

评测机给你的信息通常只有四个字母，排查顺序要按症状定，不能一律「重读题 → 改算法」。先认症状，再按下面的顺序动手，每一步都只验证一件事。

症状 先看什么 常见真凶 本机证据
RE（运行错误） 退出码与最后一次输出位置 空指针/越界、递归爆栈、除以零、mid=(l+r)/2 溢出 访问违例退出码 3221225477；栈溢出 3221225725
WA（答案错） 最小反例，而不是代码 边界 n=0/1、下标 1-index 混用、比较器写 <=、输出格式 小数据对拍 + 手算，定位到组号与下标
TLE（超时） 实际复杂度和 n 的乘积 输入太慢、复杂度选错、递归重复计算 fast_io / mod_cost 的三次耗时区间
MLE（超内存） 数组总字节数 × 元素大小 long long 当 int 开、邻接矩阵开到 1e5²、递归栈 256 MB 约能开 6700 万个 int
大白话用大白话说排查顺序

四种症状其实是四种不同的问题：RE 是「程序死了」，WA 是「程序活着但说错话」，TLE 是「说得太慢」，MLE 是「撑到站不起来」。死了先找尸体在哪（最后一行输出 + 退出码）；说错话先找一个最小的错话样本；太慢先算你到底做了多少次操作；撑不住先数你开了多少字节。先分清是哪一种，再动手，否则你会把内存问题当成算法问题改半天。

RE 的排查有个本机特有的好处：退出码是把死因写清楚了的。访问空指针/野指针是 3221225477（十六进制 0xC0000005），栈溢出是 3221225725（本机 Git Bash 把 $? 折成 127，闸门按无符号读数），abort() 是 3。程序要死前想留一行证据，打印后必须立刻 fflush(stdout)——走管道时缓冲区来不及刷，整段 stdout 会一起丢失。这几条数字来自本机实测，不要照抄到别的平台。

WA 的关键动作是把错例缩小：对拍打出「组 37 第 12 位不一致」，就手算那 12 个数上正解与暴力各走一遍。别一上来改算法——前二十七节里最常见的 WA 真凶不是算法错，而是边界（n=1、全相同）、下标（1-index 与 0-index 混用）、比较器（<= 破坏严格弱序）和输出格式（多了空格、少换行）。

TLE 先算账：n=1e6 时 O(n²) 是 1e12 次操作，这不是常数能救的，必须换算法；n=1e5 的 O(n log n) 大约 170 万次，瓶颈更可能在读入或取模——本单元的两张耗时表就是给你做这个判断用的。MLE 先数数组：int a[100000][100000] 是 400 亿字节，任何限制都装不下；该用链式前向星而不是邻接矩阵，该用 int 而不是 long long，该滚动数组而不是开满二维。

这四种症状在前几章都有实物，回头翻一遍比抽象记忆管用：第 3 单元 bad_comparator 里那个写成减法的比较器，在 int 全值域数据上让排序结果错乱，是典型的 WA——根因不是算法而是比较器；第 2 单元 uf_recursion 量过递归 find 在链状数据上撑到几万帧就崩，是典型的 RE——根因是栈深不是逻辑；本单元 fast_io 与 mod_cost 那两张表告诉你什么样的「慢」属于 TLE 里常量能救的那一档；第 1 单元的 amortized_vector 则提醒你，动态数组的扩容峰值内存往往是静态估算的两倍，MLE 要按峰值算而不是按最终大小算。把这几处串起来看，排查顺序就不是死记的口诀，而是一张指向前面各章的索引。

陷阱你怎么会被坑到：TLE 了就闷头卡常

（先说你会看到什么）你的 O(n²) 程序在 n=1e5 上超时，于是你换快读、删取模、加 inline，快了 20%，还是超时。

（再说你会怎么误判）你觉得「常数还不够小」，继续在循环里抠指令。

（最后说真相）你该算的是量级：1e5 的平方是一百亿次，再怎么卡常也差着三个数量级。卡常只在复杂度已经选对、且实测差距在几倍以内时才有意义；差着数量级就必须换算法。判断方法很机械——把 n 代进复杂度式算出操作次数，再拿本机的「1 秒约几亿次简单操作」折算成秒，先看这个估算，再决定是换算法还是卡常数。

28.9 「这题该不该做」：看数据规模反推

这是赛场上的元决策：同样一题，n≤20 和 n≤1e5 是两道完全不同的题。第 1 单元给过完整的规模表，这里把它压成一张「看到 n 就反应出做法」的速查表，并加上「什么时候该放弃」的判断。

看到的数据规模 先想到的做法 常见搭配 不该做什么
n ≤ 20 状压 / 搜索 + 剪枝 1<<n、子集枚举 别写 O(n!) 的裸排列
n ≤ 500 三方 / 区间 DP O(n³) 三重循环 别硬套单调队列优化
n ≤ 5000 平方 / 背包 O(n²)、二维 DP 别开 n×n 的 long long 数组
n ≤ 1e5 O(n log n) 排序、堆、线段树、Dijkstra 堆优化 别写 O(n²) 的暴力
n ≤ 1e6 线性 / O(n log n) 常数小 双指针、树状数组、快读 别用 std::map 替代数组
工程惯例工程惯例：用 n 给题打「值不值得做」的标签

通读四题后，给每题贴三个标签：会做（能在 10 分钟内说出复杂度对得上的方案）、规模（上表哪一档）、分数。先做「会做且规模有把握」的，再做「会做但常数紧」的，最后才碰「还没想出方案」的。代价是你得逼自己在读题阶段就判断，不能拖；收益是把有限的脑子用在能拿分的地方。「不该做」的判断不是认输——当 n=1e5 而你只会 O(n²)，这题在这一场就是不该做，把时间投给别的题是理性选择；等补完专题再回来，它就不是难题了。

还有一种「该不该做」的反向用法：用数据规模反推题意。题目说 n≤20 却要你「求最优方案」，八成是状压；说 n≤1e5 且有区间修改，八成是线段树或树状数组；说权值都是 0/1，八成是 0-1 BFS。规模是出题人给你的最大提示，它比题面文字更诚实。反过来，如果你设计的算法复杂度与规模差一个数量级，先怀疑自己读错了题，再怀疑题目出错了。

为什么出题人会「按规模配算法」？因为他的标准解必须在时限内跑完，而时限是固定的几秒。n≤20 时 O(2ⁿ) 才百万级，他自然敢出搜索题；n≤1e5 时他必须给你 O(n log n) 的题，否则自己的标程也过不了。所以数据规模不是随便写的装饰，它是出题人把标准算法的复杂度反过来编码给你的提示。读懂了这一层，你在赛场上的判断就从「这题我像不像做过」升级为「这个 n 指向的那一类做法，我会不会」。如果指向的做法你不会，这题在当时就是不该做——承认这一点，比花四十分钟硬想一个复杂度不对的方案划算得多。赛后回去补那一章，下次同规模题就是你的稳拿题。

注自测题答案
  1. 按第 2 帧的「想 → 换题」箭头，把这题压到队尾，立刻开下一道会的题；等把稳拿的都写完再回来。它是机械阈值，因为触发条件是预设的 20 分钟，不需要你临场评估「我是不是快想出来了」——情绪评估正是死磕的根源。
  2. 风险是你在考场上用错规模：比如 n=1e5 却选了 O(n²) 的静态做法，或者没意识到树状数组做不了区间最值。按 28.6 该补「复杂度 O(log n)」与「适用 n,q ≤ 1e6」，超规模时注明换线段树。
  3. 关掉同步后 C++ 流与 C stdio 各管各的缓冲，混用不再保证顺序与一致性，会出现输出乱序、读入对不上等偶发问题。两条路二选一：全程只用 cin/cout，或全程只用 scanf/printf，不要停在中间态。
  4. 先算「单项上界 × 项数」这个中间和上界，确认它装得进累加器类型。装不下就不能全程延迟：折中是每 K 轮取一次模，把 K 调到既不溢出、除法次数又足够少；本例是因为上界 2e17 远小于 64 位上限才敢只取一次。
  5. 先算量级：n=1e5 时 O(n²) 约一百亿次操作，差着数量级，卡常救不了，必须换复杂度对得上的算法（如 O(n log n)）。那次估算是「把 n 代进复杂度式得到操作次数，再按本机 1 秒约几亿次简单操作折算成秒」；只有估算显示差距在几倍以内时，才值得继续卡常数。
