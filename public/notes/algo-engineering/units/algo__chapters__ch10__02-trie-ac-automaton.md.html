10.1 先看工程长什么样

这一单元讲三个结构，但它们其实是同一件事的三种用法：把符号拆成一条路径，然后在这条路径上做点什么。Trie 把字符拆成边，01-Trie 把二进制位拆成边，AC 自动机在 Trie 上再加一层「失配往哪跳」。符号看起来不同，骨架是同一副。

先说清楚你会卡在哪。Trie 的概念你大概十分钟就能看懂，真正让代码挂掉的是三件事：数组开多大、哨兵值怎么选、失配之后往哪走。这三件事没有一个在算法课本的配图里画出来，但它们决定了你的程序是 AC 还是 MLE/RE。所以照本书的规矩，先看文件。

大白话这一节想让你先建立一个画面

把 Trie 想成一棵按字母分叉的树：从根出发，每读一个字符就走到对应的一条边，读完一个串就停在某个节点上。两个串如果开头几个字母相同，它们就会共用前面那段路，只有分叉的地方才各走各的。

  • 查一个串在不在：照着字母走一遍，走到就说明插过，半路没路可走就说明没插过；
  • 数一个串被插了几次：把次数记在终点节点上，走到终点读那个数就行；
  • 01-Trie 只是把「26 个字母的分叉」换成「0 和 1 两个分叉」，把整数按二进制位一位一位走；
  • AC 自动机则在每个节点上多记一条「如果这一位对不上，我该退到哪里继续」的捷径。

整节就围绕这四句话展开。剩下的所有技巧，都是在回答「怎么存得下、怎么跳得对」。

第 1 帧是动笔前的样子：ch10 的两层目录都还空着。第 2 帧是 Trie 的两个面孔——普通 Trie（trie_basic）与 01-Trie（trie_xor）；注意两者的 main.c 都只做一件事：造随机数据、跑正解和暴力、逐组比对。第 3 帧加入 AC 自动机，并且在这里第一次出现 C++ 应用层（ac_stl.cpp + main_stl.cpp）：原理层用 C 手写，应用层用 STL，这是本分册的硬要求。第 4 帧是三份对拍清单、三个性能探针和三份真实终端会话——它们是把「我以为对」变成「机器证实对」的那部分。

工程惯例工程惯例：为什么每个例子都要三个文件

标准对「一个程序分几个文件」没有任何规定。这里分三份，是因为接口和实现值得分开看：

语法规则语法规则：Trie 节点数组的三个约定
  1. ch[u][c] == 0 表示没有这条边。因为 0 号永远是根，而根不会作为任何节点的儿子出现，所以 0 可以安全地当哨兵；新节点从 1 开始编号。
  2. 每个新节点整块清零（memset），于是它的 26 条边一开始全是 0，cnt 也是 0。不要用 malloc 不初始化就开始插——那 26 个 int 里是上次分配留下的垃圾，你会顺着垃圾指针跳到别的节点。
  3. cnt[u] 只在终点有意义，它数的是「有多少次插入把这个串停在这里」。重复插入会让它累加；根节点的 cnt 是空串被插入的次数（本单元的对拍把空串也测了）。

为什么查询只花 O(len)

Trie 的查询代价是「串有多长就走几步」，和库里已经插了多少个串完全无关。这不是一句口号，可以从代码里数出来：trie_query 的循环变量 i 从 0 走到串尾，每一步只做两件事——算下标 c = s[i] - 'a'，然后读一次 t->node[u].ch[c]。没有内层循环，没有回溯，没有额外的比较。所以一个串长 10，无论 Trie 里已经有 10 个串还是 10 万个串，查询都是 10 次数组访问。

暴力版恰恰相反：brute_query 的循环变量 i 从 0 数到 b->n，每个存过的串都要用 strcmp 比一遍，而 strcmp 自己又是一个跟串长成正比的循环。嵌套起来就是 O(n × len)。n 一上万，这个乘法就变成了灾难。

这里有个容易误判的地方：Trie 快不是因为「不用比较字符串」，而是因为「比较工作被分摊到了插入时」。插入一个串时，你沿着路径走了一遍，把每个字符都变成了树上的一条边；查询时你只是重走这条路，不需要再拿自己的串去和别人的串逐字符比。换句话说，Trie 把「n 次串与串的比较」换成了「一次路径遍历」——共享前缀的部分只走一遍，这就是它快的全部来源。

代价也在这里：如果串之间几乎没有公共前缀，Trie 并不比存一张哈希表省多少，反而每个节点要付 26 个 int 的固定开销。所以 Trie 的主场是「大量串、前缀相似」的场景（比如词典、IP 路由表），而不是「少量长串、彼此无关」。

三种边界：空串、重复串、越界字符

syntax 里那三条约定不是纸上规则，每一条都对应一个会静默出错的边界。

空串。 trie_insert(t, "") 的循环一次都不执行，直接把 cnt[0] 加一——也就是「空串被插在根节点上」。查询同理，trie_query(t, "") 立刻返回 cnt[0]。这套口径是自洽的，但你必须在写实现之前就决定空串算不算。如果你一边让插入接受空串、一边在查询里写 if (s[0] == '\0') return 0;，就会出现「插进去了却查不到」的怪事。本单元的对拍生成器把串长取到 0，正是为了逼你把这个约定定死。

重复串。 同一个串插三次，cnt 终点会变成 3。这里的关键是 cnt 必须累加而不是置 1——很多模板写 cnt[u] = 1，在「判断在不在」的场景下没问题，一遇到「出现几次」就全错。本单元的对拍让每个串被插入 1–3 次，专门覆盖这条。

越界字符。 查询串里若出现 '{'（ASCII 比 'z' 大 1），c = s[i] - 'a' 就是 26，ch[26] 越过节点末尾读到了下一个节点的 cnt。不检查下标时，程序不会崩，只会给出一个似是而非的答案——这类错误在对拍里会被抓到，但定位很难，因为你看到的是「某个查询的答案差 1」。trie_query 里那句 c < 0 || c >= 26 就是防线。

10.3 对拍：200 组随机数据证明插入和查询没写错

Trie 的插入/查询短到让人放心，但「放心」不是证据。按本分册的规矩，每个算法单元都要有一份 mode: "run" 的清单，在程序内跑不少于 200 组随机数据，正解和暴力逐组比对。暴力这边故意写得笨：把所有插过的串存进一个扁平数组，查询时从头扫到尾数一遍。

对拍主循环做三件容易被忽略的事：① 随机数自己实现，固定种子，重跑逐字一致；② 同一个串可能被插入 1–3 次，专门逼 cnt 累加这条路径；③ 查询时七成从「确实插过的串」里挑，三成现造一个没插过的串——只测前者的话，一个永远返回正数的假实现也能过。

OK 200 这一行是结论：200 组随机数据、每组 30 次查询、合计 6000 次结论，Trie 与暴力逐次一致。失败时打印的是轮次、查询串和两个答案，不是干巴巴一句「错了」——有了轮次和固定种子，你可以把那一组单独重跑。

对拍为什么不会骗自己

对拍最怕的不是「没跑够 200 组」，而是「正解和暴力共享了同一个错误」。本单元的三个对拍都刻意避开了这一点：Trie 版的正解走节点数组，暴力版走字符串数组加 strcmp；异或版的正解走 01-Trie 的按位转移，暴力版走两重循环；AC 版的正解走 fail 树累加，暴力版走 memcmp 逐起点比较。两条路径没有共用的判定函数，所以一个错了另一个不会跟着错。

随机生成器也有讲究。三份 main.c 各自实现了一个线性同余发生器，种子写死在源码里。这意味着：

  • 同一份程序重跑 100 次，数据逐位相同——出了问题你能精确复现那一轮；
  • 换一台机器、换一个 C 库，rand() 的序列会变，但你的 LCG 不会——对拍结果跨机器可比；
  • 每轮的 n、串长、重复次数都随机变化，不会只覆盖某一种固定形状。

还有一个细节：失败信息要包含定位所需的全部字段。本单元的 printf 打出轮次、具体串、正解值和暴力值。如果你只打 FAIL，就得回去加日志、重新编译、重新跑——而加了日志之后内存布局变了，那个 bug 可能就消失了（这类「加打印就变好」的静默错误在数组越界里非常常见）。一次把信息打全，是对拍的基本功。

10.4 空间估算：n × len × 26 到底会不会爆

现在回答最要命的问题：这个结构体数组要开多大？ 很多人的第一反应是「每个串最长 len，一共 n 个串，最坏每个字符都建一个新节点，所以开 n * len 个节点，每个节点 26 个 int」。这个乘法本身没错，错在把它当成了实际用量。

计算分两步。第一步算上界：节点数最多 n × len（每个串的每个字符都开一个全新的节点）。每个节点是 26 个 int 的边加 1 个 int 的计数，也就是 27 个 int；本机一个 int 是 4 字节，所以每个节点 27 × 4 = 108 字节。于是：

  • n = 1e5, len = 10：上界 1e6 个节点 × 108 字节 = 108000000 字节，约 103 MB——还活着；
  • n = 1e5, len = 50：上界 5e6 个节点 × 108 字节 = 540000000 字节，约 515 MB——常见的 256 MB 限制下当场 MLE。

注意题目里那个「×26」是每个节点的出边数，不是节点数。真正炸掉内存的是 n × len × 26 × 4 这个连乘：它把「每个节点都长满 26 条边」这个最坏情形硬套到了每一层上。

第二步算实际用量。随机串很少共享长前缀，但短前缀一定会共享：a..z 的第一层最多 26 个节点，第二层最多 676 个，第三层最多 17576 个——到第四层，组合数 456976 已经大于 1e5 个串，于是后面的串基本只能各自走一条新路。所以实际节点数远小于 n × len。这台机器上真跑一遍给你看：

实测 616572 个节点、66589776 字节（约 63.5 MB），只有上界的六成多——前缀共享省下了三成多的空间。但别因此就按实测值开数组：换个数据集（比如所有串的前 10 个字符都不同），节点数会立刻逼近上界。本单元的实现用 realloc 翻倍扩容，正是为了不让你猜这个数。

陷阱你怎么会被坑到：把 26 乘进节点数

你会看到什么：程序在小数据上全对，一上 n = 1e5、len = 30 的样例就 MLE，或者直接起不来。你会怎么误判：以为是自己哪里多开了一维，回头文件里把 int ch[26] 改成指针。真相是：你算错了乘法的对象——26 是节点的宽度，不是节点的个数。n × len 才是节点数的上界，再乘 26 × 4 才是边数组的字节数。把 26 误乘进节点数，等于假设每个串的每个字符都重新开满 26 条边，那当然会爆。正确的防线只有两条：按 n × len 开上界并真的算一遍字节数，或者像本单元这样动态扩容、用实际节点数说话。

动态扩容的代价

本单元用 realloc 翻倍扩容，看起来完美，但并非没有代价。第一，搬动成本：容量从 c 翻到 2c 时，旧的 c 个节点要整体复制到新地址。把 n 次插入摊开看，总搬动量是 1 + 2 + 4 + … + n，即 O(n)，摊到每次插入是 O(1)——和直觉不同，翻倍扩容的平均代价并不高。第二，峰值内存：旧块和新块在 realloc 成功的瞬间同时存在，所以峰值比最终占用多出一份旧数组。对 1e5 节点、108 字节一个节点，这个峰值差是几十 MB，内存吃紧时仍需留意。第三，指针失效：如果你在某个地方存了 &t->node[u]，扩容之后那个地址就悬空了。本单元的所有访问都写成 t->node[u]（每次重新算地址），所以不会踩到——这个纪律要一直保持。

如果赛题的节点数有确定上界（比如「最多 1e5 个串、每个长度不超过 20」），直接开静态数组反而更省事：没有搬动、没有峰值翻倍、下标访问更 cache 友好。本单元选动态方案，是为了让「空间估算」这件事能被实测出来，而不是让你去猜一个上界。

10.5 01-Trie：把整数按位拆成边

大白话用大白话说 01-Trie

把一个 32 位整数写成 32 个 0/1，从最高位往最低位读，就得到一个长度为 32 的「字符串」。把一堆整数都这么拆开插进一棵 Trie，每个节点就只有两条边：这一位是 0 走左边，是 1 走右边。这棵树就叫 01-Trie。

求「哪个数和 x 异或最大」时，你从根开始，每一位都想选和 x 相反的那条边——因为异或的定义就是「相同得 0，不同得 1」。能选反的就选反的，把答案这一位置成 1；选不了才只好跟着 x 走。这就是按位贪心。

陷阱你怎么会被坑到：用有符号 int 存数，最高位全错

你会看到什么：数据里出现大于 2^31-1 的数（或者长相是负数的位串）时，答案莫名其妙偏小，而且小得很有规律——最高位总是 0。你会怎么误判：以为贪心写反了，把 want = bit ^ 1 改成 want = bit 试试，结果别的组又错了。真相是两处符号位陷阱叠加：① 有符号右移是算术右移，负数右移会在高位补 1，所以 (x >> b) & 1 在 b 很大时读到的不是真正的第 b 位；② 1 << 31 在有符号 int 上是未定义行为，编译器有权把它算成负数。修法只有一条：整个流程用 uint32_t，移位常量写 1u。本单元的对拍生成器专门用 next_rand() ^ (next_rand() << 16) 拼出跨符号位的数，就是为了把这条坑踩实。

为什么按位贪心是对的

这一步必须真写，不能拿「显然」两个字带过。论证用的工具是字典序与数值序的等价性。

把两个 32 位无符号数写成 32 位二进制串。设 j 是它们从高位往低位数的第一个不同位。那么：

  • 在这一位上取 1 的那个数，数值更大；
  • 因为第 j 位的权是 2^j，而它下面所有位的权加起来最多是 2^j - 1，所以高位上赢下 1，就赢定了——低 31 位全取反也追不回来。

换句话说，从高位到低位逐位比较的字典序，和无符号数值的大小顺序完全一致。这一条就是贪心的全部依据。

现在证明算法。维护一个不变式：处理完第 b 位之后，当前节点 u 对应的那棵子树里，一定存在一个已插入的数 y，使得 x ^ y 的前 31-b+1 位恰好等于贪心已经定下的前缀；并且不存在任何已插入的数能让这段前缀的字典序更大。

  • 初始：b = 31 时还没定任何位，u 是根，根下面就是全部已插入的数，不变式成立。
  • 归纳步：设当前位 bit 是 x 的这一位。若能走 want = bit ^ 1，则 x ^ y 这一位是 1，这是该位能取的最大值，于是贪心前缀变大，取这条路；若不能走，说明子树里所有数在这一位都是 bit，x ^ y 这一位只能是 0，没有别的选择。两种情况下不变式都保持。
  • 终止：走到最后一位时不变式给出「存在 y 使 x ^ y 等于贪心得到的串，且没有更大的串」。由前面的字典序等价性，这个串就是数值最大值。

还有一个容易被漏掉的细节：贪心走出来的路径必须真的对应某个已插入的数。它是沿着 ch 数组走出来的，而 ch 里的每条边都是插入时真建出来的，所以路径终点一定是一个真实插入过的数的末节点。于是答案不是「理论上的最大异或」，而是「两数异或的最大值」——这个区别正是暴力对拍要验的东西。

一个具体的按位例子

设已插入的数是 2 = 010、3 = 011、6 = 110，查询 x = 5 = 101，只看低三位。从最高位（第 2 位）往下：

  • 第 2 位：x 是 1，want = 0。候选里第 2 位为 0 的有 2 和 3，路走得通，于是答案这一位置 1（表示异或结果的第 2 位是 1 ^ 0 = 1），进入「第 2 位为 0」的子树；
  • 第 1 位：x 是 0，want = 1。子树里 2（010）和 3（011）的第 1 位都是 1，还是走得通，答案这一位再置 1（0 ^ 1 = 1），进入「第 1 位为 1」的子树；
  • 第 0 位：x 是 1，want = 0。2（010）第 0 位是 0，3（011）是 1，选 2，答案这一位置 1（1 ^ 0 = 1）。

得到 111 = 7，正是 5 ^ 2 = 7。注意三位里答案都置了 1——置位的关键是「x 的这一位能否取反成功」，不是「候选那一位是什么」。代码里前者对应 want = bit ^ 1，后者对应 ans |= (uint32_t)1u << b；把这两行看成一个整体，贪心就不绕了。

再看个反例形状：若只插了 6 = 110，查询 5 = 101。第 2 位想要 0 却走不通（只有 6，第 2 位是 1），只能跟随 x 的 1，答案第 2 位保持 0；第 1 位 x 是 0，want = 1，6 的第 1 位是 1，走得通，答案置 1；第 0 位 x 是 1，want = 0，6 的第 0 位是 0，走得通，答案置 1。结果 011 = 3，而 5 ^ 6 = 3，对上了。只有一项数据时答案不是 0，这一点在你的实现里也要测到。

为什么必须从高位开始：一个低位优先的反例

有人会问：既然每一位都想取反，从低位开始不也一样吗？不一样，而且错得非常具体。

设已插入 4 = 100、3 = 011，查询 x = 5 = 101。若从低位开始贪心：第 0 位 x 是 1、想要 0，两个数里 4 的第 0 位是 0、3 是 1，于是选 4；第 1 位已经没有候选能取反（4 的第 1 位是 0，与 x 的第 1 位 0 相同，只能跟随）；第 2 位同样只能跟随。得到 x ^ 4 = 001 = 1。

正确答案是 x ^ 3 = 110 = 6。问题出在哪？第 0 位上「能取反」这件事把选择锁死在了 4 那条分支上，而真正的最优解 3 在第 0 位上没能取反（x 第 0 位是 1，3 的第 0 位也是 1，异或得 0）。低位上省下的 1，远不如高位上丢掉的 4。

量化一下：第 b 位的权是 2^b，所有更低位的权之和是 2^b - 1。所以在第 2 位取到 1 带来的增益是 4，而第 0 位取反带来的增益最多是 1——低位永远补不回高位的损失。这就是「高位优先的字典序等价于数值序」的另一面：低位贪心是局部最优，但不是全局最优。按位贪心的正确性依赖的就是这个严格不等式，而不是「看起来每位都想取反」这种模糊直觉。

暴力版就朴素得多：两重循环枚举每一对，取异或最大值。

对拍把 n 取在 2–64，每轮插完 trie 再对每个数查一次，取最大值和暴力比。注意 a[i] ^ a[i] = 0 这种「自己和自己配对」的情况不影响答案，但生成器里有两个及以上的数，暴力也只枚举 j > i，两边口径一致。

10.6 AC 自动机：KMP 的多模式版本

上一单元讲 KMP 时，你为一个模式串算了 next 数组：失配时不用回头，照着 next 跳就行。现在问题变了：给你 1000 个模式串，问它们各自在文本里出现几次。对每个模式跑一遍 KMP 当然可以，代价是 1000 × |文本|——文本一长就扛不住。

大白话用大白话说 AC 自动机

把所有模式串先插进一棵 Trie，然后给每个节点加一条「失配捷径」：如果我走到这里、下一个字符对不上，我该退到哪个节点接着走。这条捷径叫 fail。

fail 指向哪里？指向「当前这串字符的最长真后缀，且这个后缀恰好也是某个模式的前缀」。比如走到表示 she 的节点，he 既是 she 的后缀又是某个模式的开头，所以 she 的 fail 就指向表示 he 的节点。

有了 fail，扫描文本时你永远只往前走：每个字符做一次转移（对不上就沿 fail 退一步再试），总代价和文本长度成正比，和模式个数无关。KMP 是一个模式一条 next 链；AC 是把所有模式的 next 链合并成了一棵树。

现在证明 BFS 构造是对的。要证的是：处理节点 u 的儿子 v（边字符为 c）时，fail[v] = ch[fail[u]][c] 恰好是「string(v) 的最长真后缀且为某模式前缀」对应的节点。

  1. string(v) = string(u) + c，它的任一真后缀必然是 string(u) 的某个后缀再接上 c。
  2. string(u) 的所有后缀按长度从长到短排成一条链，就是 u → fail[u] → fail[fail[u]] → … → root。这是因为 fail 的定义就是「最长真后缀」，而对 fail[u] 再取 fail 就得到次长的真后缀，依此类推。
  3. 所以 string(v) 的候选后缀（且以 c 结尾、又是某模式前缀）恰好是链上第一个有 c 出边的节点接上 c 的结果。补边之后，ch[fail[u]][c] 正是「从 fail[u] 出发读字符 c 应该到的节点」——它把「沿 fail 链一直找有 c 边的祖先」这件事压缩成了一次数组访问。
  4. BFS 顺序是这条式子的前提：fail[u] 的深度严格小于 u，所以 fail[u] 一定已经出队处理过，它的 26 条边已经补完。若用 DFS 或按插入顺序处理，ch[fail[u]][c] 可能还是 0，算出来的 fail[v] 就会指错。
陷阱你怎么会被坑到：根的 fail 忘了指向自己

你会看到什么：程序在模式只有一两个时正常，模式一多、文本里出现大量不匹配字符时，出现随机崩溃或计数错乱。你会怎么误判：以为是自己 fail 公式写错了，反复检查 ch[fail[u]][c]。真相是根节点的 fail 没设成 0（自己）：如果它留着未初始化的值，或者你用了 -1 表示「没有 fail」却忘了在累加时特判，那么根的儿子在补边时会去读 ch[-1]，或者 fail 树的累加会把次数加到一个不存在的节点上。本单元在 ac_init 里显式写死 a->node[0].fail = 0，同时用 memset 保证其他字段全零——这条初始化不能省。

陷阱你怎么会被坑到：用 DFS 或插入顺序代替 BFS

你会看到什么：同一份代码换个模式顺序，答案就变了；或者小样例过、大数据崩。你会怎么误判：以为是哈希表或字符串比较的问题。真相是**fail 的计算依赖「祖先先算完」：fail[v] = ch[fail[u]][c] 要读 fail[u] 已经补好的出边，而 fail[u] 又被 u 的祖先决定。只有按深度递增的 BFS 能保证这一点。DFS 走到深处时，fail[u] 所在的那一层可能还没处理，ch[fail[u]][c] 还是 0，于是 fail[v] 被算成根——错得很隐蔽，因为「指回根」也是一种合法长相。规则很简单：fail 只能 BFS 造，别自作聪明换顺序。**

与 KMP 的 next 数组逐项对应

如果你刚学完上一单元的 KMP，fail 不需要重新理解，只需要换一个角度看：

KMP（单模式） AC（多模式） 共同点
next[i] 是模式前 i 个字符的最长相等真前后缀长度 fail[u] 是 u 对应串的最长后缀、且是某模式前缀 都是「失配后还能接着用」的最长信息
失配时 j = next[j] 转移失败时沿 fail 退一步 都不回退文本指针

差异只有两处：KMP 的 next 只服务于一个串，AC 的 fail 要服务于所有模式，所以它指向的是「Trie 里另一条路径的前缀」而不是同一串里的前一段；以及 AC 在构造时顺手把缺失的边补成完整转移，把 KMP 里那个 while (j && p[j] != c) j = next[j] 循环压缩成了一次数组访问。

补边：用空间换时间的那一刀

ac_build 里那段 if (v == 0) ch[u][c] = ch[fail[u]][c] 常被初学者当成「可有可无的优化」。它不是优化，而是改变了扫描的复杂度结构。

不补边时，扫描一个字符要写成一个 while 循环：先看当前节点有没有这条边，没有就沿 fail 退，退到有边为止（或退到根）。这个循环在最坏情况下能退 O(模式最大长度) 步——比如模式是 aaaa…ab、文本是 aaaa…a，每个字符都要退一大截。补边之后，每个节点的 26 条边都指向「读这个字符该去的节点」，while 循环被消掉，每个字符严格一次数组访问，扫描时间是严格的 O(|T|)。

代价是每个节点固定存 26 个 int。模式总长 1e4 时节点数约 1e4，多出来的边表约 1e4 × 26 × 4 = 1.04 MB——完全能接受。模式总长到 1e6 时就是 104 MB，这时你才会开始考虑用哈希表或者只存实际出现过的边（稀疏存储），但那会把每次转移从 O(1) 变成一次哈希或一次对数查找。竞赛里的默认选择仍然是补边：它把不确定性从时间维度挪到了空间维度，而空间是可以估的、时间是不能赌的。

10.7 fail 树与出现次数统计

扫描文本本身只有一行循环：每个字符做一次转移，给落到的节点 vis++。难点在统计。

为什么扫描时只给「当前节点」记一笔就够了？因为每读一个字符，当前节点代表的模式就以这个字符结尾出现了一次；而如果一个模式是另一个模式的后缀，它不会作为「当前节点」被走到，但它的出现次数已经算在更长模式的 vis 里了。把 fail 树上的计数从儿子往父亲累加，就把这些「隐式出现」补上了。

陷阱你怎么会被坑到：只查当前点，不沿 fail 链累加

你会看到什么：模式 he 和 she 一起匹配文本 she，she 报 1 次，he 报 0 次。你会怎么误判：以为 he 的终点节点编号记错了，回去反复检查插入函数。真相是：扫描 s h e 时，状态走的是 root → s → sh → she，根本没经过 he 节点——he 是 she 的后缀，不是路径上的独立一步。如果不沿 fail 链把 vis[she] = 1 加到 vis[he] 上，he 的计数永远是 0。这个坑在模式有包含关系时必踩，而且样例常常只有一两个模式，恰好躲过去。规则：统计必须沿 fail 树累加，而且要逆 BFS 序做，先儿子后父亲，一遍扫完。

多模式匹配的复杂度到底怎么算

把三件事分开算，就不会混：

  1. 建 Trie：每个模式的每个字符最多开一个节点，总节点数 V ≤ 1 + Σ|p|，这一部分 O(Σ|p|)。
  2. 构造 fail：BFS 每个节点、每个字符恰好处理一次，每次是 O(1) 的数组访问，所以是 O(26 × V) = O(Σ|p|)。常数 26 来自字母表大小，不是模式个数——换个 ASCII 字母表就是 128，换成 Unicode 就得换存储方式。
  3. 扫描文本：补边之后每个字符一次转移、一次计数，O(|T|)；fail 树累加每个节点一次，O(V)。合计 O(|T| + Σ|p|)。

所以总复杂度是 O(|T| + Σ|p|)，与模式个数 k 无关（k 只通过 Σ|p| 间接影响）。这正是它和「k 次 KMP」的本质区别：后者是 O(k × |T| + Σ|p|)，文本一长，k 就成了乘数。

空间是 O(26 × V)。用本单元的节点结构算成字节：Σ|p| × 116（26 个 ch 加 fail、vis、end，共 29 个 int）。800 个长度 3–8 的模式总长约 4400，节点数不到 4400，内存约半 MB——和 1e5 的文本比起来几乎可以忽略。

fail 树统计与沿链输出的对比

统计模式出现次数还有另一种常见写法：扫描到一个节点时，沿它的 fail 链一路往上走，把链上每个终点模式的计数都加一。这种写法和本单元的「fail 树逆序累加」给出相同答案，但复杂度不同。

沿链输出的成本是 O(|T| × 链长)。链长最坏等于最长模式长度——模式是 a, aa, aaa, …, a^1000 时，扫到 a^1000 节点要沿链走 1000 步。文本 1e5、模式长 1000，就是 1e8 次操作，稳稳 TLE。fail 树累加则是每个节点一次加法，总成本 O(V)，和文本长度无关。

为什么后者能替掉前者？因为「沿链输出」做的是同一件事很多遍：每个节点的 vis 会被它所有后代沿链访问一次，而这些访问的目标完全确定（就是 fail 树的祖先）。既然目标确定，就可以反过来做一遍：让每个节点把自己的 vis 交给 fail 父亲，一次加法顶掉所有后代的沿链访问。这是「把 O(后代数量) 次推送合并成 O(1) 次拉取」的典型变换，和树上差分「先累加再查询」是同一个思想。

代价是需要额外保存 BFS 序（order 数组），多 V 个 int。对本题而言这是极划算的交易。如果模式数很少、最长模式也很短（比如只有 5 个长度不超过 4 的模式），沿链写法代码更短、也够快——复杂度分析的价值不是让你永远选最快那个，而是让你知道什么时候慢的那个会突然变慢。

从复杂度反推能过的 n

复杂度表要能指导你做题，关键是把「能过的 n」这一列推出来。方法是拿本机的实测速度去除：

  • Trie 每次操作是几次数组访问，本机 1e5 个串、1e6 次插入只花几十毫秒。所以 n=1e6 量级仍然可行，先撞到的不是时间而是内存：n × len × 108 字节，len=50 时 1e6 个串就要 5.4 GB，不可能。于是这一列的答案由内存决定，不由时间决定。
  • 01-Trie 每次查询 32 步，n=1e6 也就是 3.2e7 次数组访问，几十毫秒。同样地，空间 n × 32 × 8 字节对 n=1e6 已经偏紧，实际会把位数压到数据的真实值域（比如只用到 30 位）。
  • AC 的扫描是 O(|T|)，与 k 无关。1e5 文本单次 0.2 ms，那么 1e7 文本大约 20 ms，1e8 文本大约 200 ms——线性算法的好处就是可以直接外推。瓶颈同样在建机空间：每个节点 116 字节，256 MB 限制下节点数大约能到 2e6。

注意这三个外推都用了一个共同假设：数据能放进内存，且访问是连续的。Trie 和 01-Trie 的节点数组是连续内存，缓存友好；如果你改成链表存节点，常数会掉好几倍，上面的数字就不能照抄了。这也是为什么本单元从头到尾都用扁平数组——不是为了好看，是为了让复杂度表上的数字真的成立。

200 组为什么够

本分册把「不少于 200 组」写成了硬要求。为什么是 200，不是 20 或 2 万？

20 组太少：很多 bug 的出现概率在百分位量级——比如「两个随机串恰好互为前缀」「模式恰好是另一个模式的后缀」「数据恰好跨过符号位」。20 组里这些情况可能一次都没出现，你会以为自己写对了。200 组把这类「百分之一的概率」事件变成期望出现两次，抓到的机会大得多。

2 万组又太多：对拍的价值在于快速迭代——你改一行代码，想在三秒内知道它对不对。本单元三份对拍各跑 200 组，都在十几秒内完成（实际是几十毫秒），改完立刻能重跑。如果把轮数拉到 2 万，跑一次要几秒，你会不自觉地少跑几次，反而降低了发现 bug 的机会。

还有一条：对拍的数据规模要小。本单元每轮的 n 都在 200 以内，因为暴力是 O(n²) 或 O(n × len) 的——对拍的目标是「找出反例」，不是「压测性能」。性能是另一份探针的职责。把两件事混在一起，你会得到一个既跑不快、又抓不到 bug 的对拍程序。

三样结构怎么选：一张决策清单

面对一道题，按下面的顺序问自己：

  1. 要处理的是字符串还是整数？ 字符串且需要「前缀」语义 → Trie；整数且求按位的极值（最大异或、最接近的值）→ 01-Trie。
  2. 是一个模式还是一堆模式？ 一个模式在文本上匹配 → KMP（上一单元），上 Trie 是杀鸡用牛刀；一堆模式同时匹配 → AC 自动机。
  3. 要不要数「出现几次」？ 要，而且模式之间有包含关系 → 必须做 fail 树累加；只判断「有没有出现」→ 沿 fail 链输出也够。
  4. 内存够不够？ 先算 节点数 × 每节点字节。Trie 每节点 108 字节，01-Trie 每节点 8 字节，AC 每节点 116 字节。把 Σ|p| 或 n × len 代进去，超过限制就换稀疏存储或位压缩。
  5. 数据能不能共享前缀？ 不能的话 Trie 的节点数会逼近上界，此时哈希表的常数更小。

这张清单的用法不是「照着选」，而是「照着排除」：当你发现自己在纠结「要不要再套一层 Trie」时，回到第 1 问，通常答案是你把问题建模错了。竞赛里真正难的不是写出这些结构，而是认出题目在问哪一类。

两层写法怎么分工

到这里你手上有了两套能跑的 AC 实现。它们的分工不是「一个教学、一个实用」那么简单：

  • **原理层（C）**的价值在于每个动作都看得见：节点是数组里的第几号、队列的头尾指针怎么动、fail 树累加的逆序循环写在哪一行。当你需要调试「为什么这个模式少算了一次」时，你能一路追到具体那条语句。
  • **应用层（C++）**的价值在于改动成本低：模式个数变了、字符集变了、要按字典序输出了，改的往往是容器类型和几行算法，不用重新写内存管理。

本单元的 C++ 版仍然把 build 和 scan 单独放在 ac_stl.cpp 里，而不是塞进 main_stl.cpp——这样它的接口可以直接贴进你自己的项目，驱动文件只负责造数据和验证。代价是多一个头文件和一次 #include；收益是「换驱动不碰算法」，和对拍里「正解与暴力不共享代码」是同一个道理。

小结这一节的要点
  • Trie 用 ch[u][c] 存边、cnt[u] 存终点次数；ch == 0 当哨兵的前提是根固定为 0 号且新节点从 1 开始；
  • 空间上界是 n × len 个节点 × 每节点 27 个 int；n=1e5, len=50 时约 515 MB，常见内存限制下会爆；实测 len=10 只用了 63.5 MB，因为前缀共享；
  • 01-Trie 的最大异或对靠「高位优先的字典序等价于数值序」保证正确：每一位能取反就取反，取不到才跟随；全程 uint32_t，别碰有符号右移和 1 << 31；
  • AC 的 fail[v] = ch[fail[u]][c] 必须 BFS 构造，因为 fail 指向更短后缀、深度严格递减；根节点的 fail 指向自己；
  • 出现次数要在 fail 树上按逆 BFS 序从儿子往父亲累加，只查当前节点会漏掉「作为更长模式后缀出现」的那些次；
  • 复杂度对得上：Trie 每次 O(len)，01-Trie O(n × 32)，AC 扫描 O(|T|) 与模式数无关；本机实测 800 模式扫 1e5 文本单次 0.200–0.250 ms。

注自测题答案
  1. 因为根固定在 0 号，而根永远不会作为任何节点的儿子出现，所以 0 不可能是一条真实的边终点，可以安全当哨兵。若把根改成 1 号，0 就可能被当作真实节点编号，这个约定立刻失效——要么重新选一个不可能出现的哨兵（如 -1），要么把根继续留在 0。
  2. 节点数上界 n × len = 5e6，每节点 27 个 int = 108 字节，合计 540000000 字节，约 515 MB。26 是节点的宽度（每个节点有多少条出边），不是节点数；节点数是 n × len。把 26 乘进节点数就会多算一个数量级，得出错误的结论。
  3. 第 j 位的权是 2^j，而它下面所有位的权之和最多是 2^j - 1。所以在最高不同的那一位上取到 1 的数，无论低位怎么取都比取 0 的大。于是「从高位到低位逐位比较」的字典序与无符号数值序完全一致，逐位贪心就是逐位确定最大值的字典序。
  4. 两处：① (x >> b) & 1 对负数是算术右移，高位补的是 1，读到的不是真正的第 b 位——这是逻辑错误（也算实现定义行为）；② 1 << 31 在有符号 int 上是未定义行为，编译器可以把它算成负数——这是 UB。修法是全程 uint32_t，移位常量写 1u。
  5. fail[v] = ch[fail[u]][c] 要读 fail[u] 已经补好的出边，而 fail[u] 的深度严格小于 u。BFS 按深度递增处理，保证算 v 时 fail[u] 已经出队、边已补完。改用 DFS 时深层节点的 fail 祖先可能还没处理，ch[fail[u]][c] 还是 0，于是 fail[v] 被误算成根；症状是结果随模式顺序变化、小样例碰巧过、大数据错。
  6. 只查当前节点会得到 he 出现 0 次——扫描 she 时状态走的是 root → s → sh → she，根本没经过 he。正确做法是在 fail 树上逆 BFS 序累加：fail[she] = he，把 vis[she] = 1 加到 vis[he] 上，得到 1 次。
  7. fail 树累加是「儿子把计数交给父亲」，必须保证处理一个节点时它的所有子孙已经交完。BFS 序是浅的在前，倒着遍历正好是深的在前，满足这个条件。正着遍历时父亲的计数在儿子交上来之前就被读走并可能被继续上传，导致漏算。
