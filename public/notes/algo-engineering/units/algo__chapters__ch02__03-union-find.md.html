2.1 先看工程长什么样

并查集只有两个操作，但赛场上它有一半的坑不在算法里，在存法里：数组开多大、下标从 0 还是 1、压缩什么时候做、递归会不会爆栈。所以照本书的规矩，先看文件。

大白话这一节想让你先建立一个画面

把并查集想成一堆互相认老大的小弟。每个人手里只有一张纸条，写着「我的老大是谁」；老大自己的纸条写着自己的名字。

  • 问「你俩是不是一伙的」＝ 顺着纸条一路往上找，看最后走到的是不是同一个人；
  • 说「你俩结成一伙」＝ 把其中一伙的老大，挂到另一伙的老大下面。

整个并查集就是这两件事。剩下的所有技巧，都是在让「往上找」这一步少走几步。

第 1 帧是动笔前的样子。第 2 帧是并查集的三种面孔：基础版（union_find_basic）、带权版（uf_weighted）、扩展域版（uf_enemy）——注意它们的接口几乎一样，差别只在数组里多存了什么。第 3 帧是这本书的加码：一个对拍工程（用暴力证明正解对）和一个性能工程（量出「压缩到底省多少」），外加三份真实的运行会话（耗时、崩溃、栈深边界各一份）。

工程惯例工程惯例：为什么每个例子都要三个文件

标准对「一个程序分几个文件」没有任何规定。这里分三份，是因为并查集的接口和实现值得分开看：

  • include/uf.h 只放类型与函数声明——读接口能立刻知道它能做什么、不能做什么；
  • src/uf.c 放实现——坑都在这里（压缩、合并方向、权值累加）；
  • src/main.c 只负责造数据、调用、打印——它是读者实验的地方，改它不会碰坏算法。

代价是多一个 #include。收益是：你在赛场上抄模板时，抄的是 uf.c 那一份，而 main.c 里的实验代码不会跟着进去。

2.2 一句话说清：并查集在维护什么

一句话：它维护一棵（或一片）树，回答「两个点是不是在同一棵树里」，并且支持「把两棵树接成一棵」。 注意它不维护「怎么走」——它只知道「在不在一个集合」，不知道路径、不知道距离（除非你像 2.5 那样自己加上边权）。

接口就长这样：

parent[i] 是「我老大的编号」。size[i] 只在根上有意义，是这棵树有几个点。groups 是当前还剩几棵树（连通块数）。uf_depth 是给读者观察用的，不进模板。

语法规则语法规则：数组模拟一棵树的三个约定
  1. 根的特征是 parent[i] == i。整个结构只靠这一条判据，没有别的标记位。
  2. 所有下标自己从 0 开始（C 数组天然如此）；题目给的 1..n 要在读入时统一 -1，或者干脆全部加一位——两种都行，但一个程序里只能选一种，混用是并查集最常见的静默错误。
  3. 只有根上的 size 有意义。合并之后，被挂上去的那个根，它的 size 就作废了（以后再也读不到，也没必要清零）。

第 1 帧是初始化。第 2 帧是三次 union 之后：树长成了一条链。这时候问 find(4)，要往上爬四步。第 3 帧是 find(4) 自己做的好事：它顺手把走过来的每个点都直接挂到根上，于是整棵树变成了「一个根 + 一排儿子」，下次再问任何人只要一步。

这一帧就是路径压缩的全部内容：不是重构整棵树，而是「谁被问过，谁就被拍平」。

2.3 find 的关键：路径压缩

压缩的写法有两种：递归三行，或者迭代两段。竞赛里用迭代版，原因在 2.8 会用本机的真实数字给你看：递归版的深度跟着链长走，本机把优化开关一摘就能看到进程被栈杀死。迭代版是这样的：

为什么它不会漏掉点？因为第二个循环沿着原来的路径走：每改一个点，就把下一个点先记下来，指针再往前走。走到根时，这条路径上所有点都已经被改成指向根了。

陷阱你怎么会被坑到：把两个调用塞进同一个 printf

我第一次写这个实验时，最后一行是这么写的：

  • printf("... %d ... %d ...", uf_find(&chain, 0), uf_depth(&chain, 0))；

编译运行，打出来的压缩后台阶数是 6，也就是「压缩没生效」。我差点回去改 find。真实原因是：C 语言没有规定函数参数的求值顺序，这台机器上 gcc 先算了 uf_depth，那时 find 还没跑。

这个坑在赛场上更隐蔽的形式是：printf("%d %d", f(x++), g(x)) 这类写法——答案对不对，取决于编译器先算哪边。规则很简单：一个有副作用的调用，和另一个读同一状态的调用，不要放进同一个表达式。先算，存进变量，再打印。

2.4 第二个优化：按大小合并

只有压缩、没有按大小合并，也会退化成一条链：如果每次 union(a, b) 都把 a 的根挂到 b 的根下面，而数据恰好是「1 并 2、2 并 3、3 并 4……」这样的顺序，树会一路偏下去。压缩只在被问到的时候才救你，没被问到的部分照样是长链。

按大小合并解决的就是这件事：

三行是骨架：先各自找根；根相同就什么都不做（返回 0）；否则把小的挂到大的下面，并把大小加起来、连通块数减一。

为什么「按大小」就够了？因为每次一个点被挂走，它所在的集合至少翻倍。一个点最多被挂 log2(n) 次，所以树高不超过 log2(n)。这是最朴素的势能论证，不依赖压缩。

两个一起用，摊还复杂度是 O(α(n))——α 是反阿克曼函数，n 取到宇宙原子数级别时它也不超过 5。所以工程上直接说「近似 O(1)」。

编译器视角编译器视角：下标溢出是未定义行为，本机 gcc 在 -O2 下会直接点你的名

写这一节的性能实验时，我第一版的下标是这么算的：int a = (k * 15485863) % n;。k 跑到 1e6，k * 15485863 早就超出了 int 的范围——有符号整数溢出是未定义行为，编译器有权假设它不会发生。

本机 gcc 在 -O2 下真的点出了这一行。第一处在合并循环：k=20506 时 20506 * 104729 = 2147572874 第一次越过 int 的上界；后面两处查询循环用的 15485863 也被点了名（139 * 15485863 越界，所以那两处报的是 139）：

warning: iteration 20506 invokes undefined behavior [-Waggressive-loop-optimizations]

它不是提醒你「小心溢出」，而是在说「我按你承诺的『不会溢出』做了优化」。后果在那次实测里是两种表现：-O0 下负下标越界写，那次运行当场被访问违例杀死（退出码 3221225477，即 0xC0000005；这条路径没刷过 stdout，缓冲区里的内容整段丢掉，一行都没留下——2.8 的递归实验里那个显式 fflush 就是为了让第一行活下来）；换一批数据、换一天的堆布局就未必崩——堆上负下标会先在别人的内存里游荡一阵，2.6 的那次越界就一路全对跑完了。-O2 下循环被编译器按你的承诺重写，这次碰巧把数算完了——但它同样有权把你的循环删掉。修法只有一条：下标计算一律用无符号（(unsigned)k * 15485863u），或者一开始就用 long long——现在 perf.c 里的 idx() 就是这么写的。

2.5 带权并查集：把「差」变成边权

到目前为至，并查集只知道「在不在一个集合」。但有一类题问的是「差多少」：给一堆 prefix[r] - prefix[l] = k 的条件，判断它们自相矛盾没有。这类题的解法是：把「差」存到边上。

具体做法是给每个点加一个 delta[x]，含义是「v[x] 比 v[parent[x]] 大多少」。于是：

  • 你要的是 v[x] - v[根]，那就沿着路径把 delta 一路加起来；
  • 压缩的时候正好在走路，顺手把累加做掉。

注意这两行的顺序不能换：先把 delta[p] 加上（此时 p 已经被压到根，delta[p] 已经是「p 到根的总差」），再把 x 的父亲改成根。如果先改父亲，delta[p] 就再也拿不到正确值了。

合并时的式子要自己推一遍，别背：

推导只有三步：d = v[b] - v[a]；v[a] = va + v[ra]、v[b] = vb + v[rb]；把后两个代进去解出 v[rb] - v[ra] = d - vb + va——右边正好就是「rb 到 ra 的差」，也就是新的 delta[rb]。

陷阱你怎么会被坑到：合并时先改父亲、再去读值

带权并查集最经典的 bug 是这一行的顺序：

  • 先写 u->parent[rb] = ra;，再写 u->delta[rb] = d - wuf_value(u, b) + wuf_value(u, a);。

看起来没差别，实际上 wuf_value(u, b) 现在会沿着刚改过的新父亲去找根，vb 变成了「v[b] - v[ra]」，而公式要的是「v[b] - v[rb]」。答案会静默错掉，而且样例往往能过——因为它只在「两棵树大小相差悬殊」时才露馅。

查法：把 va、vb 先算好存进变量（就是上面代码里的两行），后面只用变量。这样顺序就无关了。

2.6 扩展域：把一个人拆成两个

「朋友的朋友是朋友，敌人的敌人也是朋友」——这句话用普通并查集表达不了，因为它有两种关系，而并查集只有一种「同集合」。标准解法是扩展域：把每个人拆成两个点，x 表示「x 是朋友这一侧」，x + n 表示「x 是敌人这一侧」。

于是两种关系都能翻译成合并：

  • 朋友：x 和 y 合并，同时 x + n 和 y + n 合并；
  • 敌人：x 和 y + n 合并，同时 y 和 x + n 合并。

判自相矛盾也简单：如果某个 x 与 x + n 落进了同一个集合，说明「x 是自己的敌人」，那就不可能成立。

最后两行要连起来读：friend(1,4) 之后，系统自相矛盾（返回 0），但 is_enemy(1,4) 仍然是 1——因为并查集不会「发现矛盾就回滚」，它只是把两个点合了，之前那条「敌人」的边还在。所以判矛盾必须靠 euf_ok 的显式检查，不能指望后续查询自己报错。

陷阱你怎么会被坑到：1 基编号 + 2n 的数组，正好差一格

这个单元的第一版就是这么翻车的，值得原样讲一遍。

编号用 1..n（题目习惯），敌人位是 x + n，于是 n = 4 时 enemy(3, 4) 要写 4 + 4 = 8。而数组按 2 * n 分配，只有 8 个格子，下标 0..7——第 8 格是别人的内存。

更麻烦的是它的表现：我在终端里跑，六行答案全对；交到当时那台 Windows 机器的闸门上跑，进程直接以 3221225477（0xC0000005，Windows 的访问冲突码）结束，stdout 一个字都没有。同一份二进制，换个启动方式就换一种结果——因为堆上第 8 格背后是什么，取决于谁先分配、谁还没分配。

定位靠打桩：在 join 和 euf_ok 里各加一行写 stderr 的日志，输出停在 join(3, 8)，一眼就看见了。

修法有两条，选一条并写进注释：① 逻辑点用 0..n-1（敌人位 n..2n-1，2n 个格子正好装下）；② 保持 1..n 编号，数组开 2n + 2（本单元用的就是这条，0 与 2n+1 空着不用）。两条都对，混着来就是这次的事故。

2.7 对拍：让机器替你怀疑

写到这里，你已经会写并查集了。但赛场上让你掉分的不是「不会写」，是「以为写对了」。这一节给你的，是让别人替你怀疑的机器。

对拍的三件套：一个生成器、一个正解（你的并查集）、一个暴力（慢慢来但一眼能看出对）。然后随机造 200 组，逐组比对。

OK 200 这一行本身就是结论：200 组随机数据，正解与暴力在「连通块数」和「随机点对连通性」上完全一致。整件事在本机 0.003 秒跑完——比你再读十遍代码便宜得多。

三个细节让它不容易骗自己：

  1. 随机数是自己实现的（g_seed + 线性同余）。用 rand() 的话，换一台机器、换一个库，序列就变了，出了问题你复现不出来。
  2. 比对的是两个维度：连通块数（全局）和随机点对（局部）。只比一个，错误可能刚好躲开。
  3. 失败就打印轮次和那两个点，而不是只打印「错了」。有轮次，你可以把种子固定下来重跑那一组。
实验记录本机实测：对拍的三个数字
  • 轮数 200，每轮 n 在 5..200 之间、ops 在 10..69 之间；
  • 每轮比对 1 次连通块数 + 20 组随机点对，合计 4200 次结论比对；
  • 整个程序在本机跑完 0.01 秒上下（墙钟，含进程启动；三次取值 9–32 ms），输出 OK 200。

为什么 n 只到 200？因为暴力那边每次查询都要 DFS 一遍，O(n²)；200 是「错误容易暴露、又跑得快」的甜点。对拍的数据要小，因为你要的是「找出反例」，不是「压测性能」。

2.8 代价表、栈溢出与两个真会踩的坑

先把这张表记住，它是本单元最有用的东西：

写法 单次操作复杂度 能过的规模（本机） 依据
只按大小合并（不压缩） O(log n) n, q ≤ 1e6 2.8 的实测：1e6 次 23 ms
按大小合并 + 路径压缩 摊还 O(α(n)) n, q ≤ 1e7 同一份数据 17 ms
两者都不用（长链） 单次 O(n) 递归版 -O2 撑到 4.3 万帧，4.4 万被杀；-O0 3.2 万活、3.3 万被杀 2.8 的实测：深度=链长，本机栈保留 2MB（边界探测在 session-boundary.txt）

表里的耗时是同一份 perf.c 跑出来的。它把两件事分开写：stdout 只留可复现的结论，耗时打到 stderr——因为时间每次都会差几毫秒，混进 stdout 会让「输出对账」变成天天失败。

这里有个反直觉的结论，值得单独说：只按大小合并已经不慢了，压缩只快了一点点（17 vs 23 ms）。原因有两个——按大小合并本身就把树高压在了 20 层以内；而这组数据的访问模式又很随机，缓存友好。所以「并查集必须写压缩」这句话不准确，准确的说法是：

  • 必须有「按大小（或按秩）合并」——没有它，长链会让复杂度退化成 O(n)；
  • 有了它之后，压缩是锦上添花，省的是常数。

深度 20000，正好等于链长：递归版每爬一步就多一层调用，每层调用都要在栈上占一个帧——深度多大，同一时刻活着的帧就有多少。迭代版干的是同样的活（找根的步数一步不少），但栈上只留 root、next 两三个变量。压平改父次数差的那 1 次（19998 vs 19999）也有解释：迭代版第二段走到链尾倒数第二个点时，发现它已经指着根，就停了；递归版回溯时不问这个，把它也改写了一遍。

陷阱你怎么会被坑到：递归 find 在长链上直接 RE

递归 find 三行，比迭代版好看，很多人就直接用了。它的栈深度等于树高——而树高取决于你的合并策略和输入顺序。最直接的风险是规模：本机 2MB 的栈、-O2 只撑到 4.4 万帧——竞赛里 n 到 1e5 的链轻轻松松越界。你在本地跑样例（链短）全对，一上大数据就 RE；换到栈更大的机器（Linux 默认 8MB，同一份代码能撑到五六十万帧）侥幸全过，评测机栈一紧又死回去。-O0 的承受能力比 -O2 更小（本机 3.3 万对 4.4 万），评测机多半不开优化。

规则：竞赛代码里凡是「深度可能等于输入规模」的递归，一律改成迭代，或者确认评测机的栈够深（多数不够）。这条同样适用于 DFS、拓扑排序的递归写法。

陷阱你怎么会被坑到：下标混用，编译器一句话都不说

题目给的顶点是 1..n，C 的数组是 0..n-1。三种写法都合法：

  • 读入时统一 -1，内部全用 0 基；
  • 数组开 n + 1，内部全用 1 基，0 空着；
  • 干脆全部按题目写法。

但一个程序里只能选一种。 混用的典型症状是：find(n) 越界读到 parent[n]（那块内存属于别的变量），结果「有时对有时错」，而且加一行打印就变好——因为布局变了。这种 bug 用对拍也未必抓得到（对拍只比结果），最好的防线是：下标转换只在一个地方做，读完数据立刻统一。

下一单元讲堆与优先队列：并查集回答「在不在一个集合」，堆回答「当前最小的那个是谁」，两者经常一起出现在 Kruskal 和 Dijkstra 里。

小结这一节的要点
  • 并查集只维护两件事：find（你的根是谁）和 union（把两个根接起来）；判断「是不是一伙」就是比较两个根；
  • 路径压缩在 find 里顺手做，迭代写法两段 while：第一段只找根，第二段改路径（先存 next 再改）；
  • 按大小合并把树高压在 log n 以内；两者合起来摊还 O(α(n))，工程上当作近似 O(1)；
  • 实测里「只按大小合并」已经不慢（1e6 次 23 ms），压缩只快一点点——必须有的是按大小合并，不是压缩；
  • 带权并查集把「差」存进 delta，合并时的新差是 d - vb + va；压缩时先累加 delta[p] 再改父亲；
  • 扩展域把一个人拆成两个点，朋友合并两次、敌人跨域合并两次；判矛盾靠 x 与 x + n 是否同根；
  • 递归版 find 的深度等于链长：本机 -O2 下 4.4 万帧就被系统杀死（0xC00000FD），竞赛代码一律用迭代；
  • 对拍要自己实现随机数、比两个维度、失败时打印轮次与具体点。
自测题自测题（先自己答，再对答案）
  1. find 的第二个 while 里，为什么必须先用 next 存下 parent[x]，再改 parent[x]？如果反过来会发生什么？
  2. 一个并查集只做了按大小合并、完全不做路径压缩。它的单次操作复杂度是多少？为什么不是 O(n)？
  3. 带权并查集合并时，delta[rb] = d - vb + va 这条式子是怎么推出来的？va 和 vb 分别是什么？
  4. 扩展域里数组要开多大？如果只开了 n，最可能的症状是什么？
  5. 为什么本单元的对拍只把 n 做到 200？如果改成 2 万，会有什么问题？
  6. 递归版 find 在本地测试全过，交上去却 RE，最可能的原因是什么？怎么改？
注自测题答案
  1. 因为 parent[x] 一改，就再也找不到「路径上的下一个点」了——你会原地打转或者跳到一个不相干的点。先存 next，改完再让 x = next。
  2. 摊还 O(log n)（最坏也是 O(log n)）。因为每次把一个集合挂走，它所在集合的大小至少翻倍，所以任何点最多被挂 log2(n) 次，树高不超过 log2(n)。
  3. d = v[b] - v[a]；va = v[a] - v[ra]、vb = v[b] - v[rb]（都是各自到根的差）。代入解出 v[rb] - v[ra] = d - vb + va，这就是新根 rb 到 ra 的差，也就是新的 delta[rb]。
  4. 数组长度 2n。只开 n 时，写 x + n 会越界到堆上别的对象，症状是结果时对时错、加打印就变好——因为内存布局被改了。
  5. 因为暴力每次查询要 DFS 一遍，O(n²)；n = 2e4 时一轮就要几亿次操作，200 轮跑不完。对拍的目标是「找反例」，数据要小而密，不是压测。
  6. 树太深导致栈溢出。深度等于链长：本机实测 -O2 下 4.4 万帧就被系统杀死（0xC00000FD，栈溢出），-O0 下 3.3 万就死——竞赛的 n 轻松越过这个数。终端里 bash 报 127、PowerShell 读 -1073741571，闸门按无符号 32 位读是 3221225725。把递归改成迭代：先用一个循环找到根，再用第二个循环把路径压平。
