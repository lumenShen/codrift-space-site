2.1 先看工程长什么样

上一节的单调栈解决的是「下一个更大元素在哪」——它只看将来。这一节的单调队列多了一根弦：元素不但会比人矮，还会过期。窗口每滑一格，就有一个下标永久出局。为了把这件事讲透，本节配了三个例子工程：一个算法类三件套（滑动窗口最大值，正解加暴力加对拍）、一个数据结构类三文件（环形双端队列）、再把同一个队列搬进 DP（窗口 DP，也是三件套）。阅读路线建议照节的顺序走：2.2–2.4 把原理和论证拿下，2.5 弄懂数据结构本身，2.7–2.8 是两份可以直接抄的模板，2.9 的表供赛时查。

大白话这一节想让你先建立一个画面

把单调队列想成一排排队等当最大值的候选人，从队头到队尾个子越来越矮：

  • 新来一个人，会把队尾所有比他矮、或者和他一样高的人请出去——只要他还在窗口里，那些人就永远轮不上「最大值」；
  • 队头个子最高，随时能报出答案，但他有任期：窗口左边界一旦越过他，他就从队头走人；
  • 于是「窗口最大值是谁」永远只需要看一眼队头。

第 1 帧是本节的起点：单调栈那一节的工程已经在 ch02/ 里落好，本节的故事直接从它接下去。第 2 帧新增 sliding_window_max/——注意它比大纲的「三件套」多出三个 STL 文件，那是 2.8 的应用层。第 3 帧一口气加了两个目录：deque_ring/ 是把「队列」本身造出来的数据结构工程，dp_window/ 把同一个队列用于 DP 转移。清单没有画进帧里：它们按程序分文件放在各自目录（sliding_window_max 三份、dp_window 两份、deque_ring 一份），六个清单全部 mode: "run"，unit 都指向本单元。

三个工程各自的角色要分清。sliding_window_max 与 dp_window 是算法类三件套：正解、暴力、驱动各是一个编译单元——正解和暴力必须分家，对拍时各跑各的，谁也不能偷偷调用谁；驱动是第三个，负责造数据、跑两版、比对。deque_ring 是数据结构类三文件：include/deque_ring.h 只放声明，src/deque_ring.c 放实现，src/main.c 是给你做实验的地方。这两类分法是本书的固定形态：要证明一个算法对，用三件套；要看一个数据结构长什么样，用三文件。每个工程都刻意保持「一条 gcc/g++ 命令编完」：源文件全部列在命令行上，不依赖任何构建系统——这不是在迁就哪台机器的安装清单，而是赛场上交题的真实形态：评测机上你只有一行编译命令，写得出来就交得进去。

2.2 滑动窗口最大值：先把「能过」的写出来

题目是 LeetCode 239 的原形：一个长 n 的数组 a，一个长度 k 的窗口从左到右每次滑一格，输出每个位置的窗口最大值，共 n-k+1 个。n 是 1e6 级别、k 是 1e3 级别时，逐窗扫描的 O(nk) 大约要做 1e9 次比较——1 秒的预算下这就是生死线。所以先把参照物（暴力）写出来，它慢，但一眼能看出对：

正解只有二十行，四步循环值得背下来——但背之前先弄懂每一步在丢什么。顺带说一句暴力自己的写法细节：它按窗口右端点 i 循环（从 k-1 到 n-1），内层从左端点 i-k+1 扫到 i——如果反过来按左端点循环，最后一个窗口的右端点是 n-k 还是 n-1 就要重新想一遍，n-k+1 这个答案个数恰恰最容易在这里差一。按右端点写，「答案写进 out[i-k+1]」的对应关系一目了然，这也是参照物的一个隐藏职责：它得写得让人一眼看出对，包括下标对应关系。正解如下：

四步各管一件事：第 1 步管「过期」——窗口是闭区间 [i-k+1, i]，下标 i-k 刚好滑出去，从队头走人；第 2 步管「没前途」——队尾那些值不超过 a[i] 的下标，只要 i 在窗口里就压它们一头，留它们只会挡路；第 3 步入队；第 4 步报答案——队头永远是当前窗口的最大值（为什么，2.4 专门论证）。注意队列里存的是下标不是值：值没法判过期，下标才能跟 i-k 比较。

语法规则单调队列四步循环的三个约定
  1. 队列里存下标，比较时才取值：a[q[tail-1]] <= a[i]——过期判定靠下标跟 i-k 比，值判定靠 a[...]。
  2. 窗口是闭区间 [i-k+1, i]：所以过期判定是 q[head] <= i - k（i-k 这个下标恰好出局）。把等号丢了，就有一个窗外元素混在队头。
  3. 队尾弹出用 <=（相等也弹）：这让队内值严格递减。等值元素只留最靠后的那个——它过期得最晚，是同类里活得最久的。

先说这题在赛场上长什么样：输入一行 n 个数和窗口长 k，输出 n-k+1 个数，n 到 1e6、k 到 1e3 是常态。暴力要做约 n·k 次比较，1e6 × 1e3 = 1e9 次——按 alg01 的规模表，1 秒的预算就卡在这条线上，所以「暴力能过小数据、正解才能过大数据」不是修辞，是这道题的判题现实。再看代码里的边界：k <= 0 或 k > n 直接返回 -1，窗口不存在就谈不上最大值；k = 1 时窗口就是你一个人，第 1 步把上一轮刚入队的下标判成过期、整个弹空，自己入队、队头即答案，每个元素各报一次（第 2 步有 head < tail 守着，队列空了它根本不触发）；k = n 时整个数组只有一个窗口，只有 i = n-1 那一步报答案。out 的容量也要对上：答案恰好 n-k+1 个。至于队列里为什么存下标而不是值——存值就丢了「它从哪来」，过期判定无从谈起；存下标还顺带解决等值问题：值相等的候选里最靠后的那个过期得最晚，<= 把前面的都弹掉，留的正是它。

样例那三行也值得读。正解： 3 3 5 5 6 7 是六个答案，对应六个窗口 [0,2] 到 [5,7]：[0,2] 的最大值 3 来自下标 1；[1,3] 还是它（窗口右移，它没出界也没遇到更大的）；[2,4] 与 [3,5] 的 5 来自下标 4——它一进来就把队尾清了场；[4,6] 的 6、[5,7] 的 7 各自独占。六个窗口只动用了四个不同的下标，因为下标 1 的值 3 连续服务了两个窗口——同一个数在不同窗口里当最大值，靠的是队列记住它的下标而不是值。暴力： 那一行逐字相同，是「两种独立写法在同一份样例上先对齐」的第一道保险——样例都对不上，对拍就不用跑了。至于对拍为什么能信：正解与暴力是两份独立写的代码（一个用队列、一个双层循环），数据是固定种子生成的四类极端形态，比对按逐窗口进行——三者凑齐，一个 bug 想同时躲过两份实现和四类数据，概率已经很低。这不是数学证明，是工程上的充分怀疑；数学证明在 2.4，两者互补。

2.3 队列的每一步：帧里走一遍

拿教科书样例走一遍队列，你就知道「过期」和「没前途」各在什么时候动手。样例 a = 1 3 -1 -3 5 3 6 7、k = 3，窗口 [i-k+1, i]：

第 1 帧是队伍的常态形状：下标递增、值递减，队头 1 的值 3 就是窗口 [0, 2] 的最大值。第 2 帧演示「没前途」的反面——-3 比队尾还小，它不弹任何人，老老实实排到队尾：它虽然现在是最小的，但等 1、2 都过期之后，它就是窗口里剩下的人。第 3 帧是两头都动的时刻：下标 1 滑出左界（i-k = 1，1 <= 1 过期），从队头走；值 5 从队尾一路弹掉 -1 和 -3，自己当队头。第 4 帧最极端：6 比队里所有人都大，整个队列被弹光，只剩它一个。八步走完，答案正好是 3 3 5 5 6 7。

对拍里那四类数据，每一类都在戳循环的某个角落。全相同（a[i] = 7）：第 2 步的等号每次都把队尾清空，队列永远只剩当前元素一个——没有等号它会涨到 k 个；递增：新元素永远比队尾大，队列同样只剩一个，每个窗口的最大值都是刚滑进来的那个数；递减：没人能弹动队尾，每个下标都进队，队列涨到 k 个，队头一直是全局最大值，直到它过期——这是「队列长度 ≤ k」的极端情形，也是 q 缓冲区要按 n 开的前奏（2.4 记这笔账）；纯随机：两头都动，最容易暴露「弹头弹尾顺序写反」「过期判定差一」这类错。200 组里四类轮着来，等于把四条极端路径各走了几十遍——这比「再想一遍代码」便宜得多。

顺带回答一个读者常问的问题：第 1 步（弹头）和第 2 步（弹尾）的顺序能不能换？能。判据不是「两步各管各的下标」，而是两种顺序跑完，队列里剩的是同一批下标：窗口内、值严格大于 a[i] 的那些（第 3 步再补上 i 自己）。为什么一样？弹头删的是「下标 ≤ i-k」的那截前缀（队内下标递增，过期的全排在队头），弹尾删的是「值 ≤ a[i]」的那截后缀（队内值递减，不够强的全排在队尾）——两截各自删完，剩下的正好是中间「没过期且够强」的一段，谁先动手都一样。注意两类被删的下标并不互斥：一个又过期又不够强的元素，两步都判定它该走（k=1 时上一轮的元素就两样占全）。不能丢的是每个 while 前面的 head < tail 守卫：弹头弹到队列空了还继续比，q[head] 就是野值。另外，答案写进 out[i-k+1]——窗口右端点是 i，答案下标是左端点，这一减一加是另一处常写错的地方；对拍把 out 的每个格子都对着暴力查过，写错了第一组就 FAIL。存下标还有个附带的好处：有的题要的是「最大值的下标」而不是值（比如后续还要查它的位置），这时候答案直接就是 q[head]，连 a[] 都不用取。

陷阱你怎么会被坑到：把过期判定的等号丢了

第 1 步写成 q[head] < i - k 而不是 <=，小数据测试全过——你会误判成「队尾弹出写错了」或者「答案取错了位置」。真相是：窗口 [i-k+1, i] 的左端点是 i-k+1，下标恰好等于 i-k 的元素这一步刚出局，判定必须是 q[head] <= i - k。

丢掉等号会怎样？拿 a = 5 1 2、k = 2 手推一遍：i=1 时队列是 [0, 1]（值 5、1），答案 5，对的；i=2 时窗口是 [1, 2]，正确答案是 2——但 q[head] = 0，判定 0 < i-k = 0 不成立，过期的 5 还赖在队头，报出来的答案是 5，而正确的 2 被它压着（值 5 比队尾大，第 2 步永远轮不到它出场）。样例数据往往躲过这个坑（窗外元素恰好不是最大值），随机数据一炸就是大面积 WA。

2.4 为什么队头就是窗口最大值：不变式与引理

赛场上敢用这段代码，靠的不是「样例过了」，是下面这套论证。它不长，但每一步都要能说出口。

不变式（每次循环的第 3 步执行完、i 入队之后成立）：

  • I1（下标递增）：队内下标从 head 到 tail-1 严格递增；
  • I2（值递减）：对应的值严格递减，即 a[q[head]] > a[q[head+1]] > … > a[q[tail-1]]；
  • I3（都在窗内）：队内下标全部属于 [i-k+1, i]。

归纳基础：i = 0 时队列只有 [0]，三条显然成立。

归纳保持：从 i-1 到 i，第 1 步把 <= i-k 的队头弹掉，剩下的都 >= i-k+1，I3 成立，弹头不动摇 I1、I2；第 2 步把队尾值 <= a[i] 的全部弹出，然后 i 入队——i 是下标最大者，I1 成立；它比新的队尾（没被弹的最后一个）值大，I2 成立。三条不变式完好。

淘汰引理（第 2 步弹掉的元素确实没用了）：设 j 在第 2 步被弹、i 随后入队，则 j < i 且 a[j] <= a[i]。对任何未来窗口 [t-k+1, t]（t > i）：如果 j 还在窗口里，那么 i 也一定还在（j >= t-k+1 而 i > j，整数下标下 i >= t-k+1），并且 a[i] >= a[j]。所以窗口最大值要么是 i、要么是别的 >= a[i] 的元素——轮到谁也轮不到 j。把它留着，只会让它有一天挡在队头冒充最大值。

两个推论合起来就是正确性：第 4 步取答案时，I3 保证队头在窗内（不是窗外的老古董），I2 保证队头值是队里最大的；再由引理，窗内所有被弹掉的下标都不可能比队头大——于是 a[q[head]] 就是整个窗口的最大值。第 1 帧到第 4 帧里你看到的每一次弹出，都是这条引理在动手。

回看三条不变式，每一条都不是白给的。**I1（下标递增）**让队列长度被窗口卡住（tail - head ≤ k），没有它「队列」就名存实亡；**I2（值严格递减）**是「队头即最大值」的实体——把 I2 弄成非严格，答案没错但队列虚胖；**I3（都在窗内）**由第 1 步维护，它是过期机制存在的意义。三条里真正吃功夫的是 I2 的保持：第 2 步弹的必须「够狠」——凡是 <= a[i] 的都弹，留一个都比 i 弱的下标，I2 在下一次入队时就断了。写代码时把这三条当成注释里的合同，每改一行就对着合同读一遍，比事后调试省得多。

不信的话可以反过来推（反证）：假如第 4 步时队头不是窗口最大值，那真正的最大值只有两种下落——要么还在队里。可 I2 说队头是队里值最大的，它在队里就轮不到别人冒充，矛盾；要么它被弹掉过。可引理说被弹的下标 j 总有一个更晚入队、值不小于它的 i 压着，而「真正的最大值」不可能被谁压着（没有谁比最大值大），矛盾。两条路都堵死，队头就是最大值。反证不给你新信息，但它能检验你有没有真读懂归纳保持那一步——哪一步说不通，回头补哪一步。

复杂度也顺出来了：每个下标恰好入队一次（tail++ 总共 n 次），最多出队一次（从队头或队尾），所以虽然有嵌套的 while，整个循环是均摊 O(n)——每个元素被「看」的总次数是常数次，这就是 2.9 的实测里 1e6 数据只要几毫秒的原因。均摊的账可以记到每个下标头上：一个下标一生只有三件事——进队一次、从队头走（第 1 步，至多一次）、从队尾走（第 2 步，至多一次）。tail 与 head 的每一次前进都有一次入队买单，n 次进队最多带来 n 次指针动作，总功 O(n)。alg01 里 vector 扩容记的是同一套账，只是那里摊的是拷贝，这里摊的是指针移动。

这笔账还顺手回答了一个内存问题：队列里同时最多 k 个元素，q 却要开 n 个。因为数组模拟不回收出队的格子——head 与 tail 只会前进，最坏情形（递减数据）一个值都不从队尾弹，tail 一路涨到 n，用过的格子全程占着。按「队列大小」开 k 个，在递减数据上就是越界写。这也是 2.5 的环形队列存在的理由之一：环形结构把出队的格子立刻变成可复用的空位，cap 个格子就够——两种模拟各有一笔账，别混着算。

时序上还有一个容易含糊的点：第 4 步取答案时，队头会不会刚好过期？不会——第 1 步已经按「当前这个 i 的窗口」弹过头了，窗口左界这一步不再变化；而队头是第 2 步之后幸存的、值最大的下标，它必然 >= i-k+1。换句话说，取答案的那一刻，队列恰好是窗口的一个合法摘要，一个多余的检查都不需要。

还有一处容易含糊的地方值得点明：第 2 步的 <= 换成 <，答案仍然全对（不变式 I2 退化成非严格递减，队头照样是最大值），只是队列里会堆着一批等值下标，最坏情况（全相同数据）队列长度涨到 k。所以等号在这里是「效率选择」，而在第 1 步（过期判定）里是「正确性开关」——两个等号，一软一硬，别记混。

2.5 环形双端队列：把队列装进定长数组

单调队列要两头都能进出，std::deque 能干，但原理层我们手写——一来竞赛里经常用它装别的状态，二来 2.8 你会看到 STL 版到底替你省了什么。

大白话双端队列与「环形」是什么意思

普通队列：一头进、另一头出，像食堂排队。双端队列（deque，double-ended queue）：两头都能进也能出——单调队列正是「队尾进、队头过期出、队尾没前途出」三件事都要做。

「环形」是数组模拟的招数：数组是死的，指针是活的。tail 走到数组末尾时绕回 0，写进前面刚腾出来的空位——元素不搬移，指针绕圈。这跟「把整个队列往前挪一格」的朴素写法相比，省掉了每次出队 O(n) 的搬运。

为什么非要绕圈？对比一下朴素的「搬移」写法：每次 pop_front 把后面 size-1 个元素整体往前挪一格，出队是 O(n)；滑动窗口要出队 n 次，光是搬运就是 O(n²) 量级。环形数组把搬运换成指针绕圈，出队入队都是 O(1)，代价只是下标计算要过一次 %。还有两个设计选择值得点破：容量固定——竞赛里队列长度都能预算出来（窗口题是 k，BFS 是 n），开够就行，自动扩容的活让给 std::deque（2.8 会看到它的分块缓冲）；下标用 int 不用 size_t——head - 1 在无符号下不是 -1 而是天文数字，绕圈运算里这个坑比 % 的负数坑还深。dr_dump 是给驱动用的调试函数：从 head 出发绕圈读 size 个——它顺便演示了「逻辑顺序 ≠ 数组下标顺序」，最后一帧的 99 1 会把这一点看得清清楚楚。

陷阱你怎么会被坑到：C 的 % 对负数不是取模

dr_push_front 里那句 (d->head - 1 + d->cap) % d->cap，中间的 + d->cap 看着多余——你可能会想「-1 % 4 不就是 3 吗」。真相是：C 的 % 对负数是向零取整的余数，-1 % 4 等于 -1，不是 3。丢了 + cap，head 一绕圈就变成 -1，接下来 buf[-1] 是越界写。

你会被坑到的路径很典型：测试数据小，head 从来没绕过圈，程序样样都对；某天数据量大了一点，head 第一次从 0 往前退，越界写发生在堆上——症状是「结果时对时错」甚至段错误，而且换个编译选项、换个机器，症状还会变（踩到谁的内存取决于分配布局）。修法只有一条：凡是可能减出负数的下标，先 + cap 再 %。这条对 pop_back（tail - 1）和 dr_back（tail - 1 只读）同样生效。

2.6 与单调栈的分工：多了一个「弹头」

上一节的单调栈和这一节的单调队列，队尾的行为一模一样（都是「来个大的就弹」），差别只在队头：

单调栈 单调队列
进出方式 只在一端（栈顶）进出 两端都能进出
队头/栈底的下标 一直留着，不管多老 过期就弹（<= i-k 出局）
回答的问题 「下一个更大元素是谁」（看将来） 「当前窗口最大是谁」（看现在）
典型题 下一个更大元素、直方图最大矩形 滑动窗口最大值、跳格子 DP
数据结构 数组 + 一个栈顶指针 数组 + head/tail（环形或直线）
大白话两个结构的心理模型差在哪

单调栈像考试交卷的队伍：你排进队之前，会把前面所有分数比你低的人一个一个挤走——「你都比不过我，等你交卷也轮不到你出头」。它从不请人离开，队尾越来越强，队头那个最弱的人能一直待到最后，直到某天被别人挤走时顺便告诉你「我就是你的下一个更大元素」。

单调队列像有大佬保护期的工作队列：同样的挤人规则，但每个人还有个合同到期日——到期的人就算还是队里最强的，也得从队头走。两句话记牢：栈问「我的下一个更大是谁」，队列问「现在窗口里谁最大」。

一句话记住分工：单调栈不弹头，所以它记得所有历史；单调队列弹头，所以它只记得一个窗口。有个安静的等价关系值得知道：把窗口长度 k 取成无穷大（没有过期这回事），单调队列就退化成单调栈——你上一节写的下一个更大元素，就是这个队列把第 1 步删掉后的样子。反过来说，单调队列 = 单调栈 + 「过期」这一维。什么时候用哪个，判据就一条：题目里有没有「窗口」这个会滑动的东西。有窗口，用队列；只有「下一个/上一个」，用栈。

还有一条通用技巧：这套代码全部是为最大值写的，要最小值就把队尾弹出的那个比较符号翻转——过期判定照旧（它看下标不看值，第 4 步取答案也没有比较），队尾弹出从「a[q[tail-1]] <= a[i] 弹掉」改成「a[q[tail-1]] >= a[i] 弹掉」，队内变成严格递增，队头就是窗口最小值。滑动窗口最小值、窗口 DP 的「最小代价转移」都是这一份代码改一个字符的事——改完记得四类对拍数据重跑一遍，别信「肯定没问题」。

弹头也带来一个新问题：会不会弹着弹着队列空了，第 4 步取队头取了个寂寞？不会——当前下标 i 自己在第 3 步刚进队，它永远在窗口里，所以队列至少有它一个。这也是四步循环不需要任何「队列非空」判断就能取答案的原因：第 1、2 步的 while 各有 head < tail 守着，第 4 步不需要守。上一节 histogram_max_rect 那道直方图题也能从队列视角重看：每根柱子被弹出的时刻，正是「它作为最小值的区段」结束的时刻——弹栈与弹头在那道题里扮演同一个角色，只是一个是被更大的数挤走，一个是被窗口滑走。

这也是为什么本节的工程里没有出现链表：数组模拟一头一尾两个指针（或一进一退一个栈顶）就够了。链式结构每存一个值要背一个指针，1e6 次进出队全是指针追逐和缓存缺失，是纯粹的常数损耗——上一节的结论在这里原样成立，只是多了一个指针。代码体积上两者也几乎一样：单调栈一个 top，单调队列一个 head 加一个 tail，多出来的那几行就是过期判定——所以赛场上写哪个都不吃亏，按题目需要的那个写就好。

2.7 窗口 DP：转移取「窗口里的最大 dp」

单调队列在赛场上最值钱的用法，是给 DP 提速。看这个跳格子问题：从位置 0 出发，每次向前跳 1 到 k 步落到位置 i，落地得 w[i] 分，问走到位置 n 的最大总得分。转移方程是 dp[i] = w[i] + max(dp[i-k .. i-1])——每一步的最优决策，都是「前一个窗口里 dp 最大的那个落点」。

值得重走一遍「怎么想到用它」的思路链，因为赛场上没人提醒你。第一步照暴力写：转移要扫窗口取最大，O(nk)，估算 n·k 超过 1e8 就该停手想优化。第二步盯住「慢在哪」：慢在重复比较——窗口每滑一格，有 k-1 个元素在上一轮比过、这一轮还要再比一遍。第三步问「能不能只留有用的」：只有「窗口里 dp 最大」的那一个落点有用，其余的等它过期就完。这三步把问题变成了 2.2 的原题，队列照搬。凡是转移形如「取一个滑动区间里的最值」的 DP，都能这么推——套路不在背模板，在这三问。

大白话为什么这能用单调队列

暴力 DP 算 dp[i] 时，要把窗口里 k 个旧状态扫一遍取最大，总共 O(nk)。但你只关心窗口里的最大值，不关心其余 k-1 个是谁——这跟滑动窗口最大值是同一个形状：i 每加 1，决策窗口 [i-k, i-1] 也滑一格。把「dp 值」当成 2.2 里的 a 值、把下标 j 当成候选，队列照搬。唯一的差别：这里的比较对象 dp[j] 不随 i 单调（w 可以是负的，dp 有升有降），但「队内 dp 严格递减」这条不变式根本不依赖 w 的单调性——队列丢的是「相对顺序里没前途的人」，不是「绝对值小的人」。

跟 2.2 摆在一起看，四步还是那四步，但有两处故意的不同，每处都是考点：

  • 窗口边界差一个等号。这里过期判定是 q[head] < i - k（严格小于），2.2 里是 q[head] <= i - k。不是笔误：滑动窗口的窗口是 [i-k+1, i]，而 DP 的决策窗口是 [i-k, i-1]——i 自己跳不到自己头上，i-k 这个下标恰好还能跳到 i（跳 k 步），所以它还活着。两个窗口错位一格，两个等号就一软一硬。
  • 先取答案、再弹队尾、最后入队。第 2 步在 i 入队之前就算 dp[i]——因为 i 不能当自己的决策。照搬 2.2 的顺序（弹尾 → 入队 → 取答案）在这里根本写不出来：弹尾要比的 dp[i] 还没算出来；要是把取答案挪到最前（先算 dp[i] 再弹过期队头），队头还没做过期判定，读到的可能已经是出窗的下标。这份代码的顺序是最省事的：弹头（判定窗口 [i-k, i-1]）、取答案、按 dp[i] 弹尾、入队——每一步用到的都是已经算好的值。

为什么 dp[q[head]] 不会读到空队列：i-1 在上一轮第 4 步刚进队，它满足 i-1 >= i-k（k >= 1），过期判定弹不掉它；队尾弹出用的是本轮刚算出的 dp[i]，发生在取答案之后，也碰不到它。所以队头永远有一个合法候选——这条论证同时是「k >= 1 必须写进接口前置条件」的理由，k = 0 时窗口空了，转移本身没有意义。

对拍比「最终答案」更严：整张 dp 表从 0 到 n 逐格比对，200 组、w 含负数、k 取遍 [1, n]——哪个格子错了都能指认出来。路径重建用的是等式反查而不是另存决策数组：dp[j] + w[i] == dp[i] 成立就说明 j 是 i 的一个最优前驱；多条最优路径都合法，这份代码只承诺给出其中一条（取窗口里最先遇到的 j，只为确定性）。

空间上还有一笔可省的账：转移只用到最近 k 个 dp 值，理论上可以把 dp 表滚动成 k+1 个格子——但这道题的路径重建要读整张表，滚动数组存不下历史。这是「省内存」与「要方案」之间的经典取舍：只要答案，滚动；要打印方案，留全表。两边都对，先问自己要什么。

陷阱你怎么会被坑到：dp 表用 int 存

w[i] 是 int，顺手就把 dp 也开成 int——样例（dp 最大 14）毫发无损，随机数据也常常没事。真相是：dp 的值域是路径长度 × 权值，n = 1e6、|w| = 1000 时 dp 能到 1e9 量级，int 的上限约 2.1e9，贴着天花板走；再宽一点的权值（比如 1e4）就当场爆掉，症状是答案突然变负或者对不上。

这份工程把 dp 定成 long long（dpwin.h 的注释里写死了「dp 至少 n+1 个 long long」），编译命令里 -Wall -Wextra 也不会替你抓这种错——类型是你自己选的，编译器只管传递。规则：DP 的答案数组，值域先估再选型，估不准就 long long。赛场上这道题 TLE 没有、WA 一片，多半就是它。

大白话multiset 是什么，为什么它能报最大值

multiset 是一棵自动排序的、允许重复的红黑树：元素丢进去，它随时保持有序。所以「当前最大值」永远是最后一个元素（*rbegin()），不用你扫。窗口滑动时插一个新数、删一个旧数，各花 O(log k)——它把整个窗口都装在手里，而不像单调队列只留「有资格的」那一小截。什么时候用它？当窗口里除了最大值还要随时查别的（中位数、第 k 大、查某个值在不在），单调队列一根筋答不了，multiset 的「全窗口在手」就值钱了。

STL 版的对拍是三方比对：std::deque、multiset、暴力各算一遍，200 组逐组一致才算过。注意暴力也重写了一份（slide_max_brute），没有去调 C 版——alg02 讲过的对拍骗局之一是「正解与暴力共享同一个错函数」，C++ 版故意用另一条语言路径（容器、迭代器、size_t）独立实现一遍参照物，两边代码长得越不像，同一个 bug 同时潜伏在两边的概率越小。这份清单同样 mode: "run"，OK 200 由闸门实跑对账：

陷阱你怎么会被坑到：multiset 的 erase(值) 删光所有相等的

窗口里最常见的就是重复值。把第 29 行的 win.erase(win.find(a[i - k]))「简化」成 win.erase(a[i - k])，编译照样过、样例照样过——erase(值) 的语义是删光所有等于该值的元素。窗口里只要有第二个和滑出元素相等的数，它也一起被删了，集合比真窗口小；下次 *rbegin() 报出来的可能是缺了人的窗口的最大值，也可能是集合变空后的未定义行为。

你会怎么误判：症状是「答案偶尔偏小」或随机段错误，你大概率去查滑动逻辑和下标，不会想到一句看起来等价的 erase。真相：按值删和按迭代器删是两个函数，erase(find(v)) 只删一个。这类坑在随机数据对拍里必炸——这也是 STL 版也要三方对拍的原因，STL 不是免检牌。

工程惯例工程惯例：三种写法什么时候用哪个

这是惯例，不是标准，判据是「窗口里还要查什么」：

  • 只问最大（或最小）：手写数组单调队列，常数最小——2.9 的表里它比 std::deque 快约 1.7 倍；
  • 只问最大、不想手写：std::deque，逻辑与手写版一一对应，容器管内存；
  • 窗口里还要查别的（中位数、第 k 大、任意值）：multiset，慢一个 log 但功能全。

代价各不相同：手写版要自己保证缓冲区（q 开 n 个）；multiset 的节点在堆上，1e6 元素的指针追逐是实打实的常数。赛时的顺序通常是：先 std::deque 写对（它跟手写版逐行对应，不容易错），确认这题卡常数再换手写——先正确后常数，这条顺序反过来就是灾难。选型之前先问一句：我到底要多少个「最」？

小结这一节的要点
  • 单调队列 = 单调栈 + 弹头：队尾照旧「来个大的弹小的」，队头多一条「过期（下标 ≤ i-k）就出局」，两步各管一类没用的下标；
  • 正确性靠三条不变式（下标递增、值严格递减、都在窗内）加淘汰引理（被弹的 j 对任何未来窗口都被 i 压着）——队头永远在窗内且值最大；
  • 整个循环均摊 O(n)：每个下标入队一次、出队至多一次；实测 n=1e6、k=1000 只要 6.6~6.9 ms，暴力 O(nk) 要 393~395 ms；
  • 环形双端队列用 head/tail 绕圈，head==tail 时靠单独的 size 分清满与空；C 的负数 % 向零取整，减出负数的下标必须先 + cap；
  • DP 版与滑动窗口版差两处：决策窗口 [i-k, i-1] 的过期判定是 q[head] < i-k（等号换边），且先取答案再弹队尾入队；
  • 应用层 std::deque 是手写版的逐行翻译，multiset 慢 7~8 倍但能随手查别的；erase(值) 删光相等的，删一个必须 erase(find(值))；
  • 溢出两处：dp 表与答案累加器都要 long long（n=1e6 时答案之和约 8e9，int 装不下）；STL 版要防 erase(值) 删光相等的元素——按迭代器删一个；
  • M12 三层差距各有名分：算法层五六十倍（O(n) 对 O(nk)）、实现层约 1.7 倍（堆上对栈上）、容器层 7~8 倍（O(n log k) 对 O(n)）——选型时先分清差距在哪一层。

注自测题答案
  1. 因为两个窗口不一样：滑动窗口的窗口是 [i-k+1, i]，下标 i-k 刚好出局，判定是 <=；DP 的决策窗口是 [i-k, i-1]（i 跳不到自己头上），下标 i-k 恰好还能跳到 i（跳 k 步），它还活着，判定只能是 <。两个等号差在窗口错位的一格上——把 DP 版的等号加回来（写成 <=），会提前弹掉 dp[i-k]，恰好它还是窗口最大时 dp[i] 就算小了。
  2. 答案不会错。非严格递减的队列，队头仍然是窗内最大值。但等值下标会全部留在队里，全相同的数据上队列长度涨到 k，比较次数从「每个元素弹一次」变多，常数变差。所以这个等号是效率选择；而过期判定里的等号（第 1 题）是正确性开关——一个错了变慢，一个错了变错，别记混。
  3. 数组模拟不回收出队的空间：head 与 tail 只前进，tail 的终值等于「整个过程进过队的下标总数」减去「从队尾弹过的次数」。最坏情形是递减数据：一个值都不从队尾弹，tail 一路涨到 n，所以缓冲区要 n 个。同时「活着的」元素确实 ≤ k（过期判定保证 tail - head ≤ k）——开的不是「队列大小」，是「历史总量」。
  4. head 从 0 往前退时算出 -1，而 C 的 -1 % 4 是 -1 不是 3（% 对负数向零取整），于是 buf[-1] 越界写。测试数据小、head 没绕圈时一切正常；数据一大就写进堆上别人的内存，症状是结果时对时错、加打印就变好——因为内存布局变了。修法是所有可能减出负数的下标都先 + cap 再 %。
  5. 不能。erase(值) 删光集合里所有等于该值的元素，窗口里有第二个相等的数时它也一起没了，集合比真窗口小，*rbegin() 从此不是真窗口的最大值；若删到集合变空还会未定义行为。erase(find(v)) 按迭代器只删一个。这个错样例抓不到（样例往往没有重复值），靠三方对拍才炸得出来。
  6. 总和约 7976084623，超过 int 上限 2147483647，溢出后的和没有规律（可能为负），症状是「两种解法的和对不上」，你会误以为某个解法错了，把两份代码翻来覆去读。小数据上抓不到：n 小的时候和只有几百万，int 装得下。值域要按「n × 单个答案的最大值」先估——1e6 × 8e3 ≈ 8e9，long long 起步。
