4.1 先看工程长什么样

前面三个单元把注意力、位置编码与完整的 Transformer block 都搭起来了。那些单元里，我们默认「token 已经躺在张量里」，关注的只是 token 之间怎样交换信息。这一单元把镜头往回拉一格：这些 token 到底是怎么来的？模型在训练时究竟被要求预测什么？预测错了又用一个什么数字来衡量？这三个问题合起来，就是语言建模目标。

答案不在模型结构里，而在一条数据处理链上。原始文本先经过分词器变成 token 序列，再被切成许多「上文—目标」对，然后模型对每个上文吐出一张词表上的概率分布，最后交叉熵把「分布」和「真正的下一个 token」压成一个标量损失。困惑度只是这个损失的指数形式，换一种读数单位而已。

这一单元仍然只用一台机器、一个 CPU、两个源文件。与前面几个单元相比，地基模块从注意力实现换成了 bpe.py——它负责把字符合并成子词；main.py 负责跑完整条链并打印数字。先把工程形状画出来，再一层层拆开。

第 1 帧是讲故事用的起点，并不是说你的磁盘上真的空着——ch02 的目录在整本书写完时当然会有别的例子。第 2 帧里冒出来一个 tokenize_and_lm/，三个新增文件各有分工：bpe.py 放分词规则，main.py 放语言建模目标与打印流程，lm04-token.json 是闸门读的清单。第 3 帧把目录外壳去掉，专门看运行时关系——入口那行 from bpe import encode, train_bpe 把本地模块拉进来，这也是 ch02 起硬规定在 Python 侧的落地方式：从第二个项目开始，不许再用一个单文件脚本糊到底。

为什么非要拆两个文件？表面理由是闸门要求，真正的理由是接缝：你想换合并策略，只动 bpe.py；你想换语言模型的目标函数，只动 main.py。代价是多一层 import 路径要操心——在例子目录下执行 python src/main.py 时，Python 把 src/ 放进模块搜索路径，所以 from bpe import ... 能找到同目录的 bpe.py；如果你在别的目录里执行，路径就变了。这条坑后面还会再提一次。

大白话三个词先分清楚

字符是文本的最小可见单位，一个英文字母、一个汉字、一个标点都算。token 是模型真正看到的最小输入单位，它可能等于一个字符，也可能等于一个词或词的一部分。词表是 token 到整数的映射表，模型只认识表里的整数，不认识字符串。分词器的全部工作，就是把字符串确定性地映射到整数序列，并且能反过来解码。

4.2 三种粒度：字符、词与子词

先看分词粒度。最直观的做法是字符级：把每个字符当成一个 token，英文就是二十六个字母加标点，中文就是每个汉字。它的词表小得可怜，几乎不会遇到「没见过的字」，代价是序列变得极长——一个英文单词 lowest 要拆成六个 token，模型得先学会字母拼写，再学会拼成词，再学会词的意思，信息被拉得很散。序列一长，注意力的平方复杂度跟着涨，训练和推理都变贵。

另一个极端是词级：按空格或词典切词，每个词一个 token。序列短、语义完整，是早期统计语言模型的默认选择。代价是词表爆炸：英语靠词形变化就能生成大量低频词，low、lower、lowest 各占一个位置；一旦测试里出现训练时没见过的词，就只能分配一个特殊的未知 token，模型对它一无所知。中文的分词还要先解决「词边界在哪里」这个本身就不唯一的问题。

子词级是两者的折中：常见词保留成完整 token，罕见词拆成若干有意义的片段。lower 可能被切成 low 加 er，newest 被切成 new 加 est。这样词表不至于爆炸，序列也不至于太长；更关键的是，拆出来的片段往往 carries 词法或词根信息，模型见到从未见过的 wider 时，仍能从 wid 与 er 的组合里猜出个大概。BPE 就是生成这种子词词表最流行的算法之一。

第 1 帧强调字符级的长度代价：六个 token 意味着注意力矩阵有三十六格，而子词级只有四格。第 2 帧强调词级的未知词问题：整词查表看着省事，一旦词不在表里就彻底失明。第 3 帧是折中——low 与 est 都是能在别处复用的片段，lowest 只是它们的一次组合。这三帧里每一帧都把原文与切法重新写了一遍，因为渲染器不会把上一帧的节点带过来；这正是读多帧图要守的第一条纪律。

工程惯例为什么词表大小是个要权衡的数

词表越大，单个词越容易被完整保留，序列越短，但嵌入层参数量与词表大小成正比，softmax 的分母也要在更大的候选集上归一化。词表越小，嵌入层越省、泛化到生僻词越容易，但序列变长，注意力开销按长度平方增长。工程上通常选几万到十几万的量级，再用 BPE 或它的变体把低频词拆开。本例只有九个符号，纯粹是为了让每一步合并都能在 stdout 里数清楚，不代表真实规模。

4.3 BPE 的合并直觉：从字符对到子词

BPE 的全称是字节对编码，核心思想一句话就能说完：反复把当前最常相邻的两个符号合成一个新符号。它不做语言学分析，不查词典，只数频次。起点是把每个词拆成字符，并在末尾加一个显式的词边界标记 </w>——这个标记很关键，它让 low 与 lower 里的 low 被区别对待：前者后面跟的是边界，后者后面跟的是 e。

bpe.py 里 pair_stats 负责数频次。它遍历词表里每个词的符号序列，对每一对相邻符号计一次数，权重是这个词在语料里的出现次数。比如语料里 low 出现五次、lower 出现两次，那么字符对 (l, o) 的频次就是七。这种带权计数保证高频词对合并规则的決定权更大。

第 19 行是带权计数的落点：加的是 freq 而不是一，所以出现五次的高频词对能压过只出现两次的低频词对。第 28 行把合并后的词表整个重写一遍——每个词里所有出现的 a b 都变成 ab，没有出现的词原样保留。注意这里用的是字符串替换而不是重新切词，因为词表里的表示本来就是空格分隔的符号串，替换恰好落在符号边界上。

挑哪一对合并，由 pick_best 决定。频次最高者优先；万一两个词对频次相同，按字典序取最小的一个。后者不是语言学考虑，纯粹是为了可复现：Python 的 Counter 在频次相同时保留插入顺序，而插入顺序又取决于字典遍历顺序，如果不加一条确定的打破平局规则，同一次训练在不同运行里可能给出不同的合并序列。

第 33 行先把 pairs 排序，再用 max 取频次最高者；排序是升序，因此频次相同时留下的是字典序最小的那个。第 46 行把每次合并的词对与当时的频次一起记进 history，这份记录有两个用处：一是给读者看合并过程，二是稍后用它把新词编码成 token。最后一行把词表里出现过的所有符号收进集合再排序，得到最终的符号词表——排序同样是為了可复现，因为集合的遍历顺序没有保证。

第 1 帧的十一种符号是四个词的字母去重后加上边界标记得到的。第 2 帧里 lo 先把 l 与 o 吃掉，接着 low 又把 lo 与 w 吃掉，所以单独的 l 与 o 从词表里消失。第 3 帧同理，es 与 est 相继合并，最终留下九个符号。真跑打印的 vocab:[</w>,d,e,est,i,low,n,r,w] 正是这九个符号，顺序是字典序——< 的码位比字母小，所以边界标记排在最前面。

陷阱把词边界标记省略掉会怎样

你会看到：合并照样进行，词表也能算出来，可 low 和 lower 的前缀被一视同仁地合并，模型分不清「词结束了」和「词还在继续」。你会误以为这是语料不够或者合并次数太少，真相是词边界本身就是一种信号：它告诉模型哪些片段后面会断开。少了它，BPE 只按相邻字符的频次合并，无法表达「这个组合只出现在词尾」这种规律。本例在起点就给每个词补上 </w>，正是为了把这个信号保住。

4.4 next-token 目标：把序列变成监督信号

有了 token 序列，下一步是把它变成训练样本。语言建模的目标极其朴素：给定前面的 token，预测下一个 token。把整条序列沿时间轴滑一遍，每个位置都产生一个样本——上文是一段固定长度的前缀，目标是紧随其后的那个 token。这就是所谓的滑动窗口打包。

本例的语料只有四个词，build_corpus 把它们循环十二次得到四十八个 token；pack_windows 用窗口长度一把它切成四十七对。为什么是四十七不是四十八？因为第一个 token 没有上文，必须从第二个位置开始。这个「少一个」的细节常被忽略，却直接影响后面算损失时分母取多少。

打包完成后，模型端做一件事：拿上文的最后一个 token 去查一张 4×4 的表，得到四个 logit，再softmax 成词表上的概率分布。这张表就是整个玩具模型的全部参数。它小到可以在纸上画出来，却能完整地演示「预测—比较—更新」的闭环。真实模型把这张表换成几十层 Transformer，目标函数一个字都不用改。

第 27 行是加一平滑：分子给每对组合加一，分母给每个上文加一个词表大小 V。没有这一步，没见过的组合概率会是零，math.log(0) 直接抛异常；有了它，任何组合都分到一个非零概率，损失永远有限。第 31 行用 len(stream) - 1 做分母，正好等于样本对数——四十七个 token 对，一个不多一个不少。

第 1 帧里，词序是排好序的，不是语料出现顺序——这样换一次运行也不会因为字典顺序变化而改变 token 流。第 2 帧只画了两个位置，实际有四十七个；窗口每次向右挪一格，上文与目标随之整体左移。第 3 帧强调所有对共用同一个损失函数，损失是它们的平均值，不是求和——求和会让样本数不同的两次实验无法比较。

4.5 交叉熵与困惑度：loss 与 ppl 怎么读

现在看损失本身。对每个样本，模型在词表上给出概率分布 p，真正的目标 token 对应概率 p_target。交叉熵取它的负对数 -log(p_target)：目标概率越接近一，损失越接近零；目标概率越小，损失越大，而且放大得越来越快。概率从零点五降到零点一，损失从约零点六九涨到约二点三；从零点一降到零点零一，损失再涨二点三。这种对数刻度正好符合直觉——把一个小概率事件预测准了，值得更大的奖励。

把全部样本的损失平均，得到 loss=1.432969。这个数本身不够直观：它是对数刻度上的平均惊讶度。困惑度把它换回线性刻度：ppl = exp(loss)，本例是 4.191124。一种好记的解释是——模型在每个位置上相当于在大约四个等可能的 token 里均匀猜；困惑度越接近一，模型越确定，越接近词表大小，模型越像在乱猜。

第 43 行打印平均负对数似然，第 44 行紧跟着把它指数化。第 47 行打印探针词 lower 的 token id 序列：token_ids:[5,2,7,0]，查一下第 46 行的词表，第五号是 low、第二号是 e、第七号是 r、第零号是边界标记，合起来正是 low 加 e 加 r 再加词尾。这说明合并记录被正确地复用了：词是从语料里学出来的，但编码规则可以施加到任何新词上，只要它的字符都在词表里。

真跑的完整 stdout 如下。前六行走等号，是待对账的数值行；后两行走冒号，是给人看的结构说明。

一个容易忽略的读法：first_prob=0.272727 是第一个样本上模型分配给正确答案的概率，约等于 3/11。它比词表大小的倒数 1/9 高，说明加一平滑后的 bigram 统计已经学到了一点东西；但它离一还很远，说明这个玩具模型远远谈不上「学会语言」。把首步概率也打出来，是为了防止只看平均损失时错过分布的形状——平均值可能掩盖开头几个样本上模型其实很差的事实。

4.6 为什么困惑度低不一定更好

困惑度是语言模型最经典的指标，也是最容易误用的指标。它低，只说明模型在这份语料、这个词表、这个分词器下，对下一个 token 的概率分配更集中。三件事里任何一件换了，数字就不可比。

第一件是分词器。同一段文本，字符级词表可能只有几十个符号，子词级词表有几万个。词表越小，随机猜的基准困惑度越低，模型的困惑度自然也越低——这不是模型更聪明，是题目更简单。用一个字符级模型的困惑度去和一个子词级模型比，就像拿小学口算成绩和高考数学成绩比，数字没有共同尺度。

第二件是语料。在维基百科上训练的模型，遇到维基风格的文本困惑度会很低；换成社交媒体上的缩写、错别字和表情符号，困惑度会飙升。它测的是「和训练分布像不像」，不是「懂不懂语言」。所以同一个模型在不同测试集上的困惑度可以差好几倍，报告时必须把测试集写清楚。

第三件是平滑与长度。加一平滑把概率分给所有组合，改变平滑系数就能改变数值，却不改变模型对真实语言的掌握。困惑度按 token 算，切词粒度不同会让 token 数差很多，平均之后的值也跟着变。

陷阱用困惑度挑模型挑出了更差的那个

你会看到：换了一版词表更小的分词器，困惑度从四点一九降到两点八，于是你宣布新模型更好。你会误以为困惑度是模型能力的绝对尺子。真相是词表变小让随机基准从九降到几十以下，分母换了，数字自然变小；若把两份文本按同样粒度重切再比，结论可能反过来。正确做法是固定分词器与测试集再比较，或者直接看下游任务的表现。困惑度是诊断工具，不是排行榜。

困惑度还有一个实践上的用途：比较同一个模型在不同检查点上的变化趋势。训练过程中每隔一段就在固定验证集上算一次困惑度，若它持续下降，说明模型在学；若它先降后升，就可能是过拟合的开始——模型开始记住训练语料的细节，却对没见过的数据更加惊讶。这种用法不需要绝对可比，只要求每次用的分词器、测试集和计算口径完全一致。换句话说，困惑度最适合当同一条曲线上的纵向刻度，而不是不同实验之间的横向排名。把这个定位摆正，它就是一个灵敏的诊断仪表；摆不正，它就是一个容易误导人的分数。

这一节还要说清一个与后面单元有关的承接关系：困惑度里的 loss 与预训练循环里打印的 loss 是同一个量——都是词表上的交叉熵。区别只在打印粒度：这里一次性算完整条流的平均，后面的预训练每一步打印一次当前参数下的全量损失。等你读到 lm05 的十二行轨迹，会发现它和这里的 loss=1.432969 用的是同一套数学，只是参数在动、数值在变。

4.7 打印纪律：数值行走等号，数组走冒号

本例的 stdout 有八行，分成两类。前六行的形状是 key=value：等号左边是合法键名，只能含字母、数字、点、方括号、下划线与连字符；右边是有限十进制数。闸门把这些行解析成数值行，按清单里声明的 atol 做容差比较。后两行的形状是 v:[...]：冒号后面的内容是数组，不是合法十进制数，闸门于是把整行当普通文字逐字比较。

为什么数组非要用冒号？假设把词表写成 vocab=[</w>,d,e,...]，等号左边的 vocab 是合法键，右边却不是数，闸门会报 numeric_value_invalid，整条清单失败。冒号让键名不成立，整行就落到文字通道，既保住了可读性，也不会误触发数值解析。这是一条贯穿全册的打印纪律：标量走等号享受容差，数组与张量走冒号逐字对账。

清单 lm04-token.json 里，expect.numbers 声明了六个黄金值，全部带 atol: 1e-6：merge_count=4、vocab_size=9、token_count=44、loss=1.432969、ppl=4.191124、first_prob=0.272727。三条整数值确保合并次数、词表大小与样本数没有漂移；三条浮点值确保目标函数与它的指数变换都算对了。为什么浮点值不只留一个？因为 ppl 是 loss 的指数，只留 loss 时，万一有人把打印的 ppl 写死成常数，闸门照样会过；两条都留，这种偷懒立刻被抓住。

语法规则数值行的两条语法

形如 key=0.123456 的行是数值行：键匹配 [A-Za-z][A-Za-z0-9_.\[\]-]*，值是有限十进制数，可以带科学计数法。形如 v:[0.1,0.2] 的行是文字行：冒号让键不成立，整行按字面量对账。容差只写在清单的 expect 里，正文里写「约等于」不算证据，程序自报的 PASS 也不算。

这六个黄金值全部来自真跑，而不是先定一个「想要」的数再改程序去凑。真跑得到 loss=1.432969，就把清单写成 1.432969；如果嫌这个数不够好看而改成 1.0，闸门会报 numeric_value_mismatch。反过来，如果为了让绿字好看而把 atol 放大到 0.5，闸门确实会过，但那条「数值必须来自计算」的纪律就被自己拆掉了。容差的作用是区分合理浮点波动与真正的错误，不是给错误放行。

4.8 图元复盘与常见误读

这一单元画了三张图，加上开头的目录树一共四张，满足每单元至少四张图元的要求。tree 标出新增的两个 Python 文件与清单；第一张 graph 比三种分词粒度，重点在序列长度与词表大小的拉扯；memory 看四次合并怎样把符号表缩小；第二张 graph 看滑动窗口怎样把 token 流变成监督样本。

读多帧图守住三条纪律。每一帧自包含：渲染器不会把上一帧的节点带过来，仍成立的节点要重写一遍，第一张图三帧里的「原文：lowest」就是这么来的。节点文字不超过十八个字，长解释留在正文——比如「加一平滑避免零概率」这种短句才适合当旁注。箭头两边留空格，原文 -> 切法 才会画成边，写成 原文->切法 只是文字。这些规矩让同一份围栏在网页、打印版和步进器里长得一样。

工程惯例亲手改一次合并次数

把 main.py 里的 MERGES = 4 改成 MERGES = 2，在例子目录下跑 python src/main.py。你会看到 merge_count=2、vocab_size=11 左右，loss 与 ppl 也跟着变——因为词表变了，加一平滑的分母变了，token 流也变了。再跑一次 node build/run.js --unit lm04-token，闸门会报 numeric_value_mismatch：黄金值还是按四次合并写的。做完把常量改回四，程序必须重新打印那八行原始 stdout。这个实验说明黄金值是实验条件的一部分，改条件就得重新取真值。

还有一个常见误读值得点破。有人看到 token_ids:[5,2,7,0] 里有个零，以为零号 token 是某种特殊占位符，其实它只是字典序排在最前的边界标记 </w>。词表 id 没有任何语义，它只是符号到整数的编号；模型从 id 里读不出「这是边界」这层意思，它读的是这个 id 对应的嵌入向量。把 id 当语义用，是初学时最容易犯的错之一。

工程惯例用三个问题复盘任何一份分词报告

拿到别人的语言模型报告，先问三件事。第一，分词器是什么、词表多大：没有这两个数，困惑度没有尺度。第二，测试集是什么、和训练集分布像不像：困惑度测的是分布匹配，不是抽象的智能。第三，损失怎么算的、分母是 token 数还是样本数：本例用 len(stream)-1 做分母，换成别的口径数字就变了。养成这三个问题的习惯，你读别人的困惑度数字时就不会只看一个孤零零的数，也不会把自己模型的分数当成通用货币。写报告时反过来用同样三问自查，读者关心的问题就都被回答过了。

4.9 从 token id 到张量：词表落在哪里

到此为止，我们一直在谈符号与整数，还没说清这些整数怎样变成模型能吃的东西。答案是一次查表：模型持有一张形状为「词表大小 × 隐藏维度」的嵌入矩阵，第 k 行就是 id 为 k 的 token 对应的向量。id 本身没有数值大小的含义，它不是「第五号比第二号大」，而只是行号。token_ids:[5,2,7,0] 里的四个整数，用来从矩阵里取出四行，仅此而已。

这个区分在调试时非常重要。有人看到 id 为零就以为是特殊填充，看到 id 变大就以为 token 「更重要」，于是写出 id * 0.1 之类的错误特征。正确的做法永远是把 id 当索引：先检查它是不是落在 [0, vocab_size) 区间里，再拿它去查表。id 越界意味着分词器与模型的词表不是同一份，这种错在玩具规模上会直接报索引错误，在真实规模上可能静默地取到别人的向量，输出一段看起来正常却完全不对的文本。

嵌入矩阵的每一行是可学习的参数。训练过程更新的正是这些行：常一起出现的 token 会逐渐被拉到相近的位置，从不一起出现的 token 会被推远。BPE 提供的子词片段让这种相似性更容易成立——low 与 lower 共享一部分token，它们的向量也有机会共享一部分语义方向。如果换成字符级，每个字母的向量要同时承担无数种上下文，学习起来就慢得多；如果换成词级，低频词根本没有足够数据把向量训好。

第 1 帧强调边界检查：九行词表的合法 id 是零到八，出现九就越界。第 2 帧把 id 与行一一对应，第五行恰好是本例词表里的 low。第 3 帧说明查表之后才轮到注意力上场——前面三个单元做的事发生在这一帧，而这一单元做的事发生在前两帧。把三帧连起来看，就得到一条完整的输入链：文本、token、id、向量、注意力。

工程惯例为什么词表顺序也要固定

嵌入表的行号由词表顺序决定，而顺序来自 sorted(symbols)。如果哪次运行忘了排序，集合的遍历顺序一变，同一个符号就可能对应不同的行号，嵌入表里学到的向量全被打乱。这不是数值末位的差异，而是整个模型语义的错位。本例在 train_bpe 的最后一步就把集合排序成列表，后续 index 字典再按这个列表建映射，从源头把顺序钉死。真实项目里，词表文件是模型工件的一部分，发布模型时必须和权重一起发布，缺了它权重就是一堆无法解读的行。

4.10 把这一单元接到预训练循环

本例只算一次损失，打印一个 loss 与一个 ppl。下一个单元要做的事，是把同一个损失函数接进一条训练循环：固定种子、打包数据、前向算损失、反向填梯度、优化器更新参数，再把每步的损失打印成一条轨迹。数学没有变，变的是参数在动，所以数值在变。理解这一点，就不会把预训练想成某种全新的东西——它只是把「算一次损失」重复许多次，并在重复之间更新参数。

为什么玩具规模的实验仍有参考价值？因为它验证的是机制，不是规模。交叉熵的形状、平滑的必要性、困惑度的读法、分词器对数字的影响，这些规律在十亿参数的模型上和九个符号的模型上是一样的。规模会改变数值的大小和收敛的速度，不会改变因果方向：数据决定分布，目标决定梯度，损失决定我们以为模型好不好。在小规模上把因果链看清，再去读大规模实验报告，才不会被漂亮的数字牵着走。

这一单元还留下一个接口。你说的「模型在预测什么」，答案已经落到 next-token 上；但真实预训练还会做掩码语言建模、下一句预测之类的变体，它们的目标函数长得不一样。有了这里的交叉熵与困惑度作底，再看那些变体就只是换一个目标分布——把「下一个 token」换成「被遮住的 token」，对数与指数的运算一字不改。这也是为什么这套书坚持先把最小机制写透：机制透了一切变体都是替换零件，机制不透就只能在术语里打转。

实验记录把损失换成别的口径会怎样

把 bigram_loss 最后一行的除法去掉，改成返回总损失而不是平均损失。你会看到 loss 从一点四三变成六十多，ppl 会大到一个几乎没有任何读数意义的数。闸门会报 numeric_value_mismatch，因为黄金值按平均口径写死。更要紧的是，这时若把样本数从四十七改成九十四，总损失几乎翻倍，但模型一点没变——数字的变化完全来自口径。这个实验说明「平均」不是可有可无的修饰，它让损失与样本数脱钩，才能让不同规模的数据在同一个尺度上比较。做完记得把除法改回。

读到这里可以回头看一眼那八行 stdout。merge_count、vocab_size、token_count 三个整数描述的是数据长什么样；loss、ppl、first_prob 三个浮点描述的是模型在这份数据上做得怎样；两行数组描述的是词表与编码结果。三组合起来，正好是一份最小实验报告该有的内容：条件、结果、可复查的中间量。后面每个单元都会沿用这个结构，只是条件与结果的具体含义换了。

小结这一节的要点
  • 分词三粒度：字符级序列长、词级词表大且怕未登录词、子词级用可复用片段在两者之间折中；
  • BPE 反复数相邻符号对频次并合并，同频按字典序打破平局，词边界标记保住「词在哪里结束」的信号；
  • next-token 目标把序列滑成上文—目标对，加一平滑保证没有零概率，损失取逐对负对数似然的平均；
  • 困惑度是平均交叉熵的指数，读作「相当于在几个等可能 token 里猜」，只在固定分词器与测试集时才可比；
  • 标量按 key=value 进黄金值对账，数组按 v:[...] 逐字对账；六个黄金值与 atol=1e-6 全部来自真跑。
自测题自测题（先自己答，再对答案）
  1. 字符级、词级、子词级分词各有什么代价？为什么 </w> 标记不能省？
  2. BPE 里两个词对频次相同时怎么处理？这条规则是为了语言学正确还是为了可复现？
  3. 四十八个 token、窗口长度为一，为什么只有四十七个监督样本？
  4. 加一平滑做了什么？去掉它会发生什么？
  5. loss=1.432969 与 ppl=4.191124 之间是什么关系？困惑度为什么不能跨词表比较？
  6. 为什么 vocab:[...] 要用冒号而不是等号？清单里为什么要同时声明 loss 与 ppl 两个黄金值？
注自测题答案
  1. 字符级词表小但序列长，注意力的平方开销大；词级序列短但词表大、遇到未登录词就失明；子词级把常见词保留、罕见词拆成可复用片段，兼顾两头。</w> 标出词边界，让 low 与 lower 里的同形片段被区别对待，省掉它模型就丢了「词在哪里结束」这个信号。
  2. 同频时按字典序取最小的词对。这条规则纯粹是为了可复现：Counter 在频次相同时保留插入顺序，不打破平局就可能让不同运行的合并序列漂移。本例用 max(sorted(pairs), key=...) 实现。
  3. 第一个 token 没有上文，滑动窗口必须从第二个位置开始，所以四十八个 token 只产生四十七对。分母取 len(stream)-1 正是这个数。
  4. 分子给每对组合加一、分母给每个上文加一个词表大小，于是没见过的组合也分到非零概率。去掉它，未见过组合的概率是零，math.log(0) 会抛异常或者得到无穷损失。
  5. 困惑度是交叉熵的指数：exp(1.432969)≈4.191124，读作相当于在约四个等可能 token 里猜。词表大小决定了随机猜的基准，换分词器就换了尺度，所以跨词表比较困惑度没有意义。
  6. 冒号让键名不成立，整行落到文字通道逐字对账；写成等号时右边不是合法十进制数，会报 numeric_value_invalid。同时声明 loss 与 ppl，是为了防止有人把其中一个写死成常数而骗过闸门——两个值由指数关系绑在一起，任何一边偷懒都会露馅。
