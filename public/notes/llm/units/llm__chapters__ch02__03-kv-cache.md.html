6.1 先看工程长什么样

前面两个单元讲的是训练：把 token 喂进模型，算损失，更新参数。这一单元转到推理，问题完全变了。训练时整条序列一次前向，所有位置的注意力并行计算；推理时却是一个 token 一个 token 地往外吐，每吐一个新 token，都要和全部历史 token 做一次注意力。如果每次都把历史从头算一遍，生成的第 n 个 token 就要重复处理 n 个前缀，总开销按长度平方增长——这就是 KV cache 要解决的问题。

KV cache 的思路很直接：历史 token 的 K 和 V 只依赖于它们自身与模型参数，不会随着新 token 的到来而改变，那就把它们存下来。每生成一个新 token，只算它自己的 Q/K/V，把新 K/V 追加到缓存里，再用这个 Q 与缓存里的全部 K 做注意力。原本每步重算整段历史，现在每步只算一个 token，单步开销从序列长度降到常数。

本单元沿用 ch02 的例子目录，工程形状与前两个单元并列。cache.py 放两种注意力的实现和缓存更新逻辑，main.py 负责固定矩阵、跑两条路径并打印对账数字。先把目录树画出来。

第 2 帧里带 + 的三行是本单元的全部新增。和前两个单元比，地基模块从 pretrain.py 换成 cache.py，职责从「造样本并训练」变成「两条推理路径的对账」；清单回到 mode=numerical，证据是六个黄金值与两行数组。第 3 帧强调运行时的 import 方向：main.py 从 cache 里导入 D、cached_step 与 full_attention，入口自己只管编排。

为什么要把两条路径放在同一个模块里？因为它们的数学必须逐位一致，放在同一个文件里最容易对照着检查。full_attention 是「正确但慢」的参考实现，cached_step 是「快但需要验证」的优化实现。真项目里也常这么写：保留一份朴素实现当测试基准，优化实现上线前先和它对账。性能换来的收益，必须用可核对的等价性证明来买单。

大白话三个词先分清楚

全序列重算指每生成一个 token，都把从第零个到当前位置的所有 token 重新做一遍注意力。单步解码指只处理新 token，历史信息从缓存里读。缓存命中指新 token 需要的 K/V 已经在缓存里，不必重新计算。本例把四步生成过程完整跑两遍，一遍朴素、一遍带缓存，再比较最后一步的输出。

6.2 自回归重复计算：浪费在哪里

自回归生成有一个刚性约束：第 n 个 token 的输出依赖它前面的所有 token。这个依赖没法绕开，但「依赖」不等于「重算」。看最后一步的注意力：查询向量 q_n 要和 k_0 到 k_n 逐个算点积，再对相应的 v 加权求和。这里真正需要的是历史的 K 和 V，而不是历史 token 的完整表示——更不是历史 token 的 Q。Q 只属于当前查询位置，历史 token 的 Q 在算它们自己那一步时用过一次，此后再也不会被用到。

朴素实现没有意识到这一点。它每次都把整条序列送进模型，重新算所有位置的 Q/K/V，重新算完整的注意力矩阵，然后只取最后一行作为输出。前面 n-1 行的计算全部被丢掉，下一次生成又从头算一遍。生成长度从一涨到 n，累计工作量大约是 1+2+...+n = n(n+1)/2，也就是二次增长。序列长到几千时，这个浪费足以让推理慢到不可用。

第 1 帧画出前三次重算：第二步把第一步的 token 又算了一遍，第三步把前两个又算了一遍。第 2 帧把四步加起来正好是十份 token 计算，而缓存路径只需要四份。第 3 帧强调缓存里存的是 K 与 V，不是整个注意力矩阵，更不是 Q——Q 只服务于当前位置，没有保存价值。三帧都把关键节点重新写了一遍，因为渲染器不会把上一帧的内容带过来。

工程惯例为什么缓存 K/V 而不是缓存注意力权重

有人会想：既然最终要用的是注意力结果，干脆把每步的注意力矩阵存下来。问题是注意力权重依赖当前查询 q_n——历史位置对当前位置的贡献会随着 q_n 改变而改变，换一个新 token，整行权重都要重算。K 和 V 则不同，它们只由历史 token 自身和固定的投影矩阵决定，不依赖当前查询，因此可以安全地复用。一句话：缓存与查询无关的量，重算与查询有关的量。

6.3 缓存里存什么：形状、内容与更新

缓存的结构可以想成两张不断变长的表：一张存 K，一张存 V。每张表有「已生成 token 数 × 隐藏维度」这么多个元素。本例的隐藏维度是四，生成四个 token 之后，两张表各是 4×4，合起来三十二个 float64，占二百五十六字节——这正是真跑打印的 cache_shape:[4,4] 与 cache_bytes=256。

起点是两张空表，形状是 (0,4)。cached_step 接收到新 token 后，先算它的 q、k、v，再用 np.vstack 把新 k 和新 v 分别追加到两张表末尾。追加之后的行数就是当前已处理的 token 数，注意力在这张变长的表上进行。整个过程没有原地修改传入的缓存，而是返回新的数组——这种写法让「状态变化」显式可见，也避免了函数副作用带来的调试困难。

第 10 行说明一个关键事实：q/k/v 都用同一套投影矩阵算，矩阵是固定的，不随位置变化。正因为固定，位置 i 算出来的 K 和 V 在位置 j 生成时仍然有效，缓存才有意义。第 22 行的参考实现一次性返回全部位置的输出与两份完整 K/V，它的作用是当基准——把它的最后一行与缓存路径的输出比较，就知道优化有没有算错。

第 1 帧强调起点是空表而不是预先分配好的固定大小数组——真实实现会预分配以省去反复扩容的开销，本例用 np.vstack 是为了让增长过程在代码里一眼可见。第 2 帧的六十四字节来自两张 1×4 的 float64 表，每表三十二字节。第 3 帧是终态：四行四列、两百五十六字节。两张表的行数永远相等，因为每处理一个 token 就各追加一行。

6.3.1 为什么起点是空表而不是固定大小

本例用 np.empty((0, D)) 造出两张零行四列的空表，然后靠 vstack 一行行追加。这种写法在教学上有个明显好处：缓存的当前长度直接等于数组的行数，不需要另外维护一个计数器，读代码的人一眼就能看出「处理了几个 token」。真实系统通常反过来——预先按最大长度申请一整块显存，再用一个长度指针记录有效部分。原因是频繁追加会导致反复分配内存，在推理的紧要路径上这种开销很贵；预分配一次，后续只移动指针，速度快得多。

两种写法各有各的坑。空表写法不会有「已分配但未填充」的位置，因此不必担心掩码漏掉空位；预分配写法必须把有效长度始终传给注意力，否则那些还没有内容的槽位会参与 softmax，把概率质量分给垃圾值。本例把数学关系放在明面上，等你去看真实推理框架的缓存实现时，就会发现它多出来的大部分代码都在管「有效长度」这件事——不是算法更复杂，而是工程上要把空间的确定性换成时间上的确定性。

缓存里也不存 embedding 向量。token 进来后先查 embedding 再投影，得到的 k/v 才是要存的东西；原始的 embedding 在投影之后就不再被用到。有人想连 embedding 一起存，理由是「万一以后要用」，结果缓存体积凭空多出一份，而且真要用时还得重新投影——存了也白存。判断该不该缓存某样东西，标准始终是它会不会在后续步骤里被原样复用。

陷阱把缓存行数与序列位置混为一谈

你会看到：缓存行数从零长到四，于是以为第零个 token 存在缓存的第零行、第三个存在第三行，没什么问题。可一旦实现里把新 token 的 k 追加到了错误的位置，或者把掩码偏移写错一位，输出会依然是一个形状正确的向量，只是内容全错。你会怀疑是投影矩阵写反了，真相是缓存的顺序就是时间顺序，注意力掩码必须按「缓存行数」而不是「当前位置编号」来构造。本例的 cached_step 每次都把新 k/v 追加到末尾，掩码由缓存自身长度决定，从结构上堵住了这个错。

6.4 单步解码：只为新 token 算 Q

缓存路径的核心在 cached_step。它接收新 token 的 id 与两份缓存，先 projections 算出这一份 q/k/v，再用 vstack 把 k/v 追加上去，然后只算一行分数：q @ K.T / √d。这一行分数已经隐含了因果掩码——因为缓存里只有到当前位置为止的 token，不可能包含未来。最后对这一行做 softmax，乘上 V，得到当前位置的输出。

这里有个容易忽略的细节：参考实现里的因果掩码是显式构造的，用 np.triu 把上三角设成负无穷；缓存实现里没有掩码，因为根本不存在未来位置。两者数学等价，前提是新 token 的 k/v 已经先追加进缓存——这样它自己也在注意力可见范围内。如果把追加放到注意力之后，当前 token 就被排除在外，输出会与参考实现差一截，diff 立刻露馅。

第 28 行先把 k/v 追加进缓存，再进入注意力计算；顺序不能颠倒。第 30 行只用 q 和 K 算一行分数，维度从参考实现的 n×n 降到 1×n——这就是单步解码省下的那部分计算。np.sqrt(D) 是缩放因子，把点积的方差拉回一附近，防止 softm ax 在维度大时饱和；这里 D=4，缩放为二。

第 1 帧的参考路径一次算出四行输出，我们只拿最后一行。第 2 帧的缓存路径其实每一步都产生了一个输出，本例只保留最后一步的那个；真实应用里每一步的输出就是新生成的 token 或它的 logit。第 3 帧是对账的关键：两条路径在最后一行上必须逐元素相等，差异取绝对值最大值，小于容差才算通过。

6.5 掩码与缓存的配合

因果掩码的作用是阻止位置 i 看到 j>i 的信息。在全序列实现里，这是一张显式矩阵：主对角线以下为允许，以上为负无穷，加在分数矩阵上再 softmax。在缓存实现里，这张矩阵被「缓存里只有历史」这个事实替代了——缓存的第零到 t 行正好是位置零到 t，不会有未来。两种做法都是对的，适用条件不同：全序列要一次算完所以必须显式屏蔽，单步解码天然只看历史所以不需要。

这带来一个实践上的推论：换到带缓存的推理时，不要顺手把掩码逻辑照搬过去。有些实现会在缓存里预留未填充的位置，这时就必须用有效的 token 数而不是缓存总容量来构造掩码，否则未填充位置会参与 softmax，输出被均匀的噪声稀释。本例用 vstack 从空表开始增长，缓存里没有空位，从结构上避开了这个问题；真实系统为了性能预分配显存时，就得自己把「有效长度」这件事管好。

多头注意力只是把这里的维度多拆了一层：每个头有自己的 K 与 V，缓存形状从 (token, d_model) 变成 (head, token, d_head)。数学完全一样，存储总量不变——所有头的 d_head 加起来就是 d_model。把每个头的缓存拼在一起看，仍然是「每个已生成 token 一份 K 和一份 V」。

掩码与缓存的配合还能从另一个角度理解：注意力要回答的问题是「当前位置可以看哪些位置」。全序列实现里，所有位置同时问这个问题，答案是一张下三角矩阵；缓存实现里，每次只有一个位置问，答案是「缓存里的全部位置」。两个答案等价的前提是缓存按时间顺序完整保存了历史——少一行就漏信息，多一行就泄未来。因此缓存的正确性不只是「存了 K/V」，还包括「存的正好是到当前为止的全部 K/V，且顺序不能乱」。本例用 vstack 从空表追加，顺序由循环保证；真实系统里请求可能中断、续接、被抢占，维护这份完整性要靠额外的状态机。

还有一个与后续单元有关的接口：解码策略只消费最后一步的 logit，不关心它是怎么算出来的。缓存把 logit 算出来之后，greedy 直接取最大值，temperature 先除一个系数再采样，top-k 与 nucleus 先截断候选再归一化。这些策略都不碰缓存，所以可以做成推理配置里的一个开关。把「算 logit」和「选 token」分开，是推理系统最重要的分层之一；KV cache 属于前一层，解码策略属于后一层，两者之间只传一行向量。

工程惯例缓存会不会改变注意力的结果

不会，只要数学写对。缓存是一个实现优化，不是近似：参考路径算最后一行时，用到的 K/V 与缓存路径 accumulated 的 K/V 是同一批数，点积、缩放、softmax、加权求和的顺序也一样，浮点结果应当逐位相同或只差末位。本例的 diff=0.000000 说明在这个规模上二者完全一致。若换成并行实现，加法的归约次序可能不同，diff 会出现 1e-7 量级的差异——这正是 atol=1e-6 存在的原因：容差容纳末位，不容纳错误。

6.6 真跑对账：两条路径的输出必须一致

main.py 把四步生成跑两遍。参考路径调用一次 full_attention，拿到四行输出；缓存路径从两张空表出发，循环四次调用 cached_step。然后取参考路径的最后一行与缓存路径最后一步的输出比较，逐元素取绝对值的最大值作为 diff。固定矩阵写死在源码里，不掺任何随机，所以两次运行 stdout 逐字一致，也不需要种子。

第 30 行把两条路径的结果取出来：full[-1] 是全序列最后一行，out 是缓存循环最后一次的输出。第 31 行先用 abs 取绝对值，再用 max 取最大分量——只要最大分量在容差内，整行就在容差内。真跑得到 diff=0.000000，说明两条路径在这个规模上完全一致。

真跑的完整 stdout 如下。前四行是结构性说明与三个整数，full_out 与 cache_out 两行是数组，最后三行是待对账的数值行。

清单 lm06-kvcache.json 里，expect.numbers 声明了六个黄金值，全部带 atol: 1e-6：q_rows=1、cache_rows=4、cache_bytes=256、full_sum=3.2、cache_sum=3.2、diff=0.0。前三个确认缓存的形状与大小没有漂移；中间两个确认两条路径的输出向量一致；最后一个是等价性的直接证据。为什么 full_sum 与 cache_sum 都要留？因为只留 diff 时，两个都打印成零向量的程序也能过关——两个向量相等且都为零，差自然是零。加上两个和，就堵住了这个漏洞。

语法规则标量走等号，数组走冒号

full_sum=3.200000 这样的行是数值行：键合法、值是有限小数，闸门按 atol=1e-6 对账。full_out:[0.780561,...] 这样的行走冒号：键不成立，整行按文字逐字比较。数组写成 full_out=[...] 会报 numeric_value_invalid，因为方括号不是合法十进制数。本例两行数组恰好相等，但闸门并不知道它们该相等——它只是逐字比较正文与真实 stdout，真正的数值证据在 diff 与两个和上。

6.6.1 缩放因子与数值稳定

点积之后除以 √d 这件事，在两条路径里都出现了：参考实现写 Q @ K.T / np.sqrt(D)，缓存实现写 q @ K.T / np.sqrt(D)。它不是可省略的装饰。若 embedding 的各分量近似独立、方差为一，两个向量的点积方差会随维度 d 线性增长；维度大时，分数矩阵里的数动辄几十上百，softmax 会饱和成接近独热的形式，梯度几乎消失。除以 √d 把方差拉回一附近，让 softmax 工作在敏感区间。

softmax 本身也做了数值稳定处理：先减掉这一行的最大值再取指数。指数函数在输入很大时会溢出，减去最大值不改变归一化后的概率——因为分子分母同时乘了同一个因子。参考实现里 scores - scores.max(axis=1, keepdims=True) 按行减，缓存实现里 scores - scores.max() 对唯一一行减，写法不同、数学相同。把这两处细节对照着看，就能明白为什么优化实现不是「另写一套」，而是把参考实现的每一步精确映射到单行版本。

diff=0.000000 还说明了一件容易被忽视的事：浮点计算的顺序在本例里完全一致。参考实现的最后一行分数来自矩阵乘法 Q @ K.T，缓存实现来自向量矩阵乘法 q @ K.T，底层调用的归约次序恰好一样，所以逐位相同。换成并行硬件或不同的矩阵乘实现，归约次序可能变化，末位会出现 1e-7 量级的差异。清单里 atol=1e-6 就是为这种情况留的——它容纳末位抖动，不容纳把输出写死。

6.7 缓存不是免费的：显存开销从哪来

KV cache 用空间换时间。每生成一个 token，缓存就要多存一份 K 和一份 V。单头、隐藏维度 d、序列长度 n 时，缓存元素数是 2×n×d；本例是 2×4×4=32 个 float64，合两百五十六字节。换成真实规模——比如三十二层、每个 token 的 K/V 各占 4096 个数、float16 存储——单个 token 就要 32×2×4096×2≈524288 字节，也就是半兆。生成两千个 token，光缓存就接近一千兆。

显存开销还随批量线性增长。推理服务为了吞吐会把多个请求打包成一个 batch，每个请求都有自己的一份缓存，互不共享。批量从一涨到十六，缓存占用也涨十六倍。这就是为什么生产系统要对并发数设上限，还要做分页缓存这类优化：把缓存按块分配到非连续的显存页上，避免为每个请求预留一整段连续空间造成浪费。

第 1 帧的二百五十六字节是 2×4×4×8 的结果，其中八是 float64 的字节数。第 2 帧提醒每层都有自己的 K/V 投影，所以缓存要按层数放大；多头只是把维度拆开，总元素数不变。第 3 帧强调批量之间不能共享缓存——不同请求的历史完全不同，共享会串话。三个因子连乘，就是生产系统里缓存占用轻易超过模型权重的根本原因。

工程惯例为什么不用缓存也能跑

短序列生成里，重算的绝对开销很小，缓存带来的实现复杂度反而不划算；某些硬件上，缓存的访存代价甚至超过重算的算力代价。缓存真正发光的地方是长序列与大模型：序列越长，重复计算的浪费越显著，单步计算越受限于访存而非算力。判断要不要上缓存，看的是「生成长度」和「模型规模」的乘积，不是一个非黑即白的教条。本例用四步生成演示机制，规模小到缓存的收益无从体现，但数学等价性已经验证清楚。

6.7.1 从整块预分配到分页缓存

既然预分配一整段连续显存会造成浪费，工程上自然会想到把它切块。分页缓存借用操作系统虚拟内存的想法：把缓存按固定大小的块分配，每块存若干 token 的 K/V，块与块在显存里不必相邻；再维护一张逻辑位置到物理块的映射表，注意力按映射表去取数据。这样每个请求只占它实际用到的块，短请求不会被迫预留最大长度的空间。

分页缓存还顺手解决了另一个问题。批量推理时各请求长度不同，若按最长请求预分配，短请求留下大量空洞；若按各自长度分配，又需要频繁整理碎片。按块分配让「长度不同」变成「块数不同」，分配器只需管理等大小的块，复杂度大幅下降。代价是注意力核函数要能按映射表做非连续访存，实现难度上了一个台阶——这也是为什么它是推理框架的核心部件，而不是一个应用层技巧。

本例的 vstack 可以看作分页缓存的极简对照：它同样不预先占满空间，只是每次追加都重新分配并拷贝，在四步规模上完全无所谓，在几千步规模上就不可接受。理解这条演进线，看到生产系统里复杂的缓存管理器时，就不会觉得那是无谓的讲究——它省的是每一步的分配开销和每一块被浪费的显存，而这两样在长序列生成里都会累积成主要成本。

6.8 常见误读与边界

第一个误读是「缓存会让结果变差」。不会，只要实现正确它就是精确的优化，本例的 diff=0.000000 是证据。真正会让结果变差的是错误实现：追加顺序颠倒、掩码偏移写错、缓存里混入未填充位置、多头的头维度搞混。这些错误不会报错，只会给出一个形状正确、内容错误的结果，所以才需要一份参考实现来对账。

第二个误读是「缓存只在解码器里有用」。缓存依赖的是自回归结构——每步只追加一个 token、历史不变。编码器一次性看完整个输入，没有逐步生成，自然用不上；但编码器—解码器架构里的解码器部分仍然自回归，照样能缓存。判断标准是「历史 K/V 会不会随新输入改变」，不会就能缓存，会就不能。

第三个误读是「有了缓存就不用管序列长度了」。缓存把单步开销从线性降到常数，但注意力那一行分数仍要对全部历史位置算点积，单步本身还是随长度线性增长；而且缓存占用也随长度线性增长。长度从两千涨到两万，生成仍然会变慢、变占显存。缓存改变的是累计开销的增长阶——从平方降到线性，不是从线性降到常数。

陷阱把缓存当成可以跨请求复用的全局状态

你会看到：把缓存做成全局变量似乎能省去每请求重建的开销，程序还能跑，于是以为找到了优化。真相是缓存里装着某个请求的完整历史 K/V，和这一个提示词绑定得死死的。把它用到另一个请求上，模型会以为新请求的开头后面跟着别人的历史，输出一段看似流畅实则串话的文本。更隐蔽的是批量里各样本的长度不同，若按最长样本预留位置而不做掩码，短样本的注意力会看到填充位。正确做法是把缓存的生命周期绑定到单个生成请求，长度信息显式传给注意力。

缓存测试里还有一个特别有用的对照：把序列顺序打乱再跑一遍，看输出是否随着历史改变而改变。如果顺序变了而最后一行输出完全不变，说明实现里某处把缓存当成了一个与顺序无关的容器，或者注意力退化成了对所有历史位置求平均。本例把 IDS 写成 [0,2,1,3] 而不是 [0,1,2,3]，正是为了让顺序成为可观察的量——换一组 id，full_out 与 cache_out 都会跟着变，两条路径仍然相等。这种「改变条件、观察变化、再核对等价性」的三步法，比只跑一次默认输入更能发现隐藏的错误。

6.8.1 把缓存当成一个可测试的部件

缓存逻辑适合单独测试，因为它有明确的输入与输出契约：给定当前缓存和新 token，返回更新后的缓存和这一步的输出。本例的 cached_step 正好符合这个形状，所以可以把它和 full_attention 放在同一个模块里互相验证。真实项目里还会加几个针对性用例：空缓存上跑一步，看输出是否与全序列第一步一致；重复跑同一个 token 两次，看缓存行数是否加二；在两个不同顺序的 token 序列上跑，看缓存内容是否按时间顺序排列。

还有一个值得测的边界是序列长度为一的情形。此时因果掩码是一行一列，softmax 只能选唯一的位置，输出应当等于那个位置的 V 向量。缓存路径从空表追加一行，也得到同样的结果。这种退化用例看着无聊，却能抓住一类常见错误：掩码偏移写错一位时，长度为一的用例会立刻给出全零输出，比在长序列上盯着 diff 的末位更容易定位。

工程惯例亲手制造一次顺序错误

把 cached_step 里 K = np.vstack([Kcache, k]) 改成 K = np.vstack([k, Kcache])，在例子目录下跑 python src/main.py。你会看到 cache_shape 仍然是 [4,4]，cache_bytes 仍然是 256，两行数组输出却变了，diff 变成一个明显大于容差的数。闸门会报 numeric_value_mismatch。这个实验说明结构正确的输出不能证明语义正确——形状、字节数这些量只能证明内存布局对，等价性必须靠逐元素对账。做完把顺序改回去，程序必须重新打印那九行原始 stdout。

工程惯例把这一单元接到解码策略

下一章讲解码策略时会看到 greedy、temperature、top-k 与 nucleus 四种采样。它们改变的是「拿到 logit 之后怎么选下一个 token」，不改 K/V 缓存——缓存负责把 logit 算出来，采样负责从 logit 里挑一个 id，两者是前后相邻、互不干扰的两个零件。这也解释了为什么缓存可以做成推理框架的底层能力，而解码策略可以做成上层配置：接口就是一行 logit，谁也不依赖谁的内部实现。

小结这一节的要点
  • 自回归生成里历史 K/V 不随新 token 改变，重算整段前缀造成平方级浪费；
  • 缓存两张表分别存 K 与 V，形状是「已生成 token 数 × 隐藏维度」，每步追加一行，不存 Q；
  • 单步解码只为新 token 算 Q/K/V，追加后只对一行分数做 softmax；缓存天然不含未来，无需显式掩码；
  • 两条路径最后一行必须一致，diff 是等价性的直接证据，full_sum 与 cache_sum 防止都输出零向量的偷懒；
  • 缓存开销按层数、序列长度、批量连乘放大，换取的是累计计算从平方降到线性。
自测题自测题（先自己答，再对答案）
  1. 为什么说历史 token 的 Q 不需要缓存？缓存 K/V 的依据是什么？
  2. 四步生成里朴素路径累计要做多少份 token 计算？缓存路径呢？
  3. cached_step 为什么要先把新 k/v 追加进缓存再算注意力？顺序颠倒会怎样？
  4. 全序列实现用显式因果掩码，缓存实现没有掩码，为什么两者数学等价？
  5. diff=0.000000 说明什么？为什么清单还要同时声明 full_sum 与 cache_sum？
  6. 缓存开销受哪三个因子放大？为什么说缓存把累计计算从平方降到线性而不是降到常数？
注自测题答案
  1. Q 只服务于当前查询位置，历史 token 的 Q 在算它自己那一步时用过后就不再需要。K/V 只由历史 token 自身与固定投影矩阵决定，不依赖当前查询，因此可以安全复用。
  2. 朴素路径累计 1+2+3+4=10 份 token 计算，缓存路径只算四份，每步一个新 token。序列变长时前者按平方增长，后者按线性增长。
  3. 追加之后当前 token 才在注意力的可见范围内，它自己的输出才能包含自身。顺序颠倒会把当前 token 排除在外，输出与参考实现差一截，diff 会立刻暴露。
  4. 缓存里只有到当前位置为止的 token，不可能包含未来，显式掩码要屏蔽的那些位置压根不存在。全序列实现一次算完所以需要掩码，单步实现天然只看历史所以不需要。
  5. 说明两条路径在最后一行上逐元素相等，缓存实现没有算错。若只留 diff，两个都打印零向量的程序也能过关；加上两个和，就要求输出既相等又非零，堵住了这个漏洞。
  6. 层数、序列长度与批量三者连乘放大缓存占用。缓存把每步开销从「重算整段历史」降到「只算新 token」，单步仍随历史长度线性增长，所以累计从平方降到线性，不是常数。
