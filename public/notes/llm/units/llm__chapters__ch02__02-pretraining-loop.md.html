5.1 先看工程长什么样

上一个单元把语言建模目标钉死了：给定上文，预测下一个 token，用交叉熵衡量预测误差，用困惑度换一种读数。那个实验里参数是固定的，我们只算了一次损失。这一单元让参数动起来——把同一个损失函数接进一条循环，每走一步更新一次参数，再看损失怎样随步数下降。这就是预训练循环的全部秘密：没有新数学，只有重复与更新。

工程上多了一个 pretrain.py：三种随机源的固定、玩具语料的构造、滑动窗口打包、极小模型、损失与准确率都在里面。main.py 只剩读种子、建优化器、跑十二步、打印数字。种子仍然不写死在源码里，而是由闸门通过环境变量 LLM_SEED 注入——写在源码里叫硬编码，写在清单里叫实验条件，后者才能被对照实验改变。

这一单元沿用 ch02 的例子目录，工程形状与上一个单元并列。先把目录树画出来，再拆开数据、种子、循环、证据四件事。

第 2 帧里带 + 的三行是本单元的全部新增。和第 4 单元比，地基模块从 bpe.py 换成 pretrain.py，职责从「把文本切成 token」变成「把 token 变成可训练样本并定义模型」；清单从 mode=numerical 换成 mode=train，证据从六个黄金值变成一条收敛轨迹加三次运行。读这类图时只盯带 + 的行，就能把一个单元的增量和之前的积累分开。

第 3 帧强调运行时的 import 方向：main.py 通过 from pretrain import ... 把本地模块拉进来，入口只负责编排。代价是多一层路径依赖，好处是改实验条件与改训练流程落在两个文件里，互不干扰。想换学习率只动 main.py 的常量；想换语料或窗口长度只动 pretrain.py。这和上两个单元的分工一脉相承：真正会变的东西要放在容易找到的地方。

大白话三个计数先分清楚

token 是语料的基本单位，本例有四十八个。样本（也叫窗口或上下文—目标对）是从 token 流里切出来的训练条目，窗口长度为一时有四十七个。step 是一次参数更新，本例跑十二步。三者不是一回事：一步里可以看全部样本，也可以只看一小批；本例取全量，所以每一步都把四十七个样本过一遍再更新一次。

5.2 数据打包：把 token 流切成滑动窗口

真实预训练的第一件事是把海量文本拼成一条长 token 流，再按固定长度切成许多窗口。本例用四个词循环十二次造出四十八个 token，词 id 直接由词表顺序决定，不掺任何随机——这一点很重要，因为我们要让对照种子改变的只是「训练起点与读取顺序」，而不是数据本身。数据与随机流分开，是后面三次运行能说清话的前提。

pack_windows 做滑动窗口打包。它在 token 流上从左向右挪一个固定长度的窗口，每个位置取前 window 个 token 当上文，取紧随其后的一个 token 当目标。窗口长度为一时，[0,1,2,...] 这条流被切成 (0→1)、(1→2)、(2→3) 这样一串样本。窗口长度改成二，上文就变成两个 token，样本数少一个，但每个样本携带的上下文更多。这条函数不需要改模型代码就能换窗口——模型那边的 forward 只取上下文的最后一个 token，所以窗口长度变化对它是透明的。

第 22 行的循环把四个词重复十二次，得到一条完全确定的 id 序列；它不读种子，也不读随机源。第 30 行是切片的落点：ids[i-window:i] 取窗口，ids[i] 取目标，两者相差一格。循环从 window 开始，跳过开头那些凑不出完整窗口的位置，所以样本数是 len(ids) - window，本例是四十七。返回的张量用 torch.long，因为 id 要用来做整数索引。

第 1 帧强调语料是固定的：词表顺序写在代码里，重复次数写在代码里，没有一处读随机源。第 2 帧只画了两个样本，实际有四十七个；关键是从第二个 token 才开始，第一个没有上文。第 3 帧把上一单元的 next-token 目标接了进来——模型只取窗口末尾的 token 查表，这和上一单元的逻辑完全一致，只是现在外面套了一层循环。

工程惯例窗口长度改了，模型要不要改

本例的 TinyLM.forward 写的是 self.table[ctx[:, -1]]，只取上下文的最后一个 token。所以窗口从一改成二，样本数从四十七变成四十六，但模型一行都不用动——它依然只看末尾 token。真实模型不一样：Transformer 会把整个窗口都喂进去，窗口变长意味着注意力矩阵变大。本例把模型简化成查表，是为了让窗口打包这件事单独可见；机制清楚以后，换成真正的 Transformer 只是替换模型那一段。

5.3 batch、step、token 三者怎么换算

打包完成以后，四十七个样本被一次性送进模型。这就是全批量训练：一步里看完所有样本，算出精确的梯度，再更新一次参数。换成小批量时，每步只看其中一小块，梯度带噪声，轨迹会抖动；好处是每步的计算量小，同样的时间能走更多步。两者没有绝对优劣，只有实验条件的差别——改了批大小，收敛阈值就得重新取真值。

本例把批大小取成样本总数，是为了让前八步的非增判定成立。从固定初值出发、用足够小的学习率，全量交叉熵的损失会平滑下降；换成小批量后，某些步可能因为抽到难样本而反弹，前八步严格非增就可能误报发散。这不是小批量不好，而是判据与条件要配套：真要用小批量，就该看移动平均的趋势，而不是逐点比较。

第 1 帧的「丢掉开头一个」是窗口打包的固有代价：第一个 token 前面没有东西可看。第 2 帧强调梯度是四十七对的平均，不是求和——平均让损失与样本数脱钩，换一批数据量也能比。第 3 帧把十二次更新串成一条轨迹，每行是更新之后在当前参数上重算的全量损失。

为什么打印的是更新后的损失，而不是用于反向的那个？因为前者是同一个函数在不同参数点上的取值，趋势干净；后者每步喂的数据可能不同，数值天然跳动。本例两步都算全量损失，数值其实一样，但把「打印值」和「反向值」写成两次调用是为了强调这件事：真正该被观察的是模型在固定数据上的表现，而不是当前这一小批有多好拟合。这个区分在换成小批量时尤其关键。

陷阱把梯度累积当成普通训练

你会看到：训练照跑，损失照打印，可每走几步才更新一次，轨迹比预期稀疏；或者忘了清账，梯度越积越大，参数被甩出去，损失不降反升。你会怀疑是学习率太大或者数据有问题。真相是 backward() 把梯度加进 .grad 而不是覆盖。常规训练必须每步 zero_grad()；想做梯度累积，就把清零挪到若干步之后，并且清楚自己是在用几步的梯度合成一次更新。判断办法很简单：数一数两次 step() 之间调了几次 backward()——常规训练是一次，累积才是多次。

5.4 三种随机源与种子：三次运行拼出完整证据

模型参数由 torch.randn 初始化，这一步是随机的。如果还要做数据打乱、增强或采样，就会用到别的随机源。本例至少有三处可能引入随机：random 模块、numpy 的随机功能、PyTorch 的初始化与打乱。只固定其中两个，剩下的那个照样能让轨迹漂移。set_all_seeds 因此一次固定三条流，缺一不可。

前四行分别固定三条互不相关的随机流：random 是标准库的源，控制增强与抽样决策；numpy 的随机模块常出现在采样与索引里；PyTorch 自己维护一条全局流，负责参数初始化、DataLoader 打乱与 Dropout 掩码。你连续调用三个 seeding 函数，得到的是三套彼此不知道对方存在的序列。第十六行不是随机源，但它把多线程归约的加法次序固定下来——在容差只有 1e-4 的单调性判定里，线程调度导致的末位抖动也可能误报反弹。

种子不写死在源码里，而是由闸门通过 LLM_SEED 注入。主种子 12345、对照种子 67890 都写在清单里。程序用 int(os.environ["LLM_SEED"]) 读取，缺了环境变量就直接抛异常，逼着实验必须显式声明条件，不许悄悄用默认值蒙混过关。写法上有个细节：程序不打印种子。如果打印了 seed=12345，换对照种子时这一行必然变化，seed_has_no_effect 这条检查就会平凡通过——哪怕十二行损失全是写死的。不打印种子，就逼着对照检查去看损失本身。

第 2 帧验证确定性，第 3 帧验证数字真的来自种子。两条缺一不可：只跑两次同种子，一份把损失写死进列表的程序也能过；只跑一次对照种子，一个用时间当随机源的程序每次都不同，看起来「有变化」却无法复现。对照种子的首行是 0.781134，主种子是 0.811439——整条轨迹都变了，说明这些数确实由种子驱动的参数初值算出来，而不是一张硬编码的表。

实验记录亲手制造一次「种子没生效」

把 main.py 里的 seed = int(os.environ["LLM_SEED"]) 改成 seed = 12345，再跑 node build/run.js --unit lm05-pretrain。闸门第三次运行会发现换种子后十二行损失完全相同，报 seed_has_no_effect。再把 set_all_seeds 里的 np.random.seed(seed) 注释掉，同种子两次虽仍一致，但那只是因为本例没用 numpy 随机——这恰好说明「漏掉一条流」未必立刻暴露，纪律要在写的时候就守住。做完把两处都改回去，程序必须重新打印主种子的十六行原始 stdout。

5.5 训练循环四步：清账、前向、反向、更新

入口代码二十来行，每一步都有明确职责。循环外层走十二步，每步开头 opt.zero_grad() 清掉旧梯度；接着把全部样本送进模型得到 logit，与目标算交叉熵；backward() 把梯度填进参数的 .grad；opt.step() 按 w ← w - lr·g 更新。更新完成后，用 torch.no_grad() 包住一次全量损失计算并打印。这样十二步下来，stdout 上就是十二行 loss=。

第 24 行的清零写在内层循环开头，每处理一批清一次，是最常规的位置。第 29 行打印的是更新之后重算的损失，torch.no_grad() 让它不建图，因此用整套数据也不必为每条样本保存中间量。循环后面的四行是实验记录：acc 是最终参数上的贪心命中率，token_count、window、pairs 三个整数把这份实验的数据条件写清楚——别人拿到 stdout 就知道这是在四十八个 token、窗口一、四十七对样本上跑出来的。

模型本体只有一张 4×4 的表。TinyLM.__init__ 用 torch.randn(vocab, vocab) * 0.3 初始化，尺度零点三是个刻意的选择：初值小，初始 logit 接近零，softmax 接近均匀，初始损失接近 ln 4≈1.386；实测首行是 0.811439，比理论均匀值低，说明小尺度初值已经带有一点偏向。尺度若放大到三，初始 logit 相差很大，损失曲线会从很高的位置开始，收敛阈值全部作废。

第 40 行的零点三是学习率与收敛阈值的前置条件——同样的学习率配不同的初始化尺度，轨迹会完全不同。第 49 行用框架内置的 cross_entropy，它内部把 log_softmax 与目标索引合并计算，比「先 softmax 再取对数」稳得多；当 logit 很大时，先算概率会先溢出或下溢，合并版本在 log 域里直接算，避开了中间那一步。这就是上一个单元讲交叉熵时留下的数值纪律。

主种子 12345 真跑得到的 stdout 如下。十二行损失从 0.811439 一路降到 0.067893，首尾差 0.743546，每一步都比上一步低；最后 acc=1.000000 说明这条完全规则的语料被模型学明白了，四行整数则把数据条件钉死。

陷阱把「损失降了」当成「模型学对了」

十二行损失平滑下降，准确率是完美的 1.000000，看起来无可挑剔。但这份语料是四个词机械循环，模式简单到几乎没有泛化可言——模型学会的只是「a 后面是 b」这条规则，不是什么语言知识。你会误以为漂亮的曲线证明了方法有效，真相是曲线只证明优化过程在工作：梯度方向对、学习率合适、数据没写反。要证明模型学到了可迁移的东西，得换一份没见过的语料再测。把闸门绿灯当成数学证明，是这套书反复要破除的误解。

5.6 收敛阈值：四条判据各防什么

清单 lm05-pretrain.json 用 mode=train，seed_env 写 LLM_SEED，seed=12345，seed_contrast=67890。expect.train 写：loss_key=loss、min_points=12、first_min=0.7、last_max=0.08、decline_min=0.7、monotone_window=8、slack=1e-4。四条阈值全部按真跑取：首行 0.811439 高于 0.7，末行 0.067893 低于 0.08，首尾差 0.743546 大于 0.7，前八步严格递减。

实验记录四条阈值各自防什么

min_points=12 防「程序只跑三步就说收敛」；first_min=0.7 防「起点已经在最优附近，下降演示没有意义」；last_max=0.08 防「每步只走微不足道的一小步」；decline_min=0.7 防「起点低终点也低的平凡通过」；monotone_window=8 加 slack=1e-4 防「前几步来回震荡却自称收敛」。这五条彼此独立，少一条都能构造出骗过闸门的写法。阈值来自真跑，不能为了让绿字好看反过来放宽——若把 last_max 改成 1.0，闸门确实会过，但那条「必须真的收敛」的纪律被自己拆掉了。

5.6.1 阈值为什么按真值取，而不是取整

first_min=0.7 而首行实际是 0.811439，last_max=0.08 而末行是 0.067893——为什么不写成 1.0 和 0.1 这种整齐的数？因为阈值不是「你想要什么」，而是「真跑给出了什么、留多少余量」。首行留约 0.11 的余量，末行留约 0.012 的余量；降幅 0.7 对实际 0.743546 留了约百分之六的余量——若把学习率改小导致降幅只有 0.6，闸门就会拦下，这正是我们想要的。

monotone_window=8 的 slack=1e-4 是给浮点比较留的余地：判定是某步损失比上一步高出 slack 才算反弹，允许极小的上浮。本例十二步严格递减，不用 slack 也过；但换成别的机器或别的浮点实现，末位可能出现微小上跳，容差让判定稳在「趋势」上而不是末位数字上。这和第 4 单元里 atol 的作用是同一类：把「合理波动」与「真的不对」分开。

阈值与种子是一体的。换一个种子，十二行损失整体平移，first_min 与 last_max 的余量就可能不够；换一个初始化尺度，首行可能从零点八掉到零点四，first_min=0.7 反而拦住一条其实在收敛的轨迹。这不是闸门太死板，而是它在提醒你：实验条件变了，报告里的阈值必须跟着重新取真值。工程上把种子、学习率与初始化尺度写进清单的备注或随附实验记录，就是为了把这种依赖关系显式化——别人拿到的不只是一组绿字，还有「这组绿字在什么条件下成立」。

还有一点值得强调：清单里的黄金阈值不是验收通过后随手填的装饰，它与 stdout 是一一对应的证据。本例的 last_max=0.08 比末行 0.067893 高约百分之十二，这个余量既容得下不同机器的浮点末位差异，又容不下把学习率减半的偷懒。余量取多大没有公式，靠的是对数值尺度的判断：太小容易被环境差异误伤，太大则失去拦截力。写作者能做的，是在每次修改条件后重新真跑，用真实数字核对余量，而不是凭感觉调一个「差不多」的数。

5.6.2 学习率四点零从哪里来

LR=4.0 是试出来的，不是推出来的。本例的目标不是凸二次函数，曲率沿轨迹变化，没法算出一个严格上界。工程办法很朴素：从保守值开始跑一次看十二行损失，若平滑下降就保留，若反弹就减半，若下降太慢就加倍。取二点零时末行是 0.156426，达不到 last_max=0.08；取四点零时首行 0.811439、末行 0.067893，前八步严格递减，是个合适的值；取八点零时首行降到 0.369764，虽然末行更低，但起点已经太接近最优，「下降演示」失去意义。

阈值不会替你选学习率，它只负责拦住不合适的选择。这是理解闸门定位的关键：它是纪律的执行者，不是参数的优化器。把绿字当成「学习率选对了」的好评，就等于把检查当成了目的——真正的目的是让实验可复现、可核对、可交接。每次调完学习率，都要重新跑一次取真值，再按真值改清单；反过来为了让绿字好看而放宽阈值，拆掉的是自己立的规矩。

5.7 计算预算 6ND 的直觉

预训练的开销常被写成 6ND：参数量 N、训练 token 数 D，乘起来再乘六，近似等于前向加反向的浮点运算次数。为什么是六？一次前向里，每个参数大致参与一次乘加，算作两次浮点运算；反向要分别对输入和参数求导，工作量约是前向的两倍，算作四次；前后相加正好六次。这个粗算不涉及注意力矩阵的二次项，对以矩阵乘法为主体的大模型是一个够用的量级估计。

本例的参数量是 4×4=16，训练 token 数是 47×12=564（每步看四十七个样本，共十二步），于是 6ND≈6×16×564=54144 次浮点运算。这个数小得可笑，但它的结构和大模型完全一样：想让损失再降一点，要么加大 N 用更大的模型，要么加大 D 喂更多数据，两者都要付钱。计算预算 fixed 时，N 与 D 之间有个取舍——模型太大而数据太少会过拟合，模型太小而数据太多则学不动。这就是规模定律研究的起点。

第 1 帧把一次乘加拆成乘法和加法两次浮点运算，所以一个参数贡献约两次。第 2 帧说明反向要算两份梯度——对输入一份、对参数一份，合计约四次，加前向正好六次。第 3 帧强调 D 是实际训练见过的 token 数，不是语料文件大小；同一个语料训练三遍，就要按三倍算。

工程惯例粗算式的边界在哪里

6ND 忽略了注意力矩阵的 n² 项、LayerNorm、softmax 与数据搬运，因此序列很长时它会低估实际开销；它也假设每步都做完整的前向反向，梯度累积或稀疏更新会改变系数。它的价值是量级判断而不是精确报价：想比较「模型翻倍」和「数据翻倍」哪个更贵，乘一下就清楚。本例的序列长度是一，二次项可以忽略，粗算反而很贴合；换成真正的长文本预训练，就得把注意力开销单独补上。

5.8 为什么小模型实验仍有参考价值

九个符号的词表、四十八个 token、一张四乘四的表——这一切离真实大模型差了好几个数量级。但小模型实验的价值不在于复现大模型的数值，而在于把因果链压缩到可以肉眼检查的尺度。损失为什么不降？在小模型里你可以把整条轨迹、参数初值、学习率、梯度范数全打出来，一眼看出是哪一环出了问题。在十亿参数的模型里，同样的问题可能被分布式训练、混合精度和调度策略层层包裹，定位成本高得多。

小模型还能当「闸门夹具」用。本单元的 train 模式之所以能可靠地检查确定性与非硬编码，正因为十二步损失在单线程 CPU 上逐值可复现。真实大模型跑一次要几小时甚至几天，同种子复现两次的成本高到不可接受，于是纪律只能降级为「记录配置与随机种子」这类纸面约定。在小规模上把纪律练成肌肉记忆，到了大规模才知道该记什么、该怀疑什么。

小模型也有明确的边界。它不能告诉你某个架构在大规模上会不会出现涌现能力，不能预测缩放曲线的拐点，也不能替代真实的评测。它只能验证机制：目标函数写对没有，梯度方向对不对，数据有没有泄漏，种子是不是真的生效。把机制验证的结果当成规模结论，是另一种常见误读。本单元交付的是一套可复现的实验纪律，不是一个关于大模型能力的主张。

实验记录用对照种子做一次完整对照

在例子目录下用 LLM_SEED=67890 python src/main.py 跑一次，把首行 0.781134 与主种子的 0.811439 摆在一起。两行不同，说明数值确实由种子驱动的参数初值算出来。再把 LR = 4.0 改成 LR = 2.0 跑一次，末行会停在第一单元算过的 0.156426 附近，last_max=0.08 这条判据会拦下它。做完把两处都改回去，重新跑一次确认 stdout 恢复成清单里那十六行。这几次运行加起来，就是 train 模式三种检查的手工版。

5.8.1 一次实验要留下什么

一次训练实验要能交给别人，光有 stdout 不够，还得留下三样东西：运行条件、结果证据与失败模式。运行条件包括种子从哪个环境变量读、主种子与对照种子各是多少、学习率与窗口长度取什么值、代码版本对应哪一次提交。本例把这些条件分散在两处：种子与阈值在清单里，学习率与窗口在源码常量里。这不算完美，但至少没有把种子写死在函数中间——把实验条件藏在算法里，别人拿到代码也无从知道这条轨迹是在什么条件下跑出来的。

结果证据就是那十六行 stdout 加清单里的四条阈值。十二行损失说明轨迹在下降，acc 说明最终参数在这份语料上做了什么，三个整数把数据规模钉死。失败模式则是一张对照表：报 train_nondeterministic，先同种子连跑两次逐行比对；报 seed_has_no_effect，先看程序是不是打印了种子或者把损失写死；报 train_loss_not_decreasing，先看学习率、清零顺序与标签方向；报 numeric_key_missing，先看 stdout 的行格式。把症状翻译成可打印的量，排查才有抓手。

工程惯例为什么清单里不写 flags 与 libs

Python 运行器的调用方式是「语法检查后直接跑第一个 .py 文件」，不接受编译期参数，所以清单里出现 flags 或 libs 只会被拒绝。这不是少了一个功能，而是少了一个藏污纳垢的地方：C 项目可以往 flags 里塞 -w 压掉警告，Python 没有这扇门，证据就只能来自真实 stdout。本例的两个源文件都放在 src/ 下，入口靠目录自动进模块搜索路径来 import 本地模块，不需要任何额外开关。规则少，能钻的空子也少。

5.8.2 从预训练到对齐：损失曲线还会再出现

预训练不是终点，后面还有监督微调与偏好优化。那些阶段换的是数据来源与目标函数，不是「跑循环、看轨迹、固定种子」这套纪律。监督微调会给每条样本加一个损失掩码，只让回答部分的 token 参与交叉熵——提示部分的损失被屏蔽掉，因为那不是模型需要学的内容。损失函数从「整条序列的下一个 token」变成「回答里的下一个 token」，但打印出来的仍是一条逐行 loss=，收敛阈值仍要从真跑取。

偏好优化走得更远，它不直接预测 token，而是比较同一个提示下「更好」与「更差」两个回答的相对概率，用一个成对逻辑损失拉开差距。目标函数换了形状，stdout 里照样可以打印损失与准确率，照样可以用同种子复现与对照种子来验收。理解本单元的循环结构之后，那些新阶段只是替换其中一两个零件：数据站换成成对偏好数据，损失站换成 DPO 目标，清账、前向、反向、更新四步照旧。

这条链路还有一个容易被忽略的环节：日志。stdout 只保留十二行损失与四行记录，真正在排查时有用的是每次运行的完整日志，包括命令、退出码与环境变量。本例的闸门把三次运行分别写进 dist/logs/run-lm05-pretrain.log，同种子两次与对照种子各占一段。真项目里把日志与清单编号绑定归档，出问题时才能回答「当时到底用了哪个种子、哪份数据」。日志不进正文，因为正文要讲的是机制；但日志必须存在，因为证据要能复查。

反过来说，如果本单元的纪律没立住——种子写在源码里、损失打印的是小批量、阈值为了绿字而放宽——后面的阶段会把这些毛病原样继承下去，而且因为数据更复杂、运行更昂贵，毛病会更难发现。这就是为什么这套书在最小的玩具规模上也要把三次运行、四条阈值、六项清单自查做完。机制小，纪律不小；现在养成习惯，后面才不用返工。

工程惯例用三个问题复盘任何一份预训练报告

拿到别人的预训练报告，先问三件事。第一，起点在哪：本例首行 0.811439，离最优还有明显距离，才有下降可演示；若首行已接近零，整条轨迹平坦，什么也证明不了。第二，中间有没有异常：十二行损失一直下降，但还要看参数范数与梯度范数，才能排除「损失降、参数在爆」的假收敛。第三，证据够不够：单看一次运行的轨迹可能是硬编码；再看同种子复现与对照种子，三条证据合起来才算数。写报告时反过来用同样三问自查，读者关心的问题就都被回答过了。

小结这一节的要点
  • 数据打包把 token 流切成滑动窗口样本，token、样本、step 三个计数各管一段，本例是四十八、四十七与十二；
  • random、numpy、torch 三条随机流一起固定，单线程归约再防住浮点末位抖动；
  • 训练四步是清账、前向、反向、更新，打印的是更新后在固定数据上重算的全量损失；
  • train 模式跑三次：同种子逐值一致证明确定性，对照种子改变输出证明非硬编码，轨迹四项阈值证明真的收敛；
  • 计算预算约 6ND，量级估计而非精确报价；小模型验证机制与纪律，不替代规模结论。

  1. 四十八个 token、窗口长度为一，为什么只有四十七个样本？batch、step、token 三个数在 stdout 里分别是多少？
  2. 为什么要固定三种随机流？torch.set_num_threads(1) 防的是哪一种误差？
  3. 训练循环里 zero_grad() 漏掉会怎样？为什么打印全量损失而不是小批量损失？
  4. train 模式为什么跑三次？程序为什么故意不打印种子？
  5. first_min=0.7、last_max=0.08、decline_min=0.7 分别对应哪几个真值？把 last_max 放宽到 1.0 错在哪里？
  6. 6ND 里的六是怎么来的？这个粗算式在哪些情况下会低估开销？
注自测题答案
  1. 第一个 token 没有上文，滑动窗口必须从第二个位置开始，所以四十八个 token 只产生四十七对。stdout 里 token_count=48、pairs=47、step 由循环次数决定是十二，批大小等于样本数四十七。
  2. random、numpy、torch 三条流互不知情，漏掉任何一条都可能让第二次运行的轨迹漂移。单线程归约固定了浮点加法次序，避免线程调度造成的末位抖动在 1e-4 的单调判定里误报反弹。
  3. backward() 把梯度加进 .grad 而不是覆盖，漏掉清零会让梯度逐轮累加、实际步长越来越大，前八步非增判定被破坏。全量损失是同一个函数在不同参数点上的值，趋势干净；小批量损失每步喂的数据可能不同，抖动得看不出趋势。
  4. 同种子两次证明程序是确定的，换对照种子证明数值来自计算而非硬编码。若打印了 seed=12345，换种子后这一行必然变化，seed_has_no_effect 会平凡通过——即使十二行损失全是写死的。
  5. first_min=0.7 对首行 0.811439，last_max=0.08 对末行 0.067893，decline_min=0.7 对降幅 0.743546。把 last_max 放宽到 1.0，闸门是过了，但「必须真的收敛」的纪律被自己拆掉。
  6. 前向每个参数约两次浮点运算，反向约四次（对输入与参数各求导），合计六次，再乘 token 数 D。长序列时注意力矩阵的二次项、LayerNorm、softmax 与数据搬运都被忽略，粗算会低估真实开销。
