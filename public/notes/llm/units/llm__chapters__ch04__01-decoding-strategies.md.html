9.1 先看工程长什么样

前面三个单元把一条 LLM 链路从注意力、预训练、KV cache 一直搭到对齐。到推理这一步，模型已经给出一个覆盖整个词表的概率分布，剩下的问题是：下一次究竟吐出哪个 token？这一单元不换模型、不训练参数，只把同一个 logits 向量交给四种不同的选择规则，看它们各自输出什么。你会看到，同一组数字经过贪心、温度、top-k、核采样之后，排序没变的部分很稳定，被改写的部分却足以决定文本读起来是死板还是自然。

工程上这一节只新增一个例子。地基 sampling.py 放所有选择规则——种子、softmax、熵、top-k、核采样、重复惩罚、抽样；入口 main.py 只管造一组固定 logits、调用四种策略、打印统计。两者放在同一个 src/ 目录下，入口靠 from sampling import ... 找到本地模块。清单 lm09-decode.json 用 mode=numerical，把十个读数钉成黄金值，闸门从真实 stdout 里解析它们，而不是听程序自报 PASS。

第 1 帧是本节故事开始时的形态：书里有 book.json，chapters/ch04/ 已经建好，但 examples/ch04/ 还不存在。第 2 帧里带 + 的五行是本单元往盘上添的全部东西。你以后读任何一节的目录树，都只看带 + 的行——它们是这一节真正的增量，没带标记的行是前面单元留下的地基。这里地基本身也是新的，所以第 2 帧把两个 .py 和清单一起标了出来。

工程惯例为什么把选择规则单独放进一个模块

main.py 里只有一组固定 logits 和一串打印语句，所有会改动「策略定义」的东西都在 sampling.py。代价是多一次 import、多一个文件要管理；好处是你要比较「top-k 取 3 还是取 5」时只动入口的常量，要改「核采样怎么累加」时只动地基里的一个函数，两边互不牵连。更重要的是，闸门规定 ch02 起的 Python 清单至少两个 .py，入口必须 import 本地模块——这不是形式主义：它逼你把「实验条件」和「算法实现」分开，别人拿到清单才知道这组数是在什么代码上跑出来的。

9.2 同一个 logits 向量：先把分布摆出来

所有策略的起点都是同一组数。本例词表大小是 8，logits:[2.500000,2.000000,1.200000,0.600000,0.100000,-0.400000,-1.000000,-2.000000]。它们不是概率——有负数，加起来也不等于 1。把它们变成概率要靠 softmax：每个 logit 先减去最大值，再取指数，最后除以指数和。减最大值这一步不改变结果，却能防止 exp(2.5) 之外的更大数溢出；它是数值稳定技巧，不是策略的一部分。

softmax 之后最大的概率落在 token 0 上，也就是 greedy_id=0，它的概率是 greedy_p=0.451329。先记住这两个数：后面所有策略都在跟它们对照。贪心解码就是「每一步取 argmax」，没有随机性，相同 logits 必然给出相同 ID。这种确定性在需要可复现的实验里是优点，在写故事时却是缺点——它永远选同一个最可能的词，于是「猫 猫 猫」和「的 的 的」这类循环极易出现。

三帧里第 1 帧强调 logits 不是概率：它们有正有负，不能直接当频率读。第 2 帧的箭头 logits -> 概率 两边都留了空格，渲染器才认它是边；写成 logits->概率 只是一串文字。第 3 帧把 greedy_p=0.451329 写在节点里，保证这一帧单独打印也读得懂——这就是帧自包含的要求：渲染器不会把上一帧的节点自动带过来。

陷阱你会以为贪心解码「最正确」

看到 greedy_id=0 与 greedy_p=0.451329，很容易得出「token0 就是正确答案」的结论。你会怎么被坑到？在翻译或摘要任务里用贪心跑一遍，发现输出不断重复同一短语；再换成采样，文本立刻自然了。真相是：最大概率只说明「在当前这一步的局部最可能」，不等于「整句话最好」，更不等于「事实正确」。概率 0.45 意味着另外 0.55 的质量分散在其余七个 token 上，贪心把这些信息全部扔掉了。本例的 base_entropy=1.461138 就是在给这份被扔掉的不确定性记账。

9.3 温度：只改分布的形状，不改排序

温度是最容易被误用的旋钮。它的定义只有一行：把每个 logit 除以同一个正数 T，再过 softmax。程序里写的是 z = logits / T 之后再做减最大值的平移。除以 T>1 缩小了 logit 之间的差距，softmax 对差距敏感，于是分布被抹平；T<1 放大差距，分布变尖；T=1 就是原始 softmax。关键性质是：除以正数不改变大小顺序，所以温度再怎么调，argmax 仍然是 token 0——它只改概率的形状，不改贪心的选择。

本例取 TEMP=1.5。结果是 temp_entropy=1.734498，比原始的 base_entropy=1.461138 高了约 0.27；同时最大概率从 greedy_p=0.451329 降到 temp_max_p=0.343410。这两个数是一件事的两面：分布变平，峰低了，不确定度就涨。注意熵的单位是 nat，因为代码用的是自然对数；换成以 2 为底要除以 ln 2，数值会变成大约 2.1 bit。

这六行里最容易被改错的是第 21 行与第 22 行的顺序。有人写成「先 softmax 再除以温度」，那得到的根本不是温度采样——除以一个常数之后概率和不再是 1，程序表面能跑，采样却会悄悄偏离。正确顺序是先除 logits，再平移、取指数、归一化。第 22 行的平移同样不能省：T 很小时，logits 除以 T 会放大到很大，exp 直接溢出成无穷，归一化后就是 nan。

第 2 帧故意把错误路径画出来，提醒你一个常见的事故：程序不报错，数字却不再是一个分布。判断方法很简单——看归一化那一步在不在最后。本例的 softmax_with_temp 把除法、平移、指数、归一四步放在同一个函数里，就是为了不给「除错地方」留缝。

9.4 top-k：先把尾巴砍掉再采样

温度改变所有 token 的概率，包括那些本来几乎不可能的尾部 token。如果你担心采样偶尔抽到一个荒唐的低概率词，更直接的办法是把尾部整个砍掉——这就是 top-k。做法是把概率按大小排序，只保留前 k 个，其余置零，再把留下来的概率除以它们的和重新归一化。本例 TOPK=3，保留 token 0、1、2；原分布里这三项的质量和是 topk_mass=0.848075。

这里有个容易混淆的量：topk_mass 是截断之前三项在原分布里占的质量，不是截断之后的单项概率。重新归一化会把这 0.848075 放大回 1，所以保留下来的每一项概率都比原来高。程序把两个量分开打印，就是让你能核对「砍掉了多少」和「剩下来的怎么重新分」。若把 mass 与归一化后的概率搞混，读代码时会以为程序漏了一步除法。

第 36 行的 clone() 不是多余的：不复制的话，后面 * mask 会就地改动传进来的张量，调用方拿到的原始分布就被悄悄改写，紧接着的核采样会在一份已经被截断的分布上再截一次。这类 bug 不会抛异常，只会让统计值无缘无故偏大。掩码用布尔张量而不是索引切片，好处是截断后的形状仍与原分布一致，后面的抽样函数不用改接口。

采样结果 topk_ids:[0,2,0,1,0,1,1,0] 是八次独立抽样。前三个位置只可能是 0、1、2，这一点可以从列表里直接验证——八次里没有出现 3 以上的 ID。样本里 token 0 出现四次、token 1 三次、token 2 一次，比例与截断后三者的相对大小一致。抽样用的是独立种子的 NumPy 生成器，不是全局随机状态，所以这段列表在本机逐位可复现。

工程惯例工程惯例：k 取多少

k=3 是为了让数字小到能手工核对，不是推荐值。工程里常见的取值是几十到几百，取决于词表大小与任务：开放域对话可以宽容一些，代码生成常常要窄一些。代价也很直接——k 太小会让输出单调，k 太大又退化成普通采样，截断形同虚设。更麻烦的是固定 k 不看分布：分布很尖时前 3 项已经占了九成以上，分布很平时前 3 项可能只占三成，同样一个 k 在两种情形下含义完全不同。这正是下一节核采样要解决的问题。

9.5 nucleus：按累计质量截断，而不是按个数

核采样也叫 top-p 采样，思路是「保留最小的集合，使它们的累计概率达到 p」。本例 P_NUCLEUS=0.9，按概率降序累加：token 0 的 0.451329 加上 token 1 的概率还不够，加上 token 2 也不够，再加上 token 3 才越过 0.9。于是 nuclep_k=4，保留四项的实际累计质量是 nuclep_mass=0.915580。它比 0.9 大一点，因为第四个 token 是跨过门槛的那一步——你不可能只取它的一部分。

把 nuclep_k=4 和 topk_k=3 放在一起看，就能看出两种截断哲学的差别。top-k 说「不管分布什么样，我只留三个」；核采样说「不管几个，我要留够九成质量」。本例两者只差一个 token，是因为这组 logits 恰好比较集中。换一组平坦 logits，top-k 仍然留三个，核采样却可能留十几个；换一组极尖的 logits，核采样可能只留一个，而 top-k 硬留三个反而把尾部噪声带了进来。

第 50 行是核心：searchsorted 找到第一个累计值不小于门槛的下标，加 1 得到保留个数。第 51、52 行再用原始下标 order[:k] 做掩码，所以截断后概率仍然落在原来的 token ID 上，不会把 token 2 的概率误记到 token 1 头上。这点很重要——如果你直接把排序后的数组当结果返回，采样出来的 ID 就全错了，而打印的概率统计看起来一切正常。

第 2 帧的 topk_mass=0.848075 小于 0.9 是这张图的关键：按个数截出来的集合，未必达到你想要的质量门槛。第 3 帧只多留了一个 token，质量就从 0.848075 涨到 0.915580——因为第四个 token 的原概率是 0.06 左右，正好把差额补上。核采样的 nuclep_ids:[0,1,1,0,1,0,1,1] 里只出现 0 和 1，这并不矛盾：可采的虽然有四个，但第 3、4 个概率小，八次抽样恰好没抽到它们。

陷阱别把核采样的 p 当成「保留 p 个 token」

P_NUCLEUS=0.9 里这个 0.9 是累计质量，不是个数、也不是概率上限。你会怎么被坑到？看到 nuclep_k=4 就以为实现错了，或者把参数从 0.9 调到 0.1 期待「更保守」，结果采样空间反而塌缩到一个 token。真相是：p 越小，越早跨过门槛，保留的 token 越少，输出越确定；p 越大，保留越多，越接近普通采样。另外 nuclep_mass=0.915580 > 0.9 也不是 bug——跨门槛的那一项要么全留、要么不留，不存在「留 40% 的 token」这种操作。

9.6 重复惩罚与束搜索：另一类选择规则

前面三种策略都在重新解释同一个分布，没有改变分布来自哪个模型。重复惩罚则直接改 logits：凡是已经出现过的 token，把它的 logit 除以一个大于 1 的因子，压低它再次被选中的机会。本例惩罚因子 1.5，被惩罚的是刚选出的 token 0。它原来的 logit 是 2.5，除以 1.5 变成 1.666667，比 token 1 的 2.0 还低，于是贪心结果从 greedy_id=0 翻成 reppen_id=1，reppen_gap=0.833333 正是 2.5 与 1.666667 的差。

这不是在「修正模型」——模型给出的原始概率并没有错，只是对重复敏感。重复惩罚是在解码阶段加的一条启发式规则，代价是会误伤 legitimate 的重复：专有名词、代码里的变量名、数字序列常常需要原样重复。因此它更像一个可以调的旋钮，而不是默认必开的开关。程序里 repetition_penalty 用 set(prev_ids) 去重：同一个 token 在上下文里出现三次和出现一次，受到的惩罚相同，这是常见实现，但它也会让「出现很多次的词」和「刚出现一次的词」被一视同仁。

束搜索是另一条路：贪心每步只看眼前最大，束搜索同时保留 b 条候选序列，每步扩展后按累计对数概率留下最好的 b 条。它的目标是找到整体概率更高的序列，而不是每一步都最可能。代价是计算量乘以 b，而且高概率序列往往短、乏味——这让束搜索在机器翻译里表现好，在开放域对话里反而容易产出安全但无聊的句子。本例不实现束搜索，因为它需要维护序列状态，超出了「在固定 logits 上比较四种规则」的范围；你只要记住它和贪心、采样不在同一个维度上：前三者改「怎么从一个分布里选」，束搜索改「同时看几条路径」。

第 2 帧的箭头 token0 -> token1 表示「最大项从 token0 移到 token1」，不是数据流。第 3 帧保留 token1 节点，保证单独读这一帧也知道是谁被选中。这个例子把重复惩罚的效果压到一个可验证的整数上：如果惩罚没生效，reppen_id 会跟 greedy_id 一样是 0，清单里的黄金值立刻不合。

工程惯例四种策略放在一张表里看

贪心确定性最好、多样性最差；温度连续可调、不改排序；top-k 按个数截断、实现简单；核采样按质量截断、对分布形状更稳；重复惩罚改 logits、专治循环；束搜索改搜索宽度、代价是 b 倍计算。这些不是互斥选项，实际系统常把它们叠起来用：先温度，再核采样，最后加重复惩罚。每叠一层，你都要重新核对输出——本例把四个读数同时钉在清单里，就是为了让「叠了哪一层」这件事有数值可查。

9.7.1 手算核对：把四个数字从 logits 推出来

屏幕上的数字看着整齐，你得能不用程序就把它们算出来，否则一旦实现写错也发现不了。先把 softmax 的分母算清楚。八个 logits 的最大值是 2.5，逐个减掉它得到 0, -0.5, -1.3, -1.9, -2.4, -2.9, -3.5, -4.5。取指数后是 1.000000, 0.606531, 0.272532, 0.149569, 0.090718, 0.055023, 0.030197, 0.011109，八项相加得 2.215679。用每一项除以这个分母，就得到原分布：0.451329, 0.273745, 0.123001, 0.067505, 0.040944, 0.024834, 0.013629, 0.005014。第一项与 greedy_p 逐位吻合，前三项相加 0.848075，正是 topk_mass；前四项相加 0.915580，正是 nuclep_mass。四个读数里有三个能在这一行算术里找到，这说明程序里的 softmax 没有偷改输入。

第四个要手算的是 reppen_gap。token 0 的 logit 是 2.5，除以惩罚因子 1.5 得 1.666667，差值 2.5 - 1.666667 = 0.833333。这里要小心：惩罚改的是 logit，不是概率；如果你先把 2.5 过 softmax 变成 0.451329 再除 1.5，得到 0.300886，跟程序打印的数完全无关。前面 9.3 节讲过「温度除在 logits 上」，重复惩罚同样除在 logits 上——这是解码层改写模型输出时的共同纪律：先在 logit 域操作，最后统一归一化一次。

熵的手算最费事，但也能做。把八个概率逐项代入 -p log p：第一项 0.451329 × 0.795559 ≈ 0.359059，第二项 0.273745 × 1.295558 ≈ 0.354653，第三项 0.123001 × 2.095563 ≈ 0.257756，第四项 0.067505 × 2.695554 ≈ 0.181963，后面四项分别约 0.130839、0.091775、0.058544、0.026552，八项合计 1.461141，与 base_entropy=1.461138 只差末位舍入。这段算术的价值不在于比谁算得快，而在于确认「熵确实是这个分布的熵」——如果哪天程序把概率归一化做错，手算这一行会立刻和屏幕对不上。

实验记录一次改常量的可证伪预测

把 main.py 里的 TOPK 从 3 改成 2，其他一行不动。按上面的算术，topk_mass 应从 0.848075 降到 0.451329 + 0.273745 = 0.725074，topk_ids 里再也不会出现 2；base_entropy 与 greedy_id 不动，因为它们只依赖未截断的分布。你可以先写下这四条预测再真跑核对。改完记得同步更新清单里的黄金值，否则闸门会报 numeric_value_mismatch——正文的数不是装饰，这条纪律在这里第三次见效。

9.8 种子与抽样：为什么 ID 列表能逐位复现

两次真跑的 stdout 完全一致，这不是运气，而是三层控制叠加的结果。set_all_seeds 固定 random、numpy、torch 三条随机流，并调用 torch.set_num_threads(1) 把归约次序钉死；draw_ids 另外用 np.random.default_rng(seed) 造一个独立生成器，采样时只认这个生成器，不去碰全局状态。两条 nuclep_ids 与 topk_ids 用的种子分别是 SEED + 2 和 SEED + 1，相差 1 却给出完全不同的序列——这正是独立生成器的典型行为：种子不同，整条随机流就错开。

为什么不直接用 torch.multinomial？它能跑，但跨版本的算法细节可能变，而本单元的纪律是「黄金值逐位对账」。NumPy 的 default_rng 在同一版本里给出稳定序列，配合固定的种子与抽样次数，ID 列表就能当证据用。代价是你要承认这份可复现性绑定在本机工具链上，换版本要重新取真值——这跟前面各册「阈值来自真跑、改环境要重新取」是同一条纪律。

第 2 帧强调「允许重复」：八次抽样是有放回的，所以 token 0 可以出现四次。第 3 帧把两条序列并排放，方便你核对它们的差别确实来自分布不同，而不是随机流不同——不对，这里两条流种子也不同。要做严格对照，你得让两个策略共用同一个种子，只改分布；本例选用不同种子是为了让两条序列彼此独立，代价是不能用它单独证明「截断改变了采样偏好」。真正证明截断效果的是 topk_mass 与 nuclep_mass 两个质量数，ID 列表只负责展示可复现性。

陷阱别用全局随机状态做可复现实验

你会习惯性地写 np.random.seed(SEED) 然后一路 np.random.choice。只要前面有人多抽了一个数，后面整条序列就错位，而程序不会报错——它只是给出另一串 ID，看着也挺合理。真相是：全局状态是共享的、隐式的，任何一处无关改动都能污染实验结果。本例给 draw_ids 传显式种子、构造局部生成器，就是把随机源变成函数参数：调用几次、在哪调用，都不影响结果。这也是为什么 ch04 的例子一律两个 .py：算法模块管随机源，入口只声明实验条件。

9.9 四种策略怎么选：一张对照表

把四个读数横着摆，选择规则就清楚了。贪心给出 greedy_id=0，确定但不多样化；温度把熵从 1.461138 抬到 1.734498，同时把峰值从 0.451329 压到 0.343410；top-k 把质量截在 0.848075，硬留三项；核采样把质量补到 0.915580，软性留四项；重复惩罚把贪心结果从 0 翻到 1。五种读数，五种不同的「改写分布的哪一处」。

策略 改什么 本例证据 什么时候用 代价
贪心 不改分布，取 argmax greedy_id=0 需要确定性、要可复现 容易重复、单调

top-k 按个数截断 topk_mass=0.848075 词表大、想限制候选 固定 k 不随分布调整
核采样 按累计质量截断 nuclep_k=4 分布形状变化大 p 调太小会塌缩

这张表不是让你挑一个「最好的」，而是让你知道调哪个旋钮会动哪一行读数。比如你把 temp_entropy 调高了却仍看到重复，说明问题在解码规则而不是温度；你把 nuclep_k 从 4 调成 2，nuclep_mass 会掉到 0.848075 附近，等于退化成 top-k 的候选数。读表时把「改什么」和「证据」两列一起看，才不会把参数当魔法。

工程惯例把策略叠起来用的顺序

实际推理服务常见的组合是：温度先把分布抹平，核采样再截掉尾部，重复惩罚最后压低已出现的 token，贪心只作为对照基线。顺序很重要——先截断再降温，会把已经砍掉的尾部重新抬高一点；先惩罚再截断，惩罚过的 token 可能直接掉出候选集，效果比预期强。本例刻意一次只看一层，让你能单独归因；等你能预判每一层的读数变化，再去叠也不迟。

9.9.1 为什么调小 p 反而更保守

核采样里的参数方向是初学时的高频错位点，值得单独说清楚。这里的 p 是「累计质量门槛」，不是「保留的比例」，更不是「保守程度」。把 P_NUCLEUS 从 0.9 调到 0.5，程序会在第三个 token 之前就跨过门槛：token 0 单独就有 0.451329，加上 token 1 的 0.273745 达到 0.725074，已经超过 0.5，于是 nuclep_k 变成 2。候选从四项缩到两项，采样空间变窄，输出更确定——也就是说，p 越小越保守，跟直觉里「概率越大越敢说」正好相反。

把 p 调到 1.0 会怎样？浮点累加到最后一项可能得到 0.9999999999999999，严格小于 1，searchsorted 于是返回数组长度 8；加一得到 9，而切片 order[:9] 仍然只覆盖全部八个 token，结果等价于不截断。这个边界行为碰巧无害，但它是切片语义兜住的，不是设计出来的保证——这提示了一条纪律：参数要落在有意义的开区间里，端点值往往触发实现细节而不是语义。工程里常见的取值是 0.9 到 0.95，太小会塌缩成贪心，太大又和原始采样没区别。

陷阱你会把 p 当成「输出的概率至少是 p」

另一种误读是把 nuclep_mass=0.915580 当成「每个输出 token 的概率至少 0.915580」。你会因此以为核采样给出的词几乎必然正确，结果一看到错误信息就震惊。真相是：0.915580 是候选集合在截断前占掉的总质量，集合里第四项的概率只有 0.067505 左右，重新归一化后也不到 0.08。集合质量高不等于集合里每一项都高，更不等于生成内容事实正确。下一单元讲置信度时会把这件事说得更透：模型对自己答案的概率和答案的正确性是两回事。

9.10 常见误解与排查顺序

第一个误解是「温度越高模型越聪明」。它只是把分布拉平，模型知道的没变多；temp_entropy 涨了 0.27，但 greedy_id 一动没动。第二个误解是「核采样的 p 越大越保守」。相反，p 越大保留的 token 越多，越接近原始采样；想保守应该调小 p。第三个误解是「重复惩罚能修好所有重复」。它只压低已出现的 token，对因为数据或训练导致的重复没有根治作用。

排查时按这个顺序走，比盯着输出猜快得多。先看 greedy_id：它变了说明 logits 本身变了，先怀疑输入或参数。再看 base_entropy：它变了说明 softmax 的输入分布不同，先怀疑 logits 或温度。然后看 topk_mass 与 nuclep_mass：它们变了说明截断逻辑被动过，先怀疑 k 与 p。最后看 ID 列表：只有它变了而前面都没变，才轮到怀疑随机源。这条顺序把「分布问题」与「抽样问题」分开，避免你在错误的地方找原因。

调试实录排查实录：ID 列表变了但质量数没变

现象：改完一行代码，topk_ids 从 [0,2,0,1,0,1,1,0] 变成别的序列，topk_mass 仍是 0.848075、熵仍是 1.461138。 推理：质量数与熵都由分布决定，它们没变说明分布没变；变的只可能是抽样这一步。 查法：对照 draw_ids 的 seed 参数与 DRAWS，看是不是有人把 SEED + 1 改成了 SEED 或改动了 DRAWS，再确认没有别处调用全局随机函数消耗了随机状态。 结论：本例的抽样走局部生成器，全局状态改动不会影响它；若序列仍变，一定是显式种子或抽样次数被改了。

9.11 接到前面各册：同一把尺子的第三次现身

概率信息论分册讲过熵与 KL：熵是惊讶度的加权平均，KL 量两个分布的差。本例的 base_entropy=1.461138 与 temp_entropy=1.734498 正是那把尺子——温度做的事可以用 KL 描述成「原分布与温度分布之间的差距」，只是本例没有把它打印出来。如果你把 TEMP 当成超参数去调，背后其实是在权衡「保持模型原有分布」与「增加多样性」两个目标，KL 可以给出后者的代价。

语言建模分册的困惑度 exp(loss) 与这里的熵也只差一个视角：困惑度用的是真实 token 的对数概率，熵用的是分布自身的加权平均。下一单元就把这把尺子用到评测上，算玩具问答的 ppl。更前面，KV cache 单元解释过生成时每一步都只看新 token 的 Q，而解码策略决定的是「这一步从分布里取哪个 token」——一个是怎么算得快，一个是算出来之后怎么选，两者在推理链路里首尾相接。偏好优化单元里的 DPO 改的是模型参数，本单元改的是推理时的选择规则；前者治疗模型本身，后者只调输出风格，不能混为一谈。

工程惯例把解码参数也写进实验记录

很多实验报告只记学习率、数据、检查点，却忘了记解码参数，于是「同一个模型」跑出两种结果就无法解释。本例把 TEMP=1.5、TOPK=3、P_NUCLEUS=0.9、惩罚因子 1.5 与种子一起写在清单能读到的源码里，打印的每一行都能追到某个常量。代价是要维护这些常量与清单黄金值的同步——改一个就要重跑取数。收益是别人拿到这份记录，能逐位复现你看到的分布统计，而不是对着一句「模型效果不错」猜你用了什么配置。这条习惯在下一单元做评测时同样成立：评测指标对解码参数一样敏感。

大白话用一句话把这一单元记住

模型给你的是一张有八个格子的概率表，解码策略决定你怎么从这张表里挑一个格子：贪心永远挑最大那格，温度把格子间的差距抹平，top-k 砍掉小格子，核采样砍到累计够九成，重复惩罚给挑过的格子上个灰色标记。挑的方式不改变你手里有哪张表，却决定别人读到的那句话是什么样。

9.12 这一节新增了什么，下一单元要什么

回到 9.1 的第 2 帧：这一节新增的是 decoding_strategies/，整本书的书目结构没动。真正的新东西是把「解码」从一句「模型输出 token」拆成五个可测量的动作——取最大值、除温度、砍尾部、按质量截、惩罚重复——每个动作都落在一行 stdout 上，都有一条清单黄金值守着。

下一单元换一个场景：不再问「怎么生成」，而是问「生成得好不好、安不安全」。你会用玩具问答算困惑度、准确率、置信度与拒答率，看到高置信度与低准确率并存时的校准问题，再用红队扰动演示一句诱导提示怎么把拒答翻成胡答。那一单元继续用两个 .py、固定种子和 mode=numerical，纪律不变，变的只是度量的对象。

小结这一节的要点

  • 温度除的是 logits，不改变排序：temp_entropy=1.734498 高于 base_entropy=1.461138，峰值降到 temp_max_p=0.343410；

注自测题答案
  1. 0.451329 只是当前这一步局部最可能 token 的概率，不等于整句最好，更不等于事实正确。其余 0.548671 的质量分散在另外七个 token 上，贪心把它们全部丢弃，这正是熵 base_entropy=1.461138 所度量的不确定性。
  2. 熵会降，因为 T<1 放大 logits 差距、分布变尖；T=0.5 时峰值会比 greedy_p=0.451329 更高。greedy_id 不变，因为除以正数不改变 logits 的大小顺序，argmax 仍是 token 0。
  3. topk_mass 是截断前前三项在原分布里的质量和；归一化把 0.848075 放大回 1，所以截断后 token 0 的概率是原概率除以 0.848075，比原来大。分开打印是为了同时核对「砍掉多少」与「剩下怎么重分」，混成一个数就看不出截断是否生效。
  4. 核采样保留「最小的、累计质量达到 0.9 的集合」。按降序累加到第四个 token 才跨过 0.9，而第四个 token 要么全留、要么不留，所以实际累计质量是 0.915580，必然不小于门槛。
  5. 惩罚因子 1.5，token 0 的原 logit 是 2.5，除以 1.5 得 1.666667；token 1 的 logit 保持 2.0，反超成为最大，reppen_gap=2.5-1.666667=0.833333，于是 reppen_id=1。
  6. top-k 固定留 k 个，不看分布形状；核采样固定留够累计质量 p，个数随分布变化。换成平坦 logits，前三个 token 占的质量会明显小于 0.9，核采样要留更多项才够门槛，因此保留的 token 更多。
  7. 需要三条随机流一起固定、线程数固定以稳定归约次序、以及给 draw_ids 传显式种子并构造局部生成器。只用全局 np.random.seed 不够：任何别处多消耗一次随机数都会让序列错位，程序却不会报错。
