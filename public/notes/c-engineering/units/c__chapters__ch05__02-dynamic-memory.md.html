12.1 先看工程长什么样

学动态内存最容易走偏的地方，是把 malloc 当成「申请一个变量」。它不是。它做的事只有一件：向堆要一块内存，交回一个地址。所以这一节照老规矩来——先看文件：这一节的每个例子都回答一个小问题，问题的答案全部落在「那块内存在哪、谁负责还、还完以后指针怎么了」这三件事上。

这是第 5 章的第二单元，也是全书的第 12 单元。前面第 4 章（examples/ch04/）已经量过栈、堆、静态区三个区，也见过 free 之后指针不变；这一节第一次完整地把堆用起来：从 malloc 到 free 的每一步，书上的规则都要落到能跑的程序上。上面那幅目录树的第 1 帧画的是这一节故事的起点：examples/ 下已经有第 1 到第 5 章五个项目，第 5 章里躺着上一单元（结构体与对齐）留下的十二个例子目录——本节一个都不动它们。

第 11 行那个写法 malloc(sizeof *p) 值得盯一眼：它量的不是类型，是「p 指的那个东西有多大」。以后元素是结构体、是 struct Node，这个写法照样对——sizeof(int) 一旦改成结构体，你忘了改的另一处就会错，而 sizeof *p 不会。这就是本书所有分配都写成 malloc(n * sizeof *p) 的原因：

语法规则分配一次的固定形状

T *p = (T *)malloc(n * sizeof *p); —— 三件事各就各位：

  • n * sizeof *p 是字节数，而且这个乘法是「以后改动最小」的写法；
  • 返回值是 void *，赋给具体类型的指针要写 (T *)（C 里可以省，本书一律写出来，为的是让读者看见类型）；
  • p 的两种坏值要分清：空指针（要不到）与悬垂指针（曾经要到了、后来还了）。判空只筛得掉第一种，这句话 12.6 节会用真程序钉住。
陷阱`n * sizeof *p` 这个乘法，自己也会害你

你会怎么被坑到：你记住了「malloc(n * sizeof *p) 是标准写法」，以为抄下来就安全了。这个乘法有两个真实的坑：

  • 用 int 装字节数：int bytes = n * 4;——n 大一点就出了 int 的范围、回绕成负数。12.11 节那个例子正是这么写的：6 亿个元素，算出来是 -1894967296，再转成 size_t 去 malloc，等于要一个天文数字；
  • 用 size_t 装，但乘出范围：size_t 是无符号的，回绕不会报错，只会悄悄变成一个小数——于是你只要到了一小块内存，却按「n 个元素」去写，越界就发生了。

检查写法只有一行（sizeof *p 是编译期常数，这次除法是安全的，SIZE_MAX 来自 <stdint.h>）：

if (n > SIZE_MAX / sizeof *p) { /* 太大了，直接拒绝 */ }

代价是多一次除法；收益是你不用猜「这次会不会刚好没溢出」。本例子里的 malloc(sizeof *p) 没有这个问题（n 就是 1）；12.9 节那个动态数组就有，见那一节末尾。

标准原文标准原文：malloc 与 calloc 各自承诺什么

C 语言标准（ISO/IEC 9899，C17）7.22.3.3 节「The malloc function」：

The malloc function allocates space for an object whose size is specified by size and whose value is indeterminate.

大意：malloc 只保证「这块地方给你」，不保证里面的值——标准用的词是 indeterminate（不确定）。所以第 1 帧里那些旧字节不是本机的毛病，是标准明确不承诺的东西。

标准原文标准原文：malloc 与 calloc 各自承诺什么（续）

同一份标准 7.22.3.4 节「The calloc function」：

The calloc function allocates space for an array of nmemb objects, each of whose size is size. The space is initialized to all bits zero.

大意：calloc 多承诺一件事：把整块内存按位清 0。两节放在一起读，「malloc 不清零、calloc 清零」这句话就有了出处——它不是经验，是两个函数各自的契约。

出处：ISO/IEC 9899:2018（C17）§7.22.3.3、§7.22.3.4。

陷阱「我试了，malloc 给我的都是 0」——这句话会骗你一整年

你会怎么看到它：写个小程序 int *p = malloc(16); printf("%d\n", p[0]);，跑出来是 0；再跑几次还是 0。于是你得出结论「malloc 会清零」，从此分配完直接开始读。

真相：你看到的是这台机器这一次恰好给了你一块干净的地。本机实测：同一个程序里，我分别要 4 个字节和 16 个字节的两块内存，4 字节那块里有非零字节（分配器留下的记账残留），16 字节那块恰好全是 0——同样的 malloc，两次结果都不一样。标准说的 indeterminate 就是这个意思：没有承诺。

陷阱「我试了，malloc 给我的都是 0」——这句话会骗你一整年（续）

你怎么会被坑到：在你自己机器上永远看不到问题，换一台机器（或换一次分配顺序、换一个运行库）就开始打出荒唐的数字，而且这种 bug 极难查——它不出现在报错里，只出现在结果里。

修法只有一条：分配完要么自己写满，要么改用 calloc，永远不要读没写过的那块内存。

12.3 要不到的时候：NULL、errno 与 perror

malloc 失败不会抛异常、不会打印任何东西——它只交回一个空指针。所以在写「要一块内存」的时候，你必须先回答一个问题：要不到怎么办？ 12.1 节那个骨架里，这件事落在第 12 到 15 行：判空、报一句、返回。真程序用三种大小的请求把这件事量出来（examples/ch05/alloc_fail/src/main.c）：

三个数字里有一个会让人意外：

  • 1 MiB 要得到，这不意外；
  • 4 GiB 也要得到——这是本机的实测结果。分配器不是立刻把 4 GiB 的内存条铺满，它先把这块地方记账记下来，等你真去写的时候才逐页落实。所以「要得到 4 GiB」不等于「你有 4 GiB」；
  • 1 TiB 要不到：返回空指针，并且 errno 是 12（ENOMEM），旁边那行字就是 strerror 把 12 翻译成人话的结果。

errno 与 perror 的用法要分两件事记：errno 是一个「可以被库函数改写的左值」（标准 7.5 节：它展开成一个类型为 int、具有线程存储期的可修改左值；库函数失败时可能往里写一个编号——不是「任何库函数都会写」，也不是「它会一直保持上一次的值」），perror / strerror 负责把编号翻译成文字。perror("malloc") 会把 malloc: Not enough space 这样的整行写到 stderr（标准错误流），所以它不会出现在上面这块 stdout 里；strerror(errno) 只返回那段文字，你可以自己决定打到哪。12.1 节那段骨架里用的就是 perror。第 14 单元讲文件与 I/O 时，perror 会天天出现——打开文件失败、读失败，报错的形状都是这一套。

陷阱只判 NULL 不判 errno，你会把「原因」丢掉

你会怎么被坑到：errno 不是「上一次调用留下的原因」，它是全局的、会被任何库函数改写的一个变量。所以下面两种写法都是错的：

  • if (errno) { /* 出错了 */ } —— errno 可能还留着上一次别处失败的编号，与这次分配毫无关系；
  • 分配失败了却只看返回值、不看清 errno，日志里就只剩下一句「失败了」——是要得太多，还是内存碎片太多，你分不出来。

正确顺序：调用之前 errno = 0（把上一次的状态清掉），调用之后立刻看返回值；要原因就在紧挨着的下一行去读 errno——中间不要插入别的库函数调用（它们可能把 errno 改掉）。上面程序第 13 行那个 errno = 0 就是这个意思。

标准原文标准原文：NULL 是标准的，errno 不是

两件事要分开看，因为它们的来源不同。

「失败给空指针」是标准规定的。7.22.3.3 节「The malloc function」的 Returns 一句：

The malloc function returns either a null pointer or a pointer to the allocated space.

大意：返回的要么是空指针，要么是可用的地址——标准把「失败」这件事就定义成空指针，没有别的出口。同一族的 calloc、realloc 也一样（7.22.3.4、7.22.3.5）。

「失败时把原因写进 errno」不是 ISO C 的要求。7.22.3 节整节讲分配函数，里面一个 errno 都没有；标准里 errno 的正式用途是给数学函数与转换函数报告 EDOM / ERANGE 这类范围问题（7.5 节、7.22.1 节）。把 ENOMEM 写进 errno 是 POSIX 给 malloc 加的要求，也是本机运行库（UCRT）的实际行为——所以你读到的 12 与 Not enough space 是本机的事实，不是语言的承诺。

出处：ISO/IEC 9899:2018（C17）§7.22.3.3、§7.5。

工程惯例工程惯例：什么时候用 calloc，什么时候用 malloc

两条惯例，都有代价：

  • 要一块「结构上必须是空」的内存，用 calloc：数组、计数表、要拿去当 hash 表用的桶——这些地方「0」是有意义的值，省掉一次 memset 也省掉一次忘写的机会。代价是**「清 0」这件事本身不免费**：标准要求那些字节是 0，实现可以真的写一遍，也可以让你拿到一页「写时才复制」的零页——本机实测 calloc(1, 4 GiB) 与 malloc(4 GiB) 都是 0 毫秒返回，说明它没有真去写那 4 GiB。所以既别指望它一定花掉那次写，也别指望它一定省下：这是实现的事；
  • 别的场合用 malloc：马上要整体写一遍的地方（比如 memcpy 一个文件进来），先清零是白干。代价是你得自己记住「这块内存现在还没初始化」。

大白话用大白话说清「生命周期」与「所有权」

  • 所有权：本子上写着「这一格是谁开的」。谁开的谁负责退，不然仓库就一直被这一格占着——这就是泄漏；
  • free 不会撕掉你手里的取物单：单据上那个格号还在，你照着号码再去开那一格的门，就是往别人的格子里伸手——这就是 use-after-free 与双重释放共同的根源。

严谨的说法只有一句：指针是「格号」，对象是「格子」，这两样要分开记账。

工程惯例工程惯例：扩容为什么按倍长，而不是每次加一个

dynamic_array 那个例子里，容量是 2 → 4 → 8 这样翻倍长的（12.9 节的输出能看到这三个数）。为什么不是「满了就加 1」？算一笔账就清楚了：

  • 每次加 1：从 1 个装到 n 个，要扩容 n 次，而每次扩容都要把已有内容搬一遍——总共搬 1 + 2 + … + n，是 n² 量级；1 万个元素要搬 50,005,000 次（约 5 千万），而且随元素个数平方增长；
  • 按倍长：第 k 次扩容搬 2^k 个元素，而后面的容量涨得更快，总搬运量是 2n 量级——均摊到每一次 push 上是常数（这就是「摊销代价」的意思）。代价是最多浪费一半空间：容量 8、装了 5 个，那 3 个位置是空着的。

所以主流做法是「翻倍」或「乘 1.5」，选哪个是空间与时间的取舍；不能选的是「每次加 1」。本例子用 realloc 实现扩容还有一个附带的好处：分配器在能原地加长时会真的原地加长，那一半的搬运就被省掉了——但不能指望它，代码必须在「换了地方」时也正确。

大白话用大白话说清「栈」与「堆」的差别

把程序想成一栋楼：

  • 栈是电梯里那把小推车：谁进电梯（谁被调用）谁用，出去（函数返回）就交还。它快、自动，但地方小（栈很小——第 13 单元会用一条深递归的链表把它量出来），而且不能带走；
  • 堆是地下仓库：地方大、谁都能租、租多久你说了算。代价是要自己退租（free）、要自己记账（谁开的谁退）、还会碎——一块块租出去又还回来之后，仓库里剩下的是一堆不连续的空隙，所以「还有 4 GiB 空着却要不到一块连续的 4 GiB」是会发生的（这就是碎片）；
  • 什么时候非用堆不可？三个信号：① 大小要跑起来才知道（数文件的字节数、用户输入几个数）；② 对象要活过这个函数（返回一块数据给调用者）；③ 对象太大，栈上放不下。

严谨的收尾只有一句：栈与堆是实现给的两个区域，它们的方向、默认大小、碎片怎么处理，标准一个字都没规定——所以本节所有的地址读数都是「本机这一次」，而规则（谁分配谁释放、多大、活多久）才是可以依赖的那部分。

还有一条更一般的：让证据出现在离错误最近的地方。把缓冲区里的输出先 fflush 出去、把「读到的值」打印出来，都是在给将来的自己留现场——本单元那两个崩溃例子（double_free、use_after_free）之所以能量出数字，全靠这一点。

12.12 每次 malloc，先问三个问题

动态内存这一节可以压缩成三条要变成习惯的规矩。它们的顺序就是出错频率的顺序：

  1. 每次 malloc，先问三个问题：谁释放？什么时候释放？要不到怎么办？ 三个问题都答得出来才允许写这一行。答不出来的时候，通常意味着这块内存应该由调用者分配（void fill(char *out, size_t n) 那种形状）——第 4 章 9.11 节那条「接口上『从哪开始』与『有几个』永远成对出现」在这里变成「接口上『谁分配』与『谁释放』也永远成对出现」；
  2. 分配完先写，再用；读一块内存之前，先想清楚它是谁写的。 malloc 的值不确定（7.22.3.3 节）、realloc 多出来的那部分也不确定——这两处是本章最容易被忽略的「不确定」；
  3. 还回去之后别再碰，并且立刻把指针置空。 置空只管得住这一个指针（别名管不住），但它把「下一次误用」从「悄悄写坏别人」（本机上往往要到进程退出才报 3221226356）变成「当场一次空指针解引用」（本机是 3221225477 那一族访问冲突）——这两种都是 UB、都不保证发生，只是后者离出错的地方近得多。在没有 ASan 的机器上，这是你能给自己争取到的最好条件。

  1. calloc 那 16 个字节保证是全 0，malloc 那 16 个字节没有承诺（本机这次恰好也是全 0，但 4 字节的请求在本机就被量到过非零字节）。这是标准的承诺，不是经验：malloc 那节写的是 whose value is indeterminate（§7.22.3.3），calloc 那节写的是 The space is initialized to all bits zero（§7.22.3.4）。
  2. 只要 p 指向一块老内存、size 非零，而这次 realloc 失败，就会泄漏（p 是空指针时 realloc 等价于 malloc，失败没有老块可丢；size 为 0 时另有规定，见 §7.22.3.5）。按 §7.22.3.5「If size is nonzero and memory for the new object is not allocated, the old object is not deallocated」——老块不会被释放，是那句赋值把老地址盖成了空指针，于是没人记得它了。正确写法是用临时指针接：int *tmp = realloc(p, n); if (tmp == NULL) { /* 老 p 还在，该 free 就 free */ } else { p = tmp; }。
  3. 没变。free 拿到的只是指针值的一份拷贝，它不会去改你的变量（本机 gdb 实测：free 前后是同一个地址）。置空只管住这一个指针：同一块内存如果还有别的指针（别名），那些指针照样悬着，用它们读或写仍然是 use-after-free——这也是「谁分配谁释放」比「记得置空」更根本的原因。
  4. 退出码 3221226356（0xC0000374），stderr 是空的——没有任何文字提示，唯一的线索就是这个码。不写成「一定会崩」是因为标准只说这是 UB；第 4 章还量过：同一个错误程序只因为启动路径不同，就会在 3221226356 与 3221225477 之间跳。所以正确说法是「本机这一次的读数 + 它是 UB」。
  5. 堆越界用 -fanalyzer：要求 malloc 的大小与越界下标都是常量、并且都写在这一个函数里（常量形状），编译退出码仍是 0（它只报告，不阻断编译），并且只在这一份源码里报——去掉参数就不报。字节数溢出用 -ftrapv：本机实测退出码 3221226505、stdout 一个字节都没有（缓冲区被一起带走了）。
