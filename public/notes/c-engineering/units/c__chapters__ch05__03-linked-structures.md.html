第一行那句 field 'next' has incomplete type 就是标准说的「成员的类型不完整」。为什么不完整：编译器读到第 7 行时，struct BadNode 还没读完（右花括号还没出现），它对这个类型只知道名字、不知道大小；而「放一个成员」必须先知道成员有多大。指针就没这个问题——本机的指针一律 8 个字节，跟它指向什么无关（第 9 单元讲指针时实测过）。所以规则是：能放指针，不能放自己。

标准原文标准原文：结构体里为什么不能放它自己

C 语言标准（ISO/IEC 9899，C17）6.7.2.1 节「Structure and union specifiers」第 3 段：

A structure or union shall not contain a member with incomplete or function type (hence, a structure shall not contain an instance of itself, but may contain a pointer to an instance of itself), …

大意：结构体里不许放「类型还不完整」或者函数类型的成员——所以结构体里不能放一个自己的实例，但可以放一个指向自己实例的指针。括号里那半句把规则一次说全了：前半个分句是「不许」，后半个分句的 may 是「可以」。

出处：ISO/IEC 9899:2018（C17）§6.7.2.1 第 3 段。

语法规则自引用结构体的写法：四行，一个字都不能少

骨架四行：typedef struct Node { 起名字、int value; 放数据、struct Node *next; 放自引用指针、} Node; 收尾并定下别名。第三行必须写 struct Node *：别名 Node 要到最后一行才生效，在结构体内部编译器还不认识它——代价是每次多打 struct 这 7 个字符。

本机的节点长这样：一个节点 16 个字节。

第 1 帧里的「空隙」不是浪费：next 是 8 字节的指针，编译器要让它落在 8 的倍数地址上，所以 int value 后面补 4 个字节。第 2 帧是链表最要紧的一张图——每个节点自己都住在堆上的一块独立内存里，节点之间只有「地址」这一条线。第 3 帧那个 NULL 是链表的终点站：它不是节点，是一个值，用来告诉所有遍历代码「到此为止」。

实验记录本机实测：16 和 8 是跑出来的
  • 工具链：gcc 16.1.0（-std=c17，也就是 C17），目标三元组 x86_64-w64-mingw32；
  • 命令：在 examples/ch05/list_head_insert/ 里跑 gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -Iinclude src/main.c src/list_head_insert.c -o app.exe，再跑 ./app.exe；
  • 结果：程序第一行打出 sizeof(Node) = 16 字节，sizeof(head) = 8 字节——节点 16 字节（4 + 4 空隙 + 8），指针 8 字节。这两行就长在第 13.3 节的输出块里，由流水线逐字对账。
陷阱自引用结构体的三个坑

你会怎么被坑到：这三个坑都能编过或者报错报得很远，你得知道自己在看什么——

  • 写成 struct Node next;：诊断是 field 'next' has incomplete type。它的措辞里一个「may not be self」都没有，所以新手会去怀疑别的地方；真相是「你要求编译器把一个还不完整的东西塞进去」。
  • 结构体末尾漏了分号（} Node 后面没 ;）：报错会跑到下一个变量声明或函数上，说 expected ';'。这是 C 里最经典的错位报错。
  • 在结构体内部写 Node *next;：诊断是 unknown type name 'Node'。那时 Node 这个别名还没出生——别名是在 } Node; 那一刻才有的。

真相只有一句：在结构体内部，只能用它自己已经完整的部分。指针是完整的（大小固定 8 字节），所以指针行得通。

头插是建链表最省事的办法：新节点永远接在最前面。list_push_front 只有三句，住在 examples/ch05/list_head_insert/src/list_head_insert.c：

这段代码里有三处值得停下来看：

  1. 第 19 行：p->next = head;。它装的是改 head 之前那个头指针。顺序不能反——先改 head 再写 p->next，新节点就指向自己，链当场成环。
  2. 第 20 行：函数返回新的头。头插会改「谁是头」，所以调用者必须这么写：head = list_push_front(head, 1);。忘了接返回值，新节点就成了没人知道的孤儿——它还在堆上，谁也找不到它，也永远释放不了。
  3. 第 24 行：遍历条件是 p != NULL，不是 p->next != NULL——后者会漏掉最后一个节点。打印、计数、释放都用前者。

大白话用大白话说链表

把内存想成一排寄存柜，链表就是「每个柜子里除了东西，还塞着一张写着下一个柜子编号的纸条」。

  • head 是你手里那张纸条（编号 3 号柜）；
  • 每个节点的 next 是柜子里的纸条，指向下一个柜子；
  • 最后一个柜子里的纸条写的内容是「没有」——程序里就是 NULL；
  • 头插是「新开一个柜子，把手里那张纸条塞进去，再把手里那张换成新柜子的编号」；
  • 删除是「把前一个柜子里那张写着「3 号柜」的纸条，改成「4 号柜」」——柜子 3 就再也没人指得到它了，这时你才能把它清空（free）。

于是「遍历」就是照着纸条一路走下去，条件自然是「手里这张纸条不是「没有」」（p != NULL）。

工程惯例工程惯例：尾指针谁维护、踩到空表怎么办

「带尾指针」不是标准规定的东西，是主流做法，代价与注意点都很具体：

  • 谁改链，谁负责把 tail 一起改。改 head 不改 tail（或者反过来）是这类代码最常见的 bug，而且往往在小数据上跑得通——因为那时的 tail 碰巧还对。本书的做法是把 head / tail / len 打包进一个 List，让「改链」只发生在少数几个函数里；
  • 空表是一个必须单独想清楚的形态。list_append_fast 里的 if (l->tail == NULL) 就是为空表准备的；删元素删到表空时，head 与 tail 又得一起回到 NULL（stack_list 里的队列出队就是这个形状：弹出最后一个元素后 rear 也要清掉，13.11 节会看到）；
  • 别忘了判 malloc 的返回值。本例里的 node_new 判了：返回 NULL 就写一行消息到 stderr 再退出。链表每插一个节点都要向分配器要一块内存，这是链表与数组最本质的差别——数组的内存一次要够，链表的内存一次要一点。

13.5 删除节点：断链重连，先取 next 再 free

删除一个节点是三件事，顺序错了就出事：找到它、把它从链上摘下来、还内存。第一部分是「找」：

prev 与 cur 一起往前走，是链表删除的标准走法：cur 是「现在看这个」，prev 是「上一个是谁」——摘链需要的是前一个节点，不是当前节点。这也是链表与数组最不一样的地方：数组删一个元素靠下标，链表删一个节点必须知道它的前驱。

第 53 行那句 Node *next = cur->next; 是整个删除里最要紧的一句，理由和第 13.7 节那个反面教材直接相关：next 要在 free 之前读走。第 54 到 58 行是两种「摘链」：删的是头节点时改 head 自己，删的是中间或尾巴时改 prev->next。第 59 行的 free(cur) 在改完指针之后——这时整条链已经不包含 cur 了，释放它是安全的。

  • 删头（第三、四行）：prev 是 NULL，走的是「改 head」那条路，删完之后新的头是 2——调用者必须用返回值更新自己的头指针，忘接就是老问题：丢了这一整条链的把手；
  • 删尾（第五、六行）：cur 的 next 本来就是 NULL，prev->next = next 把尾巴摘掉，链尾自然落到 4 上；

  • 单元素（第十一、十二行）：删的是头也是尾，删完 head 变成 NULL，表回到空表状态。

第 1 帧是「找」的结果：prev、cur、next 各就各位。第 2 帧是「摘链」：改的是 prev 的 next，cur 自己一个字都没动——它只是没人指着了。第 3 帧是「还内存」：那块内存回到分配器手里，链的形状没变。三帧就是那三句的顺序：记 next → 改指针 → free。

代价也写清楚：多一个节点（每次建表都 malloc 一个）、遍历要从 head->next 开始（忘了就会把哨兵的占位值也数进去）、空表的判断变成 head->next == NULL。换来的是删除与头插都不再分「头 / 非头」两路——用一个节点换掉一个分支，这是链表里最常见的一笔交易。工程上两种写法都有人用：前者不额外要内存，后者调用处分支更少。

语法规则头插、尾插、删除、查找，各自改哪几个指针

四种操作改的指针数量差别很大，这张表值得记下来（它也是 13.8 节「代价对照」的一半）：

  • 头插：改 2 处——新节点的 next、head；
  • 尾插（有尾指针）：改 2 处——老尾节点的 next、tail（空表时改 head 与 tail）；
  • 删除（已经有前驱 prev）：改 2 处——prev->next（或 head）、外加被删节点的 next 要先读走；
  • 按值查找：改 0 处，但要从头上一个一个走。

最下面那条是链表的命门：想删谁，得先找到谁；找到谁之前，得先走到谁。后面两节算的就是这笔账。

大意：free 把 ptr 指的那块空间还回去；如果 ptr 是空指针，什么都不做；否则，如果这个指针不是内存管理函数返回过的、或者这块空间已经释放过了，那就是未定义行为。

出处：ISO/IEC 9899:2018（C17）§7.22.3.3 第 2 段。

这条标准把「调两次安全」的条件说死了：第二次传进去的必须是空指针。本例第一次调用结束时执行了 *head = NULL;，所以第二次传的是 NULL。反过来，两个指针指着同一个节点、只 free 了一个、另一个没置空，第二次 free 就是那句 behavior is undefined——与第 12 单元讲 double free 同一条。

大白话用大白话说「谁负责置空」

置空只能由持有那个指针的人来做：节点在链表模块里 malloc，释放也就住在同一个模块，main 只把「把手」交出去；Node ** 让函数能改调用者手里那个变量，把它变成 NULL，所以再调一次不出事。而别名（好几个指针指着同一个节点）谁都救不了——list_free 只能把它知道的那一个置空。

-Wuse-after-free 报的是「这个指针在 free 之后还被用到了」，不是「这次运行会出错」。两者的差别在写代码时比在运行时更值得关心：

  • 它有来源：警告把 free 的位置（第 18 行）和「再用它的位置」（第 20、21 行）一起给出来，读的时候要一对一对地看；

  • UB 不等于崩溃：本机实测是「退出码 0 + 三次「一样」」。未定义行为的意思是「这台机器这次恰好没出事」——换分配器、换机器，或在这两次读之间再要一块内存，结果都可能变。

另一半话也得说完整：「读到旧值」只是 UB 可能的结局之一。这块内存一旦被分配器再借出去，读到的就是新主人写下的东西；具体读到什么、会不会当场崩，取决于分配器和这一刻堆的样子。我没有替这一句给出固定读数——它在同一台机器上也会变，给一个具体数字反而是骗人。能给你固定读数的是上面那条 -Wuse-after-free：它在编译期就成立，每次编译都在。

陷阱链表里两个最容易漏的边界

你会怎么被坑到：链表代码在小数据上跑得通，在边界上崩掉——而边界恰恰是链表最常见的形态：

  • 空表：head 是 NULL 时，head->value 会解引用空指针。本机实测的退出码是 3221225477（0xC0000005 访问冲突）；如果崩溃前没有 fflush(stdout)，经管道抓取时 stdout 会是空的（缓冲区没来得及刷），我另写了一个先 fflush 再解引用的探针，看到的是退出码 3221225477、stdout 只有那一行 before。所以每个收 Node * 的函数开头都要想一句：传进来是 NULL 怎么办——list_remove 的答案是「原样返回」，list_free 的答案是「什么都不做」；
  • 先 free 再取 next：本节前半的证据是「看起来完全正常」（退出码 0）。所以不要用「跑一遍没问题」来判断这类代码对不对——要按顺序检查每一处 free 之后有没有再用那个指针。

两条共同的确定性做法：判空，以及该置空的时候立刻置空。

  • 删第一个元素：数组搬移了 99999 个元素（约 399996 字节），链表搬移 0 个元素。这就是「链表插入删除便宜」的准确含义——便宜在不需要搬东西。多数情况下，搬的是「内存里的一大段字节」，改的是「两个指针变量」；

按下标取第 i 个 直接算出地址，走 0 步 从头上走 i 步
在已知位置插入 / 删除 后面每个都要挪 改两个指针

每个元素的开销 就是元素本身 元素 + 一个 8 字节指针 + 分配器的管理开销

数组大约 0.13 毫秒/遍，链表大约 10.7 到 11.9 毫秒/遍——差了八十倍上下。这两边的代码做的事情完全一样（每个元素加一次），差别只在「内存里怎么走」：

  • 数组是一整块：CPU 读第一个元素时会把附近一整段内存搬进缓存，后面几十个元素的求和几乎是白送的；
  • 链表是一堆小块：每个节点在堆上的哪个角落、离下一个节点多远，都不确定（本例是头插建的，节点在内存里基本是反着排的）。每跟着 next 跳一次，缓存基本都要重新装一次。
工程惯例工程惯例：什么时候别用链表

「链表插入删除是 O(1)」这句话没错，但要加三个前提，否则你会选错数据结构：

  • 前提一：你已经站在那个位置上。链表删一个节点的 O(1) 是「已经知道 prev 和 cur」之后的事；找到它那一步是 O(n)（第 13.5 节的 while 就是它）。所以「先按值查找、再删除」这个组合，两边一样慢；
  • 前提二：数据量不大，或者你几乎不遍历。那个八十倍是在 100 万个元素上测出来的；数据量小的时候，缓存轮不到你做主；
  • 前提三：你不按下标访问。链表的第 i 个元素没有「地址直接算出来」这回事，一旦访问模式变成「随机取第几个」，链表的代价立刻暴露（本例是 99998 步）。

反过来，真正该用链表的场合很具体：元素个数变化很大、而且增删总是发生在两头或已知位置——栈、队列（13.11 节），以及算法分册里的链表题。一句话：链表赢在「不用搬」，输在「不能跳」。

13.10 环检测：快慢指针

链表的尾巴如果没指到 NULL，而是指回了链上的某个节点，那它就不再是一条链，而是一个环。有环的链会让第 13.3 节那个标准的遍历条件失效：p != NULL 永远为真，循环永远不结束。这不是理论问题——两个链表接错了、删除时把 next 接回自己，都会当场造出一个环。

本机实测：给一条 5 节点的链（1 2 3 4 5）把尾巴指回 3 号，再用 p != NULL 走它，1000 步撞上上限还没停；同样一条无环链，5 步就走到 NULL（两个数都在下面的输出里）。

陷阱有环的表让「释放整条链」变成重复 free

你会怎么被坑到：上面那段会话说明得很清楚——while (head != NULL) { next = head->next; free(head); head = next; } 这个写法在无环的表上是对的（第 13.6 节整节都在用它），一旦表里有环，它就会绕回来把已经还回去的节点再 free 一次。你会以为「释放循环是标准写法，不会有事」，而真相是标准写法的前提是「链一定有界」。

两条纪律：

  • 造链的时候只允许一头是「开放」的：新节点只往头或尾接，绝不把已有的 next 指回链上的老节点（本例里那个 chain_close 是故意造环用的，名字就要起得让人一眼看出它在干什么）；
  • 释放之前先判环（或者约定「这条链一定有界」）。真要在有环的表上释放，得像本例的 chain_free_n 那样只释放链上的有限个节点，绝不能写 while (head != NULL)。

接口长得一样：两者都有 push / pop / size，pop 都是「返回 0 成功、-1 失败，真值从出参 int *out 拿回来」。这就是数据结构的「抽象」：调用者只关心「后进先出」，不关心底下是数组还是链表。

工程惯例工程惯例：什么时候用数组栈、什么时候用链表栈

这是本书里第一次出现「同一个接口、两种实现」的选择题，工程上的判据是两条：

  • 元素个数的上限是否可知：知道上限（比如编译器里固定 256 层的括号嵌套）就用数组栈——它一次要够内存，换来的是每次操作只改一个下标，而且内存连续（第 13.8 节那个八十倍在这里也成立）；
  • 上限未知、或者差别极大（比如解析用户输入），就用链表栈或「会自己长」的动态数组。链表把「要多少给多少」这件事做到了极致，代价是每个元素多一个指针、外加分配器的管理开销；
  • 队列要用链表，别忘了 rear。数组做队列要么搬元素，要么用环形缓冲（「空」与「满」得单独判断）；链表队列头出尾进都是常数时间，代价是本节那两处空队列特例。

代价写清楚：链表版每个元素都是一次 malloc（本例判了返回值），元素一多，分散的内存会让遍历变慢（第 13.8 节实测的 80 倍）。

  • 迭代版：flags 里加 -DDEEP_N=1000000，清单 list_head_insert_deep_iter.json，mode 是 run——退出码 0，打印出「头插建起了 1000000 个节点」与「迭代数出来 1000000 个」（上面第一个输出块）；

  • 递归版的 stdout 只有一行「头插建起了 1000000 个节点」：程序里那句 fflush(stdout) 是刻意的——不刷的话这一行也会丢（stdout 进管道是全缓冲，进程被终止时缓冲区来不及送出去；第 14 单元会专门讲缓冲，这里只要记住：崩溃前想留下输出，就得显式 fflush）；
  • 为什么是 3221225725 而不是 3221225477：栈溢出是操作系统在进程碰到栈底那一刻直接终止它；访问冲突是访问了不属于自己的地址。两类错，两个码。

这份证据里最要紧的一条是对照：同一台机器、同一份 1000000 个节点、同样的编译参数，把递归换成迭代就从「栈溢出」变成「退出码 0」。递归的代价不是代码长短，是栈的深度。

语法规则什么时候把递归换成迭代

判据只有一条：递归深度会不会大到你控制不住。

  • 链表的遍历、求长度、释放——深度就是链长，一条 100 万个节点的链就能把默认栈用光（本机实测：3221225725）。这类「顺着链走」的递归，一律改成迭代（一个 while 就够）；
  • 树的遍历——深度是树高。树高通常远小于节点数（一棵平衡的 100 万节点二叉树高度约 20），所以递归写起来更短更清楚（下一节就是这个例子）；
  • 真要深递归又改不成迭代，就得显式要更大的栈（平台相关参数），属于第 7 章的工具话题。

一句话：深度与数据规模同阶的递归要小心，深度与规模的对数同阶的递归放心用。

小结这一节的要点
  • 自引用结构体只能放自己的指针：struct Node *next 是 8 个字节的地址，struct Node next 是「不完整的类型」，编译器当场驳回（本机实测：field 'next' has incomplete type）；一个节点 16 字节、一个指针 8 字节，都是 sizeof 打出来的。建链与拆链，改的都是指针：头插改 2 处、尾插（有 tail）改 2 处、删除改 2 处。无环链上遍历的条件是 p != NULL——有环时这个条件永远为真，所以判环要用快慢指针（fast != NULL && fast->next != NULL）；
  • 删除与释放的顺序都是「先取 next，再 free」——顺序反了，本机实测的结果是「退出码 0、三次都读回原来的值」，也就是说跑起来看不出错（编译器的 -Wuse-after-free 才是可靠信号）。带哨兵的表用一个节点换掉了「删头」那个分支（代价：遍历得从 head->next 开始、空表判断变成 head->next == NULL）。所有权用类型表达：list_free(Node **head) 收地址，是为了释放完把调用者的 head 置空，于是它能安全地调两次（标准 7.22.3.3：free(NULL) 什么都不做）；而两个指向同一节点的指针各 free 一次，标准说那是未定义行为——有环的表更糟，同一个循环会把已释放的节点再 free 一遍（本机实测：退出码 -1073740940，堆损坏）；
  • 取舍要看代价：数组删头搬移 99999 个元素、链表搬移 0 个；数组 a[99998] 一句读出来（没有循环）、链表走 99998 步；100 万个整数求和，数组 0.13 毫秒/遍、链表 10.7 到 11.9 毫秒/遍（差八十倍上下）。链表赢在「不用搬」，输在「不能跳」；
  • 证据分四种：真跑的 stdout（逐字对账）、编译器的警告（-Wuse-after-free）、静态分析（-fanalyzer 的 -Wanalyzer-null-dereference，编译退出码仍是 0）、以及运行期的终止（深递归栈溢出 3221225725）。这四样要分清楚，别把「编译器看到了」说成「程序崩了」。

注自测题答案
  1. 因为 struct BadNode 在第 7 行还没读完，编译器只知道名字、不知道大小，而成员必须有完整的类型；诊断里的关键词是 incomplete type（原文：error: field 'next' has incomplete type）。改成 struct BadNode *next; 就可以——指针的大小是固定的 8 个字节（本机实测），跟它指向什么无关。
  2. 打印出来是 3 -> 2 -> 1。头插的定义就是「每个新节点都成为新的头」，所以最后插的排最前。忘接返回值的话，head 还是老的头指针，新节点还在堆上但没有任何人指着它——链上少了它，而且它永远不会被释放（内存泄漏）。
  3. 因为 cur->next 住在那块内存里，free(cur) 之后那块内存就不属于你了，再去读它是未定义行为。本机实测：退出码 0，三次循环每次都打印「从同一格读到的 next 与 free 之前一样」——它没崩，这才是最坏的结果。编译器会在编译期给出两条 -Wuse-after-free 警告（pointer 'p' used after 'free'），那才是可靠的信号。
  4. 差别在标准 7.22.3.3 第 2 段那句 If ptr is a null pointer, no action occurs：第一次 list_free 结尾执行了 *head = NULL;，所以第二次传进去的是空指针，标准说「什么都不做」；而两个别名指针各 free 一次时，第二次传进去的是非空指针、且那块空间已经释放过，正好撞上同一段的 behavior is undefined。
  5. 递归版退出码 3221225725（0xC00000FD，栈溢出），迭代版退出码 0。因为链表的递归深度就是链长（100 万层，每层都要占一份栈帧，本机默认栈装不下），而平衡二叉树的递归深度是树高——100 万个节点的平衡二叉树高度约 20 层，栈上多压 20 层调用完全不是事。
