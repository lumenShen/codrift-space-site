1.1 先看工程长什么样

学 C 最容易走偏的地方，是一上来就背语法。我们先看文件和目录：一段程序从哪个文件开始，编译器要读几个文件，最后产出什么。

大白话把这一节的目的说成人话

我写的文件叫源文件，编译器读它，产出一个可执行文件。中间它会顺手写几个临时文件（预处理结果、汇编、目标文件），平常它们写完就删，所以你看不到。这一节我们要做的，就是让它们别删，看一眼它们长什么样——因为你以后 80% 的报错，都发生在这几个文件之间的接缝上。

第 1 帧是上手第一分钟的样子：一个目录、一个 .c 文件。第 2 帧多出来的 hello.json 不是 C 的东西，它是这本书的流水线要的东西：它声明「这段程序怎么编译、跑完应该输出什么」，这样正文里的输出就不可能是手抄的（后面 1.3 会用到它）。第 3 帧是这一节结束时 examples/ch01/ 里的全部文件：多出来的四个 .c 各有用途，我们在 1.4、1.5、1.6 一个一个拆。

工程惯例工程惯例：目录怎么起名

hello/ 这种「一个程序一个目录」的摆法不是标准规定的，是三十年攒下来的主流做法：

  • 每个可独立编译运行的小程序放自己的目录，目录名用英文小写，不用空格与中文；
  • 源文件用 .c（C）与 .cpp（C++），头文件用 .h——这是惯例，标准里没写「必须叫 .c」；
  • 一个目录里只放这个程序的相关文件，编译产出的 *.exe、*.o 不要和源文件混在一起（本书统一产出到 dist/work/ 下）。

第 3 条是本书的硬规定：从第二个项目开始，不允许出现单文件工程。原因是单文件工程一旦超过 300 行，你就会开始分不清「哪些代码在互相依赖」；而分文件、写头文件这件事，越早练越省事。第一个程序（就是下面这个）允许单文件，因为它的全部意义是让你看见整条链。

陷阱中文注释与中文字符串：编码这件事现在不用管，但要记住它在

你在源文件里写的中文注释、printf 里写的中文，能不能正确显示，取决于源文件的字节、编译器用什么编码去读它、终端用什么编码去显示它三件事。本机实测（Windows 10 x64 (MSYS2 UCRT64)，gcc 16.1.0）这三件事是一致的：源文件是 UTF-8，编译出来的程序写出的也是 UTF-8，终端按 UTF-8 显示，所以上面那行 三行相加 = 6 是正常的。

你会被坑到的场合是：把同一个 .c 文件复制到另一台用 GBK 默认编码的机器上，或者把程序输出重定向进一个按 GBK 解释的文件里——那时你会看到一串像 涓夎岀浉鍔 的乱码。看到乱码先别怀疑代码：代码没有错，错的是「谁把字节当成什么编码读」。记住这个排查顺序：先看源文件编码，再看编译器有没有加编码参数，最后看终端/文件的编码。

标准原文标准原文：`#include` 到底做了什么

C 语言标准（ISO/IEC 9899，C17）6.10.2 节「Source file inclusion」对 #include <...> 的规定是：

A preprocessing directive of the form # include <h-char-sequence> new-line searches a sequence of implementation-defined places for a named header, and causes the entire contents of that header to be replaced by the contents of the file.

大意：#include 把那个头文件的全部内容就地替换进来。注意标准刻意没说「去哪个目录找」——它写的是 implementation-defined places（由实现决定）。所以 stdio.h 在哪、里面写了什么，是工具链的事，不是语言的事；换一个编译器，#include <stdio.h> 搬进来的可能是完全不同的一份文字。

出处：ISO/IEC 9899:2018（C17）§6.10.2 第 3 段。

编译器视角编译器视角：它看到的不是「一个文件」，而是一条行号链

gcc 在你按下回车后做的事，可以概括成「带着一张行号地图，逐段改写文本」：

  1. 预处理输出 .i，每段前面夹着 # 行号 "文件名" 标记（上面那 9 行的开头就是 # 3 "hello.c"）；
  2. 编译把 .i 翻成 .s，并写进 .loc 1 8 5 这样的调试指令——「接下来这段机器码对应源文件第 8 行第 5 列」；
  3. 汇编把 .s 变成 .o，符号表里留下「我引用了一个叫 printf 的外部名字」；链接再把地址填上。

所以看到报错先问一句：这是哪一步在说话？两类的修法完全不同。

1.4 printf 凭什么能用：谁能看见谁

printf 不是你写的函数，也不在 hello.c 里。它凭什么能被调用？把「谁看得见谁」画出来，这件事就清楚了：

第 1 帧是新手最容易踩的坑：编译器只认它看见过的名字。你在 main.c 里写 printf("...")，如果没有任何地方告诉它 printf 长什么样，它会当场报错（1.5 有真实的报错文本）。第 2 帧是 #include <stdio.h> 干的事：把 stdio.h 的文字搬进来，于是编译器看到了 int printf(const char * restrict format, ...); 这行声明。第 3 帧是链接期：声明只是一张「名字与参数表」，真正的实现体住在运行库里，链接器负责把两边对上。

用调试器能直接看到第 3 帧：在 printf 上打断点，程序停下时 bt 会告诉你它住在哪儿、谁调用了它。

三行关键信息：

  • Breakpoint 1 at 0x1400024f0: file D:/W/B/src/mingw-w64/mingw-w64-crt/stdio/ucrt_printf.c, line 12. —— printf 的实现体在运行库的源码文件 ucrt_printf.c 里（那是编译运行库时留下的调试信息，你机器上不一定有那个文件，所以会看到 No such file or directory 的提示）；
  • #0 printf (...) at …/ucrt_printf.c:12 —— 现在停在运行库的代码里；
  • #1 … in main () at hello.c:8 —— 调用者是你的 main，第 8 行，正是 printf 那一行。
标准原文标准原文：`printf` 是什么

同一个标准，7.21.6.3 节「The printf function」：

The printf function is equivalent to fprintf with the argument stdout interposed before the arguments to printf.

大意：printf(...) 等价于 fprintf(stdout, ...)——它只是「往标准输出写」的一个便利包装。这一节同时给出它的声明，声明决定了编译器允不允许你调用它、允许你传什么参数；实现在运行库里，标准只规定行为，不规定代码。

出处：ISO/IEC 9899:2018（C17）§7.21.6.3。

陷阱「声明」与「实现」分家，你会被这样坑到

你把程序从这台机器挪到另一台机器，hello.c 一个字没改，报错却变成了：

  • undefined reference to 'printf' —— 链接器说「这个名字找不到实现体」；不是你的语法错了，是运行库没接上。
  • 反过来，%d 写成 %s 编译器多半不拦你（参数不是常量时看不出来），程序会在运行期打出荒唐的数字或直接崩掉。

你怎么会被坑到：看到 undefined reference，新手的反应是回 hello.c 里检查拼写、改来改去——而问题根本不在你的文件里。记住分工：编译期管声明，链接期管实现，运行期管格式与参数。

现在把两个真实的编译错误摆出来。第一个：忘了写 #include <stdio.h>。源文件只有 6 行：

编译它。下面这块是真实的 stderr 原文——本书的诊断块一律照抄，连对齐用的空格都不动，所以你看到的插入符位置，就是编译器看到的位置；你按行号去源码里找，能找到同一列。

第一个诊断一次给了三样东西。读它要按 文件:行:列: 级别: 说明 拆：

  • noinclude.c:4:5: error: implicit declaration of function 'printf' [-Wimplicit-function-declaration] —— 第 4 行第 5 列（调用 printf 的位置）出错；implicit declaration 是「你调用了一个我没见过声明的函数」；方括号里是控制这条诊断的开关名，可以用 -W… 打开、用 -Wno-… 关掉。本书固定打开 -Wall -Wextra -Wpedantic，就是要把这类信号全都放出来；
  • 紧跟着它把出错的那一行源码抄给你，并在下一行用 ^~~~~~ 标出位置——行号、源码、插入符一起看，就不会数错行；
  • noinclude.c:1:1: note: include '<stdio.h>' or provide a declaration of 'printf' 是 note:，它甚至把该补的那一行都写好了（+++ |+#include <stdio.h>）。gcc 经常这样：报错归报错，顺手把正解放在你面前。

最后那条 warning: incompatible implicit declaration of built-in function 'printf' 是同一个问题的另一面：编译器认得 printf 这个内建名字，先按默认规则猜了个声明，再提醒你「这个猜测和真正的 printf 不兼容」。同一个根因，error 与 warning 各说了一遍——这也是为什么看到第一条错误就够了，后面几条经常是它的连锁反应。

第二个错误：漏了一个分号。源文件是这样——先自己找一找，再往下看编译器怎么说。

编译它。这次编译器会给你两个信号：一个 error、一个 warning，两个都值得看：先看错误本身，再看那个警告——它往往是错误的连带产物，改掉错误之后多半会自己消失。

注意报的位置：error 在第 5 行，但你要改的是第 4 行的末尾。这是 C 报错最典型的一种「错位」：编译器只有读到第 5 行的 printf 时，才能确定第 4 行的 int total = 0 后面少了东西。不要盯着报错的行号改，先往前看一行，看语句有没有收尾。

底下那条 warning: unused variable 'total' 也值得看一眼：编译器发现 total 定义了却没用上——因为第 5 行的 printf 没能成为一条合法语句，这个变量就悬空了。警告有时是错误的下游产物，改掉错误之后记得再看一遍：警告还在不在。

陷阱分号与括号：C 里最贵的两个字符

分号 ; 结束一条语句，而 if、for、while、函数定义的花括号 {} 不是语句、后面不加分号。这两条你会踩的坑：

  • 在 int main(void) { … } 后面加了分号（};）：很多编译器会默默接受，于是你无意中写出了一个「空定义」，紧接着的报错会跑到很远的地方，看起来完全不相干；
  • 在 for (...) ; 后面误加分号：循环体变成了那个空语句，循环白跑，程序不报错但结果全错——这一类错误编译器抓不到，只能靠输出对不上来发现。

这也是为什么本书要求每个程序都要有「真实输出」：输出是这类静默错误唯一的照妖镜。

编译器视角编译器视角：诊断的「级别」是它给你的分级信号

同一条问题，编译器可能用三种口吻说：

  • error: —— 我拒绝继续翻译。比如 implicit declaration of function、expected ';' before …；
  • warning: —— 我照你说的翻译了，但我认为你有地方不对。比如「变量定义了没用」（-Wunused-variable）、「格式串与参数类型不匹配」（-Wformat）；
  • note: —— 给上面那条诊断的补充信息，最常见的是一句 note: include <stdio.h> or provide a declaration of 'printf'。

本书的编译参数里不做优化（-O0）是刻意的：优化会把代码改得面目全非，调试器看到的行号会和你的源码错位（-O2 下 bt 里的行号经常跳到循环外）。等你要看「优化到底改了哪里」时，再单独用 -O2 做对照实验——那时你会用到 -fanalyzer 这类静态分析参数，它们在编译期就能报出越界、空指针这类问题（第 4 单元开始）。

1.6 字符串在内存里长什么样

上面那些 .i、.s、.o、.exe 都是文件。程序跑起来之后，数据住在内存里。"hi" 这种字符串在内存里是什么样？这段程序是真的：

三个数字要连起来读：sizeof("hi") 是 3，strlen("hi") 是 2，word[2] 是 0。

第 1 帧是本节最要紧的一张图："hi" 占三个字节——h、i、还有一个值为 0 的字节。C 用这个 0 来标记「字符串到这里结束」，写出来是 '\0'（注意是反斜杠加零，不是数字 0 那个字符 '0'）。第 2 帧解释了为什么两个函数给出不同的数：sizeof 报的是这块内存有几个字节，strlen 报的是数到 \0 之前有几个字符。第 3 帧是你以后会反复见到的对比：char word[] 是「一整块数组」，char *p 是「一个装着地址的变量」。

大白话用大白话说这三帧

把内存想成一排信箱，每个信箱装一个字节。

  • "hi" 不是「两个字母」，而是「两个字母 + 一个写着 0 的信箱」——那个信箱专门告诉函数「到这里就没了」；
  • sizeof 数「这排一共几个信箱」所以是 3；strlen 数「读到写 0 的信箱为止有几个」所以是 2；
  • char word[] 是自己复制了一排三个信箱，char *p 是手里只有一张写着「那排在哪」的纸条。

所以改 word[0] 影响不到别处，而改 *p（指向只读字面量时）可能当场崩掉：它们不是同一块内存。

实验记录本机实测：三个数字都是跑出来的
  • sizeof("hi") = 3、strlen("hi") = 2、word[2] = 0（printf 用 %d 打出来的就是这个 0）；
  • 这三个数来自 examples/ch01/string_memory.c 的真实运行，输出由流水线逐字对账（命令：gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g string_memory.c -o string_memory.exe）；
  • %zu 是打印 sizeof 结果的正确格式（它的类型是 size_t）；用 %d 打印在某些平台会打出负数。

别把这些数字当定律背：sizeof("hi") 处处是 3，但 sizeof(int) 在本机是 4、别的机器可能是 2。

工程惯例工程惯例：为什么第二个项目起必须分文件

标准只要求「一个程序有一个 main」，它对你分几个文件没有任何规定。分文件是主流做法，理由有三条：

  • 编译速度：改一个 .c 只需要重新编译它自己，链接一下就好；单文件工程每次都是全量重编；
  • 接缝可见：#include 把文件之间的依赖写在明面上。头文件里放声明，.c 里放定义，谁依赖谁一目了然；
  • 能被别人接手：一个 3000 行的 main.c 是没人愿意接的。

代价是你要多学一件事：头文件里写什么、不写什么（写重了会撞符号，写漏了会 implicit declaration）。这件事在第 3 单元讲透，现在只要记住方向：声明放头文件，定义放源文件，编译单元各管各的。

小结这一节的要点
  • 从 hello.c 到 hello.exe 有四步：预处理（.i）→ 编译（.s）→ 汇编（.o）→ 链接（.exe）；--save-temps 能把前三个留下来看；
  • #include 就是「把那个文件的全部内容就地替换进来」，所以 .i 比你写的大几十倍；报错里的行号靠预处理阶段写下的行号标记才能对回你的源文件；
  • printf 靠声明（从 stdio.h 搬进来）通过编译，靠实现体（在运行库里）通过链接；调试器能证明这一点；
  • 编译错误读法：文件:行:列: 级别: 说明，error 中断、warning 继续、note 是补充；报错的行号经常要比实际错误晚一行；
  • 字符串 "hi" 占 3 个字节，多出来的那个是 '\0'；sizeof 数字节，strlen 数到 \0 为止；
  • 本节的每个数字、每段诊断、每次运行，都来自真实文件与真实运行，由流水线逐字对账——正文里的版本号由构建期从工具链事实文件注入，不手写。

  1. hello.i 有 1525 行，而 hello.c 只有 10 行。多出来的 1515 行是什么？它们是从哪一步来的？
  2. 如果把 #include <stdio.h> 那一行删掉，程序在哪一步失败？报错里的关键词是什么？
  3. sizeof("hi") 和 strlen("hi") 分别是多少？为什么不一样？
  4. gdb 里 bt 打出来的 #0 与 #1 分别代表什么？为什么说「#1 … in main () 就是调用链的下一层」？
  5. 正文里的代码块与输出块，为什么不允许手抄？如果输出块与真实 stdout 差一个字符，哪条命令会失败、失败码是什么？
注自测题答案
  1. 多出来的是 stdio.h（以及它自己包含的头文件）的全部内容——#include 就地展开的结果，发生在预处理这一步。
  2. 失败在编译这一步（源码没变化，不会走到链接）。关键词是 implicit declaration of function 'printf'；如果编译器把它降级成警告，就会走到链接期再报 undefined reference。
  3. 分别是 3 和 2。sizeof 数的是这块内存有几个字节（含结尾的 '\0'），strlen 数的是到 '\0' 为止有几个字符（不含 '\0'）。
  4. #0 是当前停住的函数（最内层），#1 是它的调用者。#1 … in main () at trace.c:8 说明这个函数是被 main 第 8 行调用进来的，所以调用链的下一层（外面一层）就是 main。
  5. 因为手抄的东西没人对账，读者无法判断它是真跑出来的还是编的。差一个字符时，node build/run.js --all 会以失败码 stale_output（输出块）或 stale_diagnostic（编译诊断块）报错，并给出第一处不同的行号。
