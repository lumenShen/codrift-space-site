11.1 先看工程长什么样

结构体解决的是一个很朴素的问题：我想把几个值绑在一起当一个东西用。一个点有 x 和 y，一个人有姓名、年龄、分数——分开写成一堆变量，你就没法「把一个人整体传给函数」「整体存进数组」。结构体就是把它们打包成一个新的类型。

这一节是第 5 章的第一单元，也是全书的第 11 单元。照老规矩，先看文件：这一节要建起第五个项目 examples/ch05/，并且第一次让「类型定义住进头文件」。第 1 帧画的是本节故事的起点——examples/ 下已经躺着前面四章的项目，而第 5 章的项目还不存在。

第 1 帧是这一节故事的起点。第 2 到 7 帧是本节搭起来的 examples/ch05/——十六个例子目录，分六帧列完：每个都是「源文件放 src/、声明与类型定义放 include/、编译与对账的参数写在 .json 清单里」的最小工程（第 1 单元 1.7 节讲过分文件的理由，从第二个项目起本书不允许单文件工程）。第 8 到 10 帧标出四段会话：它们是编译器真吐出来的原文，抓下来存在各自的例子目录里、再逐字注入正文（后面 11.9、11.10、11.12 三节要用）。

工程惯例工程惯例：为什么这次要把类型定义放进头文件

标准只规定了一件事：一个成员表在同一个作用域里只能定义一次（6.7.2.3 节第 1 段：A specific type shall have its content defined at most once）。它对你把这段定义写在哪个文件里毫无规定。那为什么本书从这一节起，把 struct Point { … }; 写进 include/struct_basics.h？

  • 类型定义是接口的一部分：main.c 里要写 struct Point a;，编译器必须知道 Point 里有哪些成员、各占几个字节——否则它连 a.x 该往哪偏移都算不出来。把定义放进头文件，谁 #include 谁就看得见；
  • 一份定义，多处使用：src/main.c 与 src/struct_basics.c 都 #include "struct_basics.h"，两边看到的是同一个类型，布局与 sizeof 自然一致。要是各写一份、而且写得不一样，编译器与链接器都不会替你发现——本机实测：两个源文件里各写一个 struct Point（一个 int x, y，一个 long long x, y）再链接，退出码是 0，运行打出来的却是 sum = 6291088 而不是 15；
  • 代价要记住：头文件里放定义意味着「改一个成员，所有包含它的源文件都要重编」；而且这份定义对所有包含者都是公开的——想藏起来，就得用 11.12 节的「不透明结构体」。

方向性的一句话：函数声明、类型定义、宏可以进头文件；函数体、变量定义不该进（写重了会撞符号，第 17 单元讲透）。

标准原文标准原文：`==` 允许比什么

C 语言标准（ISO/IEC 9899，C17）6.5.9 节「Equality operators」第 2 段规定：

One of the following shall hold: — both operands have arithmetic type; — both operands are pointers to qualified or unqualified versions of compatible types; — one operand is a pointer to an object type and the other is a pointer to a qualified or unqualified version of void; or — one operand is a pointer and the other is a null pointer constant.

大意：== 的两边只允许是算术类型、指针（加一个空指针常量的特例），四条里必须占一条。结构体不是算术类型也不是指针，所以 a == b 直接违反这条约束——这叫约束违反（constraint violation），编译器必须报一个诊断。

顺带记住它为什么不该被允许：结构体里可能有填充字节，那些字节的内容标准不承诺（11.3 节），所以「两个结构体相等」根本没法用「字节都一样」来定义。

出处：ISO/IEC 9899:2018（C17）§6.5.9 第 2 段。本单元所有标准原文都按公开的 C11 草案 N1570 逐字核对——C17 是技术勘误，没有重编这些条款的段号。

陷阱结构体不能用 `==`，你会这样被坑到

你会看到什么：写成 if (a == b) 之后，编译器报一句 invalid operands to binary == (have 'struct Point' and 'struct Point')，位置就在这一行。

你会怎么误判：三个念头会依次冒出来——「是不是少了括号」「是不是要写 &a == &b」「是不是要 #include 点什么」。于是你加上取地址写成 &a == &b，编译器不报错了——但它比的是两个对象的地址，两个不同的对象永远不相等，哪怕是同样的值。

真相：结构体没有「相等」这个概念，标准只给了「怎么拷」，没给「怎么比」。想比就必须自己写一个函数，逐个成员比（a.x == b.x && a.y == b.y），这也是为什么头文件里通常住着一个 point_equal 而不是等着语言给你一个 ==。要小心的是：既然「相等」是你定义的，那哪些成员参与比较就是接口的一部分——比如「两条消息」比不比 len，得写清楚。

第 1 帧里那 3 个字节是本节最该记住的东西：它存在，但它不装任何东西。第 2 帧接着放 name 和 score，中间又空出 4 个字节（name 只占 4 字节，而 score 要求从 8 的倍数开始）。第 3 帧把账算平：24 字节 = 17 字节成员 + 7 字节填充，尾部一个字节都没多补（score 的 8 个字节正好落在 16 到 23）。图里每个偏移数字，都和 offsetof 打出来的一致——这不是画出来的示意图，是量出来的。

标准原文标准原文：填充字节可以出现在哪

同一个标准，6.7.2.1 节「Structure and union specifiers」里有三句话把这件事说完了：

Each non-bit-field member of a structure or union object is aligned in an implementation-defined manner appropriate to its type.

There may be unnamed padding within a structure object, but not at its beginning.

There may be unnamed padding at the end of a structure or union.

大意：① 每个成员按它的类型对齐，怎么对齐由实现决定（标准只要求「合适」，没规定具体数字）；② 结构体内部可以有未命名的填充，但开头不会有（第一个成员永远在偏移 0）；③ 结构体结尾也可以有填充。

出处：ISO/IEC 9899:2018（C17）§6.7.2.1 第 14、15、17 段。

「对齐」这个词本身也有定义，在 6.2.8 节第 1 段：

标准原文标准原文：什么叫「对齐」

Complete object types have alignment requirements which place restrictions on the addresses at which objects of that type may be allocated. An alignment is an implementation-defined integer value representing the number of bytes between successive addresses at which a given object can be allocated.

大意：一个类型对「它能放在哪些地址上」有要求，这个要求叫对齐；对齐值是实现定义的整数。所以 24 这个数字是本机 gcc 的选择，不是语言定律——标准只要求「按类型合适地对齐」，别的实现完全可以算出别的大小。

出处：ISO/IEC 9899:2018（C17）§6.2.8 第 1 段。

那填充字节里到底是什么？标准给了一个很直白的说法：

标准原文标准原文：填充字节里装的是「未指定值」

6.2.6.1 节「General」第 6 段讲的是「把值存进对象时会发生什么」：

When a value is stored in an object of structure or union type, including in a member object, the bytes of the object representation that correspond to any padding bytes take unspecified values.

大意：把一个结构体值存进一个结构体对象时，那些对应填充字节的位置取未指定的值。注意「未指定」不是「随机」也不是「保持原样」——标准的意思是：你别去看它，看了也不作数。

出处：ISO/IEC 9899:2018（C17）§6.2.6.1 第 6 段。

7.24.4.1 节「The memcmp function」第 2 段的函数说明后面跟着一条脚注（编号 310），说的正是这件事：

大意：结构体里那些为对齐留下的「洞」，内容是不确定的（indeterminate）；比它时会有麻烦。同一节第 3 段还规定返回值只要符号对：大于零、等于零、小于零分别表示「前者大、一样大、后者小」，具体数值不作承诺——本机返回的是 1，别的实现可能返回 170 或别的正数，所以判等只能写 memcmp(...) == 0，不能写 == 1。

陷阱「sizeof 比成员之和大」不是 bug，`memcmp` 比结构体才是 bug

你会看到什么：算出 sizeof(struct Person) = 24、成员只占 17，第一反应是「编译器算错了」或者「我是不是漏写了什么」。

你会怎么误判：于是你开始「优化」——把成员顺序调一调、或者给结构体加个 #pragma pack，看到 sizeof 变小了就以为赚了（11.9、11.10 两节会告诉你代价是什么）；再遇到 memcmp 判等失败，你会怀疑「是不是有一个成员没赋上值」，然后一行一行加打印——而两个结构体的成员其实一模一样。

真相：填充字节是为了对齐才出现的，它是实现的选择（§6.7.2.1 第 14、15、17 段），不是你的 bug；而 memcmp 比的是字节，填充字节的内容标准不承诺（§6.2.6.1 第 6 段、§7.24.4.1 脚注 310），所以拿 memcmp 判断两个结构体是否「内容相等」不可靠。要判等就写一个逐成员比的函数。

有人会想到「先 memset(&x, 0, sizeof x) 清零、再逐个赋值，填充字节不就一直是 0 了吗」——不行：向成员存值这个动作本身就会让填充字节取未指定的值（同一条 §6.2.6.1 第 6 段，「including in a member object」）。真要用 memcmp，顺序得反过来：所有成员都写完之后，再 memset 或逐字节清零填充区，此后不再碰任何成员；而且这个前提必须写在注释里。更稳的做法是别比内存字节，改比「你要比的那几个成员」。

工程惯例工程惯例：按对齐从大到小排成员

标准对成员顺序的规定只有一句「地址按声明顺序递增」（§6.7.2.1 第 15 段），对怎么排没有要求。把大对齐的成员排前面、小的排后面，是主流做法，理由就是上面那 8 个字节；代价有三条要说清：

  • 别为了省字节牺牲可读性：一个「姓名、年龄、分数」按逻辑顺序排就很好读，硬按对齐排会让人看不懂。先按语义排，量到浪费大再调——-Wpadded（11.9 节）和 offsetof 就是量它的工具；
  • 顺序是接口的一部分：成员顺序一改，sizeof 就变，谁按旧的大小分配了内存（比如写进文件、发给别的进程）谁就对不上；
  • 别把「省了 8 字节」当成硬指标：一个进程里十万个结构体才是一兆字节的事；在你自己的小工具里，可读性通常更值钱。

标准对参数怎么传一个字都没规定（它只说「参数按值传」），所以「多大改指针」纯粹是惯例。流传最广的阈值是「结构体超过 16 字节就传 const 指针」，理由是这样：

  • 一两个机器字大小的结构体（本机一个 struct Point 是 8 字节），按值传与传指针的差别很小，读起来按值更省事；
  • 再大就变成逐字节的内存拷贝（本机 68 字节要拷 68 个字节），而传指针只要递 8 个字节；调用次数多的时候，这个差别是真的；
  • 传指针时必须加 const（const struct Payload *p）：一是表达「我只读」，二是调用者敢放心传进来。

返回结构体是另一件事：小的结构体（本例的 8 字节 struct Point）由 ABI 用寄存器带回，几乎免费；大的就得靠「调用者提供位置 + 被调函数拷进去」，-O0 下这笔拷贝是实的（上面那个例子的第 3 条就是证据）。优化器可能把它省掉，但标准不承诺。代价还有一条：返回指针就必须交代「这块内存谁释放」（11.6、11.7 节）。阈值是惯例不是标准：小结构体按值、大结构体传 const 指针，是让代码好读的约定，不是性能定律。

陷阱浅拷贝的下半场：两次 free 把分配器的账本弄坏

你会看到什么：程序打印完你写的几行字，然后当场终止。你在 cmd 里跑会看到退出码 -1073740940；在 MSYS 的 bash 里看到 127；闸门用无符号口径抓回来是 3221226356——三个数字是同一件事（0xC0000374，堆损坏）。stderr 一个字节都没有，没有报错行可以给你看。

你会怎么误判：最早的反应是「是不是我 printf 写错了」「是不是 hello 字符串有问题」；接着会怀疑 make_message 里的 malloc 失败（可它没返回 NULL）；再往后会发现一件更吓人的事——把 free(b.text) 删掉，程序就正常了。于是你得出一个错误结论：「少 free 一次就好了」——不，你只是把双重释放换成了内存泄漏，而且还留着一个随时可能改坏别人数据的悬垂指针。

真相：a.text 与 b.text 是同一个地址，free 一次就把那块内存还给了分配器，第二次 free 同一个地址是未定义行为。标准 7.22.3.3 节第 2 段写得很直白：如果参数不是分配函数先前返回的指针、或者那块空间已经被 free/realloc 释放过，the behavior is undefined（不是「约束违反」——它没有用 shall 的措辞）。本机的现象是进程被终止、退出码 3221226356（0xC0000374，Windows 的「堆损坏」代码）：堆的内部结构被破坏了，至于具体是哪一步发现的，这个数字不告诉你。第 12 单元会把 free 的语义讲透。正确的做法只有一条：谁分配谁释放，而且只有一份所有权——要么别整体赋值（传 const 指针），要么做 11.7 节的深拷贝。

工程惯例工程惯例：深拷贝的代价，与「值语义」这个词

标准对「怎么算深拷贝」没有任何规定——它只规定整体赋值是「值的拷贝」（这份拷贝里指针成员的值照抄）。深拷贝是你写出来的一份契约，代价有三条：

  • 一条所有权规则变成了两条：每次拷贝都要配一次释放。接口上必须写清「clone_message 的返回值由调用者 free_message」——不写，接你代码的人就会漏掉一半；
  • 每次拷贝都可能失败：多一次 malloc 就多一次判 NULL（本机分配失败返回 NULL，见第 12 单元）；
  • 多一次分配与一次释放的开销：小字符串看不出来，循环里做几百万次就看出来了。

好处也是实的：副本之间完全独立——改一个不影响另一个，各释放各的，没有共享状态。这套「谁分配谁释放、谁也别省」的规矩，专业上叫结构体的值语义（value semantics）：结构体被赋值时表现得像一个值，而不是一张通往别处的纸条。C 里这个「像值」是要你自己保证的——所以结构体里有没有指针，决定了这个结构体能不能随便整体赋值，这一点必须写进头文件的注释里。

陷阱拿 union 「省内存」：你会同时丢掉可读性与可移植性

你会看到什么：写好一个 union 省下了 4 个字节，程序在本机跑得好好的；同事把代码挪到另一台机器（或者换一个编译器版本），结果全乱了——数字对不上、浮点变成荒唐值。

你会怎么误判：第一反应是「浮点精度问题」或者「编译器有 bug」，然后开始加打印、改运算顺序，越改越远。

真相：同一个 union 里「写 A 读 B」的结果依赖三样实现定义的东西：哪个成员最后被写（你忘了就是你的锅）、字节顺序（本机是小端，标准没钉死）、以及类型自己的表示（浮点是不是 IEEE-754、int 几位、有没有陷阱表示——§6.2.6.1 第 2 段把数量、顺序、编码都交给实现）。所以：① 每次换读法之前，注释里必须写清「现在里面装的是哪个成员」；② union 不该被拿来做「省内存的容器」——它省下的那几个字节远比不上它带来的沟通成本；③ 用 union 看浮点位模式是教学与调试的常见用法，写进产品代码前先想清楚：真要跟文件或网络打交道，就该显式规定「哪种字节序、每个字段几字节」（见 11.12 节关于 fwrite 的那条）。

Complete object types have alignment requirements which place restrictions on the addresses at which objects of that type may be allocated.

大意：每个完整对象类型都有对齐要求，它限制这个类型的对象能放在哪些地址上。packed 让一个 int 成员落在偏移 1，等于让一个 int 对象落在违反它对齐要求的地址上——这是编译器扩展造出来的状态，标准没有为「沿着这样的地址访问」定义行为。

如果你再把这种地址转成另一种对象类型的指针，标准有一句更直接的话（6.3.2.3 节第 7 段）：

A pointer to an object type may be converted to a pointer to a different object type. If the resulting pointer is not correctly aligned for the referenced type, the behavior is undefined.

大意：对象指针转成别的对象类型的指针后，结果若对目标类型没有正确对齐，行为未定义。(long *)&pa.i 这种写法就是直接撞上这一条。

出处：ISO/IEC 9899:2018（C17）§6.2.8 第 1 段，§6.3.2.3 第 7 段。

陷阱`packed` 在本机「看起来没事」，这正是它最坑的地方

你会看到什么：程序打印出 *ip = 7，与直接读 pa.i 一模一样。你在 x86-64 的 Windows 上跑一百次都对。

你会怎么误判：于是你认为「不对齐访问没什么大不了」，把 packed 用在了「要跟文件/网络协议对齐」的结构体上，甚至把 &pa.i 这样的指针传给了别的函数（例子里的 show_member 就是）；等你把代码拿到 ARM 或者别的架构上，或者编译器把这段代码向量化（一次搬 16 字节的指令对对齐更敏感），就会出现「值读错」或者当场异常——而你在本机是复现不出来的。

真相：对齐要求是每个类型自己的事（§6.2.8 第 1 段），packed 造出的对象违反了它；标准没有为沿着不对齐地址的访问定义行为，而把这种地址转成别的指针类型更是明确的未定义行为（§6.3.2.3 第 7 段）。本机「跑对了」只说明这台 x86-64 的标量访存宽容——同一份代码在要求对齐的 CPU 上会异常，在向量化之后也可能异常。要安全地读一个没对齐的成员，标准做法是按字节搬：例子里的 memcpy(&safe, &pa.i, sizeof safe)（输出里 safe = 7 就是它），编译器会把这几行翻成对得起任何架构的机器码。还有一条更省事的规矩：别把 packed 写进你给别人用的头文件——它省下的字节是你们两个人的协议的一部分，一改全乱。

标准原文标准原文：柔性数组成员

6.7.2.1 节第 18 段：

As a special case, the last element of a structure with more than one named member may have an incomplete array type; this is called a flexible array member. 大意：作为特例，含多个具名成员的结构体的最后一个成员可以是不完整数组类型，这叫柔性数组成员；多数场合它被忽略——结构体的大小等于「把它拿掉」之后的大小（只是可能多几个尾部填充字节）。

注意两个「必须」：它必须是最后一个成员；所在结构体必须至少有另一个具名成员（标准原文用词是 more than one named member，也就是说不能只有一个柔性数组成员）。另外它的规矩还包括：这种结构体不能作为数组元素、也不能作为另一个结构体的成员。

出处：ISO/IEC 9899:2018（C17）§6.7.2.1 第 18 段。

工程惯例工程惯例：「一次分配」比「两次分配」好在哪

另一种常见做法是分成两块：struct IntVec { size_t len; int *data; };，先 malloc 结构体、再 malloc 数组。两种都能用，惯例上的取舍是：

  • 一次分配（柔性数组）：少一次分配、少一次释放、少一次失败分支；数据连续，遍历时的缓存命中更好。代价是大小定死：想扩容就得再 malloc 一块更大的、搬过去、free 旧的（realloc 帮得上忙，见第 12 单元）；
  • 两次分配（指针成员）：扩容只需要给 data 做 realloc，结构体本身不动；代价是多一层间接（指针 → 数组）、多一次释放、多一处可能失败的地方，而且「谁释放」要写得更清楚（11.6 节的浅拷贝坑就在这儿等着）。

柔性数组成员是 C99 加进来的（在那之前大家写 int data[1]; 再「多要一点内存」，那种写法至今还能在旧代码里见到）。要不要用它，取决于你的数据会不会长大：定长就用它，会长大就用指针 + 扩容。

11.12 结构体进接口：五条纪律

结构体的定义一旦写进头文件，它就变成了接口的一部分。下面五条每一条都配了例子与证据，也都会说清代价。

① typedef 是惯例，不是必须。 你可以写 typedef struct Point Point;，之后就能写 Point a; 而不必写 struct Point a;。它为什么合法？因为 struct 的标签与普通标识符分属两个命名空间：

标准原文标准原文：标签与普通标识符是两个命名空间

6.2.3 节「Name spaces of identifiers」第 1 段列出了四类命名空间：

— label names (disambiguated by the syntax of the label declaration and use); — the tags of structures, unions, and enumerations (disambiguated by following any of the keywords struct, union, or enum); — the members of structures or unions; each structure or union has a separate name space for its members (disambiguated by the type of the expression used to access the member via the . or -> operator); — all other identifiers, called ordinary identifiers (declared in ordinary declarators or as enumeration constants).

大意：结构体的标签（struct Point 里的 Point）占一个命名空间，普通标识符（函数名、变量名、typedef 名字）占另一个。所以 typedef struct Point Point; 里那句「名字一样」根本不冲突：左边那个在标签命名空间，右边那个在普通标识符命名空间。同一节的脚注 32 补了一句：标签只有一个命名空间（struct、union、enum 的标签共用一处）——所以 struct Foo 与 union Foo 不能同时存在。

出处：ISO/IEC 9899:2018（C17）§6.2.3 第 1 段与脚注 32。

惯例上，typedef struct { … } Point;（匿名标签 + typedef）在库代码里很常见；而 Linux 内核风格明确要求不要用 typedef 掩饰结构体，理由是「读者看到 Point a; 不知道它是结构体还是整数」。所以这不是对错问题：写给自己看的小工具随便，写给别人用的接口要把「这是个结构体」留在名字里（本书的例子一律用 struct Point）。

③ 位域：布局由实现决定，所以别写进接口。 你可以写 struct Flags { unsigned a : 3; unsigned b : 5; }; 让两个字段挤进同一个存储单元，但标准对布局几乎什么都没承诺：

标准原文标准原文：位域的布局

6.7.2.1 节第 11 段：

An implementation may allocate any addressable storage unit large enough to hold a bit-field. … If insufficient space remains, whether a bit-field that does not fit is put into the next unit or overlaps adjacent units is implementation-defined. The order of allocation of bit-fields within a unit (high-order to low-order or low-order to high-order) is implementation-defined. The alignment of the addressable storage unit is unspecified.

大意：① 存放位域的存储单元多大由实现决定；② 一个位域放不下时，是换一个单元还是与相邻单元重叠，由实现决定；③ 同一个单元内位域的分配顺序（从高位到低位，还是反过来）由实现决定；④ 这个单元的对齐方式没有规定。

出处：ISO/IEC 9899:2018（C17）§6.7.2.1 第 11 段。

三个「实现定义」加一个「未规定」，所以「两个字段挤进一个字节」这句话要打折扣：那 8 个位确实挤在同一个字节里，但整个结构体仍要占一个完整的存储单元。本机实测（examples/ch05/bitfield_probe/）：

④ 别直接把结构体 fwrite 出去。 三条理由叠在一起：

  • 填充字节：padding 的内容标准不承诺（§6.2.6.1 第 6 段），写进文件就是写进一串「不知道是什么」的字节；
  • 字节序：多字节成员的存储顺序是实现定义的（§6.2.6.1 第 2 段）；本机是小端，换大端机器读同一个文件就是另一个数；
  • 类型宽度：int 在本机是 4 字节，别的实现可以是 2；long 的宽度更随平台变（本机 sizeof(long) 是 4，64 位 Linux 上通常是 8）。

小结这一节的要点
  • 结构体把成员打包成一块连续内存：声明顺序就是地址顺序，访问用 .（对象）与 ->（指针）；嵌套的结构体与数组都是「摊平」进父结构体的；整体赋值是整份拷贝，但只拷到「表面」——值成员各一份，指针成员只抄地址；
  • sizeof 比成员之和大，多出来的是对齐用的 padding（本机 struct Person 24 字节、成员 17）；== 根本不能比结构体，memcmp 也不可靠（填充字节的内容不承诺）；
  • 传参按值就拷整份（本机 struct Payload 68 字节），大结构体的惯例是传 const 指针；按值返回大结构体在 -O0 下也是一次真拷贝；浅拷贝的下半场是两次 free（本机实测 3221226356），要独立就深拷贝；
  • 进接口的纪律：类型定义可以进头文件；packed 用可移植性换字节（不对齐的访问没有标准保证）、位域别写进接口（本机 sizeof 是 4、字节排法由实现定）、结构体别直接 fwrite（填充字节与字节序都会进文件）、不想暴露内部就用「头文件只留名字」。

注自测题答案
  1. 那 7 个字节是 padding：grade 占 1 字节（偏移 0），为了让 int 落在 4 的倍数上，偏移 1–3 空 3 个字节，age 在偏移 4；name 在偏移 8（4 字节），为了让 8 字节的 double 落在 8 的倍数上，偏移 12–15 又空 4 个字节，score 在偏移 16。合计 3 + 4 = 7 字节填充。标准依据：§6.7.2.1 第 14 段（成员按类型以「实现定义的方式」对齐）、第 15 段（内部可以有未命名填充，但开头不会有）。这些数字是本机 gcc 16.1.0 算出来的（offsetof 输出为 0/4/8/16）。
  2. 填充字节的内容不一样：标准说把值存进结构体对象（包括它的成员）时，对应填充字节的位置取未指定的值（§6.2.6.1 第 6 段），而且 memcmp 的脚注专门点名了结构体里的这些「洞」内容不确定（§7.24.4.1 脚注 310）。所以「成员都一样」不等于「字节都一样」——判等要自己写逐成员比较。若真要用 memcmp，必须先把所有成员写完，再清零填充区、此后不再碰成员（先 memset 再赋值不行：赋值这个动作本身就会把填充字节变成未指定值）。
  3. 因为整体赋值只拷了 text 里那个地址：a.text 与 b.text 指向同一块堆内存，所以改 b.text[0] 等于改 a 看到的那块内存。接下来 free(a.text) 之后 free(b.text) 是同一块内存还两次——本机实测：进程被终止，退出码 3221226356（0xC0000374，Windows 把这个代码叫「堆损坏」），stderr 空，stdout 只留下崩溃前 fflush 出去的那几行（见 shallow_copy.json 的 "mode": "runtime_error"、"expect": { "exit": 3221226356 }）。这个代码说明堆的内部结构被破坏，但「是哪一步发现的」它不告诉你；标准对此只有一句：行为未定义。
  4. 只在两种情况下值得用：① 与某份外部协议/文件格式约定了逐字节布局，而且两端都按同一份声明来写；② 只在同一个程序内部用、只跟自己的代码打交道，并且你愿意为那几个字节承担「换编译器就重测」的代价。收益是 sizeof 从 12 变 8（本机实测），省下填充字节。代价至少两条：① 成员会落在不对齐的地址上（本例 i 的偏移是 1），沿着这种地址访问标准没有为它定义行为（§6.2.8 第 1 段的对齐要求被违反；再把它转成别的指针类型就是明确的 UB，§6.3.2.3 第 7 段），本机只是「CPU 宽容」；② 它不是 C 标准的东西（编译器扩展），换编译器/换架构就可能不认，而且本机实测 gcc 16.1.0 的 -Waddress-of-packed-member 只对 __attribute__((packed)) 那种写法报警告，#pragma pack 那条路一个警告都不给——「不报警告」不等于「没问题」。要读没对齐的成员，用 memcpy 按字节搬。
  5. sizeof(struct IntVec) + 5 * sizeof(int) = 8 + 20 = 28 字节（本机 size_t 8 字节、int 4 字节）。省事之处在于头与尾巴在同一块内存里：一次 malloc、一次 free、数据连续，没有第二处可能失败的分支，也不用写「先释放哪一块」；代价是容量定死，要扩容得整块搬家（第 12 单元的 realloc 就是干这个的）。柔性数组成员必须是结构体的最后一个成员，而且这个结构体不能作为数组元素或另一个结构体的成员（§6.7.2.1 第 18 段）。
