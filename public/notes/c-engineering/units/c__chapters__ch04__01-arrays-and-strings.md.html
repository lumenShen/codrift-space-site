4.1 先看工程长什么样

学数组最容易走偏的方式，是把它当成一条语法背下来（「下标写在方括号里」）。这一节照老规矩：先看文件。数组的每一个坑，最后都落在同一件事上——一排盒子挨着放，而唯一知道这排有几个盒子的人，是声明它的那一行。这句话你能在文件与命令里看见。

工程惯例工程惯例：数组参数为什么必须带长度

标准只规定了一件事：函数的形参不能真的是数组（6.7.6.3 节把 int a[] 与 int *a 规定成同一个东西）。「数组参数必须再传一个长度」是工程惯例，不是标准要求——语言没有任何机制替你记住「这排有几个」。

理由一句话：函数里 sizeof a 算的是指针大小（4.4 节有真跑的数字），长度只有调用者知道，所以让调用者说；长度和指针绑在一起递过去，接口才自解释。代价是每次调用多写一个参数，而且写错了没人替你发现：print_array(a, 4) 把 5 个元素说成 4 个，只会少打印一个；说成 6 个就踩到越界（4.3 节）。

语法规则数组的声明与初始化

两种声明：int a[5];（要五个 int 的盒子，不初始化）与 int a[] = {1, 2, 3};（长度由初始化列表数出来，只能用在有初始化的时候）。注意 int a[5]; 这五个盒子里是不确定的值，不是 0——要清零必须写 = {0}；「声明时不初始化」与「列表里没写的元素补 0」是两件事，别混。

初始化列表的三种写法：{1, 2, 3} 后面自动补 0；{0} 是把整排清零的惯用写法；{[2] = 7} 是指定初始化（下标写在方括号里），只想给某几个位置赋值时用它。

用 sizeof a / sizeof a[0] 数元素个数——这个算式只在数组还在你手上的时候有效（4.4 节讲它什么时候失效）。本书的规矩是：三种写法你都要能读、能写，但日常只推荐两种——要么明确写出全部初值，要么 {0} 清零；[2]=7 读起来省事，代价是别人要数下标才知道你改了哪几个位置。

标准原文标准原文：没写的那些元素变成了什么

C 语言标准（ISO/IEC 9899:2018，也就是 C17）6.7.9 节「Initialization」第 21 段：

If there are fewer initializers in a brace-enclosed list than there are elements or members of an aggregate, or fewer characters in a string literal used to initialize an array of known size than there are elements in the array, the remainder of the aggregate shall be initialized implicitly the same as objects that have static storage duration.

大意：花括号里的初值比元素少时，剩下的部分按「静态存储期对象」的规矩来初始化——对整数来说就是 0。第 19 段还规定了另一件事：初始化按列表顺序发生，后面写的初值会覆盖前面为同一个位置写的初值；没有显式初始化的部分，同样按静态对象处理。这两段合起来解释了 {1, 2, 3} 后面那两个 0、{0} 的整排零、以及 {[2]=7, [4]=9} 只在两个位置上有值。

注意标准说的是「一样」而不是「等于零」：静态对象的规矩里指针是空指针、浮点是 0.0。所以初值缺失时不是垃圾值。

出处：ISO/IEC 9899:2018（C17）§6.7.9 第 19、21 段。

第三段是三种写法等价。a[i]、*(a + i)、i[a] 打出同一个数。最后那个写法不是笔误：标准把下标运算定义成「先加再解引用」（下一块有原文），加法可交换。

标准没有单独定义「数组下标」这个语法，它做的是替换。6.5.2.1 节「Array subscripting」第 2 段：

The definition of the subscript operator [] is that E1[E2] is identical to (*((E1)+(E2))). … E1[E2] designates the E2-th element of E1 (counting from zero).

大意：E1[E2] 就是 *((E1)+(E2)) 的另一种写法，而且标准特意补了一句「从 0 开始数」。这句话一次解释了三件事：为什么 a[2] 与 *(a + 2) 同值；为什么 2[a] 合法；为什么 a[i] 里的 i 可以是负的（语法上它就是一个整数，编译器不会拦——但走出去就是 UB，4.3 节下面就有 a[-1] 的真实现象）。

陷阱越界：三种后果，都不报错

你会看到什么：程序照样编译、照样运行。编译器不会因为「下标越界」这四个字报错——它顶多在「长度能在编译期算出来」的写法上给一条警告（例如定长 strcpy，4.9 节有原文），而那种警告也拦不住程序跑起来。你会怎么误判：以为「没报错就是没错」，甚至以为「越界读到的那个值就是我要的」。真相是：下标越界在 C 里是未定义行为（UB）——语言不管，编译器只在少数形状上提醒，运行时也不一定有反应。它会落到三档后果里的一档，取决于越界多远、是读还是写：

  1. 改到邻居：只超出一个变量的地盘，悄悄改掉旁边变量的值，程序继续跑，结果莫名其妙——本节 oob_neighbor 有真证据，4.9 节把它画成图；
  2. 当场崩溃：越界跑到进程没有权限的内存，退出码 3221225477（0xC0000005，访问冲突）——往字符串字面量里写（4.8 节）就是这一档；
  3. stack smashing：编译器在栈上放了「校验值」，函数返回时发现它被踩坏了，于是把进程杀掉并打印 *** stack smashing detected ***——这一档要主动开保护（-fstack-protector-all）才看得见，4.9 节有清单。

三档里最危险的是第一档：它什么都不说。

标准原文标准原文：越界这件事，标准只说了四个字

标准里没有「下标越界」这一节——6.5.2.1 节把 a[i] 定义成 *(a + i) 之后，越界就变成了指针算术越界，归 6.5.6 节「Additive operators」第 8 段管：

If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined.

大意：指针加上一个整数之后，结果必须还落在这个数组对象里（或者正好落在最后一个元素的后面一格），否则行为未定义。注意标准留的那一点余地：「最后一个元素的后面一格」允许被算出来（这样你才能写 for (p = a; p != a + n; p++)），但那一格不许解引用——同段最后一句就是这么写的。

所以「越界是 UB」不是吓人的话，而是标准里一条明文规定：编译器有权假设你不会越界，并据此优化代码——-O2 下越界程序行为突变，就是这个假设在起作用。

出处：ISO/IEC 9899:2018（C17）§6.5.6 第 8 段（另见 §6.5.2.1 第 2 段对下标的定义）。

Except when it is the operand of the sizeof operator, the _Alignof operator, or the unary & operator, or is a string literal used to initialize an array, an expression that has type ''array of type'' is converted to an expression with type ''pointer to type'' that points to the initial element of the array object and is not an lvalue.

大意：除了一组列出来的场合，数组类型的表达式都会自动转成「指向首元素的指针」。原文的 except 子句一共列了四项，前三项是运算符：

  • sizeof 的操作数——所以 sizeof a 在调用者那边量到的是整块 20 字节（这就是「例外」的实际价值）；
  • _Alignof 的操作数——按标准它只接类型名（_Alignof(int[4]) 是 4，本机实测），所以日常代码里几乎碰不到这一项；GCC 额外允许 _Alignof(表达式)，但 -Wpedantic 会提示这不合标准；
  • 一元 & 的操作数——所以 &a 的类型是「指向整块数组的指针」，而不是「指向首元素的指针」（4.3 节那个 sizeof *&a = 16 就是它）。

第四项是「用来初始化数组的字符串字面量」：它说的是 char s[] = "hi"; 里的字面量不先转成指针（否则数组没法用字面量初始化），跟前三项不是一回事。本书说「三处例外」时，指的是前三个运算符——那才是你写代码时会遇到的。

标准还补了一句：转成指针之后的那个表达式不是一个左值——它不是那排盒子本身，只是「首地址」这个值。

出处：ISO/IEC 9899:2018（C17）§6.3.2.1 第 3 段。

标准原文标准原文：为什么 int a[5] 与 int *a 是同一个东西

同一件事在参数上有更直接的规定，6.7.6.3 节「Function declarators (including prototypes)」第 7 段：

A declaration of a parameter as ''array of type'' shall be adjusted to ''qualified pointer to type'', where the type qualifiers (if any) are those specified within the [ and ] of the array type derivation.

大意：参数里写「数组类型」，一律被改写为「（带限定符的）指针类型」。所以 void f(int a[5]) 与 void f(int *a) 是同一个函数签名；参数里的方括号和数字只是一种写法，不携带长度信息。

把这两段连起来读就得到一条工程结论：函数不可能通过形参知道数组有多长。这是语言层面的规定，不是实现的选择。

出处：ISO/IEC 9899:2018（C17）§6.7.6.3 第 7 段。

工程惯例工程惯例：只读的数组参数写 const T *

标准里 const 是类型限定符（6.7.3 节），规定「不许通过这个表达式去修改那个对象」。把 const int * 写成数组参数的默认形状，是工程惯例——语言不会强迫你写。

理由三条：① 意图写在签名上：const int *a 一眼是「只读输入」，int *a 是「我要改你给我的东西」；② 调用者能传的东西变多：只读接口能收 const 数组与字符串字面量，写接口收不了；③ 编译器替你守约：实现里手滑写 a[0] = 1，编译立刻报错。代价是挡住了「本来想改」的接口：真要改（比如 copy_array），就得老实写 int *dst——那也正好是它该有的样子。所以 const 不是「更安全所以都加上」，它是接口语义的一部分：本书的写法是只读 const T *、要改 T *，长度紧跟在数组参数后面。

It is unspecified whether these arrays are distinct provided their elements have the appropriate values. If the program attempts to modify such an array, the behavior is undefined.

大意：① 两处内容相同的字面量是不是同一块内存，标准没规定（这就是上一节那个 p == q 为真的来历——本机合并了，但你不能指望）；② 程序一旦试图修改字面量那个数组，行为未定义。所以崩溃不是「编译器有 bug」，而是你把 ② 撞上了。

机制：-fstack-protector-all 让编译器在每个函数的栈帧里塞一个「校验值」（canary），函数返回前检查；被动了就打印那行 *** stack smashing detected *** 并终止进程。所以它只抓写坏栈上数组、还碰了校验值这一类；堆越界、只踩到邻居没碰校验值，都抓不到。

-fanalyzer 不在本书的基础参数里，因为它慢、有误报，做的是「路径推理」。这是惯例选择，不是标准规定：标准对「编译器该给什么警告」一个字没写。

工程惯例工程惯例：strncpy 不是「安全版 strcpy」

先把界限说清：这是惯例讨论，不是标准——标准只定义每个函数做什么，不规定你该用哪一个。很多人看到 strcpy 出事就换成 strncpy(dst, src, sizeof dst)，方向对，但有坑：源比目标长时它不补结束标记，目标里的字符串「没有结尾」，后面交给 strlen、printf("%s") 就是越界读。完整答案是「先算长度、再拷、最后自己补 '\0'」，更重要的习惯是：从外部拿进来的字符串，长度必须先被限住（4.10 节的 fgets 就在做这件事）。具体现象与修法在第 15 单元，这里先记结论：换函数不等于换掉责任。

标准原文标准原文：fgets 与 scanf("%s") 各自承诺了什么

先看 fgets，7.21.7.2 节「The fgets function」第 2 段：

The fgets function reads at most one less than the number of characters specified by n from the stream pointed to by stream into the array pointed to by s. No additional characters are read after a new-line character (which is retained) or after end-of-file. A null character is written immediately after the last character read into the array.

大意：最多读 n-1 个字符；遇到换行（换行会被保留在结果里）或文件结束就停；读完之后一定在末尾补一个空字符。「n-1」和「一定补 '\0'」这两条，就是 fgets 能当安全入口的全部理由——你把 sizeof s 递进去，它自己就不会写坏。

再看 scanf 的 %s，7.21.6.2 节「The fscanf function」第 12 段里对 s 的规定：

s Matches a sequence of non-white-space characters. … If no l length modifier is present, the corresponding argument shall be a pointer to the initial element of a character array large enough to accept the sequence and a terminating null character, which will be added automatically.

大意：%s 匹配一串非空白字符，而且标准把「数组足够大」写成了对调用者的要求——它自己不检查、也不接收「数组多大」这个信息。上面 word 只有 8 个字节而输入词有 14 个字符，责任在调用者这一侧，标准把话说明白了。

出处：ISO/IEC 9899:2018（C17）§7.21.7.2 第 2 段、§7.21.6.2 第 12 段。

工程惯例工程惯例：输入一律用 fgets，再自己解析

标准提供两条路：fgets（自己给上限）与 scanf 系列（%s 不给上限，但能写 %15s 这种宽度）。本书的惯例是走 fgets，理由三条：

  • 上限只写一遍：fgets(line, sizeof line, stdin) 把「盒子多大」与「读几个」绑在一起；scanf("%15s", word) 里的 15 是手写数字，改了数组忘了改它就会漏。
  • 给你整行：连换行一起拿到，剩下的自己分（sscanf、strtol 都行）；scanf("%s") 只给一个词，容易和下一次读错位。
  • 截断通常是可见的：fgets 截断时末尾多半没有换行（正好 n-1 个字符的边界见 4.10 正文）；scanf("%s") 越界时什么都不说。

代价是换行会一起带回来，经常要自己把末尾的 '\n' 去掉。换来的是：输入的边界是你自己划的，不是运气划的。

小结这一节的要点
  • 数组是一排连续、等宽的盒子，编号从 0 起；sizeof a 量整块、sizeof a[0] 量一格，相除就是元素个数；没写的初值按静态对象处理（整数是 0），不是垃圾值；a[i] 就是 *(a + i)；越界是 UB，后果分三档——改到邻居（本机实测 guard 从 12345 变成 1111570744）、崩溃（退出码 3221225477）、stack smashing（开 -fstack-protector-all 后 3221226505 + *** stack smashing detected ***）。
  • 数组名会退化成指针（例外是 sizeof / _Alignof / &，外加一条「初始化数组的字面量」），参数里的 int a[5] 也一样——所以函数里 sizeof a 是 8，长度只能由调用者一起传；一维只读参数写 const T *（二维数组在 C17 里加不了，见 4.6）。数组不能整体赋值、不能按值传参、不能返回（b = a; 与 int[3] f(void) 各有一条真错误），整排搬只能逐元素或 memcpy。
  • 字符串 = 字符数组 + '\0'：sizeof 数字节、strlen 数到 '\0' 为止；char s[] = "hi" 是你自己的三个字节（可写），char *p = "hi" 只是一个指向只读字面量的指针（写它退出码 3221225477，且字面量可能被合并）。
  • strcpy / strcat 不接收目标长度，是越界的头号来源；-Wstringop-overflow 默认就开着（-O0 也报），-Warray-bounds 要 -O2，-fanalyzer 能把常量下标与定长 strcpy 两种形状在编译期指出来（CWE-121，栈上）——但这些都是「编译器看到的」，运行期证据仍是退出码与 stderr。读输入用 fgets(s, sizeof s, stdin)（最多 n-1 个字符、一定补 '\0'），scanf("%s") 要求你自己保证数组足够大：本机实测 14 个字符的词把一个 8 字节数组的邻居写成了 1280002633。

  3. s 的 sizeof 是 3（它自己有三个字节），p 的 sizeof 是 8（它只是一个装地址的变量）。能写的是 s 那块（s[0] = 'H' 合法，改完 s 变成 Hi 而字面量没动）；p 指向的字面量不可写，本机写它退出码 3221225477。p == q 为真说明本机把两份内容相同的字面量合并成了一块（标准 6.4.5 节第 7 段说这件事「unspecified」，即没规定），它不能说明「字符串可以用 == 比较内容」——那要用 strcmp。
  4. 两个手段：① 把源换成常量再编一次——strcpy(buf, "0123456789ABCDEF") 会让 -Wstringop-overflow 立刻指出「写 17 个字节进 8 个字节的盒子」（本机默认就开着，不用加任何开关）。它只能证明「编译器在长度可算时看得见」，抓不到运行期才确定长度的写法，所以不能当成「运行期没问题」的证据。② 开栈保护再跑一次——把清单写成 detect=stack-protector（等价于编译时加 -fstack-protector-all），本机实测 stderr 会出现 *** stack smashing detected ***、退出码 3221226505；去掉这个开关（阴性对照）退出码变成 3221225477、stderr 为空，证明这句诊断确实是这个开关抓出来的。它只能抓栈上数组被写坏、且踩到校验值的情况，堆越界与只踩到邻居它都抓不到。再加上 ②' 用分析器看编译期——把样本改成常量下标（a[7] = 1;）或定长 strcpy 形状，加 -fanalyzer 编译，本机实测报 stack-based buffer overflow [CWE-121] [-Wanalyzer-out-of-bounds]，并给出「capacity: 16 bytes」与「写到第 28 到第 31 个字节」的推理链；它的局限是源是运行期才确定的形状就报不出来（那份 copy_into_small(const char *src) 就一声不吭），而且编译退出码仍是 0。合起来：一个证明「编译期看得出来」，一个证明「运行期真的坏了」，但它们都不能替代「别让目标装不下」这件事本身。
  5. 因为 scanf("%s") 没有上限：标准 7.21.6.2 节要求调用者保证数组「足够大」，它自己不检查，写到内存哪儿它也不管（本机实测 14 个字符的词把 8 字节数组的邻居 guard 从 12345 改成了 1280002633，程序还不崩）；而 fgets 最多读 n-1 个字符并一定补 '\0'（7.21.7.2 节），sizeof line 一递，边界就是它自己划的。fgets 带来的麻烦是：它把换行一起带回来（截断时末尾没有换行，正好可以用来判断「这一行没读完」），拿到之后常常要自己把末尾的 '\n' 去掉。
