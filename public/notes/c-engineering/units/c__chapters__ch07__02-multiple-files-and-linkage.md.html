17.1 先看工程长什么样

上一单元（c16 预处理与宏）讲的是符号在编译之前怎么变形；这一单元讲的是符号在编译之后怎么汇合。它要回答的问题只有一个：我把程序拆成好几个文件之后，编译器凭什么还能把它们拼成一个可执行文件。

照老规矩，先看文件。这一节的起点很朴素：examples/ 下已经躺着前面几章的项目；第 7 章的目录由本章上一单元（c16 预处理与宏）建了起来，里面是宏的实验。本节要做的是往同一个目录里，从一个单文件草稿开始，长出一个三层工程。

第 1 帧是本节故事的起点：examples/ 下是前面六章的项目，第 7 章的目录已经由本章上一单元（c16 预处理与宏）建好，里面躺着宏实验。第 2 帧先落下一个 draft.c——它确实是本节的第一版程序，但它是个反面教材：所有东西挤在一个文件里，别人想用 greet_banner 就得把整个文件复制走。第 3 帧把它拆成 two_files/：源文件进 src/、头文件进 include/、编译参数进 .json 清单，这就是本书从第 2 个项目起一直用的最小工程形状。第 4 到第 6 帧是七组对照例子，每一组只演示一件事（少定义、重复定义、没有 guard、guard 与 #pragma once、头文件里放函数定义、链接性、头文件里的 const、不完全类型、循环依赖）。第 7 帧是本节的两件沉淀物：一个三层工程（带一个 build.sh）和八个抓下来的终端会话。

先记住每一组例子对应哪一件事，后面会逐个点名：

  • two_files、undefined_helper、double_definition —— 一个工程的正面与两类链接期的失败（17.2 到 17.5 节）；
  • no_guard、guarded_include、header_function —— 重复包含的症状与两种修法（17.6 节）；
  • static_scope、extern_shared、const_in_header —— 链接性：谁看得见谁（17.7 节）；
  • forward_decl、cycle_before、cycle_after —— 不完全类型，以及真的循环依赖怎么破（17.8 节）；
  • layered_app、split_build、build.sh —— 分层、一条命令与分步编译（17.8、17.9 节）。
工程惯例工程惯例：一个模块 = 一对文件

标准对这件事只有一个要求：一个程序有且只有一个 main。分几个文件、文件叫什么名字，全是惯例。本书的惯例是：

  • 一个模块 = 一对文件：greet.h 里放声明，greet.c 里放定义，名字必须一样；
  • 头文件在 include/，源文件在 src/，编译时加 -Iinclude；
  • 依赖方向单一：main.c 依赖 logic.h，logic.c 不依赖 main.c——箭头永远只朝一个方向走；
  • 谁用谁包含：一个 .c 里用到什么，就 #include 什么，不靠「别人替我包含过了」。

好处有三条：改一个 .c 只需要重编它自己；文件之间的接缝写在 #include 这一行上；别人接手时，看头文件就知道这个模块对外承诺了什么。

代价也说清楚：你要多学三件事——include guard、链接性、以及怎么在报错时分辨「编译期」和「链接期」。这一单元就是这三件事。

标准原文标准原文：程序不是一次翻完的

C 语言标准（ISO/IEC 9899，C17）5.1.1.1 节「Program structure」第 1 段：

A C program need not all be translated at the same time. The text of the program is kept in units called source files… A source file together with all the headers and source files included via the preprocessing directive #include is known as a preprocessing translation unit. After preprocessing, a preprocessing translation unit is called a translation unit. … The separate translation units of a program communicate by (for example) calls to functions whose identifiers have external linkage, manipulation of objects whose identifiers have external linkage, or manipulation of data files. Translation units may be separately translated and then later linked to produce an executable program.

大意：一个 C 程序不必一次翻译完。标准把「一个源文件 + 它 #include 进来的所有头文件」叫翻译单元（translation unit）——这就是我们平常说的「编译单元」在标准里的正式名字。而不同的翻译单元之间的交流靠的是「有外部链接的名字」：调用外部函数、读写外部对象。最后一句把整条流水线说完了：翻译单元可以各自翻译，之后再链接。

出处：ISO/IEC 9899:2018（C17）§5.1.1.1 第 1 段（含 Note）。

大白话用大白话说这三帧

把每个 .c 想成一间独立的办公室，每个办公室有一张贴在墙上的名单（符号表）。

  • gcc -c greet.c 就是让 greet.c 那间办公室自己干活：它把 greet 记到墙上，标注「我提供 greet」；
  • gcc -c main.c 让另一间办公室干活：它把 greet 也记到墙上，标注「我欠一个 greet，谁给我？」；
  • gcc main.o greet.o 就是把两张名单摆在桌上对一遍：欠的有人给 → 拼成程序；欠的没人给、或者两个人各给一份 → 两边都进行不下去。

所以「头文件」不是代码的一部分，它是传话的纸条：它让每间办公室知道外面有哪些名字可用，但它一丁点儿机器码都不产生。

陷阱「一个 `.c` 编不过，就是那个 `.c` 里写错了」——这个直觉会在链接期骗你

你会看到什么：命令行里 src/main.c src/greet.c 一起给，报错却只写着链接器那句 collect2.exe: error: ld returned 5 exit status（17.4 节），一个文件名、一个行号都没有。

你会怎么误判：你会回头去 main.c 里逐行找——拼写？参数？分号？然后一无所获，因为那两份源文件都编译成功了，每一份单独看都完美无缺。

真相：错的是它们之间。有了本节这张图，检错顺序就固定了：① 先确认报错发生在编译（有 文件:行:列）还是链接（没有行列，只有 collect2/ld）；② 是链接期，就去看符号表（17.5 节），那里写着每个 .o 欠谁、给谁；③ 才回去改代码。在链接期错误上逐行读源码，是最费时间的一条路。

17.3 头文件放什么、源文件放什么

上一节的头文件里只放了两行声明，于是问题来了：头文件是不是只能放声明？ 不是。头文件里能放的东西一共三类，而判断标准只有一条：

放在头文件里的 例子 为什么可以
声明（函数的、变量的） const char *greet(void);、extern int g_hits; 声明不产生目标码，念几遍都一样
宏 #define SHARED_LIMIT 3、include guard 宏是文本替换，编译之前就消失了
类型定义 struct Point { int x; int y; };、typedef … 只要内容每次都一样，"一个类型"还是同一个类型

反过来，函数体和有初值的变量属于「定义」，它们会产生目标码、要占内存，所以必须住在一个 .c 里。唯一允许出现在头文件里的定义是「每个编译单元各要一份」的那种，写法是加 static——17.7 节会拿 const double PI 这件真事把这条规则钉死。

三类东西可以用同一个问题来分：「如果 5 个 .c 各念一遍，会有 5 份吗？」

  • 声明：念 5 遍还是那一个名字、一份实现——安全；
  • 宏：念 5 遍就被替换 5 次，但每次替换的结果一样，而且它在预处理结束时已经消失——安全（除非两次定义不同，那会得到 warning: "N" redefined）；
  • 类型定义：5 个翻译单元各念一遍，只要文本一样，它们描述的就是同一个类型（标准 6.2.7 节要求这些声明相容），并不冲突；真正会出事的是同一个翻译单元里念两遍——那就是重定义（17.6 节）。
  • 函数定义与有初值的变量：每念一遍就产生一个符号，5 份就撞车。函数落在 T，只读数据落在 R，可写数据落在 D（有初值）或 B（初值为 0）——17.7 节会逐个见到这四个字母。

extern_shared/include/shared.h 第 8 行那句 #define SHARED_LIMIT 3 就是「宏进头文件」的正面例子：它既是一个可以被所有编译单元共享的常量，又没有产生任何符号。代价是它没有类型、没有作用域、调试器看不见它——这三个缺点在 c16 里已经讲过。

标准原文标准原文：引号形式找不到时会退回去

C 语言标准 6.10.2 节「Source file inclusion」第 3 段：

A preprocessing directive of the form # include "q-char-sequence" new-line causes the replacement of that directive by the entire contents of the source file identified by the specified sequence between the " delimiters. The named source file is searched for in an implementation-defined manner. If this search is not supported, or if the search fails, the directive is reprocessed as if it read # include <h-char-sequence> new-line with the identical sequence…

大意：引号形式先在实现定义的若干地方找；找不到，就退回按尖括号形式再找一遍。而尖括号形式（同一节第 2 段）找的是 a sequence of implementation-defined places——标准刻意只说「由实现决定的一些地方」，它压根不规定 stdio.h 住在哪。

所以「-Iinclude 让 "greet.h" 找得到」这件事，是我们这台机器上的 gcc 这么规定的：-I 目录既进引号形式的搜索表，也进尖括号形式的搜索表（本机实测：加 -Iinclude 之后 #include <greet.h> 同样能找到）。换一个工具链，细节可能不同——标准把这块全部留给了实现。

出处：ISO/IEC 9899:2018（C17）§6.10.2 第 2、3 段。

工程惯例工程惯例：为什么本项目统一用引号加 `-Iinclude`

三种写法都合法：#include "greet.h"（头文件在 include/，靠 -Iinclude）、#include "../include/greet.h"（相对路径，能编过但丑陋）、#include <greet.h>（尖括号找私有头文件，能编过但语义混乱）。

本书统一用第一种：引号表示「这是我们自己工程的头文件」，尖括号表示「这是系统提供的头文件」。区分开的好处是：你在几千行代码里扫一眼就知道这一行是内部依赖还是外部依赖；而且换目录结构时，只需要改 -I 参数，不用改每一行 #include。

代价是每条编译命令都要带 -Iinclude。本机没有 make/cmake（见 build/TOOLCHAIN.md 的不可用表），所以这条参数只能写在命令里、或者写进 17.9 节那个 build.sh 里。

那一行是怎么来的

collect2.exe 是 gcc 在链接阶段临时叫起来的一个小工具——想知道它住在哪，直接问 gcc 就行：gcc -print-prog-name=collect2（本机实测它会打印出 C:/msys64/ucrt64/bin/../lib/gcc/<目标三元组>/<gcc 版本>/collect2.exe）。能确定的事实只有三层：

  1. gcc 把 -o app.exe 交给 collect2，collect2 再调 ld；
  2. 本机默认环境下，ld 自己那几行 undefined reference … / multiple definition … 没有出现在 stderr 上，只剩 collect2 的一句转述；
  3. ld 以非 0 状态退出，collect2 把退出码写成 collect2.exe: error: ld returned 5 exit status。

至于第 2 步为什么、ld 的诊断在这一层去了哪里，本书没有查到可复述的机制，也不把它写成结论。你能确定的是：这一行是 ld 的结论，不是它的理由；想看理由，换干净 PATH（第 1 单元的做法）或直接调 ld（下面的反例）。

想看到完整过程，有人会加 -v。本机实测：gcc -v -std=c17 … -o app.exe 会多打几百行（预处理器的头文件搜索表、as.exe 的调用、collect2.exe 的完整命令行——那行命令里能看见 crt2.o、crtbegin.o、-lmsvcrt 这些平时被 gcc 自动带上的东西），但最后一行还是那一句 collect2.exe: error: ld returned 5 exit status。-v 让你看见「gcc 替你做了什么」，看不见「ld 为什么不干」。

17.5 用 nm 把两类错误分开

先看「少定义」那一半。把 main.c 和 base.c 各自编成 .o，然后问 main.o：你还欠谁？

  • U helper_double —— 没有任何 .o 提供它。helper.c 里明明写着函数体，但它没被列进编译命令，所以那个 .o 根本不存在。这就是「少列一个源文件」的符号表长相。
  • U helper_base —— base.o 里有一行 T helper_base（上面最后一行就是），有人还。所以它不构成问题。
  • U printf —— 它住在 C 运行库（本机是 UCRT）里，由 gcc 链接时自动接上。这是运行库的，永远不用你管。

C 语言标准 6.10.1 节「Conditional inclusion」规定 #if / #ifdef / #ifndef / #elif / #else / #endif 的语义：被跳过的组里只有预处理记号会被扫过，其余一概不处理。

工程惯例工程惯例：guard 的名字怎么起

惯例是用文件名：greet.h → GREET_H，point.h → POINT_H。这样两个不同目录下同名的头文件会撞名——于是更稳的写法是加上项目或目录前缀，比如 MYLIB_GREET_H。

代价与取舍：guard 多三行，#pragma once 只一行；guard 是标准保证的、#pragma once 依赖编译器（本机 gcc 支持，但不是所有编译器都支持）；#pragma once 在「同一个文件通过不同路径被包含」（比如 include/x.h 与 ../include/x.h）时，某些实现会认不出来，guard 则永远正确。

本书统一写 guard，只有在你已经确认目标编译器支持时才建议 #pragma once。至于「哪个更快」——两者都在预处理阶段完成，本机实测编译时间没有可观测的差别，别把这个当理由。

标准原文标准原文：链接的三条规矩

C 语言标准 6.2.2 节「Linkages of identifiers」，三段话拼起来就是本节的规则：

（第 3 段）If the declaration of a file scope identifier for an object or a function contains the storage-class specifier static, the identifier has internal linkage.

（第 4 段）For an identifier declared with the storage-class specifier extern in a scope in which a prior declaration of that identifier is visible, if the prior declaration specifies internal or external linkage, the linkage of the identifier at the later declaration is the same as the linkage specified at the prior declaration. If no prior declaration is visible, or if the prior declaration specifies no linkage, then the identifier has external linkage.

（第 5 段）If the declaration of an identifier for a function has no storage-class specifier, its linkage is determined exactly as if it were declared with the storage-class specifier extern. If the declaration of an identifier for an object has file scope and no storage-class specifier, its linkage is external.

大意：static 在文件作用域 = 内部链接；extern = 外部链接（除非前面已经有一个内部链接的声明）；函数和文件作用域的变量，什么都不写也默认外部链接。

最后那句是本单元最容易记反的一条：int greet_banner(const char *who) 前面什么都没写，它照样是外部链接、照样能跨翻译单元调用。extern 不是「允许外部用」，它是「明确声明这是外部的」——对一个本来就有外部链接的函数，写不写 extern 都一样。

顺带记住一个更普遍的判断法：头文件里的每一行，你都要问一句「它被 5 个 .o 各念一遍，会有 5 份吗？」有 5 份会冲突 → 加 static 或改成声明。

inline 的取舍：本书只用 static inline

有人会想：既然头文件里放函数定义会撞名，那我加 inline 是不是就好了？C99 的 inline 确实有一套绕口的规则（inline 定义与外部定义两套模型，还要一个 .c 来「兜底」），但它解决的是另一件事（让编译器在多个翻译单元里各生成一份内联体，同时保证只有一份外部定义），不是给初学者用的。

本书的统一做法只有一句：

语法规则头文件里的函数：写 `static inline`

形式就是三个词连写：static inline int clamp(int x, int lo, int hi) { … }。

  • static 把它关在本编译单元里，所以不会撞名（17.7 节）；
  • inline 提示编译器「能在调用点展开就展开」——注意是提示，不是命令，编译器有权不听；
  • 返回类型与参数写全，和普通函数一模一样。

代价是：每个包含它的 .c 各有一份自己的副本——代码体积会变大，而且每个 .c 里那份的地址不同（所以不能拿它的地址做跨文件比较）。对小工具函数，这个代价可以忽略；对大函数，就别往头文件里放。

static inline 是 C99 起就有的写法，也是 C 标准库里大量函数的实现方式。C99 inline 的两个模型本书不展开——你只要记住：在头文件里写函数，加 static；想让它的调用没有额外开销，再多加一个 inline。

工程惯例工程惯例：模块划分的三条硬规矩

这三条都不是标准，是三十年攒下来的经验，但每一条都有可检查的后果：

  1. 一个模块 = 一对文件，名字一样（node.c / node.h）。后果：你在报错里看到文件名就知道该开哪个头文件。
  2. 依赖方向单一：a.c 包含 b.h 之后，b.c 里就不许出现 #include "a.h"。后果：一旦出现，你会在链接期得到一个「两边都欠对方」的结构——虽然 C 允许它编过（只要都是声明），但任何一处改动都会牵动两个模块，编译顺序、测试顺序全乱。
  3. 循环依赖用前向声明破：让「被依赖更多」的那一头只暴露指针。后果：node.h 不再需要 list.h，箭头上少了一条边。

代价要说清：前向声明换来的是你不能再直接访问成员，只能通过 node_value()、node_next() 这类函数。多写几个小函数是真的麻烦，但换来的是「Node 的内部布局只在一个文件里变」——这是本节所有例子里最值钱的一条。

工程惯例工程惯例：「头文件是合同」的三条推论

这句话不是一个比喻，它有三条可以直接落地的推论：

  • 改头文件 = 改所有包含它的编译单元：所以头文件要尽量稳定。把实现细节（私有的结构体、内部函数）留在 .c 里，头文件里只放别人真正要用的东西。
  • 头文件要自足：一个头文件被单独 #include 时应当能编过。node.h 如果用到 size_t 就得自己 #include <stddef.h>，不能指望「反正调用者会包含」。forward_decl/src/list.c 里那句 #include <stddef.h> 就是这件事的现场——它用 NULL，就自己把它带进来。
  • 头文件不能有副作用：不能在里面写 printf、不能分配内存、不能依赖「包含它的顺序」。它只描述形状。

代价：拆得越细，头文件越多，改一处牵连的面越大。所以「什么该进头文件」不是越多越好——只放合同，不放实现。

注自测题答案
  1. 出现在链接期：greet.c 不参与，就没有哪个 .o 提供 greet，而 main.o 里有一个 U greet。屏幕上是一行：collect2.exe: error: ld returned 5 exit status（本机实测），退出码 1。确认办法是 nm -u main.o 看到 U greet，再对整条命令行的每个 .o 跑 nm 找 T greet——一个都没有，就是缺它。
  2. 三类是声明、宏、类型定义。函数定义会产生机器码、要占一个符号；头文件被 5 个 .c 各包含一次，就有 5 份 T greet_banner，链接期报 multiple definition（本机同样只有一行 collect2）。而声明不产生目标码，念几遍都一样。
  3. 两个 .o 各有一个全局的 PI（nm 里是大写 R PI），链接期报重复定义——本机实测仍然只有一行 collect2.exe: error: ld returned 5 exit status。两种修法：① 头文件里写 static const double PI = 3.14;，每个编译单元各一份；② 头文件里写 extern const double PI;，在一个 .c 里写定义。加 static 之后符号从 R（global）变成 r（local），链接器不再看它，所以不撞了。
  4. 它让编译器知道「有一个叫 Node 的结构体类型」，不知道它有几个成员、占几个字节。指针的大小与所指对象的大小无关，所以声明 struct Node * 和以它为参数的函数都没问题；sizeof 要的正是「多大」这条缺失的信息，所以编不过（本机诊断：invalid application of 'sizeof' to incomplete type 'struct Node'）。同理 p->value 也编不过。
  5. 因为头文件的内容是在 -c 那一步被吃进 .o 的，链接器只认 .o 里的符号名，看不见头文件。改了头文件，任何包含它的 .o 都过期。判断范围用 gcc -MM -Iinclude src/xxx.c：输出里列出 include/logic.h 的那些 .c，对应的 .o 都要重编；io.c 的依赖里没有 logic.h（本机实测 io.o: src/io.c include/io.h），所以它不用动。
