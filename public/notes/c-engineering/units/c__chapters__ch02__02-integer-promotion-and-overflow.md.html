2.1 先看工程长什么样

上一单元把 examples/ch02/ 变成了一个例子一个小工程：每个例子一个目录，src/ 放源文件、include/ 放头文件。这一单元不新增目录类型——还是 src/ + include/——只是往里加例子，并且第一次加抓下来的会话文件与汇编产物。

第 1 帧是上一单元结束时的形态：一个例子一个目录，目录里是头文件、两个源文件、一个清单。第 2 帧是这一单元新增的内容：十二个例子目录（promotion_lab、mixed_sign、overflow_u0、overflow_check、int_min_trap、twos_complement、enum_demo、shift_guards、bitops、bitfield_pack、overflow_literal、overflow_loop），外加三个会话文件；为了不把帧撑得太高，每行的 + 只标在行首，那一行整行都是新的。第 3 帧拆开最小的那个例子：overflow_loop.h 里只有声明，overflow_loop.c 里是定义，main.c 只负责调用；同一个目录里可以放多个清单，还能放汇编产物（.s 不是编译输入，是拿来讲道理的证物）。

工程惯例工程惯例：为什么第二个项目起必须分文件

标准只要求一个程序有一个 main，分文件是本书的硬规定、也是主流做法：声明放头文件、定义放源文件，main.c 用 #include "overflow_u0.h" 把声明拿进来。好处是接缝可见——谁用哪个函数、参数长什么样，读头文件就够。

代价有两条：头文件一改，所有包含它的编译单元都得重编（本书一条 gcc 命令编完，就是整条重跑）；声明与定义对不上是编译错误（本机实测 error: conflicting types for 'f'），而「声明了却没有定义」才会拖到链接期（本机 ld 退出码 1）。

闸门把这条写成了判据：第 2 章起，清单的 sources 里 .c 少于两个、或者没有 .h 被 #include "…" 进来，就报 single_file_project_forbidden。

2.2 比 int 窄的整数，先变成 int

第一个反直觉的东西：把一个 unsigned char 取反，结果不是一个无符号数，而是一个负的 int。

四个数字要连起来读。第 10 行 ~uc 先把 uc（一个 8 位的 0）提成 int 的 0，再按 int 的 32 位取反，得到 11111111 11111111 11111111 11111111，也就是 -1；所以第 11 行 sizeof(~uc) 报的是 4——如果结果和 uc 一样宽，这里该是 1。第 12 行更能说明问题：uint8_t 最大值是 255，加 1 若按 8 位算就该回绕成 0，实测却是 256，因为这次加法在 int 里做。第 14 行的 sh == -1 是同一道理的另一面：short 的 -1 提成 int 的 -1，再比较。

大白话用大白话说「整数提升」

把整数想成一排大小不同的盒子：char、short 是小盒子，int 是大盒子。

  • C 在做算术之前，会先把小盒子里的值原样搬进 int 这个大盒子，再开始算；
  • 搬的过程不丢值（小盒子能装的，大盒子都装得下），但装进去之后就是 int 了——原来那个「无符号」的身份不再参与运算；
  • 所以 ~uc 是在 32 位里取反的，得到 -1；u8 + 1 是在 32 位里加的，得到 256。

严谨的说法：这叫整数提升（integer promotions），标准规定比 int 窄的类型先转成 int（装不下才转 unsigned int）。它是自动的、隐式的，你什么都没写，它就在那里。

标准原文标准原文：整数提升

6.3.1.1 节「Boolean, characters, and integers」：

If an int can represent all values of the original type (as restricted by the width, for a bit-field), the value is converted to an int; otherwise, it is converted to an unsigned int. These are called the integer promotions.

大意：只要 int 装得下原类型的全部取值（位域按它的位宽看），就转成 int，否则转成 unsigned int。注意括号里那半句：位域也要做提升，2.14 节会用到这个伏笔。

出处：ISO/IEC 9899:2018（C17）§6.3.1.1 第 2 段。

标准原文标准原文（续）：寻常算术转换

int 与 unsigned int 相遇时的规矩，在 6.3.1.8 节「Usual arithmetic conversions」：

… if the operand that has unsigned integer type has rank greater or equal to the rank of the type of the other operand, then the operand with signed integer type is converted to the type of the operand with unsigned integer type.

大意：无符号那个操作数的等级不低于有符号的那个时，有符号的被转成无符号——负号到这里就没了。这就是下一节 -1 > 0u 的全部原因。

出处：ISO/IEC 9899:2018（C17）§6.3.1.8 第 1 段。

后四行是另一件事——同一个数值用不同格式串打印：

第 8 行按 6.3.1.8 节先转再比：a 从 -1 转成 4294967295u，于是 4294967295 > 0 成立，打出来是 1。第 10 行的 a == (unsigned)a 同样是 1——它永远是真的，因为右边那个强转就是你亲手写出来的同一个转换。编译器会给你一条 -Wsign-compare 警告（见下面第一段会话），但它说的是「两个操作数符号不同」，读起来像噪音，很多人扫一眼就过去了。

格式这一处更糟：同一个值 4294967295u，%d 打出来是 -1，%u 打出来才是 4294967295。

格式串那一处，本书固定的 -Wall -Wextra -Wpedantic 抓不到——%d 与 unsigned int 在 gcc 眼里是「同宽的有符号 / 无符号」。要显式加上 -Wformat-signedness 再编一次，它才说话：

陷阱混合比较与格式串：警告有，但它救不了你的语义

你会看到什么：-1 > 0u 打印出 1；printf("%d", 4294967295u) 打印出 -1。比较那一处有 -Wsign-compare，格式那一处默认一句话都没有。

你会怎么误判：看到 comparison of integer expressions of different signedness 以为「编译器在唠叨风格问题」，加个 (unsigned) 强转就把它压掉了——可你压掉的正是这条警告想让你想一想的那个问题。

真相：-Wsign-compare 只告诉你「两边符号不同」，不告诉你「这次转换会不会改变结果」；-Wformat 只管宽度，符号要 -Wformat-signedness 才管。两处都得靠你读懂，不是靠编译器闭嘴。防法只有两条：有符号与无符号混在一个表达式里时，先问「负值会变成什么」；打印定宽类型时格式串去查表（%zu、%" PRIu32 "），别凭手感写 %d。

2.4 有符号溢出是未定义行为，无符号回绕是模运算

这两件事长得几乎一样，标准给它们的待遇却完全相反。先看标准怎么规定：

标准原文标准原文：有符号溢出

6.5 节「Expressions」第 5 段：

If an exceptional condition occurs during the evaluation of an expression (that is, if the result is not mathematically defined or not in the range of representable values for its type), the behavior is undefined.

大意：求值过程中出现了异常情况（数学上没有定义，或者结果超出这个类型的可表示范围），行为未定义。

出处：ISO/IEC 9899:2018（C17）§6.5 第 5 段。

标准原文标准原文（续）：什么叫「未定义行为」

3.4.3 节第 1 段：

behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements

大意：对于不可移植或错误的程序构造、或者错误的数据，标准不提任何要求——注意是「不提要求」，不是「规定它会崩」。这句话是本节所有「本机实测」的注脚：下面每一条退出码，都只是这台机器这一次的选择。

出处：ISO/IEC 9899:2018（C17）§3.4.3 第 1 段。

标准原文标准原文（续）：无符号永远不会溢出

6.2.5 节「Types」第 9 段：

A computation involving unsigned operands can never overflow, because a result that cannot be represented by the resulting unsigned integer type is reduced modulo the number that is one greater than the largest value that can be represented by the resulting type.

大意：无符号参与的计算永远不会溢出——装不下的结果按「模 2 的 N 次方」折回来（unsigned int 就是模 2³²）。这是有定义的行为，任何编译器都必须这么算。

出处：ISO/IEC 9899:2018（C17）§6.2.5 第 9 段。

现在看真跑出来的现象：

第 18 行传进去的是 INT_MAX，函数里做的是 n + 1：这是运行期的溢出（不是常量表达式），所以编译时一点警告都没有——这段程序编译退出码 0、stderr 一个字都没有。它打出来 -2147483648，也就是 INT_MIN。这件事不是标准保证的：标准说它是未定义行为，本机这次恰好给了「回绕」这个结果，换个编译器、换个优化等级可能完全不同（2.5 节就去看那个不同）。第 20 行的 0u - 1 则相反：标准保证它按模 2³² 折回来，任何机器上都是 4294967295。

第 19 行是本节埋的一个钉子：n + 1 < n 这种「溢出检查」，计算结果打出来是 0——即使传进去的正是 INT_MAX。它不是这次算错了，是这个检查从原理上就不可能成立：编译器按 6.5 第 5 段认定 n + 1 不会溢出，于是 n + 1 < n 永远为假。2.5 节会把它的汇编拿出来看。

实验记录本机实测：这一节的四个数字
  • 工具链：gcc 16.1.0，-std=c17（C17），目标三元组 x86_64-w64-mingw32，固定参数 -Wall -Wextra -Wpedantic -O0 -g；
  • 命令：gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -Iinclude src/main.c src/overflow_u0.c -o app（工作目录 examples/ch02/overflow_u0/）；
  • 结果：编译退出码 0、stderr 为空；INT_MAX + 1 打出 -2147483648，0u - 1 打出 4294967295，n + 1 < n 打出 0，退出码 0；
  • sizeof(int) = 4、sizeof(unsigned int) = 4，所以两者的模都是 2³²。

上面的输出由流水线逐字对账，对不上就报 stale_output；这一节的清单 id 是 ch02-overflow-u0。

工程惯例工程惯例：无符号回绕当成「别人给你的确定性」

标准对无符号的规定是确定性的（模 2^N），所以有两类写法在工程里被广泛接受：

  • 散列、校验和、CRC、随机数发生器：就是要它回绕，靠的是「模 2³²」这条保证；
  • 位掩码与协议字段：0xFFFFFFFFu 这类值是「位」而不是「数」，回绕是它的语义。

而依赖有符号溢出在工程里一律算 bug，哪怕某台机器上「看起来正常」。代价说清楚：写无符号算术时你得自己盯着「减法会不会把小的减成大的」——那类 bug 编译器不会提醒你。

为什么标准要把有符号溢出的行为「留空」

这不是标准偷懒，是一笔交换。把有符号溢出的行为空着，编译器才敢做下面这些推理：

  • i + 1 > i 恒成立——于是循环要跑多少次可以提前算出来，数组边界检查能消除掉，归纳变量的乘法能换成加法。这类推理（归纳变量分析）是循环优化的主力；
  • a + b 不会回绕——于是「这两条分支加起来覆盖了所有情况」这句话可以放心拿去化简。

如果反过来把回绕规定成「必须发生」（也就是 -fwrapv 那种语义），上面两条推理立刻作废，编译器就得为每个有符号加法准备「万一回绕了怎么办」——这正是 2.6 节说 -fwrapv「要放弃一部分优化」的原因。

标准的选择是把正确性的责任交给写代码的人、把优化空间留给编译器。所以工程上的主流态度是「不制造溢出」，而不是「依赖溢出时会怎么样」。

编译器视角编译器视角：`-Waggressive-loop-optimizations` 是它递给你的线索

那句 warning: iteration 2 invokes undefined behavior [-Waggressive-loop-optimizations] 只在 -O2 下出现，-O0 下一个字都没有。警告名字本身就是提示：编译器在循环优化时发现「这里会踩到未定义行为」，顺手告诉你一句。

它的用法不是「照着改」，而是当作气味：看到它，就回去问「我是不是在依赖某个会溢出的运算？」反过来不成立——examples/ch02/overflow_u0 的编译 stderr 是空的，而它的第 18 行在运行期真的溢出了。没警告 ≠ 没 UB。

编译器的三种自由

「未定义行为」经常被读成「结果随机」或者「会崩」，其实它的含义更狠。标准说完「不提任何要求」之后，实际发生的事可以分成三档，下面每一档都有本机的真凭据：

  1. 假设它不发生。overflow_u0_report 里那次 INT_MAX + 1，在 -O2 下 gcc 直接把结果算成常量塞进调用参数：movl $-2147483648, %edx。它没有「算一遍看看」，而是认定这个加法就是 INT_MAX + 1 的数学结果。
  1. 删掉分支。2.4 节那个 n + 1 < n 的「溢出检查」，-O2 下编译出来是这样：

if (n + 1 < n) return 1; 整行没了，只剩 xorl %eax, %eax（把 0 放进返回值）。你写的检查代码不在程序里了——不是因为编译器坏，而是因为你已经说了「这里不会溢出」。

  1. 任意行为，包括「看起来很正常」。这是最容易骗人的一档：同一个 overflow_u0 在 -O0 下打印 -2147483648、退出码 0，看上去完全正常；它之所以正常，只是这一次这条编译路径恰好用「回绕」实现了加法。同一份源码换成 -O2，它还是打印 -2147483648（我把两档的 stdout 抓下来用 cmp 比过，逐字相同）——「看起来正常」并不意味着你的程序是对的。真正翻脸的是 overflow_loop.c 那种「结果依赖溢出」的代码：-O2 直接给你 ud2。

三档里最危险的是第 3 档：前两档至少能看出代码被改了，第 3 档会给你一个能通过测试的结果。「它在我的机器上是对的」这句话，在未定义行为面前不算证据。这也是本书每讲一处未定义行为就要贴一次真实退出码的原因——现象比断言可靠。

这一节的清单用的是检测模式 opt-diff：闸门按 build/toolchain.json 里声明的两档（-O0 与 -O2）各编译一次、各跑一次，然后比较。清单里写的是 "expect": { "differs": "exit" }——只认「退出码不同」这一种差异。实测两档退出码分别是 0 与 3221225501，differs 成立，所以这条清单算「检测到」。这也是 opt-diff 的边界：它能证明「这里存在与优化相关的未定义行为」，不能告诉你那是溢出、还是别的什么 UB。

2.6 -ftrapv 与 -fwrapv：两种把它钉住的办法

工程惯例工程惯例：这两个开关的取舍

两个开关都不是标准的一部分，是 gcc 的实现选项。-fwrapv 把回绕变成有定义的行为，代价是放弃一部分优化（编译器不能再用「这里不可能溢出」去化简）；-ftrapv 让溢出当场终止，代价是每个有符号运算都多一条检查，而且它只抓有符号整数——无符号回绕、浮点都不算。

两种都不是「修好了」：真正的修法是不写会溢出的运算（2.13 节给三种写法）。顺带一句：本书没有 -fsanitize=undefined 可用——本机 -fsanitize=address,undefined 是链接直接失败（记录在 build/TOOLCHAIN.md §4.1），所以 -ftrapv 是替代品，不是等价品。

2.7 补码：-1 的位模式，与 INT_MIN 这个死角

上面那些「回绕成 -2147483648」的说法，背后是同一件事：这台机器上的有符号整数用补码表示。

第 1 帧对上输出的第 3 行：-1 的 32 位全是 1。第 2 帧对上第 5 行：INT_MIN 是 10000000 …——最高位是 1、其余全 0，它没有对应的正数。第 3 帧是同一串位换个读法：四个 FF 按 unsigned int 读就是 4294967295。位是位，「读成几」是你（或者类型）选的。

大白话用大白话说补码

想一个只有 4 位的玩具钟，刻度是 0000 到 1111（0 到 15）。补码的规矩是：

  • 最高位当负号用：最高位是 0，值就是剩下的位读出来的数；最高位是 1，值等于「剩下的位读出来的数 − 2³」（4 位是 −8，32 位就是 −2³¹）；
  • 于是 1111 读成 −1，1000 读成 −8（32 位就是 −2147483648）；
  • 加法的机器指令不用管正负：1111 加 0001 得到 0000（进位被丢掉），读出来是 0——−1 + 1 = 0，对上了。

所以「取反加一 = 取负」在这个表示里自然成立，代价是正负数的个数不对称：32 位里有一个值（10000000 …）没有正数伙伴，它取负还是它自己。这就是 INT_MIN 所有麻烦的源头。

标准原文标准原文：标准允许三种表示

6.2.6.2 节「Integer types」第 2 段：

If the sign bit is one, the value shall be modified in one of the following ways: — the corresponding value with sign bit 0 is negated (sign and magnitude); — the sign bit has the value −(2^M) (two's complement); — the sign bit has the value −(2^M − 1) (ones' complement).

大意：符号位为 1 时，值必须是这三种之一——符号与绝对值、补码（1000 是 −8）、反码（1000 是 −7）。本机走的是补码：-1 是全 1、INT_MIN 是 1000…。

出处：ISO/IEC 9899:2018（C17）§6.2.6.2 第 2 段。

标准原文标准原文（续）：所以「位模式」只是本机事实

这一节所有位模式结论都是本机事实（gcc 16.1.0、目标 x86_64-w64-mingw32），不是语言定律。2023 年那一版 C 标准把补码定为唯一的表示，但你要读的代码库里还有大量按本书这一版标准（C17）写的代码。

要用位运算处理有符号数时，先把它转成无符号再做——(uint32_t)value 就是这个意思。转过去只改「怎么读」，不改位。

2.8 INT_MIN 上的三个坑

INT_MIN 是那个「没有正数伙伴」的值，于是三件再自然不过的事全都出问题：取负、取绝对值、除以 −1。三件都是未定义行为——这一点 2.4 节的 6.5 第 5 段已经定死了：结果不在可表示范围里，就是 UB。

输出前六行是「取负 / 取绝对值」这条线：-INT_MIN、abs(INT_MIN)、自己写的 n < 0 ? -n : n，三个打出来都是 -2147483648；换成 long long 那一行才是它的绝对值 2147483648（那个函数在文件末尾，三行）。

这些数是未定义行为在本机的一次表现，不是结果保证。 abs 那一族（abs/labs/llabs）在结果无法表示时同样是未定义行为（7.22.6.1 节）；abs 的内部实现就是「负数取负」，所以它在 INT_MIN 上与你自己写的那行一样无能为力。要算绝对值，先把类型变宽（long long）或者改用 unsigned，别指望 abs 帮你兜住。

后三行是除法与取模的符号规矩：结果一律向零截断（-7 / 2 是 -3 而不是 -4），余数的符号跟着被除数走（-7 % 2 是 -1，7 % -2 是 1）。这条规矩从 C99 起就是标准写死的，不是你机器的脾气。

INT_MIN / -1 与 INT_MIN % -1 则在标准里明确是未定义行为：商 2147483648 放不进 int。程序里那条路径长这样（清单给它传一个命令行参数就走到那里）：

2.9 除法与取模的符号规矩

标准原文标准原文：`/` 与 `%`

6.5.5 节第 5 段：

The result of the / operator is the quotient from the division of the first operand by the second; the result of the % operator is the remainder. In both operations, if the value of the second operand is zero, the behavior is undefined.

大意：/ 给商、% 给余数；除数为 0 是未定义行为。

出处：ISO/IEC 9899:2018（C17）§6.5.5 第 5 段。

标准原文标准原文（续）：余数必须让等式成立

6.5.5 节第 6 段：

When integers are divided, the result of the / operator is the algebraic quotient with any fractional part discarded. … If the quotient a/b is representable, the expression (a/b)*b + a%b shall equal a; otherwise, the behavior of both a/b and a%b is undefined.

大意：整数除法把小数部分丢掉（不是往小里取整）；只要商能表示，就必须满足 (a/b)*b + a%b == a——这条式子决定了余数的符号。

出处：ISO/IEC 9899:2018（C17）§6.5.5 第 6 段。

「余数永远让 (a/b)*b + a%b == a 成立」是最好用的记忆锚：-7 / 2 = -3，那么 % 必须给出 -1，因为 -3 * 2 + (-1) = -7。

回到 2.8 那个输出块的最后三行，逐个核对：-7 / 2 = -3、7 / -2 = -3（两个都是向零截断），-7 % 2 = -1、7 % -2 = 1（余数跟着被除数），-7 / -2 = 3、-7 % -2 = -1。注意 % 的结果可以是负数——如果你用 x % 2 == 1 判断奇偶，-7 % 2 是 -1，判断就失败。修法有两种：用位运算 x & 1（对补码机器成立），或者 ((x % 2) + 2) % 2 把结果折回非负区间。

陷阱除零不是「会崩」，是「标准什么都没说」

你会看到什么：5 / 0 在本机的退出码是 3221225620，stdout 只有崩溃前 flush 出去的那一行。看起来像「除零会崩」，很自然。

你会怎么误判：于是你觉得「反正会崩，我一眼就能看出来」。真正坑你的是编译期能算出来的那一种：int x = 1 / 0; 会让 gcc 直接给警告（[-Wdiv-by-zero]），但 a / b 里 b 是变量时它一个字都不说。

真相：除零是未定义行为，和溢出同一档——「崩掉」只是本机这次的表现。编译器有权假设除数为 0 的代码不存在，从而把「b == 0 的分支」删掉。所以判断「除数会不会是 0」必须在你自己写的代码里做（而且要在除法之前做），不能指望机器报错。

标准原文标准原文：移位量与宽度

6.5.7 节「Bitwise shift operators」第 3 段：

The integer promotions are performed on each of the operands. … If the value of the right operand is negative or is greater than or equal to the width of the promoted left operand, the behavior is undefined.

大意：两个操作数都先做整数提升（2.2 节那条规矩在这里也生效）；右操作数为负、或者不小于提升后左操作数的宽度，行为未定义。

标准原文标准原文（续）：左移的边界

6.5.7 节第 4 段：

大意：左移时若左操作数有符号且非负、乘完还放得下，结果就是那个值；否则未定义——负的左操作数、或者结果放不下，都落进「否则」。

陷阱断言放在头文件里，是「接口的守卫」

shift_left_guarded 把 assert 写在函数体第一行，这不是装饰：

  • 它守的是调用方——任何人在任何地方调它，参数越界就当场止住，不会悄悄算出错误的结果；
  • 代价是运行期开销（一次比较 + 一次分支），可以用 -DNDEBUG 整体关掉（assert 在定义了这个宏之后什么都不做）——但那时守卫就没了，所以关它之前先确认测试跑过了；
  • 本机的 assert 失败会终止进程并打印 Assertion ... failed.（这与 2.6 节 -ftrapv 的终止是两回事：一个是你自己写的检查，一个是编译器插的检查）。

2.11 位运算与逻辑运算：一个字符的差别

& 与 &&、| 与 ||、~ 与 ! 是六件事，不是三件。先看三个掩码函数和打印二进制：

掩码三件套值得背下来，因为它们是位运算的全部基础：

  • 置位：flags | (1u << n)——1u << n 是只有第 n 位是 1 的掩码，按位或把它塞进去；
  • 清位：flags & ~(1u << n)——先把掩码取反（除了第 n 位全是 1），再按位与，第 n 位被抹掉；
  • 查位：(flags >> n) & 1u——挪到最低位再取那一位，结果是 0 或 1。

1u 里那个 u 不是装饰：1u << 31 合法（无符号左移），而 1 << 31 在 32 位机器上会溢出 int（2.10 节第一条红线）。写掩码时一律用 1u，这是本书的纪律。

再看 & / && 的差别（输出最后四行）：a = 4、b = 0 时，a & b 是 0（按位与，两个位都为 1 才是 1），a && b 也是 0，但含义完全不同——&& 是「两个条件都成立吗」，结果只有 0 或 1，而且有短路求值（左边为假时右边根本不求值）。a | b = 4、a || b = 1 同理：按位或保留所有 1 位，逻辑或只回答真假。!a = 0（逻辑非）、~a = -5（按位取反）、~0u = 4294967295，也是同一对。

为什么掩码要用定宽类型写

上面三个函数的参数是 uint32_t 而不是 unsigned int，这不是啰嗦：

  • uint32_t 来自 <stdint.h>，32 位就是 32 位，换平台也一样；unsigned int 在别的平台上可能是 16 位或 64 位，那时「第 31 位」这句话本身就不成立了；
  • 打印它要用 <inttypes.h> 里的宏："0x%08" PRIx32（小写十六进制）或 PRIX32（大写）。别写 %x——类型一换平台，格式串就可能对不上，而这类错误在运行期才现形；
  • 反过来，uint8_t 这种窄类型参与运算时先提升为 int（2.2 节那条规矩在这里同样生效）：uint8_t a = 200, b = 200; 时 a + b 是 int 的 400，不会按 8 位回绕成 144。想真的按 8 位回绕，得显式写 (uint8_t)(a + b)。

一句话：宽度写在类型里，格式写在宏里。这两条合起来，位运算代码才能跨平台。

陷阱`if (a & b == 0)` —— 优先级把意思改掉了

你会看到什么：位运算的优先级低于比较。a & b == 0 被解析成 a & (b == 0)：先算 b == 0 得到一个 0 或 1，再和 a 按位与。输出的最后两行就是证据：bug(4, 0) 给出 0，正确答案是 1；而 bug(5, 0) 给出 1，碰巧对了。

你会怎么误判：这个 bug 最坑的地方不是永远错，而是有些输入碰巧对。a = 5, b = 0 时它看起来完全正常，于是你以为掩码写对了，只在某次上线后才发现判断反了。

真相：错的是优先级，不是掩码。gcc 的 -Wparentheses 会提醒你（下面会话第 3 行），读懂它：suggest parentheses around comparison in operand of '&'。同类陷阱还有：~ 的优先级高于 *、+，但 << 低于 +——1u << n + 1 是 1u << (n + 1)。位运算表达式里，该加括号就加括号。

  2. 枚举常量默认从 0 开始逐个加一：CONN_IDLE=0、CONN_OPEN=1、CONN_BUSY=2、CONN_CLOSED=3；也可以自己指定，但别依赖具体数字，代码里一律用名字；
  3. 枚举变量的本质是「某个整数类型」：sizeof(enum conn_state) = 4，enum conn_state st = 2; 能编译能跑（标准允许把 int 赋给枚举，不做检查），short_name[st] 直接当数组下标。但它不一定就是 int：输出最后一行是本机实测，与 int 兼容 = 0，与 unsigned int 兼容 = 1——这台机器给它挑的是 unsigned int（因为所有取值都非负）。加上一个负的枚举常量（比如 = -1）它才会变成 int。这也是为什么第 3 点要写成「某个整数类型」而不是「int」；
  4. switch 是枚举的天配：每个 case 写一个名字，default 兜底；case 里直接 return，所以不需要 break。
标准原文标准原文：枚举常量是 `int`

6.7.2.2 节「Enumeration specifiers」第 3 段：

The identifiers in an enumerator list are declared as constants that have type int and may appear wherever such are permitted.

大意：枚举列表里的每个名字，首先是类型为 int 的常量，凡是 int 常量能出现的地方它都能出现。所以 CONN_BUSY + 1 能算，按 int 的规矩算。

出处：ISO/IEC 9899:2018（C17）§6.7.2.2 第 3 段。

标准原文标准原文（续）：枚举类型由实现挑

6.7.2.2 节第 4 段：

Each enumerated type shall be compatible with char, a signed integer type, or an unsigned integer type. The choice of type is implementation-defined…

大意：枚举类型要与 char、某一个有符号整数类型、或某一个无符号整数类型兼容——选哪个由实现决定（本机选了 unsigned int，正如上面输出最后一行）。所以「枚举是有名字的整数」这句话对，但把 enum conn_state 断言成 int 就过度了。

工程惯例工程惯例：什么时候用 `enum`，什么时候用一组 `#define`

标准只规定「枚举是一种整数类型」，怎么用是工程问题。主流的取舍：

  • 用 enum：取值是一组有限的、有名字的状态（连接状态、日志级别、错误分类）。好处是类型名 + 一组名字一起出现在头文件里，switch 能一次列全，调试器里还能看到名字；
  • 用 #define / 常量：值是位掩码（FLAG_READ=1u << 0 那种，可以按位或起来）。enum 的各个取值是互斥的整数，而位掩码需要「组合」，两者语义不一样——本书的 bitops 例子用的就是 #define；
  • 代价：C 的 enum 不做类型检查（enum conn_state st = 99; 编译器不拦），而且底层类型由实现挑（这台是 unsigned int）。所以「枚举变量只能取合法值」要靠你在接口上守，跨模块传枚举时也别假设它一定是 int。

三种写法思路不同，结果一致（输出四行的三列都对得上）：

  • 运算前比较：在加法之前用减法判断「这一加会不会越界」，分正负两条。这两步减法本身不会溢出——b > 0 时 INT_MAX - b 落在 [INT_MAX - INT_MAX, INT_MAX - 1]，b < 0 时 INT_MIN - b 落在 [INT_MIN + 1, INT_MIN + INT_MAX]，两个区间都在 int 范围内，所以这个检查是自洽的；
  • 更宽的类型：把两个 int 提成 long long 再相加，看结果还在不在 int 范围里。本机 long 和 int 都是 32 位（LONG_MAX 也是 2147483647），所以不能用 long 偷懒——必须 long long。这一条最不容易写错，代价是多一次转换；
  • 编译器内建：__builtin_add_overflow(a, b, &out) 溢出时返回真，没溢出就把结果写进 out、返回假。它是 gcc/clang 的扩展（不是标准 C），优点是一条语句、不会写错；代价是它不跨编译器（换 MSVC 就得另写）。

2.14 位域：能省几个字节，代价是「不可移植」

位域（bit-field）让你在结构体里按位分配成员：

三个 sizeof 排在一起看，位域的脾气就清楚了：struct pack_bits（三个 1 位）是 4 字节，struct pack_nibbles（两个 4 位）也是 4 字节，而 struct pack_bytes（用 unsigned char 当分配单位）是 1 字节。「三个 1 位的成员」并没有让它变成 1 个字节——前两个结构体的分配单位是 unsigned int，编译器按 4 字节为单位打包。想让位域真的省空间，得换分配单位（类型），不是减位宽。

取值部分：bits = { a=1, b=0, c=1 } 赋值正常；nib = { lo=0xA, hi=0x5 }；而给 4 位的 hi 赋 0x1F（31）之后拿到的是 0xF（15）——超出的高位被丢掉，gcc 会给一条真实警告：

标准原文标准原文：位域的布局由实现决定

6.7.2.1 节「Structure and union specifiers」：

A bit-field is interpreted as having a signed or unsigned integer type consisting of the specified number of bits.

大意：位域是一个指定位数的整数（有符号或无符号由声明里的类型决定）。但标准没有规定「位域之间怎么排、怎么打包、分配单位是几个字节」——那些是实现定义的。

出处：ISO/IEC 9899:2018（C17）§6.7.2.1。

标准原文标准原文（续）：由此带来的三件事
  • 同一份 struct pack_bits，在这台机器上是 4 字节，换一个编译器可能是 1 字节或 8 字节；
  • 位域成员不能取地址（&p.a 非法，因为一个字节里塞了好几个成员），也不能直接 sizeof；
  • 位域参与运算前同样做整数提升（6.3.1.1 节那句「as restricted by the width, for a bit-field」）——所以 sizeof(bits.a + 0) 是 4。

还有一条：结构体的对齐与填充，标准同样只给宽松约束——第 5 章讲内存布局时会再回到这件事。

陷阱位域一用，可移植性就没了

你会看到什么：sizeof(struct pack_nibbles) 是 4。你可能顺手把它当成「两个半字节 = 1 字节」来写协议解析。

你会怎么误判：以为位域的字节数是「位数加起来除以 8」。真正决定字节数的是分配单位，而且打包方向（先放的成员占低位还是高位）也是实现定义的。

真相：要跟外部数据打交道（读文件、解网络包、对硬件寄存器），不要用位域——用 uint8_t 数组加移位与掩码（2.11 节那三件套）自己拼，位序由你写死，到处都一样。位域适合「内部用、不涉及字节序、只图代码好读」的标志集合。知道它不可移植，然后决定用不用——而不是不知道。

2.16 小结

小结这一节的要点
  • 提升与转换：比 int 窄的整数（含位域）先提升为 int——所以 ~(unsigned char)0 是 -1、(uint8_t)255 + 1 是 256；int 与 unsigned 相遇时 int 变成 unsigned——所以 -1 > 0u 为真（6.3.1.1 / 6.3.1.8）；
  • 溢出有两种命运：有符号溢出是未定义行为（6.5 第 5 段），无符号回绕是有定义的模 2^N（6.2.5 第 9 段）。未定义行为的真意是「编译器可以假设它不发生」：同一份循环 -O0 打印 -2147483648、-O2 变 ud2（3221225501）；-ftrapv 当场终止（3221226505、stdout 空），-fwrapv 让它回绕；
  • INT_MIN 是死角，三个坑都是 UB：-INT_MIN、abs(INT_MIN)（7.22.6.1）、INT_MIN / -1 与 % -1（实测 3221225621），除零是 3221225620——都是现象，不是保证。掩码用 1u << n、a & b == 0 要加括号；枚举类型由实现挑（本机 unsigned int）；位域碰外部数据别用。

自测题自测题（先自己答，再对答案）
  1. ~(unsigned char)0 是多少？sizeof 是多少？为什么两件事同时成立？
  2. int a = -1; unsigned int b = 0; 时 a > b 是真还是假？比较与格式两处各有什么警告？
  3. 2.5 的循环在 -O2 下为什么变成 ud2？bash 的 132 与闸门的 3221225501 是什么关系？
  4. -INT_MIN、abs(INT_MIN)、INT_MIN / -1 各属于哪种行为？abs 为什么救不了？
  5. -ftrapv 与 -fwrapv 各做什么、代价是什么？怎么证明是它在起作用？
注自测题答案
  1. 结果是 -1，sizeof 是 4。因为 unsigned char 参与运算前先被整数提升成 int，取反在 32 位的 int 上做（8 位全 0 取反在 8 位里才是 255）。
  2. a > b 为真（1）：a 被转成 unsigned int，-1 变成 4294967295。编译器给 -Wsign-compare（comparison of integer expressions of different signedness）。printf("%d", 4294967295u) 默认不报——要加 -Wformat-signedness 才出现 format '%d' expects argument of type 'int', but argument 2 has type 'unsigned int'；打出来的 -1 是错的，没人告诉你。
  3. 循环只能靠有符号溢出停下，而这是未定义行为：gcc 于是假设 i 不会溢出、i > 0 恒成立，那条路「不需要有结果」，于是把整个函数体换成 ud2（非法指令）。bash 的 132 是 128 + 4（信号 4 = SIGILL），闸门的 3221225501 是同一事件在 Windows 上的异常码 0xC000001D——同一个现象，两种口径。
注自测题答案（续）
  1. 三个都是未定义行为：-INT_MIN 与 INT_MIN / -1（还有 % -1）是有符号溢出（6.5 第 5 段）；abs(INT_MIN) 是运行库在结果不可表示时的 UB（7.22.6.1），它的实现就是「负数取负」，所以和自己写的那行一样失效。本机三者都得到 -2147483648，那是现象；要真正算绝对值，先换 long long（实测得 2147483648）。
  2. -ftrapv：有符号溢出时终止进程（实测 3221226505，stdout 因为没 flush 是空的），代价是每个有符号运算多一条检查、变慢，且只抓有符号整数；-fwrapv：把溢出定义成回绕（实测 -O2 -fwrapv 退出 0、打印 i = -2147483648），代价是放弃一部分优化。证明靠阴性对照：同一份源码去掉开关再跑，清单声明的证据（非零退出码、stderr 那段文字）必须在对照里不出现；闸门会自动复算这一步。
