15.1 先看工程长什么样

学标准库最容易走偏的方式，是把函数当条目背（strlen 数长度、strcpy 拷贝……）。这一节我们照老规矩来：先看文件。原因很实际——这一章里所有的坑，都出在「函数只看得到自己那一个参数」这件事上，而这件事只有把内存里的字节和真实的运行结果摆在一起才讲得清。

标准对「一个程序分几个文件」没有任何要求。本书从第二个项目起给每个例子配 src/ + include/ 的最小工程，理由是每条结论都要能被单独验证：strncpy_trap 只演示「不补 \0」这一件事，它出问题时你立刻知道是哪里错了；如果十四个结论挤在一个 main.c 里，你只会看到一个混乱的输出。

代价是要多写几行样板：一个 .h 放声明、一个 .c 放定义、main.c 只负责组装与打印。另一个代价是两处声明要一致：.h 里的原型与 .c 里的定义如果类型对不上，编译期就报 conflicting types（不是链接期）；参数名字可以不同，名字不是类型的一部分。

C 语言标准（ISO/IEC 9899，C17）7.24.2.3 节「The strcpy function」：

The strcpy function copies the string pointed to by s2 (including the terminating null character) into the array pointed to by s1.

7.24.6.3 节「The strlen function」：

The strlen function returns the number of characters that precede the terminating null character.

大意：strcpy 把整条字符串连同结尾那个 \0 一起搬过去；strlen 数的是 \0 之前有多少个字符（那个 \0 自己不算）。两句话里都出现了 the terminating null character（结尾的空字符）——这就是它们的全部依据：没人问「目标有几个字节」。

出处：ISO/IEC 9899:2018（C17）§7.24.2.3 第 2 段（Description）、§7.24.6.3 第 3 段（Returns）。

大白话用大白话说这两句话

把内存想成一排信箱，每个信箱装一个字节。C 的字符串就是「从某个信箱开始，一直念到某个信箱里写着 0 为止」。

  • strlen 干的事是数信箱：从你指的起点开始数，数到那个写着 0 的信箱就停，那个信箱本身不算；
  • strcpy 干的事是抄信箱：从起点开始，一个信箱一个信箱地抄到目标那边去，连那个写着 0 的信箱也抄过去。

所以这两个函数都不知道自己走过了几个信箱——它们只认那个 0。目标那边有 8 个信箱还是 8 万个，它们根本看不见。

标准原文标准原文：`strncpy` 与 `strncat` 各自补不补 `\0`

C 语言标准（ISO/IEC 9899，C17）7.24.2.4 节「The strncpy function」：

The strncpy function copies not more than n characters (characters that follow a null character are not copied) from the array pointed to by s2 to the array pointed to by s1. If the array pointed to by s2 is a string that is shorter than n characters, null characters are appended to the copy in the array pointed to by s1, until n characters in all have been written.

大意：strncpy 最多拷 n 个字符（\0 之后的字符不拷）；只有当源串比 n 短时，才补 \0 直到凑满 n 个。反过来说：源串不短于 n 时，它一个 \0 都不会补——这正是上面那个 tail 被读到的原因。

同一标准 7.24.3.2 节「The strncat function」：

The strncat function appends not more than n characters (a null character and characters that follow it are not appended) from the array pointed to by s2 to the end of the string pointed to by s1. … A terminating null character is always appended to the result.

大意：strncat 最多接 n 个字符，并且总会补一个结尾。两个函数的 n 含义不同，\0 的待遇也不同——这就是为什么 strncat 的 n 是「最多接几个」，而结果的长度最多是「原来的长度 + n」。

出处：ISO/IEC 9899:2018（C17）§7.24.2.4 第 2 段、§7.24.3.2 第 2 段。

第 1 帧是结构体的布局：name 与 tail 之间没有空隙（本机实测 offsetof 是 8）。第 2 帧是 copy_unsafe 干的事：8 格全写成 a..h，一个 0 都没留。第 3 帧是 strlen 的视角：它不知道 name 只有 8 格，它只认 0，于是数出 15。

陷阱「`strncpy` 更安全」是最常见的一句误传

你会看到什么：你老老实实用 strncpy(dst, src, sizeof dst) 代替 strcpy，用本书的基础参数（-O0）编译，一个字都不报，程序多数时候也正常。

你会怎么误判：你以为「带了 n 就是安全版本」，于是把 strcpy 全换掉，心里松了一口气。

真相：n 只是写多少字节的上限，它跟「结果是不是一条合法字符串」是两件事。源串长度 ≥ n 时结果没有结尾，此时任何一个读字符串的函数都会越界读——strlen、printf("%s")、strcmp、strcat 全会。

编译器帮不上多少忙：本机的 -Wall 只在「源串写在眼前、长度定死」这种形状上给 -Wstringop-truncation；源串是个参数时它看不见长度。但它也不是完全不说话：同一份代码用 -O2 编译，即使源串是参数，-Wall 也会报 'strncpy' specified bound 8 equals destination size——警告的有无取决于优化等级，别把「-O0 下没警告」当成「没问题」。

正解：要「最多拷 n-1 个字节，然后自己补 0」（copy_safe 就是），或者干脆用 snprintf(dst, sizeof dst, "%s", src)——它保证结尾，还顺便给你「本来要写多少」这个数（15.6 节）。

为什么 15.3 节要绕一圈用结构体：因为单纯的局部数组 char name[8] 后面那格是什么，由编译器决定。本机实测（会话 session-layout.txt）：同一份危险写法，-O0 下三个变体分别读到 11、15、27（连同一份代码里换一个局部变量都会变），-O2 下三个全变成 14。这种数字不能当结论，只能当现象。

这段会话是本节最要紧的一段证据：同一份源码、同一个编译器，只是换个优化等级，越界读到的地方就从 11/15/27 变成 14/14/14。它说明的不是「-O0 更危险」，而是——这件事根本不由你定。这就是未定义行为的样子：不是「一定崩」，也不是「一定没事」，而是结果不在你的控制范围里。所以你在 strncpy 之后补上那一句 dst[n-1] = '\0'，不是「保险起见」，是把不确定变成确定。

strtok：它改你的原串，还把「读到哪」藏在自己肚子里

strtok 是 string.h 里唯一的「分段」函数：给一串文本和一个分隔符集合，它每次还你一段。它有两个性质，凑在一起就成了经典事故：

你会看到什么：isalpha(c) 传负 char，本机返回 0、程序正常跑完、编译零警告。你会觉得「那就是没问题呗」。

15.5 解析三兄弟与两个数字出口

解析就是「把一段文本里的数字、名字、分隔符拆出来」。标准库里干这件事的有两组工具：scanf 一家，和 strtol 一家。

scanf / fscanf / sscanf 的分工

函数 从哪读 什么时候用
scanf(fmt, ...) 标准输入 交互式小程序
fscanf(fp, fmt, ...) 你给的 FILE * 按格式读文件
sscanf(s, fmt, ...) 一个字符串 解析「已经在你手里的一行文本」——首选

三者的格式串与返回值规则完全一样，区别只在输入源。返回值是成功赋值的字段个数，这句话要逐字读：它数的是字段，不是字符。

  • 全部顺利：返回字段数（下面例子里是 2 或 3）；
  • 中途失败：返回已经成功的那几个（比如只读到 key，就返回 1）；
  • 一上来就失败（或碰到输入末尾）：返回 EOF（stdio.h 里的一个负整数常量）。

所以「读成功了吗」必须写成 if (sscanf(...) == 期望的字段数)——拿 != EOF 当成功判据是错的：返回 1 也不是 EOF，但那次解析只拿到了一半。

陷阱`atoi` 不会报错——而你以为它会

你会看到什么：atoi("999999999999") 给你 2147483647，atoi("abc") 给你 0，编译零警告、程序正常跑完。

你会怎么误判：你看见一个正常的整数，就认为「解析成功了」，于是把 atoi 用在一个解析「配置文件里的数字」的小工具里。等到有人往文件里写了一个脏值，你的程序不报错、不退出、继续拿着一串错的数字往下算——这是最难查的一类故障。

真相：标准里 atoi 的定义只有一句话——「除了出错时的行为，等价于 (int)strtol(nptr, NULL, 10)」（7.22.1.2 节）。NULL 就是关键：它连 endptr 都不要，所以「读到哪停的」这件事在 atoi 里被丢掉了；而 int 这个返回类型也装不下「错误」这个额外状态。

正解：要解析数字就写一个像 parse_with_strtol 这样的小函数，把 endptr 与 errno 都检查一遍，返回值用「返回码」而不是「数字」。代价是调用点变长几行；收益是脏数据会在第一次遇到时就现形。

15.6 snprintf：n 是缓冲区总长，返回值是「本来要写多少」

snprintf 是 C 库里最容易被误解的一个函数，因为两个数字的含义都不是直觉上的那个：

  • 参数 n = 缓冲区一共有多少个字节（含结尾的 \0），不是「可以写的字符数」；
  • 返回值 = 假如地方够大，本来会写多少个字符（不含结尾的 \0），不是实际写了几个。

measure_line 用的是 snprintf 的一个标准技巧：缓冲区传 NULL、长度传 0，它什么都不写，只把长度算给你。有了这个数，你就能一次分配出大小刚好的内存，不用先猜一个「应该够大」的数。

  • n = 22：item-42-very-long-tail 是 22 个字符。这个数和缓冲区多大完全无关——换成 32 字节的缓冲区，返回值还是 22（倒数第三行）；
  • 缓冲区里是 item-42（7 个字符），第 8 格是 00：snprintf 把 7 个字符写完，在第 8 格（下标 7）放了结尾 \0，然后停手。sizeof 是 8、strlen 是 7，这两个数在 15.2 节已经分过了；
  • 要装得下，缓冲区至少要有 23 个字节：n + 1。判据照着标准那句话写（返回非负且小于 n），所以代码里是 if (n < 0 || n >= (int)sizeof buf) { /* 被截断了，或者出错了 */ }——少了 n < 0 那一半，编码错误时会被误判成「完整」。

… the snprintf function returns the number of characters that would have been written had n been sufficiently large, not counting the terminating null character, or a negative value if an encoding error occurred. Thus, the null-terminated output has been completely written if and only if the returned value is nonnegative and less than n.

大意：返回值是「假设 n 足够大，本来会写多少个字符」（不数结尾的 \0）；只有当返回非负、并且小于 n 时，输出才被完整写下——这句话就是「截断判据」的出处。

你会看到什么：return x->score - y->score; 在小数据上完全正常，排序结果跟 (a > b) - (a < b) 一模一样。

你会怎么误判：你看到它跑得对，就默认两种写法等价，从此一直用减法。

真相：两个 int 相减的结果可能超出 int 能表示的范围。本机 INT_MAX 是 2147483647、INT_MIN 是 -2147483648（实测：sizeof(int) 与 sizeof(long) 都是 4），两者的数学差是 4294967295——这个值在本机连 long 都装不下（long 也只有 4 字节），而在 int 里直接就溢出了，有符号整数溢出是未定义行为。于是排序算法拿着一个随机的符号继续砍区间，可能排出一个没排好的数组，也可能崩。

正解：永远用「比两次再相减」的写法（(a > b) - (a < b)），或者用显式的 if 分支。代价是多写几个字符；收益是这个比较器对任何输入都成立。strcmp 自己就是这么实现的——它也只保证符号。

标准原文标准原文：比较器的约定与「平局的顺序」

C 语言标准（ISO/IEC 9899，C17）7.22.5 节「Searching and sorting utilities」：

The function shall return an integer less than, equal to, or greater than zero if the first argument is considered to be respectively less than, equal to, or greater than the second. If two elements compare as equal, their order in the resulting sorted array is unspecified.

大意：比较器只看符号（小于 / 等于 / 大于）；而且两个「相等」的元素，排完之后谁在前面是不指定的——qsort 不保证稳定。所以平局要自己定规则：本节 csv_tool 里的比较器在分数相同时会再按名字比一次（15.10 节会看到 sun 与 zhao 同为 95 分时的处理）。

出处：ISO/IEC 9899:2018（C17）§7.22.5.2 第 4、5 段（qsort；bsearch 在 §7.22.5.1）。

15.8 数学、随机与时间：三个常用头

<math.h>：参数与返回值都是 double

几处要留意的：

  • floor / ceil / round 作用在负数上：floor(-1.5) = -2.0（往下）、ceil(-1.5) = -1.0（往上）、round(-2.5) = -3.0（往远离 0 的那边，不是「四舍五入到 -2」）；
  • 0.1 + 0.2 == 0.3 是 0：浮点数不能用 == 比相等，要用「差值小于一个容忍值」，也就是 fabs(a - b) < eps（第 10 行给出 1）；
  • 开负数得到 NaN：本机打印出来是 -nan(ind)（这个写法是这台机器的库的写法，别的地方可能印 nan）。更要记住的是 sqrt(-1.0) == sqrt(-1.0) 是 0——NaN 连它自己都不等于，所以判 NaN 要写 x != x；
  • sizeof(sqrt(2.0)) 是 8：数学函数的参数与返回值都是 double。写成 sqrt(2) 也行（2 会被转成 2.0），但把结果往 int 里塞会截断（sqrt(2) 塞进 int 就是 1）。
实验记录本机实测：链接数学函数不需要 `-lm`
  • 工具链：gcc 16.1.0（-std=c17，即 C17），目标三元组 x86_64-w64-mingw32；

<stdlib.h> 的 rand / srand：伪随机、可复现、有偏斜

rand() 产生的是伪随机数：它内部有一个状态，每次调用按固定公式推进一步。所以同一个种子（srand 的实参）在同一个实现上必然给出同一串数——这是特性，不是缺陷：调试的时候你正需要它。（标准只规定 rand 返回 0..RAND_MAX 之间的伪随机数、srand 设种子，没有规定用哪个公式；本机这串 41 18467 … 是 UCRT 的序列，换一个库就换一串。）

  • 第一行 RAND_MAX = 32767：本机 rand() 只会给出 0..32767 之间的数（标准只要求 RAND_MAX 至少 32767）；
  • rand() % 6 抽一万次：六个桶分别是 1661 / 1658 / 1710 / 1640 / 1679 / 1652，都在 1666 附近晃——这就是 % 6 的日常样子，看不出问题；
  • rand() % 100 抽一万次：最少的桶 80 次、最多的 136 次。这是个陷阱式的读数：波动看着大，但它主要是抽样波动（一万次、每桶期望 100，标准差约 10）；
  • 真正的病在 rand() % 30000 那一行：结果里小于 2768 的占了 1710 次，而「公平」应该只有 922 次。这不是波动，是结构性偏斜：2768 = 32768 - 30000，于是 0..2767 这些结果可以被两条不同的 rand() 值撞出来（比如 0 与 30000 都是 % 30000 == 0），别的结果只能被一条撞出来。% n 的偏斜大小取决于 n 与 RAND_MAX + 1 的差，n 越接近 RAND_MAX + 1，偏斜越狠；
  • 最后三行是可复现性：srand(1) 两次给出的前 5 个数一模一样（41 18467 6334 26500 19169），换成 srand(2) 就完全不同（45 29216 24198 17795 29484）。

怎么避开偏斜：不要用 % n，用「超出范围的采样丢掉重来」（拒绝采样）——先算出「RAND_MAX + 1 里能整除 n 的最大区间」，落在区间外的丢掉再抽一次。代价是循环次数不定；收益是每个结果真的等概率。另外两条工程常识：rand() 的质量不适合做密码学用途**（要随机数和安全有关，用平台提供的专门接口），rand() 也不保证线程安全。

<time.h>：time 是墙上时间，clock 是处理器时间

两者差一个字，用途完全不同：

  • time(NULL) 给你 time_t——本机这个数是从 1970-01-01 起过的秒数（Unix epoch）。这是实现事实，不是标准保证：标准只说「编码未指定」（7.27.2.4 节）。它每次运行都不一样，所以它只能用来记录「什么时候发生的」；
  • clock() 给你 clock_t：进程用掉的处理器时间，单位是 CLOCKS_PER_SEC 分之一个「时钟」。它适合测一段代码花了多久。

工程惯例工程惯例：ISO C 与 POSIX 的分界

标准库分两层，混起来用就会遇到「在我机器上能编，在别人机器上不行」：

  • ISO C（标准规定，本书用的就是它）：<string.h>、<stdlib.h>、<stdio.h>、<ctype.h>、<math.h>、<time.h>…换编译器、换操作系统都在；
  • POSIX（操作系统给的扩展，不是 C 标准的一部分）：strdup、strcasecmp、getline、strtok_r、fileno…在 Linux/macOS 上默认就能用，在 Windows 的 MSVC 上直接找不到。

三组最典型的例子：

  • strdup(s)：帮你 malloc 一块内存并把 s 拷进去。ISO C 里没有它，C 的正统写法是「malloc(strlen(s) + 1) + memcpy」，或者就用 snprintf（15.6 节）避开这层手工活；
  • strcasecmp(a, b)：忽略大小写的 strcmp。ISO C 没有，跨平台要自己写（转小写再比，用 <ctype.h> 的 tolower）；
  • getline(&line, &cap, fp)：读一整行、自动扩容，比 fgets 好用得多。它是 POSIX 2008 的，ISO C 里没有——本节的 CSV 读取用的就是纯 ISO C 的 fgets + 手工切，多写十几行，换来的是任何 C 工具链都能编。

判断方法：随手一搜发现这个函数「在 Linux 上人人都用」，就再确认一句它在 man 手册里的章节号——POSIX 的手册在 3p 章，C 标准库在 3 章。跨平台代码只用「C 标准 + 你明确选定的目标平台扩展」。

工程惯例工程惯例：为什么这两个探针不配清单

本书的清单是一份契约：它声明「这段程序怎么编译、跑完输出必须是什么」。探针做不到这一点——probe_layout.c 在 -O0 下给出 11/15/27，在 -O2 下给出 14/14/14（session-layout.txt 是原文）。把这种输出写进清单，等于把「未定义行为的结果」当成预期值，那比不写还坏：它会让人以为某个数字是「正确答案」。

所以本书的分工是：清单管「这一次编译、这一次运行逐字长这样」的读数，会话管「同一份代码换个配置就变」的现象。两者的区别不是「有没有 UB」，而是这个读数会不会随编译配置变：probe_layout.c 的 11/15/27 会变，所以它只能进会话；strncpy_trap 里那个 15 在本节的固定布局下每次运行都相同，可以进清单——但正文必须同时说清「它是这一次的读数，不是你能依赖的保证」。

  2. 因为 isalpha 这类函数的参数只允许两种值：能用 unsigned char 表示的（0..255），或者 EOF；负的 char 两种都不是。标准原文在 7.4.1 节：「In all cases the argument is an int, the value of which shall be representable as an unsigned char or shall equal the value of the macro EOF. If the argument has any other value, the behavior is undefined.」允许的两种写法是 isalpha((unsigned char)c) 与 isalpha(EOF)。本机返回 0 只是这一次的巧合（本机把 0x80..0xFF 全试了一遍，两种写法都是 0 个），它既不是标准承诺的结果，也不代表别的实现会给出同样的东西。
  3. 返回 22（item-42-very-long-tail 的长度，不含结尾），buf 里是 "item-42"（7 个字符 + 一个结尾 0，正好 8 个字节），完整装下至少要 23 字节（22 + 结尾）。判据照着标准那句话写：返回值非负且小于 n 才算完整，代码里就是 if (n < 0 || n >= (int)sizeof buf) { /* 截断或出错 */ }。
  4. 返回 2147483647（本机 LONG_MAX，因为 long 是 32 位）——一个看起来很正常的数。有：strtol 会把 ERANGE（本机 = 34）写进 errno，同时用返回值给出端点值。两个出口是 errno（有没有超出范围）和 endptr（有没有读到数字、读到哪停的）。
  5. 因为两个 int 相减可能超出 int 的范围（本机 INT_MAX 与 INT_MIN 的数学差是 4294967295，而 int 只有 4 字节，装不下），而有符号溢出是未定义行为，排序算法会拿着随机的符号继续排。正确写法是 (a > b) - (a < b)。bsearch 对没按该比较器排好的数组不保证任何结果：可能返回 NULL，也可能返回一个看起来命中的指针——本机 qsort_struct 的最后一行为这两种写法都留了措辞。
