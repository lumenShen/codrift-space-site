8.1 先看工程长什么样

这一节的对象不再是一个程序，而是一组小实验。上一单元结束时，examples/ 下已经有了七个项目；这一节要建第八个：examples/ch08/。每个例子仍然是「src/ + include/ + 清单」的最小工程，因为它们要干的事只有一件——把一个含糊的问题（「这样写会怎样？」）变成一条能被命令回答的问题。

第 1 帧是本节故事的起点：前七个项目各管一件事。第 2 到第 9 帧是这一节搭起来的 examples/ch08/——十六个例子目录，每帧只画这一批新增的两个（第 3 帧的「说明」行写着这条约定：单帧放不下十六个，前面画过的不重复）。每个目录基本只演示一个现象：这个例子只回答「越界读会读到什么」，那个例子只回答「volatile 在汇编里长什么样」。唯一的例外是 twos_complement_ub：它把 INT_MIN 的两条 UB 放在一起，因为那是同一个数的两面。本节另外留下的八份会话、三个探针与五份汇编不在这里画，它们在 8.11 节那张图里。把例子拆得这么碎，是故意的：UB 的每一个现象都依赖「这一份二进制、这一次运行」，混在一起就说不清是谁造成的。

工程惯例工程惯例：为什么一个现象一个目录，而且每条结论都要留命令

标准对「怎么组织例子」没有任何规定，这是本书自己的规矩，理由是证据要能被单独复核：

  • 一个目录只演示一个现象，读者才能把「改动」与「结果变化」对上号；把三种 UB 塞进一个 main，出了问题你也不知道是哪一句；
  • 每个例子都要有清单（examples/ch08/*/*.json），清单里写明怎么编、怎么跑、期望什么。正文里的输出块由流水线逐字对账，不是手抄的；
  • 有些现象跑出来才算数（越界读到什么、两档读数差多少），有些现象跑不出来也得讲（严格别名、重叠 memcpy）——后一类必须留下另一种证据：编译器的警告原文，或者标准条款。这两类在正文里会分开标。

代价是文件多：十六个目录、十七份清单。好处是这一章之后你回头查「当时那个结论是怎么来的」，只需要打开一个目录。

实验记录这一节的工具链与复现方式
  • 编译器：gcc 16.1.0，统一用 -std=c17（C17），目标三元组 x86_64-w64-mingw32；系统 Windows 10 x64 (MSYS2 UCRT64)；
  • 本节有一半结论要靠另一次编译才看得见（-O2、-ftrapv、-fanalyzer）：清单里那条用 -O0，正文会话里另给一条显式写 -O2 的；少数例子只有 output 块、没有会话；
  • 清单由 node dev-notes/build/run.js --unit … --fix 驱动：真编译、真运行，再把 stdout 逐字回写进正文，对不上就报 stale_output；
  • 会话文件（session-*.txt）里，命令本身也留在文件里；末尾的 2>/dev/null（或 2>&1）是命令的一部分，重跑才会得到与文件一模一样的结果；
  • 汇编用 gcc -O2 -S（不带 -g）抓取——这样 .s 里没有 .loc 行，读起来干净；带 -g 的版本会多出几百行调试指令。

8.2 四档行为：先给每件事起对名字

「这是 UB 吗？」这个问题，八成问错了。C 里跟「行为由谁决定」有关的情况有四档，它们的严重程度、排查方法、能不能依赖，全都不一样。

档位 谁说了算 C 里的例子 本书的实测
定义良好（well-defined） 标准说死了 int x = 3 + 4; 一定得到 7 到处都是
未指定（unspecified） 标准给了几种可能，实现挑一种，但不必告诉你 printf("%d %d", f(), g()) 里两个实参谁先求值 本机先算右边（8.2 的会话）
实现定义（implementation-defined） 实现挑一种，但必须写进文档 char 带不带符号、负数右移是算术还是逻辑移位、sizeof(long) (char)200 = -56；-8 >> 1 = -4；long 4 字节
未定义（undefined） 标准什么都不说 越界读、有符号溢出、除零、free 之后再读 8.3 起逐条给现象

「定义良好」是默认档，也是本书前七章几乎所有代码所处的档位：3 + 4 得 7、sizeof("hi") 是 3、strlen("hi") 是 2——这些结论在标准里被钉死了，换机器、换编译器都不会变。真正的麻烦来自另外三档，因为它们的共同点是「你的代码没有唯一的答案」，而你在读代码时几乎看不出这一点。四档的叫法值得背下来，因为它们对应四种完全不同的处理方式：定义良好不用管；未指定只能「不依赖顺序」；实现定义要去查手册、或者像下面的探针那样自己读一次；未定义必须改代码。

未指定行为的最小观察面是实参求值顺序。examples/ch08/unspecified_order/ 里两个函数各自打印一行再返回，主程序把它们一起塞进 printf：

运行结果很干脆：打印的是右参数那一行在前。这不是 UB：程序每次都会打印两行，结果集合是确定的（1 和 2 两个返回值不会变），变的是顺序。所以你可以依赖「两行都会打印」，但不能依赖「哪一行在前」。

分界线在这儿：未指定的行为有一个确定的答案集合，程序不会因此做任何「不可能」的事；未定义的行为连答案集合都没有。这条分界很实用——看到一段依赖求值顺序的代码，你该做的是把两个调用拆成两句（int a = f(); int b = g();），这样顺序由你决定；看到一段 UB，改顺序是没用的，必须改写法。顺带记一条容易混的：同一个表达式里两次修改同一个对象（i = i++ + 1; 这种）从 C99 起就是未定义，不是未指定——6.5 节第 2 段规定，一个标量对象上的副作用如果与另一个未定序的副作用（或取值）撞在一起，行为未定义。

实现定义的证据是一次性读出来的。examples/ch08/impl_defined.c 是个没有清单的探针，跑一遍就知道这台机器替你做了哪些决定：

标准原文标准原文：什么叫未定义行为

C17 的 3.4.3 节「undefined behavior」给出的定义是：

behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements

大意：标准对这种行为不施加任何要求。标准还接了一句注释，把可能的结果列成三条：完全忽略这种情况（结果不可预测）；以环境特有的、有文档的方式行为（比如弹一个陷阱）；或者终止翻译或执行（编译报错、进程被杀）。三条并列，不是一条。

出处：ISO/IEC 9899:2018（C17）§3.4.3，以及同节第 2 段的注释。

陷阱「没报错」不等于「没 UB」

你这么判定的：程序跑完了、退出码 0、输出看起来也对，于是认为这段代码没问题。

你怎么会被坑到：本单元后面每一个 opt-diff 例子，-O0 那一档都能「正常走完」——越界读打印出一个数、free 之后读打印出 7、有符号溢出循环打印「循环结束，一共 31 轮」，退出码全是 0。真相是：这些程序在每一档里都是 UB，只是 -O0 那一档恰好没有把 UB 变成你能看见的事故。编译器在 -O2 下给你换一种行为，不是因为 -O2 制造了 bug，而是因为 UB 的许可本来就允许它这么做。

8.3 UB 之下，编译器被允许做三件事

标准对 UB 的「不施加要求」落到编译器身上，有三条常用的推论。它们不是三条独立规则，而是同一句许可的三个侧面。

  1. 假设它不发生：优化器可以把「有符号加法不会溢出」当成前提。于是 i += i 配 while (i > 0) 在 -O2 下被认为是无限循环，回绕那件事被当成不可能。
  2. 删掉由它守护的检查：既然溢出不会发生，if (i + 1 > i) 就恒真，检查可以整个删掉；既然越界不会发生，边界检查也可以删。
  3. 给出任意行为，包括看起来完全正常：越界读可以读到邻居、读到一个常数、或者读到一个每次都不同的垃圾——三者都合法。

8.4 优化在做什么，以及它凭什么「改语义」

「优化」不是把代码变魔术，它主要是五类改写，每一类都以「程序的可见行为不变」为前提：

改写 在干什么 本单元的证据（都真跑过）
常量折叠 能在编译期算出来的就不留到运行期 12345 * 6789 在两档汇编里都没有乘法——前端就把它折成 83810205 了；越界读那一格也被折成常数 0
死代码消除 结果没人用的计算、走不到的分支直接删 -O0 还把 83810205 存进栈上一格（没人读），-O2 连这条 store 都删了
不变量外提 循环里不变的东西搬到循环外，只算一次 sum_plain：g 从「每轮读一次」变成「读一次再乘 n」
内联 小函数展开到调用点 call_square：-O2 汇编里没有 call，只剩 imull %ecx, %ecx；-O0 下是一条 call square
向量化 一次处理多个元素 本单元没有触发（opt_levels.c 的串行求和也没被向量化）；它同样以「没有越界」为前提

「内联」与「死代码消除」这两行，证据在 examples/ch08/opt_effects.c 这个探针里。它只有三个函数：一个只有一句乘法的 square、一个调用它的小函数、一个算完常量却不用的函数。

对比 -O0 会看到两件不同的事。第一件：call_square 里有一条 call square（opt_effects-O0.s 第 31 行），而 -O2 把它展开成了 imull——这是内联。第二件：folded_but_unused 在 -O0 下也没有乘法，前端早就折成了 movl $83810205, -4(%rbp)（第 47 行），只是它还把结果存进栈上一格；-O2 连这条 store 都删了（只剩 movl $7, %eax）。所以「常量折叠」在 -O0 就有，「死代码消除」才要等优化器——这两件事经常被混成一句「优化器把常量算了」，其实不是一回事。

还有第三件：-O2 把 call_square(7) 的结果 49 直接写进了 main（opt_effects-O2.s 第 37 行 movl $49, %edx），main 里根本没有调用 call_square。内联、常量折叠、把结果传给调用者是同一条流水线上的三步，不是三条独立规则。

这五类改写有一个共同前提：程序的行为是定义良好的。优化器做的每一步等价变换，都建立在「这个程序没有 UB」之上。反过来读这句话，就是本单元最要紧的一条：一旦你的程序里有 UB，优化器手里那份「等价」的证明就不再成立，它做的任何改写都还是合法的——因为它可以假设那条路径根本不会发生。所以「UB 让优化有理有据地改语义」不是编译器在报复你，而是你在合同里签了「这一条不会发生」，它按合同办事。-fwrapv 与 -fno-strict-aliasing 之所以有效，是因为它们把合同改写了：前者把溢出重新定义为回绕，后者撤回了「不同类型的指针不会指向同一块内存」这个假设。

sum_plain 里根本没有循环：movl g(%rip), %eax 读一次，imull %ecx, %eax 乘 n。sum_volatile 里循环原样保留，每一轮都执行一次 addl vg(%rip), %edx——volatile 的全部魔力就在这：访问必须真的发生，次数不能改，顺序不能挪。这两份汇编的抓取命令在 session-asm.txt 里，你可以自己重跑。

优化档位怎么选，以及两个「收回许可」的开关

-O0 不优化（本书所有例子的基础档位）、-O1 开一批便宜又安全的改写、-O2 是发行版的常规选择、-O3 再加激进的向量化与展开、-Os 以体积优先。这是工程惯例，标准里没有 -O 这个东西。但「越高越快、-Os 越小」是别人的经验，不是你机器上的事实，所以本书让 opt_levels.c 自己量一遍：一段一亿次的一亿次求和，五个档位各编一次。

读这张表要小心两件事。第一，目标文件大小在这里几乎不区分档位（894 到 1042 字节）：这个循环太小，-Os 省不出东西——「-Os 一定更小」是错觉，它的收益要看代码规模。第二，耗时每一次都不同（这几行数是某一次运行，换一次机器、换一次后台负载都会变），能看的是量级：-O0 大约是 -O2 的两倍，-O1 已经拿到大部分好处，-O3 与 -Os 在这段代码上没有进一步差别（串行求和没法向量化）。这就是取舍的实际含义：先量，再选。

本书自己的规矩是：讲解用 -O0（调试器里的行号对得上）、证明「这里对优化敏感」时只对照 -O0 与 -O2（也就是清单里 detect: "opt-diff" 的两档），-O3 不进教学基线。

-fwrapv 的代价要说清楚：它把有符号溢出定义成补码回绕，于是编译器不能再假设「x + 1 > x」恒真，也不能再利用「循环变量不会为负」——一些优化会因此放弃。你换来的是「溢出时行为可预测」，代价是「同一段代码可能慢一点」。-fno-strict-aliasing 的代价同理：它让编译器不敢再做基于「两个不同类型的指针不会指向同一块内存」的优化，换来的是那些类型双关的老代码不会突然算错。这两个开关都是给旧代码续命用的，不是新代码的首选；新代码该做的是把 UB 去掉，而不是把优化关掉。

6.5 节第 5 段：

If an exceptional condition occurs during the evaluation of an expression (that is, if the result is not mathematically defined or not in the range of representable values for its type), the behavior is undefined.

这两件事经常被打包成一句「会读到垃圾」。垃圾也分两种：一种只在越界时出现，一种在你根本没越界时就出现（没赋初值）。先看越界读。ub_oob_read 里有两个函数，一个读局部数组的第 4 格，一个读静态数组的第 4、5 格：

读这份会话要抓住三件事：

  1. b[0] 是唯一的合法读，两档都是 1；table[3] 虽然两档也都是 0，但它自己就是越界读（下标 3 超出 3 个元素），只是这一次读到的字节恰好是 0。合法读稳定，说明程序本身没有别的随机源；
  2. a[3] 与 table[4] 两档都不同，而且 table[4] 在 -O2 下变成了 0。-O2 并没有「读到 0」，它是把这次越界读折成了一个常数（编译器看见数组大小，就按自己的理解填了一个值）；
  3. 6291120 这个数我连着跑过很多次都没变，但 table[4] 每次重新编译都可能换一个——同一份代码、同一个档位，我先后抓到过 942951440、961367056，闸门的日志里还出现过 1894730768。别背这些数，它们是「这一次的布局」的产物。

这也就解释了为什么这个例子的清单只有一份 detect: "opt-diff"，而没有 mode: "run" 的输出块：程序确实打印得出东西，但打印的内容不是稳定的，拿它当「标准答案」会对不上账。闸门能对账的只是「两档不同」这件事本身。

未初始化读是另一种垃圾，而且它不需要越界：

32763 与 0 的差别不是「编译器算错了」，而是两档对「这块内存里有什么」采取了不同的态度：-O0 真的去读栈上那一格（那里残留着上一次调用留下的字节），-O2 干脆把它当成 0（它有权这么做，因为读未初始化对象是 UB）。结构体那个成员两档都是 0，也只是因为那一块栈恰好是 0——换一次调用、换一个函数，它就可能变。

这两件事画出来是同一个问题的两张脸：一块内存里有什么，不由你的声明决定，而由谁最后一次写过它决定。第 1 帧与第 2 帧是未初始化与「用过又还回去」的垃圾；第 3、4 帧换成严格别名：同一块四个字节，换一种类型去读，得到的是完全不同的数。

第 1 帧的数字来自 ub_uninit 的 -O0 读数，第 2 帧来自 heap_uaf（-O0 读到 7，-O2 读到分配器里的字节），第 3、4 帧是 8.7 节的主角：*(int *)&f 与 memcpy。前两帧的结论是「别读你没写过、或者已经还回去的内存」；后两帧的结论更微妙：即使内存是合法的、内容是确定的，换一种类型去读它也可能不合法——那就是严格别名。

标准原文标准原文：严格别名规则

6.5 节第 7 段（俗称「严格别名规则」）：

An object shall have its stored value accessed only by an lvalue expression that has one of the following types: a type compatible with the effective type of the object, a qualified version of a type compatible with the effective type of the object, a type that is the signed or unsigned type corresponding to the effective type of the object, a type that is the signed or unsigned type corresponding to a qualified version of the effective type of the object, an aggregate or union type that includes one of the aforementioned types among its members …, or a character type.

大意：一个对象的存储值只能通过这几类左值去访问：与它的有效类型兼容的类型、加了限定符的版本、对应的有/无符号类型、包含上述类型的聚合或联合，或者字符类型（列举有删节）。float 的对象用 int 左值去访问，不在这张名单里——所以 *(int *)&f 是 UB；而 memcpy 是按字符类型（unsigned char / char）逐字节搬，落在最后一项的许可里。

出处：ISO/IEC 9899:2018（C17）§6.5 第 7 段。

上面第三段就是合规的两种替代，本机跑出来都是同一个数 1069547520：

  1. memcpy（首选）：memcpy(&bits, &f, sizeof bits)。它明确「按字节复制」，编译器认得这个模式，常常直接优化成一条寄存器搬移，没有任何运行期开销；结果只取决于字节，不取决于对齐与别名。
  2. union（C 里可用，C++ 里不行）：把 float 与 int 放进同一个 union，写一个成员、读另一个。C 标准允许这样读（6.5.2.3 节：用非当前成员读时，那段对象表示按新类型重新解释），但它仍然依赖字节序与布局，而且同一份代码拿给 C++ 编译器就是 UB。本书的推荐是：「取字节」用 memcpy，「同一块内存的多种解释」用 union 只在 C 里、而且清楚自己在做什么的时候。

restrict 与 const、inline 常被一起问起，这里一次说清它们的语义层次：

关键字 它到底是什么 误用长什么样
const 「通过这个名字不可写」的编译期约定 以为 const 对象真的不会被改。别处拿非 const 指针去改它是 UB（6.7.3 节第 6 段），不是「能改」；放在只读段的还会当场崩
restrict 你对编译器的承诺：这块内存不会被别的途径访问 两个 restrict 指针指向重叠区域 → UB（memcpy 的声明就是这样，所以下面那个重叠搬移的例子违规）
inline 展开的建议，标准明确说它不保证 以为加了 inline 一定更快；或者以为不加就一定慢

三者都不是「性能开关」，而是合同：const 是对读代码的人的承诺，restrict 是对优化器的承诺，inline 只是提个建议。写下去就要守，尤其是 restrict——违背它不会有任何警告，只会得到一段「在 -O2 下算错」的代码。

第二件更隐蔽：把重叠的两段内存交给 memcpy。

memcpy 与 memmove 的结果逐字节相同，memcmp 也确认了；而同一件事手写成「前向逐字节」就得到 0101010101——完全不同的结果。这正是它危险的地方：重叠时结果取决于复制方向，前向会自我覆盖（buf[2] = buf[0] 之后，读 buf[2] 拿到的已经是新值），后向不会。本机的 memcpy 这一次表现得像后向（或整块）复制，所以碰巧对了；换一个 libc、换一个长度、换一个优化档，它完全可能变成前向，结果就变成 0101010101。标准允许它怎么选，因为标准根本不许你传重叠的区间。证据是编译器那句 -Wrestrict（-Wall 就带着它，-O0 也报）与标准：

标准原文标准原文：memcpy 要求不重叠

7.24.2.1 节「The memcpy function」：

The memcpy function copies n characters from the object pointed to by s2 into the object pointed to by s1. If copying takes place between objects that overlap, the behavior is undefined.

大意：memcpy 从 s2 指向的对象往 s1 指向的对象搬 n 个字符；如果两个对象重叠，行为未定义。7.24.2.2 节的 memmove 则明确写成「先把 n 个字符从 s2 复制到一个不重叠的临时数组，再从临时数组复制到 s1」——它就是为了重叠而生的。memcpy 声明里那两个 restrict 就是这条规则的类型层表述。

出处：ISO/IEC 9899:2018（C17）§7.24.2.1、§7.24.2.2。

8.8 volatile：它保证一件小事，不保证三件大事

volatile 被误解的程度比 UB 本身还高。它只保证一件事：对这个对象的每一次访问都真的发生，编译器不许合并、不许删除、不许挪到别处；它不保证原子性、顺序与可见性。先看保证的那一件，证据是汇编。

volatile_asm 把五个最小的函数摆在一起：写一次、读一次、加一次、自增并返回新值、自增丢弃返回值。它们的 -O2 汇编是这样：

bump_v 与 self_inc 的差别本身也是一课：同样一句「加一」，需要返回值时是三条指令，不需要时是一条。三条指令的版本在另一个核看来，就是「读了、加了、还没写」——中间那个窗口里任何人读到 g 都是旧值；一条指令的版本在硬件层面也仍然是读改写，只是窗口更短，标准并没有因此把它变成原子操作。

读这份汇编，先确认「保证」：store_v 是一条 movq %rcx, g(%rip)，load_v 是一条 movq g(%rip), %rax——每一次 C 里的赋值/取值都对应一条真的内存访问，没有被优化掉。bump_v 是三句（读、加、写回），因为 ++g 要返回新值；self_inc 是一条 addq $1, g(%rip)，因为 g++ 不需要返回值，编译器就把读改写合成一条指令。这五个函数里没有一条 lock。

再看「不保证」的三件：

  • 不保证原子：addq $1, g(%rip) 是一条指令，但它是「读内存、加一、写回」三件事合成的一条——CPU 执行它的时候不是不可分割的，另一个核完全可能在这中间插进来。要原子，需要的是 lock 前缀或者 stdatomic.h 的原子类型，而 volatile 一个都不给。本机的 volatile long long 读/写恰好是单条 movq，那也是因为 8 字节是这台机器的自然宽度；换成 volatile struct 或不对齐的访问，一条 C 语句就会变成多条指令，撕裂（torn read/write）立刻可见。
  • 不保证顺序：编译器不会把两个 volatile 访问彼此调换，但它完全可以把普通访问搬到 volatile 访问的前后；CPU 也会按自己的规则重排普通读写。标准只要求「在序列点上 volatile 对象的值与抽象机一致」，没有给你内存屏障。
  • 不保证可见性：它不刷缓存、不插 mfence。上面那份汇编里 grep -n "lock\|mfence\|sfence\|lfence\|xchg\|cmpxchg" 一行都没有——这是 session-asm.txt 里真跑出来的结果，不是我的断言。
标准原文标准原文：volatile 到底说了什么

6.7.3 节的类型限定符一节里，关于 volatile 的那一段说：

An object that has volatile-qualified type may be modified in ways unknown to the implementation or have other unknown side effects. Therefore any expression referring to such an object shall be evaluated strictly according to the rules of the abstract machine, as described in 5.1.2.3. … What constitutes an access to an object that has volatile-qualified type is implementation-defined.

大意：volatile 对象可能被实现不知道的方式改动，所以引用它的表达式必须严格按抽象机的规则求值（也就是每一次该发生的访问都发生）；至于「什么算一次访问」，由实现定义。5.1.2.3 节把「访问 volatile 对象」列为副作用（side effect），并规定在序列点上这些副作用必须已经完成、后续的还没开始。

注意它没说什么：这两节一个字都没提多个线程、原子性、内存序。C 标准的线程与原子语义在 stdatomic.h（7.17 节）里，volatile 不在那套模型里。

出处：ISO/IEC 9899:2018（C17）§6.7.3、§5.1.2.3。

陷阱`volatile` 当锁：你会看到「好像能用」

你这么写的：volatile int lock = 0;，加锁时 while (lock) ; lock = 1;，解锁时 lock = 0;。单线程测试完美通过，于是认为锁写好了。

你会怎么误判：这段代码的每一次读、每一次写都「真的发生了」（volatile 保证了这一点），汇编里也看得见，所以你找不到反例。真相是：while (lock) ; 与 lock = 1; 之间有一条缝，两个线程可以同时看到 lock == 0，然后都把它设成 1——检查与设置不是一个原子动作。volatile 只保证「每次都去读」，不保证「读到的值与随后的写之间有排他性」。锁需要的是原子读改写（lock cmpxchg 一类）加内存序，那是 stdatomic.h 或者 pthread 的领域。

单线程程序不可能演示出这个失败——这也是本单元只讲条款、不演示「非原子」的原因：拿一个单线程程序去「证明」它原子，本身就是一次错误的实验设计。

工程惯例工程惯例：什么时候真的需要 volatile

标准没有「要求」你在任何地方写 volatile——它只在一处给了你一条出路（信号），工程上另一处离不开它（MMIO）。其余用法基本都是误用：

  • 内存映射 I/O（MMIO）：硬件寄存器被映射到某个地址，读一次清一次标志、写一次发一次命令。编译器若把「连续读两次」合并成一次，硬件行为就变了——这里 volatile 是正解。代价是每次访问都真的访存，而且它仍然不保证原子（64 位寄存器在 32 位总线上可能要读两次）。
  • 信号处理函数里与主流程共享的 sig_atomic_t：7.14.1.1 节第 5 段给了一条出路——读写 volatile sig_atomic_t 不算 UB。sig_atomic_t 保证一次读写不会被信号打断成两半，volatile 保证编译器每次都去读。
  • 误用的典型：拿它当锁、拿它当「线程间通信的开关」、拿它当「禁止编译器乱序」的屏障。三样它都不做。要线程安全就上 stdatomic.h 或线程库；要屏障就用真正的原子操作与内存序。

一句话：volatile 是给硬件和信号用的，不是给线程用的。

8.9 检测手段：三种抓得住的，与一个抓不住的缺口

这一节把检测清单摊开：每种手段抓什么、抓不到什么、证据是退出码还是警告原文。

第一档：-fanalyzer（编译期，静态分析）。 它不运行程序，只在「编译器视角」里推演路径。同一个「越界写」，换个形状，它的表现完全不同：

两份清单都在 detect: "fanalyzer" 下通过了：一份声明它必须报 [-Wanalyzer-out-of-bounds] 与 CWE-122，另一份声明它必须报 [-Wanalyzer-possible-null-dereference] 与 CWE-690。这两份证据说明的是同一件事的两面：

  • 它能报：malloc(8) 与 memcpy(..., 17) 这种「数字都写在纸面上」的形状，它算得出来，还会画出一条从分配、判空到越界的路径。
  • 它会漏、也会报偏：循环里 i <= 4 写第 5 个 int 是真的越界写（程序真跑起来也确实写了，累加和 = 10 就是证据，标准下这已经是 UB），它一个字没提；报的是「p 可能是空指针」——这次运行里 p 不是空指针，所以这是一条这一次不成立的告警，而真正发生的那件事不在报告里。

所以 -fanalyzer 的正确定位是「多一道筛查」，不是「证明没有 UB」：它给出的永远是「从编译器看到的这条路径上，可能……」。还要记住：它没有整数溢出检查器——gcc -Q --help=warnings 里名字带 analyzer 且与溢出/除法有关的开关只有 -Wanalyzer-shift-count-overflow 与 -Wanalyzer-tainted-divisor 两项，所以别指望它抓 INT_MAX + 1。留一条证据在这儿：对 overflow_trapv 那份源码（裸加法 INT_MAX + 1）跑 -fanalyzer，stderr 一行都没有，编译退出码 0。

闸门对这份清单做了两次运行，日志里写着：带 -ftrapv 那次退出码 3221226505、stdout 为空；去掉 -ftrapv 的阴性对照那次退出码 0、打印了 INT_MAX + 1 = -2147483648 和另一行。-ftrapv 只覆盖 +、-、* 三种运算，不管无符号回绕，也不管浮点；它是运行期检测，只有真的执行到那一步才会终止——这一点和 -fanalyzer 正好互补。

第三档：-fstack-protector-all（运行期，只抓栈上的越界写）。 它往函数的栈帧里放一个哨兵，函数返回时核对；不对就打印 *** stack smashing detected ***: terminated 并以 3221226505 退出。第 4 章的 stack_smash 就是它的靶子，这里不重复。

名字里的 -all 是有含义的：它保护每一个函数，包括没有数组的函数。用 stack_probe.c（只有一个 int y = x + 1;）实测：不加参数时汇编里一处 __stack_chk 都没有（0 处），加了 -fstack-protector-all 是 11 处。

不带 -all 的 -fstack-protector 才只挑「有局部数组或 alloca」的函数——那是另一档开关，别把两者的能力混在一起。它的边界还是硬：只看得见栈帧返回时的破坏，堆越界、越界读、以及不经过栈帧返回的破坏，它都看不见。

缺口：本机没有 ASan / UBSan。 把四种手段放在一张表里，边界就清楚了：

手段 阶段 抓什么 抓不到什么 证据形态
-fanalyzer 编译期 能算出来的越界、可疑的空指针路径 循环里的越界写（本机报偏）、整数溢出（没有检查器）、只有运行期才知道的输入 警告原文，编译退出码仍是 0
-ftrapv 运行期 + - * 的有符号溢出 无符号回绕、浮点、越界、泄漏 进程被终止，退出码 3221226505
-fstack-protector-all 运行期 每个函数栈帧里的越界写（-all 就是所有函数） 堆越界、越界读、不经过栈帧返回的破坏 stderr 的 *** stack smashing detected *** + 3221226505
opt-diff 对比 「这里对优化敏感」 具体是哪一类 UB 两档的 stdout 或退出码不同
ASan / UBSan 运行期 本机没有（链接失败） 全部 无

这张表最下面一行是实测而不是选择：-fsanitize=address,undefined 能编译但链接失败（collect2.exe: error: ld returned 5，安装里没有 libasan / libubsan），本机也没有 clang。这意味着：

  • 你拿不到「越界发生在第几行、越界了几个字节」这种运行期精确报告；
  • 你能拿到的是退出码 + stderr + 汇编 + 分析器警告这四类证据，本单元每一处「实测」都标明用的是哪一类；
  • 没有检查器不代表没有 UB。8.5 那张表里，格式串错配、缺 return、数据竞争，本机一个检查器都没有——只能靠代码审查与测试。

这一节的读法也在这儿：本单元的四份 opt-diff 清单是第四类证据，它不指出 UB 的种类，只证明「这里的行为对优化档位敏感」（四份清单的 expect.differs 依次是 stdout、stdout、stdout、exit）。四个形状都真跑过：

  • ub_oob_read：两档的 6 行输出在 a[3] 与 table[4] 两处不同（table[4] 在 -O2 下变成 0）；
  • ub_uninit：-O0 读到 32763，-O2 读到 0；
  • heap_uaf：-O0 读到 7，-O2 读到分配器里的字节（每次都不一样）；
  • signed_overflow_loop：-O0 退出 0，-O2 退出 3221225477。

为什么这里不列具体读数：这四处里只有 uninit 与 overflow_loop 的读数是稳定的；oob_read 的越界值和 heap_uaf 的 -O2 值每次编译、每次运行都可能换一个（8.6 已经说过）。把会变的数写进正文，读者一跑就对不上——这正是 UB 的脾气，也提醒你：opt-diff 的证据是「两档不同」，不是某个具体的数。

8.10 把 UB 变成可观测现象

UB 最要命的地方是它可能「看起来正常」。所以真正工程化的做法不是「避免写出 UB」（那是目标），而是给每一处可疑的地方装一个观测点。本单元用到的四种做法，按成本从低到高：

  1. 前置条件 + 断言：函数入口就检查参数，assert(p != NULL);、assert(i >= 0 && i < n);。assert 在 NDEBUG 定义时会被整个去掉，所以它只适合「不该发生」的内部不变量；对外部输入要用返回错误码。
  2. 把检查写进算式：overflow_guard 用 __builtin_add_overflow 把「会不会溢出」变成一个可以问的布尔值，而不是一个「算完看结果对不对」的赌博。它真跑的输出在下面。
  3. 边界测试：对每个数组，测 0、n-1、n 三个下标；对每个整数，测 INT_MAX、INT_MIN、0。边界测试不是「多测几个数」，而是把「刚好在边界上」的那一格单独造出来：本单元两个越界形态都是差一格——a[3]（a 有 3 个元素）、i <= 4 配 malloc(4 * sizeof *p)。off-by-one 之所以是最高频的越界，就是因为它在 for (i = 0; i < n; i++) 这种最常见的循环里永远不会暴露。
  4. 保住崩溃前的输出：这一条最容易被忽略，也最容易救你一次调试。

工程惯例工程惯例：调试崩溃时的三条做法

这不是标准，是常年踩坑攒下来的：

  • 崩溃点附近若已经打印过东西，先 fflush(stdout) 或改打 stderr（stderr 默认无缓冲）。否则你会看到「程序什么都没打印就崩了」，然后去错误的地方找原因。
  • 断言写内部不变量，错误码写外部输入。assert 会被 NDEBUG 整段去掉，拿它校验用户输入，发布版里就什么都不剩了。
  • 把「这次没事」与「永远没事」分开记。add_naive(INT_MAX, 1) 这次打印 -2147483648，记成「本次实测」；不要记成「溢出会回绕」。后者需要 -fwrapv 或 unsigned 才成立。

代价：多写几行检查、多刷几次缓冲、多记几行日志。换来的是崩溃时你手里有一条线索，而不是一个退出码。

8.11 可移植性守则，以及这一节留下了什么

这一节的所有结论都指向一句：凡是标准没钉死的东西，都不要写进「这就是 C」的认知里。下面五条是本书反复强调的，本机读数都在 session-impl-defined.txt 里：

别依赖 本机读数 为什么
结构体的布局与大小 sizeof(struct pair) = 8（1 字节的 char + 4 字节的 int，中间补了 3 个字节），offsetof(pair, i) = 4 对齐规则由实现定；成员的顺序虽被标准固定，中间填充不固定
字节序 0x01020304 的四个字节是 04 03 02 01（低地址放低位，小端） 大端机器上反过来
指针大小 sizeof(void *) = 8 32 位机器上是 4
位域的顺序与宽度 本书在整数那一章讲过它不可移植；这一条没有单独做本机探针 位的分配顺序、跨存储单元的规则都由实现定
int / long 的宽度 sizeof(int) = 4，sizeof(long) = 4，LONG_MAX = 2147483647 long 在本机和 int 一样宽；想要 64 位用 long long 或 int64_t

第五行最容易骗人：不少教材写「long 是 64 位」，本机不是。你把「用 long 存 64 位」写进代码，在 Windows 上就是 4 个字节。下一单元 c20 的 portability_probe 会把这一组事实系统打印一遍（CHAR_BIT、char/short/int/long/long long/void */size_t 的 sizeof、INT_MAX/LONG_MAX/LONG_MIN、字节序）；定宽类型的宽度、位域与结构体布局不在那个探针里，要查就照本节 impl_defined.c 的写法自己加两行。这里只给出方向：要宽度就用定宽类型，要布局就用序列化，要字节序就显式判断。

小结这一节要带走的四件事
  • 四档行为要分清：定义良好、未指定、实现定义、未定义；只有最后一档「标准什么都不说」，前三档都能查到依据。
  • UB 之下编译器的三个自由度（假设不发生、删掉检查、给出任意结果）都有真跑的读数支撑：同一个循环 -O0 退出 0、-O2 退出 3221225477；同一段越界读两档读数不同。
  • volatile 只保证「每次访问都真的发生」；汇编里 movq / addq 都在、lock 与屏障一个都没有，所以它不保证原子、顺序与可见性——要线程安全请用 stdatomic.h。
  • 证据分四类：退出码、警告原文、汇编、opt-diff 差异。本机没有 ASan/UBSan，说不清的就标「没有检查器」，不要拿「跑起来没事」当结论。

注自测题答案
  1. int x = 3 + 4; 是定义良好（标准说死了结果是 7）；f / g 的调用顺序是未指定（结果集合确定，顺序由实现挑，不必告诉你）；(char)200 是实现定义（本机 -56，因为 char 带符号，实现要写进文档）；a[3] 是未定义（标准什么都不说，本机 -O0 读到 6291120 一类值、-O2 折成常数）。
  2. 不是。UB 的许可本来就允许编译器假设它不发生：i += i 溢出被当成不可能，于是 while (i > 0) 恒真，后面的取用被按「i 单调增长」安排，地址就算到了不该去的地方。-O0 那一档「正常」只是恰好没把 UB 变成事故。想收回许可就用 -fwrapv（回绕）或 -ftrapv（陷阱）。
  3. 因为「一条指令」不等于「一个不可分割的操作」：addq $1, g(%rip) 仍是读内存、加一、写回三步合成，另一个核可以在中间插进来。标准（6.7.3、5.1.2.3）只保证「每次访问都发生」，一个字都没提原子性、顺序与可见性；汇编里 lock / mfence 一个都没有（本单元 session-asm.txt 的 grep 结果是空）。要原子得用 stdatomic.h 或 lock 前缀，单线程程序演示不出这个失败。
  4. 靠标准的 7.24.2.1（「如果两个对象重叠，行为未定义」）与编译器那句 -Wrestrict 警告（-Wall 就带着，-O0 也报）。运行结果不是证据：本机的 memcpy 对 8 字节的小块恰好从头往后搬，重叠时碰巧也对，换个 libc 或换个长度就可能出错。
  5. 因为 printf 写的是全缓冲的 stdout，崩溃时缓冲区没来得及刷。两个改法：崩溃前显式 fflush(stdout)，或者改写到默认无缓冲的 stderr。本单元 crash_stdout 的两份清单（其中一份多一个 -DCH08_FLUSH）就是这两种跑法的真实 stdout：一份是「（无输出）」，一份是那一行字。
