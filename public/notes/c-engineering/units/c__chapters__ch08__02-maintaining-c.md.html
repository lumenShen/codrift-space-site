20.1 先看工程长什么样

前面十九个单元教的是「怎么写」；这一节教的是「怎么交出去」。这两件事的差距不在语法上，而在接缝上：一个能在你机器上跑的程序，和一个别人敢改的程序，中间隔着接口、测试、构建脚本、审查清单这四样东西。

照老规矩，先从文件和目录看起。这一节是《C 语言》分册的最后一节，前面那一节（chapters/ch08/01-undefined-behavior-and-optimization.md）已经在 examples/ch08/ 里摆了十六个例程；本节要在这个目录里再加五个目录组，它们合起来是一份完整的、能交给别人的小程序。

第 1 帧是这一节的起点：examples/ 下已经有八个项目，examples/ch08/ 里是一堆「一次只讲一件事」的例程，它们各自都能编译、都能跑，但合起来不是一个程序。第 2 帧是本节新增的五个目录组，每一组只回答一个问题：一个真程序长什么样（final_app）、缺陷藏得住吗（hidden_bugs）、这机器的事实是什么（portability_probe）、逻辑怎么单独测（testable_pure）、怎么用一条命令构建（build_and_run）。第 3 帧把它们各自装了什么摆出来——注意测试与构建脚本不在 final_app 里：final_app 有的是输入数据和一个自检程序（src/selfcheck.c），assert 单测在 testable_pure，build.sh 在 build_and_run。第 4 帧是全书收齐时的样子：八章二十个单元，上面这三样东西（数据、测试、构建脚本）在 examples/ch08/ 里第一次同时出现——它们合起来才是这一节要交给你的东西。

五个目录组各自的一句话：

  • final_app/ —— 综合工程：四个源文件 + 一个自检程序 + 三个头文件 + 两份输入数据。它把读文本、解析、排序、统计、写结果五步串成一条链；
  • hidden_bugs/ —— 一段藏着六个缺陷的代码。六个缺陷住在同一个文件里，清单一次只打开一个（第 1 号在开了栈保护时会终止进程，六个一起打开就只看得见它）；
  • portability_probe/ —— 实现事实探针：把 sizeof、LONG_MAX、字节序打印出来；
  • testable_pure/ —— 纯函数 + assert 测试：逻辑与输入输出分开，单独测；
  • build_and_run/ —— build.sh：本项目（examples/ch08/）的第一条构建脚本，里面只有一条 gcc。
工程惯例工程惯例：为什么「一个例子一个目录」这一条在最后一节才见效

从第二个项目（第 2 章）起，本书要求每个例子都是 src/ + include/ 的最小工程。当时给的理由是「编译速度、接缝可见、别人能接手」——那三条都是预告。到了这一节，它们第一次全都兑现了：

  • final_app 的 parse.c 与 report.c 互不相识，所以你能单独测 parse.c、单独换掉 report.c 的排版；
  • hidden_bugs 的六个缺陷分别在六个函数里，所以能一次打开一个、各留一条证据；
  • portability_probe 只把「问机器」这一件事放进 impl_facts.c，main.c 只负责打印。

代价还是那一条：你要多维护三份头文件。头文件写错（漏声明、重复定义）时，报错会出现在别的文件里——所以在行数不多的时候就把这个习惯练出来，比在三千行的 main.c 里练要便宜得多。

先把这个程序的需求说完，一个字都不含糊：

需求：data/scores.txt 里每行是「名字 分数」，名字与分数之间用一个空格分开；有些行是空行、# 开头的注释行或写坏的行。程序要读这个文件，把能认出来的记录按分数从高到低排好（同分按名字），打印前 8 名和一组统计（条数、平均分、最高分、最低分、中位数）。出错时干净地退出，并且三种情况各有一个退出码：打不开文件是 2、一条有效记录都没解析出来是 3、内存不够是 4。

需求写清楚了，后面的每一步才有对错可判。这七步是：

  1. 需求 —— 上面那段话。谁写、写多细，决定了后面每一步会不会返工；
  2. 模块划分 —— 读文件一组、解析一组、排序与统计一组、写结果一组。划分的判据只有一条：能不能单独验证；
  3. 接口 —— 三个头文件。里面只放「别人需要知道什么」：类型、函数声明、错误码、契约（参数能不能是 NULL、返回值什么时候有效）；
  4. 实现 —— 四个源文件。main.c 只决定「读哪个文件、写到哪」，流程在 app.c，活由 parse.c 与 report.c 干；
  5. 测试 —— 分两层落地：final_app/src/selfcheck.c 把「两个错误码 + 解析的边界」钉住（它有自己的 main，与主程序分开编），testable_pure 演示纯函数怎么用 assert 一条条测；
  6. 构建 —— 一条 gcc 命令固定进 build.sh。同一条命令、同一组参数，别人跑出来的结果才和你一样；
  7. 交付 —— 把「怎么构建、怎么跑、输出应该长什么样」一起交出去。本书的做法是把期望输出写进清单，让机器逐字对账——这就是交付物的一部分。

七步里最容易跳过的是第 3 步。它的产出不是一个文件，而是一份合同：别人只看 include/ 就能知道每个模块能做什么、不能做什么。这句话有个直接后果：头文件里不放实现，而 .c 里的函数要在头文件里有一条声明。

20.3 代码风格与可读性：让人敢改你的代码

风格不是审美问题。代码是写给下一个人读的，而那个人常常是三个月后的你自己——所以风格的每一条都能翻译成一句「这样写会不会让人误判」。五条最值得练的：

  1. 名字说清用途，不用缩写。parse_records、report_write、count_above：动词开头、宾语在后。反例是 pr、doIt、tmp2——它们不是错，只是每个读的人都要回跳一次上下文；
  2. 缩进一致，一个项目一套。本节的例子统一四空格、不用 Tab（Tab 在不同编辑器里显示宽度不同，一混就乱）；
  3. 注释写「为什么」，不写「是什么」。x++; /* x 加一 */ 这种注释等于没说；本节例子里真正有用的是这种：copy_bytes(buf, src, 9); /* 缺陷：8 格的地方写了 9 个字节 */——它写的是这句代码与它想干的事之间的差距；
  4. 函数短。判据不是行数，是「一次能读完、只干一件事」。本节三个例子的真实长度是：report_write 19 行、parse_line 32 行、parse_records 40 行。后两个已经偏长——它们的「一件事」分别是「解析一行」和「按行切分」，还能不能再拆是一个判断问题；如果你接手时要往里加规则，第一件事就是想这个。
  5. 头文件是合同：里面放类型、函数声明、错误码、契约说明，不放实现。同样一份声明被多个 .c 包含时，靠 #ifndef 那三行（include guard）保证只展开一次，这是第 7 章讲过的。

有一条容易被忽略的代价：这些规矩都会让你现在多打字。写 report_write 比写 pr 多敲十一个字符，写契约注释比不写多花两分钟。换来的东西是三个月后有人（包括你）能在十分钟内看懂这份代码在干什么、边界在哪。这笔帐在超过 300 行的程序上永远是划算的。

陷阱「注释写的和代码干的事不一样」比没有注释更坑

你会看到的现象：一个函数上面写着「把分数夹到 [0, 100]」，函数体里却是 if (v > 100) return 100;——下界根本没管。

你会怎么误判：读代码时眼睛先扫过大字注释，于是心里默认「下界已经处理过了」，于是当你看到 -5 被原样传下去时，会去别的地方找原因。

真相是：注释是声明，代码才是事实；两者不一致时，永远是代码说了算。这一条直接决定你读陌生代码的顺序——先读头文件与函数签名，再读实现，最后才看注释（20.11 会把顺序写成步骤）。本书的 parse_line 里那句「宁可不收，也不偷偷截断」对应的就是第 21–23 行那三行真实的检查：注释里的每个承诺，都能在代码里找到出处。

20.4 防御性编程：三种策略各有各的位置

「防御性编程」有一半的误区：很多人以为它的意思是到处写 if (p == NULL) return;。真相是它有三种策略，各自解决不同的问题，选错了会白干活甚至帮倒忙。

策略一：参数校验，返回错误码。 用在跨越模块边界的地方，也就是别人能传错的地方。看 parse_records 的头几行：

策略二：断言，抓「不可能发生」的事。 assert 管的是程序内部的逻辑不变量，不是别人的输入。第 20.5 节会大量用它。标准说得很清楚：

标准原文标准原文：`assert` 失败时到底发生了什么

C 语言标准（ISO/IEC 9899，C17）7.2.1.1 节「The assert macro」的 Description 里写：

The assert macro puts diagnostic tests into programs; it expands to a void expression. When it is executed, if expression (which shall have a scalar type) is false (that is, compares equal to 0), the assert macro writes information about the particular call that failed (including the text of the argument, the name of the source file, the source line number, and the name of the enclosing function — the latter are respectively the values of the preprocessing macros __FILE__ and __LINE__ and the identifier __func__) on the standard error stream in an implementation-defined format. It then calls the abort function.

大意：断言失败时做两件事——往 stderr 写一条诊断，然后调用 abort 终止进程。诊断必须包含四样东西（表达式原文、源文件名、行号、所在函数名）；只有「格式」是 implementation-defined。

同一章的 7.2 节第 1 段规定 assert 可以被整体关掉：

If NDEBUG is defined as a macro name at the point in the source file where <assert.h> is included, then assert is defined simply as #define assert(ignore) ((void)0).

大意：只要在包含 <assert.h> 之前定义了 NDEBUG，assert 就变成一句什么都不做的空语句。7.2 节第 2 段接着规定：assert 必须实现成宏，不是真正的函数。

出处：ISO/IEC 9899:2018（C17）§7.2.1.1 第 2 段（Description）；§7.2 第 1 段（NDEBUG）与第 2 段（必须实现成宏）。

这段话直接给出了「为什么不能拿 assert 做参数校验」：发布版常常带 -DNDEBUG 编译，那时候你写的一整排 assert 全部消失，本该拦住的东西一个都拦不住。参数校验必须能在发布版里活着，所以它得写成真正的 if 加返回值。

四个细节值得记：① 诊断里有表达式原文和行号（file src/main.c, line 62），所以断言失败不需要猜；② 它没有打函数名——而标准要求诊断「包括」表达式原文、文件名、行号、函数名四项，implementation-defined 只修饰格式：所以这是本机 UCRT 少打了一项，不是标准给它的自由；③ 退出码不是 1 也不是 2，而是 0xC0000409——那是 abort() 在这台机器上的收尾方式（第 9 单元的 -ftrapv、-fstack-protector-all 崩溃也是这个码，它们属于同一类：进程被强行终止）；④ 这个数是 Windows 的进程退出码，本书清单用 Node 的 spawnSync 读它；同一个程序在 MSYS bash 里 echo $? 会得到 127（bash 把「被异常终止」映射成 127）。两个数说的是同一件事，别以为看到了两次不同的崩溃。

策略三：干净退出。 用在「程序已经救不回来了，但要让外面知道为什么」的地方。它有三条纪律，app.c 里三个失败出口都照着做：

  1. 诊断走 stderr，不要混进 stdout（stdout 是交付物，混进去就没人能对账了）；
  2. 给一个可判定的退出码：0 成功、2 打不开文件、3 解析失败、4 内存不够。调用者只看退出码就能分流；
  3. 退出前把该还的还掉：free(text)、free(records)。虽然进程结束时操作系统会回收，但一份「遵守自己定的规矩」的代码才经得起别人加功能（比如以后要在 main 里循环调用 app_run）。
陷阱「反正进程要退出了，不 free 也没事」——这句话会咬人

你会看到的现象：本节的 app.c 在 return 2 之前老老实实 free(text)，看起来很啰嗦，因为进程马上就没了，操作系统会把内存全部收回。

你会怎么误判：把这个判断推到别的地方——「这个函数在错误路径上不 free 也没事嘛」。然后有一天，这个函数被放进一个循环里调用（比如批量处理一千个文件），而它正好是另一种用法：那时候泄漏的是一千份内存。

真相是：free 的意义不只是「还给操作系统」，更是「这段内存的使命结束了」这个声明。声明得越早、越靠近它的作用域末尾，越不容易在改需求时留下漏洞。第 12 单元讲过的那条规矩在这里再次生效：谁分配，谁释放；在哪个作用域分配，就在哪个作用域结束前释放。

— minimum value for an object of type long int LONG_MIN −2147483647 // −(2^31 − 1) — maximum value for an object of type long int LONG_MAX +2147483647 // 2^31 − 1

紧接着的一句是：这些「实现定义的值」的绝对值必须大于或等于表里给出的数。

大意：标准只保证 long 至少能表示 32 位有符号整数，多出来的位数由实现自己决定。本机正好就是这条下限（LONG_MAX = 2147483647），所以「本机 long 是 4 字节」这件事合情合理，也绝不是所有机器都这样。

出处：ISO/IEC 9899:2018（C17）§5.2.4.2.1。

CHAR_BIT（一个字节几位）至少是 8 这条出自 5.2.4.2.1；而 sizeof(char) 恒为 1 出自另一节——6.5.3.4（sizeof 运算符）规定：作用于 char、unsigned char、signed char 时结果是 1。本机读数是 8 和 1，与这两条都对得上。至于字节序，标准没有规定一个多字节整数内部的字节怎么排（它只规定值怎么表示，不规定字节顺序），所以只能问机器、不能背规则：本机 0x01020304 在内存里第一个字节是 04（低位在前），这就是小端。

工程惯例工程惯例：可移植性守则里最值钱的五条

以下五条不是标准条文，是几十年踩出来的工程共识。每条后面括号里是「不遵守会怎样」：

  • 别依赖结构体布局（字段之间可能有填充字节，sizeof(struct) 不等于字段之和——第 11 单元讲过）：不遵守就会在换编译器后读写错位；
  • 别依赖字节序（跨机器传二进制数据时必须显式转换）：不遵守就会得到 0x04030201 这种反向的数；
  • 别依赖 int / long 的宽度（要固定宽度用 <stdint.h> 的 int32_t / uint64_t）：不遵守就会在 32 位机器上溢出；
  • 别依赖 char 有没有符号（要明确就用 signed char / unsigned char）：不遵守就会出现 (char)200 在这台机器上是 −56（本机 char 是带符号的）、在另一台机器上却是 200 的区别；
  • 别依赖指针和 int 一样大：不遵守就会把指针截断成 32 位，得到一个必然出错的地址。

这五条的共同点：它们全都是「本机能跑、别处不一定」。所以可移植性的第一步永远是把读数打印出来，而不是照着一句口诀改代码。

工程惯例工程惯例：三层防线，各自抓什么

本书能用到的检测手段就这三种，它们的能力边界必须记清楚，否则你会以为「跑过检测器就没问题了」：

  • -Wall -Wextra -Wpedantic（编译期，永远开着）：本节这份代码上抓到三条——恒假的无符号比较（-Wtype-limits）、格式串与实参类型不符（-Wformat=）、free 之后使用（-Wuse-after-free，只给 -Wall 就会报，不需要 -fanalyzer）。它抓不到越界写、内存泄漏，也抓不到第 2 号那种「传了 NULL 但表面正常」；
  • -fanalyzer（编译期，静态分析）：在基础警告之外再抓到泄漏与「free 之后使用」的另一条路径；代价是编译变慢，而且会有误报和漏报；
  • -fstack-protector-all / -ftrapv（运行期，由清单声明）：只有真的发生才发作，发作的形式是先往 stderr 打一行（比如 *** stack smashing detected ***）再终止进程（退出码 3221226505），而不是变成一条「还能继续跑」的警告。它抓不到堆上的问题，也抓不到没越界的逻辑错误。

再往外一层是人工清单（20.7 那二十条）——它抓的是检测器永远抓不到的那一类：代码完全合法、只是结论错（第 3 号那个无符号相减，标准规定它回绕，不认为这是错），或者像第 2 号那样把错误咽了下去。这三层没有一层能替代另一层。

  2. 因为契约是给调用者看的。调用者在别的 .c 文件里，他只会 #include "parse.h"；写在 parse.c 的实现注释里，他根本不会打开那个文件。判据很简单：只有调用者需要知道的事才进头文件，只有维护者需要知道的事留在 .c 里。
  3. 因为 assert 可以在编译时被整体关掉：标准 7.2 节第 1 段规定，只要在包含 <assert.h> 之前定义了 NDEBUG，assert 就变成 #define assert(ignore) ((void)0)——一整排校验全部消失。发布版常常带 -DNDEBUG 编译，所以参数校验必须写成真正的 if 加返回值。assert 管的是「程序内部的逻辑不变量」，那是开发期才需要炸的东西。
