工程惯例工程惯例：为什么声明放头文件、定义放源文件

标准对「一个程序分几个文件」没有任何规定，它只要求一个程序有且只有一个 main。分家是惯例，理由有三条：

  • 改一个文件不用重编全部：func_basics.c 改一行，只需要重编它自己，然后重新链接一次；
  • 接缝写在明面上：include/func_basics.h 里谁都能看见「这个模块对外提供什么」，src/func_basics.c 里是「怎么做到的」。谁依赖谁，一眼能看穿；
  • 能被别人接手：三千行的 main.c 没人愿意读第二次。

至于「改一个文件不用重编全部」这条好处，现在还看不出来：本书一条 gcc 命令会把列出的 .c 全部重编一遍。要等第 7 章讲了分步编译（先 -c 出 .o、再链接），改一个文件才只需要重编它自己。

代价是多学一件事：头文件里写什么、不写什么。写重了（比如把函数体贴进头文件）会撞符号，写漏了会报「隐式声明」。本书从第二个项目起要求每个例子都是 src/ + include/ 的最小工程，练的就是这件事。

语法规则函数的两半长什么样
  • 声明（原型，prototype）：返回类型 名字(参数类型 参数名, …); —— 以分号结尾，没有花括号。它唯一的作用是让编译器认识这个名字：能接几个参数、各自什么类型、交回什么类型。
  • 定义：返回类型 名字(参数类型 参数名, …) { 函数体 } —— 花括号里是真正的计算。
  • 一个函数可以有很多份声明（每个用到它的 .c 都能看见一份），但定义只能有一份：两份定义会在链接期撞车（本机的报错只有一行 collect2.exe: error: ld returned 5 exit status，见本节末尾那个陷阱）。

参数名在声明里可以省（double celsius_to_fahrenheit(double); 也合法），但本书一律写上——它是给人看的文档。

这一节躲不开三个符号。它们属于指针，第 4 章（chapters/ch04/）会讲透；这里只认到「够用」：

大白话用大白话说「值传递」

把函数想成一台复印机：你递进去的每样东西，它都先复印一份再动手，你在原件上画的花它一概看不见。

  • swap_bad(x, y) 递进去的是两个数字（1 和 2）。函数在两张复印件上换来换去，原件 x、y 从头到尾没动过；
  • bump_bad(n) 同理：函数里的 n 是复印件，加一之后复印件被扔进碎纸机；
  • swap_ok(&x, &y) 递进去的也还是拷贝，但拷贝上写的是**「x 住在哪」这张纸条**。纸条是复印件，纸条上的地址是真的——顺着它写，改到的就是原件。

所以严格的说法只有一句：C 里所有参数都是值传递；想让函数改到调用者的东西，你只能把它的地址递进去。 C 里没有「引用参数」这回事（那是 C++ 的 int &），想改就传指针；不想改、也不想被拷一份大对象，也传指针（加 const）。

陷阱「我明明在函数里改了，外面没变」

你会看到什么：swap_bad(x, y) 跑完，x、y 一点没变，程序不报错、不警告，退出码还是 0。

你会怎么误判：先怀疑「函数没被调用」，于是在 swap_bad 里加一句 printf —— 它明明打印了；再怀疑「是不是要写 swap(int &a, int &b)」——那是 C++ 的写法，C 编译器会直接报语法错误；最后有人开始给形参加 *、给实参加 &，靠碰运气试出来。

真相是：形参 a、b 是两个全新的变量，住在被调函数自己的栈帧里（7.6 节会把它们的位置画出来）。函数一返回，那层栈帧连同这两个变量一起消失。「传进来的是什么」和「改的是谁」是两件事：传 int 改的只是副本，传 int * 才能改到别人。

标准原文标准原文：`(void)` 与 `()` 是两种不同的声明

C 语言标准 6.7.6.3 节「Function declarators (including prototypes)」第 14 段里有两句专门说这两种写法：

实参的求值顺序：你写的顺序不是执行的顺序

add(left(), right()) 里，left 先跑还是 right 先跑？探针只有十来行：

写的是 left 在前，打出来的却是 right 在前。 这不是笔误：本机实测 -O0 与 -O2 两档都是 right left（x86-64 上编译器从右往左准备实参）。标准对这件事的态度是「未指定」：顺序由实现决定，实现不必告诉你它选了哪个。所以别在实参里放「谁先谁后会影响结果」的写法——f(i++, i) 这种更糟，它在标准里连「未指定」都算不上，是未定义行为。

标准原文标准原文：未指定行为是什么

C 语言标准 3.4.4 节给「未指定行为」下的定义是：

unspecified behavior: behavior, for a well-formed program construct and correct data, that depends on the implementation. The implementation is not required to document which behavior occurs.

大意：未指定行为是「取决于实现」的行为，实现不必告诉你它选了哪个。它和「未定义行为」不是一回事：未指定是「几种都合法，实现选一个」，未定义是「标准什么都没说」。

出处：ISO/IEC 9899:2018（C17）§3.4.4。

大白话用大白话说「未定义」与「未指定」

这两个词在标准里都是有确切定义的术语，别混：

  • 未定义行为：标准什么都没说——程序做什么都行，包括你看到的那个 42、另一个数、或者当场崩掉；
  • 未指定行为：标准给了几种都合法的结果，具体选哪个由实现决定，但必须选一个。函数实参的求值顺序就是这一类。

你唯一能做的：别写依赖顺序的代码。要「先算 A 再算 B」，就写成两条语句——语句之间是有先后关系的，实参之间没有。

标准把这件事写得很干脆，6.9.1 节「Function definitions」第 12 段：

标准原文标准原文：漏写 return，而调用方用了那个值

If the } that terminates a function is reached, and the value of the function call is used by the caller, the behavior is undefined.

大意：函数末尾那个 } 被走到了、而调用方又用了这次调用的返回值——行为未定义。换句话说：printf("...%d", missing_return(7)) 是未定义行为（调用方用了那个值），而如果你写 missing_return(7); 什么都不接，标准就没什么可说的。

出处：ISO/IEC 9899:2018（C17）§6.9.1 第 12 段。

本机实测的现象就是那行 missing_return(7) = 23：同一个二进制反复跑，它稳定地打印 23——「稳定」不等于「有定义」，它只是「这次编译产出的这份机器码恰好这样」。

main 是个例外，标准专门给了它一条宽恕，5.1.2.2.3 节「Program termination」第 1 段：

标准原文标准原文：`main` 走到末尾等价于 `return 0`

If the return type of the main function is a type compatible with int, a return from the initial call to the main function is equivalent to calling the exit function with the value returned by the main function as its argument; reaching the } that terminates the main function returns a value of 0.

大意：main 走到底不给 return，等价于 return 0。所以上面 src/main.c 那个「故意没写 return 0;」的程序，流水线对账的退出码仍然是 0（清单里 "expect": { "exit": 0 } 这一条不是装饰，退出码对不上整条清单就失败）。这条宽恕只给 main——别的函数都不享受，包括 missing_return。

出处：ISO/IEC 9899:2018（C17）§5.1.2.2.3 第 1 段。

语法规则写递归的两半
  • 基准情形（base case）：一个能让函数直接给出答案、不再调自己的条件（这里是 n <= 1）。少写它，函数会一路往下永不回头；
  • 递归情形（recursive case）：把问题变小一点再交给自己（这里是 n - 1）。变小这件事必须是可终止的：每次都在向基准情形靠近。

两句检查口诀：①「有没有一条路不调自己？」②「每一层的调用都在往那条路走吗？」两问都答「是」，递归才算写对。

工程惯例工程惯例：递归还是迭代，怎么选

这是工程惯例，标准对「该用哪种」没有任何规定；它也不是对错题，是取舍：

  • 选递归：问题本身就是递归定义的（树的遍历、分治、括号匹配、后续要学的链表与回溯）。这时递归版本往往比迭代版本短得多、也更容易看出对不对；
  • 选迭代：问题只是「重复做一件事」（累加、查找、计数）。这时循环一目了然，还不占额外的栈（7.8 会看到代价）；
  • 判断标准：先写清楚的那个版本通常是对的；只有当深度不可控（输入能大到几十万层）或者每层开销真的成了瓶颈时，才为了性能改写成迭代。

本书的立场：先用递归把逻辑写对，再按需要换迭代。反过来的顺序——为了「省一点栈」把递归手工改成循环——是新手最常见的自伤方式（第 7.8 节末尾会看到编译器自己就会做这件事）。

真相是：一是基准情形写错或写不到（n == 0 写成 n = 0、递归时忘了减一），二是深度本来就太大（数据规模 × 每层帧大小 > 栈的限额）。两者的现象一样，区分办法是同一个数字：把 DEPTH 改成 1000 再跑一次。跑得通说明是深度问题，跑不通说明基准情形的问题。栈溢出时连一个好看的报错都不会给你——这是它比段错误更难查的地方。

第 1、2 帧是 gdb 那两行 p 的画法：fresh 每层一个地址，issued 从头到尾一个地址。第 3 帧才是 static 真正的含义：函数返回了、那一帧没了，它还在。这就是为什么同一个函数第二次进入时读到的是上一次留下的值——probe_step 的 issued 第二次进入是 2；而 next_ticket 连调三次给出 1、2、3，第四次调用会给出 4，不会回到 1。注意这是两个不同的 static 变量（各自在自己的函数里），只是碰巧同名。

标准把这件事叫存储期（storage duration）。

标准原文标准原文：`static` 对象的寿命与初始化

C 语言标准 6.2.4 节「Storage durations of objects」第 2 段：

An object whose identifier is declared without the storage-class specifier _Thread_local, and either with external or internal linkage or with the storage-class specifier static, has static storage duration. Its lifetime is the entire execution of the program and its stored value is initialized only once, prior to program startup.

大意：带 static 声明的对象有静态存储期——它的寿命是整个程序的运行期间，而且它存的值只在程序开始之前初始化一次。「初始化只做一次」这句话常被读成「第一次调用时初始化」——不是：标准写的是 prior to program startup（程序开始之前）。所以 static int issued = 0; 里那个 = 0 并不是一条「每次进入都执行」的语句，它在 main 跑起来之前就由加载器安排好了。

出处：ISO/IEC 9899:2018（C17）§6.2.4 第 2 段。

大白话用大白话说：作用域管「谁能叫它」，生命周期管「它活多久」

这是两个互不相干的问题，新手总把它们揉成一个：

  • 作用域（scope）：名字在代码的哪一段能被写出来。issued 只在 next_ticket 里有效——出了这个函数，你写 issued 编译器会说不认识它；
  • 生命周期（lifetime）：这块内存从什么时候存在到什么时候。static int issued 从程序开始活到程序结束，就算没人叫得动它的名字，它也一直活着，值也一直在。

所以别问「这个变量在不在作用域里」和「它还活着吗」当成一个问题——它们是两个问题。

大白话（续）三方对照：三把尺子量三种变量

把两个问题分开问，三种变量的差别立刻清楚了：

变量 名字在哪能写 内存活多久 初始化
自动局部变量 int x; 函数内 那次调用期间 每次进入重新初始化
static 局部变量 static int x; 函数内 整个程序 只做一次
全局变量 int x;（文件外） 整个文件（加 extern 全程序） 整个程序 只做一次

最反直觉的一格是第二行：名字没变广，寿命变长了。这不是矛盾，是两个问题用了两把不同的尺子。

工程惯例工程惯例：`static` 局部变量很顺手，但请谨慎

这是工程惯例，标准对「该不该用」没有任何规定。它是「函数记住上一件事」的最省事写法（调用计数、缓存、惰性初始化都靠它）。代价有三条，都是真代价：

  • 不好测：它带着上一次调用的状态。第一个测试把计数器加到 3，第二个测试一开始读到的就是 4——除非你专门写一个「重置」函数（那又要把这个变量挪到文件作用域去）；
  • 不是线程安全的：两个线程同时进这个函数，issued = issued + 1 这种读-改-写会互相踩（本书不写多线程教程；数据竞争只是未定义行为的一种，第 8 章会把它和 UB 放在一起提一句）；
  • 藏起来的耦合：调用者看不见它、参数里也没有它，但它的值会影响返回值。读代码的人得钻进函数体才发现「这个函数有记性」。

判断标准：状态只属于「这个函数自己的历史」时用它（比如一个只打印一次的日志开关）；状态一旦需要被外部读取、重置或检查，就应该把它挪到文件作用域，用一组函数（get/reset）明确暴露出来。

还有一件小事值得知道：static 加在函数前面（7.6 的 stack_frames.c 里，inner 与 middle 就是这么写的）意思是完全不同的另一件事——这个名字只有本文件看得见：

  • 只在本文件用的小工具函数（inner、middle、print_at、rec_quiet 都属于这类）加 static，顺便避免和别人重名；
  • 对外提供的函数不加 static，声明写进头文件——它就是模块的门面。

命名上再补一句（这是惯例，不是标准）：内部函数不必加前缀，它们不可能被外部撞见；要装进库、给别人链接的对外函数才加模块前缀。本书的例子为了读起来短，对外函数都没加（sum_to、outer、factorial_rec、checked_isqrt 都是裸名）——它们各自活在自己的可执行文件里，撞不到谁；你以后写一个要被别人链接的模块，再按 fb_sum_to 这种形式加前缀。

标准原文标准原文：`NDEBUG` 一定义，`assert` 就消失

标准对这件事的原话很短，7.2.1 节「Program diagnostics」：

If NDEBUG is defined as a macro name at the point in <assert.h> where it is included, then assert is defined simply as #define assert(ignore) ((void)0)

大意：只要在包含 <assert.h> 的那一刻 NDEBUG 已经被定义，assert 就被定义成 #define assert(ignore) ((void)0)——一个什么都不做的空语句。所以 -DNDEBUG 不是「关掉某个开关」，而是让那句 assert(n >= 0); 从预处理结果里彻底消失：它一次都不会被执行，条件也不会被求值。

出处：ISO/IEC 9899:2018（C17）§7.2.1。

陷阱`-DNDEBUG` 的代价：断言里的副作用一起消失，边界也没了

你会看到什么：开发时一切正常，打包发出去的程序（用 -DNDEBUG 编译的）行为变了——不是「断言不再报错」这么温和，而是某条路上的检查整个不见了。

你会怎么误判：把 assert 当成「运行期的参数校验」——「用户传个负数进来，assert 会拦住它」。可发布版里它压根不存在。

真相有两条，第二条更贵：

  • assert 是给程序员抓 bug 的，不是给用户兜错的。给用户的非法输入要用真正的判断分支加错误码（checked_isqrt 里的 if (n < 0) return -1; 才是那一层）；
  • 永远不要在 assert(...) 里写有副作用的东西：assert(p = malloc(n)); 或者 assert(++count > 0); —— 在 -DNDEBUG 下这两行会整句消失，malloc 不调用、count 不自增。这类 bug 的可怕之处在于：打开断言的调试版一切正常，关掉断言的发布版行为完全不同。

最后两件事，都属于「怎么写一个函数」的工程判断。

第一件：多返回值的两条路。 C 的 return 一次只能交回一个值，所以「算出一个位置 + 一个状态」这种需求要自己打包。工程上常走的路有两条，第 4 章与第 5 章各会展开一条：

  • 打包成结构体交回（第 5 章 chapters/ch05/01-structs-and-alignment.md 讲）：struct result { long long value; int ok; }; 然后 return r; —— 调用方拿到的是一整块，读起来清爽；代价是结构体按值返回会有一次拷贝（结构体大了不便宜）；
  • 用输出参数（第 4 章 chapters/ch04/03-pointer-idioms.md 讲，7.3 那个 swap_ok(int *a, int *b) 已经是它的雏形）：int parse(const char *s, long long *out) —— 函数返回 int 当状态码，真正的结果写进 *out。代价是调用处必须传对指针，而且 if (parse(s, &v) == 0) 这种「返回值既当结果又当状态」的写法容易读错。

本书的惯例：状态用返回值、结果用输出参数时，返回值统一约定 0 表示成功（本书的流水线里那一堆 exit 码就是这个约定），并且在函数名或注释里写清楚这个约定——因为编译器不认识它。

第二件：一个函数一件事。 判断标准不是行数，是这两个信号：

  • 参数越来越多（超过四五个，尤其是好几个 bool 开关）：多半是它同时干了好几件事，或者把「配置」和「数据」混在了一起。开关型参数尤其危险：f(data, true) 在调用处读起来根本不知道那个 true 是什么。拆成两个函数，或者把开关收进一个结构体；
  • 分支越来越多（一层层 if 里套 switch）：多半是它要处理好几种「情形」。把每种情形拆成独立的函数，主函数退化成一句 switch ——读代码的人只要看那一句就知道一共有几种情形。

这条纪律在第 1 章的目录树里就埋下了：为什么从第二个项目起不许单文件工程？因为文件是拆函数之后，代码放下的下一个层级——函数管「一件事」，文件管「一组相关的事」。

小结这一节的要点
  • 函数有两半：声明（原型）进头文件、定义进 .c；定义文件也包含自己的头文件，编译器才会当场核对两半一致（不一致就是 conflicting types）。
  • C 只有值传递：形参拿到的永远是拷贝，改形参改不到调用者，要改就传地址；f(void) 写明「没有参数」、f() 只是「没说」，多传一个实参一个当场报错、一个静默通过；实参求值顺序是「未指定」，别依赖。
  • 一次调用 = 一层栈帧（参数、局部变量、返回地址，本机每帧 0x40），gdb 的 bt / info frame / finish 能把它们逐个指认出来；递归 = 基准情形 + 递归情形，代价是栈（本机约 2 MB、sum_down 每层 48 字节），二十万层的结局是退出码 3221225725——-O2 可能把它改成循环，但那是运气不是承诺。
  • 作用域与生命周期是两件事：static 局部变量名字仍只在函数内，寿命却是整个程序、只初始化一次、住在数据区；assert 是给程序员的前置条件，-DNDEBUG 会让它整个消失——所以兜底分支与「断言里不放副作用」都不能省。

注自测题答案
  1. 为了让声明与定义出现在同一个编译单元里，编译器会逐项核对两半是否一致（参数类型、返回类型）。不包含的话就没有可比的对象：定义照着错的方式写它自己也不知道，错误往往推迟到调用方那里（甚至推迟到运行期给你一个荒唐的结果）。证据：把定义写成 double celsius_to_fahrenheit(float c)，编译期报 error: conflicting types …，并用 note: 指回 include/func_basics.h:9。
  2. 因为C 只有值传递：swap_bad(x, y) 把 1 和 2 这两份值拷进形参，函数换的是两份副本，函数返回后副本随栈帧消失，x、y 从头到尾没动；swap_ok(&x, &y) 拷进去的虽然是拷贝，但拷贝上写的是地址，顺着地址写就能改到调用者那块内存。所以打印出来是「1/2 不变」和「2/1 变了」。
  3. (void) 写明「这个函数没有参数」，() 只说「参数情况没说」（标准 6.7.6.3 节把两者区别对待）。本机实测：modern(1) 编译期报 error: too many arguments to function 'modern'; expected 0, have 1；legacy(21, 999) 编译通过、运行时打印 42（多出来的 999 被无声吃掉）——后者是未定义行为，本机这次的选择是「忽略多余实参」。另外 -Wall -Wextra 不报 ()，要 -Wstrict-prototypes 才报。
  4. 退出码 3221225725（0xC00000FD，栈溢出；MSYS bash 里 echo $? 显示 127，PowerShell 读 Start-Process 的 ExitCode 显示 -1073741571，三种写法是同一个数）。加 -O2 不崩是因为优化器把这种递归改写成了循环，栈上不再一层层堆帧——它只是「可能」这么优化，标准没有任何承诺，改一行代码、换一个编译器就可能变回去。所以不能当安全证据；要安全就写成迭代，或者用 DEPTH 这类参数把深度控制在栈限额之内。
  5. next_ticket 里的 issued：作用域是函数内（外面写不出这个名字），生命周期是整个程序（初始化只做一次，函数返回后它还在数据区）；auto_ticket 里的 issued 两者都限于那次调用（每次进入都是一块新内存）。地址层面的证据来自同一节的 probe_step——那是另一对同名变量（在另一个函数里），正好拿来对照：它的 static issued 两次进入都是 0x7ff774697044，而自动的 fresh 两次分别是 0x5ffe3c 与 0x5ffdfc。-DNDEBUG 让 assert(...) 被替换成 ((void)0)（标准 §7.2.1 的原话），整句宏体消失，于是括号里的 ++count 一次都不执行——断言不能被用来做任何有副作用的事。
