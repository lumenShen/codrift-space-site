3.1 先看工程长什么样

第 1 单元那个项目是草稿：一个目录、几个 .c，编译命令里只有一个源文件。从这一节起，本书的硬规定③生效——从第二个项目（examples/ch02/）开始，不允许出现单文件工程。所以这一节的第一件事不是讲类型，而是看目录。

上一张图的第 1 帧是这一节故事的起点，第 2、3 帧是本节搭起来的 examples/ch02/：八个例子目录（分两帧摆完），每个只负责一件事——量字节、认字符、抓浮点、数回绕、对格式串、看转换、玩字面量、故意编不过。下面那张图的第 1、2 帧是每个例子目录里面的样子，也是全书第一次出现 src/ 与 include/：main.c 只写「做实验、报结果」，打印这件事单独放进 report.c，而 report.c 里那几个函数长什么样，写在 report.h 里——声明放头文件，定义放源文件。它的第 3、4 帧是本节顺手抓下来的五段会话与一个探针，3.5 节到 3.9 节会逐个点到它们。

为什么要分家？标准对这件事没有任何规定（它只要求一个程序有一个 main）。分家是工程惯例，理由在第 1 单元 1.7 节讲过：编译速度、接缝可见、能被接手。这里只补代价——改一次头文件，所有包含它的编译单元都要重编；头文件里多写一行不该写的（比如函数定义），链接时会撞符号。

工程惯例工程惯例：头文件里放什么、不放什么

这是惯例，不是标准（标准里压根没有「头文件」这个概念，只有「被 #include 就地展开的文件」）：

  • 放声明（函数原型、类型定义、宏）——多个 .c 都需要知道「这个名字长什么样」；
  • 不放函数定义——#include 是文本复制，同一个定义被复制进两个 .c，链接期就是 multiple definition；
  • 头文件自己包一层 #ifndef XXX_H / #define XXX_H / #endif，防止同一个文件被包含两次。

代价是你要多维护一层「谁声明、谁定义」的对应关系；好处是接缝摆在明面上：report.h 里那几行，就是这个模块对外承诺的全部内容。

先只看第一段表格，这些数字要背下来（背的是本机的，不是永远的）：

  • char 1 字节、short 2、int 4、long 4、long long 8；
  • float 4、double 8、long double 16（注意：16 是它的存储开销，不是它的精度）；
  • void * 8：本机是 64 位系统，一个地址 8 个字节；
  • _Bool 1：它是最小的整数类型，只能存 0 与 1。unsigned char/short/int/long/long long 不用逐个打——标准要求每个有符号整数类型都有一个同样宽的无符号版本（6.2.5 节），所以它们的字节数与上面那一半相同。

int 是 4 个字节、long 也是 4 个字节，这一条是本书特意要你记住的：在别的机器上，long 常常是 8。所以同一份代码里，int 顶不顶得住、long 够不够长，都是要看平台的。

第 1、2、3 帧说的是一件很容易被忽略的事：类型决定你一次搬动几个盒子。int 一次 4 个、double 一次 8 个、char 一次 1 个。第 4 帧是下一段的引子：盒子的个数定了，能表示的值就有上下界，而 int 与 unsigned 用的是同样多的盒子、能表示的值却不是一套。

边界在哪：问 <limits.h>，别背

INT_MAX 是多少、CHAR_BIT 是几，都不用猜——<limits.h> 里每个都有名字。<limits.h> 与 <float.h> 就是干这个的：它们不提供函数，只提供一堆宏，每个宏是一个常量表达式，展开出来就是这台机器的那个数字。

上面那个输出块的 == <limits.h> 那一段就是这些边界。三行要连着念（我把它们抄出来，你对着块里的原文看）：

  • CHAR_BIT 8 CHAR_MIN -128 CHAR_MAX 127 MB_LEN_MAX 5：一个字节 8 位；plain char 的范围是 −128..127，所以本机的 char 是有符号的——这条 3.4 节还要用；MB_LEN_MAX 是「多字节字符最多几个字节」，本机是 5；
  • INT_MIN -2147483648 INT_MAX 2147483647 UINT_MAX 4294967295：int 能表示 −2³¹..2³¹−1；同样四个字节的 unsigned 换成 0..2³²−1；
  • LONG_MIN -2147483648 LONG_MAX 2147483647 ULONG_MAX 4294967295：这一行是「long 与 int 一样宽」的另一个说法——LONG_MAX 和 INT_MAX 是同一个数（换台机器通常就不是了）。
标准原文标准原文：`<limits.h>` 给的是「至少这么大」

Their implementation-defined values shall be equal or greater in magnitude (absolute value) to those shown, with the same sign.

大意：标准只规定下界——比如它要求 INT_MAX 至少是 +32767、INT_MIN 至多是 −32767，至于本机是 2147483647 还是 9223372036854775807，由实现决定（implementation-defined）。所以「int 有多大」这个问题，标准给的答案是范围，本机给你的才是数字。

同一节里 CHAR_BIT 的定义是「number of bits for smallest object that is not a bit-field (byte)」，列出的是 8；本机实测也是 8，但它属于「实现定义的 8」，不是「永远 8」。

这一节的名字是 5.2.4.2.1 节「Sizes of integer types <limits.h>」。

出处：ISO/IEC 9899:2018（C17）§5.2.4.2.1。

实验记录本机实测：这一节的数字全是跑出来的
  • 工具链：gcc 16.1.0（-std=c17，也就是 C17），目标三元组 x86_64-w64-mingw32，Windows 10 x64 (MSYS2 UCRT64)；
  • 命令：gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -Iinclude src/main.c src/report.c -o app，工作目录是 examples/ch02/type_sizes/；
  • 结果：编译退出码 0，程序退出码 0，stdout 共 16 行（就是上面那个输出块的全部内容）；
  • 关键读数：sizeof(long) = 4、LONG_MAX = 2147483647、CHAR_BIT = 8、sizeof(void *) = 8、sizeof(long double) = 16；
  • long double 占 16 个字节不代表它有 128 位精度：本机它的有效十进制位数是 LDBL_DIG = 18，比 double 的 15 位多不了多少。

这些数字由流水线逐字对账（清单 examples/ch02/type_sizes/type_sizes.json，mode=run，没有额外的检测参数）：正文里那个 output 块与程序真实 stdout 差一个字符都会报 stale_output。

实验记录（续）本单元用的是哪几种「检测」

本单元没有用任何检测模式（detect）：八个清单里七个是 mode=run、一个是 mode=compile_fail。正文里另外那几条诊断，全部来自显式打开的警告开关（-Wfloat-equal、-Wconversion -Wsign-compare、-Wvla，以及基础参数就带着的 -Wtype-limits）——它们都是真编译的 stderr，会话原文存在各自例子的 session-*.txt 里。

陷阱`sizeof` 是「字节数」，不是「能装多大的数」

这两个问题看起来像一回事，其实差了八个数量级：sizeof(int) 是 4，INT_MAX 是 2147483647。前者的单位是字节，后者是一个数本身。

你怎么会被坑到：写循环算容量时，把 sizeof(int) 当成「能装的最大整数」（以为 4 就是上限），于是给 int 加个 5 就以为溢出了；或者反过来，以为 INT_MAX 是「4 个字节」，写出 char buf[INT_MAX] 这种申请 2GB 的声明。

3.3 <float.h>：浮点能信几位

<float.h> 回答的是另一个问题：浮点数的精度。还是刚才那个输出块，最后四行（== <float.h>：浮点的有效位数与边界 == 那一段）：

  • FLT_DIG 6 DBL_DIG 15 LDBL_DIG 18
  • FLT_MIN 1.1754943508222875e-38 FLT_MAX 3.4028234663852886e+38
  • DBL_MIN 2.2250738585072014e-308 DBL_MAX 1.7976931348623157e+308

三个 _DIG 宏值得一个一个字读：

  • FLT_DIG = 6：float 在十进制下能信 6 位数字；
  • DBL_DIG = 15：double 能信 15 位；
  • LDBL_DIG = 18：本机 long double 能信 18 位（虽然它占了 16 个字节）。

FLT_MIN / FLT_MAX 那一对是取值范围（不是精度）：本机 float 能表示到 3.4028234663852886e+38，往下到 1.1754943508222875e-38（再小就是非规格化数了）。%.17g 打印出来这么长，是因为这个打印精度足以暴露双精度里每一位——3.5 节会看到，正是因为只有 15 位可信，第 16、17 位才那么难看。

标准原文标准原文：`DBL_DIG` 说的是什么

<float.h> 的 DBL_DIG 定义是：

number of decimal digits, q, such that any floating-point number with q decimal digits can be rounded into a floating-point number with p radix b digits and back again without change to the q decimal digits

大意：DBL_DIG 是「十进制下，来回转换不变形的位数」——把一个十进制数读进来再打印回去，前 q 位是可信的，第 q+1 位开始就可能变。标准给出的下界是 DBL_DIG 至少 10，本机给的是 15。

这一节的名字是 5.2.4.2.2 节「Characteristics of floating types <float.h>」。

出处：ISO/IEC 9899:2018（C17）§5.2.4.2.2。

标准原文标准原文：浮点长什么样，标准只给一个模型

The characteristics of floating types are defined in terms of a model that describes a representation of floating-point numbers and values that provide information about an implementation's floating-point arithmetic.

An implementation that defines __STDC_IEC_559__ shall implement floating point types and arithmetic conforming to IEC 60559 as specified in Annex F.

大意：标准只规定一个模型（符号位 s、基数 b、指数 e、尾数），不要求浮点一定是 IEEE 754；只有实现自己声明了 __STDC_IEC_559__，才必须按 IEC 60559（就是大家说的 IEEE 754）来。

这一节的名字是 5.2.4.2.2 节「Characteristics of floating types <float.h>」。

出处：ISO/IEC 9899:2018（C17）§5.2.4.2.2 第 1 段。

这段「模型 vs 具体实现」的区分，3.5 节会变成一行真实输出：0.1 + 0.2 不等于 0.3，原因不在 C 语言这一层，在用二进制存十进制小数这件事上。

3.4 char 的三重身份：'0'、0、'\0'

第二个例子 char_identity 要拆穿 C 里最容易混的三个「零」。它跑出来是这样：

三个数的答案，一句话记牢：

  • '0' 是 48（十六进制 0x30）。它是字符零，键盘上那个 0 键打出来的东西。所有数字字符都是连着的：'0' 是 48，'1' 是 49，'9' 是 57——所以「字符转数字」才写 c - '0'。
  • 0 是 0。它就是整数零。
  • '\0' 也是 0。它是转义写法，写的是「那个值为 0 的字节」，也就是字符串的结束标记。

'0' 与 0 差 48，'\0' 与 0 一模一样——这就是为什么第 1 单元里 word[2] 打出来是 0。

同一个例子还回答了另外三个问题，都在输出里：

  • 字符字面量的类型是 int，不是 char：输出里 sizeof('0') = 4，而 sizeof((char)'0') = 1。这不是笔误，是标准明文规定的（见下面的标准块）。所以 '0' 和 sizeof 一撞，结果会是 4。
  • "0" 与 "\0" 都是 2 个字节：一个是「字符 0 + 结束标记」，另一个是「值为 0 的字节 + 结束标记」。它俩长得完全不同，sizeof 却一样大——看 sizeof 是分不出来的，得看内容。
  • c == '0' 与 c == 0 是两件事：输出里 c 里装的是字符 '0'，所以 c == '0' 是真，c == 0 是假。把这两行连起来读：一个变量里「有个 0 的样子」和「值是 0」完全是两码事。
标准原文标准原文：字符字面量是 int

An integer character constant has type int.

大意：单引号包起来的字符常量，类型是 int——注意不是 char。（顺带一提，在 C++ 里它是 char；这是 C 与 C++ 少数会咬人的差异之一。）

这一节的名字是 6.4.4.4 节「Character constants」。

出处：ISO/IEC 9899:2018（C17）§6.4.4.4 第 10 段。

陷阱`char c = getchar(); if (c == EOF)` 这个坑

getchar() 返回的是 int（因为要能表示 EOF，EOF 是 −1）。如果你把结果先存进一个 char（本机 char 有符号，装得下 −1，看起来还对），再和 EOF 比，在另一台 char 无符号的机器上就会永远不相等。

你怎么会被坑到：本机这么写能跑对，你会以为它是对的，然后把这份代码带到别的平台。想知道本机的 plain char 到底是有符号还是无符号，别背书，问 CHAR_MIN：输出里那行 (char)200 = -56 就是答案的一半——(char)200 变成了负数，说明 char 装不下 200，它是有符号的（本机 CHAR_MIN = −128）。

上面 char_identity 那个输出块里，== 同一个 200，装进三种 char == 那一段是最值钱的三行：(char)200 = -56、(signed char)200 = -56、(unsigned char)200 = 200。

同一个 200，装进三种 char 得到三行、两种结果——本机的 plain char 就是 signed char，所以它俩一样；只有 unsigned char 走另一条路。char 装不下 200，于是它变成了 −56——注意这不是溢出，这是转换，标准允许它这样（见 3.8 节的标准块）：char 是有符号的、只有 256 个格子，200 落在外面，结果由实现决定。本机 gcc 的选择是「把 200 按 8 位补码读回来」。

标准原文标准原文：`char` 到底有没有符号

The three types char, signed char, and unsigned char are collectively called the character types. The implementation shall define char to have the same range, representation, and behavior as either signed char or unsigned char.

大意：char、signed char、unsigned char 是三种不同的类型；char（书里常叫 plain char）具体走哪一路，由实现决定——要么跟 signed char 一样，要么跟 unsigned char 一样，没有第三种可能。

这一节的名字是 6.2.5 节「Types」。

出处：ISO/IEC 9899:2018（C17）§6.2.5 第 15 段。

工程惯例工程惯例：什么时候用哪一种 char

三种 char 各有岗位，这是惯例（标准只说它们是三种类型）：

  • char：只当文本用——存字母、做字符串，从不拿它做算术；
  • signed char / unsigned char：当小整数用。特别地，「一个字节的原始数据」（二进制、位运算、memcpy 的目标）一律用 unsigned char，因为它没有符号位、不会在提升时变成负数（第 4 单元会讲提升）。
  • 判「这个字节是不是可打印字符」这类事，先把它转成 unsigned char 再传给 <ctype.h> 的函数：那些函数的形参是 int（本机 ctype.h 里写的是 int __cdecl isprint(int _c);），但要求传进来的值要么是 EOF、要么落在 unsigned char 的范围内——直接传一个负的 char 会越界查表。

代价是你要在「这是文本还是数据」上做一个明确的决定——而这个决定恰好能挡掉后面一大类 bug。

3.5 浮点：0.1 + 0.2 为什么不等于 0.3

现在到了这一节的主菜。float_trap 这个例子只有两件事要做：算一遍 0.1 + 0.2，再用两种办法判断它等不等于 0.3。

把输出的前三个数抄下来对着看：

  • 0.1 + 0.2 = 0.30000000000000004441
  • 0.3 = 0.29999999999999998890
  • 差 = 0.00000000000000005551

三个数都不是「0.3」，也都不是乱码——它们是真实存在的双精度数。写 0.1 的时候，编译器要把它塞进 8 个字节（第 2 帧那 8 个盒子），而 0.1 在二进制里是无限循环小数（就像十进制里 1/3 = 0.333… 写不完）。所以存进去的从一开始就是「离 0.1 最近的那个双精度数」，不是 0.1 本身。两个近似值相加，误差累到一起，结果自然不是 0.3。

所以「用 == 比较两个浮点数」是错的——不是编译器有 bug，是你问的问题本身没有意义：sum == 0.3 问的是「这 64 位全一样吗」，答案是「不」，于是输出里那行是 假。

正确的问法是「够不够近」：

第 12 行是 eps 比较的全部内容：|a − b| <= eps 就算相等。eps 取多大是工程决定，不是数学定理：本书例子里取 1e-9（十亿分之一），因为这一节的数都是「量级为 1」的数。经验规则是 eps 取「你要的幸福度」——比较 1 米长的东西，1e-9 米就是 1 纳米；比较 10 亿，那 1e-9 就太严了。

陷阱浮点比较这个坑，真正的坑法是「它有时又是对的」

0.5 + 0.25 == 0.75 是真的，1.0 / 8.0 == 0.125 也是真的——只要是 2 的幂组合出来的数，二进制能精确表示，== 就正常工作。

你怎么会被坑到：你拿几个「友好」的数试了试，== 都是对的，于是放心地把它写进代码；等到某一天数据变成 0.1 那一类，比较开始莫名其妙地失败，你回头怀疑的是「是不是我算错了」。记住这条分界线：能写成 / 2^n 的十进制小数是精确的，其他的都不是。想验证，把 %.20f 加上去打印——40 毫秒就能看出真相。

FLT_DIG / DBL_DIG 在这里派上用场：它们的含义就是上一条陷阱的量化版本——double 只有 15 位十进制数字可信，%.17g 那种打印（3.7 节的 format_zoo 会用到）已经能看到「不可信」的那些位了。所以本书写代码的规矩是：要判断浮点相等，写一个 nearly_equal；== 只准用在「这个值是从哪抄过来的，我一清二楚」的场合。

输出块最后一行 (float)INT_MAX = 2147483648 是同一件事的另一种量法：INT_MAX 的 31 位有效数字，float 只有 24 位尾数，装不下，于是它被舍到最近的「24 位能表示的数」上。整数能精确表示而浮点不能，这条界线在这里看得最清楚。

3.6 无符号的两个坑：倒序循环与回绕

unsigned 不是「只有正数的 int」这么简单，它有自己的算术规则。第四个例子 unsigned_sink 把两个最常踩的坑放在一起：

先读上面那个输出块的第一段。countdown_bad 打出来的是 i = 3、i = 2、i = 1、i = 0、i = 4294967295、i = 4294967294——它在 0 那里没有停。走到 0 之后再 i--，i 变成了 4294967295（UINT_MAX），而不是 −1。这就是第一个坑：i >= 0 对 unsigned 来说永远为真，循环条件恒成立，真实的程序在这里会一直转下去（本书的闸门有 15 秒超时，所以 countdown_bad 多带了一个 show 参数：打满 6 行就 return，让你看见它不在 0 处停）。同一个输出块的第二段是 int 版本，它正常停在 0。

第二个坑是「减出来一个巨大的数」：

  • u - 1 = 4294967295（u 是 unsigned 0）
  • (int)(u - 1) = −1

第一行是真·无符号算术：无符号的运算结果按 2³² 取模，−1 落在圈上就是 4294967295。第二行是「把它当 int 读出来」的结果，那是实现定义的（下一节讲）。

第 1 帧是这一圈的全貌：unsigned 的四个字节能表示 2³² 个值，0 和 4294967295 是相邻的。第 2 帧是 u - 1 的落点——不是 −1，是 4294967295。第 3 帧解释了为什么 i >= 0 在这圈上处处为真：这一圈上没有负数，所以「大于等于 0」是对所有值都成立的废话。

标准原文标准原文：无符号运算不会溢出，只会绕圈

A computation involving unsigned operands can never overflow, because a result that cannot be represented by the resulting unsigned integer type is reduced modulo the number that is one greater than the largest value that can be represented by the resulting type.

大意：无符号运算不会溢出（也不会是未定义行为）——超出范围的结果按「最大值加一」取模，也就是在圈上绕。四个字节的 unsigned 最大值加一是 2³²，所以 0 − 1 得到 2³² − 1 = 4294967295。这是标准规定的行为，不是本机的怪癖：换台机器、换个编译器，这个数还是 4294967295（只要 unsigned 是 32 位）。

出处：ISO/IEC 9899:2018（C17）§6.2.5 第 9 段。

编译器视角编译器视角：`i >= 0` 恒真这件事，它知道

陷阱`for (unsigned i = n - 1; i >= 0; i--)` 这一行会咬人

它不是「多转一圈」，它是永远不结束：如果循环体里有 printf 或写文件，你会得到一个几十 GB 的输出文件；如果循环体里有数组下标，你会读到 a[4294967295]（越界读，按标准是未定义行为——这两句是推断，本书没有为它们单独做例子）。

你怎么会被坑到：编译器给的 -Wtype-limits 警告会被你当成「风格建议」忽略掉——毕竟程序确实编译通过了。写倒序循环时，正确的写法有两条：用 int（for (int i = (int)n - 1; i >= 0; i--)），或者用 i > 0 加一次单独处理 0。本书推荐第一条：下标本来就是 int 的活。

3.7 格式串与类型必须匹配

printf 的格式串与实参之间，运行期没有任何检查：%d 说「从这个位置上取走一个 int」，printf 就真的去取一个 int。你递上去的要是别的东西，取出来的就是别的东西。format_zoo 把同一个值换成各种格式串打了一遍：

一行一行对着看，规律很硬：

  • 整数按有无符号分家：int 用 %d，unsigned 用 %u。同一个 42，%d 与 %u 打出来一样；同一个 −1，%d 打出来是 -1，而 %x 打出来是 ffffffff——那正是 4294967295 的十六进制写法；
  • 同一个整数可以换进制看：%d 十进制、%x 小写十六进制、%X 大写、%o 八进制。输出里 int -1 的十六进制是 ffffffff、八进制是 37777777777——这就是 3.6 节那一圈在十六进制下的样子。注意 show_int 里对 %x/%X/%o 传的是 (unsigned)value：这三个格式串要的是 unsigned，把 int 直接递上去就是下面标准块说的那种未定义行为（本机这样写也能打出同样的数，但那是 ABI 的运气，不是保证）；
  • 浮点有四种常用长相：%f（定点，6 位小数）、%e（科学计数法）、%g（自动挑前两种里短的那个）、%.17g（把双精度里每一位都摊开）。同一个 1.0/3：%f 是 0.333333，%e 是 3.333333e-01，%.17g 是 0.33333333333333331——最后这个尾巴就是 3.5 节说的「不可信的那些位」；
  • size_t 用 %zu、long long 用 %lld、定宽类型用 PRI 宏：输出的最后五行就是这五条。size_t 是 sizeof 的结果类型，也是 strlen 的返回类型——这两个地方的返回值用它准没错。
语法规则格式串的配对规则

一个格式串里的每个 %… 都对应后面一个实参，类型必须对得上：整数的有符号与无符号要分家（%d / %u），长度要匹配（%zu 给 size_t、%lld 给 long long），浮点用 %f / %e / %g 三兄弟。配错了标准不要求编译器报错（见下面的标准块），所以这条规矩只能靠你自己守。

一份「谁配谁」的对照表：

值的类型 格式串 说明
int %d（或 %i） 十进制，有符号
unsigned %u 十进制，无符号
unsigned（int 要先转过去） %x / %X / %o 十六进制小写 / 大写 / 八进制
double %f / %e / %g 定点 / 科学 / 自动
size_t %zu sizeof 与 strlen 的结果
long long %lld 八字节整数
uint32_t 这类定宽类型 PRIu32 / PRId64 / PRIx32 宏，定义在 <inttypes.h>

最后一行要单独说一句：uint32_t 在有的平台是 unsigned int、在别的平台可能是 unsigned long。所以你不能写死 %u 或 %lu，得写 PRIu32——它是个宏，展开出来正好是这台机器该用的那个格式串。

<stdint.h> 给的正是这种「宽度写在名字里」的类型：int8_t/int16_t/int32_t/int64_t 与它们的 uint 版本，外加 INT32_MAX、INT64_MAX 这类边界宏。输出最后两行就是实测：int32_t 的上界是 2147483647，int64_t 是 9223372036854775807，各自用 PRId32 / PRId64 打出来。它们的含义是「恰好这么多位」，而 int 只保证「至少 16 位」——这就是为什么文件格式、协议、二进制数据要指定宽类型：跨机器时你要的是那个位数，不是那台机器顺手给的那个宽度。

标准原文标准原文：`PRIu32` 这类宏是什么

Each of the following object-like macros expands to a character string literal containing a conversion specifier, possibly modified by a length modifier, suitable for use within the format argument of a formatted input/output function when converting the corresponding integer type.

大意：PRI 打头的这些宏展开出来是一段格式串（是字符串字面量），专门给对应的整数类型用。所以写法是 printf("%" PRIu32 "\n", v)——三段文字在预处理期拼成一个格式串。

这一节的名字是 7.8.1 节「Macros for format specifiers」。

出处：ISO/IEC 9899:2018（C17）§7.8.1 第 1 段。

Otherwise, the new type is signed and the value cannot be represented in it; either the result is implementation-defined or an implementation-defined signal is raised.

大意：往有符号类型里塞一个装不下的值，结果是实现定义的（或者由实现决定要不要抛个信号）——标准允许 gcc 给出 −56，也允许别的实现给出 0、给出 127，甚至报错。所以「200 装进 char 会变成 −56」这句话，正确的说法是「本机是这样」；想写可移植的代码，就别依赖这个值。

出处：ISO/IEC 9899:2018（C17）§6.3.1.3 第 3 段。

标准原文标准原文：`double` 装进 `int` 是另一回事

When a finite value of real floating type is converted to an integer type other than _Bool, the fractional part is discarded (i.e., the value is truncated toward zero). If the value of the integral part cannot be represented by the integer type, the behavior is undefined.

大意：浮点转整数规定丢掉小数部分（向零截断）——这一半是确定的；但如果连整数部分都装不下（比如把 1e10 塞进 int），那就是未定义行为，不是「绕一圈」。

出处：ISO/IEC 9899:2018（C17）§6.3.1.4 第 1 段。

上面这两条合起来，正好回答本节反复出现的那个问题：值不对的时候，先分清是哪一种。

  • 又窄又装不下：int → char 越界是实现定义（6.3.1.3 节，本机 −56、别的编译器可以是别的值，不可移植）；double → int 丢小数那半是标准规定的向零截断，但整数部分装不下就升级成 UB（6.3.1.4 节）；
  • 溢出（下一单元）：INT_MAX + 1、1e10 塞进 int——这类是未定义行为，编译器有自由，下一单元（chapters/ch02/02-integer-promotion-and-overflow.md）整节讲它。

所以「值不对」要分三层看：标准规定的（无符号回绕、向零截断）、实现定义的（有符号类型装不下、char 有没有符号）、未定义的（有符号溢出、浮点转整数越界）。越往下越不能靠猜。

  • 0x 开头是十六进制（0x1F = 31）；
  • 0 开头是八进制——所以 010 是 8，不是 10。这是 C 里最经典的安静陷阱之一：int mode = 010; 看起来是「十号模式」，实际是「八号」；
  • 其余是十进制。

再往后是后缀，它决定这个字面量的类型（不只是值）：1 是 int（4 字节）、1u 是 unsigned（4 字节）、1L 是 long（本机也是 4 字节，因为它跟 int 一样宽）、1LL 是 long long（8 字节）、1.0f 是 float（4 字节）、1.0 是 double（8 字节）。后缀不是可有可无的装饰：1u 与 1 在算术里会走出不同的结果，这就是下一个代码块里 1u - 2 = 4294967295 的原因——1u 是无符号的，减出来按 3.6 节那一圈走；写成 1 - 2 就老老实实是 −1。

第二块讲 sizeof 的一个反直觉性质：

输出里那行是 sizeof(i++) = 4，执行完这一行 i 还是 0。i++ 写了，但没发生——因为 sizeof 只需要知道「这个表达式的类型是什么」，不需要算出它的值。这是 sizeof 与函数调用最大的区别：它是编译期的东西。唯一的例外是变长数组——sizeof(VLA) 的操作数会被求值、结果也不是常量，3.9 节会看到本机的那个 VLA。

标准原文标准原文：`sizeof` 求什么、返回什么

The sizeof operator yields the size (in bytes) of its operand, which may be an expression or the parenthesized name of a type. The size is determined from the type of the operand. The result is an integer. If the type of the operand is a variable length array type, the operand is evaluated; otherwise, the operand is not evaluated and the result is an integer constant.

The value of the result of both operators is implementation-defined, and its type (an unsigned integer type) is size_t, defined in <stddef.h> (and other headers).

大意：两句话，一句管「求不求值」，一句管「结果是什么类型」。

  • 除了变长数组那种情况，操作数不被求值——所以 sizeof(i++) 不会让 i 变；
  • 结果的值由实现定义（这就是「本机 sizeof(int) 是 4，别的机器可能是 2」的标准出处），类型是 size_t（一个无符号整数类型，%zu 就是给它用的）。

这一节的名字是 6.5.3.4 节「The sizeof and _Alignof operators」。

出处：ISO/IEC 9899:2018（C17）§6.5.3.4 第 2、5 段。

陷阱「字节数是实现事实」这句话，会以两种方式咬你（一）

第一种：跨平台时数字变。本机 sizeof(long) 是 4，Linux 64 位上是 8。你用 long 当「64 位整数」写代码，换台机器就溢出或者截断。要固定宽度，用 <stdint.h> 的 int32_t / int64_t。

陷阱（续）它会咬你的第二种方式

第二种：同一台机器上也变——sizeof 给的是「几个字节」，不是「能装多大的数」。sizeof(int) == sizeof(float)（都是 4），但 int 装不下 3.5，float 也装不准 INT_MAX：float_trap 的输出里有一行 (float)INT_MAX = 2147483648（float 的尾数只有 24 位，装不下 31 位里的每一位）。别把两个 4 当成「可以互相替代」。

你怎么会被坑到：写文件读写时用 fwrite(&n, sizeof(int), 1, f)，看起来「平台无关」，实际上文件的字节序与宽度两台机器可以不同——那种场景该用定宽类型加显式的字节序转换。

const int 是「只读变量」，不是「常量」——这是 C 与 C++ 的一个重要差异：在 C++ 里上面第三行是合法的常量数组，在 C 里它是变长数组。原因在标准的一句话里：

标准原文标准原文：什么叫「整数常量表达式」

An integer constant expression shall have integer type and shall only have operands that are integer constants, enumeration constants, character constants, sizeof expressions whose results are integer constants, _Alignof expressions, and floating constants that are the immediate operands of casts.

大意：能进「整数常量表达式」这个俱乐部的，只有整数常量、枚举常量、字符常量、sizeof 的结果、_Alignof 的结果这几样。变量不在名单里——哪怕它被 const 修饰、哪怕它明明等于 7。const 管的是「不准通过这个名字改它」，那是运行期的性质。

注意这条只约束定长数组：长度不是整数常量表达式时，那个数组就是变长数组（VLA），标准对它有另一套规定（6.7.6.2 节），sizeof 也改在运行期求值。

这一节的名字是 6.6 节「Constant expressions」。

出处：ISO/IEC 9899:2018（C17）§6.6 第 6 段。

变长数组本书不教，这是一个明确的取舍：它从 C99 起进入标准，但从 C11 起变成「实现可选」：实现可以定义 __STDC_NO_VLA__ 表示不支持（MSVC 就不支持，那份代码在它那里编不过）。而且在栈上按运行期的大小开数组，很容易在输入变大时把栈撑爆（int a[n]，n 来自用户输入——这一条是推断，本书没有为栈溢出单独做例子）。要动态大小，用 malloc（第 12 单元）——显式的堆分配能报错，隐式的栈增长只能崩。

工程惯例工程惯例：`#define` / `enum` / `const` 怎么选

标准对这三样没有任何偏好，怎么选是惯例问题：

  • enum：一组相关的整数常量，且它们要一起出现在类型系统里（状态码、模式）。优点：是常量表达式，能当数组长度、能进 case，调试器里还能显示名字；
  • #define：需要「还没到语法层就得是常量」的场合（#if 里判断、条件编译），或者要给字符串拼格式串（PRIu32 就是）。缺点：它是文本替换，没有类型，出错时报错信息很难看；
  • const：真正的「只读对象」——指针目标、函数参数、const char * 这类接口约定。别拿它当常量表达式用（原因见上）。
工程惯例（续）这个选择的代价

代价是你要在动手前想一下「这个东西是常量还是只读对象」——这个问题想清楚了，第 16 单元讲宏的时候会轻松很多。

工程惯例工程惯例：整数类型怎么选

一个能省掉大量 bug 的经验顺序（惯例，标准不管这些）：

  1. 默认用 int。算术、下标、循环计数，int 够用就用 int——它是这台机器最自然的宽度；
  2. 需要「不比 int 小」时用 long long，本机的 long 与 int 一样宽，别指望 long 更宽；
  3. 需要确定的宽度就用 <stdint.h> 的定宽类型（int32_t / uint64_t）：文件格式、协议、二进制数据、哈希值——这些地方「恰好 32 位」是需求的一部分。打印它们用 PRIx32 / PRId64 这些宏；
  4. 只在确实需要回绕语义时用 unsigned（哈希、位运算、掩码）。「负数不可能出现」不是用 unsigned 的理由——它换来的是 3.6 节那两个坑；
  5. 不碰 short 与 char 做算术：它们会先被提升成 int，中间那一堆转换是下一单元的主题。

代价：定宽类型在接口上会逼你写 #include <stdint.h> 与 PRI 宏，代码看着比 int 啰嗦——但换来的可移植性是真实的。

小结这一节的要点
  • 字节数是实现事实：本机 _Bool 1、char 1、short 2、int 4、long 4、long long 8、float 4、double 8、long double 16、void * 8；标准只规定下界（5.2.4.2.1 节），sizeof 的结果值本身「由实现定义」（6.5.3.4 节）——只有 char 的 1 个字节是标准保证的。
  • 三个零不是一回事：'0' 是 48、0 是 0、'\0' 也是 0；字符字面量是 int（sizeof('0') 为 4，6.4.4.4 节）；plain char 是否有符号由实现决定（本机有符号）。
  • 值不对有三种来源：浮点不精确（0.1 + 0.2 是 0.30000000000000004441，用 eps 而不是 ==）、无符号回绕（0u - 1 是 4294967295，6.2.5 节）、实现定义的窄化（(char)200 本机是 −56，6.3.1.3 节——不是 UB，但也不是标准规定的确定值）。
  • 格式串配错是 UB（7.21.6.1 节）且可能「看着还挺对」；隐式转换藏在赋值、返回值、实参、算术表达式四处；sizeof 不求值、结果是 size_t，定长数组的长度要整数常量表达式（const int 不算，变长数组是例外）。

注自测题答案
  1. 4 / 4 / 8。这三个都是实现事实：标准只规定「至少」多大（INT_MAX 至少 +32767），本机 long 与 int 一样宽、Linux 64 位上 long 是 8 个字节，三者都没有标准保证的固定值。标准唯一钉死的是 sizeof(char) 恒为 1——「一个字节」的定义就是「一个 char 的大小」，所以 sizeof(char) 在任何实现上都是 1，同时 CHAR_BIT 是那个字节有几位（本机 8，标准只保证至少 8）。
  2. 48 / 0 / 0。sizeof('0') 是 4，因为字符字面量的类型是 int（6.4.4.4 节），不是 char；想要 1 个字节，得写 sizeof((char)'0')——本机实测这一行是 1。
  3. 因为 0.1、0.2、0.3 在二进制里都存不准（都是无限循环小数），存进去的是「最近的那个双精度数」，相加之后再和 0.3 的近似值比，64 位当然对不上（本机实测 0.1 + 0.2 = 0.30000000000000004441，与 0.3 差 0.00000000000000005551）。正确写法是 nearly_equal(a, b, eps)：先算 |a − b|，再和 eps 比。eps 的大小取决于你的数据量级——本机例子里比较的都是量级为 1 的数，取 1e-9；这不是定理，是工程决定。
