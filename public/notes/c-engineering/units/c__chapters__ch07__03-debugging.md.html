18.1 先看工程长什么样

前面两个单元把「一个 C 工程长什么样」讲完了：宏住在头文件里、声明与定义分家、每个编译单元各管各的。这一节要讲的是出问题时你手里有什么——所以工程里除了程序，还要多出一样东西：证据。

这一节是全书的第 18 单元，也是第 7 章的第 3 单元。它前面两个单元（chapters/ch07/01-preprocessing-and-macros.md 与 chapters/ch07/02-multiple-files-and-linkage.md）已经把「宏」与「多文件」讲完了，examples/ch07/ 里因此已经躺着它们留下的一堆东西。本节在同一个项目里再加七个例子目录与一批抓下来的会话。

第 1 帧是这一节故事的起点：前两个单元在 examples/ch07/ 里留下了宏实验与多文件工程（build.sh 就是那个单元把编译命令固定下来的产物）。第 2、3 帧是本节新增的七个例子目录，每个都是「源文件放 src/、声明放 include/、编译参数与期望输出写在 .json 清单里」的最小工程。第 4 帧把一个摊开看：crash_null 里只有两个函数加一个 main，两边的代码加起来不到 25 行——因为一个例子只讲一个坑，出问题时你才能立刻知道是谁错了。第 5 帧是本节另外留下的七份会话：它们是从真实终端抓下来的原文，也是这一节大部分证据的载体——调试器的输出每次都不一样（地址、线程号都在变），适合抓成会话，而不是逐字对账的 output 块。

先把七个例子各自要讲的那一件事记住，后面每一节都会点名其中一个：

  • crash_null、double_free_debug —— 两个真的会崩的程序：空指针解引用、同一块内存还两次；
  • crash_oob —— 越界写了，程序不崩，只是把邻居的数字改了；
  • wrong_sum、uninit_value —— 两个不崩但结果不对的程序：一个算错，一个没写初值；
  • opt_misleading、fanalyzer_first —— 两个用来讲「证据从哪来」的程序：一个证明优化会骗调试器，一个证明编译器能在编译期就抓住空指针。
工程惯例工程惯例：为什么排错要先摆好「证据的架子」

标准对「怎么排错」一个字都没有规定——这是工程惯例。它有一个很实在的好处，也有一个要付的代价。

好处是每条结论都能被单独验证：crash_oob 只演示「越界写能改到邻居」，它不崩、不做别的事，所以一旦看到 neighbor 变了，你不用再排除第二种可能。命令与期望值写进 .json 清单，任何人拿到这个目录都能复现你说的现象。

顺带把「src/ 放定义、include/ 放声明」这件事在排错上的两面说清（这套摆法第 17 单元讲过）：好处是出问题时一眼知道该去哪个文件找——.c 里是行为，.h 里是接口；代价是改一次头文件会波及所有 #include 它的编译单元，得整体重编。本节七个例子的头文件都只有几行声明，正是为了让这个代价可以忽略。

另一个代价是多花几分钟：写一个例子要配一份清单，抓一次会话要存一个文件。换来的是「你说的现象我看得见」——排错能力的一半就长在这里。

于是排错的第一步有两条并行的线索：退出码告诉你「怎么死的」，stderr 告诉你「死之前它自己说了什么」。两个都要看，两个都可能空着。

标准原文标准原文：退出码从哪来

标准里没有「崩溃」这个词。它只规定一件事：程序正常结束时，怎么把状态交回给运行它的环境。

5.1.2.2.3 节「Program termination」第 1 段：

If the return type of the main function is a type compatible with int, a return from the initial call to the main function is equivalent to calling the exit function with the value returned by the main function as its argument; reaching the } that terminates the main function returns a value of 0.

大意：main 里 return 0; 的那个 0，等价于调用 exit(0)；就算你不写 return，执行到 main 收尾的 } 也返回 0。

7.22.4.4 节「The exit function」第 5 段规定这个值最后去哪：

Finally, control is returned to the host environment. If the value of status is zero or EXIT_SUCCESS, an implementation-defined form of the status successful termination is returned. …

大意：最后控制权交回宿主环境；而「这个状态值以什么形式返回」是实现定义的——0 在 bash 里是 0、在别的地方长什么样，标准不管。

出处：ISO/IEC 9899:2018（C17）§5.1.2.2.3、§7.22.4.4。

要紧的那半句在标准之外：程序非正常终止（被信号或异常干掉）时，标准一个字都没承诺——那时的「退出码」是操作系统替你记下的终止原因，跟 return 的数字没有关系。

  • 运行结果：stdout 0 字节、stderr 0 字节；退出码在三个口径下分别是——
    • 本书清单里写 3221225477（流水线抓到的原始值，也就是 0xC0000005「访问冲突」）；
    • MSYS 的 bash 里 echo $? 显示 139（bash 把「被信号终止」写成 128 + 信号号，11 号信号就是段错误 SIGSEGV）；
    • cmd 里 %errorlevel% 显示 -1073741819（同一个 32 位数按有符号读的样子）。
  • 三个数是同一件事：3221225477 的十六进制是 0xC0000005，按 32 位有符号读是 3221225477 - 4294967296 = -1073741819；而 139 = 128 + 11 是 bash 换的另一套账本。

这也是本书在清单里写原始值的原因（crash_null 是 3221225477、double_free_debug 是 3221226356）：那是闸门真抓到的那个数，另外两个是终端替你翻译过的。

陷阱「屏幕上没输出，所以崩在 printf 之前」

你会看到什么：程序里有四条 printf，崩完终端上一片空白，你顺着代码往前找，觉得「连第一条都没执行到」。

你会怎么误判：你会把断点设在第一条 printf 之前，结果发现它被执行了，于是开始怀疑人生。

真相：标准输出流在不是交互式终端时是全缓冲的——输出先攒在内存的缓冲区里，攒满一块（多大由实现决定）或者程序正常结束（或者你显式 fflush）才真正写出去。进程被终止的那一刻，缓冲区直接消失。所以「没输出」与「没打印过」是两件完全不同的事，判断依据只有一条：退出码。3221225477 说明它死在一次非法访存上，与它之前打印过什么无关。

想亲眼看这个差别：把程序直接放在终端里跑（不接管道），终端是行缓冲的，那时你会看到崩溃前的那几行。本书的会话统一走管道抓取，所以你在这里只看到 0。

18.3 gdb 上手：把一次调试写成一条命令

gdb 是个交互式程序，但排错时最有用的形态是「一次性脚本」——因为一条命令才能被复制、被重跑、被抓进会话记录。

语法规则一条能重跑的命令

形式就一行：gdb --batch -ex "命令" -ex "命令" … 可执行文件。

  • --batch：执行完就退出，不进交互界面（所以能写进脚本、能贴进会话）；
  • -ex：一条 gdb 命令，按写下的顺序执行（"break …"、"run"、"bt" 都是命令），可以连着写很多次；
  • 引号别省：-ex "break src/crash_null.c:12" 里的空格与冒号是 gdb 语法的一部分；
  • 调试期可执行文件必须带调试信息，就是本书固定参数里那个 -g。没有 -g，gdb 只知道函数名，不知道行号、不知道变量名。

断点有四类，各自管一件事：

断点 写法 什么时候用
行断点 break src/crash_null.c:12 你已经怀疑到某一行
函数断点 break read_value 只知道是哪个函数出错，不知道哪一行
条件断点 break src/crash_null.c:12 if record == 0 这一行会被执行很多次，你只想停在满足条件的那一次
观察点 watch p.neighbor 不知道是谁改了这个变量，想让它一被改就停

停住之后，单步下去用的是另外五个命令。前两个的差别是跨不跨函数，后三个是「怎么往前走」：

命令 一句话
next 执行下一行，不进入它调用的函数（把整个调用当成一步）
step 执行下一行，进入它调用的函数
finish 把当前函数跑完，停在调用者那里
until 一直跑，直到走出当前这一层循环（或者走到当前函数末尾）
continue 接着跑，等下一个断点 / 观察点

这五个不是「背下来」的事，而是回答两类问题：step 回答「问题在不在我调用的这个函数里」，next 回答「这一行本身有没有做错事」。顺序上也有讲究：先用 next 把本层走完（成本低），发现「本层每一步都对、结果却不对」时，再用 step 钻进被调用的那一层。

跨文件断点是这一节要专门讲清的一件事：你的 main 和出问题的函数往往不在同一个文件里。看这张图，crash_null 的两个编译单元是怎么被 -g 与 bt 连起来的：

第 1 帧是编译期的样子：main.c 里只有 #include "crash_null.h" 搬进来的两行声明，read_value 的定义在另一个文件里。第 2 帧是链接之后：两边合成一个 app.exe，-g 把「哪个函数的哪条机器码对应哪个文件的哪一行」写了进去。第 3 帧是断点：你写 break src/crash_null.c:12 时，gdb 是在被调用者那一侧下断点——所以第 4 帧的 bt 才可能跨文件把两个编译单元接起来。

工程惯例工程惯例：断点写在「谁错」那一侧

这是惯例，标准不管调试器。三种写法各有用处，代价也不同：

  • break read_value（函数断点）：好处是不用记行号、改几行代码也不会失效；代价是这个函数被调一百次它就停一百次；
  • break src/crash_null.c:12（行断点）：最精确；代价是改代码就得改断点，所以本书的会话里那条命令是连同编译命令一起抓下来的；
  • break src/crash_null.c:12 if record == 0（条件断点）：把「哪一次」也写进命令里，一次命中就是你要的那一次；代价是条件里的变量必须当时可见（优化过的代码里它可能已经不存在了，见 18.5）。

本书的规矩是：会话里抓下来的那条命令，复制出来就能重跑——所以命令里一律带文件名，不裸写行号。

陷阱越界写「什么都没发生」，比崩溃更难查

你会看到什么：程序跑完了，退出码 0，输出也都对——只是某几个数字莫名其妙不对；改一改代码顺序，现象又没了。

你会怎么误判：你会去怀疑打印格式、怀疑算法、怀疑编译器，因为「它根本没崩啊」。

真相：越界写是未定义行为（UB），而 UB 最典型的形态就是看不出异常。标准 6.5.6 节「Additive operators」第 8 段规定：

If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined.

大意：指针加减的结果必须还落在同一个数组里（或者正好是最后一个元素的「下一格」）；出到外面就是未定义行为。上面那次 buf[10] 正是算到了数组外面——所以标准不欠你任何解释，它今天改了邻居、明天可能什么都不改、也可能当场崩（第 19 单元会讲它在优化器手里还能变成什么样）。

最直接的两样是 watch（知道变量被谁改的）与静态分析器（本机的 -fanalyzer 有时能在编译期算出来，见 18.9）；此外 -fstack-protector-all 能在栈上的数组被越界写时把它变成一次终止，assert 则适合把边界写成代码（见 18.8）。靠肉眼看代码，你看不出 10 比 8 大——那行代码长得太正常了。

18.4 崩溃现场：bt 的 #0 与 #1

现在回到 crash_null，看一次完整的崩溃现场。下面三段是 examples/ch07/crash_null/session-gdb-crash.txt 的原文，按三次停住拆开。

调试实录调试实录：一条命令看穿一个空指针

只有一条命令，做的事按顺序是：在第 12 行下断点 → run → bt → 看一眼 *record 与它的四个字节 → continue（等下一次命中）→ bt、info locals、info args、info frame → next 让它真的崩 → 再 bt。

读的时候盯三处：record 的值（第一次是合法地址、第二次是 0x0）、bt 的 #0 与 #1（谁在最里面、谁在调用）、崩溃之后 gdb 把停在哪一行。三段会话原文紧接着放在下面，命令与输出都在里面。

三段合起来读，信息量比看上去大：

① bt 的第一行就是「最里面」。 #0 read_value (record=0x0) at src/crash_null.c:12 是当前停住的函数，#1 … in main () at src/main.c:13 是调用它的那一行。所以只要 #1 是 main，你就已经找到了自己代码里的位置——不用管前面那串 0x00007ff6…，那是返回地址，每次运行都不一样。

② record = 0x0 就是病根。 第一次命中时它是一串合法地址（会话里那个 0x…3004），第二次是 0x0（空指针）。中间那句 record = 0x0 是 info args 打出来的——注意 info locals 那行说的是 No locals.：这个函数除了参数以外没有局部变量，info locals 只管局部变量，参数要用 info args，或者用 info frame 一次看全（那边写着 Arglist at 0x5ffe70, args: record=0x0）。

③ next 之后 gdb 说 Thread 1 received signal SIGSEGV, Segmentation fault. 然后停在同一个第 12 行上——不是它没动，而是这一行就是出事的那一行。这跟你第 1 单元见过的编译错误刚好相反：编译器的报错常常往后面指一行，而 -O0 -g 下调试器停的就是出事的那一行（换成 -O2 -g 这条就不成立了，见 18.5 的行号漂移）。

到 18.4 为止，本书所有调试都在 -O0 -g 下做的。为什么不用优化档？因为 -O2 -g 会给你一份「行号对不上、变量看不见」的调试信息——-g 让它记下调试信息，-O2 又把它记下的东西改掉了。

编译器在 -O2 下做的是改写，不是逐句翻译：

  1. helper 是个 static 小函数，只在本编译单元用——内联它比调用便宜，于是它的函数体被搬进 combine，原来的函数可能整个消失（这就是「2 locations」的来历）；
  2. local = v * 3; return local + 1; 两句话合起来就是 v * 3 + 1——中间量 local 不再需要一个存放的地方，它进了寄存器，然后就没了；
  3. 值一旦只在寄存器里活着，没有任何内存地址可以给 gdb 指过去。gdb 的 <optimized out> 不是「读失败了」，而是「调试信息里写着：这个位置在这一点上不存在」。

所以调试期的规矩不是「优化不好」，而是分工：-O0 -g 是给人看的，-O2 是给机器跑的。你要看行为就用前者，要看优化做了什么（像第 4 章那样去读汇编）才用后者。

工程惯例工程惯例：调试期一律 `-O0 -g`，交付期再谈优化

标准对优化档位什么也没说（那是编译器的开关，不是语言的一部分）。工程上的惯例是把它写进构建脚本的两个目标：debug 用 -O0 -g，release 用 -O2（或 -O3），而不是让人临时敲。

代价说清楚：-O0 编出来的程序慢、体积大（本机这个 20 行的小例子感觉不出来；大工程的差距可以很大，具体倍数取决于代码，本书没有量过），而且有些 bug 只在 -O2 下出现（未定义行为被优化器利用，第 19 单元专讲）。所以理智的做法是：先用 -O0 -g 把逻辑调对，再用 -O2 跑一遍回归——两边都要过，才叫真的对。

反过来的写法（拿 -O2 -g 当日常调试档）会带来上面那三样麻烦，而且它失败的时机很讨厌：小函数里变量还看得见，稍微长一点就变成 <optimized out>，你会以为是 gdb 坏了。

这一节的结论不是「-O2 修好了它」：-O2 下那个不确定的初值没有参与运算，只是因为优化器把整个循环改写成了别的形状——我拿 gcc -std=c17 -O2 -Iinclude -S src/uninit_value.c -o uninit_o2.s 看过那份汇编，sum_uninitialized 里是 xorl %edx, %edx 加一串闭式算术，根本没有一次「读那一格」。同样的未初始化读，换一份代码、换一个优化档，完全可能给出第三种结果。标准的态度是：这种代码本来就不该存在。

标准原文标准原文：没写初值的对象

6.7.9 节「Initialization」第 10 段：

If an object that has automatic storage duration is not initialized explicitly, its value is indeterminate. If an object that has static or thread storage duration is not initialized explicitly, then: …

大意：自动存储期（就是普通的局部变量）的对象如果没显式初始化，它的值是不确定的（indeterminate）；而静态存储期的对象不初始化时，标准反而规定得清清楚楚（算术类型为 0、指针为空指针）。

「不确定的值」本身还不是 UB——读它才是。6.3.2.1 节「Lvalues, arrays, and function designators」第 2 段给的就是这一环：

If the lvalue designates an object of automatic storage duration that could have been declared with the register storage class (never had its address taken), and that object is uninitialized (not declared with an initializer and no assignment to it has been performed prior to use), the behavior is undefined.

大意：一个自动存储期的对象如果从没被取过地址（本来可以声明成 register），而且在用到它之前既没初始化、也没被赋过值，那么读它就是未定义行为。total 正好符合：没有初值，第一次 total += i 就先读了它。

至于「未定义行为」是什么意思，3.4.3 节「undefined behavior」给的定义是：

behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements

大意：未定义行为就是「这份标准对它不提任何要求」。3.4.3 节第 2 段的注还专门说明这个范围可以有多大：从完全不动（结果不可预测），到按环境特有的方式办（可能给诊断），一直到终止翻译或执行。

出处：ISO/IEC 9899:2018（C17）§6.7.9、§6.3.2.1、§3.4.3。

所以「我的机器上跑出来是 5050」这句话在法律上毫无意义：它今天可以给你 5050，明天可以给你任何东西，而且不需要给你任何提示。

工程惯例工程惯例：本机没有 ASan，也没有 valgrind

这条要说得直白：这本书给不出「运行期精确的越界位置」。

  • AddressSanitizer（-fsanitize=address,undefined）本机不可用。我实测过：gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address,undefined asan_probe.c -o asan_probe.exe 的 stderr 是两行 ld.exe: cannot find -lasan: No such file or directory 与 ld.exe: cannot find -lubsan: No such file or directory，最后一行 collect2.exe: error: ld returned 1 exit status，编译退出码 1（ld returned 后面那个数是链接器的状态码，本书 build/toolchain.json 里记的是 5、我这次跑出来是 1；要紧的是它链接失败，不是那个数字）——这套 MSYS2 安装里没有 libasan/libubsan；
  • valgrind 也没装：which valgrind 在本机 PATH 上找不到它（valgrind 是 Linux 工具，Windows 上本来就没有）；
  • 所以本书「运行期越界」的证据只有三样：退出码、stderr 上那行字（如 *** stack smashing detected ***）、gdb 的栈。想抓得准一点就换编译开关：-fstack-protector-all 能护住栈上的数组，-fanalyzer 能在编译期报出一部分形状死板的越界。

代价与替代写在这里：没有 ASan，本书就不可能给你「越界写到了第几号字节」这种精度——那需要运行期插桩。能替代它的是把边界检查写进代码（assert、显式的长度参数与判空），这也是为什么本书一路强调接口上「从哪开始、有几个」成对出现。

这一节所有「实测」都靠同一样东西撑着：每个例子配一份 .json 清单。清单不是给编译器看的，是给「你下次还能不能复现」看的。这是 crash_null 的那一份：

字段 它记下来的是什么 为什么非有不可

清单体系里有两条约定值得单独记住，它们都是本机实测过的：

  • 崩溃的程序，stdout 通常一个字节都没有。所以 crash_null 的输出块里写的是一行哨兵「（无输出）」——它表示「这个清单期望 stdout 为空」；程序哪天真打印了东西，对账反而会失败（报 stale_output）。想留下崩溃前的输出，就得像 double_free_debug 那样显式 fflush(stdout)；
  • 同一个数的三种写法必须写清口径。清单里写 3221225477（流水线抓到的原始值），会话里贴 139（bash 的口径），正文里把 0xC0000005 与 -1073741819 都点一遍——它们是同一件事，但混着写就会变成三个「传说」。

小结这一节的要点
  • 崩溃第一步是退出码，第二步是 stderr：同一个空指针崩溃，清单里是 3221225477（0xC0000005）、bash 里是 139（128+11）、cmd 里是 -1073741819；而带字的崩溃（assert）是 3221226505、bash 127、cmd -1073740791。stdout 与 stderr 都可能是 0 字节——输出攒在缓冲区里，进程被终止时一起消失；
  • gdb 写成一条命令（--batch -ex）才能被复制与重跑；四类断点（行 / 函数 / 条件 / watch）各管一件事；bt 的编号越小越靠里，先找属于自己代码的那一层，再用 p、p/x、x/8xb、x/s、info locals、info args、info frame 看数据（地址每次都不同是正常的）；
  • -O2 -g 会骗你（<optimized out>、一个断点多个位置、行号漂移），调试期用 -O0 -g；没有调试器时靠 printf 二分法、-D 开关式打印、assert、fflush(stdout)；能编译期白拿的证据先拿（-Wall -Wextra -Wpedantic、-fanalyzer），但分析器只覆盖部分缺陷族，本机也没有 ASan 与 valgrind；
  • 可复现 = 清单：命令、源文件、参数、退出码一起记下来；崩溃程序的 stdout 用哨兵「（无输出）」声明。

注自测题答案
  1. 它们是同一个数（或者同一件事）的三种读法：3221225477 写成十六进制是 0xC0000005（Windows 的「访问冲突」），按 32 位有符号读是 3221225477 - 4294967296 = -1073741819（cmd 的 %errorlevel% 就这么显示）；而 139 = 128 + 11 是 bash 的另一套账本（11 号信号 SIGSEGV）。本书清单里一律写流水线真抓到的 3221225477。
  2. 去 src/crash_null.c 的第 12 行找（#0 是最内层、出事的那一行）；#1 … at src/main.c:13 是谁调用进来的，所以那一行也值得一起看。record=0x0 说明传进来的是空指针——#1 那一行把 find_record(-1) 的结果直接交给了 read_value，中间没有判空。
  3. <optimized out> 是因为 -O2 把 helper 内联、把中间量放进寄存器之后这些变量在机器码里已经不存在了，调试信息里没有地址可指；helper. (2 locations) 是「这个函数被内联到两处」的直接证据，而行号从 8 漂到 12 是「整个函数体被合成一句话、调试信息把行号挂在了合并后的位置上」。结论：调试期用 -O0 -g。
  4. 不能。 -O2 下两次读数一样、都等于正确的 5050，只是因为这个不确定的初值没有参与运算（优化器把循环算成了别的东西）。这段代码本身就是未定义行为（total 是自动存储期对象、没有初始化：§6.7.9 说它的值不确定，§6.3.2.1 第 2 段说这种对象在被读时是未定义行为），所以标准不保证任何一档的读数；换个编译器或换一份代码，完全可能给出第三种结果。正确的做法是给累加器写 int total = 0;。
  5. 它说明编译通过只意味着「语法与类型层面没有拦住你的地方」，不意味着程序是对的：分析器只负责报告，不阻断编译（本机实测：带 -fanalyzer 时编译退出码仍是 0，而且这个程序真跑起来确实崩）。本机没有 ASan（链接时 cannot find -lasan）与 valgrind，所以运行期的内存错误只能靠退出码、stderr 那行字、gdb 的栈，再加上把边界检查与判空写进代码（assert、长度参数）。
