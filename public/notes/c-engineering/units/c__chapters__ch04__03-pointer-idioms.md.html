10.1 先看工程长什么样

工程惯例工程惯例：为什么接口这件事要单独学一节

标准对函数签名只有一个硬要求：每个实参的值必须能赋给一个「形参类型去掉限定符」的对象（6.5.2.2 节第 2 段，10.2 节会引原文）。怎么写签名、参数代表输入还是输出、谁负责释放内存，标准一个字都没规定——全是惯例。

惯例值得单独学，是因为它有代价、也能被验证：const char * 写进签名，实现里就改不动它指向的东西，代价是你得在写第一版接口时想清楚；反过来，写成 char * 却打算只读，调用者看不出，早晚有人把只读字符串交给它（10.2 节的 const_loss 就是真实报错）。

这一节做的每一件事，都是把一条口头惯例变成签名上一眼能看见的东西。

标准原文标准原文：为什么丢 const 要报警告

同一个标准的 6.5.16.1 节「Simple assignment」列出了简单赋值必须满足的条件之一：

the left operand has atomic, qualified, or unqualified pointer type, and (considering the type the left operand would have after lvalue conversion) both operands are pointers to qualified or unqualified versions of compatible types, and the type pointed to by the left has all the qualifiers of the type pointed to by the right;

大意：左边指针指向的类型必须带上右边指向的类型的所有限定符。也就是说「int * ← const int *」不满足这个条件，而「const int * ← int *」满足（左边多了个 const，多出来的不算违规）。这条约束管的是赋值；传参则由 6.5.2.2 节第 2 段管住——「每个实参的类型，必须让它的值能赋给一个『形参类型去掉限定符』的对象」，于是同一条约束也落在调用点上。至于「必须给诊断」，那是 5.1.1.3 节的要求（违反任何约束或语法规则，实现至少要给一条诊断）；诊断是 warning 还是 error，标准不管——本机选了前者，也就是你上面看到的这条。

工程惯例工程惯例：`const T *` 与 `T *` 是谁的承诺

标准不管你写不写 const（6.5.16.1 只要求类型能配上），但接口上的 const 是这个函数对调用者的承诺，惯例有三条：

  • 只读的输入一律写 const T *：调用者一看就知道「我的数据不会被改」，而且实现里也改不动（改了编不过）——这是把制度写进类型里；
  • 要写出去的对象写 T *，并在头文件注释里说清「它会写你哪几个字节」。本节的 out_params（10.3 节）与 array_of_ptr（10.5 节）都是这个形状；
  • 形参上的 T * const 基本没用：形参是一份副本（上一单元讲过，指针也不例外），锁住副本管不到调用者，也不改变接口语义。它偶尔被当成「我保证不改这个指针变量」的自我约束写在函数体里（形参在函数体内就是局部对象），但作为接口它什么也没承诺。

代价也要说清：接口一旦承诺了 const T *，日后想把它改成 T * 只需删一个词——编译器只给警告、照样放行（上面那个实验），这个承诺很容易被悄悄破坏；反过来，从一个没写 const 的接口补上 const，会立刻在实现里撞出一串「不能改它」的编译错误。所以「这块是不是只读」要在写第一版接口时定下来。

陷阱「const 只是给人看的注释，加不加都一样」

你会怎么被坑到：你在头文件里顺手写下 size_t uppercase_into(char *out, …)，心里想的是「我只往里写，不会读它」。三个月后有人在另一个文件里写 uppercase_into(src, …)，src 是个 const char *——编译通过（只有一条警告，很可能被淹没在几百行输出里），程序跑起来却往只读内存里写；本节实测的后果是当场 SIGSEGV（退出码 139）。

我会怎么误判：我以前觉得「警告又不是错误，先跑起来再说」。真相是：这条警告是编译器唯一会告诉你的地方——类型系统能管的边界就到这里，它不能替你判断「你心里想的那件事」，只能判断「两个类型配不配」。

怎么查：把警告当错误跑一遍（加 -Werror，或者把编译输出存下来 grep 一遍 discards），上面那份实验里两次编译的区别就是全部证据。

语法规则输出参数的写法与它欠的三句话

形状只有一条：要交出去的结果，用 T * 收，调用者拿 & 取地址交进来。

  • 参数写成 int *out（输出一个 int）、const char **out（输出一个字符串指针）；
  • 返回值写 int，0 是成功、负数是错误码（正数留给「有效值的个数」这种用法）；
  • 接口必须写清三件事：失败时输出参数写不写（本书一律「不写」）、谁负责分配（见下面的惯例块）、错误码各是什么意思（error_text 那种函数就是干这个的）。

长度与指针永远成对出现：输出参数是 (char *out, size_t cap)，cap 是你那块缓冲区总共多大（含结尾那个 '\0' 的位置）——第 8 单元的 fgets 与第 15 单元的 snprintf 都是这个形状。

工程惯例工程惯例：谁分配谁释放，写进接口而不是记在脑子里

「谁分配谁释放」是这一行最有用的规矩，它的完整形式是：分配那块内存的人，负责把它还回去，并且这句话要能从头文件里读出来。三种常见写法：

  • 调用者出内存（最主流）：void greet(char *out, size_t cap, const char *who);——out 是调用者的数组，函数只负责写。好处是谁也不用记着 free，代价是调用者得先知道「要多大」；
  • 函数分配、调用者释放：char *make_greeting(const char *who); 返回 malloc 来的指针，头文件注释里必须写「用完 free」。代价很实在：调用者漏一次 free 就是一处泄漏（第 12 单元讲）；
  • 函数分配、函数释放：返回一个「内部缓冲区」的地址，下一次调用会把它覆盖掉（上一单元 static 那段讲过它的代价：不能重入）。

代价的读法是一致的：只要内存的生命期跨过了函数边界，就必须有人把它写成文字——写在头文件注释里、或者干脆让它在类型上消失（像第一种那样，压根没有要还的东西）。

最后三行是 show_args 打的（它上面那一行「main 的第二个参数就是这个类型」是 main 自己打的）：fake_argv 是一个以 NULL 收尾的指针数组，这也正是真实 argv 的形状——p[argc] 是空指针，所以 for (i = 0; argv[i] != NULL; i++) 这种循环不用另外传长度。

大白话二级指针没那么玄：它是「指针的地址」

把内存想成一排信箱。int **pp 的意思是：这个信箱里写的，是另一个信箱的编号；而那个信箱里写的，才是数据的编号。

  • set_pointed(int *p, …)：你交出一张写着 a 的纸条，函数按纸条找到 a，改里面的值——纸条是副本，但它指着的地方是真的；
  • point_to(int **pp, …)：你把放纸条的那个抽屉指给函数看，函数把抽屉里的纸条换成另一张（换成 b 的编号）；
  • set_via_double(int **pp, …)：函数打开抽屉拿到纸条，再按纸条找到数据去改。

所以「改指针本身」和「改指针指向的东西」的区别，就是你交出去的是纸条，还是放纸条的那个抽屉。

陷阱`T **` 用错的两种典型样子

你会怎么被坑到：这两种写法都能编过，但都不做你想做的事。

  • 想改指针，却传了指针：void point_to(int *pp, int *target) { pp = target; } 再调 point_to(p, &b);——形参 pp 是一份副本，改它等于什么都没做。编译不报错（类型完全合法），运行时调用者的 p 一动不动；
  • 写成了 T **，却顺手解引用了一次：void set_via_double(int **pp, int value) { *pp = value; }——这一行的类型就错了（int ** 赋 int 值），编译器会拦；但换个更宽的类型（比如把 value 写成指针）它就悄悄编过，然后你改掉的是指针，不是它指的东西。

真相：二级指针的每一个 * 都对应「顺着走一层」，写完先数一遍：pp 是指针的地址、*pp 是那个指针、**pp 才是数据。想改什么，就写到第几层。

语法规则函数指针的声明：括号不能省

形状是 返回类型 (*变量名)(参数类型列表)。三个位置各管一件事：

  • (*变量名) 的括号不能省。int *f(int, int) 读作「f 是一个函数，接受两个 int，返回 int *」；int (*f)(int, int) 读作「f 是一个指针，指向接受两个 int、返回 int 的函数」。区别只在那一对括号，而它们是两个完全不同的东西；
  • 参数列表只写类型就够了（int (*f)(int, int)），带参数名也行（int (*f)(int a, int b)）；
  • 觉得难读就用 typedef 起个名字（本节的 binop_fn），之后 binop_fn f = op_add; 就一眼能读了——工程代码里 typedef 是常态，因为回调的签名往往很长。

赋值与调用各有一对等价写法：f = op_add; 与 f = &op_add;；f(7, 5) 与 (*f)(7, 5)。

陷阱`int *f(int, int)` 与 `int (*f)(int, int)`：少一对括号，意思全反

你会怎么被坑到：想写一个「返回 int 的函数指针」，结果写成了 int *f(void)——编译器认为你在声明一个函数，它返回 int *。于是你在函数体里写 return op_add;，本机报的是 error: returning 'int (*)(int, int)' from a function with incompatible return type 'int *' [-Wincompatible-pointer-types]（gcc，-std=c17）。报错指向的是 return 那一行、不是声明本身——你很容易跑去改 op_add，改半天才发现错在签名。

真相：C 的声明符规则是「从名字出发、先右后左」（6.7.6 节），* 与 () 的先后由括号决定：没有括号时 f 先与 (int, int) 结合，* 只好去管返回值；有括号时 f 先与 * 结合，成了指针。

怎么查：往这行声明里塞一个故意错的类型赋值（比如 binop_fn g = 1;），让编译器把它「理解成了什么」打给你看——报错里会带回推出来的类型，比你自己读快得多。

qsort 的契约只有「三个返回值方向」，所以比较函数的写法有自己的惯例：

  • 别写 return a - b;：两个 int 相减可能溢出（上一单元讲过的有符号溢出 UB），排一个「大正数在前」的数组时就会翻车。用 (x > y) - (x < y) 或者三个 if；
  • 元素类型是「指针」时，参数多一层：排 int 数组时 const void * 指向 int，转 const int * 就够；排 char * 数组（也就是字符串数组）时它指向一个指针，要转成 const char *const * 再解引用。本节 cmp_str 那两行就是这件事；
  • 不要在比较函数里改数据、也不要 free：qsort 会在它认为合适的时候调用你，你可能被调用的次数没有保证（同一对元素比较两次是允许的）。

代价说清：这几条都不是标准强制的（标准只说返回值的方向），但各自对应一个真实的踩坑现场。

10.8 void * 与接口上的数组：为什么签名长成那样

回头看两个标准库函数的签名，现在应该能读出设计意图了：

  • void qsort(void *base, size_t nmemb, size_t size, int (*compar)(const void *, const void *));
  • void *memcpy(void *restrict s1, const void *restrict s2, size_t n);

它们都用 void * 收指针、都用额外的两个数字（元素大小 + 个数，或者字节数）补上类型信息丢掉的那部分。原因只有一个：这两个函数要对「任何类型」都管用。void * 是 C 里唯一的通用指针——标准 6.3.2.3 节第 1 段给它的承诺很小，就一句话：

标准原文标准原文：`void *` 能干什么

6.3.2.3 节「Pointers」第 1 段：

A pointer to void may be converted to or from a pointer to any object type. A pointer to any object type may be converted to a pointer to void and back again; the result shall compare equal to the original pointer.

大意：任何「指向对象」的指针都能转成 void *、也能转回来，转回来之后与原指针相等。标准就承诺了这么多——它没说 void * 能解引用，也没说能对它做算术。

出处：ISO/IEC 9899:2018（C17）§6.3.2.3 第 1 段。

void * 的这两条限制不是设计缺陷，而是信息不足的必然结果：编译器不知道它指向什么类型，就不知道一次该读写几个字节、一步该走多远。本机把这两件事的实际后果摆在这里：

工程惯例工程惯例：接口上写 `T *` + 长度，还是写 `T a[]`

标准对函数参数有一条明确的规则：形参里的 T a[] 与 T a[N] 都会被改写成 T *a（6.7.6.3 节），N 那个数字完全不参与类型。本节的接口分成两类，区别只在「长度从哪来」：

  • 以 '\0' 收尾的字符串不需要长度：count_matches(const char *text, char target)（const_params）靠 '\0' 就知道读到哪；
  • 其余数组与缓冲区一律 T * + 长度：chars_in(char **names, size_t n)（array_of_ptr）、uppercase_into(char *out, size_t cap, const char *src)（const_loss）

具体做法就两条：

  • 一律写 T *，长度单独一个参数（size_t n 或 size_t cap）。理由：T a[] 与 T * 是同一个类型，写成前者只会让人误以为「长度传进来了」；
  • 长度参数放指针后面：(const T *a, size_t n) 这个顺序在标准库里随处可见，一眼就能看出它们是配对的。
工程惯例（续）`cap` 与 `n` 别混，方括号里的数字不是长度

同一个位置上的 size_t，在输入型与输出型接口里含义不同：

  • cap（容量）：输出型接口收的是「你最多能写多少」（含结尾 '\0' 的位置），本节的 uppercase_into(char *out, size_t cap, …) 就是它；
  • n（实际长度）：输入型接口收的是「这里面有几个元素」，chars_in(char **names, size_t n) 就是它；
  • 方括号里的数字是类型的一部分，与「有几个元素」无关：char rows[][8] 里那个 8 是行宽，元素个数永远靠参数（size_t n）。

代价：多一个参数、多一处可能写错的数（sizeof 与真实长度对不上是经典 bug，10.11 节会列）；好处是函数里唯一能知道长度的办法就是这个参数——上一单元的 sizeof_in_function 实测过：函数里的 sizeof(a) 只剩 8。

「指针相减只在同一个数组里才定义良好」出自标准 6.5.6 节第 9 段：

标准原文标准原文：指针相减的合法范围

6.5.6 节「Additive operators」第 9 段：

When two pointers are subtracted, both shall point to elements of the same array object, or one past the last element of the array object; the result is the difference of the subscripts of the two array elements. The size of the result is implementation-defined, and its type (a signed integer type) is ptrdiff_t defined in the <stddef.h> header. If the result is not representable in an object of that type, the behavior is undefined.

大意：两个指针相减时，它们必须指向同一个数组对象的元素（或者最后一个元素的下一格），结果才是「两个下标之差」；结果类型是 ptrdiff_t（本机 8 字节的有符号整数），这个类型多宽由实现决定；连这个差都装不进 ptrdiff_t 时，同样是未定义行为。

出处：ISO/IEC 9899:2018（C17）§6.5.6 第 9 段。

uintptr_t（以及有符号的 intptr_t）是「能装下 void *、转回来还等于原指针」的整数类型，7.20.1.4 节还写明这两个类型是可选的（实现可以不提供）；能用它的场合比新手想的少得多：

陷阱拿 `%p` 的输出当数字用

你会怎么被坑到：你在排错时打了一行 printf("%p\n", (void *)p);，看到 00000000005FFE84，于是想把它的低几位取出来当标识符用，或者拿两次打印的字符串做比较判断「这两个指针一样不一样」。

真相：%p 的输出格式由实现决定（标准只说它用来打印指针，没说长什么样）。本机是带前导零的十六进制、没有 0x 前缀，别的运行库可能打印 0x5ffe84 甚至 (nil)。字符串不同不代表指针不同。

怎么查 / 怎么写：要比较两个指针，直接用 ==；要当数字用，先转成 uintptr_t 再按整数打印（配 PRIuPTR）。本书所有打印地址的地方都写 (void *)p，理由在上一单元讲过：%p 要的就是 void *，不写这一句 -Wformat 会警告你。

工程惯例惯例的界限：`free(p); p = NULL;` 救得了什么

上一单元的 gdb 会话实测过：free(p) 不会动 p 里的地址（free 前后都是 0x71cdc0）。所以「还回去之后立刻置空」成了一条常见惯例。

它救得了什么：p = NULL 之后，你再拿 p 去解引用会当场崩（退出码 3221225477），而不是悄悄写坏分配器的账本、等到程序退出时才报一个莫名其妙的 3221226356。把「悄悄出错」变成「当场出错」，是这条惯例的全部价值。

工程惯例（续）它救不了什么，而正解是什么
  • 别名指针。同一块内存如果还有另一个指针 q，free(p); p = NULL; 对 q 毫无影响——q 照样悬着，用它读写照样是 use-after-free。C 里没有「这块内存还有几个主人」的记账，p = NULL 只撕掉了一张纸条；
  • 把 p 交出去的那些函数。p 的副本可能住在别的栈帧里，或者已经存进了别的结构体。

所以正解是所有权纪律，不是置空：谁分配谁释放要写进接口（10.3 节的惯例块），谁拥有这块内存是设计问题，而 p = NULL 只是事后的一张创可贴。写法上仍然推荐置空——它的代价是零，收益是「下次误用会响」。

  • 输出参数 + 错误码是 C 返回多个结果的惯例：返回值 0 成功、负数是错误码，额外的结果用 T * 写出去，失败时一个字节都不写（divide_checked(17, 0) 实测把上一次的 q、r 原样留着）；谁分配谁释放必须写进接口；

小结（续）这一节的要点
  • 函数指针就是装着函数地址的变量（本机 8 字节）：f(7,5) 与 (*f)(7,5) 等价，函数名直接当地址用；分发表是「名字 + 函数地址」的数组；回调是库把比较方式交还给你的机制——gdb 的 bt 实测是 #0 cmp_int_asc / #1 ucrtbase!qsort / #2 main；
  • void * 不带类型，所以 qsort 要 size、memcpy 要字节数，回调里必须自己转回来；*p 与 p + 1 在标准里都不合法（本机前者编不过、后者只给警告）；接口上写 T * + 长度是主流，因为函数里 sizeof(参数) 只剩指针的大小（本机 8）；
  • 结果一样不等于标准承诺：重叠的 memcpy 与 memmove 在本机给出一模一样的字符串（都退出 0），但标准写着重叠时 UB，restrict 那句承诺的违反也是 UB——证据是 -Wrestrict 的诊断与标准原文，不是运行结果；指针大小与 %p 的样子都是实现事实，uintptr_t 只在少数场合该用。
