2.1 工程长什么样：这一单元往 examples/ch01/ 里加了什么

上一单元我们在 hello.c 上看见了四个阶段，也看见了两条故意写错的诊断。这一单元要把「编译器说的话」当成一门手艺来学：它说什么、按什么规矩说、哪些话只在特定开关下才说、它不说话的时候你该怎么办。

新增的东西全是实验文件：八个小程序（多数各自只考一件事），每个配一份清单（清单负责声明「怎么编译、跑完退出码是多少、正文里哪个块负责对账」），再加一份把几十条真实命令抓下来的会话文件。为什么不拿现成的 hello.c 来学？因为它太干净——诊断这门手艺得在脏代码上学。

第 1 帧是上一单元留下的家底；第 2 帧是这一单元加进来的——八个小程序、八份清单，加一份抓下来的会话（前四个偏「诊断」，后四个偏「构建」，正好对应本单元的两半）；第 3 帧说的是没加什么：这一章仍然是单文件项目，源文件与清单平铺在 examples/ch01/ 这一层，不建 src/ 与 include/。这不是偷懒：单文件阶段要先把「一条命令怎么编、诊断怎么读」学会，再谈目录怎么分；从下一个项目（examples/ch02/）起，本书不再允许单文件工程（1.1 的惯例块里说过它的代价）。

下面这一整单元的所有命令，都是在这台机器上真跑出来的，命令与输出原样抓在 examples/ch01/session-diagnostics.txt 里；正文里的每一段会话都从那个文件按行号注入，一个字都没有手打。

标准原文标准原文：诊断是「至少一条」，不是「说清楚」

C 标准对诊断只规定了底线：

A conforming implementation shall produce at least one diagnostic message (identified in an implementation-defined manner) if a preprocessing translation unit or translation unit contains a violation of any syntax rule or constraint …

大意：只要代码违反了一条语法规则或约束，编译器就至少得吐出一条诊断——说什么、叫什么名字、怎么排版，全是实现自己的事。标准甚至没说它必须是 error，也没规定「一条报错只许报一处」。

所以下面这些规矩都不是标准定的，是 gcc 自己定的：诊断长成 文件:行:列: 级别: 说明、方括号里挂一个 -W… 开关名、error 就停下、warning 就接着编。换一个编译器，同一份代码可能给你完全不同的文字。

出处：ISO/IEC 9899:2018（C17）§5.1.1.3 第 1 段。

2.2 一条诊断的四段读法

先把一条最短的诊断摆出来。这是我们马上要拆的那份 warn_zoo.c 的编译结果，命令在会话里（grep 只是把警告行挑出来，不改变内容）：

这一行里塞了四段信息，按顺序是：

  1. warn_zoo.c：哪个文件。如果编译命令里写的是相对路径，这里就是相对路径；这就是为什么本书要求「在源文件所在的目录里编译」——报错里的文件名短、能直接对回你的文件。
  2. 9:9：行:列，都是从 1 数起。行是你在编辑器里按 Ctrl+G 能跳过去的地方；列是那一行的第几个字符。上面这条说的是「第 9 行的第 9 列」——去 warn_zoo.c 第 9 行看，那一列正好是 scratch 的第一个字母。
  3. warning:：级别。三种口吻（1.5 见过前两种）：error 是「我拒绝继续翻译」，warning 是「我照做了，但我认为你有地方不对」，note 是「给上面那条的补充」。级别写在说明之前，是判断「编不编得下去」的唯一依据。
  4. unused variable 'scratch'：说明。它是人话，但它不是稳定的接口：换一个编译器版本，同一句可能被改写、被拆成两句、或者消失。

说明的末尾还挂着一对方括号，这一对方括号是全书最值得你留意的一处细节：

语法规则方括号里是「控制这条诊断的开关名」

[-Wunused-variable] 的意思是：这条警告由 -Wunused-variable 打开，也能用 -Wno-unused-variable 关掉。末尾带着 = 的（比如 [-Wformat=]）表示它属于一族开关，-Wformat=2 这种写法就是在给这一族指定档位。

有了这个名字，你能做三件事：查手册（gcc 的手册里搜 -Wunused-variable，能读到它到底在什么条件下触发）；单独关掉它（-Wno-unused-variable）；以及在团队里精确地讨论「这条要不要开」。没有这对方括号，你只能对着一句英文猜。

书里有一条纪律要说在前面：本书的清单里不允许出现 -Wno-*（构建脚本会直接拒掉，报 flag_not_allowed）。理由是：关掉一条警告不等于问题解决了，只是把眼睛闭上了；如果一条警告真的在某个场景下没意义，正确的做法是改写代码让它不再触发，或者用局部标注说明这一处是有意的——这两种做法都会在正文里留下痕迹，-Wno- 不会。

还有一处容易看漏：诊断下面常常跟着出错那一行的源码，再下一行用 ^~~~~~ 把出错的位置指出来。行号、源码、插入符三样一起看，你就不会数错行、不会改错列。note: 那一行更贴心，gcc 经常把「该补的那行代码」都替你写好了（1.5 的 noinclude.c 就是这样）。

2.3 三道开关：-Wall、-Wextra、-Wpedantic 各管什么

新手的第一个误解是「-Wall 就是打开全部警告」。不是。 -Wall 是一张手挑的名单，挑的是「几乎总是真问题」的那一类。

陷阱「-Wall」里的 W 是 warnings，不是 war on all

你会看到什么：加了 -Wall，编译器还是对你代码里的隐式转换、变量遮蔽一言不发；于是你以为「编译器没意见 = 代码没问题」。

你会怎么误判：把「编译通过」当成「代码是对的」。

真相是：-Wall 只打开一份固定名单；-Wextra 再打开一份；还有一批开关（-Wconversion、-Wshadow、-Wfloat-equal、-Wformat=2…）要你自己加，两个都不含。而本书的基础参数里也没有它们——所以「在本书的参数下编译干净」不等于「这段代码没有隐患」。

空口说「多」没用，我们让 gcc 自己报数。它会带一张自己的开关表，可以用 -Q --help=warnings 打出来；我们数一下每个档位下处于开启状态的开关有多少条：

工程惯例工程惯例：加严开关怎么加、加在哪

-Wconversion、-Wshadow、-Wfloat-equal、-Wformat=2 这一类，属于「打开会更啰嗦、但能挡住真问题」的开关。惯例做法是：

  • 开发时全开：本地和持续集成里把它们一起加上，让问题在提交前就冒出来；
  • 一次只加一个：老代码上一次性全开，你会得到几百条警告，然后就会习惯性忽略——那等于没开；一次加一个、修完再加下一个，才修得动；
  • 别用 -Wno-* 换安静：关掉一条警告不等于问题解决了，只是把眼睛闭上了；真觉得某条警告没意义，正确做法是改代码让它不再触发，或者就地标注说明这一处是有意的——两种做法都会在正文里留下痕迹，-Wno- 不会（本书的清单也直接拒收这类参数）。

代价是真实的：-Wconversion 在大量做整数运算、位操作的老代码上会非常吵，而大部分结果其实是安全的。这是惯例，不是标准——标准里没有「警告」的第二层，只有 2.1 里那句「至少给一条诊断」。

① 未用变量与未用参数（-Wunused-variable / -Wunused-parameter）。它是六类里最像「唠叨」的一条，也是最不该忽略的一条。第 7 行的 unused_flag 是「函数签名留着、实现里没用」——常见于「为了和别处保持一致先占个位」；第 9 行的 scratch 更值得警惕：写它的人本来想拿它做点什么，后来忘了——一个定义了却没用的变量，往往是「本该写的那几行还没写」。1.5 里漏分号那个例子就是它的变体：因为语句没收尾，total 悬空了，于是多出一条「变量没用」。

再看中段的两处，它们的共同点是「代码能跑，但意思不是你以为的那个意思」：

② 有符号与无符号比较（-Wsign-compare）。第 24 行的 n 是 -1，len 是 3u。你可能觉得 -1 < 3 当然成立——但比较之前，C 会把 n 转成 unsigned int，-1 于是变成一个非常大的正数，n < len 不成立。编译器的说法是 comparison of integer expressions of different signedness：两种符号性的整数放在一起比，出事的概率高到它决定提醒你。注意这一条要 -Wextra 才有：2.3 那张图的第 1 帧里就没有它。

③ 赋值与比较混淆（-Wparentheses）。第 29 行写的是 if (x = 5)，一个等号。它是合法的：先把 5 赋给 x，再判断 5 是不是非零——因为 5 非零，所以条件永远成立，里面的 printf 每次都执行。写这段的人本来想写 x == 5（判断 x 是不是 5）。编译器不拦你，因为它不能确定你是不是故意这么写的，它只说 suggest parentheses around assignment used as truth value：如果你想用赋值的结果当条件，那就加一层括号把意图写清楚。

2.4.1 一个 double 用 %d 打出来，为什么会是这个数

先把这行单独请出来看（warn_zoo.c 与 format_mismatch.c 里各写了一处，数字一样）：

1374389535 不是随机数，它每一次运行都是这个值（这两行输出由流水线逐字对账，对不上就报 stale_output）。它是什么？把 3.14 按双精度浮点放进内存，八个字节是 1f 85 eb 51 b8 1e 09 40；取低四位字节 51 eb 85 1f，按小端读出来就是十进制的 1374389535。换句话说，%d 读到的不是「那个数」，而是那个 double 机器码的低 32 位。

标准原文标准原文：格式串对不上，行为是未定义的

C 标准在 fprintf 那一节里写得很干脆：

If any argument is not the correct type for the corresponding conversion specification, the behavior is undefined.

大意：只要某个参数的类型和它对应的转换说明对不上，行为就是未定义的。注意它没有说「会打印垃圾」——未定义的意思是标准对此不作任何承诺：换一台机器、换一个编译器，打印什么都有可能。

出处：ISO/IEC 9899:2018（C17）§7.21.6.1 第 9 段。

那为什么本机每次都打到同一个值？因为这台机器的调用约定替我们定死了这件事：在 Windows x86-64 上，可变参数函数里的浮点参数会被同时抄一份到对应的整数寄存器里；%d 按整数去找，正好找到了那份副本的低 32 位。这个解释只对这个平台成立——它不是语言保证，是实现的巧合。

陷阱「这次打出来是 1374389535，那我改代码时它还会是这个数吧」

你会看到什么：改一改上面的代码，数字跟着变；不改代码，数字稳定复现。

你会怎么误判：把它当成一个「有定义的行为」，甚至拿它去写测试、去推断程序逻辑。

真相是：标准说这是未定义行为。今天你看到 1374389535，是因为寄存器里恰好躺着那个 double 的副本；把 -O2 打开、把参数顺序换一下、把 printf 换成 fprintf，它就可能变成另一个数甚至直接崩掉。见到这类「稳定复现的怪值」，要做的不是记下它，而是回到格式串去改它。

（warn_zoo.c 那份文件里还有第 ⑥ 类的现场：x = ratio; 之后 x 是 3，小数没有四舍五入——这一条留给你自己去看。）

到这里你大概已经发现：一次编译往往不止给你一条诊断。那就得有个读法。diag_chain.c 只错了一个字符——第 6 行末尾少了一个分号：

一个字符的错，编译器给了三条诊断：

按 2.2 的四段读法拆开：

  • 第 1 条 error 报在 diag_chain.c:7:5，说的是 expected ',' or ';' before 'int'——「在第 7 行这个 int 前面，我期待一个逗号或分号」。注意：要改的是第 6 行的末尾。为什么报在第 7 行？因为编译器只有读到第 7 行的 int，才能确定第 6 行那条语句还没收尾。这个「报错行号比真正的错误晚一行」的现象，1.5 的 semicolon.c 里见过一次，这里是它的第二次出现。
  • 第 2 条 error 报在 diag_chain.c:8:28，'count' undeclared (first use in this function)——「count 没有声明」。可是第 7 行明明写了 int count = 3;。原因是第 7 行自己也没被解析成一条完整语句，于是 count 这个名字没有被承认，第 8 行用它的地方就报「没声明」。
  • 第 3 条 note 是给第 2 条的补充：each undeclared identifier is reported only once for each function it appears in——「同一个没声明的名字，在一个函数里我只报一次」。这是编译器在告诉你别指望后面的重复错误，也是它劝你「先修上面那条」。

三条诊断里只有第一条是真错误，第二、三条都是它的下游。所以有一条读法要背下来：先只改第一条，重编，再看剩下的还在不在。 一次全改会让你分不清哪条诊断是哪个改动带来的；而很多时候，改完第一条，后面几条自己就消失了。这条规则在 1.5 里已经用过一次（漏分号时那条「变量没用」的警告），这一节是它更清楚的版本。

陷阱「一屏二十条错误，我从第一条一口气改到底」

你会看到什么：几十条 error 刷满屏幕，第一条和第二条看起来毫无关系。

你会怎么误判：以为代码有几十个毛病，一边改一边怀疑自己的水平。

真相是：绝大多数情况下，真错误只有一两条，剩下的全是它们的下游——一个漏掉的分号可以让编译器整段看不懂，于是「每一样东西都不认识」。做法永远是：改第一条 → 重新编译 → 看条数掉到几条 → 再改新的第一条。上面那个例子里，补上第 6 行末尾的分号，三条诊断一起消失。

大白话用大白话说这三条命令
  • -c：把 .c 翻成机器码，装进一个盒子（.o）就不管了。盒子上贴着「我引用了这些名字，但它们的地址还不知道」；

两块对着读，差别一目了然：

  • -O2 -g：程序自己把 add(2, 3) = 5 打印完就正常退出了，break add 一次都没停，bt 说 No frame selected. / No stack.。原因是 -O2 把 add 内联进了 main——函数还在，但不再是一个可以停下来的地方了。

「内联」这件事不需要猜，看汇编就知道。同一份 stages_c.c 用 -S 只生成汇编，再数一数有没有 call add：

-O0 的汇编里有 1 次 call add，-O2 的是 0 次：add 的函数体还在（所以 gdb 还能在它上面下断点），但 main 已经不调用它了——加法的两条指令被直接搬进了 main。断点停不住，不是 gdb 坏了，是程序里已经没有那次调用了。

这就是 -O0 与 -g 的价值，说清楚它们的边界：

  • -g 让编译器把「哪条机器码对应源文件哪一行、哪个变量住在哪」写进目标文件。没有它，gdb 只能给你一串地址。
  • -O0 让编译器照着你的写法生成代码：不内联、不把变量塞进寄存器、不删掉「显然没用」的语句。所以断点停得住、info args 有值、行号能对上。
  • 代价是真实的：-O0 跑得慢、汇编长、有些优化相关的分析不做。本书接受这个代价，因为这一阶段你要看的是「程序在按你写的样子走」。
工程惯例工程惯例：什么时候用什么档

标准里没有 -O 这个概念，它纯粹是编译器开关。惯例是：发布用 -O2、不带 -g（快、体积小）；要读诊断、要单步调试时用 -O0 -g。-O2 -g 也能同时存在，只是行号和变量不一定对得上（上面第二块就是活证据）。所以本书把 -O0 -g 定成默认，把 -O2 留作对照实验。

它是一把双刃剑，所以主流做法是分场合：

  • 不该默认开：本地开发。你会为了通过编译去写一些没意义的代码（比如把没用上的参数加个 (void) 骗过编译器），而不是去想「这个参数是不是本来就该删掉」；
  • 它的真实代价：-Werror 把「警告」这个可以商量的信号变成了硬门槛，而这个信号是编译器版本相关的。换一个编译器版本、加一个新开关，原本能编过的代码会突然编不过——而且失败的原因不是你改了代码，是工具变严了。所以用 -Werror 的工程通常会把「编译器版本」也钉住（或至少知道自己在哪个版本上过）。

顺带说一句本书的做法：-Werror 只用在故意编不过的教学例子上（这份清单写的就是 mode=compile_fail），所以正文里它的任务是演示「警告升格」，不是推荐你默认打开。这是惯例、不是标准——标准里同样没有 -Werror 这个东西。

  1. 它给的东西和普通警告不一样：诊断里带 [CWE-121]（一个公开的缺陷分类编号）和 [-Wanalyzer-out-of-bounds] 这个专属标签；完整输出里还会配一张缓冲区示意图（这里用 grep 只挑出了带 Wanalyzer 的那一行）。
  2. 编译退出码仍然是 0——-fanalyzer 报的是「我认为这里有缺陷」，不是「我拒绝翻译」。所以它不能替代测试，更不能当成运行结果。
  3. 它有盲区：同一个 -fanalyzer 去看 format_security.c，一条分析器诊断都没有（grep -c 数出来 0）；那 4 行 stderr 是 -Wextra 给的「参数没用上」，跟缺陷无关。它没看见那个格式串漏洞。
  4. 所以它的定位是：锦上添花的第三只眼，覆盖范围是一批特定缺陷（堆/栈越界、空指针之类），不是「全面体检」。
编译器视角编译器视角：为什么「静态分析」不等于「运行结果」

-fanalyzer 干的事是在你的代码上跑一遍模拟：假设程序会怎么走、内存会怎么变，然后看有没有一条路径上出界了。它的两个特点是：

  • 可以报到你没执行过的路径——这很有用，因为测试覆盖不到的分支正是 bug 最容易藏的地方；
  • 会误报（false positive）——它的模型不可能和真实机器一样，宁可疑心重一点也不放过。

对照着看：-fanalyzer 是编译期的话（它可能报一个永远走不到的路径，也可能漏掉一个真缺陷）；2.4.1 里的 1374389535 是运行期的话（它只在真跑的时候才存在）。这两类证据不能互相替代，本书会一直把它们分开写。

那么「一台机器上到底有哪些检测手段」这件事，得如实交代。本机的实测结论是：没有 ASan / UBSan。

-fsanitize=address,undefined 是 GCC 提供的运行期检测器（ASan 抓内存越界，UBSan 抓未定义行为）。在这台机器上它编译能过、链接失败——那一行 collect2.exe 说明链接器找不到它要的那两个运行库；按本机工具链事实文件的记录，这个 MSYS2 安装里没有 libasan / libubsan，软件仓库里也没有对应的包（这一条我没有再去仓库里核实，但链接失败本身是上面刚跑出来的）。标准里没有这两个工具的位置，它们是工具链提供的，有就有、没有就没有。

工程惯例工程惯例：为什么这些开关要写进清单的 `detect` 字段

每个例子的清单里有一项 detect，声明「靠哪个检测手段、证据是什么」。理由和 2.2 那对方括号一样：把「谁抓到的」写下来，别人才能复核。规矩三条：只能用本机真能用的手段；必须声明证据（编译期诊断文本、运行期非零退出码）；证据还得归属于这个手段——脚本会去掉检测参数再算一遍，同样的证据还在就判不通过。「程序自己打印一行 stack smashing detected 假装被抓住」这种例子在这里过不了。

最后说一个不起眼但贯穿全书的参数：-fdiagnostics-color=never。它的唯一作用是让 gcc 不要把 ANSI 颜色码写进诊断文本。这不是教学内容，是本书的流水线要求：正文里的每一段诊断都要和真实输出逐字一致，颜色码会随终端环境变化、在纸上也没意义，关掉它诊断文本才稳定可对账。你自己在终端里看时不用加它——彩色诊断更好读。

2.11 这一单元新增了什么，以及接下来

回到 2.1 的第 2 帧，现在可以逐个点名了：

  • warn_zoo.c —— 六类高频警告一次收齐，每一处错都标了原因（2.3、2.4）；
  • extra_warnings.c —— 基础参数下 0 条警告、加严开关下 4 条（2.3），用来证明「干净」这个词取决于参数；
  • format_mismatch.c —— printf("%d", 3.14) 的警告，以及跑出来的 1374389535（2.4.1）；
  • format_security.c —— printf(argv[1]) 的格式串漏洞；基础参数下只报一条未用参数，加 -Wformat=2 才多出 -Wformat-security（2.4、2.6）；
  • werror_blocks.c —— 同一份代码：不加 -Werror 退出码 0，加了退出码 1（2.9）；
  • diag_chain.c —— 一个漏分号引出三条诊断，训练「先改第一条」（2.5）；
  • undef_ref.c —— 编译能过、链接失败，诊断里给出 undefined reference to 'helper_add'（2.6）；
  • stages_c.c —— -c 两步走与一条命令的对照，以及 -O0 / -O2 的调试差异（2.7、2.8）；
  • session-diagnostics.txt —— 上面所有命令与输出的抓取，正文里的每一段会话都从它注入；
  • 另外这一单元还借用了已有的 analyzer_demo.c（越界那一段）和一份五行探针，用来讲「警告与优化等级的关系」（2.8.1）。

这一章仍然是单文件项目（第 3 帧）：.c 与清单平铺在 examples/ch01/，没有 src/ 和 include/。为什么可以这样？因为这一章的任务是「把一条命令和它的输出读懂」——诊断、警告、退出码、产物，全都发生在一个源文件上。等这些看熟了，下一章开始换题目：数据本身。下一单元我们从 int 到底能装多大的数讲起，你会第一次遇到「0.1 + 0.2 不等于 0.3」这种看起来像编译器坏了的事——那时候你会很需要这一单元学的东西：先问「用了什么参数」，再看「真实的输出是什么」。

小结这一单元的要点
  • 一条诊断按 文件:行:列: 级别: 说明 四段读，方括号里的开关名告诉你这条由谁控制（-Wno-… 能关，但本书不许关）；级别只有三种口吻：error 停、warning 继续、note 补充；
  • 标准对诊断只要求「至少一条」（§5.1.1.3），文字的格式、名字、分级全是实现的事；
  • -Wall 不是全部：基础档在 warn_zoo.c 上报 5 条，加严开关才到 7 条；同一份 extra_warnings.c 是 0 条 → 4 条；
  • 六类高频警告各有真实的代价：未用变量与参数常是「该写的还没写」，格式串不匹配是未定义行为（§7.21.6.1），-1 < 3u 会判成假，变量遮蔽让你改到另一个变量，隐式转换会悄悄改值，if (x = 5) 永远成立。
小结（续）这一单元的要点
  • 三个期各管一段：undef_ref.c 编译退出码 0、链接失败时给出 undefined reference to 'helper_add'；1374389535 是运行期的事；
  • -c 只编译（.o，2813 字节），链接后才是程序（135094 字节）；一条命令可以列多个源文件/目标文件；
  • -O0 与 -g 是本书默认：断点停得住、行号对得上（-O2 下 add 被内联，bt 直接说 No stack.）；有些警告只在优化或加严开关下出现；
  • -Werror 把警告变成硬门槛（退出码 0 → 1），代价是编译器升级可能让你的代码突然编不过——放 CI，别放本地默认；
  • 本机没有 ASan/UBSan（-fsanitize=… 链接失败）；可用的检测手段各管一摊，边界必须写清楚。

注自测题答案
  1. 由 -Wsign-compare 控制。基础参数下会报（因为基础参数里有 -Wextra），只加 -Wall 时不报——实测同一份 warn_zoo.c：-Wall 下 3 条 warning，加上 -Wextra 变 5 条，多出来的正是这条和 -Wunused-parameter。可以用 -Wno-sign-compare 关掉，但本书的清单不允许减警告参数（构建脚本会拒）。
  2. 3.14 作为双精度浮点，八个字节是 1f 85 eb 51 b8 1e 09 40，低四位字节是 51 eb 85 1f，按小端读成十进制就是 1374389535——%d 读到的是这个 double 机器码的低 32 位，因为本机（Windows x86-64）的可变参数调用约定会把浮点参数同时抄一份到整数寄存器里。标准的规定是：参数类型与转换说明对不上就是未定义行为（§7.21.6.1 第 9 段），也就是「不作任何承诺」。稳定复现只是因为这套寄存器约定在这台机器、这个编译选项下没变——换 -O2、换参数顺序、换平台就不再有任何保证。标准说的是「未定义」，不是「会打印 1374389535」，所以不能拿它当程序的行为来依赖。
  3. 三条诊断里只有第一条是真错误：报在第 7 行第 5 列（expected ',' or ';' before 'int'），而要改的是第 6 行的末尾——编译器要读到第 7 行才能确定第 6 行那条语句没收尾。第二条 'count' undeclared 是下游：第 7 行自己没被解析成完整语句，count 这个名字就没被承认，第 8 行用它的地方自然报「没声明」；第三条 note 是补充（同一个没声明的名字只报一次）。做法：只改第一条 → 重新编译 → 看剩下的还在不在（这个例子里三条会一起消失）。
  4. -c 只做编译（把源文件翻成目标文件），退出码 0：编译期只对一个源文件负责，它看见 extern int helper_add(int a, int b); 这行声明，就认为「这个名字存在、调用合法」。不加 -c 要把目标文件链接成程序，链接期才去落实「这个名字到底有没有实现体」，于是失败。三行里第二行才是关键：undefined reference to 'helper_add'，它直接点出缺的名字（第一行说问题在哪个 .o 里，第三行只是 collect2 的总结「退出码 1」）。如果只看到一行 collect2.exe: error: ld returned 5 exit status，说明链接器的正文被环境吞掉了（我实测：默认 PATH 下如此，换一个干净的 MSYS2 PATH 就恢复成三行），这时换终端重跑一次，或者直接回命令里找：哪个源文件没被列进去（补上它之后 gcc undef_ref.c helper_add.c -o app 退出码 0，程序打印 sum = 5）。
  5. 代价：-Werror 把「警告」这个可以商量的信号变成硬门槛，而警告是编译器版本相关的——升级编译器、多开一个开关，原本能编过的代码会突然编不过，失败原因还不是你改了代码。值得开的场合：持续集成、发布前构建、新写的代码（核心目的是不让警告攒起来）。别默认开在本地开发。&& 看的是前一条命令的退出码：退出码 0 才执行下一条，非 0 就停下——所以 gcc … && ./app && echo ok 要能走到 echo ok，前提是编译和运行都成功。
