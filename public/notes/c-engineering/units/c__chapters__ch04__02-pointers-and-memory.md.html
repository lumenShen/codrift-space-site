大白话用大白话说「指针不是地址」

把内存想成一排信箱，每个信箱有编号。

  • int x = 42; 是「开一个信箱，写上 42」；
  • int *p = &x; 是「另外开一个信箱（它自己也有编号），里面写的是 x 那个信箱的编号」；
  • *p = 7; 是「按 p 里写的编号找过去，把那个信箱里的内容擦掉写成 7」——所以 x 变了，而 p 自己一点没变；
  • p = &y; 是「把 p 里那张纸条换成 y 的编号」——x 与 y 的内容一个都不会变。

所以「指针」这个词指的其实是两个东西：一张写着编号的纸条（指针变量本身），和它指向的那个信箱（对象）。新手最容易把这两件事合成一件，然后就会问出「为什么我把指针改了，原来的数没变」。

标准原文标准原文：`&` 与 `*` 是怎么定义的

C 语言标准（ISO/IEC 9899，C17）6.5.3.2 节「Address and indirection operators」规定：

The unary & operator yields the address of its operand. … The unary * operator denotes indirection. … if the operand has type ''pointer to type'', the result has type ''type''.

大意：& 交出一个对象的地址，* 是间接寻址——对一个类型是「指向 T 的指针」的操作数用 *，结果的类型就是 T。标准刻意不提「地址就是一个整数」，因为标准里的地址是抽象的东西；把指针当整数算，是实现允许、但标准不保证的事。

出处：ISO/IEC 9899:2018（C17）§6.5.3.2 第 3、4 段。

陷阱「指针就是地址」——这句话会让你在后面的每一节里踩坑

你会怎么被坑到：一旦心里认定「指针 = 地址」，下面这些问题你都会答错——

  • 为什么 int * 与 char * 指同一个地址，读出来的东西完全不同？（9.3 节：类型决定一次解引用读写几个字节）
  • 为什么 p + 1 不是「地址加 1」？（9.6 节：指针运算按元素走，前进 sizeof(*p) 个字节）
  • 为什么 free(p) 之后 p 里的地址还照样打印得出来，程序却已经错了？（9.8 节：地址还在，对象没了）

真相：指针变量的值确实是一个地址，但指针的类型带着两样地址之外的信息——一次读几个字节、以及按几个字节一步往前走。所以本书的行文会是「这个指针指向类型 int 的对象」，而不是「这个指针是一个地址」。

  1. (int *) 与 (char *) 打出来的地址完全相同，它们是同一个地址吗 = 是。地址就是一个数，谁指过来都一样。
  2. 「一次解引用读几个字节」：int * 是 4，char * 是 1。这才是类型真正管的事。*ip 一次读 4 个字节，cp[i] 一次读 1 个字节——同一块内存，两种读法。
  3. 0x41424344 与 0x44 0x43 0x42 0x41：v 的十六进制值是 41424344（ASCII 里 'A'=0x41、'B'=0x42…），而按字节逐个读出来是 44 43 42 41——反的。这不是 bug：本机是小端（little-endian），一个多字节整数里，低位字节住在低地址。所以 cp[0] 打出的是 'D'（0x44），cp[3] 才是 'A'。

第 1 帧是这块内存的真实内容（四个字节，从低地址到高地址是 44 43 42 41）。第 2 帧是 int * 的读法：一次吃四个字节，按小端规则拼成一个 32 位整数 0x41424344。第 3 帧是 char * 的读法：一次只吃一个字节，所以它看不到一个整数，只能看到一个字符。第 4 帧把两个指针摆在一起：值相同、类型不同——它们指向同一块内存，但「一次看多少」不一样。

语法规则`void *`：一个不带类型的地址

本节的模块里好几个函数的参数写的是 const void *p（比如 read_head_as_int、read_via_memcpy）。void * 是通用指针：任何「指向对象的指针」都能赋给它、也能从它转回来，但标准同时给了它两条限制——不能解引用它（*p 编不过，因为编译器不知道一次该读几个字节）、不能对它做指针算术（p + 1 编不过，因为它不知道一步该走多远）。

所以在函数体里必须先转成具体类型：const int *ip = (const int *)p; 之后才谈得上解引用。这一步转换恰恰是类型的责任：int * 与 char * 的差别、对齐的约束、一次读几个字节，全都在这句转换里定下来了。

大白话同样一块地，两种量法

这段内存像一块四个格子的巧克力。int * 是拿一把四格量尺：一次量满四格，说「这一板是 0x41424344」。char * 是拿一把一格量尺：一次量一格，说「第一格是 'D'」。

尺子不一样，量出来的答案自然不一样，但地还是那块地。真正决定「量几格」的，不是地址，是尺子的类型。

标准原文标准原文：`(int *)` 这次转换意味着什么

同一个标准 6.3.2.3 节「Pointers」说：

A pointer to an object type may be converted to a pointer to a different object type. If the resulting pointer is not correctly aligned for the referenced type, the behavior is undefined.

大意：「指向 T 的指针」可以转成「指向 U 的指针」，这是标准允许的；但转换出来的指针如果没有按 U 的要求对齐，那行为就是未定义的（9.4 节会拿真程序试这件事）。

请注意标准没说的一句话：它从来没说「你可以用 int * 去读一个 char 数组里的四个字节」——那样做会同时踩到对齐规则与严格别名规则（第 19 单元讲）。标准给出的正统做法是 memcpy，9.4 节会演示。

出处：ISO/IEC 9899:2018（C17）§6.3.2.3 第 7 段。

大白话「能跑」与「保证能跑」是两件事

0x11414243 这个值，两个函数都算对了。区别不在结果，而在承诺：

  • 第一种写法（*(const int *)(p + 1)）对标准来说已经踩到未定义行为了——标准只允许你把指针转成别的类型，但如果新地址没按 int 对齐，行为就是未定义的（这是对齐规则，不是「越界」：raw + 1 那个地址本身还在数组里，越界说的是 9.6 节那种算到数组外面去的指针）。它今天在这台 x86-64 上「能跑」，只是因为 x86-64 的硬件允许未对齐访问（慢一点而已）；
  • 第二种写法（memcpy）标准明确保证：它按字节搬，不要求对齐，也不关心你搬的是什么东西。

所以规矩很简单：要跨类型看字节，用 memcpy；要用别的类型解引用，先确认地址对齐。换成 ARM 上某些配置、或者换成一个会把未对齐访问变成陷阱的编译器，第一种写法会当场给你一个非法指令。

你在标准库里会反复看到这种形状：先 memcpy 到一个对齐的局部变量里，用完再 memcpy 回去。看起来啰嗦，但这是唯一既能跨平台、又不会踩别名规则的做法。

代价是两件事：多一次内存拷贝（现代编译器通常能把它优化成一条 mov，这是它自己决定的事，不是你保证的事）；以及你得自己在注释里说清「这里搬的是什么类型」。第 11 单元讲结构体 padding 时，还会再遇到同一套规矩。

语法规则`printf` 的 `%p` 配什么类型

%p 要的是 void *。把一个 int * 直接交给 %p，本机就会警告（我实测：warning: format '%p' expects argument of type 'void *', but argument 2 has type 'int *' [-Wformat=]，-Wall -Wextra 给的），所以本书所有打印指针的地方都写成 (void *)p：这是 %p 的格式约定，不是类型转换的魔法——(void *) 只是把「指向某类型」这层信息丢掉，好让 printf 用一个统一的方式打印它（本机打出来是 16 位十六进制）。

顺带一句：%p 不是标准里为了好看定的，它的输出格式由实现决定——标准只要求「实现定义」，所以同一段代码在不同运行库上打出来的样子可能不同（本机有前导零，有些平台打印 0x 前缀）。想比较两个地址就用 == 比较指针，别去比字符串。

工程惯例工程惯例：判空到底该谁做

标准只规定「解引用空指针是 UB」，它从不说谁该判空。这件事是接口设计问题，主流惯例是：判空写在「知道该怎么处理」的那一层。

  • 库函数的一般做法：接受空指针，并把它定义成一个有意义的结果。本例子里的 write_checked(NULL, 5) 返回 -1，意思就是「我拒绝写」——这个 -1 是接口契约的一部分，写在 include/null_deref.h 的注释里（第 4 行）。
  • 调用者的一般做法：如果这个指针是你自己从 malloc 拿的，你要判（malloc 失败会返回空指针）；如果它是别人交给你、且契约上说「不会是空」的，那就不必每次都判——但那时文档与命名要写清楚。

代价要说清：每多一次判空，就多一次分支（性能上几乎为零，可读性上是实打实的）；而不判的代价是「一次空指针解引用，进程直接没了」。这就是为什么很多团队的规矩是「对外接口一律判，内部控制流内部的指针不判」。

陷阱「我判过空了」——判过一次并不等于安全

你会怎么被坑到：你在函数开头老老实实写了 if (p == NULL) return -1;，之后整段代码就再也没看它。程序平时好好的，有一天崩了，位置却在那个判空后面很远的地方。

下面三种情况，判空都拦不住：

  • 指针在别处被改掉了：p 是上一层的局部变量，中间调用的某个函数里有 free(p); p = NULL;（9.8 节那种写法）——可那只是它自己形参的副本，你的 p 还指着已经还回去的内存。9.8 节的 gdb 会话就是这件事的现场：free 之后 p 里的地址一个字没变。
  • 判的是空指针，坏的是悬垂指针：NULL 只表示「谁都不指」，而悬垂指针不是空指针——它有一个看起来完全正常的地址，p != NULL 成立，解引用照样是 UB。判空筛掉的是「从来没指过」的那一类，筛不掉「指过、但对象已经没了」的那一类。
  • 同一块内存有多条路：两个指针指向同一块 malloc 出来的内存（别名），其中一个还回去了，另一个没有任何办法知道。C 里没有「这个指针还有几个主人」的记账——所以惯例是把所有权写进接口（谁分配谁释放），而不是指望判空兜底。

真相：判空只回答「这个指针里是不是那个约定的空值」，它回答不了「它指的东西还在不在」。想覆盖后者，只能靠所有权纪律（9.8 节的 visibility 图）与工具（本机的 -fanalyzer 会报 -Wuse-after-free 那一族警告，9.9 节见过）。

标准原文标准原文：`a[i]` 到底是什么

C 语言标准 6.5.2.1 节「Array subscripting」第 2 段：

The definition of the subscript operator [] is that E1[E2] is identical to (*((E1)+(E2))).

大意：E1[E2] 与 *((E1)+(E2)) 是同一个东西（identical，一字不差）。所以 a[2] 就是 *(a + 2)，而 2[a] 也是合法的——它会先被当成 *(2 + a)，加法的两个操作数可以换位置，于是结果一样（能跑，但没人这么写）。

同一份标准的 6.5.6 节「Additive operators」第 8 段，规定了指针加减的合法范围：

If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined.

大意：只有结果仍落在同一个数组里（或者正好落在最后一个元素的「下一格」）时，指针加减才是定义良好的；出到外面就是未定义行为。

出处：ISO/IEC 9899:2018（C17）§6.5.2.1、§6.5.6。

「下一格」（one past the end）是标准给的一个特例：a + 5 合法，但 a[5]（解引用它）不合法。这个「可以算，不许读」的边界，正是 for (p = a; p != a + 5; p++) 这类循环能成立的原因。

标准原文标准原文：什么是「生命期」

C 语言标准 6.2.4 节「Storage durations of objects」第 2 段：

The lifetime of an object is the portion of program execution during which storage is guaranteed to be reserved for it. An object exists, has a constant address, and retains its last-stored value throughout its lifetime. … The value of a pointer becomes indeterminate when the object it points to (or just past) reaches the end of its lifetime.

大意：对象的「生命期」= 保证给它留着内存的那段时间；在这段时间里它一直存在、地址不变、值不变。最后那句更要紧：当它指向的对象（或对象之后的「下一格」）生命期结束时，这个指针的值就变成不确定的（indeterminate）——也就是说，这时候连「把那个地址打印出来」或「拿它比较」都不是标准保证的事。

出处：ISO/IEC 9899:2018（C17）§6.2.4 第 2 段。

大白话局部变量、static 变量、malloc 出来的，各活多久
  • 局部变量（char buf[16]，没加 static）：生命期是它所在的那次函数调用。函数一返回，内存就被收回——它住在栈上，栈是「函数调用专用的临时区」。所以把它的地址交出去，等于交给别人一张写着「我马上要搬走」的地址。
  • static 局部变量（static char buf[16]）：名字还只在这个函数里看得见，但内存从程序开始到结束一直留着——它住在静态区。所以交它的地址是安全的。本机实测（见下面那张图与会话）：静态区里的对象地址在 0x00007FF6… 这一带，栈上的局部变量在 0x00000000005FFE… 这一带，差了十万八千里——因为它们压根不在一个区里。
  • malloc 出来的：生命期由你决定——从 malloc 成功那一刻开始，到你 free 为止。它住在堆上。9.8 节讲它。

这三种生命期在标准里的名字分别是 automatic（自动存储期，栈上那些）、static（静态存储期）和 allocated（分配存储期，malloc 那些）。名字记不住没关系，记住「谁负责收回」就够了：前两种是自动收回的（编译器与程序启动/结束负责），只有第三种要你亲手 free。

工程惯例工程惯例：`static` 是权宜之计，不是标准解法

把局部数组改成 static（或者退回一个全局数组）确实能让地址活下来，很多标准库函数也这么干（比如有些老接口返回一个「内部缓冲区」的地址）。但代价写在这里：

  • 两次调用会共用同一块内存：greeting_ok() 返回的地址永远相同，调用两次拿到的字符串会被后一次覆盖；
  • 不能重入：多线程或多层嵌套调用时，两个调用者会互相踩（第 15 单元讲字符串库函数时会再遇到这个坑）；
  • 生命周期失控：那块内存一直占着，程序跑多久它就留多久。

更常见的做法是让调用者出内存（void greet(char *out, size_t n)），或者动态分配并约定谁释放（9.8 节）：分配的责任与释放的责任写进接口，而不是藏在函数里面。

同一份机器码，只因为启动时那串路径不同（相对还是绝对、名字有多长），就会在两个终止码之间跳：3221226356（0xC0000374，分配器在进程退出时发现账本被写坏）与 3221225477（0xC0000005，当场非法访问）。这不是规律，只是「那串路径影响了进程启动时的内存排布」。而 -O2 那一栏无论怎么启动都是 0——因为那句写根本没被执行，不是运气。

所以：同一个错，连「怎么死的」都取决于怎么启动它。这正是 UB 的含义——不是「一定会崩」，而是「谁都不欠你一个确定的结果」。清单里的 opt-diff 只声明「两档退出码不同」；闸门固定把可执行文件编译到 dist/work/<id>/ 下、用绝对路径启动，所以「3221226356 对 0」这个对照在闸门里是可复现的——它证明的是「两档有可观察的差异」，不是「这个错一定给出 3221226356」。

陷阱double free：同一块内存还两次，程序当场终止

你会怎么被坑到：两条 free(p) 摆在不同的分支里（比如「提前返回」的那条路上也 free 了一次），你以为只会走一条路。程序平时跑得好好的，某个输入下突然整个进程没了。

本机的真实现象（探针程序 examples/ch04/double_free.c，同样没有清单，证据是会话 session-double-free-pointers.txt）：它先把两行输出打了出来（因为那里显式 fflush(stdout)），然后被终止——退出码 3221226356（0xC0000374，同一个「堆损坏」代码），stderr 一个字节都没有。fflush 那一行不是装饰：不加它，你会连那两行输出都看不到，还会误以为「程序在第一次 free 之前就崩了」。

真相：分配器在自己的账本里记着「这块内存是空闲的」，第二次 free 等于把同一块内存还两次，账本直接乱掉，本机的运行库选择立刻终止进程（这是运行库的照顾，不是标准的要求；标准只说「UB」，见下面）。注意这里没有报错文本：终止时 stderr 是空的，唯一的线索就是那个退出码。

标准原文标准原文：`free` 的契约

C 语言标准 7.22.3 节「Memory management functions」对 free 的规定：

The free function causes the space pointed to by ptr to be deallocated, that is, made available for further allocation. If ptr is a null pointer, no action occurs. Otherwise, if the argument does not match a pointer earlier returned by a memory management function, or if the space has been deallocated by a call to free or realloc, the behavior is undefined.

大意：free 把 ptr 指向的空间还回去；ptr 是空指针时什么都不做（这就是为什么「先判空再 free」在某些老代码里很常见）；除此之外，如果这个指针不是分配函数返回的、或者这块空间已经被释放过，行为就是未定义的——标准只说 UB，后果由实现决定（本机的实现选择是：终止进程）。

出处：ISO/IEC 9899:2018（C17）§7.22.3 第 2 段。

9.9 UB 之下编译器有多大自由度

到现在为止，这一节里的错误程序有一个共同点：它们都「看起来正常」。越界写可能什么都不发生，free 之后再写可能照样打印，悬垂指针可能给你一个空指针——那编译器到底把这些代码变成了什么？看汇编。

两份文件都在例子目录里：main-O0.s 是基础参数（-O0）编出来的，main-O2.s 是 -O2 编出来的，源码都是 heap_after_free/src/main.c。先看 -O0：free(p);（源码第 15 行）与它之后那句写（第 16 行）都在。

再看 -O2：同一份源码，malloc、free、那句写全都不见了——被优化器整段删掉，只剩一句 printf 与收尾的 say_done。

编译器视角编译器视角：它凭什么删掉那两句

优化器的推理链是这样的（每一步都合法）：

  1. *p = 42; 之后紧跟 printf(..., *p)，中间没有任何东西能改 *p，所以 *p 就是 42——直接把常数 42 传给 printf，连带那句写也不再需要；
  2. free(p); *p = 7;——按标准，free(p) 之后 p 就是悬垂指针，对它解引用是 UB。UB 的意思就是：编译器可以假设它从不发生。既然不会发生，*p = 7 这句写就没有任何可观察的效果，可以删；
  3. 写被删掉之后，那次 malloc 也没有可观察的效果了（没有人读它），于是 malloc 与 free 一起被删；
  4. 删完之后，__main、printf、say_done 三次调用就是整个程序——所以 -O2 的退出码是 0，而 -O0 是 3221226356。

这条链每一步都对，这就是为什么「换个优化等级行为就变了」不能怪编译器——它只是按标准给的许可在办事。这也正是本节要你记住的那句话：UB 不是「一定会崩」，而是「谁都不欠你一个确定的结果」。

清单 examples/ch04/heap_after_free/heap_after_free.json 就是这个对照的机器核对版：它写的是 "mode": "detect"、"detect": "opt-diff"、"expect": { "differs": "exit" }——闸门按工具链配置里的两档（-O0 与 -O2）各编一次、各跑一次，发现退出码不同才算这份证据成立（闸门这次量到的是 3221226356 对 0）。注意它证明的是什么：opt-diff 只能说明「同一份源码在两档下有可观察的差异」，它不能证明「差异只可能出现在这个例子上」——我也拿 dangling_stack 试过两档，行为一模一样（都是 (null)、退出码 0），所以它当不了这个样本；而 heap_after_free 在两档之间的差别有汇编撑腰（下一节），这是实测加证据的结果，不是挑好看的写。

9.10 const 与指针：三种写法，从右往左读

指针与 const 放在一起有三种写法，区别只有一个词的位置：

语法规则从右往左读，一次读一个词

声明的读法只有一个规则：从变量名出发，先往右，再往左。

  • const int *p1：从 p1 往右没有东西，往左看 *——「p1 是一个指针」；再往左 int 带着 const——「指向 const int」。所以不能通过 p1 改它指的东西，但 p1 可以改指向（p1 = &y; 合法）。
  • int * const p2：const 紧挨着 p2，锁住的是**p2 自己**——它必须一直指着 x，但 *p2 = 5; 可以改 x。
  • const int * const p3：两边都锁：既不能改 *p3，也不能改 p3。

一句话记法：const 在 * 右边（* const p）锁的是指针本身；在 * 左边（const int *）锁的是它指的东西。

原因是这四处都是硬错误（error:）：C 语言里直接给一个 const 对象赋值，本身就是非法，不需要靠「把警告升级成错误」来拦。

真正需要 -Werror 的是另一个方向——把 const int * 交给一个 int * 参数（丢弃 const）。本机实测：那种代码只报一条警告（warning: passing argument 1 of 'set_first' discards 'const' qualifier from pointer target type [-Wdiscarded-qualifiers]），编译退出码是 0；加上 -Werror 才变成编译失败。这条差别属于「接口设计」，是下一个单元（chapters/ch04/03-pointer-idioms.md）的主角。

工程惯例工程惯例：接口上的 `const` 是谁的承诺

函数参数上写不写 const，标准不管你，但它是这个接口对调用者的承诺，惯例是：

  • 只读的输入写 const T *：告诉调用者「我不会改你的东西」，也告诉编译器「这里可以放心优化」。本例子 include/const_ptr.h 第 5 行的 int read_through(const int *p); 就是这个形状；
  • 要写的输出才写 T *，并且在注释或命名上说明「它会写你的对象」；
  • 锁指针自己的 T * const 参数很少见：形参本来就是副本，锁它没有意义。「锁指针自己」主要用在局部变量上（防止自己在后面的代码里改错指向）。

代价：接口一旦承诺了 const T *，实现里就不能改那个对象了（改了编不过）——这正是你要的；反过来说，事后想改成 const 就难了，因为要去掉所有「丢弃 const」的调用点，所以这件事要在写第一版接口时定下来。

9.11 三条要写成习惯的规矩

指针的行为到这里就讲完了。把最容易反复出错的三件事收成三条规矩，每条都能在上面找到证据：

  1. 看到 p[i]，就在心里读成 *(p + i)：它们完全等价（9.6 节的标准原文里写的是 identical）。这条规矩让你在「数组」与「指针」之间来回翻译时不会犯迷糊——p[i] 里的 p 是不是数组名，都不影响它。ptr_arith 里那个 diff_of_two_forms 就是拿这两种写法互相减，实测结果永远是 0。
  2. 接口上「从哪开始」与「有几个」永远成对出现：函数参数写成 const T *a, size_t n（ptr_arith 与 ptr_types 两个模块都是这个形状）。数组名一进参数就退化成指针，sizeof 再也问不出长度——没有任何办法在函数里把长度找回来（sizeof_in_function 实测给出 8，那是指针的大小）。
  3. 判空写在「知道该怎么处理」的那一层：能拒绝就拒绝（返回错误码 -1），拒绝不了就别解引用（那是 3221225477）。判空的责任与后果都要写在头文件注释里（null_deref.h 第 4 行）。

小结这一节的要点
  • 指针是一个变量，里面装的是地址；& 与 * 是一对逆运算；真正决定行为的是类型——一次解引用读几个字节（int * 是 4、char * 是 1）、一步走多远，都由它定，本机是小端（低位字节住低地址）；
  • 跨类型看字节用 memcpy：未对齐的硬解引用在本机能跑、在别的架子上可能直接陷阱，标准说它是 UB；a[i] 与 *(a + i) 完全等价，指针运算按元素走，越界指针的计算本身就是 UB；
  • 生命期分三种：栈上的自动存储期（函数返回就没了）、静态区（程序全程在）、堆（你 free 才没）；空指针解引用退出码 3221225477、stdout 可能一个字节都没有，free 不会把指针置空，double free 在本机当场终止；
  • UB 不是「一定会崩」：-fanalyzer 在编译期指认越界（编译仍退出 0），-fstack-protector-all 把栈越界变成 *** stack smashing detected ***（3221226505），-ftrapv 把有符号溢出变成终止（stdout 会丢）；const 的位置决定锁谁——从变量名出发「先右后左」地读。
自测题自测题（先自己答，再对答案）
  1. int x = 42; int *p = &x; 之后，&x、p、*p、&p 四个表达式里，哪几个是地址、哪几个是值？sizeof p 是多少，为什么？
  2. int v = 0x41424344; 之后用 char *cp = (char *)&v; 读，cp[0] 是多少？为什么不是 0x41？
  3. int a[5]; int *p = a; 时，p + 1 比 p 大几个字节？a + 4 - a 是多少？把 p 换成 char *，这两个答案会变吗？
  4. 一个函数 char *f(void) { char buf[16] = "hi"; return buf; }：它为什么错？本机实测调用者拿到的是什么？
  5. free(p); 之后 p 里的值变了吗？为什么 free(p); p = NULL; 仍然救不了「同一块内存还有别的指针」的情况？
注自测题答案
  1. &x 与 p 是地址（同一个地址）；&p 也是地址，但那是指针变量自己的地址（与 &x 不同）；*p 是值（42）。sizeof p 是 8——指针的大小由机器决定，与它指向什么类型无关（本机 8 字节）。
  2. cp[0] 是 0x44。本机是小端：多字节整数里低位字节住在低地址，0x41424344 的最低字节是 0x44，排在第一个；cp[3] 才是 0x41（也就是 'A'）。
  3. p + 1 比 p 大 4 个字节（sizeof(int)）；a + 4 - a 是 4（指针相减数的是元素个数）。把 p 换成 char *，第一个答案变成 1，第二个不变——相减得到元素个数，与元素大小无关（要字节数得先转成 char * 再减）。
  4. 因为 buf 是自动存储期的对象，生命期只到函数返回；把它的地址交出去等于交出一张「马上作废」的地址条，标准说这是 UB（编译器会警告 -Wreturn-local-addr）。本机实测：编译器直接把这个返回值变成了空指针，调用者拿到 NULL，打印出来是 (null)——这是本机实现的选择，不是规律（换一种写法编译器就没看穿，真能读到栈上残留的字节）。
  5. 没变。gdb 实测：free 之前 p 是 0x71cdc0，free 之后还是 0x71cdc0——free 只把内存还给分配器，不碰你的变量。置空只管住这一个指针；同一块内存如果还有别的指针（别名），那些指针照样悬垂，用它们仍是 use-after-free。这也是为什么本书反复强调「谁分配谁释放」，而不是「记得置空」。
