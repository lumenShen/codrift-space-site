16.1 先看工程长什么样

宏最容易骗人的地方是它长得像函数。你会用函数的一切经验去用它——传参、拿返回值、指望类型检查——然后被咬。这一节我们要做的事，就是把「宏到底是什么」钉死在一件具体的事上：它是一段文字，在编译之前被原地换掉。换掉之后还剩什么、丢掉了什么，全都能用文件和命令看见。

大白话把这一节的目的说成人话

你写的 .c 文件不是编译器直接读的。在它之前还有一道工序，叫预处理：它像一次「查找替换」，把 # 开头的那些行按规矩办掉，产出一份新的文本给编译器。宏就是这套替换规则里最常用的一件工具。

所以要理解宏，得先接受一件反常识的事：编译器从来没有见过 SQ 这个名字。它见到的只是替换之后的 ((1 + 2) * (1 + 2))。你要问「宏有没有类型」「宏有没有作用域」，答案都藏在这句话里。

工程惯例工程惯例：为什么宏头文件放在本章的 include/ 下

标准对「宏写在哪个文件里」没有任何规定：宏是预处理的事，它只认「从这一行往后、在当前这个编译单元里有效」。把共用宏集中到一个头文件，是惯例（不是标准要求），理由是：

  • 一处定义、多处一致：日志格式、边界值、平台开关，各写一份迟早会不一致；
  • 改一处就全改：头文件里改一行，所有包含它的源文件下次编译都跟着变；
  • #undef 有明确的落点：宏集中在头文件里，「从哪一行起换一份定义」这件事只有一处需要想清楚。

代价是污染：头文件里的宏会跟着 #include 走进每一个包含它的编译单元，名字撞了就是你的事（16.10 节会把这件事画出来）。

16.2 预处理是编译之前的一遍文字加工

上一段说的「编译之前的工序」叫预处理。它一共做四件事，全部是对文本做事：

  1. 文件包含：#include 把那个文件的全部内容就地搬进来（第 1 单元 1.3 节亲眼看过：10 行源文件变成 1525 行）；
  2. 宏替换：#define 定下的名字，从这一行往后一律换成它对应的那串文字；
  3. 条件编译：#if / #ifdef 这些按条件留着或删掉整段文本；
  4. 行控制：#line 与编译器自己写下的行号标记，管的是「这段文字在原来源文件的第几行」。

四件事有一个共同点：它们都不知道类型是什么。预处理跑在编译之前，那时候还没有 int、没有 struct、没有函数签名——只有一串一串的字符（准确说是 preprocessing token）。所以「宏有没有类型」这个问题本身就问错了：宏不是值，它是替换规则。

这一点可以直接看。下面这段会话是真的：把 macro_parens 这份源码交给 -E（只做预处理就停），看它把 SQ_OK 与 SQ_BAD 变成了什么。

三件事在这 14 行里一目了然：

  • 宏的名字消失了：SQ_OK(1 + 2) 变成了 ((1 + 2) * (1 + 2))，SQ_BAD(1 + 2) 变成了 1 + 2*1 + 2。编译器看到的就是后面这些（第二行的 sq(1 + 2) 那个函数调用没变，因为函数不是宏）；
  • 括号是你自己写进去的：SQ_OK 的展开里那两层括号，是宏定义里本来就写着的——它不会自动出现；
  • 第一行 # 4 "src/main.c" 2 是行控制：它告诉编译器「下面这段文字回到 src/main.c 的第 4 行」。所以你以后看到的报错，行号永远指向你的源文件，而不是预处理结果。

还有一件顺带的事：宏在运行期一个字节都不占——替换完就退场，程序跑起来时内存里没有叫 SQ_OK 的东西。这是它与函数最本质的区别，也是它「免费」的代价：免费意味着没有类型、没有作用域、没有调试信息。

语法规则这一节要用的两种宏与一条关闭指令
  • #define 名字 一串文字 —— 对象宏；
  • #define 名字(参数) 一串带参数的文字 —— 函数式宏；
  • #undef 名字 —— 从这个点起，这个名字不再被替换。

三条规矩：#define 那一行不写分号（多写一个，那个分号就成了替换内容的一部分）；名字与左括号之间不能有空格（#define DOUBLE (n) 会变成对象宏，不是函数式宏）；替换发生在从这一行往后的文本里，包括后面 #include 进来的头文件。

工程惯例工程惯例：全大写是惯例，不是标准

ARRAY_MAX、DOUBLE、LOG 一律全大写——这是惯例，标准里没有一个字要求你这么做。它买到的是「一眼能认出这是宏」：读到 ARRAY_MAX 你就知道它没有地址、不能取 &，而且在运行期根本不存在（16.2 节那份预处理结果就是证据：程序跑起来之后，内存里没有 ARRAY_MAX 这个名字）。代价是宏与枚举/常量必须用两套命名，团队里要有人守这个规矩。

这段输出里藏着三个结论，一个一个说：

  • DOUBLE(21) 与 times_two(21) 都是 42——宏与函数在这一件事上没区别，都算得出 21 的两倍；
  • DOUBLE(1.5) 是 3.00、DOUBLE('A') 是 130——同一个宏换着类型用，照样能编。这是函数的反面：times_two 只收 int，你传 1.5 进去会先被转成 1。宏的「什么都能用」不是本事，是它根本没有类型：((1.5) * 2) 里的 1.5 就是字面量，编译器看到的是乘法，跟宏无关；

「没有类型」的另一面是「也不做参数检查」，而这件事的后果，编译器会当着你的面说。

  • SUM_BAD(1, 2) * 3 展开成 (1) + (2) * 3，等于 1 + 6 = 7——而你要的是 9。这一次参数包了括号，整串忘了包，外面的 * 3 就只乘到了后半个参数。

两条纪律就藏在这两个数字里：每个参数外面加一层括号，整个展开式外面再加一层括号。第二层是很多人漏掉的那一层——它保的不是参数，是调用点周围的运算符优先级。

陷阱你会怎么被这两个数字坑到

你会这样误判：写完 SQ_BAD(1 + 2) 看到程序跑出了 5，第一反应是「是不是 printf 的格式串写错了」，或者回 main 里把 1 + 2 改来改去。

真相是：问题不在调用点，在宏定义那一行。宏展开是完全机械的文本替换，你写了什么括号它就带什么括号，一个都不多、一个都不少。所以：

  • 出错时的第一个动作应该是「把它展开念一遍」——gcc -E 会把展开后的文本原样给你（上一节那段会话就是干这个的）；
  • 第二个动作是去看头文件里那行 #define，而不是去改 main.c 里的调用。

还有一件更烦的事：SQ_BAD(-3) 打印出来的却是 9，是对的。因为 -3*-3 里一元负号的优先级本来就比乘号高。这类「有时候对、有时候错」的宏最坑人：你测了两个用例都过，第三个才炸。

括号加对了也不代表安全——下一节就是那个「加对了括号照样错」的例子。

陷阱宏与函数的取舍，你会怎么被坑到

你会被这样坑到：本地跑 SQ(i++) 得到 30，看起来完全正常，于是你把它留在代码里；换一台机器、换一个优化档、换一个编译器版本，它可能变成 25 或 36——而你连「这里可能出问题」的念头都没有。

你会怎么误判：把「本机跑出来的 30」当成「这段代码是对的」，于是连编译器那条 -Wsequence-point 也一并当成噪音。

真相是：这里要问的不是「结果是多少」，而是「行为有没有被规定」——30 只是这台机器这一次碰巧给的。

取舍的判断顺序是这样的：

  • 实参可能带副作用时，别用宏：函数调用里实参只求值一次，这是语言规定；宏没有这条保证；
  • 想省一次函数调用时，先别动手写宏：小函数编译器自己会内联（第 7 单元的函数调用栈、第 19 单元的优化边界都会碰到这件事）；
  • 宏留给函数做不到的事：拼名字（##）、拿到源文件名与行号（__FILE__ / __LINE__）、按 -D 开关整段代码（条件编译）——这几件才是宏的主场。

工程惯例工程惯例：`do { … } while (0)` 是惯例，不是标准

标准里没有哪一条写着「多语句宏要包 do…while(0)」——它是 C 社区三十年攒出来的惯例，几乎所有 C 代码规范里都有这一条。理由就是上面那次编译：它让「宏展开后的整块」在语法上等价于一条语句，于是调用点那个分号有了归属，if…else、while、for 都不必额外加花括号。

代价是两点：读的人得先知道这个惯例（否则会想「这里为什么有个只跑一次的循环」）；do…while(0) 里的 break 会跳到 while (0) 后面，所以它既是「失败就跳出宏」的出口，也会让宏里的 break 跳出宏而不是外面的循环。

陷阱宏后面那个分号，还有别的写法会踩

先说你会看到什么。第一条，#define ARRAY_MAX 10; 多写一个分号：主错误落在宏定义那一行（error: expected ')' before ';' token，插入符指着 10;），下面紧跟 note: in expansion of macro 'ARRAY_MAX' 指到使用处——诊断里把宏的名字写出来了，不会「跑到下一行去、看起来跟宏无关」。第二条，另一种老写法 #define SWAP_BAD(a, b) if (1) { … } else：本机实测它在 if … else 里能编、也能跑对（if (1)、if (0)、else if 链三种摆法都试过，退出码 0、行为都对），代价是每个调用点都留一个空的 else，-Wall 给你一条 -Wempty-body。

你会怎么误判：看到 expected ')' before ';'，第一反应是去改 printf 那一行的括号——因为主错误在宏定义、插入符却指着括号，你会以为括号写错了地方；看到 -Wempty-body，又会以为自己的 if…else 漏了花括号。

真相是：这两条症状都来自替换列表。#define 那一行的内容是一串纯文本，多一个分号它就跟着走；if (1) { … } else 把一个悬空的 else 塞进了替换列表，于是每个调用点都多一个空分支。规矩只有一条：#define 那一行永远不写分号，要写分号的地方是调用点；多语句就用 do { … } while (0)，别用 if (1) … else。

陷阱你会以为「变参宏就是 printf 的语法糖」

你会被这样坑到：在别的项目里见过 LOG("hello") 能用，换到本书的 -std=c17 -Wall -Wextra -Wpedantic 下，同一个调用突然编不过；或者反过来，在 GCC 下用 , ##__VA_ARGS__ 写得好好的，换 clang/MSVC 报一堆错。

真相是：零实参的变参宏在 C17 里不合法，能用的那些写法都是扩展（GNU 的 , ##）或更新的标准（__VA_OPT__）。看到这种「同一行代码换个编译器就编不过」，先问的不是「我的括号错了吗」，而是「我用了哪个工具链的扩展」。诊断里的 [-Wpedantic] 就是在提醒你这件事。

工程惯例工程惯例：日志该往哪写

上面这个 LOG 用的是 printf，日志与程序输出混在同一个流里。这是为了这一节的流水线能逐字对账才这么写的；真实项目里日志几乎都写 stderr（把宏里的 printf 换成 fprintf(stderr, …) 即可）。写 stderr 是惯例，标准没有规定日志该进哪个流，理由有三条：

  • 两个流可以分开走：./app > result.txt 只收正式输出，日志仍然打在屏幕上，不会污染结果文件；
  • 崩溃时日志更可靠：标准输出常常是全缓冲的，进程被终止时缓冲区里的内容会丢；stderr 默认不缓冲；
  • 下游的程序不会被日志噎到：./app | grep xxx 时，日志混进标准输出会把下游弄乱。

代价是你要记住「日志在 stderr」，排查时别只盯着 result.txt 发呆。

陷阱发布版里「什么都没有」，你会这样被坑到

你会被这样坑到：调试版里日志打得清清楚楚，发布版里什么都不打。你会这样误判：以为「发布版也走了这些代码，只是不打印」。真相是这些代码根本不存在：((void)0) 之后没有任何东西，n 没有被读、字符串没有进二进制、printf 也没有被调用。

三个由此而来的坑：

  • 参数里的副作用会消失：LOG("%d", i++) 两个版本行为不同；
  • 变量可能变成「未使用」：如果一个变量只出现在日志里，调试版没问题，发布版会给你一条 -Wunused-variable；
  • 别用它做业务逻辑：日志宏只负责日志。要在发布版也执行的检查，用函数、用返回值，不要藏在 #ifndef NDEBUG 里。

「宏属于一个编译单元」的另一面是：在同一个编译单元里，同一个名字不允许被定义成两份不同的东西。6.10.3 节「Macro replacement」第 2 段：

An identifier currently defined as an object-like macro shall not be redefined by another #define preprocessing directive unless the second definition is an object-like macro definition and the two replacement lists are identical.

大意：一个已经被定义过的名字，不许用另一条 #define 重新定义，除非两份的替换列表完全相同。原文这一条只说对象宏；紧接着的第二句把函数式宏也管上了——还要求参数的个数与拼写完全相同（#define F(a) 之后再 #define F(b)，一样算重定义）。标准对「相同」的解释是：预处理记号的个数、顺序、拼写相同，空白分隔也相同，但所有空白分隔被视为同一种——所以 1 + 2 与 1 + 2 是同一个替换列表（不报），1 + 2 与 1+2 不是（报 redefined）。想要换一份定义，得先用 #undef 把旧的关掉。

出处：ISO/IEC 9899:2018（C17）§6.10.3 第 2 段。

工程惯例工程惯例：`#undef` 用来「就地换一份定义」

#undef 是唯一的关闭手段，它买到的是「这一段用这份定义，那一段用那份」。怎么用它是惯例，不是标准要求（标准只规定 #undef 会让这个名字从此不再是宏）。最常见的两个用法：

  • 换掉一个已有的宏值：想给 ARRAY_MAX 换个大小，先 #undef ARRAY_MAX 再 #define ARRAY_MAX 20（不 #undef 直接重定义，编译器会给你 warning: 'ARRAY_MAX' redefined）；
  • 不污染别人：自己写了个临时宏，用完立刻 #undef 掉，免得它被下面的 #include 带进别的文件。

代价是「读代码时要知道宏现在还活着没有」——#undef 一多，读者就得一路往上找最后一处 #define。下一单元（第 17 单元）会把这件事推到头：一个头文件被两个源文件包含时，#ifndef 守门与 #undef 的分工。

大意：先把宏展开、把 defined 算完，然后剩下还没被替换掉的名字一律当成 0。所以 #if LEVEL >= 2 这句话里，LEVEL 不是变量，它就是「一个宏」；它没被定义过就等于 0，#if 因此为假。反过来，#ifdef LEVEL 问的是「这个名字到这一点为止被定义成宏了吗」——这正是理解 #undef 的关键：同一次编译里，同一个名字在文件的前半段与后半段可以是「有」或「没有」。

出处：ISO/IEC 9899:2018（C17）§6.10.1。

条件编译在工程里有三个真实用途，这一节三个都演了：前两个在下面，第三个（开关式调试代码）在 16.9 节用 -DNDEBUG 演过。顺便说清写法上的四种口吻，它们两两等价：#ifdef X 就是 #if defined X，#ifndef X 就是 #if !defined X。defined 是条件编译里唯一一个预先认识的运算符：它问的不是「这个名字的值是多少」，而是「这个名字现在是不是一个宏」。

  1. include guard（头文件的守门人）：#ifndef X_H / #define X_H / … / #endif 保证同一个头文件在一次编译里只被念一遍。这一节每个头文件都用它（cond_compile.h 第 1、2、12 行就是），而它的完整故事属于第 17 单元——那时你会看到不加守门会撞成什么样；
  2. 按平台 / 工具链分支：同一个项目要给 Windows 和 Linux 编，#if 那些平台宏（下一节的 TARGET_OS 就是这类开关）选不同的实现；gcc -dM -E - < /dev/null 还能把编译器预定义的全部平台宏列出来——它们是工具链给的，不是语言给的；
  3. 开关式调试代码：整段整段的调试打印、性能计数，用 #if 包起来，编发布版时一个字都不进二进制（这与 16.9 节那个 #ifndef NDEBUG 是同一件事，只是粒度更大）。
陷阱条件编译最坑人的地方：你读到的代码，不一定是它编出来的代码

你会被这样坑到：翻着源码排查问题，看见 extra_add(2, 3) 明明写在那儿。你会这样误判：源码里写着，就认定它被执行过。真相是那几行可能根本没进二进制——源码里写着的东西，要经过「条件编译→宏展开」两道剪切才轮到编译器看。

三个立即可用的排查动作：

  • 想知道「这段到底编进去没有」，用 gcc -E 数一数，或者 nm 看符号；
  • 想知道「这个开关现在是什么值」，在可疑的地方 #if LEVEL != 2 / #error 不是 2 / #endif——让编译器把你想要的事实打在诊断里（下一节就是这么干的）；
  • 别用条件编译藏业务逻辑：同一个函数体在不同 -D 下做不同的事，是 bug 的温床；条件编译留给平台差异与调试开关。

16.13 宏不能做的事，与什么时候不该用宏

上面每一节都在说宏能做什么，现在说它做不到的两件事——都是这一节的例子真的编不过换来的。

两条诊断，正好对上两条结论：

  • lvalue required as unary '&' operand —— 第 8 行取 &ARRAY_MAX 编不过。宏展开完是 &10，而 10 是一个字面量，不是变量，没有地址。你没法指着宏里那串文字说「它住哪」——因为它没有住处，它就是文本；
  • invalid operands to binary * (have 'char *' and 'int') —— 第 11 行 DOUBLE("hi") 展开成 ("hi") * 2，编译器在这里才把类型问题指出来。宏自己不检查参数类型（它连类型是什么都不知道），它把检查的活儿推给「展开之后的编译器」。读这条诊断要分清主次：主错误在宏定义那一行（include/macro_limits.h:8:24，插入符指着 ((n) * 2) 里的乘号），紧跟的 note: in expansion of macro 'DOUBLE' 才指到你的调用点（src/main.c:11:40）。换句话说，编译器骂的是宏展开出来的那段文字，调用点只是它被用在哪里。

那要表达「一个常量」该怎么办？同一个例子里的 macro_limits.c 给了另外两种写法，而 macro_basics 那份输出（16.3 节）打印的是同名的那两个名字，可以直接对着看：

对照那份输出：sizeof(max_const) 与 sizeof(MAX_ENUM) 都是 4，&max_const 还打出了一个真实地址（00000000005FFEAC）。但这里必须分清两件事，它们经常被混成一句「都是常量」：

  • const int max_const = 10; 是一个只读变量：有类型（int）、有地址（&max_const 合法）、调试器里看得见。但在 C 里它不是编译期常量——const int n = 10; int a[n]; 在块作用域会变成变长数组，放在文件作用域直接编不过（本机实测：error: variably modified 'a' at file scope）；
  • enum { MAX_ENUM = 10 }; 是一个整数常量：有类型（int）、能当数组大小、能进 case 标号，但它没有地址——&MAX_ENUM 报的是 lvalue required as unary '&' operand，跟 &ARRAY_MAX 是同一条错（本机实测，两条都在本节的诊断里出现过）。

所以「替代宏」这件事要分开答：要一个能当数组大小的编译期常量，用 enum（或继续用对象宏）；要一个只读的、有地址的对象，用 const。宏那条路只有一个名字和一串文字，上面两条诊断就是走不通的证明。第 3 单元的 literal_zoo 例子用这三种写法量过同一个数组长度，第 4 单元讲过枚举的取值与类型——它们的取舍在这里收口：宏是最后手段。

宏能不能定义「类型安全」的接口

这是宏的天花板。宏在替换的那一刻看不到类型（16.2 节说过，预处理只知道一串一串的记号），所以它不可能在「替换之前」检查你传了什么。上一段那条 DOUBLE("hi") 的诊断就是最好的说明：报错的主位置在宏定义那一行（include/macro_limits.h:8:24），note: in expansion of macro 'DOUBLE' 才指到调用点——宏自己一声没吭，是展开之后的编译器看不过去。这就是「宏不能定义类型安全接口」的全部含义。

C11 起有一个专门为此准备的工具：_Generic。它让编译器按实参的类型，在几条候选里挑一条，于是「一个名字、多种类型」有了类型检查：

  • 它只在编译期选一支，其余候选里的表达式仍然必须类型正确；所以它能让「一个名字支持几种类型」，不能替代函数重载；
  • 它仍然是宏：括号纪律、求值次数、没有作用域，一条都不少（ABS 展开后 x 也出现两次）；
  • 它是 C11 才有的东西，写法比函数长；只有当「一个名字要服务多种类型」这件事真的重要时才值得用，否则写两个函数最省事。

「宏是最后手段」不是口号，它可以排成一张顺序表。这是一张工程惯例清单，不是标准要求——标准只说宏能做什么，不告诉你该不该用。想做一件事时，从上往下问：

接着上一条名单往下问（这仍是工程惯例，不是标准要求）：

  1. 要「一个名字、多种类型」？ C11 起有 _Generic，它按类型挑一支，能保住类型检查（见上面那个例子）；
  2. 只剩这几件事才用宏：# 字符串化、## 拼名字、__FILE__ / __LINE__、条件编译（-D 开关）、以及那种「必须知道调用点上下文」的短小展开（比如 LOG、assert）。

小结这一节的要点
  • 预处理跑在编译之前，它做四件事：文件包含、宏替换、条件编译、行控制；它对类型一无所知，所以宏没有类型、没有作用域、也不做参数检查；
  • 宏是文字替换：SQ(1+2) 展开成 1 + 2*1 + 2 得 5（要写 ((x) * (x))）；SQ(i++) 展开出两次自增，标准说这是未定义行为（本机 gcc 实测 i 变 7，但那只是这台机器这一次的结果）；多语句宏要包 do { … } while (0)，否则分号会吃掉 else；
  • 宏只认文本范围：它属于包含它的那个编译单元，跨不过 .c 的边界，#undef 是唯一的关闭手段；条件编译是「留着或删掉」（-DLEVEL=2 与不写它编出两个程序，nm 与 gcc -E 都数得出来），#error 把「不支持」变成编译期的一句话；
  • -DNDEBUG 让 LOG 整条消失（连参数都不求值），这是从标准的 <assert.h> 推广出来的惯例；常量用 enum（能当数组大小）或 const（有地址，但不是编译期常量），行为用函数 / static inline / _Generic——宏是最后手段。

注自测题答案
  1. 是 5。宏展开是机械的文字替换：SQ(1 + 2) → 1 + 2*1 + 2，乘法先算，等于 1 + 2 + 2 = 5。正确写法是 #define SQ(x) ((x) * (x))：每个参数加一层括号，整个展开式再加一层（参数那层管数值，外面那层管调用点周围的运算符）。
  2. 标准不保证任何具体数值：i++ 在展开式里出现两次，两次之间有没有顺序的副作用，这就是未定义行为（标准 6.5 节第 2 段）。本机 gcc 16.1.0 的实测结果是宏版 i 变 7、函数版 i 是 6——但这只是这台机器这一次的结果，换编译器、换优化档都可能变。所以正确的答法是：宏版没有确定答案（UB），函数版有确定答案（6）；看到「本机是 7」不该记住 7，该记住的是「这里踩到了未定义行为」。
  3. 因为 do { … } while (0) 让整块在语法上等价于一条语句，调用点那个分号正好收在 while (0) 后面。裸花括号的写法展开后是 { … };，多出来的那个分号成了「空语句」而被当成 if 的主体，于是 if 提前结束，紧跟的 else 报 'else' without a previous 'if'（本机 gcc 原文见 16.6 节的诊断块）。
  4. __func__ 不是宏。 __FILE__ 与 __LINE__ 是预定义宏（6.10.8.1 节），预处理阶段就被换成文件名字符串与行号整数；__func__ 是标识符，由编译器在每个函数体开头隐式声明成一个 static const char __func__[] = "函数名";（6.4.2.2 节），所以它能在运行期被打印，也所以在预处理结果里原样留着（grep -c "__func__" 数得到，grep -c "__LINE__" 数不到）。
