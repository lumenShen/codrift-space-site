6.1 先看工程长什么样

前面十三个单元里，程序说的话都只说给屏幕听：printf 打完，程序一退，那些字就没了，想再看一眼只能重跑。这一单元解决的是「留下来」：把结果写进文件，把输入从文件里读回来，把出错的说明送到该去的地方。

还是老规矩，先看文件。本单元是第 6 章的第一单元，也是全书的第 14 单元，要在 examples/ 下建起第六个项目。下面第 1 帧是这一节故事的起点：examples/ 下已经有前五个项目，还没有 ch06。

第 2 到第 4 帧是本节搭起来的 examples/ch06/——十个例子目录，每个都是「源文件放 src/、声明放 include/、编译与对账的参数写在 .json 清单里」的最小工程（第 1 单元 1.7 节讲过分文件的理由：从第二个项目起，本书不允许单文件工程）。其中九个是能跑的程序，第十个 handle_not_string 是故意编不过的：它考的正是这一单元最容易犯的错——把文件句柄当成文件内容。

第 5、6 帧是本单元新出现的两类东西：

  • 数据文件：fgets_long_line/data/longline.txt 这类输入，程序读的就是它，它不属于任何源文件，只是一份文本；这是本书第一次出现 data/ 目录；
  • 抓下来的终端会话：session-*.txt 四个文件，里面的每一行都来自真实终端，正文里用 term 块注入，与文件逐字对账（1.3 节的 session-savetemps.txt 就是这个形状）。
工程惯例工程惯例：数据文件为什么不能叫 .json

本书的流水线把 books/*/examples/**/*.json 每一个 .json 都当成清单去校验（清单要写 id、sources、mode、unit 这些字段）。所以 examples/ 下不放非清单的 .json：要配数据文件就用 .txt / .csv / .tsv，它们不会被误当成清单。

这不是标准的规定，是本项目的纪律，理由很实在：机器分不清「这是数据」还是「这是配置」。名字分开了，工具链就不用猜。代价是数据文件不能享受 JSON 的语法检查——你自己写错了格式（比如 CSV 少一列），没有任何东西会替你报错，只能靠程序里的返回值与断言。

大白话把「文件」说成人话

屏幕和键盘是一次性的：程序一退出，屏幕上打过的字就跟没打过一样。文件是留得住的：它是一串字节，躺在磁盘上，你不去改它它就不变，明天、换一台机器打开它，还是同一串字节。

所以「做 I/O」这件事，本质上是在程序和磁盘之间搬字节。这一单元里所有的名字——流、缓冲、模式、定位——都是在回答搬的过程里冒出来的问题：搬多少、什么时候搬、搬错了怎么知道。

6.2 流：程序与外界之间的那根管子

printf 往哪儿写？fopen 打开的是「文件」还是别的什么东西？C 给出的答案只有一句话：你操作的不是文件，是流（stream）。

流是一条字节进出的通道。你可以往它里写字节、从它里读字节，可以问它「读到头了吗」「出错了吗」，可以关掉它。至于通道的另一头是磁盘上的一个文件、是键盘、是屏幕、还是另一个程序，流的接口不管——这就是为什么同一个 fprintf 既能往屏幕写，也能往文件写。

程序一启动，这三个流已经替你开好了，不用 fopen：

流 谁在用它 通常连到哪
stdin 输入 键盘，或者重定向进来的文件
stdout 正常输出 屏幕，或者重定向出去的文件
stderr 出错的说明 屏幕，默认只连屏幕，不跟 > 走

标准里对这三个流的地位说得很直接：

标准原文标准原文：程序一启动就有三个流

At program startup, three text streams are predefined and need not be opened explicitly — standard input (for reading conventional input), standard output (for writing conventional output), and standard error (for writing diagnostic output). As initially opened, the standard error stream is not fully buffered; the standard input and standard output streams are fully buffered if and only if the stream can be determined not to refer to an interactive device.

大意：程序启动时就有三个文本流预定义好了，不用显式打开——标准输入（读常规输入）、标准输出（写常规输出）、标准错误（写诊断输出）。而一开始，标准错误流不是全缓冲的；标准输入与标准输出只有当它们可以确定不是交互设备时才全缓冲。

这一句里藏着本单元两个大问题的答案：为什么错误信息要走 stderr、为什么崩溃前的 printf 会丢。出处：ISO/IEC 9899:2018（C17）§7.21.3。

工程惯例工程惯例：为什么错误信息一定要走 stderr

标准只说 stderr 是「写诊断输出」的流，没有规定你必须把错误写在那里。但主流做法一致：正常结果走 stdout，出错的说明走 stderr。理由是为了让重定向干净：

  • 你敲 mycat data/two_lines.txt > out.txt，只想要「文件的内容」进 out.txt；如果错误信息也在 stdout 里，它会一起被写进结果文件，把数据弄脏；
  • 而错误信息留在屏幕上（stderr 默认不跟 > 走），你能当场看见「哦，第三个文件打不开」。

代价是：看输出顺序会骗人。两个流各走各的，谁先到屏幕取决于缓冲（这一节 6.7 会用一个真实会话解释为什么）。所以调试时更稳的做法是把两个流一起抓下来：./app > out.txt 2>&1（2>&1 的意思是「让 2 号流也走到 1 号流去」）。

6.3 打开与关闭：模式表，以及那个必须判的 NULL

除了那三个预定义流，其他流都要自己开：fopen 打开，fclose 关掉。fopen 的第一个参数是文件名，第二个参数是模式字符串：

模式 含义（标准原文的措辞） 文件不存在时 已有的内容
"r" 打开文本文件读 失败，返回 NULL 保留
"w" 截断到 0 字节，或创建文本文件写 创建 丢掉
"a" 追加：打开或创建文本文件，在文件末尾写 创建 保留，写在后面
"r+" 打开文本文件读写 失败 保留
"rb" 打开二进制文件读 失败 保留
"wb" 截断到 0 字节，或创建二进制文件写 创建 丢掉

标准对返回值的说法只有一句，但它是整个单元最重要的一句：

标准原文标准原文：fopen 失败返回什么

The fopen function opens the file whose name is the string pointed to by filename, and associates a stream with it. … If the file cannot be opened, the fopen function returns a null pointer.

大意：fopen 把名字与一个流关联起来；打不开就返回空指针。——返回空指针这件事，是它唯一告诉你「失败」的方式，所以每次 fopen 都要判。

出处：ISO/IEC 9899:2018（C17）§7.21.5.3。

关于 fclose，标准里有一个短语值得单独记住：

标准原文标准原文：fclose 会做什么

The fclose function causes the stream pointed to by stream to be flushed and the associated file to be closed. Any unwritten buffered data for the stream are delivered to the host environment to be written to the file; any unread buffered data are discarded.

大意：fclose 做两件事——先把流冲干净（flush），再关掉文件。还没写出去的缓冲数据会被交给宿主环境去写进文件；还没读的缓冲数据直接丢掉。

「先冲再关」这半句是 6.7 节的伏笔：不 fclose 就等于不冲。

出处：ISO/IEC 9899:2018（C17）§7.21.5.2。

6.4 文本模式与二进制模式：同一个 "\n"，两个长度

"w" 与 "wb" 只差一个字母 b，写出去的东西却不一样长。

读这个例子的时候，先注意它的形状，而不是结论：同一个函数、同一份内容、同一句 fputs，唯一的变量是传进来的 mode。这就是对照实验——两个文件之间任何一点差别，都只能归到那个 b 上。你自己以后怀疑「某个操作改了字节」时，也照这个形状写：只改一个变量，其余全部相同。

这 2 个字节的差别来自文本模式。先别把它当成「Windows 的怪毛病」——标准早就为这种事留好了说辞，而且说辞比你想的更宽松：标准压根不承诺「你写进去几个字符，磁盘上就有几个字节」。它把流分成两类，各自给了一句保证。标准在讲流的那一节里说得很明白（这是本单元最该背下来的一句标准原文）：

标准原文标准原文：文本流

A text stream is an ordered sequence of characters composed into lines, each line consisting of zero or more characters plus a terminating new-line character. … Characters may have to be added, altered, or deleted on input and output to conform to differing conventions for representing text in the host environment. Thus, there need not be a one-to-one correspondence between the characters in a stream and those in the external representation.

大意：文本流是「按行组织」的，每一行以换行结尾；为了迁就宿主环境表示文本的惯例，字符可能在输入输出时被增加、改动或删除——所以流里的字符与外部表示之间不必一一对应。

出处：ISO/IEC 9899:2018（C17）§7.21.3。

标准原文标准原文（续）：二进制流

A binary stream is an ordered sequence of characters that can transparently record internal data.

大意：二进制流则是「能透明地记录内部数据」的字节序列。注意「透明」这个词：它不换算、不改写，你写进去什么字节，读回来就是什么字节。

本机的惯例是：文本模式下写 \n，落到磁盘上变成 \r\n 两个字节；读回来的时候再折回一个 \n。这就解释了两件事：文件变大了，而你的程序感觉不到（读回来的还是 \n）。

出处：ISO/IEC 9899:2018（C17）§7.21.3。

实验记录本机实测：6 比 4，两处证据
  • 工具链：gcc 16.1.0（-std=c17，即 C17），目标三元组 x86_64-w64-mingw32，系统 Windows 10 x64 (MSYS2 UCRT64)；
  • 程序自己数的：text.txt 6 字节、bin.txt 4 字节，差 2（examples/ch06/newline_bytes/src/main.c 真跑，输出见上面的 output 块）；
  • od -c 看的：文本文件是 a \r \n b \r \n，二进制文件是 a \n b \n；
  • wc -c 对的：6 text.txt / 4 bin.txt——与程序数出来的完全一致；
  • python 直接读字节：b'a\r\nb\r\n' 与 b'a\nb\n'（od -c、wc -c、两条 python 命令都在上面两段会话里，逐字抓下来的）。

别把 6 当定律：这是 Windows 上文本模式的换算结果。同一个程序拿到按 Unix 惯例的系统上跑，文本模式与二进制模式会给出同样的 4——那时你敲的命令、写的代码一个字都不用改，结果却变了。这正是「标准允许外部表示与流内字符不必一一对应」的意思：换算规则由实现定。

6.5 读：fgetc / fgets / fscanf 与「一行太长会怎样」

读文件有三个常用函数，分工不一样：

函数 读什么 关键行为
fgetc(fp) 一个字节 返回 int（要能装下 EOF），读到末尾返回 EOF
fgets(buf, n, fp) 至多 n-1 个字符 遇到换行或文件末尾就停，换行会被留下
fscanf(fp, "…", …) 按格式解析 返回值是「成功填了几个字段」；解析失败的收尾很麻烦

fgets 是这三个里最常用的，也是坑最多的。坑在于：它读的不一定是「一行」。标准原文把这句写得毫不含糊：

标准原文标准原文：fgets 到底答应了你什么

The fgets function reads at most one less than the number of characters specified by n from the stream pointed to by stream into the array pointed to by s. No additional characters are read after a new-line character (which is retained) or after end-of-file. A null character is written immediately after the last character read into the array.

大意：fgets 最多读 n-1 个字符；读到换行符（换行本身会被保留）或文件末尾就不再往下读；最后在读到的内容后面补一个空字符。

出处：ISO/IEC 9899:2018（C17）§7.21.7.2。

「最多 n-1 个」就是截断的根源。下面这个数据文件的第一行有 52 个字符——注意它只是一个普通文本文件，不是 C 代码：

用 16 字节的缓冲区去读它，会发生这样的事：

5 段，2 行。第 1~3 段各 15 个字符（就是 n-1），第 4 段 8 个字符带着换行，第 5 段是第二行。也就是说：fgets 每被调用一次，只交出它读到的这一段，不要把它当成「读一行」。

这就是「把一行完整读回来」的通用写法：循环里一直拼，拼到看见换行为止。它不依赖缓冲区多大——缓冲区小只是多转几圈，结果一样。（本机实测那一行拼出来是 53 字节：52 个字符 + 1 个换行。）

陷阱用 fgets 时你会被这样坑到

你会看到：数出来的「行数」比你用记事本打开看到的行数多，内容还被切成了几段。

你会怎么误判：以为是文件坏了、编码不对，或者回去改 fgets 的第二个参数，想着「调大点就好了」。调到 1024 确实能过这一次——下一份数据里有一行 5000 个字符，你又得回来。

真相是：fgets 的契约里从来没写「读一行」，它写的是「最多读 n-1 个字符」。所以正确的用法只有两种：要么循环拼到换行为止（上面的写法），要么在读之前就知道「这个文件的每一行都不会超过多少字节」——后者只要有一次不成立，就会静默出错。另外记住 fgets 连换行一起给你：想打印时去掉它，得自己把末尾那个 '\n' 换成 '\0'，而且不能想当然地认为「一定有」——最后一行没有换行时就没有。

「缓冲区在哪儿」这句话，光靠说很难讲清，画成一条路就清楚了。下面四帧跟着一个字节走：它从 printf 出发，经过两个站，最后才落到磁盘上——中间任何一站断了，它就没了：

第 1 帧是 printf 的真相：它不写文件，它写缓冲区。第 2 帧解释「什么时候真的往下走」——缓冲写满，或者你显式 fflush。第 3 帧是 fclose，它把「冲缓冲」和「关文件」一起做完（6.3 引的那句标准原文就是这件事）。第 4 帧是崩溃：进程被操作系统直接终止，用户态缓冲里的字节跟着进程一起消失，第 2 站根本没被碰到，所以磁盘上什么都没有。

为什么会有缓冲区这种设计？因为它把「很多次小写」变成「少数几次大写」：不缓冲的话，每个 printf 都要陷进内核一次，慢得没法用。代价就是你得知道它在那儿。

标准原文标准原文：fflush 干了什么

If stream points to an output stream or an update stream in which the most recent operation was not input, the fflush function causes any unwritten data for that stream to be delivered to the host environment to be written to the file; otherwise, the behavior is undefined.

大意：对一个输出流（或者最后一次操作不是读的更新流），fflush 把还没写出去的数据交给宿主环境去写文件；对其他情况，行为未定义。

最后半句要记住：fflush(stdin) 不是「清空输入缓冲」的标准做法——标准明说这是未定义行为。（顺手说一句：fflush(NULL) 会冲所有输出流，这是合法用法。）

出处：ISO/IEC 9899:2018（C17）§7.21.5.6。

那什么时候是全缓冲、什么时候不是？回到 6.2 引的那句 §7.21.3：标准错误流一开始不是全缓冲的，标准输入与标准输出只有当它们能确定不是交互设备时才全缓冲。翻译成人话：

  • 输出到屏幕（交互设备）：通常按行缓冲，每打一行就出去，所以你在终端里敲 ./app 时看到的是实时的；
  • 输出被重定向（> out.txt）或者接进管道（./app | grep x）：全缓冲，攒够一整块才出去；
  • stderr：不缓冲，写一句出去一句。

所以「崩溃前有没有输出」这件事，同一个程序在终端里跑和在管道里跑，答案可能不一样。本书的所有输出都是经管道抓回来的（流水线要拿到 stdout 才能对账），所以你会看到「stdout 是空的」这种结果——那不是 bug，是缓冲。

工程惯例工程惯例：要留下证据，就显式 fflush

想让「崩溃前打印过什么」这件事在任何情况下都可复现，主流做法是三条，按可靠程度排：

  1. 把关键信息写 stderr——它不缓冲，写完就在；
  2. 在容易崩的地方之前显式 fflush(stdout)（本节的 fflush_kept 就是这么做的）；
  3. 记录时别只写 stdout，把两个流一起抓：./app > out.txt 2>&1。

代价是：程序里多出几行「不是为了功能、而是为了可诊断」的代码。这些行的价值不在平时，在出事那一天——没有它们，你手上只剩一个退出码。

6.8 写：三个函数的返回值，以及「关掉才算写完」

写文件有三个函数，分工和读那边一一对应：

函数 写什么 返回值
fprintf(fp, "…", …) 按格式写 写出去的字符数；出错返回负值
fputs("…", fp) 一串字符，不解析格式 出错返回 EOF，否则返回非负值

标准原文标准原文：写函数的返回值

The fprintf function returns the number of characters transmitted, or a negative value if an output or encoding error occurred.

The fwrite function returns the number of elements successfully written, which will be less than nmemb only if a write error is encountered.

大意：fprintf 返回写出去的字符数，遇到输出错误或编码错误返回负值；fwrite 返回成功写出的元素个数，只有写错误才会让它小于你要求的个数（元素就是「size 字节一块」的意思，第三步 6.10 会用到）。

6.9 定位：fseek / ftell / rewind，与「怎么量一个文件多大」

流有一个文件位置指示器，你可以理解成「下一站读/写哪个字节」。三个函数围着它转：

  • fseek(fp, offset, whence)：把位置挪到 whence 加 offset 的地方；whence 取 SEEK_SET（从头算）、SEEK_CUR（从当前位置算）、SEEK_END（从末尾算）；
  • ftell(fp)：报告当前位置；
  • rewind(fp)：回到开头（等于 fseek(fp, 0, SEEK_SET)，但不返回错误，这是它的缺点）。

fseek(fp, 0, SEEK_END) 加 ftell(fp)，就是「量一个文件多大」的标准写法。思路很朴素：把读指针推到末尾，再问它现在站在第几个字节。剩下的问题只有一个——推之前、推之后，流的状态是否允许你这么做：

标准原文标准原文：文本模式下 ftell 的数「不是有意义的度量」

The ftell function obtains the current value of the file position indicator for the stream pointed to by stream. For a binary stream, the value is the number of characters from the beginning of the file. For a text stream, its file position indicator contains unspecified information, usable by the fseek function for returning the file position indicator for the stream to its position at the time of the ftell call; the difference between two such return values is not necessarily a meaningful measure of the number of characters written or read.

大意：对二进制流，ftell 给出的是「从文件开头数几个字节」；对文本流，它的位置指示器里装的是未指定的信息，唯一保证是「能喂回给 fseek 回到原地」——两个这样的数相减，不一定是读写字符数的有意义度量。

The function called at program startup is named main. … It shall be defined with a return type of int and with no parameters … or with two parameters (referred to here as argc and argv, though any names may be used, as they are local to the function in which they are declared) …

大意：main 可以没有参数，也可以有两个。

出处：ISO/IEC 9899:2018（C17）§5.1.2.2.1。

标准原文标准原文（续）：argv[0] 是程序名

If the value of argc is greater than zero, the string pointed to by argv[0] represents the program name; argv[0][0] shall be the null character if the program name is not available from the host environment. If the value of argc is greater than one, the strings pointed to by argv[1] through argv[argc-1] represent the program parameters.

大意：argc 是参数个数，argv 是一个字符串数组。argv[0] 是程序自己的名字（拿不到程序名时它是个空串），argv[1] 到 argv[argc-1] 才是你敲的那些参数。

出处：ISO/IEC 9899:2018（C17）§5.1.2.2.1。

工程惯例工程惯例：退出码的三种约定

标准只钉死了「0 成功、EXIT_FAILURE 不成功」（6.3 的原文）。那 return 2 算什么？惯例。主流约定是：

  • 0 —— 成功；
  • 1 —— 运行失败（文件打不开、数据不对、网络断了），这是最通用的一档；
  • 2 —— 用法错（参数没给、参数不认识），这一档在 GNU 工具里几乎人手一个（敲 grep 不带参数就能看到）。

为什么要把「用法错」和「运行失败」分开？因为它们要修的地方不一样：看到 2 去看帮助、检查自己敲的参数；看到 1 去查数据与文件。代价是：这套约定没有标准保证，换一个工具可能用别的数（grep 用 2 表示「有文件找不到」）。所以别在脚本里依赖具体数值，只判「是不是 0」——那一条才是标准钉死的。

6.12 FILE 是什么：你手上只有一个句柄

fopen 返回的那个 FILE *，到底是什么？答案是：一个句柄（handle）——它只是「哪个流」的编号，不是文件本身，也不是文件内容。这件事画出来是这样：

第 3 帧那个数字来自 6.8 的输出块（sizeof(FILE) = 8 字节），是本机实测。这里要老实交代一件事，因为它与你在网上常见的说法不一样：

标准原文标准原文：标准只说 FILE 是「能记录流状态的对象类型」

The header <stdio.h> declares three types, several macros, and many functions for performing input and output.

The types declared are size_t … and FILE which is an object type capable of recording all the information needed to control a stream, including its file position indicator, a pointer to its associated buffer (if any), an error indicator that records whether a read/write error has occurred, and an end-of-file indicator that records whether the end of the file has been reached …

大意：FILE 是一个对象类型，它「能记录控制一个流所需的全部信息」——位置指示器、缓冲区指针、错误指示器、文件末尾指示器。

注意标准没有说它是「不完整类型」。它只要求这个类型装得下这些信息；至于要在头文件里把内容摊开（完整类型），还是只留一个名字（不完整类型），由实现自己定。出处：ISO/IEC 9899:2018（C17）§7.21.1。

大白话把「完整」与「不完整」说成人话

「不完整类型」的意思是：编译器知道这个名字，但不知道它有几个字节。所以你可以写 FILE *p（指针多大是知道的），但不能写 FILE f（要分配内存，就得知道多大）。

不少实现（比如 glibc）选择不完整：头文件里只写 typedef struct _IO_FILE FILE;，struct _IO_FILE 的内容藏在库的源文件里。这样做的好处很实在——换一个版本、加一个字段，你的程序一个字都不用改，因为它本来就看不见里面。

本机的工具链选了另一条路：头文件里把 FILE 定义成一个只含一个占位指针的结构体，于是它是完整的，sizeof(FILE) 能算出 8。两种做法都符合标准。

但不管哪种，对你的写法要求完全一样：只能拿指针，只能通过函数去用它。别去 sizeof(FILE)、别去猜它的成员——那是库的私事，你依赖它，换平台就翻车。

小结这一节的要点
  • 你操作的不是文件，是流：stdin / stdout / stderr 一启动就有（§7.21.3），错误信息走 stderr；fopen 打不开返回 NULL（§7.21.5.3），fclose 是「先冲缓冲再关文件」（§7.21.5.2）。
  • 文本模式会换算：本机实测同一份 "a\nb\n"，"w" 写出 6 字节（多的 0d 是 CR），"wb" 写出 4 字节；量大小、按字节操作一律用 "rb"。
  • fgets 的契约是「最多读 n-1 个字符」且保留换行（§7.21.7.2）；不要 while (!feof(fp))（§7.21.10.2），拿返回值当条件，退出后用 ferror 分读完与出错。
  • printf 写的是缓冲区不是磁盘（崩溃丢输出、退出码 3221225477；fflush 后留住了）；fseek(SEEK_END) + ftell 能量大小，但文本模式下这个数标准说「不是有意义的度量」（§7.21.9.4）；argv[0] 是程序名（§5.1.2.2.1），1 / 2 这类退出码是惯例。

自测题自测题（先自己答，再对答案）
  1. 同一份内容 "a\nb\n"，用 "w" 与 "wb" 写出来各是几字节？差的那几个字节是什么？为什么你的程序读回来时感觉不到差别？
  2. while (!feof(fp)) { fgets(line, sizeof line, fp); puts(line); } 为什么最后一行会打印两遍？正确的循环条件怎么写，循环退出后还要查哪个函数？
  3. 一个程序 printf 了两行之后崩溃（进程被操作系统终止）。为什么有时候能在屏幕上看到那两行、有时候一行都看不到？要让它总能留下来，有两个办法，分别是什么？
  4. 用 fgets(buf, 16, fp) 去读一行 52 个字符，一次调用会给你多少字节？要拿到完整的一行，写法是什么？
  5. argc / argv 里，argv[0] 是什么？程序想表达「你参数给错了」，惯例上返回几？为什么这个数不能当成标准来依赖？
注自测题答案
  1. "w" 是 6 字节、"wb" 是 4 字节（本机实测）；差的是两个 \r（字节 0d），文本模式把每个 \n 写成了 \r\n。读回来感觉不到差别，是因为输入时又折回成一个 \n（§7.21.3）。
  2. feof 回答的是「上一次读有没有撞到末尾」，不是「下一次会不会」。读第 3 行成功后指示器还没置位，于是进了第 4 圈；这一圈 fgets 失败返回空指针，但循环没看返回值，line 里还是上一行，于是又打一遍。正确写法 while (fgets(line, sizeof line, fp) != NULL)，退出后用 ferror(fp) 查是不是读错了。
  3. 因为 stdout 有用户态缓冲：接终端时按行缓冲，重定向或接管道时全缓冲。进程被操作系统终止时不会冲缓冲，字节随进程消失。要总能留下：① 写 stderr（不缓冲）；② 崩之前显式 fflush(stdout)。
  4. 一次最多 15 字节（n-1，且这段里没有换行）。要拿到完整一行，就在循环里把每段拼起来，拼到看见 '\n' 为止（52 字符那一行拼出来是 53 字节，含行尾换行）。
  5. argv[0] 是程序自己的名字（§5.1.2.2.1），argv[1] 起才是用户参数。「参数给错了」惯例返回 2（1 留给运行失败）。不能依赖它，是因为标准只钉死「0 或 EXIT_SUCCESS 成功、EXIT_FAILURE 不成功」，其余数值由实现定（§5.1.2.2.3）；脚本里只判「是不是 0」。
