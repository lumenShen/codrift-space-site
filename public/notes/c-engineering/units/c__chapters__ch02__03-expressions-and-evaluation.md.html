5.2 优先级：谁先算，标准写得像一张表

优先级这件事有一个残酷的事实：它是查表，不是推理。C 的运算符有四十多个，先算谁后算谁全写在标准的一张表里，而且是十几级、不是粗分的几大块。下面是与你最相关的那些级（从高到低）：

级别 运算符 结合性 你会写的样子
后缀 () [] -> . 后缀 ++ -- 左 f(x)、a[i]、p->x、i++
一元 ! ~ + - * & 前缀 ++ -- (类型) sizeof 右 *p、&x、-i、(int)v
乘除 * / % 左 a * b / c
加减 + - 左 a + b - c
移位 << >> 左 x << 2
关系 < <= > >= 左 a < b
相等 == != 左 a == b

再往下是低优先级的一半——陷阱几乎都长在这一半里（因为它们会「等」前面的先算完）。注意 &、^、| 是三级，&&、|| 也是两级：

级别 运算符 结合性 你会写的样子
按位与 & 左 x & mask
按位异或 ^ 左 a ^ b
按位或 | 左 a | b
逻辑与 && 左 p && p->x
逻辑或 || 左 a || b
条件 ?: 右 c ? a : b
赋值 = += -= … 右 a = b = c
逗号 , 左 (a = 1, a + 1)
语法规则这张表最常咬人的三处
  1. == 比 & 紧：所以 x & 1 == 0 是 x & (1 == 0)，不是 (x & 1) == 0。这一条每年都要坑掉一批人；
  2. << 比 + 松，& 比 ^ 比 | 紧，&& 比 || 紧：所以 x << 1 + 2 是 x << (1 + 2)，a | b & c 是 a | (b & c)，a || b && c 是 a || (b && c)。这三条本机都实测过（x=2 时 x << 1 + 2 得 16，4 | 1 & 1 得 5，1 || 0 && 0 得 1），而且 gcc 对三条各给一条 -Wparentheses——它不是沉默的；
  3. 赋值右结合、逗号左结合：a = b = c 读作 a = (b = c)；而 (a, b, c) 从左边开始一个个算，整个表达式的值取最右边那个。

粗记一句「后缀 > 一元 > 乘加移位 > 关系 > 相等 > 位 > 逻辑 > 条件 > 赋值 > 逗号」可以，但要知道它只是分大块的口诀：同一块里的那几行仍然不是一级——上面第 2 条那三个陷阱，来源正是「把一块当成一级」。

这张表还能顺手解掉两个常见写法。!a == b 读作 (!a) == b——一元 ! 比 == 紧，所以它问的是「!a 与 b 相不相等」：a=1 b=0 时为真（!1 是 0，0 == 0），a=1 b=1 时为假；它不是「a 不等于 b」（那要写 a != b）。本机实测：写 !a == b 时 gcc 给一条 -Wlogical-not-parentheses，原文是 logical not is only applied to the left hand side of comparison。a = b == c 读作 a = (b == c)——== 比 = 紧，这一句是「把比较结果（0 或 1）写进 a」，本身合法，只是扫一眼很容易看反；本机 b=2 c=2 时 a 得 1。

陷阱三个优先级的坑，各自长什么样

你怎么会被坑到：这三处代码都能编译、能跑、不崩溃，只是算出来的东西不是你以为的那个。

  • a < b < c：如果 a、b、c 是「a 最小、c 最大」这种巧合，它给出的答案碰巧是对的（第一组数据就是），于是你以为写法没问题。换一组数据立刻翻车（第二组）。真相：关系运算符左结合，先算的那一对会变成一个 0 或 1，再拿去跟下一个数比；
  • x & 1 == 0：这类写法在「判断奇偶」的代码里到处都是。1 == 0 恒为 0，x & 0 恒为 0，于是整个条件永远为假——包括你想走进的那个分支。真相：== 比 & 紧；
  • *p++ 与 (*p)++：两个写法都对、都常用，区别只在「动的是指针还是它指的值」。库函数里遍历数组几乎都是 while (*p++) 那种形状，而累加器代码里常见 (*total)++。真相：后缀 ++ 与 ->、[]、() 同属「后缀」这一级，比一元的 * 高。
陷阱（续）把一块当成一级，是另一半坑

你会怎么被坑到：口诀「乘加移位 > 关系 > …」好背，于是你把它当成「同一块里从左往右算」。按这个读法，x << 1 + 2（x=2）是 (2 << 1) + 2 = 6、4 | 1 & 1 是 (4 | 1) & 1 = 1、1 || 0 && 0 是 (1 || 0) && 0 = 0——本机实测三个真值是 16、5、1。

真相：+ - 比 << >> 紧，& 比 ^ 比 | 紧，&& 比 || 紧，各差一级。我会怎么误判：我以前把 a & 0xFF == 0 读成「低八位是不是全 0」，直到 -Wparentheses 把它指出来——它算的是 a & (0xFF == 0)，恒为 0。上面第一块会话里那四条 -Wparentheses，说的都是这一类。

工程惯例工程惯例：拿不准就加括号，长表达式就拆行

标准只规定先算谁，它从不管你写得看不看得懂。主流做法有两条：

  • 拿不准就加括号：(a < b) < c 与 a < b < c 对编译器完全一样，但对读到这行的人不一样。加括号不花钱（现代编译器不会为它多生成一条指令），省的是后面接手那个人的时间；
  • 一行里最多一个副作用：*p++ 这种「取值 + 挪指针」是允许的、也是惯用的写法，但同一行里出现两个以上带副作用的子表达式（比如 *p++ = *q++ 之外的组合），就该拆成两行。

代价说清楚：多加的括号会让表达式看起来啰嗦，拆行会让函数变长几行。换来的东西很实在——编译器不在乎你怎么写，接手的人在乎。

5.3 短路求值：&& 与 || 有保证，位运算没有

上一节说的是「谁先算」的表；这一节说的是一条比表更硬的保证：&& 与 || 规定了从左往右算，而且可能根本不算右边。这条保证有真名字，叫短路求值（short-circuit evaluation）。

  • no_a() && yes_b()：b 被调 0 次。左边已经是假，&& 直接给出 0，右边根本没算——yes_b 一次都没跑；
  • no_a() & yes_b()：b 被调 1 次。位运算 & 要先把两边都算出来才能做按位与，所以右边照样跑了。结果是一样的 0，差的是「右边算没算」；
  • 后两行是同一件事的镜像：yes_a() || yes_b() 里左边已经为真，右边不跑；yes_a() | yes_b() 里两边都跑；
  • 最后一行是这个保证最实用的地方：p 是空指针，p != NULL && *p > 0 返回 0 而程序没崩——因为 *p > 0 那半句被短路跳过了。
标准原文标准原文：`&&` 保证的那件事

C 语言标准（ISO/IEC 9899，C17）6.5.13 节「Logical AND operators」：

Unlike the bitwise binary & operator, the && operator guarantees left-to-right evaluation; if the second operand is evaluated, there is a sequence point between the evaluations of the first and second operands. If the first operand compares equal to 0, the second operand is not evaluated.

大意：与位运算 & 不同，&& 保证从左往右求值；如果第二个操作数真的被求值了，那么「求值第一个」与「求值第二个」之间存在一个序列点；如果第一个操作数等于 0，第二个操作数不被求值。

标准原文标准原文（续）：`||` 是同一套措辞，方向相反

6.5.14 节「Logical OR operators」：

Unlike the bitwise | operator, the || operator guarantees left-to-right evaluation; if the second operand is evaluated, there is a sequence point between the evaluations of the first and second operands. If the first operand compares unequal to 0, the second operand is not evaluated.

大意：|| 同样保证从左往右；第一个操作数不等于 0 时，第二个操作数不被求值。

出处：ISO/IEC 9899:2018（C17）§6.5.13、§6.5.14。

「序列点」这个词第一次出现，先当它是一句人话读：序列点是代码里一个「前后有先后顺序」的位置。&& 在第一个操作数算完之后、第二个操作数开算之前，正好有一个。这句话是下面这条惯例的标准依据。

工程惯例工程惯例：`p != NULL && p->x > 0` 是接口的一部分

「判空写在左边」不是为了省一次比较，它是一条接口惯例：把「这个指针可能是空的」和「它有效时我该怎么用它」写在同一个条件里。

代价有两面，都得说清：

  • 左边的义务：既然是你在判空，你就得保证左边那半句不会解引用那个指针。写成 p->x > 0 && p != NULL 就全反了——右边还没判，左边已经把空指针解引用了（下面那个例子就是它的现场）；
  • 它不是万能的：如果 p 是别人交给你的，而契约上说「不会是空」，那每次判空就是白花一次分支；反过来，契约上说「可能是空」而你没判，后果就是进程没了。所以这条惯例背后真正的规矩是 「谁知道自己该怎么处理，谁判」。

顺带一句：&& 的短路让「先判空、再用」这种写法不需要嵌套 if，这是它比 & 实用得多的原因。

那五处「专门规定」要拆开看：&& / || / ?: / 逗号是先后上的规定（谁先算）；而函数调用 () 只规定了「实参全部算完、真正调用之前有一个序列点」——它没有规定实参之间谁先谁后。标准 6.5.2.2 节第 10 段明说：函数指示符、各个实参、以及实参内部的子表达式，求值顺序都是未指定的，只在调用之前有一个序列点。本单元 printf("%d %d\n", i++, i++) 打出 11 10，就是右边那个实参先算的现场。

「未指定」这个身份带来两个推论，都很实用：

  2. 它和「未定义」不是一回事。下一节的主角就是「未定义」——那时修法完全不同。

标准原文标准原文：「未定义」是另一个词

同一个标准 3.4.3 节「undefined behavior」给「未定义行为」的定义：

undefined behavior: behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this document imposes no requirements.

大意：未定义行为指的是——你用了不可移植的写法、错误的写法、或者错误的数据，对这种情形，本标准不施加任何要求。对照一下上一节引的 3.4.4 节：未指定说的是「程序合法、数据正确，只是结果取决于实现」，未定义说的是「这个写法本身就有问题」。一个是「不承诺」，一个是「不负责」。

这两个词的区别，落到修法上是两条完全不同的路：

  • 未指定（f() + g()）：这句代码没错，只是顺序没承诺。修法是把顺序写出来——拆成两句，或者用 && / ?: / 逗号把它们连起来；
  • 未定义（i = i++ + 1）：这句话本身就是错的。修法是把它删掉重写——写成两句：int old = i; i = old + 1; 之类，别在「标准会选哪一边」上做文章。

工程惯例工程惯例：`if (x = 0)` 该怎么处理

标准允许赋值表达式当条件用，惯例的做法有三种，按场景挑：

  • 就是想比较：写 ==。真被坑过的人常用「尤达写法」if (0 == x)——把常量放左边，一旦手滑写成 if (0 = x)，编译器直接给一条硬错误：本机实测 gcc 报 error: lvalue required as left operand of assignment（编译退出码 1）。注意它与「给 const 变量赋值」不是同一条诊断：const int c = 0; if (c = x) 报的是 error: assignment of read-only variable 'c'。代价是可读性变差（人读起来是倒的），所以本书不推广，但你可以知道有这招；
  • 就是想把赋值当条件用：加一层括号，把意图说出来——if ((c = getchar()) != EOF) 是经典写法，括号既让 -Wparentheses 闭嘴，也告诉读代码的人「我是故意这样写的」；
  • 在 if 条件里做赋值、又在别处用这个变量：拆成两句。if (x = 0) 这种写法最大的问题不是编译不过，而是读代码的人会以为那是比较。

这一块是惯例，不是标准：标准允许赋值表达式当条件（6.5.16 节），它不管你写得更好读还是更难读。几种做法的代价不同——尤达写法牺牲可读性换「手滑就编不过」；加括号牺牲一点空间换「警告消失、意图明确」；拆成两句牺牲行数换「谁都不会看错」。a = b = c 也属于这一族：它的读法由结合性定死了（右结合），但一眼看过去仍然容易数错，写开成两句同样不算亏。

顺手把 a = b = c 的读法钉住：赋值运算符右结合，它读作 a = (b = c)——先把 c 的值写进 b，b = c 这个表达式的值就是写入后的 b，再把它写进 a。本机实测 chain_assign(7) 给出 707（5.5 节那块输出里的第三行），也就是 a 与 b 都成了 7。

5.7 ?: 与逗号：两个不常用但必须认识的运算符

?: 是 C 里唯一的三元运算符（要三个操作数）。它的形状是 条件 ? 表达式甲 : 表达式乙：条件为真算甲，为假算乙，而且整个表达式的类型由甲和乙一起决定——这一条最容易出错。

四件事：

  1. flag ? 1 : 2.5 的结果是 double：一个分支是 int、另一个是 double，标准会把它们「往一起调」，整个表达式取 double，所以 pick_double(1) 返回的是 1.0 而不是整数 1。sizeof(0 ? 1 : 2) 给出 4（两个分支都是 int），sizeof(0 ? 1 : 2.5) 给出 8（调成 double）；
  2. sizeof(0 ? 'a' : 1) 也是 4：在 C 里字符常量本身是 int（不是 char），所以两个分支都是 int，结果是 4 而不是 1。这一条是第 3 单元「char 的三重身份」的延续；
  3. 逗号运算符的值是最右边那个：comma_value 里三个赋值从左往右依次做，整个表达式的值取最后一个 log[2] = 3 的值，也就是 3，同时 log 变成 {1, 2, 3}；
  4. 嵌套的 ?: 从右往左读：score >= 90 ? "A" : score >= 60 ? "及格" : "不及格" 等价于 ... : (score >= 60 ? "及格" : "不及格")。三个分数打出来是 A / 及格 / 不及格。
标准原文标准原文：`?:` 先算条件，中间的序列点

同一个标准 6.5.15 节「Conditional operator」：

The first operand is evaluated; there is a sequence point between its evaluation and the evaluation of the second or third operand (whichever is evaluated).

大意：先算条件；条件算完之后，与被选中的那个分支之间有一个序列点。所以 ?: 与 && / || 一样，顺序是标准保证的（这也是上一节说「除了这五处之外都未指定」里的一处）。

标准原文标准原文（续）：两个分支的类型怎么合

同一个 6.5.15 节的第二句话，解释了我们为什么能用 sizeof 问出类型：

If both the second and third operands have arithmetic type, the result type that would be determined by the usual arithmetic conversions, were they applied to those two operands, is the type of the result.

大意：两个分支都是算术类型时，整个表达式的类型由「寻常算术转换」在它们之间决定——int 与 double 相遇取 double，int 与 long 相遇取 long。这就是上面 sizeof 那两行的依据。

逗号运算符的规定在 6.5.17 节：它左边按 void 表达式求值、左右之间有序列点、整个表达式取右边的类型与值。

出处：ISO/IEC 9899:2018（C17）§6.5.15、§6.5.17。

工程惯例工程惯例：`?:` 该用在哪儿

先说明：这一块是惯例，不是标准——标准只说 ?: 能怎么用，不管你读起来累不累。?: 的惯例用法是**「按条件挑一个值」，而且两边的类型要一致**：

  • 好用法：const char *msg = ok ? "成功" : "失败";、printf("%d 个%s\n", n, n == 1 ? "苹果" : "苹果们");；
  • 该避免的用法一：嵌套超过两层。上面那个三档打分已经到可接受的边界了，再多一层就该换成 if / else if / else——if 有缩进，读的人不用在脑子里配括号；
  • 该避免的用法二：两边的类型不一样（flag ? 1 : 2.5）。它能编过，但你在读这行时得先在心里做一遍类型转换。

代价：?: 把「分支」压进一个表达式，省的是行数，付的是可读性——每多一层嵌套，读的人就要在脑子里多配一组冒号。真需要三档以上，if / else if 更好读。

工程惯例工程惯例：参数里的逗号不是逗号运算符

先说明：这是惯例，不是标准。逗号运算符除了 for (i = 0, j = n - 1; i < j; i++, j--) 这种明确的场景，别用。它极易和函数参数、初始化列表里的逗号混淆——f(a, b) 里那个逗号是参数分隔符，不是逗号运算符，所以 f((a, b)) 才是「先把两个都算了、只把 b 传进去」。

代价：逗号运算符让一句里塞进几个动作，顺序读者得自己数；写开成几条语句没有任何额外开销，编译器生成的代码一样。想在一个表达式里做两件事，写两句话更清楚。

5.8 显式强转：四种用途，四种理由

「强转」这个词听着就像坏事，但 (类型)值 这种写法在工程里有四种正当用途。前两种是转换值（原来是什么数、现在变成什么数），后两种是告诉编译器一件它不知道的事（我要丢掉这个返回值、我要换一种方式读这块内存）。

后两种不是「换个数值」，而是「换一种看法」与「表个态」：

四种用途逐个对上：

  1. 转换值（第 5 行）：7 / 2 是整数除法，得 3；(double)7 / 2 先把 7 变成 7.0，于是整句变成浮点除法，得 3.5。这里的关键是转换发生在除法之前——如果写成 (double)(7 / 2)，括号里的除法先算成 3，再转成 3.0，那是另一个意思；
  2. 截断浮点（第 9 行）：(int)3.99 得 3，(int)-3.99 得 -3 而不是 -4——标准规定这是朝零截断（丢掉小数部分），不是四舍五入、也不是向下取整。第 4 单元讲除法与取模时，两个整数相除也是朝零截断，同一条规则。

  4. (void) 吞返回值（第 17 行、main 第 14 行）：printf 有返回值（写了几个字符），返回 int。有些编译器与静态检查工具会提醒「你忽略了返回值」，写 (void)printf(...) 就是明说「我知道它返回值，我故意不要」。它是到 void 的一次显式转换（标准 6.5.4 节里的 cast），只是转换结果没有值可用——它不改变任何东西，作用只是「把这个表达式标成故意丢弃的」。
标准原文标准原文：浮点转整数是朝零截断

同一个标准 6.3.1.4 节「Real floating and integer」：

When a finite value of real floating type is converted to an integer type other than _Bool, the fractional part is discarded (i.e., the value is truncated toward zero).

大意：把有限的浮点值转换成一个不是 _Bool 的整数类型时，小数部分被丢掉——也就是朝零截断。所以 (int)3.99 是 3、(int)-3.99 是 -3（朝零，不是朝下）。

至于 (类型)值 这个写法本身，标准 6.5.4 节「Cast operators」规定了它的语法与含义：在一个表达式前面加上带括号的类型名，就把这个表达式的值转换到那个类型；(void)expr 也在这一节里——那是转换到 void，结果没有值可用。

「装不下」的后果要分三种说（转换规则在 6.3 节，不在 6.5.4）：无符号整数之间装不下 → 按 2 的 N 次方取模；有符号整数装不下 → 实现定义（或者由实现定义的信号）；浮点转整数而整数部分装不下 → 未定义行为。指针转换是另一套规则：转出来的指针没按目标类型对齐就是 UB（第 9 单元见过那个现场）。

出处：ISO/IEC 9899:2018（C17）§6.3.1.3、§6.3.1.4、§6.5.4。

工程惯例工程惯例：强转是一把「关掉提醒」的钥匙

显式强转写下去，编译器就不再问「这里从 double 变 int 会丢小数，你确定吗？」。所以惯例是：

  • 先问「能不能不改类型」：7 / 2 想要小数，最干净的做法是把变量本身声明成 double，或者写成 7.0 / 2，而不是在表达式里塞一个强转。强转是局部的，改类型是全局的，后者更能让下一个人看懂；
  • (void) 是唯一鼓励多加的：它没有任何副作用，只是把「故意丢弃」写出来。标准库里的 (void) 到处都是。
工程惯例工程惯例（续）：指针转换要谨慎，代价要算清
  • 指针转换要谨慎：(char *) / (unsigned char *) 用来「按字节看内存」是常规做法（这也是标准允许的少数几种别名用法之一），但把 (int *) 硬套到一个没对齐的地址上是 UB（第 9 单元的 ptr_types 就是那个现场）。跨类型看字节，memcpy 才是标准保证的写法。
  • 代价：每加一个强转，你就少了一条编译器的提示。判断标准是「我能不能用一句话解释这个转换为什么安全」——解释不了，就别加括号把它关掉。

工程惯例工程惯例：哪些假设值得写成 `_Static_assert`

工程惯例工程惯例（续）：它能查什么、查不了什么
  • 别把它写成运行时检查：_Static_assert 在编译期发作，代价是零（生成的代码里什么都没有）；而 assert(x) 在运行期发作，代价是每个进程都带着这些判断。分工很清楚：能编译期查的，绝不留到运行期；

工程惯例工程惯例：三条该写成习惯的规矩

这一节的坑，归根到底都是「你脑子里想的」与「编译器看的」不是一回事。把它收成三条可执行的规矩：

  1. 看到一行里有两个副作用，先拆。*p++ 这种只有一个副作用的写法没问题；同一句话里出现两个改同一对象的操作（i = i++ + 1、f(i++, i++)）就拆成两句。-Wsequence-point 会帮你抓一部分（本机实测它抓得到本节这两处），但它看不见的写法照样是 UB，所以规矩是「拆」，不是「等警告」；
  2. 需要顺序的地方，用有保证的构造把它写出来。&&、||、?:、逗号运算符这四处规定了谁先算；函数调用与每条语句的结尾有序列点（但实参之间没有先后，见 5.4 节）。想要「先 f 后 g」，就写成两句；想要「先判空再用」，就写 p != NULL && *p > 0；
  3. 把平台假设写成 _Static_assert，别写在注释里。注释不会编不过，断言会。

三条都不是标准逼你做的，是给接手的人省时间——代价只是多打几个字符、多写一行断言。

最后一条不是惯例而是本书的纪律，但值得在这里说一次：编译器不在乎你怎么写，接手的人在乎。本节每一个「坑」在汇编里都只是几条 mov，而读代码的人要在脑子里模拟一遍求值顺序。加一对括号、拆一行，成本是几个字符。

小结这一节的要点
  • 优先级是查表，不是推理：(a < b) < c、x & (1 == 0)、*(p++) 都能编译能跑，只是算的不是你以为的东西；*p++ 动指针，(*p)++ 动它指的值；
  • && / || 的短路是标准保证的（6.5.13、6.5.14），& / | 没有——所以 p != NULL && *p > 0 安全（实测返回 0），(p != NULL) & (*p > 0) 踩死（退出码 3221225477）；
  • 未指定与未定义是两件事：f() + g() 是未指定（本机两档都先调 f、结果 107，但标准不承诺），修法是把顺序写出来；i = i++ + 1 是未定义（-Wsequence-point 报 operation on 'i' may be undefined，-O0 两次写、-O2 折叠成一条 lea），修法是把这句删掉重写；
  • 赋值的值、?: 的类型、强转与断言：if (x = 0) 合法且会改 x（-Wparentheses 提示），a = b = c 右结合；两个分支都是算术类型时，?: 的类型由寻常算术转换决定；浮点转整数朝零截断；(void) 表示故意丢弃返回值；_Static_assert 把平台假设变成编译期检查。

  3. no_a() 返回 0（假）：&& 直接给 0，右边一次都没算（本机实测 b 被调 0 次）；& 要把两边都算出来才能按位与，所以右边照样跑了（b 被调 1 次），结果同样是 0。p != NULL && *p > 0 安全，是因为 p != NULL 为假时 && 根本不求值右边的 *p（标准 6.5.13 保证）；换成 & 后两个操作数都要算，右边那次解引用落在空指针上，本机进程以退出码 3221225477 被终止。
  4. f() + g() 是未指定：程序合法，只是子表达式的求值顺序没被规定（标准 6.5 节第 3 段）。i = i++ + 1 是未定义：同一句话里对同一个对象既读又写、还写了两次，标准对这种写法不施加任何要求（3.4.3 节）。修法不同：前者把顺序写出来（拆成两句，或用 && / ?: / 逗号这类有序列点的构造）；后者把这句删掉重写（比如 int old = i; i = old + 1;）——它不能靠加括号解决。
